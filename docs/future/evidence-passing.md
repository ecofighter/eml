# evidence passing によるエフェクトの実装

位置づけ: 将来の設計。

ネイティブ化 ([ロードマップ](roadmap.md) の「処理系」) で、エフェクトの操作と handler をどう実装するかの方針をまとめる。まだ実装しない。今の実装に入れた予防的な決定は、パラメータ付き handler の状態を handler フレームに持たせることだけである ([エフェクトと handler](../spec/effects.md) の「パラメータ付き handler」)。

## 目的と範囲

### 目的

- `perform` が継続を遡って handler を探す処理をなくし、handler を定数時間で引けるようにする
- すぐに再開する操作 (`get` など) を、継続を取り出さない直接の呼び出しにする
- `never` / `once` / `multi` の多重度と線形性の情報を、実装の選択にそのまま使う
- LLVM や WASM のように、スタックを切り替える仕組みを持たない出力先でも動くようにする

### 対象外

- レコードの evidence passing (row 多相なレコードで、フィールドの位置を証拠として渡すこと)。同じ row 多相の問題だが、論点が別なので [ロードマップ](roadmap.md) の「処理系」にある「レコードのネイティブな表現」で扱う

## 方式の選択

| 案 | 内容 | 判断 |
|---|---|---|
| A | generalized evidence passing と yield の bubbling (Koka 方式)。Core IR から Core IR への変換で実装する | 採用する |
| B | スタックの切り替えと、handler の連鎖を遡る動的な探索 (OCaml 5 方式) | A の性能が足りない場合の選択肢として残す |
| C | handler の検索とすぐに再開する操作には evidence を使い、それ以外の操作はスタックの切り替えで実装する折衷 | 同上 |

A を採る理由は次のとおり。

- 変換の結果は普通の関数呼び出しと分岐だけの IR になる。出力先にスタックを切り替える仕組みが要らない
- 継続はクロージャの列になるので、`multi` の継続を再開するときもスタックを写さずに済む
- eml の多重度と持ち越し規則が、継続のクロージャの Kind にそのまま対応する (下の「多重度ごとの実装」)
- 変換後の IR を CEK インタプリタでも実行できるので、ネイティブのバグをインタプリタで再現できる

B は `multi` にスタックのコピーが要り、LLVM の側にスタックを切り替える仕組みが要る。C は A と B の両方の実行時の仕組みを持つことになる。

### 前提とする研究

- Xie と Leijen の generalized evidence passing (EPS。Microsoft Research の技術報告 MSR-TR-2021-5) を基にする。Koka の C バックエンドが使っている方式である
- 先行の evidence passing translation (EPT。ICFP 2020 の "Effect Handlers, Evidently") は、継続を捕まえたときと同じ handler の文脈でしか再開できない (scoped resumption)。EPS はこの制限を外しており、eml の第一級の `k` をそのまま扱える

## 方式 A の概要

### evidence のベクタ

- handle の中で実行しているコードは、その時点で有効な handler の evidence を並べたベクタを持つ。ベクタはエフェクトのラベルの順に並べる。同じラベルが重なった場合 (scoped labels) は、内側の handler を先に置く
- evidence は「目印 (marker)、handler (節のクロージャと状態の欄)、その handler を定義した時点のベクタ」の3つ組である。3つ目は、すぐに再開する節をその場で実行するときに使う (下の「すぐに再開する節」)
- 今のベクタと「yield 中か」の印は、実行の文脈に持たせ、エフェクトのある関数に渡す。Koka の `ctx` に当たる。文脈は worker ごとに1つ持つので、マルチコアの「各 worker が自分の機械を持つ」構成と合う

### handle と perform

- `handle` は、新しい目印を作り、evidence をベクタに入れてから本体を実行する
- `perform` は、ベクタから操作のエフェクトの evidence を引く。row が閉じていればベクタの中の位置は定数になる。row が開いていれば (`<State | e>`)、実行時にラベルで探す
- 閉じた row の関数を、それより広い row の文脈から呼ぶ箇所では、ベクタを呼ばれる側の row に合わせる (Koka の `open`)。eml の型検査で、トップレベルの関数の閉じた row を開く箇所 ([型と Kind](../spec/types.md) の「推論」) がこれに当たる
- `mask` 付きの呼び出し ([Core IR とインタプリタ](../spec/core-ir.md)) は、`mask` のエフェクトごとに、内側の evidence を `mask` に含まれる数だけベクタから除いて呼び、戻ったら元のベクタに戻す包みにする (Koka の `mask-at`)。型検査が記録した呼び出しごとの `mask` をそのまま使う

### すぐに再開する節

- 節が `k v` を末尾で1回だけ呼び、`k` をほかに使わない場合、節を `perform` の場所でそのまま実行する。継続を取り出さない
- 節の実行中は、その節の中の操作が handler の外側に届くよう、ベクタを「handler を定義した時点のベクタ」に切り替えるフレーム (論文の `under`) を積む。`k` がスコープの外で再開されうるので、このフレームを省いたり、固定のベクタで置き換えたりすると誤りになる (論文 2.9.2 節)
- パラメータ付き handler の `| get () k st -> k st st` は、状態が handler フレームにあるので、この形になる。状態を脱糖しないことにしたのはこのためである

### yield の bubbling

- すぐに再開しない操作は、目印まで yield する。yield は、呼び出しから返るたびに「yield 中か」の印を確かめ、各フレームが自分の続きを継続に足しながら1フレームずつ戻る
- 続きは、その時点の join point と生きている変数を持つクロージャになる。継続はこのクロージャの列である (論文の short-cut resumption)
- yield しない経路では、クロージャを作らない。bind を展開し、続きを join point として共有する (論文の bind-inlining と join-point sharing)。Core IR にはすでに join point があるので、これを使う

## 多重度ごとの実装

操作の多重度は宣言で決まっているので、`perform` の箇所で実装を選べる。

| 操作 | 実装 |
|---|---|
| すぐに再開する節 | その場で実行する (上の「すぐに再開する節」)。多重度によらない |
| `never` | yield に中断の印を付ける。継続は再開されないので、途中のフレームの生きている値を解放しながら目印まで戻る。解放の方法は「未決の論点」に挙げた |
| `once` | 継続のクロージャの列を作る。クロージャは `Lin` の値を持ってよく、継続自体も `Lin` である。一意なので、再開のときに Perceus の reuse が効く |
| `multi` | 継続のクロージャは、持ち越し規則により `Unr` の値だけを持つ。クロージャは書き換えないので、2回目の再開でも写さない。インタプリタが区間を写しているのと対照的である |
| `IO` | extern のエフェクトで、handler も継続もない。extern の関数をその場で実行し、直接の呼び出しにする。今のインタプリタの扱い ([コンパイラの構成](../implementation/architecture.md) の「継続のフレーム」) と同じである |

- yield しない関数は変換しない。row が `<>` か `<IO>` だけの関数は yield しないので、evidence のベクタも「yield 中か」の確認も要らない (Koka の、型で選ぶ変換に当たる)

## Perceus と線形性との関係

- 変換は、HIR から Core IR への変換の後、Perceus の `dup` / `decref` の挿入の前に置く。変換がクロージャと join point を新しく作るので、それらにも RC の操作を付ける必要があるためである。Perceus はすでに変換の後の独立したパスなので、その前に新しいパスを挟むだけで済む
- 継続のクロージャに入った `Lin` の値は、`drop k` と `never` の中断のときに、記述子から破棄処理を引いて解放する。インタプリタが継続の区間を解放するときに、捕まっていた値を解放する (`File` はその解放で閉じる) のと同じ考え方である
- パラメータ付き handler の状態は evidence の handler の欄に置く。`perform` で節に渡し、`k v st` の再開で戻す動きは、インタプリタの handler フレームと同じである ([コンパイラの構成](../implementation/architecture.md) の「継続のフレーム」)

## マルチコアとの関係

- `par` の子タスクには、外側の handler を指す evidence の代わりに、fork の目印を指す evidence を渡す。子の row は `Row<Never>` なので、子から外に出る操作は `never` の操作だけである
- 子の中の `never` の操作は fork の目印まで yield し、fork / join の節点がそれを親に渡す。[マルチコア対応の設計](multicore.md) の「`par` の段階」にある、`never` の操作が `par` から抜けるのを perform が認識するという要件は、この形で実現する
- 継続を別のコアに移すときの共有の印付けは、継続のクロージャの列から到達できるオブジェクトをたどって行う。継続のフレームをたどる今の設計と同じである

## 実装に進むときの条件

- **Core IR の row**: Core IR に row の情報を持たせる。関数の本体の row、`perform`、閉じた row を開く箇所に要る。今の Core IR は row を持たないので、evidence passing を入れるときに HIR から Core IR への変換で足し、`simplify` などのパスがそれを保つようにする
- **ラベルの順序**: エフェクトのラベルの順序を決める。プログラム全体を1回でコンパイルするあいだは、そのコンパイルの中で決まった順序でよい。分割コンパイルをするなら、モジュールをまたいでも変わらない修飾名の順にする
- **handler の状態**: パラメータ付き handler の状態を handler フレームに持たせていること (実装済み)
- **差分テスト**: 変換後の IR をインタプリタで実行し、UI テストの出力が変換の有無で一致することを確かめる

## 未決の論点

- 「yield 中か」の確認の費用。bind の展開と join point の共有を、既存の join point の変換とどう組み合わせるか
- インタプリタの既定の実行を、変換後の IR に切り替えるか
- 開いた row で evidence を探すときのキャッシュ
- `never` の中断で、途中のフレームの `Lin` の値をどう drop するか。yield の経路に drop の命令を生成するか、継続を組み立ててから解放するか
