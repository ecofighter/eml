# マルチコア対応の設計

位置づけ: 将来の設計。

VM とネイティブのランタイムで、複数のコアを使って実行するための設計をまとめる。worker とスレッドの模型、スケジューラ、スレッドをまたぐ RC、`par` の意味、止める手順を書く。マルチコア対応は実装していない。VM はシングルスレッドで、後から並列にできる制約を守る (下の「VM の並列化の備え」)。今の実装に入れてある備えは、row の Kind の束の `Never` ([型と Kind](../spec/types.md)) と、持ち越し規則の制約を `σ ≤ Once` と書くこと ([エフェクトと handler](../spec/effects.md)) のほかに、`eml_rt` の共有の印方式の RC (`share`、負の RC、共有した物体を reuse しないこと。下の「スレッドをまたぐ RC」)、検査モードの所有者の検査、`CodeBase<M>: Sync` と `Task: Send` の型の assert (下の「VM の並列化の備え」) である。

std の `Async` の意味 (タスク、スコープ、取り消し、I/O、channel) は [非同期の設計](async.md) に、ネイティブのコードの fork / join と入口は [ネイティブ化の設計](native.md) の「並列の実行」に、GUI のプラグインは [FFI と拡張の設計](ffi.md) の「GUI」にある。この文書はその下の仕組みを書く。

## 目的と範囲

### 目的

- VM とネイティブのバックエンドで、複数のコアを使って実行できるようにする
- 並列の安全性 (共有の印付け、移し戻し、別のスレッドからの解放、下の「不変条件」) を、ネイティブ化を待たずに VM の実装で確かめる。VM の並列化では速さよりこちらを重視する
- 「線形型 × 代数的エフェクト」の性質 (`Lin` による移動、row によるエフェクトの制限) を、並列の安全性の保証にそのまま使う

### 対象

- 決定的な並列計算: データ並列に限る。`par`、`std/Par` の並列の map / fold / reduce、分割統治
- 並行処理: std の `Async` のタスク、非同期 I/O ([非同期の設計](async.md))

### 対象外

- 利用者に見せるメモリモデル。共有の可変状態を伴うマルチスレッドは扱わず、Rust の `Send` / `Sync` に当たる Kind の次元は導入しない。ランタイムが利用者に見せるのは `IO` の下の `Chan` と `Atomic.Counter` だけで、`IO` を持たない `par` の子からは届かない
- `par` の子から `IO` を使うことと、利用者の定義した再開する操作を子から外に出すこと (下の「未決の論点と将来の拡張」)

| 8 | 並列 API | `par` は1つで、子の row は `<never e>` (`e : Row<Never>`) である。`par` はすべての子の完了を待ち、いちばん左の子の中断を親で起こし直す。`Panic` は `Never` のラベルに分け直し、`IO` は `Once` のままにする。row の Kind の束は `Never ≤ Once ≤ Multi`。利用者が主に使うのは `std/Par` の集まりの関数で、2引数の `par` と逐次の `both` も公開する。並行処理は std の `Async` で書く ([非同期の設計](async.md)) |
| 9 | 不変条件 | スレッドをまたいで値や制御を渡すプリミティブは、すべて閉じた row か `Row<Never>` の制約を持つ。Rust の側の構造が持つ語はどれも数えた参照で、登録した根である (下の「不変条件」) |
| 10 | 共有の印付け | 実行系のプリミティブが、送り手のスレッドで、公開する前に自動的に行う。fork、`spawn`、channel の送りは印を付け、join、channel の受け取り、タスクの開始、取り出しは移し戻しで受ける (下の「印付けの表」)。`par` では worker の数によらず必ず行う。待ったタスクの継続には、救済のときだけ印を付ける |
| 11 | スレッドに縛られたリソース | 組み込みのリソースは、スレッドに縛られないものに限る。スレッドに縛られたもの (GUI など) は、専用の worker の上のタスクに閉じ込める。専用の worker の待ちは差し替えられる |
| 12 | `Lin` の物体 | `Lin` の値は move だけを許し、物体の RC は常に 1 である。スレッドをまたぐときは印を付けず、所有者を移す |
| 13 | スレッドの模型 | OS のスレッド1つが worker 1つで、`Ctx` と `Heap` を1つずつ持つ。`main` は大きいスタックで作る worker 0 で動く。プロセスのメインスレッドは host のスレッドで、求められたときに専用の worker (メインの worker) になる。監視のスレッドが run に1本ある。ブロックする呼び出しのプールはヒープを持たない (下の「スレッドと worker」) |
| 14 | スケジューラ | `par` は fork / join で、まだ始まっていない右の子だけを worker ごとの Chase-Lev の deque から盗ませる。`Async` のタスクは始まった worker から動かず、待った継続はその worker の受け箱に戻して印を付けない。例外は救済で、詰まった worker のタスクを、監視のスレッドの合図で空いた worker が受け箱の lock の下で移す (下の「スケジューラ」) |
| 15 | 横取り | 協調的にする。VM は安全点 (`Ctx::poll`) で worker の止める語の `PREEMPT` ビットを見て、タスクを切り替える。シグナルによる横取りはしない。ネイティブのタスクは `Async` の操作でだけ切り替わる |
| 16 | 長い呼び出し | その場で動く extern と C の呼び出しは worker を持ち続け、同じ worker のほかのタスクは救済で動く。待つべき長い呼び出しは、ヒープを持たないプールの仕事にする ([FFI と拡張の設計](ffi.md) の「長く走る呼び出し」) |
| 17 | 止める手順 | `Control` の終わりの欄に最初の書き手が書き、終わりのビットを立てる。各 worker は次の安全点で入口へ戻り、host のスレッドが全員を待ってからヒープを落とす。`exit` もこの手順を使う (下の「止める手順」) |

## 層の構成

```
std:           Std.Par (par、both、集まりの関数)    Std.Async、Std.Chan、Std.Net (タスク、スコープ、取り消し)
               ──────────────────────────────────────────────────────────────────────
eml_cli        Session::run が実行系を組み立てる (worker の数、実行系、I/O の driver、プラグイン)
eml_vm         Exec を実装する (VM)                eml_native   Exec を実装する (ネイティブ)
eml_sched      スレッド、受け箱、タスクのセル、監視のスレッド、プール、deque、待ちと起こし、Exec の trait
eml_io         IoDriver を実装する
eml_rt         語の単位の操作 (share、移し戻し、fork / join の節点、範囲のプリミティブ)、Host、Sched、IoDriver の trait
型システム:     row の Kind による制限 + Lin による移動
```

- 依存の順は `eml_rt` ← `eml_sched` ← `eml_vm` である。`eml_sched` は worker のループが呼ぶ `Exec` の trait を持ち、`eml_vm` がそれを実装する。`eml_io` は `eml_rt` に依存して `IoDriver` を実装する ([非同期の設計](async.md) の「I/O の driver」)。`eml_native` は `eml_rt`、`eml_lir`、`eml_sched`、Cranelift に依存する。`eml_cli` はすべてに依存する
- `Session::run` が実行系を組み立てるので、`Session` は今と同じく唯一のパイプラインの駆動役である。`Host`、`Sched`、`IoDriver` の trait は `eml_rt` に置き、`Ctx` を通して届く
- `eml_rt` は vstd だけに依存したまま Verus で証明する。スケジューラ (`eml_sched`) は Verus の外に置き、Miri と TSan で確かめる (下の「テスト」)
- スケジューラをエフェクトのライブラリとして書く形は採らない。救済、監視、スレッドをまたぐ起こし、根の登録は、語の外の Rust の構造を要るためである。ライブラリとして書いた協調的なスケジューラ `tests/ui/run/kinds/scheduler.em` は、継続を扱う言語のテストとして残す

## スレッドと worker

- OS のスレッド1つが worker 1つである。worker はどれも自分の `Ctx<M>` (自分の `Heap`、`evv`、yield の状態、統計、worker の止める語) を持ち、共有の `CodeBase`、`Arc<Control>`、`Arc<dyn Host>` の上で動く。セッションの根は worker 0 の `Ctx` に置く
- worker の数 N の既定は `available_parallelism` で、`--workers` と `EML_WORKERS` で変えられる。UI テストは N = 1 を既定にし、スケールの確かめと救済を強いる方針だけを N ≥ 2 で流す (下の「テスト」)。worker とヒープは run の間ずっと生きる
- worker 0 は `main` のタスクを動かす。プロセスのメインスレッドでなく、driver の求める大きさのスタック (既定は 1 GiB の予約。[ネイティブ化の設計](native.md) の「安全点とスタック」) で作るスレッドである。ほかの worker のスレッドも同じ大きさで作る
- host のスレッドはプロセスのメインスレッドである。`Session::run` の実行系を動かし (worker を作り、終わりを待つ)、シグナルの handler を持つ。そのほかの間は待っている。止める手順の後半 (worker を待つこと、プールの仕事を待つこと、ヒープを落とすこと。下の「止める手順」) も host のスレッドが行う
- 専用の worker はほかの worker から仕事を盗まず、新しいタスクを置く先にもならない worker である。宛先を名指しした仕事だけを受け、待ち (park) を差し替えられる。`rt_thread_new(stack_size)` で専用のスレッドを作れる
- メインの worker はプロセスのメインスレッドを専用の worker にしたものである。`Gui.run_on_main` を最初に呼んだとき (`rt_dedicate_main`。GUI はこの中で `Gui.open` を呼んで開く) か、`--main-dedicated` を付けたときは run の始めからメインの worker になる。メインの worker は自分の `Ctx` と `Heap` を持ち、OS の既定のスタックで動く。深い再帰は `stack_limit` の確かめで止める。メインの worker には宛先を名指しした仕事しか置かないので、メインの worker にする時期に条件はない
- メインの worker になった後は、host のスレッドの仕事も同じスレッドが行う。run の間の host の仕事は待つことだけで、それはメインの worker の待ちに含まれる。止める手順でメインの worker が入口へ戻ると、同じスレッドが host として残りの手順を行う
- 監視のスレッドは run に1本あり、最初の worker とともに始まる。どれかの worker がタスクを動かしている間は監視の刻み (既定 10 ms) ごとに起き、ほかの間は条件変数か時間切れで待つ (最初の仕事を渡したときに起こす)。シグナルの handler は async-signal-safe な書き込みで自己パイプ (Linux では eventfd) に1バイト書き、監視のスレッドは条件変数と一緒にこれも待つ。そのため、すべての worker が待っている run でもシグナルのビットを見落とさない。Windows では、コンソールの handler のスレッドが監視のスレッドを直接起こす。刻みごとに、worker の一覧の worker のそれぞれについて次を行う
  - 今のタスクの ID が前の刻みから変わっていなければ、worker の止める語に `PREEMPT` を立てる (下の「スケジューラ」の「横取り」)
  - 2刻み変わらず、受け箱に盗めるものがあれば、詰まったと印を付けて空いた worker を1つ起こす (下の「スケジューラ」の「救済」)
  - 実行待ちがしきい値 (既定 64) を超え、ほかに待っている worker があれば、その worker を過負荷とする。持ち主が詰まっていなくても、空いた worker を1つ起こして救済させる
  - シグナルのビット (`INTERRUPT`、`TERMINATE`) は、先に `Signal.wait` で待つタスクへ回す。そのシグナルを待つタスクが登録されていれば、ビットを下ろして完了として届ける (下の「止める手順」)
  - `Control` の止める語のビットを各 worker の止める語に写す。シグナルのビットを写すのは、待つタスクが登録されていないときだけである。`Control` の止める語が変わったときは、すべての worker を起こす (差し替えた待ちも、その起こし方で起きる)
  - メモリの柔らかい上限を超えていれば、確保の多いタスクに旗を立てる ([非同期の設計](async.md) の「タスクごとの上限」)
- `Control` の止める語は今と同じく `Control` の欄で ([オブジェクトモデル](../spec/object-model.md) の「実行の制御」)、run に1つある。止める理由のビットは `INTERRUPT`、`MEMORY`、`TERMINATE`、終わりのビットである
- worker の止める語は worker ごとの `AtomicU32` で、`Control` の止める語のビットの写しと、監視のスレッドが立てる `PREEMPT` を持つ。安全点と、`FileIn`、標準入力、`Child` の読みが見るのは worker の止める語である。シグナルの handler は `Control` の止める語にビットを立て、そのシグナルを待つタスクが登録されていなければ worker 0 の止める語にも同じビットを立てる (どちらも atomic な書き込みなので async-signal-safe である。登録は run のシグナルごとの atomic な数で読む)。そのため、worker 0 で `Interrupted` を受けて読み直す読み手はすぐにビットを見る。ほかの worker の止める語に写すのは監視のスレッドで、Ctrl-C は `Control` を読まない worker にも、次の安全点に来れば1刻みのうちに届く
- 止めるビットは `PREEMPT` を除く止める理由のビット (`INTERRUPT`、`MEMORY`、`TERMINATE`、終わりのビット) をまとめた呼び名である。終わりのビットは、`Control` の終わりの欄に書いた者が立てる (下の「止める手順」)
- worker の一覧は worker の止める語を作るときに載せる一覧で、監視のスレッドが刻みごとにたどる。下の「Rust の側が持つ語」の run の登録表とは別のものである
- ブロックする呼び出しのプールは、待つべき長い呼び出し (利用者の `blocking` の C の行、名前の解決) を動かすスレッドの集まりである。必要になったときに作り、上限 (既定 32) まで増え、run の間は終わらない。プールのスレッドはヒープを持たず、RC に触れず、確保もしない。仕事の記録が数えた参照で語を持ち、run の登録表に載る。完了は持ち主の worker の受け箱を通して届く ([非同期の設計](async.md) の「I/O の driver」)
- その場で動く extern と C の呼び出しは、タスクの worker のスレッドの上で動き、終わるまで worker を持ち続ける。extern から eml に入り直すことはない。救済されないタスクのその場の呼び出しは、そのタスクの間ずっと同じ OS のスレッドで動く。プロセスの外のスレッド (C のライブラリのスレッドなど) から eml へ知らせる口は、worker の受け箱を起こす口だけである

## スケジューラ

### worker のループ

worker のループは、ほかに仕事がなくなるまで次の順に見る。

1. 受け箱の中身をまとめて取る (lock を1回取る)
2. 横取りした VM のタスクのキュー
3. 自分の deque の `par` の子
4. 実行待ちの継続
5. ほかの worker の deque から `par` の子を盗む (専用の worker は盗まない)
6. 監視のスレッドが詰まった worker か過負荷の worker を知らせていれば、救済する
7. I/O の driver を見る
8. 待つ (park)

- 実行待ちは再開を待つタスクの継続の列である。項目は `{ タスクのセル, 継続 k, 渡す値 }` で、渡す値は `Wake` のような即値か数えた参照の語である
- VM は実行待ちの継続から新しい VM の `Task` (スタックは使い回しの集まりから取る) を作り、入口 `resume_task` で `k` に値を渡す。受け箱で届いた新しいタスクは入口 `start_task` で始める。ネイティブのコードは同じ2つの関数をネイティブの入口から呼ぶ
- `start_task : (Unit -> <IO, Panic, Async> a) -> <IO> Unit` と `resume_task : (once a -> <IO> Unit) -> a -> <IO> Unit` は名前で ABI が決まる std の関数である。`start_task` はタスクごとの handler をかぶせ、その節は `k` をランタイムに預けて (`rt_wait` で待ちに入れるか、実行待ちに戻す) そのまま戻る。タスクの本体が値を返すと `rt_done` が結果を記録する ([非同期の設計](async.md) の「`Async` のエフェクト」)
- タスクはループに戻るとき、入口の関数から普通に戻る。VM のタスクが切り替わるのは yield の状態がなしの安全点だけで、そのとき `evv` を `Task` に退避する

### `par` の子

- `par` の fork / join の節点は `eml_rt` にある。fork はまだ始まっていない右の子を自分の deque に積み、左の子を自分で動かす。空いた worker は deque の上から盗む
- VM では、join で待つ親の `Task` は join の節点で待ち、worker のループはほかの仕事 (先に `par` の子、次に `Async` のタスク) を動かす。待つ `Task` はデータなので、待つ費用はない。子が終わると、親は横取りした VM のタスクのキューに戻る
- ネイティブのコードはスタックを切り替えられないので、join で待つ worker は待たずに手伝う。手伝えるのは、待つ join より深い fork の子だけで、ほかに手伝えるものがなければ join の節点で待つ ([ネイティブ化の設計](native.md) の「並列の実行」)。これで待ちが輪になることはない。まだ始まっていない子のうち最も浅いものを深さ d の c とすると、c を fork した親は動いているか、深さ d - 1 の自分の join で待っていて c を取れる。盗まれた子を待つ worker は動いている worker を待っている。`par` の子は有限である
- 専用の worker は盗まず、自分の join だけを手伝う
- 分け方の木は長さと粒度だけで決まり、盗み方によらない (下の「データ並列での使い勝手」)

### `Async` のタスク

- タスクは `spawn` (と `start`) のときに置く先の worker を決め、捕まえた値に印を付けて送る。置く先は置ける worker を順に回して選ぶ。始まったタスクはその worker から動かない。待った継続 `k` はその worker の局所の構造にだけ入り、印を付けない
- 受け箱は worker ごとに1つの mutex で、実行待ち、待ちの集まり、知らせの列を守る。持ち主の worker はループの1回ごとに lock を1回取ってまとめて処理し、別の worker からの起こしは知らせごとに取り、救済する worker は盗むときに取る。横取りした VM のタスクは、受け箱の外の持ち主だけが触るキューに置き、盗まない
- 知らせは起こし (`Wake`)、タスクを置くこと (`Place`)、取り消し (`Cancel`)、宛先を名指しした仕事 (`Run`)、完了 (`Completion`)、受け付けの転送 (`Submit`) である
- タスクのセルは `Arc` の構造で、持ち主の worker、状態 (動いている、待ち、実行待ち、取り消し中、終わり)、取り消しのビット、待つ側、属するスコープを持つ ([非同期の設計](async.md) の「スコープとタスク」)。持ち主の worker は今の持ち主の受け箱の lock の下でだけ変わる。知らせを送る側は宛先の受け箱の lock を取ってから持ち主を読み直し、変わっていればやり直す。そのため、救済の後に知らせが取り残されることはない
- 待ちの集まりの項目は `{ タスクのセル, 継続 k, 待ちの理由 }` である。待ちの理由はセルの待ち (待つ相手のセル)、I/O の待ち (操作と、ハンドルを縛った worker)、channel の待ち (待つ側の登録)、時間の待ち、プールの待ち (仕事の記録) のどれかで、取り消しで待ちを外すときの手順を決める ([非同期の設計](async.md) の「待ちを外す」)
- 時間の輪は、worker ごとの I/O の driver が持つ時間の待ちの登録の表である。持ち主の worker だけが触る
- 取り消しのビットの処理と待ちを外すことは、持ち主の worker がその受け箱の lock の下でだけ行う
- 受け付けを、ハンドルを縛った別の worker へ回すときは、その worker の受け箱へ `Submit` を送る。縛った worker はループで受け付けを出し、完了をタスクのセルの持ち主へ送る ([非同期の設計](async.md) の「ハンドルと worker」)
- 予算 `ctx.budget` は、worker のループがタスクを渡すたびに戻す。待たずに済む速い道の extern がこれを減らす。worker の止める語には触れないので、VM の横取りとは別に働く ([非同期の設計](async.md) の「`Async` のエフェクト」)

### `Async.run` と入れ子

- VM では、`Async.run` の下にある組み込みが根のスコープを作り、本体の `start_task` を置き、呼んだ `Task` をスコープの待つ側として待たせてループを続ける。生きているタスクの数が 0 になると、結果を書いて呼んだ `Task` を横取りした VM のタスクのキューに戻す。ループを入れ子にせず、extern から入り直さず、Rust の再帰も使わない
- ネイティブのコードではマシンのスタックの上で worker のループを入れ子にする。呼んだ側が完了の後に再開するという約束は同じである。入れ子の順が逆になりうるので、`Async.run` は `main` から呼ぶのがよい

### 公平

- worker ごとの実行待ちは先入れ先出しで、切り替えたタスクは後ろに戻す
- 監視のスレッドはタスクの ID を刻みごとに比べるので (上の「スレッドと worker」)、VM のタスクが続けて動くのは2刻みより短い間である。刻みの直後に始まったタスクは、1刻みより長く動いてから横取りされる。`Async` の操作を持たないネイティブのタスクは終わるまで worker を持ち、同じ worker のほかのタスクは高々3刻み (約 30 ms) の後に救済される。その代わり、救済したタスクには印が付く
- I/O の driver はループの1回ごとと、待つ前に1回見る
- 新しいタスクは置ける worker を順に回して置く
- `par` の子は粒度で大きさが抑えられ、ほかの VM の `Task` と同じく横取りされる

### 横取り

- `Ctx::poll` の形は変えない (`depth > max_depth` か止める語が 0 でないか)。読むのは worker の止める語である。`Stop` に `Stop::Preempt` を足し、`#[cold]` の道で決める
- VM の `step` はどの安全点でも `Stop::Preempt` を誤りでなくタスクの切り替えにする。`evv` を `Task` に退避し、`PREEMPT` を下ろし (持ち主だけが書く。監視のスレッドが同時に立てても、切り替えが1回増えるだけである)、横取りした VM のタスクのキューに積んで、次の仕事に進む
- 検査モードと seed で決まるテストのスケジュールは、刻みでなく安全点の数で切り替える
- ネイティブのコードは worker の止める語の確かめで `PREEMPT` を定数の AND で隠す ([ネイティブ化の設計](native.md) の「安全点とスタック」)

### 救済

- 監視のスレッドは、worker が同じタスクを2刻み以上動かしているか extern の中で止まっていて、その受け箱に盗めるものがあるとき、その worker を詰まったとする。盗めるものは実行待ちの項目、`Place` の知らせ、待ちの集まりにある待ちを宛先とする `Wake` の知らせである。監視のスレッドは空いた worker を1つ起こす。過負荷の worker (上の「スレッドと worker」) も同じく救済の対象にする
- 救済する worker は元の worker の受け箱の lock の下で、`Place` を自分が置かれたものとして受け、起こされた待ちの項目と実行待ちの項目をタスクとして受ける。受けたタスクのセルの持ち主を自分にし、盗んだ継続のそれぞれに `share(k, 送り手 = 元の worker の ID)` で印を付けてから動かす。送り手の引数は今の `share(w, receiver)` に足すものである ([オブジェクトモデル](../spec/object-model.md) の「`share`」)。普通の方針では、印を付けた後のタスクは、また救済されるまで救済した worker から動かない
- 安全な理由は次のとおりである。タスクをまたぐ受け渡しはどれも印を付けるので、待ったタスクの印のない物体はそのタスクだけのものである。Rust の側の構造が持つ語はどれも数えた参照である。救済する worker が lock を持つ間、元の worker はそのタスクに触れない
- 持ち主が変わると、取り消しのビットを処理して待ちを外す務めも新しい持ち主へ移る。完了と取り消しの知らせは、宛先の lock の下で持ち主を読み直すので、移った先へ届く
- 待ちの理由がプールの仕事なら、救済する worker は仕事の記録の語も継続と同じく扱う ([非同期の設計](async.md) の「I/O の driver」の表)
- 救済は `Submit` を処理しない。縛った worker の I/O の driver が要るためである。詰まった worker へ回した受け付けはその worker が戻るまで待つ。これは遅れで、正しさの問題ではない

### 固定したタスク

- 専用の worker の上のタスクは救済しない。専用の worker は新しいタスクを置く先にならない。固定したタスクが始めた子は、同じ worker を受け継ぐ
- 仕事が専用の worker から出るのは、`compute`、固定していないタスクへの channel、`Gui.post` を通るときだけである ([FFI と拡張の設計](ffi.md) の「GUI」)
- 差し替えた待ちはtoolkit のイベントループを worker の待ちの中で回す。toolkit のコールバックは、動けるタスクがなくなるまで動かして戻る `rt_run_pending(worker)` を呼ぶ。この入れ子は VM の命令を動かしていない間に起き、`Ctx` は空いているので、extern から入り直さないという規則に反しない

### タスクごとの上限

タスクの中で深さかスタックの上限を超えたとき、またはメモリの柔らかい上限で選ばれたときは、そのタスクの IO の失敗 `ResourceLimit` にする ([非同期の設計](async.md) の「タスクごとの上限」)。スケジューラの側の仕事は、タスクのセルがそのタスクの動く間に確保したバイト数を数えること (確保器の遅い道で足す) と、監視のスレッドが柔らかい上限を超えたときに、動いているか実行待ちのタスクのうち数のいちばん大きいものに旗を立てることである。メモリの硬い上限は今と同じく run 全体を止める。

### 却下した案

- 始まったタスクも盗む Tokio の形の work stealing: 動いたタスクの作業の集合がすべて共有になり、reuse を失う
- worker の間でタスクを動かさない thread-per-core の形: 詰まった worker の接続を救えない
- 詰まった worker の役を別のスレッドに渡す形 (Go の P と M): 詰まったスレッドの `Heap` はそのタスクが使っている

## 可変状態

### API

```
new      : a -> <Heap h> Ref h a              (a : Type<Unr>)
get      : Ref h a -> <Heap h> a
set      : Ref h a -> a -> <Heap h> Unit
run_heap : (forall h. Unit -> <Heap h | e> a) -> <e> a
```

- `Ref h a` は `Unr` の値で、データ構造に入れたり、関数に渡したりできる。読み書きの権限は row の `Heap h` が管理する
- `run_heap` は組み込みとして型検査器で特別扱いする。rank-2 の型をユーザーに書かせることはしない。今の型推論の方針 (rank-1 + bidirectional) は変えない
- `new` は `a : Type<Unr>` を要求する。シグネチャの型変数で使った場合は、[線形性](../spec/linearity.md) と同じ仕組みで `Unr` の制約が加わる
- 実装は実際の可変メモリにする。`Heap h` は組み込みで、実際のメモリなので、multi-shot で再開したときの状態は**共有**される (Koka と同じ意味)

### `IO` と分離する理由

- 局所的な可変状態を外から消せる: 内部で `run_heap` を使う関数の型は純粋なままになり、並列タスクに渡せる
- 型が決定性を区別する: `<>` は純粋、`<Heap h>` は状態があるが決定的、`<IO>` は外の世界に触れて非決定的である
- 読み書きに同期が要らない: 下の「不変条件」により、`Heap h` の操作を同時に行うスレッドは1つだけで、救済での受け渡しは受け箱の lock で順序づく。`get` / `set` は atomic でない普通のロードとストアで済む
- 領域ごとに独立している: 並列タスクがそれぞれ内部で `run_heap` を使っても、互いに干渉しない

並行タスクの間で共有する可変状態 (例えば非同期のタスク同士で共有するカウンタ) は、`Heap` では書けない。`IO` の下の `Chan` (持ち主のタスクの後ろに置く actor の形) と `Atomic.Counter` で扱う ([非同期の設計](async.md) の「チャネルと共有の状態」)。

### `Lin` の値を `Ref` に入れない場合の書き方

| やりたいこと | 書き方 |
|---|---|
| `Lin` の値を書き換えたい | `Ref` を使わず、値を線形に受け渡す。一意なので、Perceus の reuse でその場の書き換えにコンパイルできる (例: `Lin` の `MutArray` の `write : MutArray a -> Int -> a -> MutArray a`)。`MutArray` を `var` に入れれば、受け渡しを書かずに `a[i] <- e` と書ける。変数の状態は handler が持ち、受け渡しは状態を渡す形の特殊化が作る |
| 一つのリソースを色々な場所から使いたい | リソースを handler に持たせる。handler が所有して操作を提供し、`return` 節で後始末する。構文としては [式](../spec/expressions.md) の「パラメータ付き handler」が基本になる |
| 一意性だけが理由の `Lin` (後始末のない可変バッファなど) を、使い終わったら共有したい | 型ごとに `freeze` を用意する (例: `freeze : MutArray a -> Array a`)。後始末を持つ型には定義しない |

- 汎用の「`Lin` → `Unr`」の変換は作らない。`FileIn` などが複製できてしまい、二重の後始末を防げなくなるため。また、RC が 0 になったときに後始末する方式は、「通常の制御フローでは暗黙の後始末を行わない」という決定 ([線形性](../spec/linearity.md)) に反する
- `Lin` の `MutArray` を並列にその場で書き換えるには、添字の範囲のプリミティブ `Par.for_mut` を使う。1つの塊の重ならない添字の範囲を子に渡し、子はその範囲だけを書く (Rust の `split_at_mut` と同じ規律)。塊を `split_at` と `concat` で別の物体に分けて戻す形は採らない。写すと O(n) で、写さない view は持ち主が2つになるためである

## スレッドをまたぐ RC

### オブジェクトがスレッドをまたぐ場面

1. `par` の子や `spawn` に渡すクロージャが捕まえた値
2. channel やタスクの結果で送る値
3. 救済で別の worker が再開する継続が参照している値
4. ブロックする呼び出しのプールの仕事に渡す値と、取り出しで戻る値

`Lin` の値は move だけを許し、`Lin` の物体の RC は常に 1 である ([LIR](../spec/lir.md) の「値の表現」)。そのため `Lin` の物体には印を付けず、所有者を移すだけで済む (下の「`Lin` の物体の所有者の移し替え」)。ただし、`Lin` な構造の中にある `Unr` のフィールドはスレッドをまたぐ。

始まったタスクの継続は救済のほかではスレッドをまたがない。これで、サーバの作業の集合は worker の局所に保たれ、reuse を失わない。

### 共有の印方式

```rust
// 局所 (正の値): Relaxed の load/store は、x86 でも ARM でも普通の mov になる
let n = rc.load(Relaxed);
if n > 0 { rc.store(n + 1, Relaxed) }
// 共有 (負の値): 本物の atomic 操作
else     { rc.fetch_sub(1, AcqRel); }
```

- オブジェクトは最初は局所的で、RC の操作は普通の加減算と同じ速さになる。代わりに、RC 操作ごとに印を確認する分岐が1つ増える
- 上の場面で、渡す値から到達できるオブジェクトをたどって共有の印を付ける。すでに印のあるオブジェクトでたどりを止めるので、各オブジェクトがたどられるのは高々1回である
- **印付けは送り手のスレッドが、公開する前に行う**。受け手が印を付けると、送り手がまだ同じオブジェクトに対して atomic でない RC 操作をしている可能性があり、data race になるため
- 例外は救済である。救済では送り手でない救済する worker が、元の worker の受け箱の lock の下で、元の worker を送り手として継続に印を付ける。lock を持つ間、元の worker はそのタスクに触れないので、競合しない (下の「スケジューラ」の「救済」)
- 印付けは下の「不変条件」に挙げる実行系のプリミティブの中で自動的に行う。ライブラリの作者が印付けを忘れることはない
- 共有したオブジェクトは、別のスレッドで RC が 0 になって解放されることがある。確保器は別のスレッドからの解放を受ける (下の「別のスレッドからの解放」)
- 共有の印の付いた物体 (RC が負) は、RC の値によらず reuse しない。Lean 4 の `lean_is_exclusive` と Koka の `kk_block_drop_reuse` と同じ規則である。Perceus の reuse の判定は、局所の RC が 1 かどうかだけになる。共有の物体を局所へ戻すのは、受け手の移し戻しだけである (下の「移し戻し」)

### 却下した案

- 常に atomic にする (Swift、Rust の `Arc`): シングルスレッドのプログラムでも、すべての `dup` / `decref` が atomic 命令になる
- Biased RC: 印付けのたどりは不要になるが、ヘッダに所有するスレッドの ID とカウンタ2つが必要で、実装がかなり複雑になる
- 型で区別する: Kind に共有の次元が必要になり、決定2に反する

### `par` の印付け

印付けをいつ行うかで、どの物体が共有になるかがスケジュールに依存するかが決まる。

| 印付けの時点 | 共有になる物体の集合 | 逐次の実行で通る経路 |
|---|---|---|
| 盗まれた時点 (private deque の方式) | スケジュールに依存する | 印付けが一度も起きない |
| fork の時点 (join では公開と移し戻し) | スケジュールによらず決まる | 並列のときと同じ物体に印が付く |

`par` は fork と join で共有の経路を通す。印を付けるのは fork だけで、join は公開と移し戻しの歩きだけを行う。

- fork: 右の子の閉包から届く物体に印を付ける。rayon の `join` と同じく、別の worker に渡りうるのは右の子だけで、左の子は親の worker で動く。`lin` ビットの立った根からは移し替えにする (下の「`Lin` の物体の所有者の移し替え」)
- join: 右の子の worker が結果を Release で公開し、親は移し戻しで受ける。印は付けない (下の「移し戻し」)

添字の範囲のプリミティブ (`Par.for_mut` と `Par.tabulate`) は、1つの塊の範囲を子に渡す。要素のうち rc > 1 のものには印を付け、rc 1 のものには印を付けない。範囲が子にその要素を一意に持たせるためである。検査モードでは、fork で子の範囲の rc 1 の要素の持ち主を子の ID に書き換え、join で範囲の rc 1 の要素の持ち主を親の ID に書き戻す。子が確保して範囲に入れた要素も、join で親の持ち主になる。速いモードでは持ち主について何もしない。生の要素の配列は走査する語を持たないので、印付けは O(1) である。

印付けは `par` の実行時の意味の一部で、検査モードだけの動作ではない。共有した物体は reuse しないので、共有の集合が決まれば reuse の判断も決まる。そのため、逐次と並列で `RunStats` の作業の回数が一致する (`peak_objects` は除く)。代償は、1つの worker の上でも `par` に渡したデータが atomic の RC になり、reuse されなくなることである。1つの worker の `par` には速さの目標がないので、受け入れる。

### 論理的な worker ID

物理的な worker が1つだと、所有者の検査で全物体が同じ所有者になり、何も検出しない。そこで worker ごとの `Heap` に論理的な worker ID を持たせる ([オブジェクトモデル](../spec/object-model.md) の「論理的な worker ID」)。所有者の ID は検査モードだけのもので、速いモードにはない。

- 逐次の `par` は左の子を親の ID のまま実行し、右の子を新しい ID で実行する
- 右の子が確保した物体の所有者は、右の子の ID である
- 検査モードでは `Async` のタスクも `par` の子と同じく、タスクごとに新しい ID で動く。救済で印を付けるときの送り手の ID は、そのタスクの ID である
- 移し替えで受け手の決まらない `Lin` の値には、予約した途中の持ち主の ID を付ける (下の「`Lin` の物体の所有者の移し替え」)
- 検査モードのヘッダは所有者 ID を持つ。Relaxed の `AtomicU32` にする。正の RC の物体への `dup`、`decref`、フィールドの書き込み、reuse のたびに、所有者が今の ID と一致するかを確かめる
- 生きている物体の数はrun の表で論理的な ID ごとに Relaxed の atomic で数える。表はタスクとともに大きくなる。範囲のプリミティブが fork と join で要素の所有者を移すときは、この数も移す。join で移し戻しが漏れて残った物体は `TransferLeak` で報告する。N = 1 では join のときに同期して確かめ、N が 2 以上では run の終わりにすべての worker が待っているときに確かめる

fork で印を付け忘れた物体に右の子が触れると、所有者が親の ID なので、検査は必ず失敗する。スケジュールに依存せず、`par` を使うすべての UI テストで毎回確かめられる。Lean 4 と Koka は eml と同じ符号の規約を使うが、どちらも印付けの漏れを直接見つける仕組みを持たない。局所の経路を `AtomicI32` の Relaxed で書くと、印を付け忘れても言語のメモリモデルの上ではデータ競合にならず、Miri、TSan、loom のどれも直接は報告しない。直接効く先例はCPython (PEP 703) の `ob_tid` のような所有者の記録である。

逐次の実行で確かめられるのは論理の誤りまでである。公開するときの順序 (Release と Acquire)、2つのスレッドからの同時の `decref`、deque の正しさは、本物のスレッドでしか現れない (下の「テスト」)。

### `Lin` の物体の所有者の移し替え

- ヘッダに `lin` のビットを、検査モードに限らず常に持つ。`FileIn` などの extern の資源は作るときにビットを立て、`con` と `closure` は静的な Kind の印が `lin` のときに立てる ([オブジェクトモデル](../spec/object-model.md) の「`lin` ビット」)
- 印付けのたどりに移し替えの形を足す。今の `share` は `lin` ビットの物体そのものの所有者だけを移し、その子はたどり続けて印を付ける ([オブジェクトモデル](../spec/object-model.md) の「`share`」)。移し替えの形はこの規則を次のように広げる。ビットの立った根から始め、道の上の物体がどれも rc 1 である間に届いた物体には印を付けず、所有者を移す。最初に rc > 1 の物体に着いたら、その下は印付けに切り替える。道の上の物体はそれぞれ道の上の親からちょうど1回参照され、根は `Lin` なので、移した物体はどれも一意である。これで、共有した物体を reuse しない規則のもとでも、`Lin` の値を子へ移して子でその場で書き換える形が成り立つ
- 受け手が決まらない `Lin` の値 (MPMC の `Chan` と `Task` の結果) は、途中の持ち主の ID を付けて送る。送り手は受け手を予約した途中の ID にして移し替えをする。`Lin` の根から rc がすべて 1 の道で届く物体だけが途中の持ち主になり、最初の rc > 1 の物体から下は印付け (rc < 0) に切り替える。受け手の移し戻しは、rc > 0 で持ち主が途中の ID の物体を受け取って (持ち主を受け手にして) 下る。持ち主の ID は検査モードにだけあるので、速いモードでは送り手の印付けだけが行われ、受け手の裏返しの歩きは変わらない
- `poly` のコードで作った `Lin` の物体はビットを持たないので、fork で共有になり、その場の書き換えができなくなる。安全の側に倒れるだけである

### 移し戻し

受け手は移し替えの歩き `rt_transfer(w)` で、受け取った値の共有の物体を局所へ戻す。

- 歩きは、自分が裏返した物体の中にだけ下りる。裏返しはrc == -1 (Acquire で読む) の物体を rc := 1 にし、所有者を自分にして、子へ進むことである。rc > 0、rc < -1、rc == 0 の物体では止まる
- 費用は裏返した物体とその直接の子の数に比例する。子が確保した局所の物体だけの結果は O(1) で受けられる
- 検査モードはrc > 0 の物体の所有者 ID を書き換える2回目の歩きを、診断のためだけに行う。意味は変わらないので、速いモードと検査モードの reuse の判断は一致する
- 裏返しが正しい理由: Rust の側の構造が持つ語はどれも数えた参照で (下の「Rust の側が持つ語」)、救済で盗むタスクは lock の下で取り除いてから印を付ける。そのため、rc == -1 の物体を参照するのはちょうど1つで、それは歩く側が持っている
- 移し戻しを使うのは、`par` の join、channel の受け取り、タスクの開始、`await` でのタスクの結果、ブロックする呼び出しの取り出し、専用の worker からの返事である。取り出しはプールへ移した `Mut*Array` と `Lin` の物体もこの歩きで受ける
- Koka は最後の共有の `drop` で 0 に戻すが、eml は戻すのを受け手の歩きだけにする。送り手が持ち続ける値は共有のままで、reuse しない

### 印付けの表

送り手は公開する前に印を付ける。救済だけは、救済する worker が印を付ける (上の「共有の印方式」)。

| 渡る所 | 送り手 | 受け手 |
|---|---|---|
| `par` の fork | 閉包が捕まえた値に印を付ける。`lin` ビットの根からは移し替え | なし |
| `par` の join | Release で公開する | 移し戻し |
| 添字の範囲のプリミティブ | rc > 1 の要素に印を付ける。検査モードでは、rc 1 の要素の持ち主を子にする | 検査モードでは、join で範囲の rc 1 の要素の持ち主を親に戻す |
| `spawn` と `start` | 閉包が捕まえた値に印を付ける | タスクの開始で移し戻し |
| 待ったときと横取りのときの継続 | なし | なし |
| 救済 | なし | 救済する worker が、元の worker を送り手として継続に印を付ける |
| channel の送りと受け取り、`Task` の結果 | 印を付ける。受け手の決まらない `Lin` の値は途中の持ち主にする | 移し戻し |
| ブロックする呼び出しのプール | 印を付けない。仕事の記録が数えた参照で持ち、`Mut*Array` は記録へ移す | 取り出しが持ち主の worker の上で移し戻し |
| 専用の worker への仕事と返事 | 印を付ける | 移し戻し |
| I/O の buffer | 所有ごと移す (一意でなければ写す) | なし |
| どこでも、`Lin` の値 | 印を付けずに所有者を移す | なし |

ブロックする呼び出しのプールの場合ごとの扱い (取り消し、救済、`exit` と致命的な誤り、回復、検査モード) は、[非同期の設計](async.md) の「I/O の driver」の表にある。

### 別のスレッドからの解放

- 自前の確保器に、別のスレッドからの解放を受ける遠隔の空きリストを足す。ページの頭に持ち主 (`owner: u32`) と遠隔の空きリスト (`remote: AtomicUsize`) を置き、大きい物体にはヒープごとの遠隔のリストを置く。遠隔に返した数を `remote_count` で atomic に数える
- 持ち主のヒープが遠隔のリストを取り込むのは、空きリストが空になったとき、ループの1回ごとに `remote_count` が 256 を超えていたとき、待つ前、漏れの検査と回復の前である
- ページは run の間 OS に返さない。そのため、RSS は worker のヒープごとの最大の和で抑えられる
- どのヒープもrun の間生きるどのヒープのページの上の rc < 0 の物体を受け付ける。検査モードは、語が即値か、凍結した領域の物体か、登録したヒープのページの上の物体かを確かめ、rc > 0 の物体では前置きの所有者が今の ID と一致するかを確かめる
- 回復は、すべての worker とプールのスレッドが待っているときにだけ行い、N 個のヒープを写す。rc < 0 の物体も写せる。凍結した領域とヒープの区別はページの持ち主で行う。`Foreign`、`lin` ビットの物体、token は今と同じく `Unrecoverable` である

### Rust の側が持つ語

- Rust の側の構造が持つ語は、どれも数えた参照である。`dup` か move で取り、構造から取り除くときに手放す
- worker ごとの構造 (受け箱、待ちの集まり、実行待ち、I/O の driver の保留の表) の語は、その worker のヒープの登録した根である
- worker の間で共有する構造の語は、run の登録表に載せる。channel の buffer、タスクのセルの結果、スコープの失敗の欄、join の節点、プールの仕事の記録である
- 漏れの検査と回復は登録表をたどる。回復は物体の番地を変えるので、登録した語は回復が書き換えられる場所に置く ([オブジェクトモデル](../spec/object-model.md) の「回復」)
- channel は `Data` の物体の連なりでなく、数えた参照を持つ Rust の構造にする。`Foreign` の Rust の値に語を入れる形は採らない。`Foreign` は走査する語を持たず、破棄処理はヒープを受け取らないためである

## 並列と並行の API

### row の Kind

```
row の Kind: Row<s>,  s ∈ { Never ≤ Once ≤ Multi }
  Never : never の操作だけを含む row
  Once  : さらに once の操作 (extern のエフェクトの IO を含む) を含んでよい
  Multi : さらに multi の操作を含んでよい
```

- `par` の子の row を `e : Row<Never>` に制限する。`IO`、`Heap h`、`once` / `multi` の操作は除外される
- `Panic` は `Never` のラベルに分け直す。`Panic` の操作は `never panicked` だけで、`Panic` を起こす extern は中断して再開しない。`Once` の根拠の「extern の関数がその場で1回だけ戻る」は extern の呼び出しのことで、呼び出しは `perform` でない。そのため、子は `Int` の足し算や `Array.get` を書ける。`IO` は `Once` のままにする。`Never ≤ Once` なので、`σ ≤ Once` の持ち越しの制約はどれも満たされたままである
- 制約は書ける形にする。シグネチャの row 変数に多重度の上限を付けた `<never e>` で、`once a -> …` と同じ並びである。`Par.map` に関数を渡す補助の関数のシグネチャに要るためで、シグネチャを書かなければ推論で付く。合わない row の関数を渡すと、呼び出しの位置で新しい型の誤りになる
- 今の実装は内部の Kind の束を3要素で用意する (`Never` を最初から入れておく)。規範は [型と Kind](../spec/types.md) にある

### 子タスクに `never` の操作だけを許す理由

- 一般の handler は並列と組み合わせられない: `once` / `multi` の handler は状態を handler の実行ごとの evidence に、計算の続きを継続のクロージャに持つ。例えば [エフェクトと handler](../spec/effects.md) の `run_state` の節 `| fn get () st -> (st, st)` の状態は、操作が起きるたびに evidence から節に渡り、その場で evidence へ戻る ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。二つの子タスクがこうした操作を同時に perform すると、どちらの節の `k` に計算の続きを返すかが決まらない
- `never` の操作は再開しない: handler の節は子をすべて片付けた後に、親のスレッドで1回だけ実行すればよい。節が並行に走ることがないので、ロックも、子のスレッドから親のフレームをたどる処理も要らない
- データ並列にはこれで足りる: データ並列の処理はもともと純粋な関数と、失敗の通知 (`Panic` と、`Fail` のような `never` のエフェクト) で書ける

### `par` の意味

```haskell
par  : (Unit -> <never e> a) -> (Unit -> <never e> b) -> <e> (a, b)
both : (Unit -> <e> a) -> (Unit -> <e> b) -> <e> (a, b)        -- 逐次の版。任意の row を許す
```

- `par` は1つで、すべての子の完了を待つ。両方の子が終わってから、いちばん左の子の中断を親で起こし直す。どちらも正常に終われば組を返す
- **`par` は常に決定的**である。子は外の世界に触れず、中断は左の子を優先するので、結果は実行のスケジュールに依存しない
- 逐次の `(f (), g ())` と違うのは、左の子が中断して右の子が停止しない場合だけである。逐次なら中断で終わるプログラムが、`par` では止まらない。子の取り消しは後で足す (下の「未決の論点と将来の拡張」)
- 実行時エラー (評価全体を止める誤り) も左を先にする。右の子が先に実行時エラーで止まっても、左の子を最後まで実行してから報告する。右の子は止めたまま解放せず、誤りを join の節点に記録する。左の子が正常に終われば右の子の誤りで、左の子も止まれば左の子の誤りで、評価全体を止める。左の子が中断すれば (`never` の操作)、右の子の誤りは捨て、左の中断を親で起こし直す。左の子が停止しなければ右の子の誤りは報告されず、逐次の実行と一致する。止めた右の子のスタックが持つ語を含め、残った物体は止める手順で落とすヒープ (REPL では回復で捨てる古いヒープ) と一緒に捨てる
- `par` の子の中の実行時エラーは worker の入口でなく子の境目まで切る。境目は VM では子のフレームの境目で、ネイティブのコードでは子ごとの `JmpBuf` である。手伝う worker では子の下に待つ親のフレームがあるので、入口まで切ると親を壊すためである。誤りは終わりの欄でなく join の節点に書き、その子の worker はほかの仕事を続ける。N が 2 以上でも同じで、親が左の子を終えたとき、記録した誤りを終わりの欄に書く。入れ子の `par` では内側の join から順にこの規則を当てる
- 止めるビットを見て止まった子は、それを自分の誤りとして join に記録せず、そのまま止める手順に入る。この規則が順序づけないのは、子が起こしたのでない run 全体の止め方 (割り込み、`TERMINATE`、メモリの硬い上限) だけで、それは起きた時点で終わりの欄に書く
- 捨てる側の子の結果が `Lin` の場合、`par` は型について多相なので、実行時にオブジェクトの記述子から破棄処理を引いて drop する。`eml_rt` の記述子は破棄処理を持たなければならない。今の `eml_rt` は型ごとの記述子の表を持たず、破棄処理をヘッダの種類で表す ([オブジェクトモデル](../spec/object-model.md) の「ヘッダ」)
- `par` は実行系の核のプリミティブ (fork / join の節点) で、std の `Par.par` から呼ぶ。子の `never` の操作が `par` から抜けるのを、次の形で親に渡す
  - 子の `evv` は空 (`()`) で始める。evidence passing はプログラムの `never` の操作 `E.op` ごとに、`fork$E.op` と `reperform$E.op` を作る。`fork$E.op` は引数を組に詰めて `rt_child_abort(&reperform$E.op, 組)` を呼び、子を中断する。`reperform$E.op(組)` は組を開いて `E.op` を普通に perform する
  - 子の中で `E` の evidence を空の `evv` から探すと、不死の印の evidence が返り、その節は `fork$E.op` である。子の中の extern の `Panic` は、VM の `failed` が `fork$Panic.panicked` へ回す
  - join の節点は `(reperform の関数, 組)` を持つ。両方の子が終わった後、親はいちばん左のものを呼ぶ。それは親の文脈で親の evidence を使って perform するので、`prompt$` は普通に動く。`par` の呼び出しの位置は巻き戻しの地点である ([Core IR](../spec/core-ir.md) の「`never` の中断」、[VM](../spec/vm.md) の「巻き戻し」)
  - 子は親の evidence に触れないので、evidence のために印を付けるものはない
- 子の取り消しを入れるときは、協調的な中断を安全点で行い、中断した子が捕まえている `Lin` の値を `drop k` と同じ後始末の情報で解放する

### データ並列での使い勝手

```haskell
pub map      : (a -> <never e> b) -> Array a -> <e> Array b
pub mapi     : (Int -> a -> <never e> b) -> Array a -> <e> Array b
pub tabulate : Int -> (Int -> <never e> a) -> <Panic | e> Array a                    -- 範囲のプリミティブ
pub fold     : (b -> b -> <never e> b) -> b -> (a -> <never e> b) -> Array a -> <e> b
pub reduce   : Int -> b -> (b -> b -> <never e> b) -> (Int -> <never e> b) -> <e> b   -- 添字の範囲の畳み込み
pub for_mut  : (Int -> a -> <never e> a) -> MutArray a -> <e> MutArray a             -- 範囲のプリミティブ
pub try_map  : (a -> <never e> Result x b) -> Array a -> <e> Result x (Array b)
```

- `std/Par` の集まりの関数が主な API である。`for_mut` と `tabulate` はランタイムのプリミティブで、子に1つの塊の添字の範囲を渡す。ほかは `par` の上の eml で書く。粒度を指定する版 (`map_grain`、`fold_grain`、`for_mut_grain`、`tabulate_grain`) と、生の要素の配列の版 (`tabulate_floats`、`tabulate_ints`、`for_mut_floats`、`for_mut_ints`) を持つ。生の配列の版の名前が型ごとに分かれるのは、クラスが `Lin` の型を受けないためである
- 分け方の木は長さと粒度だけで決まる。既定の粒度は N によらない定数 (1024 要素) である。盗まれたかどうかは節点の2つの半分を `par` で動かすかその場で動かすかだけを決め、木の形を変えない。そのため `fold` の組み合わせの順は決まっていて、浮動小数の結果はどの N とスケジュールでも同じビットになる
- `try_map` は、見つかったいちばん左の `Err` の添字 i より右にある範囲の fork だけを省く (見つかった `Err` の添字の最小を CAS で持つ)。i より左はすべて評価するので、結果は左をすべて評価した後のいちばん左の `Err` である
- 失敗の通知は `Panic` と、`Fail` のような `never` のエフェクトで書く
- 子タスクの中ではデバッグ出力 (`println`) ができない。デバッグするときだけ `par` を `both` に書き換えれば、子の中で `println` できる
- row に現れない `trace` のような抜け道は用意しない
- `fork` と `join` を普通の関数として公開する形、`Par` のエフェクト、futures の形、新しい構文は採らない

### すぐに再開する handler の最適化

handler の節が `k v` を末尾で1回だけ呼ぶ場合、継続を取り出さない直接の呼び出しにコンパイルできる (Koka や evidence passing の主要な最適化)。これは並列とは関係なく、コンパイラが handler ごとに Core IR の形から判定する。エフェクトの宣言に操作の種類を追加する必要はない。evidence passing で実装している ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。

### 並行処理

- 並行処理は std の `Async` で書く ([非同期の設計](async.md))。タスクの row は `<IO, Panic, Async>` に閉じる。並行処理はもともと非決定的なので、`IO` を許す
- タスクは中断の境目である。IO の失敗と `Panic` はタスクの底で止まり、`exit` は下の「止める手順」で run を終える ([非同期の設計](async.md) の「失敗と `exit`」)
- ユーザー定義のエフェクトはタスクのクロージャの中で handle し終えている必要がある (OCaml 5 の Eio と同じ扱い)。`Heap h` は閉じた row によって除外される
- 並行処理のための新しい構文は追加しない。ラムダと `use` で書ける ([式](../spec/expressions.md) の「並行処理」)
- CPU を多く使う仕事は `compute` で `par` の仕事にして、呼んだタスクを待たせる ([非同期の設計](async.md) の「`compute`」)

## 継続の移動と不変条件

### 不変条件

> スレッドをまたいで値や制御を渡す実行系のプリミティブ (`par` の fork、`spawn`、channel、救済、プールの仕事、専用の worker への仕事) は、すべて閉じた row か `Row<Never>` の Kind 制約を持つ。したがって、`Heap h` の操作を同時に行うスレッドは1つだけである。`run_heap` の中で待ったタスクの継続が別の worker へ移るのは救済だけで、救済は受け箱の lock の下で受け渡すので、2つのスレッドが同じ領域に同時に触れることはない。

ランタイムは次の不変条件も守る。

1. 始まったタスクが worker を変えるのは救済だけで、救済はその継続に印を付ける。スレッドをまたぐのは、まだ始まっていない閉包、送る値、結果、救済した継続だけで、どれも印を付けるか `Lin` を移す
2. Rust の側の構造で語を持つものは、どれも登録した根である (上の「Rust の側が持つ語」)
3. VM のタスクを切り替えるのは yield の状態がなしの安全点だけで、そのとき `evv` を退避する。ネイティブのタスクは `Async` の操作でだけ切り替わる。タスクは入口の関数から戻ってループへ戻る
4. `par` の join か `Async.run` で待つ VM のタスクは、worker を手放して待つ。そこで待つネイティブのフレームは、手伝うか、ループを入れ子にする
5. ヒープはすべてのスレッドを待ち終え、遠隔のリストを取り込むまで生きる。回復はすべてが待っているときにだけ行う
6. `Control` は run に1つである。監視のスレッドがその止める語のビットを、worker の一覧のすべての worker の止める語に写す。シグナルの handler は `Control` の止める語、待つタスクのないときの worker 0 の止める語、自己パイプにだけ触れる。SIGINT は worker 0 のほかのすべてのスレッドで塞ぎ、host のスレッドは止める手順が始まったとき (終わりのビットが立ったとき) に塞ぎを解く
7. 外の関数の呼び出しはプールへ出さなければタスクの worker のスレッドで動く。プールの仕事は語に仕事の記録を通してだけ届き、run は仕事が終わるまでその記録を生かしておく
8. worker のスケジューラの状態で語を持つものは、その worker の受け箱の lock の下か、持ち主のスレッドでだけ書き換える (横取りした VM のタスクのキュー、deque の持ち主の側)。取り消しの処理と待ちを外すことも受け箱の lock の下で行う。ロックフリーの構造は `par` の deque だけである
9. Rust の側の構造が持つ語は、どれも `dup` か move で取った数えた参照で、取り除くときに手放す。I/O の driver の保留の表と完了の中身も同じである

新しいプリミティブを追加するときは、これらの不変条件を満たすことを確認する。

### `once` の継続の移動

- `Async` のタスクが待つと、handler の節が継続 `k` (`once`、`Lin`) を待ちの集まりか実行待ちに預け、同じ worker が後で `k` を呼んで再開する。`k` は worker の局所にとどまるので、印を付けない
- 始まったタスクが別の worker に移るのは救済だけである。救済する worker は元の worker を送り手として、継続から届くオブジェクトに印を付ける。evidence passing の継続はクロージャの列なので ([Core IR](../spec/core-ir.md) の「継続の組み立て」)、継続のクロージャから届くオブジェクトをたどる。一度印を付けた継続のクロージャにはすでに印が付いているので、たどりはそこで止まる
- タスクは `run_heap` の中でも `Async` の操作で待てる。`k` の型は `start_task` の handler の外側の row の `once r -> <IO> Unit` なので (`r` は生の操作の結果の型で、`Wake` を持つ。`await_io` なら `(Wake, OpId)` である。[非同期の設計](async.md) の「`Async` のエフェクト」)、続きに `Heap h` の操作があっても `k` の型に `Heap h` は現れない。続きは `run_heap` のフレームを持ったまま待ちに入り、別の worker に移るのは救済のときだけである。救済は受け箱の lock の下で受け渡し、継続に印を付けてから動かすので、領域を同時に触るスレッドは1つのままで、`get` と `set` は atomic でないままでよい

### `multi` の継続の並列な再開

```haskell
| ctl choose () k -> par (fn () -> k True) (fn () -> k False)
```

- [エフェクトと handler](../spec/effects.md) の持ち越し規則により、`multi` の操作をまたいで `Lin` の値は生きていない。`k` が捕まえているのは `Unr` の値だけなので、共有しても安全である
- `k` の続きのエフェクトは上のラムダの row として `par` の制約 (`Row<Never>`) で検査される。新しい仕組みは要らない。続きが `never` 以外の操作を含む場合は、並列に再開できない

### スレッドに縛られたリソース

- 組み込みのリソースはどのスレッドで後始末してもよいものに限る (現状の `FileIn`、`FileOut` と標準入出力のハンドルはこれを満たす。閉じる処理は Rust の値の drop glue と、lock を取るか atomic の印を下ろすだけの `Drop` である。`FileOut` の drop glue は buffer を書き出すが、書き手は Host の `open_write` が返す `Send` の値である。[オブジェクトモデル](../spec/object-model.md) の「extern」の「読み手」と「出力のバッファ」)
- ハンドルは共有の印なしに所有の移動で worker へ移る。`par` の子はハンドルを使えない。ハンドルのどの操作も `<IO>` を持ち、子の row は `IO` を除くためである。子にできるのは `drop` だけで、それはストリームを親に返す。タスクの中では、ハンドルが読み手ごと worker へ移るので lock は要らず、出力は書き込みごとの lock ですでに安全である
- I/O の driver のハンドルは最初に受け付けた worker の driver に縛る。別の worker からの受け付けはその worker の受け箱を通して回す ([非同期の設計](async.md) の「ハンドルと worker」)
- スレッドに縛られたリソース (GUI のハンドル、スレッドに局所的なライブラリの状態など) は、専用の worker の上のタスクに閉じ込める。GUI はメインの worker の上で動き、プラグインはどの操作でも今の worker がメインの worker であることを確かめる ([FFI と拡張の設計](ffi.md) の「GUI」)。Kind に共有の次元は足さない

## 止める手順

run の終わり方は `main` の正常な終わり、`exit`、致命的な誤り、待つ者のないシグナルのどれでも同じ手順にする。

1. 終わりを決めた者が `Control` の終わりの欄に理由を書く。欄は `main` の正常な終わりか、`exit` と終了コードか、致命的な誤りを持ち、最初の書き手が勝つ (CAS)。書いた者は終わりのビットを立てる
   - `main` のタスクが値を返すと、worker 0 が正常な終わりを書く
   - `exit n` は今と同じく自分のタスクのスタックを底まで巻き戻し、底が欄に書く ([非同期の設計](async.md) の「失敗と `exit`」)
   - `par` の子の外での worker k の致命的な誤り (`eml_fatal`、または VM の `step` の `Err`) は、欄に誤りを書いてビットを立ててから、自分の入口へ切る。`par` の子の中の実行時エラーは子の境目まで切って join の節点に記録し、親が左の子を終えてから欄に書く (上の「`par` の意味」)
   - 待つ者のないシグナルでは、監視のスレッドが割り込みか `TERMINATE` の致命的な誤りを書く (下の「シグナル:」の項)
2. 監視のスレッドがビットを各 worker の止める語に写し、待っている worker と host のスレッドを起こす。host のスレッドはここで SIGINT の塞ぎを解く。そのため、worker を join する間とプールの仕事を待つ間の2回目の Ctrl-C も `_exit(130)` に届く。受け箱での待ち、join の節点での待ち、I/O の driver での待ち (worker を起こす口で)、差し替えた GUI の待ち (プラグインの起こす口で) のどれも起きる
3. 各 worker は次の安全点でビットを見て、自分の入口へ戻る。VM の worker は今と同じく `step` から `Err(Stop)` を返し、ネイティブの worker は入口へ longjmp する。後始末はしない。プールのスレッドは、動いている仕事が戻ったときにビットを見る
4. host のスレッドが次の順で後を片付ける
   1. すべての worker を join する
   2. 実行中のプールの仕事が終わるのを待つ
   3. I/O の driver を閉じる。操作を取り消し、限られた時間だけ完了を待つ
   4. ヒープを落とす。ファイナライザがファイルとソケットを書き出して閉じる
   5. Host を書き出す
   6. 終了コードで終わる。`main` の正常な終わりは 0、`exit n` は `n & 255`、割り込みは 130、`TERMINATE` は 143、ほかの実行時エラーと、Host の書き出しの失敗は 1 である。実行時エラー (割り込みと `TERMINATE` を含む) は今と同じく1回だけ報告する

- 待ちのタスクと実行待ちのタスクは巻き戻さない。その継続はヒープとともに放され、`Lin` の資源はファイナライザが後始末する (継続を捨てる強い取り消し。[非同期の設計](async.md) の「強い取り消し」)。ほかの worker の上のフレームごとの後始末はしない
- シグナル: シグナルの handler は async-signal-safe のまま、`Control` の止める語のビットを立て (Ctrl-C は `INTERRUPT`、`SIGTERM` は `TERMINATE`)、待つタスクがなければ worker 0 の止める語にも立て、自己パイプに1バイト書いて監視のスレッドを起こす (上の「スレッドと worker」)。Windows ではコンソールの handler (`SetConsoleCtrlHandler`) が同じビットを立て、監視のスレッドを起こす。CTRL_C は `INTERRUPT`、CTRL_CLOSE と CTRL_SHUTDOWN は `TERMINATE` である。ビットを見た監視のスレッドは、ほかの worker の止める語に写す前に、そのシグナルを `Signal.wait` で待つタスクが登録されているかを見る。登録されていればビットを下ろし (`Control` にビットごとに下ろす操作を足す)、待つタスクのセルの持ち主へ完了として届ける。登録されていなければ、終わりの欄に致命的な誤り (割り込みか `TERMINATE`) を書き、致命的な誤りと同じ手順で run を止める。`INTERRUPT` では今と同じく 130 で ([VM](../spec/vm.md) の「上限と割り込み」)、待つ者のない `TERMINATE` は 143 で終わる
- `signalfd` と `EVFILT_SIGNAL` は使わない。どちらもすべてのスレッドでシグナルを塞ぐ必要があり、今の handler とブロックする読みの `EINTR` の道と食い違う
- 2回目の Ctrl-C は今と同じく `_exit(130)` である。handler がビットを立ててから監視のスレッドが下ろすまでの間 (高々監視の刻み1つ) の2回目の Ctrl-C も終わる
- REPL では、`exit` と致命的な誤りで評価が終わる。host のスレッドは worker を join する代わりに、すべての worker とプールのスレッドが待っている状態にして、実行中のプールの仕事と I/O の driver の操作を待ちきってから回復する (上の「別のスレッドからの解放」)
- メインの worker があるときは、メインの worker が入口へ戻った後、同じスレッドが host として 4 を行う (上の「スレッドと worker」)

## VM とネイティブのランタイム

- VM とネイティブは共通ランタイム `eml_rt` と `eml_sched` を使う ([オブジェクトモデル](../spec/object-model.md))。共有の印方式の RC (上の「スレッドをまたぐ RC」) は、`eml_rt` に入れ、両方で使う。実行時の検査は、`eml_rt` の検査モードが受け持つ
- VM とネイティブのコードは混ぜない。VM は参照の実装で、検査モードを持つ唯一の実行系である ([ネイティブ化の設計](native.md) の「確定した設計判断」)
- VM はシングルスレッドで出している

### VM も並列にする理由

並列化をネイティブのランタイムだけで行う案は、次の2点から採らない。

- **検査モードを持つのが VM だけである**。印付けの漏れ、移し戻し、所有者の検査、漏れの検査は検査モードで確かめる。VM を並列にしなければ、並列の安全性を確かめる実行系がなくなる
- **確かめる時期が遅い**。ネイティブ化は `Async` と FFI と GUI の後に進める ([ロードマップ](roadmap.md) の「段の列」)。共有の印付け、別のスレッドからの解放、上の「不変条件」は、それまで実装で確かめられない

VM を並列にする費用は小さいと見積もっている。evidence passing で継続はヒープのクロージャになり、実行の文脈 (`evv` と yield の状態) は `Ctx` として worker ごとに1つ持てばよい ([LIR](../spec/lir.md) の「実行の文脈」)。RC の分岐は不死の物体 (0) を区別する比較に負の側を足すだけで済む。`par` と `Async.run` は構造化された並行性なので、REPL の入力の境目では worker が1つも動いていない。

### VM の並列化の備え

次の制約を守り、後から VM を並列にできるようにする。

| # | 制約 |
|---|---|
| 1 | VM の状態は `Ctx` と `Task` (呼び出しのスタックとレジスタの枠) に置き、スレッドに局所的な大域変数を持たない |
| 2 | `CodeBase` は追記だけにし、実行中は読むだけにする (`Sync`)。不死の定数は凍結した塊 `Frozen` に置くので、`CodeBase` の `Sync` は `Frozen` の `Sync` に頼る ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」) |
| 3 | 共有の経路は、`par` の fork と join で必ず通す (上の「`par` の印付け」) |
| 4 | `par` は `eml_rt` の fork / join の節点として実装し、逐次の版も1つの実装として持つ |
| 5 | VM の呼び出しのスタックは、Rust の再帰でなく、タスクが持つデータにする。extern が閉包を呼び戻す入れ子の中では、タスクを切り替えない |
| 6 | join と `Async.run` で待つ VM の `Task` は、worker のループを入れ子にせず、worker を手放して待つ |
| 7 | タスクを切り替えるのは、yield の状態がなしの安全点だけにする。切り替えで退避する実行の文脈は `evv` だけである |

- SIGINT のハンドラは `SA_RESTART` なしで入れ、待っている読みを `EINTR` で止める ([VM](../spec/vm.md) の「上限と割り込み」)。今はプロセスがほかのスレッドを持たないので、SIGINT は読んでいるスレッドに届く。worker のスレッドを持つときは、worker 0 のほかのスレッドで `pthread_sigmask` により SIGINT を塞ぐ。host のスレッドは止める手順が始まったときに塞ぎを解く (上の「止める手順」)

制約1と制約2の型の性質は、`Session` の `Send + Sync` の試験 (`crates/eml_cli/tests/api.rs`) と同じ形の、型の assert で固定する。`crates/eml_vm/tests/api.rs` が `CodeBase<M>: Sync` と `Task: Send` を固定している。

VM は実行の状態をワーカーごとの `Ctx` と、タスクごとの `Task` (呼び出しのスタック、命令の位置、今のフレーム) に分けている ([VM](../spec/vm.md) の「スロットとスタック」)。`perform` で止まったタスクの続きはヒープ上の継続のクロージャになるので、このタスクを別の worker へ移すことは、クロージャの語を1つ渡すことと同じである。まだ始まっていないタスク (`spawn` に渡す閉包、`par` の右の子) も同じである。安全点で切り替えたタスクと、join で子を待つ親だけは、スタックの途中で止まっているので `Task` ごと持ち続ける。こうしたタスクは worker から動かさない。

語をほかのスレッドへ公開するのは、ランタイムのプリミティブ (fork、join、`spawn`、channel の送り、救済、プールの仕事) の中で、上の「印付けの表」の扱いを通す道だけにする。VM は語をほかのスレッドに渡す経路を持たない。`Word` は `Send + Sync` なので型では守れず、文書の決まりにする。破った場合は、検査モードの所有者の検査が見つける ([オブジェクトモデル](../spec/object-model.md) の「論理的な worker ID」)。

### 1つの worker での実行

`par` と `Async` は、まず worker が1つの VM で入れる。協調的なマルチタスクで、後の複数の worker と同じコードの経路を通る。

- `par` の右の子をタスクにし、左の子は親のタスクがそのまま実行する。右の子は新しい論理的な worker ID で動く
- スケジュールの方針は4つある
  - 普通の方針: `eml run` の既定である。監視のスレッドの `PREEMPT` で、刻みごとに切り替える
  - 逐次 (`--sched sequential`): タスクが待つときだけ切り替え、横取りしない。`par` では左の子を終えてから右の子を動かす。`RunStats` を固定するテストとベンチの既定である
  - seed で決まる方針 (`--sched seeded:<n>`): seed で決めた安全点の数で切り替え、実行待ちから次のタスクを seed で選ぶ。テストに使い、失敗したときは seed を表示して再現できるようにする
  - 救済を強いる方針 (`--sched rescue-always`): N が 2 以上で使う。監視の判定によらず、起こしたタスクをいつも別の worker が救済する。同じタスクを待つたびに救済し直すことがあり、そのたびに印を付ける。救済の道の検査に使うテストのための方針である
- タスクは、yield の状態がなしの安全点でだけ切り替える。そのため、切り替えで退避する実行の文脈は `evv` だけである。`par` の子は `evv` を空 (`()`) にして始め、evidence は子をまたがない
- 実行を止める情報 `Control` (止める理由のビットを持つ止める語、確保量、上限、終わりの欄) は run に1つで、どの worker の `Ctx` とヒープも `Arc` で共有する。確保量は、worker ごとのヒープが取ったページを足し合わせた量になる ([オブジェクトモデル](../spec/object-model.md) の「実行文脈 `Ctx`」)。出力とファイルを扱う Host も run に1つで、どの worker の `Ctx` も同じ Host を `Arc` で共有する。Host は1行をロックの中で書くので、worker の出力は行の途中で混ざらない ([オブジェクトモデル](../spec/object-model.md) の「extern」の「Host」)
- 監視のスレッドと受け箱は1つの worker でも動く。N = 1 でも、監視のスレッドの横取りと、`Control` の止める語を worker の止める語へ写すことを確かめられる

### ネイティブの並列

ネイティブのコードでは、どの worker も自分の `Ctx` を持って `eml_enter` から eml のクロージャに入る。join では待たずに手伝い、`Async.run` ではループを入れ子にする。致命的な誤りは上の「止める手順」で止める。詳細は [ネイティブ化の設計](native.md) の「並列の実行」にある。

## テスト

並列化では次の方針でテストする。テスト全体の方針は [テスト戦略](../implementation/testing.md) にある。どのテストも1秒以内に終わり、結果がマシンの速さによらない。刻みはテストの刻みの源で進める。

- 共有の経路 (今の `eml_rt`): `share`、負の RC の `dup` と `decref`、最後の参照での解放、共有した物体を reuse しないこと、所有者の検査を、`eml_rt` の単体テストで確かめる。`unsafe` の核を含む `eml_rt` 全体を Verus で証明し、証明は1つのスレッドの逐次の実行を扱う。atomic の操作は信頼する部分 (信頼の一覧の T2) で、Miri が2つのスレッドのテストで確かめる ([テスト戦略](../implementation/testing.md) の「`eml_rt` の検証」)
- `par` を1つの worker で動かす段階: `run` と `run-fail` の UI テストを `--sched sequential` と2つの seed で走らせ、出力がバイト単位で一致することを確かめる。seed で走らせると、どちらのタスクが最後に `decref` するかと、タスクの中断、再開、join の待ちも確かめられる。失敗したテストは seed を表示し、その seed で再現できる。`RunStats` は `--sched sequential` で固定する。負の試験として、fork の印付けを外すと `WrongOwner` に、join の移し戻しを外すと `TransferLeak` になることを確かめる (multicoretests の負の試験に当たる)。ほかに、`poly` で作った `Lin` の物体が rc == -1 で届くこと (検査モード)、実行時エラーの優先の規則 (上の「`par` の意味」)、右を先に動かすスケジュールでの `try_map` のいちばん左の `Err`、粒度を変えても `fold` の浮動小数が同じビットになること、ほかで共有した箱の要素を `for_mut` すると印が付き、一意なら付かないことと、一意な要素を書き換えても子と親のどちらでも `WrongOwner` にならないこと (検査モード) を確かめる
- `Async`: [非同期の設計](async.md) の「テストと決定性」に従う。`tests/ui/run/async/` は N = 1 で `--sched seeded:<n>` を既定にし、どの seed でも同じ出力を返す。N が 2 以上の `--sched rescue-always` で、検査モードの漏れと所有者の検査を流す。すべての worker が待っている run に試しの `SIGTERM` を送ると、`Signal.wait` で待つタスクに届き、待つタスクがなければ 143 で終わることも確かめる。CPU を使い続けるタスクがあっても、ping-pong の組がテストの刻みの1つごとに決まった回数以上やりとりすること、`Control` を読まない worker が割り込みを1刻みのうちに見ること、漏れの検査が受け箱の語を見ることも確かめる
- 複数の worker: N = 1 のスナップショットはそのまま保つ。`par/` を N が 2 と 8 で走らせ、浮動小数の `fold` も含めて N = 1 と比べる。`async/` は順によらないものだけを N が 2 と 8 で流す。`RunStats` は逐次でだけ固定する。ほかに次のものを使う
  - 救済: worker 1 でブロックする extern を動かし、その受け箱に `Place` と `Wake` を残しても、テストの刻み3つのうちに救済されることを確かめる。印を付けずに救済すると救済した worker で `WrongOwner` になることを負の試験で確かめる
  - 手伝い: 深くて偏った `par` の木が手伝いを入れた N = 2 で終わること (進むことの試験)
  - Verus: 今の逐次の証明 (信頼の一覧の T0) を並行の証明に置き換え、印付けと公開、両側からの `dup` と `decref` (共有の側の2つの境目の並行の議論を含む)、最後の解放、join の手順を証明する。vstd の atomic は SeqCst だけを扱うので、Relaxed と AcqRel の順序の正しさは Verus では確かめられない。順序は文書の議論と Miri に任せる ([テスト戦略](../implementation/testing.md) の「Verus」)。`eml_sched` は Verus の外にある
  - Miri: `eml_rt` の `trusted` の module と `eml_sched` の並行のテスト (strict provenance、many-seeds)。遠隔の空きリストへの返却と取り込み、deque、受け箱の受け渡し、rc の裏返し、範囲への書き込みを確かめる。`par` を使う小さい UI テストを VM ごと走らせる
  - TSan: VM で `par/` の UI テストを走らせる。RC の語の誤りは見えず、フィールドの競合として結果だけが見えることを前提にする
  - work stealing の deque は自作し、スロットを atomic の語にして、crossbeam-deque の意図的な競合を避ける
  - 試験ごとに新しいプロセスとタイムアウトで動かすストレス試験
- 回復: `Async.run` の中の実行時エラーの後の回復と、N 個のヒープでの回復を確かめる

## 未決の論点と将来の拡張

- **`par` の子の取り消し**: 既定は入れず、すべての子の完了を待つ。左の子が中断したときに長い右の子を止めたいとき、または `compute` の周りの `timeout` をすぐに戻したいときに入れる。入れるときは、右の兄弟だけを取り消し (`try_map` と同じ規則)、安全点で協調的に中断し、中断した子の `Lin` の値を `drop k` と同じ後始末の情報で解放する。それまでも、子の実行時エラーは上の「`par` の意味」の左を先にする規則で報告する。残る論点は、N が 2 以上で `debug_heap` が報告するリークと不変条件の違反を、スケジュールによらず同じ内容で出すことである
- **逐次実行と同じ意味の `par_ordered`**: 任意の row を許し、右の子を最初の perform まで投機的に実行する。意味は逐次実行と完全に一致する。「perform の手前で止まる」プリミティブが実行系の核に必要になる。既定は作らない。`never` でない操作を持つ子を逐次と同じ意味で並列に動かしたいときに考える
- **`par` の子から `IO` とすぐに再開する操作を外に出す**: Kind の束の `Never` と `Once` の間に `Tail` を挿入する案。`IO` の extern の関数は handler を通らずにその場で実行するので、子のスレッドでもそのまま実行できる。ただし、IO の失敗は最も近い `try_io` まで中断し、`exit` は実行の底まで中断する ([VM](../spec/vm.md) の「extern の中断」)。子でこれが起きると中断が子をまたぐので、子の底を中断の境目にし、`try_io` と `exit` が子をまたぐ意味を決める必要がある。それまでは、`exit` が `<IO>` を持つことで、`par` の子から `exit` を呼べない ([標準ライブラリ](../spec/stdlib.md) の「`exit`」)。ユーザー定義の操作にはエフェクトの宣言に「すぐに再開する操作」の種類 (`tail`、Koka の `fun` に当たる) を足し、子から外に出る操作を `par` ごとのロックで直列化する。どちらの場合も、子どうしの `IO` と操作の順序は非決定的になる。後から挿入しても既存の制約 (`σ ≤ Never`、`σ ≤ Once`) の意味は変わらず、受け付けるプログラムが増えるだけである。既定は入れない。子からの出力が `both` で足りないときに考える
- **`fork` と `join` を普通の関数として公開すること**: 既定は公開しない。`par` と集まりの関数で足りる。不規則な並列が要るときに考える
- **Float の箱を要素ごとに作らないこと**: `Par.tabulate_floats` の関数の結果の `Float` は要素ごとに箱になる。案は2つある。結果の型の付いたクロージャの入口 (`f$ret`) か、1次のループで書く葉の範囲のプリミティブである。`std/Par` の集まりの関数を入れるときに、固定した `RunStats` の行で測って決める
- **private deque**: 印付けを実際に盗まれた子だけに限る最適化 (Acar らの方式)。既定は入れない。共有の集合がスケジュールに依存し、固定した `RunStats` が崩れるためである。印付けがプロファイルで目立つときに考える
- **ロックフリーの受け箱と channel**: 既定は mutex で、Miri で確かめられる。N が 8 以上で競合を測ったときに、同じ口の後ろで替える
- **タスクを置く worker の選び方**: 既定は置ける worker を順に回す。偏りを測ったときに、実行待ちと待ちの集まりのいちばん短い worker を選ぶ形にする
- **ページを OS に返すこと**: 既定は返さず、RSS は worker のヒープごとの最大の和である。サーバの RSS が育ち続けるときに考える
- **待ちのタスクが持つメモリを数えること**: 既定は、タスクが動く間の確保だけを数える。柔らかい上限が違うタスクを選ぶときに考える
- **監視と救済の値**: 既定は、監視の刻みが 10 ms、詰まったとみなすのが2刻み、過負荷のしきい値が 64、プールの上限が 32、遠隔のリストを取り込むしきい値が 256、粒度が 1024 である。救済は盗めるものの半分を、古いものから取る。どれも段ごとの計測で決める
- **ネイティブの `Async.run` の入れ子**: 入れ子の順が逆になりうる。既定は許し、文書に書く。`Async.run` は `main` から呼ぶのがよい
- **Windows のブロックするコンソールの読み**: 既定は、割り込みを読みが戻った後で見る
- **worker 0 のほかの worker でのその場の同期の読みへの割り込み**: SIGINT は worker 0 のほかのスレッドで塞ぐので、そうした worker でその場の `Stdin`、`FileIn`、`Child` の読みをしているタスクには `EINTR` が来ない。入れるときの既定は、`INTERRUPT` を見た監視のスレッドがその場の同期の読みの中にいる worker へ `pthread_kill` でシグナルを送って `EINTR` を起こす形である。入れるまでは、そうした読みはデータが来たときにだけ戻り、止める手順の join もそれまで待つ
- **`poly` の物体のビットの実行時の伝播**: `poly` の `con` でフィールドの `lin` ビットの OR を取り、実行時に伝える案。`MutArray` は要素を `Unr` に固定しているので決めていない。`Lin` の要素を持つ配列を入れるときに決める
- **読むだけの共有**: OxCaml は、`par` の子が親の環境を読めるが書けない形を持つ。eml の `par` の子は親の `Ref` を読めない。表現力の不足として現れたときに検討する
- **局所的な可変変数**: エフェクトで作る `var` としてある ([式](../spec/expressions.md) の「`var`」)。変数の値は地点ごとのエフェクトの handler が持ち、可変参照と `Heap` には依らない
- **`IO` が大域的な領域を含む折衷案**: Koka のように `IO` が `Heap Global` を含む形。便利だが、大域的な領域の読み書きには同期が必要になる。必要になったら検討する
- **「`Heap` を含まない row」の制約**: 子タスクの row を多相に開いたまま `Heap` だけを除外できると、並行処理の API の柔軟性が上がる。[ロードマップ](roadmap.md) の「型システム」にある「row 要素ごとの捕捉 Kind」と同じ種類の拡張として扱う
