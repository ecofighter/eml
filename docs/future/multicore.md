# マルチコア対応の設計

位置づけ: 将来の設計。

VM とネイティブのランタイムで、複数のコアを使って実行するための設計をまとめる。マルチコア対応は実装していない。VM はシングルスレッドで、後から並列にできる制約を守る (下の「VM の並列化の備え」)。VM の並列化は、ネイティブ化とは別の項目にする (下の「VM とネイティブのランタイム」)。今の実装に入れてある備えは、row の Kind の束の `Never` ([型と Kind](../spec/types.md)) と、持ち越し規則の制約を `σ ≤ Once` と書くこと ([エフェクトと handler](../spec/effects.md)) のほかに、`eml_rt` の共有の印方式の RC (`share`、負の RC、共有した物体を reuse しないこと。下の「スレッドをまたぐ RC」)、検査モードの所有者の検査、`CodeBase<M>: Sync` と `Task: Send` の型の assert (下の「VM の並列化の備え」) である。

## 目的と範囲

### 目的

- VM とネイティブのバックエンドで、複数のコアを使って実行できるようにする
- 並列の安全性 (共有の印付け、別のスレッドからの解放、下の「不変条件」) を、ネイティブ化を待たずに VM の実装で確かめる。VM の並列化では、速さよりこちらを重視する
- 「線形型 × 代数的エフェクト」の性質 (`Lin` による移動、row によるエフェクトの制限) を、並列の安全性の保証にそのまま使う

### 対象

- 決定的な並列計算: データ並列に限る。`par`、並列 map / reduce、分割統治
- 並行処理: 軽量スレッド、非同期 I/O

### 対象外

- 共有の可変状態を伴うマルチスレッド。Rust の `Send` / `Sync` に当たる Kind の次元は導入しない
- 並列タスクから `IO` を使うことと、ユーザー定義の再開する操作を外に出すこと (下の「未決の論点と将来の拡張」の a4)

## 確定した設計判断

| # | 領域 | 決定 |
|---|---|---|
| 1 | 層の構成 | 実行系の核は、並列実行、スレッド間で安全な RC、移動できる `once` 継続、atomic プリミティブ、fork / join の節点を提供する。決定的な並列計算と並行処理は、その上のライブラリとして作る |
| 2 | 可変状態 | 可変状態はエフェクトの中でだけ扱う。並列の安全性は row の制限で保証する |
| 3 | `Ref` と `Heap` | 値 `Ref h a` (`Unr`) と組み込みのエフェクト `Heap h` を持ち、`IO` とは分離する。`run_heap` は rank-2 の組み込みとして特別扱いし、ユーザーには rank-2 を書かせない。multi-shot で再開したときの状態は共有する |
| 4 | `Ref` の中身 | `Ref` には `Unr` の値だけを入れる。`Lin` を `Unr` に変える汎用の操作は作らない |
| 5 | RC | 共有の印方式 (Koka、Lean 4 と同じ)。符号付きの `AtomicI32` で、正なら局所、負なら共有。局所的なオブジェクトには Relaxed の load / store を使う。共有の印の付いた物体は reuse しない |
| 6 | VM | シングルスレッドで出し、後から並列にできる制約 (下の「VM の並列化の備え」) を守る。VM の並列化は、ネイティブ化とは別の項目にする。その前に、`par` の a1 をシングルスレッドの協調的マルチタスクとして入れるかを判断する ([ロードマップ](roadmap.md) の「マルチコア対応」) |
| 7 | 共通ランタイム | オブジェクトの形 (記述子)、RC の符号の規約、ヒープの実装方式、共有の経路 (印付けと負の RC) は、共通ランタイム `eml_rt` で決め、VM とネイティブで共有する ([オブジェクトモデル](../spec/object-model.md))。ヒープの実装方式は、64 KiB のページから切り出す自前の確保器である ([オブジェクトモデル](../spec/object-model.md) の「確保器」)。RC の方式そのものは 5 で決めてある。別のスレッドからの解放に対応したアロケータは、VM の並列化かネイティブのランタイムのうち先に来るほうで決める。実行時の検査は、`eml_rt` の検査モードが受け持つ ([オブジェクトモデル](../spec/object-model.md) の「検査モード」) |
| 8 | 並列 API | `par` はデータ並列に限り、子タスクの row は `e : Row<Never>` (`never` の操作だけ) とする。a1 → a2-wait → a2-cancel と段階的に広げる。row の Kind の束は `Never ≤ Once ≤ Multi`。並行処理は閉じた row の `spawn` にする |
| 9 | 不変条件 | スレッドをまたいで値や制御を渡すプリミティブは、すべて閉じた row か `Row<Never>` の制約を持つ |
| 10 | 共有の印付け | 実行系のプリミティブが、送り手のスレッドで、公開する前に自動的に行う。`par` では fork と join で、worker の数によらず必ず行う |
| 11 | スレッドに縛られたリソース | 組み込みのリソースは、スレッドに縛られないものに限る。スレッドに縛られたものは、専用のスレッドの handler に閉じ込める |
| 12 | `Lin` の物体 | `Lin` の値は move だけを許し、物体の RC は常に 1 である。スレッドをまたぐときは印を付けず、所有者を移す |

## 層の構成

```
ライブラリ:     並列計算 (par / par_map / par_try_map / both)    並行処理 (Async の handler、spawn、channel)
               ────────────────────────────────────────────────────────────
実行系の核:     並列実行 (worker の起動と join)
               スレッド間で安全な RC (共有の印方式)
               移動できる once 継続
               atomic / CAS のプリミティブ
               fork / join の節点 (perform が認識する)
               協調的な中断 (a2-cancel 以降)
型システム:     row の Kind による制限 + Lin による移動
```

- work stealing などのスケジューラは、エフェクトと `once` の継続を使ってライブラリとして書く。タスクの中断は perform で、別のコアでの再開は継続の移動で表す
- 先行例として、OCaml 5 は、実行系が `Domain` とエフェクトだけを提供し、並列の task pool (Domainslib) と並行 I/O (Eio) をライブラリとして作っている。Haskell の monad-par は、決定的な並列計算をライブラリとして作っている

## 可変状態

### API

```
new      : a -> <Heap h> Ref h a              (a : Type<Unr>)
get      : Ref h a -> <Heap h> a
set      : Ref h a -> a -> <Heap h> Unit
run_heap : (forall h. Unit -> <Heap h | e> a) -> <e> a
```

- `Ref h a` は `Unr` の値で、データ構造に入れたり、関数に渡したりできる。読み書きの権限は row の `Heap h` が管理する
- `run_heap` は組み込みとして型検査器で特別扱いする。rank-2 の型をユーザーに書かせることはしない。今の型推論の方針 (rank-1 + bidirectional) は変えない
- `new` は `a : Type<Unr>` を要求する。シグネチャの型変数で使った場合は、[線形性](../spec/linearity.md) と同じ仕組みで `Unr` の制約が加わる
- 実装は実際の可変メモリにする。`Heap h` は組み込みで、実際のメモリなので、multi-shot で再開したときの状態は**共有**される (Koka と同じ意味)

### `IO` と分離する理由

- 局所的な可変状態を外から消せる: 内部で `run_heap` を使う関数の型は純粋なままになり、並列タスクに渡せる
- 型が決定性を区別する: `<>` は純粋、`<Heap h>` は状態があるが決定的、`<IO>` は外の世界に触れて非決定的である
- 読み書きに同期が要らない: 下の「不変条件」により、`Heap h` の操作は `run_heap` を実行したスレッドでしか実行されない。`get` / `set` は atomic でない普通のロードとストアで済む
- 領域ごとに独立している: 並列タスクがそれぞれ内部で `run_heap` を使っても、互いに干渉しない

並行タスクの間で共有する可変状態 (例えば非同期のタスク同士で共有するカウンタ) は、`Heap` では書けない。channel や atomic な参照などの並行処理用のプリミティブを、`IO` か `Async` の側に用意して扱う。

### `Lin` の値を `Ref` に入れない場合の書き方

| やりたいこと | 書き方 |
|---|---|
| `Lin` の値を書き換えたい | `Ref` を使わず、値を線形に受け渡す。一意なので、Perceus の reuse でその場の書き換えにコンパイルできる (例: `Lin` の `MutArray` の `write : MutArray a -> Int -> a -> MutArray a`)。`MutArray` を `var` に入れれば、受け渡しを書かずに `a[i] <- e` と書ける。変数の状態は handler が持ち、受け渡しは状態を渡す形の特殊化が作る |
| 一つのリソースを色々な場所から使いたい | リソースを handler に持たせる。handler が所有して操作を提供し、`return` 節で後始末する。構文としては [式](../spec/expressions.md) の「パラメータ付き handler」が基本になる |
| 一意性だけが理由の `Lin` (後始末のない可変バッファなど) を、使い終わったら共有したい | 型ごとに `freeze` を用意する (例: `freeze : MutArray a -> Array a`)。後始末を持つ型には定義しない |

- 汎用の「`Lin` → `Unr`」の変換は作らない。`File` などが複製できてしまい、二重の後始末を防げなくなるため。また、RC が 0 になったときに後始末する方式は、「通常の制御フローでは暗黙の後始末を行わない」という決定 ([線形性](../spec/linearity.md)) に反する
- `Lin` の `MutArray` を重ならない部分に分けて、別々のタスクに移動して並列に書き換え、最後に結合する (Rust の `split_at_mut` に相当)。この処理はエフェクトを使わない純粋な計算なので、a1 の `par` の範囲で書ける。速く動かすには Perceus の reuse analysis が前提になる

## スレッドをまたぐ RC

### オブジェクトがスレッドをまたぐ場面

1. 並列タスクや `spawn` に渡すクロージャが捕まえた値
2. channel などで送る値
3. 別のコアで再開する継続が参照している値

`Lin` の値は move だけを許し、`Lin` の物体の RC は常に 1 である ([LIR](../spec/lir.md) の「値の表現」)。そのため `Lin` の物体には印を付けず、所有者を移すだけで済む (下の「`Lin` の物体の所有者の移し替え」)。ただし、`Lin` な構造の中にある `Unr` のフィールドはスレッドをまたぐ。

### 共有の印方式

```rust
// 局所 (正の値): Relaxed の load/store は、x86 でも ARM でも普通の mov になる
let n = rc.load(Relaxed);
if n > 0 { rc.store(n + 1, Relaxed) }
// 共有 (負の値): 本物の atomic 操作
else     { rc.fetch_sub(1, AcqRel); }
```

- オブジェクトは最初は局所的で、RC の操作は普通の加減算と同じ速さになる。代わりに、RC 操作ごとに印を確認する分岐が1つ増える
- 上の3つの場面で、渡す値から到達できるオブジェクトをたどって共有の印を付ける。すでに印のあるオブジェクトでたどりを止めるので、各オブジェクトがたどられるのは高々1回である
- **印付けは送り手のスレッドが、公開する前に行う**。受け手が印を付けると、送り手がまだ同じオブジェクトに対して atomic でない RC 操作をしている可能性があり、data race になるため
- 印付けは、下の「不変条件」に挙げる実行系のプリミティブの中で自動的に行う。ライブラリの作者が印付けを忘れることはない
- 共有したオブジェクトは、別のスレッドで RC が 0 になって解放されることがある。並列に動かす実行系のアロケータは、別のスレッドからの解放に対応している必要がある (Koka は mimalloc を使っている)
- 共有の印の付いた物体 (RC が負) は、RC の値によらず reuse しない。Lean 4 の `lean_is_exclusive` と Koka の `kk_block_drop_reuse` と同じ規則である。Perceus の reuse の判定は、局所の RC が 1 かどうかだけになる。join の後に共有の物体を局所へ戻す最適化 (Koka は最後の共有の drop で 0 に戻す) も、検証の手段がそろうまで入れない

### 却下した案

- 常に atomic にする (Swift、Rust の `Arc`): シングルスレッドのプログラムでも、すべての `dup` / `decref` が atomic 命令になる
- Biased RC: 印付けのたどりは不要になるが、ヘッダに所有するスレッドの ID とカウンタ2つが必要で、実装がかなり複雑になる
- 型で区別する: Kind に共有の次元が必要になり、決定2に反する

### `par` の印付け

印付けをいつ行うかで、どの物体が共有になるかがスケジュールに依存するかが決まる。

| 印付けの時点 | 共有になる物体の集合 | 逐次の実行で通る経路 |
|---|---|---|
| 盗まれた時点 (private deque の方式) | スケジュールに依存する | 印付けが一度も起きない |
| fork と join の時点 | スケジュールによらず決まる | 並列のときと同じ物体に印が付く |

`par` は fork と join の時点で印を付ける。印を付けるのは次の2か所である。

- fork: 右の子の閉包から届く物体。rayon の `join` と同じく、別の worker に渡りうるのは右の子だけで、左の子は親の worker で動く
- join: 右の子の結果から届く物体。右の子の worker が、公開する前に付ける

印付けは `par` の実行時の意味の一部で、検査モードだけの動作ではない。共有した物体は reuse しないので、共有の集合が決まれば reuse の判断も決まる。そのため、逐次と並列で `RunStats` の作業の回数が一致する (`peak_objects` は除く)。下の「継続の移動と不変条件」の、work stealing のキューに入れた時点で印を付けるという決定と同じ考え方である。代償は、シングルスレッドの VM でも `par` に渡したデータが atomic の RC になり、reuse されなくなることである。シングルスレッドの `par` には速さの目標がないので、受け入れる。

### 論理的な worker ID

物理的な worker が1つだと、所有者の検査で全物体が同じ所有者になり、何も検出しない。そこで worker ごとの `Heap` に論理的な worker ID を持たせる ([オブジェクトモデル](../spec/object-model.md) の「論理的な worker ID」)。

- 逐次の `par` は、左の子を親の ID のまま実行し、右の子を新しい ID で実行する
- 右の子が確保した物体の所有者は、右の子の ID である
- 検査モードのヘッダは所有者 ID を持つ。Relaxed の `AtomicU32` にする。正の RC の物体への `dup`、`decref`、フィールドの書き込み、reuse のたびに、所有者が今の ID と一致するかを確かめる

fork で印を付け忘れた物体に右の子が触れると、所有者が親の ID なので、検査は必ず失敗する。スケジュールに依存せず、`par` を使うすべての UI テストで毎回確かめられる。Lean 4 と Koka は eml と同じ符号の規約を使うが、どちらも印付けの漏れを直接見つける仕組みを持たない。局所の経路を `AtomicI32` の Relaxed で書くと、印を付け忘れても言語のメモリモデルの上ではデータ競合にならず、Miri、TSan、loom のどれも直接は報告しない。直接効く先例は、CPython (PEP 703) の `ob_tid` のような所有者の記録である。

逐次の実行で確かめられるのは論理の誤りまでである。公開するときの順序 (Release と Acquire)、2つのスレッドからの同時の `decref`、deque の正しさは、本物のスレッドでしか現れない (下の「テスト」)。

### `Lin` の物体の所有者の移し替え

- ヘッダに `lin` のビットを、検査モードに限らず常に持つ。`File` などの extern の資源は作るときにビットを立て、`con` と `closure` は静的な Kind の印が `lin` のときに立てる ([オブジェクトモデル](../spec/object-model.md) の「`lin` ビット」)
- fork の印付けのたどりは、ビットの立った物体には印を付けず、所有者を移す。中の `Unr` のフィールドには印を付ける。これで、共有した物体を reuse しない規則のもとでも、`Lin` の `MutArray` を分けて子でその場で書き換える形が成り立つ
- `poly` のコードで作った `Lin` の物体はビットを持たないので、fork で共有になり、その場の書き換えができなくなる。安全の側に倒れるだけである

## 並列と並行の API

### row の Kind

```
row の Kind: Row<s>,  s ∈ { Never ≤ Once ≤ Multi }
  Never : never の操作だけを含む row
  Once  : さらに once の操作 (extern のエフェクトの IO を含む) を含んでよい
  Multi : さらに multi の操作を含んでよい
```

- `par` の子タスクの row を `e : Row<Never>` に制限する。`IO`、`Heap h`、`once` / `multi` の操作は除外される
- 今の実装は、内部の Kind の束を3要素で用意する (`Never` を最初から入れておく)。規範は [型と Kind](../spec/types.md) にある

### 子タスクに `never` の操作だけを許す理由

- 一般の handler は並列と組み合わせられない: `once` / `multi` の handler は、状態を handler の実行ごとの evidence に、計算の続きを継続のクロージャに持つ。例えば [エフェクトと handler](../spec/effects.md) の `run_state` の節 `| fn get () st -> (st, st)` の状態は、操作が起きるたびに evidence から節に渡り、その場で evidence へ戻る ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。二つの子タスクがこうした操作を同時に perform すると、どちらの節の `k` に計算の続きを返すかが決まらない
- `never` の操作は再開しない: handler の節は、子をすべて片付けた後に、親のスレッドで1回だけ実行すればよい。節が並行に走ることがないので、ロックも、子のスレッドから親のフレームをたどる処理も要らない
- データ並列にはこれで足りる: データ並列の処理は、もともと純粋な関数と、失敗の通知 (`Fail` のような `never` のエフェクト) で書ける

### `par` の段階

| 段階 | 型 | エフェクトの意味 | 必要なもの |
|---|---|---|---|
| a1 | `par : (Unit -> <> a) -> (Unit -> <> b) -> (a, b)` | なし | spawn / join |
| a2-wait | `par : (Unit -> <e> a) -> (Unit -> <e> b) -> <e> (a, b)`、`e : Row<Never>` | 全員の完了を待ってから、一番左の子の例外を親で投げ直す | Kind の束、fork / join の節点、例外の値をスレッド間で渡す仕組み、実行時に記述子から行う drop |
| a2-cancel | a2-wait と同じ | 左の子が例外を投げたら、右の子を中断する | 協調的な中断と、中断した子の `Lin` の後始末 |

- どの段階に進んでも、`par` が受け付けるプログラムが増えるだけである。後の段階に進んでも既存のコードが通らなくなることはない
- **`par` は常に決定的**である。子タスクは外の世界に触れず、例外は左の子を優先するので、結果は実行のスケジュールに依存しない
- a2-cancel では、`par f g` の意味は逐次実行の `(f (), g ())` と完全に一致する
  - 左の子が例外を投げたら、右の子の結果は使われないので中断する
  - 右の子が先に例外を投げても、左の子の完了を待つ。左の子が例外を投げればそちらを優先し、正常に終われば右の子の例外を投げ直す
  - 左の子が停止しなければ、逐次実行と同じく `par` も停止しない
- a2-wait では、左の子が例外を投げて右の子が停止しない場合、逐次実行なら例外で終わるはずのプログラムが止まらない。逐次実行と異なるのはこの点だけで、a2-cancel で解消する
- 捨てる側の子の結果が `Lin` の場合、`par` は型について多相なので、実行時にオブジェクトの記述子から破棄処理を引いて drop する。`eml_rt` の記述子は、破棄処理を持たなければならない。今の `eml_rt` は型ごとの記述子の表を持たず、破棄処理をヘッダの種類で表す ([オブジェクトモデル](../spec/object-model.md) の「ヘッダ」)
- `never` の操作が `par` から抜けるのを perform が認識する必要がある。そのため、`par` 自体は実行系の核のプリミティブ (fork / join の節点) の上に作る。スケジューラはライブラリのままである
- evidence passing の上では、`par` の子タスクの `evv` に、外側の handler の evidence の代わりに、fork の目印を指す evidence を置く。子の row は `Row<Never>` なので、子から外に出る操作は `never` の操作だけである。子の中の `never` の操作は fork の目印までタスクのスタックを巻き戻し、fork / join の節点がそれを親に渡す ([Core IR](../spec/core-ir.md) の「`never` の中断」、[VM](../spec/vm.md) の「巻き戻し」)
- 協調的な中断は、安全な地点 (perform、メモリの確保、ループの先頭など) で中断の印を確認して行う。中断した子が捕まえている `Lin` の値は、`drop k` と同じ後始末の情報で解放する

### データ並列での使い勝手

- 並列 map / filter / reduce、分割統治、`run_heap` を内部で使うアルゴリズム、分割できる純粋な乱数生成器を使う計算は、a1 で書ける
- 失敗の通知は、a2 以降は `Fail` のような `never` のエフェクトを使う。a1 の段階では `Result` で返す。「どれか1つが `Err` を返したら残りを打ち切る」処理はスケジューラ側でできるので、`par_try_map : (a -> <> Result e b) -> Array a -> Result e (Array b)` のような関数をライブラリで用意する
- 子タスクの中ではデバッグ出力 (`println`) ができない。代わりに、`par` と同じ形の逐次版をライブラリに用意する。デバッグするときだけ `par` を `both` に書き換えれば、子の中で `println` できる

  ```haskell
  both : (Unit -> <e> a) -> (Unit -> <e> b) -> <e> (a, b)    -- 逐次実行。任意の row を許す
  ```

- row に現れない `trace` のような抜け道は用意しない

### すぐに再開する handler の最適化

handler の節が `k v` を末尾で1回だけ呼ぶ場合、継続を取り出さない直接の呼び出しにコンパイルできる (Koka や evidence passing の主要な最適化)。これは並列とは関係なく、コンパイラが handler ごとに Core IR の形から判定する。エフェクトの宣言に操作の種類を追加する必要はない。evidence passing で実装している ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。

### 並行処理

```
spawn         : (Unit -> <IO, Async> Unit) -> <Async> Unit
run_scheduler : (Unit -> <Async, IO> a) -> <IO> a
```

- 並行処理はもともと非決定的なので、子タスクの row を閉じて `IO` を許す
- `IO` は extern のエフェクトで、各 worker が `IO` を起こす extern の関数をその場で実行する。ただし、IO の失敗は最も近い `try_io` まで中断し、`exit` は実行の底まで中断する ([VM](../spec/vm.md) の「extern の中断」)。子タスクに `IO` を許す前に、この中断をタスクの中にとどめる必要がある。例えば各タスクの底を中断の境目にし、タスクをまたぐ `try_io` と `exit` の意味 (子の `exit` で何が終わるか、親の `try_io` が子の失敗を捕まえるか) を決める
- ユーザー定義のエフェクトは、子タスクの中で handle し終えている必要がある (OCaml 5 の Eio と同じ扱い)
- `Heap h` は閉じた row によって除外される
- 並行処理のための新しい構文は追加しない。ラムダと `use` で書ける ([式](../spec/expressions.md) の「並行処理」)

## 継続の移動と不変条件

### 不変条件

> スレッドをまたいで値や制御を渡す実行系のプリミティブ (spawn、`par` の fork、channel、スケジューラのキュー) は、すべて閉じた row か `Row<Never>` の Kind 制約を持つ。したがって、`Heap h` の操作は `run_heap` を実行したスレッドでしか実行されない。

新しいプリミティブを追加するときは、この不変条件を満たすことを確認する。

### `once` の継続の移動

- 非同期のスケジューラでは、`await` したタスクの継続 `k` (`once`、`Lin`) を handler がキューに入れ、別の worker が `k` を呼んで再開する
- `k` の続きに `Heap h` の操作があれば、`k v` の row (handle 式の外側の row) に `Heap h` が現れる。キューや `run_scheduler` の型は閉じた row なので、そのような `k` はキューに入れられない (型エラー)
- 移動するときは、送り手が継続から到達できるオブジェクトに共有の印を付ける。evidence passing の継続はクロージャの列なので ([Core IR](../spec/core-ir.md) の「継続の組み立て」)、継続のクロージャから届くオブジェクトをたどる。一度移動した継続のクロージャにはすでに印が付いているので、次に移動するときは、その後に足したクロージャだけをたどればよい
- work stealing のキューは常に盗まれ得るので、キューに入れた時点で印を付ける。その代償として、移動しない継続も atomic な RC になる。印付けを実際に移動するものだけに限る private deque 方式 (Acar らの方式) は、将来の最適化とする

### `multi` の継続の並列な再開

```haskell
| ctl choose () k -> par (fn () -> k True) (fn () -> k False)
```

- [エフェクトと handler](../spec/effects.md) の持ち越し規則により、`multi` の操作をまたいで `Lin` の値は生きていない。`k` が捕まえているのは `Unr` の値だけなので、共有しても安全である
- `k` の続きのエフェクトは、上のラムダの row として `par` の制約 (`Row<Never>`) で検査される。新しい仕組みは要らない。続きが `never` 以外の操作を含む場合は、並列に再開できない

### スレッドに縛られたリソース

- 組み込みのリソースは、どのスレッドで後始末してもよいものに限る (現状の `File` はこれを満たす。閉じる処理は Rust の値の drop glue だけである。[オブジェクトモデル](../spec/object-model.md) の「extern」の「読み手」)
- スレッドに縛られたリソース (GUI のハンドル、スレッドに局所的なライブラリの状態など) が必要になったら、専用のスレッドの handler に閉じ込める (上の「`Lin` の値を `Ref` に入れない場合の書き方」の、リソースを handler に持たせる方式)。Kind に共有の次元は足さない

## VM とネイティブのランタイム

- VM とネイティブは、共通ランタイム `eml_rt` を使う ([オブジェクトモデル](../spec/object-model.md))。共有の印方式の RC (上の「スレッドをまたぐ RC」) は、`eml_rt` に入れ、両方で使う。実行時の検査は、`eml_rt` の検査モードが受け持つ
- VM はシングルスレッドで出している。VM の並列化は、別の項目にする
- VM で並列化していないのは、並列化と性能の両方を一度に詰めることになるためである

### VM も並列にする理由

並列化をネイティブのランタイムだけで行う案は、次の2点から採らない。

- **混在実行と両立しない**。`FnEntry` で VM とネイティブのコードを混ぜて動かすと、ネイティブの標準ライブラリの `par_map` が、ユーザーのバイトコードの閉包を worker のスレッドで呼ぶ。VM がスレッドをまたいで使える作りでなければ、混在させた `par` を順に実行するしかなくなる
- **確かめる時期が遅い**。ネイティブ化は、ロードマップで言語の項目より後に置いてある。共有の印付け、別のスレッドからの解放、上の「不変条件」は、それまで実装で確かめられない

VM を並列にする費用は小さいと見積もっている。evidence passing で継続はヒープのクロージャになり、実行の文脈 (`evv` と yield の状態) は `Ctx` として worker ごとに1つ持てばよい ([LIR](../spec/lir.md) の「実行の文脈」)。RC の分岐は、不死の物体 (0) を区別する比較に負の側を足すだけで済む。`par` と `run_scheduler` は構造化された並行性なので、REPL の入力の境目では worker が1つも動いていない。

### VM の並列化の備え

次の制約を守り、後から VM を並列にできるようにする。

| # | 制約 |
|---|---|
| 1 | VM の状態は `Ctx` と `Task` (呼び出しのスタックとレジスタの枠) に置き、スレッドに局所的な大域変数を持たない |
| 2 | `CodeBase` は追記だけにし、実行中は読むだけにする (`Sync`)。不死の定数は凍結した塊 `Frozen` に置くので、`CodeBase` の `Sync` は `Frozen` の `Sync` に頼る ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」) |
| 3 | 共有の経路は、`par` の fork と join で必ず通す (上の「`par` の印付け」) |
| 4 | `par` は `eml_rt` の fork / join の節点として実装し、逐次の版も1つの実装として持つ |
| 5 | VM の呼び出しのスタックは、Rust の再帰でなく、タスクが持つデータにする。extern が閉包を呼び戻す入れ子の中では、タスクを切り替えない |

- SIGINT のハンドラは `SA_RESTART` なしで入れ、待っている読みを `EINTR` で止める ([VM](../spec/vm.md) の「上限と割り込み」)。今はプロセスがほかのスレッドを持たないので、SIGINT は読んでいるスレッドに届く。worker のスレッドを持つときは、読まないスレッドで `pthread_sigmask` により SIGINT を塞ぐ

制約1と制約2の型の性質は、`Session` の `Send + Sync` の試験 (`crates/eml_cli/tests/api.rs`) と同じ形の、型の assert で固定する。`crates/eml_vm/tests/api.rs` が `CodeBase<M>: Sync` と `Task: Send` を固定している。

VM は、実行の状態をワーカーごとの `Ctx` と、タスクごとの `Task` (呼び出しのスタック、命令の位置、今のフレーム) に分けている ([VM](../spec/vm.md) の「スロットとスタック」)。`perform` で止まったタスクの続きはヒープ上の継続のクロージャになるので、このタスクを別の worker へ移すことは、クロージャの語を1つ渡すことと同じである。まだ始まっていないタスク (`spawn` に渡す閉包、`par` の右の子) も同じである。安全点で切り替えたタスクと、`join` で子を待つ親だけは、スタックの途中で止まっているので `Task` ごと持ち続ける。こうしたタスクの数は、`par` の入れ子の深さで抑えられる。

語をほかのスレッドへ公開するのは、`eml_rt` の fork、join、キューへの push の中で `share` を通す道だけにする。VM は、語をほかのスレッドに渡す経路を持たない。`Word` は `Send + Sync` なので型では守れず、文書の決まりにする。破った場合は、検査モードの所有者の検査が見つける ([オブジェクトモデル](../spec/object-model.md) の「論理的な worker ID」)。

### `par` の a1 と協調的マルチタスク

並列 VM より前に、`par` の a1 をシングルスレッドの協調的マルチタスクとして入れるかを判断する ([ロードマップ](roadmap.md) の「マルチコア対応」)。右の子をタスクにし、左の子は親のタスクがそのまま実行する。スケジューラの方針は「逐次」(既定、ベンチ用) と「乱数種付き」(テスト用) の2つである。協調的マルチタスクは「worker が1つの並列 VM」で、後の並列 VM と同じコードの経路を通る。

タスクは、yield の状態がなしの安全点でだけ切り替える。そのため、切り替えで退避する実行の文脈は `evv` だけである。a1 の子は row が `<>` なので、`evv` を空 (`()`) にして始め、evidence はタスクをまたがない。実行を止める情報 `Control` (止める語、確保量、上限) はセッションに1つで、どの worker の `Ctx` とヒープも `Arc` で共有する。確保量は、worker ごとのヒープが取ったページを足し合わせた量になる ([オブジェクトモデル](../spec/object-model.md) の「実行文脈 `Ctx`」)。出力とファイルを扱う Host もセッションに1つで、どの worker の `Ctx` も同じ Host を `Arc` で共有する。Host は1行をロックの中で書くので、worker の出力は行の途中で混ざらない ([オブジェクトモデル](../spec/object-model.md) の「extern」の「Host」)。

### テスト

並列化の段階では、次の方針でテストする。テスト全体の方針は [テスト戦略](../implementation/testing.md) にある。

- 共有の経路 (今の `eml_rt`): `share`、負の RC の `dup` と `decref`、最後の参照での解放、共有した物体を reuse しないこと、所有者の検査を、`eml_rt` の単体テストで確かめる。`unsafe` の核を含む `eml_rt` 全体を Verus で証明し、証明は1つのスレッドの逐次の実行を扱う。atomic の操作は信頼する部分 (信頼の一覧の T2) で、Miri が2つのスレッドのテストで確かめる ([テスト戦略](../implementation/testing.md) の「`eml_rt` の検証」)
- `par` の a1: `run` と `run-fail` の UI テストを、逐次と乱数種付きの2つの方針で走らせ、出力が一致することを確かめる。検査用のフラグで印付けを1か所外したとき、どれかの試験が必ず失敗することを確かめる (multicoretests の負の試験に当たる)。実行時エラーの優先の規則を `run-fail` の UI テストにする
- VM の並列化: 本物のスレッドで、UI テストを逐次、N 個の worker、乱数種付きで走らせ、逐次のスナップショットと比べる。`RunStats` は逐次でだけ固定する。ほかに次のものを使う
  - Verus: 今の逐次の証明 (信頼の一覧の T0) を並行の証明に置き換え、印付けと公開、両側からの `dup` と `decref` (共有の側の2つの境目の並行の議論を含む)、最後の解放、join の手順を証明する。vstd の atomic は SeqCst だけを扱うので、Relaxed と AcqRel の順序の正しさは Verus では確かめられない。順序は、文書の議論と Miri に任せる ([テスト戦略](../implementation/testing.md) の「Verus」)
  - Miri: `eml_rt` の `trusted` の module の並行のテスト (strict provenance、many-seeds)。`par` を使う小さい UI テストを VM ごと走らせる
  - TSan: VM で `par` の UI テストを走らせる。RC の語の誤りは見えず、フィールドの競合として結果だけが見えることを前提にする
  - work stealing の deque を自作するなら、スロットを atomic の語にして、crossbeam-deque の意図的な競合を避ける
  - 試験ごとに新しいプロセスとタイムアウトで動かすストレス試験
- 並行処理 (`spawn`) を本物のマルチコアで動かすと出力の順序が変わり、スナップショットが安定しない。並行処理を動かすテストは、シードを固定した決定的なスケジュールで流す

## 未決の論点と将来の拡張

- **並列タスクからすぐに再開する操作を外に出す (a4)**: `IO` とユーザー定義の操作を子タスクから使えるようにする案。Kind の束の `Never` と `Once` の間に `Tail` を挿入する。`IO` の extern の関数は handler を通らずにその場で実行するので、子のスレッドでもそのまま実行できる。ただし、IO の失敗は最も近い `try_io` まで中断し、`exit` は実行の底まで中断する ([VM](../spec/vm.md) の「extern の中断」)。子でこれが起きると中断がタスクをまたぐので、`par` の子の row の上限を `Never` から `Tail` に広げて `IO` の分類を `Tail` に下げるだけでは足りない。中断をタスクの中にとどめる必要があり、例えば各タスクの底を中断の境目にし、タスクをまたぐ `try_io` と `exit` の意味 (子の `exit` で何が終わるか、親の `try_io` が子の失敗を捕まえるか) を決める。extern の呼び出しそのものを外に出す仕組みは要らない。それまでは、`exit` が `<IO>` を持つことで、`par` の子から `exit` を呼べない ([標準ライブラリ](../spec/stdlib.md) の「`exit`」)。ユーザー定義の操作には、エフェクトの宣言に「すぐに再開する操作」の種類 (`tail`、Koka の `fun` に当たる) を足す。子から外に出る操作は `par` ごとのロックで直列化し、節を子のスレッドで実行する。どちらの場合も、子どうしの `IO` と操作の順序は非決定的になる。後から挿入しても、既存の制約 (`σ ≤ Never`、`σ ≤ Once`) の意味は変わらず、`IO` の分類が下がって受け付けるプログラムが増えるだけなので、既存のコードが通らなくなることはない
- **逐次実行と同じ意味の `par_ordered` (a3)**: 任意の row を許し、右の子を最初の perform まで投機的に実行する。意味は逐次実行と完全に一致する。「perform の手前で止まる」プリミティブが実行系の核に必要になる
- **局所的な可変変数**: エフェクトで作る `var` としてある ([式](../spec/expressions.md) の「`var`」)。変数の値は地点ごとのエフェクトの handler が持ち、可変参照と `Heap` には依らない
- **`Lin` の `MutArray` の分割と結合**: 重ならない部分に分けるプリミティブと、結合のプリミティブ。`MutArray` と `freeze` はある。普通の `Array` は意味が不変で、一意ならその場で書き換える ([標準ライブラリ](../spec/stdlib.md) の「`Std.Array`」)
- **並行処理用の共有の可変状態**: channel、atomic な参照など。`IO` か `Async` の側に置く
- **`IO` が大域的な領域を含む折衷案**: Koka のように `IO` が `Heap Global` を含む形。便利だが、大域的な領域の読み書きには同期が必要になる。必要になったら検討する
- **「`Heap` を含まない row」の制約**: 子タスクの row を多相に開いたまま `Heap` だけを除外できると、並行処理の API の柔軟性が上がる。[ロードマップ](roadmap.md) の「型システム」にある「row 要素ごとの捕捉 Kind」と同じ種類の拡張として扱う
- **private deque**: 印付けを実際に移動する継続だけに限る最適化
- **別のスレッドからの解放に対応したアロケータ**: mimalloc など。VM の並列化かネイティブのランタイムのうち、先に来るほうで決める
- **fork と join での `Lin` の移し替え**: 中の `Unr` のフィールドをたどって印を付ける手順と、所有者の検査の関係。join で右の子の結果に含まれる `Lin` の物体の所有者を親に戻す手順も、ここで決める
- **`poly` の物体のビットの実行時の伝播**: `poly` の `con` でフィールドの `lin` ビットの OR を取り、実行時に伝える案。`MutArray` は要素を `Unr` に固定しているので決めていない。`Lin` の要素を持つ配列を入れるときに決める
- **読むだけの共有**: OxCaml は、`par` の子が親の環境を読めるが書けない形を持つ。eml の `par` の子は親の `Ref` を読めない。表現力の不足として現れたときに検討する
- **実行時エラーの報告の決定性**: `par` の子の row は `<>` なので、子は `Panic` を起こせない。値と入力で決まる誤り (桁あふれ、ゼロ除算、範囲外の添字) は `Panic` として型に出るので、子の中では起きない ([VM](../spec/vm.md) の「中断と実行時エラーの分担」)。残るのは型に出さない停止 (ヒープの誤り、内部の誤り、割り込みと上限) である。この停止と、`debug_heap` が報告するリークと不変条件の違反を、スケジュールによらず同じ内容で出す必要がある。左の子が止まった後に右の子をどう止めるかは、a2-cancel の協調的な中断と一緒に決める
- **言語のキュー (channel など)**: スレッドをまたぐキューのうち、ランタイムのキュー (work stealing の deque、スケジューラの実行待ち) は、印を付けたクロージャの語を持つ Rust のコードとして `eml_rt` に書ける。言語のキューには、次のものが要る
  - 共有の物体に書き込む操作。`set_field` は、ほかのスレッドが読めない物体にしか使えない。Acquire/Release 付きの atomic なフィールドの読み書きと CAS を核の操作に足し、push が値に自動で印を付ける形にする。今の証明の前提 (信頼の一覧の T0) を並行の証明に置き換える作業も、VM の並列化のときに要る
  - 別のスレッドからの解放に対応した確保器 (上の「別のスレッドからの解放に対応したアロケータ」)
  - キューの中身の置き場所。atomic なフィールドの操作があれば、channel は `Data` の物体の連なりとして書ける。`Foreign` の Rust の値に語を入れる形は採れない。`Foreign` は走査する語を持たないので、中の語は `share`、解放の連鎖、リークの検査から見えず、破棄処理はヒープを受け取らないので中の値を `decref` できないためである
  - Rust の側のキュー (deque、実行待ち) が持つ語を根として登録する仕組み。登録しないと、こうした語は、検査モードのリークの数え方と、回復から見えない。回復は根から届く物体を新しいヒープに写すので、物体の番地が変わる。そのため、登録した根の語は、回復が書き換えられる場所に置く ([オブジェクトモデル](../spec/object-model.md) の「回復」)。worker ごとにヒープを持つようになったら、回復はすべての worker を止めてから行う
  - channel の受け取りで待つこと (待ちと起こし) の仕組み
- **ネイティブのヒープの実装方式**: スレッドごとのアリーナにして (スレッド ID, インデックス) で指す方式か、ポインタ方式か
