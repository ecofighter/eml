# マルチコア対応の設計

位置づけ: 将来の設計。

VMとネイティブのランタイムで、複数のコアを使って実行するための設計をまとめる。workerとスレッドの模型、スケジューラ、スレッドをまたぐRC、`par`の意味、止める手順を書く。今のVMはworkerのスレッドを持ち、`par`の右の子を空いているworkerに置き、`Async`のタスクを`start`のときにworker 1..N-1へ順に回して置き、タスクは終わるまでそのworkerで動く ([VM](../spec/vm.md)の「タスクとスケジュール」と「`par`のforkとjoin」と「`Async`のタスク」)。`par`の盗みとネイティブの並列はまだない。VMは、並列を広げられる制約を守る (下の「VMの並列化の備え」)。今の実装に入れてある備えは、rowのKindの束の`Never` ([型とKind](../spec/types.md)) と、持ち越し規則の制約を`σ ≤ Once`と書くこと ([エフェクトとhandler](../spec/effects.md)) のほかに、`eml_rt`の共有の印方式のRC (`share`、負のRC、共有した物体をreuseしないこと。下の「スレッドをまたぐRC」)、検査モードの所有者の検査、別のスレッドからの解放とほかのヒープの物体の受け付け (下の「別のスレッドからの解放」)、workerごとの止める語、`CodeBase<M>: Sync`と`Task: Send`の型のassert (下の「VMの並列化の備え」) である。

stdの`Async`の意味 (タスク、スコープ、取り消し、I/O、channel) は[非同期の設計](async.md)に、ネイティブのコードのfork / joinとエントリは[ネイティブ化の設計](native.md)の「並列の実行」に、GUIは[FFIと拡張の設計](ffi.md)の「GUI」にある。この文書はその下の仕組みを書く。

## 目的と範囲

### 目的

- VM とネイティブのバックエンドで、複数のコアを使って実行できるようにする
- 並列の安全性 (共有の印付け、移し戻し、別のスレッドからの解放、下の「不変条件」) を、ネイティブ化を待たずに VM の実装で確かめる。VM の並列化では速さよりこちらを重視する
- 「線形型 × 代数的エフェクト」の性質 (`Lin` による移動、row によるエフェクトの制限) を、並列の安全性の保証にそのまま使う

### 対象

- 決定的な並列計算: データ並列に限る。`par`、`std/Par` の並列の map / fold / reduce、分割統治
- 並行処理: std の `Async` のタスク、非同期 I/O ([非同期の設計](async.md))

### 対象外

- 利用者に見せるメモリモデル。共有の可変状態を伴うマルチスレッドは扱わず、Rust の `Send` / `Sync` に当たる Kind の次元は導入しない。ランタイムが利用者に見せるのは `IO` の下の `Chan` と `Atomic.Counter` だけで、`IO` を持たない `par` の子からは届かない
- `par` の子から `IO` を使うことと、利用者の定義した再開する操作を子から外に出すこと (下の「未決の論点と将来の拡張」)

## 確定した設計判断

| # | 領域 | 決定 |
|---|---|---|
| 1 | 層の構成 | ランタイムが仕組みを持ち、stdが意味を持つ。仕組みはworker、受け箱、deque、待ちと起こし、監視のスレッド、I/Oのdriverのインターフェース、メインのworker、移し戻し、添字の範囲のプリミティブ、根の登録で、`eml_sched`と`eml_rt`に置く。I/Oのdriverとブロックする呼び出しのプールは`eml_io`に置く。意味は`Async`のタスクとスコープ、取り消しの方針、channelのAPI、`std/Par`で、stdに置く。`tests/ui/run/kinds/scheduler.em`は言語のテストとして残す |
| 2 | 可変状態 | 可変状態はエフェクトの中でだけ扱う。並列の安全性は row の制限で保証する |
| 3 | `Ref` と `Heap` | 値 `Ref h a` (`Unr`) と組み込みのエフェクト `Heap h` を持ち、`IO` とは分離する。`run_heap` は rank-2 の組み込みとして特別扱いし、ユーザーには rank-2 を書かせない。multi-shot で再開したときの状態は共有する |
| 4 | `Ref` の中身 | `Ref` には `Unr` の値だけを入れる。`Lin` を `Unr` に変える汎用の操作は作らない |
| 5 | RC | 共有の印方式 (Koka、Lean 4 と同じ)。符号付きの `AtomicI32` で、正なら局所、負なら共有。局所的なオブジェクトには Relaxed の load / store を使う。共有の印の付いた物体は reuse しない |
| 6 | VM | 並列を広げられる制約 (下の「VMの並列化の備え」) を守る。VMは参照の実装で、検査モードを持つ唯一の実行系なので、ネイティブより先に並列にする。`par`と`Async`は1つのworkerの上でも、複数のworkerのときと同じコードの経路で動く (下の「1つのworkerでの実行」)。並列は、workerのスレッドと`par`の右の子の配置、workerをまたぐ`Async`、メインのworker、`par`の盗みの順に広げる ([ロードマップ](roadmap.md)の「段の列」) |
| 7 | 共通ランタイム | オブジェクトの形 (記述子)、RC の符号の規約、ヒープの実装方式、共有の経路 (印付けと負の RC) は、共通ランタイム `eml_rt` で決め、VM とネイティブで共有する ([オブジェクトモデル](../spec/object-model.md))。ヒープの実装方式は、64 KiB のページから切り出す自前の確保器である ([オブジェクトモデル](../spec/object-model.md) の「確保器」)。別のスレッドからの解放は、この確保器にページごとの遠隔の空きリストを足して受ける (下の「別のスレッドからの解放」)。ヒープは worker ごとに1つで、run の間ずっと生きる。回復はすべての worker とプールのスレッドが止まっているときにだけ行う。生の要素の配列は種類 `Raw` の物体にする ([オブジェクトモデル](../spec/object-model.md) の「種類」)。実行時の検査は、`eml_rt` の検査モードが受け持つ ([オブジェクトモデル](../spec/object-model.md) の「検査モード」) |
| 8 | 並列 API | `par` は1つで、子の row は `<never e>` (`e : Row<Never>`) である。`par` はすべての子の完了を待ち、いちばん左の子の中断を親で起こし直す。`Panic` は `Never` のラベルに分け直し、`IO` は `Once` のままにする。row の Kind の束は `Never ≤ Once ≤ Multi`。利用者が主に使うのは `std/Par` の集まりの関数で、2引数の `par` と逐次の `both` も公開する。並行処理は std の `Async` で書く ([非同期の設計](async.md)) |
| 9 | 不変条件 | スレッドをまたいで値や制御を渡すプリミティブは、すべて閉じた row か `Row<Never>` の制約を持つ。Rust の側の構造が持つ語はどれも数えた参照で、run の終わりに構造を空にしてから漏れを確かめる (下の「不変条件」) |
| 10 | 共有の印付け | 実行系のプリミティブが、送り手のスレッドで、公開する前に自動的に行う。fork、`spawn`、channelの送りは印を付け、join、channelの受け取り、タスクの開始は移し戻しで受ける (下の「印付けの表」)。`par`ではworkerの数によらず必ず行う。待ったタスクの継続はworkerから動かないので、印を付けない |
| 11 | スレッドに縛られたリソース | 組み込みのリソースは、スレッドに縛られないものに限る。スレッドに縛られたもの (GUIなど) は、メインのworkerの上の固定したタスクに閉じ込める。メインのworkerの待ちは`Park`で、差し替えられる |
| 12 | `Lin` の物体 | `Lin` の値は move だけを許し、物体の RC は常に 1 である。スレッドをまたぐときは印を付けず、所有者を移す |
| 13 | スレッドの模型 | OSのスレッド1つがworker 1つで、`Ctx`と`Heap`を1つずつ持つ。`main`は大きいスタックで作るworker 0で動く。`Machine`を持つスレッド (`eml run`ではプロセスのメインスレッド) はメインのworkerである。メインのworkerは、配置で仕事を受けない追加のworkerで、その待ちはtoolkitのループにできる。REPLでは、worker 0がメインのworkerを兼ねる。監視のスレッドがrunに1本ある。ブロックする呼び出しのプールはヒープを持たない (下の「スレッドとworker」) |
| 14 | スケジューラ | `par`はfork / joinで、まだ始まっていない右の子だけをworkerごとのChase-Levのdequeから盗ませる。`Async`のタスクは`start`で置かれたworkerから終わるまで動かず、待った継続はタスクのセルが持ち、そのworkerが再開するので印を付けない (下の「スケジューラ」) |
| 15 | 切り替え | 協調的にする。タスクはVMでもネイティブでも`Async`の操作でだけ切り替わる。`Seeded`はテストの方針で、安全点でyieldを強いる。シグナルや時間による切り替えはしない |
| 16 | 長い呼び出し | その場で動くexternとCの呼び出しはworkerを持ち続け、同じworkerのほかのタスクは呼び出しが戻るまで待つ。待つべき長い呼び出しは、ヒープを持たないプールの仕事にする ([FFIと拡張の設計](ffi.md)の「長く走る呼び出し」) |
| 17 | 止める手順 | 終わりを決めたworker 0か、致命的な誤りを最初に書いたworkerが、すべてのworkerの止める語に終わりのビットを立てて起こす。各workerは次の安全点でエントリへ戻り、自分のI/Oのdriverを空にし、自分の`Ctx`をworker 0に返す。worker 0が全員をjoinしてから、Hostを書き出し、ヒープを確かめるか回復して落とす。分かれたrunでは、確かめと回復は、自分のメインのworkerの繰り返しが戻った後でworker 0をjoinした`Machine`を持つスレッドが行い、そのスレッドが終了コードで終わる。`exit`もこの手順を使う (下の「止める手順」) |

## 層の構成

```
std:           Std.Par (par、both、集まりの関数)    Std.Async、Std.Chan、Std.Net (タスク、スコープ、取り消し)
               ──────────────────────────────────────────────────────────────────────
eml_cli        Session::run が実行系を組み立てる (worker の数、実行系、I/O の driver の時計と seed、GUI の Park)
eml_native     コード生成器 (LIR → CLIF、JIT のホスト)。eml_nrt の上に立つ
eml_vm         Exec を実装する (VM)                eml_nrt      Exec を実装する (ネイティブ)
eml_sched      スレッド、受け箱、タスクのセル、監視のスレッド、deque、待ちと起こし、Exec の trait
eml_io         IoDriver を実装する (本物の driver、テストの driver、ブロックする呼び出しのプール)
eml_rt         語の単位の操作 (share、移し戻し、範囲のプリミティブ)、Host、Sched、IoDriver の trait
型システム:     row の Kind による制限 + Lin による移動
```

- 依存の順は`eml_rt` ← `eml_sched` ← `eml_vm`と、`eml_sched` ← `eml_nrt` ← `eml_native`である。`eml_sched`はworkerのループが呼ぶ`Exec`のtraitを持ち、`eml_vm`と`eml_nrt`がそれを実装する。`eml_nrt`は、出すコードが呼ぶ実行系のエントリ、エントリのstub、runの駆動を持ち、Craneliftに依存しない。`eml_io`は`eml_rt`に依存して`IoDriver`を実装する ([非同期の設計](async.md)の「I/O の driver」)。コード生成器の`eml_native`は、`eml_nrt`、`eml_lir`、`eml_rt` (定数だけ)、Craneliftに依存し、`eml_sched`には直接依存しない。`eml_cli`はすべてに依存する
- `eml_sched`は、タスクのセルの核と実行のインタフェース、時計の選び方、自己パイプ、メインのworkerの`Park`を持つ。スケジューラとworkerの表はまだ`eml_vm`の`sched.rs`と`workers.rs`にある ([VM](../spec/vm.md)の「タスクとスケジュール」)。`jit-tasks`がworkerの表、受け箱、監視のスレッド、`Exec`のtraitを`eml_sched`へ移す ([ロードマップ](roadmap.md)の「段の列」)
- `Session::run` が実行系を組み立てるので、`Session` は今と同じく唯一のパイプラインの駆動役である。`Host`、`Sched`、`IoDriver` の trait は `eml_rt` に置く。`Host` と `Sched` は `Ctx` を通して届く。`IoDriver` は、`eml_rt` の extern が要るまでは実行系が持ち、`Ctx` には入れない。`Session::run` は driver そのものでなく、`Copy + Send` の時計の選び方 (`Clock`) と seed を渡し、各 worker が自分のスレッドの上で driver を作る。driver はそのスレッドから動かない ([VM](../spec/vm.md) の「時計と driver」)
- `eml_rt` は vstd だけに依存したまま Verus で証明する。スケジューラ (`eml_sched`) は Verus の外に置き、Miri と TSan で確かめる (下の「テスト」)
- スケジューラをエフェクトのライブラリとして書く形は採らない。監視、スレッドをまたぐ起こし、根の登録は、語の外のRustの構造を要るためである。ライブラリとして書いた協調的なスケジューラ`tests/ui/run/kinds/scheduler.em`は、継続を扱う言語のテストとして残す

## スレッドと worker

- OS のスレッド1つが worker 1つである。worker はどれも自分の `Ctx<M>` (自分の `Heap`、`evv`、yield の状態、統計、worker の止める語) を持ち、共有の `CodeBase`、`Arc<Control>`、`Arc<dyn Host>` の上で動く。セッションの根は worker 0 の `Ctx` に置く
- `eml run` の worker の数 N の既定は `available_parallelism` で、`--workers` と `EML_WORKERS` で変えられる ([標準ライブラリ](../spec/stdlib.md) の「起動」)。ライブラリと UI テストの既定は N = 1 で、`par/` と `async/` の UI テストは N = 2 と 8 でも流す (下の「テスト」)
- worker 1..N-1は、使えるrun (N ≥ 2で、セッションの根がなく、読み込んだコードが根の基本操作を持たず、`Machine::with_driver`でdriverを渡していないrun) の始めに、`main`の最初の命令の前にworker 0が一度に作り、runの終わりにjoinする。使えないrunはworker 1..N-1を作らず、worker 0の1つで動く。REPLのセッションは根を持つので、いつもworker 1つで動く。成功したrunの後にも、ほかのworkerのヒープのページに物体が残りうるので、ヒープはworker 0がjoinしてから確かめて落とす。workerとヒープはrunの間ずっと生きる ([VM](../spec/vm.md)の「タスクとスケジュール」)
- worker 0 は `main` のタスクを動かす。プロセスのメインスレッドでなく、別に作るスレッドである。VM の worker のスタックは 8 MiB で、ネイティブのコードは driver の求める大きさのスタック (既定は 1 GiB の予約。[ネイティブ化の設計](native.md) の「安全点とスタック」) で作る。ほかの worker のスレッドも worker 0 と同じ大きさで作る
- `Machine`を持つスレッドは、`eml_vm::execute`か`Machine::run`を呼んだスレッドである。runの前にプログラムを読み込み、runの後にヒープを畳み込み、runの間はメインのworkerである。`eml run`ではプロセスのメインスレッドである。シグナルのhandlerはどのスレッドでも動くが、SIGINTとSIGTERMを塞がないのはworker 0だけなので、unixではworker 0のスレッドで動く (下の「VMの並列化の備え」)。`Machine`を持つスレッドは、worker 0を作ってからjoinし終えるまで2つのシグナルを塞ぐ。止める手順の後半 (workerを待つこと、ヒープを確かめて落とすこと。下の「止める手順」) はworker 0が行い、分かれたrunでは両方のjoinの後で`Machine`を持つスレッドが行う。I/Oのdriverを空にし、プールの仕事を待つのは、driverを持つworkerのスレッドである
- メインのworkerは、`Machine`を持つスレッドの上の追加のworker (欄N) である。runの始めからあり、worker 1..N-1と同じ手順で待つ。固定したタスク (`Async.start_on_main`) を動かし、配置の行き先にならず、本物の時計ではほかのworkerと同じく自分のI/Oのdriverを持ち、runの全体の務めを持たない。その待ちはtoolkitが替えられる`Park`である ([FFIと拡張の設計](ffi.md)の「GUI」)。自分の`Ctx`と`Heap`を持ち、OSの既定のスタックで動く。深い再帰は`stack_limit`の確かめで止める。REPLでは、worker 0がメインのworkerを兼ねる。ほかのスレッドに縛られたライブラリのためのworkerは、後に回した項目である ([ロードマップ](roadmap.md)の「マルチコア対応」)
- 監視のスレッドはrunに1本あり、workerが2つ以上のrunと眠るdriverのrunではrunの始めに始まる。ほかのrunでは、`MEMORY`が`Watched`の方針に限り、最初の`Async`のタスクを実行待ちに積むときに始まる。自己パイプ (`Doorbell`) を持つ監視のスレッドは、どれかのworkerが動いている間だけ監視の刻み (既定10 ms) ごとに起き、ほかの間は自己パイプで眠る。眠っていたworkerが動き始めると自己パイプが鳴る。シグナルのhandlerも自己パイプを鳴らす ([VM](../spec/vm.md)の「上限と割り込み」)。そのため、すべてのworkerが待っているrunでもシグナルを見落とさない。自己パイプのない監視のスレッドは、刻みごとに起きる ([VM](../spec/vm.md)の「タスクとスケジュール」)。起きるたびに次を行う
  - 保留のシグナルは今と同じく `Control::claim_signals` で取って中継する ([VM](../spec/vm.md) の「タスクとスケジュール」)。中継したシグナルは run の mail に積み、すべての worker の止める語に `NOTICE` を立てて起こす。最初に集めた worker が待つタスクに届ける (下の「止める手順」の「シグナル:」の項)
  - 止める語にビットが立っていれば、すべての worker を起こす (差し替えた待ちも、その起こし方で起きる)。ビットは書く側がすべての worker の止める語に直接書くので、監視のスレッドは写さない。待つタスクのいるシグナルは止める語でなく保留の語に入る
  - 確保量がメモリの柔らかい上限の閾値を越えていれば、確保の多いタスクに旗を立てる。テストのための決定的な方針では、監視のスレッドでなく各 worker が集める地点で同じことをする ([VM](../spec/vm.md) の「タスクとスケジュール」)
- `Control` は、host の読み手が読む止める語と、worker ごとの止める語 (`AtomicU32`) を持つ ([オブジェクトモデル](../spec/object-model.md) の「実行の制御」)。どちらも run に1組である。止める理由のビットは `INTERRUPT`、`MEMORY`、`TERMINATE` と、worker の止める語にだけ立つ終わりのビットである
- workerの止める語は、止める理由のビットを持つ。安全点と、`FileIn`、標準入力、`Child`の読みが見るのはworkerの止める語である。書く側 (シグナルのhandlerと確保器) は、`Control`の止める語とすべてのworkerの止める語にビットを直接立てる。書いた時点で止まる時点が決まり、監視のスレッドが動いているかに左右されない。シグナルのhandlerは、そのシグナルが`Control`の見張りの語に立っていれば、どの止める語にも立てずに保留の語に入れる (`Control::defer`。[VM](../spec/vm.md)の「上限と割り込み」)。どれもatomicな読み書きなのでasync-signal-safeである。そのため、`Interrupted`を受けて読み直す読み手はすぐにビットを見る。眠っているworkerは監視のスレッドが起こし、起きたworkerが自分の語を読む
- 止めるビットは止める理由のビット (`INTERRUPT`、`MEMORY`、`TERMINATE`、終わりのビット) をまとめた呼び名である。終わりのビットは、runの終わりを決めたworker 0か、致命的な誤りを最初に書いたworkerが立てる (下の「止める手順」)
- worker の一覧は worker の止める語を作るときに載せる一覧で、監視のスレッドが刻みごとにたどる。下の「Rust の側が持つ語」の run の登録表とは別のものである
- ブロックする呼び出しのプールは、待つべき長い呼び出し (利用者の`blocking`のCの行、`Std.Stream`のファイルの読み書き、`Std.Tls`の接続を作ることとhandshakeの間の押し込み) を動かすスレッドの集まりである。各workerのI/Oのdriverの一部で、仕事はdriverに出す操作 (`Op::Job`) である。必要になったときに作り、上限 (32) まで増え、使われないスレッドはしばらくして終わる。`blocking`の呼び出しと`Std.Tls`の仕事が同時に使えるのは24本までで、残りはファイルの仕事に空ける。プールのスレッドはヒープを持たず、RCに触れず、確保もしない。`blocking`の仕事が受け取るのは、`CCall`と`u64`のslotと、小さい引数の写しと、大きい引数のページの留めで、結果は箱に入れたRustの値で返す。仕事の記録はrunの登録表に載り、ヒープの語は持たない。完了は仕事を受け付けたdriverの完了の列を通して届き、そのdriverを持つworker (host) が集める地点で結果を記録に置く。hostが持ち主でなければ、持ち主が`Completion`の知らせを受けて記録に当てる ([非同期の設計](async.md)の「ブロックする呼び出しのプール」)
- その場で動くexternとCの呼び出しは、タスクのworkerのスレッドの上で動き、終わるまでworkerを持ち続ける。externからemlに入り直すことはない。タスクのその場の呼び出しは、そのタスクの間ずっと同じOSのスレッドで動き、同じworkerのほかのタスクは呼び出しが戻るまで待つ。プロセスの外のスレッド (Cのライブラリのスレッドなど) からemlへ知らせるインターフェースは、workerの受け箱を起こすインターフェースだけである

## スケジューラ

### worker のループ

worker のループは、ほかに仕事がなくなるまで次の順に見る。

1. 受け箱の中身をまとめて取る (lock を1回取る)
2. 自分のdequeの`par`の子
3. 実行待ち (再開を待つ継続、`Seeded`が切り替えたVMのタスク、joinを待った親)
4. ほかのworkerのdequeから`par`の子を盗む (メインのworkerは盗まない)
5. I/Oのdriverを見る
6. 待つ (park)

- 実行待ちは再開を待つタスクの継続の列である。項目は `{ タスクのセル, 継続 k, 渡す値 }` で、渡す値は `Wake` のような即値か数えた参照の語である
- VM は実行待ちの継続から新しい VM の `Task` (スタックは使い回しの集まりから取る) を作り、エントリ `resume_task` で `k` に値を渡す。受け箱で届いた新しいタスクはエントリ `start_task` で始める。ネイティブのコードは同じ2つの関数をネイティブのエントリから呼ぶ
- `start_task : (Unit -> <IO, Async> Unit) -> <IO> Unit` と `resume_task : (once Wake -> <IO> Unit) -> Wake -> <IO> Unit` は、名前で ABI が決まる単相の std の関数である。`start_task` はタスクごとの handler をかぶせ、その節は `k` をランタイムに預けて (待ちに入れるか、実行待ちに戻す) そのまま戻る。`start_task` が受け取る閉包は、std がタスクの本体にかぶせた底である。底は `Panic` と IO の失敗を捕まえ、本体の結果を値のまま、引数を預かる extern (`finish_ok`) に渡す。ランタイムはその値を写さず中身を見ず、待つ側に1回返す ([標準ライブラリ](../spec/stdlib.md) の「`Std.Async`」、[非同期の設計](async.md) の「`Async` のエフェクト」)
- タスクはループに戻るとき、エントリの関数から普通に戻る。VM のタスクが切り替わるのは yield の状態がなしの安全点だけで、そのとき `evv` を `Task` に退避する
- メインのworkerは盗まない。その待ちは`Park`で、toolkitのコールバックが`run_pending`を呼ぶ (下の「固定したタスク」)

### `par` の子

- `par` の fork と join は実行系 (VM ではタスクと join の節点を持つ `eml_vm`) が行い、印付けと移し戻しは `eml_rt` の `share` と `transfer_back` を呼ぶ ([VM](../spec/vm.md) の「`par` の fork と join」)。fork はまだ始まっていない右の子を自分の deque に積み、左の子を自分で動かす。空いた worker は deque の上から盗む
- dequeを入れるまでのVMでは、forkは空いているworkerがあれば右の子をその受け箱に置き、なければ自分の実行待ちに積む。置いた子の終わりは、結果ごと親のworkerの受け箱に知らせる ([VM](../spec/vm.md)の「`par`のforkとjoin」)。`Async`のタスクは、`start`のときにworker 1..N-1を順に回して置き、`Place`の知らせで運ぶ (下の「`Async`のタスク」)
- `compute` の仕事は join するフレームを持たない fork の子で、`par-steal` では deque の項になり、終わりで仕事のセルを終える ([VM](../spec/vm.md) の「`compute` の仕事」)
- VMでは、joinで待つ親の`Task`はjoinの節点で待ち、workerのループはほかの仕事 (先に`par`の子、次に`Async`のタスク) を動かす。待つ`Task`はデータなので、待つ費用はない。子が終わると、親は実行待ちに戻る
- ネイティブのコードはスタックを切り替えられないので、join で待つ worker は待たずに手伝う。手伝えるのは、待つ join より深い fork の子だけで、ほかに手伝えるものがなければ join の節点で待つ ([ネイティブ化の設計](native.md) の「並列の実行」)。これで待ちが輪になることはない。まだ始まっていない子のうち最も浅いものを深さ d の c とすると、c を fork した親は動いているか、深さ d - 1 の自分の join で待っていて c を取れる。盗まれた子を待つ worker は動いている worker を待っている。`par` の子は有限である
- メインのworkerは盗まず、自分のjoinだけを手伝う
- 分け方の木は長さと粒度だけで決まり、盗み方によらない (下の「データ並列での使い勝手」)

### `Async` のタスク

- タスクは`spawn` (と`start`) のときに置く先のworkerを決め、捕まえた値に印を付けて送る。置く先はworker 1..N-1を順に回して選ぶ。`main`の動くworker 0には、Nが2以上のとき置かない。置いたタスクは、終わるまでそのworkerから動かない。待った継続`k`はそのworkerの局所の構造にだけ入り、印を付けない
- 受け箱はworkerごとに1つのmutexで、知らせの列を守る。実行待ちはworkerごとに1本の列で、受け箱とは別のmutexの下にあり、持ち主のworkerが触る ([VM](../spec/vm.md)の「タスクとスケジュール」)。タスクのセルと登録表 (待ちの登録、操作の記録、時間の輪) はrunの登録表のlockの下にある ([VM](../spec/vm.md)の「セルと登録表」)。持ち主のworkerはループの1回ごとに受け箱のlockを1回取って知らせをまとめて取り、別のworkerからの知らせは積むごとに取る。実行待ちの列には、フレームを持たない項 (始める仕事と再開する仕事) と、フレームを持つVMのタスク (`Seeded`が切り替えたタスク、joinで待つ親) が並ぶ
- 知らせは起こし (`Wake`)、タスクを置くこと (`Place`)、取り消し (`Cancel`)、別のworkerのdriverから回す完了 (`Completion`)、受け付けの転送 (`Submit`)、操作の取り消しの転送 (`CancelIo`) である。自分のdriverの完了とプールの仕事の完了は、受け箱を通らず、driverの完了の列から集める。落としたハンドル、シグナル、自分のタスクの取り消しは、受け箱でなくrunに1つのmailに積む。mailはどのworkerが処理してもよく、取り消しの項だけは持ち主が取り出す ([VM](../spec/vm.md) の「セルと登録表」)
- タスクのセルはrunの登録表の項で、持ち主のworker、状態 (動いている、待ち、実行待ち、終わり)、取り消しのビット、待つ側、属するスコープを持つ ([VM](../spec/vm.md)の「セルと登録表」)。取り消し中は、待ちのままビットが立ち、待ちの欄が残っている形で表す。セルの状態の区分 (共有、公開、持ち主だけ) は[VM](../spec/vm.md)の「取り消しの届け方」のままで、どの区分もrunの登録表のlockの下で読み書きする。開く側は新しいスコープを一覧と今のスコープに載せてから旗とビットを読み、印を付ける側はビットと旗を立ててから一覧と今のスコープを読む。そのため、開くのと印を付けるのが重なっても、新しいスコープは旗を得る。持ち主のworkerは`start`で一度だけ書く。知らせを送る側はそのlockの下で持ち主を読み、そのworkerの受け箱に積む
- 待ちの集まりの項目は `{ タスクのセル, 待ちの理由 }` である。継続 `k` は待つタスクのセルが持ち、起こす側も外す側もそこから取り出す ([VM](../spec/vm.md) の「待ちの2種類」)。待ちの理由はセルの待ち (待つ相手のセル)、I/O の待ち (操作の記録と、ハンドルを縛った worker。プールの仕事の待ちもこれである)、channel の待ち (channel のセルの待ちと、その channel の待ち手の列の項)、時間の待ちのどれかで、取り消しで待ちを外すときの手順を決める ([非同期の設計](async.md) の「待ちを外す」)
- 時間の輪は、run の登録表の worker ごとの区画で、満期は run の時間の基準で見る ([VM](../spec/vm.md) の「時間の待ち」)。区画に項を足すのは持ち主だけで、満ちた項を外すのも持ち主の集める地点である。本物の時計では、各 worker が自分の driver の待ちで自分の区画のいちばん早い期限まで眠る
- 仮想の時計は run に1つで、すべての worker が空きのときに worker 0 だけが進め、期限の来た区画の持ち主を起こす。1つの worker が自分の空きだけで時刻を進めると、ほかの worker の忙しい期間の途中で時刻が飛ぶためである
- `claim_scope` は、タスクのビットと今のスコープの旗を確かめることと、`s` に旗を立てることを、スコープの lock の下で続けて行う。分けると、2つの腕が両方とも勝ち、`race` の勝ちが1つに決まらなくなる
- 取り消しのビットの処理と待ちを外すことは、持ち主の worker が run の登録表の lock の下でだけ行う
- 受け付けを、ハンドルを縛った別の worker (host) へ回すときは、その worker の受け箱へ `Submit` を送る。host は集める地点で受け付けを出し、結果を操作の記録に置いて、タスクのセルの持ち主へ `Completion` を送る。結果を記録に当てるのは持ち主である。操作の取り消しも `CancelIo` で host へ回す ([非同期の設計](async.md) の「ハンドルと worker」)
- 操作の予算はタスクのセルの予算である ([標準ライブラリ](../spec/stdlib.md)の「操作の予算」)。待たずに済む速い道の行と`Std.Net`の待ちがこれを減らし、タスクが始まるときと、操作の待ちでない再開のときと、予算を使い切った操作の待ちからの再開のときと、予算を使い切った終わった操作の待ちが譲らずに続けるときに戻す。走れるタスクがあるかはそのworkerの実行待ちの列で決める。workerの止める語には触れない ([非同期の設計](async.md)の「`Async`のエフェクト」)

### `Async.run` と入れ子

- VMでは、`Async.run`の下にある組み込みが根のスコープを作り、本体の`start_task`を置き、呼んだ`Task`をスコープの待つ側として待たせてループを続ける。生きているタスクの数が0になると、結果を書いて呼んだ`Task`を実行待ちに戻す。ループを入れ子にせず、externから入り直さず、Rustの再帰も使わない
- ネイティブのコードではマシンのスタックの上で worker のループを入れ子にする。呼んだ側が完了の後に再開するという約束は同じである。入れ子の順が逆になりうるので、`Async.run` は `main` から呼ぶのがよい

### 公平

- worker ごとの実行待ちは先入れ先出しで、切り替えたタスクは後ろに戻す
- タスクは`Async`の操作で待つか終わるまで動く。`Async`の操作を持たないタスクは終わるまでworkerを持ち、同じworkerのほかのタスクは待つ。CPUを多く使う仕事は`compute`に入れる
- I/O の driver はループの1回ごとと、待つ前に1回見る
- 新しいタスクはworker 1..N-1を順に回して置く。Nが2以上のとき、worker 0には置かない
- `par`の子は粒度で大きさが抑えられる

### 切り替え

- タスクが切り替わるのは`Async`の操作でだけである。テストでは、`Seeded`が安全点で強いるyieldでも切り替わる。時間による切り替えは、VMでもネイティブでもしない
- `Ctx::poll`の形は変えない (`depth > max_depth`か止める語が0でないか)。読むのはworkerの止める語で、止めるビットと`NOTICE`だけを見る
- seedで決まるテストのスケジュール (`Seeded`) は、安全点の数で切り替える

### タスクはworkerから動かない

- タスクは置かれたworkerで終わるまで動く。workerをまたぐ受け渡しは、`start`での配置、forkでの`par`の子と`compute`の仕事の配置 (`par-steal`では、まだ始まっていない子を盗むことも)、channelの品物、プールの仕事、joinか`take`での結果だけである
- workerが忙しいときの手立ては、`compute`、`blocking`、`Std.Stream`、`Std.Exec`、`--workers`である。Nが2以上のとき、`start`はworker 0にタスクを置かないので、`main`の同期の読みはタスクを止めない
- 待ったタスクの継続に触れるのはそのworkerだけなので、印を付けない。その場の読みが同じworkerのタスクを通してしか終わらないプログラムは止まり、処理系はそれを見つけない

### 固定したタスク

- 固定したタスクは、`Async.start_on_main`が始めたタスクとその子孫 (入れ子の`Async.run`の根を含む) である。メインのworkerの上で動き、そこから動かない。固定したタスクの`par`の子と`compute`の仕事は、ほかと同じく置く
- 仕事がメインのworkerから出るのは、`compute`、channel、toolkitの自分の投函 (post) を通るときだけである ([FFIと拡張の設計](ffi.md)の「GUI」)
- メインのworkerの待ちは`Park`である。toolkitのループは、コールバックから`run_pending` (`Pending::run`) を呼ぶ。`run_pending`は、`Park`の待ちから呼ばれたときのほかは`Busy`を返す。待ちから呼ばれれば、動けるものがなくなるまで動かし、メインのworkerをまた眠らせて、`Wait(timeout)`か`Stopping`を返す。この入れ子はVMの命令を動かしていない間に起き、`Ctx`は空いているので、externから入り直さないという規則に反しない。wakerが鳴ったときに`run_pending`を呼ぶか戻るなら、時計、デッドロックの判定、`END`は`Park`によらない。どちらもしない`Park`の下では、メインのworkerが動いているものとして数えられたままになり、仮想の時計とデッドロックの判定も止まる

### タスクごとの上限

タスクの中で深さかスタックの上限を超えたとき、またはメモリの柔らかい上限で選ばれたときは、そのタスクの IO の失敗 `ResourceLimit` にする ([非同期の設計](async.md) の「タスクごとの上限」)。スケジューラの側の仕事は2つある。1つは数えることで、確保器が worker ごとに足すページのバイト数を、切り替えの地点でその worker の動いていた `Async` のタスクに帰属させる。もう1つは選ぶことで、確保量が閾値を越えたとき、各 worker が lock なしで公開する動いているタスクと実行待ちのいちばん大きいタスクから、数のいちばん大きいものに旗を立てる。旗を送るたびに、閾値は柔らかい上限より上で残りの余裕の 1/4 だけ先に進む。規則と値は [VM](../spec/vm.md) の「上限と割り込み」、「タスクとスケジュール」、「タスクの上限」にある。メモリの硬い上限は run 全体を止める。

### 却下した案

- 始まったタスクも盗む Tokio の形の work stealing: 動いたタスクの作業の集合がすべて共有になり、reuse を失う
- 詰まった worker の役を別のスレッドに渡す形 (Go の P と M): 詰まったスレッドの `Heap` はそのタスクが使っている
- 救済 (詰まったworkerか過負荷のworkerから、フレームを持たない仕事を空いたworkerへ移す形。`rescuable`、`ready_entries`の盗み、`RescueAlways`を持っていた): なくした。救えたのは、まだ始まっていないタスクと、起こして再開できる継続だけで、I/Oの待ちのタスクと始まったタスクは救えなかった。動かす契機は壁時計の経験則で、不変条件がrunの登録表、スロット、監視のスレッド、ネイティブのエントリの規則に広がった
- 監視のスレッドの刻みによるVMの横取り (`PREEMPT`): なくした。ネイティブのコードに横取りはなく、参照の実装がそれと違ってはならない
- runの管理をメインのworkerに置く形 (時計、デッドロックの判定、driverをメインスレッドに置く): 時間が進むのにtoolkitの`Park`の協力が要り、固定したタスクのexternが、仮想の時計ではすべてのworkerのI/Oを止める
- runの管理のための専用のスレッド: worker 0がすでに行う仕事のために、runごとにスレッドが1本増える
- 時計とデッドロックの判定を分散させる形: 得るもののない新しい手順が要る
- メインのworkerが`main`も動かす形: ネイティブの`main`は大きいスタックを要り、`--workers 1`ではGUIと`main`が1列に並ぶ
- メインスレッドを、最初に使ったときか旗で後からメインのworkerにする形: メインのworkerは分かれたrunの始めからあるので、後からすることが残らない
- I/Oのdriverを持たず、そのI/Oをworker 0がhostするメインのworker: 横取りがないので、worker 0のCPUの仕事が固定したタスクのI/Oを遅らせる
- 止まらない`Park`に時間の上限を置く形: テストが時間に左右される。2回目のシグナルがすでにプロセスをその場で終える

## 可変状態

### API

```
new      : a -> <Heap h> Ref h a              (a : Type<Unr>)
get      : Ref h a -> <Heap h> a
set      : Ref h a -> a -> <Heap h> Unit
run_heap : (forall h. Unit -> <Heap h | e> a) -> <e> a
```

- `Ref h a` は `Unr` の値で、データ構造に入れたり、関数に渡したりできる。読み書きの権限は row の `Heap h` が管理する
- `run_heap` は組み込みとして型検査器で特別扱いする。rank-2 の型をユーザーに書かせることはしない。今の型推論の方針 (rank-1 + bidirectional) は変えない
- `new` は `a : Type<Unr>` を要求する。シグネチャの型変数で使った場合は、[線形性](../spec/linearity.md) と同じ仕組みで `Unr` の制約が加わる
- 実装は実際の可変メモリにする。`Heap h` は組み込みで、実際のメモリなので、multi-shot で再開したときの状態は**共有**される (Koka と同じ意味)

### `IO` と分離する理由

- 局所的な可変状態を外から消せる: 内部で `run_heap` を使う関数の型は純粋なままになり、並列タスクに渡せる
- 型が決定性を区別する: `<>` は純粋、`<Heap h>` は状態があるが決定的、`<IO>` は外の世界に触れて非決定的である
- 読み書きに同期が要らない: 下の「不変条件」により、`Heap h`の操作を同時に行うスレッドは1つだけである。`get` / `set`はatomicでない普通のロードとストアで済む
- 領域ごとに独立している: 並列タスクがそれぞれ内部で `run_heap` を使っても、互いに干渉しない

並行タスクの間で共有する可変状態 (例えば非同期のタスク同士で共有するカウンタ) は、`Heap` では書けない。`IO` の下の `Chan` (持ち主のタスクの後ろに置く actor の形) と `Atomic.Counter` で扱う ([非同期の設計](async.md) の「チャネルと共有の状態」)。

### `Lin` の値を `Ref` に入れない場合の書き方

| やりたいこと | 書き方 |
|---|---|
| `Lin` の値を書き換えたい | `Ref` を使わず、値を線形に受け渡す。一意なので、Perceus の reuse でその場の書き換えにコンパイルできる (例: `Lin` の `MutArray` の `write : MutArray a -> Int -> a -> MutArray a`)。`MutArray` を `var` に入れれば、受け渡しを書かずに `a[i] <- e` と書ける。変数の状態は handler が持ち、受け渡しは状態を渡す形の特殊化が作る |
| 一つのリソースを色々な場所から使いたい | リソースを handler に持たせる。handler が所有して操作を提供し、`return` 節で後始末する。構文としては [式](../spec/expressions.md) の「パラメータ付き handler」が基本になる |
| 一意性だけが理由の `Lin` (後始末のない可変バッファなど) を、使い終わったら共有したい | 型ごとに `freeze` を用意する (例: `freeze : MutArray a -> Array a`)。後始末を持つ型には定義しない |

- 汎用の「`Lin` → `Unr`」の変換は作らない。`FileIn` などが複製できてしまい、二重の後始末を防げなくなるため。また、RC が 0 になったときに後始末する方式は、「通常の制御フローでは暗黙の後始末を行わない」という決定 ([線形性](../spec/linearity.md)) に反する
- `Lin` の `MutArray` を並列にその場で書き換えるには、添字の範囲のプリミティブ `Par.for_mut` を使う。1つの塊の重ならない添字の範囲を子に渡し、子はその範囲だけを書く (Rust の `split_at_mut` と同じ規律)。塊を `split_at` と `concat` で別の物体に分けて戻す形は採らない。写すと O(n) で、写さない view は持ち主が2つになるためである

## スレッドをまたぐ RC

### オブジェクトがスレッドをまたぐ場面

1. `par` の子や `spawn` に渡すクロージャが捕まえた値
2. channel やタスクの結果で送る値
3. ブロックする呼び出しのプールの仕事に貸す記憶 (待つタスクの継続が参照を持ち、印は付けず、移し戻しも要らない)

`Lin` の値は move だけを許し、`Lin` の物体の RC は常に 1 である ([LIR](../spec/lir.md) の「値の表現」)。そのため `Lin` の物体には印を付けず、所有者を移すだけで済む (下の「`Lin` の物体の所有者の移し替え」)。ただし、`Lin` な構造の中にある `Unr` のフィールドはスレッドをまたぐ。

始まったタスクの継続はスレッドをまたがない。これで、サーバの作業の集合はworkerの局所に保たれ、reuseを失わない。

### 共有の印方式

```rust
// 局所 (正の値): Relaxed の load/store は、x86 でも ARM でも普通の mov になる
let n = rc.load(Relaxed);
if n > 0 { rc.store(n + 1, Relaxed) }
// 共有 (負の値): 本物の atomic 操作
else     { rc.fetch_sub(1, AcqRel); }
```

- オブジェクトは最初は局所的で、RC の操作は普通の加減算と同じ速さになる。代わりに、RC 操作ごとに印を確認する分岐が1つ増える
- 上の場面で、渡す値から到達できるオブジェクトをたどって共有の印を付ける。すでに印のあるオブジェクトでたどりを止めるので、各オブジェクトがたどられるのは高々1回である
- **印付けは送り手のスレッドが、公開する前に行う**。受け手が印を付けると、送り手がまだ同じオブジェクトに対して atomic でない RC 操作をしている可能性があり、data race になるため
- 印付けは下の「不変条件」に挙げる実行系のプリミティブの中で自動的に行う。ライブラリの作者が印付けを忘れることはない
- 共有したオブジェクトは、別のスレッドで RC が 0 になって解放されることがある。確保器は別のスレッドからの解放を受ける (下の「別のスレッドからの解放」)
- 共有の印の付いた物体 (RC が負) は、RC の値によらず reuse しない。Lean 4 の `lean_is_exclusive` と Koka の `kk_block_drop_reuse` と同じ規則である。Perceus の reuse の判定は、局所の RC が 1 かどうかだけになる。共有の物体を局所へ戻すのは、受け手の移し戻しだけである (下の「移し戻し」)

### 却下した案

- 常に atomic にする (Swift、Rust の `Arc`): シングルスレッドのプログラムでも、すべての `dup` / `decref` が atomic 命令になる
- Biased RC: 印付けのたどりは不要になるが、ヘッダに所有するスレッドの ID とカウンタ2つが必要で、実装がかなり複雑になる
- 型で区別する: Kind に共有の次元が必要になり、決定2に反する

### `par` の印付け

印付けをいつ行うかで、どの物体が共有になるかがスケジュールに依存するかが決まる。

| 印付けの時点 | 共有になる物体の集合 | 逐次の実行で通る経路 |
|---|---|---|
| 盗まれた時点 (private deque の方式) | スケジュールに依存する | 印付けが一度も起きない |
| fork の時点 (join では公開と移し戻し) | スケジュールによらず決まる | 並列のときと同じ物体に印が付く |

`par` は fork と join で共有の経路を通す。印を付けるのは fork だけで、join は公開と移し戻しの歩きだけを行う。

- fork: 右の子の閉包から届く物体に印を付ける。rayon の `join` と同じく、別の worker に渡りうるのは右の子だけで、左の子は親の worker で動く。届いた `lin` ビットの物体からは移し替えにする (下の「`Lin` の物体の所有者の移し替え」)
- join: 右の子の worker が結果を Release で公開し、親は移し戻しで受ける。印は付けない (下の「移し戻し」)

添字の範囲のプリミティブ (`Par.for_mut` と `Par.tabulate`) は、1つの塊の範囲を子に渡す。要素のうち rc > 1 のものには印を付け、rc 1 のものには印を付けない。範囲が子にその要素を一意に持たせるためである。検査モードでは、fork で子の範囲の rc 1 の要素の持ち主を子の ID に書き換え、join で範囲の rc 1 の要素の持ち主を親の ID に書き戻す。子が確保して範囲に入れた要素も、join で親の持ち主になる。速いモードでは持ち主について何もしない。生の要素の配列は走査する語を持たないので、印付けは O(1) である。

印付けは `par` の実行時の意味の一部で、検査モードだけの動作ではない。共有した物体は reuse しないので、共有の集合が決まれば reuse の判断も決まる。そのため、逐次と並列で `RunStats` の作業の回数が一致する (`peak_objects` は除く)。代償は、1つの worker の上でも `par` に渡したデータが atomic の RC になり、reuse されなくなることである。1つの worker の `par` には速さの目標がないので、受け入れる。

### 論理的な worker ID

物理的な worker が1つだと、所有者の検査で全物体が同じ所有者になり、何も検出しない。そこで worker ごとの `Heap` に論理的な worker ID を持たせる ([オブジェクトモデル](../spec/object-model.md) の「論理的な worker ID」)。所有者の ID は検査モードだけのもので、速いモードにはない。

- 逐次の `par` は左の子を親の ID のまま実行し、右の子を新しい ID で実行する
- 右の子が確保した物体の所有者は、右の子の ID である
- 検査モードでは`Async`のタスクも`par`の子と同じく、タスクごとに新しいIDで動く ([オブジェクトモデル](../spec/object-model.md)の「論理的なworker ID」)
- 移し替えで受け手の決まらない `Lin` の値には、値を預かる構造の ID (タスクの結果はタスクの ID、channel の品物は channel のセルの ID) を途中の持ち主の ID として付ける。この ID は `fork_worker` で出し、構造とともに退かせる (下の「`Lin` の物体の所有者の移し替え」)
- 検査モードのヘッダは所有者 ID を持つ。Relaxed の `AtomicU32` にする。正の RC の物体への `dup`、`decref`、フィールドの書き込み、reuse のたびに、所有者が今の ID と一致するかを確かめる
- 生きている物体の数は論理的な ID ごとに数える。表は `Control` に置き、同じ `Control` のどのヒープも Relaxed の atomic で数える。join で退いた ID を使い回すので、表は同時に生きている ID の数までしか大きくならない ([オブジェクトモデル](../spec/object-model.md) の「論理的な worker ID」)。`share` が物体の所有を移すときと、範囲のプリミティブが fork と join で要素の所有者を移すときは、この数も移す。join で移し戻しが漏れて残った物体は `TransferLeak` で報告する。確かめは `retire_worker` のときに行う。呼ぶ側が、その ID の数を変えたどのスレッドの書き込みもこの呼び出しより前に起きるようにするので (join の Release と Acquire)、N によらず正確である。数え直し (`Control::check_owned`) は、すべてのヒープが止まって取り込みを終えた時点で、すべてのヒープを1回で数える

fork で印を付け忘れた物体に右の子が触れると、所有者が親の ID なので、検査は必ず失敗する。スケジュールに依存せず、`par` を使うすべての UI テストで毎回確かめられる。Lean 4 と Koka は eml と同じ符号の規約を使うが、どちらも印付けの漏れを直接見つける仕組みを持たない。局所の経路を `AtomicI32` の Relaxed で書くと、印を付け忘れても言語のメモリモデルの上ではデータ競合にならず、Miri、TSan、loom のどれも直接は報告しない。直接効く先例はCPython (PEP 703) の `ob_tid` のような所有者の記録である。

逐次の実行で確かめられるのは論理の誤りまでである。公開するときの順序 (Release と Acquire)、2つのスレッドからの同時の `decref`、deque の正しさは、本物のスレッドでしか現れない (下の「テスト」)。

### `Lin` の物体の所有者の移し替え

- ヘッダに `lin` のビットを、検査モードに限らず常に持つ。`FileIn` などの extern の資源は作るときにビットを立て、`con` と `closure` は静的な Kind の印が `lin` のときに立てる ([オブジェクトモデル](../spec/object-model.md) の「`lin` ビット」)
- 印付けのたどりは移し替えの形を持つ ([オブジェクトモデル](../spec/object-model.md) の「`share`」)。たどりが届いたどの `lin` ビットの物体も移し替えの根になる。根から、道の上の物体がどれも rc 1 である間に届いた物体には印を付けず、所有者を移す。最初に rc > 1 の物体に着いたら、その下は印付けに切り替える。道の上の物体はそれぞれ道の上の親からちょうど1回参照され、根は `Lin` なので、移した物体はどれも一意である。これで、共有した物体を reuse しない規則のもとでも、`Lin` の値を子へ移して子でその場で書き換える形が成り立つ
- 受け手が決まらない `Lin` の値 (MPMC の `Chan` と `Task` の結果) は、途中の持ち主の ID を付けて送る。送り手は、値を預かる構造の ID (タスクの結果はタスクの ID、channel の品物は channel のセルの ID) を途中の持ち主にして移し替えをする。この ID は `fork_worker` で出し、構造とともに退かせる。`lin` の物体から rc がすべて 1 の道で届く物体だけが途中の持ち主になり、最初の rc > 1 の物体から下は印付け (rc < 0) に切り替える。受け手の移し戻しは、rc > 0 で持ち主が途中の ID の物体を受け取って (持ち主を受け手にして) 下る。持ち主の ID は検査モードにだけあるので、速いモードでは送り手の印付けだけが行われ、受け手の裏返しの歩きは変わらない
- `poly` のコードで作った `Lin` の物体はビットを持たないので、fork で共有になり、その場の書き換えができなくなる。安全の側に倒れるだけである

### 移し戻し

受け手は移し替えの歩き `rt_transfer(w)` で、受け取った値の共有の物体を局所へ戻す。

- 歩きは、自分が裏返した物体の中にだけ下りる。裏返しはrc == -1 (Acquire で読む) の物体を rc := 1 にし、所有者を自分にして、子へ進むことである。rc > 0、rc < -1、rc == 0 の物体では止まる
- 費用は裏返した物体とその直接の子の数に比例する。子が確保した局所の物体だけの結果は O(1) で受けられる
- 検査モードはrc > 0 の物体の所有者 ID を書き換える2回目の歩きを、診断のためだけに行う。意味は変わらないので、速いモードと検査モードの reuse の判断は一致する
- 裏返しが正しい理由: Rustの側の構造が持つ語はどれも数えた参照で (下の「Rustの側が持つ語」)、待ったタスクの継続はworkerから動かない。そのため、rc == -1の物体を参照するのはちょうど1つで、それは歩く側が持っている
- 移し戻しを使うのは、`par`のjoin、channelの受け取り、タスクの開始、`await`でのタスクの結果である
- Koka は最後の共有の `drop` で 0 に戻すが、eml は戻すのを受け手の歩きだけにする。送り手が持ち続ける値は共有のままで、reuse しない

### 印付けの表

送り手は公開する前に印を付ける。

| 渡る所 | 送り手 | 受け手 |
|---|---|---|
| `par` の fork | 閉包が捕まえた値に印を付ける。届いた `lin` ビットの物体からは移し替え | なし |
| `par` の join | Release で公開する | 移し戻し |
| 添字の範囲のプリミティブ | rc > 1 の要素に印を付ける。検査モードでは、rc 1 の要素の持ち主を子にする | 検査モードでは、join で範囲の rc 1 の要素の持ち主を親に戻す |
| `spawn` と `start` | 閉包が捕まえた値に印を付ける | タスクの開始で移し戻し |
| 待ったときの継続 | なし | なし |
| channel の送りと受け取り、`Task` の結果 | 印を付ける。受け手の決まらない `Lin` の値は途中の持ち主にする | 移し戻し |
| ブロックする呼び出しのプール | 印を付けない。待つタスクの継続が参照を持つ | なし |
| I/O の buffer | 所有ごと移す (読みは一意でなければ広げるときに写し、書きは写さない) | なし |
| どこでも、`Lin` の値 | 印を付けずに所有者を移す | なし |

ブロックする呼び出しのプールの場合ごとの扱い (取り消し、runを止める終わり、回復、検査モード) は、[非同期の設計](async.md)の「ブロックする呼び出しのプール」の表にある。

### 別のスレッドからの解放

- 自前の確保器に、別のスレッドからの解放を受ける遠隔の空きリストを足す。ページの頭の作った後は書かない部分に、持ち主のヒープの `RemoteSink` を指す `sink` を置き、別の語に遠隔の空きリストの先頭を置く。大きい物体は、`RemoteSink` の大きい物体の列に積む。`RemoteSink` は受けた数を atomic に数える。持ち主かは `sink` の1回の比較で見分ける ([オブジェクトモデル](../spec/object-model.md) の「ページ」と「別のスレッドからの解放」)
- 持ち主のヒープが取り込むのは、VM が決める地点 (待つ前、タスクの切り替え、join の後、run の終わりの検査の前) の `reclaim_if_due` と、ページを歩く操作の前である。`reclaim_if_due` は、大きい物体の列が空でないか、受けた数が 256 以上のときだけ取り込む。確保器の中とループの1回ごとには確かめない。確保の操作の証明が、確保の中でモデルから物体が消えることを許さないためである
- 大きい物体を空けたスレッドは、そのページのバイト数を確保量からすぐに引き、ページは持ち主が取り込むときに OS に返す。持ち主の取り込みまで待つと、確保量の上限の判定がスレッドの順番で変わるためである
- 小さい物体のページは run の間 OS に返さない。そのため、RSS は worker のヒープごとの最大の和で抑えられる
- どのヒープも、同じ `Control` のほかのヒープのページの物体を受け付ける。受け付けるのは、rc < 0 の物体、不死の物体、前置きの所有者が今の ID と一致する rc > 0 の物体である。検査モードは、即値でない語のページが `Control` のページの表にあるかを先に確かめ (`UnknownPage`)、rc > 0 の物体では所有者を確かめる。証明は1つのヒープの逐次の模型のままで、ほかのヒープのページの物体は信頼の一覧の T14 の読み方で扱う ([オブジェクトモデル](../spec/object-model.md) の「ページの表」と「`unsafe` の核」)
- 回復は、worker 0 がほかのすべての worker のスレッドを join し、プールのスレッドが待っているときにだけ行う。すべてのヒープを取り込み、worker 0 の `Ctx` で根から届く物体を写してから、ヒープ 1..N-1 を落とす。写す物体は、ほかのヒープのページにあってもよい。根を持つセッションの run は worker を作らないので、ヒープ 1..N-1 に残す物体はない。rc < 0 の物体も写せる。凍結した領域とヒープの区別は、ページの頭の `sink` が null かどうかで行う。`Foreign`、`lin` ビットの物体、token は今と同じく `Unrecoverable` である ([オブジェクトモデル](../spec/object-model.md) の「回復」)

### Rust の側が持つ語

- Rust の側の構造が持つ語は、どれも数えた参照である。`dup` か move で取り、構造から取り除くときに手放す
- worker ごとの構造 (受け箱、実行待ち、I/O の driver の保留の表) の語は数えた参照で、run の間は構造が持つ。ヒープの根には登録しない。漏れの検査は、run の終わりに `sweep_all` が構造と run の登録表を空にしてから行う。回復は、誤りの run の構造と登録表をヒープに触れずに捨ててから行う ([オブジェクトモデル](../spec/object-model.md) の「回復」)
- channel の予約の hold も worker ごとの構造で、受け取りを予約した品物の語を持つ。予約から確定までの間に安全点がないので、安全点ではいつも空である。そのため、run の終わりには `sweep_all` が空にするのでなく、各 worker が抜けるときに空であることを確かめる ([VM](../spec/vm.md) の「channel」)
- worker の間で共有する構造の語は、run の登録表に載せる。channel の buffer、タスクのセルの結果、スコープの失敗の欄、join の節点、プールのファイルの仕事の記録である (`blocking` の仕事の記録は語を持たない)
- channel は `Data` の物体の連なりでなく、数えた参照を持つ Rust の構造にする。`Foreign` の Rust の値に語を入れる形は採らない。`Foreign` は走査する語を持たず、破棄処理はヒープを受け取らないためである

## 並列と並行の API

### row の Kind

```
row の Kind: Row<s>,  s ∈ { Never ≤ Once ≤ Multi }
  Never : never の操作だけを含む row
  Once  : さらに once の操作 (extern のエフェクトの IO を含む) を含んでよい
  Multi : さらに multi の操作を含んでよい
```

- `par` の子の row を `e : Row<Never>` に制限する。`IO`、`Heap h`、`once` / `multi` の操作は除外される
- `Panic` は `Never` のラベルに分け直す。`Panic` の操作は `never panicked` だけで、`Panic` を起こす extern は中断して再開しない。`Once` の根拠の「extern の関数がその場で1回だけ戻る」は extern の呼び出しのことで、呼び出しは `perform` でない。そのため、子は `Int` の足し算や `Array.get` を書ける。`IO` は `Once` のままにする。`Never ≤ Once` なので、`σ ≤ Once` の持ち越しの制約はどれも満たされたままである
- 制約は書ける形にする。シグネチャの row 変数に多重度の上限を付けた `<never e>` で、`once a -> …` と同じ並びである。`Par.map` に関数を渡す補助の関数のシグネチャに要るためで、シグネチャを書かなければ推論で付く。合わない row の関数を渡すと、呼び出しの位置で新しい型の誤りになる
- `Panic` の多重度と `<never e>` の規則は [型と Kind](../spec/types.md) にある

### 子タスクに `never` の操作だけを許す理由

- 一般の handler は並列と組み合わせられない: `once` / `multi` の handler は状態を handler の実行ごとの evidence に、計算の続きを継続のクロージャに持つ。例えば [エフェクトと handler](../spec/effects.md) の `run_state` の節 `| fn get () st -> (st, st)` の状態は、操作が起きるたびに evidence から節に渡り、その場で evidence へ戻る ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。二つの子タスクがこうした操作を同時に perform すると、どちらの節の `k` に計算の続きを返すかが決まらない
- `never` の操作は再開しない: handler の節は子をすべて片付けた後に、親のスレッドで1回だけ実行すればよい。節が並行に走ることがないので、ロックも、子のスレッドから親のフレームをたどる処理も要らない
- データ並列にはこれで足りる: データ並列の処理はもともと純粋な関数と、失敗の通知 (`Panic` と、`Fail` のような `never` のエフェクト) で書ける

### `par` の意味

```haskell
par  : (Unit -> <never e> a) -> (Unit -> <never e> b) -> <e> (a, b)
both : (Unit -> <e> a) -> (Unit -> <e> b) -> <e> (a, b)        -- 逐次の関数。任意の row を許す
```

- `par` は1つで、すべての子の完了を待つ。両方の子が終わってから、いちばん左の子の中断を親で起こし直す。どちらも正常に終われば組を返す
- **`par` は常に決定的**である。子は外の世界に触れず、中断は左の子を優先するので、結果は実行のスケジュールに依存しない
- 逐次の `(f (), g ())` と違うのは、左の子が中断して右の子が停止しない場合だけである。逐次なら中断で終わるプログラムが、`par` では止まらない。子の取り消しは後で足す (下の「未決の論点と将来の拡張」)
- 実行時エラー (評価全体を止める誤り) も左を先にする。右の子が先に実行時エラーで止まっても、左の子を最後まで実行してから報告する。右の子は止めたまま解放せず、誤りを join の節点に記録する。左の子が終われば、右の子の誤りで評価全体を止める。左の子も止まれば、左の子の誤りで止める。左の子の中断 (`never` の操作) も右の子の誤りを救わない。止めた右の子のスタックは巻き戻しの表のない位置で止まっていて解放できないので、続けると検査モードの終わりの確かめが漏れを報告し、速いモードと食い違うためである。左の子が停止しなければ右の子の誤りは報告されず、逐次の実行と一致する。止めた右の子のスタックが持つ語を含め、残った物体は止める手順で落とすヒープ (REPL では回復で捨てる古いヒープ) と一緒に捨てる
- `par` の子の中の実行時エラーは worker のエントリでなく子の境目まで切る。境目は VM では子のフレームの境目で、ネイティブのコードでは子ごとの `JmpBuf` である。手伝う worker では子の下に待つ親のフレームがあるので、エントリまで切ると親を壊すためである。誤りは終わりの欄でなく join の節点に書き、その子の worker はほかの仕事を続ける。N が 2 以上でも同じで、ほかの worker に置いた子の誤りは親の worker に送って join の節点に記録し、親が左の子を終えてから、その誤りで評価全体を止める (下の「止める手順」)。入れ子の `par` では内側の join から順にこの規則を当てる。ヒープの誤り、内部の誤り、デッドロックだけは子の境目で止めず、すぐに run を止める。worker 0 の上ならそのまま誤りで戻り、ほかの worker の上なら run の致命的な誤りの欄に書く (下の「止める手順」)
- 止めるビットを見て止まった子は、それを自分の誤りとして join に記録せず、そのまま止める手順に入る。この規則が順序づけないのは、子が起こしたのでない run 全体の止め方 (割り込み、`TERMINATE`、メモリの硬い上限) だけで、それは起きた時点ですべての worker の止める語にビットとして立ち、worker 0 がそれを見て run を終える (下の「止める手順」)
- 捨てる側の子の結果が `Lin` の場合、`par` は型について多相なので、実行時にオブジェクトの記述子から破棄処理を引いて drop する。`eml_rt` の記述子は破棄処理を持たなければならない。今の `eml_rt` は型ごとの記述子の表を持たず、破棄処理をヘッダの種類で表す ([オブジェクトモデル](../spec/object-model.md) の「ヘッダ」)
- `par` は実行系の核のプリミティブ (fork / join の節点) で、std の `Par.par` から呼ぶ。子の `never` の操作が `par` から抜けるのを、次の形で親に渡す
  - evidence passing は、fork しうるプログラムの `never` の操作 `E.op` ごとに、`fork$E.op` と `reperform$E.op` を作る ([Core IR](../spec/core-ir.md) の「`par` の子の中断」)。`fork$E.op` は操作の引数を捕まえた閉包 `c = closure reperform$E.op(a_1, .., a_k)` を作り、`prim child_abort(ev, c)` を呼んで子を中断する。`reperform$E.op(a_1, .., a_k, u)` は `()` を受けて `E.op` を普通に perform する
  - 子の `evv` は空でなく、親の `evv` の鏡である。親の `evv` の `never` だけのエフェクトの evidence ごとに、そのエフェクトの何番目かの深さを持つ fork evidence を同じ順に並べ、`Panic` の fork evidence を末尾に置く。子の中の `mask` は数で evidence を飛ばすので、親と同じ形の列にすれば `ev_lookup` と `evv_mask` に手を入れずに済む。fork evidence の節は `fork$E.op` である。エフェクトごとの表と末尾はロードで凍結し、鏡の節点だけを fork ごとに作る ([VM](../spec/vm.md) の「`par` の fork と join」)
  - 子の中の extern の `Panic` も、ほかの `never` の操作と同じく、子の中の `try_panic` か末尾の fork evidence の `fork$Prelude.Panic.panicked` に届く。extern のエフェクトは mask されないので、`Panic` の fork evidence は深さ 0 の1つで足りる
  - join の節点は起こし直しの閉包を持つ。両方の子が終わった後、親はいちばん左のものに `()` を適用する。深さが 0 でなければ、親の `evv` をその深さまで mask してから呼ぶ。それは親の文脈で親の evidence を使って perform するので、`prompt$` は普通に動く。`par` の呼び出しの位置は巻き戻しの地点である ([Core IR](../spec/core-ir.md) の「`never` の中断」、[VM](../spec/vm.md) の「巻き戻し」)
  - 子は親の evidence に触れないので、evidence のために印を付けるものはない
- 子の取り消しを入れるときは、協調的な中断を安全点で行い、中断した子が捕まえている `Lin` の値を `drop k` と同じ後始末の情報で解放する

### データ並列での使い勝手

```haskell
pub map      : (a -> <never e> b) -> Array a -> <e> Array b
pub mapi     : (Int -> a -> <never e> b) -> Array a -> <e> Array b
pub tabulate : Int -> (Int -> <never e> a) -> <Panic | e> Array a                    -- 範囲のプリミティブ
pub fold     : (b -> b -> <never e> b) -> b -> (a -> <never e> b) -> Array a -> <e> b
pub reduce   : Int -> b -> (b -> b -> <never e> b) -> (Int -> <never e> b) -> <e> b   -- 添字の範囲の畳み込み
pub for_mut  : (Int -> a -> <never e> a) -> MutArray a -> <e> MutArray a             -- 範囲のプリミティブ
pub try_map  : (a -> <never e> Result x b) -> Array a -> <e> Result x (Array b)
```

- `std/Par` の集まりの関数が主な API である。`for_mut` と `tabulate` はランタイムのプリミティブで、子に1つの塊の添字の範囲を渡す。ほかは `par` の上の eml で書く。粒度を指定する関数 (`map_grain`、`fold_grain`、`for_mut_grain`、`tabulate_grain`) と、`UnboxedArray` と `MutUnboxedArray` 向けの関数 (`tabulate_unboxed : Unboxed a => …` と `for_mut_unboxed : MutUnboxed a => …`) を持つ
- 分け方の木は長さと粒度だけで決まる。既定の粒度は N によらない定数 (1024 要素) である。盗まれたかどうかは節点の2つの半分を `par` で動かすかその場で動かすかだけを決め、木の形を変えない。そのため `fold` の組み合わせの順は決まっていて、浮動小数の結果はどの N とスケジュールでも同じビットになる
- `try_map` は、見つかったいちばん左の `Err` の添字 i より右にある範囲の fork だけを省く (見つかった `Err` の添字の最小を CAS で持つ)。i より左はすべて評価するので、結果は左をすべて評価した後のいちばん左の `Err` である
- 失敗の通知は `Panic` と、`Fail` のような `never` のエフェクトで書く
- 子タスクの中ではデバッグ出力 (`println`) ができない。デバッグするときだけ `par` を `both` に書き換えれば、子の中で `println` できる
- row に現れない `trace` のような抜け道は用意しない
- `fork` と `join` を普通の関数として公開する形、`Par` のエフェクト、futures の形、新しい構文は採らない

### すぐに再開する handler の最適化

handler の節が `k v` を末尾で1回だけ呼ぶ場合、継続を取り出さない直接の呼び出しにコンパイルできる (Koka や evidence passing の主要な最適化)。これは並列とは関係なく、コンパイラが handler ごとに Core IR の形から判定する。エフェクトの宣言に操作の種類を追加する必要はない。evidence passing で実装している ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。

### 並行処理

- 並行処理は std の `Async` で書く ([非同期の設計](async.md))。タスクの row は `<IO, Panic, Async>` に閉じる。並行処理はもともと非決定的なので、`IO` を許す
- タスクは中断の境目である。IO の失敗と `Panic` はタスクの底で止まり、`exit` は下の「止める手順」で run を終える ([非同期の設計](async.md) の「失敗と `exit`」)
- ユーザー定義のエフェクトはタスクのクロージャの中で handle し終えている必要がある (OCaml 5 の Eio と同じ扱い)。`Heap h` は閉じた row によって除外される
- 並行処理のための新しい構文は追加しない。ラムダと `use` で書ける ([式](../spec/expressions.md) の「並行処理」)
- CPU を多く使う仕事は `compute` で `par` の仕事にして、呼んだタスクを待たせる ([標準ライブラリ](../spec/stdlib.md) の「`compute`」)

## 継続の移動と不変条件

### 不変条件

> スレッドをまたいで値や制御を渡す実行系のプリミティブ (`par`のfork、`spawn`、channel、プールの仕事) は、すべて閉じたrowか`Row<Never>`のKind制約を持つ。したがって、`Heap h`の操作を同時に行うスレッドは1つだけである。`run_heap`の中で待ったタスクの継続は別のworkerへ移らないので、2つのスレッドが同じ領域に同時に触れることはない。

ランタイムは次の不変条件も守る。

1. 始まったタスクはworkerを変えない。スレッドをまたぐのは、まだ始まっていない閉包、送る値、結果だけである。閉包、送る値、結果は印を付けるか`Lin`を移す
2. Rust の側の構造で語を持つものは、run の終わりに `sweep_all` が空にするか、抜ける worker が空であることを確かめる (上の「Rust の側が持つ語」)
3. VM のタスクを切り替えるのは yield の状態がなしの安全点だけで、そのとき `evv` を退避する。ネイティブのタスクは `Async` の操作でだけ切り替わる。タスクはエントリの関数から戻ってループへ戻る
4. `par` の join か `Async.run` で待つ VM のタスクは、worker を手放して待つ。そこで待つネイティブのフレームは、手伝うか、ループを入れ子にする
5. run のヒープは、その `RemoteSink` とページへのどの積みよりも長く生きる。ヒープ 1..N-1 は、worker 0 がすべての worker を join し、すべてのヒープを取り込み、確かめるか回復を終えてから落とす。ヒープを落とすときは、ほかのヒープのページにも `RemoteSink` にも触れない。回復はすべての worker が止まっているときにだけ、worker 0 が行う ([オブジェクトモデル](../spec/object-model.md) の「回復」)
6. `Control`はrunに1つである。止めるビットを書く側は、`Control`の止める語とすべてのworkerの止める語に直接書き、どのスレッドも語の間でビットを写さない。シグナルのhandlerは`Control`の語 (止める語、workerの止める語、見張りの語、保留の語) と自己パイプにだけ触れる。SIGINTとSIGTERMはworker 0のほかのすべてのスレッドで塞ぐ。`Machine`を持つスレッドはworker 0を作ってからjoinし終えるまで塞ぐ
7. 外の関数の呼び出しはプールへ出さなければタスクのworkerのスレッドで動く。`blocking`の仕事の記録はヒープの語を持たず、引数の物体は待つタスクの継続が生かす。プールのスレッドが届くのは、仕事のclosureが持つ`CCall`とslotが指す記憶 (小さい引数の写しと、ページを留めた大きい引数) だけである
8. worker のスケジューラの状態で語を持つものは、その worker の受け箱の lock か実行待ちの lock の下か、持ち主のスレッドでだけ書き換える (deque の持ち主の側)。タスクのセルと待ちの登録は run の登録表の lock の下で書き換え、取り消しの処理と待ちを外すことも、持ち主がその lock の下で行う。ロックフリーの構造は `par` の deque だけである
9. Rust の側の構造が持つ語は、どれも `dup` か move で取った数えた参照で、取り除くときに手放す。I/O の driver の保留の表と完了の中身も同じである

新しいプリミティブを追加するときは、これらの不変条件を満たすことを確認する。

### `once` の継続の移動

- `Async`のタスクが待つと、handlerの節が継続`k` (`once`、`Lin`) を待ちの集まりか実行待ちに預け、同じworkerが後で`k`を呼んで再開する。`k`はworkerの局所にとどまるので、印を付けない (上の「印付けの表」)
- タスクは`run_heap`の中でも`Async`の操作で待てる。`k`の型は`start_task`のhandlerの外側のrowの`once r -> <IO> Unit`なので (`r`は生の操作の結果の型で、`Wake`を持つ。`await_io`なら`(Wake, OpId)`である。[非同期の設計](async.md)の「`Async`のエフェクト」)、続きに`Heap h`の操作があっても`k`の型に`Heap h`は現れない。続きは`run_heap`のフレームを持ったまま待ちに入り、同じworkerで再開するので、領域を同時に触るスレッドは1つのままで、`get`と`set`はatomicでないままでよい

### `multi` の継続の並列な再開

```haskell
| ctl choose () k -> par (fn () -> k True) (fn () -> k False)
```

- [エフェクトと handler](../spec/effects.md) の持ち越し規則により、`multi` の操作をまたいで `Lin` の値は生きていない。`k` が捕まえているのは `Unr` の値だけなので、共有しても安全である
- `k` の続きのエフェクトは上のラムダの row として `par` の制約 (`Row<Never>`) で検査される。新しい仕組みは要らない。続きが `never` 以外の操作を含む場合は、並列に再開できない

### スレッドに縛られたリソース

- 組み込みのリソースはどのスレッドで後始末してもよいものに限る (現状の `FileIn`、`FileOut` と標準入出力のハンドルはこれを満たす。閉じる処理は Rust の値の drop glue と、lock を取るか atomic の印を下ろすだけの `Drop` である。`FileOut` の drop glue は buffer を書き出すが、書き手は Host の `open_write` が返す `Send` の値である。[オブジェクトモデル](../spec/object-model.md) の「extern」の「読み手」と「出力のバッファ」)
- ハンドルは共有の印なしに所有の移動で worker へ移る。`par` の子はハンドルを使えない。ハンドルのどの操作も `<IO>` を持ち、子の row は `IO` を除くためである。子にできるのは `drop` だけで、それはストリームを親に返す。タスクの中では、ハンドルが読み手ごと worker へ移るので lock は要らず、出力は書き込みごとの lock ですでに安全である
- I/O の driver のハンドルは最初に受け付けた worker の driver に縛る。別の worker からの受け付けはその worker の受け箱を通して回す ([非同期の設計](async.md) の「ハンドルと worker」)
- スレッドに縛られたリソース (GUIのハンドル、スレッドに局所的なライブラリの状態など) は、メインのworkerの上の固定したタスクに閉じ込める。toolkitの部品 (widget) は`Send`でなく、メインのworkerの上でだけ触れる ([FFIと拡張の設計](ffi.md)の「GUI」)。Kindに共有の次元は足さない

## 止める手順

run の終わり方は `main` の正常な終わり、`exit`、致命的な誤り、待つ者のないシグナルのどれでも同じ手順にする。

1. 終わりを決めるのは worker 0 か、ほかの worker の致命的な誤りである。worker 0 は終わりを決めたら、ほかの worker がいれば、すべての worker の止める語に終わりのビットを立てて起こす (`Control::end_run`)
   - `main` のタスクが値を返すと、worker 0 が run を終える
   - `exit n` は今と同じく自分のタスクのスタックを底まで巻き戻し、底が `Control` の終わりの欄に終了コードを書く。最初の書き手が勝つ (CAS) ([非同期の設計](async.md) の「失敗と `exit`」)
   - `par` の子の外での worker k の致命的な誤り (`eml_fatal`、または VM の `step` の `Err`) と、`par` の子の中のヒープの誤りと内部の誤りは、run の致命的な誤りの欄に最初の書き手として書き、すべての worker の止める語に終わりのビットを立てて起こしてから、自分のエントリへ切る。終了コードの欄 (`Control::exit`) に書くのは `exit` の底だけである。`par` の子の中のそのほかの実行時エラーは子の境目まで切って join の節点に記録し、親が左の子を終えてから報告する (上の「`par` の意味」)
   - 待つ者のないシグナルでは、handler がすべての worker の止める語に立てたビットを worker 0 が見て、割り込みか `TERMINATE` の誤りで run を終える (下の「シグナル:」の項)
2. 止めるビットと終わりのビットを書いた者が、待っているworkerを起こす。runの外の書き手 (シグナルのhandlerなど) の代わりには、監視のスレッドが、止める語にビットを見てすべてのworkerを起こす。受け箱での待ち、joinの節点での待ち、I/Oのdriverでの待ち (workerを起こすインターフェースで)、メインのworkerの`Park`での待ち (`Park`のwakerで) のどれも起きる。監視のスレッドを始められなかったrunだけは、VMが1回の待ちを10 msで切る ([VM](../spec/vm.md) の「時計とdriver」)。`Machine`を持つスレッドはworker 0をjoinするまでSIGINTとSIGTERMを塞いだままで、workerをjoinする間 (workerがI/Oのdriverを空にし、プールの仕事を待つ間を含む) の2回目のCtrl-CとSIGTERMは、worker 0のスレッドのhandlerでその場の終わり (`_exit(130)`と`_exit(143)`) に届く
3. 各 worker は次の安全点でビットを見て、自分のエントリへ戻る。VM の worker は今と同じく `step` から `Err(Stop)` を返し、ネイティブの worker はエントリへ longjmp する。フレームの後始末はしない。エントリへ戻った worker は、I/O の driver を持っていれば自分のスレッドの上で空にしてから、自分の `Ctx` を worker 0 に返して終わる。driver はそのスレッドから動かないためである。空にする手順は保留の操作を取り消し、ファイルの仕事は完了がすべて届くまで待って捨てる。`Op::Job` は run で合わせて予算 (1 秒) まで待ち、残りを見捨てる
4. worker 0 が次の順で後を片付ける
   1. すべての worker を join する。致命的な誤りの欄が埋まっていれば、その誤りを worker 0 の結果より先に報告する
   2. すべてのヒープで、ほかのスレッドから受けた解放を取り込む
   3. Host を書き出す。`> out 2>&1` で、出力が誤りより前に出るようにするためである
   4. 成功した run では、ヒープを確かめてからヒープ 1..N-1 を落とす。誤りか捨てた run では、N 個のヒープを回復する (上の「別のスレッドからの解放」)。落とすヒープのファイナライザがファイルとソケットを書き出して閉じる
   5. `Machine`を持つスレッドは、自分のメインのworkerの繰り返しが戻った後でworker 0をjoinし、すべてのヒープを畳み込み (メインのworkerのヒープを最後に)、`END`を下ろして、終了コードで終わる。どのスレッドもメインのworkerを待たない。長いexternかtoolkitのモーダルなループの中の固定したタスクが遅らせるのは、この最後の終わりだけである。`main`の正常な終わりは0、`exit n`は`n & 255`、割り込みは130、`TERMINATE`は143、ほかの実行時エラーと、Hostの書き出しの失敗は1である。実行時エラー (割り込みと`TERMINATE`を含む) は今と同じく1回だけ報告する

- 待ちのタスクと実行待ちのタスクは巻き戻さない。その継続はヒープとともに放され、`Lin` の資源はファイナライザが後始末する (継続を捨てる強い取り消し。[非同期の設計](async.md) の「強い取り消し」)。ほかの worker の上のフレームごとの後始末はしない
- シグナル: handler の手順は今と同じである ([VM](../spec/vm.md) の「上限と割り込み」)。そのシグナルを `Signal.wait` で待つタスクがいれば (見張りの語に立っていれば) `Control` の保留の語に入れ、いなければ `Control` の止める語とすべての worker の止める語に立てる (Ctrl-C は `INTERRUPT`、`SIGTERM` は `TERMINATE`)。どちらでも自己パイプを鳴らして監視のスレッドを起こす (上の「スレッドと worker」)。Windows ではコンソールの handler (`SetConsoleCtrlHandler`) が同じ手順で動く。CTRL_C は `INTERRUPT`、CTRL_CLOSE と CTRL_SHUTDOWN は `TERMINATE` である。監視のスレッドは保留のシグナルを run の mail へ中継し、すべての worker の止める語に `NOTICE` を立てる。最初に集めた worker が、登録表の lock の下で待つタスクに届ける。届けるときに聞く者のいなかったシグナルは、その worker がすべての止める語にビットを立てて run を止める。`INTERRUPT` では 130 で、`TERMINATE` は 143 で終わる
- `signalfd` と `EVFILT_SIGNAL` は使わない。どちらもすべてのスレッドでシグナルを塞ぐ必要があり、今の handler とブロックする読みの `EINTR` の道と食い違う
- 2回目のシグナルの扱いは今と同じである。`eml run` の handler は、止める語か保留の語に同じシグナルが立っていれば、その場で終わる (Ctrl-C は `_exit(130)`、SIGTERM は `_exit(143)`。[VM](../spec/vm.md) の「上限と割り込み」)。どちらの語も `Control` に1つなので、worker が増えても判定は変わらない
- REPL では、`exit` と致命的な誤りで評価が終わる。REPL のセッションは根を持つので worker 1つで動き (上の「スレッドと worker」)、worker 0 が自分の I/O の driver を空にし、実行中の操作と、予算までのプールの仕事を待ってから回復する。予算の後もまだ走る仕事は見捨て、入力はいつもどおり回復し、セッションは続く ([VM](../spec/vm.md)の「追記」)。REPL で複数の worker を使うには、入力の間もヒープを生かす静止の手順か、run の終わりに根から届く物体を写すことが要る ([ロードマップ](roadmap.md) の「マルチコア対応」)
- 分かれたrunでは、worker 0の本体は、worker 1..N-1をjoinし、結果を決め、`Machine`のdriverを静止させたところで終わる。4の残りは、両方のjoinの後で`Machine`を持つスレッドが行う ([VM](../spec/vm.md)の「誤り、止めること、終わり」)

## VM とネイティブのランタイム

- VM とネイティブは共通ランタイム `eml_rt` と `eml_sched` を使う ([オブジェクトモデル](../spec/object-model.md))。共有の印方式の RC (上の「スレッドをまたぐ RC」) は、`eml_rt` に入れ、両方で使う。実行時の検査は、`eml_rt` の検査モードが受け持つ
- VM とネイティブのコードは混ぜない。VM は参照の実装で、検査モードを持つ唯一の実行系である ([ネイティブ化の設計](native.md) の「確定した設計判断」)
- VMはworkerのスレッドの上で`par`の右の子と`Async`のタスクを動かす。タスクは`start`のときにworker 1..N-1を順に回って置き、worker 0には置かず、終わるまでそこから動かない。本物の時計のrunでは各workerが自分のdriverを持ち、ソケットは作ったdriverに縛る。受けたソケットは縛らずに作り、最初に操作を受け付けるworkerのdriverに縛る。driverの操作はソケットを縛ったworker (仮想の時計のrunではdriverを持つworker 0) が受け付け、結果はタスクの持ち主のworkerが当てる

### VM も並列にする理由

並列化をネイティブのランタイムだけで行う案は、次の2点から採らない。

- **検査モードを持つのが VM だけである**。印付けの漏れ、移し戻し、所有者の検査、漏れの検査は検査モードで確かめる。VM を並列にしなければ、並列の安全性を確かめる実行系がなくなる
- **確かめる時期が遅い**。ネイティブ化は `Async` と FFI と GUI の後に進める ([ロードマップ](roadmap.md) の「段の列」)。共有の印付け、別のスレッドからの解放、上の「不変条件」は、それまで実装で確かめられない

VM を並列にする費用は小さいと見積もっている。evidence passing で継続はヒープのクロージャになり、実行の文脈 (`evv` と yield の状態) は `Ctx` として worker ごとに1つ持てばよい ([LIR](../spec/lir.md) の「実行の文脈」)。RC の分岐は不死の物体 (0) を区別する比較に負の側を足すだけで済む。`par` と `Async.run` は構造化された並行性なので、REPL の入力の境目では worker が1つも動いていない。

### VM の並列化の備え

次の制約を守り、VM の並列を広げられるようにする。

| # | 制約 |
|---|---|
| 1 | VM の状態は `Ctx` と `Task` (呼び出しのスタックとレジスタの枠) に置き、スレッドに局所的な大域変数を持たない |
| 2 | `CodeBase` は追記だけにし、実行中は読むだけにする (`Sync`)。不死の定数は凍結した塊 `Frozen` に置くので、`CodeBase` の `Sync` は `Frozen` の `Sync` に頼る ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」) |
| 3 | 共有の経路は、`par` の fork と join で必ず通す (上の「`par` の印付け」) |
| 4 | `par` の fork と join は VM が持ち、印付けと移し戻しは `eml_rt` の `share` と `transfer_back` を通す。逐次の関数も1つの実装として持つ |
| 5 | VM の呼び出しのスタックは、Rust の再帰でなく、タスクが持つデータにする。extern が閉包を呼び戻す入れ子の中では、タスクを切り替えない |
| 6 | join と `Async.run` で待つ VM の `Task` は、worker のループを入れ子にせず、worker を手放して待つ |
| 7 | タスクを切り替えるのは、yield の状態がなしの安全点だけにする。切り替えで退避する実行の文脈は `evv` だけである |
| 8 | runの全体を進める務め (時計、デッドロックの判定、`END`、workerを作ることとjoinすること、ほかのworkerのI/Oのhost、監視のスレッド) は、待ちを替えられるworkerと、固定したタスクを動かすworkerに置かない |
| 9 | メインのworkerは、I/Oと空きの数え方ではほかのworkerと同じに扱う。替えられるのは待ちだけである |

- SIGINTとSIGTERMのハンドラは`SA_RESTART`なしで入れ、待っている読みを`EINTR`で止める ([VM](../spec/vm.md) の「上限と割り込み」)。worker 0のほかのスレッド (worker 1..N-1、監視のスレッド、名前の解決のスレッド、プールのスレッド、`CaptureHost`が子の出力を読むスレッド) は2つのシグナルを塞いで始まり、`Machine`を持つスレッドはworker 0を作ってからjoinし終えるまで2つを塞ぐ。そのため、SIGINTはworker 0のスレッドに届き、そこで読んでいる読みを止める。止める手順の間の2回目のCtrl-Cもworker 0のスレッドのhandlerに届く (上の「止める手順」)

制約1と制約2の型の性質は、`Session` の `Send + Sync` の試験 (`crates/eml_cli/tests/api.rs`) と同じ形の、型の assert で固定する。`crates/eml_vm/tests/api.rs` が `CodeBase<M>: Sync` と `Task: Send` を固定している。

VMは実行の状態をワーカーごとの`Ctx`と、タスクごとの`Task` (呼び出しのスタック、命令の位置、今のフレーム) に分けている ([VM](../spec/vm.md)の「スロットとスタック」)。`perform`で止まったタスクの続きはヒープ上の継続のクロージャになるので、継続は`Task`の外にあり、クロージャの語を1つ持つだけで済む。まだ始まっていないタスク (`spawn`に渡す閉包、`par`の右の子) は、クロージャの語を1つ渡すだけでほかのworkerに置ける。安全点で切り替えたタスクと、joinで子を待つ親だけは、スタックの途中で止まっているので`Task`ごと持ち続け、workerから動かさない。

語をほかのスレッドへ公開するのは、ランタイムのプリミティブ (fork、join、`spawn`、channelの送り、プールの仕事) の中で、上の「印付けの表」の扱いを通す道だけにする。VMは語をほかのスレッドに渡す経路を持たない。`Word`は`Send + Sync`なので型では守れず、文書の決まりにする。破った場合は、検査モードの所有者の検査が見つける ([オブジェクトモデル](../spec/object-model.md)の「論理的なworker ID」)。

### 1つの worker での実行

worker が1つの VM でも、`par` と `Async` は協調的なマルチタスクで動き、複数の worker のときと同じコードの経路を通る。複数の worker の run では、`Async` のタスクも各 worker の上で同じ形で動く。

- `par` の右の子をタスクにし、左の子は親のタスクがそのまま実行する。右の子は新しい論理的な worker ID で動く
- スケジュールの方針は3つある
  - 普通の方針 (`Normal`): タスクは`Async`の操作で待つか終わるまで動く。実行待ちはFIFOである ([VM](../spec/vm.md)の「タスクとスケジュール」)
  - 逐次 (`Sequential`): タスクが待つときだけ切り替える。`par`では左の子を終えてから右の子を動かす。`RunStats`を固定するテストとベンチの既定で、ライブラリの既定 (`Sched::default()`) でもある。`eml run`と`eml repl`はいつも`Normal`で動く
  - seed で決まる方針 (`Seeded`): seed で決めた安全点の数で切り替え、実行待ちから次のタスクを seed で選ぶ。テストに使い、失敗したときは seed を表示して再現できるようにする
- タスクは、yield の状態がなしの安全点でだけ切り替える。そのため、切り替えで退避する実行の文脈は `evv` だけである。`evv` と論理的な worker ID は `Ctx::switch_task` で一緒に替える ([オブジェクトモデル](../spec/object-model.md) の「タスクの切り替え」)。`par` の子は、fork のときに作る fork evidence の列 (親の `evv` の never-only のエフェクトの evidence を写した鏡) を `evv` にして始め、親の evidence は子をまたがない
- 実行を止める情報 `Control` (止める理由のビットを持つ止める語、確保量、上限、終わりの欄) は run に1つで、どの worker の `Ctx` とヒープも `Arc` で共有する。確保量は、worker ごとのヒープが取ったページを足し合わせた量になる ([オブジェクトモデル](../spec/object-model.md) の「実行文脈 `Ctx`」)。出力とファイルを扱う Host も run に1つで、どの worker の `Ctx` も同じ Host を `Arc` で共有する。Host は1行をロックの中で書くので、worker の出力は行の途中で混ざらない ([オブジェクトモデル](../spec/object-model.md) の「extern」の「Host」)
- 受け箱は1つのworkerでも動き、N = 1の本物の時計のrunでは監視のスレッドも動く。N = 1でも、監視のスレッドが中継するシグナルと、書く側が`Control`の止める語とworkerの止める語の両方に書くことを確かめられる

### ネイティブの並列

ネイティブのコードでは、どの worker も自分の `Ctx` を持って `eml_enter` から eml のクロージャに入る。join では待たずに手伝い、`Async.run` ではループを入れ子にする。致命的な誤りは上の「止める手順」で止める。詳細は [ネイティブ化の設計](native.md) の「並列の実行」にある。

## テスト

並列化では次の方針でテストする。テスト全体の方針は [テスト戦略](../implementation/testing.md) にある。どのテストも1秒以内に終わり、結果がマシンの速さによらない。刻みはテストの刻みの源で進める。

- 共有の経路 (今の `eml_rt`): `share`、負の RC の `dup` と `decref`、最後の参照での解放、共有した物体を reuse しないこと、所有者の検査、別のスレッドからの解放と取り込みを、`eml_rt` の単体テストで確かめる。`unsafe` の核を含む `eml_rt` 全体を Verus で証明し、証明は1つのヒープの逐次の実行を扱う。atomic の操作 (信頼の一覧の T2)、ほかのヒープのページに触れる関数 (T14)、run の表 (T15) は信頼する部分で、Miri が2つのスレッドのテストで、ThreadSanitizer が実際に走るスレッドの上で確かめる ([テスト戦略](../implementation/testing.md) の「`eml_rt` の検証」と「ThreadSanitizer」)
- `par` の UI テスト: `run/par/` と `run-fail/par/` の UI テストを `Sequential` と2つの seed で走らせ、出力がバイト単位で一致することを確かめる。seed で走らせるのは `par/` と `async/` の分類だけである。`par` も `Async` のタスクもないプログラムはタスクを切り替えないためである。seed で走らせると、どちらのタスクが最後に `decref` するかと、タスクの中断、再開、join の待ちも確かめられる。失敗したテストは seed を表示し、その seed で再現できる。`RunStats` は `Sequential` で固定し、seed の run ではスケジュールによらない欄を比べる ([テスト戦略](../implementation/testing.md) の「seed で流す」)。`par/` は、検査モード、逐次の方針、仮想の時計のまま worker の数を N = 2 と 8 にしても流し、N = 1 と同じ出力とスケジュールによらない `RunStats` を返すことと、所有者の検査と漏れの検査を通ることを確かめる。N = 1 のスナップショットはそのまま保つ。負の試験 (multicoretests の負の試験に当たる) は常設のテストが受け持つ。fork の印付けを外すと `run/par/shared_capture.em` が `WrongOwner` に、join の移し戻しを外すと `run/par/fresh_result.em` が `TransferLeak` になる。ほかに、`poly` で作った `Lin` の物体が rc == -1 で届くこと (検査モード。`run/par/poly_lin_resend.em`) と、実行時エラーの優先の規則 (上の「`par` の意味」) を確かめる
- データ並列の関数を足す段階 (ロードマップの `std-par`): 右を先に動かすスケジュールでの `try_map` のいちばん左の `Err`、粒度を変えても `fold` の浮動小数が同じビットになること、ほかで共有した箱の要素を `for_mut` すると印が付き、一意なら付かないことと、一意な要素を書き換えても子と親のどちらでも `WrongOwner` にならないこと (検査モード) を確かめる
- `Async`: [非同期の設計](async.md)の「テストと決定性」に従う。`tests/ui/run/async/`はN = 1で逐次と2つのseedで流し、どのseedでも同じ出力を返す ([テスト戦略](../implementation/testing.md)の「seedで流す」)。N = 2と8の逐次でも、検査モードの漏れと所有者の検査を流す。すべてのworkerが待っているrunに試しの`SIGTERM`を送ると、`Signal.wait`で待つタスクに届き、待つタスクがなければ143で終わることも確かめる。CPUを使い続けるタスクがあっても、`Control`を読まないworkerが割り込みを1刻みのうちに見ること、漏れの検査が受け箱の語を見ることも確かめる
- 複数の worker: `par/` の N = 2 と 8 の run は上の項にある。`async/` も N が 2 と 8 で流し、順に頼るファイルは印で外す ([テスト戦略](../implementation/testing.md) の「seed で流す」)。`std/Par` の集まりの関数では、浮動小数の `fold` も含めて N = 1 と比べる。`RunStats` は逐次でだけ固定する。ほかに次のものを使う
  - 手伝い: 深くて偏った `par` の木が手伝いを入れた N = 2 で終わること (進むことの試験)
  - Verus: 今の逐次の証明 (信頼の一覧のT0とT14) を並行の証明に置き換え、ほかのヒープの物体を証明の模型に入れて、印付けと公開、両側からの`dup`と`decref` (共有の側の2つの境目の並行の議論を含む)、最後の解放、joinの手順を証明する。vstdのatomicはSeqCstだけを扱うので、RelaxedとAcqRelの順序の正しさはVerusでは確かめられない。順序は文書の議論とMiriに任せる ([テスト戦略](../implementation/testing.md)の「Verus」)。`eml_sched`はVerusの外にある。協調的な配置 (持ち主を`start`で一度だけ決めること、知らせを持ち主へ送ること、`park_idle`と`wake`で起こしを取りこぼさないこと) の証明は、ロードマップの項目である。置き換える時期は[ロードマップ](roadmap.md)の「マルチコア対応」にある
  - Miri: `eml_rt` の `trusted` の module と `eml_sched` の並行のテスト (strict provenance、many-seeds)。遠隔の空きリストへの返却と取り込み、deque、受け箱の受け渡し、rc の裏返し、範囲への書き込みを確かめる。`par` を使う小さい UI テストを VM ごと走らせる。右の子を worker 1 に置く run は、1つのテストの Miri の費用の上限を超えるので、今は置いていない ([ロードマップ](roadmap.md) の「処理系」)
  - TSan: CIの`tsan`のジョブが、`eml_rt`の`trusted::`と、`eml_vm`の`workers::`、`signal::`、`io::`、`chan::`、`seat::`、`pinned::`とlibの`counters::`を流す ([テスト戦略](../implementation/testing.md)の「ThreadSanitizer」)。RCの語の誤りは見えず、フィールドの競合として結果だけが見えることを前提にする
  - work stealing の deque は自作し、スロットを atomic の語にして、crossbeam-deque の意図的な競合を避ける
  - 試験ごとに新しいプロセスとタイムアウトで動かすストレス試験
- メインのworker: 固定したタスクが`Machine`を持つスレッドで動き (記録するHostで確かめる)、そこから動かないこと、`run()`を呼ばない`Park`でも`main`が同じ出力で終わること、外の待ちを抱えると知らせる`Park`が両方の時計でデッドロックの判定を遅らせることを確かめる
- 回復: `Async.run` の中の実行時エラーの後の回復と、N 個のヒープでの回復を確かめる

## 未決の論点と将来の拡張

- **`par` の子の取り消し**: 既定は入れず、すべての子の完了を待つ。左の子が中断したときに長い右の子を止めたいとき、または `compute` の周りの `timeout` をすぐに戻したいときに入れる。入れるときは、右の兄弟だけを取り消し (`try_map` と同じ規則)、安全点で協調的に中断し、中断した子の `Lin` の値を `drop k` と同じ後始末の情報で解放する。それまでも、子の実行時エラーは上の「`par` の意味」の左を先にする規則で報告する。残る論点は、N が 2 以上で `debug_heap` が報告するリークと不変条件の違反を、スケジュールによらず同じ内容で出すことである
- **逐次実行と同じ意味の `par_ordered`**: 任意の row を許し、右の子を最初の perform まで投機的に実行する。意味は逐次実行と完全に一致する。「perform の手前で止まる」プリミティブが実行系の核に必要になる。既定は作らない。`never` でない操作を持つ子を逐次と同じ意味で並列に動かしたいときに考える
- **`par` の子から `IO` とすぐに再開する操作を外に出す**: Kind の束の `Never` と `Once` の間に `Tail` を挿入する案。`IO` の extern の関数は handler を通らずにその場で実行するので、子のスレッドでもそのまま実行できる。ただし、IO の失敗は最も近い `try_io` まで中断し、`exit` は実行の底まで中断する ([VM](../spec/vm.md) の「extern の中断」)。子でこれが起きると中断が子をまたぐので、子の底を中断の境目にし、`try_io` と `exit` が子をまたぐ意味を決める必要がある。それまでは、`exit` が `<IO>` を持つことで、`par` の子から `exit` を呼べない ([標準ライブラリ](../spec/stdlib.md) の「`exit`」)。ユーザー定義の操作にはエフェクトの宣言に「すぐに再開する操作」の種類 (`tail`、Koka の `fun` に当たる) を足し、子から外に出る操作を `par` ごとのロックで直列化する。どちらの場合も、子どうしの `IO` と操作の順序は非決定的になる。後から挿入しても既存の制約 (`σ ≤ Never`、`σ ≤ Once`) の意味は変わらず、受け付けるプログラムが増えるだけである。既定は入れない。子からの出力が `both` で足りないときに考える
- **`fork` と `join` を普通の関数として公開すること**: 既定は公開しない。`par` と集まりの関数で足りる。不規則な並列が要るときに考える
- **Float の箱を要素ごとに作らないこと**: `Par.tabulate_unboxed` の関数の結果の `Float` は要素ごとに箱になる。案は2つある。結果の型の付いたクロージャのエントリ (`f$ret`) か、1次のループで書く葉の範囲のプリミティブである。`std/Par` の集まりの関数を入れるときに、固定した `RunStats` の行で測って決める
- **private deque**: 印付けを実際に盗まれた子だけに限る最適化 (Acar らの方式)。既定は入れない。共有の集合がスケジュールに依存し、固定した `RunStats` が崩れるためである。印付けがプロファイルで目立つときに考える
- **ロックフリーの受け箱と channel**: 既定は mutex で、Miri で確かめられる。N が 8 以上で競合を測ったときに、同じインターフェースの後ろで替える
- **タスクを置くworkerの選び方**: 既定はworker 1..N-1を順に回す。偏りを測ったときに、実行待ちと待ちの集まりのいちばん短いworkerを選ぶ形にする
- **ページを OS に返すこと**: 既定は返さず、RSS は worker のヒープごとの最大の和である。サーバの RSS が育ち続けるときに考える
- **待ちのタスクが持つメモリを数えること**: 既定は、タスクが動く間の確保だけを数える。柔らかい上限が違うタスクを選ぶときに考える
- **監視の値**: 監視の刻み (10 ms) は[VM](../spec/vm.md)の「タスクとスケジュール」にある。ほかの既定は、プールの上限が32、遠隔のリストを取り込むしきい値が256、粒度が1024である。どれも段ごとの計測で決め直す
- **ネイティブの `Async.run` の入れ子**: 入れ子の順が逆になりうる。既定は許し、文書に書く。`Async.run` は `main` から呼ぶのがよい
- **Windows のコンソールの標準入力の読みへの割り込み**: 今は、Ctrl-C で戻った `ReadConsoleW` を std がその場で読み直すので、割り込みは読みが戻った後で見る ([VM](../spec/vm.md) の「上限と割り込み」)。std を通さずに `ReadConsoleW` を呼び、Ctrl-C での中断を `Interrupted` で返す読み手を標準入力にすれば、unix と同じく読みの中で止まる。既定は入れない。`Stdin` の読みを待つ間の1回目の Ctrl-C が見えないことが問題になったときに入れる
- **worker 0 のほかの worker でのその場の同期の読みへの割り込み**: SIGINT は worker 0 のほかのスレッドで塞ぐので、そうした worker でその場の `Stdin`、`FileIn`、`Child` の読みをしているタスクには `EINTR` が来ない。入れるときの既定は、`INTERRUPT` を見た監視のスレッドがその場の同期の読みの中にいる worker へ `pthread_kill` でシグナルを送って `EINTR` を起こす形である。入れるまでは、そうした読みはデータが来たときにだけ戻り、止める手順の join もそれまで待つ
- **`poly` の物体のビットの実行時の伝播**: `poly` の `con` でフィールドの `lin` ビットの OR を取り、実行時に伝える案。`MutArray` は要素を `Unr` に固定しているので決めていない。`Lin` の要素を持つ配列を入れるときに決める
- **読むだけの共有**: OxCaml は、`par` の子が親の環境を読めるが書けない形を持つ。eml の `par` の子は親の `Ref` を読めない。表現力の不足として現れたときに検討する
- **局所的な可変変数**: エフェクトで作る `var` としてある ([式](../spec/expressions.md) の「`var`」)。変数の値は地点ごとのエフェクトの handler が持ち、可変参照と `Heap` には依らない
- **`IO` が大域的な領域を含む折衷案**: Koka のように `IO` が `Heap Global` を含む形。便利だが、大域的な領域の読み書きには同期が必要になる。必要になったら検討する
- **「`Heap` を含まない row」の制約**: 子タスクの row を多相に開いたまま `Heap` だけを除外できると、並行処理の API の柔軟性が上がる。[ロードマップ](roadmap.md) の「型システム」にある「row 要素ごとの捕捉 Kind」と同じ種類の拡張として扱う
