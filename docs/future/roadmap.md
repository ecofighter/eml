# ロードマップ

位置づけ: 将来の設計。

今後の実装を、項目ごとにまとめる。今の言語の範囲は [実装の現在地](../implementation/status.md) の「今の言語の範囲」にあり、確定した設計判断は [概要](../overview.md) にある。

## 進め方

- 各段は、設計、計画、実装、閉じる作業の順に進める。設計は、この文書のその段の項目を出発点にし、設計と計画は`docs/plans/YYYY-MM-DD-<段>.md` (付録を分けるときは同じ名前のディレクトリ) に書く。承認したものを段の最初のコミットで入れ、途中で変えたときもコミットする
- いくつかの段をまとめて計画したときは、それらの段の計画のファイルと共有の付録のディレクトリ (`docs/plans/YYYY-MM-DD-<まとまり>/`。日付と、まとめた段の群の名前を付ける。例: jitの段の群なら`YYYY-MM-DD-jit/`) を、最初の段の最初のコミットで一緒に入れてよい。後の段は、その段の最初のコミットで、自分の計画を実行できる計画に書き直す
- 「決めたこと」は方針で、細部はその段の設計で決める。「論点」は、その段の設計で決める
- 機能を足さず、実装の整理だけを行う段は「段の列」に載せない。ただし、「段の列」に載せた段が前提に名指すリファクタの段と、公開のAPIが保証することを変える段は載せる。設計と計画を`docs/plans/`に置くことと、閉じる手順は、ほかの段と同じである
- `spec/` は段の中で書く。規則を実装するコミットと同じコミットで `spec/` の節を書き、コードのコメントはその節を引く。設計の文書は引かない。段を途中でやめるときは、コードと `spec/` を一緒に戻す
- テストの変更は、段の設計に、[テスト戦略](../implementation/testing.md) の「テストの変更の運用」の種類 (成否の変更、期待値の変更、機械的な追随) で書く
- 段で後に回した項目は、この文書の「その後の項目」に書き、項目の下に「後に回した理由: …。」と「見直す条件: …。」の入れ子の箇条を置く。決めた日と決め手は書かず、閉じるコミットのメッセージに残す
- 段を閉じるときは、次の順に文書を直し、1つのコミット (`Close <段>`) にまとめる。順序は引用の向きで決めてある
  1. `spec/` を仕上げる。段の名前と「今は〜、後で〜」の予告が残っていないことを確かめる
  2. 計測する。前の表のコミットから `crates/eml_vm`、`crates/eml_rt`、`crates/eml_lir`、`crates/eml_core_ir`、`std/`、`bench/` のどれかが変わった段だけが対象である。まず `bench/scripts.sh` を流し、実時間が範囲を外れた行があれば `bench/scripts.sh` の大きさを変えて別のコミット (`Resize bench rows`) にする。次に `bench/run.sh`、`bench/rt.sh`、`bench/scripts.sh` をコードの最後のコミットの作業ツリーで流し、[計測の基準](../implementation/benchmarks.md) の「今の数値」の表を入れ替える。段が変えた規則を根拠にしている「所見」は測り直して更新するか消し、今後も判断の根拠になる計測は題名の見出しで足す。測れる環境がないときは、表の入れ替えだけを直後の別のコミット (`Measure <段>`) にする
  3. [実装の現在地](../implementation/status.md) の範囲と制限を直す
  4. [コンパイラの構成](../implementation/architecture.md) を、crate かパスの構成が変わったときに直す
  5. この文書からその段の節を消す。残した項目は「後に回した理由」と「見直す条件」を添えて「その後の項目」へ移し、「前提」に書いた段の名前を項目の名前に直す
  6. [概要](../overview.md) の確定した設計判断の表と、[文書の地図](../README.md) の「文書の地図」の「内容」の欄を、変わった所だけ直す
  7. `CLAUDE.md` を、規則か道しるべが変わったときだけ直す
  8. `docs/plans/`から、その段の計画のファイルだけを消す。まとめて計画した段の共有の付録のディレクトリは、それらの段の最後の段を閉じるときに消す。そのため、それらの段の間も`main`に`docs/plans/`が残る。消す前に、`docs/`に残っていない決めがないことを確かめる
  9. コミットのメッセージに、文書で何をどこへ移したか、テストの変更の種類と理由、計測の目立つ差、大きさを変えた行、機種が変わったこと、後に回した項目の決めた日を書く。段の名前と日付はここに残る
- 段は、パイプラインの段階 (crate) とは別の呼び方である

## 段の列

次に進める段を、進める順に並べる。各段の設計はここに書いた中身と「設計」の文書の節を出発点にし、範囲と完了の条件をその段の設計で決める。「前提」は先に閉じておく段である。

- `jit-externs`: すべてのexternの行 (`Std.Gui`の行も含む) を、ネイティブのコードから呼ぶ。包みとVMの腕を表から作り、externの失敗を`Ctx.fault`で返す。タスクの操作でない`Std.Tls`と`Std.Gui`の行は、feature `tls`、`gui`、`gui-native`を引き継いで`eml_sched`へ移す。`blocking`でない利用者のCの行をネイティブのコードから呼ぶ。前提: ネイティブのコードの関数の値と`apply` ([ネイティブの実行系](../spec/native.md)の「関数の値」)。設計: [ネイティブ化の設計](native.md)の「extern のエントリ」
- `jit-effects`: エフェクトの操作をネイティブのコードで動かす。yield、戻り値で伝える中断、handlerを入れる。evidenceの欄の役割 (`evv`の節の`[evidence, next]`と、evidenceの`[入口の表, 状態, 外側のevv]`) を、`Ctx`の面 (コンストラクタか役割の定数かは、この段のエフェクトの設計で決める) に移す。同じ段で、`eml_vm`の`vm.rs`と`compile/forks.rs`、`eml_rt`のevidenceの証明の補題にある役割の番号を消す。前提: `jit-externs`。設計: [ネイティブ化の設計](native.md)の「中断と実行時エラー」
- `jit-tasks`: タスクの層をネイティブのコードで動かす。workerの表、受け箱、監視のスレッド、プールの仕事を、`Exec`の後ろに置いて`eml_sched`へ移す。`Exec`と`IoDriver`の上の`Async`のエントリ、ネイティブの`Async.run`の入れ子、親ごとに1つのworkerの上の`par`、致命的な誤りの手順、安全点での上限の中断を入れる。入れ子の`Async.run`は後に入ったものから先に終わり、外側を先に終えないと進めないrunは`BuriedRun`で終わる。上限の種類は、実行系のworkerごとの状態に置く。`blocking`の利用者のCの行も入れる。この段で、E0004で断る形がなくなる。メインのworkerの繰り返し (`eml_run_pending`の役目。Cの記号は`native-aot`で入る) と、メインのworkerの致命的な誤りの道も入れる。前提: `jit-effects`。設計: [ネイティブ化の設計](native.md)の「並列の実行」、[マルチコア対応の設計](multicore.md)の「層の構成」
- `jit-repl`: REPLをネイティブのコードで動かす。名前で足すコード、セッションの根、致命的な誤りの後の回復を入れる。前提: `jit-tasks`。設計: [ネイティブ化の設計](native.md)の「確定した設計判断」
- `engine-trust`: エンジンが受け取るプログラムを`eml_lir::Trusted`だけにする。VMとネイティブのマシンのエントリは、`eml_lir::Program`を受け取って信頼する安全な関数である。速いモードとネイティブのコードは実行の前提 ([LIR](../spec/lir.md)の「実行の前提」) を確かめず、安全なRustのコードは前提を破るプログラムを組めるので、今は安全なAPIから未定義の振る舞いに届く。`Trusted`は、作る側が`unsafe`のコンストラクタで前提を約束したプログラムで、テストの外では`Session`だけが作る。エントリが呼ぶ側に任せているほかの約束 (コードを持つマシンへ足すプログラム、`run`に渡すエントリの番号、`run_shown`の結果、差し替えた標準ライブラリ) も、型か実行時の確かめか`unsafe`で閉じる。エンジンの安全な関数がdocコメントで呼ぶ側に任せている約束をすべて挙げ、小さく閉じられるものはこの段で閉じ、残りは「その後の項目」に書く。言語の機能は足さない。前提: `jit-repl`。設計: [エンジンの信頼の境界の設計](engine-trust.md)
- `native-aot`: 3つのOSで`eml build`を動かす。`cranelift-object`でobjectを書き、システムのリンカでつなぐ。ビルドのプロファイル (`console`と`gui`) と2つの実行系の静的ライブラリ、実行系の通知のファイルもこの段で作る。出したobjectと`libeml_rt.a`が、`eml_rt`の同じネイティブのABI (物体の配置、`Ctx`のずれ、エントリのシンボル、externの語のABI) から来たことを、リンクのときに確かめる。識別子を`eml_rt`の定数からどう導くかは、この段で決める。Windowsでは、AOTのバイナリにも`/STACK:8388608`を付ける。前提: `jit-tasks`。設計: [ネイティブ化の設計](native.md)の「AOT と配布」
- `native-inline`: `String`と`Bytes`のバイトの読みと、配列の要素の読み書きを、ネイティブのコードで展開する。目標は、4本のスクリプトがRustの実装の2倍以内、スクリプトと数値のbenchがPythonの1.5倍以内であることである。`eml_rt::layout`に、`Raw`と`String`と`Bytes`の本体のための、種類ごとの語の添字の定数を2つ (長さの語は0、中身の最初の語は1) 足す。`Data`の項目は変えない。`eml_rt`の本体の箇所 (`slot_ptr(h, 1)`、`1 + i`、長さの語の読み、`8 * (cap - 1)`) はこの定数へ付け替える。`Array`の長さと要素の読みは`COUNT_WORD`と`EXTENDED_FIRST`を使う。前提: `native-aot`。設計: [ネイティブ化の設計](native.md) の「展開と最適化の前提」
- `par-steal`: VM の `par` の右の子を、空いている worker の受け箱に置く形から、worker ごとの Chase-Lev の deque と盗みに替える。join の待ちと、子の終わりを親の worker へ知らせる道は、今のものをそのまま使う。呼んだ worker に積んだ `compute` の仕事も、右の子と同じく盗まれる。今の実行待ちは、`par` の子と `Async` の仕事が混ざる worker ごとに1本の mutex の列で、切り替えのたびにその lock を取る ([VM](../spec/vm.md) の「タスクとスケジュール」、[計測の基準](../implementation/benchmarks.md) の「実行待ちの列の lock」)。`par` の子を deque に移した後に残る列の形も、この段で決め直す。前提: なし。設計: [マルチコア対応の設計](multicore.md) の「`par` の子」
- `std-par`: `std/Par` のデータ並列の集まりの関数と、添字の範囲のプリミティブを入れる。前提: `par-steal`。設計: [マルチコア対応の設計](multicore.md) の「データ並列での使い勝手」
- `native-par`: ネイティブのコードで、joinで待つworkerが手伝うfork / joinを動かす。前提: `native-inline`、`std-par`、`jit-tasks`。設計: [ネイティブ化の設計](native.md)の「並列の実行」

## その後の項目

まだ段にしていない項目を、分野ごとにまとめる。方針まで決まっている項目と、論点を挙げただけの項目がある。詳しい設計がある項目は、その文書へのリンクを付けた。「前提」は、先に済ませておく項目か段である。前提を書いていない項目は、どの段の後でも着手できる。

### 型システム

- 使い切り必須の型: 捨てることを許さない線形型。ユーザーが Kind を書けるようにする段階で、Kind に「drop できるか」の次元を追加して扱う。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- Kind の宣言化: シグネチャに Kind の境界を書き、Kind 推論を減らす。宣言にするなら、持ち越しの条件付きの制約を書く形が要る。`map`、`fold`、`keep` を注釈なしで書ける今の性質を失わないことを条件にする。ユーザーが矢印の線形性と `data` の Kind を書く記法はすでにある
  - 後に回した理由: スクリプトの5本の書き心地に関わらなかった。
  - 見直す条件: 注釈なしの推論では Kind が決まらないシグネチャが要るプログラムが出たとき。
- `<once e>`: row 変数の多重度の上限に `Once` を書けるようにする。足すのは文法の1トークンで済む ([型と Kind](../spec/types.md) の「row 変数の多重度の上限」)
  - 後に回した理由: 使う段がなく、`Tail` を束に挿入するかも決まっていない。
  - 見直す条件: `Once` の上限を使うシグネチャが要る段ができたとき。
- `data` の row の型引数の上限 (`data Task <never e> a`)
  - 後に回した理由: 型の適用ごとに制約を確かめる仕組みが要り、`par` には要らない。
  - 見直す条件: 上限を持つ row の型引数の `data` を使う段ができたとき。
- 操作の row 変数の上限
  - 後に回した理由: 操作ごとの row 変数は節の中で `Multi` 以上になり、上限と両立しない。
  - 見直す条件: 上限が節の規則 (`Multi` 以上) を置き換える設計を考えるとき。
- `:type` と診断での上限の表示
  - 後に回した理由: 表示のためだけに多重度の書き出しが要り、違反は E2020 が伝える。
  - 見直す条件: Kind の宣言化で Kind を一般に表示するとき。
- row 要素ごとの捕捉 Kind: `<IO, Async@lin>` のように、row の各要素に「捕まえてよい Kind」を推論で持たせ、`never` / `once` の持ち越し規則をより柔軟にする。マルチコア対応で挙がった「`Heap` を含まない row」の制約も、同じ種類の拡張として扱う ([マルチコア対応の設計](multicore.md))
- 借用: Rust / Austral 方式。意味論の大きな追加になる
- 関数型の深い包摂 (2段目より深い共変の位置、反変の位置、関数型の引数の矢印): 値を読む式は、一番外側の矢印と共変の1段だけを広げる ([型と Kind](../spec/types.md) の「値を読む式の矢印の線形性」)。`Option (Option (Int -> Int))` の値を2回使って `once` の位置に渡すことや、`Unr` の関数を受け取る関数を `Lin` の関数を受け取る位置に渡すことは、まだできない
  - 後に回した理由: 極性を持つ単一化の器 (すべての `unify` に向きを持たせる) か、読むたびに型の大きさに比例する写しが要る。写しは入れ子の深さに応じて2乗の時間になりうる。浅い形で書き直せば足りる。
  - 見直す条件: 入れ子の関数のコンテナを作り直す書き方が繰り返し要るとき、またはネイティブのコード生成が要るとき。
- 多重度の多相: `data` のフィールドの矢印の線形性を型引数で変えられるようにする。シグネチャの矢印は今も線形性を推論するので、要るのは `data` だけである。今は、閉包の型そのものを型引数にすれば書ける (`data Task f = | Task f`。`Task` の Kind は `f` に従う)。実用のプログラムで要る例が出たら、記法と、`data` の型引数の種類に多重度を足す形を決める。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- `Unr` の宣言: `data T : Unr` と書き、型変数のフィールドを持つ型を `Unr` に保つ。型引数への Kind の制約にすると「Kind の宣言化」に踏み込む。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- row の引数の省略: `data` の row の引数をすべて省いたとき、`<>` とみなす (`Iter a` を `Iter <> a` と読む)。矢印の row を省くと `<>` になる規則と対になる。後で入れても、今のプログラムの意味は変わらない
  - 後に回した理由: 宣言を知らないと引数の個数が読めない。
  - 見直す条件: `data` の row の引数を `<>` と書く手間が目立つプログラムが出たとき。
- 操作の引数の Kind 変数: 操作の引数の型に現れる Kind 変数は `Unr` に固定している ([エフェクトと handler](../spec/effects.md) の「handler の意味」)。線形な値を多相な操作の引数で渡せるようにするかを見直す
- 証拠が大きくなる制約付きの多相再帰: 今は型検査で弾く (E2012。[Core IR](../spec/core-ir.md) の「一様な位置と制約付きの多相再帰」)。必要な例が出たら、その場合だけ辞書渡しで許すかを見直す
- `Lin` の型を受けるクラス: 今のクラスはすべて `Unr` のクラスで、制約 `C a` は `a ≤ Unr` を意味する ([型と Kind](../spec/types.md) の「`Unr` のクラス」)。`Read` / `Write` のようにハンドルを受け取って返すクラスは、借用がなくても役に立つ。広げるときは、クラスの性質として `Lin` を受けるクラスを区別し、`Lin` を受けるクラスの instance の本体は頭の型変数の Kind に制約を足せない、という規則を置く。今のクラスの意味は変えない。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- orphan 規則をパッケージ単位に広げるか: 今の orphan 規則はモジュール単位である ([モジュールと名前解決](../spec/modules.md) の「instance の一貫性」)。パッケージの仕組みがまだないので、パッケージを入れるときに決める
- `closed` のクラス: instance を書けるのを std に限るクラス。`Unboxed` と `MutUnboxed` の instance は `Float` と `Int` だけで、ほかの型の instance は意味を持たない ([標準ライブラリ](../spec/stdlib.md) の「`Std.UnboxedArray`」)
  - 後に回した理由: 利用者の instance は使い道がないだけで、壊れることはない。
  - 見直す条件: 利用者が `Unboxed` か `MutUnboxed` の instance を書いて混乱したとき。

### 言語機能と構文

- 多相なローカル関数: ローカル関数は今は単相である ([型と Kind](../spec/types.md) の「ローカル関数の推論」)。シグネチャの書き方 (ブロックの中にシグネチャの行を書くか、`let` に型を明示するか) と、注釈のない汎化をするかを決める
  - 後に回した理由: スクリプトの5本で要る場面がなかった。
  - 見直す条件: 1つのローカル関数を違う型で使うプログラムが出たとき。
- 固定の優先順位の表: fixity の宣言をやめ、先頭の文字で決まる固定の優先順位の表にすること。整数の優先順位で、ライブラリ同士の演算子の衝突が問題になった場合の代替案 (Swift 方式の優先順位グループ) も、ここで一緒に判断する
- 字句的な負号: `f -1` を `f (-1)` と読む。GHC の LexicalNegation と同じである
- ブロック引数: 末尾の `fn`、`match`、`if`、`handle` を括弧なしで渡す。`fn () ->` が多い場合のサンクの糖衣も一緒に判断する。今は `use` とセクションで足りると判断している。今は `use` を文の位置にしか書けないので、式の途中では `Some (use …)` のように書けない。`tests/ui/run/scripts/grep/main.em` の `search` は `use try_io` を `let found =` のブロックに入れている
- 省略した row の暗黙の row 変数 ε: 今は省略した row を `<>` と読む ([型と Kind](../spec/types.md) の「関数型」)。高階関数で row 変数を書く量が負担になるなら、Frank の周囲の ability のように、1つのシグネチャの中で省略した row をすべて同じ暗黙の row 変数 ε とする規則に広げる。`map : (a -> b) -> List a -> List b` が `(a -> <ε> b) -> List a -> <ε> List b` になる。スクリプトの5本では、row 変数を書いたのは handler の関数と `use` で残りを受ける関数のシグネチャだけで、どれも1つだった
  - 互換の条件: 既存のシグネチャの型が、広げた規則の型の特別な場合 (ε := `<>`) になる形でだけ広げる。そのため、ε を入れるのは row を1つも書いていないシグネチャに限る。row を1つでも書いたシグネチャは、今と同じく省略を `<>` と読む。たとえば `twice : (Unit -> Unit) -> <IO> Unit` の引数に ε を入れると、閉じた `<IO>` の本体でコールバックを呼べなくなり、今は通るプログラムが通らなくなる
  - ε を入れるのはトップレベルのシグネチャだけで、`data` のフィールドの型には入れない。ローカルの型の明示とラムダの引数の型で省略した row は、推論用の row 変数に変えてもよい (型がより一般になるだけなので互換である)
- 同じエフェクトの2つ目のラベルを名指すこと: `<Yield a, Yield b | e>` の中で `yield (x : b)` と書くと、操作はいつも1つ目の `Yield a` に向かうので型の誤りになる。2つ目に届けるには、`mask` を書く構文 (Koka の `mask<yield>{…}`) が要る。型を変換する handler では、節が外側の row で動くので名指しは要らない (位置つきの `mask`。[エフェクトと handler](../spec/effects.md) の「handler の意味」)。実用のプログラムで要る例が出たら構文を決める
- 線形値の受け渡しの糖衣: `FileIn.read_all &input` を `let (r, input) = FileIn.read_all input` に脱糖する、Swift の `inout` 風の構文。API の返り値の形を縛ることと、巻き上げの規則が課題である。スクリプトの5本では `FileIn` が解析や中断の区間をまたぐ形が出なかった。`tests/ui/run/std/iter_file/` は `FileIn` を持つ生産者を `Iter` で引き、`match FileIn.read_line file with | (Some line, file) -> …` と組のパターンで `FileIn` を受け直す形で書ける。糖衣を入れるかはまだ決めていない
- トップレベルの値のコンパイル時の計算: 今はトップレベルの値の本体の row を `<>` に限るので、`Panic` を起こしうる計算 (`Int` と `Float` の算術を含む) を書けない ([エフェクトと handler](../spec/effects.md) の「組み込みの `Panic`」)。定数畳み込みとコンパイル時の計算を入れ、コンパイル時に `Panic` を起こさずに値が決まる本体を許す。コンパイル時に `Panic` を起こす本体は、コンパイルの誤りにする。下の「トップレベルの値を一度だけ評価すること」と、「処理系」の「Core IR の上の最適化パス」の純粋な extern の定数畳み込みと一緒に設計する。
- トップレベルの値を一度だけ評価すること: 今は参照するたびに計算する ([Core IR](../spec/core-ir.md))。一度だけ評価するのは、単相で `Unr` の値に限る。起動時に評価するか初めて使うときに評価するかと、実行時エラーの報告の仕方も決める。REPL で入力をまたいで残す束縛の評価と、意味を揃えるかも一緒に決める。評価した値を凍結すると塊が増える (下の「REPL」)
- 可変参照 (方針は決定済み): 値`Ref h a`と組み込みのエフェクト`Heap h`を持ち、`IO`と分離する。`run_heap`はrank-2の組み込みとして特別扱いする。`Ref`には`Unr`の値だけを入れ、multi-shotで再開したときの状態は共有する ([マルチコア対応の設計](multicore.md)の「可変状態」)。入れ子の`run_heap`の中から外側の`Ref`を使うには、同じエフェクトのインスタンスを区別する必要がある。名前付きのhandlerが要るかどうかを、入れるときに決める。`Ref`は循環を作れる (自分を捕まえたクロージャを入れた`Ref`)。参照カウントは循環を解放しない ([オブジェクトモデル](../spec/object-model.md)の「追跡型のGCを使わない理由」)。方針は、`run_heap`が自分の`Heap h`のセルを1つの領域として持ち、終わるときにすべて解放することである。`Ref`を通る循環は、その`run_heap`と一緒に消える。`Ref`を設計する前に、セルが何の参照を数えるか、`run_heap`の外へ出る値が領域の中を指さないことをどう保つか、`share`と`multi`の再開の下で領域がどう振る舞うかを決める
- フィールドの変換の糖衣: `{ p | age = _ + 1 }` のような、関数でフィールドを書き換える構文。`Lin` なレコードでも、分解せずに書けるようにする。今の更新は上書きされる古い値を捨てるので、`Lin` なフィールドは分解して組み直すしかない ([直積型とレコード](../spec/records.md) の「線形性の規則」)
- 型の別名: `type Name = T`。構文は予約してあり、今は `type` の宣言を HIR が E0004 にする ([宣言](../spec/declarations.md) の「`data` と `type`」)。別名を展開する位置 (HIR か型検査か)、型引数を持つ別名、診断での表示 (別名で書くか展開して書くか) を決める
- 再エクスポート: `pub import`
- 修飾した演算子の構文 (`Csv.(</>)`)
- 接頭辞付きリテラルの一般化: `re"..."` のように、ユーザーが接頭辞付きのリテラルを定義できるようにする。穴の型付けにアドホック多相が要る
- or パターン、ガード、as パターン: パターンを広げる。網羅性の検査 ([網羅性](../spec/exhaustiveness.md)) と決定木の変換を一緒に広げる
  - ガードには所有の制約がある。今の Perceus が `Lin` のフィールドを `dup` しないのは、決定木の途中で、後の行が持ち主を使うフィールドを消費しないことに依る ([LIR](../spec/lir.md) の「値の表現」)。ガードを入れると、ガードが呼び出しの引数として `Lin` のフィールドを渡し、後の行が持ち主を使う形ができる。フィールドを消費する時点で持ち主が必要なので、Perceus はそのフィールドを `dup` し ([LIR](../spec/lir.md) の「所有を取る時点」)、`FileIn` の `dup` をヒープの検査が止める。ガードを入れるときは、ガードが `Lin` のフィールドを消費しないという型の規則か、別の変換が要る
- `var` の残る制限
  - 制限: 次の5つがある
    - 配列の変数の長さを、範囲の途中で読む書き方がない。今は長さを変数とは別に持つ
    - 配列の変数を、範囲の途中でトップレベルの関数に貸す書き方がない。今は範囲の中の局所関数で書くか、変数にする前に線形に受け渡す。`bench/nbody.em` も、1 回進める計算をトップレベルの関数に分けられなかった
    - 取り出して変えて戻す `x <- f x` は、配列の変数では E3008 になる
    - 範囲の外で定義した局所関数に、変数を使う閉包を渡すと、局所関数の型に変数のエフェクトが現れるので E2019 になる
    - 配列の変数の範囲の E3006 は、`Lin` の状態を持つ handle と同じく、範囲を囲む本体の row で決める。そのため、row に `multi` のラベルを持つ関数では、範囲の中でそのラベルを何も `perform` しなくても、どの配列の変数も断る。範囲が実際に起こす row で持ち越しを確かめる形に細かくする余地がある ([線形性](../spec/linearity.md) の「配列の変数」)
  - 後に回した理由: 今のプログラムと `bench/` に要る場面がなかった。
  - 見直す条件: 要るプログラムが出たとき。
- 共有できる標準のストリームのハンドル: 今は標準のストリームごとに、生きているハンドルは高々1つで、2つ目の `open` は `Panic` になる ([標準ライブラリ](../spec/stdlib.md) の「ハンドル」)。1つのストリームに複数のハンドルを許す形を考える
  - 後に回した理由: 排他的な形から共有の形へは、`open` の `Panic` がなくなるだけで、今のプログラムを壊さずに移れる。逆向きは、2つのハンドルを持つプログラムを壊す。
  - 見直す条件: 1つのストリームに2つ以上のハンドルを要する用途が出たとき。
- ビット演算と `Bytes` の小さな操作: `pop_count`、`test_bit`、`count_leading_zeros`、`count_trailing_zeros`、`Int` の論理右シフト、`Bytes.reserve`、`Bytes` の先頭をその場で切ること、`read_chunk` の大きさの引数 ([宣言](../spec/declarations.md) の「Prelude のクラス」、[標準ライブラリ](../spec/stdlib.md) の「`Bytes`」)
  - 後に回した理由: 要る用途がまだない。論理右シフトは `(x >>> n) &&& ((1 <<< (64 - n)) - 1)` (0 < n < 64) で書ける。`reserve` は意味に現れないので、後から `Pure` の恒等の行として足しても仕様は変わらない。先頭をその場で切るには、offset の語か memmove が要る。
  - 見直す条件: 要るプログラムが出たとき。`reserve` は、計測で差が出たとき。
- 置換付きのデコード: 妥当でない UTF-8 を U+FFFD に置き換えて `String` にする関数。今は `String.decode` が `Panic` を起こし、`String.from_utf8` が `None` を返し、文字列の読みが IO の失敗 `NotUtf8` になる ([標準ライブラリ](../spec/stdlib.md) の「`Bytes` との変換」)
  - 後に回した理由: バイト列を文字列として扱いたい所がまだなく、UTF-8 でないファイルは `Bytes` の読みで受けられる。
  - 見直す条件: UTF-8 でないファイルを `grep` のように文字列の関数で扱う用途が出たとき。
- Unicode の表が要る文字の操作: ASCII でない大文字と小文字の変換、`is_alphabetic`、`is_whitespace` など。今の `Std.Char` は ASCII の判定と変換だけを持つ ([標準ライブラリ](../spec/stdlib.md) の「`Std.Char`」)
  - 後に回した理由: 表を `eml_rt` に持ち込むか、Rust の std を信頼の行で包むことになり、使う所がない。
  - 見直す条件: ASCII でない大文字と小文字の変換か文字の分類を、スクリプトが要したとき。
- `Char.from_int : Int -> Option Char` と `Char.is_scalar`: 今の `Char.of_int` は範囲外の値で `Panic` を起こし、`try_panic` で受けられる
  - 後に回した理由: `Char.of_byte` が全域なので、失敗を値で扱う所が出なかった。
  - 見直す条件: バイトや数から文字を作って、失敗を値で扱う所が出たとき。
- 範囲外の添字で `Option` を返す `Array` と `MutArray` の読み: 今は範囲外の添字は `Panic` で、`Option` を返す関数はない ([標準ライブラリ](../spec/stdlib.md) の「`Std.Array`」)
  - 後に回した理由: eml で書くと `Array.get` の `<Panic>` が型に残る。除くには、範囲を確かめない取り出しの extern が要る。スクリプトに使う所がない。
  - 見直す条件: 添字の範囲外を値で扱うプログラムが出たとき。または、`Option` を返す関数の方針を std 全体で決めるとき。
- `Lin` の要素の `Array` と `MutArray` の API: extern の関数の引数の型変数は `Unr` に固定している ([宣言](../spec/declarations.md) の「`extern`」) ので、今は `Lin` の要素の配列にどの関数も使えない
  - 後に回した理由: この固定を、行ごとに緩める仕組みが要る。
  - 見直す条件: 複数のリソースを配列に持つプログラムが出たとき。または「Kind の宣言化」に着手するとき。
- `Array` の並べ替え: 並べ替えは `List.sort` と `List.sort_by` だけにある ([標準ライブラリ](../spec/stdlib.md) の「`List`」)
  - 後に回した理由: スクリプトは `List` で並べる。
  - 見直す条件: 配列を並べるプログラムが出たとき。
- `Map` と `Set` の join を基にした演算: split と join で書く集合の演算と、整列した列から O(n) で木を作ること。今の `Set` の集合の演算は、低いほうの木の要素を高いほうの木に1つずつ入れる ([標準ライブラリ](../spec/stdlib.md) の「`Std.Set`」)
  - 後に回した理由: 差は 20 万要素どうしの `union` で約 0.06 s だけで、コードが約 150 行増える。
  - 見直す条件: 大きな集合どうしの演算が計測で目立ったとき。
- `FileOut.create_new`: すでにあるファイルを上書きせずに、新しく作る開き方 ([標準ライブラリ](../spec/stdlib.md) の「`FileOut`」)
  - 後に回した理由: 上書きを避ける使い方が、今のスクリプトにない。
  - 見直す条件: 同時に走るスクリプトが同じパスを作る使い方か、一時ファイルを作る使い方が出たとき。
- `Fs.append_text`: パスで1回に済む、末尾に足す書き込み
  - 後に回した理由: `FileOut.append` と `write` と `close` の1行で書ける。
  - 見直す条件: 同じ1行の定義が、スクリプトの2か所以上に現れたとき。
- `Proc` で標準エラーを別の文字列に取ること: `Std.Exec` は `pipe_stderr` と `stderr` で読み分けられる
  - 後に回した理由: `Proc` の extern は組を1つしか作れず、Host が2本の pipe を同時に読む仕組みが要る。
  - 見直す条件: `merge_stderr` で分けられず、`Exec` を使えない例が出たとき。
- 環境変数の削除と全消し
  - 後に回した理由: 上書きで足りる例しかない。
  - 見直す条件: `env -i` に当たる用途が出たとき。
- パッケージ: 今の import が指すのは、ユーザーの根と標準ライブラリだけである ([モジュールと名前解決](../spec/modules.md) の「標準ライブラリ」)。入れるときは、import を解決する順 (ユーザーの根、パッケージ、標準ライブラリ) と、orphan 規則の単位 (上の「型システム」) を決める
- 仮置きの式: どの型にもなる仮置きの式 (typed hole)。入れるときに、網羅されていない `match` と等式の fix (E4001 の枝の追加、E4002 の等式の追加の提案) を一緒に入れる ([診断の出し方](../implementation/diagnostics.md) の「網羅性の診断」)
- `UnboxedArray` と `MutUnboxedArray` への `e[i]`、`x[i] <- v` と、`var` の配列の変数: 添字の式と `var` の配列の変数は `Array` と `MutArray` だけに使える ([標準ライブラリ](../spec/stdlib.md) の「`Std.UnboxedArray`」、[式](../spec/expressions.md) の「`var`」)
  - 後に回した理由: `UnboxedArray.get` と `MutUnboxedArray.read`、`write` で書ける。
  - 見直す条件: `UnboxedArray` を添字の式で書きたいプログラムが出たとき。

### 診断

- 複数行のレコードの更新で、行の先頭の `|` の字下げが足りないときの E0011 (`expected |`) に、字下げの案内を付ける
- キーワードの `from` を変数名に使ったときの E0011 (`expected =`) に、`from` がキーワードであることを示す
- std の関数の中で起きた extern の誤りの位置を、std を呼んだ利用者のコードの位置で示すことは、下の「処理系」の「実行時エラーの backtrace」に置く
- 使っていない import の警告: 標準ライブラリのモジュールも、import を書いたモジュールからだけ使える ([モジュールと名前解決](../spec/modules.md) の「標準ライブラリ」)
  - 後に回した理由: 明示の import を入れた直後は、警告より、足りない import を足す E1031 の fix が先である。
  - 見直す条件: LSP に着手するとき。

### 処理系

- Kind 推論の検証: `eml_types/src/kind/` の束の上の計算 (最小解、多相化で残す制約、持ち越し、含意、instance での値) を vstd だけに依存する葉の crate に移し、Verus で証明する。型検査と evidence passing の変換は Verus で扱わない。LIR の verifier と VM の組で `eml_rt` の前提を証明するかを検討する。詳細は [Verus で検証する範囲](verification.md) にある
- `Char`、`Byte`、`Bits`、`String` の行に VM の命令を足すか: 今は `Std.Char.of_int` と `Show Char`、`Byte` の `+`、`-`、`*`、`negate`、`Byte.of_int`、`Byte.wrap`、`Show Byte`、`Bits` の12行と、`String.char_at`、`String.push` が汎用の `Op::Extern` で動く ([VM](../spec/vm.md) の「基本操作と extern」)
  - 後に回した理由: 命令の数が効くほど `Char` と `Byte` とビット演算を使う処理がまだない。`char_at` の専用の命令は、文字を読むループの命令の数を 10% も減らさなかった ([計測の基準](../implementation/benchmarks.md) の「文字を読むループと `char_at` の命令」)。
  - 見直す条件: `bench/` のプログラムかスクリプトで、汎用の `Op::Extern` の費用が目立つとき。
- 部分文字列の探索のアルゴリズム: `String.find_from` と `Bytes.find_from` は、先頭のバイトを `find_byte` で探してから比べる。最悪の場合は、探す列の長さと探す範囲の長さの積に比例する時間がかかる ([標準ライブラリ](../spec/stdlib.md) の「`Bytes`」の `find`)。std に並ぶとは約束しない。std の2倍を超えたら、同じ extern の行の中で Two-Way にする
  - 後に回した理由: `bench/rt.sh` の `find-sub` は `str::contains` の 1.33 倍の命令で、予算の 1.6 の中にある ([計測の基準](../implementation/benchmarks.md) の「予算を超えた行の既知の差」)。
  - 見直す条件: `find-sub` が `str::contains` の2倍を超えたとき。
- 共有の O(1) の部分文字列 (view): 今は切り出しがいつも写し、view を作らない ([オブジェクトモデル](../spec/object-model.md) の「バイト列と文字列」)
  - 後に回した理由: view は、小さい view が大きい buffer を生かし続け、読むたびに依存した読みが増え、物体の2つ目の形を作る。写す量は `Bytes.append_slice` で抑えられる。
  - 見直す条件: 共有の O(1) の部分文字列が要る用途が出たとき。
- 書くファイルの buffer を確保量の上限に数えること: `FileOut` の 64 KiB の buffer ([オブジェクトモデル](../spec/object-model.md) の「出力のバッファ」) は Rust の側にあり、ヒープの確保量の上限 (`max_bytes`) に数えない
  - 後に回した理由: 読み手の 64 KiB と同じく、ヒープの外の決まった量である。
  - 見直す条件: 多くのファイルを同時に開くスクリプトが出て、上限の外の量が問題になったとき。

- Core IR の上の最適化パス: 引数が定数の関数の特殊化、純粋な extern の定数畳み込み。EP より前の Core IR に置き、関数単位の作業リストで動かす。枝の部分木を置き換えると、長い `else if` の連鎖で2乗の時間がかかるためである。Repr が同じ instance (`List Int` と `List String` の instance など、同じ形のコードになるもの) をまとめるのも、このパスに置く ([Core IR](../spec/core-ir.md) の「変換の規則」)。translate と融合が行わない書き換えも、このパスで扱う。`jump` だけで終わる合流のブロックで、入る辺が2本以上あるものへの転送、枝の中でタグの分かった scrutinee をそのタグに置き換えること、引数が2つ以上で返すだけのブロックのたたみ込みである

- evidence passing の最適化 ([Core IR](../spec/core-ir.md) の「evidence passing」)。どれも EP と実行時の中に閉じ、型検査と translate は変わらない
  - evidence を探す場所ごとのキャッシュと、閉じた row の静的な添字。今は `ev_lookup` が `evv` を先頭から探し、費用は今有効な handler の数に比例する。`evv` は書き換えないので、場所ごとのキャッシュを足せる。静的な添字は Koka の open の包みを要し、包みが部分ベクタを確保して末尾呼び出しを失うので、目立ったときに採るかを決める
  - yield しうる外のエフェクトを呼ぶすぐに再開する節を、その場で実行する形 (論文の under)。yield しない外のエフェクト (`IO` と `never` の操作) を呼ぶ節は、節の実行中だけ `evv` を外側に替える under の形でその場で動く ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。yield しうるエフェクトを呼ぶ節には、yield したら `evv` を替え直す包みと、再開で作り直した evidence を探し直す仕組みが要る。`Yield a` を `Yield b` に変える handler の `yield` の節は、外側の handler の節がその場で動く場合でも1要素ごとに yield する。節の本体の `yield` が外側の操作を起こすためである ([計測の基準](../implementation/benchmarks.md) の「`Yield` を変える handler の yield」)。中断は継続を組み立てずに巻き戻すので、中断のための最適化は要らない

- Perceusの最適化: reuseは、関数の中で閉じた形がある ([LIR](../spec/lir.md)の「reuse」)。関数をまたいで値を貸すことは、借用パラメータが受け持つ ([LIR](../spec/lir.md)の「借用の推論」)。残るのは、関数をまたぐreuseと合流をまたぐtokenと、下の借用の2つの形である。どれもLIRの上のパスで、消費しない`switch`と`release`の上に、IRを作り直さずに足す。tokenを継続に入れない決まり ([LIR](../spec/lir.md)の「token の流れ」) は、足しても守る

    - 後に回した理由: token を関数の外に出さない決まりを保つため。呼び出しの引数、閉包の捕獲、`return` に token を渡さなければ、継続のクロージャに token が入らない ([LIR](../spec/lir.md) の「token の流れ」)。
    - 見直す条件: 呼び出し先で節を作る形 (赤黒木の `balance` など) の確保が計測で目立ったとき。
  - 合流をまたぐ token: token を `jump` の実引数で合流するブロックへ渡すことである
    - 後に回した理由: 道によって空の token を作る定数と、ブロックの引数の検査が要る。
    - 見直す条件: 分岐が合流した後で節を作る形の確保が計測で目立ったとき。
  - 同じブロックの引数から借りるブロック引数: 合流するブロックの引数を借りるのは、入るすべての辺が関数のエントリから借りた値を渡すときだけで、貸すのはいつも関数のエントリである ([LIR](../spec/lir.md)の「ブロックの列」)。同じブロックのほかの引数が貸し、その持ち主を宣言する引数は持たない
    - 後に回した理由: そうしたブロックを作るパスがない。持ち主を手放すには、辺ごとに違うコンストラクタとフィールドの位置が要るので、Perceusは`dup`するしかない。
    - 見直す条件: ループ化かほかのパスが、同じブロックの引数を読むだけのループの頭の引数を作るとき。
  - 薄い形の`$owned`: 借用の引数を持つ関数への値の参照は、すべての引数を所有にした関数の完全な写し`<f>$owned`へ向く ([LIR](../spec/lir.md)の「借用の推論」)。`f`を呼んで引数を手放すだけの薄い包みなら、足すコードは少ない
    - 後に回した理由: 薄い包みは、`apply`を通る末尾呼び出しの輪の下にフレームを残す。写しは、そうした輪のスタックを一定に保つ。
    - 見直す条件: `bench::owned_variants`が、プログラムごとに数個を超える写しを示すとき。または、`bench/run.sh`で読み込みの費用が動くとき。

- 末尾の構築子を除いた再帰のループ化 (tail recursion modulo cons): 再帰の呼び出しの後にコンストラクタの適用だけが続く関数 (`map`、`append`) を、埋める穴を引数で受け取る形に書き換えて、ループにする。今は、こうした関数は要素ごとにフレームを1つ使い、呼び出しをまたいでreuseのtokenを持つときは、フレームごとにスロットをもう1つ使う ([計測の基準](../implementation/benchmarks.md)の「reuse の token で増えるスタック」)
  - 後に回した理由: 穴の空いた物体に継続から届く。`multi`の再開は同じ穴を2回埋めるので、途中の物体を写す規則か、yieldしない関数に限る制限が要る。ネイティブのコードでのこの再帰の費用を、まだ測っていない。

- `miri.rs` のテストの1つあたりの Miri の費用: `crates/eml_vm/tests/miri.rs` の `par_switches_between_tasks`、`shared_struct_boxes_with_scalar_leaves`、`multi_value_returns`、`an_immediate_clause_reads_and_writes_the_state_of_its_evidence`、`a_blocking_call_runs_on_the_test_driver` の5つは、1つのテストの上限 (Tree Borrows の下で 10 秒) を超える ([テスト戦略](../implementation/testing.md) の「Miri」)。最後の1つは `Async.run` の機構を含む約 450 行の LIR を読んで流すので、検査モードだけで流しても上限の数倍かかる。上限に収めるには、1回の実行ごとの準備を安くする必要がある

- `ui::run` の実時間を5秒の条件に収めること: ファイルを集めて流すテストの全体は5秒以内という条件がある ([テスト戦略](../implementation/testing.md) の「性能のテスト」)。`ui::run` は開発機で1つずつ流して 4.2 秒から 5.3 秒で、条件の前後にある。`par/` と `async/` のファイルを、2つの seed と worker の数 N = 2 と 8 でも流すためである

  - 見直す条件: `ui::run` が開発機で1つずつ流して5秒を続けて超えるとき。
- CLIのテストが時間切れで子の`eml`を殺すこと (unixではプロセスグループ、Windowsではジョブオブジェクト、またはdropでのkill): nextestのslow-timeoutが止めたテストが、起動した`eml`を残さないようにする

- 対応するOSより古いCIのrunner: `macos-15`と`ubuntu-24.04`のimageは、macOS 26とLinux 6.12より古い ([テスト戦略](../implementation/testing.md)の「OSごとのテスト」)
  - 後に回した理由: 対応するOSの版の機能に頼るテストがまだない。
  - 見直す条件: 段が対応するOSの版の機能に頼るとき。

### REPL

- `IO` 以外のエフェクトを既定の handler で許すか。許すなら、handler のない操作の yield を REPL が受け取る
- セッションの値への連結は、RC が 2 以上になるので、いつも写しになる
- 定義し直した `let` の古い根を手放す順序。今は古い根を `close` まで手放さない ([オブジェクトモデル](../spec/object-model.md) の「セッションの根」)
- REPL の入力が、前の読み込みで翻訳したコードを通してだけ `fork_job` や `par` に届くとき、その間に宣言した never だけのエフェクトには fork の表がなく、内部の誤り `a never-only evidence of a par parent has no fork table` で止まりうる。`compute` の REPL のトランスクリプトでは再現していない
  - 後に回した理由: 再現する入力が見つかっていない。
  - 見直す条件: この誤りで止まる REPL の入力が見つかったとき。
- 凍結のときに生きている物体を詰め直して、塊のページを減らすこと。塊は使う大きさの級ごとに少なくとも1ページを持つので、新しい定数を持つ入力ごとに塊を作ると、使うメモリは入力の数に比例して増える ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」)。トップレベルの値の1回だけの評価 (上の「言語機能と構文」) を入れると、塊はさらに増える。困ったときに入れる
- 入力ごとにセッション全体を検査し直すので、セッションが大きくなるほど入力ごとの時間が延びる。困ったら増分の lowering に移る。名前が同じ関数はいつも同じコードになる規則 ([Core IR](../spec/core-ir.md) の「変換の規則」) があるので、後から移れる
- REPLのGUI (`python -m asyncio`の形): メインスレッドが`Seat::Separate`の`Machine`とtoolkitの`Park`を持ち、行の編集器は別のスレッドで動いて入力を1つずつ渡し、出力はrustylineの`ExternalPrinter`を通す ([FFIと拡張の設計](ffi.md)の「GUI」)
  - 後に回した理由: REPLのセッションは根を持ち、分かれたrunはセッションの根に触れるコードを拒む。固定したタスクの閉包から届く根の物体と、runとrunの間に動く`Machine`の`Park`も要る。それまで`eml repl`はGUIの`Park`を持たず、`Gui.run`は`NotAvailable`で失敗する。
  - 見直す条件: 対話のGUIのセッションが求められたとき。

### マルチコア対応

マルチコア対応は「段の列」の段で進め、設計は [マルチコア対応の設計](multicore.md) にある。ここには後に回した項目を置く。多くは同じ文書の「未決の論点と将来の拡張」に既定がある。

- `par` の子の取り消し: 左の子が中断したとき、長い右の子を安全点で協調的に止める
  - 後に回した理由: 既定ではすべての子の完了を待ち、決まった順に結果を出す形を先に入れる。
  - 見直す条件: 左の子が中断したときに長い右の子を止めたいとき。または、`compute` の周りの `timeout` をすぐに戻したいとき。
- 逐次実行と同じ意味の `par_ordered`: 任意の row を許し、右の子を最初の perform まで投機的に実行する
  - 後に回した理由: 「perform の手前で止まる」プリミティブが実行系の核に要る。
  - 見直す条件: `never` でない操作を持つ子を、逐次と同じ意味で並列に動かしたいとき。
- `par` の子から `IO` とすぐに再開する操作を外に出すこと
  - 後に回した理由: IO の失敗と `exit` の中断が子をまたぐので、子の底を中断の境目にし、`try_io` と `exit` が子をまたぐ意味を決める必要がある。
  - 見直す条件: 子からの出力が `both` で足りないとき。
- `fork` と `join` を普通の関数として公開すること (`Par.fork` と `Par.join`)
  - 後に回した理由: `par` と集まりの関数で足りる。
  - 見直す条件: 不規則な並列が要るとき。
- private deque: 印付けを、実際に盗まれた子だけに限る最適化
  - 後に回した理由: 共有の集合がスケジュールに依存し、固定した `RunStats` が崩れる。
  - 見直す条件: 印付けがプロファイルで目立つとき。
- ロックフリーの受け箱と channel
  - 後に回した理由: 既定の mutex は Miri で確かめられる。
  - 見直す条件: N が 8 以上で競合を測ったとき。`bench/async/chan_pingpong.em` は worker 4 つで 1 つより遅く、2回の計測で t(4) が t(1) の 12.4 倍と 12.8 倍だった ([計測の基準](../implementation/benchmarks.md) の「worker の数と実時間」)。同じインターフェースの後ろで替える。
- タスクを置く worker を、実行待ちと待ちの集まりのいちばん短いものにすること
  - 後に回した理由: 既定は置ける worker を順に回す形である。32 本の接続の echo (`serve-self-32`) は、この置き方で worker 2 つと 4 つでも 1 つと差がなく、置き方が律速になる計測はない ([計測の基準](../implementation/benchmarks.md) の「worker の数と実時間」)。
  - 見直す条件: 偏りを測ったとき。
- 仮想の時計で、同じ期限のタイマーを worker をまたいで1度に満たすこと: 今は区画ごとに持ち主が自分の集める地点で外すので、同じ期限のタイマーの worker をまたいだ順は決まらない ([VM](../spec/vm.md) の「時計と driver」)。そのため、同じ期限の順に頼る `async/` の UI テストの2つ (`drain_within_cancelled_at_deadline.em`、`drain_within_deadline_coincides.em`) は、印で N = 2 以上の run から外してある
  - 後に回した理由: 区画の項を替えるのは持ち主だけという規則を保つ。同じ期限の順は本物の時計でも決まらない。
  - 見直す条件: 同じ期限の順に頼るテストを N = 2 以上で流したいとき。
- `async/` のほかの `Async` を使う分類 (`tls/`、`http/`、`std/` の一部) の UI テストを、worker の数 N = 2 と 8 でも流すこと
  - 後に回した理由: これらは seed でも流さない分類で、出力の順がスケジュールによらないことはレビューだけが確かめている。worker をまたぐ道は、`async/` の `net_*`、`eml_vm` の `io.rs`、`eml_cli` の `cli.rs` の複数の worker の run が覆う。
  - 見直す条件: `Std.Tls` か `Std.Http` が worker に依る状態を持つとき。または、N = 2 以上でだけ出る不具合をこれらの分類で見つけたとき。
- ページを OS に返すこと
  - 後に回した理由: 返さなくても、RSS は worker のヒープごとの最大の和にとどまる。
  - 見直す条件: サーバの RSS が育ち続けるとき。
- 待ちのタスクが持つメモリを数えること
  - 後に回した理由: タスクが動く間の確保だけを数える形は安い。
  - 見直す条件: メモリの柔らかい上限が違うタスクを選ぶとき。
- 本当の待ちから起きてまだ動いていないタスクを、メモリの柔らかい上限の候補にすること: 起きたタスクは、動き始めるまで候補にならない。各workerが公開するのは、動いているタスクと、実行待ちのうちフレームを持ったまま`Seeded`に切り替えられたタスクか自分から列に戻ったタスクだけである ([VM](../spec/vm.md)の「タスクとスケジュール」と「タスクの上限」)
  - 後に回した理由: 実行待ちのタスクをすべて公開するには、走れるタスクの列の項 (`Runnable::Resume`、`Runnable::ResumeIo`) ごとに数を持たせるか、読み手が lock を取る必要がある。
  - 見直す条件: メモリの柔らかい上限が違うタスクを選ぶとき。
- 実行待ちのタスクを worker ごとに2つ以上公開すること: 欄の `top` は worker ごとに1つなので、そのタスクが動き始めて消えた後は、小さい実行待ちのタスクはもう一度 CPU を離れるまで候補にならない ([VM](../spec/vm.md) の「タスクとスケジュール」)
  - 後に回した理由: 上の項と同じく、すべてを公開するには項ごとの数か lock が要る。
  - 見直す条件: メモリの柔らかい上限が違うタスクを選ぶとき。
- `par` の右の子と `compute` の仕事の確保をタスクに数えること: 右の子と仕事の確保はどのタスクの数にも入らず、そうした増え方は硬い上限 `max_bytes` に届いて run を止める。左の子は親の `Task` の上で動くので、親のタスクに数える ([VM](../spec/vm.md) の「タスクとスケジュール」)
  - 後に回した理由: 右の子と仕事の `Task` はタスクのセルを持たないので、数を足す先がない。
  - 見直す条件: タスクの中の `par` の右の子か `compute` の仕事の確保で、硬い上限に届いて run が止まる使い方が出てきたとき。
- 右の子がほかの worker で動く間の、親のタスクへの旗: タスクの中の `par` の右の子がほかの worker で動く間に親のタスクに立った旗は、合流の後に親で起きる。子の `Task` はタスクのセルを持たないためである。子の深さの超過は子の中で起きる ([VM](../spec/vm.md) の「タスクの上限」)
  - 後に回した理由: 子の row は `IO` を含められないので、子の中では `ResourceLimit` を起こせない。旗は失われず、遅れるだけである。
  - 見直す条件: 長い `par` を持つタスクで、柔らかい上限の旗が遅れて硬い上限に届くとき。
- 同じセルのエントリの `Task` が重なるときのタスクの数: 待ちに入った前のエントリの `Task` がまだ `Finish` していない間に次のエントリが動き始めると、次のエントリは前のエントリの `top` を消し、前のエントリのまだ `leave` していない数を含まずに数え始める ([VM](../spec/vm.md) の「タスクの上限」)
  - 後に回した理由: 選び方が偏るだけで、旗は生きたセルへ行く。
  - 見直す条件: メモリの柔らかい上限が違うタスクを選ぶとき。
- `poly` の物体の `lin` ビットの実行時の伝播
  - 後に回した理由: `MutArray` の要素を `Unr` に固定しているので要らない。
  - 見直す条件: `Lin` の要素を持つ配列を入れるとき (上の「言語機能と構文」の、`Lin` の要素の `Array` と `MutArray` の API)。
- 読むだけの共有: `par` の子が親の環境を読めるが書けない形 (OxCaml)
  - 後に回した理由: 今の `par` の子は親の `Ref` を読めないが、データ並列は純粋な関数と失敗の通知で書ける。
  - 見直す条件: 親の `Ref` を読めないことが、表現力の不足として現れたとき。
- `IO` が大域的な領域を含む折衷案: Koka のように `IO` が `Heap Global` を含む形
  - 後に回した理由: 大域的な領域の読み書きには同期が要る。
  - 見直す条件: 大域的な領域が必要になったとき。
- 分けられる擬似乱数の生成器: `par` の子ごとに、互いに独立した乱数の列を作る
  - 後に回した理由: std に乱数のモジュールがまだない。
  - 見直す条件: `par` でモンテカルロ法の計算を書くとき。
- Windows のコンソールの標準入力を std を通さずに読む読み手: `ReadConsoleW` を直接呼び、Ctrl-C で戻った読みを `Interrupted` で返す。今は std がその場で読み直すので、`Stdin` の読みは Ctrl-C で止まらない ([マルチコア対応の設計](multicore.md) の「未決の論点と将来の拡張」)
  - 後に回した理由: UTF-16 の変換、Ctrl-Z の扱い、Windows だけのテストが要る。
  - 見直す条件: `Stdin` の読みを待つ間の1回目の Ctrl-C が見えないことが問題になったとき。
- Ctrl-C のハンドラで、ビットの確かめと立てを不可分にすること: Windows の handler は `INTERRUPT` が立っているかを確かめてから立てる。そのため、同時に動いた2回の handler がどちらも1回目として扱うことがある ([VM](../spec/vm.md) の「上限と割り込み」)
  - 後に回した理由: `Control` が前のビットを返す必要があり、`eml_rt` の変更になる。
  - 見直す条件: `TERMINATE` がビットごとの操作を `Control` に足すとき。
- unixでSIGINTが届くスレッドの隙間 (知られた不具合): SIGINTとSIGTERMを受けるのはworker 0だけという規則が、2つの隙間で破れる ([VM](../spec/vm.md)の「上限と割り込み」)。1つ目は、メインスレッドがworker 0を作ってから塞ぐまでの間である。そこで来たSIGINTはメインスレッドに届くことがあり、そのスレッドが動かなければハンドラはrunが終わった後で動き、`eml run`はrun自身の終了コードで終わる。このため`cli::an_interrupt_stops_a_program_waiting_for_a_child_with_130`は、並列の負荷の下でまれに失敗する (macOSで40本を並べて2000回のうち4回)。2つ目は、worker 0が`spawn_masked`でスレッドを作る間で、すべてのスレッドが塞いでいる。macOSでは、そのとき来たSIGINTはrunが終わるまでメインスレッドの保留に残る。Ctrl-Cが1回なら、runは自分の終了コードで終わる。2回なら、2回目が1回目として扱われてrunを止め、保留のSIGINTが実行時エラーを出さずに130でプロセスを終わらせる。安全点に来ないプログラムを終わらせるには3回目が要る。どちらもmacOSで、記録を書くビルドで確かめた。Linuxではどちらも確かめていない
  - 直し方: worker 0を作る前にメインスレッドで塞ぎ、worker 0が自分で塞ぎを外す。2つ目には、シグナル専用のスレッドなどの設計の選択と、advisorの確認が要る。
  - 後に回した理由: テストの直しを先に入れ、実行系の直しは小さな段に分けた。
- REPL の複数の worker: REPL は worker 1つで動く。セッションの根を持つ run と、根の基本操作に届くコードの run は、worker を作らない ([VM](../spec/vm.md) の「タスクとスケジュール」)
  - 後に回した理由: 移し戻しは物体を写さないので、`par` の後に置いた根が、ほかの worker のヒープのページの物体を指しうる。run の終わりにそのヒープを落とすには、入力の間もヒープを生かす静止の手順か、run の終わりに根から届く物体を写すことが要る。
  - 見直す条件: REPL の中の `par` を並列に動かしたいとき。
- `eml_sched`のcrate: `eml_sched`はタスクのセルの核と実行のインタフェースを持つ。workerの表、受け箱、待ち、監視のスレッドはまだ`eml_vm`の`workers.rs`、`sched.rs`、`monitor.rs`にある ([マルチコア対応の設計](multicore.md)の「層の構成」)
  - 後に回した理由: ネイティブのコードにタスクの層ができるまで、`Exec`のtraitの実装はVMの1つしかない。
  - 見直す条件: ネイティブのコードがタスクの層を持つとき。
- `par` の右の子を置く粒度: fork は、空いている worker があればいつも右の子をそこに置く ([VM](../spec/vm.md) の「`par` の fork と join」)。小さい子を置かずに親の worker で動かす下限を持たない
  - 後に回した理由: 粒度は `std-par` の集まりの関数が持つ (1024 要素。[マルチコア対応の設計](multicore.md) の「データ並列での使い勝手」)。
  - 見直す条件: `bench/par_tree.em` を `--workers 2` で動かすと `--workers 1` より遅いと計測したとき。または、`par` で分けた仕事が worker 2 つより先で伸びない理由を調べるとき。`bench/async/scale.sh` の `spread_par` は、2回の計測で S(2) と S(4) が 1.94 と 1.94、1.85 と 1.97 で、同じ仕事を `Async` のタスクに分けた `spread` (S(4) が 3.31 と 2.83) と違って worker 4 つで伸びなかった ([計測の基準](../implementation/benchmarks.md) の「worker の数と実時間」)。
- 遠隔の解放のあったページの列: 持ち主の取り込みは、ヒープのページの一覧をすべて歩き、ページごとに遠隔のリストの語を1回読む ([オブジェクトモデル](../spec/object-model.md) の「別のスレッドからの解放」)。解放を受けたページだけを積む列を持つ形がある
  - 後に回した理由: 列には、1つのページを2回積まないための2つ目の並行の手順が要る。2回積むとページのつなぎが壊れ、輪になりうる。歩く費用は、256 回の遠隔の解放か大きい物体1つの取り込みにならされる。
  - 見直す条件: channel を多く使うプログラムのプロファイルに取り込みの歩きが見えたとき。
- workerの間でのタスクの移動: まだ始まっていない`Async`のタスクを、`par-steal`のdequeを通して別のworkerの実行待ちから盗む。タスクは置かれたworkerで終わるまで動くので、CPUを使い続けるタスクやその場の読みは、ほかのworkerが空いていても、同じworkerのほかのタスクを待たせる ([VM](../spec/vm.md)の「タスクとスケジュール」)
  - 後に回した理由: 救済 (待っている継続を別のworkerへ移す形) では、フレームを持たない仕事しか移せなかった。始まっていないタスクだけを盗む形なら、始まったタスクの作業の集合は1つのworkerに残るが、`par-steal`のdequeが要る。
  - 見直す条件: 計測したサーバの仕事で、あるworkerの実行待ちが1刻みより長く伸びる間に、ほかのworkerが空いたままのとき。
- プールの上に置く`Stdin`と`FileIn`の読み: `Std.Stream`の行と同じ`Async`の行にする。`Stdin`、`FileIn`、`Proc`、`Fs`は今その場で動き、戻るまでworkerを持つので、そのworkerに置いたタスクは待つ ([実装の現在地](../implementation/status.md))
  - 後に回した理由: `start`はNが2以上のときworker 0にタスクを置かないので、`main`の同期の読みの間もタスクは動く。待つのはworker 0のdriverが受け持つI/Oだけで、`main`が作ったソケットやファイルを、`main`が同期で読みながらタスクに使わせる形に限られる。タスクの中で読むときは`Std.Stream`を使える。
  - 見直す条件: スクリプトが標準入力と、1つのworkerの上のタスクを必要とするとき。
- 協調的な配置のVerusの証明: 持ち主を`start`で一度だけ決めること、知らせを持ち主へ送ること、`park_idle`と`wake`で起こしを取りこぼさないことを証明する
  - 後に回した理由: スケジューラはVerusの外にあり、MiriとThreadSanitizerで確かめている。
  - 見直す条件: `rt-concurrent-proofs`に取りかかるとき ([マルチコア対応の設計](multicore.md)の「テスト」)。
- `eml_rt` の並行の証明 (`rt-concurrent-proofs`): Verus の証明は1つのヒープの逐次の模型で、スレッドをまたぐ所は信頼の一覧の T0、T2、T14、T15 に置いてある ([オブジェクトモデル](../spec/object-model.md) の「`unsafe` の核」)。これを並行の証明に置き換え、ほかのヒープの物体を証明の模型に入れる ([マルチコア対応の設計](multicore.md) の「テスト」)
  - 後に回した理由: vstd の atomic は SeqCst だけを扱い、今の証明は逐次の模型なので、並行の証明は証明の作り直しになる。1つのヒープの逐次の証明は、ほかのヒープが持つ物体の ghost の状態を今の値に保てないので、ほかのヒープの物体を貸し出しの token で模型に入れても、信頼は ghost の形に写るだけで減らない。T0 と T14 は、Miri の2つのスレッドのテスト、ThreadSanitizer、検査モードの N = 2 と 8 の UI テストで確かめる。
  - 見直す条件: ネイティブのコードが `eml_rt` を共有する前。または、ThreadSanitizer か Miri が T0 か T14 の誤りを見つけたとき。
- `UnboxedArray` の `slice` と `append`
  - 後に回した理由: `std-par` は添字の範囲のプリミティブで足り、`slice` と `append` を使う所がない。
  - 見直す条件: `std-par` で、添字の範囲のプリミティブでは書けないデータ並列の関数が出たとき。
- 一般の専用のworker (`rt_thread_new`): メインのworkerと同じく配置で仕事を受けず、待ちを替えられるworkerを、自分のスレッドの上に作る
  - 後に回した理由: 見えているスレッドに縛られたライブラリはGUIのtoolkitだけで、それはメインのworkerを使う。
  - 見直す条件: スレッドに縛られた2つ目のライブラリが出たとき。

### 非同期

設計は [非同期の設計](async.md) にある。ここには後に回した項目を置く。既定は同じ文書の「未決の論点と将来の拡張」にある。

- 複数の channel の `select`
  - 後に回した理由: 競わせるのは `race` と `timeout` で、集めるのは `merge` で書ける。
  - 見直す条件: 2つ以上の channel を回るループで、`race` の費用が目立つとき。
- broadcast と watch の channel
  - 後に回した理由: 1つの値を多くの受け手に配る用途がまだない。
  - 見直す条件: pub/sub の形が要るとき。
- `Counter` のほかの `Atomic`
  - 後に回した理由: 利用者にメモリモデルを見せない。共有して書き換える状態は、持ち主のタスクの後ろに `Chan` を置く形 (actor) で書く。
  - 見直す条件: actor の形では遅すぎるとき。
- `Counter` の表を縮めること: `Counter` は放さず、`Machine` の表は伸び続ける ([標準ライブラリ](../spec/stdlib.md) の「`Std.Atomic`」)
  - 後に回した理由: `Counter` は数の少ない共有の状態のためのもので、表の項は作った `Counter` の数だけである。
  - 見直す条件: `Counter` を大量に作るプログラムが出たとき。
- 最後のハンドルで放す channel: 今の channel は `close` で放し、閉じないままの channel は run の終わりまで残る ([標準ライブラリ](../spec/stdlib.md) の「`Std.Chan`」)。戻す形は [非同期の設計](async.md) の「未決の論点と将来の拡張」の「`Lin` の closer token」にある
  - 後に回した理由: `Chan a` を `Unr` の `Foreign` にして最後のハンドルで放す形は、初めての `Unr` の `Foreign` になる。回復で `Foreign` を移す信頼の一覧の行 (T3。[オブジェクトモデル](../spec/object-model.md) の「`unsafe` の核」) と、Verus と Miri の作業を `eml_rt` に要し、送受信のたびにハンドルの `dup`、`decref` と表の照らし合わせが入る。品物が自分の channel のハンドルを持つ輪では最後のハンドルが落ちないので、放す保証はどちらの形でも「閉じるか run の終わり」になる。ネイティブ化の簡潔さと速さを優先し、即値にした。
  - 見直す条件: 接続やリクエストごとに channel を作り、取り消しの巻き戻しで `close` を飛ばす形のサーバが実際に書かれ、長く走る run で登録表の slot が増え続けると測れたとき (`RunStats.channels_swept` か、検査モードの終わりの数で)。
- UDP
  - 後に回した理由: 目標のネットワークサーバは TCP で書く。
  - 見直す条件: UDP を使う最初のプログラムが出たとき。
- `SO_REUSEPORT` で複数のタスクが accept する形
  - 後に回した理由: N が 4 以下では accept が詰まりにならない。既定では1つの listener の accept を1つのタスクで行う。
  - 見直す条件: N が 8 以上で accept が詰まりになったとき。
- 書きの期限を持つ `write_within`: 書きの期限は `Async.timeout` で付け、期限が来ると巻き戻しがストリームを閉じる ([標準ライブラリ](../spec/stdlib.md) の「`Std.Net`」)
  - 後に回した理由: 書きの期限は `Async.timeout` で書ける。失うのはストリームだけである。
  - 見直す条件: 書きの期限の後もストリームを保たなければならないプロトコルが出たとき。
- `Net.resolve` と、名前での `listen`: `listen` は IP アドレスの綴りだけを受け、名前を解決するのは `connect` だけである
  - 後に回した理由: 番地の一覧も名前での bind も、使うプログラムがまだない。
  - 見直す条件: 番地の一覧か名前での bind が要るプログラムが出たとき。
- Happy Eyeballs: `connect` は解決した番地を順に1つずつ試す
  - 後に回した理由: 順に試す形で足りる。
  - 見直す条件: IPv6 が壊れたネットワークで `connect` が遅れるとき。
- TLS の server (`Tls.accept`、SNI で証明書を選ぶこと、クライアント認証、ALPN)
  - 後に回した理由: 目標は HTTPS のクライアントで、server は作らない。テストの相手はテストの driver が Rust で終端する。
  - 見直す条件: eml で HTTPS のサーバを書くとき。
- `Tls` の期限を持つ読み (`read_chunk_within`、`read_line_within`): `Tls` の関数は期限を持たず、期限は `Async.timeout` で付ける。期限が来ると巻き戻しが `Stream` を落とす ([標準ライブラリ](../spec/stdlib.md) の「`Std.Tls`」)
  - 後に回した理由: 呼び出しの全体に付く期限には、eml のプログラムが読める時計 (下の `Time` のモジュールの項目) が要る。今書けるのは `Net` の読み1回ごとに期限を付け直す形だけで、期限が1行の全体に付く `Net.read_line_within` と意味が違う。
  - 見直す条件: eml のプログラムが時計を読めるようになったとき、または期限の後も `Stream` を保つ読みが要るプログラムが出たとき。
- close_notify なしの EOF を EOF として読む `Tls` の読み
  - 後に回した理由: 既定は IO の失敗 `ConnectionReset` にした。長さを持たない本文 (EOF までの本文) が黙って切れるのを防ぐためである。
  - 見直す条件: close_notify を送らないサーバと話す必要が出たとき。
- `Http` の HTTP/2 と ALPN、gzip、keep-alive の接続のプール、ストリーミングの本文、本文の大きさの上限、プロキシ、cookie、IPv6 のアドレスの URL
  - 後に回した理由: スクリプトの HTTPS のクライアントには、要求ごとに閉じる HTTP/1.1 で足りる。gzip は展開の extern がまだない。IPv6 のアドレスの URL には、角括弧の付いた `Host`、IP のアドレスでの SNI、仮想のホストのテストが要る。
  - 見直す条件: 大きな本文を少しずつ読むプログラムか、同じホストへ多数の要求を出すプログラムが出たとき。IPv6 のアドレスの URL は、IPv6 だけのホストへつなぐプログラムが出たとき。
- libcurl の上の HTTP のクライアント: 採らない。本物のソケットが要るので、テストの driver の仮想のホストの上の UI テストが書けず、`Net` を通らないのでほかのプロトコルに使える TLS の層にならない。OS ごとに違う TLS (OpenSSL、Schannel) と libcurl、zlib、pkg-config の依存も持ち込む。
  - 見直す条件: `Http` に HTTP/2、プロキシ、圧縮が要り、eml で書くより libcurl を結ぶほうが小さいと分かったとき。
- macOS の `Std.Net` を Network.framework (`nw_connection_t`、`nw_listener_t`) で作ること: 採らない。macOS の backend は kqueue のままにする
  - 後に回した理由: Network.framework は dispatch のキューのスレッドで完了の block を呼び、受けたデータを framework が確保した `dispatch_data_t` に入れる。そのため、操作が持つ一意な buffer へ写す手間が1回増え、送りで `RawBuf` を包むと driver のスレッドの外で読まれる (理由は [非同期の設計](async.md) の「ファイルとパイプ」の `dispatch_io` と同じ)。データを消費せずに読めるかを問う操作もなく、`Readable` の歩を作れない。速さは増えず、得られるのは system の proxy と VPN に沿った経路の選択、system の trust store を使う TLS、QUIC といった機能である。
  - 見直す条件: macOS で system の proxy か VPN に沿った接続、system の trust store を使う TLS、QUIC のどれかが要るとき。または iOS を対象にするとき。
- Linux の io_uring の backend: Linux の backend は epoll で、io_uring を入れるなら、既定になる形 (作れなければ epoll) でだけ入れる。既定にならない backend は試されない `unsafe` のコードとして残り、io_uring を拒む環境 (Docker の seccomp、gVisor、`io_uring_disabled`) も多いので、epoll を基準の backend にする。`EML_IO_BACKEND` で backend を選べる実装を試して測った数字は、[計測の基準](../implementation/benchmarks.md) の「io_uring と epoll」にある
  - 後に回した理由: 比べた5件 (many-self-1000、echo-self-fresh、echo-py-fresh、echo-py-reuse、bulk-1k) のどれでも、2回のセッションで続けて、CPU の比が 0.800 以下で判定が「差」にはならなかった (いちばん縮んだのは `io_uring_direct` の many-self-1000 で、1回目が 0.779 で四分位が重なり、2回目が 0.940)。貸した buffer を1つだけカーネルに渡す契約の下では、io_uring で省けるのは、登録、接続の確かめ、空振りの読みの syscall に限られる。
  - 見直す条件: ネイティブ化の後に many-self-1000 と echo-self-fresh を測り直し、減らせる syscall の分が CPU の2割に当たるとき。buffer の契約を変え、カーネルが選ぶ buffer を受け入れる設計をするとき。`Std.Stream` のファイルの仕事で、プールの費用が計測で目立ったとき。
- musl で静的に結んだ Linux の配布物 (`x86_64-unknown-linux-musl`)
  - 後に回した理由: TLSとは別の配布の話である。aws-lc-sysのためにmuslを対象にするCのツールチェーンをflakeに足し、`nix build`の2つ目のパッケージとCIのジョブが要る。muslの名前の解決と確保の速さはglibcと違う。AOTの配布物は`libeml_rt.a`を同梱して利用者の`cc`で結ぶので、muslの配布物にはmusl向けの`libeml_rt.a`と結び方を別に用意する必要がある。静的な配布物も証明書をOSの検証器で確かめるので、OSの根のファイルか`SSL_CERT_FILE`、またはCAを渡すプログラムが要る。
  - 見直す条件: Linux の tarball を配布するとき。既定の配布物とは別の配布物にする。
- 時刻を扱う `Time` のモジュール
  - 後に回した理由: 待ちと期限は `Int` のミリ秒で足りる。
  - 見直す条件: 時刻か、時間あたりの回数の制限が要るとき。
- 期限のタスクを使わない待ち (`await_cell_until`): セルの待ちと期限の2つの登録を持つ生の操作で、`timeout` と `drain_within` の期限のタスクを省く。`unpark` と `wake` が、同じセルのもう一方の登録を外す
  - 後に回した理由: 期限のタスク1つで書ける。
  - 見直す条件: その費用が計測で目立つとき。
- 2つ目からの失敗をまとめて報告する形 (MultiError)
  - 後に回した理由: 既定では最初の失敗が勝ち、ほかは数えるだけにする (`RunStats` の `dropped_failures`)。
  - 見直す条件: 2つ目からの失敗の中身がデバッグに要るとき。
- 非同期の名前の解決: 戻らない解決のスレッドが64本たまると、名前での `connect` は IO の失敗になる ([VM](../spec/vm.md) の「時計と driver」)
  - 後に回した理由: 名前の解決は driver の解決のスレッド (同時に8本) で行い、取り消しと `quiesce` は待たない。
  - 見直す条件: その失敗か、8本の待ちが計測で見えたとき。
- タスクを置くworkerを選ぶAPI (`spawn_here`など)
  - 後に回した理由: workerを名指しする配置は`Async.start_on_main`だけで、スレッドに縛られた仕事はそれで書ける ([標準ライブラリ](../spec/stdlib.md)の「`Std.Async`」)。
  - 見直す条件: タスクをメインのworkerのほかの決まったworkerに置く必要が出たとき。
- `shield` の中で取り消しの要求を読む確かめ
  - 後に回した理由: `cancel_requested` は、`shield` の中では外から来た取り消しを読まない。`shield` の中の後始末が要求を知る使い道が、まだない。
  - 見直す条件: `shield` の中の後始末が、取り消されたかどうかで動きを変える必要が出たとき。
- プールの上限 24/8 と静止の予算 1 秒 ([VM](../spec/vm.md) の「時計と driver」)
  - 後に回した理由: 既定は計測なしで選んだ。
  - 見直す条件: 計測か報告で、ファイルの仕事か C の呼び出しが上限で待つのが見えたとき、または予算が戻るはずの呼び出しを切っているのが見えたとき。
- 1つのハンドルの1つの向きに、保留の操作を2つ以上置くこと: 今の本物の driver は、読みと書きのそれぞれに保留を1つしか置かず、2つ目を `InvalidInput` で断る ([VM](../spec/vm.md) の「時計と driver」)
  - 後に回した理由: std のストリームとリスナーは `Lin` なので、VM は同じ向きに2つの操作を出さない。backend の fd ごとの状態を最小にできる。
  - 見直す条件: 1つのハンドルを分けて同じ向きで2つ待たせる API を足すとき。そのときは backend の向きごとの待ち手を `OpKey` の列にし、核の断りを外す。
- macOS の kqueue の書きの起こし: macOS の同じ run の bulk で、非自発の切り替えが書きの重みの単位によって大きく変わる ([計測の基準](../implementation/benchmarks.md) の「書きの重みの単位」)
  - 後に回した理由: syscall の目標は epoll だけに置き、macOS の CPU に後退はない。原因 (`EVFILT_WRITE` が ACK ごとに待ちを起こすかなど) を調べていない。
  - 見直す条件: macOS の `bench/net` の bulk の CPU か実時間が目立ったとき。
- 待つ `Std.Net` の操作の確保: 操作が待つときは、継続の閉包と、再開した継続が一様な位置で受け取る組の箱 (`read_chunk` の `(Bytes, TcpStream)` と、`resume_io` が渡す `(Wake, OpId)`) を確保する。受け付けで終わった操作の道は確保しない ([VM](../spec/vm.md) の「操作の記録」)
  - 後に回した理由: 組の箱を消すには、`await_io` の結果の型と、ランタイムが名前で呼ぶ `resume_io` の形 (`eml_extern` の表と VM) を変える必要がある。継続の閉包の数は、エフェクトの実装の形とフレームの深さで決まる。
  - 見直す条件: 待つ読みの多いサーバで、1回の待ちの確保が計測で目立ったとき。
- 1回の読みで貸す量の上限 (65 536 バイト) を外すこと ([標準ライブラリ](../spec/stdlib.md) の「`Std.Net`」)
  - 後に回した理由: 上限を変える計測の根拠がない。`bench/net` の bulk-recv-py では、1回の `recvfrom` が貸した 65 536 バイトを使い切らない ([計測の基準](../implementation/benchmarks.md) の「34cad91 と e942eeb」)。
  - 見直す条件: 大きな buffer を渡す読みで、読みの回数が計測で目立ったとき。
- `read_line` の buffer を、残りがなくなっても持つこと: 今は残りがなくなれば確保を放す ([VM](../spec/vm.md) の「操作の記録」)
  - 後に回した理由: 待つだけの接続に記憶を持たせない。
  - 見直す条件: 行ごとに往復する接続で、`Readable` と確保が計測で目立ったとき。
- 監視のスレッドを `Machine` が run をまたいで持つこと: 今は1 run に高々1本で、REPL では入力ごとに起こして止める ([VM](../spec/vm.md) の「タスクとスケジュール」)
  - 後に回した理由: スレッドの寿命を run にそろえれば、入力の間に残る状態がない。起こしと join の費用は、REPL の1回の入力に比べて小さい。
  - 見直す条件: REPL の入力ごとの費用で、監視のスレッドの起こしと join が目立ったとき。
- タスクの中の `par` の子の深さの超過を、親のタスクの `ResourceLimit` にすること: `Async` のタスクの中でも、`par` の子 (左も右も) の深さの超過は run を止める。子の row は `IO` を含められず、子の `evv` に `IO` の evidence がないためである ([VM](../spec/vm.md) の「タスクの上限」)。子の超過を親で起こし直す道がある
  - 後に回した理由: 子の深さの超過は子の誤りで、親で起こし直すには、それを中断として親へ運ぶ道が要る。
  - 見直す条件: タスクの中の `par` で深さの上限に届く使い方が出てきたとき。
- 上限の近くで待ちに入ったタスクの再開の深さ: 再開は、捕まえた利用者のフレーム1段ごとに `compose$` のフレームを積み直すので、再開の後の深さは、待ちに入る前の深さに `compose$` のフレームと利用者のフレームの大きさの比を掛けたほどになる。深さが `real + LIMIT_HEADROOM` を超えるとタスクの失敗でなく run の誤りで止まり、`real` との間なら、論理的な深さが上限に届いていなくても `the call depth limit is exceeded` の `ResourceLimit` が起きる ([VM](../spec/vm.md) の「タスクの上限」)
  - 後に回した理由: 猶予 `LIMIT_HEADROOM` は巻き戻しの途中の暴走を止める硬い限度でもあり、変えずに残す。比は測っていない。
  - 見直す条件: 上限の近くで待ちに入ったタスクの再開が、run の誤りか見かけの深さの超過で止まる事例が出てきたとき。
- バッファを持つ非同期の `Writer` と `flush`: `Std.Stream` の `Writer` は buffer を持たず、書くたびに1回の操作を出す ([標準ライブラリ](../spec/stdlib.md) の「`Std.Stream`」)
  - 後に回した理由: 小さい書きを何度も出す使い方が、今のスクリプトにない。buffer を持つと、手放したときの書き出しの失敗を届ける道が要る。
  - 見直す条件: 行ごとに書く非同期のプログラムで、書きの操作の費用が計測で目立ったとき。
- `Std.Stream` の `_within` の読み: 期限は `Async.timeout` で付けるが、期限が来ると `Reader` を失う
  - 後に回した理由: 期限の後も読み手を保つ使い方がまだない。
  - 見直す条件: 期限の後も同じ `Reader` で読み続けたいプログラムが出たとき。
- `Exec.output_err`: 標準出力と標準エラーを1回で読む `Cmd -> <IO, Panic, Async> (String, String, Int)`
  - 後に回した理由: 標準出力と標準エラーを1回で読む便利な関数で、この段の3つの目的に入らない。読み分けは `Exec.stdout` と `Exec.stderr` を2つのタスクで読めば書ける。
  - 見直す条件: 同じ読み分けの定義が、スクリプトの2か所以上に現れたとき。
- パイプラインの途中の段の標準エラーを読むこと: 今は最後の段の `pipe_stderr` だけが読め、途中の段は起動の誤りである
  - 後に回した理由: 段ごとに `Child` が持つ pipe の端の数と取り出す関数を増やす設計が要る。
  - 見直す条件: 途中の段の診断を取りたいスクリプトが出たとき。
- 非同期の `Fs` の関数、`Std.Stream` の seek、位置を指定する読み書き、読み書き両用の開き方
  - 後に回した理由: 非同期のファイルを使う目的は、ファイルを読み書きしながらほかのタスクを進めることで、順に読み書きする `Stream` で足りる。
  - 見直す条件: 大きなファイルを途中から読むか、書き直すプログラムが出たとき。
- pidfd のない Linux (5.3 より前のカーネル) の `Exec.wait`: 今は種類 `NotAvailable` で失敗する
  - 後に回した理由: 対象の Linux は pidfd のある版で、代わりの待ち方 (`SIGCHLD` や待つスレッド) は別の仕組みを足す。
  - 見直す条件: 5.3 より前のカーネルで `Exec` を動かす必要が出たとき。
- パイプラインの全段の環境変数を一度に設定すること: `Proc.env` は設定した段の環境だけを変える
  - 後に回した理由: 既定は最後の段だけに当てる決めで、全段に当てるかどうかは、同じ変数を全段に設定する例を見て決める。
  - 見直す条件: 同じ変数を全段に設定するスクリプトが出たとき。
- 非同期の `Stdin` と `Stdout`: 今の `Stdin` と `Stdout` はその場で動く同期の行である
  - 後に回した理由: Windows のコンソールの標準入力は overlapped にできず、`Std.Stream` と `Std.Exec` の目的にも入らない。
  - 見直す条件: 標準入力を読みながらほかのタスクを進めたいプログラムが出たとき。
- Windows で子の pipe を読むタスクの Ctrl-C を確かめるテスト: unix では `crates/eml_cli/tests/cli.rs` が `Exec.wait` の待ちの Ctrl-C (終了コード 130) を確かめる
  - 後に回した理由: `crates/eml_cli/tests/cli.rs` にコンソールのイベントを送る仕組みがない。
  - 見直す条件: Windows のコンソールの Ctrl-C を送る仕組みを cli.rs に足すとき。または、Windows で `Std.Exec` の待ちが Ctrl-C で止まらない報告が出たとき。
- `pidfd_open`の`ENOSYS`の場合 (`eml_io`の`sys/unix.rs`) と、pidfdのないLinuxで`wait`が`NotAvailable`で失敗する規則を消すこと ([標準ライブラリ](../spec/stdlib.md)の「`Std.Exec`」)
  - 後に回した理由: 対応するLinuxは6.12以降で、`pidfd_open`はいつもあるが、この場合を残しても費用はない。
  - 見直す条件: 子の終わりを待つコードを変えるとき。

### ネイティブ化

設計は [ネイティブ化の設計](native.md) にある。ここには後に回した項目を置く。

- 引数を型どおりに受ける変種 `f$ret`: 関数の値の呼び出し規約で採らなかった案は、[ネイティブ化の設計](native.md) の「呼び出し規約とエントリ」にある
  - 後に回した理由: 今は変種の薄い形が、自分を呼ぶ `Float` のループを型どおりに保つ。
  - 見直す条件: 特殊化されなかったクロージャで `Float` や構造体を累積するループの箱が、測って問題になったとき。または、データ並列の集まりの関数を入れる段で、`Par.tabulate_unboxed` の要素ごとの `Float` の箱を固定した `RunStats` の行で測るとき ([マルチコア対応の設計](multicore.md) の「未決の論点と将来の拡張」)。
- 置き換えの所で印を下げて `run_once g` を展開する手: 関数の値の呼び出し規約 ([ネイティブ化の設計](native.md) の「呼び出し規約とエントリ」) とともに後に回した手で、展開の置き換えで Kind の印を下げることを許す
  - 後に回した理由: 今は展開の置き換えで、変数の実引数と引数の Kind の印が等しいことを求める ([Core IR](../spec/core-ir.md) の「インライン化」)。
  - 見直す条件: 測って要るとわかったとき。
- 範囲の確かめを消す最適化
  - 後に回した理由: 範囲の確かめは比較1つと冷たいブロックへの分岐で、設計の範囲の外にした。
  - 見直す条件: 範囲の確かめが測って目立つとき。
- ネイティブのコードの使い回し: 鍵は決めてある ([ネイティブ化の設計](native.md) の「AOT と配布」)
  - 後に回した理由: 鍵だけを先に決め、仕組みはコンパイルの待ち時間を測ってから作る。
  - 見直す条件: JIT のコンパイルが [ネイティブ化の設計](native.md) の「目的と範囲」のコンパイルの条件に届かないとき。std のコンパイル済みの関数を処理系のビルドごとに使い回す形から入れる。
- Windows の ARM64 での実行と配布
  - 後に回した理由: コード生成は `aarch64-pc-windows-msvc` でも確かめてあるが、AOT の段で動かして確かめるのは CI の3つの OS である。
  - 見直す条件: 利用者が Windows の ARM64 を使うとき。
- Windows でのビルドに `lld` を同梱すること
  - 後に回した理由: Visual Studio の Build Tools か、入れてある `lld-link` で足りる。
  - 見直す条件: Visual Studio の Build Tools を入れられない利用者が出たとき。
- macOS の hardened runtime の下の JIT: `cranelift-jit` は `MAP_JIT` を使わずにコードを置くので、hardened runtime で署名した処理系では C の関数の橋渡しを作れない ([VM](../spec/vm.md) の「橋渡しの関数」)
  - 後に回した理由: 今の処理系は署名して配らず、hardened runtime の下で動かさない。署名して配る形は `native-aot` で決める。
  - 見直す条件: `native-aot` の段で、署名して配る処理系の JIT (REPL と `eml run`) の扱いを決めるとき。
- ネイティブのプロファイラ: ネイティブのrun (`eml run --native`、後にAOTのバイナリ) のためのサンプリングのプロファイラ。各workerの (pc, fp) を一定の間隔で読み、フレームレコードをたどり、JITの記号の表とエントリの表で名前を引いて、emlの関数ごと、位置がわかる所ではソースの行ごと、タスクごとに報告する。Linuxでは`perf`のmapかjitdumpを書き、macOSとWindowsの道具には同じ役の記号の表を書く。行ごとに帰属させるため、LIRの文に位置を持たせる (今、位置を持つのはexternの文だけである)。足場 (フレームポインタ、stubが保つフレームレコードの鎖、エントリの記述子の表、関数ごとの変わらない記号の名前) はjitの段が置く。プロファイラは時間を測り、`RunStats`は仕事の回数を数える。どちらも、もう片方の代わりにはならない。`RunStats`はVMの検査モードが数え、作業の回数はスケジュールにもworkerの数にもよらない ([マルチコア対応の設計](multicore.md)の「`par` の印付け」)。ネイティブのコードは同じLIRを実行するので、RCの操作と確保の回数はVMと同じである。そのため、プロファイラは回数を数えず、報告は同じプログラムの`eml run --stats`の出力と並べて読む。`RunStats`がスケジュールによらないことは、このためにも保つ。プロファイラは標本を、emlの関数のほかに、実行系のエントリの種類 (確保、解放、`dup`と`decref`の遅い道、`share`、reuse) でも分けて報告する。`share`と共有の側のRCに使った時間は、private dequeを見直す条件 (上の「マルチコア対応」) を判定する材料になる。共有にした物体の数は`RunStats`の`shared_objects`にある。共有の側の`dup`と`decref`の回数の欄はなく、時間だけで判定できないときに足す。前提: `native-aot`
  - 後に回した理由: 仕上がったバックエンドと、AOTのバイナリの記号の表が要る。
  - 見直す条件: `native-aot`が閉じたとき。
- `--stack-size`: ネイティブのworkerが予約するスタックの大きさを変える選択肢
  - 後に回した理由: workerは1 GiBの仮想の予約を持ち、ネイティブのコードの深さの上限はそのスタックである。ほかの大きさを要るプログラムはまだない。
  - 見直す条件: `jit-tasks`までに利用者が出すかを決めるとき。または、プログラムがほかの深さの上限を要るとき。
- `-- max-bytes:`の印を持つ5つのUIテストのネイティブでの扱い: どれにも`native: skip`の印を付けていない
  - 後に回した理由: ネイティブのコードはVMと同じく`max-bytes`に従う。`tests/ui/run/limits/soft_limit_without_a_task.em`はネイティブでも同じ結果になる。`async/`の4つはネイティブのコードが断るタスクの行を使うので、まだネイティブでは流れない。
  - 見直す条件: `jit-tasks`がタスクの行を受け入れるとき。ネイティブでも結果が同じファイルに印は要らない。
- `ctx`をレジスタに固定すること: ネイティブのコードは呼び出しの後に`ctx`を読み直さなくなる
  - 後に回した理由: emlのどの関数もどのエントリも`ctx`を最初の引数に取るという契約を変えるので、利用者に戻して決める。`tail`の呼び出し規約は、ふつうの呼び出しをまたいでプラットフォームの呼ばれる側が保存するレジスタを保つ。だから`ctx`は空いているそのレジスタに残り、退避するのは空きがないときだけである。
  - 見直す条件: `bench/native.sh`の呼び出しの多い行 (`fib`) は、呼び出し1回あたり約66命令である ([計測の基準](../implementation/benchmarks.md)の「ネイティブの数値」)。`native-inline`がほかの費用を減らした後に、`ctx`の退避と読み直しが呼び出し1回あたりの命令の1割を超えるとき。
- ロード1つの入口の安全点: 止める要求が`stack_limit`も書き、安全点はスタックポインタだけを比べる
  - 後に回した理由: ロード3つの安全点 (ロード3つ、比較2つ、`bor`、分岐1つ) は、どの呼び出しも払う最大の決まった費用である。ロード1つの形では、ほかのスレッドが`stack_limit`を書くことになり、workerだけがそれを書くという規則に反する。
  - 見直す条件: `native-inline`の後に、安全点が`bench/native.sh`の呼び出しの多い行の呼び出し1回あたりの命令 (約66) の2割を超えるとき。
- 葉の関数の安全点を省くこと
  - 後に回した理由: どの関数も安全点で始まるという規則に例外を作る。
  - 見直す条件: ロード1つの安全点と一緒に、`bench/native.sh`の数値で決める。
- 分岐2つの安全点: 止める語と`stack_limit`をそれぞれ比較と分岐の組で確かめ、2つの比較を`bor`で合わせない
  - 後に回した理由: 参照の数え方の査読が挙げた最適化で、効きをまだ測っていないので見送った。
  - 見直す条件: ロード1つの安全点と一緒に決める。
- 比較と分岐の融合: caseの少ないタグの`switch`を、`cranelift_frontend::Switch`を通さずに比較と分岐で下ろす
  - 後に回した理由: 同じ文に2つ目の下ろし方を足すことになる。
  - 見直す条件: `native-inline`が`bench/native.sh`のデータの多い行の`switch`を測るとき。
- 分岐の配置: インラインの`dup`、`decref`、`release`の速い道のブロックの並べ方を変えること
  - 後に回した理由: 参照の数え方の査読が挙げた最適化で、効きをまだ測っていないので見送った。
  - 見直す条件: `native-inline`が`bench/native.sh`の参照の数え方の多い行 (`list`、`tree`、`upsert`) を測るとき。
- 冷たい道のエントリを、すべてのレジスタを保つ呼び出し規約で呼ぶこと
  - 後に回した理由: 参照の数え方の査読が挙げた最適化で、効きをまだ測っていないので見送った。
  - 見直す条件: 冷たい呼び出しのまわりの退避が、`bench/native.sh`の呼び出し1回あたりの命令に現れるとき。
- 熱いエントリから`catch_unwind`を外すこと
  - 後に回した理由: `catch_unwind`の速い道に費用はない。`bench/rt.sh`の`entry-plain`と`entry-shim`の差は揺れより小さい ([計測の基準](../implementation/benchmarks.md)の「ネイティブの数値」)。
  - 見直す条件: 2つの行の差が揺れを超えるとき。
- 関数の値と`apply`の道のほかの形: ネイティブの関数の値は、ヘッダが記述子の物体である ([ネイティブの実行系](../spec/native.md)の「関数の値」)。見送った案は次のとおりである。VMの`imm(f | k << 32)`と関数の表 (`apply`ごとに依存するロードが3つ)。引数の数とコードを1つの即値に詰めること (アドレスの幅に依存する)。`n`のためのヘッダの2つ目の語 (クロージャごとに8バイト)。静的な記述子を指す即値の関数の値 (呼び出しの所ごとに2回の読み解き)。部分適用のための`(f, k)`ごとのアダプタ。コードの語の決まったずれ (捕まえた値の数に上限を置くか、余りを詰める必要があり、それは特別な場合である。PAPは引数を1つしか持たないので、ずれない)。selectの代わりに`scan`のバイトで分岐すること (コードのロードが`meta`のロードに依存しなくなるが、所ごとに分岐とブロックが1つずつ増える)。`m`個の引数をすべて持ち、`(m, r)`ごとにアダプタを持つPAP (どの`m`でも1段で済むが、アダプタはおよそ`A²/2`個で、コードは`A`の3乗に比例し、`A`がおよそ176で領域が埋まる)。`eml$apply$m`の、`(m, n)`ごとに腕を持つ`n`の`Switch` (一時のPAPはできないが、`M`の3乗に比例し、`M = 253`で122 MB)。メモリを通すPAPの引数 (PAPの中のslotを埋めるか、workerごとの置き場。共有のPAPを呼ぶたびに割り当てかサービスの呼び出しが要るか、容量の不変条件を持つworkerの新しい状態が要る)。どの案もVMに触らない
  - 後に回した理由: どれも特別な場合か、重複した論理か、壊れやすい不変条件の要る最適化であるか、コードが最も幅の広い値の3乗で増える。きれいな設計を先にする。
  - 見直す条件: `native-inline`が最終の目標を判断するときに、`bench/native.sh`で`apply`の道が目立つとき。`apply`の道を測る行`apply_int`と`apply_float`は、stdの行`Std.Env.arg`を使うので、まだ断られる。
- 一意な道で箱をインラインで空けること: クロージャのエントリ`c<k>`、PAPのアダプタ`eml$pap$<r>`、`release`は、ただ1つの持ち主が持つ箱を`eml_rt_free_block`の呼び出し1つで空ける ([ネイティブの実行系](../spec/native.md)の「データ」「関数の値」)
  - 後に回した理由: インラインで空けると、インラインの割り当てと同じく、`eml_rt`の確保器の事実が生成したコードに入る。どちらも`eml_rt`がその事実を外へ出してから行う。
  - 見直す条件: `native-inline`が生成したコードで割り当てを展開するとき。
- 関数の値と`apply`が出すコードに上限を置くこと: PAPのアダプタ`eml$pap$<r>`と補助の関数`eml$apply$m`のコードは、最も幅の広い関数の値の待つ引数の数`A`と、最も幅の広い`apply`の引数の数`M`の2乗に比例する (devのプロファイルで測った: `A = 254`でアダプタ253、0.6 MB、0.16秒。`M = 253`で補助の関数253、1.1 MB、0.67秒。`A = 1000`で3.5秒)
  - 後に回した理由: UIのプログラムでは`A`は4以下で、`M`は3つのプログラム (3、29、30) を除いて2である。`M = 30`の補助の関数は全部で17,084バイトで、devのプロファイルで10 msである。だから上限は置かない。
  - 見直す条件: UIのファイルかbenchの行の、読み込みの時間かコードの大きさにそれが現れたとき。

### FFI と拡張

設計は [FFI と拡張の設計](ffi.md) にある。ここには後に回した項目を置く。既定は同じ文書の「GUI」と「未決の論点と将来の拡張」にある。

- stdの`extern`の行に付け、translateが下ろす`blocking`の属性: Rustの処理をブロックする呼び出しのプールで動かすstdの行を1つの行で書き、translateが`blocking`のCの関数と同じく受け付けと取り出しに分ける ([VM](../spec/vm.md) の「プールの仕事」)
  - 後に回した理由: Rustの処理をプールで動かすstdの行の族は1つ (`Std.Tls`) しかなく、手で書く3つ組は2つの行とemlの3行で済む。属性には、`ExternRef`のstdの行の受け付けと取り出しの変種、`eml_extern`の2つ目の導出、VMの腕の分割、translateの変更が要る。
  - 見直す条件: プラグインのような、`blocking`のCの呼び出しと`Std.Tls`に次ぐ3つ目の仕事の行の族が現れたとき。`Std.Gui`の行はメインのスレッドで動き、プールの仕事ではないので、この族に当たらない。
- 同期のコールバック: 比較の関数を渡す API (`qsort`)、常微分方程式と積分のソルバー (GSL、SUNDIALS)、訪問の API が使う
  - 後に回した理由: 目標の BLAS、LAPACK、Accelerate、MKL は要らない。同じスレッドの同期のコールバックは、巻き戻しの仕組みを変えずに後で足せる。
  - 見直す条件: 目標のライブラリで、初めてコールバックが要るものが出たとき。
- C の構造体と可変長の引数
  - 後に回した理由: これを超えるものは今と同じく Rust で書いた std の extern の行にする。
  - 見直す条件: ライブラリが要るとき。
- NUL で終わる文字列を利用者の `extern "C"` で渡すこと
  - 後に回した理由: `String` と `Bytes` は NUL を置かない。NUL で終わる `const char*` が要る C の API は、Rust で書いた std の extern の行の中で写して渡せる。
  - 見直す条件: `const char*` を受ける C の関数を、利用者の `extern "C"` で直接呼びたい用途が出たとき。
- C のレベルの受け箱: 自分のスレッドを持つ C のライブラリから eml へ知らせるインターフェース
  - 後に回した理由: そういう連携は Rust のプラグインだけで行う。
  - 見直す条件: 自分のスレッドを持つ C のライブラリを、プラグインなしで使いたいとき。
- 32 ビットの要素とバイトの要素の生の配列: `Unboxed` と `MutUnboxed` の新しい instance (`Byte` や 32 ビットの型) として足す。`Raw` の物体の要素はいつも 8 バイトで、`tag` は幅のために空けてある ([オブジェクトモデル](../spec/object-model.md) の「種類」)。幅に依る操作 (`length`、`set` と `thaw` の写す道、回復) は、物体の `tag` に幅を書くか、幅に依る関数をクラスに移すかのどちらかで決める。`Bytes` は名前を変えず、この族にも入れない。C に `uint8_t*` を書かせる API が要るときは `instance MutUnboxed Byte` を足すので、バイトの列の型が `Bytes` と `UnboxedArray Byte` の2つになり、変換の関数2つでつなぐ
  - 後に回した理由: 生の要素の配列の要素は 8 バイトで、バイトの並びには `Bytes` がある。利用者の `extern "C"` が C に貸せる配列も、要素が 64 ビットのものだけである ([宣言](../spec/declarations.md) の「型の対応」)。BLAS と ILP64 の Fortran の LAPACK はこれで呼べる。
  - 見直す条件: LP64 の LAPACK、LAPACKE の `ipiv`、`float` の buffer のように、32 ビットの要素の buffer を渡す C の API が要るとき。または、C の API が可変のバイトの buffer を求めたとき。

### GUI

設計は[FFI と拡張の設計](ffi.md)の「GUI」にある。ここには後に回した項目を置く。

- 宣言的な層: `Std.Gui`の原始的な操作の上で、画面を作る関数を動かし直し、結果の差分を取る
  - 後に回した理由: ハンドルを通して変える、持ち続けるウィジェットで、書式の画面には足りる。差分を取るには、キーで照らし合わせる仕組みが要る。
  - 見直す条件: 2つの実際のプログラムで、ハンドルの管理がコードの大半を占めたとき。
- ウィジェットの追加 (テキストエリア、スライダー、リスト、画像、ラジオボタンの組、タブ、スクロールする領域)、ダイアログ、メニュー、クリップボード、ドラッグアンドドロップ、キーボードのショートカット、字体と色とアイコン、自分で描くこと
  - 後に回した理由: ウィジェットは、3つのtoolkitのどれにも同じ性質とイベントを持つネイティブのクラスがあるものに限る。1つ足すごとに、3つのbackend、stub、std、UIテストを一度に変える。
  - 見直す条件: プログラムが要るとき。利用者が要るウィジェットが2つのtoolkitにしかないときは、この決まり自体を考え直す。
- gridの明示の置き方 (`at row col`)、名前を付けた領域、利用者が決める間隔と余白
  - 後に回した理由: 書式の画面は自動の置き方で足り、単純さを先にした。
  - 見直す条件: 自動の置き方では、実際のプログラムの配置を書けないとき。
- ウィンドウの最小の大きさを置き直すこと (`Widgets::set_min_size`)
  - 後に回した理由: ネイティブの最小の大きさは、ウィンドウを初めて表示するときに決め、後で中身が増えても変えない。
  - 見直す条件: 中身が増えて切れたウィンドウを見せるプログラムが出たとき。
- WindowsのGUIのループの源にIOCPを使うこと
  - 後に回した理由: WinUIのループはメインのworkerのdriverの源を持たず、操作が保留の間は1回の待ちを10 msまでにして問う。
  - 見直す条件: Windowsで、固定したタスクのI/Oが10 msの問いのために遅れたとき。
- Windows 10のGUI
  - 後に回した理由: Windows App SDKのruntimeをプロセスに加える関数は、Windows 11のkernelbaseにしかない。
  - 見直す条件: Windows 10でGUIを要る利用者が出たとき。
- `eml_rt`の`Plugin`のtrait
  - 後に回した理由: プラグインが1つでは、検証するcrateにtraitを入れる理由にならない。`Std.Gui`はcfgのfeatureで切り替える ([FFI と拡張の設計](ffi.md)の「拡張」)。
  - 見直す条件: 2つ目のプラグインが現れたとき、または`jit-externs`がプラグインをまたいで行ごとに型の付いたエントリを要るとき。
- `eml run`の外のプロセス (`Machine`のAPIのhost) で、ネイティブの`Gui.run`をrunをまたいで繰り返すこと
  - 後に回した理由: `eml run`はプロセスで1つのrunを動かし、それ以上を要るhostはない。試していない。
  - 見直す条件: `Machine`のAPIのhostが要るとき。
- WinUIのbackendのメインスレッドの確かめ
  - 後に回した理由: WinUIは、Rustのruntimeが`main`と名づけたスレッドかどうかで確かめる。`eml run`ではそれがプロセスのメインスレッドである。AppKitとQtはOSに問うので、変えなくてよい。
  - 見直す条件: Cの`main`を持つネイティブのAOTのバイナリか、`Machine`を埋め込むhostが、WindowsでGUIを開くとき。
- `gui::`のテストをThreadSanitizerとAddressSanitizerで流すこと: スレッドをまたぐGUIの道 (どのworkerからも鳴るwaker、どのworkerでも落ちうる`Ui`の回収の旗、メインのworkerの外のタスクの`Gui.post`) は、どちらのsanitizerの一覧にも入っていない
  - 後に回した理由: 段の計画が求めておらず、sanitizerが何かを見つけるかは確かめていない。
  - 見直す条件: GUIの`Park`か`Std.Gui`のスレッドをまたぐ道を変えるとき、またはGUIのテストが原因の分からないまま落ちたとき。
- WinUIのbindingを、公開されたwindows-rsのcrateに替えること
  - 後に回した理由: windows-rsは`Microsoft.UI`の生のbindingを公開していないので、emlがメタデータから生成する ([コンパイラの構成](../implementation/architecture.md)の「`eml_gui`の内部」)。
  - 見直す条件: そのようなcrateが公開されたとき。そのときは、生成したファイルと`nix/winui-bindings.sh`を消す。
- WinUIのメタデータの版を上げること
  - 後に回した理由: bootstrapの最小のruntimeの版はメタデータの版と同じにして、bindingのAPIがどれもruntimeにあることを保つ。両者はコメントで結んであり、一緒に上げる。
  - 見直す条件: backendが後のWindows App SDKのAPIを要るとき、または2.6の保守が終わるとき。
- Windows App SDKのインストーラの条件
  - 後に回した理由: まだ読んでいない。emlはMicrosoftのものを何も配らないので、emlの側に条件は生じない ([配布とGUIの前提](../implementation/distribution.md)の「Windows App SDKのruntime」)。
  - 見直す条件: emlかプログラムの作者がインストーラを同梱して配るとき、またはMicrosoftの2.xのライセンスを読み直すとき。
- emlのバイナリキャッシュかリリースのtarballを公開すること
  - 後に回した理由: emlは`nix build`でだけ配る。closureを公開するキャッシュはQtを配る者になり、Qtを同梱したtarballはそのQtのソースへの案内を負う ([配布とGUIの前提](../implementation/distribution.md)の「Qtを配る規則」)。
  - 見直す条件: どちらかを公開するとき。
- Slintのプラグイン
  - 後に回した理由: GUIのtoolkitはOSのウィジェットを包む。
  - 見直す条件: Slintが求められたとき。
