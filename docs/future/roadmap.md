# ロードマップ

位置づけ: 将来の設計。

今後の実装を、M1 と M2 に続くマイルストーン M3〜M9 の列と、その後の項目に分けてまとめる。今の言語の範囲は [実装の現在地](../implementation/status.md) の「今の言語の範囲」にある。

## マイルストーンの進め方

- 各マイルストーンは、spec、計画、実装の順に進める。spec は、この文書のそのマイルストーンの節を出発点にする
- 「決めたこと」は方針で、細部はそのマイルストーンの spec で決める。「論点」は、そのマイルストーンの spec で決める
- マイルストーンを終えたら、決まったことを `spec/` に移し (実装の構造に関わるものは `implementation/` に移し)、[実装の現在地](../implementation/status.md) を更新し、この文書からそのマイルストーンの節を削る
- マイルストーンは、パイプラインの段階 (crate) とは別の呼び方である

## マイルストーンの列

並べる軸は「型システムの実験を先にする」である。

| マイルストーン | 中身 | 前提 |
|---|---|---|
| M3 レコード、リスト、文字列 | 名前付きのレコードと `type`、row の仕組みを sort 付きの1つにする、射影と更新の線形性、`t.0`、レイアウト規則3と `with` の衝突、借用のオペランドと `Field`。リストのリテラルと `::`。補間 (穴は `String` に限る)、複数行の文字列、raw 文字列、lexer のモード | なし |
| M4 数値と文字 | `Float` と `Char` の型、リテラル、Prelude の演算。`+ - * < <= > >=`、`==`、前置の `-` を組み込みの型ごとに解決する | なし |
| M5 型クラス | 構文、検査、特殊化による変換、Prelude のクラス、`deriving`、タプルとレコードの構造的な instance、補間の穴を表示用のクラスに広げる | M3、M4 |
| M6 REPL | Prelude と指定したモジュールを読み込んだ対話実行。M8 の後は標準ライブラリも読み込む | M5 |
| M7 バイト列と入出力 | `Byte`、ビット演算、`Bytes`、`Array`、`Lin` のハンドルとバッファ付きの読み書き | M5 |
| M8 UTF-8 と標準ライブラリ | UTF-8 の核の intrinsic、eml で書く最初の標準ライブラリのモジュール、ストリーム処理のエフェクト | M4、M7 |
| M9 コマンドリテラル | コマンドリテラルの CST と lexer のモード、`Cmd` と `Proc` | M3、M8 |

順序の理由は次のとおり。

- M2 を最初に終えたのは、M2 で作った参照ごとの具体化の表 ([コンパイラの構成](../implementation/architecture.md) の「`eml_types` の内部」) が、M4 の演算子の解決と M5 の型クラスの証拠の土台になるためである
- M3 を M4 の前に置くのは、レコード、リスト、文字列の構文を一続きで終えるためである。M3 と M4 はどちらも前提を持たないので、入れ替えても依存は崩れない
- M4 で、型クラスより先に組み込みの型だけの多重定義を入れる。M5 と同じ曖昧さの規則を使うので、曖昧さの規則に伴うテストの振る舞いの変更 (種類1) への合意は M4 の1回で済む。M5 にも、比べられない型の診断を instance がない診断に置き換えるなど、別の種類1の変更が残る
- M6 を M5 の直後に置くのは、REPL が値を表示用のクラスで表示でき、その場しのぎの表示器が要らないためである。また、M7 以降を REPL で試しながら作れる
- M7 を M5 の後に置くのは、`Byte` と `Int` で演算子を共有するためである

## M3 レコード、リスト、文字列

前提: なし。

名前付きのレコードと `type`、row の仕組みを sort 付きの1つにすること、射影と更新の線形性、`t.0`、レイアウト規則3と `with` の衝突、借用のオペランドと `Field` を入れる。リストのリテラルと `::` を入れる。補間 (穴は `String` に限る)、複数行の文字列、raw 文字列と、そのための lexer のモードを入れる。

### 決めたこと

- 補間の穴は `String` に限り、M5 で表示用のクラスに広げる

### 論点

- row の仕組みを sort 付きの1つにし、エフェクトの row とレコードの row で共有する
- 名前付きのレコードの実行時の表し方 ([直積型とレコード](../spec/records.md)、[Core IR とインタプリタ](../spec/core-ir.md))
- 文字列のトークンを lexer のモードで分ける。lexer のモードのスタックは、補間のトークンと一緒に設計する。未対応のリテラルの E0004 を1か所で出すかどうかも、そのときに決める
- レイアウト規則3とレコードの `with` の衝突を解く
- 借用のオペランドと `Field` を決める
- `::` の fixity
- 補間、レコード、リストの CST
- spec で決めてあり実装を待つもの: タプルの射影 `t.0`、名前付きのレコード、射影と更新の線形性の規則 ([直積型とレコード](../spec/records.md))

## M4 数値と文字

前提: なし。

`Float` と `Char` の型、リテラル、Prelude の演算を入れる。`+ - * < <= > >=`、`==`、前置の `-` を組み込みの型ごとに解決する。

### 決めたこと

- リテラルは単相にする。整数のリテラルは `Int`、浮動小数のリテラルは `Float` である。`fromInteger` 相当の脱糖も defaulting も入れない。`Int` と `Float` を混ぜるときは明示的に変換する
- `Char` は Unicode のスカラー値である
- `+ - * < <= > >=`、`==`、前置の `-` (`negate`) を、組み込みの型ごとに、本体の終わりで解決する。算術は `Int` と `Float`、順序の比較は `Int`、`Float`、`Char` に使える。`String` の順序の比較は M5 の `Ord` で入れる。何も型を決めないオペランド (使われない `let sq = fn x -> x * x` など) は、`Int` に倒さず曖昧さのエラーにする。この規則は M5 の型クラスと同じである
- この規則に伴うテストの振る舞いの変更 (曖昧さのエラー、型の不一致の文言、E2006 の注記、`equality.rs` の連鎖を抑える規則) は種類1で、M4 の spec に挙げて合意を取る

### 論点

- 型ごとの意味: `Float` の `/` と `%` の有無、`Float` の `==` と NaN の結果
- `Float` をリテラルのパターンと `switch` から外すこと
- 多相な位置での `Int` と `Float` のネイティブの表現

## M5 型クラス

前提: M3、M4。

型クラスの構文、検査、特殊化による変換、Prelude のクラス、`deriving`、タプルとレコードの構造的な instance を入れる。補間の穴を表示用のクラスに広げる。

### 決めたこと

- 表面は Haskell 98 の形の単一引数の型クラスにする。`class`、`instance`、上位クラス、`deriving` を持つ。instance の頭は、`data` の型コンストラクタに互いに異なる型変数を適用した形に限る。高カインドのクラス、多引数のクラス、関連型、`Add<Rhs, Output>` 形の演算子のトレイトは入れない
- 実装は、制約に沿った特殊化にする。型検査は参照ごとの具体化を記録して制約を検査し、証拠 (どの instance を使うか) は、記録した型引数から、Core IR と共有する解決の関数で決める。Core IR への変換は、制約を持つ関数を確定した証拠ごとに複製する。制約のない関数は今と同じく1回だけ変換する。実行時の辞書は持たない。そのため、実行時、Value、Perceus、verifier、`debug_heap`、マルチコアの設計は変わらない。組み込みの instance のメソッドは PrimOp に変換するので、単相のプログラムの Core IR はほぼ今のままである。変わる部分は M5 の spec に種類2の変更として挙げる
- エフェクトの操作のシグネチャと `data` のコンストラクタのフィールドには、制約を書けない。書けると、handler の節が perform の位置で選んだ証拠を実行時に受け取る必要が生じ、実行時の辞書が要るためである
- 証拠が循環に沿って大きくなる制約付きの多相再帰 (入れ子のデータ型の `Show` など) は、型検査で弾く。これにより、すべての診断が検査の段階から出る。辞書渡しは、この形のためだけに後で足す余地として残す
- 一貫性を守る。instance は大域的に1つで、クラスか頭の型コンストラクタを定義したモジュールにだけ書ける (モジュール単位の orphan 規則)。重なる instance、局所的な instance、第一級の instance は持たない。instance は名前ではないので、修飾付きの import によらず見える
- 制約はトップレベルのシグネチャへ推論で足さない。解けない制約と曖昧な制約はエラーにする。単相性制限と defaulting は持たない
- 線形性は Kind のままにする。`Copy` や `Drop` のようなクラスは作らず、Kind は instance の選択に関わらない
- レコードとタプルには、処理系が `Eq` と表示用のクラス (タプルは `Ord` も) の構造的な instance を与える。ユーザーのクラスはレコードに instance を持てない
- クラスとエフェクトは別の仕組みである。メソッドの row は普通のシグネチャと同じ規則に従う。Prelude のクラスは純粋なので、`par` の中でも演算子を使える
- Prelude のクラスは `Eq`、`Ord`、`Num` (前置の `-` を含む)、表示用のクラスとする。`String` の順序はバイト順で、妥当な UTF-8 ではコードポイント順と一致する
- 補間の穴は表示用のクラスに広げる。`String` の穴は今と同じく引用符なしで入る
- M5 で `=>` を予約の記号に、`deriving` をキーワードにする。今は `=>` をユーザーが演算子として定義できるので、これは種類1の変更である。それまで [字句](../spec/lexical.md) の予約語と予約記号は変えない

### 論点

- クラスの形: 除算のクラス (instance ごとの小さなクラスにするか、`Integral` / `Fractional` に分けるか)、`Ord` のメソッドを `< <= > >=` にするか `compare` と `Ordering` にするか、`!=` を `Eq` のメソッドにするか普通の関数にするか、`negate` をユーザーに見せるか、既定のメソッドをいつ入れるか、表示用のクラスを `Show` 1つにするか `Show` と `Display` に分けるか、`Float` の `Eq` / `Ord` の法則、レコードの `Ord` のラベルの順
- Kind: メソッドの Kind を位置ごとにどう決めるか、instance のメソッドが推論した Kind の制約をクラスのメソッドの Kind と照らす規則、畳み込みのメソッドで `Lin` の累積値を持てるか、借用が入った後の `Lin` 型のクラス
- 導出: 導出した instance で比べないフィールドを `drop` する形
- 表示: 持ち越しの制約の表示 `a => <e> <= Once` ([型と Kind](../spec/types.md)) を `=>` と重ならない形に変える。型検査のダンプだけに出るので、種類2の変更である
- その他: 接頭辞付きリテラルの穴の型付けに多引数のクラスが要るか、多相再帰のための辞書渡し、複製の数の報告、orphan 規則をパッケージ単位に広げるか

### 方式を選んだ理由

ネイティブ化とインタプリタの効率を重視し、Haskell の型クラスを第一の候補として次の案を比べた。

| 案 | 結論 |
|---|---|
| 型クラス + 辞書渡し (GHC) | 採らない。インタプリタで `+` が PrimOp 1つから、辞書の取り出しと間接呼び出しになる。実行時に辞書の値、射影の Rhs、借用の扱いが要る |
| 辞書渡し + 既知の instance の静的解決 + 特殊化 | 採らない。無償になるのは文脈のない instance だけで、`List Int` の `==` や導出した instance は辞書を通る。辞書の仕組みと複製の仕組みを両方持つことになる |
| Rust のトレイト + すべての総称の単相化 | 採らない。row は単相化できず、仕組みが2本になる。多相再帰を検査の段階の後で弾くことになる |
| 組み込みの型だけの多重定義 | M4 の中継ぎとしてだけ使う。ユーザー定義の型に広げられない |
| 暗黙の引数 (Koka、modular implicits) | 採らない。修飾付きの import と衝突し、型クラスのまとまりも失う |
| クラスをエフェクトで表す | 採らない。row を汚し、解決が動的になる |
| **型クラス + 制約に沿った特殊化** | **採る** |

採った案が成り立つのは、eml の型が rank-1 で、シグネチャが必須で、局所的な `let` とラムダが単相で、局所的な instance も第一級の instance もなく、操作とコンストラクタが制約を持たないためである。この条件では、制約のない本体での制約付きの参照は、すべて確定した証拠を持つ。Roc (RC とその場の更新の実行系) と Austral も型クラスや abilities を特殊化で実行するが、どちらも総称をすべて単相化する。eml の案は、制約を持つ関数だけを複製し、制約のない型変数を今の一様な表現のまま残す。そのため、row の多相にも触れない。代償は、弾く多相再帰と、複製の分だけ増えるコードの大きさである。REPL では、新しい型で総称を使うたびに複製を1つ変換するが、かかるのは Core IR への変換だけである。

## M6 REPL

前提: M5。

Prelude と指定したモジュールを読み込んだ環境で、対話的に実行する。M8 の後は標準ライブラリも読み込む。

### 決めたこと

- 入力は、定義の追加か式の評価である。式は、まず row が `<IO>` に収まるものに限る
- 入力をまたいで残せるのは `Unr` の束縛だけで、`Lin` の値はその入力の中で使い切る。今の線形性の検査をそのまま使える
- orphan 規則では、セッションを1つのモジュールとみなす。後の入力で定義し直すと、変わるのはそれより後の入力だけである
- 結果は表示用のクラスで表示する。特殊化の複製はキャッシュする
- コマンドは GHCi に寄せる (`:load`、`:type`、`:quit` など)

### 論点

- シグネチャのない定義を単相にするか、REPL だけ一般化するか
- `IO` 以外のエフェクトを既定の handler で許すか
- 編集したモジュールの読み直し
- 定義し直した型の表示
- セッションの表し方 (1つの伸びるモジュールか、モジュールの鎖か)

## M7 バイト列と入出力

前提: M5。

`Byte` 型とビット演算、`Bytes`、`Array` を入れる。`Lin` のハンドルと、バッファ付きの読み書きを入れる。

### 決めたこと

- `Byte` (0〜255) を専用の型にする。ビット演算のクラスと演算子と fixity を Prelude に足し、`Int` と `Byte` で共有する
- `Bytes` は `Unr` の値である。`Array a` の Kind は要素の Kind に従う。どちらも意味は不変で、更新は、RC が 1 ならその場で書き換え、そうでなければ写す。分割と結合、並列の書き換えのための `Lin` の `MutArray` と `freeze` は、後で足す (下の「マルチコア対応」)
- ハンドルは `Lin` にする。`Stdin` / `Stdout` / `Stderr` は別の型にする。バッファ付きの読み書きもハンドルにする。intrinsic は、ハンドルに対する read/write の操作にとどめる

### 論点

- `Byte` のリテラルの書き方 (リテラルは単相なので、`Byte` を書く形が要る)
- `Byte` の算術のオーバーフロー (実行時エラーか wrap か)
- 範囲外の添字を実行時エラーにするか `Option` にするか
- 中断のときに書き込みのハンドルを flush するか
- `println` と `Stdout` のハンドルの関係
- `Lin` の要素を持つ `Array` の API
- マルチコアでのハンドルの扱い

## M8 UTF-8 と標準ライブラリ

前提: M4、M7。

UTF-8 の核の intrinsic と、eml で書く最初の標準ライブラリのモジュールを入れる。ストリーム処理のエフェクトも、このモジュールに書く。

### 決めたこと

- `String` は常に妥当な UTF-8 である
- intrinsic は小さい核にとどめる。検証付きのデコード (`Bytes` から `String`)、エンコード、バイト長、バイト位置から `Char` と次の位置を読む操作、境界を検査する切り出しである
- 分割、検索、反復などは、eml で書く最初の標準ライブラリのモジュールにする
- 「行を流す」などのストリーム処理は、ユーザー定義のエフェクトとして、このモジュールの中に書く
- 書記素クラスタと正規化は対象外にする

### 論点

- 位置の単位 (バイト位置を不透明な型にするか)
- 不正な UTF-8 の扱い (エラーか置換か)
- 大文字と小文字の変換など、Unicode の表が要る操作を intrinsic にするか対象外にするか

## M9 コマンドリテラル

前提: M3、M8。

コマンドリテラルの CST と lexer のモード、標準ライブラリの `Cmd` と `Proc` を入れる。

### 決めたこと

- コマンドリテラルはシェルを介さず、引数のリストを組む ([字句](../spec/lexical.md) の「コマンドリテラル」)

### 論点

- コマンドリテラルの CST
- `Cmd` と `Proc` の API ([標準ライブラリへの申し送り](stdlib.md) の `Cmd` の項目)

## マイルストーンの後の項目

M3〜M9 に含めない項目を、分野ごとにまとめる。方針まで決まっている項目と、論点を挙げただけの項目がある。詳しい設計がある項目は、その文書へのリンクを付けた。「前提」は、先に済ませておくマイルストーンか項目である。前提を書いていない項目は、どのマイルストーンの後でも着手できる。

### 型システム

- 使い切り必須の型: 捨てることを許さない線形型。ユーザーが Kind を書けるようにする段階で、Kind に「drop できるか」の次元を追加して扱う。前提: ユーザーによる Kind の記述
- row 要素ごとの捕捉 Kind: `<IO, Async@lin>` のように、row の各要素に「捕まえてよい Kind」を推論で持たせ、`never` / `once` の持ち越し規則をより柔軟にする。マルチコア対応で挙がった「`Heap` を含まない row」の制約も、同じ種類の拡張として扱う ([マルチコア対応の設計](multicore.md))
- ユーザーによる Kind の記述: 内部の Kind 変数を表面の構文に開放する。関数型の線形性 `m` も含む
- 借用: Rust / Austral 方式。意味論の大きな追加になる
- 関数型の部分 Kind による包摂: `Unr` の関数を `Lin` の関数型の場所に渡せるようにする。今は関数型どうしの単一化で線形性 `m` を等しくする ([型と Kind](../spec/types.md) の「関数型」)
- 省略した row の暗黙の row 変数: 今は省略した row を `<>` と読む ([型と Kind](../spec/types.md) の「関数型」)。高階関数で row 変数を書く量が負担になるなら、Frank の周囲の ability のように、1つのシグネチャの中で省略した row をすべて同じ暗黙の row 変数 ε とする規則に広げる。`map : (a -> b) -> List a -> List b` が `(a -> <ε> b) -> List a -> <ε> List b` になる
  - 互換の条件: 既存のシグネチャの型が、広げた規則の型の特別な場合 (ε := `<>`) になる形でだけ広げる。そのため、ε を入れるのは row を1つも書いていないシグネチャに限る。row を1つでも書いたシグネチャは、今と同じく省略を `<>` と読む。たとえば `twice : (Unit -> Unit) -> <IO> Unit` の引数に ε を入れると、閉じた `<IO>` の本体でコールバックを呼べなくなり、今は通るプログラムが通らなくなる
  - ε を入れるのはトップレベルのシグネチャだけで、`data` のフィールドの型には入れない。ローカルの型の明示とラムダの引数の型で省略した row は、推論用の row 変数に変えてもよい (型がより一般になるだけなので互換である)
- フィールドの関数型の線形性: `data` のフィールドに書いた関数型の線形性は、表面の構文で `m` を書けないので `Unr` に固定している ([型と Kind](../spec/types.md))。線形なクロージャを `data` に入れられるようにするかを見直す。前提: ユーザーによる Kind の記述
- 操作の引数の Kind 変数: 操作の引数の型に現れる Kind 変数は `Unr` に固定している ([エフェクトと handler](../spec/effects.md) の「handler の意味」)。線形な値を多相な操作の引数で渡せるようにするかを見直す

### 言語機能と構文

- 可変参照 (方針は決定済み): 値 `Ref h a` と組み込みのエフェクト `Heap h` を持ち、`IO` と分離する。`run_heap` は rank-2 の組み込みとして特別扱いする。`Ref` には `Unr` の値だけを入れ、multi-shot で再開したときの状態は共有する ([マルチコア対応の設計](multicore.md) の「可変状態」)
- 局所的な可変変数の糖衣構文: Koka の `var` のように、関数の中に閉じた可変変数を `Heap` を外に見せずに書けるようにする。前提: 可変参照
- 線形値の受け渡しの糖衣: `read_all &input` を `let (input, r) = read_all input` に脱糖する、Swift の `inout` 風の構文。API の返り値の形を縛ることと、巻き上げの規則が課題である。標準ライブラリを書いてみて、受け渡しが負担になるなら再検討する。前提: M8
- フィールドの変換の糖衣: `{ p with age = _ + 1 }` のような、関数でフィールドを書き換える構文。`Lin` なレコードでも、分解せずに書けるようにする。前提: M3
- サンクの糖衣: `fn () ->` が多い場合の短縮形。現時点では `use` とセクションで十分と判断した
- 抽象型: コンストラクタを公開しない `pub data`
- 再エクスポート: `pub import`
- 修飾した演算子の構文 (`Csv.(</>)`)
- 優先順位グループ: 整数の優先順位で、ライブラリ同士の演算子の衝突が問題になった場合の代替案 (Swift 方式)
- 標準ライブラリの API の範囲: M8 で最初のモジュールを作った後、`Fs`、`Path`、`Proc`、`Json` などのモジュールの API を別の spec で決める ([標準ライブラリへの申し送り](stdlib.md))。前提: M8
- 接頭辞付きリテラルの一般化: `re"..."` のように、ユーザーが接頭辞付きのリテラルを定義できるようにする。穴の型付けにアドホック多相が要る。前提: M3、M5
- or パターン、ガード、as パターン: パターンを広げる。網羅性の検査 ([網羅性](../spec/exhaustiveness.md)) と決定木の変換を一緒に広げる
- 仮置きの式: どの型にもなる仮置きの式 (typed hole)。入れるときに、網羅されていない `match` と等式の fix (E4001 の枝の追加、E4002 の等式の追加の提案) を一緒に入れる ([診断の出し方](../implementation/diagnostics.md) の「網羅性の診断」)

### 処理系

- インクリメンタル化: 各段階をクエリ (salsa など) に載せ替える。各段階を純粋な関数にしているのはこのため ([コンパイラの構成](../implementation/architecture.md))
- LSP: 診断、hover (型と row の表示)、補完、code action。診断の構造体は、LSP の診断と code action に変換できる形にしてある ([診断](../spec/diagnostics.md))。前提: インクリメンタル化
- ネイティブ化: 同じ Core IR から LLVM へ変換する。エフェクトは generalized evidence passing と yield の bubbling (Koka 方式) で実装する。スタックの切り替えは、性能が足りない場合の選択肢として残す ([evidence passing の設計](evidence-passing.md))。前提: M4 (多相な位置での `Int` と `Float` の表現)
- レコードのネイティブな表現: フィールドの位置が多相になる箇所に、オフセットを証拠として渡す (evidence passing) か、単相化するか。前提: M3、ネイティブ化
- Perceus の最適化: reuse analysis (FBIP)、借用パラメータ。あわせて次の2点を見直す
  - Core IR の変数は Kind を持たず、ボックス化した変数はすべて Perceus の対象になる。`File` も RC で数え、`read_all` と `close` は一意性を求めないので正しく動く。`Lin` の変数を Perceus の対象から外すかを、借用と reuse と一緒に決める
  - 変数の枝が scrutinee そのものを受ける `match` (`| ys -> f ys`) では、Perceus が `Switch` の前に scrutinee を `dup` するので、一意な箱でも `take_or_copy` の写す経路を通る。結果は正しいが、reuse analysis で写さずに済むようにする
- 引数のないトップレベルの値の計算: 今は参照するたびに計算する ([Core IR とインタプリタ](../spec/core-ir.md))。一度だけ計算して覚えておく形にする
- すぐに再開する handler の最適化: 節が `resume k v` を末尾で1回だけ呼ぶ場合に、継続を取り出さない直接の呼び出しにする ([evidence passing の設計](evidence-passing.md) の「すぐに再開する節」)
- 再帰する join point (ループ化): 自己末尾呼び出しを、関数の中の自分へ `jump` する join point にする。トップレベルの関数を呼び出し元の join point にする contification も同じ枠で扱う。今は join point の本体から自分へ `jump` しない ([Core IR とインタプリタ](../spec/core-ir.md))
  - 入れる時期: 今は入れない。eml のローカルの `let` は再帰せず、自己末尾呼び出しはすでにフレームを積まないので、インタプリタでの効果が小さい。ループの中で変わらない値の `dup` / `decref` を減らすには、`captures` を借用として扱う Perceus の拡張も要る。借用パラメータ、evidence passing、ネイティブ化のどれかに着手するときに一緒に入れる
  - 残りの作業: verifier の「自分へ `jump` しない」制約を外すことと、変換にループ化を足すこと。join point はすでに複数の引数を持てる
  - 生存解析には、再帰する join point だけ不動点の計算が要る。`liveness::analyze` は join point の本体を範囲より先に1回だけたどり、`jump` で行き先の `captures` を読む。そのため自分への `jump` では、まだ空の `captures` を読んでしまう。ループ化では、再帰する join point に印を付け、そこだけ不動点を計算する。simplify の F、B3、B5 も join point が非巡回であることを前提にしているので、あわせて見直す。互いに `jump` し合う join point の組は、別に設計する
- simplify の書き直し: use と def の索引の上で書き直す。足りない書き換え (別名の伝播、定数の `switch` の畳み込み) もそのときに入れる。今の規則は1巡だけ回し、最適化が効かない形があっても結果は正しい。索引が役に立つのは、書き換えを足すとき、不動点まで繰り返すとき、B2 の置き換えの時間が問題になるときである。B2 の置き換えは枝の部分木をたどるので、条件に `&&` や `||` を使う `else if` が末尾で長く続くと、続きの深さの2乗の時間がかかる。これを直すには、変数から使用の位置への索引を巡ごとに作る。このどれかに着手するときに書き直す。不動点まで繰り返すことにしたときは、B3 が長い続きの連鎖を `Switch` の枝の中へ移しうる。Perceus と verifier は `Switch` の枝を再帰でたどるので、E0013 はその深さの上限にならなくなる
- 実行時エラーの位置: 位置と backtrace、利用者向けの関数名を実行時エラーに付ける。Core IR の式は HIR の位置を持たないので、位置を運ぶ形 (次の source map) を決めてから入れる
- HIR の位置を source map に移す: HIR のノードが `TextRange` を直接持つ形をやめる。位置を別の表に分けると、編集で位置だけが変わったときに HIR を作り直さずに済む。この利点はインクリメンタル化 (salsa) に載せ替えるまで効かないので、そのときに移す
- フォーマッタ: CST がロスレスなので、その上に作る。前提: M9 (本番の構文がそろってから)
- n 列の `match`: 今は決定木の列に、最初の行でコンストラクタ、タプル、リテラルのどれかのパターンを持ついちばん左の列を選ぶ ([Core IR とインタプリタ](../spec/core-ir.md))。行列によっては部分木が大きくなりうる。今の選び方でも決定木は正しいので、部分木の大きさが問題になる例が出てから列の選び方を見直す
- doc comment: trivia の付け方を決める。doc comment を解釈するドキュメント生成と LSP の hover ([字句](../spec/lexical.md)) がまだないので、それを作るときに、使う側に合わせて決める。前提: LSP
- 記述子: ペイロードの種類ごとの方針を、記述子に持たせる。インタプリタでは `Payload` の enum が種類を表し、種類ごとの処理 (子のたどり方、写せるかどうか) を `match` で書ける。Rust の enum に頼れないネイティブ化では、静的な型の情報なしにオブジェクトを扱うために、記述子が方針を持つ必要がある ([ランタイム](../spec/runtime.md) の「オブジェクトのヘッダ」)。そのため、ネイティブ化と一緒に入れる。前提: ネイティブ化

### マルチコア対応

詳細は [マルチコア対応の設計](multicore.md) にある。主な項目は次のとおり。

- 共有の印方式の RC
- データ並列に限った `par` の段階的な拡張 (a1 → a2-wait → a2-cancel)
- 並行処理の `spawn` と `run_scheduler`
- 継続の移動
- マルチコアのインタプリタ

同じ文書の「未決の論点と将来の拡張」には、さらに先の論点がある。並列タスクからすぐに再開する操作を外に出す案 (a4)、逐次実行と同じ意味の `par_ordered` (a3)、`Lin` の `MutArray` と `freeze` (前提: M7、Perceus の reuse analysis)、並行処理用の共有の可変状態、`IO` が大域的な領域を含む折衷案、private deque、ネイティブのアロケータ、マルチコア版のヒープの実装方式である。
