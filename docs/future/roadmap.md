# ロードマップ

位置づけ: 将来の設計。

マイルストーン1 の後に扱う論点と将来の拡張を、分野ごとにまとめる。方針まで決まっている項目と、論点を挙げただけの項目がある。詳しい設計がある項目は、その文書へのリンクを付けた。マイルストーン1 の範囲は [実装の現在地](../implementation/status.md) にある。

## 型システム

- 使い切り必須の型: 捨てることを許さない線形型。ユーザーが Kind を書けるようにする段階で、Kind に「drop できるか」の次元を追加して扱う
- row 要素ごとの捕捉 Kind: `<IO, Async@lin>` のように、row の各要素に「捕まえてよい Kind」を推論で持たせ、`never` / `once` の持ち越し規則をより柔軟にする。マルチコア対応で挙がった「`Heap` を含まない row」の制約も、同じ種類の拡張として扱う ([マルチコア対応の設計](multicore.md))
- ユーザーによる Kind の記述: 内部の Kind 変数を表面の構文に開放する。関数型の線形性 `m` も含む
- アドホック多相: 型クラスやトレイト。入れたときに見直す論点が、構文の側にいくつかある
  - 補間の穴の型: `Show` 相当で、任意の型を穴に入れられるようにする (今は `String` に限る)
  - 接頭辞付きリテラルの一般化: `re"..."` のように、ユーザーが接頭辞付きのリテラルを定義できるようにする。穴の型付けにアドホック多相が要る
- 借用: Rust / Austral 方式。意味論の大きな追加になる

## 言語機能と構文

- 可変参照 (方針は決定済み): 値 `Ref h a` と組み込みのエフェクト `Heap h` を持ち、`IO` と分離する。`run_heap` は rank-2 の組み込みとして特別扱いする。`Ref` には `Unr` の値だけを入れ、multi-shot で再開したときの状態は共有する ([マルチコア対応の設計](multicore.md) の「可変状態」)
- 局所的な可変変数の糖衣構文: Koka の `var` のように、関数の中に閉じた可変変数を `Heap` を外に見せずに書けるようにする
- 線形値の受け渡しの糖衣: `read_all &input` を `let (input, r) = read_all input` に脱糖する、Swift の `inout` 風の構文。API の返り値の形を縛ることと、巻き上げの規則が課題である。標準ライブラリを書いてみて、受け渡しが辛ければ再検討する
- フィールドの変換の糖衣: `{ p with age = _ + 1 }` のような、関数でフィールドを書き換える構文。`Lin` なレコードでも、分解せずに書けるようにする
- サンクの糖衣: `fn () ->` が多い場合の短縮形。現時点では `use` とセクションで十分と判断した
- 抽象型: コンストラクタを公開しない `pub data`
- 再エクスポート: `pub import`
- 優先順位グループ: 整数の優先順位で、ライブラリ同士の演算子の衝突が問題になった場合の代替案 (Swift 方式)
- モジュールシステムと標準ライブラリの範囲: モジュールの構文と名前解決は [モジュールと名前解決](../spec/modules.md) で定めた (実装は構文の段階 S2)。標準ライブラリの API は別の spec で扱う ([標準ライブラリへの申し送り](stdlib.md))

## 処理系

- インクリメンタル化: 各段階をクエリ (salsa など) に載せ替える。各段階を純粋な関数にしているのはこのため ([コンパイラの構成](../implementation/architecture.md))
- LSP: 診断、hover (型と row の表示)、補完、code action。診断の構造体は、LSP の診断と code action に変換できる形にしてある ([診断](../spec/diagnostics.md))
- ネイティブ化: 同じ Core IR から LLVM へ変換する。`never` / `once` はスタック切り替え、`multi` は選択的な CPS 変換かスタックのコピーで実装する。evidence passing を検討する
- レコードのネイティブな表現: フィールドの位置が多相になる箇所に、オフセットを証拠として渡す (evidence passing) か、単相化するか
- Perceus の最適化: reuse analysis (FBIP)、借用パラメータ
- すぐに再開する handler の最適化: 節が `resume k v` を末尾で1回だけ呼ぶ場合に、継続を取り出さない直接の呼び出しにする ([マルチコア対応の設計](multicore.md))

## マルチコア対応

詳細は [マルチコア対応の設計](multicore.md) にある。主な項目は次のとおり。

- 共有の印方式の RC
- データ並列に限った `par` の段階的な拡張 (a1 → a2-wait → a2-cancel)
- 並行処理の `spawn` と `run_scheduler`
- 継続の移動
- マルチコアのインタプリタ

同じ文書の「未決の論点と将来の拡張」には、さらに先の論点がある。並列タスクからすぐに再開する操作を外に出す案 (a4)、逐次実行と同じ意味の `par_ordered` (a3)、`Lin` な配列、並行処理用の共有の可変状態、`IO` が大域的な領域を含む折衷案、private deque、ネイティブのアロケータ、マルチコア版のヒープの実装方式である。
