# ロードマップ

位置づけ: 将来の設計。

今後の実装を、言語の項目と処理系の項目に分けてまとめる。今の言語の範囲は [実装の現在地](../implementation/status.md) の「今の言語の範囲」にあり、確定した設計判断は [概要](../overview.md) にある。

## 進め方

- 各段は、設計、計画、実装、閉じる作業の順に進める。設計は、この文書のその段の項目を出発点にし、設計と計画は `docs/plans/YYYY-MM-DD-<段>.md` (付録を分けるときは同じ名前のディレクトリ) に書く。承認した版を段の最初のコミットで main に入れ、途中で変えたときもコミットする
- 「決めたこと」は方針で、細部はその段の設計で決める。「論点」は、その段の設計で決める
- `spec/` は段の中で書く。規則を実装するコミットと同じコミットで `spec/` の節を書き、コードのコメントはその節を引く。設計の文書は引かない。段を途中でやめるときは、コードと `spec/` を一緒に戻す
- テストの変更は、段の設計に、[テスト戦略](../implementation/testing.md) の「テストの変更の運用」の種類 (成否の変更、期待値の変更、機械的な追随) で書く
- 段で後に回した項目は、この文書の「その後の項目」に書き、項目の下に「後に回した理由: …。」と「見直す条件: …。」の入れ子の箇条を置く。決めた日と決め手は書かず、閉じるコミットのメッセージに残す
- 段を閉じるときは、次の順に文書を直し、1つのコミット (`Close <段>`) にまとめる。順序は引用の向きで決めてある
  1. `spec/` を仕上げる。段の名前と「今は〜、後で〜」の予告が残っていないことを確かめる
  2. 計測する。前の表のコミットから `crates/eml_vm`、`crates/eml_rt`、`crates/eml_lir`、`crates/eml_core_ir`、`std/`、`bench/` のどれかが変わった段だけが対象である。まず `bench/scripts.sh` を流し、実時間が範囲を外れた行があれば `bench/scripts.sh` の大きさを変えて別のコミット (`Resize bench rows`) にする。次に `bench/run.sh`、`bench/rt.sh`、`bench/scripts.sh` をコードの最後のコミットの作業ツリーで流し、[計測の基準](../implementation/benchmarks.md) の「今の数値」の表を入れ替える。段が変えた規則を根拠にしている「所見」は測り直して更新するか消し、今後も判断の根拠になる計測は題名の見出しで足す。測れる環境がないときは、表の入れ替えだけを直後の別のコミット (`Measure <段>`) にする
  3. [実装の現在地](../implementation/status.md) の範囲と制限を直す
  4. [コンパイラの構成](../implementation/architecture.md) を、crate かパスの構成が変わったときに直す
  5. この文書からその段の節を消す。残した項目は「後に回した理由」と「見直す条件」を添えて「その後の項目」へ移し、「前提」に書いた段の名前を項目の名前に直す
  6. [概要](../overview.md) の確定した設計判断の表と、[文書の地図](../README.md) の「文書の地図」の「内容」の欄を、変わった所だけ直す
  7. `CLAUDE.md` を、規則か道しるべが変わったときだけ直す
  8. `docs/plans/` の設計と計画を消す。消す前に、`docs/` に残っていない決めがないことを確かめる
  9. コミットのメッセージに、文書で何をどこへ移したか、テストの変更の種類と理由、計測の目立つ差、大きさを変えた行、機種が変わったこと、後に回した項目の決めた日を書く。段の名前と日付はここに残る
- 段は、パイプラインの段階 (crate) とは別の呼び方である

## 言語の項目

### `Char`

前提: なし。

今は文字の型と文字のリテラルがないので、`tests/ui/run/scripts/csv2jsonl/main.em` の `rows` はバイトを `34` (`"`) や `44` (`,`) の数で比べ、JSON のエスケープ (`escape`) は16進の数字を `hex_digit` が `String.slice` で取り出す。バイトから文字列を作れないので、`grep` の `-i` は書けない。

#### 決めたこと

- `Char` の型、リテラル、Prelude の演算を入れる
- `Char` は Unicode のスカラー値である
- 順序の比較は、`Int`、`Float`、`String` と同じく `Ord` のクラスで解決する

### バイト列とハンドル

前提: なし。

`Byte` 型とビット演算、`Bytes` を入れる。`Lin` のハンドルと、バッファ付きの読み書きを入れる。

#### 決めたこと

- `Byte` (0〜255) を専用の型にする。算術は `Num` の instance で、演算子を `Int` と共有する。ビット演算のクラスと演算子と fixity を Prelude に足し、`Int` と `Byte` で共有する
- `Bytes` は `Unr` の値で、意味は不変である。更新は、`Array` と同じく、RC が 1 ならその場で書き換え、そうでなければ写す
- ハンドルは `Lin` にする。`Stdin` / `Stdout` / `Stderr` は別の型にする。バッファ付きの読み書きもハンドルにする。extern は、ハンドルに対する read/write の操作にとどめる

#### 論点

- `Byte` のリテラルの書き方 (リテラルは単相なので、`Byte` を書く形が要る)
- `Byte` の算術のオーバーフロー (実行時エラーか wrap か)
- `Bytes` の範囲外の添字の扱い (`Array` の決め方 (範囲外の添字は `Panic`) に揃えるか)
- 中断のときに書き込みのハンドルを flush するか
- `println` と `Stdout` のハンドルの関係。`Std.Stdin` の関数との関係
- マルチコアでのハンドルの扱い

### UTF-8 と標準ライブラリ

前提: `Char`、バイト列とハンドル。

UTF-8 の核の extern を入れ、標準ライブラリを広げる。`std/` には `List`、`String`、`Env`、`Stdin`、`Proc` などのモジュールがある ([標準ライブラリ](../spec/stdlib.md))。

#### 決めたこと

- `String` は常に妥当な UTF-8 である
- UTF-8 の extern は小さい核にとどめる。検証付きのデコード (`Bytes` から `String`)、エンコード、バイト長、バイト位置から `Char` と次の位置を読む操作、境界を検査する切り出しである
- 「行を流す」などのストリーム処理は、ユーザー定義のエフェクトとして、標準ライブラリのモジュールの中に書く
- 書記素クラスタと正規化は対象外にする
- `Fs`、`Path`、`Proc`、`Json` などのモジュールの API を別の spec で決める ([標準ライブラリへの申し送り](stdlib.md))
- std に `Map` (釣り合いを取った木) と安定な並べ替えを入れる。今は std に連想配列がないので、`tests/ui/run/scripts/logstat/main.em` は釣り合いを取った二分探索木 (`upsert`) と安定なマージソート (`sort_by`) を自分で持つ。std に連想配列がないと、釣り合いを取らない木でキーが昇順に増えて2乗の時間になる落とし穴を、スクリプトごとに踏む
- リストの関数 `take`、`split_at`、`nth`、`zip`、`index_of`、要素があるかを調べる関数、組のリストを引く関数を入れる。`String` の空白の判定を `pub` にする

#### 論点

- `Std.String` の核 (バイトの位置で読む `byte_length`、`byte_at`、`slice`、`find_from`) を、`Char` と `Bytes` の核にどう置き換えるか
- 位置の単位 (バイト位置を不透明な型にするか)
- 不正な UTF-8 の扱い (エラーか置換か)
- 大文字と小文字の変換など、Unicode の表が要る操作を extern にするか対象外にするか
- `Map` の API (名前、キーの制約 `Ord`、更新の関数の形) と置き場所
- 並べ替えの関数の形 (比較の関数を受けるか、`Ord` を使うか、両方置くか)
- 範囲外の添字で `Option` を返す版を `Array` と `MutArray` に足すか。今は範囲外の添字は `Panic` で、`Option` を返す版はない
- `Lin` の要素を持つ `Array` と `MutArray` の API。extern の関数の引数の型変数は `Unr` に固定しているので、今は `Lin` の要素の配列にどの関数も使えない

### コマンドリテラル

前提: UTF-8 と標準ライブラリ。

コマンドリテラルの意味 (HIR から先) と、標準ライブラリの `Cmd` と `Proc` を入れる。字句と CST (`COMMAND_LIT`) はあり、HIR が E0004 を出す ([診断](../spec/diagnostics.md) の「未対応の構文と E0004」)。`Proc.run` はすでにある。

#### 決めたこと

- コマンドリテラルはシェルを介さず、引数のリストを組む ([字句](../spec/lexical.md) の「コマンドリテラル」)

#### 論点

- `Cmd` と `Proc` の API ([標準ライブラリへの申し送り](stdlib.md) の `Cmd` の項目)

## その後の項目

段と言語の項目に含めない項目を、分野ごとにまとめる。方針まで決まっている項目と、論点を挙げただけの項目がある。詳しい設計がある項目は、その文書へのリンクを付けた。「前提」は、先に済ませておく項目である。前提を書いていない項目は、どの段の後でも着手できる。

### 型システム

- 使い切り必須の型: 捨てることを許さない線形型。ユーザーが Kind を書けるようにする段階で、Kind に「drop できるか」の次元を追加して扱う。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- Kind の宣言化: シグネチャに Kind の境界を書き、Kind 推論を減らす。宣言にするなら、持ち越しの条件付きの制約を書く形が要る。`map`、`fold`、`keep` を注釈なしで書ける今の性質を失わないことを条件にする。ユーザーが矢印の線形性と `data` の Kind を書く記法はすでにある
  - 後に回した理由: スクリプトの5本の書き心地に関わらなかった。
  - 見直す条件: 注釈なしの推論では Kind が決まらないシグネチャが要るプログラムが出たとき。
- row 要素ごとの捕捉 Kind: `<IO, Async@lin>` のように、row の各要素に「捕まえてよい Kind」を推論で持たせ、`never` / `once` の持ち越し規則をより柔軟にする。マルチコア対応で挙がった「`Heap` を含まない row」の制約も、同じ種類の拡張として扱う ([マルチコア対応の設計](multicore.md))
- 借用: Rust / Austral 方式。意味論の大きな追加になる
- 関数型の部分 Kind による包摂: `Unr` の関数を `Lin` の関数型の場所に渡せるようにする。今は関数型どうしの単一化で線形性 `m` を等しくする ([型と Kind](../spec/types.md) の「関数型」)。今は、トップレベルの関数、extern の関数、コンストラクタ、クラスのメソッド、REPL の `let` の値の参照だけを `once` の位置に置ける
- 多重度の多相: `data` のフィールドの矢印の線形性を型引数で変えられるようにする。シグネチャの矢印は今も線形性を推論するので、要るのは `data` だけである。今は、閉包の型そのものを型引数にすれば書ける (`data Task f = | Task f`。`Task` の Kind は `f` に従う)。実用のプログラムで要る例が出たら、記法と、`data` の型引数の種類に多重度を足す形を決める。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- `Unr` の宣言: `data T : Unr` と書き、型変数のフィールドを持つ型を `Unr` に保つ。型引数への Kind の制約にすると「Kind の宣言化」に踏み込む。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- row の引数の省略: `data` の row の引数をすべて省いたとき、`<>` とみなす (`Iter a` を `Iter <> a` と読む)。矢印の row を省くと `<>` になる規則と対になる。後で入れても、今のプログラムの意味は変わらない
  - 後に回した理由: 宣言を知らないと引数の個数が読めない。
  - 見直す条件: `data` の row の引数を `<>` と書く手間が目立つプログラムが出たとき。
- 操作の引数の Kind 変数: 操作の引数の型に現れる Kind 変数は `Unr` に固定している ([エフェクトと handler](../spec/effects.md) の「handler の意味」)。線形な値を多相な操作の引数で渡せるようにするかを見直す
- 証拠が大きくなる制約付きの多相再帰: 今は型検査で弾く (E2012。[Core IR](../spec/core-ir.md) の「一様な位置と制約付きの多相再帰」)。必要な例が出たら、その場合だけ辞書渡しで許すかを見直す
- `Lin` の型を受けるクラス: 今のクラスはすべて `Unr` のクラスで、制約 `C a` は `a ≤ Unr` を意味する ([型と Kind](../spec/types.md) の「`Unr` のクラス」)。`Read` / `Write` のようにハンドルを受け取って返すクラスは、借用がなくても役に立つ。広げるときは、クラスの性質として `Lin` を受けるクラスを区別し、`Lin` を受けるクラスの instance の本体は頭の型変数の Kind に制約を足せない、という規則を置く。今のクラスの意味は変えない。今の Kind の記法 ([型と Kind](../spec/types.md) の「`Lin` の宣言」) の上に作る
- orphan 規則をパッケージ単位に広げるか: 今の orphan 規則はモジュール単位である ([モジュールと名前解決](../spec/modules.md) の「instance の一貫性」)。パッケージの仕組みがまだないので、パッケージを入れるときに決める

### 言語機能と構文

- 多相なローカル関数: ローカル関数は今は単相である ([型と Kind](../spec/types.md) の「ローカル関数の推論」)。シグネチャの書き方 (ブロックの中にシグネチャの行を書くか、`let` に型を明示するか) と、注釈のない汎化をするかを決める
  - 後に回した理由: スクリプトの5本で要る場面がなかった。
  - 見直す条件: 1つのローカル関数を違う型で使うプログラムが出たとき。
- 固定の優先順位の表: fixity の宣言をやめ、先頭の文字で決まる固定の優先順位の表にすること。整数の優先順位で、ライブラリ同士の演算子の衝突が問題になった場合の代替案 (Swift 方式の優先順位グループ) も、ここで一緒に判断する
- 字句的な負号: `f -1` を `f (-1)` と読む。GHC の LexicalNegation と同じである
- ブロック引数: 末尾の `fn`、`match`、`if`、`handle` を括弧なしで渡す。`fn () ->` が多い場合のサンクの糖衣も一緒に判断する。今は `use` とセクションで足りると判断している。今は `use` を文の位置にしか書けないので、式の途中では `Some (use …)` のように書けない。`tests/ui/run/scripts/grep/main.em` の `search` は `use try_io` を `let found =` のブロックに入れている
- 省略した row の暗黙の row 変数 ε: 今は省略した row を `<>` と読む ([型と Kind](../spec/types.md) の「関数型」)。高階関数で row 変数を書く量が負担になるなら、Frank の周囲の ability のように、1つのシグネチャの中で省略した row をすべて同じ暗黙の row 変数 ε とする規則に広げる。`map : (a -> b) -> List a -> List b` が `(a -> <ε> b) -> List a -> <ε> List b` になる。スクリプトの5本では、row 変数を書いたのは handler の関数と `use` で残りを受ける関数のシグネチャだけで、どれも1つだった
  - 互換の条件: 既存のシグネチャの型が、広げた規則の型の特別な場合 (ε := `<>`) になる形でだけ広げる。そのため、ε を入れるのは row を1つも書いていないシグネチャに限る。row を1つでも書いたシグネチャは、今と同じく省略を `<>` と読む。たとえば `twice : (Unit -> Unit) -> <IO> Unit` の引数に ε を入れると、閉じた `<IO>` の本体でコールバックを呼べなくなり、今は通るプログラムが通らなくなる
  - ε を入れるのはトップレベルのシグネチャだけで、`data` のフィールドの型には入れない。ローカルの型の明示とラムダの引数の型で省略した row は、推論用の row 変数に変えてもよい (型がより一般になるだけなので互換である)
- 同じエフェクトの2つ目のラベルを名指すこと: `<Yield a, Yield b | e>` の中で `yield (x : b)` と書くと、操作はいつも1つ目の `Yield a` に向かうので型の誤りになる。2つ目に届けるには、`mask` を書く構文 (Koka の `mask<yield>{…}`) が要る。型を変換する handler では、節が外側の row で動くので名指しは要らない (位置つきの `mask`。[エフェクトと handler](../spec/effects.md) の「handler の意味」)。実用のプログラムで要る例が出たら構文を決める
- 線形値の受け渡しの糖衣: `Fs.read_all &input` を `let (input, r) = Fs.read_all input` に脱糖する、Swift の `inout` 風の構文。API の返り値の形を縛ることと、巻き上げの規則が課題である。スクリプトの5本では `File` が解析や中断の区間をまたぐ形が出なかった。`tests/ui/run/std/iter_file/` は `File` を持つ生産者を `Iter` で引き、`match Fs.read_line file with | (file, Some line) -> …` と組のパターンで `File` を受け直す形で書ける。糖衣を入れるかはまだ決めていない
- トップレベルの値のコンパイル時の計算: 今はトップレベルの値の本体の row を `<>` に限るので、`Panic` を起こしうる計算 (`Int` と `Float` の算術を含む) を書けない ([エフェクトと handler](../spec/effects.md) の「組み込みの `Panic`」)。定数畳み込みとコンパイル時の計算を入れ、コンパイル時に `Panic` を起こさずに値が決まる本体を許す。コンパイル時に `Panic` を起こす本体は、コンパイルの誤りにする。下の「トップレベルの値を一度だけ評価すること」と、「処理系」の「Core IR の上の最適化パス」の純粋な extern の定数畳み込みと一緒に設計する。
- トップレベルの値を一度だけ評価すること: 今は参照するたびに計算する ([Core IR](../spec/core-ir.md))。一度だけ評価するのは、単相で `Unr` の値に限る。起動時に評価するか初めて使うときに評価するかと、実行時エラーの報告の仕方も決める。REPL で入力をまたいで残す束縛の評価と、意味を揃えるかも一緒に決める。評価した値を凍結すると塊が増える (下の「REPL」)
- 可変参照 (方針は決定済み): 値 `Ref h a` と組み込みのエフェクト `Heap h` を持ち、`IO` と分離する。`run_heap` は rank-2 の組み込みとして特別扱いする。`Ref` には `Unr` の値だけを入れ、multi-shot で再開したときの状態は共有する ([マルチコア対応の設計](multicore.md) の「可変状態」)。入れ子の `run_heap` の中から外側の `Ref` を使うには、同じエフェクトのインスタンスを区別する必要がある。名前付きの handler が要るかどうかを、入れるときに決める
- フィールドの変換の糖衣: `{ p | age = _ + 1 }` のような、関数でフィールドを書き換える構文。`Lin` なレコードでも、分解せずに書けるようにする。今の更新は上書きされる古い値を捨てるので、`Lin` なフィールドは分解して組み直すしかない ([直積型とレコード](../spec/records.md) の「線形性の規則」)
- 型の別名: `type Name = T`。構文は予約してあり、今は `type` の宣言を HIR が E0004 にする ([宣言](../spec/declarations.md) の「`data` と `type`」)。別名を展開する位置 (HIR か型検査か)、型引数を持つ別名、診断での表示 (別名で書くか展開して書くか) を決める
- 抽象型: コンストラクタを公開しない `pub data`。名前付きのフィールドも、コンストラクタと一緒に隠す規則を決める。今は射影と更新がフィールドの見える範囲を検査しない ([モジュールと名前解決](../spec/modules.md) の「名前空間」)
- 再エクスポート: `pub import`
- 修飾した演算子の構文 (`Csv.(</>)`)
- 接頭辞付きリテラルの一般化: `re"..."` のように、ユーザーが接頭辞付きのリテラルを定義できるようにする。穴の型付けにアドホック多相が要る
- or パターン、ガード、as パターン: パターンを広げる。網羅性の検査 ([網羅性](../spec/exhaustiveness.md)) と決定木の変換を一緒に広げる
  - ガードには所有の制約がある。今の Perceus が `Lin` のフィールドを `dup` しないのは、決定木の途中で、後の行が持ち主を使うフィールドを消費しないことに依る ([LIR](../spec/lir.md) の「値の表現」)。ガードを入れると、ガードが呼び出しの引数として `Lin` のフィールドを渡し、後の行が持ち主を使う形ができる。フィールドを消費する時点で持ち主が必要なので、Perceus はそのフィールドを `dup` し ([LIR](../spec/lir.md) の「所有を取る時点」)、`File` の `dup` をヒープの検査が止める。ガードを入れるときは、ガードが `Lin` のフィールドを消費しないという型の規則か、別の変換が要る
- `var` の残る制限
  - 制限: 次の5つがある
    - 配列の変数の長さを、範囲の途中で読む書き方がない。今は長さを変数とは別に持つ
    - 配列の変数を、範囲の途中でトップレベルの関数に貸す書き方がない。今は範囲の中の局所関数で書くか、変数にする前に線形に受け渡す。`bench/nbody.em` も、1 回進める計算をトップレベルの関数に分けられなかった
    - 取り出して変えて戻す `x <- f x` は、配列の変数では E3008 になる
    - 範囲の外で定義した局所関数に、変数を使う閉包を渡すと、局所関数の型に変数のエフェクトが現れるので E2019 になる
    - 配列の変数の範囲の E3006 は、`Lin` の状態を持つ handle と同じく、範囲を囲む本体の row で決める。そのため、row に `multi` のラベルを持つ関数では、範囲の中でそのラベルを何も `perform` しなくても、どの配列の変数も断る。範囲が実際に起こす row で持ち越しを確かめる形に細かくする余地がある ([線形性](../spec/linearity.md) の「配列の変数」)
  - 後に回した理由: 今のプログラムと `bench/` に要る場面がなかった。
  - 見直す条件: 要るプログラムが出たとき。
- 仮置きの式: どの型にもなる仮置きの式 (typed hole)。入れるときに、網羅されていない `match` と等式の fix (E4001 の枝の追加、E4002 の等式の追加の提案) を一緒に入れる ([診断の出し方](../implementation/diagnostics.md) の「網羅性の診断」)

- キーワードの `from` を変数名に使ったときの E0011 (`expected =`) に、`from` がキーワードであることを示す
- std の関数の中で起きた extern の誤りの位置を、std を呼んだ利用者のコードの位置で示すことは、下の「処理系」の「実行時エラーの backtrace」に置く

### 処理系

- Kind 推論の検証: `eml_types/src/kind/` の束の上の計算 (最小解、多相化で残す制約、持ち越し、含意、instance での値) を vstd だけに依存する葉の crate に移し、Verus で証明する。型検査と evidence passing の変換は Verus で扱わない。LIR の verifier と VM の組で `eml_rt` の前提を証明するかを検討する。詳細は [Verus で検証する範囲](verification.md) にある
- インクリメンタル化: 各段階をクエリ (salsa など) に載せ替える。各段階を純粋な関数にしているのはこのため ([コンパイラの構成](../implementation/architecture.md))
- LSP: 診断、hover (型と row の表示)、補完、code action。診断の構造体は、LSP の診断と code action に変換できる形にしてある ([診断](../spec/diagnostics.md))。前提: インクリメンタル化
- ネイティブ化: LIR から Cranelift でネイティブのコードを出す。LIR のブロックの列とブロック引数は、Cranelift のブロック引数に1対1で写る。多相な位置の `Int` は語の表現 ([オブジェクトモデル](../spec/object-model.md) の「語」)、`Float` は `float` の位置では生の 64 ビット、`tobj` では箱という表現を前提にする。VM とネイティブは `eml_rt` の値とヒープを共有し、関数表 `FnEntry` を接続点にして混ぜて動かせる。たとえば、標準ライブラリだけをネイティブにし、ユーザーのコードをバイトコードで動かす。VM からネイティブの関数を呼ぶ入口は、下の「入口とシグネチャ」にある。`eml_extern` の表は、`eml_rt` の語の ABI の関数になる。ネイティブの `par` がバイトコードの閉包を worker で呼ぶには、VM の並列化 (下の「マルチコア対応」) が要る。前提: 借用パラメータ
  - 完了の条件: 実用的なプログラム (`tests/ui/run/scripts/` のスクリプトのような文字列の処理と、数値計算の計測) で、Python 3.14 の1.5倍以下の実時間になること。今の比は [計測の基準](../implementation/benchmarks.md) の「今の数値」にある。VM では、素のループは CPython より速いが、Python が C で書かれた組み込みの関数に任せる処理には届かない ([計測の基準](../implementation/benchmarks.md) の「1バイトずつ回すループ」)。extern は本当に必要なもの (OS や Host に触れるもの、文字列の表現に触れる核、eml で書くと計算量の桁が悪くなるもの) にとどめ、この条件はネイティブ化で満たす。ネイティブにしたときの見込みは [計測の基準](../implementation/benchmarks.md) の「ネイティブ化の見込み」にある。確保の多い `logstat` は測っていないので、借用パラメータと reuse (下の「Perceus の最適化」) の効果を見て詰める
  - Cranelift の mid-end は制御フローをほとんど変えないので、jump threading と既知のコンストラクタの畳み込みは Core IR の融合が行い ([Core IR](../spec/core-ir.md) の「既知のコンストラクタ」)、Cranelift の mid-end に頼らない
  - VM は、中断 (`never` の操作、`try_io` が捕まえる IO の失敗、`exit`) を、コード生成が作る呼び出しの位置ごとの表でタスクのスタックを巻き戻して行い、実行時エラー (オーバーフロー、ゼロ除算) は巻き戻さずに評価全体を止める ([VM](../spec/vm.md) の「巻き戻し」と「中断と実行時エラーの分担」)。ネイティブのコードで中断を巻き戻すには、同じ表を Cranelift のコードの呼び出しの位置ごとに持たせる
  - ネイティブのコードの中で起きた実行時エラーを、評価全体の中断にする方法は未設計である。旗を立てて戻る方式は効果を持たない関数にも確認を足し、巻き戻しは Cranelift のコードに展開情報を要する。中断と同じ呼び出しの位置ごとの表で巻き戻す形が候補になる
  - extern の C ABI の入口 (`extern "C"`) は、この項目で足す。今の extern は、引数がどれも 64 ビットの語で数が決まっているので、そのまま移せる。Host と読み手は panic しうるので、入口で `catch_unwind` する。`extern "C"` を越える panic はプロセスを落とすためである。`Fault` を `Ctx` の欄に置いて状態の語を返す形にするかは、`Ctx` の配置 (yield の状態は `#[repr(C)]`) の決まりと一緒に決める ([オブジェクトモデル](../spec/object-model.md) の「extern」)
  - 利用者のモジュールに許す `extern "C"` は最小の形にする。引数と結果は、スカラー (`Int` は `int64_t`、`Float` は `double`、`Bool` と enum は `int64_t`、`Unit`)、借りて (ポインタ, 長さ) の組で渡す `String` と `Bytes`、不透明な C のハンドルに限る。C の構造体 (値でもポインタでも)、出力の引数、コールバック、eml の物体の配列は扱わない。これを超えるものは、今と同じく Rust で書いた extern の行にする。今の語の ABI (引数の数が決まった 64 ビットの語、`borrowed`、長さの語を持つ物体、ファイナライザを持つ `Foreign`) に、この形に要るものはそろっている。C の構造体やコールバックを要する std の外のライブラリを使うときに見直す
  - C のハンドルは `Foreign` の包み `CHandle { ptr: *mut c_void, dtor: Option<unsafe extern "C" fn(*mut c_void)> }` にし、`unsafe impl Send` を付ける。ほかの `Foreign` と同じく回収できない。中身のポインタは `eml_rt` のアクセサで取り、C の側で定数のオフセットを使わない。利用者の `extern "C"` を拒む E1033 は、これを足すまで残す
  - データの配置は eml 独自のものを保ち、C との間は境目で変換する。`repr(C)` の data、1語より小さいフィールド、宣言の順のフィールド、C の形の構造体の型は作らない。C との受け渡しは、std の extern が今使う境目 (Repr で型を決めた 64 ビットの語のスカラー、文字列、`Foreign`) と、長さの語の後に連続した中身を置く物体 (今は `String`) で行う。Cranelift にとって今の配置は障害にならない。オフセットは配置ごとに決まった定数で、生の葉はそのまま `i64` か `f64` になる。C と食い違うヘッダ、参照を前に寄せるフィールドの順、1語のフィールド、一様な位置のタグ付きの `Int` と箱の `Float`、構造体にメモリの形がないことは、どれも配置を型の具体化から独立させるためのものである。配列の物体の形は要素の型によらない。要素の型で形を変える `Array a` は、一様なコードのすべての読み書きに種類の確かめが要るので採らない。一様な位置の箱がネイティブでホットパスに目立つときに見直す
  - 配列を、要素の数を常に長さの語に持つ形 (`scan = 255`) にする案は、ネイティブのコードが配列の要素を直接読むコミットで入れる。そのとき `crates/eml_rt/src/heap/ctx/arrays.rs` の Verus の仕様が変わる
  - 入口とシグネチャ: 関数の ABI は型と役割で決まり、`apply` は `FnEntry` のシグネチャと比べて実行時に変換する ([VM](../spec/vm.md) の「シグネチャ」)。ネイティブの `apply` もシグネチャの番号の比べと変換を持つ。捕まえた値の数と並べ方は実行時に決まるので、ネイティブのコードはバックエンドが作る入口を使う。関数と捕まえた値の数の組ごとの入口 (クロージャの中身と残りの引数を型どおりに受ける) と、シグネチャごとの入口 (VM との行き来と、変換の遅い道のための、語の並びを受ける入口) である。VM のスロットは生の語を持つので、語の並びの入口は箱を要らない。VM の `RetN` が戻り先の直前の命令を読むのは VM の中だけの約束なので、VM とネイティブのコードを混ぜるときは、境目の直接の呼び出しをシグネチャごとの入口で扱う
  - 開いた後の LIR は構造体を葉の変数の並びとして持ち ([LIR](../spec/lir.md) の「開く」)、葉はそのまま Cranelift の値になる。葉はどれも 8 バイトで、`float` の葉は浮動小数のレジスタに、ほかは整数のレジスタに載る。複数の値の戻りは eml の中の規約で、extern や C の境目を越えない。eml の中の呼び出しは、`return_call` が求める Cranelift の `tail` の呼び出しの規約を使う。結果がレジスタに収まらなければ、バックエンドが呼ぶ側の用意した領域で返す。`tail` の規約でこの形の `return_call` が使えることを確かめる
  - 結果の変換が要る末尾呼び出しの扱いは、未決の危険として残す。Cranelift の `return_call` は今のフレームしか置き換えないので、VM の変換のフレームの合成 ([VM](../spec/vm.md) の「変換のフレーム」) をそのまま写すには、決まった形の包みを手で書いた命令列で作る必要がある。代わりに、直接の呼び出しの相手を結果の変換の種類ごとの版 (`f[ret=int]` と `f[ret=tobj]`) にして、静的な変換をフレームなしで済ませ、実行時の合成を `apply` の道だけに残す形もある。変換の遅い道の末尾呼び出しの保証には、`Ctx` に置く作業用の領域 (VM の `scratch` に当たる) と、シグネチャごとの末尾の入口が要る。Rust で書いた実行時の関数からは、保証のある末尾呼び出しができないためである
  - ネイティブのコードを使い回すときの鍵は、名前だけでも、名前と開いた後のシグネチャでも足りない。関数のコードは中で開く形と配置、呼ぶ関数のシグネチャにも依存するためである。開いた後の LIR と、それが指す形、配置、呼ぶ関数のシグネチャの中身のハッシュを鍵にする
  - 定数の静的なデータは、凍結した領域と同じ約束 (rc 0、書き込まない、検査ビルドでは前置きを持つ) に乗る ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」)。検査モードの範囲の確かめのようにページの頭を読む道は、起動時に `freeze` で定数を作る形を既定にする。静的なデータに容量を持たせる形は、起動時の `freeze` が測定で重いときの代案にする
- スカラーの要素を生で持つ配列: 配列の要素は一様な位置なので、`Array Float` と `MutArray Float` の要素は書くたびに `Float` の箱に入る。spectral-norm では、確保のほとんどがこの箱である ([計測の基準](../implementation/benchmarks.md) の「配列の `Float` の要素の箱」)。構造体の表現もこの箱を消さない。要素の型から配列の物体の形を決め、`Float` や `Int` を生の語で並べる形を考える
  - 後に回した理由: 数値の bench はすでに Python の 0.4〜0.6 倍で、1.5 倍の条件に入っている ([計測の基準](../implementation/benchmarks.md) の「今の数値」)。
  - 見直す条件: ネイティブで測った `bench/` の数値のプログラムが Python の 1.5 倍を超え、その `RunStats` の `boxes` が `allocations` の半分を超えたとき (今の spectral-norm は 4043 のうち 4001)。または FFI で `double*` が要るとき。
  - 設計の要点: `Array a` とは別の型にし、長さの語と連続した中身を持つ物体の仲間 (`String`、`Bytes`) にする。`Bytes` を作るときに要素の数を長さの語に持つ形にしておくと、平らな `Float` の配列はそれを 8 バイトの要素にしたものになる。
- 構造体のフィールドを親の物体に並べること: 構造体の表現は、配置で構造体の型を宣言したフィールド (`data Shape = | Ball Vec3 Float | Empty` の `Vec3`) を `tobj` にし、構造体を箱に入れて置く ([Core IR](../spec/core-ir.md) の「translate の配置」)。構造体の葉を親の物体のフィールドに直に並べる形を考える。配置を具体化した型ごとに分けることになるので、一様な位置を通るコードと配置が食い違わない形を一緒に決める。配列の要素の構造体も箱に入る (nbody では、配列に書く `Vec3` の箱が1回進めるごとに 25 残る。[計測の基準](../implementation/benchmarks.md) の「配列に書く構造体の箱」)。上の「スカラーの要素を生で持つ配列」と一緒に考える
  - 後に回した理由: 構造体の型のフィールドを持つコンストラクタは `bench/` と `std/` に1つもなく、UI テストの6つだけにある。親が構造体なら、入れ子の構造体はもう葉に並んでいる。nbody の箱は配列の要素で、フィールドへの埋め込みでは減らない。
  - 見直す条件: `bench/` か `tests/ui/run/scripts/` のプログラムで、構造体でないコンストラクタの、構造体の型のフィールドの箱が `allocations` の 10% を超えたとき。
  - 設計の要点: 配置のフィールドの Repr を、そのフィールドの型の scheme が構造体の型で、配置自身の型変数を含まないときに `struct(S)` にする。`Shape` は `struct(S)` のフィールドを深さ優先で葉に展開してから、今の規則 (参照を前、生を後ろ、`unit` の葉は0語) で並べる。flatten の前は、1つのフィールドを1つの構造体の変数で運び、flatten が展開する。配置の表は REPL の追記のために中身で引く。組の配置は型変数のフィールドなので埋め込まない。
- Core IR の上の最適化パス: 引数が定数の関数の特殊化、純粋な extern の定数畳み込み。EP より前の Core IR に置き、関数単位の作業リストで動かす。枝の部分木を置き換えると、長い `else if` の連鎖で2乗の時間がかかるためである。Repr が同じ instance (`List Int` と `List String` の instance など、同じ形のコードになるもの) をまとめるのも、このパスに置く ([Core IR](../spec/core-ir.md) の「変換の規則」)。translate と融合が行わない書き換えも、このパスで扱う。`jump` だけで終わる合流のブロックで、入る辺が2本以上あるものへの転送、枝の中でタグの分かった scrutinee をそのタグに置き換えること、引数が2つ以上で返すだけのブロックのたたみ込みである
  - 再帰する生産者の継続についての特殊化: 融合は、`Iter.filter` が要素を飛ばすループのような再帰する関数の結果を見通せない。再帰する関数は展開しないので、ループが作って返す `Some ((x, Iter k))` が、残した要素ごとの確保として残る。これをなくすには、呼び出しの後の継続を関数に切り出し、再帰する呼び出し先をその継続について複製する。複製の `return` は継続の呼び出しになり、自分を末尾で呼ぶ所は同じ継続を持ったまま呼ぶ。こうすると、消費者と生産者が互いを末尾で呼ぶ確保のないループになる。末尾でない再帰の生産者 (木の走査など。[実装の現在地](../implementation/status.md) の「最適化が扱わない形」) と一緒に考える
    - 後に回した理由: 融合だけでは扱えず、呼び出しの後の継続を切り出して複製する新しい変換が要る。
    - 見直す条件: `Async` を作るとき。末尾でない再帰の生産者には、フレームごとに継続を作って渡す CPS の拡張が要るので、そのときに測って決める。
- evidence passing の最適化 ([Core IR](../spec/core-ir.md) の「evidence passing」)。どれも EP と実行時の中に閉じ、型検査と translate は変わらない
  - evidence を探す場所ごとのキャッシュと、閉じた row の静的な添字。今は `ev_lookup` が `evv` を先頭から探し、費用は今有効な handler の数に比例する。`evv` は書き換えないので、場所ごとのキャッシュを足せる。静的な添字は Koka の open の包みを要し、包みが部分ベクタを確保して末尾呼び出しを失うので、目立ったときに採るかを決める
  - yield しうる外のエフェクトを呼ぶすぐに再開する節を、その場で実行する形 (論文の under)。yield しない外のエフェクト (`IO` と `never` の操作) を呼ぶ節は、節の実行中だけ `evv` を外側に替える under の形でその場で動く ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。yield しうるエフェクトを呼ぶ節には、yield したら `evv` を替え直す包みと、再開で作り直した evidence を探し直す仕組みが要る。`Yield a` を `Yield b` に変える handler の `yield` の節は、外側の handler の節がその場で動く場合でも1要素ごとに yield する。節の本体の `yield` が外側の操作を起こすためである ([計測の基準](../implementation/benchmarks.md) の「`Yield` を変える handler の yield」)。中断は継続を組み立てずに巻き戻すので、中断のための最適化は要らない
  - `mask` 付きの呼び出しのたびに `evv_mask` が `evv` の節点を写して確保しないようにすること
  - 末尾の位置の `mask` 付きの呼び出しで、x を返すだけの `f$kN` を作らないこと
- Perceus の最適化: reuse は、関数の中で閉じた形がある ([LIR](../spec/lir.md) の「reuse」)。残るのは、関数をまたぐ reuse、合流をまたぐ token、借用パラメータである。どれも LIR の上のパスで、消費しない `switch` と `release` の上に、IR を作り直さずに足す。token を継続に入れない決まり ([LIR](../spec/lir.md) の「token の流れ」) は、足しても守る
  - 関数をまたぐ reuse: token を呼び出しの引数や戻り値で渡すことである。Okasaki の書き方の赤黒木 (`balance c l k r`) は、節を作るのが呼び出し先の `balance` なので、これが要る。今は token をフレームの中に限る (frame-limited reuse) ので、`ins` の token は `balance` への末尾呼び出しの前で消える
    - 後に回した理由: token を関数の外に出さない決まりを保つため。呼び出しの引数、閉包の捕獲、`return` に token を渡さなければ、継続のクロージャに token が入らない ([LIR](../spec/lir.md) の「token の流れ」)。
    - 見直す条件: 呼び出し先で節を作る形 (赤黒木の `balance` など) の確保が計測で目立ったとき。
  - 合流をまたぐ token: token を `jump` の実引数で合流するブロックへ渡すことである
    - 後に回した理由: 道によって空の token を作る定数と、ブロックの引数の検査が要る。
    - 見直す条件: 分岐が合流した後で節を作る形の確保が計測で目立ったとき。
  - 借用パラメータ: 1つの呼び出しでは、所有の引数を消費した後で借用の引数を確かめる。借用の推論では、同じ配置の `con` を作る行き先を持つ `switch` の scrutinee を所有にする。借用にすると、その値の箱が reuse の元にならないためである。継続のクロージャが捕まえる値に借用の部分を含めない。借用のブロック引数は持ち主 (同じブロックの引数か関数の入口) を宣言し、verifier は辺ごとに確かめる
    - 所有の都合で `TailCall` を `let r = <呼び出し>` と `return r` に降格するのも、借用パラメータと一緒に入れる。今は `tail` の前に実引数をすべて所有にし、保持している変数をすべて手放す ([LIR](../spec/lir.md) の「持ち主を手放す時点」) ので、借用パラメータを入れるまで降格は起きない。Perceus は、終端を文と新しい終端に置き換える編集をその場でできる形にしてある
    - 降格は、末尾の位置の呼び出しの輪の上の `tail` には当てない ([LIR](../spec/lir.md) の「末尾の位置の呼び出し」)。借用の推論は、輪の上の `tail` が渡す引数の仮引数を所有にして、降格を避ける (Lean の `ownParamsUsingArgs`)。降格してよいのは、輪の上にない末尾呼び出しだけである
    - extern の行は引数ごとの借用の列 (`FunctionRow::borrowed`) を持ち、配列を読む4行 (`Array.length`、`Array.get`、`MutArray.length`、`MutArray.read`) は配列を借りる ([LIR](../spec/lir.md) の「extern の借用」)。ほかの extern の引数も借用にする。最初の対象は `String.byte_at` である。今は文字列を消費するので、`wc` のループは1バイトごとに `dup` と `decref` を通る
    - 部分適用される関数と値として使う関数は借用を持てないので、所有の版の包みが要る (Ullrich と de Moura)。包みは名前で決まる関数 (`f$owned` など) にし、借用を入れるときに決める。`apply` の実行時の変換に借用を手放す仕事を入れると、変換のフレームが要り、末尾呼び出しの扱いが重くなるためである
    - 借りたまま読む射影も、借用パラメータで扱う。今の所有の形では、射影で得たフィールドを読むだけなら RC の命令は出ない。しかし `f p.name` の後に `p` を使う形は、呼び出しがフィールドを消費するので、今と同じく `dup` する ([Core IR](../spec/core-ir.md) の「変換の規則」)。これを減らすには、`f` の引数を借用にする必要がある
  - FP² (Lorenzen、Leijen、Swierstra) の `fip` のような、確保なしで動くことの静的な検査を置くかは、`multi` の継続が同じ値を共有しうる点との相性を確かめてから決める
- ループ化 (後ろ向きの辺): 自己末尾呼び出しを、関数の中のブロックへ戻る `jump` にする。トップレベルの関数を呼び出し元のブロックにする contification も同じ枠で扱う。今は辺がすべて番号の大きいブロックへ向かう ([LIR](../spec/lir.md) の「構造の規則」の R2)
  - 入れる時期: VM は、自己末尾呼び出しをバイトコードの出力で入口へのジャンプにする (`TailSelf`。[VM](../spec/vm.md) の「呼び出しと戻り」)ので、IR の R2 を緩めずに済む。R2 を緩めるのは、ループの中で変わらない値の移動や、ループの頭のブロックの引数を借用として扱う Perceus の拡張が要るときにする。借用パラメータかネイティブ化に着手するときに一緒に入れる
  - 残りの作業: R2 を、ループの頭への後ろ向きの辺だけを許す形に緩めることと、変換にループ化を足すこと。ブロックはすでに複数の引数を持てる
  - 生存解析、縮約、verifier は、辺がすべて前向きであることを使って1回のループで済ませている。ループ化では、ループの頭に印を付け、そこだけ不動点を計算する。支配木の計算も、後ろ向きの辺を含む形に広げる
- 実行時エラーの backtrace: extern の呼び出しの中で起きた実行時エラーは位置を持つ。呼び出しの連なり (backtrace) と、位置のない誤り (extern の外で起きたヒープの誤りや内部の誤り) の利用者向けの表示を、その後に足す。VM では、エラー位置の表の上に作る
  - std の関数の中で起きた extern の誤りの位置 (`<std>/Stdin.em:11:14` など。`Fs.read_line` の読みの誤りも `<std>/Fs.em:27:22`) を、std を呼んだ利用者のコードの位置で示す。実行時にフレームをたどって最も近い利用者のフレームを探す形なら、backtrace の一部になる。利用者のコードから std への末尾呼び出しでは利用者のフレームが残らないので、そのときに何を示すかも決める
- HIR の位置を source map に移す: HIR のノードが `TextRange` を直接持つ形をやめる。位置を別の表に分けると、編集で位置だけが変わったときに HIR を作り直さずに済む。この利点はインクリメンタル化 (salsa) に載せ替えるまで効かないので、そのときに移す
- フォーマッタ: CST がロスレスなので、その上に作る。前提: コマンドリテラル (本番の構文がそろってから)
- n 列の `match`: 今は決定木の列に、最初の行でコンストラクタ、タプル、リテラルのどれかのパターンを持ついちばん左の列を選ぶ ([Core IR](../spec/core-ir.md))。行列によっては部分木が大きくなりうる。今の選び方でも決定木は正しいので、部分木の大きさが問題になる例が出てから列の選び方を見直す
- doc comment: trivia の付け方を決める。doc comment を解釈するドキュメント生成と LSP の hover ([字句](../spec/lexical.md)) がまだないので、それを作るときに、使う側に合わせて決める。前提: LSP
- JIT (投機的): バイトコードから機械語を安く作る copy-and-patch や、トレース JIT。VM が安定し、起動時間が支配的になってから検討する。トレース JIT はバイトコードにスタックのスタックを持たせる別の道で、evidence passing とは前提が合わない。前提: ネイティブ化

### REPL

- `IO` 以外のエフェクトを既定の handler で許すか。許すなら、handler のない操作の yield を REPL が受け取る
- セッションの値への連結は、RC が 2 以上になるので、いつも写しになる
- 定義し直した `let` の古い根を手放す順序。今は古い根を `close` まで手放さない ([オブジェクトモデル](../spec/object-model.md) の「セッションの根」)
- 凍結のときに生きている物体を詰め直して、塊のページを減らすこと。塊は使う大きさの級ごとに少なくとも1ページを持つので、新しい定数を持つ入力ごとに塊を作ると、使うメモリは入力の数に比例して増える ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」)。トップレベルの値の1回だけの評価 (上の「言語機能と構文」) を入れると、塊はさらに増える。困ったときに入れる
- 入力ごとにセッション全体を検査し直すので、セッションが大きくなるほど入力ごとの時間が延びる。困ったら増分の lowering に移る。名前が同じ関数はいつも同じコードになる規則 ([Core IR](../spec/core-ir.md) の「変換の規則」) があるので、後から移れる

### マルチコア対応

詳細は [マルチコア対応の設計](multicore.md) にある。VM とネイティブのランタイムの両方を並列にする。VM はシングルスレッドで、後から並列にできる制約を守っている。VM の並列化は、ネイティブ化とは別の項目にする。主な項目は次のとおり。

- VM の並列化: 本物のスレッドで `par` を動かす。fork と join の印付けに使う共有の経路と、論理的な worker ID と所有者の検査はすでにある。`par` の a1 (下) を入れれば、そこで UI テストでも確かめる。この項目で足すのは、worker の起動と join、work stealing、別のスレッドからの解放に対応したアロケータと、本物のスレッドでしか現れない誤り (公開の順序、2つのスレッドからの同時の `decref`、deque) の検査である (同じ文書の「テスト」)。前提: `par` の a1
  - 別の worker が持つ物体 (共有、rc < 0) を、ヒープの操作が受け付けること。rc の並行の書き込みが要る。受け付けるブロックを付けた塊に広げた形 ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」) は、この拡張を妨げない
- `par` の a1 を協調的マルチタスクとして入れること: `par : (Unit -> <> a) -> (Unit -> <> b) -> (a, b)` を、並列 VM より前に、シングルスレッドの協調的マルチタスクとして入れる。a1 は `Row<Never>` の Kind の制約も型システムの変更も要らないので、組み込みの関数1つで入れられる。タスクが持つ呼び出しのスタックと、実行時エラーの後の回復はすでにある。スクリプトの書き心地ではなく、並列の安全性を並列 VM より前に確かめるかどうかで採るかを決める
  - 右の子を1つのタスクにし、左の子は親のタスクがそのまま実行する。右のタスクは新しい論理的な worker ID で動く
  - スケジューラは、呼び出しと戻りの安全点でタスクを切り替えてよい。方針は2つ持つ。「逐次」は切り替えず、左の子を終えてから右の子を実行する。`eml run` の既定と、ベンチの `RunStats` の固定に使う。「乱数種付き」は種で決めた間隔で切り替える。テストで使い、失敗したときは種を表示して再現できるようにする
  - 逐次の実行より多く確かめられるのは、所有者でない worker が共有の物体を解放する経路 (2つのタスクのどちらが最後に `decref` するかが種で変わる) と、タスクの中断、再開、join の待ちである
  - 実行時エラーは、右の子が先に失敗しても、左の子を最後まで実行してから報告する。右のタスクは止めたまま解放せず、評価全体を中断する。止めた右のタスクのスタックが持つ語を含め、残った物体は、中断の後の回復で古いヒープと一緒に捨てる。左の子が停止しなければ右のエラーは報告されず、逐次の実行と一致する
  - a1 の子は row が `<>` なので、どう切り替えても出力は変わらない。`run` と `run-fail` の UI テストを2つの方針で走らせ、出力が一致することを確かめる。検査用のフラグで印付けを1か所外すと、どれかの試験が必ず失敗することも確かめる (負の試験)
- データ並列に限った `par` の段階的な拡張 (a1 → a2-wait → a2-cancel)
- 並行処理の `spawn` と `run_scheduler`
- 継続の移動
- `poly` の物体の `lin` ビットの実行時の伝播 ([マルチコア対応の設計](multicore.md) の「未決の論点と将来の拡張」)
  - 後に回した理由: `MutArray` の要素を `Unr` に固定しているので要らない。
  - 見直す条件: `Lin` の要素を持つ配列を入れるとき (上の「UTF-8 と標準ライブラリ」の論点)。

同じ文書の「未決の論点と将来の拡張」には、さらに先の論点がある。並列タスクからすぐに再開する操作を外に出す案 (a4)、逐次実行と同じ意味の `par_ordered` (a3)、`Lin` の `MutArray` の分割と結合、並行処理用の共有の可変状態、`IO` が大域的な領域を含む折衷案、private deque、別のスレッドからの解放に対応したアロケータである。
