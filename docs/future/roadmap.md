# ロードマップ

位置づけ: 将来の設計。

今後の実装を、再設計のサブプロジェクト S8〜S13 と、その後の言語の項目、処理系の項目に分けてまとめる。今の言語の範囲は [実装の現在地](../implementation/status.md) の「今の言語の範囲」にある。再設計の決定のうち、確定した設計判断は [概要](../overview.md) にもある。S4〜S13 の順序は、VM とネイティブコード生成、REPL 向けのランタイムの2つの調査 (2026-10-09) を踏まえて決めた。S8〜S10 と S13 には、VM のマルチコア対応の議論 (2026-10-10) で決めたことを入れた。

## 進め方

- 各段は、spec、計画、実装の順に進める。spec は、この文書のその段の節を出発点にする
- 「決めたこと」は方針で、細部はその段の spec で決める。「論点」は、その段の spec で決める
- 段を終えたら、決まったことを `spec/` に移し (実装の構造に関わるものは `implementation/` に移し)、この文書からその段の節を削る。[実装の現在地](../implementation/status.md) と [コンパイラの構成](../implementation/architecture.md) は、段の途中では直さず、段の終わりに1回で直す
- テストの変更は、各段の spec に、[テスト戦略](../implementation/testing.md) の「テストの変更の運用」の種類 (成否の変更、期待値の変更、機械的な追随) で書く
- 段は、パイプラインの段階 (crate) とは別の呼び方である

## 段の列

優先するのは、VM と REPL、ランタイムの再編である。リスト (S6a)、文字列 (S6b)、レコード (S6c) は、データ構造のランタイム表現を実際のデータで詰めるために前に置いた。スクリプトの MVP は、その後に小さくして置く。

| 段 | 中身 | 前提 | 完了の条件 |
|---|---|---|---|
| S8 LIR | Core IR の下の LIR、box の挿入・縮約・Perceus を LIR に移す、`Lin` の move と Kind の印 | なし | パスを移す作業の前後で、EP を通したプログラムのダンプがバイト単位で一致する。所有の形を変える作業と Kind の印による差分は、期待値の変更として spec に範囲で挙げたものに限る。CEK が LIR を読んで全 UI テストを通す |
| S9 共通ランタイム `eml_rt` | 語の値、ヘッダ付きのオブジェクト、共有の印方式の RC、検査モード、不死の定数の凍結した領域、extern の語の ABI、`Ctx` | S8 | extern を今の実装と差分テストで比べる。核を Verus で検証し、信頼する部分を Miri で検査する |
| S10 VM と切り替え | LIR からのレジスタ型のバイトコード、関数表 `FnEntry` と `CodeBase`、`eml run` を VM に切り替え、CEK の削除 | S9 | VM が全 UI テストを `debug_heap` 付きで通す。CEK を消す前に、基準のプログラムで CEK との差を記録する |
| S11 REPL | セッション、再定義、回復、表示 | S10 | トランスクリプトの golden テストが通る。誤りや割り込みの後に、生きている物体が根だけになる |
| S12 スクリプトの MVP | `try_io` と `exit`、ローカルの再帰関数、extern の標準ライブラリ、`eml file.em args...` | S11 | wc、grep、ログの集計、CSV の変換、デプロイ手順の5本のスクリプトが UI テストとして動く |
| S13 実例による判断 | S12 のスクリプトを見て決める項目 | S12 | 各項目を採るか採らないか決め、採ったものを実装する |

S13 の後は、言語の項目を次の順に並べる。

| 順 | 項目 | 前提 |
|---|---|---|
| 1 | `Float`、`Char`、`Num` | なし |
| 2 | バイト列と `Array` | `Float`、`Char`、`Num` |
| 3 | UTF-8 と標準ライブラリ | バイト列と `Array` |
| 4 | コマンドリテラル | UTF-8 と標準ライブラリ |

処理系の項目 (Perceus の最適化、Core IR の上の最適化パス、ネイティブ化、マルチコアなど) は、言語の項目とは別の列にして、下の「その後の項目」に置く。

順序の理由は次のとおりである。

- 単相化 (S4b) を先に終えたのは、translate の出力の形を、EP、`eml_rt`、VM のすべてが受け取るためである。表面の構文を変えないので、段を小さく保てた
- CPS のラムダの位置の変換 (box の挿入を作ったときの試作で 200,125 回) は、単相化では消えず、既知の閉包への特殊化 (下の「処理系」の最適化パス) が要る。そのため S4b は減る量を約束せず、前後の回数を記録するにとどめた ([計測の基準](../implementation/benchmarks.md) の「S4b (単相化)」)
- 型クラス (S5) を S6a〜S6c より先に終えたのは、S6b の補間の穴と、リストやレコードの `deriving` が、`Show` などのクラスに従うためである。S6c の UI テストでは、レコードの `deriving (Eq, Ord, Show)` を使えた
- S6 は S6a リスト、S6b 文字列、S6c レコードの3段に分けた。S6a を先に終えたのは、括弧で書く構文の CST を、論点の少ないリストで先に作るためである。S6b の補間の UI テストでは、`Show (List a)` を穴に使えた
- S7 の evidence passing を S8 より先に終えたのは、Core IR から Core IR への変換なので、LIR がなくても CEK に流して変換の有無を比べられたためである
- S8 を S9 と S10 より前に置くのは、S10 で VM と一緒に作る関数表 `FnEntry` と `CodeBase` が、LIR の関数の集合を前提にするためである。関数の集合は、box の挿入が `f$boxed` を足して初めて決まる
- S9 を S6 の後に置いたのは、データの表現を、実際のリスト、文字列、レコードで測って決めるためである。S11 が要る仕組みのうち、ページを歩くブロックの列挙と RC の上限は S9 で、`CodeBase` は S10 で入れる。後から差し込むと作り直しになるためである。S11b の回復は、この列挙で、根から届く語がヒープの物体か凍結した領域の物体かを見分ける ([オブジェクトモデル](../spec/object-model.md) の「生存の列挙」)
- VM はシングルスレッドで出し (S10)、後から並列にできる制約を S9 と S10 で守る。VM の並列化は、ネイティブ化とは別の項目にする (下の「マルチコア対応」)。並列化を S10 で行わないのは、VM の最初の版で並列化と性能の両方を詰めることになるためである
- CEK の確保を除くことと、CEK の上に REPL を作ることは行わなかった。どちらも、S10 で消す CEK への投資になるためである。調査の測定では、`fib 22` の実行命令の約53%が確保と解放、引数と退避の `Vec` の組み立てだった。VM とランタイムは、この費用を持たない形で作る
- `Float`、`Char`、`Num` を型クラス (S5) の後に置いたのは、`Num` をクラスとして入れ、型ごとの多重定義を別に作らないためである
- バイト列と `Array` を `Num` の後に置くのは、`Byte` と `Int` で演算子を共有するためである

## S8 LIR

前提: なし。

S8 を、S8a から S8d の4つの作業に分けて順に進める。段の列では S8 の1行のままにする。初めは、完了の条件がダンプをバイト単位で一致させる部分と期待値を変える部分に分かれるので、S8a と S8b の2つに分けた。S8b の設計で、Kind の印には `eml_types` が解いた Kind を書き出す作業が要ると分かったので、それを S8c に分けた。S8c の設計で、Kind の書き出しだけで1つの作業になる大きさだと分かったので、印の作業を S8d にした。

| 作業 | 中身 | 状態 |
|---|---|---|
| S8a | LIR の型、テキスト形式、パーサ、verifier、Core IR から LIR への変換。box の挿入、縮約、Perceus を LIR に移し、CEK が LIR を読む | 終えた。決めたことは [Core IR](../spec/core-ir.md) と [LIR](../spec/lir.md) に移した。移す作業の前後で、EP、box の挿入、縮約、Perceus の後のダンプは、UI テストと `bench/` のすべてのプログラムでバイト単位で一致した |
| S8b | Perceus の所有の形 (フィールドを借りたまま使い、所有が要る所でだけ所有を取る形)、基本操作の引数の借用、`File` の実行時の検査 | 終えた。決めたことは [LIR](../spec/lir.md) の「値の表現」、「基本操作」、「Perceus」と、`runtime.md` の「`File` の参照の検査」に移した。`bench/` の仕事の回数で変わったのは `state` の RC の増減だけである ([計測の基準](../implementation/benchmarks.md) の「S8b (所有の形と基本操作の借用)」) |
| S8c | 書き出す型の線形性 (`Lin`、`Flexible(Lin)`、`OpVar(_, Lin)`)、SCC ごとに解いてから書き出す型検査の順、instance での Kind の評価 (`kind_values`)、型の線形性 (`linearity`)、instance の名前の `%1` / `%m`、debug ビルドの食い違いの検査 | 終えた。決めたことは [型と Kind](../spec/types.md) の「Kind の書き出し」、[Core IR](../spec/core-ir.md) の「変換の規則」と「食い違いがないことの検査」、[コンパイラの構成](../implementation/architecture.md) の「`eml_types` の内部」に移した。UI テストの出力、診断の文字列、`bench/` の仕事の回数は変わらない |
| S8d | translate と EP と box の挿入の Kind の印、EP の明示の drop、extern の行の Kind の列、V1 と V2、テキストの形の印 | 終えた。決めたことは [Core IR](../spec/core-ir.md) の「Kind の印」、[LIR](../spec/lir.md) の「Kind の印」と「Kind の印の検査」、`runtime.md` の「`File` の参照の検査」に移した。UI テストの出力と `bench/` の仕事の回数は変わらない ([計測の基準](../implementation/benchmarks.md) の「S8d (Kind の印と明示の drop)」) |

Kind の印を S8d に分け、書き出しを S8c にした理由は次のとおりである。

- 型だけから印を決める案は採れない。`tests/ui/run/files/file_in_return_clause_on_abort.em` では、使われない `return x ->` の `x` は型が `_` で、使用回数のパスが `x` の Kind を `Unr` に決めている。型だけから決めると `x` は `poly` になり、今ある `decref x` を V1 が拒む。解いた Kind を型に持たせて書き出す必要があり、これは `eml_types` の段の組み替えを伴う
- S8c は S8d がなくても検査できる。書き出した型と評価の結果は `eml_types` の単体テストで、instance の分かれ方は `eml_core_ir` のテストで確かめる
- 「`Lin` の物体の RC は 1」([LIR](../spec/lir.md) の「値の表現」) のうち `File` の物体そのものは、V1 がなくても実行時に確かめられる (`runtime.md` の「`File` の参照の検査」)。`File` を含む `Lin` のデータとクロージャは、S8d の V1 で静的に覆った

### 決めたこと

- 層の分担のうち、S8a と S8b で決まらなかったものは次のとおりである。S8a で決まった分担 (変数の Repr、配置の表と印、`mask`、extern の位置、T3 と一様化) は spec にある

  | 項目 | 置き場所 |
  |---|---|
  | 書き出す型の線形性 | `eml_types` が書き出し、`kind_values` と `linearity` で評価する ([型と Kind](../spec/types.md) の「Kind の書き出し」) |
  | 変数の Kind の印 | Core IR で決まり、LIR に写す ([Core IR](../spec/core-ir.md) の「Kind の印」) |
  | verifier の段 | Core IR (translate の後、EP の後) と LIR (入口、範囲、所有)。V1 は LIR の所有の段、V2 と作る所の検査は Core IR と LIR の各段に足す |

#### Kind の印

決めたことは spec に移した。変数と関数の戻り値が持つ印の意味と、V1、V2、作る所の検査は [LIR](../spec/lir.md) の「Kind の印」と「Kind の印の検査」に、translate と EP と box の挿入が印をどう決めるか、EP と決定木の明示の `drop` は [Core IR](../spec/core-ir.md) の「Kind の印」にある。

S8d で閉じた論点は次のとおりである。

- LIR のパスは配置を足さない。そのため、`unpack` と case で得たフィールドの印は、配置の表から確かめられず、translate を信用する。S9 のヘッダの `lin` ビットが実行時に覆う
- box の挿入が足す変数の印は `unr` で、`f$boxed` の引数と戻り値は元の関数の印を写す
- EP の yield の地点の結果 x は、遅い道で EP が `drop x` を出す。Perceus の `decref` を V1 の例外にはしない
- 操作の箇所の継続の印は、操作の宣言の多重度から決めない。節の `k` の印は、translate が `k` の型の矢印の線形性から決める。EP が作る継続のクロージャの印は、捕まえた値の印の結びである

## S9 共通ランタイム `eml_rt`

前提: S8。

S9 を、S9a、S9v、S9b-1、S9b-2a、S9b-2b、S9b-3 の6つの作業に分けて順に進め、すべて終えた。段の列では S9 の1行のままにする。S9 の間、`eml_rt` はパイプラインから使わない。Verus、単体テスト、Miri、extern の期待値の表 (S9b-3) で確かめ、実際のプログラムで通すのは S10 の VM からである。CEK と `eml_runtime` は S10 まで変えなかった。S10 で消す CEK に投資しないためである (上の「段の列」)。

| 作業 | 中身 | 状態 |
|---|---|---|
| S9a | 語、ヘッダ、ページの確保器、局所と共有の RC、`share`、`lin` ビット、reuse の部品、検査モード、Miri と Verus | 終えた。決めたことは [オブジェクトモデル](../spec/object-model.md) に移した。`eml_rt` はまだパイプラインから使わないので、UI テストの出力と `bench/` の仕事の回数は変わらない ([計測の基準](../implementation/benchmarks.md) の「S9a (`eml_rt` の核)」) |
| S9v | vstd への依存を受け入れ、`eml_rt` のコードを `verus!` の中に書いて、`unsafe` の核を含む crate 全体を Verus で検証する。Verus で確かめない部分を信頼の一覧にまとめ、Miri はそこを通るテストだけを流す。nixpkgs を nixos-unstable に上げ、Rust の toolchain を fenix から取り、Verus と verusfmt を flake の input にする | 終えた。決めたことは [オブジェクトモデル](../spec/object-model.md) の「`unsafe` の核」と [テスト戦略](../implementation/testing.md) の「`eml_rt` の検証」に移した。S9b の extern の語の ABI が FFI の最初の境界になるので、境界を信頼の一覧と Miri のテストに足す決まりを、S9b より前に決めておくために、S9a と S9b の間に置いた ([計測の基準](../implementation/benchmarks.md) の「S9v (`eml_rt` の検証)」) |
| S9b-1 | 物体の種類ごとの中身。データの物理的な形の規則、クロージャ、evidence の3つの物体、文字列、`File` の表し方 | 終えた。決めたことは [オブジェクトモデル](../spec/object-model.md) の「種類」、「物体の形」、「文字列」、「`unsafe` の核」に移した。UI テストの出力と `bench/` の仕事の回数は変わらない ([計測の基準](../implementation/benchmarks.md) の「S9b-1 (文字列)」) |
| S9b-2a | 不死の定数を置く凍結した領域。作る、凍結する、ヒープに付ける、寿命 | 終えた。決めたことは [オブジェクトモデル](../spec/object-model.md) の「凍結した領域」、「核の操作」、「文字列」、「不死の物体の数え方」、「報告する誤り」、「`unsafe` の核」に移した。UI テストの出力と `bench/` の仕事の回数は変わらない ([計測の基準](../implementation/benchmarks.md) の「S9b-2a (凍結した領域)」) |
| S9b-2b | `Ctx`、基本操作、SIGINT | 終えた。決めたことは [オブジェクトモデル](../spec/object-model.md) の「実行文脈 `Ctx`」、「evidence の3つの物体」、「確保と解放」、「核の操作」、「報告する誤り」、「検査モードの約束」、「論理的な worker ID」、「`unsafe` の核」と、[LIR](../spec/lir.md) の「実行の文脈」と「基本操作」に移した。UI テストの出力と `bench/` の仕事の回数は変わらない ([計測の基準](../implementation/benchmarks.md) の「S9b-2b (実行文脈)」) |
| S9b-3 | 語の ABI の extern、`File` の物体の中身の型、今の実装との差分テスト、FFI の境界の信頼の一覧の行と Miri | 終えた。決めたことは [オブジェクトモデル](../spec/object-model.md) の「extern」、「種類」、「物体の形」、「`lin` ビット」、「核の操作」、「文字列」、「検査モード」、「実行文脈 `Ctx`」、「`unsafe` の核」と、[LIR](../spec/lir.md) の「実行時エラー」、[テスト戦略](../implementation/testing.md) の「期待値の表」に移した。今の実装との差分テストは、2つの実装が同じ期待値の表を確かめる形にした。UI テストの出力と `bench/` の仕事の回数は変わらない ([計測の基準](../implementation/benchmarks.md) の「S9b-3 (extern)」) |

この順にしたのは、extern が文字列と `File` と出力先 (`Ctx`) を使い、凍結した領域の定数が文字列と物体の形を使うためである。S9b-2a を S9b-2b より前に置いたのは、核の操作の安全の前提を広げる作業を、基本操作の証明より前に独立して確かめるためである。

S9a で閉じた論点は次のとおりである。

- 確保器は、自前のページの確保器にする。64 KiB に揃えたページから大きさの級ごとに切り出し、物体の大きさはページの頭から引く (mimalloc と同じ方式)。ヘッダが 8 バイトに収まり、確保と解放が空きリストの数命令で済み、検証の道具が確保器の経路も確かめられ、生存の列挙がページを歩くだけで済むためである ([オブジェクトモデル](../spec/object-model.md) の「確保器」)
- `tobj` の中の `enum` のタグは、即値にする ([オブジェクトモデル](../spec/object-model.md) の「語」)
- 検証の道具は、Miri の2つの設定 (strict provenance と、それに Tree Borrows を足したもの) と Verus にする ([テスト戦略](../implementation/testing.md) の「`eml_rt` の検証」)
  - Kani は採らない。初めに試したが、CBMC は 3 個の節点のグラフでも `share_walk` の検査でメモリか時間が尽きた。Verus は、値の全域と任意の大きさのグラフについての証明が通る
  - loom は採らず、atomic と確保を `cfg(loom)` で差し替える層も置かない。atomic と確保は std の関数を1回呼ぶ薄い関数で包み、Verus は本体のコードそのものを検証するので、本体の型を差し替える必要がないためである。並行の振る舞いは、Miri の2つのスレッドのテストで確かめる ([オブジェクトモデル](../spec/object-model.md) の「`unsafe` の核」)
  - 並行の手順は、VM の並列化のときに Verus で証明する。vstd の atomic は SeqCst だけを扱うので、atomic の順序の正しさは、文書の議論と Miri に任せる ([テスト戦略](../implementation/testing.md) の「Verus」)

S9b-2a で閉じた論点は次のとおりである。

- `box 5` の定数や文字列リテラルなどの定数は、生成したときから不死の物体にし、どのヒープにも属さない凍結した領域に置く。領域は凍結した塊の鎖で、どのヒープも、付けた塊とその祖先の定数を指す語を受け付ける。領域の物体には、検査モードも含めてどの操作も書き込まず、検査モードは数えない。Koka の PR #910 の誤り (プロセス全体で共有する物体が atomic でない RC を持っていたために、2つのスレッドで動かすとヒープが壊れた) は、書き込まないことで起きない ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」)。evidence は不死の定数にしない (空の `evv` は即値の `()` である。[オブジェクトモデル](../spec/object-model.md) の「物体の形」)

S9b-2b で閉じた論点は次のとおりである。

- SIGINT の受け方: `eml_rt` は止める語を持つセッションの `Control` だけを持ち、vstd だけに依存したままにする。OS のハンドラは `eml_cli` が入れて `Control::interrupt()` を呼び、VM は安全点の `Ctx::poll` で止める語を読む。並列 VM でも、どの worker の `Ctx` も同じ `Control` を見る ([オブジェクトモデル](../spec/object-model.md) の「実行の制御」)。ハンドラを入れるのは S10 で、2回目の Ctrl-C の扱いはハンドラの設定にする (下の「S10 VM と切り替え」と「S11 REPL」)

S9b-3 で閉じた論点は次のとおりである。

- 出力先: OS とのやりとりを、セッションに1つの Host にまとめ、`Ctx` が持つ。`eml_rt` の `StdHost` は C の stdio と同じく、標準出力が端末なら行ごとに、そうでなければ 64 KiB ずつまとめて書く ([オブジェクトモデル](../spec/object-model.md) の「extern」)
- `File` の物体の中身: `Foreign` の中身を、パス、`BufRead` の読み手、長さの見込みを持つ Rust の値にし、閉じる処理は drop glue だけにする ([オブジェクトモデル](../spec/object-model.md) の「extern」の「`File`」)

### 決めたこと

- VM とネイティブで共有するランタイム `eml_rt` を作る。値の表現とヒープを共有しなければ、VM とネイティブのコードを混ぜて動かせないためである
- 値は 8 バイトの語にする ([オブジェクトモデル](../spec/object-model.md) の「語」)
- `tobj` の `Int` は 63 ビットの即値にし、収まらない値は box の物体にする ([オブジェクトモデル](../spec/object-model.md) の「語」)
- オブジェクトは、ヘッダとフィールドが続く1つのブロックにする ([オブジェクトモデル](../spec/object-model.md) の「ヘッダ」)
- 記述子は型ごとの表にせず、ヘッダの `scan` と種類と `lin` ビットで表す ([オブジェクトモデル](../spec/object-model.md) の「ヘッダ」)
- RC の符号は、0 を不死、正を局所、負を共有にし、上限に達した数は動かさない ([オブジェクトモデル](../spec/object-model.md) の「参照カウント」)
- 共有の経路 (`share`、負の RC の `dup` と `decref`、最後の参照での解放) も S9 で入れる ([オブジェクトモデル](../spec/object-model.md) の「`share`」)
- 共有の印の付いた物体は、RC の値によらず reuse しない ([オブジェクトモデル](../spec/object-model.md) の「reuse」)
- ヘッダの `lin` ビットは、検査モードに限らず常に持つ ([オブジェクトモデル](../spec/object-model.md) の「`lin` ビット」)
- 検査モードを持ち、今の検査付きヒープの役を引き継ぐ ([オブジェクトモデル](../spec/object-model.md) の「検査モード」)。生存の列挙では「共有の物体から届くのは、共有か不死の物体か、`lin` ビットの立った局所の物体だけ」も確かめる。`lin` ビットの立った局所の物体を許すのは、`poly` の親の中に `lin` の子がありうるためである ([オブジェクトモデル](../spec/object-model.md) の「`share`」)
- reuse を後から入れられるように、token と `con_at` を持つ ([オブジェクトモデル](../spec/object-model.md) の「reuse」)
- EP のダミーの値の約束を守る ([オブジェクトモデル](../spec/object-model.md) の「ダミーの値」)
- `unsafe` は小さい核に閉じ、核を含む `eml_rt` 全体を Verus で検証する。Verus で確かめない部分は信頼の一覧にまとめ、Miri で検査する。FFI の境界を足すときは、一覧に行を足し、Miri のテストを足す ([オブジェクトモデル](../spec/object-model.md) の「`unsafe` の核」)
- extern を語の ABI で1回だけ書く ([オブジェクトモデル](../spec/object-model.md) の「extern」)
- 実行文脈 `Ctx` を持つ。ヒープ、yield の状態と `evv` ([LIR](../spec/lir.md) の「実行の文脈」)、割り込みの旗と深さと確保量の上限を持つセッションの `Control` を置く ([オブジェクトモデル](../spec/object-model.md) の「実行文脈 `Ctx`」)。論理的な worker ID は `Heap` に置く ([オブジェクトモデル](../spec/object-model.md) の「論理的な worker ID」)。出力とファイルは `Ctx` が持つセッションの Host を通す ([オブジェクトモデル](../spec/object-model.md) の「extern」)。セッションの根は S11 で足す
- リスト、文字列、レコードの物理的な表現は、S9b-1 で決めた。データは、走査する語 (`obj` と `tobj` のフィールド) を宣言の順に並べ、その後に生の語を宣言の順に並べる。cons セルは [要素, 残り] になる。文字列は長さの語と UTF-8 のバイト列を持つ種類 `String` の物体で、一意なときはその場で連結する ([オブジェクトモデル](../spec/object-model.md) の「ペイロード」、「物体の形」、「文字列」)

## S10 VM と切り替え

前提: S9。

S10 を、S10a と S10b の2つの作業に分けて順に進める。段の列では S10 の1行のままにする。CEK を差分の基準として残したまま VM を作り、命令の形を実際に動かしながら決めるためである。

| 作業 | 中身 | 状態 |
|---|---|---|
| S10a | VM の本体を CEK と並べて作る。LIR から `CodeBase` を作るコード生成、`eml_rt` の `Ctx` の上で動く VM、逆アセンブラ、命令の位置から源の位置への表。`eml run --vm` と、`run` と `run-fail` の UI テストを VM でも流すこと | 終えた。決めたことは [VM](../spec/vm.md) と、[オブジェクトモデル](../spec/object-model.md) の「語」、「ペイロード」、「`lin` ビット」、「凍結した領域」、[LIR](../spec/lir.md) の「一様な関数」と「生存解析」、[テスト戦略](../implementation/testing.md) の「`eml_vm` のテスト」、「2つのモードで流す」、「Miri」に移した。既定の `eml run` は CEK のままなので、UI テストの出力と CEK の `bench/` の仕事の回数は変わらない。VM の実行の分の命令の数は、`bench/` のどのプログラムでも CEK の約 0.10〜0.17 倍だった ([計測の基準](../implementation/benchmarks.md) の「S10a (VM)」) |
| S10b | `eml run` を VM に切り替え、SIGINT のハンドラと上限を入れ、CEK、`eml_runtime`、`saved` を消し、spec を書き直す | 終えた。決めたことは [VM](../spec/vm.md) の「置き場所」、「スロットとスタック」、「上限と割り込み」、「`RunStats`」、「並列化への備え」と、[オブジェクトモデル](../spec/object-model.md) の「実行の制御」、[LIR](../spec/lir.md) の「値の表現」、「所有を取る時点」、「持ち主を手放す時点」、「実行の意味」、「実行時エラー」、[テスト戦略](../implementation/testing.md) の「期待値の表」、「2つのモードで流す」、「性能のテスト」、「CLI のテスト」に移した。`runtime.md` は消した。UI テストの出力は変わらなかった。`bench/` の数は [計測の基準](../implementation/benchmarks.md) の「S10b」にある |

S10a では、この節で決めていた次の3つを変えた。

- 算術と比較以外の extern は、「行の番号と引数のレジスタの範囲を持つ命令」にすると決めていた。S10a では、引数をオペランドの表のスロットの並びで渡す。レジスタの範囲にすると、引数を連続したスロットへ移す `Move` の命令が引数ごとに要り、色塗りでは連続を保証できないためである。直接の呼び出し、`apply`、`clause` も同じ形にそろえた ([VM](../spec/vm.md) の「呼び出しと戻り」)
- 呼び出しと戻りを安全点にし、「LIR に後ろ向きの辺がないので、無限に走るプログラムも必ず安全点を通る」としていた。VM は自己末尾呼び出しを関数の入口へのジャンプにするので、バイトコードには後ろ向きの辺ができる。そのため、このジャンプも安全点にした。呼び出し、戻り、自己末尾呼び出しのジャンプのどれかを、無限に走るプログラムは必ず通る ([VM](../spec/vm.md) の「呼び出しと戻り」)
- `f$boxed` の `yields` の指定は「S10 の VM が読む」としていた。evidence passing の後の LIR では、yield は普通の戻りと基本操作で表され、VM が `yields` で動作を変える所はない。VM は `yields` を読まない ([LIR](../spec/lir.md) の「一様な関数」)

S10a で閉じた論点は次のとおりである。

- 比較と分岐の融合命令は入れない。融合なしでも VM の実行の分の命令の数が CEK の約 0.10〜0.17 倍に収まり、命令を足すと `Op` の種類、コード生成の形の照合、逆アセンブラ、テストが増えるためである ([VM](../spec/vm.md) の「switch」)
- release のプロファイルの `codegen-units` は既定の値のままにする。インライン化の注釈が「definition is unavailable」と示した `eml_rt` の関数は、どれも実行の繰り返しの外か冷えた道にあったので、`#[inline]` も足していない ([VM](../spec/vm.md) の「置き場所」)
- `RunStats` の各項目の VM での意味は、[VM](../spec/vm.md) の「`RunStats`」に決めた。不死の物体の参照の数え方 (`rc_increments`) を CEK と比べられる形にする論点は、比べられる形にしないことで閉じた。凍結した領域の物体は検査モードでも数えない ([オブジェクトモデル](../spec/object-model.md) の「検査モードでは数えない」) ので、VM は文字列の定数の参照を数えない。CEK はリテラルの参照ごとに1つ数える。この差は `rc_increments` の期待値の違いとして記録し ([計測の基準](../implementation/benchmarks.md) の「S10a (VM)」)、S10b でスナップショットを替えるときの理由にする
- 定数の表は、`CodeBase` の `constants` (定数の語) と `region` (凍結した塊) にした。コード生成が作業用のヒープで定数を作って凍結する ([VM](../spec/vm.md) の「`CodeBase` と `FnEntry`」)

### 決めたこと

S10a と S10b で決めたことは spec に移した。S10b では、この節で決めていた次の4つを変えた。

- 上限の既定の値と、`RunConfig` での指定を決める、としていた。上限は `Control` が持ち、`RunConfig` は `Control` を持つ形にした。CLI が SIGINT のハンドラと実行に同じ `Control` を渡すためである ([VM](../spec/vm.md) の「置き場所」)
- `crates/eml_interp/tests/bench.rs` のスナップショットを VM のものに替えることを、期待値の変更としていた。VM のスナップショットは S10a で `crates/eml_vm/tests/bench.rs` にあったので、CEK の `bench.rs` は消した (成否の変更)
- `saved` と、Perceus でそれを埋める処理を消す、としていた。`saved` に結びついた規則 R7 も消し、Perceus の「所有を取る時点」の 2 のうち、呼び出しの後で生きる借りた変数を `dup` する枝も消した。どちらも、フレームが借りた値を持てない CEK のための規則だったためである。保持されている持ち主を呼び出しの前に解く枝は、空間のために残した ([LIR](../spec/lir.md) の「持ち主を手放す時点」)
- 期待値の表を `eml_rt` と CEK の両方と照らす形にしていた。CEK を消したので、表は `eml_rt` の回帰の表にした ([テスト戦略](../implementation/testing.md) の「期待値の表」)

## S11 REPL

前提: S10。

Prelude と `std/` の標準ライブラリと、指定したモジュールを読み込んだ環境で、対話的に実行する。S11 を、S11a、S11b、S11c の3つの作業に分けて順に進める。S11c は、触れる crate と決めることが違うので、さらに S11c-1 (端末)、S11c-2 (前端に触れるコマンド)、S11c-3 (表示器) に分けた。段の列では S11 の1行のままにする。S11b は `eml_rt` を大きく変え、Verus の証明が要るので独立させた。S11a を先に置くのは、回復が S11a の根の表を前提にするためである。

| 作業 | 中身 | 状態 |
|---|---|---|
| S11a | lib API だけで動く REPL のセッション。入力の読み分けと終わりの判定、セッションのモジュール、根の表、名前で照らして `CodeBase` に追記すること、`Show` による結果の表示、トランスクリプトのテスト | 終えた。決めたことは [VM](../spec/vm.md) の「追記」、[オブジェクトモデル](../spec/object-model.md) の「セッションの根」、[Core IR](../spec/core-ir.md) の「変換の規則」と「REPL の入力」、[LIR](../spec/lir.md) の「基本操作」、[モジュールと名前解決](../spec/modules.md) の「REPL のセッション」、[型と Kind](../spec/types.md) の「REPL の入力」、[レイアウト規則](../spec/layout.md) の「REPL の入力の終わり」、[文法](../spec/grammar.md) の「REPL の入力」、[テスト戦略](../implementation/testing.md) の「REPL のトランスクリプト」に移した |
| S11b | 根から届く物体を新しいヒープに写す回復 (Verus の証明を含む)。`evv` と yield の状態とスタックに残った語を古いヒープと一緒に捨て、確保量の上限で止まった後にページを確保量から戻す。コード表を更新する間の割り込みの保留を文書とテストで固定する | 終えた。決めたことは [オブジェクトモデル](../spec/object-model.md) の「回復」、「種類」、「確保と解放」、「生存の列挙」、「セッションの根」、「実行の制御」、[VM](../spec/vm.md) の「追記」と「`RunStats`」、[テスト戦略](../implementation/testing.md) の「REPL のトランスクリプト」に移した |
| S11c-1 | `eml repl` のコマンド、行の編集、`:{ … :}` の複数行の入力、`:quit` / `:help`、REPL 用の SIGINT のハンドラ、読みの中の割り込み、実行の前の割り込みでの取り消し、REPL の確保量の上限 | 終えた。決めたことは [REPL の端末](../spec/repl.md)、[VM](../spec/vm.md) の「上限と割り込み」と「追記」、[オブジェクトモデル](../spec/object-model.md) の「実行の制御」と「`File`」、[モジュールと名前解決](../spec/modules.md) の「REPL のセッション」、[レイアウト規則](../spec/layout.md) の「REPL の入力の終わり」、[テスト戦略](../implementation/testing.md) の「CLI のテスト」に移した |
| S11c-2 | `:load` / `:reload` / `:type` | 終えた。決めたことは [REPL の端末](../spec/repl.md) の「コマンド」「ファイルの読み込み」「型の表示」、[モジュールと名前解決](../spec/modules.md) の「REPL のセッション」、[型と Kind](../spec/types.md) の「REPL の入力」、[文法](../spec/grammar.md) の「REPL の入力」に移した |
| S11c-3 | `Show` を持たない型の表示器 | これから |

S11a では、この節で決めていた次の4つを変えた。

- 定義ごとに IR を保存し、総称な定義の instance をキャッシュするとしていた。S11a では、入力ごとにプログラム全体を前端から Perceus まで流し直し、名前で照らして新しい関数だけを `CodeBase` に追記する。中段の各パスを純粋な関数のまま保てるためである。代わりに、名前が同じ関数はいつも同じコードになることを、全パスが守る規則にした ([Core IR](../spec/core-ir.md) の「変換の規則」)
- 配置の番号を正規の順にするとしていた。VM は実行時に配置の番号を使わないので、名前で照らす追記では要らない
- 入力が使うセッションの値を、`input$N` の引数として根から `dup` して渡すとしていた。この形では関数の定義から `let` の値を読めないので、基本操作 `root_get` と `root_set` を足した ([LIR](../spec/lir.md) の「基本操作」)。新しい `Rhs` や `Atom` は要らない
- 入力の始めの `Control::clear` は割り込みとともに書いていた。確保量の上限で止まった後に `MEMORY` のビットが残り、後の入力が止まるので、S11a で入れた

S11b では、この節で決めていた次の3つを変えた。

- 回復の手順は、根から届くものを残し、届かないものを解放し、RC を数え直すとしていた。S11b では、根から届くものを新しいヒープに写し、古いヒープを丸ごと捨てる。根から届くものだけが残るという意味は同じである。その場で解放して数え直す手順をとらないのは、Verus の RC のモデルに多くのブロックと辺をまとめて消す新しい遷移が要ること、速いモードでは token の箱を生きている `Data` と見分けられないこと、小さい物体のページは OS に返さないので確保量が減らないことのためである ([オブジェクトモデル](../spec/object-model.md) の「回復」)
- REPL 用の SIGINT のハンドラ (2回目の Ctrl-C でも終わらない) を S11b に置いていた。S11b の `Repl` は lib API だけで、入力を読むプロセスの繰り返しがないので、ハンドラが働くのも、プロセスにシグナルを送って確かめられるのも、S11c-1 の `eml repl` からである。そのため S11c-1 に移した
- コード表を更新する区間では割り込みを保留するとしていた。`Machine::load` は止める理由のビットを見ないので、その間に来た割り込みは、ビットに残ったまま同じ入力の実行の最初の安全点まで保留される。S11b は新しい仕組みを足さず、この扱いを文書に書き、テストで固定した ([VM](../spec/vm.md) の「追記」)

S11a で閉じた論点は、シグネチャのない定義 (関数はシグネチャを必須にし、値は `let` で単相に推論する)、セッションの表し方 (1つのモジュールとみなし、HIR では入力ごとのモジュールで表す)、定義し直した型の表示 (古い版に `#N` を付ける) の3つである。

### S11c-1 で決めたこと

- 2回目の Ctrl-C でも REPL を終わらせない代わりに、待っている読みを止められるようにした。ハンドラを `SA_RESTART` なしで入れ、`Fs.read_all` は止める語が立った後の `EINTR` で止まる。前端の検査と回復は有限の時間で終わるので待ち、ほかに抜けられない処理 (import の FIFO、書き手のいない FIFO の `Fs.open`、詰まった標準出力) は Ctrl-\ で抜ける ([REPL の端末](../spec/repl.md) の「残る制限」)。Ctrl-C の扱いは unix だけのものにした
- 前端の検査の間に来た割り込みは、入力の種類によらず、その入力を受け付けない扱いにした (`Outcome::Interrupted`)。`load` の前に止める語を読む
- REPL の確保量の上限の既定の値は、物理メモリの 40% にした。回復が古いヒープと写しを同時に持っても、`eml run` と同じ 80% に収めるためである

### S11c-2 で決めたこと

- `:load` は GHCi と同じくセッションを作り直す。ファイルを今のセッションに足す形にすると、E1035 と import のキャッシュのために `:reload` が成り立たない。セッションを作り直すので、`:load` で型が変わるときに値を持ち越す問題は起きない
- ファイルは入力 1 で、既存のセッションの規則をそのまま使う
- `:type` は残った型変数に名前を付け、型に現れない型変数だけを `Unit` に決める

### 決めたこと

- 異常終了と割り込みからは、根から届く物体を新しいヒープに写し、古いヒープを捨てて回復する ([オブジェクトモデル](../spec/object-model.md) の「回復」)。実行時エラーと割り込みは Perceus の規則の外の中断なので、RC の規則だけでは回復できないためである (調査の実験では、S10b で消したインタプリタで、実行時エラーの後に局所変数が残った)
- コード表を更新する区間 (`Machine::load`) では、割り込みを保留する。`load` は止める理由のビットを見ないので、その間の割り込みは実行の最初の安全点まで保留される ([VM](../spec/vm.md) の「追記」)
- 2回目の Ctrl-C でも REPL は終わらない。`eml run` と違うこの扱いは、`eml_cli` のハンドラの設定で分ける (上の「S10 VM と切り替え」)
- `Show` を持たない型 (関数、継続) には、型に従う表示器を使う。表示器は深さと要素の数の上限を持ち、表示中も割り込みを見る。S11a は型だけを表示する
- コマンドは GHCi に寄せる (`:load`、`:type`、`:quit` など)

### 論点

- `IO` 以外のエフェクトを既定の handler で許すか。許すなら、handler のない操作の yield を REPL が受け取る
- セッションの値への連結は、RC が 2 以上になるので、いつも写しになる。定義し直した `let` の古い根を手放す順序。S11a は古い根を手放さない
- 凍結のときに生きている物体を詰め直して、塊のページを減らすこと。塊は使う大きさの級ごとに少なくとも1ページを持つので、新しい定数を持つ入力ごとに塊を作ると、使うメモリは入力の数に比例して増える ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」)。S13 で採りうるトップレベルの値の1回だけの評価でも塊が増える。困ったときに入れる
- 入力ごとにセッション全体を検査し直すので、セッションが大きくなるほど入力ごとの時間が延びる。困ったら増分の lowering に移る。名前が同じ関数はいつも同じコードになる規則があるので、後から移れる

## S12 スクリプトの MVP

前提: S11。

引き直す前のロードマップでスクリプトの MVP を型システムの実験より前に置いていたのは、線形型の負担 (`drop`、線形な値を返して受け渡すこと) が実用で許せるかを、機構を積む前に実際のスクリプトで確かめるためだった。S4a〜S11 を先に置いたので、この確かめは S12 と S13 で行う。

### 決めたこと

- IO の失敗は中断として伝え、組み込みの `try_io : (Unit -> <IO | e> a) -> <IO | e> Result IOError a` で捕まえる。中断の途中で捕まっていた `Lin` の値は、`never` の操作の中断と同じく、S7 の中断の経路で後始末する。捕まえなければ、エラーを表示して終了コード 1 で止まる
- `exit : Int -> <IO> a` は、同じ中断で `Lin` の値を後始末してから終了する。`<IO>` を持たせるのは、`par` の子から呼べないようにするためである。`try_io` は `exit` を捕まえない
  - 戻らない extern (`exit`) の結果の Repr は、`never` の操作の `clause` の結果と同じ考え方で扱いを決める。値を返さないので位置として扱わず、box の挿入は受け直さず、T3 は見ず、verifier は比べない ([LIR](../spec/lir.md) の「`never` の操作」)
- ローカルの再帰関数を入れる。`let (f, text) = Fs.read_all f` のような再束縛を壊さないように、引数を持つ関数の形のローカル定義だけを再帰的にする。単相で、lambda lifting する
- Rust で実装した extern の標準ライブラリを入れる。`String` (lines、split、trim、contains、replace、join、to_int)、`Env` (引数、環境変数)、`Stdin`、`Fs` (すでにある `open` などに足す、ファイル全体の読み書き)、`Proc.run`、`eprintln` である。S9 の語の ABI で書く
- CLI は `eml file.em args...` でスクリプトを直接起動できるようにする
- std の extern が名前的なデータ (`List`、`Option`、`Result`) を作るときは、extern の行がその型の正規の名前を持ち、translate がその配置を配置の表に入れる。今の extern が作るデータは、タグの決まった `Bool` と、大きさだけで配置が決まる `Fs.read_all` の組なので、行は配置を持たない ([Core IR](../spec/core-ir.md) の「translate の配置」)

### 論点

- ローカルの再帰関数の構文
- `Stdin` は入力全体と行を読む関数にとどめる。後の「バイト列と `Array`」の `Lin` のハンドルとの関係を決める
- extern が閉包を呼び戻す形。`&mut Ctx` を受ける今の extern の形では書けないので、呼び戻しの引数を渡すか、VM の側で作る行にするかを、その extern を足すときに決める ([マルチコア対応の設計](multicore.md) の「VM の並列化の備え」の制約5の、呼び戻しの入れ子の中でタスクを切り替えない決まり)
- 多相な extern の行の Repr を、std のシグネチャの型とどう比べるか。今の結び付けのテスト ([テスト戦略](../implementation/testing.md)) は、型で選ぶ行を除いて、extern の行のシグネチャに型変数がないことを確かめている

## S13 実例による判断

前提: S12。

S12 で書いたスクリプトの書き心地を見て、次の項目を採るかどうかを決める。最後の `par` の a1 だけは、スクリプトの書き心地でなく、並列の安全性を並列 VM より前に確かめるかどうかで決める。

- Kind の宣言化: シグネチャに Kind の境界を書き、段2の Kind 推論を減らす。宣言にするなら、持ち越しの条件付きの制約を書く形が要る。`map`、`fold`、`keep` を注釈なしで書ける今の性質を失わないことを条件にする。あわせて、ユーザーが Kind を書けるようにするか (関数型の線形性 `m` を含む) と、診断で矢印の線形性をどう表示するかを決める。今の診断は、`once` の `k` や `Lin` のクロージャを、ほかの関数と同じ形で表示する
- fixity の宣言をやめ、先頭の文字で決まる固定の優先順位の表にすること。整数の優先順位で、ライブラリ同士の演算子の衝突が問題になった場合の代替案 (Swift 方式の優先順位グループ) も、ここで一緒に判断する
- 字句的な負号 (`f -1` を `f (-1)` と読む。GHC の LexicalNegation と同じ)
- ブロック引数 (末尾の `fn`、`match`、`if`、`handle` を括弧なしで渡す)。`fn () ->` が多い場合のサンクの糖衣も一緒に判断する。今は `use` とセクションで足りると判断している
- 省略した row の暗黙の row 変数 ε: 今は省略した row を `<>` と読む ([型と Kind](../spec/types.md) の「関数型」)。高階関数で row 変数を書く量が負担になるなら、Frank の周囲の ability のように、1つのシグネチャの中で省略した row をすべて同じ暗黙の row 変数 ε とする規則に広げる。`map : (a -> b) -> List a -> List b` が `(a -> <ε> b) -> List a -> <ε> List b` になる
  - 互換の条件: 既存のシグネチャの型が、広げた規則の型の特別な場合 (ε := `<>`) になる形でだけ広げる。そのため、ε を入れるのは row を1つも書いていないシグネチャに限る。row を1つでも書いたシグネチャは、今と同じく省略を `<>` と読む。たとえば `twice : (Unit -> Unit) -> <IO> Unit` の引数に ε を入れると、閉じた `<IO>` の本体でコールバックを呼べなくなり、今は通るプログラムが通らなくなる
  - ε を入れるのはトップレベルのシグネチャだけで、`data` のフィールドの型には入れない。ローカルの型の明示とラムダの引数の型で省略した row は、推論用の row 変数に変えてもよい (型がより一般になるだけなので互換である)
- 中断で終わる経路での `Lin` の値の暗黙の後始末: `never` の操作や `exit` で終わる経路では、生きている `Lin` の値 (`k` を含む) を明示の `drop` なしに後始末する。「通常の制御フローでは暗黙の後始末をしない」原則 ([線形性](../spec/linearity.md)) を広げる変更なので、後始末の処理がエフェクトを起こしたり失敗したりする場合の扱いも決める
- 線形値の受け渡しの糖衣: `Fs.read_all &input` を `let (input, r) = Fs.read_all input` に脱糖する、Swift の `inout` 風の構文。API の返り値の形を縛ることと、巻き上げの規則が課題である
- トップレベルの値を一度だけ評価すること: 今は参照するたびに計算する ([Core IR](../spec/core-ir.md))。一度だけ評価するのは、単相で `Unr` の値に限る。起動時に評価するか初めて使うときに評価するかと、実行時エラーの報告の仕方も決める。S11 の REPL で入力をまたいで残す束縛の評価と、意味を揃えるかも一緒に決める
- `par` の a1 を協調的マルチタスクとして入れること: `par : (Unit -> <> a) -> (Unit -> <> b) -> (a, b)` を、並列 VM (下の「マルチコア対応」) より前に、シングルスレッドの協調的マルチタスクとして入れる。a1 は `Row<Never>` の Kind の制約も型システムの変更も要らないので、組み込みの関数1つで入れられる。前提は、タスクが持つ呼び出しのスタック (S10) と、実行時エラーの後の回復 (S11) である
  - 右の子を1つのタスクにし、左の子は親のタスクがそのまま実行する。右のタスクは新しい論理的な worker ID で動く
  - スケジューラは、呼び出しと戻りの安全点でタスクを切り替えてよい。方針は2つ持つ。「逐次」は切り替えず、左の子を終えてから右の子を実行する。`eml run` の既定と、ベンチの `RunStats` の固定に使う。「乱数種付き」は種で決めた間隔で切り替える。テストで使い、失敗したときは種を表示して再現できるようにする
  - 逐次の実行より多く確かめられるのは、所有者でない worker が共有の物体を解放する経路 (2つのタスクのどちらが最後に `decref` するかが種で変わる) と、タスクの中断、再開、join の待ちである
  - 実行時エラーは、右の子が先に失敗しても、左の子を最後まで実行してから報告する。右のタスクは止めたまま解放せず、評価全体を中断する。止めた右のタスクのスタックが持つ語を含め、残った物体は、中断の後の S11 の回復で古いヒープと一緒に捨てる。左の子が停止しなければ右のエラーは報告されず、逐次の実行と一致する
  - a1 の子は row が `<>` なので、どう切り替えても出力は変わらない。`run` と `run-fail` の UI テストを2つの方針で走らせ、出力が一致することを確かめる。検査用のフラグで印付けを1か所外すと、どれかの試験が必ず失敗することも確かめる (負の試験)

## S13 の後の言語の項目

### `Float`、`Char`、`Num`

前提: なし。

#### 決めたこと

- `Float` と `Char` の型、リテラル、Prelude の演算を入れる
- リテラルは単相にする。整数のリテラルは `Int`、浮動小数のリテラルは `Float` である。`fromInteger` 相当の脱糖も defaulting も入れない。`Int` と `Float` を混ぜるときは明示的に変換する
- `Char` は Unicode のスカラー値である
- `Float` の Repr と、`eml_rt` の語での `Float` の表現を入れる。型とリテラルより前に入れると、テストできない死んだコードになるためである
- `+ - * < <= > >=` と前置の `-` (`negate`) は `Num` と `Ord` のクラスで解決する。算術は `Int` と `Float`、順序の比較は `Int`、`Float`、`Char`、`String` に使える。何も型を決めないオペランドは、型クラスの規則どおり曖昧さのエラー (E2009) にする

#### 論点

- 型ごとの意味: `Float` の `/` と `%` の有無、`Float` の `==` と NaN の結果、`Float` の `Eq` / `Ord` の法則
- 除算のクラスを instance ごとの小さなクラスにするか、`Integral` / `Fractional` に分けるか。`negate` をユーザーに見せるか
- `Float` をリテラルのパターンと `switch` から外すこと
- 多相な位置での `Float` の表現と、`eml_rt` の語での表現をここで決める (方向は、`tobj` では `BigInt` と同じく箱、`float` の位置では生の 64 ビット)

### バイト列と `Array`

前提: `Float`、`Char`、`Num`。

`Byte` 型とビット演算、`Bytes`、`Array` を入れる。`Lin` のハンドルと、バッファ付きの読み書きを入れる。

#### 決めたこと

- `Byte` (0〜255) を専用の型にする。ビット演算のクラスと演算子と fixity を Prelude に足し、`Int` と `Byte` で共有する
- `Bytes` は `Unr` の値である。`Array a` の Kind は要素の Kind に従う。どちらも意味は不変で、更新は、RC が 1 ならその場で書き換え、そうでなければ写す。分割と結合、並列の書き換えのための `Lin` の `MutArray` と `freeze` は、後で足す (下の「マルチコア対応」)
- ハンドルは `Lin` にする。`Stdin` / `Stdout` / `Stderr` は別の型にする。バッファ付きの読み書きもハンドルにする。extern は、ハンドルに対する read/write の操作にとどめる

#### 論点

- `Byte` のリテラルの書き方 (リテラルは単相なので、`Byte` を書く形が要る)
- `Byte` の算術のオーバーフロー (実行時エラーか wrap か)
- 範囲外の添字を実行時エラーにするか `Option` にするか
- 中断のときに書き込みのハンドルを flush するか
- `println` と `Stdout` のハンドルの関係。S12 の `Stdin` の関数との関係
- `Lin` の要素を持つ `Array` の API
- マルチコアでのハンドルの扱い

### UTF-8 と標準ライブラリ

前提: バイト列と `Array`。

UTF-8 の核の extern を入れ、標準ライブラリを広げる。`std/` ツリーと最初のモジュール `Fs` はすでにあり、S12 で Rust で実装した extern のモジュールが入っている。

#### 決めたこと

- `String` は常に妥当な UTF-8 である
- UTF-8 の extern は小さい核にとどめる。検証付きのデコード (`Bytes` から `String`)、エンコード、バイト長、バイト位置から `Char` と次の位置を読む操作、境界を検査する切り出しである
- 「行を流す」などのストリーム処理は、ユーザー定義のエフェクトとして、標準ライブラリのモジュールの中に書く
- 書記素クラスタと正規化は対象外にする
- `Fs`、`Path`、`Proc`、`Json` などのモジュールの API を別の spec で決める ([標準ライブラリへの申し送り](stdlib.md))

#### 論点

- S12 で Rust の extern として入れた `String` の関数 (分割、検索、反復など) を、eml で書き直すか
- 位置の単位 (バイト位置を不透明な型にするか)
- 不正な UTF-8 の扱い (エラーか置換か)
- 大文字と小文字の変換など、Unicode の表が要る操作を extern にするか対象外にするか

### コマンドリテラル

前提: UTF-8 と標準ライブラリ。

コマンドリテラルの意味 (HIR から先) と、標準ライブラリの `Cmd` と `Proc` を入れる。字句と CST (`COMMAND_LIT`) は S6b で入れてあり、今は HIR が E0004 を出す。`Proc.run` は S12 で extern として先に入っている。

#### 決めたこと

- コマンドリテラルはシェルを介さず、引数のリストを組む ([字句](../spec/lexical.md) の「コマンドリテラル」)

#### 論点

- `Cmd` と `Proc` の API ([標準ライブラリへの申し送り](stdlib.md) の `Cmd` の項目)

## その後の項目

段と言語の項目に含めない項目を、分野ごとにまとめる。方針まで決まっている項目と、論点を挙げただけの項目がある。詳しい設計がある項目は、その文書へのリンクを付けた。「前提」は、先に済ませておく段か項目である。前提を書いていない項目は、どの段の後でも着手できる。

### 型システム

- 使い切り必須の型: 捨てることを許さない線形型。ユーザーが Kind を書けるようにする段階で、Kind に「drop できるか」の次元を追加して扱う。前提: ユーザーによる Kind の記述 (S13 で判断する)
- row 要素ごとの捕捉 Kind: `<IO, Async@lin>` のように、row の各要素に「捕まえてよい Kind」を推論で持たせ、`never` / `once` の持ち越し規則をより柔軟にする。マルチコア対応で挙がった「`Heap` を含まない row」の制約も、同じ種類の拡張として扱う ([マルチコア対応の設計](multicore.md))
- 借用: Rust / Austral 方式。意味論の大きな追加になる
- 関数型の部分 Kind による包摂: `Unr` の関数を `Lin` の関数型の場所に渡せるようにする。今は関数型どうしの単一化で線形性 `m` を等しくする ([型と Kind](../spec/types.md) の「関数型」)
- フィールドの関数型の線形性: `data` のフィールドに書いた関数型の線形性は、表面の構文で `m` を書けないので `Unr` に固定している ([型と Kind](../spec/types.md))。線形なクロージャを `data` に入れられるようにするかを見直す。前提: ユーザーによる Kind の記述 (S13 で判断する)
- 操作の引数の Kind 変数: 操作の引数の型に現れる Kind 変数は `Unr` に固定している ([エフェクトと handler](../spec/effects.md) の「handler の意味」)。線形な値を多相な操作の引数で渡せるようにするかを見直す
- 証拠が大きくなる制約付きの多相再帰: 今は型検査で弾く (E2012。[Core IR](../spec/core-ir.md) の「一様な位置と制約付きの多相再帰」)。必要な例が出たら、その場合だけ辞書渡しで許すかを見直す
- `Lin` の型を受けるクラス: 今のクラスはすべて `Unr` のクラスで、制約 `C a` は `a ≤ Unr` を意味する ([型と Kind](../spec/types.md) の「`Unr` のクラス」)。`Read` / `Write` のようにハンドルを受け取って返すクラスは、借用がなくても役に立つ。広げるときは、クラスの性質として `Lin` を受けるクラスを区別し、`Lin` を受けるクラスの instance の本体は頭の型変数の Kind に制約を足せない、という規則を置く。今のクラスの意味は変えない。前提: ユーザーによる Kind の記述 (S13 で判断する)
- orphan 規則をパッケージ単位に広げるか: 今の orphan 規則はモジュール単位である ([モジュールと名前解決](../spec/modules.md) の「instance の一貫性」)。パッケージの仕組みがまだないので、パッケージを入れるときに決める

### 言語機能と構文

- 可変参照 (方針は決定済み): 値 `Ref h a` と組み込みのエフェクト `Heap h` を持ち、`IO` と分離する。`run_heap` は rank-2 の組み込みとして特別扱いする。`Ref` には `Unr` の値だけを入れ、multi-shot で再開したときの状態は共有する ([マルチコア対応の設計](multicore.md) の「可変状態」)。入れ子の `run_heap` の中から外側の `Ref` を使うには、同じエフェクトのインスタンスを区別する必要がある。名前付きの handler が要るかどうかを、入れるときに決める
- 局所的な可変変数の糖衣構文: Koka の `var` のように、関数の中に閉じた可変変数を `Heap` を外に見せずに書けるようにする。前提: 可変参照
- フィールドの変換の糖衣: `{ p | age = _ + 1 }` のような、関数でフィールドを書き換える構文。`Lin` なレコードでも、分解せずに書けるようにする。今の更新は上書きされる古い値を捨てるので、`Lin` なフィールドは分解して組み直すしかない ([直積型とレコード](../spec/records.md) の「線形性の規則」)
- 型の別名: `type Name = T`。構文は予約してあり、今は `type` の宣言を HIR が E0004 にする ([宣言](../spec/declarations.md) の「`data` と `type`」)。別名を展開する位置 (HIR か型検査か)、型引数を持つ別名、診断での表示 (別名で書くか展開して書くか) を決める
- 抽象型: コンストラクタを公開しない `pub data`。名前付きのフィールドも、コンストラクタと一緒に隠す規則を決める。今は射影と更新がフィールドの見える範囲を検査しない ([モジュールと名前解決](../spec/modules.md) の「名前空間」)
- 再エクスポート: `pub import`
- 修飾した演算子の構文 (`Csv.(</>)`)
- 接頭辞付きリテラルの一般化: `re"..."` のように、ユーザーが接頭辞付きのリテラルを定義できるようにする。穴の型付けにアドホック多相が要る
- or パターン、ガード、as パターン: パターンを広げる。網羅性の検査 ([網羅性](../spec/exhaustiveness.md)) と決定木の変換を一緒に広げる
  - ガードには所有の制約がある。今の Perceus が `Lin` のフィールドを `dup` しないのは、決定木の途中で、後の行が持ち主を使うフィールドを消費しないことに依る ([LIR](../spec/lir.md) の「値の表現」)。ガードを入れると、ガードが呼び出しの引数として `Lin` のフィールドを渡し、後の行が持ち主を使う形ができる。フィールドを消費する時点で持ち主が必要なので、Perceus はそのフィールドを `dup` し ([LIR](../spec/lir.md) の「所有を取る時点」)、`File` の `dup` をヒープの検査が止める。ガードを入れるときは、ガードが `Lin` のフィールドを消費しないという型の規則か、別の変換が要る
- 仮置きの式: どの型にもなる仮置きの式 (typed hole)。入れるときに、網羅されていない `match` と等式の fix (E4001 の枝の追加、E4002 の等式の追加の提案) を一緒に入れる ([診断の出し方](../implementation/diagnostics.md) の「網羅性の診断」)

### 処理系

- Kind 推論の検証: `eml_types/src/kind/` の束の上の計算 (最小解、多相化で残す制約、持ち越し、含意、instance での値) を vstd だけに依存する葉の crate に移し、Verus で証明する。型検査と evidence passing の変換は Verus で扱わない。S10 の後に、LIR の verifier と VM の組で `eml_rt` の前提を証明するかを検討する。詳細は [Verus で検証する範囲](verification.md) にある
- インクリメンタル化: 各段階をクエリ (salsa など) に載せ替える。各段階を純粋な関数にしているのはこのため ([コンパイラの構成](../implementation/architecture.md))
- LSP: 診断、hover (型と row の表示)、補完、code action。診断の構造体は、LSP の診断と code action に変換できる形にしてある ([診断](../spec/diagnostics.md))。前提: インクリメンタル化
- ネイティブ化: LIR から Cranelift でネイティブのコードを出す。LIR のブロックの列とブロック引数は、Cranelift のブロック引数に1対1で写る。多相な位置の `Int` の表現は S9 で決めた語の表現を、`Float` の表現は「`Float`、`Char`、`Num`」で決める表現を前提にする。VM とネイティブは `eml_rt` の値とヒープを共有し、関数表 `FnEntry` を接続点にして混ぜて動かせる。たとえば、標準ライブラリだけをネイティブにし、ユーザーのコードをバイトコードで動かす。VM からネイティブの関数を呼ぶときは `f$boxed` の一様な入口を使う。`eml_extern` の表は、`eml_rt` の語の ABI の関数になる。ネイティブの `par` がバイトコードの閉包を worker で呼ぶには、VM の並列化 (下の「マルチコア対応」) が要る。前提: S10、`Float`、`Char`、`Num`
  - Cranelift の mid-end は制御フローをほとんど変えないので、jump threading と既知のコンストラクタの畳み込みは Core IR の側で行う
  - ネイティブのコードの中で起きた実行時エラー (オーバーフロー、ゼロ除算) を、評価全体の中断にする方法は未設計である。旗を立てて戻る方式は効果を持たない関数にも確認を足し、巻き戻しは Cranelift のコードに展開情報を要する
  - extern の C ABI の入口 (`extern "C"`) は、この項目で足す。今の extern は、引数がどれも 64 ビットの語で数が決まっているので、そのまま移せる。Host と読み手は panic しうるので、入口で `catch_unwind` する。`extern "C"` を越える panic はプロセスを落とすためである。`Fault` を `Ctx` の欄に置いて状態の語を返す形にするかは、`Ctx` の配置 (yield の状態は `#[repr(C)]`) の決まりと一緒に決める ([オブジェクトモデル](../spec/object-model.md) の「extern」)
  - 定数の静的なデータは、凍結した領域と同じ約束 (rc 0、書き込まない、検査ビルドでは前置きを持つ) に乗る ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」)。検査モードの範囲の確かめのようにページの頭を読む道は、起動時に `freeze` で定数を作る形か、静的なデータに容量を持たせる形で扱う
- Core IR の上の最適化パス: 既知の閉包への `apply` を `call` に置き換えること、引数が定数の関数の特殊化、純粋な extern の定数畳み込み。EP より前の Core IR に置き、関数単位の作業リストで動かす。枝の部分木を置き換えると、S3b-1 までの `simplify` のように長い `else if` の連鎖で2乗の時間がかかるためである。CPS のラムダの位置の変換 (試作で 200,125 回) は、既知の閉包への特殊化で減らす。Repr が同じ instance (`List Int` と `List String` の instance など、同じ形のコードになるもの) をまとめるのも、このパスに置く ([Core IR](../spec/core-ir.md) の「変換の規則」)
- evidence passing の最適化 ([Core IR](../spec/core-ir.md) の「evidence passing」)。どれも EP と実行時の中に閉じ、型検査と translate は変わらない
  - evidence を探す場所ごとのキャッシュと、閉じた row の静的な添字。今は `ev_lookup` が `evv` を先頭から探し、費用は今有効な handler の数に比例する。`evv` は書き換えないので、場所ごとのキャッシュを足せる。静的な添字は Koka の open の包みを要し、包みが部分ベクタを確保して末尾呼び出しを失うので、目立ったときに採るかを決める
  - 中断の yield でクロージャを作らない形。今は中断も普通の yield と同じく κ を組み立ててから `prompt$` が捨てる
  - 外のエフェクトを呼ぶすぐに再開する節をその場で実行する形 (論文の under)。節の実行中に `evv` を外側に替え、yield したら替え直す包みと、再開で作り直した evidence を探し直す仕組みが要る。今はこうした節を再開する節として扱う
  - `mask` 付きの呼び出しのたびに `evv_mask` が `evv` の節点を写して確保しないようにすること
  - 末尾の位置の `mask` 付きの呼び出しで、x を返すだけの `f$kN` を作らないこと
  - T3 で `ret` を上げた関数の遅い道で、ダミーの `0` を `box` しないこと
- Perceus の最適化: reuse analysis (FBIP)、借用パラメータ。どちらも LIR の上のパスで、消費しない `switch` と `release` の上に、IR を作り直さずに足す。reuse の確保の API と検査モードでの扱いは S9 で入れてある。足すときは次の約束を守る
  - reuse は、`release` を `release_reuse` に、それが空けた箱を使う `con` を `con@token` に書き換えて入れる (Lorenzen と Leijen の drop-guided reuse と同じ方向)。共有の印の付いた物体は reuse しない (S9)。reuse のトークンは、継続が捕まえる値 (EP の後は継続のクロージャ) に入れない。入れると、複数回の再開が同じ箱に2つの値を作るためである
  - 借用パラメータ: 1つの呼び出しでは、所有の引数を消費した後で借用の引数を確かめる。継続のクロージャが捕まえる値に借用の部分を含めない。借用のブロック引数は持ち主 (同じブロックの引数か関数の入口) を宣言し、verifier は辺ごとに確かめる
    - 所有の都合で `TailCall` を `let r = <呼び出し>` と `return r` に降格するのも、借用パラメータと一緒に入れる。今は `tail` の前に実引数をすべて所有にし、保持している変数をすべて手放す ([LIR](../spec/lir.md) の「持ち主を手放す時点」) ので、借用パラメータを入れるまで降格は起きない。Perceus は、終端を文と新しい終端に置き換える編集をその場でできる形にしてある
    - 降格は、末尾の位置の呼び出しの輪の上の `tail` には当てない ([LIR](../spec/lir.md) の「末尾の位置の呼び出し」)。借用の推論は、輪の上の `tail` が渡す引数の仮引数を所有にして、降格を避ける (Lean の `ownParamsUsingArgs`)。降格してよいのは、輪の上にない末尾呼び出しだけである
    - extern の行に、引数ごとの所有と借用の列を足すのも、借用パラメータと一緒に入れる
    - 部分適用される関数は借用を持てないので、所有の版の包みが要る (Ullrich と de Moura)。`f$boxed` との合成を、借用を入れるときに決める
    - 借りたまま読む射影も、借用パラメータで扱う。S8b の所有の形では、射影で得たフィールドを読むだけなら RC の命令は出ない。しかし `f p.name` の後に `p` を使う形は、呼び出しがフィールドを消費するので、今と同じく `dup` する ([Core IR](../spec/core-ir.md) の「変換の規則」)。これを減らすには、`f` の引数を借用にする必要がある
  - 借用の推論では、同じ配置の `con` を作る行き先を持つ scrutinee を所有にする。reuse の機会を残すためである
  - FP² (Lorenzen、Leijen、Swierstra) の `fip` のような、確保なしで動くことの静的な検査を置くかは、`multi` の継続が同じ値を共有しうる点との相性を確かめてから決める
- ループ化 (後ろ向きの辺): 自己末尾呼び出しを、関数の中のブロックへ戻る `jump` にする。トップレベルの関数を呼び出し元のブロックにする contification も同じ枠で扱う。今は辺がすべて番号の大きいブロックへ向かう ([LIR](../spec/lir.md) の「構造の規則」の R2)
  - 入れる時期: S10 の VM は、自己末尾呼び出しをバイトコードの出力で入口へのジャンプにするので、IR の R2 を緩めずに済む。R2 を緩めるのは、ループの中で変わらない値の移動や、ループの頭のブロックの引数を借用として扱う Perceus の拡張が要るときにする。借用パラメータかネイティブ化に着手するときに一緒に入れる
  - 残りの作業: R2 を、ループの頭への後ろ向きの辺だけを許す形に緩めることと、変換にループ化を足すこと。ブロックはすでに複数の引数を持てる
  - 生存解析、縮約、verifier は、辺がすべて前向きであることを使って1回のループで済ませている。ループ化では、ループの頭に印を付け、そこだけ不動点を計算する。支配木の計算も、後ろ向きの辺を含む形に広げる
- jump threading とインライン化: 呼び出しの結果に対する case-of-case と、translate の後に現れる case-of-case は、今は扱わない。インライン化を入れるときに、ブロックの引数を通した既知のコンストラクタの jump threading として一緒に入れる。インライン化の後で初めて、呼び出しの結果が既知のコンストラクタになるためである
  - インライン化は Core IR の上で EP の前に置き、`tail`、`box`、`unbox` を出さない。box の挿入がプログラム全体の ABI と変換を1か所で決め、縮約が末尾呼び出しを作るためである ([Core IR](../spec/core-ir.md) の「パス」)。Prelude の `|>`、`>>`、`<|` のような普通の関数の合成子も、インライン化で展開する
  - 規則: `jump M(a)` の行き先 `M(p)` が `switch p` か `unpack p` で始まり、`p` をほかで使わず、`a` が `Tag` や `Int` の定数か、`let` で束縛した `con L #k(fs)` なら、`switch` を `jump` の側で決める
  - R3 を守る作り方: 選ばれる case の行き先 C を、辺のブロック `C: jump N(f')` と、元の本体を持つ合流のブロック `N(フィールド)` に分け、`jump N(fs)` へ付け替える。パスの終わりに番号を1回振り直し (R2)、届かなくなったブロックを消す
  - 最初の段は、合流のブロックの引数の展開である。すべての入る辺が、コンストラクタが1つだけの型の既知の `con` を渡し、`M` が `unpack p` で始まるなら、`p` をフィールドの引数に置き換えて `unpack` を消す。ブロックは増えず、R2 と R3 にも触れない。`if` や `match` を通るタプルを受ける形 (状態を回すループでよく出る) は、これで覆える
  - S3b-1 までの `simplify` が行っていて、S3b-2a の translate が行わない書き換え (値を渡すだけの合流のブロックの転送、枝の中でタグの分かった scrutinee をそのタグに置き換えること、引数が2つ以上で返すだけのブロックのたたみ込み) も、ここで一緒に考える
- 実行時エラーの backtrace: S3b-2a で、extern の呼び出しの中で起きた実行時エラーに位置を付けた。呼び出しの連なり (backtrace) と、位置のない誤り (extern の外で起きたヒープの誤りや内部の誤り) の利用者向けの表示を、その後に足す。VM では、S10 のエラー位置の表の上に作る
- HIR の位置を source map に移す: HIR のノードが `TextRange` を直接持つ形をやめる。位置を別の表に分けると、編集で位置だけが変わったときに HIR を作り直さずに済む。この利点はインクリメンタル化 (salsa) に載せ替えるまで効かないので、そのときに移す
- フォーマッタ: CST がロスレスなので、その上に作る。前提: コマンドリテラル (本番の構文がそろってから)
- n 列の `match`: 今は決定木の列に、最初の行でコンストラクタ、タプル、リテラルのどれかのパターンを持ついちばん左の列を選ぶ ([Core IR](../spec/core-ir.md))。行列によっては部分木が大きくなりうる。今の選び方でも決定木は正しいので、部分木の大きさが問題になる例が出てから列の選び方を見直す
- doc comment: trivia の付け方を決める。doc comment を解釈するドキュメント生成と LSP の hover ([字句](../spec/lexical.md)) がまだないので、それを作るときに、使う側に合わせて決める。前提: LSP
- JIT (投機的): バイトコードから機械語を安く作る copy-and-patch や、トレース JIT。VM が安定し、起動時間が支配的になってから検討する。トレース JIT はバイトコードにスタックのスタックを持たせる別の道で、evidence passing とは前提が合わない。前提: S10、ネイティブ化

### マルチコア対応

詳細は [マルチコア対応の設計](multicore.md) にある。VM とネイティブのランタイムの両方を並列にする。S10 の VM はシングルスレッドで出し、後から並列にできる制約を S9 と S10 で守る。VM の並列化は、ネイティブ化とは別の項目にする。主な項目は次のとおり。

- VM の並列化: 本物のスレッドで `par` を動かす。fork と join の印付けに使う共有の経路と、論理的な worker ID と所有者の検査は S9 で入れてある。S13 で `par` の a1 を採れば、そこで UI テストでも確かめる。この項目で足すのは、worker の起動と join、work stealing、別のスレッドからの解放に対応したアロケータと、本物のスレッドでしか現れない誤り (公開の順序、2つのスレッドからの同時の `decref`、deque) の検査である (同じ文書の「テスト」)。前提: S10、`par` の a1 (S13 で採った場合)
  - 別の worker が持つ物体 (共有、rc < 0) を、ヒープの操作が受け付けること。rc の並行の書き込みが要る。受け付けるブロックを付けた塊に広げた形 ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」) は、この拡張を妨げない
- 共有の印方式の RC (S9 で `eml_rt` に入れ、VM とネイティブで共有する)
- データ並列に限った `par` の段階的な拡張 (a1 → a2-wait → a2-cancel)
- 並行処理の `spawn` と `run_scheduler`
- 継続の移動
