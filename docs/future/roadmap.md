# ロードマップ

位置づけ: 将来の設計。

今後の実装を、再設計のサブプロジェクト S4〜S13 と、その後の言語の項目、処理系の項目に分けてまとめる。今の言語の範囲は [実装の現在地](../implementation/status.md) の「今の言語の範囲」にある。再設計の決定のうち、確定した設計判断は [概要](../overview.md) にもある。S4〜S13 の順序は、`docs/reports/eml/` の2本の調査レポート (VM とネイティブコード生成、REPL 向けのランタイム) を踏まえて決めた。

## 進め方

- 各段は、spec、計画、実装の順に進める。spec は、この文書のその段の節を出発点にする
- 「決めたこと」は方針で、細部はその段の spec で決める。「論点」は、その段の spec で決める
- 段を終えたら、決まったことを `spec/` に移し (実装の構造に関わるものは `implementation/` に移し)、この文書からその段の節を削る。[実装の現在地](../implementation/status.md) と [コンパイラの構成](../implementation/architecture.md) は、段の途中では直さず、段の終わりに1回で直す
- テストの変更は、各段の spec に、[テスト戦略](../implementation/testing.md) の「テストの変更の運用」の種類 (成否の変更、期待値の変更、機械的な追随) で書く
- 段は、パイプラインの段階 (crate) とは別の呼び方である

順序の理由は次のとおりである。

- S4 を先頭に置くのは、translate の出力の形を、EP、`eml_rt`、VM のすべてが受け取るためである。表面の構文を変えないので、段を小さく保てる
- CPS のラムダの位置の変換 (box の挿入を作ったときの試作で 200,125 回) は、単相化では消えず、既知の閉包への特殊化 (下の「処理系」の最適化パス) が要る。そのため S4 は、減る量を約束せず、回数を記録するにとどめる
- S6 が S5 に依るのは、補間と `deriving` だけである
- S7 は Core IR から Core IR への変換なので、LIR がなくても今の経路で CEK に流して比べられる
- S8 を S9 より前に置くのは、`eml_rt` の関数表と `CodeBase` が LIR の関数の集合を前提にするためである。関数の集合は、box の挿入が `f$boxed` を足して初めて決まる
- S9 を S6 の後に置くのは、データの表現を、実際のリスト、文字列、レコードで測って決めるためである。S11 が要る仕組み (`CodeBase`、生存の列挙、RC の上限) は S9 で入れる。後から差し込むと作り直しになるためである
- CEK の確保を除くこと (レポート1の提案1) と、CEK の上に REPL を作ること (レポート2の提案1) は行わない。どちらも、S10 で消す CEK への投資になるためである。レポート1の測定では、`fib 22` の実行命令の約53%が確保と解放、引数と退避の `Vec` の組み立てだった。VM とランタイムは、この費用を持たない形で作る
- `Float`、`Char`、`Num` を S5 の後に置くのは、`Num` をクラスとして入れ、型ごとの多重定義を別に作らないためである
- バイト列と `Array` を `Num` の後に置くのは、`Byte` と `Int` で演算子を共有するためである

## S4 単相化と計測の基準

前提: なし。

### 決めたこと

- 表面の構文は変えない
- translate に (関数, 型引数) の instance の表を持たせ、`main` から届く具体化だけを変換する。関数のコードは、型変数をすべて具体化した型で変換する
- 多相再帰で具体化が上限を超えたときは、型変数の位置を `tobj` のまま扱う一様な版を使う
- 操作ごとに量化した型変数を持つ操作 ([宣言](../spec/declarations.md) の「`effect`」) の節も、一様な版にする。節はすべての具体化を1つのコードで受けるためである。節が呼ぶ総称な関数は、「一様」という型引数の鍵で instance の表に入り、その鍵は呼ぶ先にも伝わる
- row は単相化しない。row の多相は S7 の evidence passing で扱う
- データの配置は一様のまま変えない。型変数のフィールドは `tobj` で、`Option Int` と `Option a` は同じ配置を使う ([Core IR とインタプリタ](../spec/core-ir.md) の「データの配置」)。配置まで型ごとに分けると、一様な版のコードと配置が食い違うためである。`tobj` の `Int` の費用は、S9 で即値にして下げる
- 計測の基準を作る。`fib`、`loop`、`state`、リスト、木のプログラムを基準にし、`RunStats` に `box` と `unbox` の回数を足す。callgrind の実行命令数を、測定の環境と一緒に記録する
- instance の数とコンパイル時間の scaling テストを、具体的な上限付きで足す
- `f$boxed` の規則の根拠のうち「標準ライブラリを一度だけ変換して使い回す」([Core IR とインタプリタ](../spec/core-ir.md) の「box の挿入」) は、単相化で総称な std のコードがプログラムごとに変換されるようになるので書き直す
- 変わる Core IR のダンプ (多相な関数を含むもの) は、S4 の spec に期待値の変更として範囲で挙げる

### 論点

- 具体化の上限の値
- instance の名前の付け方 (ダンプと診断での表示)
- 型の表の rigid な型変数は名前だけで書き出すので、関数の型変数と、同じ名前の handler の節の型変数を表の上で区別できない ([コンパイラの構成](../implementation/architecture.md) の「`eml_types` の内部」)。単相化で型引数へ代入する前に、節の型変数を区別する表し方を決める

## S5 型クラス

前提: S4。

### 決めたこと

- 表面は Haskell 98 の形の単一引数の型クラスにする。`class`、`instance`、上位クラス、`deriving` を持つ。instance の頭は、`data` の型コンストラクタに互いに異なる型変数を適用した形に限る。高カインドのクラス、多引数のクラス、関連型、`Add<Rhs, Output>` 形の演算子のトレイトは入れない
- 等価、比較、表示は、Prelude のクラス `Eq`、`Ord`、`Show` で作る
  - シグネチャの制約 `Eq a =>` と `deriving (Eq, Ord, Show)` を持つ。`=>` を予約の記号に、`deriving` をキーワードにする。今は `=>` をユーザーが演算子として定義できるので、`=>` を定義するテストは成否の変更になる
  - 証拠 (どの instance を使うか) は、型検査が記録した参照ごとの型引数から、S4 の instance の表で確定する。実行時の辞書は持たない。組み込みの instance のメソッドは extern に変換する。`Eq` の `Int`、`String`、`Bool` のインスタンスは、Prelude の `int_eq`、`string_eq`、`bool_eq` と、それぞれの `_ne` の extern を呼ぶ
  - M2 の参照ごとの具体化の表 ([コンパイラの構成](../implementation/architecture.md) の「`eml_types` の内部」) の型引数から、証拠を解決する
  - エフェクトの操作のシグネチャと `data` のコンストラクタのフィールドには、制約を書けない。書けると、handler の節が perform の位置で選んだ証拠を実行時に受け取る必要が生じ、実行時の辞書が要るためである
  - 証拠が循環に沿って大きくなる制約付きの多相再帰 (入れ子のデータ型の `Show` など) は、型検査で弾く
  - 制約はトップレベルのシグネチャへ推論で足さない。解けない制約と曖昧な制約はエラーにする。何も型を決めないオペランドを `Int` に倒さない。単相性制限と defaulting は持たない
  - 線形性は Kind のままにする。`Copy` や `Drop` のようなクラスは作らず、Kind は instance の選択に関わらない
  - クラスとエフェクトは別の仕組みである。メソッドの row は普通のシグネチャと同じ規則に従う。Prelude のクラスは純粋なので、`par` の中でも使える
  - タプルには処理系が `Eq`、`Ord`、`Show` の構造的な instance を与える。`data` は `deriving` で instance を得る
  - `String` の順序はバイト順で、妥当な UTF-8 ではコードポイント順と一致する
  - `Num` は `Float`、`Char`、`Num` の項目に回す。それまで算術は `Int -> Int -> Int` のままにする
  - 今の `==` の特別扱い (`equality` と E2006) は、この仕組みに置き換える
  - 実行時に値の構造をたどる方式 (OCaml、Gleam) は採らない
- 一貫性を守る。instance は大域的に1つで、クラスか頭の型コンストラクタを定義したモジュールにだけ書ける (モジュール単位の orphan 規則)。重なる instance、局所的な instance、第一級の instance は持たない。instance は名前ではないので、修飾付きの import によらず見える
- 持ち越しの制約の表示 `a => <e> <= Once` ([型と Kind](../spec/types.md)) を、`=>` と重ならない形に変える。型検査のダンプだけに出るので、期待値の変更である

### 論点

- `Ord` のメソッドを `< <= > >=` にするか `compare` と `Ordering` にするか。`!=` を `Eq` のメソッドにするか普通の関数にするか
- 表示用のクラスを `Show` 1つにするか、`Show` と `Display` に分けるか。S6 の補間の穴と S11 の REPL の表示が、この決定に従う
- レコードの `Ord` のフィールドの順
- メソッドの Kind を、位置ごとにどう決めるか。畳み込みのメソッドで `Lin` の累積値を持てるか。instance のメソッドが推論した Kind の制約を、クラスのメソッドの Kind と照らす規則。借用が入った後の `Lin` 型のクラス
- 導出した instance で比べないフィールドを `drop` する形
- 既定のメソッドをいつ入れるか
- 証拠が大きくなる多相再帰のための辞書渡し
- orphan 規則をパッケージ単位に広げるか
- instance の複製の数を報告するか

### 方式を選んだ理由

ネイティブ化とインタプリタの効率を重視し、Haskell の型クラスを第一の候補として次の案を比べた。

| 案 | 結論 |
|---|---|
| 型クラス + 辞書渡し (GHC) | 採らない。インタプリタで `+` が extern 1つから、辞書の取り出しと間接呼び出しになる。実行時に辞書の値、射影の Rhs、借用の扱いが要る |
| 辞書渡し + 既知の instance の静的解決 + 特殊化 | 採らない。無償になるのは文脈のない instance だけで、`List Int` の `==` や導出した instance は辞書を通る。辞書の仕組みと複製の仕組みを両方持つことになる |
| Rust のトレイト + すべての総称の単相化 | 採らない。データの配置まで型ごとに分けると、多相再帰と操作ごとに量化した型変数の節で一様なコードと配置が食い違い、言語を制限することになる。関数のコードの単相化は S4 で採る |
| 組み込みの型だけの多重定義 | 採らない。ユーザー定義の型に広げられない |
| 実行時に値の構造をたどる方式 (OCaml、Gleam) | 採らない。型クラスに移るときに捨てる機構になる |
| 暗黙の引数 (Koka、modular implicits) | 採らない。修飾付きの import と衝突し、型クラスのまとまりも失う |
| クラスをエフェクトで表す | 採らない。row を汚し、解決が動的になる |
| **型クラス + 関数のコードの単相化** | **採る**。証拠は S4 の instance の表で確定する。データの配置は一様のままにする |

採った案が成り立つのは、eml の型が rank-1 で、シグネチャが必須で、局所的な `let` とラムダが単相で、局所的な instance も第一級の instance もなく、操作とコンストラクタが制約を持たないためである。この条件では、制約のない本体での制約付きの参照は、すべて確定した証拠を持つ。Roc (RC とその場の更新の実行系) と Austral も型クラスや abilities を特殊化で実行するが、どちらも総称をデータの表現まで含めて単相化する。eml は関数のコードを単相化するが、データの配置は一様のまま残し、多相再帰と操作の節では一様な版を使う。そのため、row の多相にも触れない。代償は、複製の分だけ増えるコードの大きさと、REPL で新しい型の組を使うたびに変換が1つ増えることである。

## S6 リスト、文字列、レコード

前提: S5 (補間と `deriving` のため)。

### 決めたこと

- リストのリテラルと `::` を入れる。`List`、`Option`、`Result` を標準ライブラリに置く
- 補間、複数行の文字列、raw 文字列と、そのための lexer のモードを入れる。補間の穴の型は、S5 で決める表示のクラスに従う。`String` の穴は引用符なしで入れる ([字句](../spec/lexical.md))
- レコードは名前的なレコードにする

  ```haskell
  data Person = Person { name : String, age : Int }

  let p = Person { name = "a", age = 3 }
  p.name
  { p | age = 31 }
  let Person { name, age } = p
  ```

  - フィールド付きの構文は、コンストラクタが1つの `data` に限る
  - `p.name` は、その時点で `p` の型が分かっていることを求める。分からなければ型の注釈を求める診断を出す。本体の終わりまで解決を遅らせる仕組みは作らない
  - 射影と更新の線形性の規則 (取り出さない残りのフィールドは `Unr`、上書きされる古い値は `Unr`) は [直積型とレコード](../spec/records.md) から引き継ぐ
  - 更新 `{ p | age = 31 }` は、意味としては不変で、写す。一意な値をその場で書き換えるのは、Perceus の reuse (下の「処理系」) に任せる
  - タプルは構造的なまま残し、`t.0` で射影できるようにする。Unit は 0 要素のタプル `()` である
  - フィールドの配置は translate が決める。名前付きのレコードは、Core IR の配置の表に、コンストラクタが1つの配置として入る ([Core IR とインタプリタ](../spec/core-ir.md) の「データの配置」)
  - row 多相の構造的なレコードは採らない。レコードの row の sort、ネイティブでのオフセットの証拠か単相化、`with` とレイアウトの衝突を持ち込み、ユーザーの instance も書けないためである
- レコード、`List`、`Option`、`Result` に `deriving` を使えるようにする
- 物理的な表現 (ヘッダ、フィールドの並び、文字列の形) は S9 で決める

### 論点

- 文字列のトークンを lexer のモードで分ける。lexer のモードのスタックは、補間のトークンと一緒に設計する。未対応のリテラルの E0004 を1か所で出すかどうかも、そのときに決める
- `{…}` と `[…]` で書くレコードとリストと、レイアウト規則3の関わり。更新は `{ p | age = 31 }` で `with` を使わない
- 借用のオペランドと `Field`。消費しない `switch` と借りたフィールド ([Core IR とインタプリタ](../spec/core-ir.md)) の上で決める
- `::` の fixity
- 補間、レコード、リストの CST

## S7 evidence passing

前提: S4。

[evidence passing の設計](evidence-passing.md) を実装する。

### 決めたこと

- Core IR に row の情報を持たせ、エフェクトのラベルの順序を決める
- EP を、Core IR から Core IR への変換として、translate と box の挿入の間に置く
- EP の出力を、Core IR の下位言語として定める
  - `handle`、`perform`、`resume`、`mask` を含まない
  - evidence と yield の基本操作を、extern の行と同じく Repr の決まった表の形で持つ。box の挿入と Perceus に特別な規則を足さないためである
  - 出力は、既存の命令の種類と上の基本操作だけにする。S8 で LIR に移す作業を機械的にするためである
  - Core IR の verifier に、この下位言語を確かめる段を足す
- 末尾の位置は縮約の定義 ([Core IR とインタプリタ](../spec/core-ir.md) の「縮約」) に合わせ、末尾の位置の呼び出しの後には yield の確認を入れない。末尾呼び出しの保証を守るためである
- T3 と `never` の操作の規則 ([Core IR とインタプリタ](../spec/core-ir.md) の「位置の規則」) を、EP の出力 (`perform` と `resume` が `apply` になった形) に合わせて書き直す
- すぐに再開する節を、継続を取り出さずにその場で実行する
- `never` の中断で、途中の `Lin` の値を破棄する。この中断の経路は、S12 の `try_io` と `exit` も使う
- 操作の宣言した Repr を決める。今はエフェクトの位置を一様にしている ([Core IR とインタプリタ](../spec/core-ir.md) の「位置の規則」)。`perform` の引数と結果、操作の節の引数、`resume` の値を操作のスキームの Repr にする形を、ここで決める。配置の表と同じ考え方で、box の挿入を作ったときの試作では UI で動的な変換を 220,123 回減らす。一方で、エフェクトの表に操作の Repr を、`resume` に操作の名前を、操作ごとの `cont$` を要する。操作の Repr はエフェクトの表に足し、box の挿入は型を読まずにそれを読む
- 開発中は、CEK に EP の基本操作を一時的に足し、変換の有無で UI テストの出力を比べる。RC の回数は変換で変わるので比べない
- 段の終わりに EP を常に通すようにし、エフェクトを直接扱う部分を消す。消すのは、CEK の handler の連鎖と継続の区間と、box の挿入、Perceus、verifier の `perform`、`handle`、`resume` の規則である
- `RunStats` に新しい指標 (evidence を引いた回数、yield が越えたフレームの数など) を足す。今の `handler_visits` は CEK のフレームをたどる回数なので、EP の後は意味を持たない

### 論点

- 「yield 中か」の確認の費用。bind の展開と続きの共有を、translate が作る引数を持つ合流のブロックとどう組み合わせるか
- 開いた row で evidence を探すときのキャッシュ
- `never` の中断で、途中のフレームの `Lin` の値をどう drop するか。yield の経路に drop の命令を生成するか、継続を組み立ててから解放するか

## S8 LIR

前提: S7。

### 決めたこと

- Core IR の下に LIR を置く。境界は EP の直後、box の挿入の前である
  - Core IR は意味の層である。ブロック、Repr、配置、エフェクトの命令を持ち、RC と box は持たない。後の最適化パス (インライン化、jump threading など) も Core IR に置く
  - LIR はエフェクトの命令を持たない。`box` と `unbox`、`dup`、`decref`、`release`、evidence と yield の基本操作を持つ。VM とネイティブの共通の入力である
  - 意味の層と RC と box の層を分けるのは、Lean の LCNF と IR (λRC) と同じ構成である。エフェクトの命令がないことを、verifier の段でなく LIR の型で保証できる
- LIR の型、テキスト形式、パーサ、verifier を作る
- エフェクトのない Core IR から LIR への変換を作る。変換は構造を写すだけで、エフェクトの命令が残っていれば断る
- box の挿入、縮約、Perceus と所有の verifier (R6、R7) を LIR に移し、Core IR から RC と box を消す
- CEK が読む IR を LIR に替える。S7 の後の CEK はエフェクトを持たないので、型の付け替えで済む
- 関数、配置、文字列、extern の、プログラム単位の表を LIR に置く
- 層の分担は次のとおりにする

  | 項目 | 置き場所 |
  |---|---|
  | 変数の Repr | Core IR で決まり、LIR に写す |
  | 配置の表と `internal` の印 | Core IR と LIR で共有する |
  | `mask` | Core IR だけ。EP が使う |
  | extern の位置 | LIR に写す。エラー位置の表に使う |
  | T3、`f$boxed`、一様化 | LIR の規則 |
  | verifier の段 | Core IR (translate の後、EP の後) と LIR (スコープ、所有) |

- Perceus の後の Core IR のダンプは、LIR のダンプになる。期待値の変更として S8 の spec に範囲で挙げる
- `spec/core-ir.md` を、Core IR と LIR の2つの spec に分ける

### 論点

- LIR が配置を足せるか
- `saved` を S10 まで LIR に残す形 (CEK だけが使う)

## S9 共通ランタイム `eml_rt`

前提: S6、S8。

### 決めたこと

- VM とネイティブで共有するランタイム `eml_rt` を作る。値の表現とヒープを共有しなければ、VM とネイティブのコードを混ぜて動かせないためである
- 値は 8 バイトの語にする。`obj` と `tobj` の位置は「ポインタか即値」で、`int`、`enum`、`unit` の変数は生のスロットに置く
- `tobj` の `Int` は 63 ビットの即値にし、収まらない値は box の物体にする。`Int` の意味は 64 ビットのまま変えない
- オブジェクトは、ヘッダとフィールドが続く1つのブロックにする。ヘッダは RC、タグ、記述子を持つ
- 記述子は、静的な型の情報なしにオブジェクトを扱うための方針 (子のたどり方、写せるかどうか、`Lin` の破棄処理) を持つ。データの物体の記述子は、配置の表をもとに作る。たとえば、包んだ `k` を `drop` したときは、継続が捕まえている `Lin` の値の破棄処理を呼ぶ必要がある ([ランタイム](../spec/runtime.md) の「オブジェクトのヘッダ」)
- RC の符号は、0 を RC なし (今の不死の物体)、正を単一スレッド、負を複数スレッド用に予約する。上限に達したカウントは動かさない (Perceus の論文と Lean と同じ)
- 検査モードを持つ。解放した領域を再利用せず、ヘッダに印を付け、確保の台帳で生存を数える。生きているオブジェクトを列挙できるようにする。今の検査付きヒープの役を引き継ぐ
- reuse を後から入れられるようにする。reuse に対応した確保の API (`alloc_at` と token)、検査モードでの再利用の扱い (token による再利用は所有の受け渡しで、解放の後の使用ではない)、ヘッダのタグを書き換える規約を入れる。ランタイムの単体テストで、手で組んだ「解放して、同じ箱でコンストラクタを作る」列を流し、生存の数と RC の釣り合いを確かめる
- extern を語の ABI で1回だけ書く
- 実行文脈 `Ctx` を持つ。割り込みの旗、深さと確保量の上限、yield の印と evidence のベクタ、セッションの根、出力先を置く
- 関数表 `FnEntry` と、追記だけの `CodeBase` (関数、文字列、配置、エフェクト) を、S8 の LIR の表をもとに作る。クロージャは今と同じく関数の番号を持つので、位置に依存しない
- リスト、文字列、レコードの物理的な表現を決める
- `unsafe` は小さい核 (確保、解放、ヘッダ、フィールドの読み書き、`dup`、`decref`) に閉じ、Miri で検査する

### 論点

- 確保器の選定
- 文字列の表現 (一意なときのその場の連結 ([ランタイム](../spec/runtime.md) の「文字列の連結」) を保つ形)
- `Float` を入れたときの語の表現
- SIGINT の受け方
- `box 5` の定数を共有の不死の物体にするか (Lean の `_boxed_const`)

## S10 VM と切り替え

前提: S9。

### 決めたこと

- LIR からレジスタ型のバイトコードを作る。中間に別の IR は挟まない。命令列への変換は1回の走査で済むためである
- レジスタは関数ごとの連続した枠にし、生存区間の彩色でスロットに割り当てる。ブロック引数は並列な代入の `move` の列に展開する
- 算術と比較は extern の行ごとに専用の命令にする。それ以外の extern は、行の番号と引数のレジスタの範囲を持つ命令にする
- 自己の末尾呼び出しは、バイトコードの出力で関数の入口へのジャンプにする。Core IR の R2 は緩めない
- フィールドのない `#N` の行き先では、scrutinee が `tobj` でも即値と分かる。VM は `switch` の配置の ID を見て、その行き先の scrutinee の `decref` をその場で消す。IR の規則にはしない。IR の規則にすると、verifier に「即値と分かっている」という3つ目の状態が要るためである
- 呼び出しと戻りを安全点にし、割り込み、深さの上限、確保量の上限を確かめる。Core IR に後ろ向きの辺がないので、無限に走るプログラムも必ず安全点を通る
- エラー位置の表 (pc から位置) と逆アセンブラを作る
- `eml run` を VM に切り替え、CEK、今の `eml_runtime`、`saved` を消す
- spec を改める。`runtime.md`、`evidence-passing.md` (CEK の役割)、`multicore.md`、`architecture.md`、`testing.md` である

### 論点

- 比較と分岐の融合命令の有無。試作で実行命令数を測って決める
- `RunStats` の各項目の VM での意味

## S11 REPL

前提: S10。

Prelude と `std/` の標準ライブラリと、指定したモジュールを読み込んだ環境で、対話的に実行する。

### 決めたこと

- 入力は、定義の追加か式の評価である。式は、まず row が `<IO>` に収まるものに限る
- 入力をまたいで残せるのは `Unr` の束縛だけで、`Lin` の値はその入力の中で使い切る。今の線形性の検査をそのまま使える
- セッションの根の表を持ち、入力ごとに関数 `input$N` を作る。入力が使うセッションの値は、`input$N` の引数として根から `dup` して渡す。新しい `Rhs` や `Atom` は要らない
- orphan 規則では、セッションを1つのモジュールとみなす。後の入力で定義し直すと、変わるのはそれより後の入力だけである。再定義は、新しい番号の関数と、名前から最新の番号への写像で表す。古いクロージャは古い定義を呼び続ける
- 総称な定義は使われたときに変換し、(定義, 型引数) ごとの instance をキャッシュする
- 定義ごとに IR を保存するので、配置の番号を translate のたどり方によらない正規の順にする。今は translate が最初に使った順に振る ([Core IR とインタプリタ](../spec/core-ir.md) の「データの配置」)
- 定義ごとに IR を保存しても、box の挿入をプログラム全体に走らせ直さずに済む ([Core IR とインタプリタ](../spec/core-ir.md) の「box の挿入」)
  - 後の定義によって変わる ABI は、`f$boxed` を足すかどうかだけである。`f$boxed` は足すだけで、元の関数もそれまでの参照も変えない。ある関数への最初の値の参照が現れた入力で `f$boxed` を足せばよい
  - 内部の関数の一様化は、それを作った定義の中で決まる
  - T3 は、関数の本体と、それが末尾の位置で直接呼ぶ関数の `ret` だけで決まる。呼ぶ関数は前の入力か同じ再帰の組で定義されるので、新しい定義が古い定義の `ret` を変えることはない
- 異常終了と割り込みからは、根からの走査で回復する。根から届くものを残し、届かないものを解放し、RC を数え直す。実行時エラーと割り込みは Perceus の規則の外の中断なので、RC の規則だけでは回復できないためである (レポート2の実験では、CEK で実行時エラーの後に局所変数が残った)
- コード表を更新する区間では、割り込みを保留する
- 結果は S5 の表示のクラスで表示する。表示のクラスを持たない型 (関数、継続) には、型に従う表示器を使う。表示器は深さと要素の数の上限を持ち、表示中も割り込みを見る
- コマンドは GHCi に寄せる (`:load`、`:type`、`:quit` など)
- 入力ごとにプログラム全体を処理し直す費用は小さい (レポート2の測定で、関数 1000 個で約 37 ms)。そのため、増分の lowering は最初の必須条件にしない

### 論点

- シグネチャのない定義を単相にするか、REPL だけ一般化するか
- `IO` 以外のエフェクトを既定の handler で許すか。許すなら、handler のない操作の yield を REPL が受け取る
- 編集したモジュールの読み直し。`:load` で型が変わるときのセッションの値の扱い
- 定義し直した型の表示と、古い値の表示
- セッションの表し方 (1つの伸びるモジュールか、モジュールの鎖か)
- セッションの値への連結は、RC が 2 以上になるので、いつも写しになる。再束縛の後で古い根を手放す順序

## S12 スクリプトの MVP

前提: S11。

S4 を型システムの実験より前に置いていたのは、線形型の負担 (`drop`、線形な値を返して受け渡すこと) が実用で許せるかを、機構を積む前に実際のスクリプトで確かめるためだった。S4〜S11 を先に置いたので、この確かめは S12 と S13 で行う。

### 決めたこと

- IO の失敗は中断として伝え、組み込みの `try_io : (Unit -> <IO | e> a) -> <IO | e> Result IOError a` で捕まえる。中断の途中で捕まっていた `Lin` の値は、`never` の操作の中断と同じく、S7 の中断の経路で後始末する。捕まえなければ、エラーを表示して終了コード 1 で止まる
- `exit : Int -> <IO> a` は、同じ中断で `Lin` の値を後始末してから終了する。`<IO>` を持たせるのは、`par` の子から呼べないようにするためである。`try_io` は `exit` を捕まえない
  - 戻らない extern (`exit`) の結果の Repr は、`never` の操作の `perform` の結果と同じ考え方で扱いを決める。値を返さないので位置として扱わず、box の挿入は受け直さず、T3 は見ず、verifier は比べない ([Core IR とインタプリタ](../spec/core-ir.md) の「位置の規則」)
- ローカルの再帰関数を入れる。`let (f, text) = Fs.read_all f` のような再束縛を壊さないように、引数を持つ関数の形のローカル定義だけを再帰的にする。単相で、lambda lifting する
- Rust で実装した extern の標準ライブラリを入れる。`String` (lines、split、trim、contains、replace、join、to_int)、`Env` (引数、環境変数)、`Stdin`、`Fs` (すでにある `open` などに足す、ファイル全体の読み書き)、`Proc.run`、`eprintln` である。S9 の語の ABI で書く
- CLI は `eml file.em args...` でスクリプトを直接起動できるようにする
- std の extern が名前的なデータ (`List`、`Option`、`Result`) を作るときは、extern の行がその型の正規の名前を持ち、translate がその配置を配置の表に入れる。今の extern が作るデータは、タグの決まった `Bool` と、大きさだけで配置が決まる `Fs.read_all` の組なので、行は配置を持たない ([Core IR とインタプリタ](../spec/core-ir.md) の「データの配置」)

### 論点

- ローカルの再帰関数の構文
- `Stdin` は入力全体と行を読む関数にとどめる。後の「バイト列と `Array`」の `Lin` のハンドルとの関係を決める
- 多相な extern の行の Repr を、std のシグネチャの型とどう比べるか。今の結び付けのテスト ([テスト戦略](../implementation/testing.md)) は、型で選ぶ行を除いて、extern の行のシグネチャに型変数がないことを確かめている

## S13 実例による判断

前提: S12。

S12 で書いたスクリプトの書き心地を見て、次の項目を採るかどうかを決める。

- Kind の宣言化: シグネチャに Kind の境界を書き、段2の Kind 推論を減らす。宣言にするなら、持ち越しの条件付きの制約を書く形が要る。`map`、`fold`、`keep` を注釈なしで書ける今の性質を失わないことを条件にする。あわせて、ユーザーが Kind を書けるようにするか (関数型の線形性 `m` を含む) と、診断で矢印の線形性をどう表示するかを決める。今の診断は、`once` の `k` や `Lin` のクロージャを、ほかの関数と同じ形で表示する
- fixity の宣言をやめ、先頭の文字で決まる固定の優先順位の表にすること。整数の優先順位で、ライブラリ同士の演算子の衝突が問題になった場合の代替案 (Swift 方式の優先順位グループ) も、ここで一緒に判断する
- 字句的な負号 (`f -1` を `f (-1)` と読む。GHC の LexicalNegation と同じ)
- ブロック引数 (末尾の `fn`、`match`、`if`、`handle` を括弧なしで渡す)。`fn () ->` が多い場合のサンクの糖衣も一緒に判断する。今は `use` とセクションで足りると判断している
- 省略した row の暗黙の row 変数 ε: 今は省略した row を `<>` と読む ([型と Kind](../spec/types.md) の「関数型」)。高階関数で row 変数を書く量が負担になるなら、Frank の周囲の ability のように、1つのシグネチャの中で省略した row をすべて同じ暗黙の row 変数 ε とする規則に広げる。`map : (a -> b) -> List a -> List b` が `(a -> <ε> b) -> List a -> <ε> List b` になる
  - 互換の条件: 既存のシグネチャの型が、広げた規則の型の特別な場合 (ε := `<>`) になる形でだけ広げる。そのため、ε を入れるのは row を1つも書いていないシグネチャに限る。row を1つでも書いたシグネチャは、今と同じく省略を `<>` と読む。たとえば `twice : (Unit -> Unit) -> <IO> Unit` の引数に ε を入れると、閉じた `<IO>` の本体でコールバックを呼べなくなり、今は通るプログラムが通らなくなる
  - ε を入れるのはトップレベルのシグネチャだけで、`data` のフィールドの型には入れない。ローカルの型の明示とラムダの引数の型で省略した row は、推論用の row 変数に変えてもよい (型がより一般になるだけなので互換である)
- 中断で終わる経路での `Lin` の値の暗黙の後始末: `never` の操作や `exit` で終わる経路では、生きている `Lin` の値 (`k` を含む) を明示の `drop` なしに後始末する。「通常の制御フローでは暗黙の後始末をしない」原則 ([線形性](../spec/linearity.md)) を広げる変更なので、後始末の処理がエフェクトを起こしたり失敗したりする場合の扱いも決める
- 線形値の受け渡しの糖衣: `Fs.read_all &input` を `let (input, r) = Fs.read_all input` に脱糖する、Swift の `inout` 風の構文。API の返り値の形を縛ることと、巻き上げの規則が課題である
- トップレベルの値を一度だけ評価すること: 今は参照するたびに計算する ([Core IR とインタプリタ](../spec/core-ir.md))。一度だけ評価するのは、単相で `Unr` の値に限る。起動時に評価するか初めて使うときに評価するかと、実行時エラーの報告の仕方も決める。S11 の REPL の束縛は一度だけ評価するので、それと意味を揃えるかも一緒に決める

## S13 の後の言語の項目

### `Float`、`Char`、`Num`

前提: S5。

#### 決めたこと

- `Float` と `Char` の型、リテラル、Prelude の演算を入れる
- リテラルは単相にする。整数のリテラルは `Int`、浮動小数のリテラルは `Float` である。`fromInteger` 相当の脱糖も defaulting も入れない。`Int` と `Float` を混ぜるときは明示的に変換する
- `Char` は Unicode のスカラー値である
- `Float` の Repr と、`eml_rt` の語での `Float` の表現を入れる。型とリテラルより前に入れると、テストできない死んだコードになるためである
- `+ - * < <= > >=` と前置の `-` (`negate`) は `Num` と `Ord` のクラスで解決する。算術は `Int` と `Float`、順序の比較は `Int`、`Float`、`Char`、`String` に使える。何も型を決めないオペランドは、S5 の規則どおり曖昧さのエラーにする

#### 論点

- 型ごとの意味: `Float` の `/` と `%` の有無、`Float` の `==` と NaN の結果、`Float` の `Eq` / `Ord` の法則
- 除算のクラスを instance ごとの小さなクラスにするか、`Integral` / `Fractional` に分けるか。`negate` をユーザーに見せるか
- `Float` をリテラルのパターンと `switch` から外すこと
- 多相な位置での `Float` の表現は、S9 の語の表現の上で決める

### バイト列と `Array`

前提: S5、`Float`、`Char`、`Num`。

`Byte` 型とビット演算、`Bytes`、`Array` を入れる。`Lin` のハンドルと、バッファ付きの読み書きを入れる。

#### 決めたこと

- `Byte` (0〜255) を専用の型にする。ビット演算のクラスと演算子と fixity を Prelude に足し、`Int` と `Byte` で共有する
- `Bytes` は `Unr` の値である。`Array a` の Kind は要素の Kind に従う。どちらも意味は不変で、更新は、RC が 1 ならその場で書き換え、そうでなければ写す。分割と結合、並列の書き換えのための `Lin` の `MutArray` と `freeze` は、後で足す (下の「マルチコア対応」)
- ハンドルは `Lin` にする。`Stdin` / `Stdout` / `Stderr` は別の型にする。バッファ付きの読み書きもハンドルにする。extern は、ハンドルに対する read/write の操作にとどめる

#### 論点

- `Byte` のリテラルの書き方 (リテラルは単相なので、`Byte` を書く形が要る)
- `Byte` の算術のオーバーフロー (実行時エラーか wrap か)
- 範囲外の添字を実行時エラーにするか `Option` にするか
- 中断のときに書き込みのハンドルを flush するか
- `println` と `Stdout` のハンドルの関係。S12 の `Stdin` の関数との関係
- `Lin` の要素を持つ `Array` の API
- マルチコアでのハンドルの扱い

### UTF-8 と標準ライブラリ

前提: バイト列と `Array`。

UTF-8 の核の extern を入れ、標準ライブラリを広げる。`std/` ツリーと最初のモジュール `Fs` はすでにあり、S12 で Rust で実装した extern のモジュールが入っている。

#### 決めたこと

- `String` は常に妥当な UTF-8 である
- UTF-8 の extern は小さい核にとどめる。検証付きのデコード (`Bytes` から `String`)、エンコード、バイト長、バイト位置から `Char` と次の位置を読む操作、境界を検査する切り出しである
- 「行を流す」などのストリーム処理は、ユーザー定義のエフェクトとして、標準ライブラリのモジュールの中に書く
- 書記素クラスタと正規化は対象外にする
- `Fs`、`Path`、`Proc`、`Json` などのモジュールの API を別の spec で決める ([標準ライブラリへの申し送り](stdlib.md))

#### 論点

- S12 で Rust の extern として入れた `String` の関数 (分割、検索、反復など) を、eml で書き直すか
- 位置の単位 (バイト位置を不透明な型にするか)
- 不正な UTF-8 の扱い (エラーか置換か)
- 大文字と小文字の変換など、Unicode の表が要る操作を extern にするか対象外にするか

### コマンドリテラル

前提: UTF-8 と標準ライブラリ。

コマンドリテラルの CST と lexer のモード、標準ライブラリの `Cmd` と `Proc` を入れる。`Proc.run` は S12 で extern として先に入っている。

#### 決めたこと

- コマンドリテラルはシェルを介さず、引数のリストを組む ([字句](../spec/lexical.md) の「コマンドリテラル」)

#### 論点

- コマンドリテラルの CST
- `Cmd` と `Proc` の API ([標準ライブラリへの申し送り](stdlib.md) の `Cmd` の項目)

## その後の項目

段と言語の項目に含めない項目を、分野ごとにまとめる。方針まで決まっている項目と、論点を挙げただけの項目がある。詳しい設計がある項目は、その文書へのリンクを付けた。「前提」は、先に済ませておく段か項目である。前提を書いていない項目は、どの段の後でも着手できる。

### 型システム

- 使い切り必須の型: 捨てることを許さない線形型。ユーザーが Kind を書けるようにする段階で、Kind に「drop できるか」の次元を追加して扱う。前提: ユーザーによる Kind の記述 (S13 で判断する)
- row 要素ごとの捕捉 Kind: `<IO, Async@lin>` のように、row の各要素に「捕まえてよい Kind」を推論で持たせ、`never` / `once` の持ち越し規則をより柔軟にする。マルチコア対応で挙がった「`Heap` を含まない row」の制約も、同じ種類の拡張として扱う ([マルチコア対応の設計](multicore.md))
- 借用: Rust / Austral 方式。意味論の大きな追加になる
- 関数型の部分 Kind による包摂: `Unr` の関数を `Lin` の関数型の場所に渡せるようにする。今は関数型どうしの単一化で線形性 `m` を等しくする ([型と Kind](../spec/types.md) の「関数型」)
- フィールドの関数型の線形性: `data` のフィールドに書いた関数型の線形性は、表面の構文で `m` を書けないので `Unr` に固定している ([型と Kind](../spec/types.md))。線形なクロージャを `data` に入れられるようにするかを見直す。前提: ユーザーによる Kind の記述 (S13 で判断する)
- 操作の引数の Kind 変数: 操作の引数の型に現れる Kind 変数は `Unr` に固定している ([エフェクトと handler](../spec/effects.md) の「handler の意味」)。線形な値を多相な操作の引数で渡せるようにするかを見直す

### 言語機能と構文

- 可変参照 (方針は決定済み): 値 `Ref h a` と組み込みのエフェクト `Heap h` を持ち、`IO` と分離する。`run_heap` は rank-2 の組み込みとして特別扱いする。`Ref` には `Unr` の値だけを入れ、multi-shot で再開したときの状態は共有する ([マルチコア対応の設計](multicore.md) の「可変状態」)。入れ子の `run_heap` の中から外側の `Ref` を使うには、同じエフェクトのインスタンスを区別する必要がある。名前付きの handler が要るかどうかを、入れるときに決める
- 局所的な可変変数の糖衣構文: Koka の `var` のように、関数の中に閉じた可変変数を `Heap` を外に見せずに書けるようにする。前提: 可変参照
- フィールドの変換の糖衣: `{ p | age = _ + 1 }` のような、関数でフィールドを書き換える構文。`Lin` なレコードでも、分解せずに書けるようにする。前提: S6
- 抽象型: コンストラクタを公開しない `pub data`
- 再エクスポート: `pub import`
- 修飾した演算子の構文 (`Csv.(</>)`)
- 接頭辞付きリテラルの一般化: `re"..."` のように、ユーザーが接頭辞付きのリテラルを定義できるようにする。穴の型付けにアドホック多相が要る。前提: S5、S6
- or パターン、ガード、as パターン: パターンを広げる。網羅性の検査 ([網羅性](../spec/exhaustiveness.md)) と決定木の変換を一緒に広げる
- 仮置きの式: どの型にもなる仮置きの式 (typed hole)。入れるときに、網羅されていない `match` と等式の fix (E4001 の枝の追加、E4002 の等式の追加の提案) を一緒に入れる ([診断の出し方](../implementation/diagnostics.md) の「網羅性の診断」)

### 処理系

- インクリメンタル化: 各段階をクエリ (salsa など) に載せ替える。各段階を純粋な関数にしているのはこのため ([コンパイラの構成](../implementation/architecture.md))
- LSP: 診断、hover (型と row の表示)、補完、code action。診断の構造体は、LSP の診断と code action に変換できる形にしてある ([診断](../spec/diagnostics.md))。前提: インクリメンタル化
- ネイティブ化: LIR から Cranelift でネイティブのコードを出す。Core IR のブロックの列とブロック引数は、Cranelift のブロック引数に1対1で写る。VM とネイティブは `eml_rt` の値とヒープを共有し、関数表 `FnEntry` を接続点にして混ぜて動かせる。たとえば、標準ライブラリだけをネイティブにし、ユーザーのコードをバイトコードで動かす。VM からネイティブの関数を呼ぶときは `f$boxed` の一様な入口を使う。`eml_extern` の表は、`eml_rt` の語の ABI の関数になる。前提: S10、`Float`、`Char`、`Num`
  - Cranelift の mid-end は制御フローをほとんど変えないので、jump threading と既知のコンストラクタの畳み込みは Core IR の側で行う
  - ネイティブのコードの中で起きた実行時エラー (オーバーフロー、ゼロ除算) を、評価全体の中断にする方法は未設計である。旗を立てて戻る方式は効果を持たない関数にも確認を足し、巻き戻しは Cranelift のコードに展開情報を要する
- Core IR の上の最適化パス: 既知の閉包への `apply` を `call` に置き換えること、引数が定数の関数の特殊化、純粋な extern の定数畳み込み。EP より前の Core IR に置き、関数単位の作業リストで動かす。枝の部分木を置き換えると、S3b-1 までの `simplify` のように長い `else if` の連鎖で2乗の時間がかかるためである。CPS のラムダの位置の変換 (試作で 200,125 回) は、既知の閉包への特殊化で減らす
- Perceus の最適化: reuse analysis (FBIP)、借用パラメータ。どちらも LIR の上のパスで、消費しない `switch` と `release` の上に、IR を作り直さずに足す。reuse の確保の API と検査モードでの扱いは S9 で入れてある。足すときは次の約束を守る
  - reuse は、`release` を `release_reuse` に、それが空けた箱を使う `con` を `con@token` に書き換えて入れる (Lorenzen と Leijen の drop-guided reuse と同じ方向)。reuse のトークンは `save` に入れない。入れると、複数回の再開が同じ箱に2つの値を作るためである
  - 借用パラメータ: 1つの呼び出しでは、所有の引数を消費した後で借用の引数を確かめる。`save` に借用の部分を足し、R7 は所有の部分だけを所有の多重集合と比べる。フレームの解放と `copy_segment` は借用の部分を数えない。借用のブロック引数は持ち主 (同じブロックの引数か関数の入口) を宣言し、verifier は辺ごとに確かめる
    - 所有の都合で `TailCall` を `let r = <呼び出し>` と `return r` に降格するのも、借用パラメータと一緒に入れる。S3b-2b でフィールドは呼び出しより前にすべて所有になったので、借用パラメータを入れるまで降格は起きない。Perceus は、終端を文と新しい終端に置き換える編集をその場でできる形にしてある
    - 降格は、末尾の位置の呼び出しの輪の上の `tail` には当てない ([Core IR とインタプリタ](../spec/core-ir.md) の「変換の規則」の末尾呼び出しの保証)。借用の推論は、輪の上の `tail` が渡す引数の仮引数を所有にして、降格を避ける (Lean の `ownParamsUsingArgs`)。降格してよいのは、輪の上にない末尾呼び出しだけである
    - extern の行に、引数ごとの所有と借用の列を足すのも、借用パラメータと一緒に入れる
    - 部分適用される関数は借用を持てないので、所有の版の包みが要る (Ullrich と de Moura)。`f$boxed` との合成を、借用を入れるときに決める
  - 借用の推論では、同じ配置の `con` を作る行き先を持つ scrutinee を所有にする。reuse の機会を残すためである
  - フィールドを死ぬ所で手放す形 (遅らせる形): 今の Perceus は、case の行き先の入口でフィールドを `dup` するか `release` する。そのため入れ子のパターンでは、フィールドを `dup` してから読むだけの所が残る (UI のプログラムで7か所)。借りた変数への `switch` を使い、経路ごとに分解した値が死ぬ最初の所で `dup` か `release` を置けば、この `dup` を省ける
    - `unbox` の後の `decref` と、型変数のフィールドで増える `release` も、この形で減らせる。box の挿入を作ったときの試作では、静的な `unbox` 197 個のうち 195 個の後に `decref` が付き、UI の `release` は 50 から 65 に増えた。`unbox` は読む使いなので、`release` の前にまだ借りているフィールドも `unbox` で読める
  - Core IR の変数は Kind を持たず、RC の対象の Repr (`obj` と `tobj`) の変数はすべて Perceus の対象になる。`File` も RC で数え、`read_all` と `close` は一意性を求めないので正しく動く。`Lin` の変数を Perceus の対象から外すかと、静的に一意と分かる `Lin` の値の `release` で共有の側を省くかを、借用と reuse と一緒に決める。どちらも健全なのは、分解した値とその祖先が分解の所で死んでいるときか、遅らせる形でフィールドの `dup` をなくした後だけである。後の行のパターンが分解した値かその祖先を束縛すると、分解した `Lin` の値は分解の後も生きていて、そのフィールドも `File` のような `Lin` のものを含めて `dup` される ([Core IR とインタプリタ](../spec/core-ir.md) の「値の表現」)
  - FP² (Lorenzen、Leijen、Swierstra) の `fip` のような、確保なしで動くことの静的な検査を置くかは、`multi` の継続が同じ値を共有しうる点との相性を確かめてから決める
- すぐに再開する handler の最適化: 節が `k` を末尾で1回だけ呼ぶ場合に、継続を取り出さない直接の呼び出しにする ([evidence passing の設計](evidence-passing.md) の「すぐに再開する節」)。S7 で入れる
- ループ化 (後ろ向きの辺): 自己末尾呼び出しを、関数の中のブロックへ戻る `jump` にする。トップレベルの関数を呼び出し元のブロックにする contification も同じ枠で扱う。今は辺がすべて番号の大きいブロックへ向かう ([Core IR とインタプリタ](../spec/core-ir.md) の「構造の規則」の R2)
  - 入れる時期: S10 の VM は、自己末尾呼び出しをバイトコードの出力で入口へのジャンプにするので、IR の R2 を緩めずに済む。R2 を緩めるのは、ループの中で変わらない値の移動や、ループの頭のブロックの引数を借用として扱う Perceus の拡張が要るときにする。借用パラメータかネイティブ化に着手するときに一緒に入れる
  - 残りの作業: R2 を、ループの頭への後ろ向きの辺だけを許す形に緩めることと、変換にループ化を足すこと。ブロックはすでに複数の引数を持てる
  - 生存解析、縮約、verifier は、辺がすべて前向きであることを使って1回のループで済ませている。ループ化では、ループの頭に印を付け、そこだけ不動点を計算する。支配木の計算も、後ろ向きの辺を含む形に広げる
- jump threading とインライン化: 呼び出しの結果に対する case-of-case と、translate の後に現れる case-of-case は、今は扱わない。インライン化を入れるときに、ブロックの引数を通した既知のコンストラクタの jump threading として一緒に入れる。インライン化の後で初めて、呼び出しの結果が既知のコンストラクタになるためである
  - インライン化は Core IR の上で EP の前に置き、`tail`、`box`、`unbox` を出さない。box の挿入がプログラム全体の ABI と変換を1か所で決め、縮約が末尾呼び出しを作るためである ([Core IR とインタプリタ](../spec/core-ir.md) の「box の挿入」)。Prelude の `|>`、`>>`、`<|` のような普通の関数の合成子も、インライン化で展開する
  - 規則: `jump M(a)` の行き先 `M(p)` が `switch p` か `unpack p` で始まり、`p` をほかで使わず、`a` が `Tag` や `Int` の定数か、`let` で束縛した `con L #k(fs)` なら、`switch` を `jump` の側で決める
  - R3 を守る作り方: 選ばれる case の行き先 C を、辺のブロック `C: jump N(f')` と、元の本体を持つ合流のブロック `N(フィールド)` に分け、`jump N(fs)` へ付け替える。パスの終わりに番号を1回振り直し (R2)、届かなくなったブロックを消す
  - 最初の段は、合流のブロックの引数の展開である。すべての入る辺が、コンストラクタが1つだけの型の既知の `con` を渡し、`M` が `unpack p` で始まるなら、`p` をフィールドの引数に置き換えて `unpack` を消す。ブロックは増えず、R2 と R3 にも触れない。`if` や `match` を通るタプルを受ける形 (状態を回すループでよく出る) は、これで覆える
  - S3b-1 までの `simplify` が行っていて、S3b-2a の translate が行わない書き換え (値を渡すだけの合流のブロックの転送、枝の中でタグの分かった scrutinee をそのタグに置き換えること、引数が2つ以上で返すだけのブロックのたたみ込み) も、ここで一緒に考える
- 実行時エラーの backtrace: S3b-2a で、extern の呼び出しの中で起きた実行時エラーに位置を付けた。呼び出しの連なり (backtrace) と、位置のない誤り (extern の外で起きたヒープの誤りや内部の誤り) の利用者向けの表示を、その後に足す。VM では、S10 のエラー位置の表の上に作る
- HIR の位置を source map に移す: HIR のノードが `TextRange` を直接持つ形をやめる。位置を別の表に分けると、編集で位置だけが変わったときに HIR を作り直さずに済む。この利点はインクリメンタル化 (salsa) に載せ替えるまで効かないので、そのときに移す
- フォーマッタ: CST がロスレスなので、その上に作る。前提: コマンドリテラル (本番の構文がそろってから)
- n 列の `match`: 今は決定木の列に、最初の行でコンストラクタ、タプル、リテラルのどれかのパターンを持ついちばん左の列を選ぶ ([Core IR とインタプリタ](../spec/core-ir.md))。行列によっては部分木が大きくなりうる。今の選び方でも決定木は正しいので、部分木の大きさが問題になる例が出てから列の選び方を見直す
- doc comment: trivia の付け方を決める。doc comment を解釈するドキュメント生成と LSP の hover ([字句](../spec/lexical.md)) がまだないので、それを作るときに、使う側に合わせて決める。前提: LSP
- JIT (投機的): バイトコードから機械語を安く作る copy-and-patch や、トレース JIT。VM が安定し、起動時間が支配的になってから検討する。トレース JIT はバイトコードにスタックのスタックを持たせる別の道で、evidence passing とは前提が合わない。前提: S10、ネイティブ化

### マルチコア対応

詳細は [マルチコア対応の設計](multicore.md) にある。VM はシングルスレッドにし、並列化はネイティブのランタイムだけで行う。VM では、`par` の子を順に実行し、`spawn` は決まった順で動くスケジューラで動かす。主な項目は次のとおり。

- 共有の印方式の RC
- データ並列に限った `par` の段階的な拡張 (a1 → a2-wait → a2-cancel)
