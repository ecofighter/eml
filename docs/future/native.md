# ネイティブ化の設計

位置づけ: 将来の設計。

LIR から Cranelift でネイティブのコードを出す設計をまとめる。ネイティブ化は実装していない。VM は参照の実装として残り、検査モードを持つ実行系は VM だけである。複数のコアで動かす仕組み (worker、スケジューラ、スレッドをまたぐ RC) は [マルチコア対応の設計](multicore.md) にあり、この文書はそのうちネイティブのコードに関わる所だけを書く。

## 目的と範囲

- 完了の条件: 実用的なプログラム (`tests/ui/run/scripts/` のスクリプトのような文字列の処理と、数値計算の計測) で、Python 3.14 の1.5倍以下の実時間になること。今の比は [計測の基準](../implementation/benchmarks.md) の「今の数値」にある。VM では、素のループは CPython より速いが、Python が C で書かれた組み込みの関数に任せる処理には届かない ([計測の基準](../implementation/benchmarks.md) の「1バイトずつ回すループ」)。extern は本当に必要なもの (OS や Host に触れるもの、文字列の表現に触れる核、eml で書くと計算量の桁が悪くなるもの) にとどめ、この条件はネイティブ化で満たす。ネイティブにしたときの見込みは [計測の基準](../implementation/benchmarks.md) の「Cranelift のコードと Rust の1回の走査」にある。確保の多い `logstat` は測っていないので、借用パラメータ ([ロードマップ](roadmap.md) の「段の列」) と reuse (同じ文書の「処理系」の Perceus の最適化の項目) の効果を見て詰める
- 目標: `tests/ui/run/scripts/` の `wc`、`grep -n`、`logstat`、`csv2jsonl` で、同じ出力を返す Rust の版の約2倍以内の実時間にする。Rust の版は eml の版と同じ手順 (走査の回数、標準ライブラリの操作、同じ計算量のデータ構造) を標準ライブラリだけで書いたもので、`bench/scripts/rust/` に置く。測り方は [計測の基準](../implementation/benchmarks.md) の「C/Rust との比べ方」にある。上の完了の条件は変えない。今の入力では、4本でこの目標を満たせば Python の1.5倍の条件も満たす。`csv2jsonl` は欄ごとに新しい文字列を作る今の書き方では届かない見込みである。2倍を超えた行では原因 (1バイトずつの呼び出し、RC、確保、写し、境界と桁あふれの確かめ、ベクトル化の有無、読み込み) を計測の基準に記録する
- コンパイルの条件: JIT は std と 1000 行のプログラムを release のビルドで 300 ms 未満でコンパイルする
- 範囲: コード生成器、呼び出し規約と入口、中断と実行時エラー、安全点とスタック、extern の入口、展開、生の要素の配列、並列の実行、AOT と配布、テスト
- 範囲の外: 利用者の `extern "C"` の宣言と型の対応、GUI のプラグイン。これらはネイティブのバックエンドなしに VM の上で動く。Cranelift で作るのは、VM から C の関数を呼ぶ橋渡しの関数だけである。この文書は、ネイティブのコードがそれらを呼ぶ所だけを書く。宣言と型の対応とプラグインの設計は [FFI と拡張の設計](ffi.md) にある

## 確定した設計判断

| # | 領域 | 決定 |
|---|---|---|
| 1 | コード生成器 | コード生成器は1つで、開いた後の LIR を CLIF にする crate `eml_native` である。JIT (`eml run --native` と REPL。`cranelift-jit`) と AOT (`eml build`。`cranelift-object`) の両方が、同じ CLIF と同じ `eml_rt` の入口を使う。`eml_native` は `eml_rt`、`eml_lir`、`eml_sched`、Cranelift に依存し、入口の stub と、FFI の橋渡しの関数を作る部分を持つ |
| 2 | コンパイルの単位 | プログラム全体 (利用者のモジュールと、届く std) を、Core IR の最適化の後で一度にコンパイルする。`eml run --native` は始めに、REPL は入力の境目ごとに、その入力が足す関数をコンパイルする。どちらも worker が動いていない間に行う。関数ごとに遅れてコンパイルする stub は置かない |
| 3 | VM との関係 | VM とネイティブのコードは混ぜない。ネイティブのコードはバイトコードを呼ばず、バイトコードもネイティブの eml の関数を呼ばない。VM は参照の実装で、検査モード (`--debug-heap`) を持つ唯一の実行系である。ネイティブは `eml_rt` を速いモードで具体化する。バックエンドを作る途中は、扱わない形を含むプログラムを E0004 で断る。断る形の一覧は空になるまで減らし、仕上がったバックエンドは何も断らない |
| 4 | 呼び出し規約 | eml の中の呼び出しは Cranelift の `tail` 規約で、末尾呼び出しは `return_call` と `return_call_indirect` である。extern と C の関数は OS の既定の規約で、`tail` のコードから普通の `call` で呼ぶ |
| 5 | `ctx` | `ctx: *mut Ctx` は、すべての eml の関数とすべての extern の最初の引数である。スレッドに局所的な変数は使わない |
| 6 | 中断 | 中断 (`never` の操作、`try_io` が捕まえる IO の失敗、`try_panic`、`exit`) は戻り値で伝える。巻き戻しの地点ごとに旗を1回確かめ、yield の確かめと一緒にする |
| 7 | 実行時エラー | 評価全体を止める誤りは、自前の setjmp と longjmp の組 (`eml_enter` と `eml_fatal`) で入口まで切る。後始末はしない。extern の失敗は `Ctx.fault` で返す |
| 8 | 安全点 | 関数の入口とループの後ろ向きの辺で、止めるビットとスタックの限度を確かめる。ネイティブのタスクは `Async` の操作でだけ切り替わる |
| 9 | スタック | eml のコードを動かすスレッドは、スタックを明示して予約する。worker のスレッドの既定は 1 GiB の仮想の予約で、`--stack-size` で変えられる。メインの worker ([マルチコア対応の設計](multicore.md) の「スレッドと worker」) だけは、OS の既定のスタックで動く |
| 10 | 使い回しの鍵 | ネイティブのコードを使い回す単位は関数1つで、鍵は名前と、開いた後の LIR と、それが指す形と配置の中身のハッシュである |
| 11 | 生の要素の配列 | 新しい物体の種類 `Raw` (番号 6) に `Float` と `Int` の要素を生の 8 バイトで並べる。要素の読み書きは呼び出しにせず展開する |

## IR の層

- LIR のブロックの列とブロック引数は、Cranelift のブロック引数に1対1で写る。多相な位置の `Int` は語の表現 ([オブジェクトモデル](../spec/object-model.md) の「語」)、`Float` は `float` の位置では生の 64 ビット、`tobj` では箱という表現を前提にする。VM とネイティブは `eml_rt` の値とヒープの形を共有する。`eml_extern` の表は、`eml_rt` の語の ABI の関数になる
- 型で分けた Core IR と LIR、1対1の `to_lir`、今のパスの順番を保つ ([Core IR](../spec/core-ir.md) の「実行系の方針」)。1つの IR にまとめると、約9つのパスに届かない命令の枝が要り、減る行 (`to_lir` の約150行、Core IR の生存解析の約70行と末尾の位置の判定の約50行) より増える行が多い。そのため、次の重複は分かったうえで残す。構造体にする型を決める2つの道が `MAX_STRUCT_WORDS` を共有すること、推移的でない Repr の互換、スカラーの箱、2つの生存解析と2つの末尾の位置の判定 (EP が Core IR の上のものを要る)、Core IR と LIR のテキストの形が同じであること (共通の右辺の読み書きは `eml_lir::syntax` の部品を使う)、`eml_lir::check` を共有する2つの verifier である。ネイティブのバックエンドが LIR のほかの形を要るときに見直す
- コード生成は関数の開いた後の LIR と、それが指す配置だけを読む。extern の行には記号の名前で届く

## 呼び出し規約と入口

- 開いた後の LIR は構造体を葉の変数の並びとして持ち ([LIR](../spec/lir.md) の「開く」)、葉はそのまま Cranelift の値になる。葉はどれも 8 バイトで、`float` の葉は浮動小数のレジスタに、ほかは整数のレジスタに載る。複数の値の戻りは eml の中の規約で、extern や C の境目を越えない。結果がレジスタに収まらなければ、バックエンドが呼ぶ側の用意した領域で返す。スタックで渡す引数が呼び出し元より多い関数への `return_call` も、`tail` の規約で出せる。コード生成は5つのターゲット (`aarch64-apple-darwin`、`x86_64-unknown-linux-gnu`、`aarch64-unknown-linux-gnu`、`x86_64-pc-windows-msvc`、`aarch64-pc-windows-msvc`) で確かめてあり、実行は macOS の上で確かめてある
- 末尾の位置の呼び出しは、結果の Repr が呼び出し元の結果と互換なときだけ末尾呼び出しになる ([LIR](../spec/lir.md) の「末尾の位置の呼び出し」)。結果を変えるフレームがないので、Cranelift の `return_call` をそのまま使える。`return_call` は両側に末尾呼び出しのできる規約を要るので、eml の中は `tail` にする。1つの関数の中で `tail` の呼び出しと OS の既定の規約 (`system_v`、`apple_aarch64`、`windows_fastcall`) の呼び出しは並べられる。C の関数に `tail` の関数のポインタは渡さない
- 関数の ABI は開いた後の引数と `rets` と `split` で決まり、関数の値の捕まえた値より後ろの引数と結果はいつも一様な語である ([LIR](../spec/lir.md) の「関数の ABI」)。`apply` は引数の数だけを比べ、実行時に Repr を変えない ([VM](../spec/vm.md) の「呼び出しと戻り」)。そのため、ネイティブの関数の入口は、関数と、クロージャの捕まえた値の数 k の組で決まり、シグネチャごとの入口や変換の遅い道は要らない。k で入口が分かれるのは、部分適用で k が変わり、クロージャから入るときに捕まえた値を Repr ごとに読んで引数に置くためである ([オブジェクトモデル](../spec/object-model.md) の「クロージャ」)。VM の `RetN` が戻り先の直前の命令を読むのは VM の中だけの約束で、ネイティブのコードは VM と混ぜないので、境目の入口は要らない
- 関数の値の呼び出し規約では、次の案を採らない。実行時に Repr を変える規約にしてフレームの合成を Cranelift に任せる案は、複雑さが残る。すべての関数の値を薄い包みにする案は、末尾呼び出しの保証を失い、2^27 語の `DepthLimit` に届く。値として使うすべての関数に `$uniform` を作る案は、値として生まれる関数の一様さを複製で作り直すことになる。結果の変換の種類ごとに版を作る案は、呼ぶ場所のシグネチャごとに版が要り、合成の問題が戻る。すべての関数の結果を一様にする案は、`Float` を返すたびに確保する
- Rust から eml に入る口は `eml_enter(ctx, fnptr, argv, argc) -> Status` で、ISA と ABI ごとに asm の stub を1つ置く (x86_64 の SysV、x86_64 の Win64、AAPCS64 の3つ)。stub は SP、FP、呼ばれる側が保存するレジスタを `Ctx` の中の `JmpBuf` に保存する。`JmpBuf` は1つ前のものとつながり、入口は入れ子にできる。stub は Cranelift が作る `tail` の adapter `enter$k(ctx, argv)` を呼び、adapter は (関数, k) の入口の引数を `argv` から読んで関数へ `return_call` する。戻ったら結果の語を写す。`Status` は Ok (結果の語) か Fatal である。OS と CRT の setjmp は使わないので、Windows の SEH はこのフレームを見ない
- stub が保存するレジスタは、SysV の x86_64 では rbx、rbp、r12〜r15、Win64 ではそれに rdi、rsi、xmm6〜xmm15 を足したもの、AAPCS64 では x19〜x28、x29、x30、d8〜d15 である。足りないと、致命的な誤りの後に Rust の局所変数がおかしくなる。3つの OS の run-fail の UI テストがこれを確かめる

## 中断と実行時エラー

VM は中断を、コード生成が作る呼び出しの位置ごとの表でタスクのスタックを巻き戻して行い、実行時エラー (オーバーフロー、ゼロ除算) は巻き戻さずに評価全体を止める ([VM](../spec/vm.md) の「巻き戻し」と「中断と実行時エラーの分担」)。ネイティブも同じ分担にする。中断は表を実行時に引かず、巻き戻しの行を冷たいブロックの後始末のコードにして戻り値で伝える。実行時エラーは自前の longjmp で入口まで切る。

### 戻り値で伝える中断

- LIR の巻き戻しの地点 (`eml_lir::unwind::points`。中断しうる関数の末尾でない呼び出し、末尾でない `apply` と節の呼び出し、`Pure` でない extern、`prim yield_abort`。[LIR](../spec/lir.md) の「巻き戻しの地点」) の後に、`ctx.yielding.target` を読み、`()` でなければ冷たいブロックへ分岐する。yield の地点でもある位置では、これは LIR がすでに求める確かめ (`prim yielding()`) なので、何も足さない
- 冷たいブロックはその地点の `UnwindPoint` の行と、yield の遅い道から作る。`yield_status(ev)` で次のどれかを決める
  - この地点の `landing` の evidence に向かう中断なら、結果の変数にダミーの値を書き、普通の道を続ける。VM の着地と同じである
  - ほかの中断なら、`owned` の変数を数の分だけ `decref` し、token を `drop_token` し、ダミーの値を返す。呼び出し元の確かめが同じことをくり返す
  - yield なら、今の κ を作る遅い道に進む
- `prim yield_abort` は状態を書いてダミーの値を返す。入口の adapter まで届いた中断は、中断の状態を立てたまま Ok (ダミー) を返す。Rust の側は VM の `Finish` と同じく終える (`exit` の終了コード、`yield_finish`、`evv_set(())`)
- 費用は巻き戻しの地点ごとに読み込み1つと比較1つである。下の「タスクごとの上限」のため、末尾でない呼び出しの位置はどれも巻き戻しの地点になり、yield の地点でない位置には確かめが1つ入る。効果を持たない関数の中の呼び出しも同じである。効果を持たない関数で起きる実行時エラーは、旗でなく下の longjmp で扱う

### extern の失敗

- `Pure` でない extern はその `extern "C"` の包みへの普通の `call` である。包みは結果の語を返し、失敗を `#[repr(C)]` の新しい欄 `Ctx.fault` (種類の語が先頭) に書く。`Fault` を戻り値から外すのは、Windows の x64 が整数のレジスタ1つでしか返さず、`Result<i64, Fault>` が 24 バイトになるためである
- 呼び出しの後で `ctx.fault` の種類を読み、0 でなければ冷たいブロックへ分岐する。冷たいブロックは今の `eml_vm::vm::failed` と同じことをする。種類 (`Panic`、IO、致命的) を分け、`ev_find` で handler を探す。なければ `eml_fatal` を呼ぶ。あれば、節の入口を節の ABI で失敗の引数とともに呼び (入口は `yield_abort` をしてダミーを返す)、上の中断の冷たい道へ進む
- handler のコードには分岐だけで届く。後始末のブロックは巻き戻しの地点ごとに1つで、失敗の道と中断の道が共有する
- `par` の子の中では、子の `evv` は空で、evidence を探すと印の evidence が返る。冷たいブロックは VM と同じ規則で、印の evidence から `fork$` の節へ進む

### 評価全体を止める誤り

- オーバーフロー、ゼロ除算、捕まらない `Panic` と IO の失敗、ヒープの誤り、割り込み、上限は、`eml_fatal(ctx, code) -> !` で扱う。`eml_fatal` は `Ctx` の中のいちばん内側の `JmpBuf` へ自前の longjmp をし、呼ばれる側が保存するレジスタと SP と FP を戻して、`eml_enter` から Fatal を返す
- フレームごとの後始末も、表も、展開の情報も、Cranelift の例外の仕組みも使わない。VM と同じく、ヒープは落とすか回復する
- 誤りの起きた所と入口の stub の間にあるのは `tail` のフレームだけである。extern は失敗を投げずに返し、extern の中の Rust の panic はどの包みでも `catch_unwind` で捕まえて失敗にする

### タスクごとの上限

タスクごとの深さ、スタック、メモリの柔らかい上限を入れると、すべての安全点と、末尾でないすべての呼び出しの位置が巻き戻しの地点になる。タスクの中で深さかスタックの上限を安全点で超えたとき、またはメモリの柔らかい上限で選ばれたときは、そのタスクの IO の失敗 `ResourceLimit` を起こし、上の戻り値の道で巻き戻す。ネイティブのコードでは yield の地点でない末尾でない呼び出しの位置ごとに、旗の確かめが1つ増える。この費用は受け入れる。メモリの硬い上限は今と同じく評価全体を止める。

`Wake.Cancelled` で取り消しを受けたタスク ([VM](../spec/vm.md) の「取り消しの届け方」) は、普通の起こしと同じ入口からネイティブの入口の stub を通って再開する。止めるビットも longjmp も使わない。

## 安全点とスタック

- 安全点は関数の入口とループの後ろ向きの辺に置く。worker の止める語 ([マルチコア対応の設計](multicore.md) の「スレッドと worker」) とスタックの限度を読み、止めるビットが立っているか、SP が限度より下なら冷たいブロックへ分岐する。SP は CLIF の `get_stack_pointer` で読む
- 冷たいブロックは止めるビットなら `eml_fatal` を呼ぶ。スタックの限度を超えたときは、`Async` のタスクの中ならその安全点でタスクの IO の失敗 `ResourceLimit` を起こし、戻り値の道で巻き戻す (上の「タスクごとの上限」)。タスクの外では評価全体を止める `DepthLimit` として `eml_fatal` を呼ぶ
- `PREEMPT` は、ネイティブの確かめでは定数の AND で隠す。ネイティブのタスクは `Async` の操作でだけ切り替わり、安全点はスタックと止めるビットのためにあって、時間の配分のためにはない。VM は `PREEMPT` を、タスクを渡すときに消す。`Control`、SIGINT、EINTR の扱いは VM と同じである ([VM](../spec/vm.md) の「上限と割り込み」)
- eml のコードを動かすスレッドは、スタックを明示して予約する。worker のスレッド (worker 0 と、別に作るスレッドの専用の worker を含む) は既定で 1 GiB の仮想の予約で、`--stack-size` で変えられる。Linux で `vm.overcommit_memory=2` のときは小さい値を使うよう文書に書く。`main` のタスクはプロセスのメインスレッドの 8 MiB のスタックでなく、大きいスタックで作る worker 0 のスレッドで動く。例外はメインの worker ([マルチコア対応の設計](multicore.md) の「スレッドと worker」) で、OS の既定のスタックで動き、下の限度で深い再帰を止める。ブロックする呼び出しのプールのスレッドは eml のコードを動かさないので、OS の既定のスタックで足りる
- 限度は `ctx.stack_limit = stack_base + 1 MiB` である。eml のフレームの大きさは LIR の verifier のフレームの上限 (VM では `u16::MAX` 語 = 512 KiB。ネイティブのフレームはこれより大きくならない) で抑えられ、`eml_rt` の Rust の extern はスタックで再帰しない (解放は明示したワークリストで行う) ので、1 MiB で eml のフレーム1つと任意の extern が収まる
- ページより大きいフレームにはその場で stack probe を入れる (`probestack_strategy=inline`)。Windows で要り、ほかの OS でも害がない
- ネイティブでは `max_depth` を使わず、スタックの限度で深さを止める。タスクの外で止めるときの誤りの文は `DepthLimit` のままにする
- `Ctx` は、ネイティブのコードが決まったオフセットで読む `#[repr(C)]` の欄を持つ。`yielding` (今もある)、`fault`、worker の止める語へのポインタ、`stack_limit`、`jmp: *mut JmpBuf`、`worker` である。オフセットは今の `YieldState` と同じくテストで確かめる

## extern の入口

- extern の C ABI の入口 (`extern "C"`) は、この設計で足す。今の extern は、引数がどれも 64 ビットの語で数が決まっているので、そのまま移せる。Host と読み手は panic しうるので、どの包みも入口で `catch_unwind` する。`extern "C"` を越える panic はプロセスを落とすためである。包みは失敗を `Ctx.fault` に書き、語を1つ返す ([オブジェクトモデル](../spec/object-model.md) の「extern」)
- `eml_rt` の行の `extern "C"` の包みと、VM の `match` の枝は、表から1つのマクロで作る。std の行を足すときに書くのは、今と同じく表の行と `Ctx` のメソッドと std の宣言で、どちらのバックエンドにも手で書くコードは増えない
- 表の行は失敗を返しうるかを表す `faults: bool` を持つ。`Fault` を返す `eml_rt` の行は true、利用者の C の行は false である。`may_abort` と `points` は失敗を返さない extern を巻き戻しの地点に数えない。そのため、`blocking` でない利用者の C の関数の呼び出しには失敗の確かめも後始末のブロックもなく、普通の `call` になる。`blocking` の C の行は `<IO, Async>` を要し、ブロックする呼び出しのプールへの受け付けと待ちと取り出しに下ろすので、普通の `call` にならない ([FFI と拡張の設計](ffi.md) の「効果と中断の分類」と「長く走る呼び出し」)。プラグインの行は普通の表の行なので、ほかの行と同じ包みを通る ([FFI と拡張の設計](ffi.md) の「拡張」)
- 巻き戻しの地点の出どころは `points` だけである。コード生成は断った関数を受け取ったら panic する

## 展開と最適化の前提

- 前提は借用パラメータ ([ロードマップ](roadmap.md) の「段の列」) である。所有の引数で1バイトごとに `dup` する形と展開した形の差が、2倍の目標までの差で、これは LIR の変更なので VM で先に測れる
- 目標には、`String` と `Bytes` を1バイトずつ読む行の展開 (呼び出しにせず、長さの読み込みと範囲の確かめとバイトの読み込みにする) が要る。読む行はすでに引数を借り ([LIR](../spec/lir.md) の「extern の借用」)、VM では専用の命令になる ([VM](../spec/vm.md) の「基本操作と extern」)。`wc` の内側のループを Cranelift で書いた試作を、同じ1回の走査で書いた Rust (LLVM) のループと比べると、展開した形が約1.5〜1.7倍、借用した extern を呼ぶ形が約2.2〜2.6倍、所有の引数で1バイトごとに `dup` する LIR の形が約3.7〜4.0倍だった。数は [計測の基準](../implementation/benchmarks.md) の「Cranelift のコードと Rust の1回の走査」にある
- ネイティブのバックエンドが頼る要件は次のとおりである。借りた `String` と `Bytes` の i 番目のバイトは中身の先頭から i の位置にあり、中身の先頭と長さは借りるごとに1回読めばよいので、ループの外に巻き上げられる ([オブジェクトモデル](../spec/object-model.md) の「バイト列と文字列」)。1バイトを読む行の展開は、長さの読み、符号なしの比較1つ、`Panic` への冷たい分岐、バイトの読みである。`String.char_at` の展開も、バイトの読みまでは同じである。読んだバイト `b` が `0x80` より小さければ結果は `b` で、そうでなければ冷たいブロックへ分岐する。そこでは、続きのバイトなら `Panic` を起こし、先頭のバイトなら残りのバイトを読んで文字を組み立てる。その場の更新は、所有した rc 1 の値だけに行い、借りた値と共有の値は書き換えない。これが中身の先頭と長さの巻き上げを正しくする。桁あふれと範囲の確かめは、どれも比較1つと冷たいブロックへの分岐になる
- `Array` と `MutArray` の要素の読み書きも同じ形で展開する
- 巻き上げにループ化 ([ロードマップ](roadmap.md) の「処理系」のループ化の項目) は要らない。自分への `return_call` は機械語ではすでにループである。測ったループが回るたびに中身の先頭と長さを読み直すせいで目標に届かないときだけ、ループ化を入れる
- Cranelift の mid-end は制御フローをほとんど変えないので、jump threading と既知のコンストラクタの畳み込みは Core IR の融合が行い ([Core IR](../spec/core-ir.md) の「既知のコンストラクタ」)、Cranelift の mid-end に頼らない
- 範囲の確かめを消す最適化は、この設計の範囲の外にする

## 生の要素の配列

- 型は `Std.FloatArray` (`Unr`) と `Std.MutFloatArray` (`Lin`)、`Std.IntArray` と `Std.MutIntArray` である。API は `Array` と `MutArray` と同じ (`make`、`length`、`get` と `read`、`set` と `write`、`freeze` と `thaw`、`tabulate`、`from_list`) で、`copy_slice`、`concat`、`fill` を足す。要素は 8 バイトで、バイトの配列は作らない (`Bytes` がある)。`Array a` は要素が走査する語なので、今の `Data` の形のままにする
- 物体の形は新しい種類 `Raw` (番号 6) である。生の語 0 が要素の数で、その後に生の 8 バイトの要素が並ぶ。`scan = 0` で、`String` と `Bytes` と同じく `raw` と `set_raw` からは中身が見えない。要素の型は静的に決まるので、`Float` と `Int` の配列は種類を共有する
- `eml_rt` の中では、回復は `String` と同じく生の語を写し、`share` は子がないので O(1) で印を付け、`freeze` は受け付け、`foreign` と `unbox` は `WrongKind` で断る。検査モードは中身を不透明に扱う。`arrays.rs` の Verus の仕様に新しい種類を足す。VM の操作は extern で、新しい命令は作らない
- `Mut*Array` は `Lin` で、型付けにより rc はいつも 1 である。`write` はいつもその場で書き、ネイティブの展開した `write` も rc 1 を前提にする (速いモード。VM の検査モードは、今の `MutArray` と同じく一意であることを確かめる)。`FloatArray.set` は `is_unique` でなければ写す。`thaw` は一意でなければ写して `lin` ビットを立て、`freeze` は消す。`lin` ビットを立てるのは `make` と `thaw` で、この種類の `Mut*Array` の値を作るのはこれらの extern だけなので、ビットのない `Lin` の物体は生じない
- ネイティブのコードは `get`、`read`、`write` を展開する。要素の数を読み、符号なしで比べ、`Panic` の道へ冷たい分岐をし、`base + 8 + 8*i` の位置を `load.f64` か `store.f64` で浮動小数のレジスタとやりとりする。`Float` の箱は作らない
- 並列の書き込みは1つの塊の添字の範囲を子に渡すプリミティブで行う。`split_at` と `concat` で分けて戻す形は採らず、`MutFloatArray` に `split_at` はない。変えない配列の `concat` と `copy_slice` は逐次の操作として残す
- 配列を、要素の数を常に長さの語に持つ形 (`scan = 255`) にする案は、生の要素の配列と一緒に、ネイティブのコードが配列の要素を直接読むより前に入れる。そのとき `crates/eml_rt/src/heap/ctx/arrays.rs` の Verus の仕様のうち、`n >= 255` で `scan` を決める所がすべて変わる。仕様を変えるのは1回で済む

## 並列の実行

- どの worker も自分の `Ctx` を持って `eml_enter` から任意の eml のクロージャに入れる。入口は (関数, k) で決まる。添字の範囲のプリミティブは添字ごとに `f` を呼ぶネイティブの入口を持つ
- `par` は fork / join で、fork と join の印付けは VM と同じである ([マルチコア対応の設計](multicore.md) の「`par` の印付け」)。ネイティブのコードはスタックを切り替えられないので、join で待つ worker は待たずに手伝う。手伝えるのは、待つ join より深い fork の子だけで、ほかに手伝えるものがなければ join の節点で待つ。専用の worker は盗まず、自分の join だけを手伝う
- ネイティブのタスクは `Async` の操作でだけ切り替わる。`Async` の操作を持たないタスクは、終わるまで worker を持ち続ける。同じ worker のほかのタスクは、監視のスレッドが詰まりを見つけたときに、空いた worker が救済する。`Async.run` は、VM ではタスクを待たせるが、ネイティブではマシンのスタックの上で worker のループを入れ子にする ([非同期の設計](async.md) の「スコープとタスク」)。約束 (呼んだ側は完了の後に再開する) は同じである。入れ子の順が逆になりうるので、`Async.run` は `main` から呼ぶのがよい
- 致命的な誤りは複数の worker でも次の手順で止める。`par` の子の外では、worker k の `eml_fatal` は `Control` の終わりの欄に誤りを書き (最初の書き手が勝つ)、終わりのビットを立ててから、自分の入口へ切る。`par` の子の中では、子ごとの `JmpBuf` (子の境目) まで切り、誤りを join の節点に記録する。手伝う worker では子の下に待つ親のフレームがあるので、入口まで切らない ([マルチコア対応の設計](multicore.md) の「`par` の意味」)。監視のスレッドがビットを各 worker の止める語に写し、待っている worker (join で待つ worker を含む) を起こす。ほかの worker は次の安全点でビットを見て、それぞれの入口へ切る。後始末はしない。各 worker は入口へ戻った後、自分のスレッドの上で I/O の driver を空にする (実行中のプールの仕事も待つ)。host のスレッドはすべての worker を待ってから、終わるか回復する ([マルチコア対応の設計](multicore.md) の「止める手順」)
- 捨てたネイティブのフレームは、Rust の局所変数 (extern はもう戻っている) もデストラクタも持たない。`Foreign` のファイナライザは VM と同じく、ヒープを落とすときか回復のときに走る

## AOT と配布

- `eml build` は `cranelift-object` で object を書き、システムのリンカを呼ぶ。リンカは rustc と同じやり方で探す (Unix では `cc`、Windows では Visual Studio の `link.exe`、あれば `lld-link`)。モジュールの `link` の指示は `-l` と `-framework` にして渡す。利用者のマシンに rustc も cargo も要らない
- eml の配布物 (Nix のパッケージと、リリースの tarball) は、`eml_rt` と実行系と入口の stub をまとめた静的ライブラリを、eml のビルドのときに固定した toolchain で作って同梱する。プラグインの静的ライブラリ (`libeml_gui.a` など) も同梱し、そのモジュールを import したときだけリンクする
- 展開の情報は正しさに要らない (中断も致命的な誤りも使わない)。`cranelift-object` が出せる所ではデバッガのためだけに出す
- 使い回しの鍵は、名前と、開いた後の LIR と、それが指す形と配置の中身のハッシュにする。関数の値の ABI は一様で、直接呼ぶ関数の ABI はその名前で決まるので、呼ぶ関数のシグネチャは鍵に入れなくてよい。鍵は今決め、使い回しの仕組みは後で作る
- 定数の静的なデータは、凍結した領域と同じ約束 (rc 0、書き込まない、検査ビルドでは前置きを持つ) に乗る ([オブジェクトモデル](../spec/object-model.md) の「凍結した領域」)。検査モードの範囲の確かめのようにページの頭を読む道は、起動時に `freeze` で定数を作る形を既定にする。静的なデータに容量を持たせる形は、起動時の `freeze` が測定で重いときの代案にする

## テスト

- `tests/ui/run` と `tests/ui/run-fail` を、ネイティブで速いモードで流す ([テスト戦略](../implementation/testing.md) の「UI テスト」)。標準出力、標準エラー、終了コードは VM とバイト単位で同じでなければならない。除くのは `// native: skip` の印を付けたテストだけで、文が `max_depth` や語の数を名指す深さとメモリの上限のテストと、検査モードを要るテストに付ける。印はネイティブの UI テストを入れるときに [テスト戦略](../implementation/testing.md) に節を書いて導入し、印を付けるテストを1つずつ挙げる (成否の変更)
- バックエンドを作る途中は、扱わない形を含むテストが E0004 で断られる。各テストは VM と同じ出力になるか、E0004 で断られるかのどちらかで、断られた数はスナップショットで固定する。仕上がったバックエンドでは断られる数が 0 になり、UI テストのすべてをネイティブで流す。飛ばすのは、一覧に挙げた `// native: skip` のテストだけである
- `Async` の UI テストはどの seed でも同じ出力を返すので、ネイティブでも同じになる。worker の数はすべてのテストで 1 にし、順によらない `Async`、channel、ネットのテストでは 2 と 8 でも流す
- `RunStats` のスナップショットは VM だけのものである ([VM](../spec/vm.md) の「`RunStats`」)

## 却下した案

- Cranelift の `try_call` と、FP をたどる巻き戻し器で中断を伝える案: 試作では動いた。`tail` のフレームから投げ、handler のないフレームを飛ばし、2つ上のフレームの handler と、既定の規約の入口の handler に着地した。しかし、例外の辺ではすべてのレジスタが壊れる扱いになり、呼び出しをまたいで生きる値を退避するので、中断しうる呼び出しの位置ごとの費用が旗の確かめより重かった。そのうえ、例外の表を取り出して AOT の object に再配置すること、巻き戻し器の始まりの stub、内部向けの crate への依存が要る。旗の確かめは位置ごとに安く、数は同じなので、`try_call` に戻る理由はない
- VM とネイティブを混ぜて動かす案 (関数表 `FnEntry` を接続点にする): すべての `apply` に2つの道が要り、ネイティブが同じタスクの上で VM のループに入り直す。VM の並列化の備えの制約は外から閉包を呼び戻す入れ子の中でタスクを切り替えることを禁じる ([マルチコア対応の設計](multicore.md) の「VM の並列化の備え」) ので、この入れ子の間はタスクを切り替えられない。std だけをネイティブにし、利用者のコードを VM で動かす形も、std の高階関数が利用者のクロージャを `apply` するので同じ問題を持つ。段階的に進める道は扱わない形を E0004 で断ることで得る
- 関数ごとに遅れてコンパイルする stub: 書き換えられる間接の呼び出しは直接の `return_call` を妨げ、複数の worker の下での書き換えには書き込みの手順が要る
- Rust の `catch_unwind` や OS の巻き戻しで致命的な誤りを扱う案: Cranelift のフレームに展開の情報が要る。Windows の SEH には、Cranelift が出さない funclet が要る
- CRT の `setjmp` と `longjmp`: MSVC の `longjmp` は飛ばすフレームの上で SEH の巻き戻しをし、そのフレームの展開の情報を要る。自前の組は要らない
- Cranelift の `stack_limit` の大域の値: 分岐でなく trap になり、JIT のコードへ戻るシグナルの handler が要る
- JIT だけにする案は配布できる成果物がなく、AOT だけにする案は REPL にリンカが要る

## 未決の論点と将来の拡張

- `ctx` を固定のレジスタに置くか: 既定は明示した引数である
- Windows でのビルドに `lld` を同梱するか: 既定は同梱しない。Visual Studio の Build Tools か、入れてある `lld-link` を求める
- コンパイルの待ち時間: 上の「目的と範囲」のコンパイルの条件に届かないときの既定は、std のコンパイル済みの関数を処理系のビルドごとに使い回すことで、使い回しの鍵がこれを許す
- worker 0 のスタック: 大きいスタックのスレッドを作る形と、`main` を大きいスタックで実行し直す形がある。既定はスレッドを作る形である
- Windows での `return_call` と `tail` の実行はまだ試していない。確かめたのは Cranelift が出すコードだけである。Windows だけの不具合が見つかったときは、Unix だけで `tail` を使い、Windows では自分への末尾呼び出しを trampoline で行う (コードは悪くなるが、意味は同じ)
- `cranelift-object` が3つのターゲット (Mach-O、ELF、COFF) でシステムのリンカの受け付ける object を出すことも、まだ試していない。出せないターゲットは直るまで JIT だけにする
- 範囲の確かめを消す最適化: 範囲の確かめが測って目立つときに考える
