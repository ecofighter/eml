# Verus で検証する範囲

位置づけ: 将来の設計。

型検査、Kind 推論、evidence passing (EP) のように数理的な性質が大事な部分を、Verus で保証するかどうかの検討をまとめる。各部分について、Verus で保証するのに値するかと、値するなら実際にできるかを判断した。`eml_rt` の検証のやり方は [テスト戦略](../implementation/testing.md) の「Verus」にある。

## 結論

| 対象 | 保証する価値 | できるか |
|---|---|---|
| Kind 推論の解く部分 (`eml_types/src/kind/` の束の上の計算) | 高い | できる。最初に取り組む |
| 型検査 (単一化、row、制約の解決) | Verus では低い | 費用が見合わない。Verus では扱わない |
| EP | 守る性質の価値は高い | 変換そのものの証明はできない。LIR の verifier と VM の側で扱う |

## 判断の軸

`eml_rt` は、操作の前提が成り立つときの安全を証明している。速いモードは前提を確かめず、安全の前提として扱う ([オブジェクトモデル](../spec/object-model.md) の「速いモードと検査モード」)。VM は、この前提を守る命令の列を出す義務を負う ([オブジェクトモデル](../spec/object-model.md) の「核の操作」)。その義務は、コンパイラの各段が次のように分けて負っている。

| 速いモードの前提 | 前提を作る段 |
|---|---|
| RC のモデル (消費する操作では呼ぶ側が参照を1つ持つ、など) | Perceus。LIR の verifier が確かめるが、debug ビルドだけである |
| `Fs.read_all` と `read_line_raw` の `File` は局所で rc が 1 である ([オブジェクトモデル](../spec/object-model.md) の「読み手」) | Kind の印 (Kind 推論、`kind_values`、translate) と V1 |
| `ev_lookup` の `evv` に、探すエフェクトの evidence がある | 型検査の row と `mask` ([エフェクトと handler](../spec/effects.md) の「健全性」) と EP |
| 外側の `evv` が `evv_wf` を満たす、yield の状態の手順を守る | EP ([オブジェクトモデル](../spec/object-model.md) の「基本操作の契約」) |

数理的な性質には、次の3つの層がある。

- (a) 言語のメタ理論: 型の付いたプログラムが行き詰まらないことや、[エフェクトと handler](../spec/effects.md) の「健全性」の不変条件
- (b) アルゴリズムの正しさ: 実装が仕様どおりの答えを出すこと
- (c) 出力の検査: 1つのプログラムについて、段の出力を検査器で確かめること

Verus が向いているのは、(b) のうち小さく安定した純粋なデータの上の計算と、(c) の検査器である。(a) は Rust のコードでなく言語の定義についての定理なので、Verus の対象にしない。

## Kind 推論

### 値する理由

- 印の正しさを、後の段は確かめられない。V2 では `poly` が `unr` とも `lin` とも合うので、LIR の verifier は「`unr` の変数が `Lin` の物体を持たない」ことを確かめられない ([LIR](../spec/lir.md) の「Kind の印の検査」)。`unpack` と case のフィールドの印は translate を信用している。`poly` のコードで作った `Lin` の物体には `lin` ビットが立たないので ([オブジェクトモデル](../spec/object-model.md) の「`lin` ビット」)、検査モードでも捕まらない。印の根拠は Kind 推論だけで、translate の `check_linearity` が debug ビルドで、テストしたプログラムについて突き合わせているだけである。誤りがあると、速いモードの `File` の rc が 1 という前提が成り立たなくなる
- 規則の議論が繊細である。[型と Kind](../spec/types.md) は、反例を挙げて規則を選んでいる。「書き出すときの規則」の `f eat x n` の例、「instance での評価」の多相再帰の `f x eat g n` の例、`Unr` への固定で `μ` の instance での値を使わない理由がそれに当たる
- 数学として閉じている。扱うのは、2つの値の束 (`Unr ≤ Lin`)、3つの値の鎖 (`Never ≤ Once ≤ Multi`)、`Poly` を足した3つの値の結び、変数の間の辺と定数の境界だけである。SMT に向いていて、`eml_rt` で `share_walk` を任意のグラフについて証明したやり方 ([テスト戦略](../implementation/testing.md) の「Verus」) がそのまま使える

### できる理由

- `kind/problem.rs` の Kind の問題とスキームは、推論の表を指さず、変数を番号だけで表す純粋なデータである。`solve`、`eval`、`summary`、`entail` は、`Vec<Vec<usize>>` の辺、ワークリスト、強連結成分の分解だけで書かれている
- `eml_hir` に依存するのは、診断のための制約の由来 (`Provenance`) だけである。`solve` は、違反と原因を制約の番号で返している。由来は番号で引けるので、検証する側の外に置ける
- `kind/` は `eml_types` の中で小さく閉じた部分である。検証する計算は、`mod.rs` (大半が由来の型) を除く `entail.rs`、`eval.rs`、`problem.rs`、`solve.rs`、`summary.rs` にある

### 証明する定理

1. `solve`: 返す値は最小解である。違反として返す制約は、最小解が定数の上限を超える制約にちょうど一致する。違反がなければ、解がある
2. 持ち越し: `carry(l, s)` は、どちらの束の最小解も動かさない。違反の判定は、`l` の最小解が `Lin` で `s` の最小解が `Multi` の組を探すだけで正しい ([型と Kind](../spec/types.md) の「推論」)
3. `residual` と `carry_residual`: 残す制約は、元の制約の射影として正確である。つまり、残す変数への代入が残した制約を満たすのは、その代入を元の制約全体の解に延ばせるときに限る。持ち越しの制約については、多相化した後の組で確かめた結果が、多相化の前の組を最小解で確かめた結果と一致する。証明の中心はここである
4. `entail`: コメントにあるとおり、導き方は健全だが完全ではない。健全の側、つまり導けない制約を返さなければ、前提のスキームから対象のスキームが導けることを証明する。E2011 を出さない判断の正しさに当たる
5. `eval::values` と `summary`: 呼び出し側の SCC が複写したスキームを解いた値と、呼ばれる側の instance での値 (`kind_values` と本体の変数の値) が、V2 の意味で食い違わない。片方が `Unr` でもう片方が `Lin` になることはない。`check_linearity` がテストしたプログラムについて確かめている性質を、すべてのプログラムについて言える。最も価値の高い定理である

### 範囲の外

- 制約を集める側 (`usage.rs`、`carry.rs`、本体の検査) は証明しない。そこが [線形性](../spec/linearity.md) の規則どおりに制約を出すかは、テストで確かめる。保証するのは「与えられた制約を正しく解く」ことまでで、「`Lin` の値がちょうど1回使われる」ことを端から端まで保証するものではない
- 診断の由来の選び方 (どの制約を原因として報告するか) は、制約の番号であることだけを約束し、どの番号を選ぶかは約束しない

### 進め方

- `eml_rt` と同じく、vstd だけに依存する葉の crate に移し、`verus!` の中に書く。`eml_types` はその crate を呼び、由来を制約の番号で受け渡す。純粋な関数のままなので、各段階をクエリに載せ替える方針 ([ロードマップ](roadmap.md) の「処理系」) とも合う
- `verus!` の中では使える Rust が限られるので、`la-arena`、`HashMap`、iterator のアダプタ、`impl Fn` の引数 (`eval::values` の `base`) を書き換える
- 今の単体テスト (`kind/` と `table/tests.rs`) は残す

### 論点

- 着手の時期: Kind の規則を変えるたびに証明も直す。[ロードマップ](roadmap.md) の「型システム」には、ユーザーによる Kind の記述のように、制約の形を変えうる項目がある。関数型の包摂は、読む式で矢印を広げて今の `≤` の制約で書くので、制約の形を変えない。規則がどこまで落ち着いたかを見て決める
- `cargo verus verify` の範囲: 葉の crate を `eml_rt` と同じ確認の手順に入れるか

## 型検査

Verus では扱わない。理由は次のとおりである。

- 守りたい性質の1つ目は「型の付いたプログラムは行き詰まらない」で、(a) の層に当たる。2つ目は「推論が宣言的な型の体系に対して健全である」だが、[型と Kind](../spec/types.md) は推論の手順を定めた文書で、宣言的な規則を持たない。証明するには、その体系を書くところから要る
- 実装は `kind/` の何倍も大きく、union-find の推論の表と `HashMap` を使い、ラムダを後に回す手順のような診断のための手続きも多い。`verus!` の中に書き直すことは、仕様を積極的に変えていく今の進め方と両立しない
- 型の誤りの多くは、後の段の verifier (R7、R8、V2) で捕まる。捕まらないのは「handler が見つかる」ことで、これは row と `mask` の健全性という (a) の層の性質である

例外として、`mask` の計算 (scoped labels の対にする手順、rest、エフェクトごとの n と m) は列の上の小さな関数である。[エフェクトと handler](../spec/effects.md) の「健全性」の「呼び出し」の段で不変条件が保たれることは、Verus の proof fn でも書ける。ただし、コードと結び付かない補題になるので、文書の議論を確かめる以上の価値はなく、優先しない。

## evidence passing

### 価値と難しさ

守りたい性質 (`evv_wf`、handler が見つかること、yield の状態の手順、普通に戻ったときに `evv` が元に戻ること。[LIR](../spec/lir.md) の「`evv` の不変条件」) は、速いモードの安全の前提そのものである。しかし、変換そのものを Verus で証明することはできない。

- 変換の正しさを示すには、handle、perform、resume、`mask` を持つ Core IR の意味と、`evv` と yield の状態を持つ Core IR の意味を両方定め、何度も再開する継続を含めて、2つの意味の間の模倣の関係を示す必要がある。Xie と Leijen の論文の規模の証明で、機械化は研究の仕事になる。Verus では意味も模倣の関係も spec の関数で書くことになり、Verus の向く範囲を外れる
- EP は `kind/` と同じくらいの大きさだが、ブロックの分割、生存解析、継続の区間の写しで Core IR を大きく書き換える。`eml_core_ir` のほかの部分と型を共有していて、切り出しにくい
- 守りたい性質は、EP の出力を VM が実行したときに成り立つ動的な性質である。そのため、検証の対象は EP の変換ではなく、出力の形と VM の組み合わせのほうが合う

### 扱い方

- UI テストは検査モードと速いモードで流す ([テスト戦略](../implementation/testing.md) の「2つのモードで流す」)。検査モードでは `YieldMisuse`、`BadEvidence`、`NoHandler` が実行時の網になる ([オブジェクトモデル](../spec/object-model.md) の「受け入れる制約」)
- VM の1歩は、Verus で書ける大きさに保つ
- その後、LIR の verifier を Verus で書き、「verifier を通った LIR を VM が実行すると、`eml_rt` の前提が毎回成り立つ」ことを証明するかを検討する。証明できれば、Perceus、box の挿入、EP の出力の形の誤りがあってもメモリの安全は損なわれなくなる。印の正しさは LIR から確かめられないので、その部分は Kind 推論の証明に頼る

## 順序

1. Kind 推論の解く部分を葉の crate に移し、上の定理 1〜5 を Verus で証明する
2. LIR の verifier と VM の証明を検討する

型検査と EP の変換そのものは、Verus では扱わない。
