# ネイティブの計測でロードと実行を分け、`release`の一意でない道を1つのエントリへ移す段 (native-load)

- 作成日: 2026-11-16
- 基準: main @ 19ecda4a (`Close jit-effects`の後)。`ファイル:行`の参照はその状態を指す。行の番号は手がかりで、名指した項目が決める
- 状態: 設計の段階の計画。下の数値は、ツリーに入れていない試作で測ったものである。段を始めるときに、最初の作業で測り直して確かめる

## 1. 目的と完了の条件

- 前提: VMは開発と検証のための実行系で、ネイティブのコードはリリースのための実行系であり、いずれ事前にコンパイルする。どちらも、妥当なコンパイルの時間は受け入れる。だから、ネイティブのコードの物差しは実行で、ロードの費用は記録であって目標ではない
- 目的: `bench/native.sh`が、実行をロードと分けて測るようにする。`release`の一意でない道を、生成したコードから実行系のエントリ1つへ移し、生成したコードには一意な道だけを残す。Craneliftのverifierを、debugのビルドの外では止める。`bench/nbody.em`の`mass`を生の要素の配列にする。言語の機能は足さない
- 背景: main @ 19ecda4aでは、`bench/`のどのプログラムも、`tests/ui/run/scripts/`のどのスクリプトも、ネイティブのコードでVMより遅くは走らない。プログラムごとのロードの分を除くと、ネイティブの実行の分は、`bench/`の40本でVMの0.09から0.36、スクリプトで0.13から0.50である。`bench/native.sh`で比が0.70以上の行 (`nbody` 1.50、`sieve_var` 0.91、`std_map` 0.87、`rbtree` 0.83、`fannkuch_var` 0.81、`sieve_by_hand` 0.72、`ep_float` 0.70) が大きいのは、スクリプトが`empty`の分だけを引き、プログラム自身のコンパイルがネイティブの列に残るためである。`nbody`はVMで7200万命令を実行し、コンパイルにはVMのロードより1億4600万命令多く使う
- `docs/implementation/benchmarks.md`の「ネイティブの数値」の`nbody`の段落は、`var`の読み書きが操作の呼び出しのまま残ると書いている。`nbody`のLIRでは、どのループにもエフェクトの操作がない。最適化が4つの`var`のhandlerを状態を渡す形にするためである。この段でその段落を直す
- 完了の条件:
  1. `bench/native.sh`が、プログラムごとに、VMとネイティブのロードの命令の数と、比を1つ出す。比は、ネイティブの実行の分をVMの実行の分で割ったものである。実行の分は、全体からそのプログラム自身のロードを引いたものである
  2. 生成したコードのどの`release`も、一意でない道は`eml_rt_release`の呼び出し1つである。`release`の下ろしは`eml_rt_is_last`を呼ばず、インラインの`dup`を展開しない。CLIFのスナップショットがこれを留める
  3. `bench/native.sh`の`nbody`のほかのどの行も、実行の分が基準から3% (計測の揺れ) を超えて増えない。`nbody`の実行の分は減る
  4. すべてのテストが通り、`cargo clippy --all-targets -- -D warnings`、featureの組み合わせのclippy、`nix/crate-graph.sh --check`が通る。1秒の規則を守る。新しいエントリのテストが、Miriの2つの設定とAddressSanitizerで通る
- ロードの命令の数とコードの大きさは、段を閉じるときに記録するもので、条件ではない。試作では、ネイティブのロードからVMのロードを引いた値が、3節の4本で41%から75%減り、`rbtree`の機械語は33008バイトから14772バイトになる

## 2. 範囲

- 範囲に入るもの: `release`の下ろし (`crates/eml_native/src/lower/data.rs`)、新しいエントリ`eml_rt_release` (`crates/eml_nrt/src/heap.rs`)、その`keep`のバイトのデータの物 (`lower/consts.rs`、`lower/names.rs`)。`eml_native::abi::isa`と`eml_clink::bridge::new_module`のCraneliftのフラグ`enable_verifier`。`eml run`のフラグ`--load-only`。`bench/native.sh`、`bench/nbody.em`、`docs/implementation/benchmarks.md`。これらの規則を書く`docs/spec/native.md`の節
- 範囲に入らないもの: 配列の行とバイトの読みをインラインに展開すること (段`native-inline`。5節)。コンパイルしたコードのキャッシュ (段`native-aot`)。`eml_rt`、LIR、Core IRの変更と、VMのコードの変更。エフェクトの下ろしの変更。クロージャのエントリとPAPのアダプタ (`eml_rt_is_last`を使い続ける)

## 4. 決定

- **L-1** Craneliftのverifierは、debug assertionsを持つビルドでだけ走らせる。`abi::isa`と`eml_clink::bridge::new_module`は、`enable_verifier`を`cfg!(debug_assertions)`にする。devのプロファイルはdebug assertionsを持つので、どのテストもCIのどのジョブも、今と同じくすべての関数を確かめる。Core IRとLIRのverifierと同じ規則である。このverifierはCLIFの形が正しいことを確かめるもので、メモリ安全の境界ではなく、生成したコードはこれに頼らない。`apply.rs`は、末尾呼び出しの結果の型を、このフラグに頼らずにどのビルドでも確かめている
- **L-2** `release`の生成したコードは、一意な道だけを持つ。コードは数を読む。1なら、残さない子をインラインの`decref`で手放し、`eml_rt_free_block`で箱を空けるか、箱をtokenにする。そうでなければ、冷たいブロックで`eml_rt_release(ctx, x, keep, n)`を呼び、tokenは空である。`unboxed`の形は、今と同じく先にダミーを確かめる
- **L-3** `eml_rt_release`は、表`HEAP`の新しい`shim`のエントリである。本体は、今の生成したコードが展開し、VMの`release_fields`が走らせるのと同じ列で、同じヒープの操作を同じ順に呼ぶ。`is_last(x)`なら、走査する語`i`を小さい順に見て、`keep[i] == 0`のものに`decref(scanned(x, i))`を行い、その後に`free_block(x)`を行う。そうでなければ、`i`を小さい順に見て、`keep[i] != 0`のものに`dup(scanned(x, i))`を行い、その後に`decref(x)`を行う。子は`Heap::scanned`で読む。これは走査する語の番号で読むので、走査する語が数の語の後ろに並ぶ構築子 (255個以上) でも正しい位置を読む。`n`は構築子の形の走査する語の数で、`keep`は走査する語ごとに1バイトを持つ`n`バイトのアドレスである。バイトは、`release`が変数に束縛する欄なら1、ほかは0である。エントリはtagを受け取らない。速いモードはtagを読まないためである。エントリは`n`を`usize::try_from`で変え、失敗は致命的な誤りにする。debugのビルドでは、`x`が走査する語の数が`n`の`Data`の物体であることと、`keep`のどのバイトも0か1であることを確かめる。`keep`はバイト (`&[u8]`) として読むので、バイトの値で未定義の振る舞いになることはない。エントリは自分のSafetyの約束をdocコメントに書き、実行系のcrateの関数を名指して済ませない。下ろしは、debugのビルドで、`release`が書く欄の数が構築子の欄の数と等しいことを確かめる
- **L-4** `keep`のバイトは、moduleの読み取り専用のデータの物で、中身で名前を決める。名前は`k:`の後ろに0と1の数字を並べたものである (`Datum::Keep`)。moduleはこれを書き込めない物として宣言し、0を足して8バイトの倍数かつ8バイト以上にしたバイトで定義する。だから、`n`が0でもアドレスは有効である。ローダーはこれに書かず、`Image.data`にも入れない。テストがこの2つを留める。同じ並びの`release`は1つの物を共有する。名前は並びだけで決まるので、「関数の名前がコードを決める」を守る
- **L-5** `eml run --load-only`は、ファイルを検査し、コンパイルし、選んだ実行系にロードして、`main`を実行せずに終了コード0で終わる。`--native`があってもなくても働く。誤りのあるファイルと、ネイティブのコードが断るプログラムは、フラグがないときと同じに失敗する。パイプラインを進めるのは今と同じく`Session`だけである。フラグは実行の設定の1つで、実行系の`execute`が受け取り、実行の前に戻る。公開のフラグにする
- **L-6** `bench/native.sh`は、プログラムごとに、プロセス全体と`--load-only`を、VMとネイティブのそれぞれで測る。表は、今と同じ全体の命令の数、2つのロード、比1つ「native / VM (実行)」を持つ。プロセス全体の比は消す。1節の前提では、リリースのビルドのコンパイルは実行の前に済むので、JITのコンパイルを実行に混ぜた比は、このプロジェクトが問うことに答えない。`nbody`の読み違いもこの比から出た。全体の命令の数とロードは表に残るので、前の比は行から計算できる
- **L-7** `bench/nbody.em`は、質量を`UnboxedArray Float`で持つ。`bench/numeric/nbody.py`は変えない。浮動小数の演算の順は同じである
- **L-8** 数は記録で、門ではない。完了の条件の3は、段を閉じるときに開発機で1回確かめる
- **L-9** `native-inline`の配列の部分は、この段に入れず、別の段にもしない (5節)

## 5. 段の列での位置と`native-inline`

- この段は列の先頭に置いたままにする。前提がなく、触るのは`release`の下ろし、エントリ1つ、フラグ、benchだけである。先頭に置く理由は、もうロードの費用ではない。`bench/native.sh`の表は、jitの段の群の後の段が閉じるたびに入れ替える記録で、後の多くの項目の見直す条件がその行を読む。読むべき値は実行である。この段は、中身を変えずに、`native-inline`より前のどこへでも動かせる
- `native-inline`は`native-aot`の後のままにし、配列の部分を分けない。配列の行、`String`と`Bytes`のバイトの読み、割り当て、解放の展開は、どれも`eml_rt`の配置と確保器の事実を生成したコードから読む。`native-inline`は、その事実を`eml_rt`から1回で外へ出し、`eml_rt`の門 (Verusと`bench/rt-gate.sh`) を1回通り、展開の表1つと`spec/`の規則1組を持つ。配列の行だけを先に取ると、事実の一部を今、残りを後で出すことになり、1つの設計のために`eml_rt`の門を2回通る。`native-inline`の目標は、リリースのビルドをRustとPythonと比べる形で書いてあり、そのビルドは`native-aot`が作る。3節の実行の内訳は、この段を閉じるときに`benchmarks.md`に入れ、`native-inline`の出発点にする

## 6. 比べた案

- **案A**: `release`の共有の道で、残す子ごとに`eml_rt_dup_slow`を、箱に`eml_rt_decref`を呼ぶ。新しいエントリも新しい`unsafe`もない。弱み: 生成したコードに一意でない道 (`is_last`、分岐、呼び出し) が残り、コードは案Bより大きい。採らない
- **案B (採る)**: L-2、L-3、L-4。生成したコードが持つのは一意な道だけである。もう一方の道は実行系の関数1つで、2つの実行系がもう使っているヒープの操作をVMと同じ列で呼ぶ。だから振る舞いは、子を手放す順も含めて、どの状態でも今のネイティブのコードとVMに等しい。コードは、実行の時間を保つ形の中でいちばん小さい。弱み: 生成したコードのポインタからスライスを作る`unsafe`のエントリが1つ増える。7節で扱う
- **案B'**: 案Bと同じ形で、エントリが`eml_rt`の検証済みの`Heap::release`を包む。助言者の検討 (7節) の後に退けた。`Heap::release`は、今は`eml_rt`のテストの外に呼ぶ所がない。数が-1のとき、直接の子の数を先に減らしてから箱を空け、その後で残りを片付けるので、順がVMとも今のネイティブのコードとも違う。Verusの事前条件`release_ok`は、最後の参照のときにも残す子が`lin`ビットを持たないことを求め、`share`の後のふつうの状態がこれを満たさない。共有した木では、案Bより命令が3.9%多い
- **案C**: 案B'に加えて、tokenを作らない`release`をいつも呼び出しにする。採らない。`iter_pipeline`の命令が39%、`std_list`が7%増える。使い切るリストの一意な道が、`keep`をたどる一般の列を払うためである
- **案D**: どの`release`も呼び出しにする (`Heap::release`か`Heap::release_reuse`)。下ろしはいちばん短い。採らない。tokenを作る一意な道は関数的な更新の速い道で、実行の分が22%から129%増える
- **案E**: Craneliftの安い設定 (`regalloc_algorithm=single_pass`、`opt_level=none`) でコンパイルする。採らない。実行の実時間が30%から40%増える
- **案F**: 関数を初めて呼ばれたときにコンパイルするか、VMで始めてネイティブのコードへ移る。採らない。ロードの費用は目標でなく (1節)、マシンは1回だけロードし、`Image`の表はロードのときに決まる

## 7. 助言者によるエントリの検討

新しいエージェントが、コードと設計だけを受け取って、エントリの健全性を検討した。先に案B'を、次に案Bを見た。

- 1回目 (案B'): 変更を条件に健全。案B'を退けた所見は6節に書いた。`Heap::release`が初めて実行の道で呼ばれること、数が-1のときに子を手放す順がVMと違うこと、`release_ok`が残す`lin`の子についてSafetyの文より厳しいことである。ほかに、負の語を`n as usize`にすると`slice::from_raw_parts`の中で未定義の振る舞いになることと、moduleのデータの物は今はどれも書き込める物でローダーが書くので、`keep`の物は書き込めない物として宣言し`Image.data`の外に置かなければならないことを挙げた
- 2回目 (案B): 変更を条件に健全。変更を入れた案Bは、どの状態でも今のネイティブの下ろしとVMに1手ずつ等しい。見た状態は、1より大きい局所の数、上限に張り付いた数、不死の物体、付けた塊の物体、最後の参照を含む共有の数、数が-1の親の下の残す`lin`の子 (触れない)、即値、`unboxed`の形のダミー、tokenを作る形と作らない形である。エントリが呼ぶどの操作も、その約束の中に収まる。ほかのworkerとのどの重なりも、今より悪くならない。エントリは同じ関数で判定をやり直し、どの欄も`decref(x)`より前、呼ぶ側の参照が`x`を生かしている間に読み、残す子は箱を手放す前に`dup`する。速いモードで、今の列が失敗しない所でこの呼び出しが失敗することはない
- 求められた変更は、どれもL-3とL-4に入れた。子を`Heap::scanned`で読むこと (試作は`Heap::field`を使った。これはペイロードの位置で読むので、走査する語が255個以上の構築子で数の語を子として読む。試作のメモリ安全の誤りである)。`n`を`usize::try_from`で変えること。debugの確かめ。`keep`をバイトとして読むこと。エントリ自身のSafetyの約束。`Image.data`の外にある読み取り専用の`k:`の物と、それを留めるテスト。入れるコードに、漏らした確保と切り替えのスイッチを残さないこと
- 助言者が残した危険: 「残さない子を手放してから`free_block`」の列は、`docs/spec/object-model.md`の「核の操作」のモデルの前提 (残さない子は呼ぶ側の参照と数える) に頼っていて、Verusの事前条件の連なりには載っていない。VMの`release_fields`と今のネイティブの下ろしも同じ立場なので、エントリが負債を増やすことはない。JITのメモリの供給が読み取り専用のデータをどこに置き、どう保護するかは確かめていない。作業の単位5で先に確かめる

## 10. 後に回す項目

- `eml_rt`の`release_ok`の、残す子の条件
  - 後に回した理由: `Heap::release`のVerusの事前条件は、どの残す子も`lin`ビットを持たないことを求めるが、Safetyの文と`spec/`は`is_last`が偽のときだけ求める。`Heap::release`は`eml_rt`のテストの外に呼ぶ所がなく、この段のエントリも呼ばない。直すのは`eml_rt`で、その門を通る。
  - 見直す条件: `eml_rt`のテストの外で、`Heap::release`か`Heap::release_reuse`を初めて呼ぶ前。
- `Heap::release`が、数が-1のときに子を手放す順
  - 後に回した理由: VMの`release_fields`とこの段のエントリと順が違い、違いは共有の物体の破棄処理の順でだけ見える。実行の道は`Heap::release`を呼ばない。
  - 見直す条件: 上の項目と同じ。
- `evv_get`、`evv_set`、evidenceの欄の読みをインラインに展開すること
  - 後に回した理由: 熱い道でこれらのエントリに届くのは`ep_float`だけで (実行の71%)、`ep_float`は最適化が特殊化しないhandlerを測る行である。
  - 見直す条件: `ep_float`のほかの行かスクリプトが、エフェクトの基本操作のエントリに実行の10%より多くを使うとき。
- クロージャのエントリとPAPのアダプタの一意でない道を、エントリにすること
  - 後に回した理由: どちらも`eml_rt_is_last`とインラインの`dup`を使い続ける。測ったプログラムでは、その地点の数が少ない。
  - 見直す条件: `native-inline`がクロージャのエントリのコードの大きさを測るとき。または、ネイティブのコードが`par`を動かし、共有の道がふつうに通る道になるとき。
