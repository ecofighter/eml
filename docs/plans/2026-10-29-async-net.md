## 1. 目的と成功の基準

- 目的
  - macOS と Linux で、`Std.Net` の TCP (listen、accept、connect、読み書き) と、`connect` の中の名前の解決を動かす。
  - `Std.Signal` で、SIGTERM と Ctrl-C をタスクが待てるようにする。待つタスクがなければ、今と同じく run を止める。
  - テストのための std のモジュール `Std.IoTest` と、CLI のフラグ `--clock` を消す。仮想の時計とテストの driver は、テストのハーネスだけが選ぶ。
  - TLS と HTTPS のクライアントを、後の2つの段 `net-tls` と `std-http` として roadmap に載せ、設計を docs/future/async.md に書く。
- 成功の基準 (確かめ方は 9 章)
  - 9 章の全体の検証のコマンドがすべて通る。
  - `git grep -n -- '--clock'` と `git grep -n 'IoTest'` が、`docs/plans/` のほかで何も返さない。
  - UI テストの `tests/ui/run/async/net_*.em` と `signal_*.em` が、検査モード、速いモード、2つの seed で通る。
  - 手で確かめる3点 (9 章) が期待どおりに動く。

## 3. 背景

- driver の操作は `Readable`、`Read`、`Write`、`Job` の4つだけである (`crates/eml_rt/src/driver.rs:25-36`)。`Completion` は `io::Result<usize>` しか持たず、本物の driver は `pop` が返す操作を捨てる (`crates/eml_io/src/real.rs`)。完了で中身 (受けたソケット、相手の番地) を返す形はまだない。
- driver がハンドルを作るのは `IoDriver::pair` だけで、これを使うのは `Std.IoTest` だけである。Windows の本物の driver は `pair` で `Unsupported` を返し、`Proactor::attach` をどこでも呼ばない。
- `std/IoTest.em` は91行で、extern の行は10ある (`crates/eml_extern/src/lib.rs:1290-1393`)。使うテストは、UI テスト7本 (`tests/ui/run/async/io_*.em` 6本と `tests/ui/run-fail/async/io_read_deadlock.em`)、REPL のトランスクリプト1本 (`crates/eml_cli/tests/repl/async/io_in_flight.repl`)、`crates/eml_vm/tests/{io,api,machine}.rs`、`crates/eml_vm/src/cells.rs` の単体テスト、eml_io のテストである。
- シグナルで扱うのは SIGINT だけである。unix は `sigaction` (`SA_RESTART` なし)、Windows は `SetConsoleCtrlHandler` で、`eml run` の2回目の Ctrl-C は `_exit(130)` になる。SIGTERM、`TERMINATE` のビット、自己パイプはない。`Control` のビットは `INTERRUPT = 1`、`MEMORY = 2`、worker の語の `PREEMPT = 1 << 31` である。object-model.md は 8 を `TERMINATE` のために空けている。
- 監視のスレッドは `PREEMPT` を立てるだけである。`spawn_masked` が監視のスレッドのシグナルを塞ぐ (`crates/eml_vm/src/monitor.rs:97-124`。unix 版と `#[cfg(not(unix))]` 版がある)。compio のプールのスレッドは `push` を呼んだスレッドから `std::thread::spawn` で生まれ、シグナルを塞がない (compio-driver 0.12.5 の `asyncify.rs:113-130`)。今の `checksum` の仕事でも、プールのスレッドが SIGINT を受けうる。
- compio-driver 0.12.5 の unix の polling backend では、`CreateSocket`、`Bind`、`Listen`、`ShutdownSocket`、`CloseSocket` が `Decision::Blocking` でプールに回り、`Accept`、`Connect`、`Recv`、`Send` は readiness で動く。compio は `socket2::SockAddr` を `pub(super)` でしか再公開しないので、eml_io が socket2 0.6 を直接使う。Windows の compio-driver に `CreateSocket`、`Bind`、`Listen`、`ShutdownSocket` はない。
- `IOErrorKind` は10種類で、`Cancelled`、`TimedOut`、`ConnectionReset`、`AddrInUse`、`ResourceLimit` (タグ 5 から 9) は `fail_io` だけが出す。extern が出すのは最初の5種類だけである (docs/future/async.md の決定 #8)。
- UI テストはいつもテストの driver の上で流れる (docs/implementation/testing.md:325)。ハーネスの表示 `crates/eml_cli/tests/ui.rs:274` は `--clock virtual` と書く。先頭の印は今は1行目の `windows: skip` だけを読む (`crates/eml_cli/tests/common/mod.rs:62-109`)。
- `RunStats` の I/O の欄は `completions` で、bench の44か所は `completions: 0` を固定している (`crates/eml_vm/tests/bench.rs`)。bench のプログラムは `Async` を使わない。
- `Plugin` の trait は docs/future/ffi.md の「拡張」にあるだけで、コードはない。今の roadmap では、TLS は `gui-plugin` のプラグインの仕組みを待つ「その後の項目」にある。
- ビルドの基盤: devShell は stdenv の `cc` を持つ。`nix build` は `rustPlatform.buildRustPackage` である。`.#cross` は clippy だけを流し、リンクしない。ring と aws-lc-rs はどちらも 1.99.1 で組めるが、`.#cross` の Windows msvc の clippy では失敗する。これは scratch のコピーで確かめた。この段は暗号の crate を入れないので、`.#cross` のコマンドは変わらない。

## 5. 決定

### 5.1 長く効く方針 (変えるときは見直しが要る)

実装がこの節の方針とぶつかったら、止めて報告する。

#### D-1: TLS と HTTPS のクライアントは、async-net の後の2つの段にする
- 決定
  - roadmap の「段の列」で、`async-net` の直後、`net-windows` の前に、段 `net-tls` と `std-http` を置く。
  - `net-tls` は `Std.Tls` のクライアントだけを入れる。TLS の状態は、rustls 0.23 の上の新しい crate `crates/eml_tls` が持つ。`eml_vm` と `eml_io` の feature `tls` で結び、`eml_cli` の既定の feature で有効にする。
  - TLS の形は sans-IO である。`Tls.Conn` は rustls の接続と復号した平文の列を持つ `Lin` の `Foreign` で、I/O を持たない。ソケットの I/O はすべて `Std.Net` が行い、`std/Tls.em` の eml のコードが `TcpStream` と `Conn` の間でバイトを汲む。
  - 暗号は aws-lc-rs、根の証明書は webpki-roots にし、追加の CA は `Tls.connect_with_ca` に PEM で渡す。
  - TLS はプラグインにしない。`Plugin` の trait は GUI のためだけに残し、docs/future/ffi.md は変えない。
  - `std-http` は、HTTP/1.1 のクライアントを `Net` と `Tls` の上に eml で書く。extern は足さない。
- 理由
  - sans-IO にすると、待ち、取り消し、期限、決定的なテストの driver が `Net` の1か所に残り、`Tls` は組み合わせでそれを受け継ぐ。
  - `Plugin` の仕組みは GUI の要件 (スレッドの固定、イベントループ) のためのもので、TLS はどれも要らない。C の暗号を外してビルドする道は cargo の feature で足りる。
  - aws-lc-rs は rustls の既定で、rustc がリンクに使う C のツールチェーンのほかに要るものがない。ring の最後のリリースは 2025-03 である。
- 退けた案
  - libcurl やその crate: 本物のソケットを要るのでテストの driver の上で試せず、`Net` を通らないので TLS の層にならない。OpenSSL、Schannel、zlib、pkg-config の依存も入る。
  - musl で静的に結ぶこと: TLS とは別の配布の話として後に回す。musl を対象にする C のツールチェーン、2つ目の nix のパッケージ、CI のジョブが要る。
  - 公開の `Tls.accept`: 利用者に見せるのはクライアントだけにする。テストの相手はテストの側に置く (付録3)。
- 影響の範囲: 後の2つの段。この段では、`Net` の読みの保証 (D-4) と、テストの driver の継ぎ目の関数 (D-12) に効く。
- 見直す条件: `net-tls` の最初の作業で、`nix build` か CI で aws-lc-sys が組めないとき (付録3の代わりの案は ring)。
- リポジトリに残す所: roadmap の「段の列」と「その後の項目」、docs/future/async.md の新しい節「TLS と HTTP」。T-12 が書く。

#### D-2: 仮想の時計とテストの driver はハーネスだけが選び、テストのための std の API を持たない
- 決定
  - CLI の `run` と `repl` から `--clock` を消す。CLI はいつも本物の時計と本物の driver で動く。
  - 仮想の時計とテストの driver は、UI テスト、REPL のトランスクリプト、Rust のテストが `RunConfig` と `Machine` で選ぶ。型の名前 `Clock` は変えない。
  - `Std.IoTest` を丸ごと消す。プールの仕事 (`Op::Job`) とプールそのものは残し、Rust のテストで試す。
  - 仮想のシグナルは、ハーネスが `RunConfig::with_signals` と `Machine::with_signals` に渡す予定で起こす。UI テストは、先頭の印の行 `-- signal: <interrupt|terminate> at <ms>` で予定を書く。
- 理由: 利用者に見える面からテストのための入口がなくなり、roadmap の「`Clock` と `--clock` の名前」の項目も要らなくなる。
- 退けた案: `--clock` を `--io` に改名すること。`Std.IoTest` を `checksum` だけ残すこと。仮想のシグナルを起こす std の関数 (`raise_after`)。
- 影響の範囲: eml_cli、eml_vm の `RunConfig`、テストのハーネス、docs/implementation/testing.md。
- 見直す条件: 利用者が仮想の時計でスクリプトを試す必要が出たとき。
- 失うもの: 段の後、VM から本物のプールの仕事までを通して流すテストはない。プールの待ちは eml_io のテストだけが確かめる。段 `ffi-blocking` が通しのテストを戻す。
- リポジトリに残す所: docs/spec/vm.md の「時計と driver」、docs/implementation/testing.md の「UI テスト」と「OS ごとのテスト」。T-1、T-9、T-10 が書く。

#### D-3: シグナルの意味と、強制の終わり
- 決定
  - `Std.Signal` は `data Signal = | Interrupt | Terminate` (`Eq`、`Show`) と `wait : Signal -> <IO, Async> Unit` だけを持つ。
  - シグナルは貯めない。届けたときに同じシグナルを待つタスクをすべて、待ち始めた順に起こす。待つタスクがなければ既定の動きをする。`Interrupt` は run を止めて 130 で終わり、`Terminate` は同じ止め方で 143 で終わる。
  - `eml run` では、前の同じシグナルをまだ届けていない間か、そのシグナルがもう run を止めている間に来たシグナルで、その場で終わる。Ctrl-C は `_exit(130)`、SIGTERM は `_exit(143)` である。届けた後のシグナルは1回目として扱う。2種類は互いを数えない。
  - `wait` は取り消しの地点で、取り消されると IO の失敗 `Prelude.Cancelled` を投げる。
  - `eml repl` は SIGTERM を受けず、強制の終わりもない。
- 理由: 待つタスクがあって worker が同期の読みで止まっていても、2回目のシグナルで必ず終われる。Ctrl-C の規則も、それに合わせた SIGTERM の規則も、利用者が承認した (2026-10-29)。
- 退けた案: 「監視の刻み1つの間だけ」の2回目で終わる形 (docs/future/async.md の今の決定 #18 の文)。この形では、待つタスクがいて同期の読みで止まったプログラムを Ctrl-C で止められない。
- 影響の範囲: eml_rt の `Control`、eml_cli のシグナルの handler、docs/spec/stdlib.md、docs/spec/vm.md、docs/future/async.md の決定 #18。
- 見直す条件: process manager が SIGTERM の2回目に別の意味を求めたとき。
- リポジトリに残す所: docs/spec/stdlib.md の「`Std.Signal`」、docs/spec/vm.md の「上限と割り込み」、docs/future/async.md の決定 #18 (T-3、T-10、T-11、T-13)。決定 #18 の文案は付録2の 5.4 にある。

#### D-4: `Std.Net` の API と誤りの種類
- 決定
  - API は付録1の 1.1 の表のとおりである。docs/future/async.md の「ネットワークとシグナル」の素案から変わるのは次の点だけである。
    - `listen` は `<IO, Async>` で、`host` は IP アドレスの綴りだけを受ける。
    - `read_line` はストリームごとの Rust の buffer (`rest`) に読む。期限は1行の全体に付き、1行は 1 MiB (`LINE_LIMIT = 1_048_576`) までである。返す行は終わりの改行を含まない。
    - `read_chunk` は1回に 65 536 バイトまでを足し、EOF では何も足さない。`read_line` が読みすぎたバイトを先に返す。`read_line` を使っていないストリームは、隠れた読みの buffer を持たない。
    - `read_chunk_within` が `None` を返したときは、読んだバイトはない。
    - 書きの関数は buffer をすべて書く。`write_within` は作らず、書きの期限は `Async.timeout` で書く。
  - `IOErrorKind` にタグ 10 の `ConnectionRefused` を足す。今のタグは動かさない。包みが `fail_io` で出す種類は、`ConnectionRefused`、`ConnectionReset` (ECONNRESET、EPIPE、ECONNABORTED)、`AddrInUse`、`TimedOut`、`Cancelled` である。EPIPE を `ConnectionReset` にするのは `Net` だけで、`Child` と `FileOut` の書きは変えない。
- 理由
  - D-1 の TLS の層は `read_chunk`、`write_bytes`、`shutdown_write` と読みの保証だけに頼る。
  - 拒まれた接続は最もよくある失敗なので、文言で見分けさせない。
- 影響の範囲: std、利用者のプログラム、後の段の `Tls` と `Http`。
- 見直す条件: 書きの期限の後にストリームを残す必要のあるプロトコルが出たとき (`write_within`)。
- リポジトリに残す所: docs/spec/stdlib.md の「`Std.Net`」(T-6 から T-8)、docs/overview.md の決定の表と docs/future/async.md の決定 #8 (T-13)。

### 5.2 短中期の設計

理由があれば実装の中で変えてよいが、変えたらコミットのメッセージに書く。細部は付録1と付録2にある。

#### D-10: driver の面
- `Op` に `Listen { addr }`、`Accept { listener }`、`Connect { host, port }` を足す。`Op::Write` は buffer をすべて書く。`Op::Job` は残す。
- 完了の中身を `Done` (`Size`、`Listener { handle, port }`、`Stream { handle, peer }`) で返し、`Completion` に `cancelled: bool` を足す。期限に負けたとみなすのは、期限の取り消しで終わった完了 (`cancelled: true`) だけである。期限と競った本物の誤りは、その種類で投げる。
- `shutdown_write` と `set_nodelay` は同期の trait のメソッドにする。`pair` は T-9 で消す。
- 本物の driver では、bind と listen をプールに回さず、socket2 で持ち主のスレッドの上で行う。
- `OpKey` は1つの操作に1つで、本物の driver はその下で compio の key を複数使ってよい。取り消しの印があれば出し直さない。
- 細部: 付録1の 1.4 と 5.1。

#### D-11: 名前の解決のスレッド
- 名前の解決は compio のプールでなく、本物の driver の中の解決のスレッドで行う。
- 同時に動く解決は8本 (`RESOLVE_LIMIT`) までで、残りは FIFO で待つ。取り消し、期限、`quiesce`、Ctrl-C のどれも、解決の結果を待たずに手放す。手放した解決のスレッドは別に数え、64本 (`ABANDONED_LIMIT`) たまると、新しい解決は即座に種類 `Other` の IO の失敗 (`… too many name lookups are stuck`) になる。
- 解決のスレッドは SIGINT と SIGTERM を塞いで起動する (D-16)。
- `RealDriver::with_lookup` は解決の関数 (`fn` のポインタ) を差し替える。テストと組み込み先のためで、テストは機械の `/etc/hosts` に頼らない。
- 細部: 付録1の 1.4。

#### D-12: テストの driver の仮想のネットワーク
- 仮想のホストは1つで、ポートの名前空間も1つである。IP アドレスの綴りはどれもこのホストを指し、`localhost` は `127.0.0.1` に解決する。ほかの名前は `NotFound` で終わる。
- ポート 0 と接続する側のポートには、49152 から 65535 の間で使っていないポートを順に振り、端まで行ったら戻る。backlog は 1024 で、満ちた backlog への接続は accept を待つ。
- 名前の確かめと `virtual_connect(port)` は、それぞれ1つの関数にしておく。後の段で、TLS を終端する相手 (`tls.localhost`) がこの2つを使う。
- 細部: 付録1の 1.5。

#### D-13: UI テストの置き場所
- `Net` と `Signal` の UI テストは `tests/ui/{run,run-fail}/async/net_*.em` と `signal_*.em` に置く。どれもテストの driver の上で流れ、seed の run も受ける。`tests/ui/run/net/` は作らない。
- 本物のソケットは Rust のテスト (`crates/eml_io/tests/real.rs`、`crates/eml_vm/tests/api.rs` と `signal.rs`) だけで試す。unix のものは `#[cfg(unix)]` にし、Windows のものは `NotAvailable` を確かめる。

#### D-14: 包みと結果の場合分け
- `Net` の待つ関数は、どれも同じ型の包みで書く。`submit_*`、`Async.io_wait` (期限付きは `io_wait_until`)、`op_*`、`op_outcome`、`take_*`、`finish` の形である。
- 結果の番号は次の6つである。`0` 成功、`1` 期限に負けた、`2` reset、`3` 使用中の番地、`4` 時間切れ、`5` そのほかの失敗。
- 決める順は次のとおりである。
  1. タスクの取り消しが最初に勝つ。
  2. 成功の完了は、期限と競ってもデータとして扱う。
  3. 期限の取り消しで終わった完了は `1` (期限に負けた) である。
  4. 残りは誤りの種類ごとに分ける。
- 行の表と包みの型は付録1の 5.2 にある。

#### D-15: 自己パイプと監視のスレッド
- 自己パイプ (`Doorbell`) は `Machine` ごとに1つで、`RunConfig::with_doorbell` か `Machine::with_doorbell` で渡す。プロセスに1つの static にはしない。1つのプロセスで動く `cargo test` の中で、監視のスレッドどうしが起こしを取り合わないためである。
- CLI は自己パイプを1つ作り、シグナルの handler と run の設定の両方に渡す。自己パイプのない `Machine` は、今の 10 ms の監視の刻みに戻る。
- シグナルの handler は、unix では自己パイプに1バイト書いて errno を戻し、Windows では condvar を鳴らす。起きた監視のスレッドは、知らせを受け箱に積み、worker の語の新しいビット `NOTICE` (`1 << 30`) を立て、driver の waker を鳴らす。これが waker の本番の最初の呼び出しになる。
- `NOTICE` を見た worker は、次の安全点で、タスクを切り替えずに知らせを集める。`preempt()` は呼ばないので、`Sequential` のスケジュールは今と同じく切り替えない。
- 監視のスレッドの持ち主は `Normal` のスケジュールから `Scheduler` に移る。
- `IDLE_TICK` (10 ms) の上限はこの段では残す。roadmap の項目は「10 ms の上限をなくすこと」に狭める (T-13)。
- 細部: 付録2の 1.3。

#### D-16: driver のスレッドは SIGINT と SIGTERM を塞ぐ
- プールに回る `Op::Job` を `push` する間、本物の driver は SIGINT と SIGTERM を塞ぎ、終わったら元に戻す。そこから生まれるプールのスレッドは、塞いだ状態を受け継ぐ。
- 塞ぐのはこの2つだけにする。SIGSEGV などの同期のシグナルを塞ぐと、その動きが未定義になる。
- `spawn_masked` は eml_vm の `monitor.rs` から eml_io へ移す。unix 版が上と同じ2つを塞ぎ、unix でない版はふつうの spawn のままにする。監視のスレッドと解決のスレッドの両方がこれを使う。
- eml_io は unix で `libc` に依存する。

#### D-17: この段の Windows
- `Std.Net` の `listen`、`accept`、`connect` は、`submit` で `Err(Unsupported)` を完了にする。利用者には `NotAvailable` の IO の失敗 (`cannot listen on 127.0.0.1:0: unsupported`) として届く。
- `Interrupt` を待つタスクへ届けることは、ほかの OS と同じ道で動く。`Terminate` を起こす OS の出来事は扱わない。
- UI テストは Windows でも同じに流れ、`windows: skip` の印は要らない。OS のシグナルを送るテストは `#[cfg(unix)]` にする。

#### D-18: 2つの設計の作業を交互に並べる
- Net と Signal の作業は、`real.rs`、`monitor.rs`、`cells.rs`、`ui.rs`、`io.rs`、`std/Async.em`、vm.md を共有する。そのため 8 章の順で交互に進める。
- Signal の期待値の変更 (`<std>/Async.em` の行と `RunStats` の固定) は、`Std.IoTest` を消した後の T-10 で1回だけ求める。

## 付録の外の記録: 検討で決まったこと

蒸し返さないために、検討の中で決まったことだけを書く。

- `Std.IoTest` は `checksum` だけ残す案もあったが、テストのための std の API を残さないことを優先して、丸ごと消した。
- 名前の解決を compio のプールで行う案は、`quiesce` と Ctrl-C が `getaddrinfo` の終わりまで上限なしに待つので退けた。手放した解決が溜まる問題は、64本の上限と即座の失敗で扱う。
- 監視のスレッドを 10 ms ごとに見に行かせる案は、`Signal.wait` を持つプログラムが CPU を 100 Hz で起こし続け、決定 #18 の「監視のスレッドを起こす」から外れるので、自己パイプにした。
- 自己パイプをプロセスに1つの static にする案は、1つのプロセスの `cargo test` で監視のスレッドどうしが起こしを取り合うので、`Machine` ごとにした。
- 届けるときに `preempt()` を呼ぶ案は `Sequential` の決定性を壊すので、`NOTICE` のビットにした。
- 期限の後に来た本物の誤りを「次の操作が報告する」とする案は、ECONNRESET と EPIPE を失敗したシステムコールが消費するので誤りである。`Completion::cancelled` で期限の取り消しだけを区別する。
