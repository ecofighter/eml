# タスクをネイティブで動かす段 (jit-tasks)

- 作成日: 2026-11-11
- 基準: 前の段 (jit-effects) の`Close jit-effects`のコミット。付録の`ファイル:行`の参照はmain @ 432fffb4の状態を指す。基準とのずれは、段を始めるときに最初の作業で確かめる。行の番号は手がかりで、名指した項目が決める
- 状態: 設計の段階の計画。段を始めるときに、前の段の結果に合わせて実行できる計画へ書き直し、この段の最初のコミットで置き換える。付録は`docs/plans/2026-11-11-jit/`にある。この段の設計は付録05の§1.2と§5.2 (あわせて§1.0、§3、§3.1、§4、§6) で、付録00と食い違う所は付録00に従う

## 1. 目的と完了の条件

- 目的: workerの表、受け箱、monitor、job、`Exec`のtraitをeml_schedに移し、そのうえでネイティブの`Exec`を実装する。101のasync-classの行、入れ子の`Async.run`、`par`、`compute`、blocking C、タスクの上限、worker全体を止める手順、メインのworker、シグナルである。この段で、ネイティブで断る形がなくなる
- 完了の条件 (付録01の§5.3): 断られるものが0であること。数える仕組みと`Unsupported`を消してあること。どのUIのファイルも、ネイティブの1 workerで結果が同じか、N-43の違いを理由に書いた印を持つこと。順に依らない`async`、`chan`、ネットのファイルは、2と8 workerでも同じであること。TSanのjobを広げてあること。stdlib.mdとspec/native.mdに入れ子のrunの規則があること。`par_tree`、`bench/async/scale.sh`、`bench/net.sh`のネイティブの数値を記録してあること

## 2. 範囲

- 範囲に入るもの: VMの側をeml_schedへ移すこと (先に行い、VMはバイト単位で変わらない)。`eml_sched/testing`のfeatureを消すこと (N-41)。ネイティブの`Exec`。`extern_rows!`の`task`の節の本体。入れ子の`Async.run` (LIFOの段、`BuriedRun`)。子ごとの`JmpBuf`で親のworkerで動かす`par`。`child_abort`。`compute`。blocking C (`CSubmit`と`CTake`)。上限の種別と、それを移す1つの関数。`ResourceLimit`。メインのworkerと、Rustの関数としてのその待ちのループ。シグナル。`--native`に1でない`--workers`、1でない`EML_WORKERS`、`--gui`、`EML_GUI`を付けたときの使い方の誤りをなくすこと (R-7、C-7、C-11)。`bench/async/scale.sh`と`bench/net.sh`に`--native`を渡すこと
- 範囲に入らないもの: ネイティブのREPL (jit-repl)。`par`の右の子を空いたworkerで動かすことと、joinの手伝い (native-par)。Cのシンボル`eml_run_pending` (native-aot)。eml_rtは変えない見込みである (付録01のR-9)。要るとわかったら計画に載せ、N-29のゲートを通す

## 4. 決定

IDは付録05のものをそのまま使う。全文は付録05にあり、食い違う所は付録00に従う。

- この段が頼る契約の決定 (付録01): §1.3の「Task layer」と「Stacks」、§1.4、N-5、N-9、N-11、N-12、N-17、N-18、N-20、N-25、N-28、N-32、N-38、N-39、N-41、N-42、N-43。付録00のU-9 (スタックの配置)、U-10 (`BuriedRun`はN-43の違い(3))、R-7、C-7、C-11 (この段で外す使い方の誤り。`EML_GUI`はC-11)。C-10 (CLIの文は段を名指さない)、C-6 (データのシンボル`c:`)
- **D-7** eml_schedは、実行系に依らない部分と小さな`Exec`を持つ。ループを回す部分は実行系ごとに持つ。移すもの (先にVMだけのコミットで、バイト単位で同じ): `workers.rs`の`Run`、`Slot`、`Notice<E>`、`Ready<E>`、`Entry`、`Workers`、spawnとjoin、止める手順。`Scheduler<P>`のうち実行系に依らない半分を`WorkerCore<P>`として。`monitor.rs`、`jobs.rs`、`counters.rs`。空きの待ちとデッドロックの判定。メインのworkerの`Park`のループと`Pending`のguard。`join_outcomes`と`reraise_mask`。`ffi`のsubmitとtake。asyncの行の本体。`Exec: GateHost`は`job`、`accept_child`、`joined`、`limited`、`token`を持つ (付録05のD-7の例示)。`Current`は`{ cell, worker, depth_offset, site, outcome, exit, counted, added }`で、ネイティブでは`depth_offset = 0`である
- **D-8** asyncの行: `extern_rows!`の`task`の節を、共通の文法の行にする。行ごとにエントリの識別子を書く (`fn AsyncSleep as eml_x_AsyncSleep (cx, ms: int) -> unit { .. }`。R-1)。文脈は`cx: &mut AsyncCx<'_, E>`で、本体は`Result<RowEnd, RowFault>`を返す。この段は4つの展開 (`defs`、`entries`、`vm_arms`、`names`) に`task`の腕を足す
- **D-9** ネイティブのタスクはエントリで、切り替えはエントリの間でだけ起こる。エントリの間では`Ctx.evv`は`()`で、何も所有しない。用意のできた項目を動かす手順は、`cur := item`、`switch_task((), cur.worker, 0)`、`limits::enter_task`、`enter`である。ネイティブでは`Seeded`は使い方の誤りである (N-43の違い(2))
- **D-10** 入れ子の`Async.run`: `run_raw`のwrapperの中のLIFOのループにする。いちばん内側でない段へのトークンはその段を閉じ、内側の段が戻ったときに処理する。共有の判定は、入れ子のループで空いているworkerを止まっているものと数える。知らせるworkerの下に閉じて埋もれた段があれば、誤りは`RunFault::BuriedRun`で、文は`deadlock: an Async.run waits under a nested Async.run on the same worker`である。止まったままになることはない。入れ子のエントリは、スレッドの深さの余りを分け合う。これはN-43の違い(3) (U-10) で、この段の利用者に見える意味の項目である。入れ子のループを足すコミットで、spec/native.mdの「VMとの違い」の3とstdlib.mdの「`Std.Async`」を書く
- **D-11** `par`: `pair = call eml_nrt_par(ctx, f, g, site)`の後に`After::Call`を置く。`eml_nrt_par`はデータの語を返し、失敗はfatalの道だけである (R-8)。forkの印と`fork_evv`の後、左の子、右の子の順に、それぞれ自分の`JmpBuf`を持つ`enter`で動かす。子の`Err(Fatal)`はそのまま返す。abortは`reraise_mask`と`enter(reperform)`で親に投げ直す。`child_abort`は`eml_nrt_child_abort(ctx, ev, c)`になり、その後に`After::Never { raise: None }`を置く
- **D-12** `compute`のjobは、フレームのない`Child`の項目である。abortの結果を持つ`take_job`は、投げ直しを行い、要求`AbortStarted`を置いて`Fault::Engine`を置く。そのあと`eml_nrt_failed`が`RAISE_DONE`を返す
- **D-13** blocking C: submitとtakeの本体を、VMの`ffi.rs`から`eml_sched::ffi`へ移す。ネイティブでは`eml_x_`の約束に従う手書きのwrapper`eml_x_c_submit(ctx, cfn, argv)`と`eml_x_c_take(ctx, cfn, token, argv)`の2つになる。`cfn`はjit-externsのデータのシンボル`c:<Module.f>`のアドレスである (C-6。付録05の`eml$cfn:`はこれに置き換わる)。そのためこの段はデータのシンボルを足さない。2つの間の待ちは`Std.Async.io_wait`の行である
- **D-14** タスクの上限: `Native`に欄を足さない。`eml_nrt/src/limits.rs`に`enum Class { Stops, Task, Pending, Aborting { pending } }`と`limits::set`を置く。`limits::set`は、スレッドの開始より後で`stack_limit`を書く唯一の関数である (`Stops`と`Task`は`real`、`Pending`は`usize::MAX`、`Aborting`は`hard`)。配置はjit-coreのもので (U-9)、この段は定数を足さない。`eml_nrt_safepoint`は、VMの`limit_hit`の順の9つの手順に従う (付録05のD-14)
- **D-15** 入れ子のenterを越えるfatalな誤りと止まり: `eml_fatal(`が現れるのは、eml_nrtの`entries.rs`と`enter.rs`だけである (R-10)。入り直すservice (`eml_nrt_par`) は子の`Err(fatal)`を返す。入り直す行 (`run_raw`、`take_job`) は、worker structに要求`Propagate(Fatal)`を置いて`Fault::Engine`を置き、`eml_nrt_failed`の手順1がそれを返す。入り直すフレームはどれも、`enter`を越えて`Copy`の値だけを持つ (N-12)
- **D-16** worker structと別名: `enter`を越えて生きる`&`や`&mut`の`Worker`と`Ctx`はない。触るときはいつも`with_worker(ctx_ptr, |w, ctx| …)`を通す。Miriのテストは`loops::a_row_inside_an_entry_reborrows_the_worker`である
- **D-17** メインのworker: ネイティブの`Pending::run`はRustの関数`eml_nrt::run_pending(ctx: *mut Ctx<Fast>) -> Progress`である。Cのシンボル`eml_run_pending`はnative-aotで入る (N-8)。メインのworkerの`hard`は`stack_base + 2 MiB`である。スタックの底はOSに問い合わせて得る (macOSは`pthread_get_stackaddr_np`と`pthread_get_stacksize_np`、Linuxは`pthread_getattr_np`、Windowsは`GetCurrentThreadStackLimits`)
- **D-18** (jit-tasksの部分) `bench/async/scale.sh`と`bench/net.sh`に`--native`を渡すことは作業の単位の1つである。閉じるときに`par_tree`、`bench/async/scale.sh`、`bench/net.sh`を記録する
- **D-19** プロファイラのためのhook: タスクの帰属。公開している今のタスクの語`Slot.current`を、ネイティブのエントリの始めと終わりに書き、入れ子の段から戻ったときと`par`の子の後に戻す
- 費用のモデルと見送った最適化 (N-38): 付録05の§1.0 (タスクの切り替え、`par`、エントリの安全点) と§3.1 (workerのループごとに1回の`eml_enter`、workerごとの`fork_evv`のメモ)。書き直すときに、実行できる計画へ写す

## 6. 既存のコードの変更と費用

N-18の一覧 (付録05の§5.2):
- `eml_nrt_safepoint`の本体。`eml_nrt_failed`の手順1と`RAISE_DONE`。`eml_nrt_landed`の本体。`lower/safepoint.rs`で`ACTION_RAISE`を`eml$raise`へ回すこと (付録03の§2)
- `eml$apply$m`の`n < m`の腕のスタックの確かめ (`lower/apply.rs`の`define_apply`、jit-apply)。腕は入れ子にする前にスタックポインタを`stack_limit`と比べ、下なら`eml_nrt_safepoint(ctx, me, 0)`を呼び、`ACTION_CONTINUE`でないどの行動でもtrapする。補助の関数はそこで`clo`と`a_1..a_m`を所有し、後始末の道を持たないためである。この段の上限の種類の下では、これでプロセスが止まる。`Pending`は`stack_limit = usize::MAX`を置くので、どの`n < m`の腕もサービスに入り、サービスは`ACTION_RAISE`を返しうる。この段は腕に、深さだけの確かめ (またはほかの行動を返さないサービス) か、入口の`leave`のような、所有する`clo`と引数の後始末の道のどちらかを与える。そこでの誤りがどの場所を名指すかも決める。今は`<native code>`である。補助の関数は`Image.functions`に行を持たないためで、VMと違うならN-43の違いである
- `Worker`を広げること (`cur`、段、子の記録、要求の場所、`limits`)。jit-coreの`run`を共有のorchestration (`Separate`のseat) で置き換えること
- `extern_rows!`の`task`の節 (名前を行にする) と、4つの展開のその腕
- `--native`に1でない`--workers`、1でない`EML_WORKERS`、`--gui`、`EML_GUI`を付けたときのCLIの使い方の誤りを消すこと (R-7、C-7、C-11)
- `Image.runtime_entries`と`fork_plan`の静的なもの
- `Unsupported`と数える仕組みを消すこと
- テストの仕組みのworkerの数
- `eml_sched/testing`を消すこと (N-41)

費用: いちばん大きいのは、`Exec`の後ろへのVMの作り直し (付録01の§9のR-9) で、結果はバイト単位で変わらない。段が約25コミットを超えるなら分ける (U-S4-2)。

## 7. テストとテストの変更の種類

- 新しいテスト: MiriとTSanのループのテスト (`loops::`)。単位9と11の`par`、`compute`、上限のテスト。ネイティブの`async/`の1 workerでの流し。順に依らない`async`、`chan`、ネットのファイルを2と8 workerで流すテストの仕組みの流し (`WORKER_RUNS`)
- 種類(1):
  - U-S4-1の測定で見つかるファイルの`-- native: skip (<reason>)`と`# native: skip (<reason>)`の印。理由はどれも「VMとの違い」の3を引く。単位8の測定の後に、計画に1つずつ並べる
  - 上限の印を持つファイル: `max-depth`のファイルはN-43の(1)を引くjit-coreの印を残す。`max-bytes`だけで制限され、今は結果が同じになるファイルは印を外す (U-S4-3)
  - R-7、C-7、C-11の使い方の誤りを期待するjit-coreのCLIのテスト。1つずつ並べ、消すか、ネイティブでworkerの数とstubのGUIを確かめるrunのテストに変える
  - `Unsupported`のsnapshotのテストと数える仕組みを消すこと
  - `testing`のfeatureを使い、確かめる中身を公開のAPIで書けないテスト。消すか移し、理由を書く
- 種類(2): `crates/eml_native/tests/placement.rs`の`placement::the_stack_limit_is_set_once`は、`set_stack_limit(`の呼び出しを`run.rs`の1つから、スレッドの開始の所と`limits::set`の2つ (N-42) に変え、テストの名前を内容に合わせる。`docs/implementation/architecture.md`の「`eml_nrt`の内部」の`stack_limit`の規則も同じコミットで直す。上限の種類が`stack_limit`を書き換えるためである
- 種類(2): 数える仕組みを消すまでの、ネイティブのUIのsnapshot
- 種類(3): VMの部分をeml_schedへ移すこと。期待値をすべてバイト単位で保ったまま、fixtureの使い方を公開のAPIで書き直すこと
