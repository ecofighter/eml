# `local-free` の設計と計画

- 作成: 2026-11-03
- 基準: main @ 08a1e01 (worker-threads は 2c8de78 で入った。比べる前の表は 90147ff)
- 状態: 承認待ち。コードはまだ変えていない
- 段の種類: 機能を足さない実装の整理なので、roadmap の「段の列」には載せない (docs/future/roadmap.md の「進め方」)

## 1. 目的と完了の条件

worker-threads は、`eml_rt` の速いモードの局所の解放に、ブロックの持ち主を確かめる分岐を足した。その計画の基準 G-S2-9 は、増やしてよい分を1回の読みと1回の比較と分岐までとしていた。ところが `bench/rt.sh` の `free` は、1回の解放あたり約11命令増えた (1,827,880,474 → 1,937,605,652、10M 回)。この段では、増えた11命令の出どころを分け、コードが足した分を予算の内に戻す。コード生成単位の分け方で増えた分は直さずに記録する。

完了の条件は次のとおり。

- `Heap::free_box` の局所の解放の道が、1回の解放あたり 90147ff の 25 命令以下になる。数え方は 6 章の lldb の1回分の数え上げである
- `codegen-units = 1` で組んだ `rt_bench` の `free` と `list` が、同じ設定の 90147ff 以下になる
- `bench/run.sh` の実行の部分が、どの行も main から +2% を超えて増えない
- `crates/eml_rt/CLAUDE.md` の関門 (テスト、clippy、fmt、`cargo verus verify -p eml_rt`、verusfmt、Miri の2つの借用の規則と CPU の予算) を通る
- 既定の設定のビルドで残る差を、[計測の基準](../implementation/benchmarks.md) の「所見」に数値と原因つきで書く

`rt_bench free` の1回の繰り返し (`Heap::free_chain` の入口から次の入口まで) を lldb で1命令ずつ進め、関数ごとに数えた。

合計の差 11 は、`rt.sh` の差 (110M / 10M 回) と一致する。8a948ce7 の `Heap::free_box` の `if !self.core.pages.owns(h, Tracked(hdr)) { self.free_remote(h, finalizer); return; }` を `if false` にしただけの X1 で、`free` は 1,837,647,385、`list` は 1,223,183,807 に戻り、`map-reuse` (608,715,375)、`handle` (609,794,722)、`mask` (3,817,845,803) も 90147ff の値に戻る。11命令はすべて、この分岐1つから来ている。

### 2.3 `free_box` の +5 はコードの形による

90147ff の `free_box` は、破棄処理を呼ぶ道 (`blr`) のために callee-saved のレジスタを2つ退避し、ページの頭から級を読み、空きリストに積んでいた。main は、この前に持ち主の確かめを置いた。

- ページの頭の `sink` を読む (`ldr x8, [x20, #0x8]`)、`Pages` の `sink` を読む (`ldr x9, [x0, #0x28]`)、比べて分岐する。これで4命令である
- 破棄処理 `finalizer` を持ち主の確かめより前に求め、`free_remote` に渡している。そのため、ページの番地と `finalizer` が破棄処理の呼び出しをまたいで生き、退避するレジスタが1組増える (`stp`/`ldp` が1組増える)

持ち主の確かめを先に置くだけの形 (X2) と、ページの頭を一度に読む形 (X10) は、1回あたり 1 命令しか減らさなかった。退避の組が残るためである。`sink` を引数で渡す形 (X3) は 1 命令増やした。`drain` の中で確かめる形 (X5) は `free_box` を 25 命令に戻したが、`drain` が 4 命令増えた。

### 2.4 `free_chain` と `drain` の +6 はコード生成単位の分け方による

`free_chain` と `drain` のソースは 8a948ce7 で変わっていない。`codegen-units = 1` で出した LLVM IR も、main と X1 で同じである。それでも既定の設定 (release、16 単位) では、次の2つが変わる。

- `drain` が `free_box` の呼び出しの後で作業リストの長さとポインタを読み直す (+2)
- `free_chain` の2回目の `mem::swap` が、捨てる局所の `Vec` をスタックに書き戻し、`__rust_dealloc` を末尾呼び出しにしなくなる (+4。うち +1 は `codegen-units = 1` でも残る)

リンカの map で見ると、90147ff と X1 では `alloc_data`、`Ctx::evv_mask`、解放の連鎖が同じ単位 (cgu.0) にある。main では `evv_mask` が別の単位に移る。`mask` の1回分の内訳でも、`alloc_data` が +6 になる (引数2つの定数の伝播が外れ、`raw` と `lin` を実行時に計算する) のと `evv_mask` の +2 が、この分け方の変化と重なる。`codegen-units = 1` で組むと、main と 90147ff の差は `free` で 1回あたり +6.0、`list` で +5.0 で、ほぼ `free_box` の +5 と `free_chain` の +1 である。

| 設定 | 90147ff | main | X1 |
|---|---:|---:|---:|
| 既定 `free` | 1,827,727,910 | 1,938,358,028 | 1,837,647,385 |
| `codegen-units = 1` の `free` | 1,827,774,762 | 1,888,065,443 | 1,838,014,013 |
| `codegen-units = 1` の `list` | 1,223,928,456 | 1,274,112,107 | 1,222,296,014 |

これは [計測の基準](../implementation/benchmarks.md) の「`eml_rt` のインライン化」が書く脆さと同じ種類である。単位の分け方は計測のプログラムごとに決まるので、`rt_bench` の11命令はそのまま VM の数にはならない。

### 2.5 VM の差は平均 +0.47%

`bench/run.sh` の実行の部分 (`empty` を引いた命令の数) を 90147ff と main で比べると、40 行の平均は +0.47%、最大は `fib` の +1.60%、`list` は +0.97% である。c1762173 の表 (`list` 157,867,303 → 160,319,034) と同じ傾向である。

## 3. 決めたこと

### D-1: `free_box` を、持ち主の確かめを先に置いた葉の関数にする

- 決定: `Heap::free_box` を次の順に組み替える
  1. 検査モードの `count_id` は今の位置 (先頭) のまま
  2. `self.core.pages.owns(h, Tracked(hdr))` で持ち主を確かめ、ほかのヒープのページなら `free_remote(h)` を呼んで戻る。`free_remote` は破棄処理を自分で求める (今は `free_box` が求めて渡している)
  3. `M::CHECKED` か、`meta` が破棄処理を持つときは、`#[cold]` `#[inline(never)]` の新しい関数 (仮に `free_box_slow`) に任せて戻る。この関数は今の `free_box` の残り (破棄処理の呼び出し、検査モードの隔離、速いモードの `FREE_META`) をそのまま持つ
  4. 残る速いモードの局所の道は、ブロックの権限を外して `self.core.pages.free(h, Tracked(perm))` を呼ぶだけにする
- 理由: 速いモードの破棄処理のない局所の解放が、呼び出しを含まない葉の道になる。退避するレジスタがなくなり、持ち主の確かめの4命令を足しても 90147ff より短い
- 測った値: この形を手で組んだ木 (X17。証明は付けていない) で、`free_box` は1回あたり 22 命令 (90147ff は 25、main は 30)。`rt_bench` の数は次のとおり

  | 計測 | 90147ff | main | X17 |
  |---|---:|---:|---:|
  | `free` | 1,827,727,910 | 1,938,358,028 | 1,857,803,431 |
  | `list` | 1,222,613,686 | 1,323,104,742 | 1,246,398,477 |
  | `map` | 1,812,459,731 | 1,909,321,000 | 1,823,552,522 |
  | `map-reuse` | 610,292,979 | 698,827,614 | 692,236,448 |
  | `handle` | 607,810,125 | 664,349,713 | 640,466,691 |
  | `mask` | 3,808,202,698 | 3,998,659,723 | 3,918,627,720 |
  | `codegen-units = 1` の `free` | 1,827,774,762 | 1,888,065,443 | 1,808,285,085 |
  | `codegen-units = 1` の `list` | 1,223,928,456 | 1,274,112,107 | 1,194,266,144 |

  `dup`、`append`、`perform`、`yield`、`poll` は main から 0.5% 以上は動かない。`empty` は 16,446,442 から 17,102,147 になった (+0.66M で、繰り返しを持たない計測)。VM では、同じ形 (`owns` の代わりにページの頭を写して比べた X11。`rt_bench` の数は X17 と同じ) が main と比べて40行の平均 +0.00%、範囲は -0.99% (`apply_float`) から +1.54% (`par_tree`) だった。X17 そのものの VM の数は、実装の段で測る
- 証明: `free_box_slow` に今の `free_box` と同じ `requires` と `ensures` を付け、今の本体の証明をそのまま移す。速いモードの道の証明は、今の `!M::CHECKED` の枝の証明 (`lemma_block_released` ほか) を使う。`free_remote` の `requires` は変えない
- コメント: `free_box` の組み方の理由 (葉の道に保つこと) を、「所見」の新しい見出し (D-2) を引いて書く。見出しは組み替えと同じコミットで足す
- リポジトリに残す所: docs/spec/object-model.md の「別のスレッドからの解放」は、持ち主の確かめと破棄処理の順を書いていないので変えない。実装の段で文面を確かめ、順を書いている文があれば同じコミットで直す

### D-2: コード生成単位の分け方で残る差は直さず、「所見」に書く

- 決定: X17 の後も既定の設定で残る差 (`free` は1回あたり約 +3、`list` は約 +2.4、`map-reuse` +13%、`handle` +5%、`mask` +3%) は、`rt_bench` の単位の分け方の差として受け入れる。「所見」に「局所の解放の費用とコード生成単位」の見出しを足し、2 章の内訳、`codegen-units = 1` の数、6 章の数え方、下の却下した案を書く
- 理由: 単位の分け方は計測のプログラムごとに違い、VM の数には出ていない (2.5 節)。`rt_bench` の分け方に合わせた手当ては VM を悪くした (次の項)
- 却下した案
  - `alloc_data` に `#[inline]` を付ける (X15、X16): `rt_bench` では X17 と合わせて全計測が 90147ff 以下になった (`free` 1,807,205,471、`mask` 3,367,405,994)。しかし VM の実行の部分が main から +0.8%〜+5.2% 増えた (`par_tree` +5.18%、`fib` +4.68%、`list` +4.06%)
  - `eml_rt` を `codegen-units = 1` で組む: `free` は下がるが、`map-reuse` が 608M から 1,119M になる
  - `Pages` に8バイトの詰め物を足して `Heap` の `work` の位置を 90147ff の位置 (0x3c0) に戻す (X6): `free_chain` の命令は変わらなかった
  - `free_remote` の本体を総称でない関数にする (X13): X11 と同じ数で、単位の分け方は戻らなかった

### D-3: G-S2-9 の確かめ方は、関数ごとの1回分の数にする

- 決定: 局所の解放の予算は、`rt.sh` の合計でなく、6 章の数え方で `free_box` の1回分を数え、`codegen-units = 1` の `rt_bench` の `free` と合わせて確かめる。D-2 の見出しにこの数え方を書く
- 理由: `rt.sh` の合計は単位の分け方で 1回あたり 5〜6 命令動き、予算 (2命令) より大きい。8a948ce7 のコミットのメッセージが測った VM の `list` (x86_64 の cachegrind で1回の解放あたり約 +1.0) も、同じ理由で `rt_bench` とは別の数になる

## 4. テストの変更

- 成否の変更、期待値の変更: なし。`crates/eml_vm/tests/bench.rs` の `RunStats` は仕事の数を測るので、命令の並びが変わっても値は変わらない
- 足すテスト: `crates/eml_rt/src/heap/tests/trusted.rs` に、ほかのヒープの `Foreign` の値を別のスレッドで最後に手放し、破棄処理がちょうど1回走って持ち主が取り込むことを確かめるテストを、両方のモードで足す。今は、ほかのヒープのページの物体で破棄処理を呼ぶ道を通るテストがない (`free_remote` に破棄処理を求める処理を移すのはこの道である)。このテストは main でも通る。組み替えの前に入れ、組み替えた後も通ることを確かめる。Tree Borrows の Miri の予算は、`trusted` のテスト1本 (両方のモード) につき 5 秒まで増やせる (`crates/eml_rt/CLAUDE.md`)

## 6. 計測の方法

- 合計: `cargo build --release -p eml_rt --example rt_bench` の後、`env -u MallocNanoZone /usr/bin/time -l target/release/examples/rt_bench <計測>` を3回走らせ、`instructions retired` の中央値を取る。Claude Code の shell は `MallocNanoZone=0` を置くので外す (c1762173 のメッセージ)
- `codegen-units = 1`: 同じ手順を `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1` で、別の target ディレクトリに組む
- 1回分の内訳: lldb の Python API で、ASLR を切って起動し、`main` で止まってから、数える関数 (`free` では `Heap::free_chain`、`mask` では `Ctx::evv_mask`) の番地に無視の回数 1000 の breakpoint を置く。止まったら breakpoint を外し、同じ番地に戻るまで `StepInstruction` で進め、各 PC の関数名で数える。起動前に番地の breakpoint を置くと解決されず、止まらない
- 単位の割り当て: `cargo rustc --release -p eml_rt --example rt_bench -- -C link-arg=-Wl,-map,<file>` の map で、関数がどの `cgu.N.rcgu.o` にあるかを見る
