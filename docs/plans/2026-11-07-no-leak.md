## 1. Goal and success criteria

- Goal: `eml_vm` stops leaking heaps on purpose.
  - A `blocking` C call no longer lends heap memory to a pool thread. Abandoning a hung call is then not an error: the run ends with its own outcome, and the `Machine` recovers and frees its heaps as after any run.
  - A driver that keeps ops after quiesce is dropped before any heap is touched.
  - A panicked worker's heap is released pages-only, after every worker has joined.
  - `poisoned` and everything built on it go away.
- Success criteria:
  - `ffi_abandon::` and the `worker_panic::` tests run under AddressSanitizer with LeakSanitizer on (x86_64 and aarch64 Linux CI), with no `detect_leaks=0` step.
  - `git grep -n -e is_poisoned -e poisoned_fault -e 'CompileError::Poisoned' -e printed_poisoned -e 'Flow::Poisoned' -e 'fn kept_pending' -- crates` → no output.
  - Every existing test passes, with only the test changes listed in §6.
  - eml_rt's gate passes after `Heap::abandon` is added.
  - Programs that do not call `blocking` functions do no extra work on the fast path, and the `RunStats` snapshots in `crates/eml_vm/tests/bench.rs` stay byte-identical.

## 2. Background (facts the decisions rest on)

- `marshal` passes raw heap pointers to C: `unboxed_ptr`, `unboxed_ptr_mut` and `text_payload`, plus `CHandle.ptr`. The `Op::Job` closure of a `blocking` call owns only `args: Vec<u64>` (crates/eml_vm/src/ffi.rs:68-108, 172-198) [V].
- `abandon_jobs` removes the slot and forgets the ticket, so the thread keeps running. `abandoned` is read only by `pending()` (crates/eml_io/src/driver/mod.rs:664-683, 931-933; field :193, :287) [V].
- `Driver::drop` waits for, or aborts on, every op that lends memory: IOCP overlapped ops and file jobs. An `Op::Job` is not such an op (docs/spec/vm.md:557) [V].
- std pool jobs (`jobs::submit`) hold their inputs by value (crates/eml_vm/src/jobs.rs:1-3) [V per the advice; not re-read].
- `FfiTake`'s operands already list the object arguments after the record and `Wake` (crates/eml_vm/src/op.rs:409-414; vm.md 「`blocking` の呼び出し」). So `take` can reach every `MutUnboxedArray` argument at take time [V].
- `text_payload` exposes the payload with no NUL, and C gets the length as a separate `Int` (object-model.md:437; declarations.md table) [V]. The advice said "NUL included"; that was wrong, and no NUL is copied.
- A worker's driver is dropped on its own thread right after quiesce (`retire_driver`, crates/eml_vm/src/workers.rs:1339-1351). Worker 0 in a merged run returns its driver to `Machine` (`entry_body`, crates/eml_vm/src/lib.rs:1336-1354) [V].
- `RunClock::Injected` cannot make a driver (`unreachable!`, crates/eml_vm/src/driver.rs:70) [V].
- `is_broken` covers `VmFault::Driver(_)`. The REPL ends with exit code 1 after a broken outcome and does not call `close` (crates/eml_cli/src/terminal.rs:110-111) [V].
- `Machine::close` decrefs roots, then runs `check_heap` and `at_close`. Nothing in it is specific to poisoned except the early return (lib.rs:893-906) [V].
- `on_own_ctx` leaks a panicked worker's `Ctx` (workers.rs:925-969) [V].
- When worker 0 itself panics, the panic unwinds out of `run_entry` before `poisoned` is set. `Machine::Drop` then runs the full `Heap::drop` on that mid-state heap. Merged runs: the unwind goes through `entry_body` and `thread::scope`. Separate runs: through `join` and `resume_unwind` (lib.rs:1131-1133) [V]. This is a latent hazard today; Rule C below also closes it.
- In `entry_body`, a panic in worker 0 between spawning workers and joining them drops `handles` while unwinding. That can drop a joined worker's returned `Ctx` before the other workers have exited [I: from `ScopedJoinHandle` semantics; the scope joins only after the closure unwinds].
- `Heap::drop` = `reclaim` + `finalize_all` + `release_region`, then the field drops, including `Pages::drop` (crates/eml_rt/src/heap/walk.rs:966-978) [V]. `Drop for Heap` is trust row T4 in crates/eml_rt/src/trust.rs:239 [V].
- `both_modes!` makes two tests per name (crates/eml_rt/src/heap/tests/mod.rs:10-19) [V].
- LeakSanitizer does not run on arm64 macOS (commit 34e717c5). So local runs on this Mac check memory errors only; leaks are checked only on Linux CI [V: commit message].
- The fixtures `rs_gate_open`, `rs_gate_wait` (10 s watchdog), `rs_handle_new`, `rs_handle_wait`, `rs_handle_free` and `rs_frees` exist in crates/eml_vm/tests/common/c.rs:225-300 [V].

## 3. Decisions

### D-1: a `blocking` call copies its arguments (Rule A)

- `ffi::job` builds the job's arguments by value:
  - `UnboxedArray`: a job-owned `Box<[u64]>` copy of the elements, with the length from `Heap::unboxed_len`.
  - `MutUnboxedArray`: the same kind of copy.
  - `Text`: a `Box<[u8]>` copy of exactly the bytes `text_payload` exposes. The length comes from `Heap::string` or `Heap::bytes`, depending on the object's kind. No NUL is added.
  - Integers and floats: as today.
- The slot of each copied argument points at element 0 of its copy. An empty array gets a dangling but aligned pointer that C never reads (the same rule as today).
- The closure returns `CAnswer { ret: u64, back: Vec<Box<[u64]>> }`, where `back` holds the `MutUnboxedArray` copies in parameter order. It drops the other copies when it returns.
- `ffi::take` writes each `back[i]` into its `MutUnboxedArray` argument before it unmarshals the result. The argument comes from the take operands: `unboxed_ptr_mut` on the owner worker, then `copy_nonoverlapping`. It writes back on both the `WOKE` and the `CANCELLED` branch, because C's side effects remain. With no answer (`Err(e)`: the job panicked or could not run), it writes nothing back.
- Handles: `CHandle` becomes `CHandle { cell: Arc<HandleCell> }`, where `HandleCell { ptr, dtor }` has the `Drop` that calls the dtor.
  - The job captures an `Arc` clone of the cell for every handle argument and passes `cell.ptr`.
  - The dtor runs once, when the last `Arc` goes away. Normally that is the freeing worker. When an abandoned call outlives the object, it is the pool thread right after C returns. If the call never returns, the dtor never runs.
  - `unsafe impl Send + Sync for HandleCell`. SAFETY: the VM never dereferences `ptr`, and the dtor runs exactly once.
  - The advice's `lent: AtomicU32` counter is rejected. A job that finishes within the budget but is never taken (its task was dropped by `exit`) would never decrement it, so that handle's dtor would never run. The `Arc` has no such case.
- These copies are not counted in `string_bytes_copied` or in any other `RunStats` field.
- Synchronous `Op::Ffi` calls are unchanged: they still lend heap pointers for the duration of the call.
- Conformance:
  - The existing UI tests `tests/ui/run/async/blocking_fixture_*.em` and `tests/ui/run-fail/async/blocking_fixture_*.em` keep byte-identical output.
  - The `crates/eml_vm/tests/ffi.rs` tests keep their assertions, apart from the §6 item.
  - The closure passed to `Op::Job` captures no heap pointer: by review of `ffi::job`, no `unboxed_ptr*` or `text_payload` value flows into the closure, only copies.

### D-2: abandoned jobs are not pending

- Remove `Driver::abandoned` and its term in `pending()`. Add no accessor.
- An abandoned job still holds one of the 24 `Op::Job` threads until it returns or the driver is dropped. This is documented as the cost of a hung call.
- Change the trait doc of `IoDriver::quiesce` and `pending` in crates/eml_rt/src/driver.rs:285-306 to "an abandoned job is not counted in `pending()`; its late answer is dropped".

### D-3: a driver that keeps ops after quiesce is dropped at once (Rule B)

- Every place that quiesces a driver and then sees `pending() > 0` drops that driver on its own thread before any heap is touched:
  - worker `k` and the main worker: `retire_driver`, already done;
  - worker 0: `entry_body` returns `None` instead of the driver when its `pending() > 0`, so the driver is dropped right there;
  - `Machine::recover`: after its `quiesce`, `pending() > 0` sets `self.driver = None`.
- In both worker-0 cases, `Machine` also sets `self.run_clock = None` when it is `RunClock::Injected`, so the next run builds a driver from `clock`. Real and virtual run clocks are kept, so time stays continuous.
- The run's outcome when any driver kept pending ops:
  - An exit code is set and the result is `Ok(())` or `Stopped(Ended)` → `Ran::Abandoned(Finished { exit: Some(n), .. }, cause)`. The `Machine` recovers as after any `exit`; `close` then works normally. Today this path returns `Ran::Done` without recovery.
  - The result is an error → that error. `run_recovering` recovers when the error is not broken; today recovery is skipped.
  - The result is `Ok(())` with no exit code → `VmFault::Driver(KEPT_PENDING)` at `Finish`: unchanged text, broken, no recovery.
  - In every case Host output is flushed first, as today.
- After a broken error, `close` and `Drop` follow the general rule:
  - `close` touches the heap: it decrefs roots, then runs `check_heap` and the leak check. This is memory-safe because no driver is left. It may return `Leak`, because the broken run was not recovered.
  - The REPL never calls `close` after a broken outcome.
  - `Drop` drops `driver`, then `others`, then `ctx`. It frees everything.
- `KEPT_PENDING` stays in error.rs. `RuntimeError::kept_pending()` is deleted (its only user was the terminal).

### D-4: what happens when a `blocking` call is abandoned (real clock, call outlives the budget)

| Ending | `run` result | Recovery | `close` | REPL | `eml run` |
|---|---|---|---|---|---|
| Normal end | cannot happen: `Async.run` waits for its tasks and `Finish` requires no records, so the run waits for the call (unchanged) | — | — | — | — |
| `exit n` (any task) | `Ok(Finished { exit: Some(n) })` | yes | `Ok` (checked mode: leak check as usual) | prints nothing extra; session continues | exits with `n` |
| Ctrl-C / SIGTERM | `Err(interrupted/terminated)` | yes | `Ok` | `interrupted`; session continues | 130 / 143 as today |
| Fatal error, deadlock, memory limit, uncaught runtime error | that error | yes if not broken | as after that error | as after that error | as after that error |
| `execute` | the run's result; `close` is always called (the `is_poisoned` early return is deleted) | — | — | — | — |

- After the run, the hung thread keeps its copies and its handle `Arc`s. When it returns, the `Pool` inbox or the dropped driver discards the answer, and the last `Arc` runs the handle's dtor on that thread.
- `RunStats` and `--stats`: unchanged; no `abandoned_jobs` field. Reasons: a new field would rewrite every `RunStats` snapshot and `--stats` output (kind 2) for an event that is not program work, and the visible cost (the budget delay) is documented.

### D-5: a panicked heap is released pages-only (Rule C)

- eml_rt:
  - `Heap` gets a field `abandoned: bool` (false in every constructor, recovery's new heap included).
  - Add a verified `pub fn abandon(&mut self)` inside `verus!` that sets it, with `ensures` stating that every spec view is unchanged. Add a `Ctx::abandon(&mut self)` that forwards to it.
  - `Drop for Heap`: if `abandoned`, skip `reclaim` and `finalize_all`; still call `release_region` and let the fields drop, so `Pages::drop` returns the pages, refunds `Control` and frees the `RemoteSink`.
  - No new trusted code: `abandon` is verified, and the `Drop for Heap` row T4 keeps its name. trust.rs needs no new row [I: `abandon` has no `external_body`; the T4 scan keys on `Drop for Heap`, which stays].
- eml_vm:
  - `WorkerExit<M> = Result<Retired<M>, Panicked<M>>` with `Panicked<M> { payload, ctx: Option<Ctx<M>> }`. `on_own_ctx` calls `ctx.abandon()` on the panic path and returns the `Ctx` instead of leaking it. `ManuallyDrop` leaves `on_own_ctx`.
  - Worker 0 (`entry_body`) runs everything from spawning workers 1..N-1 up to its explicit `join` loop under `catch_unwind`. On a panic it:
    - drops the `Shutdown` guard, which raises `END` and wakes everyone;
    - joins every worker explicitly;
    - calls `ctx.abandon()` on its own `Ctx` (the `Machine`'s);
    - records the payload in `body.panic`;
    - drops its `Scheduler` and driver without `quiesce` (`Driver::drop` waits for or aborts on memory-lending ops);
    - returns normally.

    So a worker-0 panic never crosses `join` or `thread::scope`, and no `Ctx` is dropped before every worker has joined.
  - `Body` and `Scheduled` get `abandoned: Vec<Ctx<M>>`, filled from `Panicked.ctx`. `end_run` does not reclaim or read stats from them.
  - `Machine` gets `abandoned: Vec<Ctx<M>>` and `panicked: bool`. In `run_entry`, when `scheduled.panic` is set: move `others` and `abandoned` into the `Machine`, set `panicked`, `resume_unwind`.
  - As a backstop, `run_entry` wraps `run_scheduled` in `catch_unwind`. A panic that still reaches it (Machine-owner code in a separate run, or `end_run`) is handled as follows: `self.ctx.abandon()`, set `panicked`, `resume_unwind`. When it is caught, every scoped thread has been joined.
  - A `Machine` with `panicked` panics with `"a Machine is used after a run panicked"` in `load`, `run`, `run_shown` and `close`, and does nothing else. `write_line` still writes, because it touches only the Host. Reason: the panic unwinds instead of returning an error, so a caller who catches it holds a `Machine` whose worker-0 heap may be abandoned. A panic keeps every safe method sound with no new error variant.
  - `Machine::Drop` order: `driver`, `others`, `abandoned`, `ctx`. `ctx` is a plain `Ctx<M>`; `ManuallyDrop` leaves `Machine`.
- Accepted residual (user decision): the Rust payloads of the `Foreign` objects on a panicked heap are not finalized.
- Conformance:
  - `seat::worker_panic::*` and `pinned::worker_panic::*` keep their assertions.
  - The Linux ASan legs run them with leak detection on.
  - The new eml_rt trusted test shows that `abandon` runs no finalizer and leaks nothing under Miri.

- LSan risk and fallback: LSan should treat a hung thread's job copies as reachable from its stack, and the tests open every gate before they return (testing.md:286 rule 2) [I]. If a Linux ASan leg still reports a leak:
  - From `ffi_abandon::`: restore a separate `ffi_abandon::` step with `ASAN_OPTIONS=detect_leaks=0`. Add one sentence to testing.md 「AddressSanitizer」: "a hung call's job copies may still be live when the binary exits; the heaps are freed". Keep `worker_panic::` in the normal step.
