## 1. 目的と成功の基準

- 目的
  - 1つの worker の VM の上で `par` と `both` を動かす。`std/Par.em` の `pub extern par : (Unit -> <never e> a) -> (Unit -> <never e> b) -> <e> (a, b)` は、`<never e>` を書いた最初の extern である
  - fork で右の子の閉包に印を付け、join で移し戻す。論理的な worker ID で、検査モードの所有者の検査を `par` の子に働かせる
  - 子の `never` の操作の中断を、いちばん左のものから親で起こし直す
  - スケジュールの方針として、逐次 (`--sched sequential`) と seed で決まる方針 (`--sched seeded:<n>`) を入れる
  - 子は `Lin` の値を捕まえて消費でき、`Lin` の値を返せる
- 成功の基準 (確かめ方は 9 章)
  - `tests/ui/{run,run-fail}/par/` の UI テストが、逐次と2つの seed (1 と 2026) で同じ出力になり、seed ごとに横取りが1回以上起きる
  - `par` の子に `IO` を起こす関数を渡すと E2020 になる
  - fork の印付けを外すと `WrongOwner` に、join の移し戻しを外すと `TransferLeak` になる。どちらも常設のテストが捕まえる
  - `par` を使わないプログラムの `RunStats`、Core IR と LIR の書き出し、`unwind_points` は1つも変わらない
  - 全体の検証のコマンド (9 章) がすべて通る

## 3. 背景

詳しい事実と出どころは付録にある。ここには、どのタスクでも前提にする事実だけを置く。

- `eml_rt`
  - `share(w, receiver)` (crates/eml_rt/src/heap/share.rs:2370) は Verus で証明してあり、`lin` ビットの物体そのものの所有者だけを移す。テストのほかに呼ぶ所はない。証明は share.rs の 2447 行である
  - 移し戻しの歩き、`TransferLeak`、論理 ID ごとの数、ID の割り当てはない。`Heap.worker: u32` と `set_worker` (heap/mod.rs:155、:754) はある。検査モードの所有者は前置きの最初の u32 にあり (heap/check.rs:182-205)、`WrongOwner` は rc > 0 の物体だけを確かめる
  - `HeapError` は 12 バイトである。`{u32, u32}` の形の誤りを足しても 12 バイトのままである
  - 回復は rc < 0 の物体を `Unrecoverable` で断る (heap/recover.rs:644)
  - `Ctx` は `heap, evv, yielding, roots, control, max_depth, max_evv, stats, host` を持つ (heap/ctx.rs:814)。`evv_get` は `dup` し、`evv_set` は古い evv を `decref` する
  - 基点での測った値: `cargo verus verify -p eml_rt` は `1043 verified, 0 errors` (37 s)。`cargo nextest run -p eml_rt` は 637 本。Miri の `trusted::` は 108 本で、`user` は Stacked Borrows で 19.8 s、Tree Borrows で 24.4 s
- VM
  - `Task` (crates/eml_vm/src/vm.rs:17-34) を作るのは `Machine::run_entry` だけで、`vm::run` は `step` を回す。タスクの切り替えはない
  - 安全点は呼び出し、戻り、自分への末尾の跳びなどで (vm.rs の `ctx.poll(task.depth())`、vm.md:145)、`Stop` は `Interrupted | DepthLimit | MemoryLimit` である
  - extern は `Ctx` しか受け取らず、閉包を呼べない
  - 巻き戻しは landing の evidence で着地点を決める (vm.rs:677-741)。extern の失敗は `abort_to` (vm.rs:861) が evidence を探し、なければ実行時エラーにする
  - `RunStats` は 13 の欄で、検査モードでだけ数える。crates/eml_vm/tests/bench.rs が 40 本の bench の値を丸ごと固定している
- 前段と中段
  - `<never e>` は extern の宣言にも書け、E2020 まで通る (付録の probe で確かめた)
  - extern の表と std の宣言を結ぶ試験 (`eml_hir` の `every_extern_function_is_declared_once_in_std`、`eml_core_ir` の `faulting_rows_carry_panic`) は、開いた row を断る
  - 型検査は extern の引数の型変数を `Unr` に固定する (eml_types check/mod.rs:719-726)
  - `par` の呼び出しには型検査が `mask` を記録する。今の translate は extern の呼び出しの mask を断言で断る (translate/expr.rs:395)
- テストと CLI
  - UI テストは run 473 本、run-fail 37 本、check-fail 220 本で、run と run-fail は検査モードの後に速いモードで流す。`ui::run` は並列で 0.78 s、1本の直列で 4.25 s、1ファイルは 0.036 s 前後である
  - 走らせる口は `eml_cli::execute(&Program, &RunConfig, HostRef)` で、`RunConfig` (`#[non_exhaustive]`) は `debug_heap` と `control` を持つ
  - CLI の `split_script_args` (crates/eml_cli/src/main.rs:114-124) は、`run` の後で `-` で始まらない最初の引数をファイルとみなす。そのため `run --sched seeded:7 main.em` は今の規則では `seeded:7` をファイルと読む

## 5. 決めたこと

### 5.1 長く守る方針

実装でこれらと食い違う所が出たら、止めて報告する。

#### D-1: `par` の表し方

- 決定
  - `std/Par.em` に `pub extern par : (Unit -> <never e> a) -> (Unit -> <never e> b) -> <e> (a, b)` と、eml で書く `pub both` を置く。`par` は Prelude から出さず、`import Std.Par` か `import Par (par, both)` で使う
  - extern の表の行は `Extern::Par = kinded("Std.Par.par", &[TObj, TObj], &[Unr, Unr], Obj, Unr, Purity::Pure)` である。行は std の宣言を型検査器に結ぶためだけにあり、`Rhs::Extern` にはならない
  - translate は `par` の呼び出しを `Rhs::Call { call: Call::Par { left, right, pair, at }, mask }` にする。`pair` は `tuple_layout(2)` の `TUPLE` の構築子である。結果は組の型 (`obj` か `struct`) にそのまま束ね、struct なら box の挿入が `obj` からの `unbox` を足す。`$externN` の包みも同じ本体を持つ
  - `Call::Par` は末尾呼び出しにならず、巻き戻しの地点 (`Abort::Always`) で、VM の `Op::Par { dst, at }` になる
  - 子の中断は `prim child_abort(ev, f, t)` で表す。引数の Repr は `[Obj, TObj, TObj]`、借用は `[true, false, false]`、印は `[Unr, Unr, Poly] -> Unr` で、VM の `Op::ChildAbort` になる
  - 新しい組み込みの pc `CHILD_DONE = 2` を `Finish` (0) と `ApplyRest` (1) の隣に置く
  - `both` は `par` と独立した eml の関数である。「逐次の版も1つの実装として持つ」(multicore.md の「VM の並列化の備え」の4) は、`--sched sequential` が同じ fork と join の道を通ることで満たす
- 理由: extern は閉包を呼べない。`Call::Clause` と同じく呼び出しの一種にすれば、mask の仕組みと巻き戻しの表をそのまま使える
- 却下した案: `run_extern` で `par` だけを特別扱いする形 (extern は `Ctx` しか持たない)、2つの値を返す `Call::Par` (Core IR に複数の値の束ねがない)、`Rhs::Par` (mask の仕組みを失う)、translate で unpack と `con` を書く形 (形が1つ増え、組ごとに確保が増える)
- 影響する範囲: Core IR、LIR、VM、std
- 見直す条件: 2つより多い子の `par`、または `fork` と `join` を関数として出すとき
- リポジトリに残す所: core-ir.md、lir.md、vm.md、stdlib.md の各節。T-7、T-9、T-11 が書く

#### D-2: 子の evidence

- 決定
  - ロードのたびに凍結するもの: `fork$E.op_i` がすべて名前で引ける never-only のエフェクト `E` ごとの表 (`Data(tag 0)` に即値 `&fork$E.op_i` を並べたもの) と、`Panic` の fork evidence `[table_Panic, 即値 0, ()]` を持つ凍結した節点 1つ (末尾)。引けるエフェクトの集まりが増えたロードで作り直す
  - fork ごとに作るもの: mask を当てた後の親の `evv` を頭からたどり、`Panic` を除く never-only のエフェクトの evidence ごとに、深さ `d` (そのエフェクトの evidence のうち何番目か、0 から) を状態の欄に持つ fork evidence `[fork_tables[E], 即値 d, ()]` と節点を順に作り、凍結した末尾につなぐ。該当する evidence がなければ子の `evv` は凍結した末尾そのもので、確保しない。作ったら `dup` し、`share(head, child)` で印を付ける
  - 子の中で `E` の evidence を探すと fork evidence が見つかり、その節は `fork$E.op` である。`fork$E.op` は引数を詰めて `prim child_abort(ev, &reperform$E.op, t)` を呼ぶ。VM は `ev` から `(E, d)` を読む
  - 起こし直しでは、`d > 0` なら、`complete_join` が親の文脈で `w = ctx.evv_get()`、`m = ctx.evv_mask(&[(E, 0, d)], w)`、`heap.decref(w)`、`ctx.evv_set(m)` の順に `evv` を mask してから `reperform$E.op(t)` を呼ぶ。コードの `mask` の包み (core-ir.md の「`mask` の包み」) と同じ基本操作である。`evv_set` は `Ctx` の持つ親の `evv` の参照を手放すが、`m` は親の列の後ろを共有するので、届く物体は生きたまま残る。`switch_task` は使わない。`E` は never-only なので `reperform$E.op` は戻らず、返された親の `evv` を入れ直す時がないためである。起こし直しは join ごとに1回なので、切り替えで `RunStats` を変えないという理由も当たらない。巻き戻しが着く親の handler の `prompt$` は、`evv` を handler の外側の `evv` に戻すときに今の `evv` (`m`) を手放す (core-ir.md の「handle と `prompt$`」)。`evv_get` の `dup` は `decref(w)` が、`Ctx` の参照は `evv_set` が手放すので、検査モードでも漏れは残らない。`reperform$E.op` は今の `evv` の最初の `E` の evidence で perform する
  - 子の中の extern の `Panic` は、子の中の `try_panic` か末尾の `Panic` の fork evidence に届く。`failed` には手を入れない
- 理由: 子の中の `mask` は数で evidence を飛ばす。エフェクトごとに印を1つしか置かないと、`mask (E, 0, 1)` を越えた perform に handler がなく、速いモードで未定義動作になる (`probe/deepmask_par.em`)。親の列と同じ形を子に持たせれば、`ev_lookup` と `evv_mask` に手を入れずに済む。extern のエフェクトは mask されない (types.md:174) ので、`Panic` は深さ 0 の1つで足りる
- 却下した案: 子の `evv` を空にして探索で補う形 (`ev_lookup` の前提を破る)、`(E, d)` ごとの凍結した evidence の集まり (d に上限がない)、起こし直しで VM が handler を探す形 (`ev_lookup` を写すことになる)、`reperform$` に深さを渡す形 (動的な mask の prim が要る)、VM が `Panic` を別に扱う形 (中断の表し方が2つになり、ネイティブでも写すことになる)
- 影響する範囲: VM、Core IR の evidence passing、後のネイティブの `par`
- 見直す条件: `par` の子から `IO` やすぐに再開する操作を出すとき (multicore.md の「未決の論点と将来の拡張」)
- リポジトリに残す所: vm.md の新しい節「`par` の fork と join」、object-model.md の「evidence の3つの物体」、core-ir.md の新しい節「`par` の子の中断」。T-8 と T-9 が書く

#### D-3: `fork$E.op` と `reperform$E.op` の生成

- 決定
  - evidence passing の最後に `evidence/forks.rs` で作る。作るのは、プログラムが `par` を走らせうるとき、すなわち `Call::Par` か `prim root_get` を含むときだけである。`root_get` を条件に含めるのは、REPL の束縛が前の入力の `par` を走らせる閉包を持てるためである
  - 作るエフェクトは、操作を1つ以上持ち、`EffectInfo::never_only()` が真のものすべてである。extern のエフェクトの多重度は `eml_extern` の行から取るので、`Prelude.Panic` は入り、`Prelude.IO` は入らない
  - 名前は効果の表の名前から `fork$<effect>.<op>`、`reperform$<effect>.<op>` とする (例: `fork$Fail.Fail.fail`、`reperform$Prelude.Panic.panicked`)。セッションのエフェクトは版を持つ (`fork$E#2.op`)。どちらも `internal` でなく、`yields` でなく、split しない
  - `fork$E.op` は `clause (E, op)` の印を持ち、引数は `(ev: obj unr, a_i: P_i M_i)`、戻りは `obj poly` である。詰める値 `t` は、操作の引数が0個なら `()`、1個ならその値、2個以上なら `tuple_layout(k)` の `con` (印は `M_i` の join) である。本体は `prim child_abort(ev, &reperform$E.op, t)` と `return prim dummy()` である。`ev` は節の入口が持ち、`child_abort` は借りる
  - `reperform$E.op` は引数 `t` を1つ取り (`unit`、一様な `P_1`、`obj`)、戻りは `tobj poly` である。本体は (k ≥ 2 なら `unpack` の後で) `ev_lookup[E]`、`ev_clause[E.op]`、`clause` である。`Panic` は `extern Prelude.panic(t)` (位置なし) である
  - `eml_lir::Program::may_run_par()` を述語にし、LIR の verifier は `may_run_par()` なのに fork の関数がないプログラムを断る。VM は `may_run_par()` のプログラムで名前が引けなければ、ロードで内部の誤りにする
- 理由: `par` を使わないプログラムの書き出しを1バイトも変えずに、REPL を含めて漏れなく作れる最小の条件である
- 却下した案: いつも作る形 (Core IR と LIR の書き出しがすべて変わる)、セッションに「一度でもロードした」印を持たせる形 (段階が純粋な関数でなくなる)、`IO` を名前で外す形 (表の多重度がすでにある)
- 影響する範囲: Core IR、LIR、VM のロード
- リポジトリに残す所: core-ir.md の新しい節「`par` の子の中断」と「EP が作る補助の関数」、lir.md の「verifier」。T-8 が書く

#### D-4: タスクとスケジューラ

- 決定
  - 新しい crate (`eml_sched`) は作らない。`Sched`、`Policy`、`Scheduler`、`JoinNode` は `crates/eml_vm/src/sched.rs` に置く
  - `Task` に `evv: Word` (動いていない間に退避した evv)、`worker: u32`、`depth_offset: usize`、`boundaries: Vec<JoinId>` (開いている子の境目。内側が最後)、`state: TaskState { Running, Ready, Waiting(JoinId), Unstarted(Word) }` を足す。`depth()` は `depth_offset + base + frame_size` で、`stack_limit` は `max_depth - depth_offset` から作る
  - 安全点の足し算は `Ctx` に移す。`Ctx` は今のタスクの深さの上限 `depth_limit` (`max_depth - depth_offset`、起点が `max_depth` を超えれば 0) を持ち、`Ctx::switch_task(l, worker, depth_offset)` だけがそれを決め直す。安全点は `ctx.poll(base + frame_size)` を呼び、`poll` は `depth_limit` と比べる。`depth()` は fork の起点と `peak_stack` に使う。理由: VM が安全点ごとに `depth_offset` を足すと、`bench/run.sh` で `fib` の命令の数が 1.19 % 増えた (Q-8 の 0.5 % を超える。T-9 で測った)。利用者が決めた。この計画の `switch_task(l, worker)` は、どれも3つ目の引数に次のタスクの `depth_offset` を渡す。この変更は T-9 の前の独立したコミット (「Keep each task's depth bias in Ctx」) で入れ、Gate G を通す
  - `Scheduler<P: Policy> { tasks, current, ready: VecDeque<TaskId>, joins, policy, preemptions, peak_depth, main_worker }` を run ごとに `Machine::run_entry` で作り、`vm::run<M, P>` が戻ると捨てる
  - `JoinNode { parent, right, right_worker, parent_evv, fork_evv, left: Option<Outcome>, right_outcome: Option<Outcome>, ret, dst }`、`Outcome { Value(Word), Abort { effect, depth, reperform, tuple }, Error(RuntimeError) }` である。join の節点は Rust の構造で、`eml_rt` の物体にしない
  - `Scheduler`、`Task`、`JoinNode` の `Drop` はヒープに触れない。語は数えた参照で、VM のコードがちょうど1回入れて1回出す。`Failure` のときは触れずに捨て、`vm::run` が戻った後でヒープを落とす (`execute`) か回復で置き換える (REPL)。この段では根の登録をしない
  - 子の境目は `push_frame(ret, dst, 2)` のフレームで、slot 0 が子の結果、slot 1 が即値の `join_id` である。左の子は親のスタックに積み、右の子はスタックの底に持つ。子の本体は `Target::Frame { ret: CHILD_DONE, dst: 0 }` で入る
  - 安全点の `ctx.poll(task.depth())?` を `safepoint(ctx, task, sched)?` に替える。`poll` の後で `policy.tick()` が真で `ctx.yielding() == 0` なら切り替える。`Sequential::tick` は定数の `false` なので、逐次の機械語は今と同じになる
  - VM の補助の関数は、`M: Mode` の代わりに `Mode` と `Policy` を束ねた1つの型 (例: `R` で `R::M` と `R::P` を持つ) で総称にする。`run<M, P>` の写しごとに補助の関数の呼び手を1つに保ち、今の inline の判断を変えないためである (T-1 で、`M` だけで総称な補助の関数が2つの写しから呼ばれて inline されず、`records_wide` で命令の数が 9.8 % 増えたことを測った。利用者が決めた)
  - 切り替えは `prev.evv = ctx.switch_task(next.evv, next.worker)` の1回で行う。`evv` と worker を1つの検証した操作で替え、VM は `heap_mut()` で `set_worker` を呼ばない。`evv_swap` の後で `set_worker` を呼ぶ形は、`Ctx` の前提が `evv` の持ち主を今の worker と比べ、`heap_mut` が `set_worker` を禁じるので、子から親へ戻る切り替えで前提を満たせなかった (T-6 のレビュー。利用者が決めた)。次が `Unstarted(g)` なら、その ID の下で `apply(g, [()], Frame { ret: CHILD_DONE, dst: 0 })` で始める
  - 右の子の `depth_offset` は fork のときの親の `depth()` である。`peak_stack` はタスクの `depth_offset + stack.len()` の最大にする
  - `crates/eml_vm/tests/api.rs` で `Scheduler<Sequential>: Send`、`Scheduler<Seeded>: Send`、`Sched: Send + Sync + Copy` を固定する
- 理由: 入れ子の `vm::run` を作らず、待つタスクをデータとして持つ (multicore.md の「VM の並列化の備え」の5、6、7)。方針を型の引数にすれば逐次の道に費用がかからない
- 却下した案: `eml_sched` を今作る形 (N = 1 では共有するものがない)、join の節点を `eml_rt` の物体にする形 (公開するものがなく、Verus の範囲が広がる)、`evv_get` と `evv_set` での切り替え (切り替えごとに `dup` と `decref` が増え、`RunStats` がスケジュールに依存する)
- 影響する範囲: VM。async-tasks、worker-threads、par-steal がこの上に積む。後の段で書き直すのは、タスクの slab、公開するセルとしての `right_outcome`、記録としての `Error(RuntimeError)` である。そのまま使うのは、`Sched` の値、`Policy` の trait、安全点での切り替えと yield の規則、境目のフレームと `CHILD_DONE`、`Outcome` の語彙と解決の順、移し戻しの順、まだ始まっていない右の子を閉包の語1つで表すこと、fork の取り決めである
- 見直す条件: async-tasks の段
- リポジトリに残す所: vm.md の「置き場所」、新しい節「タスクとスケジュール」、「`par` の fork と join」、「並列化への備え」。T-1、T-9、T-15 が書く

#### D-5: fork と join の順序

- 決定
  - `Op::Par` (親の文脈。mask は evidence passing の包みがすでに当てている)
    1. `f` と `g` を読む
    2. `child = heap.fork_worker()`
    3. セッションの根 `r` ごとに `heap.share(r, child)`、続けて `heap.share(g, child)`
    4. 子の `evv` を D-2 のとおりに作り、`dup` して `share(fork_evv, child)`
    5. 右の子のタスクを作る (`worker = child`、`evv = fork_evv`、`depth_offset = task.depth()`、`state = Unstarted(g)`、`boundaries = [j]`)
    6. join の節点 `j` を作り、`parent_evv` に `ctx.switch_task(fork_evv, task.worker)` の戻りを入れる (左の子は親の ID で動く)
    7. 境目のフレームを積み、`boundaries.push(j)`、`apply(f, [()], Frame { ret: CHILD_DONE, dst: 0 })`、`ready.push_back(right)`、安全点
  - `Op::ChildDone` (境目のフレームの slot 1 が `j`)
    - 右の子: `right_outcome` に記録し、`heap.decref(ctx.switch_task(UNIT, right_worker))` で、子の ID のまま子の残りの `evv` を手放し、タスクを捨てる。親が `Waiting(j)` なら起こし (逐次は `push_front`、seed は `push_back`)、切り替える
    - 左の子: `left` に記録し、境目のフレームを外し、`heap.decref(ctx.switch_task(parent_evv, task.worker))` で親の `evv` に戻す。`right_outcome` があれば `complete_join(j)`、なければ `Waiting(j)` にして切り替える
  - `complete_join(j)` (親の文脈と ID)
    1. `left` が `Error(e)` なら `Err(e)`、そうでなく `right_outcome` が `Error(e)` なら `Err(e)`
    2. 右の側の語 (`Value(w)` か、`reperform` と `tuple`) ごとに `heap.transfer_back(w, right_worker)`、その後 `heap.retire_worker(right_worker)`
    3. 左が `Abort` なら右の語を `decref` して左を起こし直す。左が `Value` で右が `Abort` なら左の値を `decref` して右を起こし直す。どちらも `Value` なら `alloc_data(tag, 2, 0, lin = false)` で組を作り、`dst` に書いて安全点
    4. 起こし直しは D-2 のとおりで、`apply(reperform, [tuple], Frame { ret: joins[j].ret, dst })` で呼ぶ。`reperform$E.op` の perform は `par` のフレームを抜けて親の handler の `prompt$` まで巻き戻す
    5. join の節点を捨てる
  - `Op::ChildAbort` は `boundaries` が空なら内部の誤りである。`effect = meta(ev).tag() - 1`、`depth` は `ev` の状態の欄から読み、不死の dummy を的にして巻き戻す。巻き戻しのループの最初の腕で `task.pc == CHILD_DONE` なら止まり、`child_done(Abort { .. })` にする
  - `vm::run` は `Err` を返す前に `ctx.switch_task(UNIT, sched.main_worker)` を呼び、ヒープの worker を main の ID に戻す。回復は新しいヒープの worker を古いヒープから写すので、写した根は main の ID の局所の物体に戻り、次の fork でまた印が付く。返る語 (失敗したタスクの `evv`) は `decref` せずに捨てる。子の ID の節点を main の ID の下で手放すと、検査モードは `WrongOwner` を返すためである。誤りの後のヒープは、回復で置き換える (続けられる誤り。REPL も `execute` も `run` を通る) か、`Ctx` ごと落とす (`is_broken` の誤り) だけで、どちらも古いヒープを丸ごと捨てる (object-model.md の「回復」、vm.md の「追記」)。リークの確かめ (`Machine::close`) は置き換えた後のヒープを見るので、捨てた語は漏れに数えない。`switch_task` の前提は検査モードでは `wf` と `word_in(())` だけで、誤りの後でも成り立つ。速いモードでは ID はどれも 0 なので、worker は変わらず、`Ctx` が `evv` を手放した文脈の `held_ok()` は元の `held_ok()` から従う
  - `Op::Finish` は、main でないタスクか join が残っていれば内部の誤り (`a task is left at the end`) にする。`boundaries` が開いているのに `exit` が立っていれば内部の誤りにする
- 理由: 印付けは送り手が公開する前に行い、移し戻しは受け手が `retire_worker` の前にすべて済ませる (multicore.md の「印付けの表」)。根の印付けを fork のときに行えば、`par` を使わない REPL のセッションは変わらない
- 却下した案: `RootSet` で根に印を付ける形 (すべての REPL の `let` の値が reuse されなくなる)
- 影響する範囲: VM と `eml_rt` の呼び方
- リポジトリに残す所: vm.md の「`par` の fork と join」、object-model.md の「セッションの根」と「回復」。T-9 と T-10 が書く

#### D-6: 子の中断と実行時エラーの規則 (利用者が決めた)

- 決定
  - 子の中の `Stopped(Interrupted | MemoryLimit)`、`Extern(Fault::Heap(_))`、`Internal(_)` はすぐに run を止める
  - `Stopped(DepthLimit)` とそのほかの `Extern` の誤りは子の誤りである。左の子の誤りはすぐに評価を止める。右の子の誤りは join に記録し、右のタスクのスタックは巻き戻さずに捨て、左の子が終わったときに評価を止める
  - 子の誤りは、左の子の中断でも値でも救わない。左の子が中断し、右の子が誤りで止まったときも、右の誤りで評価を止める。誤りが両方にあれば左の誤りを報告する
  - 中断は両方の子が終わった後で、いちばん左のものを起こし直す。中断しなかった側の値は捨てる (`Lin` の値も汎用の `decref` で落とす)
  - 捕まえられなかった子の `Panic` の文言は ``panicked: <message> in `reperform$Prelude.Panic.panicked` `` で、ソースの位置を持たない。status.md の制限に書く
- 理由: 止めた右の子のスタックは巻き戻しの表のない位置で止まっていて、解放できない。続けると検査モードの `close` が `Leak` を報告し、速いモードと食い違う
- 却下した案: multicore.md の「左の子が中断すれば右の子の誤りは捨てる」(上の理由で、利用者の判断により改める)
- 影響する範囲: `par` の意味。worker-threads の終わりの欄の規則もこれに合わせる
- リポジトリに残す所: multicore.md の「`par` の意味」の該当の文を T-9 で直し、vm.md の「`par` の fork と join」に書く

#### D-7: スケジュールの方針

- 決定
  - `pub enum Sched { Sequential, Seeded(u64) }` (`Copy`、`FromStr`) を `eml_vm` に置き、`eml_cli` から出す。`RunConfig.sched` の既定は `Sequential` で、`with_sched` で変える
  - `trait Policy { tick, reload, pick, wake }`。`Sequential` は横取りせず、`pick` は先頭から取り、起こした親は先頭に入れる。`Seeded` は splitmix64 で、予算は `1 + rng % 16` の安全点、次のタスクは `rng % len` で選び、起こした親は後ろに入れる。予算が 0 になっても yield の途中なら切り替えず、次の安全点でまた試す
  - CLI は `run` と `repl` に `--sched <sequential|seeded:N>` を持つ。既定は `sequential` で、知らない値は終了コード 2 である。`check` には付けず、環境変数も読まない
  - `eml_test_support` と bench は逐次で走らせる。テストの seed は 1 と 2026 である
  - `Finished` に `preemptions: u64` を足す。数えるのは方針が安全点で始めた切り替えだけで、join で待つ切り替えや子が終わったときの切り替えは数えない。逐次では常に 0 である
  - `RunStats` には欄を足さない。スケジュールによらない欄の一覧は `eml_test_support::schedule_independent` にあり、今は `peak_objects` だけを 0 にする。欄ごとに理由を1行で書く
- 理由: 監視のスレッドのない段なので、普通の方針はまだない。逐次を既定にすれば今のプログラムの振る舞いは変わらない。すべての切り替えを数えると `par` があるだけで 0 でなくなり、seed で横取りが起きたかを確かめられない
- 却下した案: 環境変数、seed で `RunStats` に欄を足す形、すべての切り替えを数える `switches`
- 影響する範囲: VM、CLI、テストの仕組み。async-tasks で `Normal` を、worker-threads で `RescueAlways` を足す
- リポジトリに残す所: vm.md の「タスクとスケジュール」と「`RunStats`」、stdlib.md の「起動」、testing.md の「UI テスト」。T-1 と T-13 が書く

#### D-8: `eml_rt` の操作

- 決定 (API の全体は付録 b-rt.md の 5 章)
  - `share(w, receiver)` は1つの操作のまま広げる。たどりは印付け、移し替え、所有者だけ (検査モードのみ) の3つのスタックを持つ。届いたどの `lin` の物体からも移し替えを始め、その下の rc 1 の物体には印を付けずに所有者を `receiver` にし、最初の rc > 1 の物体から下は印付けに切り替える。所有者だけのスタックは rc を書かず、印付けと移し替えのスタックに積まないので、速いモードと検査モードの rc の変化は同じになる。2回目の到達は検査モードの訪問済みの集まり (`HashSetWithView<usize>`) で見つけて `LinReachedTwice` にする。`receiver == worker` も許す
  - `transfer_back(w, from)` は rc == -1 の物体を 1 に裏返して所有者を今の worker にし、裏返した物体の中にだけ下りる。検査モードは所有者だけのスタックで、`from` の持つ rc > 0 の物体を今の worker に書き換え、第三の ID の物体は `WrongOwner` にする。`from == worker` は呼び手の誤りである
  - `fork_worker()` は検査モードで退いた ID を使い回すか新しい ID を出し、速いモードでは 0 を返して何もしない。`retire_worker(id)` は検査モードで `owned[id] > 0` なら `TransferLeak { worker, live }` を返し、0 なら ID を退かせる。`set_worker` は検査モードで `next_worker` を越えさせる
  - 検査モードの `owned: Vec<u64>` は ID ごとの局所の生きている物体の数で、wrapping の加減で更新する。証明には入れず、`check_invariants` が数え直して `OwnedMiscount { worker }` を返す
  - `Ctx::switch_task(l, worker) -> Word` は失敗しない。`l` を入れ、worker を `worker` にし (`set_worker` と同じく ID を使っている ID にする)、古い evv を返す。RC と仕事の回数には触れない。`l` の前提は切り替えた後の文脈 (worker が `worker`) で書き、返す語の約束は前の文脈で書く (D-4)
  - 回復は rc < 0 の物体を局所の物体として写す。2つ目からの使い手は `dup` し、`lin` ビットの物体は今と同じく `Unrecoverable` である
- 理由: 所有者を訪問済みの印に使うと、新しい受け手の前提が要り、ID を使い回せず、根の印付けとぶつかる。所有者だけのスタックを分ければ、2つのモードの rc の一致が構造で決まる
- 却下した案: `fork_share` を別の操作にする形 (同じたどり)、所有者を印に使う形、`switch_task` が `Result` を返す形 (確かめることがない)、`evv_swap` と `set_worker` を別々に呼ぶ形 (D-4)、ID ごとの数を Verus で証明する形 (実行時の数え直しで足りる)、共有を保つ回復 (回復の証明に新しい遷移が要る)
- 影響する範囲: `eml_rt` と、それを呼ぶ VM。worker-threads は ID ごとの数を run の表へ移すが、API は変えない
- リポジトリに残す所: object-model.md の「`share`」、新しい節「`transfer_back`」、「論理的な worker ID」、「報告する誤り」、「タスクの切り替え」、「基本操作の契約」、「回復」、「種類」。multicore.md の「`Lin` の物体の所有者の移し替え」と「論理的な worker ID」。T-2 から T-6 が書く

#### D-9: `par` の子が `Lin` の値を返すこと (利用者が決めた)

- 決定: `declaration_schemes` の `param_type_vars` は、関数型の引数の最後の結果にだけ現れる型変数を集めない。その関数型の引数の型変数と、関数でない引数の型変数は今と同じく `Unr` に固定する
- 理由: extern が受け取った値で、`par` はそれを組に1回だけ入れるか、ほかの子が中断したときに落とす。落とすのは `Lin` の値を持つフレームを巻き戻すのと同じである (linearity.md の「暗黙の後始末」)。実行系の側に追加の仕事はない
- 影響する範囲: extern の Kind のスキーム。関数型の引数を持つ extern は今 `par` だけである
- リポジトリに残す所: declarations.md:122 (コールバックを取る extern はその結果を高々1回使う、という義務)、core-ir.md:166 と :198、stdlib.md の「`Std.Par`」。T-12 が書く

### 5.2 短中期の設計

#### D-10: extern の結び付けの試験の一般化

- `every_extern_function_is_declared_once_in_std`: 方法に縛られない `Pure` の行では、最後の外側の矢印に、ラベルのない開いた row を許す。ただし、その変数がどれかの引数の矢印の row の末尾でもあるときに限る。内側の矢印のラベルのない開いた row は、その変数が最後の外側の矢印の末尾のときだけ許す
- `faulting_rows_carry_panic`: `tail == None` を「`None` か、関数型の引数の row の末尾」に広げる
- `kind_of` の注釈 (「extern の引数の型変数は `Unr`」) を直す
- 計画のための範囲の文: 「extern の結び付けの試験は、高階の extern を受け付ける。`Pure` の行で、コールバックの引数と結果が共有するラベルのない開いた row である。理由は、`Std.Par.par` が `<never e>` の row を持つ最初の extern であることである」

#### D-11: `Call::Par` の印と各パス

- 引数は `apply` と同じく `Poly` で確かめる。`lin` の閉包も渡せ、使った後でまた使えば V1 が断る。Perceus は後で使う `unr` と `poly` の引数を `dup` し、`lin` の引数には何もしない。結果の印は `Poly` である
- パスごとの変更の表は付録 c-front.md の Q4 にある。verifier の文言もそこにある
- `Rhs::Extern { ext: Par }` は T-11 から verifier が断る (``"`Std.Par.par` is not an extern instruction"``)

#### D-12: 最適化

- `Call::Par` は yield の地点でなく、`H` に触れず、`reach` はその引数をたどる
- never-only のエフェクトの handler は消えない (handler の特殊化は never-only を断り、`inline` は `handle` を持つ関数を断る)。T-11 でこれを固定するテストを足す

#### D-13: 子の evidence の凍結した部分

- 凍結した表と末尾は定数と同じ作業用のヒープで作り、凍結する。`ev_lookup`、`ev_clause`、`evv_mask`、`apply_clause` が凍結した `Data` を読めることを前提にする (Q-2)

#### D-14: スクリプトの引数の分け方

- `run` の後の引数を順に見る。値を取る `run` のオプションの長い名前 (今は `--sched`) と同じ引数は、自分と次の引数を取る。そのほかの `-` で始まる引数は自分だけを取る (`--debug-heap`、`--sched=seeded:7`)。残った最初の引数がファイルで、その後はすべてスクリプトに渡す
- 値を取るオプションの集まりは clap の `run` の定義から読む (`<Cli as clap::CommandFactory>::command()`)。読めなければ clap の構造の隣に `const RUN_VALUE_FLAGS` を1つ置く (Q-3)
- 確かめる場合の表は付録 d-tests.md の Q5 にある。`run main.em --sched bogus` は 0 で終わり、スクリプトが `["--sched", "bogus"]` を受け取る

#### D-15: テストの仕組み

- seed で流す UI テストは `ui::run` と `ui::run_fail` の中で行い、6本目のファイルを集めるテストは作らない。対象は接尾辞が `par/` で始まるファイルだけである
- ファイルごとの順は、検査モードの逐次とスナップショット、今の速いモードの比べ、その後に seed ごとの検査モードの run である。逐次の結果が VM の誤り (`Leak`、`Internal`、ヒープの誤り) なら seed では流さない。誤りの文言に worker ID が入り、ID はスケジュールに依存するためである
- 比べるのは stdout、stderr、書いたファイル、結果 (`Ok(exit)` か `Err` の `to_string()`) で、`run/par/` では `schedule_independent(stats)` も比べる。食い違ったら `` `eml run --debug-heap --sched seeded:{seed}` `` を含む文言で落とす
- `run/par/` のファイルは seed ごとに `finished.preemptions > 0` でなければならない。そのため、各ファイルの少なくとも1つの `par` の左の子は、再帰する補助の関数 `spin 40` を走らせる (inline されないように再帰にする)
- seed で流すのは検査モードだけである。速いモードのスケジューラの誤りは、共有のテストのプロセスの中の未定義動作になるためである
- Windows の印は付けない

## 付録: レビューで変わった主な所

議論を繰り返さないために、結論だけを置く。

- 子の evidence を空にする設計は、子の中の `mask` で handler を失う (`probe/deepmask_par.em`) → 親の鏡の列と深さに改めた (D-2)
- `par` の呼び出しの mask が translate の断言に当たる (`probe/mask.em`) → `Call::Par` が mask を持ち、evidence passing の包みを使う (D-1)
- VM が `Panic` を別に扱う案 → 設計どおり `fork$Prelude.Panic.panicked` を通す。中断の表し方を1つにし、ネイティブで写さずに済む (D-2)
- 所有者を訪問済みの印に使う案は、新しい受け手の前提、ID の使い回し、根の印付けとぶつかる → 検査モードの訪問済みの集まりに改めた (D-8)
- 所有者を書き換えるだけのたどりが印付けのスタックに積むと、2つのモードの rc が食い違う → スタックを分けた (D-8)
- fork の関数を `Call::Par` のときだけ作ると、REPL の束縛の閉包で漏れる → `root_get` も条件にした (D-3)
- `RootSet` で根に印を付けると、すべての REPL の `let` の値が reuse されなくなる → fork のときに印を付ける (D-5)
- すべての切り替えを数えると、seed で横取りが起きたかを確かめられない → `preemptions` に改めた (D-7)
- 子の実行時エラーは UI テストで起こせない (値の誤りは `Panic` の中断になり、`DepthLimit` は既定の上限で 1 GiB かかる) → `par.rs` に小さい `max_depth` のソースのテストを置く (T-13)
