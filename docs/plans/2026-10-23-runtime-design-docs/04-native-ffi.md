# S3: Native code generation strategy and FFI design (r2)

Scope: Q1-Q8 of the S3 briefing (Q8 = GUI layer), the premise "fast data-parallel pure-eml numeric kernels in native code on multiple cores", and the review in S3-review-r1.md (response table at the end). Thread model, offload semantics and the `par` API are S1's (S1-response-r1.md): worker 0 = main thread, dedicated; `rt_thread_new`; `Main.run`; pluggable `Park`/`Unpark`; three FFI call modes (inline, `rt_offload`, foreign-thread callback via inbox). Requirements this design places on S1 are named `REQ-S1-n` and collected in §5.

Tags: [V] verified (how is stated), [I] inferred. Probe = the throwaway Cargo project `S3-scratch/clif-probe` (Cranelift 0.137.0 from the local registry, offline; `src/main.rs` cross-target codegen + JIT run, `src/bin/throw.rs` unwinder prototype + call-site cost), run on Apple M5, macOS 27.

Changes from r1 in one paragraph: aborts no longer use Cranelift `try_call`; they return through frames with a flag check merged into the existing yield check, and whole-evaluation errors cut the stack to the entry stub with our own setjmp/longjmp pair. The review's C-1 asked for a measurement; the probe shows `try_call` costs 0.82 ns per call site against 0.29 ns for a flag check (§7), and the by-return design also removes the unverified pieces A-1/A-2 (exception-table extraction for AOT, unwinder start, `wasmtime-internal-unwinder`) and the Windows exception question (C-5). B-1 is resolved by moving the FFI trampoline generation to the driver (`eml_cli`), so `eml_vm` has no Cranelift edge and the "VM as no-Cranelift fallback" claim is withdrawn. B-2 is resolved by making extern sites plain calls with a fault check whose cold path joins the abort path.

## 1. Conclusion

### Q1. Backend strategy
- **One code generator (`eml_native`: opened LIR → CLIF), two `cranelift_module` backends**: `cranelift-jit` for `eml run --native` and the REPL, `cranelift-object` for `eml build`. Same CLIF, same `eml_rt` entry points. [V] both crates exist; the JIT ran `tail`-convention code on this machine (probe).
- **Compilation unit: the whole program** (user modules + reachable std) after Core IR optimize (already whole-program). Compilation is eager: at `eml run --native` start, and at each REPL input boundary for the functions that input adds (append-only module, "same name, same code"). No lazy per-function stubs (B-4 accepted): all compilation happens on the driver thread while no worker runs (REPL input boundaries have no running worker, multicore.md 「VM の並列化の備え」), so no code-memory write protocol and no concurrent `MAP_JIT` toggling is needed. Compile latency is measured in N1 (criterion: std + a 1000-line program compiles in < 300 ms in debug-less release; unresolved default if missed: cache std's compiled functions per toolchain build, which the cache key allows).
- **Mixed VM/native execution via `FnEntry`: dropped.** Native never calls bytecode and bytecode never calls native eml functions. Reasons in §2; C-2's module-granularity variant is rejected there. Incremental delivery inside N1 is by *refusing* programs: `--native` reports E0004 (not yet supported) for a listed set of LIR constructs until the list is empty; the completion criterion is the full UI suite.
- **The VM stays as the reference implementation and the only checked mode** (`--debug-heap`); native monomorphizes `eml_rt` for `Fast`. The r1 claim "fallback on hosts without a Cranelift backend" is withdrawn: all three targets are Cranelift targets and the `eml` binary always links Cranelift (B-1). The two backends are kept in sync mechanically: a std row = table row + `Ctx` method + std declaration (as today); the VM's `match` arm and the native `extern "C"` wrapper are both generated from the table by a macro in N1, so a new row adds no hand-written code in either backend (C-2 cost).
- **Cache unit: one function**, keyed as roadmap.md:193 (name + opened LIR + hash of referenced layouts/shapes). The key is fixed now; the cache itself is a follow-up.

### Q2. Calling convention and control
- **eml-internal calls: `CallConv::Tail`, tail calls as `return_call`/`return_call_indirect`, on all three OSes.** [V] codegen on `aarch64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc` (probe, incl. `return_call` to a callee with more stack args); [V] runtime on the host only: 200M-iteration self `return_call` loop and 100M-deep mutual `return_call` in constant stack. Windows runtime behaviour is **unverified** (C-5; A3).
- **Externs (`eml_rt` word ABI) and user C functions: the platform default convention** (`system_v` / `apple_aarch64` / `windows_fastcall`), called from `tail` code with plain `call`. [V] codegen on all five triples. No C function ever receives a `tail` pointer.
- **`ctx: *mut Ctx` is an explicit first parameter of every eml function and every extern.** No thread-locals. Any worker can enter any eml closure with its own `Ctx` through the entry stub (S1 M2b "native fork/join entry by (function, k)").
- **Entry from Rust into eml: `eml_enter(ctx, fnptr, argv, argc) -> Status`, an asm stub per ISA/ABI** (x86_64 SysV, x86_64 Win64, aarch64 AAPCS; 3 variants). It saves SP, FP and the callee-saved registers into a `JmpBuf` in `Ctx` (linked to the previous one, so entries nest), calls a Cranelift-generated `tail` adapter `enter$k(ctx, argv)` that loads the (function, k) entry's arguments from `argv` and `return_call`s the function, and on return copies the result word out. Status ∈ {Ok(word), Fatal}. This is our own setjmp; nothing from the OS or the CRT is involved, so Windows SEH never sees these frames (C-5).
- **Aborts (`never` ops, `try_io`-caught IO failure, `try_panic`, `exit`): by return, with one flag check per unwind point, merged with the yield check.** Each LIR unwind point (`eml_lir::unwind::points_all`: non-tail call of a may-abort function, non-tail `apply`/`clause`, non-Pure extern, `prim yield_abort`) is followed by `load ctx.yielding.target; brif != () → cold block`. For sites that are also yield points this is the check LIR already requires (`prim yielding()`), so nothing is added there. The cold block is generated from the `UnwindPoint` row and the yield slow path together: `yield_status(ev)` decides: *abort targeting this site's `landing` evidence* → write the dummy to the result variable, continue the normal path (the VM's landing); *other abort* → `decref` the `owned` vars (count times), `drop_token` the tokens, `return dummy` (the caller's check repeats this); *yield* → the existing κ-building slow path. `prim yield_abort` sets the state and `return dummy`s. An abort reaching the entry adapter returns Ok(dummy) with the abort state set; the Rust driver finishes it as the VM's `Finish` does (`exit` code, `yield_finish`, `evv_set(())`). Cost: one load + compare per unwind point; [V] probe: 0.29 ns per call (1.08 vs 0.79 ns/iter) with 4 values live across the call, versus 0.82 ns for `try_call`.
- **Extern faults (B-2)**: a non-Pure extern is a plain `call` to its `extern "C"` wrapper, which returns the result word and writes the fault into a new `#[repr(C)]` field `Ctx.fault` (kind word first; decided: `Fault` moves out of the return value because Windows x64 returns one integer register and `Result<i64, Fault>` is 24 bytes). After the call: `load ctx.fault.kind; brif != 0 → cold block`. The cold block does what `eml_vm::vm::failed` does today: classify (Panic / IO / fatal), `ev_find` the handler; none → `eml_fatal`; else `call` the clause entry through the clause ABI with the fault's arguments (the entry performs `yield_abort` and returns a dummy), then falls into the same abort cold path as above (this site's `owned`/`tokens`/`landing` row). So handler code is reached by plain branches only; there is one cleanup block per unwind point, shared by the fault route and the abort route.
- **Whole-evaluation runtime errors (overflow, division by zero, uncaught Panic/IO, heap errors, interrupt, limits): `eml_fatal(ctx, code) -> !`, our own longjmp** to the innermost `JmpBuf` in `Ctx` (restores callee-saved registers, SP, FP, returns Status::Fatal from `eml_enter`). No per-frame cleanup, no tables, no unwind info, no Cranelift exception support (same semantics as the VM: the heap is dropped or recovered). Only `tail` frames lie between the fatal point and the entry stub: externs return faults instead of raising, and Rust panics in externs are caught by `catch_unwind` in every wrapper (roadmap.md:180 kept) and turned into a fault. Multi-worker fatal: §5 REQ-S1-4.
- **Safe points**: poll at function entry and at loop back-edges: `load ctx.stop_bits; load ctx.stack_limit; brif (bits != 0) | (sp < limit) → cold → eml_fatal` (`get_stack_pointer` is a CLIF instruction). `Control`, SIGINT and EINTR handling unchanged. Native tasks are descheduled only at Async operations (S1 Q3); the poll is for stop bits and the stack, not for budgets.
- **Stack (B-6)**: each thread that runs eml code reserves its stack explicitly: workers and dedicated workers 1 GiB virtual by default (`--stack-size`, documented: under Linux `vm.overcommit_memory=2` use a smaller value), the main eml task runs on a spawned worker-0 thread rather than the process main thread's 8 MiB stack (S1's worker 0 is "the main thread" logically; REQ-S1-5 lets it be a thread with a chosen stack size, or S1 re-execs `main` on such a thread). Blocking-pool threads run only C thunks and Rust, never eml code: default OS stack size (the r1 requirement on pool threads is withdrawn). `ctx.stack_limit = stack_base + 1 MiB` guard: the largest eml frame is bounded by the LIR verifier's frame limit (today `u16::MAX` words = 512 KiB in the VM; native frames are no larger) and Rust externs do not recurse on the stack (`eml_rt` frees with an explicit worklist, [V] R1 §1 `work: Vec<Word>`), so 1 MiB covers one eml frame plus any extern. Frames larger than a page get inline stack probes (`probestack_strategy=inline`, needed on Windows, harmless elsewhere) — a Cranelift setting. `max_depth` is retired for native; the error text stays `DepthLimit`; docs/spec/vm.md 「上限と割り込み」 gets a native paragraph in N1.

### Q3. Prerequisites and ordering
- **Prerequisite: borrowed parameters** (roadmap.md:219-224, with the `TailCall` demotion and the `f$owned` wrapper): the measured 3.7-4.0x (owned, per-byte `dup`) vs 1.5-1.7x (inlined) [V] benchmarks.md is the gap to the 2x goal, and it is an LIR change measurable in the VM first.
- **In the native stage, not prerequisites**: (a) inlining of the borrowed byte-read rows and `Array`/`MutArray` element access; (b) loop-ification (R2 relaxation) only if measured loops miss the goal because of per-iteration reload of content pointer/length (a self `return_call` is already a loop at machine level [V] probe); (c) `scan = 255` for all arrays, done with raw arrays (Q5) so `arrays.rs` Verus specs change once.
- **Raw scalar arrays: an own milestone** after the first native milestone.

### Q4. User-facing FFI
- **Declaration** (user modules allowed; E1033 narrows to the bare `extern` that names a table row):
  ```
  pub extern "C" cblas_ddot : Int -> FloatArray -> Int -> FloatArray -> Int -> <IO> Float
  pub extern "C" blocking symbol "sqlite3_step" step : Db -> <IO> Int
  pub extern "C" pure symbol "cblas_ddot" ddot : Int -> FloatArray -> Int -> FloatArray -> Int -> Float
  pub extern "C" data Db drop "sqlite3_close"
  link "openblas"             -- module level; AOT: -lopenblas; JIT/VM: dlopen("libopenblas.{dylib,so,dll}")
  link framework "Accelerate" -- macOS only; ignored elsewhere
  ```
  Attributes are contextual words between the ABI string and the name: `blocking` (Q6), `pure`, `symbol "<c name>"` (default: the eml name). `extern "C" data` declares an opaque handle type (a `CHandle` `Foreign` with the named destructor, `Lin`).
- **Type mapping**: `Int`→`int64_t`, `Float`→`double`, `Bool`/field-less enums→`int64_t`, `Unit`; `String`, `Bytes`, `FloatArray`, `IntArray` borrowed as two C parameters `(const T*, int64_t len)`; `MutFloatArray`, `MutIntArray` as `(T*, int64_t len)` that C may write, consumed and returned to eml by the `with_arg` convention (the eml type says `... -> MutFloatArray -> ... -> (R, MutFloatArray)`); handle types as `void*`; results: scalar, `Unit`, or a handle. The r1 "unique `Bytes` room" is dropped (A-4): C-filled byte buffers come with `read_into` (roadmap.md:174) later, not in N5.
- **Effect and abort classification (C-4)**: a C call carries `<IO>` unless `pure`. A C row is `Effectful` for purity but **cannot fault**: the table gets a per-row `faults: bool` (true for `eml_rt` rows that return `Fault`, false for user C rows), and `may_abort`/`points_all` treat a non-faulting extern as *not* an unwind point. So a C call site has no fault check and no cleanup block; it is a plain call. `pure` makes the row `Pure` (removable when unused, trusted). Aliasing is not an issue: `FloatArray` is `Unr` and immutable (copy-on-write unless unique), `Mut*Array` is `Lin` and passed `with_arg`, and `removable()` already excludes rows that consume a `Lin` argument.
- **Not supported**: C structs by value or pointer, out-parameters other than the writable unique arrays, arrays of eml objects, variadics, callbacks. Anything beyond is a Rust extern row in std (today's path). **Callbacks** (C-6): consumers that would need them are comparator-style APIs (`qsort`), ODE/quadrature solvers (GSL, SUNDIALS) and visitor APIs; their cost under this design is "write a Rust row in std" or "wait". Synchronous same-thread callbacks (C-ABI thunk → `eml_enter` with the calling worker's `Ctx`, row `<>`) are feasible later without changing the unwinder (a fatal inside such a callback cannot cut through C frames and ends the process); trigger to add them: the first library on the target list (BLAS/LAPACK/Accelerate/MKL need none) that requires one.
- **Safety boundary**: an `extern "C"` declaration is trusted like a std row; the declaration is the boundary. Missing libraries and symbols are load-time errors (new E-code at `Session::run`).
- **How the VM calls user C functions (B-1)**: the driver (`eml_cli`, which depends on `eml_native`) generates a per-signature trampoline `unsafe extern "C" fn(ctx: *mut Ctx, argv: *const Word) -> Word` with `cranelift-jit` at load time and hands the VM an `FfiTable` of function pointers (one per declaration); `eml_vm` keeps its dependency on `eml_rt` + `eml_lir` only and calls through the pointer in a new `Op::Ffi { table_index }`. Checked mode runs the same trampolines. One marshalling implementation, no libffi. User FFI therefore lands after the JIT milestone.

### Q5. Raw scalar arrays (matrix math and pure-eml kernels)
- **Types**: `Std.FloatArray` (`Unr`) / `Std.MutFloatArray` (`Lin`), `Std.IntArray` / `Std.MutIntArray`; API as `Array`/`MutArray` (`make`, `length`, `get`/`read`, `set`/`write`, `freeze`/`thaw`, `tabulate`, `from_list`) plus `copy_slice`, `concat`, `fill`, `split_at`. Elements 8 bytes; no `Byte` array (`Bytes` exists).
- **Object layout: one new kind `Raw` (number 6)**: raw word 0 = element count, then raw 8-byte elements; `scan = 0`; opaque to `raw`/`set_raw` like `String`/`Bytes`; element type is static, so `Float` and `Int` arrays share the kind. Everything the kind needs in `eml_rt` (B-11): recovery copies it like `String` (raw words), `share` marks it in O(1) (no children), `freeze` accepts it, `foreign`/`unbox` reject it (`WrongKind`), checked mode treats its payload as opaque; `arrays.rs` Verus specs get the new kind; VM `Op`s are externs (no new instructions). **REQ-S1-3**: S1's M2b "unboxed arrays" are this kind, not `Data` with raw words.
- **Mutability (A-3)**: `Mut*Array` is `Lin`, always rc 1 by typing; its `write` is in place unconditionally and the native inline `write` assumes rc 1 (fast mode; the VM's checked mode asserts uniqueness as `MutArray` does today). `FloatArray.set` copies unless `is_unique`; `thaw` copies unless unique and sets the lin bit; `freeze` clears it. The lin bit is set by `make`/`thaw`/`split_at`; a `Lin` object without the bit cannot arise for this kind because only these externs create `Mut*Array` values.
- **Native codegen**: `get`/`read`/`write` inline: load count, unsigned compare, cold branch to the `Panic` path, `load.f64`/`store.f64` at `base + 8 + 8*i` into float registers; no `Float` box. Bounds-check elimination out of scope.
- **To C**: `FloatArray` → `(const double*, n)`, `MutFloatArray` → `(double*, n)` `with_arg`; valid for the duration of an inline call (non-moving heap, the frame holds the reference). Long-lived C buffers remain handles (roadmap.md:183 kept).
- **Parallel children**: pattern 1 (read-parallel): children receive the whole `FloatArray` (share-marked at fork in O(1)) and return new arrays; parent `concat`s. Pattern 2 (write-parallel): S1's `split_at`/`concat` on `Lin` arrays, copy-based (no views; roadmap.md:161 reasoning), children write in place (lin-bit objects are transferred, not marked), `concat` copies at join. Workers enter eml closures through `eml_enter` with their own `Ctx`.
- **BLAS thread pools (C-7)**: no mechanism, advice only, documented in the FFI section: eml never sets environment variables (they must precede library load, and `eml run` does not own the process environment); a program that uses several eml workers calls `openblas_set_num_threads(1)` / `mkl_set_num_threads(1)` through the same FFI at start; Accelerate has no knob (GCD) and is left alone. Declare BLAS calls non-`blocking` (CPU-bound).

### Q6. Blocking and long-running foreign calls
- **One attribute, `blocking`; one runtime call, S1's `rt_offload`.** Plain `extern "C"` = S1 inline mode (runs on the task's worker thread, holds the worker). `blocking` = offloaded: codegen emits a C-ABI thunk `fn(*const Word) -> Word` and the call site becomes `rt_offload(ctx, thunk, args)`; the task suspends and resumes on its own worker; under S1 M1 `rt_offload` may run the thunk inline.
- **Argument rule** (S1 invariant 7: an offloaded call sees only marked or moved inputs): scalars and handles by value; `Unr` heap args share-marked at submit (O(1) for `String`/`Bytes`/raw arrays) and passed as `(ptr,len)`; `Mut*Array` args moved to the pool thread and returned with the result. **REQ-S1-1** (B-7): `Lin` objects moved into an offload and `Lin` results coming back are *transferred* (lin bit, not marked), exactly as `par` join transfers them, so a `blocking` `dgemm` keeps its in-place `MutFloatArray`; the receiving heap owns and frees them (S1's remote-free path in M2). Scalars/handles need nothing.
- std's own blocking rows (`FileIn.read_*`, `Proc.wait`, ...) get the same `blocking` flag in `FunctionRow`.

### Q8. GUI layer: built-in Rust plugin, not a library over the C FFI
- **Decision (a)**: `crates/eml_gui` (egui-winit + egui-wgpu, hand-wired; eframe is not used because it owns `run_app` — B-9), reached through std externs in `std/Gui.em` whose rows are implemented by a `Plugin` trait object registered by the driver, the shape of today's `Host` (trait in `eml_rt`, implementation outside the verified core, trust class T11). `eml_rt` stays vstd-only; Slint can be a second plugin later.
- **Why not (b)**: egui/winit/Slint are Rust-ABI crates without a C API; a C shim would need everything Q4 excludes (structs, callbacks on the loop thread, loop ownership, closures across the boundary).
- **Rows and registration (B-8)**: plugin rows are ordinary `eml_extern` rows with Reprs, kinds, purity, borrowed flags and an `Extern` variant each, so type checking, LIR, codegen ABI and the table-to-std tests are unchanged; only the *implementation* differs: the generated `extern "C"` wrapper in `eml_rt` dispatches `ctx.plugin("gui").call(row, args)` on a `dyn Plugin` method (typed per row, like `Host` methods), `external_body` like Host rows. A program importing `Std.Gui` without the plugin registered fails at load with a new E-code. `Plugin: Send + Sync` holds only thread-safe parts: an `EventLoopProxy` (Send) for `Unpark`, the inbox, and a `SendCell<Option<GuiState>>` (the `!Send` winit/egui/wgpu state; `unsafe impl Send`, T11) whose every access is preceded by `assert ctx.worker == 0` — the same worker-ownership check as handles. [I]
- **Event loop**: S1's dedicated worker 0 with a plugin-supplied `Park`. Default (B-9): `park` = winit `run_app`-style driving where the worker loop is called from inside winit's callbacks (`about_to_wait` and user events), so eml keeps running during Windows/macOS modal resize and move loops; `pump_app_events` is the alternative, not the default. **REQ-S1-2**: `Park` may invoke the worker's run loop re-entrantly from inside a toolkit callback (the worker loop must be callable as "run ready tasks until none, then return"), and `Unpark` is `EventLoopProxy::send_event`.
- **UI state and closures (B-9)**: none cross the boundary. egui `Ui` values own an `Arc<Context>` and are `'static`; `Ui::new`/`new_child(UiBuilder)` are public and are what egui's own closure containers use internally [I, from egui's API; to be confirmed in the N7 spike]. The plugin keeps a stack of owned `Ui`s per frame; eml drives it with a `Lin` `Ui` handle: `Gui.begin_frame : Window -> <IO> Ui`, widgets `Gui.button : Ui -> String -> <IO> (Bool, Ui)`, containers `Gui.begin_horizontal : Ui -> <IO> Ui` / `Gui.end_horizontal : Ui -> <IO> Ui` (plugin checks nesting at runtime; mismatch is a runtime error), `Gui.end_frame : Ui -> <IO> Unit` renders. Events: `Gui.next_event : Window -> <IO, Async> Event` (S2's op, resumed via `Unpark`). Thread-boundness: worker-0 assertion on every handle op; other workers use `Main.run`.
- **Cost**: feature-gated in `eml_cli` (`--features gui`); AOT links `libeml_gui.a` only when `Std.Gui` is imported (B-5 toolchain below).

## 2. Rationale
- **By-return aborts + longjmp fatal, not `try_call`** (C-1): measured 0.29 vs 0.82 ns per call site; the by-return form is the VM's design re-expressed (unwind rows → cleanup), needs no exception tables, no unwinder, no AOT data section, nothing OS-specific, and merges with the yield check LIR already mandates. The roadmap's rejection of "flags" (roadmap.md:179) was for runtime errors in pure functions; those use the longjmp, so pure functions get no checks. [V] probe for the numbers; [I] for the merge (the yield check is `ctx.yielding.target != ()` and abort sets the same field, R2 §1.5 [V]).
- **Own setjmp/longjmp, not `try_call` for fatal either**: once aborts do not need tables, keeping Cranelift exceptions only for fatal would keep the entire unwinder/table pipeline for one catch per entry; a 40-line asm pair per ABI replaces it and is independent of Windows unwind data.
- **Why not mixed execution** (C-2): two code paths at every `apply`, native re-entering the VM loop on the same `Task` (the nesting multicore.md constraint 5 forbids switching in), and `FnEntry` kinds. Module-granularity mixing (std native, user VM) has the same `apply` problem: a std higher-order function applies user closures. The "incremental path" is E0004 refusal inside N1, which gives earlier benefit (programs that compile run natively) without a second ABI.
- **Default convention outside, `tail` inside**: `return_call` requires a tail-capable convention on both sides ([V] `supports_tail_calls()` only for `Tail`); both coexist in one function on all five triples [V].
- **Explicit `ctx`**: thread-agnostic without TLS; matches the word ABI of externs (`Ctx` methods, [V] R1 §3).
- **Raw arrays as a kind**: `Data` payloads are scanned words; raw floats must not be scanned; `String`/`Bytes` are the precedent ([V] kinds table).
- **GUI as a plugin outside `eml_rt`**: `Host` already shows the pattern; S1's dedicated worker 0 + `Park` gives the loop the main thread.
- **`blocking` = `rt_offload`**: S1 fixed the semantics; a thunk + one call is the smallest surface.

## 3. Alternatives considered and rejected
- **Cranelift `try_call` + FP-walking unwinder for aborts** (r1's choice): works ([V] probe `throw.rs`: throw from a `tail` frame, skip a frame without a handler, resume in a tagged handler two frames up and in a `Default` handler in the host-convention entry; 2000 repeats), but costs 0.82 ns per may-abort call site (all registers clobbered on the exceptional edge → spills) vs 0.29 for a flag check, needs the exception table extracted and relocated into AOT objects, an unwinder start stub, and ties the design to an `-internal-` crate (A-1, A-2). Kept as the fallback if the flag check is ever measured to dominate (it cannot: it is strictly cheaper per site and equal in count).
- **Rust `catch_unwind` / OS unwinding for fatal**: needs unwind info through Cranelift frames; SEH on Windows needs funclets Cranelift does not emit (cg_clif [V] R5 §3).
- **CRT `setjmp`/`longjmp`**: MSVC `longjmp` performs an SEH unwind over the frames it skips and needs their unwind data; our own pair does not.
- **Cranelift `stack_limit` global value**: traps instead of branching; needs a signal handler that resumes JIT code.
- **JIT only / AOT only**; **libffi** for VM-mode FFI; **Bigarray-style out-of-heap arrays**; **array views**; **a new `Foreign` effect**; **GUI as a C shim**; **GUI inside `eml_rt`**: as in r1 (JIT only: no deployable artifact; AOT only: REPL needs a linker; libffi: a C dependency and a second marshaller; Bigarray: second object world; views: roadmap.md:161; effect: nothing over `pure`/`IO`; C shim: needs what Q4 excludes; in-rt: toolkit code inside the verified crate).
- **Lazy per-function JIT stubs** (r1): patchable indirection defeats direct `return_call`, and multi-worker patching needs a write protocol (B-4).

## 4. Assumptions made
- A1. `cranelift-object` can produce objects for the three targets that the system linker accepts (Mach-O, ELF, COFF). [I] from its purpose (cg_clif uses it for all three); if a target fails, that target ships JIT-only until fixed. No unwind data is required for correctness (fatal/abort do not use it); it is emitted where `cranelift-object` supports it, for debuggers only.
- A2. The entry stub's save/restore set is complete per ABI: SysV x86_64 rbx, rbp, r12-r15; Win64 adds rdi, rsi, xmm6-xmm15; AAPCS x19-x28, x29, x30, d8-d15. [I] from the ABI documents; a wrong set shows up as corrupted Rust locals after a fatal, caught by the N1 run-fail tests on all three OSes (N2 for Windows).
- A3. `return_call`/`Tail` have no Windows-only runtime defect. Evidence is codegen only [V]; no Windows machine. If wrong: `tail` only on Unix and trampoline-based self tail calls on Windows (worse code, same semantics).
- A4. The abort flag check merged with the yield check is one load+compare at every unwind point and costs ≤ 0.3 ns/site in real code as in the probe. If real code shows more (unlikely: the probe has 4 live values and a trivial callee, the worst ratio), the check still never exceeds the `try_call` alternative.
- A5. 1 GiB lazily committed reserve per eml thread is acceptable on the three OSes; a `--stack-size` flag and documentation cover overcommit-restricted Linux.
- A6. S1's `split_at`/`concat` are copy-based and `par` transfers lin-bit objects without marking (multicore.md:156-160).
- A7. egui's public `Ui::new`/`new_child` allow a plugin-side owned `Ui` stack without closures. If not, the plugin keeps the closure form internally and the eml container API becomes `Gui.horizontal : Ui -> (Ui -> <IO> Ui) -> <IO> Ui` implemented by re-entering eml through `eml_enter` on worker 0 (an in-plugin synchronous callback with the restrictions of Q4; `<IO>` is allowed there because the plugin, not C, is between the frames and a fatal cuts through Rust frames via longjmp only if the plugin holds no destructors across the call — it must not).
- A8. The worker loop can be invoked re-entrantly from a winit callback (REQ-S1-2); if S1 refuses, `pump_app_events` becomes the default and eml pauses during modal loops.

## 5. Implications for implementation
Constraints:
- `eml_native` depends on `eml_lir` + `eml_rt` + Cranelift; `eml_vm` on `eml_rt` + `eml_lir` only (FFI pointers arrive as data); the driver crate that owns threads, entry stubs (asm), `JmpBuf`, FFI trampolines and the linker invocation is `eml_cli` (or a new `eml_driver` it uses). `eml_rt` stays vstd-only; `Ctx` gains `#[repr(C)]` fields read at fixed offsets: `yielding` (exists), `fault`, `stop_bits` pointer, `stack_limit`, `jmp: *mut JmpBuf`, `worker`; offsets asserted in tests as `YieldState` is today.
- Codegen reads only the function's opened LIR and referenced layouts; extern rows are reached by symbol name.
- `extern "C"` wrappers for `eml_rt` rows and the VM's `match` arms are generated from the table by one macro; every wrapper: `catch_unwind`, write `ctx.fault`, return one word.
- `points_all` stays the single source of unwind points; codegen panics on a function it rejected.
- **Toolchain for `eml build` (B-5)**: the eml distribution (the Nix package, and any release tarball) ships `libeml_rt_driver.a` (= `eml_rt` + driver + entry stubs, built with the pinned toolchain at eml's build time) and optional plugin archives (`libeml_gui.a`); `eml build` writes the object with `cranelift-object` and invokes the system linker found the way rustc finds it (`cc` on Unix, `link.exe` from a Visual Studio installation or `lld-link` if present on Windows), passing `link` directives as `-l`/`-framework`. No rustc/cargo on the user's machine. Unresolved: bundling `lld` (default: no).
- Multi-worker fatal: **REQ-S1-4**: `eml_fatal` on worker k records the error in `Control` and sets a stop bit before cutting to its entry stub; every other worker observes the bit at its next poll and cuts to its own entry (no cleanup, like the VM); `Park`ed workers (including `par` join waiters) are unparked by the stop; the driver joins all workers, then exits or recovers. Abandoned native frames hold no Rust-side locals (externs have returned) and no destructors; `Foreign` finalizers run when the heaps are dropped or at recovery, as in the VM.
- **REQ-S1-5**: worker 0's OS thread is created (or re-entered) with the native stack size the driver asks for; `rt_thread_new` takes a stack size.
- **REQ-S1-1**, **REQ-S1-2**, **REQ-S1-3**: in Q6, Q8, Q5.
- **N1 test rule (B-10)**: `tests/ui/run` and `run-fail` run natively in fast mode; expected stdout/stderr/exit code must be byte-identical except for tests marked `// native: skip` (depth-limit and memory-limit tests whose message text names `max_depth`/word counts, and tests that need checked mode); `RunStats` snapshots are VM-only. The skip list is in the stage plan as a kind-1 test change.

Milestones:

## 7. Additional checks
- Probe `src/main.rs` (r1): cross-compiled `tail` `return_call` (incl. more stack args), `tail` calling the default convention, `try_call`/`try_call_indirect` to `tail` callees on the five triples; verifier refusal of `try_call` to a `windows_fastcall` callee; JIT run on the host of self and mutual `return_call` loops (constant stack) and of `return_call` into a callee with more stack args (correct result).
