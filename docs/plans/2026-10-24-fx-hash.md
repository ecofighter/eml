# fx-hash

- 作成日: 2026-10-24
- 基点: claude/loving-ride-tjwfhl @ lean-pipeline を閉じた後
- 状態: 計画は確定

この計画は、コンパイラの段階のハッシュ表を速いハッシュ関数に替える段 `fx-hash` の設計と計画である。機能を足さない整理の段なので roadmap の「段の列」に載せない。この文書を段の最初のコミットで入れ、段を閉じるときに消す。

## 1. 目的と成功の基準

- 目的: `eml check` と `eml run` のコンパイルの時間で、std の `HashMap` と `HashSet` の SipHash が占める分を減らす。release の `eml run bench/nbody.em` の callgrind では、SipHash の関数が命令の 2〜3% を占め、`hash_one` の呼び出しが型検査の表の索引に散っている
- 成功の基準
  - テストの成否と期待値が1つも変わらない
  - `bench/` のプログラムの `eml check` の命令の数 (Linux の callgrind) が減り、どれも増えない
  - 全体の検証のコマンドが通る

## 2. 決めたこと

- 外部 crate `rustc-hash` (2.x) の `FxHashMap` と `FxHashSet` を使う。rustc と rust-analyzer が同じ用途で使う。キーは処理系の内部の ID、型、名前で、入力は利用者自身のプログラムなので、衝突を狙った入力への耐性は要らない。std の `RandomState` はプロセスごとに順が変わるが、どの段階の出力も表の順に依存しない (今のテストが毎回通ることで確かめてある) ので、順が決まっても出力は変わらない
- 対象は、ハッシュ表を引く回数がコンパイルの時間に効く crate だけにする: `eml_hir`、`eml_types`、`eml_core_ir`、`eml_lir`、`eml_vm` (コード生成と名前の表)。`eml_cli` と `eml_diagnostics` は表を数回しか引かないので std のままにする。`eml_rt` (vstd だけに依存する)、`eml_extern` (依存を持たない)、`eml_syntax` (表を使わない) は変えない
- 自前のハッシュ関数は書かない。広く使われている crate の方が、品質の確かめと保守の手間が少ないためである

## 3. 作業

- F-1 workspace の依存に `rustc-hash` を足し、対象の crate の `HashMap` と `HashSet` を `FxHashMap` と `FxHashSet` に替える。公開の型の欄と引数も替える
- F-2 `docs/implementation/architecture.md` の「外部 crate」の表に `rustc-hash` を足し、`eml_lir` が依存する workspace の crate が `eml_extern` だけであることを、外部 crate と分けて書く

## 4. テストの変更

- 全体の制約: 成否と期待値は変えない。期待値を変えない機械的な追随は許す (公開の型が `FxHashMap` になる所でテストが組む表の型を替えるなど)

## 5. 確かめ方

- `cargo test --workspace`、`cargo clippy --all-targets -- -D warnings`、feature の組み合わせの clippy、`cargo fmt --check`
- release ビルドで、`bench/` のプログラムの `eml check` と `eml run` の命令の数を、段の前後で callgrind で比べる。`benchmarks.md` の表の入れ替えは `lean-pipeline` と合わせて macOS で行う
