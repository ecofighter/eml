## 1. 目的と成功の基準

- 目的
  - 利用者のモジュールに `extern "C"` で宣言した C の関数を、VM の上で呼べるようにする。
  - 新しい crate `eml_native` が、`cranelift-jit` で橋渡しの関数を作り、`link on <os>` と `--link` に従ってライブラリと記号を解決する。
  - C の整数の幅は `Int as int` のように書く。配列、`String`、`Bytes`、不透明なハンドルを C に貸せるようにする。
  - BLAS (CBLAS の `cblas_dgemm`) と、ILP64 の Fortran の LAPACK (Accelerate の `dgesv$NEWLAPACK$ILP64`) を、利用者のモジュールから呼べるようにする。
- 成功の基準 (確かめ方は 9 章)
  - 9 章の全体の検証のコマンドがすべて通る。
  - 5.1 の D-1 から D-9 の「適合の確かめ」がすべて通る。
  - CI の全部の job が、4つの OS (ubuntu-24.04、ubuntu-24.04-arm、macos-15、windows-2025) で、再実行なしに通る。
  - macOS で、BLAS の `#[ignore]` のテスト2本を手で流して通る (T-13)。
  - roadmap の `ffi-c` の節が消え、残した項目が「その後の項目」に理由と条件を付けて移っている (T-15)。

## 3. 背景

基点 e97567b2 の事実である。

- 構文
  - `extern` の構文は、署名、`data`、`effect` を直接取る。ABI の文字列、属性、`drop` の節はない。`as` は AS_KW で、今は import でだけ読む (`crates/eml_syntax/src/grammar/items.rs:557`)。`drop` は DROP_KW である。`link`、`pure`、`symbol`、`blocking`、`on`、`framework` は普通の LIDENT で、文脈で決まる語の仕組みはない。
  - 構文の診断の番号は E0017 まで使っている (`crates/eml_syntax/src/lib.rs`)。HIR は E1058、型は E2021 まで使っている。
- HIR
  - E1033 `EXTERN_OUTSIDE_STD` は `extern_row` だけが出す (`crates/eml_hir/src/lower/mod.rs:328`)。std の行は正規の名前で `from_name` から引く。
- `eml_extern`
  - 行は `FunctionRow { name, params: &[Repr], ret: OpRet, param_marks, ret_mark, purity: Pure|Panics|Effectful, borrowed, with_arg, held }` で、関数のポインタ、`faults`、記号、ライブラリの欄はない。
  - `removable()` は `purity == Pure` で、`Lin` の引数をすべて借りる行である (`crates/eml_extern/src/lib.rs:2285-2292`)。
  - `with_arg: Some(k)` は 50 か所にある (`grep -c "with_arg: Some" crates/eml_extern/src/lib.rs`)。`Extern::ALL` は lib.rs:27 にある。
  - 配列を書く std の行は、配列を消費して返す。`MutUnboxed Float.write` と `Int.write` は `Panics`、`fill` は `Pure` で、どれも `Lin` を借りず、`Obj Lin` を返す (lib.rs:1185-1216)。`MutUnboxedArray` を借りる std の行は読むだけである (`length` と2つの `read`)。
  - crate の中に `unsafe` はない。`[lib] test = false` で、`[[test]]` はない。
- Core IR と LIR
  - 巻き戻しの地点は `purity != Pure` の extern である (`crates/eml_lir/src/unwind.rs:57`)。evidence passing の under の形の判断も同じ式である (`crates/eml_core_ir/src/evidence/handlers.rs:491`)。
  - 使われない extern の `let` は、行が `removable()` のときに消す (`crates/eml_lir/src/contract.rs:203-217`、`crates/eml_core_ir/src/tail.rs:41-49`)。
  - `lending_call` は extern の結果を自分の変数に束ね、呼ぶ前の貸した atom と組の `con` を作る (`crates/eml_core_ir/src/translate/program.rs:518-541`)。既知のコンストラクタの最適化が組を開く (docs/spec/core-ir.md の「組を返す extern」)。
  - `unwind::point` の呼び手は verify.rs:564 だけである。`for_each_consumed` と `for_each_lent` の呼び手は perceus.rs:264、267、388、verify.rs:1507、`crates/eml_lir/tests/text.rs:671`、674 である。
  - `extern_row` の呼び手は `crates/eml_core_ir/src/translate/mod.rs:142` (builder を持たない自由関数 `numbering` の中)、expr.rs:571、661 である。`FnLowering` は `program: &'a mut ProgramBuilder` を持つ (mod.rs:644)。
- VM
  - `Op::Extern { dst, at }` の operand は `[行の番号, 引数の数, slot…]` である。関数のポインタの表はない。
  - `CodeBase::load` は関数を名前で追記する (`crates/eml_vm/src/compile/mod.rs:52`)。`Index` (`crates/eml_vm/src/code.rs:208`) が名前の表を持つ。`struct Links` が compile/mod.rs:21、74、134、172、231 にある。
  - `RunConfig` は `#[derive(Clone)]` である (`crates/eml_vm/src/lib.rs:178`)。`Machine::with_driver(Box<dyn IoDriver>)` が実行時の物を `Machine` に入れる前例である (lib.rs:439)。`Machine::load(&mut self, program)` は lib.rs:451、`execute` は lib.rs:252 にある。
  - `CodeBase` はすべての worker のスレッドから借りる (`spawn_workers(code: &'scope CodeBase<M>, …)`、`crates/eml_vm/src/workers.rs:876-900`)。だから `CodeBase: Sync` が要る。
  - `failed(.., purity)` (vm.rs:3469、3811) が purity で fault を振り分ける。
- 物体
  - `Foreign` は `alloc_foreign::<T: Send + 'static>` と vtable の後始末で作る (信頼の行 T3)。`String` と `Bytes` は長さの語の後にバイトが並び、NUL はない。`Heap::string` と `Heap::bytes` は生のポインタを返す。配列は種類 `Raw` で、語 0 が数、要素 0 が `base + 8` にある。配列の要素へのポインタを返す accessor はない。

- 外部の crate とライセンス
  - `about.toml` の `accepted` は MIT、Apache-2.0、ISC、BSD-3-Clause、BSL-1.0、CDLA-Permissive-2.0、Unicode-3.0 で、`Apache-2.0 WITH LLVM-exception` はない。cranelift の crate、regalloc2、target-lexicon はみなこのライセンスである。cargo-about 0.9.0 は、この項目がないと `failed to satisfy license requirements` で落ち、あると Apache-2.0 の文面で書き出す (試作で確かめた)。

### 5.1 長く効く方針 (変えるときは設計からやり直す)

実装の途中でこれらとぶつかったら、止めて報告する。各項の「適合の確かめ」の MUST と MUST NOT が守るべき規則で、コマンドの形で確かめられるものはそのまま書いた。

#### D-1: C の呼び出しの境目は、`CSignature` ごとの橋渡しの関数と、`load` に渡す `Linked` の値

- 決定
  - 橋渡しの関数の型は `unsafe extern "C" fn(callee: *const (), args: *const u64) -> u64` である。C の型の並び `CSignature` (要素は `I32 | I64 | F64`) ごとに1つ作り、呼ぶ C の関数のアドレスを最初の引数で受ける。
  - `Bridge`、`Dtor`、`CCall`、`Linked` は、新しい葉の crate `eml_cabi` に置く。`eml_cabi` は `eml_extern` だけに依存する。
  - crate の依存は `eml_extern ← eml_cabi ← {eml_vm, eml_native}` である。`eml_native` は `eml_extern`、`eml_cabi`、Cranelift の5つの crate、libloading に依存する。`eml_cli` と `eml_test_support` の feature `run` が `eml_native` に依存する。別の cargo の feature は作らない。
  - `eml_vm` は、つないだコードを `load` に渡す `Linked` の値としてだけ受け取る。linker、それを作る関数、trait object を持たない。`RunConfig` と `Machine` に linker の欄はない。
  - ネイティブのコードを足す後の段も同じ形にする。`load` の前に作る値で渡し、`Ctx` に関わらないポインタの型は `eml_cabi` に、`Ctx` に関わる型は `eml_rt` に置く。
- 理由
  - pool のスレッドとネイティブのコードが、ヒープなしで同じ記述を使える。
  - つなぐ作業を作るのは `eml_native` の1つで、呼ぶのは `eml run`、REPL、テストの道具の3つである。3つとも `load` の前にプログラムを持っているので、境目は trait でなく結果の値で足りる。共有する面が4つの item に減る。
  - linker は `load` のときに1つのスレッドで使うだけである。`Machine` はもともと `!Send` である (`Box<dyn IoDriver>` を持つ)。VM の中に `Sync` も lock も要らない。
  - ライブラリを閉じず、JIT のメモリも解放しないので、`CCall` と `Dtor` のポインタはプロセスの間ずっと有効である。`Linker` や `Machine` の寿命とつなげる必要がない。
- 退けた案
  - `fn(ctx, argv: *const Word) -> Word` の橋渡し: `eml_native` を `eml_rt` と `Ctx<M>` に縛り、ヒープの配置を CLIF に写し、pool のスレッドに `Ctx` を求める。
  - `eml_extern` に `CLinker: Send` の trait と `Arc<Mutex<dyn CLinker>>` を置く形: `RunConfig: Clone` を避けるために、葉の crate に lock と `unsafe` を入れる。lock が毒になったときの道も要る。
  - 新しい crate に trait を置く形: 実装するのは `eml_native` だけで、テストの linker もただの `Linked` の値で足りる。
  - 型を `eml_extern` に置き、`#![deny(unsafe_code)]` と2つの `allow` にする形: 動くが、extern の表の crate が実行時のコードのポインタを持つことになる。
  - 型を `eml_rt` に置く形: `eml_native` は `eml_rt` に依存しない (下の確かめ)。2つのポインタの型のために Verus と信頼の門を通すのは重い。

  - `load` に linker のクロージャを渡す形: trait と同じことで、値の形のほうが小さく、誤りの扱いが呼び手に残る。
  - `RunConfig` を `Clone` でなくして linker を持たせる形: VM が要らない欄のために API を変える。
  - libffi: Cranelift で作ると決めてある (roadmap の `ffi-c`)。

#### D-2: C の関数も extern の行で、中断と削除は `purity`、`faults`、`writes` の3つで決める

- 決定
  - 利用者の C の関数は行である。IR では `Rhs::Extern { ext: ExternRef, .. }` で表し、行は `program.row(ext)` で引く。行で動くパスは、C の関数のために枝を分けない。
  - `ExternRef::C` (と、次の段が足す `ExternRef::CSubmit`、`ExternRef::CTake`) を match してよいのは、次の所だけである。
    - `eml_extern/src/` (定義と行の見え方)
    - `eml_core_ir/src/translate/` (作る所)
    - Core IR と LIR の print と parse (`crates/eml_core_ir/src/text.rs`、`crates/eml_lir/src/{syntax,text}.rs`)
    - `eml_vm/src/compile/emit.rs`、`eml_vm/src/ffi.rs`、`eml_vm/src/disasm.rs`
  - 行は3つの独立した事実を持つ。
    - `purity`: 呼び出しが何を上げうるか。C の行では、`pure && !faults` のとき `Pure`、`pure && faults` のとき `Panics`、`!pure` のとき `Effectful` である。
    - `faults`: 失敗して中断を始めうるか。std の行では `purity != Pure` である。同期の C の行 (`ExternRef::C`) では、狭める `as` の引数か、ハンドルの結果があるときである。次の段の `CSubmit` は狭める引数があるとき、`CTake` はいつもである。
    - `writes`: 借りた引数の中身を書き換えるか。std の行はどれも `false` である。C の行 (`C`、`CSubmit`、`CTake` のどれも) は、`CParam::MutUnboxedArray` の引数があるとき `true` である。
  - 読む所ごとの規則は次のとおりである。

    | 読む所 | 基点 | 新しい規則 |
    |---|---|---|
    | 巻き戻しの地点 (`eml_lir/src/unwind.rs:57`) | `purity != Pure` | `row.faults` |
    | under の形と、すぐ再開する節の判断 (`eml_core_ir/src/evidence/handlers.rs:491`。core-ir.md:1020、1045、1052) | `purity != Pure` | `row.faults` |
    | 使われない呼び出しの削除 (`eml_lir/src/contract.rs:216`、`eml_core_ir/src/tail.rs:48`) | `removable()` | `removable()` のまま。中身は `purity == Pure && !writes && Lin の引数をすべて借りる` になる |
    | VM の fault の振り分け (`eml_vm/src/vm.rs:3469`、3811 の `failed(.., purity)`) | purity で振り分ける | std の行は変えない。C の行は橋渡しの fault をここに通さない。範囲と null の `Panic` は `ffi.rs` から `abort_to` で直接上げる |
    | `Op::Async` と専用の命令の固定の purity (`vm.rs:3322`、3346、3785-3790) | 固定 | 変えない |
    | yield の地点 (core-ir.md:887) | `Pure` でない extern は yield の地点にしない | std は変えない。C の行も yield の地点にしない |

  - extern の文を消す、まとめる、複製する、並べ替えるパスは、`writes` の行を、借りた `MutUnboxedArray` の引数それぞれへの書き込みとして扱う。今あるのは削除だけで、それは `removable()` が受け持つ。
- 理由
  - 巻き戻しの地点も under の形も、「中断を始めうるか」で決まる。今はそれを `purity != Pure` で書いている。`pure` でない C の行は IO を上げられないし、`pure` でも狭める引数かハンドルの結果があれば `Panic` を上げうる。2つの判断を同じ `faults` で決めれば、互いに食い違わない。
  - 書き込みを `Effectful` で表すと、「メモリを書く」と「IO を上げうる」が混ざり、`failed()` の振り分けや後のコード生成 (`jit-externs` は extern の失敗を `Ctx.fault` で返す) が読み違える。
  - `writes` がないと、結果の `Unit` を捨てた `pure` の `dgemm` が、書き込みごと消える。`lending_call` は C の結果を自分の変数に束ね、組を開いた後でその変数が使われなくなるためである (3 章)。std にはこの形がない。std の書く行は配列を消費して返すので、「Lin を借りない」の条件で消えない。
  - IR はこの書き込みを行にだけ持ち、データの依存として持たない。後のパスがこれを見落とさないよう、規則として書いておく。
- 退けた案
  - 書く C の行を `Effectful` にする: 正しく動くが、上の理由で読み違えを招く。
  - C の `MutUnboxedArray` を、std と同じく消費して返す: 1つの結果の語では、複数の配列を返せない。複数の結果を持つ extern は、2つの IR、Perceus、VM の命令にまたがる変更になる。
  - `removable()` を「借りた Lin の引数がない」にする: `MutUnboxedArray.length` や `read`、`FileIn`、`Net`、`Tls` の読みも消えなくなり、bench の `RunStats` が変わる。
  - `Purity::Writes` を足す: 2つの軸を1つの enum に混ぜ、`Purity` の `match` がすべて腕を増やす。
  - `pure` の書く行を消せるままにして文書に書く: 黙って誤った答え (`dgemm` が0を返す) になる。
  - C の呼び出しを別の `Rhs::CCall` にする: すべてのパスに行の扱いを写す。
  - `Extern` の enum に実行時の行を足す: `Extern` は `Copy` で静的で、網羅的に match されるので、プログラムが定義できない。
- 及ぶ範囲: `eml_extern` (`FunctionRow`、`removable`、C の行の見え方)、`eml_lir` の `unwind` と `contract`、`eml_core_ir` の `evidence` と `tail`、VM の `failed`、`jit-core` のコード生成
- 見直す条件: extern を消す以外の最適化 (CSE、並べ替え、複製) を入れるとき。複数の結果を持つ extern を入れるとき。
- 適合の確かめ
  - C の関数は `Rhs::Extern { ext: ExternRef }` と `program.row(ext)` で表さなければならない (MUST)。パスは上の場所のほかで `ExternRef::C` によって枝を分けてはならない (MUST NOT)。確かめ方: `grep -rln "ExternRef::C" crates/*/src` (3つの変種すべてに当たる) が上の場所のファイルだけを出す。
  - 巻き戻しの地点と under の形の判断は `row.faults` を使わなければならない (MUST)。確かめ方: `grep -rn "purity != Purity::Pure" crates/eml_lir/src/unwind.rs crates/eml_core_ir/src/evidence` が何も出さない。
  - 削除は `removable()` を使い続け、`removable()` は `purity == Pure && !writes && Lin の引数をすべて借りる` でなければならない (MUST)。確かめ方: `grep -n "writes" crates/eml_extern/src/lib.rs` が欄と `removable` の中の使い方を出す。
  - VM の fault の振り分けは `purity` のままでなければならない (MUST)。確かめ方: vm.rs の `failed(.., purity)` が変わっていない。
  - C の行の `purity`、`faults`、`writes` は上の規則に従い、std の行はどれも `writes == false` でなければならない (MUST)。確かめ方: `c::the_purity_of_a_c_row` が、`pure`、狭める引数、ハンドルの結果、`MutUnboxedArray` のすべての組み合わせで、3つの導き方と `removable() == (purity == Pure && !writes)` を確かめる。`externs::no_std_row_writes_a_borrowed_argument` が `Extern::ALL.iter().all(|e| !e.row().writes)` を確かめる。
  - `<IO>` で狭める引数のない C の行は巻き戻しの地点にならず、狭める行はなる。確かめ方: `unwind::an_io_c_row_without_narrowing_is_no_unwind_point` と `unwind::a_narrowing_c_row_is_an_unwind_point` が通る。
  - extern の文を消す、まとめる、複製する、並べ替えるパスは、`writes` の行を借りた `MutUnboxedArray` の引数それぞれへの書き込みとして扱わなければならない (MUST)。確かめ方: lir.md の「縮約」にこの規則がある。`contract::a_pure_c_call_that_writes_an_array_is_kept` と `contract::an_unused_pure_c_call_is_removed` が通る。`tests/ui/run/ffi/fixture_fill.em` が両方のモードで書いた値を出す。
- リポジトリに残す所
  - docs/spec/lir.md の「extern の借用」(`writes`)、「縮約」(`removable()` と書く行の規則)、「巻き戻しの地点」(`faults`)、「extern の行」(C の行の見え方): T-3、T-4

#### D-3: 型の対応は決まった表だけで、`Lin` の引数は借りて組で返す

- 決定
  - 引数の型の対応は次の表だけである。

    | eml の引数 | C | 渡し方 |
    |---|---|---|
    | `Int`、`Int as int64_t` | `int64_t` | 値 |
    | `Int as int`、`Int as int32_t` | `int32_t` | 値。範囲を確かめる |
    | `Int as size_t` | `size_t` | 値。範囲を確かめる (`>= 0`) |
    | `Float` | `double` | 値 |
    | `UnboxedArray Float`、`UnboxedArray Int` | `const double*`、`const int64_t*` | 借りた配列の要素 0 へのポインタ |
    | `MutUnboxedArray Float`、`MutUnboxedArray Int` | `double*`、`int64_t*` | 借りた配列の要素 0 へのポインタ。結果の組で返す |
    | `String`、`Bytes` | `const char*`、`const uint8_t*` | 借りた本体へのポインタだけ。長さは利用者が別の `Int [as …]` の引数で渡す |
    | ハンドル (`extern "C" data`) | `void*` | 借りる。結果の組で返す |
    | ただ1つの引数の `Unit` | 引数なし | なし |

  - 結果 R は `Unit` (void)、`Int` (`as` を付けてよい)、`Float`、ハンドルのどれかである。`Lin` の引数 (`MutUnboxedArray` とハンドル) があるときは、結果をちょうど組 `(R, Lin の引数の型を引数の順に)` と書く。R が `Unit` でも組の先頭に置く。利用者が組を書き、処理系は推論しない。
  - `as` の後に書ける C の型の名前は `int`、`int32_t`、`int64_t`、`size_t` の4つだけである。`long` は Win64 で 32 bit なので入れない。
  - `Bool` と enum は対応させない (`Int` を使う)。型変数、関数の型、`Array`、ハンドルでない data とレコード、結果の位置の `String`、`Bytes`、配列は E2022 になる。
  - 範囲: 範囲の外の `Int as int|int32_t|size_t` の引数は、呼ぶ前に `Panic` を上げる。文言は `` argument {i} of `{name}` does not fit in C `{ctype}`: {value} `` で、位置は呼び出しの `Loc` である。`int` の文言も `int32_t` と書く。結果は確かめない (`int` は符号を広げ、`size_t` は読み替える)。
  - null: ハンドルを返す C の関数が NULL を返すと、呼んだ後で `` `{name}` returned a null handle `` の `Panic` を上げ、何も確保しない。だからハンドルの物体は null にならず、`Option` の型は要らない。
  - 効果: 最後の矢印の行は、ちょうど {`faults` のとき `Panic`} ∪ {`pure` でないとき `IO`} ∪ {`blocking` のとき `Async`} でなければならない。内側の矢印は行を持たない。違えば E2023 である。
  - `Lin` の引数は借りて返す。C の行は引数を消費しない。`MutUnboxedArray` を貸す C の行は `writes` を持つ。呼び手の配列は C が書き込んだその配列なので、呼んだ後の `con` は書かれた配列を返す。
  - 次の段の `CSubmit` は、返す値が操作の番号だけで、何も貸し戻さない (`with_args = []`)。その `Lin` の引数は借りたままで、呼び手が持ち続ける。`CTake` は自分の `Lin` の位置を `with_args` に持つ。
  - スカラーを指すポインタの専用の構文は作らない。ILP64 の Fortran の LAPACK は、入力を長さ1の `UnboxedArray Int`、`info` と `ipiv` を `MutUnboxedArray Int`、行列を `MutUnboxedArray Float` で渡して呼ぶ。スカラーごとに1回の小さな確保が要るが、O(n^3) の LAPACK の仕事に比べて小さい。
  - `pure` の約束: 結果と、`MutUnboxedArray` の引数に書き込む中身は、引数の値と渡した物体の中身だけで決まり、呼び出しはほかに観測できる効果を持たない。処理系は、使われない `pure` の呼び出しを、行が `MutUnboxedArray` の引数を持たないときだけ消してよい。C の呼び出しを複製も並べ替えもしない。
  - 宣言する側の約束 (宣言を境目として信頼する部分)
    - `UnboxedArray`、`String`、`Bytes` で宣言した関数は、そのポインタを通して書かない。物体は共有されているかもしれず、凍った定数かもしれない。
    - ハンドルの状態を変える関数は `pure` にしない。
    - ポインタは呼び出しの間だけ有効である。
    - C の関数は橋渡しの関数を通して巻き戻らない (C++ の例外、SEH)。
- 理由
  - C の型が eml の型だけから決まる。信頼の境目を、利用者が読む所に書ける。
  - 借りて返す形は `lending_call` を使い回せ、`removable()` も正しいままである。ジョブの記録が「この物体を持ち続ける」の1つの規則で済む。
  - ポインタを運ぶ型がすべて「ポインタだけ、長さは明示」にそろう。長さの幅も利用者が選べ、`strlen` のような API も終端を明示すれば呼べる。
  - 範囲と null の `Panic` は worker の上の安い検査で、寸法の誤りや失敗したコンストラクタによる C の側のメモリの誤りを防ぐ。`faults` の行が `<Panic>` で費用を型に見せる。
- 退けた案
  - `Int as int` を黙って切り詰める、null のハンドルを値にする、`Option` のハンドルを返す: 危ないか重い。
  - スカラーを指すポインタの構文: 1つのライブラリの族のために3つ目の渡し方を作る。
  - `String`、`Bytes` を `(ptr, len)` の対で渡す: 長さが `int64_t` に固定され、ほとんどの C の API に合わない。
- 及ぶ範囲: 行の見え方、E2022、translate、変換、declarations.md
- 見直す条件: LP64 の LAPACK か `float` の buffer が要るとき (32 bit の要素の配列)。コールバック、構造体、可変長引数を入れるとき。
- 適合の確かめ
  - `Lin` の引数は借りて `(R, Lin の引数を順に)` で返さなければならず、C の行は引数を消費してはならない (MUST、MUST NOT)。`String`、`Bytes`、配列は本体へのポインタだけを渡さなければならない (MUST)。確かめ方: `c::a_c_row_borrows_every_object_and_returns_its_lin_arguments` が、C の行の `borrowed` が `Obj` の引数ですべて `true` で、`with_args` がその `Lin` の位置に等しいことを確かめる。`c::text_is_one_pointer_slot` が、`CParam::Text` が `CSignature` に `I64` を1つ足すことを確かめる。
  - 型の対応はちょうど上の表でなければならず、ほかは E2022 でなければならない (MUST)。確かめ方: 除く形ごとの check-fail の UI テストと `crates/eml_types/tests/ffi.rs` のテストが通る。declarations.md の「型の対応」の表の行が `CParam` と `CRet` の変種に等しい。
  - 宣言する側の約束と `pure` の約束は declarations.md に書かなければならない (MUST)。確かめ方: declarations.md に「宣言する側の約束」の見出しがある。`grep -n "MutUnboxedArray\` の引数を持つ行は消さない" docs/spec/declarations.md` と `grep -n "C の呼び出しを複製も並べ替えもしない" docs/spec/declarations.md` が当たる。
- リポジトリに残す所: docs/spec/declarations.md の「`extern "C"`」(T-6)、その下の「型の対応」と「宣言する側の約束」(T-7)、docs/spec/core-ir.md の「組を返す extern」(T-4、T-8)

#### D-4: 記号は宣言したモジュールの `link` から解決し、つなぐ失敗は診断にしない

- 決定
  - 関数の記号とハンドルの dtor の記号は、宣言したモジュールの `link` の item から解決する。translate がそのモジュールの `link` の並びを各 `CFunction` と `CHandleType` の `links` に写す。
  - 解決の順は次のとおりである。
    1. 登録した記号 (`Linker::with_symbols`。テストの fixture が使う)
    2. 動いている OS の `link` の item を、書いた順に。そのライブラリは、書いた文字列が `--link` の KEY ならその VALUE、ほかは書いた名前である。動いている OS のライブラリはすべて開けなければならず、開けなければ `LinkError::Library { name }` である。記号はそれぞれのライブラリで探す
    3. プロセス (unix は `libloading::os::unix::Library::this()`。Windows は実行ファイル、その次に `ucrtbase.dll`)
    4. どこにもなければ `LinkError::Symbol { symbol, library }`。`library` は 2 の名前を並べたもので、2 がなければ `None` である
  - 名前の飾り: `/`、`\`、`.` を含む文字列はそのままローダーに渡す。ほかは `lib<name>.so`、`lib<name>.dylib`、`<name>.dll` にする。`framework "N"` は `/System/Library/Frameworks/N.framework/N`、次に `/Library/Frameworks/N.framework/N` を試す。
  - `--link KEY=VALUE` は繰り返して書け、`run` と `repl` で使える。KEY は `link` の item に書いた文字列と、OS によらず比べる。書いた文字列は名前か framework の名前で、道の文字列はそのまま比べる。合う item のうち動いている OS のものは、すべて VALUE (同じ規則で飾る) を代わりに開く。プログラム全体で、書いた名前ごとに効く。
    - `eml run`: コンパイルしたプログラムのどの `link` の item にも合わない KEY は `LinkError::UnknownOverride` で、exit 1 にする。
    - `eml repl`: この検査をしない。上書きはセッションの間 `Linker` が持ち、後の入力の `link` の item にも効く。`:load` と `:reload` で作り直すセッションにも引き継ぐ。
  - 使われない C の宣言はつながない。
  - ライブラリと JIT のコードは、プロセスの間ずっと閉じず、解放しない。ライブラリは `ManuallyDrop<libloading::Library>` で持ち、`free_memory` は呼ばない。
  - つなぐ失敗は `eml_native::LinkError` で、文言は決まっていて、OS の文言を含まない。
    - `library "{name}" was not found`
    - `symbol "{symbol}" was not found`。2 のライブラリがあれば、後ろに ` in {library}` (引用した名前を `", "` でつないだもの) を付ける
    - `--link names no library "{key}"`
    - `C functions cannot be called on this machine: {reason}`
  - `eml_cli` が `link error: {e}` を stderr に出し、`run` は exit 1、REPL は `Outcome::Unlinked` にする。診断にも `CompileError` にもしない。`eml check` はつながない。
- 理由
  - モジュールごとの解決は、複数のライブラリがあっても順序によらない。
  - `links` を写すので、`eml_extern` がモジュールの識別 (`ModuleKey`、HIR の物) を持たずに済む。
  - 閉じないので、`CCall` と `Dtor` のポインタを寿命の結びつきなしに使える。
  - ライブラリがあるかは機械の事実で、ソースの診断ではない。文言を固定するので、テストが stderr をバイトまで比べられる。
- 退けた案
  - `--link` で全部のライブラリを置き換える、モジュールごとに置き換える: 2つのライブラリで壊れ、CLI にモジュールを指す手がない。
  - cranelift-jit 自身の `dlsym` の検索: モジュールごとのライブラリも上書きも表せない。
  - つなぐ失敗に E の番号を付ける: 上の理由。
  - すべての宣言をつなぐ: 1つの任意の記号がないだけで、すべてのプログラムが動かなくなる。
- 及ぶ範囲: `eml_native::Linker`、`eml_cli` の引数の読み、REPL。AOT には及ばない (`native-aot` では `link` の item がリンカの引数になる)。
- 見直す条件: パッケージを入れるとき。AOT を作るとき。
- 適合の確かめ
  - 記号 (関数と dtor) は、`CFunction` と `CHandleType` に写した `links`、次にプロセスの順で、宣言したモジュールごとに解決しなければならない (MUST)。確かめ方: `linker::each_function_uses_its_own_links`、`linker::a_dtor_resolves_like_a_function`、`linker::a_missing_dtor_is_a_symbol_error` が通る。
  - `--link KEY=VALUE` は、書いた文字列でプログラム全体に効かなければならない (MUST)。確かめ方: `linker::an_override_replaces_the_written_name` と `cli::link_override_replaces_the_library` が通る。`terminal::link_overrides_survive_reload` が通る。
  - ライブラリと JIT のコードは、プロセスの間ずっと閉じても解放してもならない (MUST NOT)。確かめ方: `grep -rn "ManuallyDrop<libloading::Library>" crates/eml_native/src` が当たる。`grep -rn "free_memory" crates/eml_native/src` が何も出さない。
  - つなぐ失敗は決まった文言の `eml_native::LinkError` で、OS の文言を含まず、`eml_cli` が `link error: {e}` で exit 1 (`run`) か `Outcome::Unlinked` (`repl`) にしなければならない (MUST)。診断にも `CompileError` にもしてはならない (MUST NOT)。確かめ方: `cli::a_missing_library_is_a_link_error` と `cli::a_missing_symbol_is_a_link_error` が4つの OS の CI で通る。この2つは `crates/eml_cli/tests/ffi/` のファイルを binary で流す。UI の run-fail の道は `RuntimeError` を求めるので使わない。`grep -rnE "LinkError|NoLinker|Link\(" crates/eml_vm/src` が何も出さない。`linker::link_error_texts` が通る。
  - `eml check` はつないではならない (MUST NOT)。確かめ方: `timeout 20 cargo run -p eml_cli -- check crates/eml_cli/tests/ffi/missing_library.em` が何も出さずに exit 0 になる。`cli::check_loads_no_library` が通る。
- リポジトリに残す所: docs/spec/vm.md の「ライブラリと記号」(T-2) と「`--link`」(T-11)、docs/spec/stdlib.md の「起動」(T-11)、docs/spec/repl.md (T-11)、docs/spec/declarations.md の「`extern "C"`」(T-6)

#### D-5: 変換は `ffi.rs` の1か所で、命令は名前で振った `CodeBase` の番号で C の関数を指す

- 決定
  - 引数を `u64` の slot にする変換と、結果を値に戻す変換は、`eml_vm/src/ffi.rs` に1つだけ置き、両方のモードで使う。範囲の検査は呼ぶ前に、null のハンドルの検査は呼んだ直後に行い、どちらも `abort_to` で `Panic` を上げる。
  - `Op::Ffi` の operand は、`load` が `Index.c_functions` で名前から振った `CodeBase` の C の関数の番号である。逆アセンブラは正規の名前を出す。
  - `load` は、すでにある名前で違う `CFunction` が来たら `CompileError::Mismatch` を返し、誤りのときは何も書かない。`Machine` が生きている間、何も外さない。REPL で同じ名前を宣言し直すと、別の `Session(k)` のモジュールの別の名前になる。
- 理由
  - 変換の実装が1つで済む。C の呼び出しそのものは失敗しない (範囲の検査が前に済んでいる)。null のハンドルの物体はない。
  - vm.md の「追記」は、関数、定数、効果、ファイルを名前か中身で振り直し、作り直したコードを、operand を名前で書いた逆アセンブラの文字で比べる。名前で振れば、C の関数もこの比べ方に乗る。「同じ名前なら同じコードと ABI」も保てる。
- 退けた案: 行の番号のように生の番号を operand にする: 追記のたびに番号がずれ、作り直しの比べ方が壊れる。
- 及ぶ範囲: `Op::Ffi`、`load`、`disasm`。次の段の `blocking` の道も同じ変換を使う。
- 見直す条件: `jit-core` がネイティブのコードで変換を展開するとき。
- 適合の確かめ
  - 変換は `eml_vm/src/ffi.rs` に1つだけ置き、両方のモードで使わなければならない (MUST)。範囲の検査は呼ぶ前に、null の検査は呼んだ直後に、`abort_to` で `Panic` を上げなければならない (MUST)。確かめ方: 橋渡しにモードの枝がない。`ffi::an_i32_argument_is_range_checked_before_the_call`、`ffi::a_null_handle_raises_panic_and_allocates_nothing` と、run-fail の UI テスト `range_panic.em` と `fixture_null_handle.em` が両方のモードで通る。
  - `Op::Ffi` の operand は `Index.c_functions` で名前から振った `CodeBase` の番号でなければならず、逆アセンブラは正規の名前を出さなければならない (MUST)。確かめ方: `ffi::loading_the_same_c_function_twice_keeps_one_entry` が debug の作り直しの比べ方に通り、`ffi::a_redeclared_c_function_with_another_signature_is_a_mismatch` が `Mismatch` を返す。`ffi::the_disassembly_names_the_c_function` が通る。

#### D-7: 構文は文脈で決まる語と、C の署名の中だけの `as`

- 決定
  - 文法 (docs/spec/grammar.md の「項目」)

    ```
    item        ::= 'pub'? 'abstract'? ('extern' extern_decl | 'extern' STRING c_decl | link_decl | decl)
    c_decl      ::= c_attr* (c_signature | 'data' UIDENT ('drop' STRING)?)
    c_attr      ::= 'pure' | 'blocking' | 'symbol' STRING
    c_signature ::= var ':' c_type                        -- 原子の `Int` に 'as' LIDENT を付けてよい `type`
    link_decl   ::= 'link' 'on' LIDENT (STRING | 'framework' STRING)
    ```

  - `as`: `extern "C"` の署名の中でだけ、型の parser は原子の型の後に `'as' LIDENT` を受ける。`->`、`,`、効果の行より強く結びつく。だから `-> <IO, Panic> Int as int` と `-> <IO> (Int as int, MutUnboxedArray Float)` は曖昧でない (行はどこでも結果の型の前に来る)。結果は原子の型の節の子 `C_WIDTH` である。HIR は幅を型の横に記録し (`CDecl.widths`)、`TypeRef` は普通の `Int` のままである。普通の型の文法は AS_KW を読まない。どの位置に `as` を書けるかは、parser でなく型の段 (E2022) が決める。
  - 文脈で決まる語: `pure`、`blocking`、`symbol`、`link`、`on`、`framework` は LIDENT のままで、この位置でだけ字面で見分ける。lexer の `keyword()` は変えない。item の始めの `LIDENT("link") LIDENT("on") LIDENT (STRING_START | LIDENT("framework"))` は `link` の item で、`at_equation` より先に見る。この形の等式は書けなくなる (grammar.md の「文法上の補足」に書く)。
  - `extern "C"` はどの種類のモジュールにも書ける。属性のない `extern` は、利用者のモジュールでは今のまま E1033 である。`pub` は `extern` と同じに扱う。`abstract`、instance の `extern` のメンバー、`extern "C" effect`、`extern "C" data` の型の引数、C の署名の文脈は、今のまま E0011 か E1040 である。
  - 属性はどれも1回までで、`pure` と `blocking` は一緒に書けない。`symbol` の文字列はそのまま使い、既定の記号は宣言した eml の名前である。
  - `extern "C" data T drop "f"`: 不透明なハンドルの型で、`Lin`、`Repr::Obj`、`CHandle` で表す。`drop` は書かなくてよい。dtor の C の署名は `void f(void*)` で、値を返す関数 (`fclose`) を書いてもよく、戻り値は捨てる。dtor は物体を解放するときに、その物体を解放する worker のスレッドで走る。スレッドの固定は保証しない。
  - `link on <os> …` は最上位の item で、いくつでも、どこにでも書ける。`<os>` は `linux`、`macos`、`windows` で、`framework` は `macos` とだけ書ける。
  - C の署名に型変数を書けない (E2022)。
  - `blocking` は、この段では構文と型の検査を通したうえで E0004 で断る。
  - 診断
    - E0018 `EXTERN_C_ATTRIBUTES` (`eml_syntax`): 属性の重複、`pure` と `blocking`、置けない所の属性、`symbol` と `drop` の後の文字列がない、補間のある文字列、形の崩れた `link`、ABI のない属性
    - E1059 `INVALID_EXTERN_C` (`eml_hir`): `C` でない ABI の文字列、`as` の後の知らない C の型の名前、空の `symbol` と `drop`
    - E1060 `INVALID_LINK` (`eml_hir`): 知らない OS、`macos` でない所の `framework`
    - E2022 `FFI_UNSUPPORTED_TYPE` と E2023 `FFI_EFFECTS` (`eml_types`): D-3
    - E0004 (`eml_types`): `blocking`
- 理由: 識別子を奪わない。行と組との曖昧さがない。Haskell も文脈で決まる語を使う。
- 退けた案: `link`、`pure`、`symbol` を固い予約語にする: 識別子を奪う。
- 及ぶ範囲: `eml_syntax`、`eml_hir`、`eml_types`、lexical.md、grammar.md、declarations.md、diagnostics.md
- 見直す条件: 構文の文脈で決まる語を、ほかの所にも入れるとき。
- 適合の確かめ
  - 文法は、それぞれの位置でだけ字面で見分ける文脈の語と、今ある `as` と `drop` のキーワードを使わなければならない (MUST)。`as` は `extern "C"` の署名の中でだけ、前の原子の型に結びつかなければならない (MUST)。確かめ方: `git diff --exit-code <T-5 の前のコミット> -- crates/eml_syntax/src/lexer` が差分を出さない。`types::as_binds_before_the_row_and_the_tuple` が `-> <IO, Panic> Int as int` と `(Int as int, MutUnboxedArray Float)` を確かめる。`declarations::pure_is_still_a_variable_name` と `types::as_outside_extern_c_is_not_a_type` が通る。
  - `blocking` は、この段で構文と型の検査を通し、E0004 で断らなければならない (MUST)。確かめ方: `tests/ui/check-fail/ffi/blocking.em` のスナップショットが E0004 の診断をちょうど1つだけ持つ。
- リポジトリに残す所: docs/spec/grammar.md の「項目」と「文法上の補足」、lexical.md の「キーワード」、diagnostics.md (T-5)、declarations.md の「`extern "C"`」(T-6、T-7)、diagnostics.md の E1059、E1060 (T-6)、E2022、E2023、E0004 の一覧 (T-7)

#### D-8: C の呼び出しのテストは、何も入れずに4つの OS で走る

- 決定
  - 4つの OS の CI で、何も入れずに C の呼び出しを確かめる。Rust で書いた fixture の関数を `Linker::with_symbols` で登録し、C の標準ライブラリを `link` で開く。
  - BLAS は `#[ignore]` のテストと例のプログラムにだけ置く。
  - OS で飛ばしてよい FFI のテストは、macOS の framework の道の単体テスト (`#[cfg(target_os = "macos")] linker::accelerate_loads_as_a_framework`) と、`#[ignore]` の BLAS のテスト (macOS だけの `cli::blas_dgesv` を含む) だけである。
  - `eml_vm` のテストと Miri は、Rust の橋渡しで手で作った `Linked` を通して `Op::Ffi` を流し、Cranelift を使わない。`eml_native` は、自分の複数スレッドのテストと、2回目の finalize のテストを持つ。
- 理由: テストの規則は、道具がないことによる飛ばしを禁じている。CI に BLAS はない。Miri は JIT のコードを動かせず、JIT の道のスレッドの安全さには専用のテストが要る。
- 退けた案
  - ワークスペースの `cdylib` を fixture にする、テストの binary から記号を出す: OS ごとに道と出し方の規則が違う。
- 及ぶ範囲: UI、`eml_native`、`eml_vm`、`eml_cli` のテスト
- 見直す条件: CI に C のコンパイラか BLAS を入れるとき。
- 適合の確かめ
  - テストは、何も入れずに4つの OS の CI で C の呼び出しを確かめなければならない (MUST)。確かめ方: `tests/ui/run/ffi/` の `libm_*.em` と `fixture_*.em` が4つの OS の CI で通る。
  - BLAS は `#[ignore]` のテストと例に留めなければならない (MUST)。確かめ方: `cli::blas_dgemm` と `cli::blas_dgesv` が `#[ignore]` を持つ。上の2つのほかに、OS で飛ばす FFI のテストがない。
  - `eml_vm` のテストと Miri は、手で作った Rust の橋渡しの `Linked` で `Op::Ffi` を流し、Cranelift を使ってはならない (MUST、MUST NOT)。確かめ方: Miri の `-p eml_vm --test integration miri::` が2つの設定で通る。`crates/eml_vm/tests` が `eml_native` を使わない (`grep -rn "eml_native" crates/eml_vm` が何も出さない)。
  - `eml_native` は、複数スレッドと2回目の finalize の橋渡しのテストを持たなければならない (MUST)。確かめ方: `bridge::eight_threads` と `bridge::second_finalize_keeps_pointers` があって通る。
- リポジトリに残す所: docs/implementation/testing.md の「`eml_native` の検証」(T-2)、「UI テスト」(T-12)、「AddressSanitizer」と「ThreadSanitizer」(T-14)

#### D-9: 段は、行を変える Step A と ABI の門を、最初の C の行より先に通す

- 決定
  - `eml_extern` の作り直しは Step A として、組み込みの行だけで、テストの期待値を変えずに入れる。Step A のコミット (T-3) は、種類3の機械的な変更と、足すだけの変更 (たとえば `faulting_rows_carry_panic` の `faults` の assert、`row_result` の受け渡し) を含んでよい。`.snap`、inline のスナップショット、UI の出力は変えない。期待値の変わる既存のテストは `only_the_listed_rows_borrow_or_return_a_pair` だけである。
  - `eml_native` の橋渡しのテストを4つの OS の CI で通してから、Step B (最初の `ExternRef::C`、T-4) に進む。データだけの C の型 (T-1) と `eml_cabi` (T-1b) は、Step A より先に入れてよい。
- 理由: 変更の及ぶ範囲を小さく保ち、ABI の障害を先に見つける。
- 退けた案: 行の変更と C の行を1つのコミットにする: 約 35 のファイルにまたがる機械的な変更を、意味の変更と分けて読めない。
- 及ぶ範囲: この段のコミットの順
- 見直す条件: なし
- 適合の確かめ
  - `eml_extern` の作り直しは、C の行より前に Step A として入れなければならない (MUST)。確かめ方: T-3 のコミットで `git diff --stat HEAD~1 -- '*.snap'` が何も出さず、`git diff HEAD~1 -U0 -- 'crates/*/tests/*.rs' | grep -E '^[-+].*@"'` が何も出さない。
  - `eml_native` の橋渡しのテストは、Step B より前に4つの OS の CI で通らなければならない (MUST)。確かめ方: `git log --reverse --format=%s main..HEAD` で `Add eml_native with C bridges and the linker` が `Add C rows to Core IR and LIR` より前にある。T-2 の後の CI の門の記録がある。
- リポジトリに残す所: 要らない (段の中の順で、閉じるコミットのメッセージに残す)

#### D-13: Step A の行の形

```rust

    pub held: &'a [bool],

#[derive(Clone, Copy, Debug, PartialEq, Eq, Hash)] pub enum ExternRef { Std(Extern) }
impl From<Extern> for ExternRef
impl ExternRef {
    pub fn std(self) -> Option<Extern>;
    pub fn row(self, c: &[CFunction]) -> FunctionRow<'_>;
    pub fn from_name(name: &str, c: &[CFunction]) -> Option<ExternRef>;
```

- 静的な表は `FunctionRow<'static>` である。`kinded` とほかのすべての作る関数は、`faults: !matches!(purity, Purity::Pure)`、`writes: false`、`with_args: &[]` を入れる。50 の `with_arg: Some(k)` は `with_args: &[k]` に、`with_arg: None` は `&[]` にする。

#### D-16: 型の検査

- 番号: `FFI_UNSUPPORTED_TYPE = ErrorCode(2022)`、`FFI_EFFECTS = ErrorCode(2023)`

  ```rust
  pub enum CArg { Int(CInt), Float, UnboxedArray, MutUnboxedArray, Text, Handle(TypeDefId), NoArg }
  ```

- E2022 は、メッセージ `` `{type}` cannot cross to C here `` と、理由ごとのラベルを持つ。理由は、型変数、関数の型、`Array`、data とレコードと `Bool` と enum (`Bool` のラベルは `use Int`)、R の位置の `String`、`Bytes`、`UnboxedArray`、`MutUnboxedArray`、`Lin` の引数がないのに組の結果、R の後ろが `Lin` の引数の型の順でない組、引数の `Int` と `Int` の R のほかの `as`、ほかの引数と一緒の `Unit` である。宣言ごとに、位置ごとに1つずつ、すべての誤りを出す。

#### D-17: translate

- `extern_row` (expr.rs:24) を、純粋な `extern_target(hir, function) -> Option<ExternTarget>` にする。`pub(super) enum ExternTarget { Std(Extern), C(FunctionId) }` で、`ExternTarget::arity(self, hir) -> usize` は std では `row.params.len()`、C では署名の引数の数である。`numbering` (mod.rs:142) は `ExternTarget` と `arity` だけを使う。

## 6. 実装の決まり

- どのコミットの後も、`cargo build`、`cargo nextest run`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` が通る (CLAUDE.md)。どのタスクの完了の基準にも、書いていなくても含まれる。
- テストの集まりの確かめ (どのタスクにも当てる)
  - タスクの前に `cargo nextest list --workspace --message-format oneline | sort > "$SCRATCH/tests-before.txt"` を流す。後に同じものを `tests-after.txt` に書く。`$SCRATCH` はリポジトリの外の作業用のディレクトリである。

## 付録: レビューで変わったこと (蒸し返さないために)

- `pure` の C の行が `MutUnboxedArray` を書く場合: 初めの案は、こうした行を消してよい `Pure` にしていた。結果の `Unit` を捨てると書き込みごと消えるとレビューが確かめた。次の案の「書く行を `Effectful` にする」も、「メモリを書く」と「IO を上げうる」を混ぜるので退け、行に `writes` の印を足して `removable()` が `!writes` を見る形にした (D-2)。
- linker の境目: 初めの案は `CLinker` の trait を `eml_extern` に置き、`Arc<Mutex<dyn CLinker>>` を `RunConfig` に持たせていた。葉の crate に lock と `unsafe` が入り、`Machine` の欄の順に頼る安全の議論になるので退けた。`eml_cabi` を作り、呼び手が `Linker::link` で作った `Linked` を `load` に渡す形にした。`CompileError::Link`、`CompileError::NoLinker`、`RuntimeError::Link`、`RunConfig::with_linker` は作らない (D-1、D-4)。
- `LinkError` の置き場所: `eml_extern` から `eml_native` に移した。VM がつなぐ失敗を知らないためである (D-4)。
- `eml_extern` の `unsafe`: 一時は `#![deny(unsafe_code)]` と `CCall` の2つの `allow` にしていた。`eml_cabi` に移したので、`eml_extern` は `unsafe` を持たない (D-1)。
- ライブラリを閉じないこと: 初めは `Machine` の欄の順で `Linker` を最後に drop させていた。`ManuallyDrop` と、cranelift-jit が drop でコードを解放しないことに頼る形に替えた (D-4)。
- null のハンドル: 初めは null のハンドルを値にできた。呼んだ後の `Panic` にし、`faults` に入れた (D-3)。
- `String` と `Bytes`: 初めは `(ptr, len)` の2つの slot で、長さが `int64_t` に固定されていた。ポインタだけにして、長さは利用者が幅を選んで渡す形にした (D-3)。
- under の形の判断: 初めは巻き戻しの地点だけを `faults` にしていた。under の形も「中断を始めうるか」で決まるので、同じ `faults` にした (D-2)。
- `faults` の範囲: 同期の C の行の規則 (狭める引数かハンドルの結果) は、次の段の `CSubmit` (狭める引数) と `CTake` (いつも) には当てない (D-2)。
- `ExternRef::C` を match してよい場所: 初めの一覧は定義、print と parse、逆アセンブラを落としていた。D-2 の一覧に広げた。
- つなぐ失敗のテスト: 初めは UI の run-fail のテストだった。`link error:` は `eml run` だけが出し、UI の run-fail の道は `RuntimeError` を求めるので、`cli.rs` から binary で4つの OS を確かめる形にした (D-4)。
- `eml_vm` の中の `Link` の grep: 初めの確かめは `grep -rn "Link" crates/eml_vm/src/error.rs crates/eml_vm/src/compile/mod.rs` だった。基点の `struct Links` と、`load` が受け取る `Linked` に当たるので、`grep -rnE "LinkError|NoLinker|Link\(" crates/eml_vm/src` に替えた (D-4)。
- Step A のテストの変更: 「期待値を変えない」を、種類3と足すだけの変更は許し、`.snap`、inline のスナップショット、UI の出力は変えず、期待値の変わる既存のテストは1つだけ、と読むことにした (D-9)。
- 引用の決まり: 初めの案は、まだない見出しを注釈から引いていて、`citations.rs` が落ちる形だった。見出しを作るタスクを D-22 に決め、引用はその後のコミットに置く (6 章)。
- `ffi.rs` の形: 次の段が使えるように、`marshal` と `unmarshal` は値か `Raise` を返し、slot に書くのは `call` だけにした。`call` は `raise` と `write_out` の2つの補助を使い、次の段はこれを使い回す (D-19)。
- `CFunction` の行の作り直し: 欄を書き換えると `row` が古くなるので、作るのはいつも `CFunction::new` にした (D-10)。
- REPL の `--link`: 初めは始めのセッションにだけ上書きを渡していた。`:load` と `:reload` が作るセッションにも渡すようにした (D-20)。
- REPL のつなぐ失敗の入力: コンパイルの誤りの入力と同じに捨て、`Machine` もセッションのモジュールの並びも変えない (D-20)。
- 途中で panic する状態: 一覧に、T-10 と T-11 の間の `linked.fits` の assert を足した (6 章)。
- fixture の番号: 初めは tag の範囲を書くだけだった。fixture のファイルがどれも `-- fixture ids: A..B` を持ち、範囲が重ならない形にした。確かめるテストは次の段が足す (D-21)。
- 段を閉じるときの roadmap: `ffi-blocking` と `jit-core` の「前提」から `ffi-c` を外す手順を足し、grep の範囲に `docs/future` を足した (T-15)。
- スカラーを指すポインタの構文: LAPACK のために作る案は退け、長さ1の配列で呼ぶ形にした (D-3)。
- 別の cargo の feature: `eml_native` を別の feature にする案は、試作で測った費用 (準備は 1 ms 未満で、最初に使うときにだけ払う) に見合わないので退けた (D-1)。
