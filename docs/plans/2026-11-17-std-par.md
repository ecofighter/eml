- Created: 2026-11-17 (design-level plan).
- Base: the `Close task-limits` commit. Facts in 01 describe main @ 4a2954c1; the refresh re-checks them.

## 1. Goal and completion conditions

- Goal: `std/Par` gets the data-parallel API, written in eml over `par` with a two-level spine split; results are stitched by the pure rows `Array.concat` and `UnboxedArray.concat`. No runtime entry forks over a range and no block is written by two threads.
- Completion conditions:
  - G-5: `grep -nE '^(pub )?extern' std/Par.em` shows `fork_join` only; float `reduce` is bit-equal at N = 1, 2, 8 and two seeds.
  - The API of D-SP-1 exists with the rows and signatures stated in stdlib.md; every callback has row `<Panic>` and every function has `Panic` in its row.
  - The spine's shape for three lengths is pinned by a test; `try_map` returns the leftmost `Err` after evaluating every element.
  - New `bench/` rows (boxed and unboxed cheap map, `reduce`, `tabulate_unboxed` over `Float`) with pinned `RunStats` in `crates/eml_vm/tests/bench.rs`.

## 2. Scope

- In: D-SP-1..D-SP-6; the two `concat` rows in every place a row lives today (VM arm, `extern_rows!` line, native lowering, the `eml_extern` table and the std declaration, tied by the existing tests).
- Out: moving unique chunks in `concat` and lending a `Raw` payload (later items with conditions, already in the roadmap); native speed-up measurements (`jit-tasks` JT-14, which also measures bytes per spine level and may add the three-level split of D-SP-2).

## 3. Received from earlier stages

- `par-total`: `par : (Unit -> <Panic> a) -> (Unit -> <Panic> b) -> <Panic> (a, b)` over `fork_join`; a child's error ends the run.

## 4. Decisions (01 §8)

- D-SP-1: API: `for_range`, `reduce_range`, their `_grain` forms, `tabulate`, `map`, `mapi`, `reduce`, `for_mut`, `try_map`, `tabulate_unboxed`, `for_mut_unboxed`; `par` and `both` stay public.
- D-SP-2: chunks of `GRAIN = 1024`, groups of `B = ceil(sqrt(chunks))`; the top level forks `par (rest) (last group)`, a group forks `par (rest) (last chunk)`; the shape depends only on length and grain; `reduce`'s combination order is the left-nested order of this shape (stated in stdlib.md). Fork depth is `O(sqrt(n / grain))`.
- D-SP-3: a leaf builds its chunk with the sequential `tabulate`; inner nodes return a std-private rope; the caller makes an `Array (Array a)` and calls `pub extern concat : Array (Array a) -> <Panic> Array a` (std/Array.em) and `pub extern concat : Array (UnboxedArray a) -> <Panic> UnboxedArray a` (std/UnboxedArray.em); `Panic` because the summed length can exceed `MAX_LEN`; first version: one new reference per element, then the outer array is released; no `eml_rt` change.
- D-SP-4: `for_mut f a` = `freeze`, `mapi`, `thaw`; `for_mut_unboxed` copies once per pass.
- D-SP-5: `try_map` evaluates every element and returns the leftmost `Err`.
- D-SP-6: no runtime entry forks over a range.
- Criteria: G-5, S-20, E3.

## 5. Units (in order)

1. SP-1 `Start std-par`: plan; the names that clash with existing `std/Par` or `std/Array` items; baseline.
2. SP-2: the `concat` rows (VM arm, `extern_rows!` line, native lowering, table and std declarations).
3. SP-3: range functions and the spine (`for_range`, `reduce_range`, `_grain` forms).
4. SP-4: collections (`tabulate`, `map`, `mapi`, `reduce`, `for_mut`, `try_map`, the unboxed forms).
5. SP-5: tests (float bits across N = 1, 2, 8 and two seeds; leftmost `Err`; marking of a boxed input; the spine's shape for three lengths) and the `bench/` rows with pinned `RunStats`. The `Float` row calls `Par.tabulate_unboxed` with a body that returns a `Float` computed from the index, over at least four chunks, and is pinned at two lengths n and 2n; boxes per element = (allocations(2n) - allocations(n)) / n minus the same quotient of the unboxed `Int` row. The executable plan states the expected value.
6. SP-6 `Close std-par`. Reads two later items: `f$ret` (second review condition) with the `Float` row's boxes per element, and 「row変数の上限`<never e>`を言語からなくすこと」 with `grep -rnE '<never' std/`. Outcomes as 00 §D D-14 (c) says; the Close message carries both results and the report to the user asks whether to schedule the `<never e>` removal.
