## 1. 目的と完了の条件

- 目的: コードはまだ生成せずに、ネイティブのコード生成器が立つ土台を置く。`eml_rt`では、ネイティブのコードが読む欄を1つの`#[repr(C)]`の構造体`Native`にまとめて`Ctx`の先頭に置き、`offset_of!`から求めた定数、faultを置く仕組み、信頼の行T18を足す。`Meta`、`Word`、`rc`の符号と箱の値の語を外に出し、`Ctx::bytes_empty`を失敗しないものにする。新しいcrate `eml_nrt`に、AAPCS64、SysV x86_64、Win64の`eml_enter`と`eml_fatal`のstub (フレームレコード付き)、`JmpBuf`、エントリのマクロと記述子の表を置く。`eml_native`に`eml_rt`、`eml_lir`、`eml_nrt`への辺、Craneliftのフラグを作る唯一の関数、reuseの上限のconstのassert、ABIのテストを足す。`bench/rt-gate.sh`と`nrt_bench`の行を足す。`docs/future/`のネイティブの設計の文を、jitの段の決定に合わせて書き直す (T0)
- 完了の条件: T-plan、T0、R0〜R4、N1〜N3、A1、Closeをそれぞれ1コミットで入れ (7のCIの手順で足す直しのコミットは別に数える)、各作業の完了の条件と9の全体の検証が、すべて期待どおりになること。CIのチェックポイントG1、G2、G3が、CIの4つの対象 (macOS、Linux x86_64、Linux aarch64、Windows) で緑になること。赤い対象が1つでもあれば段を閉じない。利用者の決定をこの計画に書かずに、`cfg`で対象を外すことはしない (N-33)。VMのスナップショットは変わらない。`nrt_bench`の行がbenchmarks.mdの「ネイティブの数値」に記録されている (N-39)

## 3. 背景

- `Ctx<M>`は`repr(Rust)`である (`crates/eml_rt/src/heap/ctx.rs:819-836`)。`yielding`はその欄の1つで、`heap/`の下の10のファイルに`.yielding`が195回現れる (メソッドの`yielding()`は別)。欄を名指す構造体の式は`for_worker` (L1065-1100) だけである。`size_of::<Heap<Fast>>()`は1232、`size_of::<Ctx<Fast>>()`は1456である [付録02の§7の1]
- 生のポインタの欄を持つと`Ctx`は`!Send`になり、`eml_vm`がコンパイルできなくなる (`workers.rs:883`、`lib.rs:1088`) [付録01の§7の1]。`unsafe impl Send`は、`verus!`の外で許された書き方である (`trust.rs:254-259`)
- `Meta` (`meta.rs:153-161`) は`KIND_SHIFT`、`KIND_MASK`、`LIN`を非公開で持つ。`Word` (`word.rs:45-47`) にはタグの定数がない。`rc.rs`の`LOCAL_MAX`と`DUP_LIMIT`は`pub`でなく、`rc`は公開のモジュールでない (`lib.rs:30`)。rt-layoutの`layout.rs`は`INLINE_SCAN_LIMIT` (L35) を持つ。箱の値の語は、`heap/mod.rs`、`heap/recover.rs`、不変条件、`eml_vm/src/compile/constants.rs:8, 94-95, 113-114`に、リテラルの`0`と`1`で書いてある
- `Ctx::bytes_empty` (`heap/ctx/bytes.rs:405-422`) は要求ごとの予算を確かめるが、`array_empty`は確かめない
- `alloc.rs`のファイルの中のテストのモジュールに`catch_unwind` (L3655) があるので、N-3はgrepでなく単体テストで確かめる
- CIが流れるのは、`main`へのpush、pull request、`workflow_dispatch`だけである (`ci.yml:4-8`)。ブランチをpushしただけでは何も流れない。依存の辺の手順は`ci.yml:95-102`、clippyの行はL80である

### 5.1 長期の方針 (変えるには見直しが要る)

実装がこの節と食い違ったら、止めて報告する。全文と適合の基準N-1〜N-43は付録01にある (§8が基準)。付録01の§1.4が「契約で固定する」とする項目を変えるときは、利用者に戻す。それ以外は、§1.4の手順で変える (段の計画に変更を挙げ、同じコミットで`docs/spec/native.md`と呼ぶ所をすべて直し、記述子のテストが通る)。

#### D-1: crateと辺
- 決定: crateを2つ新しく作る。`eml_nrt`は、出すコードが呼ぶ`extern "C"`のエントリすべて、asmのstub、`JmpBuf`、`eml_fatal`、後で`Image`と実行の駆動を持ち、Cranelift、`eml_lir`、`eml_core_ir`、`eml_vm`、`eml_native`に依存しない。`eml_sched` (sched-splitで作る) は、実行の方式によらない共有の層である。`eml_native`はコード生成器とJITのホストで、`eml_nrt`、`eml_lir`、`eml_rt` (定数だけ) に依存し、`eml_vm`には依存しない。`eml_vm`は、Cranelift、`eml_native`、`eml_nrt`のどれにも依存しない。`eml_rt`は検証されたcrateのままでvstdだけに依存し、`extern "C"`、asm、`catch_unwind`を持たない
- 理由: native-aotは実行系とstubを`libeml_rt.a`にまとめ、利用者の機械にコンパイラを要しない。だからCraneliftと`eml_lir`なしでビルドできなければならない。`eml_rt`の規則は、shim、asm、`eml_io`や`eml_gui`の要る行を許さない
- 及ぶ範囲: jitのすべての段とnative-aot
- 見直す条件: 実行系のある部分が`eml_lir`かCraneliftのものを要するとき
- 適合の確かめ: N-1、N-2 (CIの依存の辺の手順。A1の5行)、N-3 (`trust::the_core_has_no_native_boundary`、R1)
- リポジトリに残す所: architecture.md (N1、A1)、native.mdの決定#1とmulticore.mdの「層の構成」(T0)

#### D-2: `Ctx`の先頭の`Native`
- 決定: `Ctx<M>`を`#[repr(C)]`にする。最初の欄は総称でない`#[repr(C)]`の構造体`Native`で、6つの欄 (`yielding`、`fault`、`stop`、`stack_limit`、`jmp`、`runtime`) を持ち、そのすぐ後が`heap`である。出すコードと`eml_nrt`は、`Ctx`の隣に置く`offset_of!`から求めた`CTX_*`の定数で読む。constのassertで、両方のモードでずれが0であること、`heap`が`Native`のすぐ後にあること、`CTX_*`の定数がどれも120以下で8の倍数であることを固定する。欄は、出すコードかasmにそれを読む所が初めてできる段で足す。Rustのコードだけが読むworkerごとの状態は、`runtime`の先の`eml_nrt`のworkerの構造体に置く。`eml_nrt`と`eml_native`はthread-localを使わない。ネイティブのコードは`Ctx<Fast>`だけを使う
- 理由: 出すコードは、末尾でない呼び出しのたび、関数の入り口のたび、`faults`の行の後のたびにこれらの欄を読む。ずれが0〜64なら、どの対象でも読みの符号がいちばん短く、yieldの語は対の命令で届く。代わりに、`Ctx`のメソッドから`Heap`の外の関数を呼ぶたびに`add`が1つ増える (付録01の§1.2(c)で測った)。この順は利用者が選んだ (付録00のU-6)
- 採らなかった案: `heap`を先に置く案 (共有の実行系の行はどれも遅くならないが、`yield`の得が約10%でなく2.7%になり、x86-64での読みがすべて32ビットのずれになる)。R1のゲートが落ちたときの代わりの手になる
- 及ぶ範囲: `eml_rt`、`eml_nrt`、`eml_native`、`eml_vm` (欄の書き方だけ)
- 見直す条件: R1のゲートが落ちたとき (`heap`を先にするかを利用者が決める)。後の段で、出すコードが読む欄が要るとき
- 適合の確かめ: N-4 (constのassertがコンパイルできる。`grep -rnE 'CTX_[A-Z_]+\s*(:|=)' crates/eml_native/src crates/eml_nrt/src` → 出力なし)、N-5 (`grep -rn 'thread_local' crates/eml_nrt/src crates/eml_native/src` → 出力なし)、N-6 (`grep -rnw 'Checked' crates/eml_nrt/src crates/eml_native/src` → 出力なし)
- リポジトリに残す所: object-model.mdの「欄」(R1)、native.mdの「安全点とスタック」(T0)

#### D-3: `eml_rt`が解釈しない欄のために出すもの
- 決定: 安全な関数として、`set_fault(Fault) -> Option<Fault>`、`take_fault()`、`stack_limit`と`set_stack_limit`、`runtime`と`set_runtime`、`jmp`と`stop_word` (この2つには書く関数を置かない) を出す。`fault`と`fault_value`は必ず一緒に変わる。3つのポインタの欄は`unsafe impl Send`を持つ`#[repr(transparent)]`の包みで、信頼の行T18が、それぞれのポインタの持ち主、有効な間、書く所、スレッドを越えるときの状態を述べる。`eml_nrt`は、`Ctx`がスレッドを移る所で`jmp`と`runtime`がnullであることをassertする (assertの所はjit-coreとjit-tasksで入る)
- 理由: 実行系はこれらの欄を検証されないコードから書く。検証されたcrateは、自分で守れることだけを述べる
- 及ぶ範囲: `eml_rt`、`eml_nrt`
- 見直す条件: `Native`に欄を足すとき
- 適合の確かめ: N-32 (`grep -n 'fn set_stop' crates/eml_rt/src -r` → 出力なし。T18の行。`eml_nrt::detached`)
- リポジトリに残す所: object-model.mdの「欄」、「置いた失敗」、「`unsafe` の核」(R1)

#### D-4: エントリ、そのABI、接頭辞ごとの失敗の手順
- 決定: 出すコードが呼ぶ実行系の関数は、すべて1つのマクロ`eml_nrt::entries!`で宣言し、関数と記述子の行を一緒に出す。ABIは、Cの既定の呼び出し規約、最初の引数が`ctx: *mut Ctx<Fast>`、ほかの引数はどれも`i64`か`f64`、結果は`i64`か`f64`を高々1つ、またはなし、または`!`である。接頭辞ごとの手順 (出すコードから見たもの): `eml_rt_*`は致命的な誤りだけで終わり、出すコードは何も確かめない。`eml_x_*`は、`faults`の行なら失敗を`Ctx`に置き、出すコードがfaultの語を確かめる。内部の種類の誤りと捕まえたpanicはshimの致命的な誤りの道で終わり、wrapperの本体は`eml_fatal`を名指さない (利用者がこの文を確かめた。付録00のU-8)。`eml_nrt_*`は行動の語を返すか、失敗の道が致命的な誤りだけなら値の語を返す (R-8)。任意のRustを走らせうるエントリはすべて`shim` (`catch_unwind`の後で`eml_fatal`を呼ぶ) にする。`plain`にするには、panicしない理由をspec/native.mdに書く。エントリは、それを呼ぶ所と同じ段で足す
- 理由: 宣言を1つにすれば、関数と、出すコードが作る呼び出しの型が一致する。速いモードのヒープの操作が返す`Err`は内部の種類だけである。`shim`は速い道で費用がない (測った)
- 及ぶ範囲: jitのすべての段
- 見直す条件: エントリが構造体か狭い整数の型を要するとき (契約の変更なので利用者に戻す)
- 適合の確かめ: N-7 (記述子の単体テスト。`Linkage::Import`が1つの関数にだけある。ABIのテスト(2))、N-8 (`the_table_has_only_named_prefixes`)、N-9、N-10 (shimの形を書くのはマクロだけ)、R-10 (`eml_fatal(`は`entries.rs`と`enter.rs`にだけ現れる)
- リポジトリに残す所: spec/native.mdの「エントリ」(N1)、native.mdの「extern のエントリ」と「extern の失敗」(T0)

#### D-5: `eml_enter`、`eml_fatal`、フレームレコード
- 決定: `eml_enter(ctx, thunk, entry, argv) -> u64` (0、または符号を32ビット左へずらしてsiteを足したもの) は、ABIごと (AAPCS64、SysV x86_64、Win64 x86_64) の`eml_nrt/src/arch/`のnakedのstubである。callee-savedのレジスタを自分のフレームの`JmpBuf`に保存し、`ctx.jmp`でつなぎ、標準のフレームレコードを作ってから、既定の呼び出し規約のthunkを呼ぶ。stubは`tail`のコードを直接呼ばない。`eml_fatal(ctx, code, site) -> !`は何も記録せずにlongjmpする。致命的な誤りの規則: longjmpが越えるのは、`tail`のフレーム、thunk、誤りを見つけた1つのエントリと`eml_fatal`のRustのフレーム (デストラクタを持つ値を持たない) だけである。入り直しの規則: emlのコードに入り直すRustのエントリは、`eml_enter`や`eml_fatal`をまたいで、`&Ctx`や`&mut Ctx`、workerの構造体への参照、`Drop`を持つ値を持たない。スタックを切り替えず、戻らない移動は致命的な誤りのlongjmpだけである
- 理由: Craneliftの`tail`の規約は引数のレジスタの割り当てが違い、すべてのレジスタを壊す。入れ子には、入るたびに1つのバッファが要る。フレームレコードの鎖は、将来のプロファイラがたどるものである
- 及ぶ範囲: `eml_nrt`、`eml_native`、emlのコードに入るすべての段
- 見直す条件: CIの対象が手で書いた`ret`を断るとき (shadow stackやbranch protection。付録02のA-2)。shimで捕まえたpanicがその上の巻き戻しの情報を要するとき (A-3)。どちらも利用者に戻す
- 適合の確かめ: N-11、N-12、N-33、N-35 (CIの4つの対象でのstubのテスト。callee-savedのレジスタのテストとフレームレコードのテストを含む)

### 5.2 短中期の設計

CIのチェックポイントの手順 (G1、G2、G3。付録02のD-12)。チェックポイントは指揮する側の手順で、実装者の作業ではなく、コミットを作らない:
1. 利用者にpushの許しを求めてから、次を流す。`<sha>`はチェックポイントのコミットの`git rev-parse HEAD`である
   ```
   git push -u origin plan/jit-rt
   gh workflow run CI --ref plan/jit-rt
   gh run list --workflow CI --branch plan/jit-rt --limit 5 --json databaseId,headSha,status --jq '.[] | select(.headSha == "<sha>") | .databaseId'
   ```
   最後のコマンドが何も出さなければ、数十秒おいて流し直す (直後は前の実行しか見えないことがある)。`--limit 1`で選ばず、必ず`headSha`で選ぶ
2. 実行は17〜18分かかり、前で待てる時間を超えるので、後ろで待つか、間をおいて状態を見る
   ```
   gh run view <databaseId> --json status,conclusion
   ```
   `status`が`completed`になるまでくり返す。通る条件: `conclusion`が`success`。(`gh run watch <databaseId> --exit-status`を後ろで流し、終わりの知らせを待ってもよい)
3. 赤のとき: `gh run view <databaseId> --log-failed`。失敗がこの段のコードにあるなら、新しいコミット (`Fix the <ABI> stub: <what>`) で直す。直しのコミットはそれぞれ1つの作業として、実装と査読を通す。手元の確かめを流し直してから手順1をくり返す。直しのコミットは残し、Closeのコミットのメッセージに挙げる
4. ある対象を緑にできないとき: 止めて、対象、テスト、ログを利用者に報告する。`fatal::`のテストだけが、終了コード`0xC0000409` (Windows) か、longjmpの側の`ret`でのSIGILLやSIGSEGVで落ちるなら、レジスタの一覧の誤りではなく、shadow stackかbranch protectionの方針を疑う (A-2)
