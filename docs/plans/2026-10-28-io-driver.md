## 1. 目的と完了の条件

- 目的: `Async` のタスクの下に、本物の完了型の I/O の driver と、ブロックする呼び出しのプールを入れる。後の `async-net`、`async-files`、`ffi-blocking`、`async-threads` が、設計を変えずにこの上に乗れるようにする。あわせて、Windows で `run (merge_stderr c)` を動かし、子のプロセスを起こす UI テストを Windows でも流す
- 完了の条件（確かめ方は9節）
  - `eml_rt::IoDriver` が D-1 の形になり、`eml_io` の本物の driver とテストの driver が、その trait を実装している
  - `Std.Async` に生の操作 `await_io` と `await_io_until` があり、`Std.IoTest` の書き、読み、期限付きの読み、プールの仕事が、UI テストで検査モード、速いモード、2つの seed のすべてで通る
  - 本物の driver の `eml_io` のテストが、macOS、Linux、Windows の CI で通る
  - Windows の CI で、`-- windows: skip` の印を外した13本の `Proc` の UI テストが通る
  - 段を閉じる作業（T-14）が終わり、この文書が消えている

## 2. 範囲

- 範囲に入るもの
  - `IoDriver` の trait の拡張、新しい crate `eml_io`（本物の driver、テストの driver、プール）、compio-driver の採用
  - `Std.Async` の生の操作 `await_io` と `await_io_until`、`Registry` の操作の記録、読めるようになってから読みの buffer を取る規則、`_within` の期限

  - `RunStats.completions`
  - `IoDriver` から `Send` を外し、`Machine`、`AnyMachine`、`Scheduler`、`Repl` を作ったスレッドの上でだけ使う型にすること（D-5）
  - Windows の `inherited_stdout` をなくすことと、`eml` 自身を子にする `Proc` の UI テスト（docs/future/roadmap.md の「その後の項目」の「Windows の子のプロセスのテストと `inherited_stdout`」）
- 範囲の外
  - 公開の `Std.Net`、シグナル、名前の解決（`async-net`）。Windows のソケット（`net-windows`）

  - 別のスレッドから worker を起こす本番の経路と、10 ms の上限をなくすこと（`worker-threads`）
  - 複数の worker（`async-threads`）。この段は、その設計を妨げないことだけを守る

## 3. 前提の事実

- 今の `IoDriver` は時間だけを扱う。`now(&self) -> Duration` と `wait_until(&mut self, deadline_ms: u64)` の2つで、`Send` だけを求める（`crates/eml_rt/src/driver.rs:9-15`）。`verus!` の外にあり、信頼の一覧に行はない（docs/spec/object-model.md:1234）
- 実装は `eml_vm` の `RealClock` と `VirtualClock` で、選び方が `Clock` である（`crates/eml_vm/src/driver.rs`）。`RealClock::wait_until` は1回に高々 `IDLE_TICK`（10 ms）眠る
- `wait_until` を呼ぶのは、`switch_away` の空きのループの1か所だけである（`crates/eml_vm/src/vm.rs:1227-1235`）。期限は時間の輪のいちばん早い期限で、時間の輪は `Registry` の `timers` にある。走れるタスクも期限もなければ `Deadlock` になる
- driver は `Machine` が持ち、run ごとに `Scheduler` に貸す（`crates/eml_vm/src/lib.rs:192,373-378,396`、`sched.rs:294`）。`Ctx` は持たない
- `Registry`（`crates/eml_vm/src/cells.rs`）は、slot の表、`timers: BTreeMap<TimerKey, CellRef>`、`inbox: Arc<Inbox>`、統計を持つ。待ちは `Wait::{Cell, Ready, Time}`（`cells.rs:163`）、走れる仕事は `Runnable::{Start, Resume, Token}` である。取り消しは `mark` が知らせを積み、`drain` が `unpark` で待ちを外して `Cancelled` で再開する。`sweep_all` は `main` の `Finish` でだけ走る
- 待ちはどれも同じ道を通る。`std/Async.em` のエフェクトの操作、`start_task` の handler の節、継続を保持する extern の行（`holding(&[false, true], ..)`）、`Op::Async` の命令（`vm.rs:1667` の `async_op`）、`Registry::park*` の順である。`Wake` は `Woke`（0）と `Cancelled`（1）
- `TaskHandle` は `Foreign` で、`Drop` は受け箱に積むだけである（`cells.rs:289-304`）。前の run のハンドルは、受け箱の `Arc::ptr_eq` で見分ける（`cells.rs:836-844`）
- 別のスレッドから眠る worker を起こす仕組みはない。`Control` は Relaxed の atomic だけを持つ。docs/spec/vm.md:420 は「今は取らない」と書いている。監視のスレッドは `Normal` の方針のときだけあり、横取りのビットを立てるだけである
- `Machine<Fast>`、`Machine<Checked>`、`AnyMachine` が `Send` であることを `crates/eml_vm/tests/api.rs:40-46`（`a_machine_moves`）が、`Scheduler<P>` が `Send` であることを同じファイルの32-34行（`a_scheduler_moves_and_a_sched_is_shared`）が、`Repl` が `Send` であることを `crates/eml_cli/tests/api.rs:351-355`（`a_repl_is_send`）が固定している。どれも、テストのファイルを丸ごと作ったコミット `439783d` で入り、コメントが引く docs/spec/vm.md の「追記」と docs/spec/modules.md の「REPL のセッション」には `Send` の規則がない。理由が書いてあるのは `Session: Send + Sync` だけで、実行とは関係ない（docs/implementation/architecture.md:367）
- 今のコードで `Machine` を別のスレッドへ移す所はない。`IoDriver` から `Send` を外すと、壊れるのは上の型の assert の7行だけで、ライブラリ、バイナリ、ほかのテストはそのままコンパイルできる（scratch のコピーで `cargo check --workspace --all-targets --keep-going` を流して確かめた）
- 将来の設計は、driver を worker のスレッドで作り、移さない（docs/spec/vm.md の「時計と driver」、docs/future/multicore.md:68-72 と :479、docs/future/async.md の確定した判断 #11）。compio-driver は `Proactor` が `Send` でないことを、feature によらず `assert_not_impl!` で固定している（`src/lib.rs:150`）
- `crates/eml_core_ir/tests/externs.rs:575-581` は、保持する引数がどれも `Unr` でないことを確かめる。`Bytes` は `Unr` である
- `Heap::share` は、届く局所の `Unr` の物体を、どちらのモードでも共有にする（`crates/eml_rt/src/heap/share.rs:2240-2247`）。共有にした物体では `is_unique` が成り立たない
- `cells::with_worker` は、RC に触れずに論理的な worker ID を切り替える（`cells.rs:1733`）
- `Heap::bytes(w)` は `Result<*const [u8], HeapError>` を返す。T10 の `bytes_ptr` の上の検証済みのコードである（`crates/eml_rt/src/heap/string.rs:780`）。`alloc_bytes_room` は失敗しない（`string.rs:522`）。`Control::charge` は確保量の上限を超えると `MEMORY` のビットを立てる（`crates/eml_rt/src/control.rs:169-177`）
- `IOErrorKind` は10種類すべてがある。extern が出すのは最初の5種類だけで、残りは `fail_io` だけが出す（docs/spec/stdlib.md:50-61,84）。docs/future/async.md:26 の「足す」は古い
- `inherited_stdout` は `crates/eml_rt/src/host.rs:1170-1182` にあり、unix では標準出力の fd を写し、ほかの OS では `Unsupported` を返す。そのため Windows の `run (merge_stderr c)` は起動の誤りになる（docs/spec/stdlib.md:700）
- `git grep -l '^-- windows: skip (' -- tests/ui` は14本を返す。13本が POSIX のツールを子にする `Proc` のテストで、残りが `tests/ui/run/scripts/deploy/main.em` である
- `RunStats` を丸ごと写すスナップショットは、`crates/eml_vm/tests/bench.rs` の44本だけである
- CI は `pull_request` と `workflow_dispatch` で走る（`.github/workflows/ci.yml:4-8`）。`test` の job は ubuntu-24.04、macos-15、windows-2025 の3つで、Miri の job は nix で `.#miri` を使う
- compio-driver 0.12.5 の事実（Linux で試作して確かめた）
  - compio の実行系なしで `Proactor` を作れる。スレッドごとに1つ持てる。`waker()` で別のスレッドから `poll` を起こせる。実行中の `Recv` の取り消しは `ECANCELED` で終わる。`Asyncify` の仕事は終わると `poll` を起こす
  - `Proactor` は `!Send` である。原因は、`Rc` に似た参照の数え方をする3つのグラフ（`ThinCell` の `Key`、`SharedFd`、後から作る buffer pool）だけである。スレッドに縛られた状態は、`FrozenKey` の drop のときの確認（`compio-send-wrapper` の `thread_local!`）だけで、通常の道では `into_inner` で消費されて動かない
  - polling の backend で `PollOnce(Readable)` は、データがなければ待ち続け、1バイト来ると `Ok(0)` で終わる。容量0の `Recv` の振る舞いは、カーネルによる
  - 空いた `Proactor` も、保留の操作を持つ `Proactor` も、別のスレッドへ移して ThreadSanitizer の報告なしに動いた（Linux）
  - Miri では polling の backend を動かせない。`timerfd_create` と `EPOLLONESHOT` を Miri の shim が扱えないためである
  - `features = ["polling", "sync"]` で依存は40個増え、きれいな debug ビルドに4コアで7秒かかる。`cargo tree -d` は Linux と windows-msvc のどちらでも空で、compio の `windows-sys` は 0.61.2（eml の固定と同じ）である
  - 上位の crate `compio` の最新の安定版 0.19.2 は、`compio-driver ^0.12.5` と `compio-buf ^0.8.3` に依存する。compio-driver の次の版は 0.13.0-beta.1 だけである
  - macOS と Windows では何も動かしていない（Windows の型の検査だけは `.#cross` で通した）

### 5.1 長期の方針（変えるときは設計を見直す）

実装でこれらと食い違うことが分かったら、止めて報告する。

#### D-1: `IoDriver` の trait の形と置き場

- 決めたこと: `crates/eml_rt/src/driver.rs` を次の形にする。`verus!` の外の安全なつなぎのコードのままで、`external_body` も信頼の一覧の行も持たない

  ```rust
  /// driver が振り、1つの driver の寿命の間は使い回さない。`submit` のたびに新しい値を返す。
  pub type OpKey = u64;
  /// driver が持つハンドル（この段では `pair` の両端）。1つの driver の寿命の間は使い回さない。
  pub type IoHandle = u64;

  /// カーネルが読み書きする記憶。driver を持つスレッドの外へは出さないので `Send` ではない。`cap == 0` は
  /// 記憶がないことを表し、`ptr` は空でない任意の番地で、読みも書きもしない。貸した側は、その操作の完了を
  /// `completions` から取り出すまで、物体を生かし、一意に保ち、動かさない。
  #[derive(Clone, Copy)]
  pub struct RawBuf { pub ptr: *mut u8, pub cap: usize }

  pub enum Op {
      /// `handle` の読みがブロックしなくなったら（データか EOF）`Ok(0)` で終わる。
      Readable { handle: IoHandle },
      /// `buf.ptr[0..cap]` に読む。`Ok(n)` で終わり、n == 0 は EOF。
      Read { handle: IoHandle, buf: RawBuf },
      /// `buf.ptr[0..cap]` を書く。`Ok(n)` で終わり、n は短いことがある。
      Write { handle: IoHandle, buf: RawBuf },
      /// ブロックする呼び出しのプールの仕事。自分が持つ値（写した入力）だけに触れ、結果を値で返す。ヒープにも RC にも触れない。
      Job(Box<dyn FnOnce() -> io::Result<usize> + Send + 'static>),
  }

  pub struct Completion { pub key: OpKey, pub result: io::Result<usize> }

  /// どのスレッドからも呼べる。シグナルの handler からは呼ばない。
  pub trait IoWaker: Send + Sync { fn wake(&self); }

  /// `Lin` の `Foreign` が落とされたハンドル。driver は次の `wait`、`completions`、`quiesce` と drop のときに閉じる。
  #[derive(Default)]
  pub struct HandleBin { pub dropped: Mutex<Vec<IoHandle>> }

  pub trait IoDriver {
      fn now(&self) -> Duration;
      /// `now() >= deadline_ms` か、完了が届くか、waker が鳴るまで待つ。早く戻ってよい。
      /// `Ok(false)` は外からの入力なしには何も進まないこと、`Err` は driver が壊れたことを表す。
      fn wait(&mut self, deadline_ms: Option<u64>) -> io::Result<bool>;
      /// 失敗しない。出せなかった操作は、次の `completions` で誤りとして終わる。
      fn submit(&mut self, op: Op) -> OpKey;
      /// できるだけ取り消す。`key` の完了はそれでも届く。`Op::Job` には何もしない。
      fn cancel(&mut self, key: OpKey);
      /// 届いた完了をすべて `out` に移す。順は driver が決める。
      fn completions(&mut self, out: &mut Vec<Completion>);
      /// 出してまだ `completions` で返していない操作の数。
      fn pending(&self) -> usize;
      fn waker(&self) -> Arc<dyn IoWaker>;
      fn bin(&self) -> Arc<HandleBin>;
      /// つながった2つの端。本物の driver は unix の `socketpair` で、Windows は `ErrorKind::Unsupported`。
      fn pair(&mut self) -> io::Result<(IoHandle, IoHandle)>;
      /// driver の参照を落とす。保留の操作は、終わるまで OS の資源を生かす。前提はない。
      fn close(&mut self, handle: IoHandle);
      /// 保留の操作をすべて取り消し、完了がすべて届くまで待って捨て、`bin` のハンドルを閉じる。仕事は待ちきる。
      fn quiesce(&mut self);
  }
  ```

- `IoDriver` は `Send` も `Sync` も求めない。driver は作ったスレッドの上でだけ使う（D-5）。`IoWaker` だけが `Send + Sync` で、スレッドをまたぐ口である
- 理由: 時間の輪と eml の語は `Registry` に残し、driver には語を見せない。`wait` の3つの結果で、VM が区別する「進みうる」「決して進まない」「壊れた」を表せる。鍵で引く完了の列は compio の `pop` にも、テストの driver の決着にもそのまま合う
- 退けた案: trait を `eml_io` に置く案は、docs/future/async.md の確定した判断 #10 と docs/future/multicore.md:64 に反する。`Send` を残す案は D-5 にある
- 及ぶ範囲: `eml_rt`、`eml_io`、`eml_vm`。後で `Ctx` が driver を持つ段で、`external_body` と信頼の一覧の行を足す
- 見直す条件: `eml_rt` の extern が driver を要するとき
- リポジトリに残す所: docs/spec/vm.md の「時計と driver」と docs/spec/object-model.md の `verus!` の外の一覧（T-5）。docs/future/async.md:239 の「`external_body` で T11」を「`Ctx` が driver を持つときに足す」に直す（T-6）

#### D-2: 操作の記録と token

- 決めたこと
  - `OpId`（`Std.Async.OpId`）は `Lin` の `Foreign`（`Repr::Obj`）で、Rust の値は `OpToken { op: CellRef, inbox: Arc<Inbox>, taken: bool }` である
  - 保留の表は `Registry` の slot の表の `CellKind::Op` である。driver は `Word` を見ない
  - 受け付けの extern は、保持の印のない普通の消費の行である。呼んだ側の参照を記録に移し、移した後で `is_unique` でなければ、同じ中身の新しい一意な `Bytes` を作って元を `decref` する。記録の buffer の語は、受け付けから取り出しまで、その物体へのただ1つの参照である
  - 記録の語は `Depot` で公開しない。記録は受け付けたタスクの論理的な worker ID（`worker`）を持ち、そのタスクの外で記録の語に触れるヒープの作業は `with_worker(record.worker)` の下で行う
  - 取り出し（`take_*`）は受け付けたタスクで行う。std の包みが守らせ、実行時にも `an op is taken by another task` で確かめる。`OpId` を返す行は `pub` にせず、包みは同じ呼び出しの中で token を消費するので、利用者のコードは token を持てず、`Chan` で送れない
- 理由: `Heap::share` は届く `Unr` の物体を共有にするので、`Depot` で公開すると `bytes_lend` の前提の一意さが崩れる。保持の印は型だけを変え、`Bytes` には付けられない（3節）
- 退けた案: driver が語を持つ形（層が崩れる）。`Depot` での公開（上の理由）
- 及ぶ範囲: `eml_vm` の `cells.rs`、`std/Async.em`、`std/IoTest.em`
- 見直す条件: `async-threads` と `async-rescue`。救済でタスクが worker を移るときは、記録の `worker` を書き換え、語の持ち主を所有ごと移す（`transfer_back` と同じ形）。`share` の印では移さない。docs/future/multicore.md:313-317 の「I/O の buffer: 所有ごと移す」と同じ方針である
- リポジトリに残す所: docs/spec/vm.md の「`Async` のタスク」と「セルと登録表」（T-9）

#### D-3: crate の構成とプールの置き場

- 決めたこと
  - 新しい crate `crates/eml_io` を作る。依存の順は `eml_cli > eml_vm > eml_io > eml_rt` で、`eml_io` は `eml_vm` に依存しない。後の `eml_sched` は `eml_vm` と `eml_io` の間に入る
  - `eml_rt` に置くのは trait と型と `bytes_lend`/`bytes_commit` である。`eml_io` に置くのは本物の driver（`real.rs`）、テストの driver（`test.rs`）、`IDLE_TICK` である。`eml_vm` には `Clock`、`floor_ms`/`ceil_ms`、操作の記録、`Wait::Io`、`OpToken`、`IoStream`、`async_op` の腕、`jobs.rs` を置く
  - プールのスレッドは `eml_io` の driver の一部で、`Op::Job` の後ろにある。仕事の記録は `Registry` に載る。`Op::Job` の closure を作るのは `crates/eml_vm/src/jobs.rs` だけで、このファイルは `std` と `eml_rt::Op` だけを import し、`unsafe` を持たない
- 理由: 1つの待ちの仕組みで I/O と仕事の両方を扱え、テストの driver は仕事をその場で決定的に動かせる
- 退けた案: プールを `eml_sched` に置く（まだない crate で、待ちの仕組みが2つになる）
- 見直す条件: `eml_sched` を作るとき

#### D-5: driver は作ったスレッドから動かない

- 決めたこと
  - `IoDriver` から `Send` を外す。`Box<dyn IoDriver>` を持つ `Scheduler<P>`、`Machine<M>`、`AnyMachine` と、`Machine` を持つ `Repl` は `Send` でなくなる。これらは作ったスレッドの上でだけ使う。`Session: Send + Sync`、`Sched: Send + Sync + Copy`、`Normal: Send`、`CodeBase<M>: Sync`、`Task: Send`、`Ctx: Send` はそのまま保つ
  - `eml_io/src/real.rs` は compio の `Proactor` をそのまま持つ。eml の側に `unsafe impl Send` も持ち主のスレッドの確認も書かない。スレッドから出さないことはコンパイラが守らせる

    ```rust
    pub struct RealDriver {
        proactor: Proactor,
        ops: HashMap<OpKey, Slot>,                          // compio の鍵はすべてここにある
        handles: HashMap<IoHandle, SharedFd<OwnedFd>>,
        bin: Arc<HandleBin>,
        epoch: Instant, next_key: u64, next_handle: u64,
    }
    enum Slot {
        #[cfg(unix)] Readable(Key<PollOnce<SharedFd<OwnedFd>>>),
        #[cfg(windows)] Readable(Key<Recv<RawBuf, SharedFd<OwnedSocket>>>),
        Read(Key<Recv<RawBuf, SharedFd<OwnedFd>>>),
        Write(Key<Send<RawBuf, SharedFd<OwnedFd>>>),
        Job(Key<Asyncify<Box<dyn FnOnce() -> BufResult<usize, ()> + Send>, ()>>),
    }
    ```

  - `Proactor::buffer_pool()` は呼ばない
  - `eml_io` の `unsafe` は、`RawBuf` の `IoBuf`/`IoBufMut`/`SetLen` の impl（`cap == 0` は空の slice）と、読みの後の `set_len` だけである。eml は I/O のために `unsafe impl Send` を1つも書かない。`RawBuf` も `Send` にせず、プールの仕事には入力を `Vec<u8>` に写して渡す（D-13）
  - Miri と ThreadSanitizer は `eml_io` に使わない
- 理由: `Machine` と `Repl` の `Send` には使い手も文書の根拠もない（3節）。将来の設計は driver を worker のスレッドに固定し、IOCP もハンドルを1つのポートに結び付ける。compio は `Proactor` が `Send` でないことを固定している。`Send` を外すと、`unsafe impl Send`、debug の確認、移しのテスト、ThreadSanitizer の CI の job がいらなくなり、型が性質を守る
- 退けた案
  - `Send` を残し、空のときだけ移す newtype に `unsafe impl Send` を付ける: 健全だが、使い道のない性質を eml 自身の推論で守ることになる
  - 専用の実行系のスレッドが状態を持ち、`Machine` と `Repl` を頼みを送るハンドルにする: 入力のたびにスレッドを渡り、GUI をメインスレッドの worker にする設計（docs/future/multicore.md:72-73）と逆向きになる
  - `thread_local!` の driver か run ごとの `Proactor`: 移った `Machine` が別の driver を使うか、IOCP がハンドルを1つのポートにしか結べないので、REPL の入力をまたぐハンドルが壊れる
  - 型の上で `Send` になる backend（unix の `polling` と手で書く IOCP）: `polling` の Windows は AFD で readiness を真似る。手で書く IOCP も `unsafe impl Send` を eml の側へ移すだけである。D-4 の代わりの案としてだけ残す
  - `Mutex`/`Arc` で包む: `Mutex<T>` が `Send` にも `Sync` にもなるには `T: Send` が要るので、成り立たない
  - 専用の I/O のスレッド: 操作ごとにスレッドを渡り、後の段も求めない
- 見直す条件: `Machine` か REPL のセッションを別のスレッドへ移す使い道（ホストの埋め込みなど）が出たとき。そのときは専用の実行系のスレッドの案を見直す。また、compio は `Decision::Blocking` と判定した操作（Linux のファイルの `ReadAt`/`WriteAt` など）を、`Send` を求めずに自分の `unsafe impl Send for FrozenKey` でプールのスレッドへ送る。`async-files` と `ffi-blocking` でその種の操作に `RawBuf` を渡すときは、コンパイラが捕まえないので、`RawBuf` の `Send`、T10 の別のスレッドから読む文、Miri のテストを見直す
- リポジトリに残す所: docs/spec/vm.md の「時計と driver」と394行のあたり、docs/implementation/architecture.md:367 のあたり（T-5）

#### D-6: 読めるようになってから読みの buffer を取る

- 決めたこと
  - 読みは1つの記録で2つの driver の操作を使う。`submit_read` は buffer をそのまま移し（容量0でよい）、`Op::Readable` を出す（`phase = Probe`）。`Probe` の完了で、VM が buffer の容量を `len + 64 KiB` にし、`bytes_lend` で貸して `Op::Read` を出す（`phase = Transfer`、新しい `OpKey`）。`Transfer` の完了で `bytes_commit(buf, n)` を行う
  - unix の `Readable` は compio の `PollOnce(fd, Interest::Readable)` である。IOCP の `Readable` は `RawBuf { cap: 0 }` の `Recv`（長さ0の `WSARecv`）で、`net-windows` まで実際には動かない。unix で容量0の `Recv` は使わない
  - `Readable` は EOF でも終わる。その後の `Read` が `Ok(0)` を返すことが、ただ1つの EOF の知らせである
  - `eml_rt` に、T10 の行に属する2つの関数を足す。T-4 では、信頼する `external_body` を `crates/eml_rt/src/heap/text.rs` の2つの小さな補助関数にし、公開の `Heap::bytes_lend`/`bytes_commit` はその上で Verus が検証した（`bytes` と `bytes_ptr` と同じ形）。Verus に `RawBuf` の欄を見せるため、`ExRawBuf`（`external_type_specification`）を T10 の信頼の項として足した。仕様の名前は eml_rt の今の名前に合わせた（`words_kept_except_text` は `pushed(old, w, w)`）

    ```rust
    /// `Bytes` だけ（`String` は除く）で、一意なもの。長さの後の空きを返す。ghost の状態は変えない。
    pub unsafe fn bytes_lend(&mut self, w: Word) -> (r: Result<RawBuf, HeapError>)
        requires old(self).wf(), old(self).is_bytes(w), old(self).owned(w)
        ensures *self == *old(self),
                r matches Ok(b) ==> b.cap == old(self).capacity(w) - old(self).text_of(w).len()
    /// 外から貸した空きに書かれた `n` バイトを確定する。ghost の中身は、今の記憶の値の `n` バイトだけ伸びる。
    pub unsafe fn bytes_commit(&mut self, w: Word, n: usize) -> (r: Result<(), HeapError>)
        requires old(self).wf(), old(self).is_bytes(w), old(self).owned(w),
                 n <= old(self).capacity(w) - old(self).text_of(w).len()
        ensures self.wf(),
                r is Ok ==> (exists|s: Seq<u8>| s.len() == n && self.text_of(w) == old(self).text_of(w) + s)
                    && self.capacity(w) == old(self).capacity(w)
                    && self.words_kept_except_text(*old(self), w)
    ```

    `bytes_commit` は長さの語だけを書く。`Bytes` には UTF-8 の不変条件がないので、中身を決めない事後条件でよい。事後条件の形（存在量化か、ghost の `Seq` を返すか）は T-4 で選ぶ
  - 書きの `RawBuf` は、`Heap::bytes(w)` の返す位置から作り、driver を持つスレッドの上でカーネルが読むだけである。新しい関数も Verus の行も足さず、T10 の行に次の内容の1文を置く: `bytes` が返す位置を、driver を持つスレッドの上で I/O の driver に読ませてよいのは、`bytes_lend` と同じく、完了を取り出すまで物体を生かし、一意に保ち、書き換えない間だけである。別のスレッドからは読ませない
  - プールの仕事は `RawBuf` を受けない。仕事の入力は `Vec<u8>` に写して渡す（D-13）
- 理由: T10 は、`String` と `Bytes` のペイロードの語を書くのは T10 の関数だけだと約束している。カーネルに物体へ直接書かせるには、この2つの関数が要る。何も来ない接続は読みの buffer を持たない（docs/future/async.md の確定した判断 #12）
- 退けた案: 受け付けで容量を足す（確定した規則に反する）。`Vec` を通して写す（読みのたびに2回写す。下の代わりの案としてだけ使う）
- 代わりの案: T-4 の `bytes_lend`/`bytes_commit` が2回の作業で Verus を通らなければ、driver は `Probe` の完了で 64 KiB の `Vec<u8>` を自分で確保して読み、VM は `Transfer` の完了で既存の `bytes_extend` で写す。trait は同じで、`RawBuf` が `Vec` を指す。そのときは「カーネルが物体に直接書く」を docs/future/roadmap.md の「その後の項目」に移し、見直す条件を「`bytes_lend` と `bytes_commit` が Verus を通ったとき」とする
- 見直す条件: 上の代わりの案を採ったとき
- リポジトリに残す所: docs/spec/object-model.md の T10 の行（T-4）、docs/spec/vm.md の「`Async` のタスク」の読みの規則（T-10）

#### D-7: run の外に保留の操作を残さない

- 決めたこと
  - `run_scheduled` の外では、driver は保留の操作を持たない。`quiesce` を、`main` の `finish`（`sweep_all` の前）、`run_scheduled` の `vm::run` の直後（どの道でも）、`Machine::recover` の `ctx.recover()` の前の3か所で呼ぶ
  - `quiesce` は、走っている仕事が終わるまで上限なしに待つ。仕事を取り消せず、完了の前に記録とヒープを放すと、届いた完了を当てる記録がなくなるためである。この段の仕事は std の内部のものだけで、長さに上限がある。2回目の Ctrl-C は今と同じく `_exit(130)` で終わる。`eml run` は `process::exit` で終わるので、CLI は待たずに終わってよい。予算と、放さずに終わる方針は `ffi-blocking` で決める
  - driver の `wait` が `Err` を返したら、run は `is_broken` の誤り `VmFault::Driver`（表示は `the I/O driver failed: {e}`）で終わる。`quiesce` の後も `pending() > 0` なら `Machine` を毒された状態にする。`ctx` を `ManuallyDrop<Ctx<M>>` にし、`impl Drop for Machine` は毒されていないときだけ `ctx` を落とす。毒された `Machine` の `close`、`recover`、後の run は、ヒープに触れずに `VmFault::Driver("the driver kept pending ops after quiesce")` を返す
  - 本物の driver では、`poll` の `Ok`、`Err(TimedOut)`、`Err(Interrupted)` は「戻った」と読む。ほかの誤りは driver を壊れた状態にし、以後の `wait` は `Err` を返し、`completions` は新しいものを返さない。保留の操作の buffer は貸したまま残す
  - 落としたハンドルは、`HandleBin` に積まれ、次の `wait`、`completions`、`quiesce` と driver の drop で閉じる。REPL の入力の間に落としたハンドルは、次の run が始まるか `Machine` を落とすまで開いたままである
- 理由: カーネルやプールのスレッドが書いている記憶を、回復や `close` が放したり写したりしない
- 見直す条件: `ffi-blocking`（利用者の `blocking` の行が来るとき）
- リポジトリに残す所: docs/spec/vm.md の「時計と driver」と「終わり」（T-8）、docs/spec/object-model.md の「回復」の前提（T-8）

#### D-8: この段では別のスレッドから起こさない

- 決めたこと: 本物の driver の `wait` は、今と同じく1回に高々 `IDLE_TICK`（10 ms）眠り、空きのループが毎回止める語を読む。waker は作って3つの OS でテストするが、本番のコードからは呼ばない。シグナルの handler からも、監視のスレッドからも呼ばない。プールの仕事の完了は driver の完了のポートで届く
- 理由: kqueue の notify（`kevent(EVFILT_USER)`）と compio の起こしの道は、async-signal-safe と書かれていない。10 ms の上限で、`an_interrupt_wakes_a_sleeping_worker` はそのまま通る
- 見直す条件: `worker-threads`。docs/future/async.md:241 と docs/future/multicore.md:465 の「どの待ちも起こしで戻る」は、そこで満たす
- リポジトリに残す所: docs/spec/vm.md の「時計と driver」の「今は取らない」の文を、この食い違いと解く段の名前に置き換える（T-5）。docs/future/roadmap.md の「その後の項目」（T-14）

#### D-9: 取り消し、期限、データの区別は記録の状態で決める

- 決めたこと
  - 誤りの種類では区別しない
  - `cancelling` の記録: タスクは `Cancelled` で再開し、包みは結果によらず `Cancelled` を投げる。読みならデータを確定して buffer を返し、包みが落とす
  - `timed_out` で `cancelling` でない記録: `Err(_)` は `TimedOut`（`None` とストリーム）で、本物の誤りが期限と競ったときも同じである。`Ok(n)` はデータである。ストリームの誤り（EOF、reset、broken pipe）は残るので、次の操作が報告する
  - どちらでもない記録: `Err(e)` は IO の失敗である
  - 仕事は取り消せないので、`TimedOut` にならない。短い書きは `Ok(n)`（`n < len`）で、`take_write` が `n` を返す
- 理由: 誤りの種類は OS と backend で違い、記録の状態は VM が決めている
- 見直す条件: `async-net` で書きの期限（`write_within`）を足すとき
- リポジトリに残す所: docs/spec/stdlib.md の「`Std.IoTest`」と docs/spec/vm.md の「取り消しの届け方」（T-9、T-11）

### 5.2 短中期の設計（理由があれば実装で調整してよい。調整したらコミットのメッセージに残す）

#### D-10: テストの driver

- `eml_io::TestDriver::new(seed: Option<u64>)`。`Clock::Virtual` で選び、`Sched::Seeded(n)` のときだけ `Some(n)` である
- 時計は0から始まり、`wait(Some(d))` で、決着の後に終わる操作がないときだけ `d` ちょうどに進む。終わる操作がなければ `wait(None)` は `Ok(false)` を返す。`Err` は返さない
- ストリーム: `pair()` は `VecDeque<u8>` と `closed` の旗を持つ2つの端である。`close(h)` の後、相手は残りを読みきってから EOF を受ける
- 決着は `completions` と `wait` の始めで、次の順に行う。まず bin を空にしてハンドルを閉じる。次に受け付けの順に操作を決着させる。seed があれば、その決着で終わった操作の組を混ぜる
  - `Write`: 相手が開いていれば全部を写して `Ok(len)`。閉じているかいなければ `Err(io::Error::from(ErrorKind::BrokenPipe))`
  - `Readable`: 相手の buffer が空でないか、相手が閉じていれば `Ok(0)`
  - `Read`: 同じ条件で `min(cap, available)` を写し、EOF では `Ok(0)`
  - `Job`: その場で動かす
  - まだ終わっていない操作を `cancel` すると、次の決着で `io::Error::new(ErrorKind::Other, "cancelled")` で終わる。すでに終わってまだ返していない操作は、`cancel` しても終わったときの結果のまま返す。返した後の鍵の `cancel` は何もしない
- waker は旗だけである。`quiesce` はすべてを取り消しとして終わらせて捨てる
- 完了は集めの時点でだけ届くので、UI の出力はプログラム、方針、seed で決まる。読めるデータがある読みは、どの期限よりも先に終わる

#### D-13: `eml_vm` の操作の記録

- `cells.rs` の import は `std` と `eml_rt` のままにする（`eml_rt::{IoDriver, Op, RawBuf, Completion, OpKey, IoHandle, HandleBin}` が増える。`RawBuf` は書きと読みにだけ使う）
- 記録 `CellKind::Op(OpRecord)` は、同じ slot と世代の表に入る（`OpRef` = `CellRef`）。欄は `key: OpKey`、`kind: Read | Write | Job`、`phase: Probe | Transfer | Done(io::Result<usize>)`、`worker: u32`、`buf`/`stream`/`token: Option<Word>`（`token` は待つ間だけ持つ）、`waiter: Option<CellRef>`、`timer: Option<TimerKey>`、`cancelling: bool`、`timed_out: bool` である。持ち主のない記録（`ownerless`）は作らない
- `Registry` に `ops: HashMap<OpKey, CellRef>`、使い回す `completed: Vec<Completion>`、`stats.completions` を足す
- `Foreign` は2つで、どちらも `lin = true` である
  - `OpToken { op, inbox: Arc<Inbox>, taken: bool }`。`!taken` の `Drop` は `Notice::OpDropped(op)` を積む。前の run の token は `an op token outlived its run`
  - `IoStream { handle: IoHandle, peer: Option<IoHandle>, bin: Arc<HandleBin> }`。`Drop` は `handle` と、あれば `peer` を `bin.dropped` に積む
- `Wait::Io(CellRef)` を足す。`k.is_some()` は `wait` が `Cell`、`Time`、`Io` のどれかであることと同値である。`timers` の項 `key → task` は、`wait == Time(key)` か、`wait == Io(op)` かつ `op.timer == Some(key)` のときだけある
- 関数の約束
  - `submit_write`/`submit_read`（`ctx, driver, worker, buf, stream`）→ token の語: buffer を一意にし（D-2）、`IoStream.handle` を読み、書きは内容の `RawBuf` で `Op::Write`（`Transfer`）、読みは `Op::Readable`（`Probe`）を出し、記録と `ops` の項を入れ、token を作る
  - `submit_job`（`ctx, driver, worker, buf, make: impl FnOnce(Vec<u8>) -> Op`）: buffer の中身を `Vec<u8>` に写して `make` に渡し、`kind = Job`、`phase = Transfer` とする。記録の buffer は一意でなくてよい。`submit_checksum` の行が `Bytes` を借りる形にするかは実装者が決める（借りるなら D-12 の行の表を直す）
  - `park_io`（`ctx, driver, token, me, k`）→ `Option<Runnable>`: token から記録を引く（`waiter` があれば `an op is awaited twice`）。`suspend(me)`、`parks += 1`。取り消しの地点（`point(me)`）なら `cancels += 1` とし、`Done` なら `ResumeIo{me, k, CANCELLED, token}` を返し、そうでなければ `driver.cancel(key)`、`cancelling = true` として待つ。地点でなく `Done` なら `ResumeIo{me, k, WOKE, token}` を返す。待つときは `task.k = Some(k)`、`task.wait = Some(Io(op))`、`record.waiter = Some(me)`、`record.token = Some(token)` とする
  - `park_io_until`（`.., now_ms, ms, ..`）: `park_io` と同じで、実際に待ち、`cancelling` でないときに、`ms <= 0` なら `driver.cancel(key)`、`timed_out = true` とし、そうでなければ `TimerKey{now_ms.saturating_add(ms), seq}` → `me` を入れて `record.timer` に覚え、`stats.timers += 1` とする。VM は `ms > 0` のときだけ `ceil_ms(driver.now())` を読む
  - `complete`（`ctx, driver, depth_offset, out`）。`collect` から呼び、`ops` が空なら何もしない。`driver.completions(&mut completed)` を呼び、driver の順に、`stats.completions += 1`、`ops.remove(key)`（なければ `a completion names no op`）を行う
    - `Probe` の完了: `cancelling || timed_out` なら `Done(Err(cancelled))`、`Err(e)` なら `Done(Err(e))`。`Ok(_)` なら、`with_worker(ctx, record.worker, depth_offset, ..)` の下で容量を足す。容量 − 長さが 65 536 未満なら `alloc_bytes_room(len + 65_536)` で新しい物体を作り、長さが正なら `bytes_extend` で中身を写し、記録を新しい語にして古い語を `decref` する。その後 `bytes_lend` で貸し、`record.key = driver.submit(Op::Read{..})` として `ops` に入れ直し、`Transfer` にする
    - この段の `HeapError`（`bytes_extend`、`decref`、`bytes_lend`）は、検査モードの前提の違反で、`CellFault::Heap`（壊れた run）にする。`submit` の前には何も貸さないので、誤りで貸したままの記憶は残らない。確保量の上限は誤りにせず、`MEMORY` のビットで次の `poll` に止まり、最後の `quiesce` が読みを取り消す
    - `Transfer` の読みの `Ok(n)`: `with_worker` の下で `bytes_commit(buf, n)`。`HeapError` は `CellFault::Heap`
    - ほかの完了: `Done(result)`
    - `Done` になったら、`record.timer` を `timers` から外す。待つタスクがあれば `task.wait = None` とし、`task.k` と `record.token` を取り、`Runnable::ResumeIo{cell, k, wake: if cancelling {CANCELLED} else {WOKE}, op: token}` を積む
  - `expire`（`driver` を受ける）: `wait == Io(op)` で `op.timer == Some(key)` の項は、`timer = None`、`timed_out = true`、`driver.cancel(op.key)` とし、再開しない。ほかの食い違いは今と同じ `a timer names no waiting task`
  - `unpark`（`driver` を受ける）: `wait == Io(op)`、地点で、`cancelling` でなければ、`driver.cancel(op.key)`、`cancelling = true`、期限があれば外し、`cancels += 1`。再開は `complete` で行う
  - `drain`（`driver` を受ける）: 生きた記録の `Notice::OpDropped(op)` は `CellFault::Internal("an op token was dropped before its take")` にする。std の包みは受け付けから `park_io` まで投げうる呼び出しなしに token を移し、待つ間は `record.token` が持ち、`take` は投げる前に `taken` を立てるので、std からは届かない。放した記録への古い知らせは、今の `let_go` と同じく無視する
  - `open_stream`（`ctx, a, Some(b), bin`）は最初の `IoStream` を作る。`peer`（`ctx, stream`）は `IoStream.peer` を取り（`None` なら `a stream pair is split twice`）、2つ目を作る
  - `op_stream`（`ctx, token`）: `Done` で `stream` があることを求め、ストリームの語を移し出す。`op_timed_out`（`ctx, token`）: `Done` を求め、`timed_out && result.is_err()` を返す
  - `take`（`ctx, token, worker`）→ `Taken { result, buf, cancelling, timed_out }`: `Done`（`an op is taken before its completion`）と `worker == record.worker` を求め、`taken = true`、token の `decref`、残ったストリームの語の `decref`、slot の解放を行う
  - `sweep_all`: 前提は `driver.pending() == 0`。1回目に `CellKind::Op` を回り、`buf`/`stream`/`token` のある語を `Depot::of(record.worker).discard(ctx, w, depth_offset)` で捨てて解放する。`Depot::close` は呼ばない（ID はタスクのセルか main のもので、`free_task` が退かせる）。2回目は今のタスク、スコープ、channel の回りで、最後に `ops.clear()`。操作の記録は `RunStats` に数えない
- `TaskStats` に `completions` を足す。`parks` の説明に `park_io*` を、`timers` の説明に `ms > 0` の `park_io_until` を足す
- `vm.rs`
  - `async_op` の腕: `AsyncParkIo`/`AsyncParkIoUntil` は `cells.park_io*` と `schedule` で、`dst` は `UNIT`。`IoTestOpenPair` は `driver.pair()` が `Ok((a, b))` なら `cells.open_stream`、`Err(e)` なら `raise_again(.., Raise::Io{kind: io_kind(&e), message})`。`IoTestPeer`/`IoTestOpStream` は `dst` に書き、借りた引数は slot に残す。`IoTestOpTimedOut` は `set_raw(dst, b as i64)`。`IoTestSubmit*` は `cells.submit_*(ctx, driver, task.worker, ..)` で、checksum は `|b| jobs::checksum(b, delay)`。`IoTestTakeRead` は、`Err` で中断（`cancelling || timed_out`）でなければ buffer を `decref` して投げ、そうでなければ buffer を返す。`IoTestTakeWrite`/`IoTestTakeChecksum` はまず buffer を `decref` し、`Ok(n)` なら `n`、中断でない `Err` なら投げ、中断なら 0 を返す
  - `schedule`: `Runnable::ResumeIo{cell, k, wake, op}` → `(entries.resume_io, [k, wake, op], 3, cell)`。`TaskState::Entry.args` と `enter` は `[Word; 3]` を受ける
  - `collect` の順: `cells.drain(ctx, driver, ..)` → `cells.complete(ctx, driver, ..)` → 期限があれば `cells.expire(floor_ms(driver.now()), driver, ..)` → すべてを `schedule`
  - `finish`（main）: `drain` → `sched.driver.quiesce()` → `sweep_all` → 今の確認
- `jobs.rs`: `pub(crate) fn checksum(input: Vec<u8>, delay: Duration) -> Op`。中身は `Op::Job(Box::new(move || { thread::sleep(delay); Ok(input.iter().map(|&b| usize::from(b)).sum()) }))` で、`unsafe` を持たない

#### D-14: `RunStats.completions`

- `collect` が driver から取り出し、記録に当てた `Completion` の数で、検査モードだけで数える。最後の欄に足し、docs/spec/vm.md の欄の数は22から23になる

- `crates/eml_vm/tests/bench.rs` の44本のスナップショットに `completions: 0,` が増える

#### D-15: driver の作り方と差し込み

- `Machine` は `clock: Clock` の欄を持ち、driver を最初の run で作る。`driver: Option<..>` は `run_entry` が `clock` と `sched.seed()` から作るまで `None` である。`with_clock`/`with_sched` は欄を変えて `driver` を `None` に戻す。run の後に呼ぶと、次の run で driver を作り直し、仮想の時計は0から始まる（driver は run の外では空なので許される）
- `Clock::driver(self, seed: Option<u64>) -> io::Result<Box<dyn IoDriver>>` と `Sched::seed(self) -> Option<u64>` を足す。作れなければ、その run は `VmFault::Driver` で終わり、ヒープに触れない
- `driver` を `Machine` の最初の欄にする（`code` と `ctx` より先に落ちる）
- `pub fn with_driver(self, driver: Box<dyn IoDriver>) -> Machine<M>` を足す（docs/future/async.md:240 の差し込みの口）。後の `with_clock`/`with_sched` はこれを上書きする
- driver は run を行うスレッドの上で作り、`Machine` はそのスレッドの上でだけ使う。`with_driver` に渡す driver も同じスレッドで作る。複数の worker の段では、`Session::run` は driver そのものではなく、`Copy + Send` の `Clock` と seed を渡し、各 worker が自分のスレッドで作る
- 理由: `RealDriver::new` は失敗しうる。seed は `with_sched` から来るので、先に作ると builder の順に依る。走らない `Machine` と Miri のテストは `Proactor` を作らない

#### D-16: 仕事の遅れは本物の時計でだけ効く

- VM は、`Machine` の時計が `Clock::Real` のときだけ `delay = ms.clamp(0, 1000)` ms を渡し、`Clock::Virtual` では0を渡す。`Start` が `real_clock: bool` を `Scheduler` へ運ぶ
- テストの driver は仕事を次の決着でその場で動かすので、仕事の間に仮想の時間は進まない。UI テストは本物の時間を眠らない

#### D-17: `inherited_stdout` をなくす

- `StdHost::spawn`（`crates/eml_rt/src/host.rs`）の `(Stdio::Inherit, StderrMode::ToStdout)` の腕を `.stdout(process::Stdio::inherit()).stderr(io::stdout())` にし、`inherited_stdout` の2つの関数を消す。std の `impl From<io::Stdout> for process::Stdio`（1.74 から）は、unix では fd 1 を写し、Windows では標準出力のハンドルを受け継げる形で写す。`cfg`、`unsafe`、windows-sys の feature は要らない
- `(stdout, StderrMode::Inherit)` の腕の `.stderr(process::Stdio::inherit())` は変えない
- 結果: どの OS でも `run (merge_stderr c)` は子の標準エラーを eml の標準出力の行き先へ送り、Windows の起動の誤りはなくなる。eml に標準出力のハンドルがない Windows では、std が標準出力と一緒に捨てる（`2>&1` の意味どおり）
- 退けた案: `cfg(windows)` でハンドルを写す（std がすでに移植できる形で行う）

#### D-18: テストの Host の子の環境と、自分を子にするテスト

#### D-19: Windows のテストの扱い

## 付録: レビューで変わったこと

設計の見直しを繰り返さないために、レビューと確かめで変えた点だけを書く。

- unix で読めるようになるまで待つ操作を、容量0の `Recv` から `PollOnce` に変えた。容量0の `recv` はカーネルによって振る舞いが違い、macOS で確かめていないためである
- 最初の計画は、`Proactor` を空のときだけ移す newtype に `unsafe impl Send` を付けていた（Fable のアドバイザが健全と確かめた）。利用者の求めで `Machine` と `Repl` の `Send` を見直し、別の Fable のアドバイザが、`Send` の assert に使い手も根拠もないことを確かめたので、`IoDriver` から `Send` を外した（D-5）。ThreadSanitizer の job（元の T-7）も消した
- 受け付けの行に保持の印を付ける案と、記録の語を `Depot` で公開する案は、どちらも既存のテストと `Heap::share` の振る舞いに反するので退けた（D-2）
- trait を `eml_io` に置く案は、確定した判断 #10 に反するので退けた（D-1）
- `quiesce` に上限を付ける案は、仕事を取り消せず、完了の前に記録を放せないので退け、方針を `ffi-blocking` に回した（D-7）
- `RawBuf` の `Send` は、別の Opus のアドバイザが比べ、プールの仕事にだけ入力を写す形にして消した。compio はソケットの操作に `Send` を求めない。すべての操作を `Vec` で写す案は、64 KiB の転送で写しの費用が +25〜61% と目に見え、確定した判断（所有ごと渡す buffer）を覆すので退けた（D-5、D-6、D-13）
- 持ち主のない記録（`ownerless`）は std から届かないので作らず、内部の誤りにした（D-13）
- 期限が `Probe` と `Transfer` のどちらに当たるかで `completions` が seed に依るという指摘は、テストの driver の決着の規則で起きないので退けた（D-14）
- compio の版: 上位の `compio` の最新の安定版 0.19.2 が使う部品の版が 0.12.5 と 0.8.3 で、計画の固定と同じである（D-4）
- `inherited_stdout` を Windows に移さず消した。std がどの OS でも標準出力を子の標準エラーに渡せるためである（D-17）
