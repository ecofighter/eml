## 5. 決定

### 5.1 長期の方針 (変えるには見直しが要る)

実装がこの節と食い違ったら、止めて報告する。全文は付録の`01-contract.md` (1.1〜1.7節と、8節の基準) と`00-decisions.md`にある。

#### D-1: crate、依存の辺、置き場所
- 決定: crateと辺は`01-contract.md`の1.1節のとおりにする。ネイティブの実行系のコードは`eml_nrt`に、エンジンによらない共有のコードは`eml_sched`に、コード生成器とJITのホストは`eml_native`に置く。`eml_nrt`は、プログラムについての事実を`Image` (`#[repr(C)]`) からだけ得る。`eml_native`は`eml_sched`への辺を持たない。実行の境界の型 (`RunConfig`、`Finished`、`RuntimeError`、`RunFault`、`HostRef`。R-9) と、`eml_sched::rows`の行の関数と`LISTED` (C-3) は、`eml_nrt`が再エクスポートする。`eml_native`のテストもそれを通して使い、dev-dependencyの例外は作らない。`eml_native`の中で`eml_rt`を名指すのは`mem.rs`だけで、`jit.rs`は`eml_nrt`の再エクスポートを使う (C-9)。`eml_nrt`と`eml_native`はthread-localを使わない
- 理由: native-aotで`libeml_rt.a`を`eml_nrt`から作れるように、`eml_nrt`にはCraneliftもLIRも入れない。VMはネイティブのコードと混ぜない
- 及ぶ範囲: `eml_native`、`eml_nrt`、`eml_sched`、`eml_cli`、`eml_test_support`
- 見直す条件: 後の段が新しい辺を要るとき
- 適合の確かめ: N-1、N-2 (CIの辺の段)、N-5、N-14、N-31。`grep -rlnw 'eml_rt' crates/eml_native/src | sort` → `crates/eml_native/src/mem.rs`。`grep -rn 'eml_sched' crates/eml_native/src crates/eml_native/Cargo.toml` → 出力なし。`grep -rnE 'eml_rt::(Ctx|Heap)|Ctx<' crates/eml_native/src` → 出力なし。`grep -rn 'thread_local' crates/eml_nrt/src crates/eml_native/src` → 出力なし
- リポジトリに残す所: `docs/implementation/architecture.md`の「`eml_native` の内部」と、`eml_nrt`の内部の節 (K23)

#### D-2: エントリのABIと、接頭辞ごとの失敗の約束
- 決定: 出すコードがモジュールの外で呼ぶ関数は、すべて`entries!`で宣言する (Cの既定の呼び出し規約、最初の引数は`ctx`、ほかの引数は機械の型で`i64`か`f64`、結果は`i64`か`f64`の高々1つ。Rustのシグネチャでは、物体の語 (`obj`、`tobj`、`token`) は`Word`で、対象のどのABIでも`i64`と同じ渡し方である。語のprovenanceを保つためで、エントリは整数からポインタを作らない)。`eml_rt_*`のエントリは、失敗すればfatalで終わるだけで、出すコードは呼んだ後に何も確かめない。`eml_x_<Variant>` (externの行ごとに1つ。識別子は一覧に書き下す。R-1) は、`faults`のある行なら`RunFault::Extern(f)`を`ctx.set_fault(f)`で預けて仮の値を返し、出すコードはその直後に`ctx.native.fault`を確かめる。中身をエンジンが持つ失敗は、中身をworkerの構造体に置き、`set_fault(Fault::Engine)`で預ける。ほかの`Err`と捕まえたpanicは内部の類で、誤りを記録してから、shimのfatalの道で終わる (U-8)。wrapperの本体は`eml_fatal`を名指さない。`never`の行は結果なしで普通に戻り、出すコードはその後で無条件に分岐する (R-3)。`eml_nrt_*`のサービスは、行動の語を返す。失敗の道がfatalしかないものは、データの語を返す (R-8)。fatalの番号は、1 `FATAL_PANICKED`、2 `FATAL_FAULT` (jit-rt)、3 `FATAL_RECORDED` (この段) で、すべて`crates/eml_nrt/src/enter.rs`で定める (R-2、C-5)。fatalの規則: fatalのlongjmpが越えるのは、`tail`のフレーム、thunk、誤りを見つけた1つのエントリのデストラクタを持たないRustのフレームだけである。だから誤りは、`Err`がshimに届く前にworkerの構造体へ移す。入り直しの規則: emlのコードに入るRustのコードは、`enter`をまたいで`&Ctx`や`&mut Ctx`を持たない。`catch_unwind`はすべてのエントリに残す (`01-contract.md`の6.2節のU4)
- 理由: 出すコードが確かめることを接頭辞ごとに固定すれば、熱い道の費用はどれも1つに決まり、判断はすべて共有の手続きに入る
- 及ぶ範囲: `eml_nrt`のすべてのエントリと、`eml_native`のすべての呼び出しの所
- 見直す条件: 3つのどれでも足りない約束がエントリに要るとき (契約の変更なので、利用者に戻す)
- 適合の確かめ: N-7、N-8、N-9、N-10、N-12。CLIFの固定`a_faulting_row`、`a_row_that_does_not_fault`、`a_never_row`、`a_call_and_its_unwind_check`。`grep -rn 'eml_fatal(' crates/eml_nrt/src | grep -v -e src/entries.rs -e src/enter.rs` → 出力なし。`grep -c 'eml_fatal' crates/eml_nrt/src/rows.rs` → `0`。実行の駆動が、終わりに預けたままのfaultを報告する
- リポジトリに残す所: `docs/spec/native.md`の「エントリ」(jit-rt) と「externの失敗」(K7、K10、K13)

#### D-3: 出すコードの形
- 決定: emlの関数はすべて`tail`の規約で、`(ctx, 葉..) -> 葉..`の形にする。末尾呼び出しは`return_call`か`return_call_indirect`である。決まった関数、アダプタ、補助の関数の直接の呼び出しは、`Linkage::Local`で宣言した関数への`call`か`return_call`で、Craneliftはそれをcolocatedにする。`call_indirect`は、呼ぶ先が実行時の値のときだけ使う。emlのコードはすべて`abi::isa`のフラグでコンパイルする。外の参照はモジュールのシンボルかデータで、プロセスのアドレスを即値にしない。`JITModule`を名指すのは`jit.rs`と`bridge.rs`だけである。関数のコードは、その関数のLIRと、それが参照する名前だけで決まる。プログラムのほかの部分や読み込みの順で変わる数 (関数の番号、プログラム全体の地点の番号、表の添字) をコードに埋め込まない (R-6)。読み込み時のデータは、名前ごとのデータのシンボルにする (C-6)。関数、アダプタ、補助の関数は、どれも変わらないシンボルの名前を持つ。アドレスから名前への写しは`NativeMachine::symbols()`と`Image.functions[i].{code, size}`が与える
- 理由: 後の段のreuseの鍵とAOTの形は「同じLIRなら同じコード」に頼る。プロファイラはフレームポインタと変わらない名前を要る
- 及ぶ範囲: `crates/eml_native/src/lower/`の下のすべてと`jit.rs`
- 見直す条件: native-aotが別のリンクの種類を要るとき
- 適合の確かめ: N-13、N-16、N-34、N-36、N-37。7の毎回流すgrep (`Linkage::Import`、`CallConv::Tail`、`JITModule`、`preserve_frame_pointers`、`settings::builder`、`call_indirect`)。`machine::symbols_cover_every_function`。固定`a_call_and_its_unwind_check`で呼ぶ先が`colocated`と出ること。`rows::the_same_function_has_the_same_code_in_two_programs`と`data::a_function_with_constants_has_the_same_code_in_two_programs`
- リポジトリに残す所: `docs/spec/native.md`の「関数の形」(K11、K14) と「値と定数」(K17)

#### D-4: メモリには1つのモジュールを通して触る
- 決定: `eml_native`が物体のメモリと`Ctx`に触るのは`src/mem.rs`を通してだけである。`mem.rs`が出すのは、builderを受け取る関数と、`eml_rt`のconstと`const fn`から求めた定数だけである。ほかのファイルは`ins().load`や`store`を書かず (`thunk.rs`と`bridge.rs`は除く)、配置の数も書かない。出すコードが読む`Native`の欄はどれも、ずれが120以下で、`CTX_*`の定数を通して読み、その場で定めない。ネイティブのコードが作るのは`Ctx<Fast>`だけである
- 理由: 配置の事実は`eml_rt`に1つの定義を持つ。外に置いた写しは、同じであることを証明できない
- 及ぶ範囲: `eml_native`
- 見直す条件: native-inlineが割り当ての事実を足すとき
- 適合の確かめ: N-4、N-6、N-15。`grep -rnE 'ins\(\)\.(load|store|uload|sload)' crates/eml_native/src | grep -v -e src/mem.rs -e src/thunk.rs -e src/bridge.rs` → 出力なし。`grep -rnE 'CTX_[A-Z_]+\s*(:|=)' crates/eml_native/src crates/eml_nrt/src` → 出力なし。`grep -rnw 'Checked' crates/eml_nrt/src crates/eml_native/src` → 出力なし

#### D-5: 効果と割り込みのうち、この段が敷くもの
- 決定: 出すコードには熱い確かめを置き、地点ごとに持ち物の数に比例する大きさの冷たいブロックを置き、判断はすべて共有の手続きに入れる (`01-contract.md`の1.4節)。この段は、受け入れる関数すべてに次を出す。末尾でない呼び出しの後ごとの巻き戻しの確かめ (`yielding.target`)。`eml_lir::unwind::points`から作る後始末のブロック。モジュールに1つの`tail`の関数`eml$raise(ctx, function, site, purity)`とサービス`eml_nrt_failed(ctx, function, site, purity)`を通るfaultの道。冷たい側が`eml_nrt_safepoint`の1回の呼び出しである入口の安全点。`function`は呼んだ関数のコードのアドレス、`site`はその関数の中の地点の番号である (C-2)。後の段が広げるのは「巻き戻しの地点の後」の下ろしの関数だけである。`exit`は`Ctx::exit_abort()`で中断を始め、`panic`はメッセージの語をworkerの構造体に預ける
- 理由: 後の段 (jit-externs、jit-effects、jit-tasks) は、`eml$raise`、サービス、「巻き戻しの地点の後」の関数の本体を変えるだけで振る舞いを足し、熱いコードは変えない
- 及ぶ範囲: `lower/unwind.rs`、`lower/safepoint.rs`、`eml_nrt/src/services.rs`
- 見直す条件: `01-contract.md`の1.4節が固定する項目を後の段が変える必要があるとき (利用者に戻す)
- 適合の確かめ: N-17、N-18、N-19。固定`the_entry_safepoint`と`a_call_and_its_unwind_check`。`abort::exit_unwinds_two_frames_holding_owned_values_and_a_token`
- リポジトリに残す所: `docs/spec/native.md`の「巻き戻しの地点」と「安全点」(K6、K7、K13〜K15)

#### D-6: スタックの形
- 決定: workerのスタックの最も低いアドレスを`base`として、`hard = base + STACK_HARD_MARGIN` (1 MiB)、`real = hard + LIMIT_HEADROOM_BYTES` (2 MiB) とする。3つの定数`WORKER_STACK` (1 GiB)、`STACK_HARD_MARGIN`、`LIMIT_HEADROOM_BYTES`は`crates/eml_nrt/src/run.rs`で1回だけ定める (R-11)。この段は、スレッドの始めに`stack_limit = real`を1回だけ置き (`eml_nrt`の中の`set_stack_limit`の呼び出しはこれだけ)、後で変えない。`hard`を使うのはjit-tasksからである (U-9)。ネイティブでは`Limits.max_depth`を読まず、深さの上限はworkerのスタックである。深く再帰するテストは、64 MiBのworkerのスタックを明示して流す (R-16)
- 理由: jit-tasksが上限の類を足しても、プログラムが届く深さを変えないため。`real`の下の3 MiBで、emlのフレーム1つと実行系のエントリのどれでもが収まる
- 及ぶ範囲: `eml_nrt/src/run.rs`と安全点
- 見直す条件: 利用者が`--stack-size`を求めるとき (10を見る)
- 適合の確かめ: N-42。`grep -rn 'set_stack_limit(' crates/eml_nrt/src | wc -l` → `1`。`run::the_stack_limit_is_three_mebibytes_above_the_base`
- リポジトリに残す所: `docs/spec/native.md`の「安全点」(K6)

#### D-7: 断ること、VMとの違い、ネイティブのUIテスト
- 決定: 何を断るかは`eml_native::unsupported(&Program)`だけが述べる。`Session::compile_native`はそれをE0004にする (違う形ごとに1つ、決まった順)。断る形に出会った下ろしはpanicする。ネイティブの実行とVMの速いモードの実行の、外から見える違いは、`docs/spec/native.md`の「VMとの違い」に挙げたものだけである。(1) 語の数による深さの上限はなく、上限はスレッドのスタックである。(3) `--debug-heap`、`--stats`、`Seeded`の方針はネイティブにはない。(2) はjit-tasksが足す。`--native`に1以外の`--workers`、1以外の`EML_WORKERS` (C-7)、`--gui`、`EML_GUI` (C-11) を合わせるのは、jit-tasksまで使い方の誤りで、そのメッセージは段を名指さない (R-7、C-10)。テスト`ui::run_native`と`ui::run_fail_native`は、受け入れた各ファイルを同じプロセスの中でVMの速いモードと比べる。`run-fail`のファイルは、先にcheckedのVMで流す。ファイルは、同じになるか、断られるか、「VMとの違い」の項目を理由に名指す`-- native: skip (<理由>)`を持つかのどれかである。テストのネイティブの実行は、どれもcensusで終わる。受け入れたのに同じにできないファイルは、原因が下ろしの誤りでなければ、計画を改めて印を付ける (種類1)。そういうファイルが10を超えたら利用者に戻す
- 理由: ネイティブが断るものは1か所で決める。censusは、checkedモードに代わるRCの安全網である
- 及ぶ範囲: `eml_native/src/unsupported.rs`、`eml_cli`、UIテストの仕掛け
- 見直す条件: ほかの違いが要る段は、利用者に見える意味の項目として、その段の計画に足す

#### D-8: ネイティブの性能を先にし、それをきれいな設計で得る

## 8. 実行の順

K0 → K1 → ... → K15 → CP-1 → K16 → ... → K19 → CP-2 → K20 → (下ろしの直し) → K21 → K22 → CP-3 → K23 → CP-4の順に1つずつ行う。どの作業も、前の作業のコードだけを使う。K3は`is_broken`で`RunFault`を名指すのでK1の後に置く。分類を最初から確かめるために、K4とK5を下ろしより先に置く。K6〜K10で実行系の側を作ってから、K11でコード生成器を始める。CP-1 (JITのホスト、faultの道、呼び出し、安全点、スタックの形) とCP-2 (データとインラインの行) で、macOSのほかの3つの対象での振る舞いを早く確かめる。チェックポイントはorchestratorの手順で、コミットを作らず、直しはそれぞれ別の作業になる。macOSが要るのは、K0の基準の値、K3のゲート、K22の`bench/native.sh`、K23の計測で、ほかの作業はどのOSでもできる。

## 付録: 査読と照合で大きく変わった所

- 設計 (r4) は、出すコードからプログラム全体で決まる数をすべて除いた。定数は名前ごとのデータのシンボル、faultの地点は (関数自身のコードのアドレス、関数の中の番号) の組、安全点は関数自身のアドレスを渡す。`Image`はプログラム全体の地点の表もデータの表も持たない
- `extern_rows!`の行はエントリの識別子を書き下し、種類の字句はそのまま`entries!`に渡し、インラインの行は一覧を入れる作業 (この計画のK9、付録03のK9) から`inline fn`の行にする (C-1)
- fatalの番号3 `FATAL_RECORDED`を、jit-rtの1と2の隣の`enter.rs`に足す (C-5)。`impl Raise for HeapError`はjit-rtのものを使う
- `never`の行は結果なしで普通に戻る
- `eml run --native`と、1以外の`--workers`、`--gui`、1以外の`EML_WORKERS`の組み合わせは、jit-tasksまで使い方の誤りにする (R-7、C-7)。初めの設計は`EML_WORKERS`を黙って無視していた
- eml_nativeは、実行の境界の型と共有の行の関数を`eml_nrt`の再エクスポートを通して名指し、`eml_rt`を名指すのは`mem.rs`だけにする (R-9、C-3、C-9)
- スタックの形の定数は`run.rs`だけで定め、深いスタックのテストは64 MiBのスタックを明示して流す (R-11、R-16)
- インラインの`dup`と`decref`の差分のテストは、共有と張り付きの類も扱う (C-8)
- `LISTED`は組ではなく、付録04の構造体`Listed`を使う (C-4)。欄は付録04のとおり`row`である
- 利用者に見えるCLIのメッセージは段を名指さない (C-10)。`EML_GUI`も`--gui`と同じく、jit-tasksまで使い方の誤りにする (C-11)
- Fableの助言 (r1) を受けて: 自分への末尾呼び出しのテストを、算術を下ろせるK19へ移した。jit-applyで消える形を、K4とK20のテストの題材から外した。G-rtで、コミット、きれいな木でのゲート、メッセージだけのamendの順を決めた。CIのチェックポイントをorchestratorの手順にし、K15とK19の後にも置き、走りを`headSha`で選ぶようにした。Craneliftの未確認の振る舞いは、jit-rtのG2で先に確かめる。K9をcrateの境で分け、`Engine`の配線を独立させた (番号を付け直した)。K21の前の下ろしの直しを別のコミットにし、5秒の基準を足した。`bench/native.sh`が出力を比べ、呼び出しの多い行を含めるようにした
