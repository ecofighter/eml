## 1. 目的と成功の基準

- 目的
  - `String` を、`Char` と UTF-8 の小さい核の上の API にする。
  - std を広げる。`Map`、`Set`、安定な並べ替え、List の関数、`Char` と `Byte` の変換、書けるファイルを入れる。
  - std のモジュールを、`import` したモジュールからだけ見えるようにする。
  - ファイルのハンドルを、型ごとのモジュール (`FileIn`、`FileOut`) にそろえる。
  - スクリプトを、バイトの数でなく文字のリテラルと std の関数で書き直す。
- 成功の基準 (確かめ方は 9 章)
  - 全体の検証のコマンドがすべて通る。
  - roadmap のこの段の「決めたこと」がすべて実装され、「論点」がすべて決まるか、「その後の項目」に理由と条件を付けて移っている。
  - `tests/ui/run/scripts/` の5本の出力が変わらない。

## 3. 背景

- std は 19 のモジュールで、`eml_hir::STD` に埋め込む (`crates/eml_hir/src/lib.rs:26-45`、docs/spec/modules.md:62)。
- 今の名前解決では、`import` していない std のモジュールも短い修飾子で引ける (docs/spec/modules.md:96)。
  - 修飾子は構文木から拾い、そのモジュールを読み込む (`crates/eml_hir/src/load.rs:279-292` `load_qualified_std`、modules.md:63-68)。
  - 修飾子の解決の最後の分岐は `crates/eml_hir/src/def_map.rs:1565-1569` にある。
- import なしで std を修飾して使うファイルの数
  - `tests/ui`: 246
  - `bench/`: 17
  - REPL のトランスクリプト: 16
  - std の中はもとから import を書いている。
- `Std.String` の extern は `byte_length`、`byte_at`、`slice`、`find_from` (非公開)、`valid_utf8`、`decode` の6つである (`std/String.em:5-14`)。
  - `byte_at` は `Int` を返す。
  - `String` と `Char` をつなぐのは `show` と `display` だけである。
- `Std.Char` の extern は `to_int` と `of_int` だけで、ASCII の判定は eml で書いてある (`std/Char.em`)。
- 専用の VM 命令を持つ行は `StrByteAt`、`StrByteLength`、`BytesGet`、`BytesLength` の4つだけで、ほかは汎用の `Op::Extern` で動く (`crates/eml_vm/src/op.rs:332-350`、docs/spec/vm.md:227-230)。
- `eml_rt` の `encode_char` と `char_display` は Verus で UTF-8 の符号化を証明してある (`crates/eml_rt/src/heap/ctx/strings.rs:648`、`:1376`)。vstd には `decode_first_scalar`、`is_char_boundary`、`valid_utf8_split` などの仕様と補題がある。
- 妥当でない UTF-8 の扱い
  - `decode` は `Panic` (``invalid UTF-8 at byte N``) になる。
  - `Fs`、`Stdin`、`Env` の文字列の読みは IO の失敗 `NotUtf8` になる。
- `Fs.open` は読むためだけに開く。書く道はファイル全体を書く `Fs.write_text` (extern) だけである。
  - `Host` に開いて書くメソッドはない (`crates/eml_rt/src/host.rs`)。
  - `Stdout` と `Stderr` のハンドルは Host の `BufWriter` に書き、自分の buffer を持たない。
- `Stdout` と `Stderr` の書く関数の名前は `write : Bytes`、`write_string : String`、`write_line : String` である (`std/Stdout.em`)。
- `List` の公開の関数は8つ (`reverse`、`append`、`length`、`map`、`filter`、`filter_map`、`fold`、`each`) である。
- スクリプトは std にない関数を自分で持っている。
  - `logstat`: AA 木の `upsert`、`sort_by`、`split_at`、`take`
  - `csv2jsonl`: `index_of`、`nth`、`zip`
  - `deploy`: 連想リストを引く `command_of`
- `csv2jsonl` と `wc` はバイトを `10`、`13`、`34`、`44`、`32` などの数で比べている。
- `crates/eml_vm/tests/bench.rs` は、bench の `RunStats` と、スクリプトの巻き戻しの地点の数 (wc 46、grep 61、logstat 102、csv2jsonl 109、deploy 109) を固定している。
- macOS のファイルシステムは大文字と小文字を区別しない。UI テストの根は分類のディレクトリなので、`tests/ui/run/std/map.em` から `import Map` を書くと、隣の `map.em` が当たって E1026 になる。
  - 同じ理由で、`bench/list.em` がある `bench/` (`bench/run.sh` と `bench/scripts.sh` の根) では、`import List` が E1026 になる。
  - `bench.rs` は本文を `MemorySource(&[])` で読むので、この衝突は起きない。

## 5. 決めたこと

### 5.1 長く効く方針 (変えるときは設計からやり直す)

実装の途中でこれらとぶつかったら、止めて報告する。

#### D-1: std のモジュールは import したモジュールからだけ見える

- 決定
  - Prelude のほかの std のモジュール `X` は、次のどれかを書いたモジュールからだけ、修飾子として使える: `import X`、`import Std.X`、`import Std.X as A`、`import X (…)`。暗黙の短い修飾子 (modules.md:96 の手順3) はなくす。
  - REPL も同じ規則にする。式、`let`、`:type` の入力は import を書けないので、利用者は先に `import X` を入力する。入力の import は後の入力から見える (今の規則のまま)。
  - 読み込みは import だけをたどる。構文木から修飾子を拾う処理と、`eml_syntax::Parse::paths` を消す。
  - Prelude に置くものを3つに限る。
    1. 構文が名前を引かずに指す item (lang item) と、それが要る型、クラス、instance
    2. リテラルを持つ型の宣言と、その `Eq`、`Ord`、`Show` の instance
    3. どのプログラムでも要る入出力と制御 (今の Prelude の `pub` の関数)
  - 型 `T` を扱う関数の集まりは `Std.T` に置く。lang item の脱糖が呼ぶ補助の関数は `pub` にしない。`LangItems` は `pub` によらずに引き、`pub` でない Prelude の item は利用者から見えない。
  - 変えないもの: `import Fs` はユーザーの根の `Fs.em` を優先し、`import Std.Fs` はいつも std を指す。import の並び、別名、合流の規則もそのままである。
- 理由
  - 修飾子の指す先が import だけで決まる。今は同じ `Fs.open` が、`import Fs` を書いたモジュールではユーザーの `Fs` を、書かないモジュールでは std を指す。
  - 読み込みの段が構文木の形に依存しなくなり、インクリメンタル化と LSP の import の操作に乗る。
  - REPL の特例 (modules.md:148、165) が消える。
  - Haskell に寄せる (CLAUDE.md)。
- 退けた案
  - 今のまま: 上の理由の裏返しである。
  - 小さな集合だけ暗黙にする: std が2種類になり、拾い出しも残る。
  - REPL だけ暗黙にする: 式の入力は受け付けても持たない (modules.md:149) ので、セッションの状態を変える特例が要る。`:load` のファイルとも規則がずれる。
  - リテラルが std のモジュールを暗黙に読み込む: 拾い出しを戻すことになる。
- 及ぶ範囲: すべてのプログラム、REPL、E1031 の診断。次の段の `Cmd` を Prelude に置く根拠でもある。
- 見直す条件: パッケージを入れるとき。そのとき import の解決の順 (ユーザーの根、パッケージ、std) を決める。
- リポジトリに残す所: docs/spec/modules.md の「Prelude」「標準ライブラリ」「名前の解決」「REPL のセッション」。T-2 で書く。

#### D-2: `String` の位置はバイト位置の `Int`、UTF-8 の extern は7行

- 決定
  - `String` は常に妥当な UTF-8 である (roadmap で決まっている)。位置はバイト位置の `Int` のままにし、不透明な型は作らない。境界でない位置は、`char_at` と `slice` が `Panic` で捕まえる。
  - `Std.String` の extern を次の7行にする。

    | 名前 | 型 | Purity | 借用 | 核の操作 |
    |---|---|---|---|---|
    | `byte_length` | `String -> Int` | Pure | `s` 借 | バイト長 (今のまま) |
    | `char_at` | `Int -> String -> <Panic> Char` | Panics | `s` 借 | 位置から `Char` を読む (新規) |
    | `slice` | `Int -> Int -> String -> <Panic> String` | Panics | `s` 借 | 境界を検査する切り出し (今のまま) |
    | `push` | `Char -> String -> String` | Pure | なし (`s` を消費) | エンコード (新規)。`s` が一意ならその場で伸ばす |
    | `decode` | `Bytes -> <Panic> String` | Panics | なし (消費) | 検証付きのデコード (今のまま) |
    | `byte_at` | `Int -> String -> <Panic> Byte` | Panics | `s` 借 | 核の外。結果を `Int` から `Byte` に変える |
    | `find_from` | `String -> Int -> String -> <Panic> Int` | Panics | 両方借 | 核の外。`pub` でない (今のまま) |

  - `valid_utf8` の行は消す。`from_utf8` は `try_panic` で `decode` を包む。
  - `char_at` が返すのは `Char` だけである。次の位置は eml で `i + Char.utf8_length c` と計算する。extern は組を作れないので (stdlib.md の「extern の境界」)、この形にする。
  - `char_at` の文言は2つある。
    - 範囲の外: `byte_at` と同じ ``string index 5 is out of range for length 3``
    - 境界でない: ``string index 1 is not on a character boundary``
  - `char_at` の証明は vstd の補題で閉じる。信頼の一覧 (T0-T13) は増やさない。
- 理由
  - roadmap の「小さい核」の5つ (検証付きのデコード、エンコード、バイト長、位置から `Char` と次の位置を読む操作、境界を検査する切り出し) に、1対1で対応する。
  - `byte_at` を残す理由
    - ネイティブ化の要件 (roadmap の「ネイティブ化」) が、借りた `String` のバイトの読みの展開を名指しで求めている。
    - `String` のバイトを借りて読む道は、これしかない (`Bytes.of_string` は消費する)。
  - `find_from` は T13 の SWAR の検索を使う行である。
- 退けた案
  - 不透明な位置の型: 防げるのは `Int` との取り違えだけである。std とスクリプトはすべて `Int` の算術で位置を組んでいる。
  - `byte_at` を消して `Bytes` に寄せる: 借りて読めなくなる。
  - `next` を extern にする: 呼び出しが1回増える。
  - `Char` と幅を1つの `Int` に詰めて返す: 要らない。
  - `valid_utf8` を残す: `from_utf8` が2回確かめる形のままになる。
- 及ぶ範囲: すべての文字列の処理、ネイティブ化の要件、`eml_rt` の検証。
- 見直す条件
  - 位置の取り違えの誤りが実際のプログラムで繰り返し出たとき
  - 共有の部分文字列 (view) を入れるとき
- リポジトリに残す所: stdlib.md の「`String`」「`Bytes` との変換」「extern の境界」「実行時エラー」、object-model.md の「extern」の表と「文字列の操作」。T-6、T-7、T-8 で書く。

#### D-3: ASCII の区切りの走査は `byte_at`、コードポイントが要る所は `char_at`

- 決定
  - 区切りがすべて ASCII の走査は、`byte_at` と `'x'u8` のリテラルで書く。コードポイントが要る所だけ `char_at` で読む。
  - `char_at` のネイティブの展開の約束を、roadmap の「ネイティブ化」の要件に足す。
    - 長さの読み、符号なしの比較1つ、`Panic` への冷たい分岐、バイトの読みまでは `byte_at` と同じである。
    - 読んだバイト `b` が `b < 0x80` なら、結果は `b` である。
    - そうでなければ冷たいブロックへ分岐し、続きのバイトなら `Panic`、先頭のバイトなら残りを読んで組み立てる。
- 理由: ネイティブ化で `wc` と `csv2jsonl` を Rust の約2倍以内にする目標 (roadmap の「ネイティブ化」) が、バイトの読みの展開に頼っている。
- 退けた案: スクリプトの走査をすべて `char_at` にする。バイトの読みの展開から外れる。
- 見直す条件: 段を閉じるとき、`bench/scripts.sh` の `wc` の行の eml の時間が benchmarks.md の今の値の 1.3 倍を超えたとき。そのときは `wc` をバイトの走査に戻す (T-17)。
- リポジトリに残す所: stdlib.md の「`String`」に走査の方針を1段落で書く (T-8)。roadmap の「ネイティブ化」の要件に `char_at` の約束を足す (T-17)。

#### D-4: 名前の規則と、ハンドルの型ごとのモジュール

- 決定
  - std 全体で、文字列を読み書きする関数が短い名前を持つ。バイト列の版は `_bytes` を足す。
    - 読み: `read_all`/`read_all_bytes`、`read_line`/`read_line_bytes`
    - 書き: `write`/`write_bytes`、`write_line` (文字列だけ)
    - バイト列にしかない読み (`read_chunk`) は、その名前のままである。
  - ハンドルの型ごとに1つのモジュールを置く: `Stdin`、`Stdout`、`Stderr`、`FileIn`、`FileOut`。
    - どれも `open` か `create`、`close`、規則どおりの読みか書きを持つ。
    - `FileIn` の読みは `Stdin` の読みと同じ名前と形にする。`FileOut` の書きは `Stdout` の書きと同じ名前と形にする。
  - `Fs` には、パスで1回に済む関数 (`read_text`、`write_text`) を置く。roadmap が `Fs`、`Path` に予定するパスの操作も後でここに足す。`Fs` は extern を持たない。
  - `Stdout` と `Stderr` を改名する: `write : Bytes` → `write_bytes`、`write_string` → `write`。
- 理由
  - スクリプトの大半は文字列を読む。
  - 文字列の読みが UTF-8 を確かめることが、「`String` は常に妥当な UTF-8」を支えている。
  - 型ごとに分けると、読みと書きの取り違えが型の誤りになる。`Stdout` と `Stderr` を分けた方針と同じである。
- 退けた案
  - 短い名前を `Bytes` に渡す: 文字列を読む多くのテストと effects.md の記述が動き、文字列の読みが既定でなくなる。
  - `Fs.File` 1つにモードを持たせる: 取り違えが実行時の失敗になる。
  - `Fs` に `FileIn` と `FileOut` を置く: `close_in` と `close_out` がほかのハンドルの `close` とそろわない。
  - 読みを `Fs` に残し、`FileOut` だけを別にする: 読む側だけが `Fs` に残る形になる。D-1 で同じファイルの import を書き換えるので、改名の費用は小さい。
- 及ぶ範囲: すべての入出力の API と、次の段の `Child` の読み書き。
- 見直す条件: なし。新しいハンドルの型もこの規則に従う。
- リポジトリに残す所: stdlib.md の「ハンドル」に規則を1段落で書く (T-10)。

#### D-5: 妥当でない UTF-8 と Unicode の表

- 決定
  - 今の扱いを変えない (`decode` は `Panic`、文字列の読みは `NotUtf8`、`from_utf8` は `Option`)。
  - 置換 (U+FFFD) の版は入れない。
  - Unicode の表が要る操作 (ASCII でない大文字と小文字の変換、`is_alphabetic`、`is_whitespace`) は、extern にしない。
  - `Char.from_int : Int -> Option Char` と `Char.is_scalar` は足さない。
- 理由: 使う所がない。UTF-8 でないファイルは `Bytes` の読みで受けられる。
- 見直す条件と、リポジトリに残す所: D-19 の項目として roadmap の「その後の項目」に書く (T-17)。

#### D-6: `FileOut` の buffer と、失敗の後の約束

- 決定
  - `FileOut` は自分の書き込みの buffer (64 KiB、`StdHost` の `BUFFER_BYTES` を共有する) を持つ。書き出すのは3つの場合だけで、`fsync` はしない。
    - buffer があふれたとき
    - `flush` を呼んだとき
    - `close` を呼んだとき
  - VM の書き出しの地点 (`main` の終わり、実行時エラーの前など) は、`FileOut` の buffer に触れない。
  - 暗黙に手放すときは、drop glue (`BufWriter` の drop) が buffer を書き、誤りを捨てる。手で書いた `Drop` は置かない。手放す場面は次のとおりである。
    - 巻き戻し
    - `exit`
    - 捕まえなかった実行時エラーの回復
    - `Heap` の `Drop`
    - REPL
    - Rust の panic
  - 失うのは、2回目の Ctrl-C (`_exit(130)`) と abort のときだけである。
  - `write`、`write_bytes`、`write_line`、`flush`、`close` が IO の失敗を返したときの約束は4つある。
    1. ハンドルは閉じている。
    2. ファイルには、そのハンドルに渡したバイトの先頭の部分 (prefix) が残る。どこまで書けたかは約束しない。
    3. 書いていない残りの buffer は捨て、それ以上書かない。
    4. 誤りは「この呼び出しか、同じハンドルのそれより前の書き込み」の失敗を表す。
  - 書けない誤りは `Io { op: Write }` (``cannot write `p`: …``) にし、`try_io` で捕まえる。
  - `close` は eml で `close h = close_raw (flush h)` と書く。
- 理由
  - roadmap の「決めたこと」(57 行) のとおりである。
  - 誤りがハンドルの書き込みの順で決まるので、捕まえられる。標準出力は共有の buffer なので、捕まえない。
  - 失敗の後に書かないので、誤りを返した後にファイルが伸びない。
  - `close` を eml で書けば、`handle_close` の証明に新しい枝が要らない。
- 退けた案
  - 失敗の後も drop に残りを書かせる: 誤りの後にファイルが伸びる。
  - `close` を extern にして中で書き出す: 検証したコードに枝が増える。
  - `close` の誤りを捨てる: ふつうの流れでも誤りを失う。
- 見直す条件: 多くのファイルを同時に開くスクリプトで、buffer の量が問題になったとき (D-19)。
- リポジトリに残す所: stdlib.md の「`FileOut`」、object-model.md の「出力のバッファ」「誤りのときの約束」。T-9、T-10 で書く。

#### D-10: `Char` と `Byte`

| 名前 | 型 | 実装 |
|---|---|---|
| `Char.of_byte` | `Byte -> Char` | extern、Pure。Latin-1 (0 から 255 はどれもスカラー値)。VM は `Move` に写す |
| `Char.to_byte` | `Char -> <Panic> Byte` | eml。`if c <= '\u{ff}' then Byte.wrap (to_int c) else panic "char \{show c} does not fit in `Byte`"` |
| `Char.utf8_length` | `Char -> Int` | eml。`if c < '\u{80}' then 1 else if c < '\u{800}' then 2 else if c < '\u{10000}' then 3 else 4` |
| `Char.to_ascii_upper` | `Char -> Char` | eml、Pure。`if is_ascii_lower c then of_byte (Byte.wrap (to_int c ^^^ 32)) else c` |
| `Char.to_ascii_lower` | `Char -> Char` | eml、Pure。同じ形 (`is_ascii_upper`) |

- `of_byte` は UTF-8 のバイトをデコードしない。stdlib.md の「`Std.Char`」に次の注意を書く。
  - 文字列のバイトを渡すと、先頭のバイトや続きのバイトは、別の Latin-1 の文字になる。
  - 文字列から文字を読む関数は `String.char_at` である。
- `Byte` のリテラルに `'x'u8` の形を足す。値はコードポイントである。
  - 0xFF を超えれば E0007 (``byte literal `'あ'u8` is too large``、ラベル ``the largest `Byte` is 255``)。
  - 今は `'"'u8` が `CHAR` と識別子 `u8` に分かれる (E1001 になる)。変えるのは字句だけで、文法、AST、HIR は `BYTE` のトークンをすでに式とパターンで受ける。
  - 接頭辞 `b'x'` は識別子と衝突するので採らない。

#### D-13: `Std.Map` は釣り合いの印をコンストラクタに持つ AVL 木

- 表現 (付録 `Map.em`)

  ```haskell
  pub data Map k v =
    | Empty
    | LeftHigh (Map k v) k v (Map k v)
    | Even (Map k v) k v (Map k v)
    | RightHigh (Map k v) k v (Map k v)
  ```

  - 挿入と削除は、部分木の高さが増えたか減ったかを `Bool` で返す。
  - 回す関数 (`grow_left`、`grow_right`、`shrink_left`、`shrink_right`) は組み直す節を受け取り、同じ関数の中で節を作る。
  - 高さを数で持たないので、算術がなく、`Panic` もない。
- 公開する関数

  | 関数 | 型 |
  |---|---|
  | `empty` | `Map k v` |
  | `insert` | `Ord k => k -> v -> Map k v -> Map k v` |
  | `upsert` | `Ord k => k -> (Option v -> <e> v) -> Map k v -> <e> Map k v` |
  | `delete` | `Ord k => k -> Map k v -> Map k v` |
  | `lookup` | `Ord k => k -> Map k v -> Option v` |
  | `member` | `Ord k => k -> Map k v -> Bool` |
  | `size` | `Map k v -> <Panic> Int` (O(n)) |
  | `fold` | `(b -> k -> v -> <e> b) -> b -> Map k v -> <e> b` (キーの昇順) |
  | `to_list` | `Map k v -> List (k, v)` (キーの昇順) |
  | `from_list` | `Ord k => List (k, v) -> Map k v` (同じキーは後の組が勝つ) |

- 意味
  - `upsert key f m` は、`key` があれば値を `f (Some v)` に、なければ `f None` を入れる。`f` はちょうど1回呼び、キーは前からあるものを残す。
  - `insert` は `upsert key (fn _ -> value)` と同じである。
  - `delete` は、キーがなければ同じ木を返す。
- 値もキーも `Unr` に限る。`Lin` の値は E3001 になる (回す関数の `_ -> t` の枝のため)。
- `size` のほかは型に `Panic` を持たない。トップレベルの値 (row は `<>` に限る) と `Show` の instance の本体でも使える。
- コンストラクタは公開される。抽象型がまだない (roadmap の「抽象型」) ためである。
  - spec には関数の表だけを API とすることと、利用者が作った木では結果を決めないこと (どの関数も全域で、実行時エラーは出さない) を書く。
  - `import Map (Map(..))` で `Empty` が利用者のコンストラクタと重なりうる。spec の例は `Map.empty` と関数だけを使う。
  - roadmap の「抽象型」の項目に、`Map` と `Set` がコンストラクタを公開していることを1行足す。
- 測った根拠 (release、5回の中央値、HEAD 2319493b)

  | 入力 | 採る形 | 赤黒木 (色をコンストラクタに持つ) | 高さの欄の AVL | OCaml の AVL | Adams の木 | AA 木 |
  |---|---|---|---|---|---|---|
  | 文字列のキー 2000 種に 30 万回の `upsert` | 0.21 s | 0.26 s | 0.49 s | 0.37 s | 0.36 s | 0.32 s |
  | 昇順の Int のキー 30 万 (引くのを含む) | 0.37 s | 0.53 s | 0.69 s | 0.64 s | 0.62 s | 0.55 s |
  | 乱数の Int のキー 30 万 | 0.26 s | 0.35 s | 0.57 s | 0.49 s | 0.45 s | 0.38 s |
  | 5 万個に 100 万回の `lookup` | 0.43 s | 0.45 s | 0.45 s | 0.45 s | 0.45 s | 0.44 s |

  - 確保の数 (検査モード、昇順の 2 万): 採る形が 40012、赤黒木が 99955、高さの AVL が 327230、OCaml の AVL が 347213、Adams の木が 416480。
  - 高さか大きさを `match` か `if` の値として読む釣り合いの関数は、合流のブロックを作る。token は合流へ流れない (lir.md の「token の流れ」) ので、reuse されない。
  - 成分を受ける `bal l k v r` の形 (OCaml の AVL、Adams の木) は、reuse が 0 である。
- 退けた案
  - 赤黒木: 確保が約2倍で、更新が 25 から 45% 遅い。
  - 高さの欄の AVL、OCaml の AVL、Adams の木、AA 木: 合流か成分の受け渡しで reuse を失う。高さ、大きさ、段の算術で `Panic` も出る。
  - `Map.alter`、`keys`、`values`、`singleton`: 今は要る所がない。

#### D-14: `Std.Set` は `Map` と同じ形の AVL 木

- 表現 (付録 `Set.em`): `| Empty | LeftHigh (Set a) a (Set a) | Even (Set a) a (Set a) | RightHigh (Set a) a (Set a)`。`std/Set.em` は `import List` を書き、`Map` は import しない。
- 公開する関数

  | 関数 | 型 | 計算量 |
  |---|---|---|
  | `empty` | `Set a` | |
  | `insert`、`delete` | `Ord a => a -> Set a -> Set a` | O(log n) |
  | `member` | `Ord a => a -> Set a -> Bool` | O(log n) |
  | `size` | `Set a -> <Panic> Int` | O(n) |
  | `fold` | `(b -> a -> <e> b) -> b -> Set a -> <e> b` | O(n)、昇順 |
  | `to_list` | `Set a -> List a` | O(n)、昇順 |
  | `from_list` | `Ord a => List a -> Set a` | O(n log n) |
  | `union`、`intersection`、`difference` | `Ord a => Set a -> Set a -> Set a` | O(m log n)。m は低いほうの木の大きさ |

- 意味
  - `insert` は、等しい要素があれば前からあるものを残す。
  - 3つの集合の演算は `Ord` で等しい要素のうち、左の引数のものを残す。
  - `difference a b` は、`a` の要素のうち `b` にないものである。
- 集合の演算は低いほうの木をたどって高いほうの木に入れる形で書く。
  - 木の高さは印の高いほうの子をたどる O(log n) の関数で、`1 <<< 高さ` として数える (シフトだけなので `Panic` がない)。
  - split と join の形と比べて測った。20 万要素どうしの `union` で、今の形は 0.15 s、split と join は 0.09 s だった。確保は 2 万要素どうしで 19439 と 76495 だった。
- `Map a Unit` にしない。確保の数は同じで、節が1語小さく、API に `Unit` が出ない。回す関数の約 200 行が `Map` と重なるが、同じ形の検査のテストで両方を確かめる。

#### D-15: 安定な並べ替え

- `List.sort : Ord a => List a -> List a`、`List.sort_by : (a -> a -> <e> Ordering) -> List a -> <e> List a`。
- 下からのマージソートで、隣り合う列を2つずつ合わせる。右の要素が真に小さい (`GT`) ときだけ右を先に取るので、安定である。どのループも末尾再帰で、長さを数えないので、`Panic` がない。
- 比較の関数を呼ぶ順と回数は決めない。
  - `std/List.em` の頭の注釈の「関数を受ける関数は要素の順に呼ぶ」の例外として、注釈と spec に書く。
  - エフェクトのある比較の関数も渡せるが、そのエフェクトの起きる順は決まらない。
- `Array` には置かない (D-19)。30 万個の Int で 0.25 s、logstat の今の形は 0.50 s だった。

#### D-16: List の関数

| 関数 | 型 | 範囲の外 |

| `split_at` | `Int -> List a -> <Panic> (List a, List a)` | `n <= 0` なら `(Nil, xs)`、長さ以上なら `(xs, Nil)` |

| `contains` | `Eq a => a -> List a -> Bool` | |

  - `drop`: 線形の値を捨てる `drop` と名前が重なる。
  - `Option` と `Result` の補助関数
- 探すものが先に来る形は、`String.contains` と `Map.lookup` とそろう。

#### D-18: `FileOut` の API と実装

```haskell

import Bytes
```

|---|---|---|
| 置換付きのデコード (U+FFFD) | バイト列を文字列として扱いたい所がまだなく、`Bytes` の読みで受けられる | UTF-8 でないファイルを `grep` のように文字列の関数で扱う用途が出たとき |
| Unicode の表が要る操作 | 表を `eml_rt` に持ち込むか、Rust の std を信頼の行で包むことになり、使う所がない | ASCII でない大文字小文字の変換や文字の分類をスクリプトが要したとき |
| `Char.from_int` と `Char.is_scalar` (今の論点から移す) | `Char.of_byte` が全域なので、失敗を値で扱う所が出なかった | バイトや数から文字を作って失敗を値で扱う所が出たとき |
| 範囲外で `Option` を返す配列の添字 | eml で書くと `Array.get` の `<Panic>` が型に残る。除くには範囲を確かめない取り出しの extern が要る。スクリプトに使う所がない | 添字の範囲外を値で扱うプログラムが出たとき。または `Option` を返す版の方針を std 全体で決めるとき |
| `Lin` の要素の `Array` と `MutArray` の API | extern の引数の型変数を `Unr` に固定する規則 (declarations.md:121) を、行ごとに緩める仕組みが要る | 複数のリソースを配列に持つプログラムが出たとき。または「Kind の宣言化」に着手するとき |
| `Array` の並べ替え | スクリプトは List で並べる | 配列を並べるプログラムが出たとき |
| join を基にした集合の演算と、整列済みの列からの O(n) の構築 (`Map` と `Set`) | 差は 20 万要素どうしで約 0.06 s だけで、コードが約 150 行増える | 大きな集合どうしの演算が計測で目立ったとき |
| `FileOut.create_new` | 上書きを避ける使い方が、今のスクリプトにない | 同時に走るスクリプトが同じパスを作る使い方か、一時ファイルを作る使い方が出たとき |
| `Fs.append_text` | `FileOut.append` と `write` と `close` の1行で書ける | 同じ1行の定義がスクリプトの2か所以上に現れたとき |
| 書くファイルの buffer を確保量の上限に数えること | 読み手の 64 KiB と同じく、ヒープの外の決まった量である | 多くのファイルを同時に開くスクリプトが出て、上限の外の量が問題になったとき |
| 使っていない import の警告 | 明示の import を入れた直後は、警告より fix が先である | LSP に着手するとき |

## 付録: レビューで変わったこと (蒸し返さないために)

- `Map` の表現は、初めは赤黒木だった。利用者の依頼で AVL、OCaml の AVL、Adams の木と比べ、測り直した。合流で token を失わない「印をコンストラクタに持つ AVL」がいちばん速く、確保も少なかったので、これに変えた (D-13)。
- `Set` の集合の演算は利用者の指示でこの段に入れた。split と join の形は測ったうえで後に回した (D-14)。
- 書くファイルは3案 (`Fs.File` にモード、`Fs` に2つの型、別のモジュール) を比べた。利用者の追加の案で、読む側も `FileIn` に移した (D-4)。
- `FileOut` の失敗の後は buffer を捨てて書かない形にした。初めの案は drop に残りを書かせていた (D-6)。
- `byte_at` を消す案と、スクリプトの走査をすべて `char_at` にする案は、ネイティブ化の要件から外れるので退けた (D-2、D-3)。
- `valid_utf8` は、`from_utf8` を `try_panic` で書くので消した (D-2)。
- std の見え方で、REPL だけ暗黙にする案と、式の入力で import を自動で足す案は、セッションの状態を変える特例が要るので退けた (D-1)。
