| U-13 | JIT memory (jit-rt A1 review; Fable advice A1-advice-1, approved by the user): a JIT module's code and data live in one region of address space reserved when the module is made, `JIT_REGION_BYTES` = 128 MiB, and eml code is compiled with `is_pic=false` (cranelift-jit has no PIC path on aarch64). Every colocated reference (`Linkage::Local` data, `func_addr`, direct `call`/`return_call`) is then PC-relative and in range by construction: 128 MiB is the reach of an aarch64 `bl` (no veneer inside a module) and far below the ±2 GiB the loader resolves for address references on both ISAs. Imports (eml_nrt entries, libcalls, C functions) are absolute `Abs8` and need no proximity. `crates/eml_native/src/abi.rs` builds the ISA and the region in one function (cranelift-jit `ArenaMemoryProvider`), which every JIT module uses (the C bridges in `bridge.rs` keep their own module: their code names no symbol). A full region is a load error (`ModuleError::Allocation`); after it the module accepts no further load (a later `finalize_definitions` would panic). The owner releases the region on every exit path of the machine (Drop, not only `close`), after its workers have stopped; one module per machine, shared by its workers, never process-wide. Every data object is defined with `set_align(8)`. The size is one constant for every OS; Windows charges it to the commit limit, which is why it is not larger. Trigger for a custom `JITMemoryProvider` (reserve without commit on Windows, `MAP_JIT`, a capacity query): the 128 MiB limit or the Windows commit charge becomes a measured problem; it replaces the provider inside the one `abi.rs` function. jit-repl: one append costs up to three pages (about 10,900 appends at 4 KiB pages, 2,700 at 16 KiB, 680 at 64 KiB). `bench/native.sh` measures the 16-byte veneer reserve per call site and the absolute form of entry calls. |


## B. Resolutions of the first cross-check (all applied in the appendices' final texts)

R-1 entry identifiers: `extern_rows!` spells each variant's entry identifier (`fn IntShow as eml_x_IntShow(ctx, a: int) -> obj { .. }`; multi-variant `fn A as eml_x_A | B as eml_x_B (..)`); kind tokens (`obj`, `tobj`, `unit`, `int`, `enum`, `float`, `never`) go straight to `entries!`; a test checks every identifier is `eml_x_` + variant. R-2 fatal codes: 1 caught panic, 2 `FATAL_FAULT` (jit-rt); 3 `FATAL_RECORDED` (jit-core); `impl Raise for HeapError`/`Fault` defined once in jit-rt. R-3 `never` rows return normally with no result; generated code branches unconditionally after the call. R-4 inline rows are `inline fn` lines (shared `rows::` function, no entry); eml_native's inline table is tested equal to the marked set. R-5 one list: async rows are the `task` section of `extern_rows!`. R-6 no program-wide load-order numbers in generated code: per-name data symbols, sites relative to their function, functions by symbol. R-7 `eml run --native` with `--workers` other than 1 or `--gui` is a usage error until jit-tasks. R-8 an `eml_nrt_` service returns an action word, or a data word when its only failure path is the fatal path (contract wording fixed in 01). R-9 eml_nrt re-exports the run-interface types eml_native names; no eml_native → eml_sched edge. R-10 `eml_fatal(` appears only in eml_nrt's `entries.rs` and `enter.rs`. R-11 stack-geometry consts defined once in `crates/eml_nrt/src/run.rs`. R-12 N-37 exempts `bridge.rs` (fixed in 01). R-13 jit-externs floor: ≥323 `run`, ≥42 `run-fail` files native. R-14 sched-split already moves `doorbell.rs` and `Seat`. R-15 native.md L41 is rewritten by T0 only. R-16 deep-stack tests run on an explicit 64 MiB worker stack. R-17 jit-rt's 「エントリ」 spec outline includes the failure protocols by prefix and the fast-mode `Err` list. R-18 R1 updates the Miri budget text.

## D. Placement of the plan files

Each stage has its own plan file under docs/plans/, committed as that stage's first commit (roadmap 「進め方」). The design-level plans of the later stages and this shared appendix directory are committed with jit-rt's plan, so every stage reads the same decisions; each stage's Close deletes its own plan file, and the Close of jit-repl (the last stage) deletes this appendix directory. When a later stage starts, its design-level plan is refreshed into an executable plan (by the planning process) and replaces its file in that stage's first commit.
