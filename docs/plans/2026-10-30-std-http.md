## 3. 前提の事実

- `Net.read_line : TcpStream -> <IO, Panic, Async> (Option String, TcpStream)` と `Tls.read_line : Stream -> <IO, Panic, Async> (Option String, Stream)` の行の上限は 1048576 バイトで固定である (`std/Net.em:150`、`std/Tls.em:78`)。`read_chunk : Bytes -> s -> <IO, Async> (Bytes, s)` は buffer の後ろに足し、EOF では何も足さない。`Net.read_chunk` は空きが 8 バイト未満の buffer を広げる
- `Tls` は close_notify のない EOF を `ConnectionReset` (`cannot read the stream: the peer closed the connection without close_notify`) にする。`Tls.connect_with_ca ca host port` の `ca` は根に足す PEM で、`""` なら既定の根だけである
- IO の失敗は `fail_io : IOErrorKind -> String -> <IO> a` (`std/Prelude.em:48`) で投げ、`try_io` で受ける。`Lin` の値は投げる前に落とす (`std/Tls.em` の `drop conn`、`drop sock`)
- テストの driver では、`tls.localhost:PORT` への接続は TLS の終端器を通って平文の `localhost:PORT` の listener に届く。`tls-cut.localhost` は close_notify を送らずに閉じる。バイトは決着の始めごとに送られる。閉じる server のタスクは、先にその接続で読むか書く (`docs/spec/vm.md:478-479`)
- 今のテストの leaf の証明書の SAN は `DNS:tls.localhost`、`DNS:localhost`、`IP:127.0.0.1` で、`tls-cut.localhost` を持たない。`crates/eml_tls/fixtures/gen.sh` は OpenSSL 3.4 以上を要り、`ca.pem` を `tests/ui/run/tls` と `tests/ui/run-fail/tls` に写す。`crates/eml_tls/tests/fixtures.rs` の `every_ca_copy_is_the_fixture` が写しを確かめる
- seed で流すのは `par/` と `async/` だけである (`crates/eml_cli/tests/ui.rs:275-277`)。UI テストの期待値は `crates/eml_cli/tests/snapshots/integration__ui__{run,run_fail}@<分類>__<名前>.em.snap` の insta の snapshot である
- std のモジュールを足すと `eml_hir::STD` (`crates/eml_hir/src/lib.rs:38-58`、`Tls.em` は 56 行目) に1行が要る。`the_embedded_std_matches_the_std_directory` (`crates/eml_hir/tests/load.rs:986`) が `std/` と照らし合わせる
- `bench/scripts.sh` は macOS でしか動かない (`uname` を確かめ、`/usr/bin/time -l` を使う)。各コマンドを3回流して中央値を取り、`compare.sh --paths` で出力と終了コードが同じことを先に確かめる。ネットワークを使う行はまだない。CI は bench を流さない
- リポジトリに単独の TLS の server はない。rustls の server は、テスト専用の sans-IO の `Conn::server` (`crates/eml_tls/src/lib.rs:97`) だけである。rustls は `eml_tls` の普通の依存なので、example は Cargo.toml を変えずに組める
- `bench/` の直下の `.em` は `crates/eml_vm/tests/bench.rs` が `RunStats` を snapshot で固める。`bench/scripts/` の下は対象でない

### 5.2 段の中の設計

#### D-10: 公開の面

- 決めたこと: 次の5つだけを公開する。設計の文書 (`docs/future/async.md` の「TLS と HTTP」) の面に `deriving (Eq, Show)` を足しただけである
  ```haskell
  pub data Options  = | Options { headers : List (String, String), ca : String, max_redirects : Int } deriving (Eq, Show)
  pub data Response = | Response { status : Int, headers : List (String, String), body : Bytes } deriving (Eq, Show)
  pub defaults : Options          -- Options { headers = [], ca = "", max_redirects = 5 }
  pub get      : String -> <IO, Panic, Async> Response
  pub request  : String -> String -> Bytes -> Options -> <IO, Panic, Async> Response   -- method url body options
  ```
- 中の型: `data Conn = | Plain Net.TcpStream | Secure Tls.Stream` (Lin)、`data Reader = | Reader { conn : Conn, buf : Bytes, pos : Int }` (Lin。`buf[pos..]` が未読)、`data Url = | Url { secure : Bool, host : String, port : Int, target : String }`、`data Outcome = | Done Response | Moved Int String`。全文は A.1

#### D-11: 行は `Std.Http` が自分の buffer で切り出し、1行 64 KiB までにする

- 決めたこと: 状態行、ヘッダー、chunk の大きさの行、chunk の後の行、trailer の行を、`read_chunk` の上の `Reader` で切り出す。行の中身の上限は 65536 バイトで、ヘッダーの全体の上限は置かない
- 理由: `read_chunk` は読みすぎたバイトを戻せないので、chunked の本文には `Std.Http` の buffer が要る。行も同じ buffer で読めば、規則と失敗の文言が1つで済む。`read_line` の 1 MiB の上限は設計の文書の 64 KiB と合わない
- 退けた案: `read_line` を使う (buffer と上限と文言が2つずつになる)。`read_line` の後に 64 KiB を確かめる (1 MiB を超える行だけ別の文言になる)。ヘッダーの全体に上限を置く (本文に上限がないので、何も新しく抑えない)

#### D-12: 本文の区切りと応答の読み方

- 決めたこと: 本文の長さは RFC 9112 の 6.3 の順に決める。`HEAD`、204、304 は本文なし。`Transfer-Encoding` があれば chunked だけを受け (ほかの coding は失敗)、`Content-Length` は見ない。次に `Content-Length`。どちらもなければ EOF まで。1xx は中間の応答として読み捨て、次の応答を返す。ヘッダーの名前は ASCII の小文字にし、同じ名前は残す。規則の全文は付録 C の 5.3
- 理由: 設計の文書の「`Content-Length` > chunked > EOF」の順では、両方のヘッダーを持つ chunked の本文を生のバイトとして読む。名前を小文字にすると「大文字小文字を区別しない」を `List.lookup` で使える
- 退けた案: `Transfer-Encoding` と `Content-Length` が両方あれば失敗にする (要求ごとに閉じるので smuggling の恐れがなく、実際のクライアントより厳しすぎる)

#### D-13: 本文を1つの `Bytes` に足していく

- 決めたこと: `Content-Length` が n の本文は `Bytes.with_capacity (min n 67108864 + 8)` を取り、`read_chunk` で後ろに足し、`truncate n` で余りを切る。EOF までの本文は `with_capacity 65536` から倍々に広げる。chunked は `append_slice` で写し、`Reader` の buffer を `truncate 0` で使い回す
- 理由: `+ 8` で `Net.read_chunk` の「空きが 8 バイト未満なら広げる」に当たらず、64 MiB までは広げ直さない。64 MiB の上限は、偽りの `Content-Length` で大きな容量を取らないためである。ちょうど n を取ると、偽りの値で1バイトも届く前に `max_bytes` に当たり、受け止められない
- 確かめたこと: 実際の driver で 64 MiB の本文が `Content-Length` で 0.35 s、EOF で 0.36 s、平文の chunked で 0.28 s

#### D-14: 呼ぶ側のヘッダーとメソッド

- 決めたこと: `options.headers` に `Host`、`Connection`、`Content-Length`、`Transfer-Encoding` (大文字小文字を区別しない) があれば失敗にする。呼ぶ側の `User-Agent` は既定の `User-Agent: eml` に代わる。本文が空でないときと、メソッドが `POST`、`PUT`、`PATCH` のときに `Content-Length` を付ける。メソッドは token であることだけを確かめ、綴りのまま送る。`HEAD` などの扱いは大文字の綴りにだけ当たり、そのことを spec に書く
- 理由: `Content-Length` が2つになると server は 400 を返す。呼ぶ側の `Connection: keep-alive` があると、EOF までの本文が終わらない

#### D-15: URL

- 決めたこと: `http` と `https` だけ。fragment は除いて送らない。userinfo と IPv6 のアドレス (`[` で始まる authority) は失敗にする。host は英数字、`-`、`.`、`_` で、小文字にする。port は 1 から 65535。空の path は `/`。バイトはどれも 0x21 から 0x7E。理由の文言は付録 C の 5.3
- 退けた案: IPv6 のアドレスを受ける (角括弧の `Host`、IP の SNI、仮想のホストのテストが要る。ロードマップの「その後の項目」に送る)

#### D-16: リダイレクト

- 決めたこと: `max_redirects` が 1 以上なら、301、302、303、307、308 で `Location` のある応答を追い、本文を読まずに閉じる。回数が上限に達したら失敗にする。`max_redirects` が 0 以下なら追わず、3xx をほかの応答と同じく本文まで読んで返す。`Location` は絶対パス (`/` で始まり `//` で始まらない) か、大文字小文字を区別せずに `http://` か `https://` で始まる絶対 URL だけ。301、302、303 は `HEAD` ならそのまま、ほかは `GET` にして本文を空にし、呼ぶ側の `Content-Type` を落とす。307 と 308 は同じメソッド、本文、ヘッダーで送る。オリジンが変われば `Authorization`、`Cookie`、`Proxy-Authorization` を落とし、元のオリジンに戻っても戻さない。https から http へは失敗、http から https へは追う
- 理由: 0 で 3xx を返すと、呼ぶ側が `Location` を読める (curl の `-L` なし、Go の `CheckRedirect` と同じ)。`HEAD` を `GET` にすると、頼んでいない本文を取る (RFC 9110 の 15.4.4 が `HEAD` を保つことを許す)。`String.contains "://"` で絶対 URL を見分けると、`next?u=http://x` に誤った理由が出る

#### D-17: 失敗

- 決めたこと: `Std.Http` が投げるのは IO の失敗だけで、`Panic` は起こさない。row の `Panic` は使う `String` と `Bytes` の関数から来る。`Net` と `Tls` の失敗 (接続、名前、TLS、読み書き、`ConnectionReset`、`Cancelled`) はそのまま伝える。投げる前に接続を close_notify なしで落とす。16 の失敗の種類と文言は付録 C の 5.3 の表のとおり
- 制限として書くもの: 本文を書き終える前に相手が応答して閉じると、本文の書きの失敗になり、応答は読めない。`Net` と `Tls` の書きの包みはストリームを落としてから投げるので、読むストリームが残らない。ヘッダーと trailer の行の数に上限がなく、短い行を送り続ける相手からは戻らない (抜けるには `Async.timeout` で期限を付ける)

#### D-18: テストの証明書に `tls-cut.localhost` を足す

- 決めたこと: leaf の SAN に `DNS:tls-cut.localhost` を足して作り直し、`run-fail/http/truncated.em` を置く
- 理由: EOF までの https の本文で `Tls` の `ConnectionReset` をそのまま伝える、という `Std.Http` の規則を確かめるテストはこれだけである。この失敗を EOF とみなす実装は切れた本文を黙って返し、`tls/truncated.em` ではそれを見つけられない。`Std.Http` は URL の host でつなぐので、`tls/truncated.em` のように `Net` で開いて別の名前で handshake する形が取れない
- 退けた案: テストを省き、`tls/truncated.em` を引く (証明書の作り直しは省けるが、上の規則が確かめられなくなる)
- 影響: CA、証明書、鍵がすべて変わる。証明書のバイトに頼る snapshot と assertion はない (全 UI テストを作り直した証明書で流して確かめた)。古い CA を写すか固めた別のブランチは壊れる

#### D-19: UI テストの置き場所と形

- 決めたこと: `tests/ui/run/http/` と `tests/ui/run-fail/http/` に置き、seed では流さない。1つのプログラムで、`Net` で書いた server のタスクと client のタスクを動かす。server のタスクは要求を読んでから応答を書いて閉じ、印字は応答を書く前だけにする。client は要求が返ってから印字する。`run-fail` のテストは `try_io` で受けて `show e.kind` を印字し、`fail_io e.kind e.message` で投げ直す。https は `tls.localhost` で、`Fs.read_text "ca.pem"` を `ca` に渡す。Windows の印は付けない。エントリのファイルを `http.em` にしない (`import Http` が E1026 になる)
- ファイルの一覧と中身は A.2、期待値は A.3

#### D-20: 行 `https-get` の server

- 決めたこと: `crates/eml_tls/examples/https_server.rs` (B.1)。`rustls::ServerConfig` と `StreamOwned` をブロックする `TcpStream` の上で使い、鍵と証明書は `eml_tls::fixtures::{CERT_PEM, KEY_PEM}`。`Conn::server` は使わない。`https_server MIB` は先に本文 (`format!("{i:015}\n")` の 16 バイトの行の列) を作り、`127.0.0.1:0` で待ち受けて標準出力の1行目にポートを出す。TLS 1.3 の `TLS13_AES_256_GCM_SHA384` だけで応える。接続ごとにスレッドを立て、要求の頭を `\r\n\r\n` まで読み、`Content-Length` 付きの 200 を 1 MiB ずつ書き、close_notify の後に書く側を閉じ、2 s まで読み捨ててから落とす
- 理由: 依存も Cargo.toml も変わらず、`THIRD-PARTY-LICENSES.md` も変わらない。`bench/rt.sh` が `crates/eml_rt/examples/` を組むのと同じ形である。接続ごとのスレッドと書く側だけの close により、`Std.Http` がどの順で閉じても次の計測を遅らせない (close_notify の後に閉じる、close_notify なしで落とす、EOF まで読む、の3通りで確かめた)。暗号を1つに絞るのは、eml と Python を同じ暗号で比べるためである。chunked にしないのは、chunk の解析でなく `Net` と `Tls` の読みの道を測るためである
- 退けた案: Python の `ssl` の server (設計の文書の「rustls の server」を変える理由がない)。`Conn::server` (テスト専用で、写しが1回多い)。新しい crate か `[[bin]]` (重いか、配る binary になる)。`bench/scripts/rust/` の下で `rustc` で組む (rustls を結べない)

#### D-21: 行 `https-get` のクライアントと組み込み

- 決めたこと: `bench/scripts/https_get.em` と `bench/scripts/https_get.py` (B.2)。どちらも `https_get CA_PEM URL` で動き、状態、本文の長さ、本文の最後の行を出す (64 MiB なら `200`、`67108864`、`000000004194303`)。引数の数が違えば `usage: https_get CA_PEM URL` を標準エラーに出して終了コード 2。URL は `https://127.0.0.1:PORT/`、CA は `crates/eml_tls/fixtures/ca.pem`。`bench/scripts.sh` に `https_row LABEL MIB` (B.3) を足し、今の `row` をそのまま使う。スクリプトの表の6行目で、大きさは `64 MiB`
- 理由: 本文の検査和は VM の 64 Mi 回のループになり、行の時間を占める。各行が自分の番号を持つので、長さと最後の行で欠けと重なりが分かる。`127.0.0.1` は名前の解決を測らず、`::1` を先に試す差も出ない。eml の実装は `tests/ui/run/scripts/` に置けない (UI テストはテストの driver で動く) し、`bench/` の直下にも置けない (`RunStats` の snapshot が要る)
- 大きさの 64 MiB は仮である。Linux の代わりのプログラム (`Tls` を直接使う eml) で eml 0.25-0.33 s、Python 0.22-0.26 s だった。本当の大きさは T-5 の macOS の計測で決める
