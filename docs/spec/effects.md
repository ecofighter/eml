# エフェクトと handler

位置づけ: 規範。

エフェクト操作の多重度、`Lin` 値の持ち越し規則、handler の意味、extern のエフェクトである組み込みの `IO` と、標準ライブラリの `FileIn` を定める。`effect` 宣言と handler の構文は [宣言](declarations.md) と [式](expressions.md) で扱い、この文書では意味を定める。

## エフェクトと row

- エフェクトは Koka 方式の row 多相で扱う (scoped labels)。row 変数は Kind `Row<s>` (`s ∈ {Never ≤ Once ≤ Multi}`) を持つ ([型と Kind](types.md))。
- 副作用は組み込みの `IO` エフェクトとして管理する。`IO` は extern のエフェクトである (下の「組み込みの `IO`」)。

## エフェクトの宣言と操作

```haskell
effect State s where
  get : Unit -> s
  put : s -> Unit

effect Fail where
  never fail : String -> a
```

- 操作ごとに多重度 `never` / `once` / `multi` を宣言する。省略したら `once` である。宣言の構文 (操作のカリー化、操作のシグネチャに row を書けないこと) は [宣言](declarations.md) の「`effect`」で定める。
- エフェクトは型引数を持てる (`effect State s`)。row に付ける型引数の個数 (E1015) と、操作のシグネチャの型変数の扱いは [宣言](declarations.md) の「`effect`」で定める。
- `never` の操作の結果の型は自由な型変数なので、呼び出した側ではどんな型として使ってもよい。結果の型に書けるもの (E1008) は [宣言](declarations.md) の「`effect`」で定める。
- 操作は普通の関数として呼ぶ (`get ()`)。表面の構文に `perform` はなく、HIR から Core IR への変換で操作の呼び出しを `perform` 命令に変える ([Core IR](core-ir.md))。
- 操作は値の名前空間に置くトップレベルの値で、エフェクト名は型名と同じ型の名前空間に置く。名前の重複と、handler の節の先頭の名前の解決は [モジュールと名前解決](modules.md) で定める。

## 継続の多重度と持ち越し規則

`multi` (多回の再開ができる継続) を持つのは、`multi` と線形性の衝突 (持ち越し規則と、`map` などの総称の関数が注釈なしで推論する条件付きの制約) が、eml の実験として新しい部分だからである。`multi` を捨てて1回だけ再開するエフェクトに絞る案は、実装は最も小さくなるが、実験の独自な部分を失うので採らなかった。

| 操作の宣言 | handler 側の `k` | 呼び出しをまたいで生きていてよい値 |
|---|---|---|
| `never` | なし | `Unr`、`Lin` (中断時に drop される) |
| `once` (デフォルト) | `Lin` の矢印を持つ関数。`ctl` の節は、戻らない呼び出し (`fail` など) で終わる経路を除き、`k` を呼ぶ (`k v`、状態のある handler では `k v st`) か `drop k` を必ず書く ([線形性](linearity.md) の「戻らない経路の検査」) | `Unr`、`Lin` (同上) |
| `multi` | `Unr` の矢印を持つ関数 | `Unr` のみ |

`multi` の操作の `k` は何度でも呼べ、`drop k` しても使わなくてもよい。継続はクロージャの列で、共有された継続を再開するときは、クロージャの捕獲を写してから再開する ([Core IR](core-ir.md) の「継続の組み立て」)。

- 呼び出しをまたいで `Lin` の値を持っている場合、その呼び出しの row について次のように扱う。持っている値は、呼び出しの後の評価で使う局所変数と、評価済みで呼び出しの後に消費される部分式の値 (途中の値) である。評価の順は [式](expressions.md) の「関数適用」が定める。引数はすべて評価してから矢印を順に適用するので、矢印 `i` の呼び出しの間は、後の矢印に渡す評価済みの引数 `e(i+1)` … `en` の値も持つ。評価済みの引数が局所変数そのものなら、途中の値でなくその局所変数として持ち、診断は変数を名指しする。
  - row に `multi` な操作が含まれていれば、エラーにする。
  - row 変数 `e : Row<σ>` を含む場合は、制約 `σ ≤ Once` を追加する。その結果、`e` に `multi` な操作が入るような呼び出し方は、制約違反として検出される。束が3要素なので、`σ = Once` ではなく `≤` で書く (`σ = Once` は誤り)。
  - 値の型の Kind が Kind 変数を含むときは、「その値が `Lin` なら」という条件つきの制約にする ([型と Kind](types.md) の「推論」)。
- 規則を当てはめる形と、見る row は次のとおりである。

| 形 | 見る row | またいで持っている値 |
|---|---|---|
| 関数とクロージャの呼び出し | 矢印ごとの row。トップレベルの値を呼ぶときは、開く前の宣言の row | 呼び出しの後で使う値。後の矢印に渡す評価済みの引数を含む |
| 操作の直接の呼び出し | 操作の多重度 | 同上 |
| `k` の呼び出し (`k v` / `k v st`。`k` は節の継続) | `k` の最後の矢印の row (handle の外側の row) | 節の中で後で使う値 |
| `handle` | 外側の row | handle の後で使う値 |
| 同上 | 本体の row 全体 | `return` の節が捕まえた値 |

- 操作を直接呼ぶときは、エフェクトの単位ではなく、その操作の多重度だけを見る。`once` の操作の呼び出しのフレームは、その操作の区間の先頭にあり、再開されると値をすぐに受け取って消えるので、ほかの `multi` の操作の区間に入らないためである。そのフレームが `k` の中で中断している間、節は `k` を `Lin` の値として持っているので、節が `multi` の操作を起こすと `k` を `multi` の操作をまたいで持つことになり、持ち越し規則が節を拒否する。
- `fn` の節 (下の「handler の意味」) も同じである。隠れた `k` は本体の間ずっと生きているので、`once` の操作の `fn` の節の本体が `multi` の操作を起こすと E3006 になる。`| ctl ask () k -> k (choose ())` と書いても同じ誤りになる。診断は、隠れた名前 `$k` でなく「この `fn` の節の継続」(the continuation of this `fn` clause) と書いて節を指し、help で呼び出しを `fn` の節の外で行うように勧める。
- この検査は各呼び出し箇所で局所的に行えば、全体として健全になる。`multi` の継続を再開するときに写されるのは区間のフレームが持つ値 (呼び出しの後で使う値、余った引数、内側の handler の節と `return` の節のクロージャ) だけで、フレームが区間に入るのは、そのフレームを積んだ呼び出しの row に現れるエフェクトの操作が起きたときに限られるためである。
- 持ち越し規則の検査は、線形性の検査パスで行う ([線形性](linearity.md))。違反は E3006 にする ([診断](diagnostics.md))。

## 組み込みの `IO`

- `IO` は、Prelude が `pub extern effect IO where never io_failed : IOErrorKind -> String -> a` と宣言する extern のエフェクトである。操作 `io_failed` は Prelude の外から見えず、Prelude の `try_io` だけが handle する ([標準ライブラリ](stdlib.md) の「`try_io`」)。
- `IO` を起こすのは、`IO` を row に持つ extern の関数 (`println` など) である。extern の関数は handler を通らず、その場で実行して値を返す。ただし、`try_io` が捕まえる種類の誤りで失敗すると、VM が `io_failed` の節の入口を呼んで中断を始める。`exit` と `fail_io` はいつも中断を始める ([VM](vm.md) の「extern の中断」)。中断は継続を作らずに巻き戻しで進むので、`IO` を起こす extern の呼び出しは yield の地点でなく ([Core IR](core-ir.md) の「IO の extern」)、`IO` は yield しうるラベルでない ([型と Kind](types.md) の「row の具体化の記録」)。
- extern の関数の呼び出しは、操作の呼び出しと違って `perform` 命令にならない ([Core IR](core-ir.md))。多重度は `once` として扱う。
- handler の節の先頭に、`IO` を起こす extern の関数の名前を書いたらエラーにする (E1009)。節の先頭の名前は、まず操作として引き、見つからないときだけ extern の関数を引く。extern のエフェクト (`IO` か `Panic`) を起こす extern の関数が見つかれば E1009 で、それ以外 (純粋な extern の関数) は E1001 である。ユーザーが定義した同名の関数は、`Prelude` の extern の関数を隠さない ([モジュールと名前解決](modules.md) の「名前の解決」)。

`IO` を起こす extern の関数のうち、線形なファイルを扱うものは次のとおりである。ほかの標準ライブラリの関数 (`eprintln`、`Env`、`Fs.write_text`、`Proc.run` など) と、ほかの線形なハンドル (書くファイルの `FileOut`、標準のストリームの `Stdin`、`Stdout`、`Stderr`、子のプロセスの `Proc.Child`) の関数は [標準ライブラリ](stdlib.md) にある。`println` は、`Stdout` のハンドルと同じ Host の標準出力の buffer に書く ([標準ライブラリ](stdlib.md) の「`Stdout` と `Stderr`」)。

| 名前 | 所属 | 型 |
|---|---|---|
| `println` | `Prelude` | `String -> <IO> Unit` |
| `open` | `FileIn` | `String -> <IO> FileIn` |
| `read_all` | `FileIn` | `FileIn -> <IO> (String, FileIn)` |
| `close` | `FileIn` | `FileIn -> <IO> Unit` |
| `FileIn` | `FileIn` | extern の線形型 (`Lin`)。破棄処理は `close` |

ファイルを読む操作は標準ライブラリのモジュール `FileIn` にあり、`import FileIn` を書いたモジュールで `FileIn.open` のように修飾付きで使う ([モジュールと名前解決](modules.md) の「標準ライブラリ」)。`println` は `Prelude` にある。

- `open` の相対パスは、Host の基準ディレクトリ (`file_root`。[オブジェクトモデル](object-model.md) の `StdHost` の項) から解釈する。CLI の `run` はカレントディレクトリを基準にする。絶対パスはそのまま開く。`file_root` の既定 (空のパス) はカレントディレクトリを指す。
- `read_all` は現在の位置から最後までを UTF-8 として読み、読んだ文字列を先に、同じ `FileIn` を後に置いた組で返す。ファイルを読む関数はどれも、`FileIn` を借りて読み、結果を先に置いて `FileIn` と組にして返す (行は `FileIn` を借り、組は translate が作る。[Core IR](core-ir.md) の「組を返す extern」)。読めなかったときも `FileIn` は手放さない。1行ずつ読む `FileIn.read_line` は、std の中だけの extern の上に eml で書いた関数で、[標準ライブラリ](stdlib.md) の「`FileIn`」にある。バイト列の読み (`FileIn.read_all_bytes`、`read_line_bytes`、`read_chunk`) も同じ形で、同じ節にある。
- `close f` と `drop f` は、どちらも `FileIn` の破棄処理 (オブジェクトの解放) を呼ぶ。
- 開けない、読めない、UTF-8 でないときは、`try_io` が捕まえなければ実行時エラーにする ([LIR](lir.md) の「実行時エラー」、[標準ライブラリ](stdlib.md) の「`try_io`」)。

extern のエフェクトは、型検査では普通のエフェクトと次の点が違う ([型と Kind](types.md) の「推論」)。row の中で重なったラベルは1つにまとめ、`mask` には入れない。多重度は処理系の表の行が決め、`IO` は `Once` である ([型と Kind](types.md) の「Kind」)。

重なりを1つにまとめ、`mask` に入れなくてよいのは、`IO` の操作が `never` の `io_failed` だけで、捕まえるのが例外と同じく実行の時点で最も近い `try_io` だからである。どちらの `IO` に届いても、捕まえる `try_io` は同じになる。

組み込みのリソースは、どのスレッドで後始末してもよいものに限る。現状の `FileIn` と `FileOut` はこれを満たす ([マルチコア対応の設計](../future/multicore.md))。

## 組み込みの `Panic`

- `Panic` は、Prelude が `pub extern effect Panic where never panicked : String -> a` と宣言する extern のエフェクトである。`IO` と同じく、操作 `panicked` は Prelude の外から見えず、Prelude の `try_panic` だけが handle する ([標準ライブラリ](stdlib.md) の「`try_panic`」)。利用者は、Prelude の `panic : String -> <Panic> a` で起こし、`try_panic` で捕まえる
- `Panic` が表すのは、値と入力で決まる誤りである。整数の桁あふれとゼロ除算、文字列の範囲外の位置と文字の境界でない切り出し、範囲外のスクリプトの引数、利用者の `panic` がこれに当たる。これらを起こしうる関数は、最後の矢印の row に `Panic` を持つ。`Num` と `Div` のメソッド (`+`、`-`、`*`、`/`、`%`、前置の `-` が呼ぶ `negate`) と、extern の関数 `String.byte_at` がこれに当たる。一覧は [標準ライブラリ](stdlib.md) の「`try_panic`」の表にある。`Env.arg` の row は `<IO, Panic>` である
- ヒープの誤り、内部の誤り、割り込み、深さと確保量の上限、標準出力への書き出しの失敗は、型に出さない。どの呼び出しでも起きうるか、起きた位置が決まらないためである
- `panic` は、`exit` と同じく戻らない extern の関数である。結果の型は量化した型変数なので、手前で `Lin` の値を手放さなくてよい ([線形性](linearity.md) の「暗黙の後始末」)
- 型検査では、重なったラベルを1つにまとめ、`mask` に入れない点が `IO` と同じである。多重度は `Never` で、`never` の操作だけを含む row (`Row<Never>`) に入れられる。並列のタスクに渡す関数も `Panic` を起こせる ([マルチコア対応の設計](../future/multicore.md))。操作は `never` の `panicked` だけなので、`Panic` は yield しうるラベルでない ([型と Kind](types.md) の「row の具体化の記録」)。row に `Panic` を足しても、yield の確かめは増えない
- トップレベルの値の本体と、`Eq`、`Ord`、`Show` のメソッドの row は空なので、そこでは `Panic` を起こせない ([宣言](declarations.md) の「シグネチャと等式」)。`main` の row と REPL の入力の row は `Panic` を許す ([モジュールと名前解決](modules.md) の「モジュール」、[型と Kind](types.md) の「REPL の入力」)

## 抽象エフェクト

`pub abstract effect E where …` は、エフェクトの名前を公開し、操作を宣言したモジュールの外から隠す。外のモジュールは row に `E` を書き、`E` を持つ関数を呼べるが、操作を perform できず、`handle` の節に書けず (どちらも E1058)、import の並びの `E(..)` でも取り込めない。extern のエフェクトはいつも隠す (上の「組み込みの `IO`」)。型検査、evidence passing、`mask` は普通のエフェクトと同じで、違いは名前解決だけである。

## handler の意味

```haskell
try : (Unit -> <Fail | e> a) -> <e> Option a
try action =
  handle action () with
    | ctl fail _ -> None
    | return x -> Some x
```

- 操作の節は `ctl` の節か `fn` の節である ([式](expressions.md) の「handler」)。`ctl` の節は継続 `k` を受け取る。`never` の操作の節は `k` を受け取らない `ctl` の節である。`fn` の節 `| fn op 引数 -> 本体` は `k` を受け取らず、`| ctl op 引数 k -> k (本体)` と同じ意味である。本体の値ですぐに再開する。
- deep handler とする。`k` を呼んで (`k v` / `k v st`) 再開した継続の中で同じ操作が呼ばれたら、同じ handler が処理する。
- 継続は `k` を呼んで再開し (状態のない handler は `k v`、状態のある handler は `k v st`)、`drop k` で捨てる。
- `k` の引数の個数の誤りは、どちらの handler でも普通の関数適用の誤り (E2001 など) として報告する。
- 1つの handler は1つのエフェクトを扱い、そのエフェクトのすべての操作に節を書く。複数のエフェクトは handler を入れ子にして扱う。別のエフェクトの節が混ざったら E1012、節のない操作があれば E1013、同じ操作の節が2つあれば E1014 にする ([診断](diagnostics.md))。
- `ctl` の節の `k` は、線形性を持つ第一級の普通の関数である。変数に束縛し、関数に渡し、データにしまい、クロージャで捕まえられる。`k` の型は表面の構文に名前を持たず、シグネチャには書けない。型は次のとおりで、`m` は `once` の操作なら `Lin`、`multi` の操作なら `Unr`、`a` は操作の結果の型、`r` は handle の結果の型、`<outer>` は handle の外側の row である。

  | handler | `k` の型 |
  |---|---|
  | 状態なし | `a -[m]-> <outer> r` |
  | 状態あり (`from`) | `a -[m]-> σ -[m₂]-> <outer> r` |

  `m` が `Lin` のとき、表面の型では `once a -> <outer> r` と書く (`σ` の矢印も同じ)。

- 破棄は `drop k` で行う。`once` の `k` を入れたデータやクロージャは、`Lin` の値を捕まえた値と同じく `Lin` になる。
- handle が値を返した後でも、`k` を再開してよい。deep handler では、再開した先の文脈の上に、同じ handler の新しい実行がもう一度設けられる。状態のある handler では、`k v st` の `st` がその実行の状態になる ([Core IR](core-ir.md) の「再開と状態」)。
- 診断は `k` の型を普通の関数と同じ形で表示する。`once` / `never` の操作では `once a -> <outer> r` と書く。
- 操作の節は、handler が生きている間、操作が起きるたびに呼ばれる。そのため、節が捕まえる変数には `Unr` の制約が付く。節は引数を何度使ってもよく、`once` の位置に渡してもよい。引数を読む式の矢印は広がるからである ([型と Kind](types.md) の「値を読む式の矢印の線形性」)。handle の本体と `return` の節は高々1回しか動かないので、`Lin` の値も捕まえられる ([線形性](linearity.md))。ただし、`return` の節のクロージャは handle の実行 (`prompt$` のフレーム) が持ち、本体の実行中に起きた `multi` の操作の区間に入ると写される。そのため、`return` の節が捕まえた値は、本体の row 全体をまたいで持つ値として持ち越し規則にかかる (上の「継続の多重度と持ち越し規則」)。
- 操作の型の Kind 変数 (型変数の Kind、矢印の線形性、row 変数の多重度) は、次のように決める。操作は本体を持たないので、節が値をどう使うかを操作の型に推論できない。そこで、操作を呼ぶ側から節へ渡る値は宣言で縛り、節は、呼ぶ側がスキームの範囲でどう選んでも正しくなるように検査する。
  - 引数の型に現れる線形性の Kind 変数は `Unr` に固定する。そのため、`k` のような線形な値は、多相な操作の引数や、引数の関数型の位置に渡せない (E3001)。節でも同じく `Unr` として扱うので、節はその引数を何回使ってもよいが、`Lin` の値として扱うことはできない
  - 結果の型の矢印は、節から見た位置の向きで決める。呼ぶ側から節へ渡る位置 (結果の中の関数型の引数の側。向きは下の項目のとおり反転を重ねて決める) の矢印は、引数と同じく宣言で `Unr` に固定する。たとえば `each : Unit -> ((Int -> <IO> Unit) -> <IO> Unit, Int)` の節は、受け取った callback を何回呼んでもよく、呼ぶ側はそこに `FileIn` を捕まえたラムダを渡せない (E3001)。節が作って渡す位置 (結果の型そのものの中や、関数型の戻り値の側) の矢印は、呼ぶ側がその関数を何回でも呼べるので、節の中では `Unr` 以下にする。たとえば `mk : Unit -> (Unit -> <IO> Unit, Int)` の節が `FileIn` を捕まえたラムダで再開すると誤り (E3001) になる。両方の向きに現れる位置 (`data Ref a = | Ref (a -> Unit) a` の `a` に置いた関数型など) の矢印は、呼ぶ側から節へ渡る位置と同じく宣言で `Unr` に固定する
  - 位置の向きは、関数型の引数で反転し、タプルの要素と関数型の戻り値ではそのまま保つ。型構成子の型引数の位置は、`data` の型引数ごとの変位 ([型と Kind](types.md) の「Kind」) で決める。row のラベルの型引数は両方の向きとして扱う
  - 結果の型だけに現れる型変数は縛らないので、`never fail : String -> a` はどの型としても使える。そのかわり、操作を呼ぶ側はそういう型変数を `Lin` の型 (`FileIn` など) で具体化できるので、節はその型の値を線形に扱う。引数の型に現れない操作ごとの型変数の Kind は、節の中では `Lin` 以上である。たとえば `mk : Unit -> Box a` (`data Box a = | Box (a -> (a, a))`) の節で `Box (fn x -> (x, x))` を作ると、`a` の値 `x` を2回使うので誤り (E3002) になる
  - 操作ごとの row 変数は縛らない。そのかわり、呼ぶ側は `multi` の操作を含む row で具体化できるので、その多重度は節の中では `Multi` 以上である。たとえば `mk : Unit -> ((Unit -> <IO | e> Int) -> <IO | e> Int, Int)` の節で、受け取った `g` の呼び出しをまたいで `FileIn` を持つと誤り (E3006) になる
  - 単相な `Lin` 型の引数には、これらの規則は関わらない ([線形性](linearity.md))。エフェクトの型引数の Kind 変数は固定しない。handle ごとに具体的な型で節を検査するので、節での使い方がその型の Kind に伝わる
- handle は、扱うエフェクトの型引数を handle ごとの新しい推論用の変数にし、本体を `<E α1 .. αn | ρ>` で検査する。節では、エフェクトの型引数をその変数で、操作自身の型変数を節だけの rigid な変数で具体化する。
- 呼び出しは `mask` を持ちうる。`k` の呼び出し (`k v` / `k v st`) も普通の呼び出しなので、`mask` を持ちうる。型検査が、row 変数の手前に余ったラベルから決める ([型と Kind](types.md) の「推論」)。`mask` はエフェクトごとの項目の集まりで、項目は (エフェクト `L`、残す数 n、飛ばす数 m) である。m は 1 以上、n は 0 以上で、1つの `mask` は同じエフェクトの項目を2つ持たない。`mask` 付きの呼び出しの間に起きた `L` の操作が handler を探すときは、その呼び出しより外側にある `L` の handler のうち、内側から数えて n 個を残し、続く m 個を飛ばす。呼び出しの中で設けた handler は飛ばさない。項目のないエフェクトの handler も飛ばさない。n が 0 の項目は Koka の `mask` と同じ意味で、n が正の項目は Koka の `mask behind` を広げたものに当たる。`k` の呼び出しの `mask` は、再開した継続の中の操作が `k` の handler より外側を探すときに効く。
- 中断 (`never` の操作の perform、`try_io` が捕まえる IO の失敗、`exit`) で外れるフレームが持つ値と、`drop k` で捨てた継続が捕まえていた値は、破棄処理で解放する。戻らない呼び出しで終わる経路では、その経路で消費しない `Lin` の値を呼び出しの前で手放す。通常の制御フローでは、この2つのほかに暗黙の後始末を行わない ([線形性](linearity.md) の「暗黙の後始末」)。
- 節の書き方、節の引数の個数、`return` の節の省略は [式](expressions.md) の「handler」で定める。

## パラメータ付き handler

```haskell
run_state : s -> (Unit -> <State s | e> a) -> <e> (a, s)
run_state init action =
  handle action () from init with
    | fn get () st -> (st, st)
    | fn put st2 _ -> ((), st2)
    | return x st -> (x, st)
```

- パラメータ付き handler は、状態を handler の実行ごとの evidence に持つ。脱糖はしない。構文、評価の順、省略した `return` の節は [式](expressions.md) の「パラメータ付き handler」で定める。deep handler の意味と中断時の後始末は、状態のない handler と同じである。
- 初期値の型を状態の型 σ とする。各操作の節は最後の引数に σ を受け取り、`return` の節は本体の値と σ を受け取る。
- `fn` の節 `| fn op 引数 st -> 本体` の本体は、操作の結果と次の状態の組を返す。意味は `| ctl op 引数 k st -> let (v, st2) = 本体 in k v st2` と同じである。組の順は `k v st` の引数の順に合わせる。
- 状態のある handler の `k` は、`a -[m]-> σ -[m₂]-> <outer> r` という2引数の関数で、`k v st` で再開する。状態のない handler の `k` は1引数の関数で、`k v` で再開する。`from ()` と書いた handler は状態のある handler で、状態の型は `Unit` である。
- row は最後の矢印に付ける。`k v` は部分適用でエフェクトを起こさないので、最初の矢印の row は空の閉じた row である。
- 2つ目の矢印の線形性 `m₂` は、`m` と `a` の Kind の join である。`k v` を部分適用したクロージャは `v` を捕まえるので、`multi` の `k` でも `a` が `Lin` なら、そのクロージャは1回しか呼べない。コンストラクタやラムダの部分適用と同じ規則である。`once` の `k` では `m₂` は `Lin` になる。
- HIR は、節の `k` を引数の数が分かる呼び出し先 (状態なしは1、状態ありは2) として扱うので、`k st (st + 1)` のように引数に式を書いても1回の再開になる ([式](expressions.md) の「関数適用」)。
- 状態は区間の外 (節の手元) にあるので、σ は `k` の Kind に影響しない。
- 操作が起きると、evidence から状態を取り出して節に渡す。継続の区間に残る handler の実行は、状態を持たない。`k v st` は、`st` を状態にした新しい evidence を作ってから再開する。すぐに再開する節は、その場で状態を取り出して戻す。本体の値が handle に戻ったら、状態を取り出して `return` の節に渡す ([Core IR](core-ir.md) の「handle と `prompt$`」と「再開と状態」)。
- 中断 (`drop k`、または `never` の操作の perform) のとき、状態は節が持っている。そのため、継続の解放では状態を解放しない。状態の後始末は、節の線形性の検査で確かめる。
- 節の中の状態は普通の引数なので、線形性の検査がそのまま当てはまる ([線形性](linearity.md) の「パラメータ付き handler の状態」)。
- handle の本体を実行している間、状態は evidence にある。そのため、状態は handle の外側の row をまたいで生きている値として、持ち越し規則にかける。扱うエフェクトの操作が起きると、状態は節に渡って区間に残らないので、本体の row 全体は対象にならない。外側のエフェクトの操作で区間が捕まったときは、handle の実行が状態を持ったまま区間に入り (`prompt$` が状態を取り出して `rewind$` のクロージャに入れる)、`multi` なら写される。たとえば handle の外側の row に `multi` の操作があれば、状態は `Unr` でなければならない。

## `var` のエフェクト

HIR は `var` の地点ごとに合成のエフェクト `L` を1つ作る ([式](expressions.md) の「`var`」)。`L` は名前空間に入らず、型引数も操作も持たない。ラベルの鍵はほかのエフェクトと同じく `EffectId` なので、row の表、Core IR の効果の表、EP の evidence は今の形で使える。診断では `var x` と表示する。

- `var x = e` の範囲は `L` を扱う handle の本体と同じく、今の row の前に `L` を足した row で動く。変数を使う所はどれも `L` の `perform` と同じく row に `L` を求める ([型と Kind](types.md) の「`var` の変数」)
- `L` の多重度は `Once` である。エフェクトの多重度は操作の多重度の最大から決めるので、操作がないと `Never` になり、`may_yield` も Kind と持ち越しの検査も、`L` を yield しないラベルとして扱ってしまう。変数の操作はどれもすぐに再開するので `Once` にする。これで、変数を使う関数は `yields` になり、[Core IR](core-ir.md) の「handler への特殊化」の経路に入る
- 持ち越し規則は変数の範囲を、状態が初期値の handle と同じく扱う (上の「継続の多重度と持ち越し規則」の表の `handle` の行)

## 健全性

型検査が `mask` を決め ([型と Kind](types.md) の「推論」)、実行時がそれを守ることで、操作はその静的な row のラベルが約束した handler に捕まる。これは次の不変条件から従う。ここで、実行中のある点の具体化した row とは、その点で動いている instance (またはクロージャ) の具体化で、静的な row の rigid な row 変数を置き換えた row である。この row は具体的な row で、末尾は `main` の `<IO>` に行き着く。

> 実行中のある点で、継続を外側に向かってたどり、途中の `mask` 付きの呼び出しが飛ばす handler を除く。そのとき、どのエフェクトについても、見える handler の並びは、その点の具体化した row にある同じエフェクトの handle できるラベルの並びで始まる。

エフェクトごとに見るのは、scoped labels の row で順に意味があるのが、同じエフェクトのラベルどうしだけだからである。不変条件を具体化した row で述べるのは、rigid な末尾 `e` の手前のラベルの後ろに、`e` の具体化に当たる handler が見えることまで含めるためである。下の呼び出しの項は、m 個を飛ばすと残りが `e` の具体化に当たることを使う。並びの全体でなく先頭の部分で述べるのは、閉じた row の呼び出し先とラムダの中では、外側の handler が見えたまま残るためである。不変条件は、プログラムの入口で成り立ち (`main` の row の handle できるラベルは空である)、次の各形で保たれる。

- 呼び出し: 呼び出し先の row を `<ls | e>` とする。`ls` のラベルは、今の row の同じエフェクトのラベルと先頭から対になる。`e` が rigid なとき、エフェクト `L` ごとに見ると、`e` の手前にある今の row の `L` は、先頭の n 個が `ls` と対になり、残りの m 個が rest (`ls` と対にならずに `e` の手前に余った今の row のラベル) にある。`L` が handle できるエフェクト (extern のエフェクト以外。利用者は `IO` を handle できず、Prelude の `try_io` だけが handle する) で m が正なら、`mask` は `L` の項目 (n、m) を持つ。今の点で見える `L` の handler の並びは、不変条件により `[n 個, m 個, e の具体化の L の分]` で始まる。項目が n 個を残して続く m 個を飛ばすので、呼び出し先の中で見える `L` の handler の並びは `[n 個, e の具体化の L の分]` で始まり、これは呼び出し先の具体化した row の `L` のラベルの並びである。m が 0 なら項目はなく、今の row の `L` はすべて `ls` と対になるので、同じ並びになる。`L` が `ls` に現れなければ n = 0 で、`e` を通る `L` の操作は rest の `L` の handler をすべて飛ばし、`e` の具体化に当たる handler に届く。末尾が閉じた row なら、`ls` のラベルを今の row の同じエフェクトのラベルと前から順に対にするだけで、今の row の残りのラベルには関わらない。見える handler の並びは呼び出し先の row の `L` のラベルの並びで始まり、その後ろに外側の handler が残る。`mask` はない。末尾が推論用の変数の呼び出しは、型検査が包含を解いた後 ([型と Kind](types.md) の「呼び出しの包含を解く」)、次の3つのどれかになる。どの引数からもエフェクトが入らずに `<>` に閉じた末尾は、閉じた row と同じである。rigid な変数に決まった末尾は、rigid なときと同じく `mask` で保たれる。自由な変数のまま残った末尾 (今の row のラベルの型引数に現れる末尾や、REPL の `:type` で問い合わせた式の型に現れる末尾) は、今の row と単一化するので、余ったラベルはその変数が受け、呼び出し先の row の `L` の並びは今の row と同じになる。このときも `mask` はない。どの場合も、呼び出し先の中で、呼び出し先の具体化した row について不変条件が成り立つ。
- `handle`: 本体の row は、扱うエフェクトのラベルを今の row の先頭に足したものである。設けた handler は、そのエフェクトの見える handler の先頭になる。
- 節と `k` の呼び出し: `perform` は、handler まで yield してから節を呼ぶ。区間の中の `mask` の包みも継続に入り、`prompt$` が `evv` を handle の外側の `evv` に戻すので、節は handle の外側の row で動く。その場で動くすぐに再開する節も、何かを呼ぶなら入口が `evv` を handle の外側の `evv` に替えてから本体を動かすので (under)、同じ row で動く。何も呼ばない節は `evv` を読まないので、`perform` の場所の `evv` のままでも違いは見えない ([Core IR](core-ir.md) の「`perform` と節の3つの形」)。`k` の呼び出しの `mask` は、`k` の最後の矢印の row (handle の外側の row) を今の row に含めたときに、呼び出しと同じ規則で決まる。再開した区間の中から見ると、`k` の handler より外側は、呼び出し先から見た呼び出し元と同じ形になるので、呼び出しと同じ議論になる。`multi` の `k` を写して再開するときも、区間は同じなので同じである。
- extern のエフェクト (`IO`): handler は Prelude の `try_io` だけで、`io_failed` は外から名指せない。`IO` の失敗は row の上の位置でなく、実行の時点で最も近い `try_io` に届くと定める。そのため、row の中の `IO` の数は、どの handler に届くかに関わらない。extern のエフェクトは `mask` に入れず、row の中で重なったら1つにまとめる ([型と Kind](types.md) の「推論」)。
- extern のエフェクト (`Panic`): `IO` と同じく、`Panic` の失敗も row の上の位置でなく、実行の時点で最も近い `try_panic` に届くと定める。`try_io` は `IO` のラベルを残すが、`try_panic` は引数の関数の row から `Panic` を取り除く。これが健全なのは、どの `try_panic` も、その下で起きた `Panic` をすべて捕まえるためである。最も近い handler が捕まえ、`mask` は extern のエフェクトを飛ばさないので、`Panic` が `try_panic` の外へ出ることはない。

`mask` の `L` の項目が飛ばす m 個の handler は、不変条件により、その呼び出しの時点で見える別々の `L` の handler である。外側の `mask` が飛ばす handler は内側の点からは見えないので、同じ継続の上の別々の `mask` の項目が飛ばす handler も、互いに別々である。どの項目も1つ以上の handler を飛ばし、空の `mask` は包みを作らないので、継続の上で `mask` の包みが残すフレームの数は handler の数以下に収まる ([LIR](lir.md) の「`evv` の不変条件」)。
