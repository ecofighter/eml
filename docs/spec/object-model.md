# オブジェクトモデル

位置づけ: 規範。

VM とネイティブで共有するランタイム `eml_rt` の核と、その上に置く実行文脈 `Ctx` を定める。核は、語、物体 (ヘッダ、ペイロード、種類)、ページ単位の確保器と生存の列挙、局所と共有の参照カウント、`share`、`lin` ビット、核の操作、バイト列と文字列、凍結した領域、reuse の部品、検査モードから成る。核は物体の中身の種類をほとんど知らない。中身を知るのは `BigInt`、`Float`、`Foreign`、`String`、`Bytes` だけで、データとクロージャの物体の形 (下の「物体の形」) は VM が受け持つ。evidence の3つの物体の形は、`Ctx` の基本操作が受け持つ (下の「実行文脈 `Ctx`」)。`eml_extern` の表の関数の行は、`Ctx` の上に extern として置く (下の「extern」)。`eml_rt` を使うのは [VM](vm.md) で、`eml run` は VM で動く。

設計の基準は、実用的なプログラムで速いことである。関数型のプログラムで回数の多い経路は、多い順に次のとおりで、核はこの順に速さを優先する。

1. `dup` と `decref`。ほとんどの命令の周りに出る
2. 小さい物体の確保と解放。cons セル、タプル、`Some x` などの多くはすぐ死ぬ
3. `switch` のタグの読み出し
4. `tobj` の位置の `box` と `unbox`
5. Perceus の reuse (LIR の reuse のパスが入れる。[LIR](lir.md) の「reuse」)。一意の道で、確保と解放とヘッダの書き込みを省く

`share`、検査モード、生存の列挙、`Lin` の破棄処理は回数が少ないので、速さより単純さを優先する。形は Lean 4 と Koka のランタイムに近く、確保器は mimalloc の考え方を借りる。速さのために受け入れる制約は、下の「受け入れる制約」にまとめる。

`eml_rt` は vstd だけに依存する crate で、コードを Verus の `verus!` の中に書き、Verus が全体を検証する (下の「`unsafe` の核」)。検証 (Verus、単体テスト、Miri) は [テスト戦略](../implementation/testing.md) の「`eml_rt` の検証」に、命令の数の計測は [計測の基準](../implementation/benchmarks.md) にある。

## 語

- 値は 8 バイトの語 `Word` である。Rust ではポインタ型 (`*mut ()` を包む `#[repr(transparent)]` の型) で持つ。`u64` で持たないのは、Miri の strict provenance の下でポインタの出所を失わないためである。即値は `ptr::without_provenance_mut` で作り、ポインタの下位ビットの検査と書き換えは `addr` と `with_addr` で行う
- 下位ビットが 1 なら即値、0 ならヘッダを指すポインタである。物体は 8 バイトに揃えるので、ポインタの下位3ビットはいつも 0 になる
- 即値の値は、語を算術右シフトで1ビットずらした `i64` である。即値で表すものは次のとおりである
  - 63 ビットに収まる `Int` (`tobj` の位置の `box`)
  - `tobj` の位置の `enum` のタグ `#N`
  - `()`。値 0 の即値、つまり語の値 1 にする
  - 関数の値 `&f`。値は関数の番号で、クロージャの最初の語では上の 32 ビットに捕まえた値の数を詰める (下の「クロージャ」)
- `obj` と `tobj` の位置は、ポインタか即値の語である。`int`、`float`、`enum`、`unit` の変数とフィールドは、タグのない生の 64 ビットで持つ。`float` の生の値は `f64` のビット列である。`unit` の生の値も `()` の即値と同じ語の値 1 にする。[LIR](lir.md) の「値の表現」の「`unit` の値の機械の形は、`tobj` の即値 `()` と同じにする」を守るためである
- `Int` の意味は 64 ビットのまま変えない。`box` は、`Int` が 63 ビットに収まれば (`(n << 1) >> 1 == n`) 即値にし、収まらなければ種類 `BigInt` の物体を確保する。`unbox` は、即値なら右シフトし、物体なら `BigInt` の中身を読む。型変数の位置の `Int` は、総称のフィールドに入るたびに変換が要る。データの配置を一様に保つので ([Core IR](core-ir.md) の「変換の規則」)、この変換を即値にして安くする
- `enum` の `box` と `unbox` は、いつも即値のシフトである
- `&f` を即値にするのは、捕まえる値のない関数の値で確保しないためである。`apply` は、語が即値なら関数の番号を直接呼び、物体ならクロージャを呼ぶ
- `Word::from_bits` は、provenance を持たない語をビット列から作る。VM は、生の `int` と `enum` の値とフレームの見出しを `from_bits` でスロットの語にし、`bits()` で読む ([VM](vm.md) の「スロットとスタック」)。こうした語は即値やポインタに見えることがあるので、VM はコード生成が知っている Repr でだけ扱い、RC の操作と即値の判定には渡さない
- `Word` は `Send` と `Sync` を実装する (`unsafe impl`)。語は値で、スレッドをまたいでよいかは、型でなく RC の規約 (下の「`share`」) が守るためである。`CodeBase` が不死の定数の語を持って `Sync` になるにも、これが要る ([マルチコア対応の設計](../future/multicore.md) の「VM の並列化の備え」の制約2)。`Heap` は `Send` で `Sync` でない。worker ごとに1つ持ち、worker のスレッドに移せるようにするためである。どちらも型の assert で固定する

`Float` の語の表現は、上の `float` の生の値と、下の「種類」の `Float` の箱にある。クロージャの形は下の「物体の形」にある。

## ダミーの値

- EP のダミー (`prim dummy()`) は、`Heap` が作るときに1つ確保する不死の物体を指す語である (`Heap::dummy`)。種類は `BigInt` で、値は 0 である。静的な物体にしないのは、検査モードの前置き (下の「前置き」) を静的な物体のために特別扱いしないためである
- ダミーへの `dup` と `decref` は、rc が 0 (不死) なので速い道から外れ、何もしない。`unbox_int` と `unbox_float` は 0 を読む。速い道に、ダミーのための分岐を足さずに済む
- [LIR](lir.md) の「ダミーの値」の約束 (`dup`、`decref`、`drop` は何もしない、`unbox` は誤りにしない、`box` はダミーを受けたらダミーを返す) は、こうして守る。`box` が受けるのは生の `int`、`float`、`enum` で、そこでのダミーは `0`、`0.0`、`#0` なので、普通に box してよい
- ダミーは、検査モードの不死の物体の数え方 (下の「不死の物体の数え方」) の対象にしない。EP は、作っていないダミーを `drop` するためである

## 物体

物体は、ヘッダとペイロードが続く1つのブロックである。ポインタはヘッダの先頭を指す。

### ヘッダ

ヘッダは 8 バイトである。

```
rc:   i32         0 = 不死、正 = 局所、負 = 共有
meta: u32         tag (16 ビット) | scan (8 ビット) | info (8 ビット)
```

- `tag` はコンストラクタの添字である。データでない種類では、種類ごとに意味を決める (使わなければ 0)
- `scan` は、走査する語 (`obj` と `tobj` の値) の数である。0 から 254 はそのまま数を表す。255 は「数がペイロードにある」印で、そのときは走査の始まりの位置の生の1語が数を持ち、走査する語はその次から並ぶ。走査する語が 255 個以上の物体 (フィールドの多いデータ、EP の継続のクロージャが捕まえる多くの値) も、同じヘッダで扱うためである。継続のクロージャはコンパイラが作るので、数の上限をユーザーの誤りにできない
- `info` は、最上位のビットが `lin` ビット (下の「`lin` ビット」)、下位の4ビットが種類である。残りの3ビットは予約し、0 にする
- ヘッダを `rc` と `meta` の2つに分けるのは、reuse の書き込みを少なくするためである。確保は rc と `meta` の2つの欄を続けて書く。reuse でコンストラクタが変わるときは `meta` の 32 ビットの1回の store で済み、rc は 1 のままなので書かない。同じコンストラクタの reuse は、ヘッダに何も書かない
- `meta` は atomic でない。`meta` を書くのは、確保と、一意な箱の reuse と、解放と、一意な配列の `lin` ビットを変える `set_lin` (下の「配列」) と、一意な文字列とバイト列の種類を変える `set_body_kind` (下の「バイト列と文字列」の「変換」) だけである。どれも、ほかのスレッドがその物体を読めないときに起きる
- `rc` の欄は整数の型で持ち、atomic の読み書きは欄を受ける関数が `AtomicI32::from_ptr` を通して行う (下の「`unsafe` の核」の T2)。Verus は atomic の型の欄を扱わないためである。配置は `AtomicI32` と同じである
- ヘッダの大きさは、数字の 8 でなく `size_of::<Header>()` で書く。ヘッダの形を変えたときに、数え直す所を1か所にするためである
- 物体の大きさはヘッダに持たない。確保器のページが持つ (下の「確保器」)
- 型ごとの記述子の表は持たない。静的な型の情報なしに物体を扱うための方針 (子のたどり方、`Lin` の破棄処理) は、ヘッダの `scan` と種類と `lin` ビットで表し、解放とたどりはそれだけで済む。物体だけからは型と配置が分からない (配置の ID を持たず、型をまたぐ reuse でタグの意味も変わる) ので、リークの報告は種類の名前で数える。どの型のデータも `Data` と数える

### ペイロード

- ペイロードは、走査する語を並べ、その後に生の語を並べる。走査する語は、即値なら何もせず、ポインタなら子として RC とたどりの対象にする
- データの物体で、宣言の順のフィールドを走査する語と生の語に並べ替える規則を、物理的な形と呼ぶ。コンパイラのパス (LIR の reuse のパス) とランタイム (`CodeBase`) は、同じ規則を使わなければならない。reuse のパスは、物理的な語の数と物理的な位置で reuse の組を決めるためである
- 物理的な形は次のとおりである。フィールドのうち Repr が `obj` か `tobj` のもの (`Repr::is_rc`) を宣言の順に走査する語として並べ、その後に残り (`int`、`float`、`enum`、`unit`) を宣言の順に生の語として並べる。`unit` のフィールドも1語を取る。宣言で `()` を持つフィールドはまれなので、語を取らない3つ目の場合を作らない
- 規則を出す関数は `eml_lir` に置く。`Layout` から、宣言の位置ごとの物理的な位置と、走査する語と生の語の数を出す。`eml_rt` は tag、走査する語の数、生の語の数だけを受け、規則を知らない。規則を使うのは `CodeBase` を組み立てる側 (VM) と LIR の reuse のパスで、どちらも `eml_lir` に依存する。そのため規則は1か所にあり、結び付けのテストは要らない
- 関数は `LayoutCtor::shape` で、宣言の位置ごとの物理的な位置 (`positions`)、走査する語の数 (`scanned`)、生の語の数 (`raw`) を持つ `Shape` を返す。位置は、走査する語が 255 個以上のときの数の語 (上の「ヘッダ」) を数えない。VM のコード生成が `con`、`switch`、`unpack`、`release` の位置を決めるのに使う ([VM](vm.md) の「データとクロージャ」)
- extern が作るデータ (`Bool`、`Ordering`。下の「extern」) は、どれもタグだけなので、規則の関数を使わずに形が決まる

### 種類

種類は `info` の下位4ビットで、最大 16 種類である。種類ごとに次の欄を決める。欄は表を引かず、`Kind` の `match` で決める。種類を足すときに、どの欄も決め忘れないようにするためである。ただし破棄処理の欄は、箱を空けるたびに読むので、`Meta::has_finalizer` が種類のビットを `Foreign` の番号と直に比べる。`match` で種類に戻すと、種類を1つ足しただけで解放の多い計測の命令の数が数 % 増えたためである ([計測の基準](../implementation/benchmarks.md) の「破棄処理の判定」)。比べた結果が種類の欄と同じであることは、Verus が確かめる。

| 欄 | 意味 |
|---|---|
| 名前 | リークの報告の種類の名前 |
| 走査の始まり | 走査する語 (`scan` が 255 なら数の語) がペイロードの何語目から始まるか |
| token にできるか | reuse の token にしてよいか |
| 破棄処理 | 解放のときに呼ぶ処理があるか |
| ペイロードが不透明か | 核の操作から見て、ペイロードを語として読み書きできないか。`raw` と `set_raw` はこの欄で断る |

今ある種類は次の7つである。

| 種類 | 番号 | ペイロード | 走査の始まり | token | 破棄処理 | 不透明 |
|---|---|---|---|---|---|---|
| `Data` | 0 | フィールド | 0 | できる | なし | いいえ |
| `BigInt` | 1 | `i64` の1語 | 0 (`scan` は 0) | できない | なし | いいえ |
| `Foreign` | 2 | 破棄処理の表への `&'static` のポインタ、その後に Rust の値 | 0 (`scan` は 0) | できない | 表の `finalize` | 不透明 |
| `String` | 3 | 生の1語目にバイト長、その後に UTF-8 のバイト列 (下の「バイト列と文字列」) | 0 (`scan` は 0) | できない | なし | 不透明 |
| `Float` | 4 | `f64` のビット列の1語 | 0 (`scan` は 0) | できない | なし | いいえ |
| `Bytes` | 5 | 生の1語目にバイト長、その後にバイト列 (下の「バイト列と文字列」) | 0 (`scan` は 0) | できない | なし | 不透明 |
| `Free` | 15 | 空きリストの次のブロックへのポインタ | なし | できない | なし | いいえ |

- `Foreign` は、`FileIn` のように Rust の値を持つ物体である。`alloc_foreign::<T>(value, lin)` が、`T` ごとに1つの静的な表 (値の型を照らす `TypeId` を返す関数と、`drop_in_place::<T>` を呼ぶ破棄処理) を作って先頭に置く。`T` は `Send + 'static` で、揃えは 8 バイト以下に限る。後で別のスレッドが最後の参照を手放しても、破棄処理をそのスレッドで呼べるようにするためである ([マルチコア対応の設計](../future/multicore.md) の「スレッドに縛られたリソース」)
- `Foreign` の箱を空けるときは、表を読み、箱を先に死んだことにしてから破棄処理を呼び、その後でブロックを確保器に返す。破棄処理が panic しても同じ値を2回破棄せず、返した大きい物体のページを読まないためである。panic したときは、その箱が漏れる
- `Foreign` を token にしないのは、破棄処理を飛ばして別の物体に使い回すと、`Lin` の資源の後始末が漏れるためである。`BigInt` と `Float` は reuse のパスの対象にならないので、token にしない
- `String` と `Bytes` を token にしないのは、token の箱はいつも `Data` であるという性質を崩さないためである。`con_at` が書き直さない語の扱いは、この性質に頼る。reuse のパスも文字列とバイト列を対象にしない
- `Foreign`、`String`、`Bytes` のペイロードは不透明である。`Foreign` は Rust の値を持ち、`String` と `Bytes` の語は途中までしか書いていないことがある。`raw` で語として読むと未初期化のメモリを読み、`set_raw` で書くと不変条件が崩れる
- `Free` は、確保器が空いたブロックに付ける内部の種類である (下の「確保器」)。生きている物体がこの種類を持つことはない
- クロージャ、evidence の入口の表、evidence、`evv` の節点は種類を分けず、`Data` にする (下の「物体の形」)
- `Float` は `BigInt` と同じ形の1語の箱で、種類だけを分ける。検査モードの `unbox_int` と `unbox_float` が取り違えを `WrongKind` で断れるようにするためである。`Float` には `Int` の即値のような空きのビットがないので、`box` はいつも確保する (`alloc_float`)。値の語はビット列のまま書いて読み、浮動小数の算術をしないので、`-0.0` と NaN のペイロードもそのまま残る。生きている箱は値の語を書いてある。不変条件は `BigInt` と `Float` を1つの述語 (`Kind::boxes_value`) で扱う
- `unbox_float` は、`Float` の物体のほかにダミー (値 0 の `BigInt`) も受け、ビット列 0 (`0.0`) を返す。yield 中に返るダミーが `float` の位置で `unbox` されることがあるためである (上の「ダミーの値」、[LIR](lir.md) の「ダミーの値」)。検査モードは、ダミーでない `BigInt` を `WrongKind` で断る
- 後の項目の種類の見通しは次のとおりである。種類の数の上限 16 には余裕がある。`Array` と `MutArray` は種類を足さず、`Data` の形を使う (下の「配列」)

回復 (下の「回復」) は、根から届く物体を種類ごとに次のように写す。

| 種類 | 写し方 |
|---|---|
| 即値 | そのまま |
| rc が 0 の物体 | 古いヒープのダミーなら新しいヒープのダミーにする。凍結した領域の物体なら、語をそのまま使う。ヒープの不死の物体のうち、ダミーでないものは写せない (`Unrecoverable`) |
| `Data` | 子を写した後に、同じ tag、走査する語の数、容量で作り、生の語を写し、走査する語に子の新しい語を置く |
| `String` | 古いバイト列から `alloc_string` で作る。`alloc_string_room` が作った余りの容量は写さない |
| `Bytes` | 古いバイト列から `alloc_bytes` で作る。`alloc_bytes_room` が作った余りの容量は写さない |
| `BigInt` | 古い値から `alloc_int` で作る。値は 63 ビットに収まらないので、また `BigInt` になる |
| `Float` | 古いビット列から `alloc_float` で作る |
| `Foreign`、`lin` ビットの物体、token の箱、解放した物体、rc が負の物体 (共有) | 写せない (`Unrecoverable`) |

- `Data` の物体は生の語の数を持たないので、容量から走査する語 (と数の語) を引いた残りをすべて生の語として写す。前のコンストラクタの残りの語も写すが、走査しないので害はない。そのために、生の語はいつも書いてある (下の「確保と解放」)
- 種類を足すときは、その種類の写し方もこの表に決める。`Unr` の `Foreign` の種類を足すなら、写すか移す処理を、信頼する部分の新しい行と一緒に足す

## 物体の形

物体の種類ごとの tag とペイロードは次のとおりである。

| 物体 | 種類と tag | ペイロード |
|---|---|---|
| データ | `Data`、コンストラクタの添字 | 上の「ペイロード」の物理的な形 |
| クロージャ | `Data`、0 | 走査する語に [`&f` と捕まえた値の数の即値, 参照の引数...]、生の語に [ほかの引数...] |
| `evv` の節点 | `Data`、エフェクトの番号 + 1 | [evidence, next] |
| evidence | `Data`、エフェクトの番号 + 1 | [入口の表, 状態, 外側の `evv`] |
| 入口の表 | `Data`、0 | [入口のクロージャ...] |
| 文字列 | `String`、0 | 上の「種類」と下の「バイト列と文字列」 |
| バイト列 | `Bytes`、0 | 上の「種類」と下の「バイト列と文字列」 |
| `FileIn` | `Foreign`、`lin` ビットを立てる | 破棄処理の表と、Rust の値 `FileIn` (下の「extern」の「読み手」) |

### クロージャ

- 関数は、最初の走査する語に即値で置く。即値は走査で飛ばされるので、生の語に分ける必要がない。`apply` は即値か物体かを語で見分けるので (上の「語」)、クロージャに別の種類は要らない
- 捕まえた値と部分適用の引数は、呼ばれる関数の引数の Repr で持つ ([LIR](lir.md) の「関数の ABI」)。捕まえた値より後ろの引数は一様な Repr なので、VM が部分適用で足す引数は一様な語のまま写せばよい。並べ方はデータと同じく、Repr が `obj` か `tobj` の語を `&f` の後の走査する語に、ほかの語 (`int`、`float`、`enum` の生のビット列と `unit`) を生の語に、それぞれ関数の引数の順に置く。構造体の引数は葉の語に開いて並べる。並べ方は関数の `FnEntry` の引数の語の Repr の並びから決まるので、クロージャごとの記述子は要らない ([VM](vm.md) の「`CodeBase` と `FnEntry`」)
- 捕まえた値の数 k (開いた後の引数の語の単位) は、関数の番号と一緒に `&f` の即値に詰める (`f | k << 32`)。1回の読み込みで関数と数が分かり、クロージャの大きさも変わらない。関数の値 `&f` は k が 0 の場合である。tag は、検査モードが evidence とクロージャを見分けるのに使っているので使わない (下の「evidence の3つの物体」)。即値を読む所 (`apply`、`clause`、関数の番号の確かめ、逆アセンブラ) は、どれも数を除いて関数の番号を読む。検査モードの `apply` は、k から求めた参照の語の数が、クロージャの走査する語の数と合うことを確かめる
- VM は、関数と数を `scanned(w, 0)` で、参照の捕獲を `scanned(w, 1..)` で、ほかの捕獲を生の語で読む。`field(w, 0)` では読まない。走査する語が 255 個以上のクロージャ (EP の継続のクロージャがありうる) では、ペイロードの先頭に数の語があり、関数は `field(w, 1)` にあるためである。`apply` の場所ではクロージャの形が静的に分からないので、この規則を守る
- 共有されたクロージャの中身を使うとき (`apply` が中身を写す) のための別の操作 `copy` は作らない。VM が今ある部品を並べる。`is_last` なら捕獲を読んでから `free_block` し、そうでなければ参照の捕獲を `dup` してから `decref` する。捕獲は一時の列を通さず、クロージャから新しいフレームへ直に写す
- VM が実行時に作るクロージャ (部分適用で引数を足したもの) の `lin` ビットは、元のクロージャのビットを写す。元が即値の `&f` なら、ビットを立てない。クロージャの印は捕まえた値の印の結びで ([LIR](lir.md) の「Kind の印」)、足す引数は `apply` のオペランドなので `poly` である。`poly` はビットを立てる理由にならない
- クロージャは `Data` なので token にできるが、reuse の危険はない。クロージャを `release` する命令はなく、reuse のパスが token にするのは、`release` か、構築子が分かっている値の `decref` で手放すデータの箱だけであるためである ([LIR](lir.md) の「reuse の元」)

### evidence の3つの物体

- `evv` の節点の tag は、エフェクトの番号に 1 を足した値である。`ev_lookup` と `evv_mask` は、節点ごとに節点自身の `meta` の tag を比べるだけで済み、evidence の物体を読まない。`perform` のたびに、節点ごとの依存した読み込みが1回減る
- evidence の tag も、エフェクトの番号に 1 を足した値である。`evv_push` は、引数の evidence の tag を1回読んで節点の tag に写す。入口の表の tag は読まないので 0 にする。1 を足すのは、tag 0 の入口の表とクロージャから evidence を見分けて、検査モードが evidence の形を確かめられるようにするためである
- エフェクトの数の上限は、16 ビットの tag から 0 を除いた 65535 になる
- 関数の値 `&f` は関数の番号の即値なので (上の「語」)、関数 0 の値と `()` は同じ語である。そのため、入口の欄や κ の欄が空 (`()`) かを確かめる検査モードの確かめは、関数 0 の値が入った欄を空と見て、誤りを見逃しうる。空の欄を空でないと見ることはないので、正しい呼び出しを誤って断ることはない
- 3つの物体を別の種類にしない。速いモードの振る舞いは `Data` と同じで、分けて得られるのは、リークの報告の名前と検査モードの種類の検査だけだからである。リークの報告では、クロージャと evidence の物体も `Data` と数える
- `ev_set_state` と `ev_take_state` は、状態の欄を `set_field` でその場で書き換える。`set_field` の前提 (ほかのスレッドが読めない) は、シングルスレッドの VM では成り立つ。`par` で evidence を子のタスクに渡すなら、evidence を共有の印の付いた物体にしないか、状態の欄の書き換えを見直す。`par` の a1 の子は `evv` を空にして始めるので、evidence を子のタスクに渡さない (下の「実行文脈 `Ctx`」の「タスクの切り替え」)
- evidence は `CodeBase` の不死の定数にしない。空の `evv` は即値の `()` である

## 確保器

自前の確保器にする理由は次のとおりである。

- 大きさをページの頭から引けるので、ヘッダが 8 バイトに収まる
- 確保と解放が、空きリストの pop と push の数命令で済む。macOS の malloc は1回に数十 ns かかる
- Verus が確保器の経路も証明できる
- 生存の列挙が、ページを歩くだけで済み、別の台帳が要らない

### ページ

- 物体は、64 KiB に揃えたページから切り出す。ページは `std::alloc` から揃えを指定して取る。ページの先頭にページの頭 (大きさの級、ブロックの大きさ、ページの一覧の中の添字、まだ切り出していない残りの位置) を置く。物体のポインタの下位 16 ビットを落とせば (`with_addr`)、ページの頭が分かる。mimalloc と同じ方式で、ヘッダに大きさを持たずに済む
- 小さい物体の大きさの級は語の単位で決める。ブロックの語の数 (ヘッダを含み、検査モードの前置きを含む) が 2 語から 16 語 (16 B から 128 B) は1語刻み、その上は 20、24、28、32、40、48、56、64、80、96、112、128 語である。いちばん小さい級を 2 語にするのは、空いたブロックにヘッダと空きリストのポインタを置くためである
- 128 語を超える物体は大きい物体として、その物体だけの揃えたページに置く。ページの頭の形は同じで、解放の道もページの頭を読むところまでは同じである
- `alloc` と `con_at` は、ヘッダを含まないペイロードの語の数を受け取る。ヘッダの語の数を、呼ぶ側に数えさせないためである。級は、ヘッダとペイロードの語の数の和から決め、検査モードでは前置きの語の数も足す。ペイロードは少なくとも1語にする。空いたブロックのペイロードの先頭に、空きリストのポインタを置くためである。語の数の和やバイト数が `usize` を超える大きさは、どちらのモードでも panic にする。桁あふれが回ると小さいブロックを取り、安全な `alloc_data` がその先まで書いてしまうためである

### 確保と解放

- 確保器は級ごとに、空いたブロックの空きリスト (LIFO) と、今のページの切り出しの位置を持つ。確保は、空きリストから pop し、空なら今のページから切り出し、ページが尽きたら新しいページを取る
- 今のページの切り出しの位置は確保器の欄だけが正しく、速い道はその位置だけを進める。今のページを替えるときに、古いページの最後の位置をそのページの頭に書き戻す。ページを歩く処理 (生存の列挙、`Heap` を落とすとき) は、各級の今のページでは確保器の位置を、ほかのページではページの頭の位置を読む。まだ切り出していないメモリをブロックとして読まないためである
- 確保器は、取ったすべてのページの一覧を持つ。ページの頭は一覧の中の自分の添字を持ち、大きい物体のページを返すときは `swap_remove` で一覧から外し、移ってきたページの添字を書き直す。返すたびに一覧を探すと、大きくなっていく文字列を作るループが2乗の時間になるためである
- 解放は、ページの頭を読み、小さい物体のページなら、ブロックの `meta` を種類 `Free` にし、ペイロードの先頭の語に次のブロックへのポインタを書いて、その級の空きリストに push する。書き込みは2回で、ヘッダの後半とその次の語に書く。2つは続いた 12 バイトの中にあるので、ほとんどは同じキャッシュラインに入る。ヘッダが 64 バイトの境目の直前の語にあると (たとえば 3 語のブロックがページの先頭から 56 バイトの位置にあるとき)、2つのラインに分かれる。`Free` の印を書くのは、速いモードでもページを歩いて生きている物体を見分けられるようにするためである (下の「生存の列挙」)
- 大きい物体のページなら、解放したときにすぐ `std::alloc::dealloc` で返す。大きい物体を級の空きリストで使い回すことはないので、返さないと、大きくなっていく文字列や配列を作るループで使う量が限りなく増えるためである
- `alloc_data` は、走査する語の後ろから容量の終わりまでを 0 で埋める。ペイロードを呼ぶ側が書く `alloc` と `alloc_immortal` も、ペイロード全体を先に 0 で埋める。ヒープの不変条件は「解放していない `Data` のブロックのペイロードの語は、容量の終わりまですべて書いてある」を含む。`Data` の物体は生の語の数を持たないので、回復が生の語を容量の終わりまで写せるようにするためである (下の「回復」)。再使用 (`con_at`、`reuse_in_place`) は token の箱の語を書き直すだけなので、この不変条件を保つ
- 形の分かっている物体の解放 (`free_block`。下の「核の操作」) も同じ道を通る。ページの頭を読むのは、マスク1回と読み込み1回である
- 小さい物体のページは、実行中に OS へ返さない。ページは `Heap` を落としたときにまとめて返す
- ヒープは、使っているメモリのバイト数 (`bytes_in_use`) を両方のモードで数える。速いモードでは OS から取ったページのバイト数で、ページを取るときと返すときだけ数えるので、速い道の費用はない。検査モードでは、そこから隔離した (解放して使い回さない) ブロックのバイト数を引く
- 確保器は、ページを取るときと返すときに、そのバイト数をセッションの `Control` にも足し引きする (下の「実行文脈 `Ctx`」の「実行の制御」)。確保量の上限は、この数で確かめる。ページの単位でしか数えないので、速い道の費用はない
- `Control` の数は OS から取ったページの量なので、検査モードでは、隔離したブロックと前置きの分だけ速いモードより多くなる。上限は暴走するメモリを止めるための安全網で、厳密な会計ではないので、この違いは受け入れる。上限すれすれのプログラムは、モードによって止まったり止まらなかったりしうる

決めていないこと: 小さい物体のページを OS に返すこと、ページごとの空きリスト、別のスレッドからの解放 (ページの頭に持ち主を置く遠隔の空きリスト)。どれも VM の並列化かネイティブのランタイムで要る ([マルチコア対応の設計](../future/multicore.md) の「確定した設計判断」の 7)。

### 生存の列挙

- 生きている物体は、両方のモードでページを歩いて列挙できる (`live_objects`)。各ページの切り出したブロックのうち、速いモードでは種類が `Free` でないもの、検査モードでは前置きの状態が解放でないものが、生きている箱である
- `live_objects` は、テストと検査のための列挙である。回復 (下の「回復」) は生きている物体を列挙せず、根からたどって写す
- 回復は、根から届く語が古いヒープのブロックか凍結した領域の物体かを、そのブロックのページの頭で見分ける。ページの頭の `index` は持ち主のヒープのページの一覧の添字なので、古いヒープの一覧のその項がそのページなら古いヒープのブロックで、そうでなければ凍結した領域のブロックである。ヒープのページと凍結した領域のページは重ならないことが証明済みである。2つのモードで同じ見分け方をする
- `Heap` を落とすときは、ページを1枚ずつ歩いて、生きている `Foreign` の物体の破棄処理を呼んでから、すべてのページを返す。Rust の値が持つメモリを漏らさないためである。Miri は漏れを誤りにする。回復は古いヒープを落とすことで、届かない `Foreign` の物体を閉じる
- 回復と古いヒープの後始末は、ヒープ全体のブロックの一覧や集合を作らない。回復は確保量の上限で止まった直後にも走るので、古いヒープに比例するメモリを足すと、機械のメモリを使い切る前に止めるという上限の意味がなくなるためである

## 参照カウント

### 符号

- rc が 0 の物体は不死で、解放しない。`alloc_immortal` の物体、ダミー、凍結した領域の物体 (下の「凍結した領域」) がこれに当たる
- 正の rc n は、局所の物体の参照の数 n である。局所の rc は、Relaxed の load と store で読み書きする。aarch64 でも x86_64 でも、普通の読み込みと書き込みの命令になる
- 負の rc -n は、共有の物体の参照の数 n である。共有の rc は、atomic の加減算で読み書きする ([マルチコア対応の設計](../future/multicore.md) の「共有の印方式」)

### 局所の速い道

`dup` と `decref` の速い道は、比較1回で決める。

- `dup`: rc を符号なしで見て `rc - 1 < MAX - 1` なら、つまり rc が 1 以上 `MAX - 1` 以下なら、rc + 1 を書き戻す。それ以外 (不死、共有、上限) は遅い道に進む
- `decref`: rc が 2 以上 `MAX - 1` 以下 (同じく符号なしの比較1回) なら、rc - 1 を書き戻す。rc が 1 なら解放する。それ以外は遅い道に進む
- `tobj` の値には、この前に下位ビットの検査が1回入る。`obj` の値は、つねにポインタなので検査しない

### 上限

上限に達した数は動かさない (張り付き)。Perceus の論文と Lean と同じである。

- 局所の rc が `MAX` (`i32::MAX`) に達したら、その物体の数は動かさない。その物体は解放されずに残る。速い道の範囲から `MAX` を外してあるので、張り付いた数は速い道で動かない。局所の数は1つのスレッドだけが書くので、境目はちょうど `MAX` でよい
- 共有の側では、上限の判定と加減算の間に別のスレッドが割り込める。そこで境目を2つ置く (ヒステリシス)
  - `dup` は、rc が `DUP_LIMIT = MIN + 2^16` より小さければ数を動かさない
  - `decref` は、rc が `DROP_LIMIT = MIN + 2^17` より小さければ数を動かさない
- 境目を2つにする理由は次のとおりである。境目が1つだと、境目の外の値を読んだ `decref` が加算する前に、別のスレッドの `dup` が数を境目の中に入れ、さらに別の `dup` がそれを見て数えずに飛ばすことがある。その後に最初の `decref` が加算すると、数は境目の外に戻り、数えなかった参照の分だけ実際より少なくなる。2つの境目なら、`dup` を1回でも飛ばした物体の rc は `DUP_LIMIT` より小さい。それを `DROP_LIMIT` まで戻せるのは、rc が `DROP_LIMIT` 以上のうちに読んで、まだ加算していない `decref` だけである。その数は同時に動く worker の数より少ないので、worker が 2^16 未満なら、rc は `DROP_LIMIT` に戻らない。その後の `decref` はすべて飛ばされ、物体は解放されずに残る。数が実際より少なくなっても、参照が残っている物体を解放することはない
- 張り付いた物体は解放しないが、不死 (rc 0) には変えない。`share` が不死の物体でたどりを止めるので、張り付いた局所の物体を不死にすると、その子が共有の印なしに別のスレッドから届くためである

### 共有の側

- `dup` は、`DUP_LIMIT` 以上なら `fetch_sub(1, Relaxed)` で数を増やす (負の向きに進める)
- `decref` は、`DROP_LIMIT` 以上なら `fetch_add(1, AcqRel)` で数を減らし、古い値が -1 なら最後の参照なので解放する。`fence(Acquire)` は使わず、AcqRel の加算で最後の解放を順序付ける
- 解放の連鎖では、子を1つずつ、その子の rc の符号に合う側の `decref` で減らす。共有の物体の子は、共有か不死の物体か、`lin` ビットの立った局所の物体である (下の「`share`」)

### 遷移の関数

RC の遷移は、rc の値だけを受け取って次の状態を返す純粋な関数 (`dup_step`、`decref_step`、`mark_step`) にする。ヒープはそれを呼んで書き込むだけである。単体テストとヒープが同じ関数を使い、Verus がその関数を証明して ([テスト戦略](../implementation/testing.md) の「Verus」)、遷移の正しさを1か所で確かめるためである。共有の側の加減算そのもの (`rc_dup_shared`、`rc_decref_shared`) と `is_last` の読み込みは、rc の欄の権限を受ける T2 の関数にする (下の「`unsafe` の核」)。

## `share`

- `share(w, receiver)` は、送り手のスレッドが、値を公開する前に呼ぶ ([マルチコア対応の設計](../future/multicore.md) の「共有の印方式」)。w から届く物体を明示のスタックでたどり、局所の rc n を -n に変える。局所の上限 `MAX` は共有の上限 `MIN` に変える。-n が `DROP_LIMIT` より小さくなるときも `MIN` に変える
- すでに負の物体と不死の物体で、たどりを止める。不死の物体は、`lin` ビットが立っていても変えない。印を付けた物体はもう一度たどらないので、`lin` でない物体がたどられるのは高々1回である
- `lin` ビットの立った物体には印を付けず、所有者を `receiver` に移す。ただし、その子はたどり続ける。`Lin` の物体の中の `Unr` の子は、送り手がほかの所からも参照していることがあるためである。`Lin` の物体は rc が 1 なので、受け手は局所の物体としてそのまま使える
  - `lin` の物体は rc が 1 なので、正しいプログラムでは2回届かない。検査モードは、たどりで同じ `lin` の物体に2回届いたら誤りにする (訪れた `lin` の物体の集合を持つ)。すでに共有の側にある `lin` の物体に届いたときも誤りにする。速いモードは、正しいプログラムに頼る
  - 検査モードは、たどりで届いた物体が生きていなければ誤りにする
- `lin` ビットのない親の中に `lin` ビットの立った子があることは、ふつうに起きる。`poly` の印の `con` (`(a, FileIn)` の組の型は `poly` になる) と、EP の継続のクロージャ (印は捕まえた値の印の結び) は `lin` ビットを持たないが、中の `FileIn` はビットを持つ。このとき `share` の後は、共有の親から局所の `lin` の子が届く。そのため、共有の物体から届いてよいのは、共有か不死の物体か、`lin` ビットの立った局所の物体である
  - そうした親は、実際には `Lin` の値なので参照は1つで、所有も受け手に移っている。親の最後の参照を手放すのは受け手で、子の所有者の検査とも合う
  - 受け手がその親を手放すとき、親の rc は -1 である。-1 の物体は、参照が自分の1つだけなので、最後の参照として扱い、残すフィールドを `dup` せずに受け取る (下の「核の操作」の `is_last`)。残す `lin` の子を `dup` すると、正しいプログラムでも検査モードの誤りになるためである
- たどりのコードは、物体への読み書き (生存、rc、`lin` ビット、所有者、子) を `Graph` trait の裏に置いて書く。Verus が、たどりのコードを trait のメソッドの約束の上で、任意のグラフについて証明するためである ([テスト戦略](../implementation/testing.md) の「Verus」)。ヒープの上の実装も証明し、たどりの結果をヒープの抽象のモデルの遷移と結ぶ
- VM はシングルスレッドだが、`par` の fork と join は worker の数によらず印を付けるので ([マルチコア対応の設計](../future/multicore.md) の「`par` の印付け」)、この経路を通る。物理的なスレッドが1つの間、`receiver` は論理的な worker ID (下の「論理的な worker ID」) である。`par` はまだ実装していないので、今 `share` を呼ぶのは単体テストだけである

## `lin` ビット

- `info` の `lin` ビットは、検査モードに限らず常に持つ。`par` の fork で、印付けの代わりに所有者を移すのに使うためである ([マルチコア対応の設計](../future/multicore.md) の「`Lin` の物体の所有者の移し替え」)
- `alloc` と `con_at` は、呼ぶ側が渡す `meta` の `lin` ビットをそのまま書く。どの物体にビットを立てるかは、呼ぶ側が決める。`FileIn` などの extern の資源は作るときに立てる。`con` と `closure` は、Kind の印 ([LIR](lir.md) の「Kind の印」) が `lin` なら立て、`unr` と `poly` なら立てない
- `poly` のコードで作った `Lin` の物体はビットを持たないので、fork で共有になり、その場の書き換えができなくなる。安全の側に倒れるだけである
- `reuse_in_place` はヘッダを書かないので、箱の `lin` ビットがそのまま残る。ビットが欠けるのは安全の側である (`share` で印が付いて共有になり、その場の書き換えができなくなるだけ)。危ないのは、ビットが誤って残ることで、`Unr` の値の正しい `dup` を検査モードが誤りにする。印が `lin` の変数の箱がビットを持つとは限らない (`map Some files` のように、`poly` の `$con$Some` が作った箱が `lin` の変数に入る) が、印が `unr` の変数の箱はビットを持たない
- そのため、`reuse_in_place` を使ってよいのは、古い物体の印が `unr` のときか、新しい物体の印が `lin` のときである。それ以外は `con_at` で `meta` を書く。検査モードの照らし合わせも、`lin` ビットについては「箱がビットを持ち、新しい `meta` が持たない」ときだけを誤りにする
- `unpack` と case で得たフィールドの印は、配置の表から確かめられず、translate を信用する ([LIR](lir.md) の「Kind の印の検査」)。検査モードの `lin` ビットの誤り (下の「報告する誤り」) が、これを実行時に覆う

`FileIn` の物体は、`FileIn.open` が作るときにビットを立てる (下の「extern」の「読み手」)。

VM の `con` と `closure` は、束縛する変数の印が `lin` なら、`alloc_data` の `lin` を真にしてビットを立てる。`apply` の部分適用で作るクロージャは、元のクロージャのビットを写し、元が即値の関数の値なら立てない ([VM](vm.md) の「呼び出しと戻り」)。

## 核の操作

語を受ける操作は `unsafe fn` にする。条件は、Verus の `requires` に抽象のモデル (ブロックの状態、参照の数、語ごとの書き込みの状態) の言葉で書き、`# Safety` の文も同じ条件を指す。大きくは次のとおりである。速いモードはこれを確かめない。検査モードは、確かめられる違反を `Err` で返す (下の「検査モード」)。

- 語は即値か、生きている物体を指す。生きている物体とは、`meta` に合うペイロード (走査する語、`scan` が 255 なら数の語、`BigInt` と `Float` なら値、`String` と `Bytes` なら長さの語) をすべて書いた物体である。データの物体の生の語は、この条件に入らない
- 参照を消費する操作 (`decref`、`release`、`into_token` など) では、呼ぶ側がその参照を1つ持っている。読むだけの操作 (`field`、`raw`、`is_unique` など) では、呼ぶ側が参照を持っているか、生きている持ち主から借りている。Perceus の借りたフィールドと、基本操作の借用の引数がこれに当たる
- 物体は、同じ `Heap` が確保したものか、その `Heap` に付けた凍結した塊とその祖先の物体に限る (下の「凍結した領域」)
- rc が正の物体を書き換えるか、その rc を読んで判定する操作 (下の「報告する誤り」の `WrongOwner` に挙げた操作) では、物体の持ち主が今の worker である (下の「論理的な worker ID」)
- 構築中の物体 (`alloc`、`alloc_immortal`、`con_at`、`reuse_in_place` が返し、呼ぶ側がまだペイロードを書き終えていない物体) は一度に1つまでで、それに使えるのは `set_field` と `set_raw` だけである。ほかの操作は、構築中の物体が書き終えていることを前提にする

操作ごとの条件は次の表のとおりである。前提は、下の「検査モードの約束」の3種類 (安全の前提、モデルの前提、検査する前提) に分ける。速いモードは、表の下に挙げる2つ (`foreign` の照らし合わせと、`reuse_in_place` が空の token を断ること) を除いて、どれも確かめない。括弧の中は、検査する前提を破ったときに検査モードが返す誤りである。VM は、この表を守る命令の列を出す。

| 操作 | 安全の前提 | モデルの前提 | 検査する前提 (検査モードの `Err`) |
|---|---|---|---|
| どの操作も | 語は即値か、このヒープのブロックか、このヒープに付けた塊とその祖先のブロックである。構築中の物体は書き終えている (`set_field` と `set_raw` を除く) | 読むだけの操作の語は、モデルで生きている物体 (参照の数が正か、不死) を指す | 物体は生きている (`UseAfterFree`)。rc が正の物体を書き換えるか rc を読んで判定するなら、持ち主は今の worker である (`WrongOwner`) |
| 物体を受ける操作 (`meta`、`field`、`set_field`、`raw`、`set_raw`、`scanned_len`、`scanned`、`set_lin`、`free_block`、`release`、`release_reuse`、`into_token`、`foreign`、`foreign_unique`、`string`、`bytes`、`string_push`、`string_concat`) | 語はポインタである (即値でも `Word::EMPTY` でもない) | | |
| `alloc` / `alloc_immortal` / `con_at` | `meta` の種類は `Foreign`、`String`、`Bytes`、`Free` のどれでもない。`scan` は 255 でなく、走査する語はペイロードに収まる | | |
| `field` / `set_field` | | `set_field` が書く語は、呼ぶ側が数えた参照を持つ | i 語目は走査する語である (`OutOfBounds`)。`set_field` の物体は、ほかのスレッドが読めない (局所か、構築中。`NotWritable`) |
| `scanned` | | | i は `scanned_len` より小さい (`OutOfBounds`) |
| `raw` / `set_raw` | `raw` で読む語は先に書いてある。`alloc_data` は生の語を書かず、新しいページのメモリは初期化されていないためである | | 物体のペイロードは不透明でない (`WrongKind`。上の「種類」)。i 語目は、走査する語の後のブロックの中の語である (`OutOfBounds`)。`set_raw` の物体は、ほかのスレッドが読めない (`NotWritable`)。`alloc_immortal` で作る `BigInt` と `Float` の値の語も `set_raw` で書く |
| `unbox_int` | | | 物体は `BigInt` である (`WrongKind`) |
| `unbox_float` | | | 物体は `Float` かダミーである (`WrongKind`) |
| `dup` | | 呼ぶ側が参照を持つか、借りている | 物体は `lin` ビットを持たない (`LinDup`) |
| `decref` / `release` / `release_reuse` | | 呼ぶ側が参照を1つ持つ。残さない子は呼ぶ側の参照と数える | 不死の物体の参照は `acquire_immortal` か `dup` で作った (`ImmortalOverRelease`)。共有の物体は `lin` ビットを持たない (`LinShared`)。`release` と `release_reuse` の物体はデータで、tag と走査する語の数が名指したものである (`WrongLayout`)。残さない子は `decref` の、`is_last` が偽のときの残す子は `dup` の検査する前提を満たす |
| `acquire_immortal` | | | 物体は不死である (`NotImmortal`) |
| `foreign_unique` | 返すポインタを使うのは、この物体の参照を手放すか、ほかの参照を作るまでの間だけである | | rc が 1 である (`NotUnique`。共有の物体も断る) |
| `set_lin` | | 呼ぶ側が唯一の参照を持つ | 物体は `Data` である (`WrongKind`)。rc が 1 である (`NotUnique`。共有の物体も断る) |
| `free_block` | | 呼ぶ側が最後の参照を持ち、子の参照はもう処理してある | rc が 1 か -1 である (`NotLast`)。種類は破棄処理を持たない (`FinalizerSkipped`) |
| `into_token` | | 呼ぶ側が唯一の参照を持ち、子の参照はもう処理してある | token にできる種類である (`NotTokenable`)。rc が 1 である (`NotUnique`) |
| `con_at` / `reuse_in_place` / `drop_token` | | token の箱の「残した」語 (`con_at` と `reuse_in_place` で書き直さない語) の参照を呼ぶ側が持つ | token はまだ使っていない (`StaleToken`)。`con_at` の箱は `payload_words` の物体のこのモードでの級にある (`WrongClass`。同じ物理的な語の数の物体から作った token なら、どちらのモードでも満たす)。`reuse_in_place` の `meta` の tag、scan、種類は箱と同じで (`WrongMeta`)、箱が `lin` ビットを持つなら `meta` も持つ (`LinBitKept`) |
| `share` | | | 届く物体はどれも生きている (`UseAfterFree`)。局所の `lin` の物体には1回だけ届き (`LinReachedTwice`)、共有の側の `lin` の物体には届かない (`LinShared`) |
| `string` | 返す位置を読むのは、物体が生きていて、`string_push` か `string_concat` でその物体を書き換えていない間だけである | | 物体は `String` である (`WrongKind`) |
| `bytes` | 返す位置を読むのは、物体が生きていて、その物体を書き換えていない間だけである | | 物体は `Bytes` である (`WrongKind`) |
| `string_push` | `s` は left 自身の中身を指さない (下の「バイト列と文字列」) | 呼ぶ側が left の参照を1つ持つ | left は `String` である (`WrongKind`)。left は `decref` の検査する前提を満たす |
| `string_concat` | | 呼ぶ側が left と right の参照を1つずつ持つ (同じ物体なら2つ持つ) | 両辺は `String` である (`WrongKind`)。両辺は `decref` の検査する前提を満たし、同じ物体なら2回続けた `decref` の検査する前提を満たす |

戻り値は、どちらのモードでも `Result` である。速いモードの操作は、次の2つを除いて `Err` を作らない。

- `foreign` と `foreign_unique` は、物体の種類と値の型を、どちらのモードでも照らす。違えば `WrongKind` を返す。`foreign` の安全の条件は物体が生きていることだけで、違う型の値を指すポインタを返さないことは、この照らし合わせが受け持つためである
- `reuse_in_place` は、空の token を受けると `StaleToken` を返す。空の token には箱がなく、返す語がないためである

`Err` を作らない操作は、呼ぶ側に展開すれば、最適化で `Result` の分岐が消える。そのため、`dup` と `decref` は、局所の rc を書き換えるだけの速い道を `#[inline]` にし、残り (共有、不死、張り付いた数、検査モードの仕事) を、`#[cold]` と `#[inline(never)]` を付けた遅い道の関数に出す。速いモードの `decref` の速い道は、rc が 1 なら解放の連鎖を直に呼ぶ。解放の連鎖は `#[inline(never)]` にするが、一意な物体を空けることはよく起きるので、`#[cold]` にはしない。確保と箱の解放の速い道、`release`、`release_reuse`、`con_at`、`into_token`、`drop_token` と、語とヘッダの小さい関数も `#[inline]` にする。VM は `eml_rt` の外の crate なので、付けないと、総称でない関数は crate をまたぐ呼び出しになりうるためである。`Ctx::poll` が読む `Control::stop_bits` も、同じ理由で `#[inline]` にする。`field`、`set_field`、`meta`、`scanned`、`string_push` と、`string_push` の中で呼ぶ `push_unchecked` と、`release` と `release_reuse` の子の処理 (`release_children`) が呼ぶ `release_unkept` も `#[inline]` にする。総称な関数の実体は、使う側の crate のコード生成単位の1つにしかできず、ほかの単位からは展開できないためである ([計測の基準](../implementation/benchmarks.md) の「`eml_rt` のインライン化」)。確保器の遅い道 (ページを替えること、大きい物体の確保と返却) は `#[cold]` にする。`decref` の解放の道を選んだ計測は [計測の基準](../implementation/benchmarks.md) の「`decref` が一意な物体を空ける道」に、今の命令の数は同じ文書の「今の数値」にある。

ペイロードを呼ぶ側が書く `alloc` と `alloc_immortal` も `unsafe fn` である。`meta` の種類は `Foreign`、`String`、`Bytes`、`Free` のどれでもなく、`scan` は 255 でない。呼ぶ側は、ほかのヒープの操作の前に `meta` に合うペイロードを書く。`scan` が 255 の物体は走査する語の数をペイロードの先頭の数の語から読むので、数の語を書く前には、走査する語と生の語の境目が決まらない。走査する語が 255 個以上の物体は `alloc_data` で作る。ペイロードの形が正しいかは VM が受け持ち、確保のたびに実行時に確かめると速い道の費用になるためである。ペイロードを自分で書く `alloc_data`、`alloc_int`、`alloc_foreign`、`alloc_string`、`alloc_string_room`、`alloc_string_immortal`、`alloc_bytes`、`alloc_bytes_room`、`alloc_bytes_immortal` は安全な関数である。`String` と `Bytes` の物体を作れるのは、下の「バイト列と文字列」の操作だけである。

| 操作 | 動作 |
|---|---|
| `alloc(payload_words, meta)` | 級のブロックを取り、rc 1 と `meta` を書く。ペイロードは呼ぶ側が書く |
| `alloc_data(tag, scanned, raw, lin)` | データの物体を作る。走査する語が 255 個以上なら、ペイロードの先頭に数の語を置く。走査する語は `()` で埋めておく |
| `alloc_immortal(payload_words, meta)` | rc 0 で確保する |
| `acquire_immortal(w)` | 不死の物体の参照を1つ作る。速いモードでは何もしない (下の「不死の物体の数え方」) |
| `alloc_int(n)` / `unbox_int(w)` | 上の「語」の `box` と `unbox` |
| `alloc_foreign::<T>(value, lin)` / `foreign::<T>(w)` / `foreign_unique::<T>(w)` | `alloc_foreign` は種類 `Foreign` の物体を作り、`foreign` はその中の値へのポインタを返す。`foreign_unique` は、局所で rc が 1 の物体の値を、書き換えるために借りる。`Ctx::handle_read` が `FileIn` と標準入力のハンドルの読み手を進めるのに使う (下の「extern」と「読み手」) |
| `dup(w)` / `decref(w)` | 上の「参照カウント」。`decref` が 0 にした物体は、解放の連鎖に入れる |
| `is_unique(w)` | rc が 1 か。共有、不死、張り付いた数は、この1回の比較でみな偽になる。reuse とその場の書き換えに使う |
| `is_last(w)` | rc が 1 か -1 か。手放そうとしている参照が最後のものかを判定し、フィールドを `dup` せずに受け取ってよいかに使う。rc は Relaxed で読み、-1 のときだけ Acquire で読み直す。読み直しは同じ値を返し、最後の AcqRel の `decref` と同期する。ふだんの rc が 1 の道に、aarch64 の Acquire の読み込みの費用を足さないためである |
| `meta(w)` | ヘッダの `meta` を読む |
| `field(w, i)` / `set_field(w, i, v)` | ペイロードの物理的な i 語目を読み書きする。ヘッダを読まない。生の語の読み書き (`raw` / `set_raw`) も同じ添字で持つ。VM は形を静的に知っているので、`scan` が 255 かどうかで添字を直す必要がない |
| `scanned_len(w)` / `scanned(w, i)` | 走査する語の数と、その i 番目を読む。`scan` が 255 のときの数の語と、種類の走査の始まりを考える。形を知らない処理 (解放の連鎖、`share`、生存の列挙) が使う |
| `free_block(w)` | `is_last` が真で、子をすでに処理した物体の箱を空ける。ヘッダの `scan` を読まない。破棄処理を持つ種類には使えない |
| `into_token(w)` | 一意な物体の箱を、フィールドに触れずに token にする |
| `con_at(token, payload_words, meta)` | token が空でなければ、その箱に `meta` を書いて返す。空なら `alloc` する。どちらだったかも返す |
| `reuse_in_place(token, meta)` | 同じコンストラクタの reuse。ヘッダに何も書かずに箱を返す。`meta` は検査モードが照らすためだけに渡す |
| `drop_token(token)` | 使わなかった token の箱を空ける |
| `release(w, tag, keep)` | LIR の `release`。`is_last` が真なら、残さない子を手放して箱を空け、残す子は箱の参照を受け継ぐ。そうでなければ、残す子を `dup` してから w を手放す |
| `release_reuse(w, tag, keep)` | w が一意なら、残さない子を手放して箱を token にする。そうでなければ `release` と同じにして、空の token を返す |
| `share(w, receiver)` | 上の「`share`」 |
| `alloc_string(s)` / `alloc_string_room(room)` / `alloc_string_immortal(s)` / `string(w)` / `string_push(left, s)` / `string_concat(left, right)` | 下の「バイト列と文字列」 |
| `alloc_bytes(b)` / `alloc_bytes_room(room)` / `alloc_bytes_immortal(b)` / `bytes(w)` | 下の「バイト列と文字列」 |

- `con_at` で箱を使い回したときは、残したフィールドを書き直さなくてよい。呼ぶ側は、ほかのヒープの操作の前に、走査する語がみな `meta` に合う値を持つようにする
- LIR の `decref` と `drop` は、どちらも `decref` で実行する。実行時の動作も検査モードの規則も同じだからである。`unr` でない値に `decref` を出さない規則 (V1) は静的な検査で、実行時には区別しない
- `release` と `release_reuse` は、上の部品を組んだ一般の版である。VM は形の分かっている所では部品 (`is_unique`、`is_last`、`decref`、`free_block`、`into_token`) を直接並べ、一般の版は形の分からない所でだけ使う。Perceus の drop の特殊化と、Lean の reset/reuse の展開を、VM の命令の列で作れるようにするためである。形の分かっている `release` の展開は次のとおりである

  ```
  is_last(x)
    真: 残さない子を decref → free_block(x)
    偽: 残す子を dup → decref x
  ```

- 判定を `is_unique` と `is_last` の2つに分けるのは、上の「`share`」の、共有の親から `lin` の子が届く形のためである。rc -1 の物体は最後の参照なので、フィールドを `dup` せずに受け取ってよい (`is_last`)。しかし共有の印を持つので、reuse もその場の書き換えもしない (`is_unique` は偽)
- `keep` は、走査する語ごとに残すかどうかを持つ
- 解放の連鎖は、ヒープが持つ作業リストの `Vec` を使い回してたどる。再帰しないので Rust のスタックを溢れさせず、解放のたびに確保もしない。物体を解放するときは、子を走査の逆の順に1つずつ `decref` し、0 になった子を作業リストに積み、`Foreign` なら破棄処理を呼んでから箱を空ける。逆の順に積むのは、最初の走査する語を先に、最後の走査する語を後に解放するためである
- cons セル (`a :: List a`) の物理的な形は [要素, 残り] である (上の「ペイロード」)。要素を解放し終えてから残りに進むので、要素が物体のリスト (`List (Int, Int)` など) でも作業リストの長さは定数に収まる。この性質は、再帰するフィールドが最後の走査する語であるときに成り立つ。`data Snoc a = Nil | Snoc (Snoc a) a` のように再帰するフィールドが前にある型では、作業リストは長さに比例して伸びる。作業リストはヒープの `Vec` なので、伸びても Rust のスタックは溢れない

操作は、呼ぶ側が次の操作の前提を示せるように、次のことも約束する。中で証明した事実を外に出すだけで、実行するコードは変わらない。`Ctx` の基本操作 (下の「実行文脈 `Ctx`」) の証明は、これに頼る。

- `dup`、`decref`、`release`、`release_reuse`、`free_block` の後で生きているブロックは、前から生きていて、`meta`、走査する語と生の語、文字列のバイト列、rc の符号、持ち主 (rc が正のとき) を変えない (`kept_live`)。これがないと、途中の `decref` の後で、外の参照を持たないリストの後ろの節点や evidence の形について何も言えない
- 検査モードで状態を変える操作は、前に `word_in` だった語 (即値か、このヒープが受け付けるブロックを指す語) を、後も `word_in` に保つ。検査モードは解放したブロックを使い回さないためである
- `alloc_data` は、tag と `lin` ビットが引数のとおりで、走査する語がどれも `()` の物体を返す。前から生きているブロックは、同じブロックのまま生きている。検査モードでは、その物体の走査する語への `set_field` は `Ok` を返す

決めていないこと: `share` の後に、別の worker の `Heap` が持つ共有の物体 (rc < 0) を受け付ける形。凍結した領域と同じく、受け付けるブロックを広げて扱う。決めていない理由は、rc の並行の書き込みが要ることである ([ロードマップ](../future/roadmap.md) の「マルチコア対応」)。

## バイト列と文字列

文字列は種類 `String` の物体で、バイト列は種類 `Bytes` の物体である (上の「種類」)。2つは同じ形を持つ。ペイロードは、生の1語目にバイト長を持ち、その後にバイト列を持つ。バイト列は 8 バイトに揃った `slot_ptr(h, 1)` から始まる。走査する語はなく、容量の語、NUL、コードポイントの数は持たない。違いは不変条件だけで、文字列のバイト列は妥当な UTF-8 である。

`String` と `Bytes` は別の種類で、実行時に一方を他方として扱わない。`string` は `Bytes` を、`bytes` は `String` を受けず、検査モードは `WrongKind` を返し、速いモードは種類を前提にする。実行時の部分型にすると、ヒープの不変条件が種類で条件付きになり、どの操作も2つの種類を確かめることになるためである。

### 中身の不変条件

- 種類 `String` と `Bytes` の物体は、バイト長が容量以下である。`String` のバイト列は妥当な UTF-8 である。作れるのは下の文字列とバイト列の操作だけである
  - `alloc`、`alloc_immortal`、`con_at` は、安全の前提で種類 `String` と `Bytes` の `meta` を断る (`Foreign` と `Free` と同じ)。`reuse_in_place` は箱と同じ種類の `meta` しか受けず、token の箱は `Data` なので、断る必要がない
  - `raw` と `set_raw` は、不透明なペイロードを断る (上の「種類」)。速いモードでは前提にし、検査モードは `WrongKind` を返す
  - `release` と `release_reuse` はデータだけを受ける (`WrongLayout`)
  - 構築中の物体は `String` でも `Bytes` でもない。構築中の物体を作る道 (`alloc`、`alloc_immortal`、`con_at`、`reuse_in_place`) は、どれもこの2つの種類を受けないためである
- 2つの種類のバイト列はどちらも Verus の ghost の値としてブロックの権限に持つ。述語 (`holds_body`) と ghost のバイト列は1つで、種類が追加の不変条件を決める。メモリのバイト列はこの ghost のバイト列に等しい (下の「`unsafe` の核」の T10)。バイト長はその長さに等しく、容量以下である。文字列のバイト列が UTF-8 であることは vstd の `valid_utf8` で書き、連結で保たれることを `valid_utf8_concat` で示す。そのため、UTF-8 であることは信頼の一覧に入れず、Verus が確かめる
- ghost のバイト列は、隠した欄を持つ型にし、`meta.rs` の外では作れない。列を変えるのは、確保のたびに列を空にする処理 (`alloc_header` が、手渡すどのブロックにも行う)、列を前の部分に縮める `truncate_text`、T10 の書き込みの関数だけである。使い回したブロックに前の物体の列が残らないように、確保で空にする。`truncate_text` は、`Bytes.truncate` がその場で長さの語だけを書くときに使う (下の「バイト列の操作」)。メモリの前の部分は列のその部分に等しいままなので、T10 の約束は崩れない
- この条件は、速いモードの不変条件 (`full`)、検査モードの不変条件 (`safe_wf`)、ブロックの形の条件のすべてに置く。`BigInt` の値の条件と同じ場所である。速いモードの `string` と `bytes` が範囲の中を読むことの証明にも要るためである。`set_field` が `String` と `Bytes` の物体の走査する語の数 0 を保つことも、同じ条件で示す。UTF-8 の条件は、種類が `String` のときだけ置く
- 容量は、ブロックのペイロードの語の数から長さの1語を引いたバイト数である。大きい物体も、ページの頭のブロックの大きさから同じ式で出る。検査モードでは前置きの分だけ容量が1語小さくなることがあるので、テストは期待値を容量から求める

### 文字列の操作

| 操作 | 動作 |
|---|---|
| `alloc_string(s: &str) -> Word` | 安全な関数。`s` を写した文字列を作る。容量は級の大きさまで |
| `alloc_string_room(room: usize) -> Word` | 安全な関数。容量が `room` バイト以上の空の文字列を作る。`String.show` が、先に数えた結果の長さで1回だけ確保するのに使う (下の「extern」) |
| `alloc_string_immortal(s: &str) -> Word` | 安全な関数。rc 0 の不死の物体として作る。凍結した領域の文字列の定数を作るのに使う (下の「凍結した領域」)。`alloc_immortal` が `String` を断るので、別に持つ |
| `string(w) -> Result<*const str, HeapError>` | `unsafe fn`。中身の位置を返す。`foreign` と同じく生のポインタにし、ヒープの借用に縛らない。指す先は、w の物体が生きていて、`string_push` か `string_concat` でその物体を書き換えていない間だけ読める |
| `string_push(left, s: &str) -> Result<Word, HeapError>` | `unsafe fn`。left の参照を受け取り、`s` を後ろに足した文字列の参照を返す |
| `string_concat(left, right) -> Result<Word, HeapError>` | `unsafe fn`。`++` そのもの。両辺の参照を受け取り、結果の参照を返す。`string_push(left, string(right))` の後に right を `decref` するのと同じ結果になる |

`string_push` の動作は次のとおりである。

```
left が一意 (is_unique)
  容量が足りる → その場で s を書き、長さを書き換える
  足りない     → max(必要量, 2 × 容量) で確保し、left と s を写してから、left の箱を free_block
そうでない (共有、不死) → 和の長さで確保し、left と s を写してから、left を decref
```

- 文字列のバイトを書くのは、作るときと後ろに足すときだけである。`string_concat` は `string_push` と同じ道で右辺を写し、`String.show` と `String.slice` も同じ道でその場に足す (下の「extern」)。バイトを書く信頼の関数を1つにするためである。後で Rust の側の `&str` を足す extern を入れるときも、`string_push` を使えば余分な写しが要らない
- `s` は、ほかの文字列の物体の中身を指してよい。その物体は呼び出しの間生きている。写すのは left を手放す前である。速いモードでは、大きい物体のページを `free_block` がすぐに返すためである
- `s` は left 自身の中身を指さない。一意な left を作り直すと、`string_push` の中で left の箱を空け、大きい物体ならページも返す。引数の `&str` が指すメモリを呼び出しの間に返すと、写した後でも未定義の動作になる。自分自身との連結は、`dup` してから `string_concat(x, x)` で行う。`string_concat` の右辺は `&str` の引数でなく、写す直前にヒープの権限から借りるので、この制約を受けない。`x ++ x` は `dup` で rc が 2 になって届くので、写す枝に進む
- 容量を読むのは、left が一意なときだけである。共有と不死の left (凍結した領域のリテラルを含む) は容量を使わないためである。そのため、速いモードの操作は rc 0 の物体のページの頭を読まない。ネイティブの静的なデータにはページの頭がないので、この性質を約束にする (下の「凍結した領域」)
- 容量を倍にするので、一意な左辺に足していくループは、ならすと右辺の長さに比例する時間で済む
- 和の長さと倍の容量は `checked_add` と `checked_mul` で求め、桁あふれは今の確保と同じく panic にする (T5)
- 検査モードの誤りは、語を受ける操作の共通の誤り (`UseAfterFree`、`WrongOwner`)、種類が `String` でないときの `WrongKind`、数が 0 の不死の物体の手放し (`ImmortalOverRelease`) である。どの誤りも最初の確保より前に返すので、`Err` のときヒープは変わらない。文字列は子を持たないので、left と right の `decref` の誤りをすべて先に確かめられる。left と right が同じ物体で rc が 1 のとき (参照を2つ持つという前提を破った呼び出し) も、2回の `decref` を続けて確かめるので、ここで断る。後の手放しは、先に確かめたので誤りにならない
- モデルが合っていて前提がすべて成り立つときの結果は、`decref` と同じく、`Ok` か、モデルが照らさない誤り (下の「検査モードの約束」) である。モデルは不死の物体の外の参照の数を持たないので、不死の left の `ImmortalOverRelease` はモデルの前提の下でも返りうる
- extern の比較、`++`、`println` は、文字列を借りて読むか、`string_concat` を使う。足した核の操作は、`String.show` が結果を1回で確保するための `alloc_string_room` だけである。`String.show` の区間の写しは、写す元の文字列を借りた `&str` を vstd の `str::split_at` で切って渡すので、T10 に関数を足さない (下の「extern」)
- `String.push` (`Ctx::string_push_char`) は、`Char` の UTF-8 を4バイトの作業領域に書き、その `&str` を `string_push` に渡す。そのため、一意な文字列は容量が足りればその場で伸び、足りなければ上の動作のとおり作り直す。作業領域は left の中身を指さないので、`string_push` の前提を満たす。検査モードの写したバイトの数え方は `Bytes.push` と同じで、一意なら足したバイトだけ、共有なら left の長さも数える
- `String.char_at` (`Ctx::string_char_at`) は、文字列を借りて位置の1文字を読むだけで、物体を書き換えない (下の「extern」)

### バイト列の操作

| 操作 | 動作 |
|---|---|
| `alloc_bytes(b: &[u8]) -> Word` | 安全な関数。`b` を写したバイト列を作る。容量は級の大きさまで |
| `alloc_bytes_room(room: usize) -> Word` | 安全な関数。容量が `room` バイト以上の空のバイト列を作る |
| `alloc_bytes_immortal(b: &[u8]) -> Word` | 安全な関数。rc 0 の不死の物体として作る。`freeze` はこの物体を受ける |
| `bytes(w) -> Result<*const [u8], HeapError>` | `unsafe fn`。中身の位置を返す。`string` と同じく生のポインタにする。指す先は、w の物体が生きていて、その物体を書き換えていない間だけ読める |
| `bytes_extend(left, b: &[u8]) -> Result<Word, HeapError>` | `unsafe fn`。`string_push` のバイト列の版で、動作も約束も同じである。`b` は left 自身の中身を指さない |

- バイト列は文字列と同じ道で作り、中身を写すのも文字列と同じ T10 の `write_bytes` である
- バイト列を書き換える extern (下の「extern」) は、文字列の操作と同じ本体を種類 `Bytes` で使う。`Bytes.append` は `string_concat` と同じ本体で、`Bytes.push` は1バイトの `bytes_extend` である。検査モードの誤りも文字列の操作と同じで、種類が `Bytes` でなければ `WrongKind` を返す。どの誤りも最初の確保より前に返すので、`Err` のときヒープは変わらない
- `Bytes.make n b` は、確保の前に `n` を確かめる。負なら `Index` の誤り (`bytes length <n> is negative`)、`Limits::max_bytes` を超えるなら `Stopped(MemoryLimit)` を返す (`Array.make` と同じ)。`Bytes.get` は借りた物体の位置を読み、`Bytes.set` は一意ならその位置の1バイトだけを `write_byte` で書き換え、一意でなければ写してから書き換える
- `Bytes.truncate` は、left が一意ならその場で長さの語だけを書き、容量を保つ。ghost のバイト列は `truncate_text` で縮める (上の「中身の不変条件」)。一意でなければ、前の部分を新しいバイト列に写して left を `decref` する
- `Bytes.set` は、left が一意ならその場で T10 の `write_byte` で1バイトを書き換える。一意でなければ、写してから書く
- `Bytes.append_slice` (`Ctx::bytes_append_part(from, to, src, dst)`) は dst の参照を受け取り、src を借りる。dst が一意ならその場で src の範囲を足す。src と dst が同じ物体なら、呼ぶ側は借りる分と消費する分の参照を2つ持つので ([LIR](lir.md) の「extern の借用」)、dst は一意でなく写す枝に進む。そのため、T10 の写す元と写す先は重ならない。検査モードはこの前提を確かめ、同じ物体で rc が 1 なら `NotUnique` を返す。速いモードでは前提にする
- 容量は文字列と同じ式で、ページの頭のブロックの大きさから出す
- `Bytes` の物体は `lin` ビットを立てず、token にもならない (上の「種類」)

### 変換

`String` と `Bytes` の変換は、どちらも引数の参照を受け取る。引数が一意 (rc 1 の局所の物体) なら、`meta` の種類だけをその場で書き換えて同じ語を返す。そうでなければ、中身を新しい物体に写し、引数の参照を手放す。

| 操作 | 動作 |
|---|---|
| `bytes_of_string(s) -> Result<Word, Fault>` | `Bytes.of_string`。`s` の参照を受け取り、同じバイトのバイト列を返す。`s` が一意なら種類を `Bytes` に書き換えて `s` を返す。リテラルと共有の文字列は写す |
| `bytes_valid_utf8(b) -> Result<i64, Fault>` | `b` を借りて、T5 の `utf8_valid` で確かめる。妥当なら真、そうでなければ偽を返す。何も作らず、手放さない。これを呼ぶ extern の行はない |
| `string_decode(b) -> Result<Word, Fault>` | `String.decode`。`b` の参照を受け取り、T5 の `utf8_valid` で確かめる。妥当なら同じバイトの文字列を返す。`b` が一意なら種類を `String` に書き換えて `b` を返し、そうでなければ写す。妥当でなければ何も作らずに `b` を手放し、最初の妥当でない位置を持つ `Fault::Utf8 { at }` を返す |

- 写したバイトは `string_bytes_copied` に数える。一意な引数と妥当でないバイト列は何も写さないので数えない (下の「仕事の回数」)
- 種類を書き換えるのは `Heap::set_body_kind` で、`meta` の種類のビットだけを書く。tag、scan、`lin` ビット、rc、長さの語、バイト列、容量は変えない。`String` と `Bytes` は同じ形で、種類で違うのは `String` の UTF-8 の条件だけである。そのため `String` にするのは、`decode` が `utf8_valid` で確かめた後だけである
- 一意な物体はほかの物体から辺で指されず、ほかのスレッドも読めない。そのため、種類を変えても、`evv` のリストと evidence の形や、`Ctx` の持つ語の条件は崩れない。Verus はこの変化を、`evolved_by` の代わりに `evolved_kind` (`a` だけは `meta` の種類も変わってよい変化) で書いて証明する。`set_lin` の `evolved_lin` (下の「配列」) と同じ形である
- 検査モードの誤りは、種類が違うときの `WrongKind` と、`decref` の誤り (`UseAfterFree` など) である。どちらも最初の確保より前に返すので、`Err` のときヒープは変わらない。`Utf8` を返すときは `b` の参照だけを手放している
- `string_decode` は、確かめた全体を `String` の物体に足すか、確かめた物体の種類を `String` にする。どちらも妥当な UTF-8 にだけ行うので、`String` の不変条件は保たれる

## 配列

`Array a` と `MutArray a` は同じ形の物体である。tag 0 の `Data` で、要素を走査する語として順に並べ、生の語は持たない。要素が 255 個以上なら、ほかの `Data` と同じく数の語を先に置く (上の「ヘッダ」)。要素の位置は一様な位置なので、`Int` は即値で、`Float` は箱で入る。`MutArray` の物体は `lin` ビットを持つ。種類を分けないので、回復は `lin` ビットのない配列を `Data` として写し、`MutArray` を `lin` ビットの物体として断る (上の「種類」の回復の表)。

配列の extern は `Ctx` のメソッドである (`heap/ctx/arrays.rs`)。

| メソッド | 引数の所有 | 動作 |
|---|---|---|
| `array_make(n, x, lin)` | `x` を消費する | どの要素も `x` の、長さ `n` の新しい配列を返す。要素ごとに `x` を `dup` し、最後の要素には受け取った参照を入れる。`n` が 0 なら `x` を手放し、負なら `x` を手放して `Index` を返す |
| `array_empty(lin)` | | 長さ 0 の新しい配列を返す |
| `array_length(a)` | `a` を借りる | 長さを返す |
| `array_get(a, i)` | `a` を借りる | i 番目の要素を `dup` して返す |
| `array_set(a, i, x)` | `a` と `x` を消費する | i 番目を `x` にした配列を返す。`a` が一意 (`is_unique`) なら、その場で書き換えて `a` を返し、前の要素を手放す。一意でなければ、要素を `dup` して新しい物体に写し、`a` を手放す。写しは `a` の `lin` ビットを引き継ぐ |
| `array_freeze(m)` / `array_thaw(a)` | 消費する | `lin` ビットを下ろすか立てた配列を返す。一意なら `set_lin` でその場で変え、同じ語を返す。一意でなければ、要素を `dup` して写した物体にビットを付け、元を手放す |

- 添字が範囲の外なら、`get` は何も変えずに、`set` は `a` と `x` を手放してから、`Fault::Index` を返す。範囲と長さは、確保より前に確かめる
- `make` の長さは利用者が決めるので、確保より前に大きさも確かめる。確保器が作れる語の数 (2^32 未満) に収まらない長さと、今の確保量に足すと上限 (`Limits::max_bytes`) を超える長さには、何も確保せずに `x` を手放して `Fault::Stopped(Stop::MemoryLimit)` を返す。確保器に任せると、プロセスが panic で落ちるか、上限を報告する前に OS に止められるためである。上限との比べ方は、`FileIn` の読みが確保を試す前に止めるのと同じである。物体全体のバイト数をページ単位で数える `bytes()` と比べるので、この確かめは早めの断りであり、確保器自身のページの勘定と停止はそのあとにも働く
- `MutArray` はいつも一意なので、共有の物体の `freeze` は型の誤りである。検査モードは `NotUnique` で断り、速いモードは写す。速いモードが写すのは、VM が確かめられない前提 (一意であること) をメソッドに置かないためである
- `set_lin` は、一意な物体の `meta` の `lin` ビットだけを書き換え、tag、scan、種類、rc は変えない。一意な物体はほかの物体から辺で指されず、ほかのスレッドも読めない。そのため、ビットを変えても、`evv` のリストと evidence の形や、`Ctx` の持つ語の条件は崩れない。Verus はこの変化を、`evolved_by` の代わりに `evolved_lin` (`a` だけは `meta` の `lin` ビットも変わってよい変化) で書いて証明する
- 写しも書き換えも語の単位なので、信頼の一覧に行を足さない
- `var` の配列の変数を取り出した後の状態は、VM が凍結した領域に1つだけ置く、`lin` ビットを立てた長さ 0 の配列である (下の「凍結した領域」)。`alloc_immortal` は `lin` ビットのある `Data` を作れ、凍結は参照の数が 0 の物体を受け付けるので、このために `eml_rt` に足すものはない。長さが 0 なので、添字を確かめてから読み書きする `var` の節はこの物体を書き換えない ([Core IR](core-ir.md) の「`var` の変換」)

## 凍結した領域

不死の定数 (文字列リテラル、即値に収まらない `Int` の定数、`var` の配列の変数が取り出された後に持つ空の `MutArray`、それらを指すデータ) は、どのヒープにも属さない凍結した領域に置く。どのヒープも、領域の定数を指す語を受け付ける。定数を共有の領域に置く理由は次のとおりである。

- ネイティブ化では、文字列リテラルは、バイナリの読み出し専用のデータに置いた rc 0 の物体にするのが自然である (Lean、Koka と同じ)。どのヒープにも属さない物体なので、ヒープの操作は、自分のページにない rc 0 の物体を受け付ける必要がある
- `share` は不死の物体でたどりを止めるので、`par` で値を別の worker に渡すと、受け手は渡し手のヒープの不死の物体を指す語を受け取る。自分のヒープにない不死の物体を受け付ける条件は、いずれ要る
- `Ctx` ごとに定数を作る案は採らない。ネイティブ化で静的なデータの形に作り直すことになり、リテラルを使うたびに表を1回引く手間も残るためである

### 塊の鎖

- 領域は、凍結した塊 `Frozen<M>` の鎖である。塊は、親の塊への `Option<Arc<Frozen<M>>>` を持つ。親は、塊を作ったヒープに付けていた塊である
- 塊の物体の走査する語は、即値か、その塊か祖先の塊のブロックを指す。祖先は子の持つ `Arc` が生かすので、塊が生きている間は、指す先も生きている
- ヒープが付けるのは、鎖の先頭の塊1つである。ヒープは、付けた塊とその祖先のブロックを指す語を受け付ける (上の「核の操作」の「どの操作も」の行)
- REPL では、新しい定数を持つ入力ごとに、`Machine::load` が新しい塊を作って鎖を伸ばし、実行のヒープの塊を先頭の塊に替える ([VM](vm.md) の「追記」)
- 塊は、使う大きさの級ごとに少なくとも1ページ (64 KiB) を持つ。入力ごとに塊を作ると、使うメモリは入力の数に比例して増える。定数をまとめて凍結するか、後で凍結のときに詰め直すことで抑える ([ロードマップ](../future/roadmap.md) の「REPL」)

| 操作 | 動作 |
|---|---|
| `Heap<M>::freeze(self) -> Result<Frozen<M>, HeapError>` | ヒープを、付けていた塊を親とする新しい塊にする |
| `Heap<M>::attach(&mut self, region: Arc<Frozen<M>>)` | 付けている塊を、その子孫の塊 `region` に替える。何も付けていなければ、そのまま付ける。子孫でなければ panic する |

### 作る

- 塊を作るヒープ (作り手) は、普通の `Heap<M>` である。定数は `alloc_string_immortal` と `alloc_immortal` (と `set_field`、`set_raw`) で作る。作り手のための別の型は作らない
- 作り手は、前の塊を付けていてよい。後から足す定数が、前の塊の定数を指せるようにするためである
- VM のコード生成 (`CodeBase::load`) は、新しい文字列のリテラルと即値に収まらない `box` の定数を、`Heap::with_control` で作って今の先頭の塊を付けた作業用のヒープに不死の物体として作り、`freeze` で1つの塊にする。実行のヒープは、`attach` でその塊に付け替える。塊の物体は検査モードでも数えないので (下の「検査モードでは数えない」)、VM は定数を読むときに `acquire_immortal` を呼ばず、語を写すだけにする ([VM](vm.md) の「`CodeBase` と `FnEntry`」)

### 凍結する

- `freeze` は、構築中の物体を書き終えさせてから、どちらのモードでも実行時に次を確かめる。凍結はまれなので、速さより単純さを優先する
  - 生きている箱 (検査モードの解放したブロックを除く) は、どれも rc 0 で、`Foreign` でない。token の箱と `Foreign` の物体は rc 1 なので rc で断られるが、`Foreign` は種類でも断る。塊は値を複数のスレッドから読ませるが、`Foreign` の値は `Send` しか求めないためである
  - 検査モードでは、どの箱も前置きの状態が生存 (token でも空ける途中でもない) で、走査する語の行き先も生存の状態である
- 断るときの誤りは、下の「報告する誤り」にある。誤りなら `Err` を返し、作り手のヒープは普通に落ちる
- 走査する語がどこを指すかは、これ以上確かめない。どのブロックも rc 0 なので、自分のブロックを指す語は rc 0 の物体を指し、ほかの語は即値か、付けていた塊とその祖先のブロックを指すためである
- 検査モードでは、前置きの1つ目の欄をどれも数えない印 `UNCOUNTED` にする (下の「検査モードでは数えない」)
- 通れば、ページと、生きているブロックの権限と、ページの頭の読む権限を塊に移す。作り手のヒープは、中身を空の中身と入れ替えてから落とす
- 塊は型の引数 `M` を持つので、前置きの形はいつも、付けるヒープのモードと合う

### 付ける

- `attach` は、`region` の親を順にたどり、今付けている塊が `region` かその祖先であることを、`Arc` の番地を比べて実行時に確かめる。2つの塊のブロックが重ならないことを示せるのは、鎖でつながる塊だけだからである。子の塊のブロックは作り手のヒープが確保したので、作り手が付けていた塊のブロックと重ならない
- ヒープ自身のブロックと付けた塊のブロックが重ならないことは、付けるときにヒープの権限と塊の権限から示す。その後の確保でも、新しいブロックと塊の権限から同じことを示す
- 付け替えても、前の塊は新しい塊の鎖が生かすので、ヒープの物体は前の塊の定数を指し続けてよい

### 寿命

- ヒープは、付けた塊の `Arc` を持つ。`Heap` を落とすときは、生きている物体の後始末の後で `Arc` を手放す
- 最後の `Arc` を落とすと、`Frozen` の `Drop` がページを返す。親への `Arc` は、再帰せずにループで手放す。長い鎖でもスタックを溢れさせないためである (下の「`unsafe` の核」の T4)

### スレッドの性質

- `Frozen<M>` は `Send` と `Sync` である。型の assert で固定する。凍結した後は、どの操作も塊のメモリに書き込まないので、複数のスレッドが同時に読んでも安全である (下の「`unsafe` の核」の T0)
- 書き込まないことは、操作ごとに次のように守る。速いモードの `dup` と `decref` は rc 0 を読んで何もせず、`share` と解放の連鎖も rc 0 の物体に書き込まない。`set_field` と `set_raw` は、ほかのスレッドが読めない物体 (局所か、構築中) にだけ書く。速いモードではこれを前提にし、検査モードは塊の物体への書き込みを `NotWritable` で断る。`string_push` は、不死の left を写す道に進む。検査モードも、下の「検査モードでは数えない」により書き込まない
- 速いモードの操作は、rc 0 の物体のページの頭を読まない (上の「バイト列と文字列」)。検査モードの範囲の確かめは、領域のブロックでもページの頭を読むので、塊はページの頭の読む権限も持つ
- [マルチコア対応の設計](../future/multicore.md) の「VM の並列化の備え」の制約2 (`CodeBase` は `Sync`) は、この性質に頼る

### 検査モードでは数えない

- 領域の物体は、前置きの1つ目の欄をダミーと同じ `UNCOUNTED` にする。`acquire_immortal`、`dup`、`decref` は、数を変えず、確かめもしない (下の「不死の物体の数え方」)
- 数えると、どのスレッドも領域の物体の数を書き換えるので、凍結した塊は公開した後は読むだけ、という性質が崩れる。atomic に数える案は採らない。権限の値が実際の数と食い違わないようにする印、worker をまたぐ確かめと変更を1つの CAS にまとめる手間、文字列の操作の巻き戻し、回復で領域の物体の数を合わせ直すこと、領域のリークの報告、ネイティブの検査ビルドの書き込める静的なデータが要り、得るものに比べて大きいためである
- 失うのは、リテラルだけに起きる RC の誤り (手放しすぎと手放し忘れ) の検出である。速いモードでは、不死の物体の RC の誤りは何も起こさない。Perceus はリテラルを特別に扱わないので、同じ誤りは死ぬ物体の値でも起き、検査モードはそちらで見つける。Lean と Koka も、持続する物体を数えない
- ヒープ自身の不死の物体 (`alloc_immortal` で作り、凍結していないもの) は、下の「不死の物体の数え方」のとおりに数える

### 検証

- Verus のモデルでは、ヒープが受け付けるブロックを、自分のブロックと、付けた塊とその祖先のブロックにする。領域のブロックの読み取りは塊の権限を読み、領域のブロックの状態はいつも生存である。ヒープの物体のフィールドには、領域の語を入れてよい
- 塊の権限 (ブロック、ページの頭、親の塊の権限の写し) は vstd の `Shared` に入れて読むだけにし、付けたヒープの ghost の欄に写す。写しは、ヒープが持つ `Arc` の指す塊の権限に等しい
- RC の遷移のモデルには、rc 0 の行き先の場合を足す。状態と数は変えず、辺だけを外す
- 塊の不変条件 (ブロックの形、生存、rc 0、`Foreign` でないこと、検査モードの数えない印、走査する語の行き先、祖先の鎖、祖先とブロックが重ならないこと) は、Verus の型の不変条件である

## reuse

LIR の reuse のパスは、Perceus の `release` と、構築子が分かっている値の `decref` を token を定義する `release` に、それが空けた箱を使う `con` を token を受ける `con` に書き換える ([LIR](lir.md) の「reuse」)。核は、その一意の道が次の命令の列になるように部品を持つ。VM は、この列を命令の中に並べる ([VM](vm.md) の「reuse」)。

```
is_unique(x)
  真: 残さない子を decref → into_token(x)
      → コンストラクタが変わるか、lin ビットが誤って残りうるなら con_at で meta を書き、そうでなければ reuse_in_place
      → 変わったフィールドだけを書く
  偽: is_last(x)
        真: 残さない子を decref → free_block(x) → alloc してすべてのフィールドを書く
        偽: 残す子を dup → decref x → alloc してすべてのフィールドを書く
```

`is_last` の枝は rc -1 の物体 (共有の親から `lin` の子が届く形) のためにあり、そこでも箱は使い回さない。

- token による再利用は所有の受け渡しで、解放の後の使用ではない
- token の箱は中身を消さない。一意の道で「同じ位置の同じフィールドは書かない」特殊化 (Koka の reuse の特殊化) は、古いフィールドが箱に残っていることに頼るためである
- token にできるのは、種類の欄で「token にできる」物体 (`Data`) だけである
- reuse の条件は、物理的な語の数が同じことである。型やコンストラクタが違ってもよい (cons の箱をタプルに使える。Koka と同じ)。語の数が同じ物体はいつも同じ級なので、級の刻み方は reuse に関係しない。検査モードが確かめられるのは級が同じことまでで、語の数が同じことはコンパイラが守る
- 共有の印の付いた物体は、rc の値によらず reuse しない (Lean 4、Koka と同じ)。`is_unique` が偽になるので、部品の側で特別に扱う必要はない
- reuse の token を継続のクロージャに入れない約束 ([LIR](lir.md) の「token の流れ」) はコンパイラが守る。検査モードは、破ったときに起きる2回の使用を見つける (下の「検査モードの token」)

## 検査モード

検査モードは、`eml run --debug-heap` と UI テストが使う、検査付きのヒープである。解放した領域を使い回さず、前置きに状態を書き、生きている物体を数えて、下の「報告する誤り」を見つける。

### モードの選び方

- モードは `Heap<M: Mode>` の型の引数で選ぶ。`Mode` は封じた trait で、`Fast` と `Checked` の2つがある。各操作は `if M::CHECKED { … }` で検査を書き、速いモードではこの分岐が単相化で消える
- 実行時の旗にしないのは、速いモードの RC の速い道に、検査のための分岐を1つも足さないためである。VM は2つのモードで単相化して2つ作る。ネイティブは、コンパイル時にどちらかを選ぶ
- 仕事の回数 (`Stats` の `rc_increments`、`rc_decrements`、確保の回数 `allocations`、生きている箱の数 `live` とその最大 `peak_live` と、`Ctx` の `CtxStats` の `evidence_steps`、`yields`、`yield_frames`、`string_bytes_copied`) は、検査モードだけで数える。速いモードは数える費用も持たない。VM では、`RunStats` の回数の固定と UI テストを検査モードで走らせ、`bench/run.sh` の命令の数は速いモードで測る。OS から取ったページのバイト数だけは、両方のモードで数える (上の「確保と解放」)

`RunStats` の各項目の意味と VM での出どころは、[VM](vm.md) の「`RunStats`」にある。`string_bytes_copied` は、extern が数える `CtxStats` の定義を引き継ぐ (下の「extern」の「仕事の回数」)。

### 前置き

- 検査モードでは、各ブロックがヘッダの前に1語の前置きを持つ。ポインタはどちらのモードでもヘッダを指すので、命令の側のコードは同じである
- 前置きは2つの `u32` の欄で、T2 の関数が Relaxed で読み書きする
  - 1つ目は、普通の物体では所有者 ID、`alloc_immortal` の物体では外に出ている参照の数 (下の「不死の物体の数え方」) である。不死の物体は持ち主を持たないので、同じ欄を使う
  - 2つ目は、状態 (生存、token、空ける途中、解放の4つ) と世代の番号 (残りのビット) である。世代の番号は、`into_token` と解放のたびに1つ進める
- 検査モードのどの操作も、rc を見る前に前置きを読む。解放した共有の物体は、最後の `decref` で rc が 0 になっているので、rc を先に見ると不死の物体と区別できないためである
- 検査モードは、解放したブロックを空きリストに戻さず、状態を「解放」にして残す (隔離)。そのため、解放した物体の語を後で使っても、指す先はまだ確保したままのメモリで、UB にならずに見つけられる。大きい物体のページも、検査モードでは解放したときに返さず、`Heap` を落とすときに返す

### 検査モードの token

token (`Token`) はどちらのモードでも1語である。VM のレジスタと、ネイティブの値の大きさを、モードで変えないためである。VM は `into_word` で語にしてレジスタに置き、`from_word` で token に戻す。

- 速いモードの token は、箱を指す語か、空を表す語 (`Token::EMPTY`) である
- 検査モードの token は、`Heap` が持つ token の表の添字を入れた即値である。表の項目は、箱と、`into_token` のときの世代の番号の組である
- 項目は、token を使ったときか `drop_token` のときに空ける。添字は使い回さない。空けた項目を空のまま残して、古い token を確実に断るためである
- token を使う操作は、表の項目を引き、項目が空でないこと、箱の状態が token であること、世代の番号が項目のものと同じことを確かめる

多重の再開では ABA の形が起きうる。たとえば、1回目の再開が `con_at(t)` で y を作り、y が後で一意になって `into_token` でまた token になったとする。箱の状態は token に戻るが、新しい token は別の添字を持ち、t の項目は空のままなので、2回目の再開が古い t を使うと断られる。世代の番号も進んでいるので、箱の側から見ても古い t とは合わない。

### 不死の物体の数え方

`eml_rt` の不死の物体は、`CodeBase` の定数のように子を持ちうる。親が子への参照を構造として持ち、親を作るときに `set_field` で子を書き、子を親から借りて読む。そのため、不死の物体の外に出ている参照を数え、数が 0 の物体へのどの操作も解放の後の使用として断る形では、正しいプログラムを断ってしまう。そこで、検査モードは次の形で数える。

- 数えるのは、外に出ている参照、つまり `acquire_immortal` と `dup` で作り、`decref` で手放す参照だけである。不死の親が子に持つ参照は構造の一部で、数えない
- `alloc_immortal` の物体は、数を 0 にして作る。`acquire_immortal` が数を1つ増やし、`dup` が1つ増やし、`decref` が1つ減らす。数が 0 になっても解放しない
- 誤りにするのは、数が 0 の物体への `decref` (作っていない参照を手放すこと) と、不死でない物体への `acquire_immortal` である。読む操作 (`field`、`raw`、`scanned`) と `set_field` と `dup` は、数を見ない。`dup` を断らないのは、不死の親から借りた子を `dup` して所有するのが正しい形だからである
- リークの報告では、数が 0 でない不死の物体の数を、件数に足す
- ダミーは数えない (上の「ダミーの値」)。前置きの1つ目の欄を `u32::MAX` (`UNCOUNTED`) にして作り、この値の物体は数を変えも確かめもしない
- 凍結した領域の物体も数えない。`freeze` が前置きの1つ目の欄を `UNCOUNTED` にする。理由は上の「凍結した領域」の「検査モードでは数えない」にある
- 速いモードでは、`acquire_immortal` は何もせず、不死の物体の `dup` と `decref` は rc 0 を見て何もしない
- この形で断らないのは、数が 0 の不死の物体を読むことである。不死の物体のメモリは解放されないので、読んでも UB にはならない。手放しすぎと手放し忘れは、`decref` の誤りとリークの報告で見つかる

### 報告する誤り

検査モードは次を `Err` (`HeapError`) で返す。

- 解放した物体の使用 (`UseAfterFree`)。語を受ける操作は、前置きの状態が生存でない語を断る。解放の連鎖が、空ける途中の物体にもう一度届いたときも同じ誤りにする (下の「検査モードの約束」)
- 数が 0 の不死の物体への `decref` (`ImmortalOverRelease`) と、不死でない物体への `acquire_immortal` (`NotImmortal`)。上の「不死の物体の数え方」
- `freeze` の断り。どちらのモードでも返す。rc が 0 でない物体 (token の箱を含む) か `Foreign` の物体があれば `NotImmortal` を返す。検査モードでは、前置きの状態が生存でない箱 (token の箱と空ける途中の物体) があるときと、走査する語が生存でないブロックを指すときも断る。その行き先が解放したブロックなら `UseAfterFree`、そうでなければ `NotImmortal` である。上の「凍結した領域」
- `lin` ビットの立った物体への `dup` (`LinDup`)。`lin` の物体の rc は 1 なので、rc が 1 を超える誤りは、この `dup` で見つかる
- `lin` ビットの立った共有の物体の `release` と `decref` (`LinShared`)。`share` は `lin` の物体に印を付けないので、これは印付けの誤りである。`share` のたどりが、すでに共有の `lin` の物体に届いたときも同じ誤りにする
- `share` のたどりで、同じ `lin` の物体に2回届くこと (`LinReachedTwice`)
- 所有者の不一致 (`WrongOwner`)。正の rc の物体への `dup`、`decref`、`set_field`、`set_raw`、`is_unique`、`is_last`、`free_block`、`into_token`、`release`、`release_reuse`、`foreign_unique`、`string_push`、`string_concat` が、今の worker ID と違う所有者の物体に対して行われたとき
- ほかのスレッドが読みうる物体への書き込み (`NotWritable`)。`set_field` と `set_raw` は、rc が 0 以下 (不死か共有) で構築中でない物体を断る。凍結した塊の物体と、書き終えたヒープ自身の不死の物体もこれに当たる。前置きの状態は構築中と生存を分けないので、検査モードのヒープは構築中の物体の番地を持ち、それと比べて見分ける
- token の誤り。token にできない種類の `into_token` (`NotTokenable`)、一意でない物体の `into_token` (`NotUnique`。rc が 1 でない物体の `foreign_unique` と `set_lin` も同じ誤りにする)、空けた表の項目の使用、箱の状態が token でないこと、世代の番号の不一致 (`StaleToken`。token を受ける操作が断る。同じ token の2回の使用と ABA の形)、級の合わない `con_at` (`WrongClass`)、`reuse_in_place` の `meta` の tag と scan と種類が箱と違うこと (`WrongMeta`)、`reuse_in_place` で箱が `lin` ビットを持ち新しい `meta` が持たないこと (`LinBitKept`)
- `free_block` を、破棄処理を持つ種類の物体に使うこと (`FinalizerSkipped`) と、最後の参照でない物体に使うこと (`NotLast`)
- `release` と `release_reuse` で、物体がデータでないか、タグと走査する語の数が名指したものと違うこと (`WrongLayout`)
- `unbox_int`、`foreign`、`foreign_unique`、`string`、`bytes`、`string_push`、`string_concat`、`set_lin` で、物体の種類が違うこと (`WrongKind`)。`foreign` と `foreign_unique` は値の型も照らし、速いモードでも同じ誤りを返す (上の「核の操作」)
- 添字の範囲の外 (`OutOfBounds`)。`field` と `set_field` は、添字が走査する語を指さないことを断る。`raw` と `set_raw` は、添字が走査する語の後のブロックの中の語を指さないことを断り、ペイロードが不透明な物体 (`Foreign`、`String`、`Bytes`) を `WrongKind` で断る。`scanned` は、添字が走査する語の数以上であることを断る。走査する語に生の値を書くと、解放の連鎖がその値をポインタとして読み、`Foreign` の破棄処理の表を上書きすると、破棄処理が正しくない関数のポインタを呼ぶ。`String` と `Bytes` の長さの語を書き換えると、`string` と `bytes` が容量の外を読む。どれも検査モードの安全を崩すので、断る
- `Ctx` の基本操作の誤り (下の「実行文脈 `Ctx`」)
  - 節点、evidence、入口の表の形が違うこと、入口の欄の番号が入口の数以上であること、入口の欄に2回入れること、`evv` の長さが上限を超えること、`ev_new` のエフェクトの番号が 65535 であること、`ev_set_clause` で `lin` ビットの立った節の本体を入れること (`BadEvidence`)
  - `ev_lookup` と `evv_mask` で、合う evidence が `evv` にないこと (`NoHandler`)
  - 空の根を読むことと、空でない根に置くこと (`RootMisuse`)。速いモードでも返す (下の「セッションの根」)
  - yield の状態についての前提を破ること (`YieldMisuse`)。yield 中の `yield_to` と `yield_abort`、物体でない宛先、yield していないときの `yield_cont_take`、`yield_cont_set`、`yield_finish`、κ の欄が空でないときの `yield_cont_set` と `yield_finish` がこれに当たる
- 回復で、根から写せない物体に届くこと (`Unrecoverable`)。写せない物体は、上の「種類」の写し方の表と、下の「回復」の輪である。どちらのモードでも返す
- 生存の列挙 (`check_invariants`) で見つかる不変条件の違反
  - 共有の物体から、共有でも不死でもない物体が届き、それが `lin` ビットの立った局所の物体でもないこと (`SharedReachesLocal`)。上の「`share`」の理由で、`lin` ビットの立った局所の物体は許す
  - 不死の物体から、不死でない物体が届くこと (`ImmortalReachesMortal`)。`share` は不死の物体でたどりを止めるので、不死の物体の子が局所なら、印なしに別のスレッドから届く。Koka の PR #910 は、プロセス全体で共有する物体が atomic でない RC を持っていたために、2つのスレッドで動かすとヒープが壊れたと報告している。その誤りがこの形である
- リーク (`leaks`)。生きている不死でない物体と、使われずに残った token を、種類の名前ごとに数える。token は種類の名前 `Token` で数える

`Err` を返した後もヒープを使い続けてよいかは、状態を変える前の `Err` かどうかで決まる (下の「検査モードの約束」)。

### 検査モードの約束

検査モードは、空けたブロックを使い回さず、その権限を `Heap` に持ったままにする。大きい物体のページも返さない。そのため、検査モードのメモリの安全には、モデルの数が正しいことが要らない。

各操作の前提は、次の3種類に分かれる。

- 安全の前提: どちらのモードでも前提にし、検査モードも確かめない。破ると、検査モードでもメモリの安全が崩れうる
- モデルの前提: どちらのモードでも前提にし、検査モードも確かめない。破るとモデルの数が合わなくなるが、検査モードのメモリの安全は崩れない。速いモードでは、モデルの数が合わないとメモリの安全が崩れる
- 検査する前提: 速いモードでは前提にし、検査モードでは確かめて `Err` を返す

不変条件も2つに分かれる。`safe_wf` は権限の持ち方とブロックの状態の不変条件で、モデルの数と辺には触れない。`full` は、抽象のモデルとの対応を含む不変条件である。`full` が成り立つことを、モデルが合っていると言う。性質は次のとおりである。

- 検査モードの操作は、安全の前提の下で `safe_wf` を保つ
- モデルが合っていて、モデルの前提と検査する前提がすべて成り立つなら、操作は `Ok` を返し、結果は速いモードと同じモデルの遷移になる。ただし、モデルは不死の物体の外の参照の数、共有の物体の `lin` ビット、物体の持ち主、確保器の級、箱の `meta` を照らす規則を持たない。そのため、解放の連鎖が手放す子についての `ImmortalOverRelease`、`LinShared`、`WrongOwner`、`con_at` の `WrongClass`、`reuse_in_place` の `WrongMeta` と `LinBitKept` は、モデルが合っていても返りうる
- `Err` を返すのは、その誤りに対応する違反が操作の前にあったときだけである
- 状態を変える前に `Err` を返す操作では、ヒープは変わらない。状態を変えた後で `Err` を返しうるのは、解放の連鎖 (`decref`、`release`、`release_reuse` の子の処理)、`release` の最後でない枝の `dup` の列、`share`、`con_at` (token の項目を取り出した後の `WrongClass`) と、`Ctx` の基本操作の `evv_set`、`ev_set_state`、`yield_finish` (元の `evv`、元の状態、宛先を手放す解放の連鎖で起きた誤り) と、extern の `handle_close` (ハンドルを手放す解放の連鎖で起きた誤り。下の「extern」) である。その後はモデルが合わなくてよく、ヒープを使わない。ただし `Heap` と `Ctx` を落とすことは安全である

同じ物体を2回空けないように、最後の参照と決めた時点で、その物体の前置きを「空ける途中」にする。`release_ref`、`release` の最後の参照の枝、`release_reuse` の子の処理の前がこれに当たる。呼ぶ側が `dup` せずに同じ語を2つのフィールドに書いた親を空けると、同じ子に2回届く。2回目に届いたときは、生きていないので `UseAfterFree` を返す。`Err` で解放の連鎖が途中で止まると、積んだまま空けていない物体が「空ける途中」で残る。`Heap` を落とすときは、その中の `Foreign` の破棄処理を1回だけ呼ぶ。生存の列挙、不変条件の検査、リークは、「空ける途中」の物体を生きている物体と同じに扱う。

token の表の項目は、`into_token` と `release_reuse` が添字を使い回さずに積み、取り出すと空にする。そのため、項目があればその箱は token の状態で、世代の番号は項目のものに等しい。`safe_wf` はこの不変条件を持つので、世代の番号が回っても検出は外れない。

不死の物体の数が `u32` の上限に届くときは panic する。

### 論理的な worker ID

- `Heap` は今の論理的な worker ID を持つ。確保した物体の所有者を今の ID にする
- 物理的な worker が1つでも所有者の検査を働かせるために、ID を切り替える操作 (`set_worker`) を持つ。所有者 ID の使い方は [マルチコア対応の設計](../future/multicore.md) の「論理的な worker ID」にある
- ID を切り替えるのは単体テストだけなので、UI テストでは所有者の検査が効かない
- ID は実行文脈 `Ctx` でなく `Heap` に置く。確保のたびに物体の所有者を書くのは `Heap` だからである。`Ctx` は自分のヒープを通して ID を使う (下の「実行文脈 `Ctx`」)

## 実行文脈 `Ctx`

実行文脈 `Ctx<M>` は、ヒープと、[LIR](lir.md) の「実行の文脈」の `evv` と yield の状態を持ち、同じ文書の「基本操作」の表のうち `dummy` を除く21個をメソッドにする (`dummy` は上の「ダミーの値」の `Heap::dummy`)。VM は `&mut Ctx` だけを持ち回す。ヒープと実行の状態を別の構造体にしないのは、持ち回すものが2つになり、基本操作の契約が2つの値をまたぐためである。

### 欄

| 欄 | 中身 |
|---|---|
| `heap` | `Heap<M>` |
| `evv` | 今の `evv`。`Ctx` が持つ参照で、空のリストは即値の `()` である |
| `yielding` | yield の状態 (下の「yield の状態」) |
| `control` | セッションの `Arc<Control>` (下の「実行の制御」)。安全点の確かめがヒープの中をたどらずに読めるように、ヒープとは別に持つ |
| `max_depth`、`max_evv` | `Control` の上限の写し。`Ctx::new` が写す |
| `host` | セッションの Host (下の「extern」の「Host」)。出力とファイルは、これを通す |
| `stats` | 仕事の回数 `CtxStats` (`evidence_steps`、`yields`、`yield_frames`、`string_bytes_copied`)。`Heap` の `Stats` と同じく、検査モードだけで数える。`yields` は `yield_to` の回数で、中断は数えない |
| `roots` | セッションの根の表 (下の「セッションの根」) |

- `Ctx` は `Send` で `Sync` でない (`Heap` と同じ)。`Control` は `Send` と `Sync` である。どちらも型の assert で固定する
- 論理的な worker ID はヒープに置く (上の「論理的な worker ID」)
- `heap()` は安全なメソッドで、`heap_mut()` は `unsafe fn` である。安全なコードがヒープを入れ替えると、`Ctx` の持つ語が、落としたヒープを指すためである。`heap_mut()` の前提は次の3つである。ヒープを入れ替えない (入れ替えるのは下の「回復」の `recover` だけである)。`Ctx` の持つ語 (`evv` と yield の状態の語) を手放したり書き換えたりせず、そこからたどれる物体 (`evv` の節点、evidence、入口の表) も書き換えない。`Ctx` のメソッドを次に呼ぶ前に、作っている物体を書き終える
- `Ctx` は `Drop` を実装しない。`evv` と yield の状態の参照は個別に手放さず、ヒープと一緒に消える。そのため、基本操作の中の `decref` で破棄処理が panic しても、`Ctx` を落とすことは安全である (下の「`unsafe` の核」の T7)
- `check_finished()` は、`evv` が空で yield の状態がなしであることを確かめる。VM がリークの検査の前に呼ぶ ([LIR](lir.md) の「`evv` の不変条件」の最後の項)
- `copy_string(s, max_chars) -> Result<String, Fault>` は、文字列の参照 `s` を1つ受けて手放し、中身の先頭 `max_chars` 文字を Rust の `String` に写して返す。VM が、文字列を返す入口の結果を受け取るのに使う ([VM](vm.md) の「追記」)。`unsafe fn` で、前提と事後条件 (`held_ok`、`evolved_by`) は `println` と同じである。検査モードは種類を確かめ、文字列でなければ何も写さずに `Fault::Heap(WrongKind)` を返す。写す長さを切るのは、利用者の `show` が巨大な文字列を返しても、確保量の上限の外で同じ大きさを写さないためである。文字の始まりは `str::is_char_boundary` で数え、写すのは `str::to_owned` である。どちらも vstd が仕様を持つので、下の「`unsafe` の核」の信頼の一覧は増えない
- `ev_find(effect)` は `ev_lookup` と同じく `evv` をたどり、見つけた evidence を `dup` して返す。見つからなければ `None` を返す。検査モードでは、形の違う節点に `BadEvidence` を返す。`evidence_steps` は検査モードでたどった節点ごとに数える。`exit_abort` は、宛先を不死のダミーの物体、節と κ を `()` にした中断を始める。`yield_abort` と同じく `yields` には数えない。`fresh_string` は文言から文字列を作る

### セッションの根

- `Ctx` は根の表 `roots` を持つ。根は番号で指す欄で、空か、参照を1つ持つ `tobj` の語である。REPL の `let` の束縛の値を、入力をまたいで残すために使う ([VM](vm.md) の「追記」)
- 根を読み書きする基本操作は `root_get` と `root_set` である (下の「基本操作の契約」)。表は、まだない番号に置くときに伸びる。根の番号は `let` の入力の番号で、使い回さない。同じ名前の `let` を定義し直しても、古い根は `close` まで手放さない ([ロードマップ](../future/roadmap.md) の「REPL」)。実行時エラーで失敗した `let` の根は、`root_set` の前に失敗すれば空のまま残る。`root_set` の後の安全点 (`Ret`) や、終わりの flush の `Output` の誤りで失敗すれば、根は埋まったまま残る。どちらでも入力は受け付けない。失敗した入力の名前は後の入力から見えないので、その根を読むコードは実行されない。埋まったまま残った根の値は `close` まで残り、回復のたびに写される。害はないので受け入れる
- 空の根を読むことと、空でない根に置くことは、2つのモードとも `HeapError::RootMisuse` にして、何も変えない。REPL が根の番号を誤ったことを示すので、VM は続けられない誤りとして扱う ([VM](vm.md) の「追記」)
- 根の語は `held_ok` の外に置く。VM のスタックのスロットと同じく、根の語が持つ参照は VM が保証する。根を `held_ok` に入れると、ほかの基本操作のすべての証明を直すことになるためである。Verus は、根の操作が `held_ok` を保つこと、`root_get` が根の語の参照を1つ増やすこと (RC のモデル)、誤った使い方では何も変えずに `RootMisuse` を返すことを証明する
- `take_roots()` は、すべての根の語を表から取り出して返す。`Machine::close` が取り出した語を手放してから、リークを確かめる
- 根は回復の起点である。回復は、根から届く物体を新しいヒープに写し、根の語を写した語に書き換える (下の「回復」)

### 回復

続けられる実行時エラー (extern の誤り、深さと確保量の上限、割り込み) の後に、VM は `Ctx::recover()` を呼ぶ。`recover` は基本操作でない。根から届く物体を新しいヒープに写し、古いヒープを丸ごと捨てる。実行時エラーと割り込みは Perceus の規則の外の中断なので、RC の規則だけでは後始末できないためである。回復の後に生きている物体は、根から届く物体と、凍結した領域の物体と、ヒープのダミーだけになる。

- 古いヒープを捨てると、失敗した実行が残したもの (捨てたスタックと `evv` と yield の状態の語、token の箱) がすべて消える。届かない `Foreign` の物体は、古いヒープを落とすときに破棄処理が呼ばれる (`FileIn` なら閉じる。上の「生存の列挙」)。古いヒープのページはすべて `Control` に戻るので、確保量は新しいヒープの分に戻る
- 写すと物体の番地が変わる。失敗した実行の後に、ヒープの外でヒープの語を持つのは根だけである。`CodeBase` の定数は凍結した領域にあり、写しても変わらない。VM のタスクは実行の局所の値として捨て、Host はヒープの語を持たない
- その場で解放して RC を数え直す形にしないのは、次の3つのためである。Verus の RC のモデルは外からの参照をただの数で持つので、捨てたスタックや `evv` の参照がなくなったことを表すには、多くのブロックと辺をまとめて消す新しい遷移が要る。速いモードでは token の箱を生きている `Data` と見分けられないので、数え直しの誤りが速いモードのメモリの安全を崩す。小さい物体のページは OS に返さないので、その場で解放しても確保量は減らない
- 根の値は `Unr` なので、`lin` の物体、`lin` ビットの物体、token の箱には届かない。届いたら写すのをやめ、`Unrecoverable` を返す
- 写す費用は根から届く物体の数に比例し、古いヒープを落とすときの破棄処理の走査は古いヒープのブロックの数に比例する。写している間は古いヒープと新しいヒープが同時にあり、使うメモリは古いヒープと写しを足した量になる。ほかに要るのは写像と、写している途中の物体のスタックだけで、どちらも根から届く物体の数で決まる (上の「生存の列挙」)。OS の確保が失敗すると、ほかの確保と同じく処理系が止まる
- 回復は止める理由のビットを見ない。写すことで確保量の上限を超えて `MEMORY` のビットが立っても、写すのはやめない (下の「実行の制御」)

手順は次のとおりである。新しい信頼する部分は足さない。写像には vstd の `HashMapWithView` を使う。vstd が std の型に置く仮定の仕様で、`Vec` や `Arc` と同じ種類の信頼である。

1. 古いヒープの作りかけの物体を書き終える。古いヒープと同じ `Control`、worker ID、凍結した領域の先頭を持つ空のヒープを作る
2. 根から届くポインタの語は、そのブロックのページの頭で見分ける (上の「生存の列挙」)。古いヒープのページにあれば古いヒープのブロックで、なければ凍結した領域の物体である。rc が 0 の古いヒープのブロックがダミーでなければ、ヒープの不死の物体なので `Unrecoverable` を返す。実行のヒープで不死の物体を作るのは定数を作る作業用のヒープだけなので、実行のヒープではこの誤りは起きない
3. 根の語から深さ優先で、帰りがけ順に写す。枠のスタックは (古いブロック, 次に見るフィールドの番号) を積み、枠を積む前にそのブロックを写像に「写している途中」として入れる。写した子の新しい語は別の語のスタックに積み、枠のフィールドを見終えたら、語のスタックの末尾から走査する語の数だけ取って物体を作る。写している途中の物体にまた着いたら、輪なので `Unrecoverable` を返す
4. 参照は余分な `dup` なしで配る。新しい物体の最初の参照は最初の使い手 (親のフィールドか根) に渡し、2つ目からの使い手には `dup` を1回ずつする。写像に入る物体は、どれもそれを使うフィールドか根から見つけたものなので、最後に余る参照はない
5. 根の表を新しい語に書き換え、ヒープを入れ替え、`evv` を `()` に、yield の状態をなしに戻し、古いヒープを落とす。新しいヒープには作りかけの物体も token もない

- 各物体は、読む前に写せる状態かを確かめる。速いモードでは、前提 (根の語は生きている物体を指す) から写せる状態が出る。検査モードは前置きの状態を読み、解放した物体と token の箱を `Unrecoverable` にする。凍結した領域の物体は読まず、語をそのまま使う
- 前提は `root_get` と同じ形である。根の語は即値か、このヒープか付けた塊の生きている物体を指し、それぞれ参照を1つ持つ。Verus は、古いヒープを安全に読むことと、成功したときに新しいヒープの不変条件が成り立ち、各ブロックの外からの参照の数が根の表の中の出現の数に等しいこと (速いモード)、`evv` が空で yield していないことを証明する
- `Unrecoverable` のときは、根の表と `evv` と yield の状態を変えずに返す。古いヒープは作りかけの物体を書き終えた形になるだけで、物体は変わらない。作りかけの新しいヒープは落とし、そのページは `Control` に戻る。作りかけの新しいヒープには `Foreign` の物体がないので、破棄処理は呼ばれない。VM は、元の誤りと回復の誤りを持つ `RuntimeError::Unrecovered` を返し、セッションを使えなくする ([VM](vm.md) の「追記」)

### yield の状態

- yield の状態は、平らな `#[repr(C)]` の記録 `YieldState { target, clause, cont, abort }` である。`target` は宛先の evidence、`clause` は節の本体、`cont` は組み立て中の継続 κ、`abort` は中断かどうかで、`target` が `()` のときを「なし」とする。Rust の enum は配置が決まらないが、この形なら、ネイティブのコードが「yield 中か」を、決まった位置の語と即値の1回の比較で読める (Koka の `yielding` の欄と同じ形)
- 不変条件は「`target` が `()` なら、`clause` と `cont` も `()` で、`abort` は偽である」の1つである。VM から見た動作は、なし、yield 中、中断中の3つの値の enum と変わらない
- `yield_to` と `yield_abort` の宛先は物体でなければならない。`()` を宛先にすると、yield の状態が「なし」と区別できないためである
- 中断 (`yield_abort` と `exit_abort`) は κ の欄を `()` にする。中断は継続を組み立てず、VM がタスクのスタックを巻き戻すためである ([VM](vm.md) の「巻き戻し」)。そのため、中断中の `yield_finish` は κ を取り出さずに呼べる。`yield_abort` は κ を受けない。成功したときに κ の欄が空であることは、Verus で証明する
- `yield_status` は、宛先を語の値 (番地) で比べる。yield の状態が宛先の参照を持つので、比べる間に番地が使い回されることはない
- `yielding`、`yield_status`、`yield_cont_take`、`check_finished` は、ヒープに触れないので安全な関数である。前提を崩しても、リークするだけである。`yield_cont_take` は、yield していなければ、検査モードでは `YieldMisuse` を返し、速いモードでは空の欄の `()` を返す

### タスクの切り替え

[LIR](lir.md) の「実行の文脈」は、協調的な `par` の a1 ([ロードマップ](../future/roadmap.md) の「マルチコア対応」) でタスクを切り替えるとき、実行の文脈をタスクごとに持つか、切り替えで退避するかを求める。次のように決める。

- タスクは、yield の状態がなしの安全点でだけ切り替える。そのため、退避するのは `evv` だけで、`evv_get` と `evv_set` で足りる。切り替えのための基本操作は足さない
- `par` の a1 の子は、`evv` を空 (`()`) にして始める。子の row は `<>` なので、evidence がタスクをまたがない。上の「evidence の3つの物体」が、状態の欄をその場で書き換える条件として挙げたことでもある

### 実行の制御

`Control` は、実行を止める情報で、セッションに1つある。CLI と、どの worker の `Ctx` とヒープも、`Arc<Control>` で同じものを見る。

| 欄 | 中身 |
|---|---|
| 止める語 | 止める理由のビットを持つ `AtomicU32`。ビットは `Control::INTERRUPT` (1) と `Control::MEMORY` (2) である |
| 確保量 | セッションのヒープが OS から取ったページのバイト数を持つ `AtomicUsize` |
| 上限 (`Limits`) | `max_bytes` (確保量)、`max_depth` (深さ)、`max_evv` (`evv` の長さ)。`Control::new(limits)` で作るときに決め、変えない。既定の値は、どれも `usize::MAX` である |

- 安全点の確かめは `Ctx::poll(depth) -> Result<(), Stop>` である。速い道は、`depth` が `max_depth` を超えるかと、止める語が 0 でないかの2つの比較で、どちらも偽なら `Ok` を返す。真なら `#[cold]` の関数が、速い道で読んだビットから `Stop` を決める。優先の順は `Interrupted`、`MemoryLimit`、`DepthLimit` である。ビットを読み直さないのは、その間にほかのスレッドが `clear` すると、深さの上限を超えていないのに `DepthLimit` を返すためである。VM は呼び出し、戻り、自己末尾呼び出しのジャンプで `poll` を呼ぶ ([VM](vm.md) の「呼び出しと戻り」)
- 深さは、VM のタスクが持つスタックの語の数で数える。フレームの数で数えないのは、スタックの大きさを抑えるのが目的だからである
- 確保量は、確保器がページを取るときと返すときに数え (上の「確保と解放」)、上限を超えたら `MEMORY` を立てる。worker ごとのヒープの数を足し合わせた、セッション全体の量になる。凍結した塊のページも、塊が生きている間は数に入る。ページを `Frozen` に移しても数はそのまま残り、塊を落とすときに減る
- 確保器に `Control` を渡すため、ヒープの確保器が `Arc<Control>` を持つ。`Heap::with_control(control)` は共有の `Control` でヒープを作り、`Heap::new()` は上限のない新しい `Control` で作る。`Heap::control()` がそれを返す。`Ctx::new(control, host)` は `with_control` でヒープを作る
- `Control::interrupt()` は `INTERRUPT` を立て、`Control::clear()` はすべてのビットを下ろす。確保量が上限を下回ってもビットは下りないので、下ろすのは `clear` だけである。REPL (`eml_cli::Repl`) は、入力の始めに `clear` を呼ぶ。確保量の上限で止まった後も、`MEMORY` のビットで次の入力が止まらないようにするためである。`clear` は確保量を減らさない。確保量を戻すのは、続けられる誤りの後の回復である。回復は古いヒープのページをすべて `Control` に戻すので、上限で止まった後の入力も、新しいヒープの分から数える (上の「回復」)。回復は写す間に古いヒープと写しを同時に持つので、写すことで上限を超えることがある。そのとき立つ `MEMORY` のビットは、次の入力の始めの `clear` が下ろす
- 止める語が伝えるのは「止めよ」のビットだけで、ほかのメモリへの書き込みを公開する役はない。そのため、どの読み書きも Relaxed で行う
- `poll`、`interrupt`、`clear` と確保量の加減と `over_budget` は、`verus!` の外の安全なコードで、値について何も約束しない。確保器が確保量を加減する関数と、`make` が確保の前に上限と比べる関数は、信頼の一覧の T1 に入る (下の「`unsafe` の核」)
- `eml_rt` は止める語だけを持ち、SIGINT のハンドラを持たない。vstd だけに依存したままにするためである。ハンドラは `eml_cli` が `libc::sigaction` で入れ、`Control::interrupt()` を呼ぶ ([VM](vm.md) の「上限と割り込み」)
- `eml run` の上限の既定の値は、`eml_cli::default_limits()` が決める ([VM](vm.md) の「上限と割り込み」)。上の表の既定の値 (`usize::MAX`) は `Limits::default()` のもので、`RunConfig::default()` とテストが使う

### 基本操作の契約

`Ctx` は ghost の状態を持たず、`evv` のリストと evidence を、ヒープの上の spec の関数で表す。VM は検証しないコードで、基本操作の合間にヒープを変えるので、`Ctx` の中に ghost のリストを保ち続けられないためである。

- `ev_shape(e)`: e は evidence の浅い形をしている。tag が 0 でない `Data` で、走査する語が3つ (入口の表、状態、外側の `evv`) で、`lin` ビットを持たない。入口の表は tag 0 の `Data` で、`lin` ビットを持たない。入口の欄と外側の `evv` の語は `dup` でき、状態の語は手放せる。再帰しない浅い形である。ここで物体を指す語は、どれも持ち主が今の worker である
- `evv_path(w, fuel)`: w から節点をたどり、`fuel` 歩以内に `()` に着くなら、(tag, evidence) の組の列になる。どの節点も走査する語が2つの `Data` で、`lin` ビットを持たず、tag はその evidence の tag と同じで、evidence は `ev_shape` を満たす。輪になったリストと形の違う節点では、列はない
- `evv_seq(w)` はその列で、`evv_wf(w)` は、列があって長さが `max_evv` 以下であることである
- `mask_spec(items, seq)`: `items` の各項目 (エフェクト、残す数 n、飛ばす数 m) について、先頭から tag の合う組を数え、n 個を残して続く m 個を除いた列。i 番目の組の tag があるエフェクトに当たり、それより前に同じ tag の組が s 個あるとき、そのエフェクトの項目について n ≤ s < n + m なら、その組を除く。項目のないエフェクトの組は残す。どんな項目の並びにも定まり、同じエフェクトの項目が2つあれば先の項目を使い、m が 0 の項目は何も除かない。n と m は自然数として扱う。組が tag を持つので、ヒープを読まずに定まる
- `held_ok()`: モデルが合っていて、`evv_wf(evv)` が成り立ち、`Ctx` の持つ4つの語 (`evv` と、yield の状態の `target`、`clause`、`cont`) の参照を `Ctx` が持っている

外側の `evv` が `evv_wf` であることは、`ev_shape` に入れない。入れると2つの述語が互いに再帰し、検査モードで確かめる費用が、handler の入れ子の深さについて指数で増えるためである。外側の `evv` が正しいことは EP の不変条件として速いモードの前提にし、`ev_evv` の結果は語そのものだけを約束する。

どの基本操作も `held_ok()` を前提にし、保つ。VM の義務は、基本操作の合間に、`Ctx` の持つ語とそこからたどれる物体に触れないことである (`heap_mut()` の前提)。各操作の結果は、RC のモデルで物体ごとの外の参照の数がどう増減するかで書く。借用の引数 ([LIR](lir.md) の「基本操作」の表) は手放さず、ほかの引数は消費する。消費する引数の参照は、呼ぶ側が `Ctx` の参照と別に持つ。同じ物体を指す引数が並べば、その数だけ持つ。`evv_set(evv_get())` のように、`Ctx` の持つ物体を引数に渡せるようにするためである。

| 操作 | 前提 (速いモード) | 結果と動作 |
|---|---|---|
| `evv_get()` | | `evv` を `dup` して返す |
| `evv_set(l)` | `evv_wf(l)` | `evv` を l にし、元の `evv` を手放す |
| `evv_push(l, e)` | `evv_wf(l)`、l の長さが `max_evv` より小さい、`ev_shape(e)` | e と同じ tag の新しい節点を返す。結果の `evv_seq` は、(tag, e) の後に `evv_seq(l)` を続けた列である |
| `evv_mask(items, w)` | `evv_wf(w)`、どの項目についても合う組が n + m 個以上ある (`mask_spec(items, evv_seq(w))` の長さに、各エフェクトの先の項目の m を足すと、`evv_seq(w)` の長さになる) | 結果の `evv_seq` は `mask_spec(items, evv_seq(w))` である。除いた最後の節点までに残す節点を写し、その後ろは元のリストを共有する |
| `ev_new(effect, n_ops, state, outer)` | `evv_wf(outer)`、effect が 65535 より小さい | 欄が `n_ops` 個でどれも `()` の入口の表と、それを指す tag が effect + 1 の evidence を作る |
| `ev_set_clause(ev, op, c)` | `ev_shape(ev)`、op が入口の数より小さい、欄が `()`、入口の表の rc が正、c が `lin` ビットを持たない | 入口の欄 op を c にする |
| `ev_renew(ev, state)` | `ev_shape(ev)` | ev と同じ入口の表と tag を持ち、状態を state に、外側を今の `evv` にした新しい evidence を作る |
| `ev_lookup(effect)` | `evv` に tag が effect + 1 の組がある | `evv_seq(evv)` で tag が effect + 1 の最初の evidence を `dup` して返す |
| `ev_clause(ev, op)` | `ev_shape(ev)`、op が入口の数より小さい | 入口の欄 op を `dup` して返す |
| `ev_evv(ev)` | `ev_shape(ev)` | 外側の `evv` を `dup` して返す |
| `ev_take_state(ev)` | `ev_shape(ev)`、ev の rc が正 | 状態を返し、欄を `()` にする |
| `ev_set_state(ev, s)` | `ev_shape(ev)`、ev の rc が正、呼ぶ側が s と別に ev の参照を持つ | 状態の欄を s にし、元の状態を手放す |
| `yielding()` | | yield 中か中断中なら 1、そうでなければ 0 |
| `yield_status(ev)` | | [LIR](lir.md) の「基本操作」の表の 0 / 1 / 2 / 3 |
| `yield_to(ev, clause, k)` | yield していない、ev が物体 | yield 中にする。3つの参照を `Ctx` が持つ |
| `yield_abort(ev, clause)` | yield していない、ev が物体 | 中断中にする。2つの参照を `Ctx` が持ち、κ の欄は `()` のままにする |
| `yield_cont_take()` | yield 中 | κ を返し、欄を `()` にする |
| `yield_cont_set(k)` | yield 中で、κ の欄が `()` | κ を入れる |
| `yield_finish()` | yield 中で、κ の欄が `()` | 宛先の参照を手放し、節の本体を返し、yield の状態をなしにする |
| `root_get(i)` | 根 i が空でない、根の語が生きている | 根 i の語を `dup` して返す |
| `root_set(i, v)` | 根 i が空 | v を根 i に置く。参照は根が持つ |

- `ev_set_clause`、`ev_take_state`、`ev_set_state` は、書く物体の rc が正であることを前提にする。これらの操作は書き終えた物体を書くので、核の `set_field` の前提 (ほかのスレッドが読めない) は、局所であることと同じになる。後の `par` で evidence が共有になると、検査モードは `set_field` の `NotWritable` を返し、速いモードではこの前提を満たさない呼び出しになる
- `ev_set_state` が ev の参照を s と別に求めるのは、元の状態を手放す連鎖が ev 自身に届いても、ev を空けないためである ([LIR](lir.md) の「evidence」の、状態の欄を通る輪)
- `ev_new` は入口の数を引数で受ける。VM とネイティブのコードは、エフェクトの操作の数をコードの定数として持つためである
- evidence (3語) と節点 (2語) は、`field` と `set_field` で読み書きする。速いモードで1回の読み込みで済むためである。入口の表は、欄が 255 個以上なら先頭に数の語があるので (上の「ヘッダ」)、`scanned` で読み、書くときは位置を1つずらす
- `perform` の道は `ev_lookup` と `ev_clause` である。速いモードの `ev_lookup` の1歩は、節点の `meta` を、作っておいた値 (tag が effect + 1、走査する語が2つ、`Data`、`lin` ビットなし) と1回比べ、次の節点を1回読むだけである
- `evv_mask` の `items` は `&[MaskItem]` である。`MaskItem` はエフェクトの番号 (`u16`) と n と m (どちらも `u32`) を持つ `Copy` の構造体である。項目の昇順と重なりのなさと m が 1 以上であることは verifier が確かめ、`evv_mask` の前提には入れない。VM はセッションでエフェクトの番号を引き直すので ([VM](vm.md) の「追記」)、`evv_mask` に届く並びは verifier を通った並びそのものでないためである。写す節点は先頭から順に作り、1つ前の写しの次の欄を `set_field` で書く。除いた数を配列にも `Vec` にも持たず、tag に合う項目のある節点ごとに、それより前の節点を先頭からたどり直して数える。たどり直しは、合う節点を n 個見つけるまでと n + m 個見つけるまでの高々2回で、n + m は桁があふれないよう `u64` で比べる。節点ごとに `items` も見直す。そのため、たどった先頭の i 個の節点のうち、tag に合う項目のある節点が p 個で、項目の数が q なら、費用は O(i·q + p·i) である。`evv_mask` を通るのは `mask` の包みと `mask$` だけで ([Core IR](core-ir.md) の「`mask` の包み」)、`perform` の道にはない
- evidence と節点は不死の物体にしない。`freeze` はヒープを消費し、evidence は定数にしないためである

### 速いモードと検査モード

- 核の操作と同じ分け方にする。速いモードは上の表の前提を安全の前提にし、検査モードは確かめて `Err` を返す (上の「報告する誤り」)
- 検査モードは、各操作が読む所だけを確かめる。`ev_lookup` と `evv_mask` は、たどる節点ごとに形と tag を確かめ、`ev_*` は evidence の形を確かめる。`evv_set` はリストをたどらず、`evv_push` は l の長さを数えるためにたどる
- 検査モードのリストをたどるループは、`max_evv` 歩を超えたら `BadEvidence` を返す。`evv_wf` が長さを `max_evv` 以下と定めるので、超えるのは前提を破ったとき (輪になったリストなど) だけである。既定の `max_evv` は `usize::MAX` なので、輪になったリストのテストは小さい上限で作る
- 検査モードは、状態を変える前に、確かめることをすべて確かめる。たとえば `evv_push` は、確保の前に e の形と l の長さを確かめる。`Err` のとき、ヒープと、`Ctx` の `evv` と yield の状態は変わらない。`ev_evv`、`ev_clause`、`ev_take_state`、`ev_set_clause`、`ev_lookup`、`ev_set_state` は例外で、`Err` を返す前に構築中の物体を書き終えて生きている物体にすることがあり、ヒープはその点だけ変わりうる。仕事の回数は、`ev_lookup` がたどった分だけ増えうる (下の仕事の回数の項)。ただし `evv_set`、`ev_set_state`、`yield_finish` は、状態を変えた後の解放の連鎖で起きた誤りを返しうる。その後は `Ctx` を落とすことしかできない (上の「検査モードの約束」)。extern の誤りのときの約束は、下の「extern」にある
- 検査モードの `evv_mask` は、確保の前にリストをたどって確かめ、項目ごとに合う evidence が n + m 個に足りなければ `NoHandler` を返す。たどった節点の数は、たどりが通ったときだけ `evidence_steps` に足し、`Err` のときは数えない
- モデルが合っていて `held_ok()` と表の前提が成り立てば、検査モードの基本操作は `Ok` を返し、結果は速いモードと同じになる。ただし `evv_set`、`ev_set_state`、`yield_finish` の解放の連鎖は、核の `decref` と同じく、モデルが照らさない誤りを返しうる。`evv_mask` が合う evidence の足りないときに `NoHandler` を返すことは、テストで確かめ、Verus では約束しない
- 仕事の回数の数え方は、`heap/tests/ctx.rs` の3つのテストが固定する。

## extern

`eml_extern` の表の関数の行のうち `exit` と `panic` を除く162個を、`eml_rt` に語の ABI で1回だけ書く。VM と、ネイティブのコードが同じ関数を呼ぶ。ヒープを使わない算術と比較は module `externs` の関数で、文字列と I/O の extern は `Ctx` のメソッドである。純粋な extern は、結果をバイト列や整数の spec に対して Verus で証明する。`exit` と `panic` は VM が実行する。`exit` は終了コードを覚えて、`Ctx::exit_abort` で中断を始める。`panic` は文言を `panicked` の節の入口に渡す ([VM](vm.md) の「extern の中断」)。

### 語の ABI

- 関数は、行ごとに引数の数が決まった形にする。`args: &[Word]` を受ける一律の形は採らない。引数がメモリを通り、ネイティブのコードでもレジスタで渡せなくなるためである
- 引数と結果の型は Repr で決める。`int` は生の `i64`、`obj` は `Word`、`unit` は `()` である。`enum` のタグも `i64` にする。VM のレジスタは生の 64 ビットの語で、`yielding` と `yield_status` も `i64` を返すので、VM の側で型を変えずに済む
- `Bool`、`Ordering`、`IOErrorKind` のタグ (`FALSE=0`、`TRUE=1`、`LT=0`、`EQ=1`、`GT=2`、`IO_NOT_FOUND=0` から `IO_OTHER=4`) は `i64` の定数として `externs` に置く。`eml_lir` の定数と同じであることは、両方に依存する `eml_vm` のテスト (`tags.rs`) で確かめる
- ヒープも Host も使わない算術と比較は、`Ctx` を取らない `#[inline]` の関数にする。VM の専用の命令が呼び、ほかの crate でも展開できるようにするためである。総称でない関数は、`#[inline]` がないと crate をまたいで展開されない ([計測の基準](../implementation/benchmarks.md) の「`eml_rt` のインライン化」)
- `Word` を受ける extern は `unsafe fn` にし、`# Safety` に前提を書く。`Word` は別のヒープからも持ち込めるためで、核の操作と同じである。前提は、`heap_mut()` の前提を守っていることと、語が即値か、このヒープか付けた塊の生きている物体を指し、呼ぶ側がその参照を1つ持つことである。速いモードでは、文字列を受ける引数が文字列であること、読むハンドルが局所で rc が 1 であること、`read_chunk` の `buf` がバイト列であることも前提にする。ハンドルの型は、どちらのモードでも確かめる
- 引数の所有は LIR の規則のとおりにする。借用の印の立つ引数 ([LIR](lir.md) の「extern の借用」) は手放さず、事後条件は、その物体の rc が変わらないことである。ほかの `obj` の引数は消費する。借りる引数に同じ物体を2つ渡すときも、参照は1つでよい。`Int.show` は `Word` を受けないので、安全な関数である。`Char.show` と `Char.display` も `Word` を受けないが、引数がスカラー値であることを `requires` に持つので `unsafe fn` にし、呼ぶ側が [LIR](lir.md) の「値の表現」の不変条件を守る

### 誤り

算術の誤りは `ArithFault` (`DivisionByZero`、`IntegerOverflow`、`FloatToInt(u64)`、`FixedDigits(i64)`、`NotScalar(i64)`、`NotByte(i64)`) で、`Copy` である。`FloatToInt` は `Int` に収まらない `Float` をビット列で持ち、`FixedDigits` は `Float.to_fixed` の範囲の外の桁数を持ち、`NotScalar` は `Char.of_int` が断ったスカラー値でない `Int` を、`NotByte` は `Byte.of_int` が断った 0..=255 の外の `Int` を持つ。`Result<i64, ArithFault>` は 16 バイトで、展開されないときも2つのレジスタで返る。`Ctx` のメソッドの誤りは `Fault` (24 バイト) で、`From<ArithFault>` と `From<HeapError>` を持つ。24 バイトに収めるため、まれな誤り (`NotUtf8` と `Index`) の中身は `Box` に入れる。

| `InUse(StdStream)` | 標準のストリーム (`Stdin`、`Stdout`、`Stderr`) のハンドルが生きている間の、2つ目の `open` | `the standard input is already open`、`the standard output is already open`、`the standard error is already open` |

`Fault::io_error_kind` は、`try_io` が捕まえる誤り (`Io`、`Stdin`、`NotUtf8`) に `IOErrorKind` のタグ (`IO_NOT_FOUND` 0 から `IO_OTHER` 4) を返し、ほかには `None` を返す ([標準ライブラリ](stdlib.md) の「`try_io`」)。

`Fault::panics` は、`try_panic` が捕まえる誤り (`Arith`、`Utf8`、`Index`、`InUse`) で真を返し、ほかでは偽を返す ([標準ライブラリ](stdlib.md) の「`try_panic`」)。値と入力で決まる誤りと、プログラムの順で決まる2つ目の `open` だけを `Panic` にし、どの呼び出しでも起きうるか起きた位置が決まらない誤り (`Heap`、`Output`、`Stopped`) は型に出さない。`io_error_kind` が `Some` を返す誤りとは重ならない。VM はこの2つで、誤りを `Panic` に届けるか、`IO` に届けるか、実行時エラーにするかを決める ([VM](vm.md) の「`IO` と `Panic` への中断」)。

- `name` は extern に渡されたパスの文字列そのもの (`file_root` をつなぐ前) か、`Run` ならプログラムの名前である
- `NotAvailable` は、その実行の Host が持たない入出力である。REPL の標準入力と、組み込み先の Host が実装しなかったメソッドが当たる (下の「Host」)
- I/O の誤りを文字列でなく値の種類で分けるのは、`try_io` が I/O の誤りを eml の `IOError` の値に変えるためである
- `Arith`、`Output`、`Io`、`Stdin`、`NotUtf8`、`Utf8`、`Index`、`InUse` の表示は、[LIR](lir.md) の「実行時エラー」の文言と1文字も違わない。これは verifier を通るプログラムでの約束である。`Heap(_)` の表示は `eml_rt::HeapError` のものである
- 位置 (`at path:line:column`) を付けるのは VM の役で、`Fault` は持たない
- VM は `Stopped` を、安全点の `Ctx::poll` が返す `Err(Stop)` と同じに扱う

### 誤りのときの約束

約束の書き方は、`Ctx` の基本操作と同じである (上の「基本操作の契約」)。速いモードは前提を安全の前提にし、検査モードは確かめて `Err` を返す。RC の増減は、引数の参照が減り、結果の参照が増える形で `ensures` に書く。

| 誤り | 約束 |
|---|---|
| `Heap(_)` | どの確かめも、状態を変える前、Host を呼ぶ前に行う。ヒープは変わらず、何も書かず、何も開かない。確かめるのは、種類 (文字列か、ハンドルの型の `Foreign` か)、`decref` が通ること (消費する引数に同じ物体を2つ渡したときは2回続けて通ること。`string_concat` と同じ。借りる引数は1つずつ確かめる)、ハンドルを読む extern のハンドルが一意であること (`foreign_unique`)、`read_chunk` の `buf` がバイト列で `decref` が通ること (補充の前に確かめる) である。ただし `handle_close` は、確かめた後でハンドルを手放す解放の連鎖の誤りも返しうる。バイト列の行の読みは、Host から読んで行の物体を作った後に、それを伸ばすか手放すときのモデルが照らさない誤りも返しうる (下の項) |
| `Output`、`Io`、`Stdin`、`NotUtf8`、`Utf8`、`Index`、`Stopped` | 借りる引数は成功のときと同じく手放さず、消費する引数は成功のときと同じく消費する。ハンドルの読み (`handle_read`) はハンドルを借りるので手放さない。文字列の読みとバイト列の全部の読みは、読んだバイト列を Rust の中で落とし、ヒープを変えない。`read_line_bytes_raw` は途中まで読んだ行のバイト列を手放し、`read_chunk` は消費する `buf` を手放す。`slice` は範囲と境界を確保の前に確かめ、誤りなら何も作らない。`Env.arg` は、誤りならヒープを変えない。ほかのヒープは変わらず、`held_ok` は保たれる。REPL が続けて使うためである |
| `InUse` | `handle_open` は開いた印と Host の slot を確かめ、何も作らずに返す。ヒープは変わらない |
| `ArithFault` | ヒープに触れない |

- `handle_close` の `Heap(_)` は、ヒープが変わらないか、ハンドルを手放す解放の連鎖で起きたモデルが照らさない誤り (上の「検査モードの約束」) である。モデルは `Foreign` の物体が走査する語を持たないことを知らないので、約束はこの形になる。基本操作の `evv_set`、`ev_set_state`、`yield_finish` と同じく、その後は `Ctx` を落とすことしかできない
- `foreign` と `foreign_unique` は速いモードでも型の違いを `WrongKind` で返すので、`handle_read`、`handle_close`、`handle_write`、`handle_flush` は速いモードでも `Err(Heap(WrongKind))` を返しうる。この4つは、即値のハンドルもどちらのモードでも `WrongKind` にする。`handle_read` は書くためのハンドルも `WrongKind` にする。このときヒープは変わらない。`handle_read` はハンドルを手放さない。文字列の読みとバイト列の全部の読みは、`Heap(_)` を含むどの誤りでもヒープを変えない。バイト列の行の読みの検査モードの `Heap(_)` は、引数の確かめのほかに、Host から読んだ後で作りかけの行を伸ばすか手放すときにも起きうる。そのときはヒープが変わっていて、`handle_close` と同じく、その後は `Ctx` を落とすことしかできない。塊の読みは `buf` を補充の前に確かめるので、補充の後の `Heap(_)` は、確かめた `buf` を伸ばすときのモデルが照らさない誤りだけである
- `println` は書けなくても文字列を手放し、`open` は開けなくてもパスを手放し、ハンドルの読みは誤りのときもハンドルを借りたままで手放さない。ハンドルの書き込みと `flush` は、書けなければ消費したハンドルを手放し、借りたデータは手放さない。上の約束はこの規則に従う

### 証明すること

整数の extern は、結果を vstd の spec で約束する。

- `+`、`-`、`*` は、vstd の `checked_add`、`checked_sub`、`checked_mul` の spec で約束する。収まらなければ `IntegerOverflow` である
- `negate` は `0.checked_sub(a)` で作る。vstd に `checked_neg` の spec がないためである
- `/` と `%` は、`rust_div` と `rust_rem` の spec (0 の方向に切り捨て、余りの符号は割られる数に合わせる) で約束する。0 で割れば `DivisionByZero`、`MIN / -1` と `MIN % -1` は `IntegerOverflow` である
- 比較の6つと `compare`、`Bool` の `==` と `!=` は、タグの値で約束する。`Bool` の引数には前提を置かず、タグの値の等しさで比べる

浮動小数の extern は、引数と結果を `f64` で受け渡す。VM はスロットのビット列を `f64::from_bits` で戻して渡す。

- 比較の6つ (`==`、`!=`、`<`、`<=`、`>`、`>=`) は `verus!` の中に書き、結果が `Bool` のタグであることだけを約束する。vstd は `f64` の比較の演算子に仕様を持つが、値を表さないためである
- 算術 (`+`、`-`、`*`、`/`、`%`、`negate`) と全順序の `compare` は、T12 (下の「`unsafe` の核」) で信頼する。算術の結果が NaN なら、いつも正の quiet NaN (`f64::NAN`) を返す (`canonical_nan`)。Rust は演算の結果の NaN の符号を決めず、x86_64 では符号の立った NaN になるので、そろえないと `compare` の答えがプラットフォームで変わるためである ([宣言](declarations.md) の「Prelude のクラス」)。`compare` は結果が `Ordering` のタグであることを約束する。値は期待値の表で確かめる ([テスト戦略](../implementation/testing.md) の「期待値の表」)。どれも誤りを返さない
- `Std.Float` の変換 (`of_int`、`truncate`、`floor`、`ceil`、`round`)、数学の関数 (`sqrt`、`abs`、`sin`、`cos`、`exp`、`log`、`pow`)、`infinity_value`、`nan_value`、`Prelude.shows_minus` も T12 で信頼する。本体は Rust の `f64` の関数を呼ぶだけである。数学の関数の NaN の結果も、`canonical_nan` で正の quiet NaN にそろえる。`truncate` などの4つは、結果が `Int` の範囲 `[-2^63, 2^63)` を外れれば (NaN と ±無限大も) `ArithFault::FloatToInt` を返す。誤りは元の値のビット列を持ち、文言 ``float `1e+19` does not fit in `Int` `` の値は `show` の形で書く。`shows_minus` は結果が `Bool` のタグであることを約束する
- `Show Float` の `show`、`to_fixed`、`parse` の書式と読みも T12 で信頼する。`float_repr` が Python の `repr` の形 (正しく丸めた最短の桁が読み戻せない 2 の冪では、`{:e}` の桁を使う) を、`float_fixed` が Python の `f"{x:.{n}f}"` の形を、Rust の `format!` で作る。`float_parse` は前後の空白を除いて `str::parse` で読む。結果の文字列は `Ctx::float_show` と `float_to_fixed` が `fresh_string` で作り、`string_to_float` は文字列の引数を `env_has` と同じく借りて読んで手放す。この3つは `verus!` の中で確かめる。`to_fixed` の桁数が 0 から 100 の外なら、何も作らずに `ArithFault::FixedDigits` を返す

文字列の extern は、結果を ghost のバイト列の spec で約束する。文字列のバイト列は、T10 の `bytes` の上に書いた `text` で `str` として借りて読む。

- `==` と `!=` は、長さが違えば先に返し、同じなら slice の `==` で比べる。slice の `==` は vstd に spec があるので、信頼は要らない
- `compare` は、辞書式の順序 (バイトの順) の spec `lex(a, b)` に一致することを約束する。比べるのは `<[u8] as Ord>::cmp` を1回呼ぶ包み `bytes_cmp` で、その結果が `lex` に一致することを T5 で信頼する。長さで先に返す近道は使わない (`"b" > "ab"` のため)
- `++` は、`string_concat` の約束 (上の「バイト列と文字列」) をそのまま使う。左が一意ならその場で連結する
- `Int.show` は、ghost のバイト列が spec `decimal(i)` (負なら `-`、続けて先頭に 0 のない10進の数字。0 は `"0"`) に等しいことを証明する。数字は `u64` の絶対値から作る (`-i64::MIN` は溢れるため)。20 バイトの作業領域 (`"-9223372036854775808"` がちょうど 20 バイト) に後ろから書き、ASCII なら UTF-8 であることを証明して `from_utf8_unchecked` で `&str` にし、`alloc_string` で作る
- `Char.show` と `Char.display` は、ghost のバイト列が spec `char_show_spec(c)` (`'` で囲んだ `escape_char(c)`) と `char_display_spec(c)` (vstd の `encode_scalar`) に等しいことを証明する。`requires` はスカラー値であること。ASCII の文字は `String.show` と同じ `escape_byte` の規則に `'` の escape を足して書き、ASCII でない文字は `encode_scalar` の式のとおりに書く。結果が UTF-8 であることは、ASCII の補題と vstd の `encode_utf8_valid_utf8` で証明し、`from_utf8_unchecked` で `&str` にして `alloc_string` で作る
- `String.show` は、ghost のバイト列がバイトの単位の spec `escape(bytes)` に等しいことを証明する
  - 全体を `"` で囲む。`"` と `\` には `\` を前に付ける。`\n`、`\t`、`\r`、`\0` は名前付きのエスケープにする。そのほかの制御文字 (0x01〜0x1F と 0x7F) は `\u{16進の小文字、桁埋めなし}` にする。それ以外のバイトは、0x80 以上も含めてそのまま写す
  - C1 の制御文字 (U+0080〜U+009F) もそのまま写す。UTF-8 の先頭と続きのバイトはどれも 0x80 以上なので、バイトの単位の規則は、文字の単位の規則と同じ結果になる
  - 1回目の走査で結果の長さを数え (桁あふれは `checked_add` で確かめる)、`alloc_string_room` でその容量の空の文字列を1回だけ確保する。2回目の走査で、エスケープのない区間はまとめて写し、エスケープは短い ASCII の列を足す。どれも容量に収まるので、作り直しは起きない
  - 足すのは、`string_push` と同じ道の内部の関数 (`append_str` と `append_part`) である。公開の `string_push` は検査モードで確かめ直し、その場で足すことを約束しないので使わない
  - 区間を写すときは、写す元の文字列を `text` で借りた `&str` を、vstd の `str::split_at` で `[from, to)` に切って渡す。そのため T10 に関数を足さない。切る位置が文字の境目であることは、「正しい UTF-8 の列で、ASCII のバイトの直前と直後は文字の境目である」という補題で示す。結果が UTF-8 であることは `valid_utf8_concat` から出る
- 文字列の核 (`String.byte_length`、`byte_at`、`char_at`、`slice`、`find_from`) は、位置を UTF-8 のバイトの位置で読む ([標準ライブラリ](stdlib.md) の「`String`」)
  - `byte_length` は ghost のバイト列の長さを、`byte_at` は範囲の中ならその位置のバイトを約束する
  - `char_at` は、範囲の中で位置が vstd の `is_char_boundary` を満たすとき、結果が `decode_first_scalar(text[i..])` に等しいスカラー値であることを約束する。範囲の外は `byte_at` と同じ誤りを、境界でない位置は `IndexFault::NotBoundary` を返す
    - 境界は、その位置のバイトが続きのバイト (0x80〜0xBF) でないことで確かめる。vstd の `is_char_boundary_iff_not_is_continuation_byte` が、これを `is_char_boundary` に結ぶ
    - `text[i..]` が UTF-8 であることは `valid_utf8_split` から出す。そこから、先頭の1文字の幅だけバイトがあること、長すぎる符号化でないこと、サロゲートでないことが出る。スカラー値であることは、この3つと幅ごとの値の上限から示す
    - 値は、幅ごとの分岐を vstd の `codepoint_width_1` から `codepoint_width_4` と同じ式で組む。ASCII の分岐を先に置く
  - `slice` は、範囲の中で両端が vstd の `is_char_boundary` を満たすとき、結果の ghost のバイト列が部分の列に等しいことを約束する。結果は `String.show` と同じ道 (`alloc_string_room` と `append_part`) で作る。部分が UTF-8 であることは、ASCII の補題と同じく `valid_utf8_split` から出す (`lemma_boundary_in_prefix`)。範囲と境界は確保の前に確かめる
- `String.push` は、結果の ghost のバイト列が `text + encode_scalar(c)` に等しいことを約束する。`requires` はスカラー値であること。符号化は `Char.display` と同じ `encode_char` で、足すのは `string_push` である (上の「文字列の操作」)
  - `find_from` は、開始位置以降で探す文字列と一致する最小の位置か、なければ -1 であることを約束する (spec `found_from`)。照合は、探す文字列の先頭のバイトを T13 の `find_byte` (下の「`unsafe` の核」) で探し、見つけた位置ごとに残りのバイトを比べる。先頭のバイトがない位置では一致しないことを、`find_byte` の約束から証明する
- 検査モードでは、引数が `String` の物体でなければ `Heap(WrongKind)` を返す。速いモードは、読めることと所有を前提にする

バイト列の extern (`Bytes.empty`、`length`、`append`、`append_slice`、`slice`、`truncate`、`of_string`、`find_from`、`find_byte_from` と `Bytes` の `==`、`!=`、`compare`) も、結果を ghost のバイト列の spec で約束する。物体の本体は文字列と同じで、種類が `Bytes` であることだけが違う。

- `append`、`append_slice`、`slice`、`truncate` の結果は、`text_of` が `a + b`、`dst + src[from..to]`、`s[start..end]`、`w[0..n]` に等しい。範囲の誤りは確保の前に返す
- `find_from` は文字列の `find_from` と同じ spec `found_from` を約束し、照合も同じである。開始位置が `0 <= from <= len` でなければ `IndexFault::BytesIndex` を返す
- `find_byte_from` は、開始位置以降でバイトが等しい最小の位置か、なければ -1 であることを約束する (spec `found_byte`)。探すのは T13 の `find_byte` で、結果はその約束から出る。開始位置の誤りは `find_from` と同じである
- `empty` は `Bytes.make` と同じ道で作る長さ 0 のバイト列で、確保量の上限を確かめる
- `Ctx::bytes_valid_utf8` は、結果が vstd の `valid_utf8` に一致することを約束する。バイト列は借りるだけで、手放さない
- `String.decode` は、妥当なバイト列には同じバイトの `String` を返し、妥当でなければ `Fault::Utf8` を返す。どちらのときも `b` の参照を手放す。検査モードでは、引数が `Bytes` の物体でなければ `Heap(WrongKind)` を返す
- 検査モードでは、引数が `Bytes` の物体でなければ `Heap(WrongKind)` を返す。`String` の物体も断る

I/O の extern (`println`、`eprintln`、`FileIn.open`、標準のストリームの `open`、ハンドルの読みと書き込み、`Stdout.flush`、`close`、`Fs.write_text`、`Env` と `Proc.status` の extern) は、メモリの安全と、RC のモデルでの増減を証明する。引数を消費すること (借りるハンドルと、書き込みの借りるデータは参照の数を変えないこと。書き込みと `flush` は受け取ったハンドルをそのまま返すこと)、結果を持つこと、ハンドルの種類と `lin` ビット、誤りのときに作りかけの物体を手放すことを含む。OS とのやりとりの中身 (何が書かれ、何が読めたか) は約束せず、T11 (下の「`unsafe` の核」) と期待値の表 ([テスト戦略](../implementation/testing.md) の「期待値の表」) に任せる。ハンドルの読みの結果は `alloc_string`、`alloc_bytes`、`bytes_extend` で作るので、ghost のバイト列と、文字列なら UTF-8 であることは、今ある約束と `read_text` の約束から出る。

### Host

OS とのやりとりは、セッションに1つの Host にまとめ、`Ctx` が持つ。

```rust
pub trait Host: Send + Sync {
    fn write_line(&self, stream: Stream, line: &str) -> io::Result<()>;
    fn write(&self, stream: Stream, bytes: &[u8]) -> io::Result<()>;
    fn flush(&self) -> io::Result<()>;
    fn open(&self, path: &str) -> io::Result<Opened>;
    fn args(&self) -> &[OsString] { &[] }
    fn env_var(&self, name: &str) -> Option<OsString> { None }
    fn stdin(&self) -> Option<Arc<StdinSlot>> { None }
    fn write_file(&self, path: &str, text: &str) -> io::Result<()> { /* Unsupported */ }
    fn run(&self, program: &str, args: &[&str]) -> io::Result<i32> { /* Unsupported */ }
}

pub struct Opened {
    pub reader: Box<dyn Read + Send>,
    pub size: Option<u64>,
}
```

- `write_line` は、本文と `\n` を、ほかの行と途中で混ざらないように書く。`&str` を受けるのは、eml の文字列は UTF-8 が証明されており、テキストしか受けない出力先 (WASM の console、GUI) にも渡せるためである。`Stream` は `Out` と `Err` で、標準エラーは `eprintln` と `Stderr` のハンドルが使う
- `write` は、バイト列をそのまま、ほかの書き込みと途中で混ざらないように書く。書くためのハンドルの `write` と `write_string` が使う。バイト列は UTF-8 とは限らないので、テキストしか受けない出力先の Host は、受けられないバイトの扱いを自分で決める
- `open` は、読み手と、読む前に分かる長さ (ふつうのファイルならメタデータの長さ) を返す。読み手は buffer のない `Read` でよい。buffer は `eml_rt` の読み手 (下の「読み手」) が持ち、標準入力と `FileIn` が同じ読みの部品を使うためである
- `Ctx` は Host を不透明な型 `HostRef` で持ち、何も約束しない関数を通して呼ぶ (下の「`unsafe` の核」の T11)。Verus は `dyn Host` も `io::Error` も扱えないためである。`HostRef` は `Arc<dyn Host>` を `ManuallyDrop` の欄に持ち、`Drop` で `#[inline(never)]` の関数に渡して手放す。標準のストリームのハンドルの開いた印 `Arc<OpenFlags>` も持ち (下の「出力のバッファ」)、`HostRef` の写しは印を共有する。`Control` と凍結した領域の鎖と同じ形で、`Ctx` を使うコードのコード生成単位の分け方を変えないための予防である。`Ctx` 自身は、今と同じく `Drop` を実装しない
- `Ctx::new(control, host)` で受け取る。`par` の子の `Ctx` は、同じ Host を `Arc` で写して持つ
- `Send + Sync` を求めるので、`JsValue` を持つブラウザの Host は `unsafe impl` が要る。これは受け入れる
- Host を総称の型引数 (`Ctx<M, H>`) にはしない。基本操作がすべて `H` ごとにも単相化され、証明にも `H` が入るためである。動的な呼び出しの分は、書き込みの費用と比べて小さい ([計測の基準](../implementation/benchmarks.md) の「出力のバッファと Host の呼び出し」)
- ネイティブ、WASM (WASI)、アプリへの組み込み、REPL は、渡す Host を替えるだけで済む。標準入力、環境変数、子のプロセスなどの extern を足すときも、Host のメソッドを足す
- `args`、`env_var`、`stdin`、`write_file`、`run` は、その入出力を持たない Host の振る舞いを既定に持つ。引数は空、環境変数は設定されていない、標準入力はない (`None`。extern の理由は `not available`)、ほかは `Unsupported` の誤り (extern の理由は同じく `not available`) である。組み込み先の Host は、出力とファイルの読みだけを実装すれば済む
- `stdin` は、Host が持つ標準入力の読み手の slot (`Arc<StdinSlot>`) を返す。`Stdin.open` が slot から読み手を取り、ハンドルを落とすときに buffer に残ったバイトごと返す (下の「読み手」)。Host のメソッドは `&self` を受けるので、slot は中の `Mutex` で守る。`StdinSlot::new(reader)` は、buffer のない `Read` を受けて読み手にする
- `run` は、`PATH` からプログラムを探して子を起動し、終わるのを待って終了コードを返す。シグナルで終わった子は、シェルと同じく 128 + 番号にする (`exit_code`)

### 出力のバッファ

`eml_rt` は Host の実装 `StdHost` を持つ。ネイティブのプログラムも `eml_rt` をつないで、同じ方針を使うためである。

- `StdHost::stdio(file_root)` は、標準出力と標準エラーに書く。`StdHost::new(out, err, file_root, mode)` は、テストと組み込みのために書き込み先と書き方 (`Buffering` の `Line` か `Block`) を受ける。どちらも引数と標準入力を持たず (REPL の Host)、`with_args` と `with_stdin` で足す (`eml run` の Host。[VM](vm.md) の「置き場所」)。`with_stdin` は buffer のない `Read` を受けて slot に置き、`eml run` は `io::stdin()` をそのまま渡す
- `StdHost` の `env_var` はプロセスの環境を読む。空の名前と、`=` か NUL を含む名前は `std::env::var_os` が panic しうるので、読まずに `None` を返す。`write_file` は `file_root` にパスをつないで、作るか切り詰めて書く。`run` は、子に標準入出力と環境を受け継がせ、`file_root` が空でなければそこを作業ディレクトリにする
- 出力の方針は C の stdio と同じにする。標準出力が端末なら、対話ですぐ見えるように行ごとに書く (`Line`)。端末でなければ、64 KiB の `BufWriter` でまとめて書く (`Block`)。標準エラーは、いつも書くたびに書き出す
- バイト列の書き込み (`Host::write`) は、標準出力が `Line` なら、`\n` を含むときに書き出す。`\n` を探す走査は `Line` のときだけ行い、`Block` の書き込みには費用を足さない。標準エラーへの書き込みは、`write_line` と同じく書くたびに書き出す
- まとめて書くと、行ごとに flush する書き方より速い ([計測の基準](../implementation/benchmarks.md) の「出力のバッファと Host の呼び出し」)
- ストリームごとに `Mutex` を1つ持ち、ロックの中で本文と `\n` を書く。`write` も1回の呼び出しをロックの中で書く。ロックが毒されていたら、`PoisonError::into_inner` で取り出して続ける。中身は書き込みのバッファだけで、続けても壊れないためである
- `StdHost` を落とすときは、`BufWriter` の `Drop` がまだ書いていない出力を書く (unwind のときも同じ)。誤りは捨てる
- `StdHost::open` は、`file_root` に `path` をつないで開く。`path` が絶対パスなら、そのパスを開く。長さの見込みは、ふつうのファイルにだけ返す。ディレクトリも開け、読むときに `I/O error` になる
- `Ctx::flush() -> Result<(), Fault>` は、Host の `flush` を呼ぶ。ヒープには触れない。VM は次の所で呼ぶ
  - プログラムの終わり
  - 実行時エラーを出す前。`> out 2>&1` のときに、出力と誤りの順を保つためである
  - 割り込みと上限で止めたとき
  - 標準入力の読み手を補充する前 (標準入力のハンドルの読み。下の「読み手」) と、REPL の入力の区切り。buffer から読むときは書き出さない ([標準ライブラリ](stdlib.md) の「`Stdin`」)
- Host の `run` は、子を起動する前に標準出力を書き出す。子と eml の出力が順に並ぶようにするためである
- `Ctx::print_line(line) -> Result<(), Fault>` は、Rust の文字列 `line` を `Stream::Out` に1行として書き (`write_line`)、続けて書き出す (`flush`)。REPL が整形した結果を書くのに使う ([REPL の端末](repl.md) の「結果の表示」)。どちらかが誤りなら `Fault::Output` を返す。ヒープには触れない
- まとめて書くと、書き込みの誤り (`| head` での EPIPE など) が見つかるのは、後でバッファがあふれた `println` か、終わりの flush になる。そのため `println` の `Err(Output)` は、「この行か、それより前の行を書けなかった」ことを表す。終わりの flush の誤りは、VM が位置なしで出す
- 2回目の Ctrl-C ですぐ終わるときは、まだ書いていない出力は失われる (C と同じ)
- 標準出力と標準エラーのハンドルは、`StdoutHandle` と `StderrHandle` を中身にした `Foreign` の物体で、作るときに `lin` ビットを立てる。中身は開いた印 (`Arc<OpenFlags>`) だけで、buffer を持たない。ハンドルの書き込みも `println` と `eprintln` と同じ Host の buffer に書くので、ハンドルを `close`、巻き戻し、`exit`、`Heap` を落とすときの破棄処理のどれで手放しても、書いた出力は失われない。2つの型を分けるのは、`foreign` の型の確かめが2つのハンドルの取り違えを捕まえるためである
- 開いた印 `OpenFlags` は、標準入力、標準出力、標準エラーの3つの atomic の印で、`HostRef` ごとに持ち、写した `HostRef` (`par` の worker の `Ctx`) と共有する。`Ctx::handle_open(Handle::Stdout)` と `Handle::Stderr` は、信頼の関数 `open_stream(host, stream)` で印を立て、その印を持つハンドルを `OutputHandle` (`Stdout(StdoutHandle)` か `Stderr(StderrHandle)`) で受け取る。印がすでに立っていれば、何も作らずに `InUse` を返す。2つのハンドルを作れるのは `open_stream` だけで、その `ensures` が `stream` とハンドルの型の組を決めるので、検証したコードは一方の印を他方のハンドルに持たせられない。中身の `Drop` は印を下ろすだけで、失敗せず I/O をしないので、どのスレッドで落としてもよい。標準入力のハンドルも同じ印を立てる (下の「読み手」)
- `Ctx::handle_write(h, stream, data, write)` は、データ `data` を借りて Host に書き、受け取ったハンドル `h` をそのまま返す。`write` が `Write::Bytes` ならバイト列を、`Text` なら文字列のバイト列を `Host::write` で書き、`Line` なら文字列を `Host::write_line` で1行として書く。`stream` のハンドルでない `h` は、どちらのモードでも `WrongKind` で断る。確かめはどれも Host を呼ぶ前に済ませる。証明は、借りたデータを含め、呼ぶ前から生きている物体の参照の数が変わらないこと (`evolved_by` の変化が 0) と、呼ぶ側が `h` を持ったままであることを言う。書けなければ `h` を `handle_close` で手放してから `Output` を返す
- `Ctx::handle_flush(h)` は、標準出力のハンドル `h` を受け、Host の `flush` を呼んで `h` をそのまま返す。ヒープは変わらない。書き出せなければ、`handle_write` と同じく `h` を手放してから `Output` を返す

### 読み手

- 読み手 `Reader { inner: Box<dyn Read + Send>, buf: Box<[u8]>, pos, filled }` は、Host が渡した読み手 `inner` と 64 KiB の buffer を持つ。Verus には `external_body` の不透明な型として見せる。buffer は最初の補充で確保する。全部を読むだけの `FileIn` は buffer を使わないためである
- `Reader::fill_buf(control, host)` は、buffer に残ったバイトの slice を返す。残りがなければ、1回補充してから返す。補充では、止める語と確保量を見てから (下の `FileIn.read_all` の 3 と同じ確かめで、`Vec` の領域は 0)、`inner` の `read` を1回呼んで最大 64 KiB を読む。止める語の立っていない `Interrupted` は読み直し、立っていれば次の確かめで止める。読みの誤りは、止める語が立っていれば `Stopped`、立っていなければ `Io` である。終わりなら空の slice を返す。`read` が渡した buffer より大きい長さを返したら (`Read` の約束を破る読み手)、`pos` と `filled` を書く前に `Io(Other)` で断る。読み手は壊れずに次の読みへ残る
- `host` を渡すと、`fill_buf` は補充の前に Host の `flush` を呼ぶ。標準入力の読みが使う (上の「出力のバッファ」)。書き出せなければ `Failure::Output` になる
- `Reader::consume(n)` は、`fill_buf` が返したバイトの先頭の `n` バイトを使ったことにする
- `fill_buf` と `consume` は安全なメソッドで、slice の寿命は読み手の借用に縛られる。`verus!` の外の読みの部品 (`read_line`、`read_all`) はこれを使うので、次の補充の後に古い slice を読むコードはコンパイルできない
- 検証した `Ctx` のコードは、`foreign_unique` で借りたハンドルの生のポインタしか持たず、不透明なハンドルの欄 (読み手やパス) を開けない。そのため、読み手を読む入口は、ハンドルの型 `S` について総称の信頼の関数 `fill(src: *mut S, control, host) -> Result<&[u8], Fault>` と `consume(src: *mut S, n)` にする。`S` は安全な trait `Source` を実装する。`Source::reader` がハンドルの読み手を返し (読み手のないハンドルは `None` で、読みは `not available` の誤りになる)、`Source::take_size` がまだ使っていない長さの見込みを取り出し、`Source::name` が誤りに付ける名前 (`SourceName` の `FileIn(path)` か `Stdin`) を返す。読みの誤り (`Failure` の `Io`、`Stopped`、`Output`、`NotUtf8`) を `Fault` にするのは信頼の関数の側で、`FileIn` の `Io` は `Io { op: Read, name: path, reason }`、`NotUtf8` は `NotUtf8(FileIn(path))`、標準入力の `Io` は `Stdin(reason)`、`NotUtf8` は `NotUtf8(Stdin)` である。この対応は `Fault::Heap` を作らないので、`fill` と `read_text` の約束は `Source` の実装に依らない。`fill` の中身は、`fill_buf` と `consume` を呼んで、slice の寿命を呼ぶ側の約束に付け替えるだけである
- `fill` が返す slice は、次に同じハンドルを使うか (`fill`、`consume`、そのほかハンドルを受ける T11 の関数のどれでも)、ハンドルを落とすまで読める。slice は読み手の buffer を指し、ヒープのページを指さないので、その間にヒープで確保しても解放してもよい (下の「`unsafe` の核」の T11)
- Rust の buffer に読む読み (文字列の読みと、バイト列の全部の読み) は、総称の信頼の関数 `read_text(src: *mut S, control, host, line, form) -> Result<Vec<u8>, Fault>` で読む。`line` なら `read_line` で次の `\n` まで、そうでなければ `Source::take_size` の見込みを渡して `read_all` で終わりまで読む。`form` が `Form::Text` なら `str::from_utf8` で確かめ、`ensures` で結果が vstd の `valid_utf8` を満たすと約束する。検証したコードはそれを使って `str::from_utf8_unchecked` で `&str` にする。誤りには `fill` と同じく `Source::name` の名前を付ける。UTF-8 でなければ `Failure::NotUtf8` の誤りにする
- `Ctx::handle_read(h, handle, read, form)` は、ハンドル `h` を `foreign_unique` で借りて読み、結果の物体だけを返す。`handle` が中身の型 (`Handle::FileIn` か `Handle::Stdin`)、`read` が量 (`ReadAmount::All`、`Line`、`Chunk(buf)`)、`form` が形 (`Form::Text` か `Form::Bytes`) を決める。組は作らず、`h` の参照は呼ぶ側に残る。`Handle::Stdin` なら、`fill` と `read_text` に Host を渡し、補充の前ごとに標準出力を書き出させる (上の「出力のバッファ」)
  - 全部の読みと文字列の行の読みは `read_text` で読み、`alloc_string` か `alloc_bytes` でヒープへ1回写す。証明は、呼ぶ前から生きている物体の参照の数を変えないことを言う (`evolved_by` の変化が 0)。読みの誤り、UTF-8 でない中身、止めたときも、ハンドルを手放さず、ヒープを変えない
  - バイト列の行の読みは、検証したコードが `fill` と `consume` を呼び、`fill` が返した読み手の buffer の slice をそのまま `alloc_bytes` に渡し、補充をまたぐ行は `Heap::bytes_extend` で伸ばす。`\n` は、buffer の中を T13 の `find_byte` (下の「`unsafe` の核」) で探す。1つの buffer に収まる行は、buffer から1回だけ写す。補充をまたぐ行は、最初の部分を空きのない物体に作るので、伸ばすたびに作り直しうる。作り直しは `Bytes.push` と同じく容量を倍にし、それまでの部分を写し直すので、長い行の写しの合計は行の長さの約3倍以下になる。証明は全部の読みと同じく `evolved_by` の変化が 0 であることを言う。ループの不変条件は、呼ぶ前のヒープから物体を作って伸ばしただけで、呼ぶ前に生きていた物体はみな同じブロックのまま生きていることである (`bytes_extend` が約束する `others_kept`)。止まることは、読んだ長さの和を `checked_add` で数え、それが増えることで示す。読みの誤りと止めたときは、途中まで読んだ行を手放してから返す
  - 塊の読み `Chunk(buf)` は `buf` を消費する。`fill` が返した slice を `bytes_extend(buf, slice)` で足してから、その長さを `consume` する。結果はいつもバイト列で、`form` を見ない。証明は `Bytes.push` と同じ変化 (`buf` の参照を結果の参照に替える) を言う。読みの誤りと止めたときは `buf` を手放してから返す
- 標準入力の読み手は、Host の slot `StdinSlot` (`Mutex<Option<Reader>>`) に置く。`Ctx::handle_open(Handle::Stdin)` (`Stdin.open`) は、信頼の関数 `open_stdin` で slot から読み手を取り出し、`StdinHandle { reader: Option<Reader>, slot: Option<Arc<StdinSlot>>, flags: Arc<OpenFlags> }` を中身にした `Foreign` の物体を、`lin` ビットを立てて作る。`open_stdin` は、先に `HostRef` の標準入力の印を立てる (上の「出力のバッファ」)。印がすでに立っていれば、ほかのハンドルが開いているので、何も作らずに `InUse(Stdin)` を返す。slot が空なら、同じ Host の別の `HostRef` のハンドルが読み手を持っているので、印を下ろして同じく `InUse(Stdin)` を返す。Host が slot を持たなければ、読み手のないハンドルを作り、その読みは `Stdin(NotAvailable)` になる。この Host でも印は同じく働くので、生きている標準入力のハンドルは高々1つである。`StdinHandle` の `Drop` は、読み手を buffer に残ったバイトごと slot に返してから、印を下ろす。lock を取るだけで、失敗せず I/O をしないので、`close`、巻き戻し、`Heap` を落とすときの破棄処理のどれで落としてもよく、どのスレッドで落としてもよい。そのため、同じ Host で `Machine::run` を繰り返しても、読んでいない入力が残る。ロックが毒されていたら、中身を取り出して続ける。中身は読み手だけで、続けても壊れないためである
- `FileIn` の物体は、`Foreign` の中身を `FileIn { path: Box<str>, reader: Reader, size: Option<u64> }` にしたもので、作るときに `lin` ビットを立てる。Verus には `external_body` の不透明な型として見せる
- 閉じる処理は、`FileIn` の drop glue だけである (手で書いた `Drop` は置かない)。どのスレッドで落としてもよい ([マルチコア対応の設計](../future/multicore.md) の「スレッドに縛られたリソース」)
- `FileIn.open`: 確かめの後、借りたパスの `&str` を Host の `open` に渡す。パスは1回だけ写して `FileIn` に持たせる。開けたら `FileIn` の物体を作ってから、パスの文字列を手放す。先に手放すと、空けたパスの箱を `FileIn` が使い回しうるので、呼ぶ前からの変化を証明で言えないためである。Host が誤りを返せば、パスを手放して `Io { op: Open, .. }` を返す
- `FileIn.close`、`Stdin.close`、`Stdout.close`、`Stderr.close` (`Ctx::handle_close`): 検査モードは型と `decref` の前提を確かめ、その後 `decref` するだけである。閉じる処理は中身の破棄処理である
- `FileIn.read_all`
  1. `FileIn` は、局所で rc が 1 で、今の worker が持つものでなければならない。中の読み手を書き換えるためである。`foreign_unique` で借り、検査モードは確かめて `NotUnique` か `WrongOwner` を返す。速いモードでは安全の前提にする
  2. 長さの見込みを取り出す (`Option::take`)。見込みがあれば、その大きさで 3 の確かめをしてから、`Vec<u8>` に `try_reserve` する。確保より先に上限と比べるので、確保できないほど大きい見込みも、上限があれば I/O の誤りでなく `Stopped(MemoryLimit)` になる。確保の失敗は `Io { op: Read, reason: Other }` にする (今の `read_to_end` と同じ)。2回目の `FileIn.read_all` には見込みがないので、余分に確保しない。その後、読み手の buffer に残ったバイト (前の `FileIn.read_line_raw` が読んだ分) を `Vec` に移す。3 と 4 は buffer を通さずに `inner` を読む
  3. 64 KiB ずつ読む。区切りの前ごとに、`Vec` の容量で次の確かめをする
     - 止める語が立っていれば、`Stopped` で止める。理由は `Ctx::poll` と同じ関数 `stop_reason` で決める (`INTERRUPT` なら `Interrupted`、`MEMORY` なら `MemoryLimit`)
     - 次に、領域の大きさと `Control` の確保量の和を上限 `max_bytes` と比べ、超えれば `Stopped(MemoryLimit)` で止める。`Vec` はヒープの外にあり、そのままでは上限に数えられないためである
  4. 各区切りは `take(64 KiB).read_to_end(&mut vec)` で読み、0 バイトなら終わる。std が、短い読みと、終わりを小さな読みで確かめることを受け持つ。読み手は `StopOnInterrupt` で包む。中の読み手が `Interrupted` を返したとき、止める語が立っていれば `Interrupted` でない誤りに変えて返し、立っていなければそのまま返して `read_to_end` に読み直させる。中の読み手が渡した buffer より大きい長さを返したら、`StopOnInterrupt` が誤りに変える (`fill_buf` と同じく `Io(Other)` になる)。そのまま返すと `read_to_end` が std の中で panic するためである。区切りの読みが誤りを返したとき、止める語が立っていれば `Stopped` で止め、立っていなければ `Io` の誤りにする。SIGINT のハンドラが `SA_RESTART` を外して入れるので ([VM](vm.md) の「上限と割り込み」)、待っている読みは `EINTR` で戻り、この道で止まる。`StopOnInterrupt` は `read_buf` を実装できない (stable の Rust) ので、`read_to_end` は空き領域を各バイトにつき1回 0 で埋めてから読む。測った費用は [計測の基準](../implementation/benchmarks.md) の「`FileIn.read_all` の読み方」にある
  5. 読み終えたら `String::from_utf8` で確かめ、`alloc_string(&str)` でヒープへ写し、`Vec` を手放す
  6. 結果は文字列だけで、組は作らない。`FileIn` の参照は呼ぶ側に残り、宣言の型の組 `(String, FileIn)` は translate が作る ([Core IR](core-ir.md) の「組を返す extern」)
  - 読みの誤りなら `Io { op: Read, .. }`、UTF-8 でなければ `NotUtf8`、止めたら `Stopped` を返す。どのときも `Vec` を手放し、`FileIn` は手放さない。`try_io` の下では巻き戻しが `FileIn` を手放して閉じ、実行時エラーなら実行が止まる
- `FileIn.read_line_raw` も同じ `Ctx::handle_read` で、`ReadAmount::Line` で読む。1、5、6 と誤りのときの扱いは `FileIn.read_all` と同じで、違いは次の2つである
  - 長さの見込みはファイル全体の長さなので、確保に使わずに取り出して捨てる。読んだ後の残りの長さとは合わないためである
  - 下の標準入力の1行の読みと同じく、`fill` と `consume` で次の `\n` まで (それを含めて) 写す。`\n` は、buffer の中を T13 の `find_byte` (下の「`unsafe` の核」) で探す。buffer に `\n` がなければ buffer の残りをすべて写し、補充して続ける。64 KiB を超える行も、補充の前ごとに 3 の確かめをしながら読み続ける。終わりなら空の文字列を返す
- `FileIn.read_all_bytes` は `FileIn.read_all` と同じ手順で、5 の確かめをせず `alloc_bytes` で写す。UTF-8 でなくても失敗しない
- `FileIn.read_line_bytes_raw` は `FileIn.read_line_raw` と同じく見込みを使わず、上のバイト列の行の読みで写す。`fill` が 64 KiB の補充の前ごとに 3 の確かめ (`Vec` の領域は 0) をするので、長い行の途中でも止まれる。伸ばす行はヒープの物体なので、確保量に数えられる
- `FileIn.read_chunk` は上の塊の読みで、buffer に残りがあれば補充しない。1回で足すのは 64 KiB 以下である
- ヒープに直接読む形、mmap で読む形、`Vec` をそのままヒープの文字列にする形は採らない。計測と理由は [計測の基準](../implementation/benchmarks.md) の「`FileIn.read_all` の読み方」にある
- 標準入力の読み (`Std.Stdin.read_all`、`read_line_raw`、`read_all_bytes`、`read_line_bytes_raw`、`read_chunk`) は、ハンドルの読み手を `FileIn` と同じ `handle_read` の道で読み、同じく区切りごとに止める語と確保量を見る。長さの見込みは持たない。1行の読みは、std の `read_until` を使わず `fill_buf` と `consume` で `\n` まで写す。`read_until` は `Interrupted` を自分で読み直すので、止める語を見られないためである。補充の前ごとに標準出力を書き出す (行の途中の補充と、buffer が空の塊の読みも含む)。全部の読みは、buffer の残りを移した後、`inner` を読む前に1回書き出す
- `Proc.status` は、子を起動する前と、子が終わった後に止める語を見る。待つ間の Ctrl-C は同じプロセスグループの子にも届くので、子が終わって待ちから戻る。起動と同時に届いた Ctrl-C は子に届かないことがあり、そのときは子が終わってから止まる
- 読む途中か待つ間に止める語を見るのは、`FileIn` の読み (`FileIn.read_all`、`read_line_raw`、`read_all_bytes`、`read_line_bytes_raw`、`read_chunk`)、標準入力の読み、`Proc.status` だけである。ほかの extern は短い時間で終わるので、安全点を通らない

### 仕事の回数

検査モードの `CtxStats` の `string_bytes_copied` は、extern がヒープの文字列とバイト列の物体に写したバイト数である。VM の `RunStats` の `string_bytes_copied` はこの数である ([VM](vm.md) の「`RunStats`」)。

- `Int.show`: 数字の列の長さ
- `Char.show`、`Char.display`: 結果の長さ
- `String.show`: 結果の長さ
- `FileIn.read_all`: ファイルの長さ
- `FileIn.read_line_raw`: 読んだ行の長さ (行の終わりを含む)
- `FileIn.read_all_bytes`: 読んだ長さ
- `FileIn.read_line_bytes_raw`: 読んだ行の長さ (行の終わりを含む)。補充をまたぐ行を伸ばすときの作り直しは、一意な左に足す `++` と同じく数えない
- `FileIn.read_chunk`: `Bytes.push` と同じく、一意な `buf` には足した長さだけを数え、共有か不死の `buf` には `buf` の長さも足して数える
- `String.slice`: 結果の長さ
- 標準入力の読み: `FileIn` の同じ名前の読みと同じ
- `Env.arg`、`Env.lookup`: 写した文字列の長さ
- `++`: 左が一意 (rc 1 の局所の物体) なら右の長さだけを数え、容量が足りずに作り直しても同じである。左が共有か不死なら、両辺の長さを数える
- `Bytes.make`、`Bytes.slice`: 結果の長さ
- `Bytes.of_string`、`String.decode`: 一意な引数は種類だけを書き換えるので数えない。共有か不死の引数は、写したバイトの数を数える。`decode` が `Utf8` を返すときは数えない
- `Bytes.append`、`Bytes.push`、`Bytes.append_slice`: `++` と同じく、一意な左には足した長さだけを数え、共有か不死の左には左の長さも足して数える。`push` の足す長さは 1 で、`append_slice` は範囲の長さである
- `String.push`: `Bytes.push` と同じく数える。足す長さは、その `Char` の UTF-8 のバイト数である
- `Bytes.set`、`Bytes.truncate`: 一意ならその場で書き換えるので数えない。共有か不死なら、写した結果の長さを数える

## `unsafe` の核

- `unsafe` は小さい核に閉じる。核は、確保器、ヘッダとフィールドの読み書き、バイト列の読み書き、`dup`、`decref`、解放の連鎖、token の操作である。それ以外 (`share` のたどり、`release` の組み立て、生存の列挙) は核の操作を呼んで書く
- 核では SeqCst と `fence` を使わない
- `eml_rt` のコードは、核を含めて Verus の `verus!` の中に書き、`cargo verus verify -p eml_rt` が crate 全体を検証する ([テスト戦略](../implementation/testing.md) の「Verus」)。生のポインタの読み書きは、どれも Verus の権限 (`PointsTo`) の上で行う。証明するのは、公開の操作の前提 (上の「核の操作」の表) の下でのメモリの安全、ヒープの形の不変条件、RC と抽象のモデルの対応、`share` と `release` と reuse の遷移、上の「検査モードの約束」の性質である
- 確保と atomic の操作は、std の関数を薄い関数で包み、その関数の約束を信頼する (下の表の T1 と T2)。vstd の確保は失敗すると `process::abort` を呼び、vstd の atomic は SeqCst だけを扱うので、使わない。包みは std の関数を1回呼ぶだけで、型を差し替える層ではない

Verus で確かめない部分は、次の信頼の一覧にまとめる。`external_body`、`assume_specification` などの信頼の項目は、どれもこの表のどれかに属する。`eml_rt` の `trust.rs` のテストが、テストでないコードの項目を探し、表の番号を付けた一覧と同じであることを確かめる。`verus!` の外に置くのは、`fmt` と `Default` の実装、T4 の `Drop`、`unsafe impl Send` と `Sync`、`Sync` でないことの型の assert と配置を確かめるコンパイル時の assert、`leaks` の `BTreeMap` を組む安全な関数と `check_invariants`、前置きの構造体 `Prefix` の宣言、panic の文言の `const`、`Foreign` の表の `const` (T3)、`Control` の止める語と確保量を読み書きする安全な関数と `Ctx::poll` (上の「実行の制御」)、Host の trait (既定のメソッドを含む) と `Opened`、`StdinSlot` の `new` と、読み手を取り出す `take` と返す `put`、`StdinHandle`、`StdoutHandle`、`StderrHandle` の `Drop` (T4)、`OpenFlags` の `new` と、印を選ぶ `flag`、立てる `raise`、下ろす `lower`、`Reader` の `new`、`fill_buf`、`consume` と buffer の残りを取り出す `take_buffered`、trait `Source` と `FileIn` と `StdinHandle` の実装、読みの誤りに名前を付ける `fault`、`exit_code`、`Buffering`、`StdHost`、`HostRef::new` と `HostRef` の `Drop` (T4)、`Fault`、`ArithFault`、`IoReason`、`Stop` の `Display`、`io::Error` を `IoReason` に写す関数 `io_reason` (上の「extern」)、止める語が立った後の `Interrupted` を変える読み手 `StopOnInterrupt` と、読みの部品 `check`、`line_part`、`read_line`、`read_all` (上の「読み手」)、テストだけである。

## 受け入れる制約

| 制約 | 理由 |
|---|---|
| 1つのデータの型のコンストラクタは 65536 個まで | `tag` を 16 ビットにするため |
| エフェクトは 65535 個まで | evidence の `tag` をエフェクトの番号 + 1 にするため (上の「evidence の3つの物体」) |
| 物体の種類は 16 個まで | `info` の4ビットにするため |
| 64 ビットの環境だけを対象にする | 語を 8 バイトにするため |
| 速いモードでは、解放の後の使用、token の2回の使用、`FileIn` の参照の重複を検出しない | 速い道に検査を置かないため。`lin` の物体の rc は 1 なので、その `dup` は速い道を通る。検出は verifier と、検査モードで走らせる UI テストに任せる。`eml run` では、どれも `--debug-heap` のときだけ見つかる ([LIR](lir.md) の「実行時エラー」) |
| 小さい物体のページを、実行中に OS へ返さない | 核を小さく保つため。空きリストは級ごとなので、使う量は級ごとの生きていた量の最大の和で抑えられる (2 語の物体が多い時期の後に 4 語の物体が多い時期が来ると、両方の分を使う)。上の「確保と解放」の「決めていないこと」に挙げてある |
| 局所の数が `i32::MAX` に達した物体と、共有の数が `DROP_LIMIT` を下回った物体は解放されない | 張り付きの方式による。物体を 2^31 - 2^17 回参照するには、参照だけで 16 GiB 近くが要る |
| 検査モードでは、使うメモリがそれまでに確保した量の合計になる | 解放したブロックを使い回さないため。token の表も `into_token` の回数に比例して伸びる。生存の列挙とリークの検査の時間も、確保した量の合計に比例する。UI テスト、`bench.rs`、`--debug-heap` の実行が検査モードで動くので、確保の多いプログラムではメモリが増える。足りなくなったら、隔離する量に上限を付ける |
| 検査モードでは、前置きの分だけブロックが大きくなる | 速いモードでちょうど 128 語の物体は、検査モードでは大きい物体の道を通る。2つのモードの確保器の道は、境目の大きさで違う |
