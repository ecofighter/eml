# オブジェクトモデル

位置づけ: 規範。

VM とネイティブで共有するランタイム `eml_rt` の核を定める。核は、語、物体 (ヘッダ、ペイロード、種類)、ページ単位の確保器と生存の列挙、局所と共有の参照カウント、`share`、`lin` ビット、核の操作、文字列、reuse の部品、検査モードから成る。核は物体の中身の種類をほとんど知らない。中身を知るのは `BigInt`、`Foreign`、`String` だけで、データ、クロージャ、evidence の物体の形 (下の「物体の形」) は VM が受け持つ。`eml_rt` はまだパイプラインから使わず、今のインタプリタのヒープは [ランタイム](runtime.md) が定める。S10 で VM が `eml_rt` を使うときに、2つの文書を合わせる。

設計の基準は、実用的なプログラムで速いことである。関数型のプログラムで回数の多い経路は、多い順に次のとおりで、核はこの順に速さを優先する。

1. `dup` と `decref`。ほとんどの命令の周りに出る
2. 小さい物体の確保と解放。cons セル、タプル、`Some x` などの多くはすぐ死ぬ
3. `switch` のタグの読み出し
4. `tobj` の位置の `box` と `unbox`
5. Perceus の reuse (後の reuse analysis が入れる)。一意の道で、確保と解放とヘッダの書き込みを省く

`share`、検査モード、生存の列挙、`Lin` の破棄処理は回数が少ないので、速さより単純さを優先する。形は Lean 4 と Koka のランタイムに近く、確保器は mimalloc の考え方を借りる。速さのために受け入れる制約は、下の「受け入れる制約」にまとめる。

`eml_rt` は vstd だけに依存する crate で、コードを Verus の `verus!` の中に書き、Verus が全体を検証する (下の「`unsafe` の核」)。検証 (Verus、単体テスト、Miri) は [テスト戦略](../implementation/testing.md) の「`eml_rt` の検証」に、命令の数の計測は [計測の基準](../implementation/benchmarks.md) にある。

## 語

- 値は 8 バイトの語 `Word` である。Rust ではポインタ型 (`*mut ()` を包む `#[repr(transparent)]` の型) で持つ。`u64` で持たないのは、Miri の strict provenance の下でポインタの出所を失わないためである。即値は `ptr::without_provenance_mut` で作り、ポインタの下位ビットの検査と書き換えは `addr` と `with_addr` で行う
- 下位ビットが 1 なら即値、0 ならヘッダを指すポインタである。物体は 8 バイトに揃えるので、ポインタの下位3ビットはいつも 0 になる
- 即値の値は、語を算術右シフトで1ビットずらした `i64` である。即値で表すものは次のとおりである
  - 63 ビットに収まる `Int` (`tobj` の位置の `box`)
  - `tobj` の位置の `enum` のタグ `#N`
  - `()`。値 0 の即値、つまり語の値 1 にする
  - 関数の値 `&f`。値は関数の番号である
- `obj` と `tobj` の位置は、ポインタか即値の語である。`int`、`enum`、`unit` の変数とフィールドは、タグのない生の 64 ビットで持つ。`unit` の生の値も `()` の即値と同じ語の値 1 にする。[LIR とインタプリタ](lir.md) の「値の表現」の「`unit` の値の機械の形は、`tobj` の即値 `()` と同じにする」を守るためである
- `Int` の意味は 64 ビットのまま変えない。`box` は、`Int` が 63 ビットに収まれば (`(n << 1) >> 1 == n`) 即値にし、収まらなければ種類 `BigInt` の物体を確保する。`unbox` は、即値なら右シフトし、物体なら `BigInt` の中身を読む。型変数の位置の `Int` の変換は、box の挿入を作ったときの試作で、UI テストの `List a` のフィールドで 302,149 回あった。データの配置を一様に保つので ([Core IR](core-ir.md) の「変換の規則」)、この変換を即値にして安くする
- `enum` の `box` と `unbox` は、いつも即値のシフトである
- `&f` を即値にするのは、捕まえる値のない関数の値で確保しないためである。`apply` は、語が即値なら関数の番号を直接呼び、物体ならクロージャを呼ぶ
- `Word` は `Send` と `Sync` を実装する (`unsafe impl`)。語は値で、スレッドをまたいでよいかは、型でなく RC の規約 (下の「`share`」) が守るためである。`CodeBase` が不死の定数の語を持って `Sync` になるにも、これが要る ([マルチコア対応の設計](../future/multicore.md) の「VM の並列化の備え」の制約2)。`Heap` は `Send` で `Sync` でない。worker ごとに1つ持ち、worker のスレッドに移せるようにするためである。どちらも型の assert で固定する

`Float` を入れたときの語の表現は、[ロードマップ](../future/roadmap.md) の「`Float`、`Char`、`Num`」に移した。型とリテラルより前に入れると、テストできない死んだコードになるためである。クロージャの形は下の「物体の形」にある。

## ダミーの値

- EP のダミー (`prim dummy()`) は、`Heap` が作るときに1つ確保する不死の物体を指す語である (`Heap::dummy`)。種類は `BigInt` で、値は 0 である。静的な物体にしないのは、検査モードの前置き (下の「前置き」) を静的な物体のために特別扱いしないためである
- ダミーへの `dup` と `decref` は、rc が 0 (不死) なので速い道から外れ、何もしない。`unbox` は 0 を読む。速い道に、ダミーのための分岐を足さずに済む
- [LIR とインタプリタ](lir.md) の「ダミーの値」の約束 (`dup`、`decref`、`drop` は何もしない、`unbox` は誤りにしない、`box` はダミーを受けたらダミーを返す) は、こうして守る。`box` が受けるのは生の `int` か `enum` で、そこでのダミーは `0` か `#0` なので、普通に box してよい
- ダミーは、検査モードの不死の物体の数え方 (下の「不死の物体の数え方」) の対象にしない。EP は、作っていないダミーを `drop` するためである

## 物体

物体は、ヘッダとペイロードが続く1つのブロックである。ポインタはヘッダの先頭を指す。

### ヘッダ

ヘッダは 8 バイトである。

```
rc:   i32         0 = 不死、正 = 局所、負 = 共有
meta: u32         tag (16 ビット) | scan (8 ビット) | info (8 ビット)
```

- `tag` はコンストラクタの添字である。データでない種類では、種類ごとに意味を決める (使わなければ 0)
- `scan` は、走査する語 (`obj` と `tobj` の値) の数である。0 から 254 はそのまま数を表す。255 は「数がペイロードにある」印で、そのときは走査の始まりの位置の生の1語が数を持ち、走査する語はその次から並ぶ。走査する語が 255 個以上の物体 (フィールドの多いデータ、EP の継続のクロージャが捕まえる多くの値) も、同じヘッダで扱うためである。継続のクロージャはコンパイラが作るので、数の上限をユーザーの誤りにできない
- `info` は、最上位のビットが `lin` ビット (下の「`lin` ビット」)、下位の4ビットが種類である。残りの3ビットは予約し、0 にする
- ヘッダを `rc` と `meta` の2つに分けるのは、reuse の書き込みを少なくするためである。確保は rc と `meta` の2つの欄を続けて書く。reuse でコンストラクタが変わるときは `meta` の 32 ビットの1回の store で済み、rc は 1 のままなので書かない。同じコンストラクタの reuse は、ヘッダに何も書かない
- `meta` は atomic でない。`meta` を書くのは、確保と、一意な箱の reuse と、解放だけである。どれも、ほかのスレッドがその物体を読めないときに起きる
- `rc` の欄は整数の型で持ち、atomic の読み書きは欄を受ける関数が `AtomicI32::from_ptr` を通して行う (下の「`unsafe` の核」の T2)。Verus は atomic の型の欄を扱わないためである。配置は `AtomicI32` と同じである
- ヘッダの大きさは、数字の 8 でなく `size_of::<Header>()` で書く。ヘッダの形を変えたときに、数え直す所を1か所にするためである
- 物体の大きさはヘッダに持たない。確保器のページが持つ (下の「確保器」)
- 型ごとの記述子の表は持たない。静的な型の情報なしに物体を扱うための方針 (子のたどり方、`Lin` の破棄処理) は、ヘッダの `scan` と種類と `lin` ビットで表し、解放とたどりはそれだけで済む。物体だけからは型と配置が分からない (配置の ID を持たず、型をまたぐ reuse でタグの意味も変わる) ので、リークの報告は種類の名前で数える。今の `eml_runtime` が、どの型のデータも `Data` と数えるのと同じである

### ペイロード

- ペイロードは、走査する語を並べ、その後に生の語を並べる。走査する語は、即値なら何もせず、ポインタなら子として RC とたどりの対象にする
- データの物体で、宣言の順のフィールドを走査する語と生の語に並べ替える規則を、物理的な形と呼ぶ。コンパイラのパス (後の reuse analysis) とランタイム (`CodeBase`) は、同じ規則を使わなければならない。reuse analysis は、物理的な語の数と物理的な位置で reuse の組を決めるためである
- 物理的な形は次のとおりである。フィールドのうち Repr が `obj` か `tobj` のもの (`Repr::is_rc`) を宣言の順に走査する語として並べ、その後に残り (`int`、`enum`、`unit`) を宣言の順に生の語として並べる。`unit` のフィールドも1語を取る。宣言で `()` を持つフィールドはまれなので、語を取らない3つ目の場合を作らない
- 規則を出す関数は `eml_lir` に置く。`Layout` から、宣言の位置ごとの物理的な位置と、走査する語と生の語の数を出す。`eml_rt` は tag、走査する語の数、生の語の数だけを受け、規則を知らない。規則を使うのは `CodeBase` を組み立てる側 (S10 の VM) と後の reuse analysis で、どちらも `eml_lir` に依存する。そのため規則は1か所にあり、結び付けのテストは要らない
- 関数は、最初に使う S10 で足す。今足すと使われないコードになるためである。S9b-3 の extern が作るデータ (`Bool`、`Ordering`、`Fs.read_all` の組 `(File, String)`) は、どれもタグだけか走査する語だけなので、規則の関数がなくても形が決まる

### 種類

種類は `info` の下位4ビットで、最大 16 種類である。種類ごとに次の欄を決める。欄は表を引かず、`Kind` の `match` で決める。種類を足すときに、どの欄も決め忘れないようにするためである。ただし破棄処理の欄は、箱を空けるたびに読むので、`Meta::has_finalizer` が種類のビットを `Foreign` の番号と直に比べる。`match` で種類に戻すと、種類を1つ足しただけで解放の多い計測の命令の数が数 % 増えたためである ([計測の基準](../implementation/benchmarks.md) の「S9b-1 (文字列)」)。比べた結果が種類の欄と同じであることは、Verus が確かめる。

| 欄 | 意味 |
|---|---|
| 名前 | リークの報告の種類の名前 |
| 走査の始まり | 走査する語 (`scan` が 255 なら数の語) がペイロードの何語目から始まるか |
| token にできるか | reuse の token にしてよいか |
| 破棄処理 | 解放のときに呼ぶ処理があるか |
| ペイロードが不透明か | 核の操作から見て、ペイロードを語として読み書きできないか。`raw` と `set_raw` はこの欄で断る |

今ある種類は次の5つである。

| 種類 | 番号 | ペイロード | 走査の始まり | token | 破棄処理 | 不透明 |
|---|---|---|---|---|---|---|
| `Data` | 0 | フィールド | 0 | できる | なし | いいえ |
| `BigInt` | 1 | `i64` の1語 | 0 (`scan` は 0) | できない | なし | いいえ |
| `Foreign` | 2 | 破棄処理の表への `&'static` のポインタ、その後に Rust の値 | 0 (`scan` は 0) | できない | 表の `finalize` | 不透明 |
| `String` | 3 | 生の1語目にバイト長、その後に UTF-8 のバイト列 (下の「文字列」) | 0 (`scan` は 0) | できない | なし | 不透明 |
| `Free` | 15 | 空きリストの次のブロックへのポインタ | なし | できない | なし | いいえ |

- `Foreign` は、`File` のように Rust の値を持つ物体である。`alloc_foreign::<T>(value, lin)` が、`T` ごとに1つの静的な表 (値の型を照らす `TypeId` を返す関数と、`drop_in_place::<T>` を呼ぶ破棄処理) を作って先頭に置く。`T` は `Send + 'static` で、揃えは 8 バイト以下に限る。後で別のスレッドが最後の参照を手放しても、破棄処理をそのスレッドで呼べるようにするためである ([マルチコア対応の設計](../future/multicore.md) の「スレッドに縛られたリソース」)
- `Foreign` の箱を空けるときは、表を読み、箱を先に死んだことにしてから破棄処理を呼び、その後でブロックを確保器に返す。破棄処理が panic しても同じ値を2回破棄せず、返した大きい物体のページを読まないためである。panic したときは、その箱が漏れる
- `Foreign` を token にしないのは、破棄処理を飛ばして別の物体に使い回すと、`Lin` の資源の後始末が漏れるためである。`BigInt` は reuse analysis の対象にならないので、token にしない
- `String` を token にしないのは、token の箱はいつも `Data` であるという性質を崩さないためである。`con_at` が書き直さない語の扱いは、この性質に頼る。reuse analysis も文字列を対象にしない
- `Foreign` と `String` のペイロードは不透明である。`Foreign` は Rust の値を持ち、`String` の語は途中までしか書いていないことがある。`raw` で語として読むと未初期化のメモリを読み、`set_raw` で書くと不変条件が崩れる
- `Free` は、確保器が空いたブロックに付ける内部の種類である (下の「確保器」)。生きている物体がこの種類を持つことはない
- クロージャ、evidence の入口の表、evidence、`evv` の節点は種類を分けず、`Data` にする (下の「物体の形」)
- 後の項目の種類の見通しは次のとおりである。`Float` は、`BigInt` と同じく1語の箱の種類を足すか、`BigInt` の形を使う。`Bytes` は `String` と同じ形 (長さとバイト列) を使える。`Array` は別の種類が要る。種類の数の上限 16 には余裕がある

まだ決めていないこと: `File` の物体の中身の型。S9b-3 で extern と一緒に置く ([ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)。

## 物体の形

物体の種類ごとの tag とペイロードは次のとおりである。

| 物体 | 種類と tag | ペイロード |
|---|---|---|
| データ | `Data`、コンストラクタの添字 | 上の「ペイロード」の物理的な形 |
| クロージャ | `Data`、0 | 走査する語に [`&f` の即値, 引数...] |
| `evv` の節点 | `Data`、エフェクトの番号 | [evidence, next] |
| evidence | `Data`、エフェクトの番号 | [入口の表, 状態, 外側の `evv`] |
| 入口の表 | `Data`、0 | [入口のクロージャ...] |
| 文字列 | `String`、0 | 上の「種類」と下の「文字列」 |
| `File` | `Foreign`、`lin` ビットを立てる | 中身の型は S9b-3 で extern と一緒に置く |

### クロージャ

- 関数は、最初の走査する語に即値で置く。即値は走査で飛ばされるので、生の語に分ける必要がない。`apply` は即値か物体かを語で見分けるので (上の「語」)、クロージャに別の種類は要らない
- VM は、関数を `scanned(w, 0)` で、捕まえた値と部分適用の引数を `scanned(w, 1..)` で読み、その数を `scanned_len(w) - 1` とする。`field(w, 0)` では読まない。走査する語が 255 個以上のクロージャ (EP の継続のクロージャがありうる) では、ペイロードの先頭に数の語があり、関数は `field(w, 1)` にあるためである。`apply` の場所ではクロージャの形が静的に分からないので、この規則を守る
- 共有されたクロージャの中身を使うとき (`apply` が中身を写す) のための別の操作 `copy` は作らない。VM が今ある部品を並べる。`is_last` なら引数を読んでから `free_block` し、そうでなければ引数を `dup` してから `decref` する。引数の数と関数の引数の数は、`apply` が読む `FnEntry` (S9b-2) と `scanned_len` で決まる
- VM が実行時に作るクロージャ (部分適用で引数を足したもの) の `lin` ビットは、元のクロージャのビットを写す。元が即値の `&f` なら、ビットを立てない。クロージャの印は捕まえた値の印の結びで ([LIR とインタプリタ](lir.md) の「Kind の印」)、足す引数は `apply` のオペランドなので `poly` である。`poly` はビットを立てる理由にならない
- クロージャは `Data` なので token にできるが、reuse の危険はない。クロージャを `release` する命令はなく、reuse analysis は `release` を書き換えて token を作るためである

### evidence の3つの物体

- `evv` の節点の tag はエフェクトの番号である。`ev_lookup` と `evv_mask` は、節点ごとに節点自身の `meta` の tag を比べるだけで済み、evidence の物体を読まない。`perform` のたびに、節点ごとの依存した読み込みが1回減る
- evidence の tag もエフェクトの番号である。`evv_push` は、引数の evidence の tag を1回読んで節点の tag に写す。入口の表の tag は読まないので 0 にする
- エフェクトの数の上限は、コンストラクタと同じ 65536 になる
- 3つの物体を別の種類にしない。速いモードの振る舞いは `Data` と同じで、分けて得られるのは、リークの報告の名前と検査モードの種類の検査だけだからである。リークの報告では、クロージャと evidence の物体も `Data` と数える
- `ev_set_state` と `ev_take_state` は、状態の欄を `set_field` でその場で書き換える。`set_field` の安全の前提 (ほかのスレッドが読めない) は、S10 のシングルスレッドの VM では成り立つ。`par` を入れるときは、evidence を共有の印の付いた物体にしない (子のタスクに渡さない) か、状態の欄の書き換えを見直す
- evidence は `CodeBase` の不死の定数にしない。空の `evv` は即値の `()` である

## 確保器

自前の確保器にする理由は次のとおりである。

- 大きさをページの頭から引けるので、ヘッダが 8 バイトに収まる
- 確保と解放が、空きリストの pop と push の数命令で済む。macOS の malloc は1回に数十 ns かかる
- Verus が確保器の経路も証明できる
- 生存の列挙が、ページを歩くだけで済み、別の台帳が要らない

### ページ

- 物体は、64 KiB に揃えたページから切り出す。ページは `std::alloc` から揃えを指定して取る。ページの先頭にページの頭 (大きさの級、ブロックの大きさ、ページの一覧の中の添字、まだ切り出していない残りの位置) を置く。物体のポインタの下位 16 ビットを落とせば (`with_addr`)、ページの頭が分かる。mimalloc と同じ方式で、ヘッダに大きさを持たずに済む
- 小さい物体の大きさの級は語の単位で決める。ブロックの語の数 (ヘッダを含み、検査モードの前置きを含む) が 2 語から 16 語 (16 B から 128 B) は1語刻み、その上は 20、24、28、32、40、48、56、64、80、96、112、128 語である。いちばん小さい級を 2 語にするのは、空いたブロックにヘッダと空きリストのポインタを置くためである
- 128 語を超える物体は大きい物体として、その物体だけの揃えたページに置く。ページの頭の形は同じで、解放の道もページの頭を読むところまでは同じである
- `alloc` と `con_at` は、ヘッダを含まないペイロードの語の数を受け取る。ヘッダの語の数を、呼ぶ側に数えさせないためである。級は、ヘッダとペイロードの語の数の和から決め、検査モードでは前置きの語の数も足す。ペイロードは少なくとも1語にする。空いたブロックのペイロードの先頭に、空きリストのポインタを置くためである。語の数の和やバイト数が `usize` を超える大きさは、どちらのモードでも panic にする。桁あふれが回ると小さいブロックを取り、安全な `alloc_data` がその先まで書いてしまうためである

### 確保と解放

- 確保器は級ごとに、空いたブロックの空きリスト (LIFO) と、今のページの切り出しの位置を持つ。確保は、空きリストから pop し、空なら今のページから切り出し、ページが尽きたら新しいページを取る
- 今のページの切り出しの位置は確保器の欄だけが正しく、速い道はその位置だけを進める。今のページを替えるときに、古いページの最後の位置をそのページの頭に書き戻す。ページを歩く処理 (生存の列挙、`Heap` を落とすとき) は、各級の今のページでは確保器の位置を、ほかのページではページの頭の位置を読む。まだ切り出していないメモリをブロックとして読まないためである
- 確保器は、取ったすべてのページの一覧を持つ。ページの頭は一覧の中の自分の添字を持ち、大きい物体のページを返すときは `swap_remove` で一覧から外し、移ってきたページの添字を書き直す。返すたびに一覧を探すと、大きくなっていく文字列を作るループが2乗の時間になるためである
- 解放は、ページの頭を読み、小さい物体のページなら、ブロックの `meta` を種類 `Free` にし、ペイロードの先頭の語に次のブロックへのポインタを書いて、その級の空きリストに push する。書き込みは2回で、ヘッダの後半とその次の語に書く。2つは続いた 12 バイトの中にあるので、ほとんどは同じキャッシュラインに入る。ヘッダが 64 バイトの境目の直前の語にあると (たとえば 3 語のブロックがページの先頭から 56 バイトの位置にあるとき)、2つのラインに分かれる。`Free` の印を書くのは、速いモードでもページを歩いて生きている物体を見分けられるようにするためである (下の「生存の列挙」)
- 大きい物体のページなら、解放したときにすぐ `std::alloc::dealloc` で返す。大きい物体を級の空きリストで使い回すことはないので、返さないと、大きくなっていく文字列や配列を作るループで使う量が限りなく増えるためである
- 形の分かっている物体の解放 (`free_block`。下の「核の操作」) も同じ道を通る。ページの頭を読むのは、マスク1回と読み込み1回である
- 小さい物体のページは、実行中に OS へ返さない。ページは `Heap` を落としたときにまとめて返す
- ヒープは、使っているメモリのバイト数 (`bytes_in_use`) を両方のモードで数える。速いモードでは OS から取ったページのバイト数で、ページを取るときと返すときだけ数えるので、速い道の費用はない。検査モードでは、そこから隔離した (解放して使い回さない) ブロックのバイト数を引く。`Ctx` の確保量の上限と、S10 の安全点の確かめは、この数を使う
- 2つのモードの数は、空きリストに残っているブロックの分だけ違いうる。上限は暴走するメモリを止めるための安全網で、厳密な会計ではないので、この違いは受け入れる。上限すれすれのプログラムは、モードによって止まったり止まらなかったりしうる

まだ決めていないこと: 小さい物体のページを OS に返すこと、ページごとの空きリスト、別のスレッドからの解放 (ページの頭に持ち主を置く遠隔の空きリスト)。VM の並列化かネイティブのランタイムのうち、先に来るほうで入れる ([マルチコア対応の設計](../future/multicore.md) の「確定した設計判断」の 7)。

### 生存の列挙

- 生きている物体は、両方のモードでページを歩いて列挙できる (`live_objects`)。各ページの切り出したブロックのうち、速いモードでは種類が `Free` でないもの、検査モードでは前置きの状態が解放でないものが、生きている箱である
- 列挙は、S11 の根からの走査による回復が使う。届かない物体を解放し、届かない `Foreign` の物体の破棄処理を呼ぶためである ([ロードマップ](../future/roadmap.md) の「S11 REPL」)。REPL は速いモードでも動けなければならないので、列挙を検査モードだけのものにしない
- 回復を列挙の上で安全に組めるように、次の2つを守る
  - rc が 0 の物体 (ダミーと `alloc_immortal` の物体) は、根から届かなくても解放しない
  - 速いモードの token の箱は、生きている `Data` と区別が付かず、そのフィールドはもう解放した子を指しうる。そのため、届かない箱は、フィールドをたどらずに1つずつ空ける (`Foreign` だけ破棄処理を呼ぶ)。届く物体の RC は、根からたどって数え直す
- `Heap` を落とすときは、ページを歩いて、生きている `Foreign` の物体の破棄処理を呼んでから、すべてのページを返す。Rust の値が持つメモリを漏らさないためである。Miri は漏れを誤りにする

まだ決めていないこと: 回復の手順 ([ロードマップ](../future/roadmap.md) の「S11 REPL」)。

## 参照カウント

### 符号

- rc が 0 の物体は不死で、解放しない。`alloc_immortal` の物体とダミーがこれに当たる
- 正の rc n は、局所の物体の参照の数 n である。局所の rc は、Relaxed の load と store で読み書きする。aarch64 でも x86_64 でも、普通の読み込みと書き込みの命令になる
- 負の rc -n は、共有の物体の参照の数 n である。共有の rc は、atomic の加減算で読み書きする ([マルチコア対応の設計](../future/multicore.md) の「共有の印方式」)

### 局所の速い道

`dup` と `decref` の速い道は、比較1回で決める。

- `dup`: rc を符号なしで見て `rc - 1 < MAX - 1` なら、つまり rc が 1 以上 `MAX - 1` 以下なら、rc + 1 を書き戻す。それ以外 (不死、共有、上限) は遅い道に進む
- `decref`: rc が 2 以上 `MAX - 1` 以下 (同じく符号なしの比較1回) なら、rc - 1 を書き戻す。rc が 1 なら解放する。それ以外は遅い道に進む
- `tobj` の値には、この前に下位ビットの検査が1回入る。`obj` の値は、つねにポインタなので検査しない

### 上限

上限に達した数は動かさない (張り付き)。Perceus の論文と Lean と同じである。

- 局所の rc が `MAX` (`i32::MAX`) に達したら、その物体の数は動かさない。その物体は解放されずに残る。速い道の範囲から `MAX` を外してあるので、張り付いた数は速い道で動かない。局所の数は1つのスレッドだけが書くので、境目はちょうど `MAX` でよい
- 共有の側では、上限の判定と加減算の間に別のスレッドが割り込める。そこで境目を2つ置く (ヒステリシス)
  - `dup` は、rc が `DUP_LIMIT = MIN + 2^16` より小さければ数を動かさない
  - `decref` は、rc が `DROP_LIMIT = MIN + 2^17` より小さければ数を動かさない
- 境目を2つにする理由は次のとおりである。境目が1つだと、境目の外の値を読んだ `decref` が加算する前に、別のスレッドの `dup` が数を境目の中に入れ、さらに別の `dup` がそれを見て数えずに飛ばすことがある。その後に最初の `decref` が加算すると、数は境目の外に戻り、数えなかった参照の分だけ実際より少なくなる。2つの境目なら、`dup` を1回でも飛ばした物体の rc は `DUP_LIMIT` より小さい。それを `DROP_LIMIT` まで戻せるのは、rc が `DROP_LIMIT` 以上のうちに読んで、まだ加算していない `decref` だけである。その数は同時に動く worker の数より少ないので、worker が 2^16 未満なら、rc は `DROP_LIMIT` に戻らない。その後の `decref` はすべて飛ばされ、物体は解放されずに残る。数が実際より少なくなっても、参照が残っている物体を解放することはない
- 張り付いた物体は解放しないが、不死 (rc 0) には変えない。`share` が不死の物体でたどりを止めるので、張り付いた局所の物体を不死にすると、その子が共有の印なしに別のスレッドから届くためである

### 共有の側

- `dup` は、`DUP_LIMIT` 以上なら `fetch_sub(1, Relaxed)` で数を増やす (負の向きに進める)
- `decref` は、`DROP_LIMIT` 以上なら `fetch_add(1, AcqRel)` で数を減らし、古い値が -1 なら最後の参照なので解放する。`fence(Acquire)` は使わず、AcqRel の加算で最後の解放を順序付ける
- 解放の連鎖では、子を1つずつ、その子の rc の符号に合う側の `decref` で減らす。共有の物体の子は、共有か不死の物体か、`lin` ビットの立った局所の物体である (下の「`share`」)

### 遷移の関数

RC の遷移は、rc の値だけを受け取って次の状態を返す純粋な関数 (`dup_step`、`decref_step`、`mark_step`) にする。ヒープはそれを呼んで書き込むだけである。単体テストとヒープが同じ関数を使い、Verus がその関数を証明して ([テスト戦略](../implementation/testing.md) の「Verus」)、遷移の正しさを1か所で確かめるためである。共有の側の加減算そのもの (`rc_dup_shared`、`rc_decref_shared`) と `is_last` の読み込みは、rc の欄の権限を受ける T2 の関数にする (下の「`unsafe` の核」)。

## `share`

- `share(w, receiver)` は、送り手のスレッドが、値を公開する前に呼ぶ ([マルチコア対応の設計](../future/multicore.md) の「共有の印方式」)。w から届く物体を明示のスタックでたどり、局所の rc n を -n に変える。局所の上限 `MAX` は共有の上限 `MIN` に変える。-n が `DROP_LIMIT` より小さくなるときも `MIN` に変える
- すでに負の物体と不死の物体で、たどりを止める。不死の物体は、`lin` ビットが立っていても変えない。印を付けた物体はもう一度たどらないので、`lin` でない物体がたどられるのは高々1回である
- `lin` ビットの立った物体には印を付けず、所有者を `receiver` に移す。ただし、その子はたどり続ける。`Lin` の物体の中の `Unr` の子は、送り手がほかの所からも参照していることがあるためである。`Lin` の物体は rc が 1 なので、受け手は局所の物体としてそのまま使える
  - `lin` の物体は rc が 1 なので、正しいプログラムでは2回届かない。検査モードは、たどりで同じ `lin` の物体に2回届いたら誤りにする (訪れた `lin` の物体の集合を持つ)。すでに共有の側にある `lin` の物体に届いたときも誤りにする。速いモードは、正しいプログラムに頼る
  - 検査モードは、たどりで届いた物体が生きていなければ誤りにする
- `lin` ビットのない親の中に `lin` ビットの立った子があることは、ふつうに起きる。`poly` の印の `con` (`(a, File)` の組の型は `poly` になる) と、EP の継続のクロージャ (印は捕まえた値の印の結び) は `lin` ビットを持たないが、中の `File` はビットを持つ。このとき `share` の後は、共有の親から局所の `lin` の子が届く。そのため、共有の物体から届いてよいのは、共有か不死の物体か、`lin` ビットの立った局所の物体である
  - そうした親は、実際には `Lin` の値なので参照は1つで、所有も受け手に移っている。親の最後の参照を手放すのは受け手で、子の所有者の検査とも合う
  - 受け手がその親を手放すとき、親の rc は -1 である。-1 の物体は、参照が自分の1つだけなので、最後の参照として扱い、残すフィールドを `dup` せずに受け取る (下の「核の操作」の `is_last`)。残す `lin` の子を `dup` すると、正しいプログラムでも検査モードの誤りになるためである
- たどりのコードは、物体への読み書き (生存、rc、`lin` ビット、所有者、子) を `Graph` trait の裏に置いて書く。Verus が、たどりのコードを trait のメソッドの約束の上で、任意のグラフについて証明するためである ([テスト戦略](../implementation/testing.md) の「Verus」)。ヒープの上の実装も証明し、たどりの結果をヒープの抽象のモデルの遷移と結ぶ
- S10 の VM はシングルスレッドだが、`par` の fork と join は worker の数によらず印を付けるので ([マルチコア対応の設計](../future/multicore.md) の「`par` の印付け」)、この経路を通る。物理的なスレッドが1つの間、`receiver` は論理的な worker ID (下の「論理的な worker ID」) である。`par` を入れるまで、`share` を呼ぶのは単体テストだけである

## `lin` ビット

- `info` の `lin` ビットは、検査モードに限らず常に持つ。`par` の fork で、印付けの代わりに所有者を移すのに使うためである ([マルチコア対応の設計](../future/multicore.md) の「`Lin` の物体の所有者の移し替え」)
- `alloc` と `con_at` は、呼ぶ側が渡す `meta` の `lin` ビットをそのまま書く。どの物体にビットを立てるかは、呼ぶ側が決める。`File` などの extern の資源は作るときに立てる。`con` と `closure` は、Kind の印 ([LIR とインタプリタ](lir.md) の「Kind の印」) が `lin` なら立て、`unr` と `poly` なら立てない
- `poly` のコードで作った `Lin` の物体はビットを持たないので、fork で共有になり、その場の書き換えができなくなる。安全の側に倒れるだけである
- `reuse_in_place` はヘッダを書かないので、箱の `lin` ビットがそのまま残る。ビットが欠けるのは安全の側である (`share` で印が付いて共有になり、その場の書き換えができなくなるだけ)。危ないのは、ビットが誤って残ることで、`Unr` の値の正しい `dup` を検査モードが誤りにする。印が `lin` の変数の箱がビットを持つとは限らない (`map Some files` のように、`poly` の `con$Some` が作った箱が `lin` の変数に入る) が、印が `unr` の変数の箱はビットを持たない
- そのため、`reuse_in_place` を使ってよいのは、古い物体の印が `unr` のときか、新しい物体の印が `lin` のときである。それ以外は `con_at` で `meta` を書く。検査モードの照らし合わせも、`lin` ビットについては「箱がビットを持ち、新しい `meta` が持たない」ときだけを誤りにする
- `unpack` と case で得たフィールドの印は、配置の表から確かめられず、translate を信用する ([LIR とインタプリタ](lir.md) の「Kind の印の検査」)。検査モードの `lin` ビットの誤り (下の「報告する誤り」) が、これを実行時に覆う

まだ決めていないこと: 呼ぶ側がビットを立てる実装 (`File` の物体と、VM の `con` と `closure`)。S9b-3 と S10 で入れる ([ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)。

## 核の操作

語を受ける操作は `unsafe fn` にする。条件は、Verus の `requires` に抽象のモデル (ブロックの状態、参照の数、語ごとの書き込みの状態) の言葉で書き、`# Safety` の文も同じ条件を指す。大きくは次のとおりである。速いモードはこれを確かめない。検査モードは、確かめられる違反を `Err` で返す (下の「検査モード」)。

- 語は即値か、生きている物体を指す。生きている物体とは、`meta` に合うペイロード (走査する語、`scan` が 255 なら数の語、`BigInt` なら値、`String` なら長さの語) をすべて書いた物体である。データの物体の生の語は、この条件に入らない
- 参照を消費する操作 (`decref`、`release`、`into_token` など) では、呼ぶ側がその参照を1つ持っている。読むだけの操作 (`field`、`raw`、`is_unique` など) では、呼ぶ側が参照を持っているか、生きている持ち主から借りている。Perceus の借りたフィールドと、基本操作の借用の引数がこれに当たる
- 物体は、同じ `Heap` が確保したものに限る
- rc が正の物体を書き換えるか、その rc を読んで判定する操作 (下の「報告する誤り」の `WrongOwner` に挙げた操作) では、物体の持ち主が今の worker である (下の「論理的な worker ID」)
- 構築中の物体 (`alloc`、`alloc_immortal`、`con_at`、`reuse_in_place` が返し、呼ぶ側がまだペイロードを書き終えていない物体) は一度に1つまでで、それに使えるのは `set_field` と `set_raw` だけである。ほかの操作は、構築中の物体が書き終えていることを前提にする

操作ごとの条件は次の表のとおりである。前提は、下の「検査モードの約束」の3種類 (安全の前提、モデルの前提、検査する前提) に分ける。速いモードは、表の下に挙げる2つ (`foreign` の照らし合わせと、`reuse_in_place` が空の token を断ること) を除いて、どれも確かめない。括弧の中は、検査する前提を破ったときに検査モードが返す誤りである。S10 の VM は、この表を守る命令の列を出す。

| 操作 | 安全の前提 | モデルの前提 | 検査する前提 (検査モードの `Err`) |
|---|---|---|---|
| どの操作も | 語は即値か、このヒープが確保したブロックを指す。構築中の物体は書き終えている (`set_field` と `set_raw` を除く) | 読むだけの操作の語は、モデルで生きている物体 (参照の数が正か、不死) を指す | 物体は生きている (`UseAfterFree`)。rc が正の物体を書き換えるか rc を読んで判定するなら、持ち主は今の worker である (`WrongOwner`) |
| 物体を受ける操作 (`meta`、`field`、`set_field`、`raw`、`set_raw`、`scanned_len`、`scanned`、`free_block`、`release`、`release_reuse`、`into_token`、`foreign`、`string`、`string_push`、`string_concat`) | 語はポインタである (即値でも `Word::EMPTY` でもない) | | |
| `alloc` / `alloc_immortal` / `con_at` | `meta` の種類は `Foreign`、`String`、`Free` のどれでもない。`scan` は 255 でなく、走査する語はペイロードに収まる | | |
| `field` / `set_field` | `set_field` の物体は、ほかのスレッドが読めない (局所か、構築中) | `set_field` が書く語は、呼ぶ側が数えた参照を持つ | i 語目は走査する語である (`OutOfBounds`) |
| `scanned` | | | i は `scanned_len` より小さい (`OutOfBounds`) |
| `raw` / `set_raw` | `raw` で読む語は先に書いてある。`alloc_data` は生の語を書かず、新しいページのメモリは初期化されていないためである。`set_raw` の物体は、ほかのスレッドが読めない | | 物体のペイロードは不透明でない (`WrongKind`。上の「種類」)。i 語目は、走査する語の後のブロックの中の語である (`OutOfBounds`)。`alloc_immortal` で作る `BigInt` の値の語も `set_raw` で書く |
| `unbox_int` | | | 物体は `BigInt` である (`WrongKind`) |
| `dup` | | 呼ぶ側が参照を持つか、借りている | 物体は `lin` ビットを持たない (`LinDup`) |
| `decref` / `release` / `release_reuse` | | 呼ぶ側が参照を1つ持つ。残さない子は呼ぶ側の参照と数える | 不死の物体の参照は `acquire_immortal` か `dup` で作った (`ImmortalOverRelease`)。共有の物体は `lin` ビットを持たない (`LinShared`)。`release` と `release_reuse` の物体はデータで、tag と走査する語の数が名指したものである (`WrongLayout`)。残さない子は `decref` の、`is_last` が偽のときの残す子は `dup` の検査する前提を満たす |
| `acquire_immortal` | | | 物体は不死である (`NotImmortal`) |
| `free_block` | | 呼ぶ側が最後の参照を持ち、子の参照はもう処理してある | rc が 1 か -1 である (`NotLast`)。種類は破棄処理を持たない (`FinalizerSkipped`) |
| `into_token` | | 呼ぶ側が唯一の参照を持ち、子の参照はもう処理してある | token にできる種類である (`NotTokenable`)。rc が 1 である (`NotUnique`) |
| `con_at` / `reuse_in_place` / `drop_token` | | token の箱の「残した」語 (`con_at` と `reuse_in_place` で書き直さない語) の参照を呼ぶ側が持つ | token はまだ使っていない (`StaleToken`)。`con_at` の箱は `payload_words` の物体のこのモードでの級にある (`WrongClass`。同じ物理的な語の数の物体から作った token なら、どちらのモードでも満たす)。`reuse_in_place` の `meta` の tag、scan、種類は箱と同じで (`WrongMeta`)、箱が `lin` ビットを持つなら `meta` も持つ (`LinBitKept`) |
| `share` | | | 届く物体はどれも生きている (`UseAfterFree`)。局所の `lin` の物体には1回だけ届き (`LinReachedTwice`)、共有の側の `lin` の物体には届かない (`LinShared`) |
| `string` | 返す位置を読むのは、物体が生きていて、`string_push` でその物体を書き換えていない間だけである | | 物体は `String` である (`WrongKind`) |
| `string_push` | `s` は left 自身の中身を指さない (下の「文字列」) | 呼ぶ側が left の参照を1つ持つ | left は `String` である (`WrongKind`)。left は `decref` の検査する前提を満たす |
| `string_concat` | | 呼ぶ側が left と right の参照を1つずつ持つ (同じ物体なら2つ持つ) | 両辺は `String` である (`WrongKind`)。両辺は `decref` の検査する前提を満たし、同じ物体なら2回続けた `decref` の検査する前提を満たす |

戻り値は、どちらのモードでも `Result` である。速いモードの操作は、次の2つを除いて `Err` を作らない。

- `foreign` は、物体の種類と値の型を、どちらのモードでも照らす。違えば `WrongKind` を返す。`foreign` の安全の条件は物体が生きていることだけで、違う型の値を指すポインタを返さないことは、この照らし合わせが受け持つためである
- `reuse_in_place` は、空の token を受けると `StaleToken` を返す。空の token には箱がなく、返す語がないためである

`Err` を作らない操作は、呼ぶ側に展開すれば、最適化で `Result` の分岐が消える。そのため、`dup` と `decref` は、局所の rc を書き換えるだけの速い道を `#[inline]` にし、残り (共有、不死、張り付いた数、検査モードの仕事) を、`#[cold]` と `#[inline(never)]` を付けた遅い道の関数に出す。速いモードの `decref` の速い道は、rc が 1 なら解放の連鎖を直に呼ぶ。解放の連鎖は `#[inline(never)]` にするが、一意な物体を空けることはよく起きるので、`#[cold]` にはしない。確保と箱の解放の速い道、`release`、`release_reuse`、`con_at` と、語とヘッダの小さい関数も `#[inline]` にする。VM は `eml_rt` の外の crate なので、付けないと、総称でない関数は crate をまたぐ呼び出しになりうるためである。確保器の遅い道 (ページを替えること、大きい物体の確保と返却) は `#[cold]` にする。命令の数は [計測の基準](../implementation/benchmarks.md) の「S9a (`eml_rt` の核)」にある。

ペイロードを呼ぶ側が書く `alloc` と `alloc_immortal` も `unsafe fn` である。`meta` の種類は `Foreign`、`String`、`Free` のどれでもなく、`scan` は 255 でない。呼ぶ側は、ほかのヒープの操作の前に `meta` に合うペイロードを書く。`scan` が 255 の物体は走査する語の数をペイロードの先頭の数の語から読むので、数の語を書く前には、走査する語と生の語の境目が決まらない。走査する語が 255 個以上の物体は `alloc_data` で作る。ペイロードの形が正しいかは VM が受け持ち、確保のたびに実行時に確かめると速い道の費用になるためである。ペイロードを自分で書く `alloc_data`、`alloc_int`、`alloc_foreign`、`alloc_string`、`alloc_string_immortal` は安全な関数である。`String` の物体を作れるのは、下の「文字列」の操作だけである。

| 操作 | 動作 |
|---|---|
| `alloc(payload_words, meta)` | 級のブロックを取り、rc 1 と `meta` を書く。ペイロードは呼ぶ側が書く |
| `alloc_data(tag, scanned, raw, lin)` | データの物体を作る。走査する語が 255 個以上なら、ペイロードの先頭に数の語を置く。走査する語は `()` で埋めておく |
| `alloc_immortal(payload_words, meta)` | rc 0 で確保する |
| `acquire_immortal(w)` | 不死の物体の参照を1つ作る。速いモードでは何もしない (下の「不死の物体の数え方」) |
| `alloc_int(n)` / `unbox_int(w)` | 上の「語」の `box` と `unbox` |
| `alloc_foreign::<T>(value, lin)` / `foreign::<T>(w)` | `alloc_foreign` は種類 `Foreign` の物体を作り、`foreign` はその中の値へのポインタを返す |
| `dup(w)` / `decref(w)` | 上の「参照カウント」。`decref` が 0 にした物体は、解放の連鎖に入れる |
| `is_unique(w)` | rc が 1 か。共有、不死、張り付いた数は、この1回の比較でみな偽になる。reuse とその場の書き換えに使う |
| `is_last(w)` | rc が 1 か -1 か。手放そうとしている参照が最後のものかを判定し、フィールドを `dup` せずに受け取ってよいかに使う。rc は Relaxed で読み、-1 のときだけ Acquire で読み直す。読み直しは同じ値を返し、最後の AcqRel の `decref` と同期する。ふだんの rc が 1 の道に、aarch64 の Acquire の読み込みの費用を足さないためである |
| `meta(w)` | ヘッダの `meta` を読む |
| `field(w, i)` / `set_field(w, i, v)` | ペイロードの物理的な i 語目を読み書きする。ヘッダを読まない。生の語の読み書き (`raw` / `set_raw`) も同じ添字で持つ。VM は形を静的に知っているので、`scan` が 255 かどうかで添字を直す必要がない |
| `scanned_len(w)` / `scanned(w, i)` | 走査する語の数と、その i 番目を読む。`scan` が 255 のときの数の語と、種類の走査の始まりを考える。形を知らない処理 (解放の連鎖、`share`、生存の列挙) が使う |
| `free_block(w)` | `is_last` が真で、子をすでに処理した物体の箱を空ける。ヘッダの `scan` を読まない。破棄処理を持つ種類には使えない |
| `into_token(w)` | 一意な物体の箱を、フィールドに触れずに token にする |
| `con_at(token, payload_words, meta)` | token が空でなければ、その箱に `meta` を書いて返す。空なら `alloc` する。どちらだったかも返す |
| `reuse_in_place(token, meta)` | 同じコンストラクタの reuse。ヘッダに何も書かずに箱を返す。`meta` は検査モードが照らすためだけに渡す |
| `drop_token(token)` | 使わなかった token の箱を空ける |
| `release(w, tag, keep)` | LIR の `release`。`is_last` が真なら、残さない子を手放して箱を空け、残す子は箱の参照を受け継ぐ。そうでなければ、残す子を `dup` してから w を手放す |
| `release_reuse(w, tag, keep)` | w が一意なら、残さない子を手放して箱を token にする。そうでなければ `release` と同じにして、空の token を返す |
| `share(w, receiver)` | 上の「`share`」 |
| `alloc_string(s)` / `alloc_string_immortal(s)` / `string(w)` / `string_push(left, s)` / `string_concat(left, right)` | 下の「文字列」 |

- `con_at` で箱を使い回したときは、残したフィールドを書き直さなくてよい。呼ぶ側は、ほかのヒープの操作の前に、走査する語がみな `meta` に合う値を持つようにする
- LIR の `decref` と `drop` は、どちらも `decref` で実行する。実行時の動作も検査モードの規則も同じだからである。`unr` でない値に `decref` を出さない規則 (V1) は静的な検査で、実行時には区別しない
- `release` と `release_reuse` は、上の部品を組んだ一般の版である。VM は形の分かっている所では部品 (`is_unique`、`is_last`、`decref`、`free_block`、`into_token`) を直接並べ、一般の版は形の分からない所でだけ使う。Perceus の drop の特殊化と、Lean の reset/reuse の展開を、VM の命令の列で作れるようにするためである。形の分かっている `release` の展開は次のとおりである

  ```
  is_last(x)
    真: 残さない子を decref → free_block(x)
    偽: 残す子を dup → decref x
  ```

- 判定を `is_unique` と `is_last` の2つに分けるのは、上の「`share`」の、共有の親から `lin` の子が届く形のためである。rc -1 の物体は最後の参照なので、フィールドを `dup` せずに受け取ってよい (`is_last`)。しかし共有の印を持つので、reuse もその場の書き換えもしない (`is_unique` は偽)
- `keep` は、走査する語ごとに残すかどうかを持つ
- 解放の連鎖は、ヒープが持つ作業リストの `Vec` を使い回してたどる。再帰しないので Rust のスタックを溢れさせず、解放のたびに確保もしない。物体を解放するときは、子を走査の逆の順に1つずつ `decref` し、0 になった子を作業リストに積み、`Foreign` なら破棄処理を呼んでから箱を空ける。逆の順に積むのは、最初の走査する語を先に、最後の走査する語を後に解放するためである
- cons セル (`a :: List a`) の物理的な形は [要素, 残り] である (上の「ペイロード」)。要素を解放し終えてから残りに進むので、要素が物体のリスト (`List (Int, Int)` など) でも作業リストの長さは定数に収まる。この性質は、再帰するフィールドが最後の走査する語であるときに成り立つ。`data Snoc a = Nil | Snoc (Snoc a) a` のように再帰するフィールドが前にある型では、作業リストは長さに比例して伸びる。作業リストはヒープの `Vec` なので、伸びても Rust のスタックは溢れない

まだ決めていないこと: `share` の後に別の worker の `Heap` が触る形と、`CodeBase` の不死の定数は、安全の条件を広げて扱う (`par` を入れるときと S9b-2。[ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)。

## 文字列

文字列は種類 `String` の物体である (上の「種類」)。ペイロードは、生の1語目にバイト長を持ち、その後に UTF-8 のバイト列を持つ。走査する語はない。

### 文字列の不変条件

- 種類 `String` の物体は、バイト長が容量以下で、バイト列が妥当な UTF-8 である。作れるのは下の文字列の操作だけである
  - `alloc`、`alloc_immortal`、`con_at` は、安全の前提で種類 `String` の `meta` を断る (`Foreign` と `Free` と同じ)。`reuse_in_place` は箱と同じ種類の `meta` しか受けず、token の箱は `Data` なので、断る必要がない
  - `raw` と `set_raw` は、不透明なペイロードを断る (上の「種類」)。速いモードでは前提にし、検査モードは `WrongKind` を返す
  - `release` と `release_reuse` はデータだけを受ける (`WrongLayout`)
  - 構築中の物体は `String` でない。構築中の物体を作る道 (`alloc`、`alloc_immortal`、`con_at`、`reuse_in_place`) は、どれも `String` を受けないためである
- 文字列のバイト列は、Verus の ghost の値としてブロックの権限に持つ。メモリのバイト列はこの ghost のバイト列に等しい (下の「`unsafe` の核」の T10)。バイト長はその長さに等しく、容量以下である。UTF-8 であることは vstd の `valid_utf8` で書き、連結で保たれることを `valid_utf8_concat` で示す。そのため、UTF-8 であることは信頼の一覧に入れず、Verus が確かめる
- ghost のバイト列は、隠した欄を持つ型にし、`meta.rs` の外では作れない。列を変えるのは、確保のたびに列を空にする処理 (`alloc_header` が、手渡すどのブロックにも行う) と、T10 の書き込みの関数だけである。使い回したブロックに前の物体の列が残らないように、確保で空にする
- この条件は、速いモードの不変条件 (`full`)、検査モードの不変条件 (`safe_wf`)、ブロックの形の条件のすべてに置く。`BigInt` の値の条件と同じ場所である。速いモードの `string` が範囲の中を読むことの証明にも要るためである。`set_field` が `String` の物体の走査する語の数 0 を保つことも、同じ条件で示す
- 容量は、ブロックのペイロードの語の数から長さの1語を引いたバイト数である。大きい物体も、ページの頭のブロックの大きさから同じ式で出る。検査モードでは前置きの分だけ容量が1語小さくなることがあるので、テストは期待値を容量から求める

### 文字列の操作

| 操作 | 動作 |
|---|---|
| `alloc_string(s: &str) -> Word` | 安全な関数。`s` を写した文字列を作る。容量は級の大きさまで |
| `alloc_string_immortal(s: &str) -> Word` | 安全な関数。rc 0 の不死の物体として作る。S9b-2 の `CodeBase` の文字列の定数が使う。`alloc_immortal` が `String` を断るので、別に持つ |
| `string(w) -> Result<*const str, HeapError>` | `unsafe fn`。中身の位置を返す。`foreign` と同じく生のポインタにし、ヒープの借用に縛らない。指す先は、w の物体が生きていて、`string_push` でその物体を書き換えていない間だけ読める |
| `string_push(left, s: &str) -> Result<Word, HeapError>` | `unsafe fn`。left の参照を受け取り、`s` を後ろに足した文字列の参照を返す |
| `string_concat(left, right) -> Result<Word, HeapError>` | `unsafe fn`。`++` そのもの。両辺の参照を受け取り、結果の参照を返す。`string_push(left, string(right))` の後に right を `decref` するのと同じ結果になる |

`string_push` の動作は次のとおりである。

```
left が一意 (is_unique)
  容量が足りる → その場で s を書き、長さを書き換える
  足りない     → max(必要量, 2 × 容量) で確保し、left と s を写してから、left の箱を free_block
そうでない (共有、不死) → 和の長さで確保し、left と s を写してから、left を decref
```

- 文字列のバイトを書くのは、作るときと `string_push` だけである。`string_concat` は `string_push` と同じ道で右辺を写す。バイトを書く信頼の関数を1つにするためである。S12 の extern (`join`、`replace` など) が Rust の側の `&str` を足すときも、`string_push` を使えば余分な写しが要らない
- `s` は、ほかの文字列の物体の中身を指してよい。その物体は呼び出しの間生きている。写すのは left を手放す前である。速いモードでは、大きい物体のページを `free_block` がすぐに返すためである
- `s` は left 自身の中身を指さない。一意な left を作り直すと、`string_push` の中で left の箱を空け、大きい物体ならページも返す。引数の `&str` が指すメモリを呼び出しの間に返すと、写した後でも未定義の動作になる。自分自身との連結は、`dup` してから `string_concat(x, x)` で行う。`string_concat` の右辺は `&str` の引数でなく、写す直前にヒープの権限から借りるので、この制約を受けない。`x ++ x` は `dup` で rc が 2 になって届くので、写す枝に進む
- 容量を倍にするので、一意な左辺に足していくループは、ならすと右辺の長さに比例する時間で済む。今の `eml_runtime` と同じ性質である ([ランタイム](runtime.md) の「文字列の連結」)
- 和の長さと倍の容量は `checked_add` と `checked_mul` で求め、桁あふれは今の確保と同じく panic にする (T5)
- 検査モードの誤りは、語を受ける操作の共通の誤り (`UseAfterFree`、`WrongOwner`)、種類が `String` でないときの `WrongKind`、数が 0 の不死の物体の手放し (`ImmortalOverRelease`) である。どの誤りも最初の確保より前に返すので、`Err` のときヒープは変わらない。文字列は子を持たないので、left と right の `decref` の誤りをすべて先に確かめられる。left と right が同じ物体で rc が 1 のとき (参照を2つ持つという前提を破った呼び出し) も、2回の `decref` を続けて確かめるので、ここで断る。後の手放しは、先に確かめたので誤りにならない
- モデルが合っていて前提がすべて成り立つときの結果は、`decref` と同じく、`Ok` か、モデルが照らさない誤り (下の「検査モードの約束」) である。モデルは不死の物体の外の参照の数を持たないので、不死の left の `ImmortalOverRelease` はモデルの前提の下でも返りうる
- 文字列の不死の定数のほかの扱い、`show`、比較、`println` は S9b-2 と S9b-3 で作る。どれも `string` で読むだけなので、足す操作はない

## reuse

後の reuse analysis は、`release` を `release_reuse` に、それが空けた箱を使う `con` を `con@token` に書き換えて入れる ([ロードマップ](../future/roadmap.md) の「処理系」の Perceus の最適化)。核は、その一意の道が次の命令の列になるように部品を持つ。

```
is_unique(x)
  真: 残さない子を decref → into_token(x)
      → コンストラクタが変わるか、lin ビットが誤って残りうるなら con_at で meta を書き、そうでなければ reuse_in_place
      → 変わったフィールドだけを書く
  偽: is_last(x)
        真: 残さない子を decref → free_block(x) → alloc してすべてのフィールドを書く
        偽: 残す子を dup → decref x → alloc してすべてのフィールドを書く
```

`is_last` の枝は rc -1 の物体 (共有の親から `lin` の子が届く形) のためにあり、そこでも箱は使い回さない。

- token による再利用は所有の受け渡しで、解放の後の使用ではない
- token の箱は中身を消さない。一意の道で「同じ位置の同じフィールドは書かない」特殊化 (Koka の reuse の特殊化) は、古いフィールドが箱に残っていることに頼るためである
- token にできるのは、種類の欄で「token にできる」物体 (今は `Data`) だけである
- reuse の条件は、物理的な語の数が同じことである。型やコンストラクタが違ってもよい (cons の箱をタプルに使える。Koka と同じ)。語の数が同じ物体はいつも同じ級なので、級の刻み方は reuse に関係しない。検査モードが確かめられるのは級が同じことまでで、語の数が同じことはコンパイラが守る
- 共有の印の付いた物体は、rc の値によらず reuse しない (Lean 4、Koka と同じ)。`is_unique` が偽になるので、部品の側で特別に扱う必要はない
- reuse の token を継続のクロージャに入れない約束 ([ロードマップ](../future/roadmap.md) の「処理系」) はコンパイラが守る。検査モードは、破ったときに起きる2回の使用を見つける (下の「検査モードの token」)

## 検査モード

検査モードは、今の `eml_runtime` の検査付きヒープ ([ランタイム](runtime.md) の「`debug_heap`」) の役を引き継ぐ。解放した領域を使い回さず、前置きに状態を書き、生きている物体を数えて、下の「報告する誤り」を見つける。

### モードの選び方

- モードは `Heap<M: Mode>` の型の引数で選ぶ。`Mode` は封じた trait で、`Fast` と `Checked` の2つがある。各操作は `if M::CHECKED { … }` で検査を書き、速いモードではこの分岐が単相化で消える
- 実行時の旗にしないのは、速いモードの RC の速い道に、検査のための分岐を1つも足さないためである。VM は2つのモードで単相化して2つ作る。ネイティブは、コンパイル時にどちらかを選ぶ
- 仕事の回数 (`Stats` の `rc_increments`、`rc_decrements`、確保の回数 `allocations`、生きている箱の数 `live` とその最大 `peak_live`) は、検査モードだけで数える。速いモードは数える費用も持たない。S10 では、`RunStats` の回数の固定と UI テストを検査モードで走らせ、`bench/run.sh` の命令の数は速いモードで測る。OS から取ったページのバイト数だけは、両方のモードで数える (上の「確保と解放」)

まだ決めていないこと: `RunStats` の各項目の VM での意味 ([ロードマップ](../future/roadmap.md) の「S10 VM と切り替え」)。`string_bytes_copied` は、VM が `string_push` を呼ぶ前に `is_unique` と容量を見れば数えられるので、`eml_rt` に欄を足さない。一意な左辺を作り直すときの数え方は、そこで決める。

### 前置き

- 検査モードでは、各ブロックがヘッダの前に1語の前置きを持つ。ポインタはどちらのモードでもヘッダを指すので、命令の側のコードは同じである
- 前置きは2つの `u32` の欄で、T2 の関数が Relaxed で読み書きする
  - 1つ目は、普通の物体では所有者 ID、`alloc_immortal` の物体では外に出ている参照の数 (下の「不死の物体の数え方」) である。不死の物体は持ち主を持たないので、同じ欄を使う
  - 2つ目は、状態 (生存、token、空ける途中、解放の4つ) と世代の番号 (残りのビット) である。世代の番号は、`into_token` と解放のたびに1つ進める
- 検査モードのどの操作も、rc を見る前に前置きを読む。解放した共有の物体は、最後の `decref` で rc が 0 になっているので、rc を先に見ると不死の物体と区別できないためである
- 検査モードは、解放したブロックを空きリストに戻さず、状態を「解放」にして残す (隔離)。そのため、解放した物体の語を後で使っても、指す先はまだ確保したままのメモリで、UB にならずに見つけられる。大きい物体のページも、検査モードでは解放したときに返さず、`Heap` を落とすときに返す

### 検査モードの token

token (`Token`) はどちらのモードでも1語である。S10 の VM のレジスタと、後のネイティブの値の大きさを、モードで変えないためである。VM は `into_word` で語にしてレジスタに置き、`from_word` で token に戻す。

- 速いモードの token は、箱を指す語か、空を表す語 (`Token::EMPTY`) である
- 検査モードの token は、`Heap` が持つ token の表の添字を入れた即値である。表の項目は、箱と、`into_token` のときの世代の番号の組である
- 項目は、token を使ったときか `drop_token` のときに空ける。添字は使い回さない。空けた項目を空のまま残して、古い token を確実に断るためである
- token を使う操作は、表の項目を引き、項目が空でないこと、箱の状態が token であること、世代の番号が項目のものと同じことを確かめる

多重の再開では ABA の形が起きうる。たとえば、1回目の再開が `con_at(t)` で y を作り、y が後で一意になって `into_token` でまた token になったとする。箱の状態は token に戻るが、新しい token は別の添字を持ち、t の項目は空のままなので、2回目の再開が古い t を使うと断られる。世代の番号も進んでいるので、箱の側から見ても古い t とは合わない。

### 不死の物体の数え方

今の `eml_runtime` の検査付きヒープは、不死の物体の外に出ている参照を数え、数が 0 の物体へのどの操作も解放の後の使用として断る ([ランタイム](runtime.md) の「不死の物体」)。そこでの不死の物体は子を持たない文字列のリテラルだけなので、この形で足りている。`eml_rt` の不死の物体は、`CodeBase` の定数のように子を持ちうる。親が子への参照を構造として持ち、親を作るときに `set_field` で子を書き、子を親から借りて読むので、同じ規則では正しいプログラムを断ってしまう。そこで、検査モードは次の形で数える。

- 数えるのは、外に出ている参照、つまり `acquire_immortal` と `dup` で作り、`decref` で手放す参照だけである。不死の親が子に持つ参照は構造の一部で、数えない
- `alloc_immortal` の物体は、数を 0 にして作る。`acquire_immortal` が数を1つ増やし、`dup` が1つ増やし、`decref` が1つ減らす。数が 0 になっても解放しない
- 誤りにするのは、数が 0 の物体への `decref` (作っていない参照を手放すこと) と、不死でない物体への `acquire_immortal` である。読む操作 (`field`、`raw`、`scanned`) と `set_field` と `dup` は、数を見ない。`dup` を断らないのは、不死の親から借りた子を `dup` して所有するのが正しい形だからである
- リークの報告では、数が 0 でない不死の物体の数を、件数に足す
- ダミーは数えない (上の「ダミーの値」)。前置きの1つ目の欄を `u32::MAX` にして作り、この値の物体は数を変えも確かめもしない
- 速いモードでは、`acquire_immortal` は何もせず、不死の物体の `dup` と `decref` は rc 0 を見て何もしない
- 今の検査より弱くなるのは、数が 0 の不死の物体を読むことを断らない点である。不死の物体のメモリは解放されないので、読んでも UB にはならない。手放しすぎと手放し忘れは、`decref` の誤りとリークの報告で見つかる

まだ決めていないこと: `box 5` の定数や文字列リテラルなど、`CodeBase` の定数を、生成したときから不死の物体にするか ([ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)。

### 報告する誤り

検査モードは次を `Err` (`HeapError`) で返す。

- 解放した物体の使用 (`UseAfterFree`)。語を受ける操作は、前置きの状態が生存でない語を断る。解放の連鎖が、空ける途中の物体にもう一度届いたときも同じ誤りにする (下の「検査モードの約束」)
- 数が 0 の不死の物体への `decref` (`ImmortalOverRelease`) と、不死でない物体への `acquire_immortal` (`NotImmortal`)。上の「不死の物体の数え方」
- `lin` ビットの立った物体への `dup` (`LinDup`)。`lin` の物体の rc は 1 なので、rc が 1 を超える誤りは、この `dup` で見つかる
- `lin` ビットの立った共有の物体の `release` と `decref` (`LinShared`)。`share` は `lin` の物体に印を付けないので、これは印付けの誤りである。`share` のたどりが、すでに共有の `lin` の物体に届いたときも同じ誤りにする
- `share` のたどりで、同じ `lin` の物体に2回届くこと (`LinReachedTwice`)
- 所有者の不一致 (`WrongOwner`)。正の rc の物体への `dup`、`decref`、`set_field`、`set_raw`、`is_unique`、`is_last`、`free_block`、`into_token`、`release`、`release_reuse` が、今の worker ID と違う所有者の物体に対して行われたとき
- token の誤り。token にできない種類の `into_token` (`NotTokenable`)、一意でない物体の `into_token` (`NotUnique`)、空けた表の項目の使用、箱の状態が token でないこと、世代の番号の不一致 (`StaleToken`。token を受ける操作が断る。同じ token の2回の使用と ABA の形)、級の合わない `con_at` (`WrongClass`)、`reuse_in_place` の `meta` の tag と scan と種類が箱と違うこと (`WrongMeta`)、`reuse_in_place` で箱が `lin` ビットを持ち新しい `meta` が持たないこと (`LinBitKept`)
- `free_block` を、破棄処理を持つ種類の物体に使うこと (`FinalizerSkipped`) と、最後の参照でない物体に使うこと (`NotLast`)
- `release` と `release_reuse` で、物体がデータでないか、タグと走査する語の数が名指したものと違うこと (`WrongLayout`)
- `unbox_int`、`foreign`、`string`、`string_push`、`string_concat` で、物体の種類が違うこと (`WrongKind`)。`foreign` は値の型も照らし、速いモードでも同じ誤りを返す (上の「核の操作」)
- 添字の範囲の外 (`OutOfBounds`)。`field` と `set_field` は、添字が走査する語を指さないことを断る。`raw` と `set_raw` は、添字が走査する語の後のブロックの中の語を指さないことを断り、ペイロードが不透明な物体 (`Foreign` と `String`) を `WrongKind` で断る。`scanned` は、添字が走査する語の数以上であることを断る。走査する語に生の値を書くと、解放の連鎖がその値をポインタとして読み、`Foreign` の破棄処理の表を上書きすると、破棄処理が正しくない関数のポインタを呼ぶ。`String` の長さの語を書き換えると、`string` が容量の外を読む。どれも検査モードの安全を崩すので、断る
- 生存の列挙 (`check_invariants`) で見つかる不変条件の違反
  - 共有の物体から、共有でも不死でもない物体が届き、それが `lin` ビットの立った局所の物体でもないこと (`SharedReachesLocal`)。上の「`share`」の理由で、`lin` ビットの立った局所の物体は許す
  - 不死の物体から、不死でない物体が届くこと (`ImmortalReachesMortal`)。`share` は不死の物体でたどりを止めるので、不死の物体の子が局所なら、印なしに別のスレッドから届く。Koka の PR #910 は、プロセス全体で共有する物体が atomic でない RC を持っていたために、2つのスレッドで動かすとヒープが壊れたと報告している。その誤りがこの形である
- リーク (`leaks`)。生きている不死でない物体と、使われずに残った token を、種類の名前ごとに数える。token は種類の名前 `Token` で数える

`Err` を返した後もヒープを使い続けてよいかは、状態を変える前の `Err` かどうかで決まる (下の「検査モードの約束」)。

### 検査モードの約束

検査モードは、空けたブロックを使い回さず、その権限を `Heap` に持ったままにする。大きい物体のページも返さない。そのため、検査モードのメモリの安全には、モデルの数が正しいことが要らない。

各操作の前提は、次の3種類に分かれる。

- 安全の前提: どちらのモードでも前提にし、検査モードも確かめない。破ると、検査モードでもメモリの安全が崩れうる
- モデルの前提: どちらのモードでも前提にし、検査モードも確かめない。破るとモデルの数が合わなくなるが、検査モードのメモリの安全は崩れない。速いモードでは、モデルの数が合わないとメモリの安全が崩れる
- 検査する前提: 速いモードでは前提にし、検査モードでは確かめて `Err` を返す

不変条件も2つに分かれる。`safe_wf` は権限の持ち方とブロックの状態の不変条件で、モデルの数と辺には触れない。`full` は、抽象のモデルとの対応を含む不変条件である。`full` が成り立つことを、モデルが合っていると言う。性質は次のとおりである。

- 検査モードの操作は、安全の前提の下で `safe_wf` を保つ
- モデルが合っていて、モデルの前提と検査する前提がすべて成り立つなら、操作は `Ok` を返し、結果は速いモードと同じモデルの遷移になる。ただし、モデルは不死の物体の外の参照の数、共有の物体の `lin` ビット、物体の持ち主、確保器の級、箱の `meta` を照らす規則を持たない。そのため、解放の連鎖が手放す子についての `ImmortalOverRelease`、`LinShared`、`WrongOwner`、`con_at` の `WrongClass`、`reuse_in_place` の `WrongMeta` と `LinBitKept` は、モデルが合っていても返りうる
- `Err` を返すのは、その誤りに対応する違反が操作の前にあったときだけである
- 状態を変える前に `Err` を返す操作では、ヒープは変わらない。状態を変えた後で `Err` を返しうるのは、解放の連鎖 (`decref`、`release`、`release_reuse` の子の処理)、`release` の最後でない枝の `dup` の列、`share`、`con_at` (token の項目を取り出した後の `WrongClass`) である。その後はモデルが合わなくてよく、ヒープを使わない。ただし `Heap` を落とすことは安全である

同じ物体を2回空けないように、最後の参照と決めた時点で、その物体の前置きを「空ける途中」にする。`release_ref`、`release` の最後の参照の枝、`release_reuse` の子の処理の前がこれに当たる。呼ぶ側が `dup` せずに同じ語を2つのフィールドに書いた親を空けると、同じ子に2回届く。2回目に届いたときは、生きていないので `UseAfterFree` を返す。`Err` で解放の連鎖が途中で止まると、積んだまま空けていない物体が「空ける途中」で残る。`Heap` を落とすときは、その中の `Foreign` の破棄処理を1回だけ呼ぶ。生存の列挙、不変条件の検査、リークは、「空ける途中」の物体を生きている物体と同じに扱う。

token の表の項目は、`into_token` と `release_reuse` が添字を使い回さずに積み、取り出すと空にする。そのため、項目があればその箱は token の状態で、世代の番号は項目のものに等しい。`safe_wf` はこの不変条件を持つので、世代の番号が回っても検出は外れない。

不死の物体の数が `u32` の上限に届くときは panic する。

### 論理的な worker ID

- `Heap` は今の論理的な worker ID を持つ。確保した物体の所有者を今の ID にする
- 物理的な worker が1つでも所有者の検査を働かせるために、ID を切り替える操作 (`set_worker`) を持つ。所有者 ID の使い方は [マルチコア対応の設計](../future/multicore.md) の「論理的な worker ID」にある
- 今 ID を切り替えるのは単体テストだけである。UI テストで所有者の検査が効き始めるのは、`par` を入れたときである

まだ決めていないこと: 論理的な worker ID を置く実行文脈 `Ctx` の形 ([ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)。

## `unsafe` の核

- `unsafe` は小さい核に閉じる。核は、確保器、ヘッダとフィールドの読み書き、文字列のバイトの読み書き、`dup`、`decref`、解放の連鎖、token の操作である。それ以外 (`share` のたどり、`release` の組み立て、生存の列挙) は核の操作を呼んで書く
- 核では SeqCst と `fence` を使わない
- `eml_rt` のコードは、核を含めて Verus の `verus!` の中に書き、`cargo verus verify -p eml_rt` が crate 全体を検証する ([テスト戦略](../implementation/testing.md) の「Verus」)。生のポインタの読み書きは、どれも Verus の権限 (`PointsTo`) の上で行う。証明するのは、公開の操作の前提 (上の「核の操作」の表) の下でのメモリの安全、ヒープの形の不変条件、RC と抽象のモデルの対応、`share` と `release` と reuse の遷移、上の「検査モードの約束」の性質である
- 確保と atomic の操作は、std の関数を薄い関数で包み、その関数の約束を信頼する (下の表の T1 と T2)。vstd の確保は失敗すると `process::abort` を呼び、vstd の atomic は SeqCst だけを扱うので、使わない。包みは std の関数を1回呼ぶだけで、型を差し替える層ではない

Verus で確かめない部分は、次の信頼の一覧にまとめる。`external_body`、`assume_specification` などの信頼の項目は、どれもこの表のどれかに属する。`eml_rt` の `trust.rs` のテストが、テストでないコードの項目を探し、表の番号を付けた一覧と同じであることを確かめる。`verus!` の外に置くのは、`fmt` の実装、T4 の `Drop`、`unsafe impl Send` と `Sync`、`Sync` でないことの型の assert、`leaks` の `BTreeMap` を組む安全な関数、`Foreign` の表の `const` (T3)、テストだけである。

| T3 | `Foreign` の物体の中身。破棄処理の表 (関数のポインタ)、`TypeId` の照らし合わせ、`drop_in_place` | Verus は関数のポインタと `TypeId` を扱わない | 型の違う照らし合わせ、`Drop` を持つ値 (`Box`、`String`、`Vec`)、大きさ 0 の型、破棄処理が panic する場合、解放と `Heap` の破棄での破棄処理の呼び出しが1回だけであること |
| T4 | `verus!` の外の `Drop` の実装 (`Heap`、`Pages`) | Verus は利用者の `Drop` を扱わない。中身は検証した関数を呼ぶだけにする | T1 と T3 のテストが通る道 |
| T5 | 証明に使う std の約束のうち vstd にないもの。`ptr::without_provenance_mut` (`Word::imm` が const fn のまま即値を作るため) と、panic で止める関数 (大きさの桁あふれ、即値に収まらない `Word::imm`、不死の物体の数の桁あふれ、ページの配置の誤り) | vstd の std の約束が足りない。panic の関数は値を返さないことだけを約束する | なし (値の約束で、メモリに触れない) |
| T6 | `global` の宣言: 64 ビットの環境、`Word`、`Header`、`PageHeader`、前置きの配置 | Verus は `global` の宣言をコンパイル時に照らす | なし |
| T7 | unwind。検証した関数は、決まった所でしか unwind しないとして証明する。決まった所は、T5 の panic の関数 (状態を変える前に呼ぶ)、T3 の破棄処理 (箱を先に死んだことにしてから呼ぶ)、`Vec` の伸長である | Verus の `ensures` は正常に戻ったときだけを扱う。unwind の後も `Heap` を落とすことは安全でなければならない | 解放の連鎖の途中で破棄処理が panic した後に、`Heap` を落とすこと |
| T8 | 借用の規則 (Stacked Borrows と Tree Borrows) | vstd の権限のモデルは、参照と生のポインタの借用の規則を表さない | 核の各操作を両方のモードで1回ずつ通す小さいテスト |
| T9 | Verus、Z3、rustc、vstd (その std の約束を含む) | 道具そのもの | なし |
| T10 | 文字列のバイトの読み書き。`String` のブロックの権限を受けてペイロードにバイトを写す関数と、ペイロードを `str` として借りる関数と、その位置を返す関数。約束は、権限が渡したポインタの `String` のブロックのもので、長さの語とバイト列の語を持つとき、メモリのバイト列が権限の ghost のバイト列に等しいこと、写すのは長さの語の後ろの容量の中だけで、長さの語の値と権限の位置を変えないこと | Verus の権限は語の単位で、語の中のバイトの位置を扱わない | 語に揃わない位置への追記、大きい物体のページをまたぐ長さ、大きい左辺からの作り直し、空の文字列、多バイトの文字、1ページの長さを含む自分自身との連結 (`x ++ x`)、`string` で読んだ位置の使用が終わった後の追記、2つの借用の規則での読み書き |

T10 の約束は、関数そのものの外の次の2つにも頼る。

- `String` のバイト列の語を書くのは、T10 の書き込みの関数だけである。ほかの検証した書き込みは、この語に届かない。`raw` と `set_raw` は不透明なペイロードを断り (上の「種類」)、`set_field` は走査する語だけを書くためである。`string_concat` も同じ書き込みの関数で右辺を写す
- ghost のバイト列を、別の権限の列から写して代入しない。列の型は `meta.rs` の外では作れないが、ほかの権限の列を写すことはできてしまう。`trust.rs` のテスト `only_meta_assigns_the_ghost_text` が、`meta.rs` の外の代入を断る

写すのは生のポインタ (`ptr::copy_nonoverlapping`) だけで行い、同じブロックに `&mut [u8]` と `&[u8]` を同時に作らない。読み書きの範囲は、検証したコードの側の `requires` と `ensures` で縛る。T3 と同じ形である。

Miri は、表の「Miri で確かめること」を確かめる `trusted` の module のテストだけを流す ([テスト戦略](../implementation/testing.md) の「Miri」)。テストは信頼の部分へ届く検証したコードも通るので、T8 もそこで確かめる。

FFI の境界 (S9b-3 の extern の語の ABI と、その後の外の関数の呼び出し) を足すときは、この表に行を足し、Miri のテストを `trusted` の module に足す。

## 受け入れる制約

| 制約 | 理由 |
|---|---|
| 1つのデータの型のコンストラクタは 65536 個まで | `tag` を 16 ビットにするため |
| 物体の種類は 16 個まで | `info` の4ビットにするため |
| 64 ビットの環境だけを対象にする | 語を 8 バイトにするため |
| 速いモードでは、解放の後の使用、token の2回の使用、`File` の参照の重複を検出しない | 速い道に検査を置かないため。`lin` の物体の rc は 1 なので、その `dup` は速い道を通る。検出は verifier と、検査モードで走らせる UI テスト (S10 から) に任せる。今の `eml_runtime` は、解放の後の使用を世代番号で、`File` の重複を `Heap::dup` で、`debug_heap` によらず常に検出しているので、S10 からはどちらも `--debug-heap` のときだけになる。[ランタイム](runtime.md) と [LIR とインタプリタ](lir.md) の「実行時エラー」の該当の文は、S10 で改める |
| 小さい物体のページを、実行中に OS へ返さない | 核を小さく保つため。空きリストは級ごとなので、使う量は級ごとの生きていた量の最大の和で抑えられる (2 語の物体が多い時期の後に 4 語の物体が多い時期が来ると、両方の分を使う)。上の「確保と解放」のとおり、後で入れる |
| 局所の数が `i32::MAX` に達した物体と、共有の数が `DROP_LIMIT` を下回った物体は解放されない | 張り付きの方式による。物体を 2^31 - 2^17 回参照するには、参照だけで 16 GiB 近くが要る |
| 検査モードでは、使うメモリがそれまでに確保した量の合計になる | 解放したブロックを使い回さないため。token の表も `into_token` の回数に比例して伸びる。生存の列挙とリークの検査の時間も、確保した量の合計に比例する。UI テスト、`bench.rs`、`--debug-heap` の実行が検査モードで動くので、確保の多いプログラムではメモリが増える。足りなくなったら、隔離する量に上限を付ける |
| 検査モードでは、前置きの分だけブロックが大きくなる | 速いモードでちょうど 128 語の物体は、検査モードでは大きい物体の道を通る。2つのモードの確保器の道は、境目の大きさで違う |
