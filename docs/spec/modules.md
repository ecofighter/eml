# モジュールと名前解決

位置づけ: 規範。

モジュールの単位と置き場所、import の書き方、標準ライブラリ、名前の解決の順序、名前空間、公開の範囲を定める。

## モジュール

- 1ファイル = 1モジュールとする。`module` ヘッダは書かない
- 根は入口のファイル (`eml check` と `eml run` に渡したファイル) のディレクトリである。`eml run app/main.em` の根は `app/` になる
- モジュール名は根からのパスで決まり、大文字小文字まで完全に一致させる。`import Report.Csv` は `<根>/Report/Csv.em` を読む
- 入口のモジュールの名前は、ファイル名によらず `Main` である。入口のモジュールは、どの名前でも import できない
- `Prelude`、`Main`、`Std` は予約したモジュール名である。根に `Prelude.em`、`Main.em`、`Std.em` があっても import できない
- `Prelude` (`Bool`、`println` など。`Option`、`Result`、`List` は S4 で入る) を暗黙に取り込む (下の「Prelude」)
- エントリポイントは、入口のモジュールの `main : Unit -> <IO> Unit` とする。終了コードは標準ライブラリの `exit` で扱う ([標準ライブラリへの申し送り](../future/stdlib.md))
- 公開するものには `pub` を付ける ([宣言](declarations.md) の「`pub`」と、下の「公開の範囲」)

```
app/
  main.em          -- Main (入口)
  Report/
    Csv.em         -- Report.Csv
    Format.em      -- Report.Format
```

## import

| 書き方 | 効果 |
|---|---|
| `import Report.Csv` | 修飾子 `Csv` を作る。`Csv.parse` のように使える |
| `import Report.Csv as C` | 修飾子 `C` だけを作る。`C.parse` |
| `import Report.Csv (parse, Row)` | 修飾付きに加えて、列挙した名前を修飾なしで使える |
| `import Report.Format (Style(..))` | 型とそのコンストラクタを、修飾なしで使える |
| `import State (State(..))` | エフェクトとその操作を、修飾なしで使える |

- import は、ファイルの先頭で宣言より前に書く。宣言の後の import は E0011 にする
- import は既定で修飾付きである。修飾子は1つのセグメントで、パス全体を使った `Report.Csv.parse` は E1031 になる
- 同じ修飾子を2つの import が作ったときは、両方のモジュールを合わせて引く。同じモジュールを2回 import しても誤りにしない
- import の並びの小文字の名前と `(op)` は値を取り込む。`(op)` は `:` で始まらない演算子に限り、`(:+)` は E0011 にする。中置のコンストラクタは `T(..)` で取り込む
- import の並びに書いた大文字の名前は、型かエフェクトだけを取り込む。コンストラクタは `T(..)` の形で、操作は `E(..)` の形でだけ修飾なしにできる。型とコンストラクタが同じ名前を持てるため、`import M (Point)` は型の `Point` だけを取り込む
- 並びの名前がモジュールにないときは、値なら E1001、型とエフェクトなら E1002 にする。ユーザーのモジュールの `pub` でない名前なら E1029 にする。どれも並びの位置で1回だけ報告する。並びにコンストラクタを書いたときも E1002 で、型と一緒に取り込む `T(..)` の形を help で示す
- 演算子の fixity は、宣言が `pub` のときに演算子と一緒に付いてくる ([宣言](declarations.md) の「fixity」)。修飾した演算子の構文はないので、別のモジュールの演算子は import の並びで取り込んで使う
- import したモジュールのファイルがないか、読めない (UTF-8 でない、IO の誤り) ときは E1026 にする。大文字小文字だけが違うファイルやディレクトリがあるときも E1026 で、メッセージに実際の名前を書く。ユーザーの根にファイルがないときの標準ライブラリへの探し方は、「標準ライブラリ」に書く
- 標準ライブラリのモジュール (`Fs` など) の読み方は、下の「標準ライブラリ」にある

### import の循環

import の循環は E1027 にする。型検査は item と SCC の単位で動くので、循環を許しても実装の負担はほぼない。それでも禁じるのは、モジュールの依存をいつも DAG にしておけば、インクリメンタル化、REPL の `:load`、型クラスの段の orphan 規則をモジュールの順で考えられるためである。後で許すように緩めても、通っていたプログラムは通り続ける。

### Prelude

- Prelude は暗黙に取り込む。`Prelude` はどのモジュールでも修飾子として使え、自分の定義で隠した名前も `Prelude.not` のように引ける
- 修飾子が `Prelude` になる import は E1030 にする。`import Prelude`、最後のセグメントが `Prelude` のパス (`import Util.Prelude`)、別名の `as Prelude` である。暗黙の修飾子 `Prelude` が、ほかのモジュールと合流しないようにするためである。`import Main` と、入口のファイルを指す import も E1030 にする
- Haskell の `import Prelude hiding (...)` にあたる構文はなく、Prelude の取り込み方を変える手段を設けない
- Prelude は標準ライブラリのモジュールの1つで、置き場所は `std/Prelude.em` である (次の「標準ライブラリ」)

## 標準ライブラリ

標準ライブラリは、リポジトリの `std/` ツリーのモジュールで、処理系のバイナリに埋め込まれている。`std/` は `Prelude.em` と `Fs.em` の2つからなる。`Fs` はファイルを読む標準モジュールで、`File`、`open`、`read_all`、`close` を持つ。標準ライブラリのモジュールだけが `extern` を書ける ([宣言](declarations.md) の「`extern`」)。

- 標準ライブラリのモジュールの正式な名前は、予約した根 `Std` の下に置く (`Std.Fs`)。`Prelude` だけは `Prelude` のままである。診断に出すパスは `<std>/Prelude.em`、`<std>/Fs.em` のように書き、手元の相対パスと区別する
- 標準ライブラリのモジュールは、使うかどうかによらずすべて読み込む
- `import Std.Fs` はいつも標準ライブラリを指す。`import Std.Nope` は E1026 で、ユーザーの根は読まない。`import Std` は `Std` が標準ライブラリの根なので E1030 にする
- `import Std.Prelude` は、別名を付けても E1030 にする。Prelude は暗黙に取り込むので、import できない
- `import Fs` は、まずユーザーの根の `Fs.em` を探し、ファイルが見つからないときだけ標準ライブラリの `Fs` を探す。ユーザーの `Fs.em` があれば、それを優先する。大文字小文字だけが違うファイルがあるときや、あっても読めないときは E1026 で、標準ライブラリには進まない
- `as Std` の別名は書ける。`Std` は暗黙の修飾子ではないので、ほかのモジュールと合流しない
- 標準ライブラリのモジュールも `Prelude` を暗黙に取り込む。標準ライブラリのモジュールどうしは、`import` で明示して使う。標準ライブラリのモジュールの import は `std/` だけを探し、ユーザーの根は読まない。循環 (E1027) は標準ライブラリの中の依存もすべて見る
- 標準ライブラリのモジュールの `pub` でない item (`Prelude` の `negate` など) は、ユーザーからは定義がないものとして扱う。`Prelude.negate` は E1029 ではなく E1001 である
- ユーザーのモジュールが `File` を定義していて標準ライブラリの `File` と重なるときだけ、型の表示は標準ライブラリのものを `Std.Fs.File` と書く。ほかは `File` と短く書く

## 名前の解決

修飾しない名前は次の順に引く。

1. ローカルの束縛
2. 自分のモジュールのトップレベル。import した名前と Prelude の名前を、診断を出さずに隠す
3. import の並びで修飾なしにした名前
4. Prelude の `pub` の名前

- 3 で、同じ名前が別々の定義を指すときだけ、その名前を使った位置で E1028 にする。同じ定義を複数の import が出しても曖昧にしない。import を書いた時点では誤りにしない
- 修飾した名前 `Q.x` は、修飾子 `Q` のモジュールだけを引き、上の順は通らない。修飾子は次の順で決める
  1. `Prelude` は Prelude を引く
  2. そのモジュールの import が修飾子 `Q` を作るなら、その import のモジュールだけを引く。標準ライブラリには進まない
  3. そうでなければ、標準ライブラリのモジュール `Q` (正式な名前 `Std.Q`) を引く。この短い名前は、import なしで使えるが、ユーザーのモジュールでだけ使える。import していないユーザーの `Fs.em` は引かない
  4. どれもなければ E1031 にする。修飾子が `Std.Fs` のように標準ライブラリのモジュールの正式な名前なら、短い名前での書き方 (`Fs.close`) を help で示す

  合流した修飾子では、別々の定義が2つ以上見つかったときに E1028 にする。モジュールに名前がなければ E1001 か E1002 (メッセージに「in module `Report.Csv`」と書く)、ユーザーのモジュールの `pub` でない名前なら E1029 である
- 修飾した名前は、式、型、パターン、row のエフェクト、handler の節の先頭に書ける
- ユーザーのモジュールが標準ライブラリのモジュールと同じ名前でも、import が作る修飾子はユーザーのモジュールだけを引く。この優先は import にだけかかる
- handler の節の先頭の名前 (`| get () k ->` の `get`、`| State.get () k ->` の `State.get`) は、エフェクトの操作だけから解決する。ローカルの変数が同じ名前で操作を隠していても、節の解決には影響しない
- 種類の決まった位置 (パターンの先頭はコンストラクタだけ、節の先頭は操作だけ) では、修飾しない名前の各段でも、修飾子を通る場合でも、その種類の定義だけを見る。曖昧さも、同じ種類の定義どうしでだけ数える。各段では、名前の定義のうちその種類で最初のものを引く。ユーザーが `println` という関数を定義していても、自分のモジュールに `println` という操作がなければ、節の `| println s k` は操作が見つからず、次に extern の関数だけを引いて `Prelude` の `println` に届くので E1009 になる ([エフェクトと handler](effects.md) の「組み込みの `IO`」)

```haskell
-- State.em
pub effect State where
  get : Unit -> Int

-- main.em
import State

counter : Unit -> <State.State> Int
counter () = State.get () + 1

run : Int -> Int
run n =
  handle counter () with
    | State.get () k -> k n
    | return x -> x
```

## 名前空間

- 値の名前空間には、変数、関数、エフェクトの操作、コンストラクタを置く。エフェクトの操作は関数と同じく import する。変数・関数・操作は小文字、コンストラクタは大文字で始まるので、字句の上で区別できる
- 型の名前空間には、型名とエフェクト名を置く
- 型とコンストラクタは別の名前空間にあるので、同じ名前を持てる (`data Point = | Point Int Int`)
- 同じ名前空間でのトップレベルの定義の重複はエラーとする。エフェクトの操作はトップレベルの値なので、操作名がトップレベルの関数名や他の操作名 (別のエフェクトの操作を含む) と重なれば重複エラーになる。別々の `data` が同じ名前のコンストラクタを持つ場合も同じである。同じ名前の操作を使い分けたいときは、別のモジュールに置いて修飾付きの名前 (`Reader.get`) で区別する
- 重複は次の3つの規則で扱う
  1. 名前ごとに、その名前の定義をソースの順にすべて持つ。最初の定義がその名前の定義で、2つ目以降は E1003 になる。E1003 は最初の定義を「first defined here」で指す。重複した定義の本体も変換して検査するので、本体の中の誤りも報告する
  2. 重複した `data` のコンストラクタと、重複した `effect` の操作は使えない。それらを参照した位置は、診断を出さずに誤りの式として扱う。最初の定義の型と比べて「expected `T`, found `T`」のような誤りを連鎖させないためである
  3. 種類の決まった位置 (「名前の解決」のパターンと節の先頭) では、名前の定義のうち、その種類で最初のものを引く。操作の後に同じ名前の関数を定義すると、関数が E1003 になり、節は操作を引く。関数を先に定義した場合も、節は操作を引く
- `data` とエフェクトの型引数の重複も E1003 で、宣言の中で最初の定義を残す

## 公開の範囲

- `pub` を付けた item の型に、同じモジュールの `pub` でない型かエフェクトが現れたら E1032 にする。対象は、`pub` のシグネチャ、`pub data` のコンストラクタのフィールド、`pub effect` の操作のシグネチャである。row の中のエフェクトも含む
- 理由は2つある。1つは、コンストラクタを隠した抽象型を、後で `pub data` の形で意図して入れるためである ([ロードマップ](../future/roadmap.md) の「言語機能と構文」)。非公開の型を返す公開の関数を許すと、その前に裏口の抽象型ができてしまう。もう1つは、非公開のエフェクトを row に持つ公開の関数を、import する側が handle できないためである。その関数を呼ぶと、名前も書けないエフェクトが残る

名前解決の診断 (重複定義、未定義の名前など) の番号の範囲は [診断](diagnostics.md) にある。
