# モジュールと名前解決

位置づけ: 規範。

モジュールの単位と置き場所、import の書き方、標準ライブラリ、名前の解決の順序、名前空間、公開の範囲を定める。

## モジュール

- 1ファイル = 1モジュールとする。`module` ヘッダは書かない
- 根は入口のファイル (`eml check` と `eml run` に渡したファイル) のディレクトリである。`eml run app/main.em` の根は `app/` になる
- モジュール名は根からのパスで決まり、大文字小文字まで完全に一致させる。`import Report.Csv` は `<根>/Report/Csv.em` を読む
- 入口のモジュールの名前は、ファイル名によらず `Main` である。入口のモジュールは、どの名前でも import できない
- `Prelude`、`Main`、`Std` は予約したモジュール名である。根に `Prelude.em`、`Main.em`、`Std.em` があっても import できない
- `Prelude` (`Bool`、`List`、`Option`、`Result`、`println` など) を暗黙に取り込む (下の「Prelude」)
- エントリポイントは、入口のモジュールの `main` とする。型は `Unit -> <…> Unit` で、row のラベルは `IO` と `Panic` だけ (順は問わず、どちらも省ける) で、row 変数の末尾を持たない。`Unit -> Unit`、`Unit -> <IO> Unit`、`Unit -> <Panic> Unit`、`Unit -> <IO, Panic> Unit` のどれでもよい。ほかの型は E2004 にする。終了コードは標準ライブラリの `exit` で扱う ([標準ライブラリ](stdlib.md) の「`exit`」)
- 公開するものには `pub` を付ける ([宣言](declarations.md) の「`pub`」と、下の「公開の範囲」)

```
app/
  main.em          -- Main (入口)
  Report/
    Csv.em         -- Report.Csv
    Format.em      -- Report.Format
```

## import

| 書き方 | 効果 |
|---|---|
| `import Report.Csv` | 修飾子 `Csv` を作る。`Csv.parse` のように使える |
| `import Report.Csv as C` | 修飾子 `C` だけを作る。`C.parse` |
| `import Report.Csv (parse, Row)` | 修飾付きに加えて、列挙した名前を修飾なしで使える |
| `import Report.Format (Style(..))` | 型とそのコンストラクタを、修飾なしで使える |
| `import State (State(..))` | エフェクトとその操作を、修飾なしで使える |
| `import Shapes (Area(..))` | クラスとそのメソッドを、修飾なしで使える |

- import は、ファイルの先頭で宣言より前に書く。宣言の後の import は E0011 にする
- import は既定で修飾付きである。修飾子は1つのセグメントで、パス全体を使った `Report.Csv.parse` は E1031 になる
- 同じ修飾子を2つの import が作ったときは、両方のモジュールを合わせて引く。同じモジュールを2回 import しても誤りにしない
- import の並びの小文字の名前と `(op)` は値を取り込む。`(op)` は `:` で始まらない演算子に限り、`(:+)` は E0011 にする。中置のコンストラクタは `T(..)` で取り込む
- import の並びに書いた大文字の名前は、型、エフェクト、クラスだけを取り込む。コンストラクタは `T(..)` の形で、操作は `E(..)` の形で、メソッドは `C(..)` の形でだけ修飾なしにできる。型とコンストラクタが同じ名前を持てるため、`import M (Point)` は型の `Point` だけを取り込む。`import M (Eq)` もクラスだけを取り込み、メソッドは修飾して使う (`M.same`)。修飾した演算子の構文はないので、演算子のメソッドを修飾なしで使うには `C(..)` で取り込む
- 並びの名前がモジュールにないときは、値なら E1001、型とエフェクトなら E1002 にする。ユーザーのモジュールの `pub` でない名前なら E1029 にする。どれも並びの位置で1回だけ報告する。並びにコンストラクタを書いたときも E1002 で、型と一緒に取り込む `T(..)` の形を help で示す
- 演算子の fixity は、宣言が `pub` のときに演算子と一緒に付いてくる ([宣言](declarations.md) の「fixity」)。修飾した演算子の構文はないので、別のモジュールの演算子は import の並びで取り込んで使う
- import したモジュールのファイルがないか、読めない (UTF-8 でない、IO の誤り) ときは E1026 にする。大文字小文字だけが違うファイルやディレクトリがあるときも E1026 で、メッセージに実際の名前を書く。ユーザーの根にファイルがないときの標準ライブラリへの探し方は、「標準ライブラリ」に書く
- 標準ライブラリのモジュール (`Fs` など) の読み方は、下の「標準ライブラリ」にある

### import の循環

import の循環は E1027 にする。型検査は item と SCC の単位で動くので、循環を許しても実装の負担はほぼない。それでも禁じるのは、モジュールの依存をいつも DAG にしておけば、インクリメンタル化、REPL の `:load`、型クラスの orphan 規則 (下の「instance の一貫性」) をモジュールの順で考えられるためである。後で許すように緩めても、通っていたプログラムは通り続ける。

### Prelude

- Prelude は暗黙に取り込む。`Prelude` はどのモジュールでも修飾子として使え、自分の定義で隠した名前も `Prelude.not` のように引ける
- Prelude の `pub class` のメソッド (`==`、`compare`、`show` など) も、ほかの Prelude の名前と同じく修飾なしで見える。自分のモジュールで `show` を定義すると Prelude の `show` を隠すので、そのモジュールでは `Prelude.show` と書いて引く
- リストの構文 `[…]` は、名前を引かずに Prelude の `Nil` と `::` を指す。自分の `Nil` で Prelude の `Nil` を隠しても、`[]` は Prelude の空のリストである ([式](expressions.md) の「リスト」)
- 修飾子が `Prelude` になる import は E1030 にする。`import Prelude`、最後のセグメントが `Prelude` のパス (`import Util.Prelude`)、別名の `as Prelude` である。暗黙の修飾子 `Prelude` が、ほかのモジュールと合流しないようにするためである。`import Main` と、入口のファイルを指す import も E1030 にする
- Haskell の `import Prelude hiding (...)` にあたる構文はなく、Prelude の取り込み方を変える手段を設けない
- Prelude は標準ライブラリのモジュールの1つで、置き場所は `std/Prelude.em` である (次の「標準ライブラリ」)

## 標準ライブラリ

標準ライブラリは、リポジトリの `std/` ツリーのモジュールで、処理系のバイナリに埋め込まれている。`std/` は `Prelude.em`、`Fs.em`、`List.em`、`String.em`、`Env.em`、`Stdin.em`、`Proc.em`、`Yield.em`、`Fail.em`、`State.em`、`Iter.em`、`Float.em`、`Char.em`、`Byte.em`、`Bytes.em`、`Array.em`、`MutArray.em` からなる。各モジュールの関数は [標準ライブラリ](stdlib.md) にある。標準ライブラリのモジュールだけが `extern` を書ける ([宣言](declarations.md) の「`extern`」)。

- 標準ライブラリのモジュールの正式な名前は、予約した根 `Std` の下に置く (`Std.Fs`)。`Prelude` だけは `Prelude` のままである。診断に出すパスは `<std>/Prelude.em`、`<std>/Fs.em` のように書き、手元の相対パスと区別する
- Prelude はいつも読み込む。ほかの標準ライブラリのモジュール `X` は、次のどれかのときだけ読み込む。すべてを毎回読み込むと、標準ライブラリを足すたびに、すべての実行と REPL の入力の検査が遅くなるためである
  - 読み込んだモジュールが `X` を import する (`import String`、`import Std.String as S`)
  - 読み込んだユーザーのモジュールが、パスが `X` の import を書く。ユーザーの根の `X.em` が import の先になる場合も読む。そのユーザーのモジュールにない名前を引いたときに、`import Std.X as F` と書けば標準ライブラリに届くことを示す help (下の「名前の解決」の手順 4) を付けるためである
  - 読み込んだユーザーのモジュールの構文に、`X` か `Std.X` が修飾子として現れる。修飾子は名前解決より前に、位置によらず構文木の名前の経路のすべてから拾う (式、型、パターン、row のエフェクト、handler の節の頭、クラスの制約、instance の頭、レコードを作る式、補間の穴の中など)。`Std.X` を数えるのは、E1031 の help (下の「名前の解決」) が標準ライブラリの `X` を引くためである
- 標準ライブラリのモジュールどうしは import で明示するので、読み込む集合は import をたどって閉じる。ユーザーが自分の `X` を import していると、使わない標準ライブラリの `X` を読むことがあるが、名前解決は import を先に見るので結果は変わらない
- モジュールの番号は読み込んだ順である。Prelude が 0、入口が 1 で、その後は、モジュールを番号の順に処理しながら、import と修飾子をたどって見つけた順に並ぶ。1つのモジュールでは、import の先を宣言の順に読んでから、修飾子の標準ライブラリを読む。標準ライブラリのモジュールとユーザーのモジュールは混ざって並ぶ。番号はファイルを足したときに決まり、構文の診断がもう持っているので、後から並べ替えない
- `import Std.Fs` はいつも標準ライブラリを指す。`import Std.Nope` は E1026 で、ユーザーの根は読まない。`import Std` は `Std` が標準ライブラリの根なので E1030 にする
- `import Std.Prelude` は、別名を付けても E1030 にする。Prelude は暗黙に取り込むので、import できない
- `import Fs` は、まずユーザーの根の `Fs.em` を探し、ファイルが見つからないときだけ標準ライブラリの `Fs` を探す。ユーザーの `Fs.em` があれば、それを優先する。大文字小文字だけが違うファイルがあるときや、あっても読めないときは E1026 で、標準ライブラリには進まない
- ユーザーの `Fs.em` を `import Fs` で読むと、修飾子 `Fs` はユーザーのモジュールを指し、標準ライブラリの `Fs` は隠れる。`Fs.open` のように修飾して引いた名前がユーザーの `Fs` になく、標準ライブラリの `Fs` が `pub` で定義していれば、E1001 か E1002 に「`import Std.Fs as F` で標準ライブラリに届く」という help を付ける
- `as Std` の別名は書ける。`Std` は暗黙の修飾子ではないので、ほかのモジュールと合流しない
- 標準ライブラリのモジュールも `Prelude` を暗黙に取り込む。そのため、`import Prelude` などの予約したモジュールの規則 (E1030) は標準ライブラリの import にもかける。入口のファイルを指す import の検査だけは、標準ライブラリの import がユーザーの根を探さないので、かけない
- 標準ライブラリのモジュールどうしは、`import` で明示して使う。`import Fs` と `import Std.Fs` のどちらで書いてもよい。標準ライブラリのモジュールの import は `std/` だけを探し、ユーザーの根は読まない。循環 (E1027) は標準ライブラリの中の依存もすべて見る
- 標準ライブラリのモジュールの `pub` でない item (`Prelude` の `show_rest` など) は、ユーザーからは定義がないものとして扱う。`Prelude.show_rest` は E1029 ではなく E1001 である
- extern のエフェクトの操作 (Prelude の `io_failed`) は、`pub` のエフェクトでも、宣言したモジュールの外から見えない。修飾しても修飾しなくても E1001 である。handler の節の先頭に書いても同じである
- ユーザーのモジュールが `File` を定義していて標準ライブラリの `File` と重なるときだけ、型の表示は標準ライブラリのものを `Std.Fs.File` と書く。ほかは `File` と短く書く。重なりは、読み込んだモジュールの型だけで決まる。そのため、利用者の `data File` は、`Fs` を読み込んだプログラムでだけ `Main.File` と書く。標準ライブラリの `pub` でない item は、利用者が書けないので重なりに数えず、ほかの定義元と同じ名前ならその item だけを修飾する

## 名前の解決

修飾しない名前は次の順に引く。

1. ローカルの束縛
2. 自分のモジュールのトップレベル。import した名前と Prelude の名前を、診断を出さずに隠す
3. import の並びで修飾なしにした名前
4. Prelude の `pub` の名前

- 3 で、同じ名前が別々の定義を指すときだけ、その名前を使った位置で E1028 にする。同じ定義を複数の import が出しても曖昧にしない。import を書いた時点では誤りにしない
- 修飾した名前 `Q.x` は、修飾子 `Q` のモジュールだけを引き、上の順は通らない。修飾子は次の順で決める
  1. `Prelude` は Prelude を引く
  2. そのモジュールの import が修飾子 `Q` を作るなら、その import のモジュールだけを引く。標準ライブラリには進まない
  3. そうでなければ、標準ライブラリのモジュール `Q` (正式な名前 `Std.Q`) を引く。この短い名前は、import なしで使えるが、ユーザーのモジュールでだけ使える。import していないユーザーの `Fs.em` は引かない
  4. どれもなければ E1031 にする。help は2つの場合に分ける。修飾子のモジュールを別名で import していれば、使える修飾子を示す (``the import of `Std.String` gives the qualifier `S`; write `S.length` ``)。import がなく、修飾子が `Std.String` のように標準ライブラリのモジュールの正式な名前なら、短い名前での書き方と import の書き方を示す (``write `String.length`, or `import Std.String as S` ``)

  合流した修飾子では、別々の定義が2つ以上見つかったときに E1028 にする。モジュールに名前がなければ E1001 か E1002 (メッセージに「in module `Report.Csv`」と書く)、ユーザーのモジュールの `pub` でない名前なら E1029 である
- 修飾した名前は、式、型、パターン、row のエフェクト、handler の節の先頭に書ける
- ユーザーのモジュールが標準ライブラリのモジュールと同じ名前でも、import が作る修飾子はユーザーのモジュールだけを引く。この優先は import にだけかかる
- handler の節の先頭の名前 (`| fn get () ->` の `get`、`| fn State.get () ->` の `State.get`) は、エフェクトの操作だけから解決する。ローカルの変数が同じ名前で操作を隠していても、節の解決には影響しない
- 種類の決まった位置 (パターンの先頭はコンストラクタだけ、節の先頭は操作だけ) では、修飾しない名前の各段でも、修飾子を通る場合でも、その種類の定義だけを見る。曖昧さも、同じ種類の定義どうしでだけ数える。各段では、名前の定義のうちその種類で最初のものを引く。ユーザーが `println` という関数を定義していても、自分のモジュールに `println` という操作がなければ、節の `| ctl println s k` は操作が見つからず、次に extern の関数だけを引いて `Prelude` の `println` に届くので E1009 になる ([エフェクトと handler](effects.md) の「組み込みの `IO`」)

```haskell
-- State.em
pub effect State where
  get : Unit -> Int

-- main.em
import State

counter : Unit -> <State.State, Panic> Int
counter () = State.get () + 1

run : Int -> <Panic> Int
run n =
  handle counter () with
    | fn State.get () -> n
    | return x -> x
```

## 名前空間

- 値の名前空間には、変数、関数、エフェクトの操作、クラスのメソッド、コンストラクタを置く。エフェクトの操作とメソッドは関数と同じく import する。変数・関数・操作・メソッドは小文字、コンストラクタは大文字で始まるので、字句の上で区別できる
- 型の名前空間には、型名、エフェクト名、クラス名を置く
- クラスを書く位置 (制約、instance の頭のクラス、`deriving`) の名前は型の名前空間で引き、型かエフェクトに当たれば E1041 にする。型を書く位置の名前がクラスに当たれば E1043 にする
- 型とコンストラクタは別の名前空間にあるので、同じ名前を持てる (`data Point = | Point Int Int`)
- 名前付きのレコードのフィールドの名前は、どの名前空間にも入れない。作る式とパターンのコンストラクタは、ほかのコンストラクタと同じく名前で引く (`M.Person { … }`)。射影と更新のフィールドは値の型から引き ([型と Kind](types.md) の「フィールドの解決」)、フィールドの見える範囲は検査しない。型の名前がそのモジュールで見えている必要もない。コンストラクタはいつも型と一緒に公開される (`pub data` がコンストラクタも公開する) ので、これで足りる
- 同じ名前空間でのトップレベルの定義の重複はエラーとする。クラスが型、エフェクト、ほかのクラスと名前が重なれば重複エラーになる。メソッドはエフェクトの操作と同じく、関数、操作、コンストラクタ、ほかのメソッドと名前が重なれば重複エラーになる。既定のメソッドの本体と instance のメソッドの本体は名前の表に入らず、重複にも数えない。エフェクトの操作はトップレベルの値なので、操作名がトップレベルの関数名や他の操作名 (別のエフェクトの操作を含む) と重なれば重複エラーになる。別々の `data` が同じ名前のコンストラクタを持つ場合も同じである。同じ名前の操作を使い分けたいときは、別のモジュールに置いて修飾付きの名前 (`Reader.get`) で区別する
- 重複は次の3つの規則で扱う
  1. 名前ごとに、その名前の定義をソースの順にすべて持つ。最初の定義がその名前の定義で、2つ目以降は E1003 になる。E1003 は最初の定義を「first defined here」で指す。重複した定義の本体も変換して検査するので、本体の中の誤りも報告する
  2. 重複した `data` のコンストラクタと、重複した `effect` の操作は使えない。それらを参照した位置は、診断を出さずに誤りの式として扱う。最初の定義の型と比べて「expected `T`, found `T`」のような誤りを連鎖させないためである
  3. 種類の決まった位置 (「名前の解決」のパターンと節の先頭) では、名前の定義のうち、その種類で最初のものを引く。操作の後に同じ名前の関数を定義すると、関数が E1003 になり、節は操作を引く。関数を先に定義した場合も、節は操作を引く
- `data` とエフェクトの型引数の重複も E1003 で、宣言の中で最初の定義を残す

## instance の一貫性

- (クラス, 型) ごとの instance は、プログラム全体でたかだか1つである。2つ目は E1035 にする ([宣言](declarations.md) の「宣言の検査」)。重なる instance、局所的な instance、第一級の instance は持たない。そのため、制約を解く先はいつも1つに決まる
- orphan 規則: instance は、クラスか頭の型コンストラクタを定義したモジュールにだけ書ける (E1034)。規則はモジュール単位である。パッケージ単位に広げるかは、パッケージの仕組みと一緒に決める ([ロードマップ](../future/roadmap.md) の「型システム」)
- instance は名前ではないので、import の書き方によらず、読み込んだプログラムのどこからでも見える。orphan 規則により、instance はクラスか型と同じモジュールにあるので、クラスと型を使えるモジュールからは、その instance のモジュールもいつも読み込まれている
- REPL では、セッションを1つのモジュールとみなす (下の「REPL のセッション」)

## REPL のセッション

REPL (`eml_cli::Repl`) では、セッションを1つのモジュールとみなす。orphan 規則と fixity を1つのモジュールとして当て、名前を入力の番号で解決する。HIR では、入力ごとに1つのモジュール (セッションのモジュール) を作り、名前解決、lowering、型検査がそれらを1つのセッションとして扱う。入力ごとに分けるのは、読み込んだモジュールが構文木と `ItemTree` を1つずつ持ち、モジュールの番号とファイルの番号が同じで、名前ごとに使える定義を1つ持つ (E1003 が頼る) という形を変えずに済むためである。

- 読み込みの段の入口は `load_session` である。モジュールの並びは、Prelude、セッションのモジュール (入力の順。最後が今の入力で、入口のモジュール) の後に、セッションのモジュールから import と修飾子をたどって見つけた順のモジュールが続く (上の「標準ライブラリ」)。修飾子は、すべての入力 (今の入力と `:type` の問い合わせを含む) から拾う。そのため、ある入力で初めて使った標準ライブラリのモジュールは、その入力から読み込む。セッションのモジュールは `ModuleOrigin::Session(N)` を持ち、名前は利用者が書けない `<input N>` で、表示のパスも同じである。ただし `:load` のファイルの入力 (入力 1) は、ファイルの文法で読み、表示のパスはファイルのパスである ([REPL の端末](repl.md) の「ファイルの読み込み」)。そのセッションの import の根は、`eml run` と同じくファイルのディレクトリである。`main` の検査は当てない。入口のファイルは `:load` のファイルで、ファイルの依存先と後の入力がそれを import すると、`eml run` と同じく E1030 にする。ファイルを受け付けなかったセッションでも同じである。診断の文言は `eml run` のものを使う。ほかのモジュールはセッションのモジュールを import できない
- 受け付けた入力は、定義と `let` の入力だけを持つ。式の入力は、後の入力から参照されないので持たない。モジュールとファイルの番号は入力ごとに振り直す。前の入力は前の入力しか見ないので、どの入力のときも同じように解決される
- 重複の検査 (E1003) は、モジュールの中、つまり入力の中で行う。後の入力の同じ名前は、エラーにせず新しい版として扱う
- 入力 N の修飾しない名前は、次の順に引く
  1. ローカルの束縛
  2. 自分のモジュールのトップレベル。ファイルと同じく、種類が合わない定義を飛ばして探し続ける。`let` の束縛は自分の入力の中では見えないので、`let x = x + 1` の右辺の `x` は前の版を指す
  3. N より前のセッションのモジュールのトップレベルを、新しい入力から順に。`pub` は見ない。その名前空間でその名前を定義している最も新しいモジュールで止まり、種類が合わなければ上の「名前の解決」と同じ誤りにする。種類で絞って古い版まで探し続けると、操作の `ask` を関数で定義し直した後の handler の節が古い操作を見つけるように、定義し直した名前の古い版が戻ってくるためである
  4. import の並びで修飾なしにした名前を、入力 N、N − 1、… の順に、入力ごとに引く。E1028 は、1つの入力の import の中で2つ以上の別の定義に当たったときだけにする。後の入力の import が前の入力の import を隠すので、別々の入力で同じ名前を import しても、ずっと E1028 になることはない
  5. Prelude の `pub` の名前
- 2 と 3 は、ファイルのトップレベルと同じく、入力の順によらず import した名前と Prelude の名前を隠す。後の入力の item は見えない。同じ入力の中では相互再帰ができる
- 修飾子と別名など、import の範囲を読むほかの処理も、N 以前の入力の import を新しい入力から順に見る。E1028 の2つ目以降の位置は前の入力の import を指しうるので、ファイルと位置の組で持つ。1つの入力の中で import を宣言より前に書く決まりは、ファイルと同じである
- セッションの中では `pub` を見ず、E1032 も当てない。セッションのモジュールはどこからも import されないためである
- orphan 規則 (E1034) では、セッションのどのモジュールで定義したクラスや型も、セッションの instance にとって同じモジュールに数える。同じ (クラス, 型) の instance は、入力が違っても定義し直せない (E1035)。定義し直せると、総称な関数の instance を後の入力で初めて作ったときに新しい instance を使い、すでに実行のコードにある同じ名前の関数と食い違うためである。間違えた instance を直すには、型かクラスを定義し直し、その新しい版に対して instance を書く
- fixity の宣言は、その演算子を定義した入力の中に書く (E1022。文言は「この入力」と言う)。fixity は定義に付くので、後の入力で前の入力の演算子に fixity を足すと、前の入力の式の結合が変わり、同じ名前の関数が違うコードになるためである。前の入力の fixity は、`pub` でなくても後の入力に効く ([宣言](declarations.md) の「fixity」)
- import したモジュールは、最初に受け付けた入力が読んだテキストと、解決した先 (ユーザーのファイルか、見つからずに落ちた標準ライブラリか) を、間接の依存先も含めて使い続ける (`ImportCache`)。ディスクのファイルが変わったり新しくできたりしても、セッションの中のモジュールは変わらない。読み直すと、同じ名前の関数が違うコードになるためである。受け付けなかった入力が読んだものは残さない
- `:load` は新しいセッションを作るので、キャッシュも空から始まる。`:reload` は、ファイルと import したモジュールを読み直す
- 利用者向けの表示 (`DisplayNames`) では、セッションを1つの定義元として数え、定義し直された item の古い版に、定義した入力の番号を付けて `Shape#1` と書く。最新の版には付けない。利用者が今その名前で書けるものを、印なしで見せるためである。版は (名前空間, 名前) ごとに数え、`let` の束縛と関数は同じ値の名前空間にある。セッションの item がほかのモジュールの item と同じ名前のときは、ほかのモジュールの item を修飾し、セッションの item は修飾しない (`Prelude.Bool` と `Bool`)
- 後の入力の instance によって、前の入力の関数の一様な位置が変わる入力は受け付けない (E2018。[型と Kind](types.md) の「REPL の入力」)。`Repl` は受け付けた関数と instance の一様な位置を、モジュールの名前とモジュールの中の item の番号で覚えて比べる。前の入力のテキストもキャッシュした import も変わらないので、この組は入力をまたいで同じ item を指す。標準ライブラリのモジュールは使う入力でだけ読み込むので、式の入力だけが使ったモジュールは次の入力にない。今の入力が読み込まなかったモジュールの item は比べず、覚えた位置をそのまま残す
- 誤りがどのファイルにあっても、入力を受け付けない。警告 (E4004、E4005) は、その入力で初めて読んだファイル (パスで見分ける) のものだけを返す。セッション全体を入力ごとに検査し直すので、前の入力の警告が毎回出るのを防ぐためである
- 前端の検査に誤りのない入力は、lowering の後、`Machine::load` の前に止める語を読み、割り込みが立っていれば入力の種類によらず受け付けない (`Outcome::Interrupted`)。セッションは変わらない ([REPL の端末](repl.md) の「割り込み」)
- `:type` の問い合わせは、受け付けた入力の後に、次の入力の番号を持つセッションのモジュールとして読む。入力の関数は `InputKind::Query` で、検査だけをし、lowering も実行もせず、受け付けない ([型と Kind](types.md) の「REPL の入力」)

## 公開の範囲

- `pub` を付けた item の型に、同じモジュールの `pub` でない型かエフェクトが現れたら E1032 にする。対象は、`pub` のシグネチャ、`pub data` のコンストラクタのフィールド、`pub effect` の操作のシグネチャ、`pub class` の上位クラスとメソッドのシグネチャである。row の中のエフェクトも含む。`pub` のシグネチャの制約に書いた `pub` でないクラスも E1032 にする
- 理由は2つある。1つは、コンストラクタを隠した抽象型を、後で `pub data` の形で意図して入れるためである ([ロードマップ](../future/roadmap.md) の「言語機能と構文」)。非公開の型を返す公開の関数を許すと、その前に裏口の抽象型ができてしまう。もう1つは、非公開のエフェクトを row に持つ公開の関数を、import する側が handle できないためである。その関数を呼ぶと、名前も書けないエフェクトが残る

名前解決の診断 (重複定義、未定義の名前など) の番号の範囲は [診断](diagnostics.md) にある。
