# モジュールと名前解決

位置づけ: 規範。

モジュールの単位、import の書き方、名前の解決の順序、名前空間を定める。モジュールと import は S2 で実装する。マイルストーン1 は単一ファイルである。

## モジュール

- 1ファイル = 1モジュールとする。モジュール名はパスから決まる (`report/Csv.em` は `Report.Csv`)。`module` ヘッダは書かない
- `Prelude` (`Option`、`Result`、`List`、`Bool`、`println` など) を暗黙に取り込む
- エントリポイントは `main : Unit -> <IO> Unit` とする。終了コードは標準ライブラリの `exit` で扱う ([標準ライブラリへの申し送り](../future/stdlib.md))
- 公開するものには `pub` を付ける ([宣言](declarations.md) の「`pub`」)

## import

| 書き方 | 効果 |
|---|---|
| `import Report.Csv` | `Csv.parse` のように、最後のセグメントで修飾して使える |
| `import Report.Csv as C` | `C.parse` |
| `import Report.Csv (parse, Row)` | 修飾付きに加えて、列挙した名前を修飾なしで使える |
| `import Report.Format (Style(..))` | 型とそのコンストラクタを、修飾なしで使える |

- import は既定で修飾付きである
- import の並びに書いた大文字の名前は、型かエフェクトを指す。コンストラクタは `T(..)` の形でだけ修飾なしにできる。型とコンストラクタが同じ名前を持てるため、`import M (Point)` は型の `Point` だけを取り込む
- **標準ライブラリのモジュール** (`Fs`、`Json`、`String`、`Proc` など) は、import しなくても `Fs.read_text` のように修飾付きで使える

## 名前の解決

- 名前の解決の順序は次のとおり。ローカルの束縛 → 自分のモジュールのトップレベル → import で修飾なしにした名前 → `Prelude` の `pub` の名前 → (修飾付きの場合) import したモジュール → 標準ライブラリのモジュール
- 自分のモジュールの定義は、`Prelude` の同じ名前を隠す
- ユーザーのモジュールが標準ライブラリのモジュールと同じ名前なら、ユーザーのモジュールを優先する
- 修飾なしの名前の衝突 (2つの import が同じ名前を出す) は、使った箇所でエラーとする (E1xxx)
- handler の節の先頭の名前 (`| get () k ->` の `get`) は、エフェクトの操作だけから解決する。ローカルの変数が同じ名前で操作を隠していても、節の解決には影響しない
- パターンの先頭の名前はコンストラクタだけから、節の先頭の名前は操作だけから引く。どちらも上の順にたどり、名前の定義のうちその種類で最初のものを引く。ユーザーが `println` という関数を定義していても、自分のモジュールに `println` という操作がなければ、節の `| println s k` は `Prelude` の操作を引いて E1009 になる

## 名前空間

- 値の名前空間には、変数、関数、エフェクトの操作、コンストラクタを置く。エフェクトの操作は関数と同じく import する。変数・関数・操作は小文字、コンストラクタは大文字で始まるので、字句の上で区別できる
- 型の名前空間には、型名とエフェクト名を置く
- 型とコンストラクタは別の名前空間にあるので、同じ名前を持てる (`data Point = | Point Int Int`)
- 同じ名前空間でのトップレベルの定義の重複はエラーとする。エフェクトの操作はトップレベルの値なので、操作名がトップレベルの関数名や他の操作名 (別のエフェクトの操作を含む) と重なれば重複エラーになる。別々の `data` が同じ名前のコンストラクタを持つ場合も同じである。同じ名前の操作を使い分けたいときは、別のモジュールに置いて修飾付きの名前 (`Reader.get`) で区別する
- 重複は次の3つの規則で扱う
  1. 名前ごとに、その名前の定義をソースの順にすべて持つ。最初の定義がその名前の定義で、2つ目以降は E1003 になる。E1003 は最初の定義を「first defined here」で指す。重複した定義の本体も変換して検査するので、本体の中の誤りも報告する
  2. 重複した `data` のコンストラクタと、重複した `effect` の操作は使えない。それらを参照した位置は、診断を出さずに誤りの式として扱う。最初の定義の型と比べて「expected `T`, found `T`」のような誤りを連鎖させないためである
  3. 種類の決まった位置 (「名前の解決」のパターンと節の先頭) では、名前の定義のうち、その種類で最初のものを引く。操作の後に同じ名前の関数を定義すると、関数が E1003 になり、節は操作を引く。関数を先に定義した場合も、節は操作を引く
- `data` とエフェクトの型引数の重複も E1003 で、宣言の中で最初の定義を残す

名前解決の診断 (重複定義、未定義の名前など) の番号の範囲は [診断](diagnostics.md) にある。
