# Core IR とインタプリタ

位置づけ: 規範。

型付き HIR から変換する Core IR と、それを実行する CEK 風のインタプリタを定める。ヒープと参照カウントは [ランタイム](runtime.md) で扱う。

## 実行系の方針

- 実行系は、型付き Core IR と CEK 風のインタプリタで構成する。Core IR は、前向きの辺だけを持つ基本ブロックの列で、すべての中間値に名前を付け、RC とエフェクトを明示する。ネイティブ化でも同じ IR から変換する。バックエンドは未定である ([ロードマップ](../future/roadmap.md))
- ブロックの列にしたのは、将来インタプリタをバイトコード VM に組み替えることと、ネイティブ化 (Cranelift か LLVM) の土台にすることを見込んだためである。ブロックの列は、バイトコードへは1回の線形なループで写り、Cranelift のブロック引数と LLVM の phi へは 1:1 で写る

## Core IR

型付き HIR から変換する IR で、すべての中間値に名前を付ける。関数は基本ブロックの列で、ブロックは引数、文の列、終端を持つ。

| 種類 | 命令 |
|---|---|
| 文 | `let x = 右辺`、`unpack v L #t(f1, .., fn)`、`dup x`、`decref x`、`release x L #t(p1, .., pn)` |
| 右辺 | 呼び出し (`call`、`apply`、`clause`、`perform`、`resume`、`handle`)、`closure`、`con`、`const`、`extern`、`prim`、`drop`、`box`、`unbox` |
| 終端 | `return a`、`tail <呼び出し>`、`jump bN(a1, .., an)`、`switch a L { #0 -> bN, #1(y1, .., yn) -> bN, _ -> bN }`、`switch a { 1 -> bN, _ -> bN }` |
| RC (RC の対象の変数のみ) | `dup x`、`decref x`、`release x L #t(p1, .., pn)` |
| 線形値 | `drop x` (宣言された破棄処理を呼ぶ) |
| エフェクト (translate の出力だけ) | `perform op args`、`handle E(init, body) { 節 } return r`、`resume k(v, s)` (内部の命令)、`drop k` |
| evidence passing の出力 | `prim` (基本操作)、`clause` (節の呼び出し) |

`perform`、`handle`、`resume`、呼び出しの `mask` は translate だけが出し、evidence passing (EP) が基本操作と節の呼び出しに置き換える (下の「evidence passing」)。EP より後のパスとインタプリタは、エフェクトの命令を受け取らない。

### ブロックの列

- 関数は、名前、内部の関数かどうかの印 (下の「位置の規則」)、yield しうるかの印 (下の「`yields` の印」)、入口の関数の印 (下の「入口の関数の印」)、変数の表、`ret`、ブロックの列を持つ。変数の表は、変数の番号ごとに名前と Repr (下の「値の表現」) を持つ
- `blocks[0]` が入口で、その引数が関数の引数である。ほかのブロックは番号 `bN` で指す
- `ret` は、直接の呼び出しの結果の Repr である
- 文は、変数を定義する `let` と `unpack` と、RC の命令 `dup`、`decref`、`release` である。ブロックの最後に終端が1つある
- 値 (アトム) は、変数、`Int` の定数、`()`、引数のないコンストラクタのタグ `#N`、関数の値 `&f` のどれかである
- `con` は引数を1つ以上とる。フィールドのないコンストラクタの値は、`#N` (`Atom::Tag`) の1つの書き方にそろえる
- `con L #t(a1, .., an)`、`unpack`、`release` の `L #t` は、配置 L のタグ t のコンストラクタ (`Ctor`) を指す (下の「データの配置」)。タグの case を持つ `switch` は、scrutinee の後に配置 L を1つ持ち、case のタグ `#N` はその配置のタグである
- `jump bN(a1, .., an)` は並列な代入である。実引数をすべて読んでから、行き先の引数に書き、行き先の先頭へ進む
- `switch` は scrutinee、case の並び、省略できる `default` を持つ。case と `default` を合わせて、行き先を1つ以上持つ。case は、タグ (`#N`)、`Int`、`String` (文字列定数の番号) のどれかで比べ、1つの `switch` の case は同じ種類にする。リテラルの `switch` はつねに `default` を持つ。`#N(x, ..)` の case だけがフィールドを束縛し、リテラルの case はフィールドを持たない。同じ case を2回書かない。合う case がなければ `default` に進む
- `unpack v L #t(f1, .., fn)` は、コンストラクタが1つで、そのコンストラクタがフィールドを持つ配置の値を分解する。行き先が「ブロックの残り」である1つの case の `switch` と同じ意味である
- `switch` と `unpack` は、タグとフィールドを読むだけである。参照の数を変えず、scrutinee を消費しない。scrutinee は、どの行き先でも、`unpack` の後でも、所有されたままである。フィールドのある case、フィールドのない `#N` の case、`default`、文字列の `switch` のどれも同じである。`int` と `enum` のリテラルの `switch` は、何も所有していない
- `Case` のフィールドと `unpack` のフィールドは、同じ「フィールドの束縛」の規則に従う。Repr が `obj` か `tobj` のフィールドは、束縛したときには借りた値である。自分の参照を持たず、上の持ち主が参照を持っている間だけ使える (下の「verifier」)。ほかの Repr のフィールドは、ただの値である
- `release x L #t(p1, .., pn)` は、分解した値 x を手放す。`unpack` と同じく、フィールドの位置ごとに、参照を引き継ぐ変数か `_` を書く
  - x は、タグが t でフィールドが n 個のデータでなければならない。違えば内部の誤りである
  - x が一意 (参照の数が1で、不死でない) なら、x の箱を解放し、`_` の位置のフィールドの値を `decref` する。名前を書いた変数は、箱が持っていた参照をそのまま引き継ぐ
  - そうでなければ、名前を書いた位置のフィールドを `dup` してから、x を `decref` する
  - 所有の上では、x の参照が1つ減り、名前を書いた変数の参照がそれぞれ1つ増える
  - 名前は1つ以上書く。1つも残さないときは `decref x` を使う
  - Perceus だけが出す RC の命令である。`Stmt::defs` は空で、`dup` や `decref` と同じく値の使いとは数えない
- `let b = box a` は、箱を要するスカラー (下の「値の表現」) の値 a を `tobj` の値にする。`let v = unbox w` は、`tobj` の値 w から箱を要するスカラーを取り出す。スカラーの種類は、`box` ではオペランドの Repr から、`unbox` では束縛の Repr から決まる。オペランドと束縛の規則は「値の表現」にある
  - `box` はオペランドを消費し、所有した `tobj` を定義する。オペランドはスカラーか定数なので、RC の対象ではない
  - `unbox` はオペランドを読むだけで、所有権を受け取らない。借りたフィールドも読める
- 値 (アトム) の使い方は「消費」と「読む」に分かれる。`switch` の scrutinee、`unpack` の値、`unbox` のオペランドだけが「読む」で、参照を受け取らない。ほかの使い方 (呼び出し、`apply`、`clause`、呼ばれる側、extern、`prim`、`con`、`closure`、`perform`、`resume`、`handle` の引数、`drop`、`box`、`return`、`tail`、`jump` の実引数) はすべて「消費」で、参照を1つ受け取る
- `tail <呼び出し>` (`TailCall`) は、縮約が作る末尾呼び出しの要求である。呼び出し元のフレームを積まずに呼ぶ。呼び出しの結果は、呼び出し元の `ret` と互換である (下の「縮約」)。所有の都合で `let r = <呼び出し>` と `return r` に戻す降格は、借用パラメータを入れるときに、末尾の位置の呼び出しの輪の上にない末尾呼び出しにだけ足す (下の「変換の規則」の末尾呼び出しの保証、[ロードマップ](../future/roadmap.md) の「処理系」)

### 構造の規則

ブロックの列は次の規則を満たす。verifier が検査する (下の「パス」)。

- R1: 入口のブロックへ向かう辺はない
- R2: 辺はすべて、番号の大きいブロックへ向かう
- R3: `switch` の行き先 (case と `default`) は引数を持たず、入る辺はその `switch` の辺1本だけである。合流するブロック (`jump` で入るブロック) は、`switch` の行き先にならない
- R4: 入口と `switch` の行き先を除くブロックには、`jump` が1本以上入る。`jump` の実引数の数は、行き先の引数の数と同じである
- R5: 変数は、関数の中で多くとも1回定義される。パスが消した変数のように、変数の表には定義のない番号が残ってよい。定義する位置は、ブロックの引数、`let`、`unpack` のフィールド、case のフィールドである
- R6: 変数が見えるのは、その定義の位置が使う位置を支配するときだけである (同じブロックなら前の文)。所有の検査の段では、合流するブロックに入るすべての `jump` で所有の多重集合が一致しなければならず、その集合が入口の所有になる
- R7: 所有の検査の段では、`let x = <呼び出し> save S` の後に見える変数は S と x だけである。S は呼び出しの前に見えていなければならず、S のうち RC の対象の部分は、所有の多重集合と一致する。呼び出しの後に定義した変数は、次の呼び出しまで見える。合流するブロックでは、入るすべての辺で見えている変数だけが見える
- R8: `extern` 命令の引数と、その結果を束縛する変数は、`eml_extern` の表の行の `params` と `ret` と Repr が同じである。定数の引数は、正確な位置の当てはめで行の Repr に収まる。`unpack` の値は Repr が `obj` の変数である。`jump` の実引数と行き先の引数、`return` の値と `ret`、直接の呼び出しと `apply`、`clause`、`prim` の引数と結果、`closure` の引数、`tail` の結果は、互換の関係で比べ、定数は互換の位置の当てはめで比べる (下の「値の表現」と「位置の規則」)。`never` の操作の `clause` の結果と、その束縛の使いは比べない。関数の値として使う関数は一様である。`box` と `unbox` は「値の表現」の規則に従う
- R9: 配置を指す命令は、その配置と合う (下の「データの配置」)
  - 命令が指す配置は表にあり、タグはその配置のコンストラクタの数より小さい
  - `switch` が配置を持つのは、タグの case を持つときだけである
  - `con` の引数の数と、case、`unpack`、`release` のフィールドの数は、コンストラクタのフィールドの数と同じである
  - タグの `switch` の scrutinee は変数で、その Repr は配置の Repr と同じである。`default` のないタグの `switch` は、すべてのコンストラクタを case に持つ
  - リテラルの `switch` の scrutinee は、`Int` のリテラルなら `int` に、`String` のリテラルなら `obj` に収まる
  - `unpack` の配置は、コンストラクタが1つで、Repr が `obj` である
  - `con` で束縛する変数の Repr は、配置の Repr と同じである
  - 宣言した Repr が `tobj` でないフィールドでは、`con` の引数と、case と `unpack` のフィールドの Repr が、その Repr と同じである。定数の引数は、正確な位置の当てはめでその Repr に収まる
  - 宣言した Repr が `tobj` のフィールドでは、`con` の引数と、case と `unpack` のフィールドの Repr が `tobj` と互換である。定数の引数は、互換の位置の当てはめで `tobj` に収まる
  - R9 は、それぞれの命令を、その命令が指す配置と比べるだけである。値がどの配置で作られたかは追わない。それを保証するのは translate の型である。そのため、配置の違う値を読む IR も R9 を通りうる。タグかフィールドの数が違えば、インタプリタが内部の誤りとして止める。形が同じなら気付かない (下の「インタプリタ (CEK 機械)」)

R1 と R2 から、ブロックの番号の順は辺の向きに沿った順 (トポロジカル順) になり、ループはない。R3 から、`switch` の行き先の入口の状態は、その `switch` のブロックだけで決まる。

### 値の表現

- 変数は、型から決まる値の表現 (Repr) を持つ。Kind (`Unr` / `Lin`) は残さない

  | 型 | Repr |
  |---|---|
  | `Int` | `int` |
  | `Unit` (要素のないタプル)、`Error` | `unit` |
  | 引数のないコンストラクタだけの data | `enum` |
  | `String`、`File`、要素のあるタプル、全コンストラクタがフィールドを持つ data | `obj` |
  | 引数のないコンストラクタとフィールドを持つコンストラクタが混ざる data | `tobj` |
  | 関数 (関数の値 `&f` は即値)、型変数 | `tobj` |

- `obj` はつねにヒープの物体を指す。`tobj` は、即値 (タグか関数の値) かヒープの物体を指す。RC の対象は `obj` と `tobj` の変数で、Perceus はこの変数にだけ RC の命令を付ける
- 多相な位置 (総称的なフィールド、`apply` の結果) の束縛も、具体化した型から Repr を決める。値を受ける位置の Repr は下の「位置の規則」が決め、変数の Repr と互換でなければ、box の挿入 (下の「box の挿入」) が変換を入れる。`Float` の Repr は、`Float` の型とリテラルと一緒に入れる ([ロードマップ](../future/roadmap.md) の「`Float`、`Char`、`Num`」)
- 局所の変数はスカラーのまま持ち、呼ぶ側か呼ばれる側が具体的な型を知らない位置 (一様な位置) だけを参照にする。一様な位置の Repr は `tobj` である。Lean の IR と同じ方式である。`int`、`enum`、`unit` の変数は、VM ではタグのないスロットに、ネイティブではレジスタに置ける
- `tobj` の位置との間で `box` と `unbox` を要するスカラーの Repr を、箱を要するスカラーと呼ぶ。今は `int` と `enum` で、後の `Float` の Repr もここに入る。規則と verifier の文言は、この集合の1つの定義 (`Repr::BOXED_SCALARS`) から作る。`Float` を足すときに、規則を1つずつ探して直さずに済むためである。命令なしで `tobj` と行き来するスカラーは `unit` だけである。`obj` と `tobj` の間は、命令なしで渡せる
- 2つの Repr a と b は、次のどれかのとき互換 (`Repr::compatible`) である
  - a と b が同じ
  - a と b がどちらも参照 (`obj` か `tobj`)
  - 片方が `unit` で、もう片方が `tobj`
- 互換の関係は推移的でない (`unit` と `obj` は互換でない)。どの検査も実際の2つの位置を比べるだけなので、推移律は使わない。2つの位置を1つにつなぐ変形は、つないだ後の2つの位置が互換なときだけ行う。縮約の末尾呼び出しの規則がこれに当たる (下の「縮約」)
- 正確な位置では Repr が同じでなければならない。`extern` の引数と結果、宣言した Repr が `tobj` でないフィールド、タグの `switch` の scrutinee と配置、`unpack` の値、`con` の束縛と配置、`box` と `unbox` のオペランドと束縛である。正確な位置では、`unit` と `tobj` も行き来しない。Repr が表で決まり、translate の出力も表に合わせて作るためである
- 互換の位置では、互換であればよい。`jump` の実引数と行き先の引数、`return` の値と `ret`、直接の呼び出しの引数と結果、`closure` の引数、`apply` のオペランドと結果 (相手は `tobj`)、`clause` の引数と結果 (相手は操作の表の Repr)、`prim` の引数と結果 (相手は基本操作の表の Repr)、宣言した Repr が `tobj` のフィールド、`tail` の結果と呼び出し元の `ret`、関数の値として使う関数の引数と `ret` (相手は `tobj`) である
  - `jump` と `return` を正確にしても、バックエンドが得るものはない。互換な2つの Repr は、機械の形が同じだからである。正確にすると、後のインライン化と contification が作る形を書けない。たとえば `tobj` を返す `id` を `let t: obj = call id(x)` の所でインライン化すると、`id` の `return x` は、`tobj` の x を `obj` の引数へ渡す `jump` になる
- 定数の当てはめも、位置の種類に従う
  - 正確な位置では、`Int` の定数は `int`、`()` は `unit`、タグ `#N` は `enum` か `tobj`、関数の値 `&f` は `tobj` に収まる
  - 互換の位置では、これに加えて `()` が `tobj` にも収まる。`Int` の定数は `tobj` に収まらないので、`let b = box 5` を置いて b を渡す
  - 範囲の段と所有の段の verifier では、`&f` は f が一様なときだけ収まる (下の「位置の規則」)。変換の段では一様かを見ない。translate は、一様でない関数の `&f` を `jump` の実引数に出しうるからである (`let h = if c then double else inc` の `jump b3(&double)`)
  - `#N` が `tobj` に収まるのに `enum` の変数が収まらないのは、定数ならコンパイルの時点で `tobj` の形に書けるからである。`Int` の定数を同じ扱いにしないのは、`box` が確保しうる (ネイティブの 64 ビットの `Int`、後の `Float`) からである
- `box a` の a は、箱を要するスカラーの変数か、`Int` の定数である。束縛の Repr は `tobj` である。`unit` の変数、`()`、`#N`、`&f`、参照の変数は拒む。どれも命令なしで `tobj` に収まるので、1つの値の書き方を1つに保つ
- `unbox a` の a は、`tobj` の変数である。束縛の Repr は箱を要するスカラーである。`obj` の変数は拒む。`obj` はつねにヒープの物体を指し、スカラーを入れた値にならない。定数と、`unit` の束縛も拒む
- `int` と `enum` を明示する理由
  - `box` は確保しうる (ネイティブの 64 ビットの `Int`、後の `Float`)。所有している `tobj` を `unbox` した後には `decref` が要る。どちらも Perceus と所有の検査に見えなければならない
  - `Int` を命令なしで通すと、「小さい `Int` は `tobj` の即値」を今決めることになる。`tobj` の `Int` の表し方は S9 で決める ([ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)
  - `enum` を明示するのは、タグを `tobj` の中でどう表すかを、バックエンドに任せるためである
- `unit` を命令なしにするのは、値が `()` の1つだけで、変換がデータも確保も RC も持たないためである
- バックエンドは次を守る
  - `unit` の値の機械の形は、`tobj` の即値 `()` と同じにする。`unit` を返す関数の戻り値も、この形で返す。呼び出しの結果、`jump`、`return`、`tail` が、`unit` と `tobj` の間を命令なしでつなぐためである
  - `obj` の値は、そのまま `tobj` の値でもある
  - `tobj` の位置に置いた定数 `#N` は、値が N の `enum` を `box` した値と同じである。`unbox` が、どちらの値も同じに読むためである
- 後のバイトコード VM とネイティブ化は、変数の Repr と `box` と `unbox` から、スロットかレジスタの種類、確保、RC の操作をすべて IR から読める
- `Lin` の値は2回以上消費されない。`Lin` の値はちょうど1回使われる ([線形性](linearity.md)) ので、消費のための `dup` は要らない。ただし、後の行のパターンが分解した値そのものかその祖先を束縛するとき (`| other -> ..`、`| W h _ -> ..`) は、分解した `Lin` の値が分解の後も生きていることがある。このとき Perceus は、ほかの値と同じフィールドの規則で、生きているフィールドを `Lin` のものも含めて `dup` する。内側の `release` や `decref` も共有の側を通ることがある。`Lin` のフィールドを消費する腕は、祖先も使うと同じ値を2回使うことになるので、祖先を使わない。そのため、その腕の入口では祖先が死んでいる。入口の順 (フィールドの `dup`、死んだ所有の `decref`、`release`) で祖先を先に手放すので、`Lin` のフィールドは消費するときには参照が1つに戻っている。`Lin` のフィールドは必ず使われるので、`release` は生きているすべての `Lin` のフィールドを名前で書く。IR は Kind を持たないので、これは決まりとして書き、verifier では確かめない

### データの配置

- `Program.layouts` は配置の表で、`LayoutId` で引く。`con`、`unpack`、`release` は配置とタグの組 (`Ctor`) を持つ。タグは配置の中のコンストラクタの添字で、宣言の順である。タグの case を持つ `switch` は配置を1つ持つ。`if` と条件が出す `Bool` の `switch` も含む。リテラルの `switch` と、`default` だけの `switch` は持たない
- タグの定数 `#N` (`Atom::Tag`) と case のタグ (`CasePattern::Tag`) は配置を持たない。配置は `switch` に1つだけ置く
- 配置は、名前と、タグの順に並んだコンストラクタを持つ。コンストラクタは、名前と、宣言したフィールドの型の Repr の列を持つ。Repr はコンストラクタの型スキームのフィールドの型から決める。型変数のフィールドは `tobj` で、具体化した型は見ない。`data Pair a = Pair a Int` は `Pair(tobj, int)` になり、`Option Int` と `Option a` は同じ配置 `Option { None, Some(tobj) }` を使う
- 名前は、テキストの形と、後の値の表示とデバッグ情報のためにある。名前では何も解決しない
- 配置の Repr は表に持たない。上の「値の表現」の data の規則で、コンストラクタのフィールドの数から決まる。フィールドのないコンストラクタだけなら `enum`、どれもフィールドを持てば `obj`、混ざれば `tobj` である。translate の型の Repr と配置の Repr は、同じ関数で決める
- 配置を持つのは、translate が出す IR が指すデータ型 (Prelude の `Bool` を含む) と、組の大きさごとの配置である。extern の型と `Unit` は持たない。名前は関数と同じく、入口以外のモジュールの型を修飾する (`Prelude.Bool`)。組の配置は宣言がないので大きさだけで決まり、名前は `(,)`、`(,,)` のように、大きさより1少ないカンマを括弧で囲む。組のコンストラクタは1つで、名前は配置と同じで、フィールドはどれも `tobj` である
- translate は、命令を出すそれぞれの所で、コンストラクタか型から配置を決める。値の型からは決めない。配置は最初に使った順に表に入れる。後のパスは表を変えないので、使われなくなった配置が残ることがある。番号をたどり方によらない正規の順にするのは、定義ごとに Core IR を保存する S11 である ([ロードマップ](../future/roadmap.md) の「S11 REPL」)
- extern が作るデータは、比べる extern の `Bool`、`compare` の extern の `Ordering`、`Fs.read_all` の組である。`Bool` は機械の定数 `FALSE` と `TRUE` で、`Ordering` は `LT`、`EQ`、`GT` で作る。そのタグが `Prelude.Bool` と `Prelude.Ordering` の宣言の順と合うことを、テストが確かめる。組の配置は大きさだけで決まる。そのため、extern の行は配置を持たない。std の extern が名前的なデータ (`List`、`Option`、`Result`) を作るようになったら、行がその型の正規の名前を持ち、translate がその配置を表に入れる ([ロードマップ](../future/roadmap.md) の「S12 スクリプトの MVP」)
- 名前付きのレコードは、ほかの `data` と同じく、型ごとの配置に入る。名前付きのフィールドを持つコンストラクタも、フィールドの名前は持たず、宣言の順のフィールドの Repr の列を持つ
- 宣言した Repr が `tobj` のフィールドは、互換の位置である (上の「値の表現」)。`obj` の値は変換なしで `tobj` のフィールドに置け、`tobj` のフィールドは `obj` の変数に束縛できる。`box` と `unbox` が要るのは、スカラーと参照の間だけである。ただし `unit` は、命令なしで `tobj` のフィールドと行き来する
- verifier の R9 は、命令をその命令が指す配置と比べるだけで、値を作った配置を追わない。それを保証するのは translate の型である (上の「構造の規則」の R9)
- 後のバイトコード VM はジャンプ表の大きさとポインタのフィールドを、ネイティブ化は物体の記述子を、reuse は同じ配置かどうかを、この表から知る ([ランタイム](runtime.md) の「オブジェクトのヘッダ」)

### 位置の規則

位置ごとに、そこへ渡す値に期待する Repr は次のとおりである。正確に合わせるか互換でよいかは、上の「値の表現」の互換の関係で決まる。

| 位置 | 期待する Repr |
|---|---|
| 局所の変数、ブロックの引数 | 具体化した型の Repr |
| データのフィールド (`con` の引数、case と `unpack` の束縛) | 配置の表の、宣言したフィールドの Repr。型変数と組のフィールドは `tobj` |
| 直接の呼び出し `call g(..)` の引数と結果 | `g` の引数の Repr と `ret` |
| `extern` の引数と結果 | 表の行の `params` と `ret` |
| `apply` のオペランドと結果 | `tobj` |
| `clause` の引数と結果 | 先頭の evidence は `obj`、残りの引数と結果は操作の表の `params` と `ret` (下の「エフェクトの位置」)。`never` の操作の `clause` の結果は値を持たない (下の「`never` の操作」) |
| `prim` の引数と結果 | 基本操作の表の Repr (下の「基本操作」) |
| `closure g(..)` の引数 (捕獲と部分適用) | `g` の引数の Repr。`g` は下の規則で一様なので、一様になる |
| 関数の値として使う関数 (`&g`、`closure g`) の引数と `ret` | `tobj` と互換 (下の「一様な関数」) |
| `return a` | 関数の `ret` |
| `jump bN(..)` | 行き先の引数の Repr |

- translate が決める関数のシグネチャは、具体化した型の Repr である。トップレベルの関数は instance の代入をかけた宣言の型から (下の「変換の規則」)、`op$`、`con$`、`$externN` はスキームから、ラムダ、節、handle の本体は使う所の型から決める。`cont$` と `cont$state` はすべて `tobj` である。EP が作る関数のシグネチャは、下の「evidence passing」の各項目で決まる
- translate の出力の `perform`、`resume`、`handle` は、box の挿入より前に EP が消すので、この表に位置を持たない
- 一様でない関数を一様にし、`ret` を上げ (下の「T3」)、位置に合わない値を変換するのは、box の挿入 (下の「box の挿入」) である

#### 一様な関数

- 関数の値として参照される関数は一様でなければならない。関数の値として参照されるとは、IR のどこかに `&f` があるか、`closure f(..)` の対象であることである。一様とは、引数と `ret` の Repr がすべて `tobj` と互換 (`obj`、`tobj`、`unit`) であることである。`apply` は、関数ごとの Repr を知らずにその関数を呼ぶためである
- 関数 (`CoreFn`) は、内部の関数かどうかの印 (`internal`) を持つ。内部の関数は、translate が定義の中から作る関数と、translate が作る補助の関数と、EP が定義の中から作る関数である。ラムダ、節、handle の本体、`op$`、`con$`、`$externN`、`cont$`、`cont$state` と、EP の入口の関数 (`g$entry`)、継続の関数 (`f$kN`)、合流のブロックの関数 (`f$jJ`) が当たり、S12 のローカルの関数もここに入る。トップレベルの関数 (標準ライブラリを含む)、入口の関数、EP の補助の関数 (`id$`、`compose$` など。下の「EP が作る補助の関数」) は内部の関数でない。内部の関数を直接呼ぶのは、それを作った定義の中だけである。EP が作る関数は、元の関数 f の定義に属するとみなす。`f$kN` と `f$jJ` は同じ定義の別の継続の関数から直接呼ばれるが、この規則の「定義」は、EP がその定義から作った関数を含む
  - translate が印を付ける。テキストの形では、内部の関数を `internal fn main$lambda3(..)` と書く ([テスト戦略](../implementation/testing.md) の「Core IR のテキストの形」)
- どの関数を一様にするかは、IR の参照と内部の印だけで決まり、型は読まない
  - 値としてだけ参照され、直接は呼ばれない内部の関数は、その場で一様にする。箱を要するスカラーの引数を、同じ名前の新しい `tobj` の引数に替え、入口のブロックの先頭で、引数の順に `let p = unbox p'` を置く。箱を要するスカラーの `ret` は `tobj` にする。`obj` と `unit` の引数と `ret` は変えない
  - そのほかの、値として参照され一様でない関数 (直接も呼ばれる内部の関数と、トップレベルの関数) は、形を変えずに残し、一様な関数 `f$boxed` を足す。値の参照 (`&f` と `closure f`) は、すべて `f$boxed` へ向ける
- 入口の関数の印 (`clause`) を持つ関数は、一様化の対象から外し、操作の ABI に合わせる (下の「box の挿入」)。`ev_set_clause` の引数として値で参照されるが、`apply` では呼ばれないためである
- `f$boxed` の引数と `ret` は、`f` の箱を要するスカラーを `tobj` にし、`obj` と `unit` はそのままにする。本体は変換の前の形 `let t: <f の ret> = call f(p0, ..)` と `return t` で作り、変換はほかの関数と同じく box の挿入が入れる。`f$boxed` の内部の印と `yields` の印は `f` と同じにする。`yields` の印を写すのは、S8 で LIR に写すためである。`f` の `ret` が一様なら、縮約がこの呼び出しを `tail` にする
- トップレベルの関数をその場で一様にしないのは、トップレベルの関数の ABI を、その関数の定義 (と instance の型引数) と、それが末尾の位置で呼ぶ関数だけで決めるためである (下の「T3」)。その場で一様にすると、ほかの定義が後から値として参照するかどうかで ABI が変わる。定義ごとに Core IR を保存する REPL では、古い定義を書き換えることになる。ネイティブ化では、翻訳した関数を使い回せなくなる。総称な関数は単相化でプログラムごとに変換するので (下の「変換の規則」)、使い回せるのは型変数を持たない関数と、同じ鍵の instance である。内部の関数は、直接の呼び出しがすべて同じ定義の中にあるので、その場で一様にしても困らない。LLVM が引数の形を変えてよい関数を、内部の linkage の関数に限るのと同じ考え方である
- 捕獲も一様にする。`closure f(..)` の引数は `f` の引数の Repr に変換し、`f` は一様なので、捕まえた `int` と `enum` は `box` される。捕獲を具体的な Repr のまま持つには、クロージャごとのペイロードの記述子と、関数ごとの一様な入口が要る。その入口は `f$boxed` と同じものなので、2つの仕組みが重なる
- クロージャの呼び出しの規約は変えない。共有されたクロージャへの `apply` は、中身を写す (Lean の `pap` と同じ)

#### エフェクトの位置

- エフェクトの表の操作は、引数の Repr の列 `params` と、結果 `ret: OpRet` を持つ。操作のスキームの型から決め、型変数は `tobj` にする。データの配置のフィールドの Repr と同じ考え方である。`effect Counter where put : Int -> Unit` の `put` は `int` を受けて `unit` を返し、`effect State s` の `get` は `tobj` を返す
- `OpRet` は `Repr` か `Never` である。`never` の操作の結果は `Never` で、呼び出した側の位置と比べない (下の「`never` の操作」)。操作の引数の数は `params` の長さで、別には持たない。操作が再開するかどうか (`resumable`) も持つ
- 操作の宣言した Repr は、`clause` の引数と結果、つまり in-place の入口 (下の「`perform` と節の3つの形」) の引数と結果に使う。`clause` の先頭の引数の evidence は `obj` である
- 継続を再開する値と、yield で運ぶ節の引数は一様のままにする。EP の後は継続の再開も yield も一様な `apply` で動くので、そこに操作の Repr を通すには、継続ごとと節ごとに別の呼び出しの規約が要るためである。効くのは再開する操作だけで、すぐに再開する操作 (状態の `get` と `put`) は in-place の入口の境界だけで効く
- translate の出力の `handle` の節と本体、`return` の節は、値として参照されるので一様になる。translate の出力の `perform`、`resume`、`handle` のオペランドと結果は、EP が消すので境界の検査を受けない

#### `never` の操作

- `never` の操作の `clause` は値を返さない。節が継続を捨てるので、`clause` の後へ制御が戻らない。そのため、その結果は位置でなく、束縛の Repr は translate が決めたまま (具体化した型の Repr) にする。EP の後は、その値は `never` の節の入口が返すダミーである (下の「ダミーの値」)
  - box の挿入は、`never` の `clause` の束縛を受け直さず、その束縛を使う所にも変換を入れない。束縛の使いには制御が届かないからである
  - T3 は `never` の `clause` を見ない。縮約は、末尾の位置の `never` の操作の `clause` を、どの `ret` とも互換として扱う
  - verifier は、`never` の `clause` の結果を束縛と比べず、末尾の `never` の操作の `clause` の結果を呼び出し元の `ret` と比べない。互換の位置では、`never` の `clause` の束縛の使い (`return` の値、呼び出しの引数など) も位置と比べない。正確な位置の使いは、ほかの変数と同じく比べる
  - 縮約の前の `let t = clause Fail.fail ..` と `return t` の形は、t の Repr が `ret` と互換でなくても、そのまま `tail clause` になる。この呼び出しは末尾の位置にあるので、EP は yield の地点にしない
- 結果を `tobj` とすると、T3 が「確かめて失敗する」形の関数の `ret` を上げる。`tail clause Fail.fail ..` だけのために `ret` が `tobj` になり、成功する経路で `box` が、呼び出し元で `unbox` と `decref` が要る。ネイティブの 64 ビットの `Int` では、成功する呼び出しのたびに箱を確保しうる。`never` の操作の `clause` は戻らないので、末尾呼び出しの保証にも関わらない
- `never` の操作の引数は、ほかの操作と同じく操作の表の `params` に従う。in-place の入口の `ret` は `obj` である (下の「`perform` と節の3つの形」)

#### T3

- 末尾の位置の `apply` の結果は `tobj` である。`ret` が箱を要するスカラーの関数では、その結果を `unbox` するので、呼び出しは末尾呼び出しでなくなる。そのままでは、関数の値を通るループ (`loop f n = if n == 0 then 0 else f (n - 1)` と `go n = loop go n`) がフレームを積む。インタプリタはフレームをヒープに置くのでメモリが O(n) になるだけだが、ネイティブではスタックがあふれる
- T3 の規則: 関数の `ret` が箱を要するスカラーで、その関数の末尾の位置の呼び出し (下の「変換の規則」) のどれかの結果が `ret` と互換でなければ、`ret` を `tobj` にする
  - 呼び出しの結果は、直接の呼び出しなら呼ばれる関数の `ret`、`clause` なら操作の表の `ret`、`apply` なら `tobj` である。`never` の操作の `clause` は見ない
  - 上げた関数を末尾の位置で直接呼ぶ関数も、同じ規則で上げる。不動点まで伝える
  - `unit` の `ret` は上げない。`unit` の関数の末尾の位置の呼び出しの結果は、型から `unit` か `tobj` に決まり、どちらも互換だからである
  - 上げた関数の直接の呼び出し元は、結果を `unbox` で受ける。Perceus がその後に `decref` を置く
- T3 が作る末尾呼び出しの保証は、下の「変換の規則」にある
- 呼ばれる側の `ret` は上げない。保証には要らず、呼ばれる側のほかの呼び出し元すべての ABI を変えるためである。Lean の `InferBorrow.ownParamsUsingArgs` が、末尾呼び出しを保つために ABI を変えるのと同じ考え方である

### 変換の規則

- extern の関数の引数のそろった呼び出しは、`extern` 命令 (`Rhs::Extern`) にする。extern は、その場で実行して値を返す1階の命令で、eml のコードを呼び返さず、継続のフレームも積まない。`mask` は持たない。引数の所有権は、コンストラクタの呼び出しと同じく命令に移る。どの extern があり、引数と結果の Repr が何で、純粋かどうかは処理系の表 (`eml_extern`) が決める。
- 表面の構文には `perform` はない。HIR から Core IR への変換で、操作の呼び出しを `perform` 命令に変える。
- クロージャは「関数 + すでに渡された先頭の引数の並び」で表す。ラムダは、捕まえた変数を先頭の引数に持つ関数に持ち上げる。ラムダの捕獲と部分適用は、どちらもこの形のクロージャになる。
- 関数値の呼び出しは、実行時に引数の個数を比べる eval/apply 方式で行う。個数が揃えば呼び、足りなければ引数を足した新しいクロージャを作り、余れば先頭の分で呼んだ結果に残りを適用する。呼ぶ相手が分かっている呼び出しは、変換の時点で同じ場合分けをする。
- 捕まえた変数がなく、部分適用の引数もない関数は、クロージャを確保せず、関数の値 (`Atom::Fn`) にする。関数の値はヒープに置かず、RC の対象にならない。`closure` (`Rhs::MakeClosure`) はつねに1つ以上の引数を持ち、同じ値に2つの書き方を残さない。関数の値の呼び出しも、引数のないクロージャと同じ eval/apply で行う。
- 引数のないトップレベルの値は、参照するたびに計算する。値は純粋なので結果は変わらない。一度だけ計算する形は後で入れる ([ロードマップ](../future/roadmap.md))。
- コンストラクタのタグは、`data` の宣言の順の番号で、その型の配置の中の添字である。引数のないコンストラクタの値は即値のタグで、引数を持つコンストラクタの値はヒープのオブジェクト (`Payload::Data`) である。`Bool` は Prelude の `data Bool = | False | True` で、`False` のタグが 0、`True` のタグが 1 になる。Core IR の定数 `FALSE` と `TRUE` はこの値を持ち、`eml_core_ir` のテストが Prelude の宣言のタグと一致することを確かめる。`Ordering` の定数 `LT`、`EQ`、`GT` (タグ 0、1、2) も同じく確かめる。
- タプルの値は、タグ 0 のコンストラクタの値と同じオブジェクトで表す。配置は大きさごとの `(,)`、`(,,)` である。`Unit` (要素のないタプル) は即値の `()` である。
- リストのリテラル `[e1, …, en]` は、要素を左から評価して変数に入れた後、`Nil` のタグから始めて、右の要素から順に `::` の `con` を積む。ループで組むので、要素が多くても変換のスタックは深くならない。`[]` は、コンストラクタ `Nil` の参照と同じタグの定数 (`Atom::Tag`) である。`Prelude.List` の配置は、ほかのデータ型と同じく、IR が初めて使ったときに表に入る
- レコードの作る式は、フィールドの式を書いた順に評価して変数に入れ、宣言の順に並べ替えて `con L #t(…)` を作る ([式](expressions.md) の「レコード」)。配置はほかの `data` と同じで、名前付きのフィールドのためだけの配置や命令はない
- 射影 `e.f` は、`e` を評価し、`unpack v L #t(f0, …, fn)` で分解して、`f` の位置の変数を結果にする。タプルの `t.0` も同じ形で、配置は組の配置である。`unpack` の変数の Repr は、取り出すフィールドの変数だけ射影の式の型の Repr にし、ほかのフィールドは配置のフィールドの Repr にする。型変数のフィールドの `tobj` から `int` への `unbox` などの変換は、box の挿入が足す (下の「box の挿入」)。取り出したフィールドは、今の規則どおり Perceus が所有にする (`dup`、または値が一意なら `release` で参照を引き継ぐ)。借りたまま読む命令は足さない
- 更新 `{ e | f = v }` は、`e` を評価し、フィールドの式を書いた順に評価してから、`unpack` で古いフィールドを取り出し、置き換えるもの以外の古いフィールドと新しい値を宣言の順に並べて、新しい `con` を作る。`unpack` の変数の Repr は、残すフィールドの変数を、型引数で具体化したフィールドの型の Repr にする。作る式の `con` の引数と同じく、後の決定木はこの `con` の引数をパターンの変数にそのまま渡すためである。置き換えるフィールドの変数は、配置のフィールドの Repr のままにする。意味は写しで、残したフィールドは Perceus が所有にし、上書きされる古い値と元の値は手放す。一意な値をその場で書き換えるのは、Perceus の reuse ([ロードマップ](../future/roadmap.md) の「処理系」) に任せる
- レコードの分解のパターンは、HIR がコンストラクタのパターンに組むので、決定木の規則は変わらない。フィールドのセクションは、ほかのラムダと同じく変換する
- 穴のある文字列は、本文と穴を左から1つずつ処理する ([式](expressions.md) の「補間」)。最初の部分 (本文の文字列の定数か、穴の結果) を、組み立て中の文字列にする。それ以降の部分は、評価するたびに `extern` 命令の `Prelude.++` (`Extern::StrConcat`) で組み立て中の文字列につなぐ。部分が1つだけなら (`"\{x}"`)、連結はしない。連結の命令は、導出した `Show` と同じく表の行を直接指し、位置を持たない。ユーザーが自分の `++` を定義しても変わらない
- 評価の途中でつなぐので、穴の呼び出しをまたいで退避するのは組み立て中の文字列だけである。リストのリテラルのように、すべての部分を評価してから組むと、退避の大きさの合計が部分の数の2乗になる
- 最初の連結は、左辺が不死のリテラルか共有された文字列なら、写して新しい文字列を作る。2つ目からは、一意な左辺をその場で伸ばす ([ランタイム](runtime.md) の「文字列の連結」)。そのため、全体の長さに比例する時間で済む
- コンストラクタを部分適用したときと関数値として使ったときは、コンストラクタの値を作るだけの関数 (`con$…`) で包む。
- クラスのメソッドへの参照は、instance のメソッドの関数、既定のメソッドの関数、`extern` 命令、生成した関数のどれかに変換する (下の「メソッドの解決」)。
- extern の関数を値として使うとき (引数が足りないときを含む) は、参照する場所ごとに、それを呼ぶだけの関数 `<外側の関数>$externN` で包む。本体は `let t.1: unit = extern Prelude.println(p.0) @"main.em":6:9` と `return t.1` のような形で、`extern` 命令はその参照の場所の位置を持つ (下の「位置」)。instance の `extern` で結んだメソッドを値として使うときも、同じく包む。包む関数の型は参照の型から取る。メソッドの参照が extern になるかは instance によるので、`$externN` の番号は、同じ本体でも instance ごとに変わりうる。
- `if c then a else b` は `match c with | True -> a | False -> b` と同じ分岐にする。条件 (`&&`、`||`、入れ子の `if`、条件の位置の `match`) は `Bool` の値を作らずに分岐し、短絡評価の順を保つ。値が静的に決まる条件は、`switch` を出さずにその枝だけを変換する。
- 末尾にない分岐の値は、引数を持つ合流のブロックで受ける。各枝は値を `jump` で合流のブロックに渡し、合流のブロックが続きを実行する。値を返す枝が1つだけなら、合流のブロックを作らず、その枝のブロックで続きを変換する。末尾の分岐は合流のブロックを作らず、各枝が直接返す。
- `match` は決定木にコンパイルする。決定木は、最初の行でコンストラクタ、タプル、リテラルのどれかのパターンを持ついちばん左の列を選ぶ。コンストラクタの列は、その列の値で `switch` する。列のどの行にも現れないコンストラクタは、case を作らず `default` にまとめる。リテラルの列は、列に現れる異なるリテラルを case に持つ1つの `switch` にし、リテラルに当たらない値の行列を `default` で続ける。リテラルを比べる命令の連なりにしないのは、枝の数だけ入れ子を深くしないためである。`match` は網羅性の検査を通っているので、どの枝にも当たらない値の受け皿は作らない。
- コンストラクタが1つでフィールドを持つ型 (タプルを含む) の列は、`switch` ではなく `unpack` で分解する。フィールドのない唯一のコンストラクタは、`()` と同じくワイルドカードとして扱い、何も出さない。
- scrutinee がタプルのリテラルなら、タプルを作らず、その要素を決定木の列にする。複数の等式を持つ関数で HIR が作るタプルも含む。値全体を束縛する行があれば、その葉でだけタプルを作る。
- 決定木の葉が1つの枝にだけ届くとき、その枝の本体は葉のブロックに置き、パターンが束縛する変数を葉の値で置き換える (別名の `let` を作らない)。複数の葉から届く枝は、パターンが束縛する変数を引数に持つ合流のブロックにし、葉から `jump` する。どの葉にも届かない枝は出さない。
- `let`、ラムダの引数、等式の引数のパターンも、同じ決定木で分解する。葉が1つなら今のブロックに `unpack` を並べ、続きもそのブロックで変換する。葉が複数なら、葉から続きのブロックへ `jump` し、束縛した変数をその引数にする。
- 頭のコンストラクタかリテラルが変換の時点で分かっている値 (コンストラクタの適用、タプルのリテラル、タグと `Int` の定数、同じ関数の中で `let x = con ..` で束縛した変数) を調べるときは、`switch` を出さずにその場で case を選ぶ。
- `match`、分解する `let`、条件の scrutinee が分岐 (`if`、`match`、それで終わるブロック) なら、分岐の各出口の値を `match` に直接渡す (case-of-case)。`let x = <分岐>` の直後の本体が `match x` である形も含める。出口の値で1つの枝に決まれば、コンストラクタを作らずにその枝へ `jump` し、決まらない出口の値だけを合流させて `switch` する。束縛と `match` の間に文がある形と、呼び出しの結果は扱わない。
- 関数の末尾の呼び出しは末尾呼び出し (`tail`) にし、呼び出し元のフレームを積まない。末尾呼び出しは、縮約だけが IR の形から作る (下の「縮約」)。translate は、値を返すだけの合流のブロック (文がなく、`return p` だけを持ち、引数が `p` だけ) へ向かう `jump` を `return` に置き換え、`let x = <呼び出し>` と `return x` を残す。translate の出力では `jump` の実引数と行き先の引数の Repr が同じなので、この転送は Repr に関わらない。対象の呼び出しは、直接の呼び出し、`mask` で分けた `apply` の最後の部分、余った引数を渡す呼び出し、`handle`、`perform`、`resume`、引数のないトップレベルの値である。EP の後は、`clause` も対象になる。
  - 末尾の位置の呼び出しは、IR の形で決まる。1つのブロックの終端が `return x` で、同じブロックに x を定義する `let x = <呼び出し>` があり、その後の文がすべて純粋な `let` (縮約が消すもの) であるとき、その呼び出しを末尾の位置の呼び出しという。後ろの純粋な `let` の変数は `return` が使わないので、縮約がすべて消し、そこで `tail` を作る。形だけで決まるので、`never` の操作の `clause` も含む。EP (下の「yield の地点」) と T3 (上の「位置の規則」) は、この定義を使う
  - 保証: 末尾の位置の呼び出しをたどって元の関数に戻る輪の上にある末尾の位置の呼び出しは、どれも `tail` になる。輪の辺は、直接の呼び出しなら呼ばれる関数へ向き、`apply` ならどの関数へも向きうるとみなす。`clause` の辺は輪に乗らない。入口の関数 (すぐに再開する節、再開する節、`never` の節のどれでも) は末尾呼び出しを持たないためである。`mask` 付きの呼び出しは保証の外に置く。戻りで `evv` を戻すのでフレームを残すが、そのフレームの数は handler の数で抑えられる (下の「`evv` の不変条件」)。結果に変換の要る末尾の位置の呼び出しは、普通の呼び出しになる
  - EP の補助の関数 (`compose$`、`prompt$`、`resume$`、`rewind$`) の末尾呼び出しは、どれも `tobj` から `tobj` への呼び出しなので、いつも `tail` になる
  - 保証の理由: T3 の後に結果が互換でない末尾の位置の呼び出しは (`never` の操作の `clause` を除く)、`ret` が `tobj` の関数から、`ret` が箱を要するスカラーの関数への直接の呼び出しと、スカラーを返す操作の `clause` だけである。呼び出し元の `ret` がスカラーなら T3 が上げており、`obj` なら呼ばれる側の `ret` は `obj` か `tobj` になるからである。`clause` の辺は輪に乗らないので、残るのは直接の呼び出しである。そのような呼ばれる側 g が輪の上にあり、`ret` がスカラー s だとする。g の末尾の位置の呼び出しは互換なので、`ret` が s の関数への直接の呼び出しである。輪をたどると、輪の上の関数の `ret` はすべて s になり、輪の上に `ret` が `tobj` の呼び出し元があることと矛盾する。`f$boxed` は直接呼ばれず、`ret` が一様なので、`f$boxed` を足した後の IR でも同じ議論が成り立つ
  - 保証は IR の形についての文である。呼び出しの値が、文を持つ合流のブロックを通って `return` に届く形 (`let r = if n == 0 then 0 else f (n - 1) in let s = "unused" in r`) は、末尾の位置の呼び出しでなく、保証の外にある ([実装の現在地](../implementation/status.md) の「深さと性能」)
  - 後のパスもこの保証を保つ。所有の都合の降格は、輪の上の `tail` に当てない (上の「ブロックの列」の `tail`)
- 関数のコードは instance ごとに変換する (単相化)。instance は、定義された関数、型引数の列、row のビットの組で、この組を instance の鍵と呼ぶ。型引数は型の表の `TypeId` で、シグネチャの型変数の順 (`generics.type_vars` の順) に並ぶ。型変数を持たない関数の型引数は、空の列である。row のビットは、row 変数ごとに「yield しうる row が入ったか」を持つ (下の「row のビットと instance の鍵」)。変換は、入口から届く instance だけを Core IR にする。標準ライブラリのうち使わない関数は Core IR に入らない。
  - 鍵は型そのものである。`List Int` と `List String` のように Repr が同じ型引数も、関数型の row だけが違う型引数 (`Unit -> <e> Int` と `Unit -> <IO> Int`) も、別の instance になる。型クラスの証拠が型ごとに変わるためである。Repr が同じ instance をまとめるのは、後の最適化に回す ([ロードマップ](../future/roadmap.md) の「処理系」)
  - 本体の中の関数への参照 (呼び出しと、値としての参照の両方) は、型検査が参照ごとに記録した型引数を持つ。呼ぶ先の鍵は、この型引数に、参照を含む instance の代入をかけて作る。instance の代入は、その instance の関数自身のシグネチャの型変数を instance の型引数に置き換え、handler の節の操作ごとの型変数をいつも `Flexible` に置き換える。row の末尾は変えない。その後、呼ぶ先の一様な位置 (次の項目) の型引数を、参照の型引数によらず `Flexible` にする。残った `Flexible` (節の型変数から来たもの、型検査で最後まで決まらなかったもの) は、そのまま鍵に入る。`Flexible` の Repr は `tobj` である。extern の関数、操作、コンストラクタへの参照は instance を作らない
  - 多相再帰 (`depth : Int -> a -> Int` の本体が `depth (n - 1) (x, x)` と呼ぶ形) は、型変数の流れのグラフで見つけ、その位置を一様な位置にする。グラフは型検査 (`eml_types`) が型検査の後に計算して `TypedProgram::uniform` に入れ、変換はそれを読む。この項目は関数の節点と関数の参照の辺だけを書く。クラスのメソッドと instance の節点と辺は、下の「一様な位置と制約付きの多相再帰」にある。グラフの節点は (関数, 型変数の番号) で、HIR のすべての定義された関数について作る。関数 f の本体の参照 `g @[T0, T1, …]` で f の型変数 i が Tj に現れるとき、(f, i) から (g, j) へ辺を引く。「現れる」は、型構成子の引数、タプルの要素、関数型の引数と結果とエフェクトの型引数のどこかにあることである。Tj が i の型変数そのものでなければ、その辺は大きくなる辺である。大きくなる辺の両端を含む強連結成分を大きくなる成分と呼び、その節点を一様な位置とする。自分自身への大きくなる辺を持つ節点 (`depth` の型変数) も、大きくなる成分である
  - 一様な位置は、関数ごとでなく型変数の位置ごとに決める。`walk : Int -> a -> b -> b` が `a` だけを大きくして自分を呼ぶとき、`walk` を `b := Int` で使った instance は `walk@[_, Int]` で、`b` の位置の引数と `ret` は `int` である。大きくならない型変数の制約の証拠を、具体的な型から確定するためである
  - 一様な位置の型引数は `Flexible` なので、大きくなる成分を通る型の大きさは有界になる。大きくなる成分の外の位置に流れ込む型も、有界な型と `Flexible` から作られるので有界である。そのため、instance を集める手順は止まる。instance の総数に上限は置かない ([実装の現在地](../implementation/status.md) の「深さと性能」)
  - 入口の関数の鍵は、型変数を持たなければ空の列、持てばすべて `Flexible` である。入口は `main` とは限らず、変換の呼び出し側が選ぶ
  - instance は、入口の instance から始めて、見つけた順に処理する (FIFO)。各 instance の本体では、関数への参照を HIR の式の ID の順にたどり、まだない鍵を列の後ろに足す。すべて集めてから、instance を HIR の関数の順に並べ、同じ関数の instance は見つけた順に並べて、その順に関数の番号を振る。`TypeId` の値の順には並べない。後の段階が `TypeId` の値に意味を持たせないためである。型変数を持たない関数だけのプログラムでは、関数の並びは HIR の関数の順になる
  - 型変数を持つ関数の instance の名前は、元の名前 (モジュールの修飾を含む) に `@[型引数, …]` を付けた形である (`map@[Int, String]`、`Prelude.>>@[Int, Int, Int]`、`length@[List Int]`)。一様な位置の型引数 (`Flexible`) は `_` と書く (`depth@[_]`)。型引数は診断と同じ表示で書き、型の名前は、名前が重なるときだけモジュールで修飾する。いつもモジュールで修飾するデータの配置の名前とは、規則が違う
  - `@[` と `]` の間が 64 文字を超える instance は、`@[…]` の代わりに、その関数の instance の中の順番 (上の番号の順で、1 から数える) を `@` の後に付ける (`ident@3`)。部分を共有する型の型引数で、名前が指数の長さになるのを防ぐためである。異なる型が同じ表示になり (row の末尾の表示など)、同じ関数の2つの instance の `@[…]` の名前が重なったときは、後の instance を順番の名前にする。`@[` で始まる名前と、`@` に数字が続く名前は重ならない
  - 型変数を持たない関数の名前は、元の名前のままである。立ったビットの row 変数は、名前の後ろに `<e>` の形で書く (下の「row のビットと instance の鍵」)。ラムダ、handle の本体と節、`$externN` の名前は、instance の名前を根にする (`twice@[Int]$lambda0`)。box の挿入が足す `f$boxed` も、instance の名前に付ける (`inc@[Unit]$boxed`)。入口を呼ぶ関数の名前は、instance の名前でなく元の名前から作る (`entry$first`)。位置を持たない実行時エラー (下の「実行時エラー」) は、instance の名前を出す
  - instance の本体は、本体の型 (式、局所変数、パターン、参照の型引数) に instance の代入をかけた型で変換する。トップレベルの関数の引数と `ret` の Repr は、宣言の型に代入をかけた型から決める。メソッドの解決も、代入をかけた型引数から行う。ラムダ、handle の本体、節は、外側の instance の型を使う。節の型変数は `Flexible` になるので、節の中のコードは一様なままである
  - データの配置、`op$`、`con$`、`cont$`、`cont$state` は、instance によらずスキームから作る。データの配置まで型ごとに分けると、一様な位置を通るコードと配置が食い違うためである (上の「データの配置」)
- テキストの形 ([テスト戦略](../implementation/testing.md) の「Core IR のテキストの形」) は関数とエフェクトを名前で引くので、モジュールをまたいで名前が重なってはいけない。入口以外のモジュールでは、関数、操作を包む関数、コンストラクタを包む関数、エフェクトの表の名前に `モジュール名.` を付ける (`Report.Csv.parse`、`con$Report.Csv.Row`)。標準ライブラリのモジュールもこの規則に含め、正式な名前を使う (`Prelude.not`、ラムダは `Prelude.>>$lambda0`)。入口のモジュールの名前には付けない (`parse`、`op$get`)。extern の呼び出し (`extern <正式な名前>(…)`) は、正式な名前をそのまま使う (`extern Std.Fs.open`)。
- 持ち上げた関数の番号 (`$lambdaN`、`$handleN`、`$externN` の N) は、外側の関数の本体の中で、HIR の式の ID の順に振る。変換の順に依らないようにするためである。
- 変換は、`main` を `()` で呼ぶ入口の関数を作る。等式に引数のない `main` は関数値を返すので、入口の関数が返った値に `()` を適用する。
- `handle`、`perform`、`resume` は、translate の出力では呼び出しの一種である。表面の構文に `resume` はなく、`resume` は変換が作る Core IR の内部の命令 (`Call::Resume`) である。EP がどれも基本操作と普通の呼び出しに置き換える (下の「evidence passing」)。
- 呼び出し (`Rhs::Call` の `Call::Direct`、`Call::Apply`、`Call::Resume`) と末尾呼び出し (`Term::TailCall`) は `mask` を持つ ([エフェクトと handler](effects.md) の「handler の意味」)。`mask` は、呼び出しの間に飛ばすエフェクトの多重集合で、エフェクトの番号の昇順に並べ、飛ばす数だけ同じ番号を繰り返す。空なら `mask` なしである。extern のエフェクトは入れない。`Call::Handle` と `Call::Perform` は `mask` を持たない。`handle` の本体の中の呼び出しは、持ち上げた本体の関数の中の呼び出しとして `mask` を持つ。
- 変換は、型検査が呼び出しの矢印ごとに記録した `mask` ([型と Kind](types.md) の「推論」) を、Core IR の呼び出しに付ける。
  - 引数がそろう既知の関数の呼び出し (`Call::Direct`) は、最後の矢印の `mask` を使う。前の矢印は部分適用で、エフェクトを起こさないためである。同じ理由で、引数が足りずにクロージャを作るときは `mask` を付けない。extern、操作、コンストラクタの呼び出しには、型検査が `mask` を記録しない。
  - 余った引数を `Call::Apply` で渡すときは、矢印ごとの `mask` が変わる境目で `apply` を分ける。`mask` は1つの Core IR の呼び出し全体に効くので、違う `mask` の矢印を1つの `apply` にまとめると、片方の矢印に余計な `mask` が効くためである。yield しうる矢印の後でも分ける (下の「`apply` の印と分け方」)。
  - `mask` が効くのは呼び出しそのものだけで、引数の評価には効かない。Core IR の呼び出しの引数は値 (アトム) なので、引数は呼び出しより前の文で評価し終えている。そのため、これは形から決まる。
- `mask` は translate の出力にだけある。EP が `evv_mask` の包みに置き換える (下の「`mask` の包み」)。包みは戻りで `evv` を戻すので、`mask` 付きの末尾の位置の呼び出しは末尾呼び出しにならない。
- 変換の段の verifier は、`mask` のエフェクトの番号がエフェクトの表にあること、昇順に並んでいること、`mask` が `handle` と `perform` に付いていないことを確かめる。EP の後の段は、`mask` が残っていれば誤りにする。
- extern のエフェクト (`IO`) は、Core IR のエフェクトの表に入れない。`handle`、`perform`、`mask` と EP の基本操作は extern のエフェクトを指さないためである。エフェクトの番号は、extern のエフェクトを飛ばして数える。また verifier は、`extern` 命令の引数の数と、引数と結果の Repr を表の行と比べる。
- handle の本体、操作の節、`return` の節は、ラムダと同じく、捕まえた変数を先頭の引数に持つ関数に持ち上げ、そのクロージャか関数の値を `handle` に渡す。本体の関数は `()` を受ける。節はエフェクトの操作の順に並べる。操作を値として使うときは、`perform` を呼ぶだけの関数 (`op$…`) で包む。
- 変換は、節ごとに `k` の使い方を HIR で調べ、次の2つの形のどちらかにする。
  - 直接の形: 節の本体のどこでも (入れ子のラムダや handle の本体の中を含む)、`k` の使用がすべて引数をそろえた直接の呼び出し (`k v`、状態ありなら `k v st`) か `drop k` なら、クロージャを作らない。その呼び出しを、生の継続への `Call::Resume` にする。生の継続をラムダや handle の本体が捕まえても、`Call::Resume` で再開できる。引数が余る呼び出し (`r` が関数型のときの `k v x`) は、`Call::Resume` の結果への `apply` を続ける。`mask` は、その呼び出しの最後の矢印の記録を付ける。
  - 包む形: `k` を関数の値として使う (渡す、しまう、部分適用する) なら、節の入口で、生の継続を継続を包む関数のクロージャにし、それを `k` とする。`k` の呼び出しは普通の関数値の呼び出し (`Call::Apply`) になる。
- 継続を包む関数は、状態のない handler 用の `cont$` と、状態のある handler 用の `cont$state` の2つで、使うときだけプログラムに1つずつ作る。`cont$` は `k` と `v` を受けて `resume k(v, ())` を、`cont$state` は `k`、`v`、`s` を受けて `resume k(v, s)` を、それぞれ末尾呼び出しする。
- 包んだ `k` は、`once` なら1回しか使わないので、Perceus は `dup` / `decref` を付けず、クロージャも一意で、呼ぶと消費される。
- 包んだ `k` を `drop` するとクロージャが解放され、それが継続を解放する。
- パラメータ付き handler は脱糖しない。Core IR では、すべての handler を状態のある handler として扱い、状態のない handler は状態を `()` にする。`handle` はつねに状態の初期値を、`resume` はつねに次の状態を持つ。状態のない handler の `k v` は、直接の形なら `resume k(v, ())` に変換し、包む形なら `cont$` を通って `resume k(v, ())` になる。この `()` は Core IR の中の決まりで、表面の構文では状態のない `k` は1引数の関数である ([エフェクトと handler](effects.md) の「パラメータ付き handler」)。節のクロージャはつねに状態を最後の引数で受け、`return` の節はつねに本体の値と状態を受ける。呼び出しの規約を1つにして、EP で状態の有無を場合分けしないためである。`return` の節はつねにある。省略した handler は、HIR が `| return x -> x` の節 (状態のある handler では、状態を `_` で捨てる `| return x _ -> x`) を合成するので、本体の値をそのまま返し、状態の引数は Perceus が捨てる (RC の対象の状態だけ decref する)。省略した節は状態を `_` で捨てるので、状態の型は `Unr` である ([式](expressions.md) の「パラメータ付き handler」)。
- メモリ管理は Perceus 方式の参照カウントである。`Lin` の値は2回以上消費されないが、`dup` や共有の側を通る `release` を受けることはある (上の「値の表現」)。

### row のビットと instance の鍵

row は「yield しうるか」だけで単相化する。handler を使わないプログラムには、EP が何も足さない。Core IR は row そのものとラベルの順序を持たず、row の情報は関数と `apply` の「yield しうるか」の印 (下の「`yields` の印」と「`apply` の印と分け方」) だけである。

- 型検査は、参照ごとの row 変数の具体化を、yield しうるかの分類 `RowYield` として記録する ([型と Kind](types.md) の「row の具体化の記録」)
- 参照の row のビットは、参照の `rows` の各要素を、参照を含む instance のビットで解いたものである。`Always` は立つ、`Never` は立たない、`Var(i)` は含む instance の i 番目のビットに従う
- メソッドの参照の row 変数は、メソッドのシグネチャの row 変数である。instance のメソッドの関数と既定のメソッドの関数は、メソッドのシグネチャをそのまま row 変数に持つので、ビットを同じ順に写す。導出とタプルの生成器が作る関数は row 変数を持たない
- 入口の instance のビットは、すべて立てる。安全側の選び方で、`main` は row 変数を持たないので影響しない
- ビットの組は、row 変数が k 個なら 2^k 通りなので、instance を集める手順は止まる。一様な位置の議論 (下の「一様な位置と制約付きの多相再帰」) は型変数だけのもので、row には当てはめない
- 名前: 立ったビットの row 変数だけを、`@[…]` の後ろに `<e>` の形で書く。`map@[Int, String]<e>`、型引数のない関数なら `twice<e>`、長い名前の番号の形なら `ident@3<e>` である。2つ立てば `<e, f>` とシグネチャの順に書く。ビットがすべて立たない instance の名前は、ビットのない形のままである。`<` と `>` はテキストの形の名前の文字でないので、こういう名前は空白を含む名前と同じく引用符で囲む ([テスト戦略](../implementation/testing.md) の「Core IR のテキストの形」)

### `yields` の印

関数 (`CoreFn::yields`) は、本体が yield しうるかの印を持つ。テキストの形では、`internal` の後に `yields fn f(..)` と書く (`internal yields fn main$lambda0(..)`)。

- translate は、関数の型の「引数の数番目の矢印」の row が yield しうるとき (`RowYield` をその instance のビットで解いて立つとき) に立てる。本体はその矢印の row で動くためである ([型と Kind](types.md) の「推論」)。`f : Int -> <State> (Int -> Int)` の `f x = …` では1番目の矢印である。引数のない値は純粋なので立てない
- トップレベルの関数は宣言の型から、ラムダは外側の instance の代入をかけた自分の型から決める
- 入口の関数 `entry$<名前>` の印と、その中の `apply f(())` の印は、入口の関数の宣言の型の最初の矢印から決める。等式に引数のない入口 (`main = fn () -> ..`) では、入口の関数の instance の印 (引数の数が 0 なので立たない) が使えないためである。型検査が記録したその矢印の分類 (`BodyTypes::first_arrow_yield`、[型と Kind](types.md) の「row の具体化の記録」) を、入口の instance のビットで解く
- handle の本体はいつも立てる。本体の row は扱うエフェクトを含むためである
- 操作の節と `return` の節は、handle を含む関数の印と同じにする。節は handle の外側の row で動き、その row は handle を含む関数が動いている row である
- `op$` は、その操作を呼ぶ形なので立てる。`cont$` と `cont$state` は、どの文脈からも呼ばれる補助の関数なので立てる。`con$`、`$externN`、導出とタプルの生成器が作る関数、`tag$` は立てない
- box の挿入が足す `f$boxed` は、`f` の印を写す (上の「一様な関数」)
- EP が作る関数の印は、下の「evidence passing」の各項目で決まる
- `evv` を関数の引数でなく実行の文脈に持つので (下の「実行の文脈」)、yield しうる関数とそうでない関数の呼び出しの規約は同じである。そのため、印が保守的でも規約は食い違わない

### `apply` の印と分け方

- translate は、`mask` の変わる境目で余った引数を渡す `apply` を分けるのに加えて、yield しうる矢印の後でも `apply` を分ける。実行時の `apply` は、呼ばれる関数の引数の数で引数を分けて順に呼ぶ (eval/apply) ので、1つの `apply` の途中の矢印で yield すると、残りの引数を渡す処理が継続に入らないためである。分けた後の1つの `apply` の中では、最後の矢印のほかは yield しない
- `Call::Apply` は `yields` の印を持ち、translate は、その `apply` が受け持つ矢印のどれかが yield しうるなら立てる。分け方から、これは最後の矢印が yield しうるときである
- テキストの形では `yields apply c.0(x.1)` と書く。`mask` があれば `mask [State] yields apply …` の順にする
- `Call::Resume` から EP が作る `apply` の印は、その命令を含む関数の印と同じにする。`k` の最後の矢印の row は handle の外側の row である。生の継続をラムダや handle の本体が捕まえて再開する形でも、それを含む関数の row は `k` の row を含まなければならないので、この印は安全側である

### メソッドの解決

instance の代入をかけた後のメソッドの参照 `m@[T, U1, …]` (T はクラスの型変数の型引数、Ui はメソッド自身の型引数) は、`T` の頭で instance を引いて変換する。instance は一貫しているので ([モジュールと名前解決](modules.md) の「instance の一貫性」)、1つに決まる。証拠は型検査が記録しない。参照の型引数から、ここで引き直す ([型と Kind](types.md) の「制約」)。

| instance の種類 | 変換先 |
|---|---|
| 手で書いた instance で、メソッドを定義している | instance のメソッドの関数の instance。鍵は、頭の型引数とメソッド自身の型引数を並べた列 |
| 手で書いた instance で、メソッドを省いた | 既定のメソッドの関数の instance。鍵は `[T, U1, …]` |
| `extern` で結んだメソッド | `extern` 命令。値として使えば、extern の関数と同じく `$externN` で包む (上の「変換の規則」)。引数の数と Repr は表の行から取る |
| 導出した instance、タプルと `Unit` の instance | 中心のメソッド (`==`、`compare`、`show_prec`、`show`) は、下の「導出とタプルの生成器」が作る関数。ほかのメソッドは、手で書いた instance と同じく既定のメソッドの関数 |

- 鍵の一様な位置は、型検査が計算した一様な位置 (下の「一様な位置と制約付きの多相再帰」) を読んで `Flexible` にする。生成する関数の鍵の位置は、instance の節点の一様な位置に従う
- 解決に `Flexible` が要る位置は、どれも型検査の誤りになる。操作ごとの型変数は与えられた制約を持てないので E2006 に、決まらない推論用の変数は E2009 に、一様な位置の制約は E2012 になる。そのため translate は、制約付きの参照の解決で `Flexible` に出会わない。出会えば内部の誤りとして止める
- 変換の入口には、制約を持つ関数を選べない。入口は変換の呼び出し側が選び、制約を持つ関数を渡すのは呼び出し側の誤りとして `assert` で止める。`main` は制約を持たない
- メソッドの呼び出しの引数の数は、instance の等式の引数の数でなく、メソッドのシグネチャの矢印の数で決まる ([式](expressions.md) の「関数適用」)。instance のメソッドの等式がそれより少ない引数しか取らないときは、その関数を等式の引数の数で呼び、残りの引数を結果に `apply` する。引数のない instance のメソッドの直接の呼び出しは `mask` を持たず、残りの矢印の `mask` は `apply` が持つ

関数の名前は次のとおりである。

- instance のメソッドの関数の名前は、`<モジュールの修飾><クラス> <型>.<メソッド>` に、単相化の鍵の表示 (`@[…]`) を付けた形である (`"Prelude.Eq Option.==@[Int]"`、入口のモジュールなら `"Show Color.show"`)。修飾は instance のモジュールの規則 (上の「変換の規則」) に従う。クラスと型は、診断と同じ表示 (名前が重なるときだけモジュールで修飾) で書く。そのため、別のモジュールを足して名前が重なると、名前が変わることがある。空白を含むので、テキストの形では引用符で囲む
- 既定のメソッドの関数の名前は、メソッドの正式な名前に鍵を付けた形である (`"Prelude.!=@[Color]"`)
- 生成した関数の名前は、手で書いた instance のメソッドと同じ形にする。型の名前は、タプルなら配置の名前 (`(,)`)、`Unit` なら `()` である (`"Prelude.Eq (,).==@[Int, String]"`、`"Prelude.Show ().show"`)。修飾は、導出した instance なら型を定義したモジュール、タプルと `Unit` なら `Prelude.` である
- 補助の関数 `tag$<型>` は、`con$` と同じ修飾の規則に従う (`tag$Option`、`tag$Report.Csv.Row`)
- 生成した関数と `tag$` は `internal` にしない。多くの関数から呼ばれるためである
- instance の `extern` の行の名前 (`Prelude.Eq Int.==`) も空白を含むので、テキストの形の `extern` の位置でも、関数の名前と同じ規則で引用符で囲む (`extern "Prelude.Eq Int.=="(a.0, b.1)`)

### 導出とタプルの生成器

translate は、導出した instance とタプルと `Unit` の instance の中心のメソッドを、(クラス, 型, 型引数) ごとに Core IR の関数として作る。フィールドの値は、`switch` の case の束縛か `unpack` で受ける (R9: `unpack` はコンストラクタが1つの配置にだけ使える)。フィールドの型のメソッドは、ほかの参照と同じく上の「メソッドの解決」で解いた行き先を呼ぶ。意味は [宣言](declarations.md) の「`deriving`」にある。

- 生成するのは中心のメソッドだけである。`Eq` は `==`、`Ord` は `compare`、`Show` は `show_prec` と `show` (`show x = show_prec 0 x`) を作る。`!=`、`<`、`<=`、`>`、`>=`、`display` はクラスの既定のメソッドを通る
- `==`: 左の値で `switch` し、コンストラクタ Ci の case で右の値を `switch` する。右の `switch` は Ci の case と `default` を持つ。Ci の case では、両方のフィールドの `==` を左から短絡して呼ぶ。`default` は `False` を返す。コンストラクタが1つの型 (タプルを含む) は、`switch` せずに両方を `unpack` する
- `compare`: 左の値で `switch` し、Ci の case で右の値を `switch` する。右の `switch` の Ci の case では、フィールドを左から `compare` し、最初に `EQ` でない結果を返す (すべて `EQ` なら `EQ`)。`default` では、補助の関数 `tag$<型>` で両方のタグの番号を `Int` で求め、`Int` の `compare` の結果を返す。`tag$<型>` は型ごとに1つ作り、`switch` 1つと、定数を返す case からなる。コンストラクタの組ごとに case を作ると大きさが `n²` になるので、この形にする。コンストラクタが1つの型は、`unpack` してフィールドを比べるだけである
- `show_prec d x`: `x` で `switch` し、[宣言](declarations.md) の「`deriving`」の形の文字列を `++` でつないで作る。`d` との比べ方で括弧を付けるかを決める
- タプルは、コンストラクタが1つの配置として同じ規則を通る。`Unit` の `==` は `True`、`compare` は `EQ`、`show_prec` は `"()"` を返す
- 型がすべて `Unr` なので、写しと解放は Perceus に任せる。生成した関数は、translate の出力として verifier を通る
- 生成した関数の中の `extern` 命令は位置を持たない。使う行はどれも純粋で、実行時エラーを起こさない
- 生成した関数は、HIR の関数の instance の後に、見つけた順に並べる

### 一様な位置と制約付きの多相再帰

一様な位置のグラフ (上の「変換の規則」) は、型検査 (`eml_types`) が型検査の後に、書き出した本体の表から計算する。translate は結果 (`TypedProgram::uniform`) を読むだけである。型クラスのために、節点と辺を次のように広げる。

節点は次の3種類である。

- (関数, 型変数の番号): 関数には、instance のメソッドの関数と既定のメソッドの関数を含む
- (instance, 頭の型変数の番号): 手で書いた instance、導出した instance、プログラムに現れる大きさのタプルの instance である。以下、instance の節点と呼ぶ。タプルの節点は、大きさごとに `Eq`、`Ord`、`Show` で1つを共有する。`Unit` は位置を持たない
- (メソッド, メソッド自身の型変数の番号): 以下、メソッドの節点と呼ぶ

辺は、本体の関数 f の中の参照ごとに引く。「f の型変数 i が型 T に現れるとき、(f, i) から X へ辺を引く」の形で書き、T が i の型変数そのものでなければ大きくなる辺とする。「現れる」は関数の辺と同じである。

1. 関数の参照 `g @[T0, …]`: Tj について (g, j) へ辺を引く (上の「変換の規則」と同じ)
2. メソッドの参照 `m @[T, U1, …, Uk]` の `T` の頭で instance I が決まるとき (型コンストラクタの適用かタプル): 解決先の関数へ直接辺を引く
   - 解決先が I のメソッドの関数 F (頭の型変数が n 個) なら、`T` の型引数 Tj について (F, j) へ、Ul について (F, n + l) へ引く
   - 解決先が既定のメソッド D なら、`T` について (D, 0) へ、Ul について (D, l) へ引く。さらに、根の制約 `C T` も 4. の規則で解決の木として扱い、(I, j)、I の文脈の部分木、頭の型の上位クラスの instance へ辺を引く。D の本体は、与えられた制約 `C a` を通して I のほかのメソッドを呼ぶので、D への辺だけではその流れがグラフから漏れるためである。たとえば、`same (Box x) (Box y) = differ (Box (Box x)) (Box (Box y))` が既定の `differ x y = not (same x y)` を呼ぶと、単相化は `same@[T]`、`differ@[Box (Box T)]`、`same@[Box T]` と止まらない。この辺は保守的で、クラスの制約を使わない既定のメソッド (`differ x y = True`) でも、同じ形を E2012 にする
   - 解決先が生成する関数 (導出とタプル) なら、`T` の型引数 Tj について (I, j) へ引く
3. メソッドの参照の `T` が与えられた制約で解けるとき: `T` については辺を引かない。Ul について (m, l) へ辺を引く
4. 制約の解決: 本体の中の参照が求める制約 (関数の参照の制約と、メソッドの参照のメソッド自身の制約) を、[型と Kind](types.md) の「制約の解決」と同じ規則で解く。メソッドの参照の `C T` は、解決の木の根を 2. が扱い、根の instance の文脈から下の部分木だけをここで扱う。解決の木の、instance で解いた各節点 `D (H T1 … Tn)` について、Tj について (D の instance, j) へ辺を引く。各節点で、`D` の上位クラスの (H の) instance にも同じ辺を引き、その instance の文脈の解決の木にも同じ規則を当てはめる。与えられた制約で解けた部分には辺を引かない。その証拠は、呼び出し側の解決の辺が表す
5. instance の節点から: (I, j) から I のメソッドの関数の (F, j) へ、大きくならない辺を引く。逆向きの辺は引かない。メソッドの関数は頭の型を作り出さないので、逆向きの流れはないためである。I がメソッド m を省いて既定のメソッド D を使うときは、(I, j) から (D, 0) へ大きくなる辺を引く (既定のメソッドのクラスの型変数には頭の型そのものが入るため)。導出した instance とタプルの instance は、生成するコードが求める制約 (フィールドの型 `F` の `C F`) を、本体を (I, ·) とみなして 4. の規則で扱い、使う既定のメソッドへの辺を同じく引く
6. メソッドの節点から: (m, l) から、m を定義するすべての instance のメソッドの関数の (F, n_F + l) と、m の既定のメソッドの (D, l) へ、大きくならない辺を引く

関数の参照の制約を解いた先 (4. と 5.) は、instance のすべてのメソッドへ辺を引くので保守的である。メソッドの参照は、2. で解決先にだけ辺を引くので、同じ instance の別のメソッドの間に偽の循環を作らない。ただし、既定のメソッドへの解決は、2. の追加の辺で instance の節点を通る。

大きくなる成分の節点を一様な位置とする。一様な位置と制約の関係は次のとおりである。

- 一様な位置の型変数が与えられた制約を持てば、E2012 にする。与えられた制約を持つ位置は、関数のシグネチャで制約を持つ型変数、instance のメソッドの関数で instance の文脈かメソッド自身の制約を持つ型変数、既定のメソッドのクラスの型変数とメソッド自身の制約を持つ型変数、instance の節点で文脈を持つ型変数である。証拠を単相化で確定するには、大きくなる型ごとに instance が要り、その数に限りがないためである
- 誤りは、関数ならシグネチャの名前を、instance のメソッドと instance の節点なら instance の頭を指す。既定のメソッドの位置なら、その位置を含む大きくなる成分へ 5. の辺 (既定のメソッドへの辺) を引いた instance の頭を指す。既定のメソッドは Prelude にあることが多く、そこを指しても直す場所が分からないためである。報告は大きくなる成分ごとに1つにまとめる。成分の中で与えられた制約を持つ位置 (instance の頭と関数など) のうち、プログラムの順 (モジュールの順、その中のソースの順) で最初の位置を主な位置にし、ほかの位置を副の位置として示す。どの位置も同じ循環で大きくなるので、位置ごとに報告すると同じ原因の誤りが重なるためである。ほかの成分で同じクラスについて示した位置は重ねて示さない。同じ instance の頭で、別の型変数が別のクラスの制約を持って別の成分で大きくなるときは、成分ごとに報告する。報告の順は、成分の最初の位置の順で、同じ位置なら成分の番号 (強連結成分を求めた順) の順である
- 入れ子のデータ型に `deriving Show` を付けた形 (`data Nested a = | Flat a | Nest (Nested (a, a)) deriving Show`) は、5. の辺の自己ループが大きくなる辺なので、E2012 になる

### 位置

- `extern` 命令は、呼ばれる側の位置 (`Loc`) を持てる。位置は、呼ばれる側の範囲の先頭 (演算子のトークンか extern の名前) である。値として使う extern は、参照した場所の位置を包む関数の `extern` 命令が持つ
- `Loc` は、ファイル、行、列を持つ。ファイルは `Program.files` (表示用のパスの表) の添字で、行と列は1から数える。列は行の中の文字の位置である
- 位置を持つのは `extern` 命令だけである。実行時エラーの表示に使う (下の「実行時エラー」)

## パス

型付き HIR から、実行する Core IR までを、次のパスの順に作る。

| パス | 受け取る IR | 渡す IR |
|---|---|---|
| 変換 (`translate`) | 誤りのない型付き HIR | ブロックの列。末尾呼び出し、`box` と `unbox`、RC の命令、`saved`、基本操作、`clause` はない |
| evidence passing (`evidence`) | translate の出力 | `handle`、`perform`、`resume`、`mask` のない IR。基本操作、`clause`、EP が作る関数を含む |
| box の挿入 (`boxing`) | エフェクトの命令、末尾呼び出し、`box` と `unbox`、RC の命令のない IR | 位置の規則を満たす IR。一様にした関数と `f$boxed` を含む |
| 縮約 (`contract`) | RC の命令のない IR | 使われない純粋な `let` を消し、末尾呼び出しを作った IR |
| Perceus | RC の命令のない IR | `dup` / `decref` / `release` と `saved` が入った IR |

- パイプラインは、変換、verifier (変換の段)、EP、verifier (EP の段)、box の挿入、verifier (範囲の段)、縮約、verifier (範囲の段)、Perceus、verifier (所有の段) の順に流す。verifier はデバッグビルドだけでかけ、誤りはパスの名前を付けて報告する
- `Pass` は `Translate`、`Evidence`、`Boxing`、`Contract`、`Perceus` の5つである。`lower_until` は指定したパスの直後で止まるので、テストは各パスの直後の IR を見られる
- どのパスの後でも、ブロックの列は上の「構造の規則」を満たす。パスの間で古くなる索引やキャッシュは IR に持たせない
- 今あるパスは、EP、box の挿入、縮約、Perceus の `dup` / `decref` / `release` の挿入である。reuse analysis と借用パラメータの最適化は後で追加する ([ロードマップ](../future/roadmap.md))
- 再帰の深さ: パス、verifier、テキストの表示と読み込み、インタプリタ、`Drop`、`Clone`、`Debug` のどれも、プログラムの大きさに比例して Rust のスタックを使わない。残るのは、変換が HIR の式の入れ子をたどる分 (E0013 が抑える) と、決定木のパターンの大きさの分 ([実装の現在地](../implementation/status.md) の「深さと性能」) だけである

### evidence passing

エフェクトの操作と handler を、Core IR から Core IR への evidence passing (EP) の変換で実装する。Xie と Leijen の generalized evidence passing (MSR-TR-2021-5。Koka の C バックエンドの方式) を基にする。先行の evidence passing translation (ICFP 2020) は、継続を捕まえたときと同じ handler の文脈でしか再開できないが、この方式はその制限を持たないので、第一級の `k` をそのまま扱える。スタックを切り替えて handler を探す方式 (OCaml 5) は採らない。`multi` の継続にスタックの複写が要り、出力先にスタックを切り替える仕組みが要るためである。変換の後の IR は、普通の呼び出しと分岐、節の呼び出し、決まった表の基本操作だけになる。S8 の LIR、S10 の VM、後のネイティブ化は、`handle`、`perform`、`resume`、`mask` を持たない入力を受け取る。

- EP は translate と box の挿入の間に置く。型は読まない。読むのは、関数の `yields` と `clause` の印、`apply` の印、操作の表、Core IR の形と生存解析だけである
- EP は `tail`、`box`、`unbox`、RC の命令を出さない。後のパスの置き場所の規則 (下の「box の挿入」の最後の項目) のとおりである
- 書き換えるのは、translate が作った関数のうち、`yields` の関数と、`handle`、`perform`、`resume`、`mask` を含む関数である。`yields` でない関数も、row が純粋なまま handle を含むことがある (handle の本体は yield する)。どれにも当たらない関数は変えない
- EP が作る関数 (補助の関数、継続の関数、合流のブロックの関数、入口の関数) は、作るときに最終の形 (yield の確認と遅い道を置いた形) で作り、もう一度は書き換えない
- evidence は実行時にエフェクトの番号で探す (下の「evidence を探す」)。閉じた row の静的な添字と、閉じた row の関数を広い row の文脈から呼ぶときにベクタを合わせる包み (Koka の open) は作らない。トップレベルの関数の row はすべて閉じているので、handler の下での呼び出しの多くが包みを通り、包みは部分ベクタを確保して末尾呼び出しも失うためである。動的に探す費用は handler の数に比例する数命令である

#### 実行の文脈

インタプリタの機械は、次の2つを持つ。後の VM とネイティブでは、これを実行の単位ごとに持つ。S13 の協調的な `par` でタスクを切り替えるなら、タスクごとに持つか、切り替えで退避する。

- `evv`: 今有効な evidence の並び。内側の handler を先頭にした永続リストで、書き換えない。handler を設けるたびに、先頭に足した新しいリストを作る。空のリストは `()` である
- yield の状態: なし、yield 中、中断中のどれか。yield 中と中断中は、宛先の evidence、節の本体のクロージャ、組み立て中の継続 κ を持つ

`evv` を関数の引数で渡す形は採らない。関数の値の呼び出しの規約が「yield しうるか」で分かれ、関数の値として使う関数に evidence の引数を足す一様化が要るためである。`mask` の包みが残すフレームは handler の数で抑えられる (下の「`evv` の不変条件」) ので、文脈に持つ形にした。

#### evidence

evidence は、handler の1回の実行を表すヒープの物体で、次を持つ。

- 入口の表: エフェクトの番号と、操作ごとの in-place の入口のクロージャ (下の「`perform` と節の3つの形」) を持つ物体。handle で入れた後は変えない
- 状態の欄 (`tobj`)
- 外側の `evv`: その実行の外側で有効な `evv`。作るときに決め、変えない。その evidence 自身を含まない

handle の実行と、継続の再開のたびに、新しい evidence を作る。入口の表は handle のときに1つ作り、再開で作る evidence はその表を共有し、状態と外側の `evv` だけを新しくするので、作る費用は操作の数によらない。yield の宛先は evidence の物体そのもので比べるので、目印の番号は持たない。

状態の欄だけは書き換える。書き換えるのは、その evidence の実行が動いている間の、in-place の節 (`ev_take_state`、`ev_set_state`) と `prompt$` (状態の取り出し) だけである。別の実行は別の evidence を持つので、欄を共有しない。handle 1回につき evidence を1つにして状態を yield と再開で出し入れする形は採らない。handler の実行中にその handler 自身の継続を再開すると (下の「再開と状態」の例)、2つの実行が状態の欄と外側の `evv` の欄を共有して壊し、外側の `evv` がその evidence 自身を指す参照の輪もできるためである。

状態の欄を通る参照の輪は、一時的にはできうる。外側の handler O の本体の中で内側の handler I を動かし、I の継続 `k_I` をデータに包んで O の状態に入れると、`evO.状態 → k_I → evI → evI.外側の evv → evO` の輪になる。`prompt$` は、どの出口 (下の「handle と `prompt$`」の 0〜3) でも状態の欄を空にするので、O の実行が終われば輪は切れる。これを不変条件とし、`debug_heap` 付きの UI テスト (`tests/ui/run/effects/continuation_in_outer_state.em`) で確かめる。

#### evidence を探す

- `ev_lookup[E]` は、`evv` を先頭からたどり、エフェクトの番号が E の最初の evidence を返す。費用は今有効な handler の数に比例し、呼び出しの深さにはよらない
- `evv_mask[effects](w)` は、`effects` の多重集合の各エフェクトについて、w の先頭から合う evidence をその数だけ除いたリストを作る。除く位置までの節点を写し、残りは共有する。evidence の物体は写さない
- `evv` は書き換えないので、探す場所ごとのキャッシュを後で足せる ([ロードマップ](../future/roadmap.md) の「処理系」)

#### 基本操作

右辺 `Rhs::Prim(Prim, Vec<Atom>)` は基本操作である。`Prim` は基本操作の種類と、その即値 (エフェクトの番号、操作、エフェクトの多重集合) を持つ。テキストの形は `prim ev_lookup[State]()`、`prim ev_clause[State.get](ev.2)`、`prim evv_mask[State, State](w.3)` のように、即値を `[…]` に書く。

- 引数と結果の Repr は、次の表で決まる。引数と結果は、直接の呼び出しの引数と結果と同じく互換の位置で、合わなければ box の挿入が変換を入れる。状態とクロージャの引数には、translate が決めた Repr の値 (`State Int` の状態なら `int`、状態のない handler なら `()`) が来るためである
- 引数はすべて消費し、結果は所有した参照である (extern の行と同じ)
- 表は `eml_core_ir` に置き (`Prim::row`)、`eml_extern` には入れない。`eml_extern` の表は `std/` と1対1に結び付けるテストを持ち、基本操作はソースに現れないためである
- 基本操作は純粋でないとみなし、縮約は消さない

| 基本操作 | 引数 | 結果 | 動作 |
|---|---|---|---|
| `evv_get` | なし | `tobj` | 今の `evv` |
| `evv_set` | `tobj` | `unit` | `evv` を替える。元の `evv` は手放す |
| `evv_push` | `tobj`、`obj` | `tobj` | リストの先頭に evidence を足す |
| `evv_mask[effects]` | `tobj` | `tobj` | 上の「evidence を探す」 |
| `ev_new[E]` | `tobj` (状態)、`tobj` (外側の `evv`) | `obj` | 新しい入口の表 (欄は空) と、それを指す新しい evidence |
| `ev_set_clause[E.op]` | `obj`、`tobj` | `unit` | 入口の表の欄に入れる。handle の場所だけが、本体を始める前に使う |
| `ev_renew` | `obj`、`tobj` (状態) | `obj` | 元の evidence と同じ入口の表を指し、状態を引数に、外側の `evv` を今の `evv` にした新しい evidence |
| `ev_lookup[E]` | なし | `obj` | 上の「evidence を探す」 |
| `ev_clause[E.op]` | `obj` | `tobj` | 入口の欄を読む |
| `ev_evv` | `obj` | `tobj` | 外側の `evv` を読む |
| `ev_take_state` | `obj` | `tobj` | 状態を取り出し、欄を `()` にする |
| `ev_set_state` | `obj`、`tobj` | `unit` | 状態の欄を替える |
| `yielding` | なし | `int` | yield 中か中断中なら 1、そうでなければ 0 |
| `yield_status` | `obj` | `int` | 0: yield していない、1: この evidence 宛ての yield、2: この evidence 宛ての中断、3: ほかの宛先の yield か中断 |
| `yield_to` | `obj`、`tobj` (節の本体)、`tobj` (最初の κ) | `unit` | yield を始める |
| `yield_abort` | `obj`、`tobj`、`tobj` | `unit` | 中断を始める |
| `yield_cont_take` | なし | `tobj` | κ を取り出す (欄は空になる) |
| `yield_cont_set` | `tobj` | `unit` | κ を入れる |
| `yield_finish` | なし | `tobj` | 節の本体を取り出し、宛先の evidence への参照を手放し、yield の状態をなしに戻す |
| `dummy` | なし | `obj` | ダミーの物体 (下の「ダミーの値」) |

- `ev_set_clause` と `ev_clause` の即値は、操作をエフェクトで修飾して書く (`ev_clause[State.get]`)。テキストの形で操作の名前をエフェクトで修飾するためである
- `yielding` と `yield_status` の結果を `int` にするのは、リテラルの `switch` で分けるためである。`Bool` で分けると、EP が配置の表に `Prelude.Bool` を足すことになり、translate の後のパスは配置の表を変えないという規則 (上の「データの配置」) を崩す

#### 節の呼び出し

- `Call::Clause { effect, op, callee, args }` は、操作の ABI を知っている呼び出しである。テキストの形は `clause State.get c.3(ev.2, ())` である
- `callee` は in-place の入口のクロージャ、`args` の先頭は evidence (`obj`)、残りは操作の引数である。引数と結果の Repr は、操作の表の `params` と `ret` から取る (上の「エフェクトの位置」)
- インタプリタでは `apply` と同じに動く。VM とネイティブでは、操作の ABI を知っている間接呼び出しになる。S8 では、LIR の操作の ABI を持つ間接呼び出しにそのまま写す
- `mask` は持たない
- 操作の Repr を `perform` の境界に通すために、この呼び出しを足した。box の挿入、T3、縮約、verifier にその規則がある。Perceus には規則を足さない

#### 入口の関数の印

- 関数 (`CoreFn::clause`) は、in-place の入口の関数にだけ `(effect, op)` の印を持つ。テキストの形では `internal yields clause State.get fn …` と書く
- 入口の関数は、捕獲の後に evidence と操作の引数を受け、操作の結果を返す。`ev_set_clause` に渡す値としてだけ参照され、`apply` でも直接の呼び出しでも呼ばれない

#### EP が作る補助の関数

EP は、使うときだけ次の関数をプログラムに1つずつ足す。どれも `yields` の印を立て、`internal` にしない。多くの定義から直接呼ばれるためで、導出の生成器が作る関数を `internal` にしないのと同じ理由である。`internal` の関数を直接呼ぶのはそれを作った定義の中だけ、という規則 (上の「一様な関数」) を保つ。evidence を受ける引数は `obj`、ほかの引数と `ret` は `tobj` で、どれも一様である。

| 関数 | 引数 | 本体 |
|---|---|---|
| `id$` | `x` | `return x` |
| `compose$` | `κ`、`c`、`x` | `r = apply κ(x)`。yield 中なら、取り出した κ' と c で `compose$(κ', c)` を κ にしてダミーを返す。そうでなければ `apply c(r)` を末尾で呼ぶ |
| `prompt$` | `ev`、`ret`、`x` | 下の「handle と `prompt$`」 |
| `resume$` | `ev`、`ret`、`κ`、`v`、`s` | 下の「再開と状態」 |
| `rewind$` | `ev`、`ret`、`s`、`κ`、`v` | `resume$(ev, ret, κ, v, s)` を末尾で呼ぶ |
| `mask$[effects]` | `κ`、`v` | 下の「`mask` の包み」。`effects` の多重集合ごとに1つ作り、名前に多重集合を書く (`mask$[State]`) |

補助の関数の中の `apply` (κ、c、`ret`、節の本体を呼ぶもの) は、どれも印を立てる。

#### yield の地点

- `yields` の関数の中で、末尾でない次の呼び出しを yield の地点とする
  - `yields` の関数への直接の呼び出し (EP が作る関数を含む)
  - 印の立った `apply`
  - `Call::Clause`
- 末尾の位置の呼び出し (上の「変換の規則」と同じ、形だけで決まる定義) は、yield の地点にしない。呼ばれた側の yield は、そのまま呼び出し元へ返るためである。末尾の位置の `never` の操作の `clause` も yield の地点にせず、縮約が `tail clause` にする
- yield の地点 `let x = <呼び出し>` の直後でブロックを切り、次の形にする

  ```
    let x = call g(a)
    let y: int = prim yielding()
    switch y { 0 -> b_fast, _ -> b_slow }
  b_slow:
    let k0: tobj = prim yield_cont_take()
    let c: tobj = closure f$k1(v1, .., vn)
    let k1: tobj = closure compose$(k0, c)
    let u: unit = prim yield_cont_set(k1)
    return <ダミー>
  b_fast:
    (元のブロックの残り)
  ```

  生きている変数がなければ、`c` は `&f$k1` である
- ブロックを切ると番号が変わるので、EP は関数ごとにブロックを番号の順に作り直し、構造の規則 R1〜R6 を保つ
- 「yield 中か」の確認は、呼び出しごとに文脈の旗を1回読む

#### ダミーの値

- yield 中に返す値は、呼び出し元が使わずに捨てる
- 関数の `ret` が `obj` か `tobj` なら `prim dummy()` の値を、`int` なら `0` を、`enum` なら `#0` を、`unit` なら `()` を返す。`tobj` にも物体を使うのは、互換の位置を通って `obj` の変数に入ることがあるためである (`ret` が `tobj` の関数の結果を `obj` の変数で受ける形)
- ダミーは、変換と RC の命令に当たる。Perceus は遅い道で死ぬ x に `decref` を置き、box の挿入は呼び出しの結果を受け直す `unbox` と `box` を呼び出しの直後 (yield の確認の前) に置く。box の挿入が足す `f$boxed` は yield の確認を持たないので、`f` が返したダミーを `box` してから返す (`never` の操作で失敗する関数を値として使う形)。そのため、実行時は次を守る。S9 の `eml_rt` も同じ約束を守る
  - `dummy` の値は、`dup` と `decref` で何も起こさない
  - `unbox` は、ダミーを受けても誤りにせず、何かの値を返す。その値は捨てられる
  - `box` は、ダミーを受けたらダミーを返す。`0` と `#0` は普通に箱に入れ、その値は捨てられる
- box の挿入が、yield の地点の結果の変換を確認の後に置く形は採らない。box の挿入に EP の形を知る特別な規則が要るためである

#### yield の確認のない呼び出しの後

- 末尾の位置の呼び出しは yield の確認を持たない。box の挿入の後でも、結果の変換が要る呼び出しは `tail` にならず、呼び出しの後に変換が残る (`f$boxed`、`ret` が `tobj` の関数から `ret` が `int` の関数への呼び出し、`ret` が `tobj` の関数の中のスカラーの `clause`)。yield 中はこの変換がダミーに当たったまま呼び出し元へ返り、κ には入らない
- これが正しいのは、次の2つが成り立つためである。この2つを不変条件とする。後で借用パラメータの降格 (`let r = call g(y)`、`decref y`、`return r`) を入れるときも、この不変条件を保つ
  - yield の確認のない呼び出しの後には、変換 (T3 の後では `box` だけ) と RC の命令と `return` しか続かない
  - κ に入るフレームの関数 (`f$kN`、`compose$` などの補助の関数) は一様なので、再開で届く値はすでに `tobj` で、飛ばした `box` は要らない
- 後で T3 が `ret` を上げても、box の挿入がほかの `return` と同じく変換を入れる

#### 継続の関数

- yield の地点 p ごとに、関数 `f$kN` を1つ作る。N は f の中の yield の地点の通し番号で、ブロックと文の順に振る
  - 引数は、p の後で生きている変数 (x を除き、変数の番号の順) と、x である。`ret` は f の `ret` と同じである
  - 印は `internal` と `yields` である
- 本体は、p の直後からの区間の写しである。区間は p の直後から辺をたどり、次のどちらかに当たる所で止める
  - 次の yield の地点 q: 呼び出しと確認を同じ形で置く。遅い道は `f$kq` を κ に足して返し、速い道は `let r = call f$kq(..)` と `return r` にする。後で縮約が `tail` にするので、継続の関数どうしの速い道はフレームを積まない
  - 合流のブロック J (`jump` で入るブロック): 区間の中の `jump bJ(args)` を、`let r = call f$jJ(..)` と `return r` にする。`f$jJ` の引数は、J の入口で生きている変数 (J の引数を除き、変数の番号の順) と J の引数で、`ret` は f と同じである。`f$jJ` は、区間から届く J についてだけ作る
- 区間の根は yield の地点と合流のブロックである。根でないブロック (`switch` の行き先) は入る辺が1本なので、各ブロックは元の関数と、多くとも1つの区間にしか写されない。そのため、写す文の数は元の約2倍に収まる。これとは別に、遅い道が生きている変数を捕獲する。その大きさは yield の地点ごとの生きている変数の数の和で、yield しうる要素を n 個並べたリストのリテラルのような形では n の2乗になる。根ごとに続きを最後まで写す形では、写す文の数そのものが yield の地点の数と関数の大きさの積になる
- 元の関数 f は、速い道をそのまま続けるので、yield の地点の確認と遅い道を足すだけである。論文の bind-inlining は f の速い道に、join-point sharing は `f$jJ` に当たる
- 生きている変数は、生存解析 (下の「生存解析」) で求める。`int` と `enum` の捕獲は、ほかのクロージャと同じく box の挿入が `box` する
- `f$kN` は値として参照され、直接も呼ばれるので、box の挿入の規則で `f$kN$boxed` が足されることがある

#### 継続の組み立て

- κ は、いつも普通のクロージャである。yield を始めるとき、κ は `&id$` である
- 普通のフレームは、上のとおり `compose$(κ, c)` で κ を作り直す。κ を先に呼び、その結果で c を呼ぶ
- 包むフレーム (`prompt$` と `mask` の包み) は、κ を最後の捕獲に持つクロージャ (`rewind$`、`mask$`) で κ を作り直す。再開されると、包むフレームが `evv` を整えてから κ を呼ぶ
- 再開は `apply κ(v)` で、内側のフレームの続きから順に動き、値は外側へ返る
- `once` の継続は `Lin` の値を持ってよく、`multi` の継続は持ち越し規則で `Unr` の値だけを持つ。共有されたクロージャへの `apply` は中身を写すので (上の「一様な関数」)、`multi` の継続を2回再開しても写すのは捕獲だけである

#### handle と `prompt$`

translate の `let r = handle E(init, body) { c_0, .., c_n } return ret` を、次の形にする。

```
  let w0 = prim evv_get()
  let ev = prim ev_new[E](init, w0)
  (操作ごとに) let u_i = prim ev_set_clause[E.op_i](ev, <i 番目の in-place の入口>)
  let w1 = prim evv_push(w0, ev)
  let u = prim evv_set(w1)
  let x = yields apply body(())
  let r = call prompt$(ev, ret, x)
```

- `w0` と `ev` は2回以上使うので、Perceus が `dup` を足す
- `apply body(())` は yield の地点にしない。yield したかは `prompt$` が見る。`call prompt$` は、handle を含む関数が `yields` なら yield の地点である (その関数が `yields` でなければ、その row から外へ出る yield はない)
- `prompt$(ev, ret, x)` は、最初に `evv` を `ev` の外側の `evv` に戻し、`yield_status(ev)` で4つに分ける
  - 0 (yield していない): `st = ev_take_state(ev)` で状態を取り出し、`apply ret(x, st)` を末尾で呼ぶ
  - 1 (`ev` 宛ての yield): `κ = yield_cont_take()`、`c = yield_finish()`、`st = ev_take_state(ev)` を得て、`k = closure resume$(ev, ret, κ)` を作り、`apply c(k, st)` を末尾で呼ぶ
  - 2 (`ev` 宛ての中断): κ を取り出して `drop κ` し、`c = yield_finish()` と状態を得て、`apply c(st)` を末尾で呼ぶ
  - 3 (ほかの宛先): 状態を `ev_take_state(ev)` で取り出し、κ を `rewind$(ev, ret, st, κ)` のクロージャで作り直して、ダミーを返す

#### 再開と状態

- `resume$(ev, ret, κ, v, s)` は、`ev2 = ev_renew(ev, s)` で新しい evidence を作り、今の `evv` の先頭に `ev2` を足して `evv` にする。その後 `x = apply κ(v)` を呼び、`prompt$(ev2, ret, x)` を末尾で呼ぶ。deep handler の再接続と、スコープの外での再開に当たる。`ev2` の外側の `evv` は再開した時点の `evv` なので、handle が返った後の再開も、ほかの handler の中での再開も、その場の文脈の上につながる
- `rewind$` は、外側のフレームの yield で handler の外へ出たときに `prompt$` が取り出した状態で、`resume$` を呼ぶ
- 再開した計算の中の操作は、`ev_lookup` で `ev2` を見つける。古い `ev` を持ったまま止まっているフレームはない。`ev` を持つのは、`prompt$` (止まるときは `rewind$` が `ev` の写す部分だけを使う)、`resume$` のクロージャ (同じ)、yield を始める入口 (止まらない)、in-place の節 (本体に yield の地点がないので止まらない) だけだからである
- handler の実行中にその handler 自身の継続を再開する形も、deep handler の意味 ([エフェクトと handler](effects.md) の「handler の意味」) のとおりに動く。次のプログラムでは、`k r 100` の再開が状態 100 の新しい evidence を作り、外側の実行の evidence (状態 1) は変わらないので、101 を表示する (`tests/ui/run/effects/resume_inside_own_handler.em`)

  ```haskell
  data Re = | Re (Re -> Int -> Int)

  effect G where
    multi grab : Unit -> Re
    get : Unit -> Int
    put : Int -> Unit

  body : Unit -> <G> Int
  body () =
    let r = grab ()
    let n = get ()
    if n == 0 then
      put 1
      match r with
        | Re k -> let inner = k r 100 in inner + get ()
    else n

  run : Unit -> Int
  run () =
    handle body () from 0 with
      | grab () k st -> k (Re k) st
      | get () k st -> k st st
      | put n k _ -> k () n
      | return x _ -> x
  ```

- translate の `Call::Resume { k, v, s }` は `apply k(v, s)` にする。`k` は `resume$` のクロージャ (直接の形) か、`cont$` と `cont$state` のクロージャ (包む形) である。`resume` の `mask` は下の「`mask` の包み」の形にする
- `drop k` は、そのままクロージャの破棄になる。継続のクロージャが捕まえていた値は、解放の連鎖で1回ずつ解放される

#### `perform` と節の3つの形

translate の `let r = perform E.op(a_1, .., a_n)` を、次の形にする。末尾でなければ `Call::Clause` が yield の地点になる。

```
  let ev = prim ev_lookup[E]()
  let c = prim ev_clause[E.op](ev)
  let r = clause E.op c(ev, a_1, .., a_n)
```

in-place の入口は、translate が作った節の関数 g から、EP が節ごとに作る。節は次の3つの形に分かれ、EP は Core IR の形から決める。

- **すぐに再開する節**: 次をすべて満たす節である
  - `never` の操作の節でない
  - g の `k` の引数の使いが、末尾の位置の `mask` のない `resume k(v, s)` だけである
  - g のすべての `return` が、そのような `resume` の結果を返す
  - g の本体に、yield の地点になる呼び出しがない。EP は translate の出力の上でこれを決めるので、translate の命令で書くと次のどれもないことである: 末尾でない `perform`、g が `yields` のときの `handle`、`mask` 付きの呼び出し、最後の末尾の `resume` のほかの `resume`、`yields` の関数への末尾でない直接の呼び出し、印の立った末尾でない `apply`

  入口の関数 `g$entry` (`clause` の印) は g の写しである。引数は、捕獲、evidence `ev`、操作の引数の順にし、g の `k` と状態の引数を除く。状態は入口の先頭の `ev_take_state(ev)` で得る。末尾の `let r = resume k(v, s)` と `return r` を、`ev_set_state(ev, s)` と `return v` に替える。`yields` の印は g の印を写す。g は使われなくなるので消す

  本体は yield しないので、`evv` を替えずに `perform` の場所の `evv` のまま動かしてよい。g が `yields` でないときは、本体に `handle` や `mask` 付きの呼び出しが残りうるが、それらが呼ぶ関数は yield しない。健全性の不変条件 ([エフェクトと handler](effects.md) の「健全性」) から、その中の操作はその中で設けた handler に届くので、外側の `evv` の違いは見えない
- **再開する節** (`once` と `multi` の操作のうち、上に当たらない節): 入口の関数は、捕獲、`ev`、操作の引数を受け、`c = closure g(捕獲, 操作の引数)` を作り、`yield_to(ev, c, &id$)` を呼んで、ダミーを返す。入口はいつも yield を始めるので、g の印によらず `yields` の印を立てる。`prompt$` が後で `apply c(k, st)` を呼ぶ。外のエフェクトを呼ぶすぐに再開する節もここに入り、節の本体は handle の外側の `evv` で動く。節の実行中に `evv` を外側に替える包み (論文の under) は作らない。再開で evidence を作り直すと、包みと節の本体が古い evidence を持ち続けるので、探し直す仕組みも要るためである
- **`never` の節**: 入口は同じ形で `yield_abort(ev, c, &id$)` を呼び、`yields` の印を立てる。`prompt$` が後で `apply c(st)` を呼ぶ。入口の `ret` は `obj` で、`prim dummy()` を返す。`never` の操作の `clause` の束縛は、`OpRet::Never` なので位置と比べない。その値はダミーで、上の「ダミーの値」の約束で安全である
- handle の場所では、節の値 c_i がどの関数のクロージャかを知る必要がある。translate は節を `&g` か、同じ関数の中の `closure g(..)` で渡すので、EP はそれを読む。そうでない形は内部の誤りとしてパニックする
- `ev_set_clause` には、入口の関数のクロージャ (捕獲がなければ関数の値) を渡す。捕獲は節の捕獲をそのまま写す。再開する節と `never` の節の入口が作る c も、捕獲も操作の引数もなければ `&g` にする (`closure` は引数を1つ以上とる)

#### `never` の中断

- 中断の yield も、途中のフレームが普通の yield と同じく κ を組み立てる。`prompt$` が κ を `drop` すると、クロージャの解放の連鎖で、捕まっていた値が1回ずつ解放される。`File` はこの解放で閉じる
- 途中のフレームは、生きている `Lin` の値に `decref` を置かない。生きている値は継続のクロージャに捕まるためである。遅い道で `decref` されるのは、yield の地点の結果 x (ダミー) だけである ([ロードマップ](../future/roadmap.md) の「S8 LIR」)
- 中断の経路に `drop` の命令を生成する形は採らない。Core IR は Kind を持たないので、`Lin` の値を `decref` で解放することになり、S8 の V1 と合わないためである

#### `mask` の包み

translate の `mask` 付きの呼び出し (直接の呼び出し、`apply`、`resume` から作った `apply`) を、次の形にする。

```
  let w0 = prim evv_get()
  let w1 = prim evv_mask[effects](w0)
  let u = prim evv_set(w1)
  let x = <mask を外した呼び出し>
  let y: int = prim yielding()
  switch y { 0 -> b_fast, _ -> b_slow }
b_slow:
  (κ を mask$[effects](κ) で包み、その上で f$kN を compose$ で足して、ダミーを返す)
b_fast:
  let u2 = prim evv_set(w0)
  (元のブロックの残り)
```

- 遅い道は、κ を `compose$(mask$[effects](κ), f$kN)` にする。`mask$` が内側のフレームの再開のときに `evv` を整え、`f$kN` が f の残りを続ける
- `f$kN` の区間は、`evv_set(w0)` の後から始まる。`w0` は区間で生きていないので捕獲しない。再開した後の `evv` は、外側の包むフレームが作り直した `evv` で、`mask$` が戻るときにそれへ戻すので、f の残りはその `evv` で動く
- `mask$[effects](κ, v)` は、再開されたとき、`w = evv_get()` を得て、`evv` を `evv_mask[effects](w)` にし、`r = apply κ(v)` を呼ぶ。yield していなければ `evv` を `w` に戻して r を返す。yield 中なら、もう一度 `mask$` で包んでダミーを返す
- `mask` のラベルは今の row の handle できるラベルなので、`mask` を持つ関数はいつも `yields` である
- `mask` 付きの末尾の位置の呼び出しの後には `evv_set(w0)` が続くので、末尾呼び出しにならない

#### `evv` の不変条件

- 呼び出しが普通に返ったとき、`evv` は呼び出しの前と同じである。`evv` を替える所 (handle の `prompt$`、`resume$`、`mask` の包み) が、戻るときに必ず元に戻すためである
- yield 中の `evv` には意味がない。再開のときに、包むフレームが外側から順に `evv` を作り直す
- `mask` 付きの呼び出しは、戻りで `evv` を戻すのでフレームを残す。`mask` は見える別々の handler を飛ばすので、継続の上で `mask` が残すフレームは handler の数以下である ([エフェクトと handler](effects.md) の「健全性」の最後の段落)。`prompt$` と `resume$` のフレームは、handler 1つにつき1つである
- そのため、末尾呼び出しの保証 (上の「変換の規則」) は、`mask` 付きの呼び出しを除いて保てる
- 実行が正しく終わったとき、`evv` は空で、yield の状態はなしである。インタプリタはこれを `debug_heap` のリークの検査の前に確かめる

### box の挿入

- box の挿入 (`boxing`) は、プログラム全体を1回で扱う。関数の ABI (T3、一様化、`f$boxed`) を決めてから、位置の規則 (上の「位置の規則」) に合わない値に `box` と `unbox` を入れる
- 型は読まない。読むのは、呼ばれる関数のシグネチャ、内部の印と `clause` の印、配置の表、extern の行、操作の表の `params` と `ret`、基本操作の表だけである
- 入力はエフェクトの命令を持たない (EP の段の verifier が確かめる)。`clause` は操作の表の `params` と `ret` を相手に、`prim` は基本操作の表を相手に、直接の呼び出しと同じく変換を入れる。`clause` の先頭の evidence は `obj` である
- translate が変換を入れる形にしないのは、translate が関数ごとに働くためである。値の参照で決まる一様化と T3 のような、プログラム全体で決まる ABI を、translate は決められない
- 縮約の前に置くので、パスは変換を位置ごとに素朴に入れればよい。使われなくなった `box` と `unbox` は、縮約がほかの使われない純粋な `let` と一緒に消す
- 手順は次の順である
  1. 分類: 各関数について、値として参照されるか (どこかの `&f`、`closure f` の対象) と、直接呼ばれるか (`call f`) を記録する。入力に `tail`、`box`、`unbox`、RC の命令はない (EP の段の verifier が拒む)
  2. T3: 関数の数と末尾の辺の数に比例する時間で、`ret` を上げる。各関数の末尾の位置の呼び出しを集め、直接の呼び出し f → g は、g の逆の表に f を入れる。`never` の操作の `clause` は集めない。`ret` が箱を要するスカラーで、結果が互換でない末尾の位置の呼び出しを持つ関数を上げ、作業の列に積む。列から g を取り出し、逆の表の各 f について、f の `ret` が箱を要するスカラーなら上げて積む。`ret` はスカラーから `tobj` へ1回だけ動くので、各関数は多くとも1回積まれ、各辺は1回だけ見る
  3. 一様化: 値として参照され、T3 の後でも一様でない関数のうち、直接呼ばれない内部の関数はその場で一様にし、ほかの関数には `f$boxed` を足す (上の「位置の規則」)。`f$boxed` は、関数の表の末尾に、元の関数の番号の順に足す。名前は、関数の Core IR の名前に `$boxed` を付けたものである。Core IR の名前は、修飾を含み、instance では `inc@[Unit]` のような instance の名前である (instance の名前は「変換の規則」で定める)。その後、すべての関数の `&f` と `closure f` を `f$boxed` に向け直す。`clause` の印の関数は一様化の対象から外し、操作の ABI に合わせる。捕獲は `tobj` と互換、evidence は `obj`、残りの引数と `ret` は操作の表の Repr (`never` の操作の `ret` は `obj`) である。合わない引数は、その場で一様にする手順と同じく、入口で `unbox` (または `box`) を置いて受け直す。`ret` が合わなければ、`return` で変換する
  4. 変換: 関数ごとに、ブロックを番号の順に、文を前から見て、各アトムを位置の Repr にする。extern の引数と結果は正確な位置で、translate の出力ですでに合うので、何も入れない。`jump` と `return` も translate の出力では Repr が同じなので、変換が要るのは `ret` を変えた関数の `return` だけである
     - 互換でないアトムは、箱を要するスカラーから `tobj` へは `let b = box a` を、`tobj` から箱を要するスカラーへは `let v = unbox a` を、使う文の前に置いて渡す。下の覗き穴を先に試す
     - 束縛の位置 (直接の呼び出し、`apply`、`clause`、`prim` の結果、`unpack` と case のフィールド) で、受け取る Repr と変数の Repr が互換でなければ、受け取る Repr の新しい変数で受ける。元の変数は、その直後で `unbox` か `box` で定義する。case のフィールドなら、その定義を行き先のブロックの先頭に置く。R3 から行き先へ入る辺はその `switch` の1本だけなので、定義は使いをすべて支配する。`never` の操作の `clause` の束縛は受け直さず、その束縛を使う所にも変換を入れない (上の「`never` の操作」)。呼び出しの結果を受け直す `unbox` と `box` は、呼び出しの直後 (EP の yield の確認の前) に置く。yield 中はダミーに当たる (上の「ダミーの値」)
     - 使う所の変数は書き換えないので、R5 と R6 はそのまま成り立つ
     - 新しい変数は、元の変数の名前に、変数の表の末尾の番号を付けたものにする (`x.5: tobj`)。`Int` の定数を `box` した変数は `b`、`f$boxed` の結果の変数は `t` とする。その場で一様にした関数の新しい引数と `f$boxed` の引数も、元の引数の名前を使う
  5. 型から起きない変換に当たったら、パスはパニックする。箱を要するスカラーと `obj` の間 (どちら向きも)、違う Repr のスカラーどうし、`unit` と箱を要するスカラーの間である。translate の出力では起きないので、内部の誤りである
- 覗き穴: 変換を作る代わりに、定義をさかのぼって元の値を渡す
  - 箱を要するスカラーの変数 v を `tobj` の位置へ渡すとき、v が `let v = unbox w` で定義されていれば、`box` を作らずに w を渡す
  - `tobj` の変数 v を Repr が s のスカラーの位置へ渡すとき、v が `let v = box w` で定義され、w の Repr が s なら、`unbox` を作らずに w を渡す
  - 表は、パスが作る定義 (受け直しの `unbox` と `box`、その場で一様にした関数の入口の `unbox`) からだけ作る。w は v の定義より前で定義されるので、v の使いをすべて支配し、R6 を保つ。使う所で作った変換は、使う所がほかの使いを支配しないので、同じ変数のほかの使いで使い回さない
  - 覗き穴がないと、恒等に近い一様な関数 (`main$lambda3(m) = m`、handler の `return` の節、`cont$` の転送) が値を往復させ、末尾呼び出しも失う。覗き穴があれば `return r'` になり、縮約が使われない `unbox` を消して `tail` を作る。Perceus から見ると、w の寿命が延びるだけである
- translate の転送が box の挿入より前にあるので、`return` だけの合流のブロックへ入る枝は、それぞれの `return` で `box` する
- パスはブロックと文のループだけで、IR の大きさに比例して再帰しない
- 後のパスの置き場所: 呼び出しを作るか行き先を変えるパス (インライン化、evidence passing など) は、translate と box の挿入の間に置き、`tail` も `box` も `unbox` も出さない。box の挿入がプログラム全体の ABI と変換を1か所で決め、縮約が末尾呼び出しを作るためである。box の挿入より後に置くパスは、位置の規則を保たなければならない

### 縮約

- 使われない純粋な `let` を消す。純粋なのは `const`、`con`、`closure`、`box`、`unbox` と、表の行が `Pure` の `extern` である。呼び出し、`MayFail` と `Effectful` の `extern`、`prim`、`drop` は、使われなくても消さない。基本操作は実行の文脈か evidence を読み書きするので、純粋でないとみなす。使われない `box` を消しても確保が1つ減るだけで、`unbox` は読むだけなので、どちらも評価の順を変えない
- ブロックを後ろから、文を後ろから見る1回のパスで、関数全体の使用の数を使う。定義は使う位置を支配し、辺は番号の大きいブロックへ向かうので、`let` を見る時点でその変数の使用はすべて見終わっている。消した `let` だけが使っていた束縛も同じパスで消えるので、1回で不動点に達する。デバッグビルドでは、2回目のパスが何も変えないことを確かめる
- 末尾呼び出しを作るのは縮約だけである。使われない `let` を消した後で、すべてのブロックに末尾呼び出しの規則を当てる。`let x = <呼び出し>` の直後の終端が `return x` で、呼び出しの結果と関数の `ret` が互換なら、2つを `tail` にする。結果は、直接の呼び出しなら呼ばれる関数の `ret`、`clause` なら操作の表の `ret`、`apply` なら `tobj` で、`never` の操作の `clause` はどの `ret` とも互換とする。文を消したかに関わらずすべてのブロックを1回見るので、時間はブロックの数に比例する
  - 互換の条件は、互換が推移的でないために要る。x を通すと `unit` から `tobj`、`tobj` から `obj` とつながる IR でも、`tail` にすると `unit` と `obj` を直接比べることになる。translate と box の挿入の出力では、この条件はいつも成り立つ。T3 と box の挿入が、互換でない末尾の位置の呼び出しの後に変換を入れているためである
  - 末尾呼び出しを変換を入れた後に作るので、Repr のための降格は要らない
- 縮約は、評価の順も短絡評価も変えない。消すのは実行時に何も起こさない右辺だけである

### 生存解析

- ブロックを後ろからたどる1回のループで、ブロックごとの入口の生存集合を求め、側の表として返す。IR には書かない。後ろからたどれば、行き先の入口の集合はいつも求め終わっている
- `switch` の出口の生存集合は、各 case の (行き先の入口 − case のフィールド) と `default` の行き先の入口の和に、scrutinee を足したものである
- 使いは「消費」と「読む」の両方を数える
- `jump` の出口の生存集合は、(行き先の入口 − 行き先の引数) に、実引数を足したものである
- 生存集合はすべての変数を持つ。Perceus は RC の対象だけを見るが、`saved` は RC の対象でない変数も退避するためである

### Perceus

- ブロックを前からたどり、その場で書き換える。入力は RC の命令を持たない
- EP の出力のための規則は足さない。`prim` は extern と同じく引数をすべて消費し、所有した結果を定義する。`clause` は呼び出しとして退避 (`saved`) を持つ
- 関数の入口と合流するブロックは、(入口の生存集合 − 引数) のうち RC の対象と、RC の対象の引数を所有して始まる
- `switch` と `unpack` は値を読むだけなので、`switch` の行き先は、`switch` の前の所有をそのまま持って始まる。それは、終端の後で生きている RC の対象に scrutinee を足したものである。フィールドは借りて始まり、所有に入らない
- case の行き先の入口と `unpack` の直後では、x を分解した値、F をそこで生きている RC の対象のフィールドとして、次のどれかにする
  - x が死んでいて F がある: F の位置に名前を書いた `release x L #t(..)`。`L #t` は、`unpack` ならその `Ctor` を、case なら `switch` の配置と case のタグを写す。2回以上使うフィールドは、その後でほかの変数と同じく `dup` する
  - x が死んでいて F がない: `decref x`。フィールドのない case、`default`、文字列の `switch` の行き先でも、死んだ scrutinee は `decref` で手放す
  - x が生きている: F の各フィールドを `dup` する
- タグの case を持つのに配置のない `switch` を見たら、Perceus はパニックする。verifier が拒む形なので、黙って飛ばさない
- 行き先の入口での順は、フィールドの `dup`、死んだ所有の `decref` (変数の番号の順)、`release` である。親を先に手放すと入れ子の値の参照が1つになり、`release` が一意の側を通れるためである。変数の番号の順が親から子の順になるのは、translate が束縛の順に番号を振るからである。`unpack` の直後では、`dup`、`release`、`decref x` のどれかをその文のすぐ後に置く
- ブロックの先頭で、所有していて死んでいる変数を `decref` する。各文の後で、その文が定義した RC の対象の変数のうち死んでいるものを `decref` する。そのため、`jump` で渡さない所有は `jump` の前に残らない
- 変数を消費することは所有権の移動である。`dup` が要るかは消費の数だけで決め、後でも使う変数は、消費する前に `dup` する。読む使い (`switch` の scrutinee、`unpack` の値、`unbox` のオペランド) は所有権を動かさないので、`dup` を要さない
- `let x = unbox w` の後で、w がこの時点で所有している RC の対象で、この文の後で死んでいれば、文の直後に `decref w` を置く。`unpack` の直後の規則の、読む使いの版である。w がこの後も生きていれば何も置かない
  - 生きている RC の対象は、フィールドも含めてこの時点で所有になっている (フィールドは case の行き先の入口か `unpack` の直後で所有になる)。そのため、この `decref` は所有を手放すだけである。借用パラメータを入れたら、借りている w には置かない
- `saved` は、呼び出しの後で生きている変数から、結果の変数を除いたものである。フィールドは呼び出しより前にすべて所有になるので、借りた変数が `saved` に入ることも、そのために末尾呼び出しを降格することもない
- 入れ子のパターンでは、フィールドを `dup` してから読むだけの所が残る。借りた変数への `switch` を使い、フィールドを死ぬ所で手放す形 (遅らせる形) にすれば取り戻せる ([ロードマップ](../future/roadmap.md) の「処理系」)
- 終端を、文と新しい終端に置き換える編集をその場でできる形にしておく。借用パラメータを入れるときに、末尾の位置の呼び出しの輪の上にない `TailCall` を降格するためである (上の「変換の規則」)

### verifier

- verifier は4つの段を持つ。段はパスの順に直線に並ぶので、境界の検査だけを切り替える別の旗は持たない
  - 変換の段 (`verify_translated`) は translate の後にかける。構造の規則のうち所有に関わらないもの (R1〜R5、R6 の支配、R8 と R9 のうち境界の検査を除くもの) と下の引き継ぐ検査を確かめ、`tail`、`box`、`unbox`、`dup`、`decref`、`release`、空でない `saved` がないことを確かめる。box の挿入は末尾呼び出しと変換のない入力を前提にし、T3 は `let` と `return` の形から末尾の位置を見るためである。Perceus より前に `release` を拒むのと同じく、パスの入力の約束を verifier が確かめる。EP が作るもの (`prim`、`clause`、`clause` の印の関数) も拒む (`` `prim evv_get` is used before the evidence pass ``、`a clause call is used before the evidence pass`、``a clause of `Counter.get` is defined before the evidence pass``)
  - EP の段 (`verify_evidence`) は EP の後にかける。変換の段の検査から EP が作るものの拒否を除き、下の「EP の段の検査」を足す
  - 範囲の段 (`verify_scopes`) は box の挿入と縮約の後にかける。EP の段から `tail`、`box`、`unbox` の拒否を除き、`box` と `unbox` の規則 (上の「値の表現」) と境界の検査を足す
  - 所有の段 (`verify`) は Perceus の後にかけ、範囲の段に加えて、RC の対象の所有の多重集合 (R6、R7) と、呼び出しの後に見える変数 (R7) を確かめる
- EP の段、範囲の段、所有の段は、`handle`、`perform`、`resume` と、呼び出しの `mask` を拒む (``a perform remains after the evidence pass``。`a handler`、`a resume`、`a mask` も同じ形)。translate の出力は今のままなので、`handle`、`perform`、`resume`、`mask` の規則は変換の段にだけ残る
- 境界の検査は、R8 と R9 の検査のうち、`jump`、`return`、`box`、`unbox` を除くものである。直接の呼び出しの引数と結果、`closure` の引数、関数の値の対象が一様であること、`apply`、`clause`、`prim` のオペランドと結果、`clause` の印の関数の引数と `ret` が操作の表と互換であること、`tail` の結果、宣言した Repr が `tobj` のフィールドである。translate と EP の出力は、box の挿入より前には境界に合わないので、変換の段と EP の段は境界を見ない
- 関数の値の対象が一様かは、verifier を始めるときに関数ごとに1回求めて表にし、`&g` と `closure g` では表を引くだけにする。参照ごとに引数をたどると、時間が参照の数と引数の数の積になるためである
- 所有は、どの経路でも、関数の入口と束縛で得た参照と、`dup` と `release` で増やした参照が、消費と `decref` と `release` でちょうど使い切られることを確かめる。経路ごとに持つのは、RC の対象の変数ごとの所有の数だけである。呼び出しでは、退避する RC の対象の変数が、その時点で所有している変数とちょうど一致する (同じ変数を2回退避しない)。`return` と `tail` の時点では、所有が残らない
- RC の対象のフィールドには、定義のとき (R5 で1回だけ) 持ち主と出どころを記録する
  - 持ち主: 分解した値 s が、束縛の時点で所有の数を1つ以上持っていれば s、そうでなければ s の持ち主
  - 出どころ: `(s, Ctor, 位置)`。case の `Ctor` は、`switch` の配置と case のタグである。フィールドの数は R9 が配置で確かめるので、出どころに持たない
- 変数 v が有効なのは、v の所有の数が1つ以上か、v の持ち主の所有の数が1つ以上のときである。1回の参照で決まるので、verifier は線形のままである。所有の数が正なら、その経路は実際の参照を持ち、物体は生きている。データは変更されないので、その下の物体もすべて生きている
- 所有の段では、次の規則を確かめる
  - 分解 (case のフィールド、`unpack`): 値は見えて有効な RC の対象の変数である。RC の対象のフィールドは所有の数0で始まる。借りた変数への `switch` と `unpack` も受け入れる
  - 読む (`switch` の scrutinee、`unpack` の値、`unbox` のオペランド、`dup` の対象): 見えて有効である。`dup v` は v の所有の数を1つ増やす
  - 消費と `decref v`: 見えて、v の所有の数が1つ以上である。1つ減らす。1つの命令の中では左から順に当てる
  - `release x L #t(p1, .., pn)`: 名前が1つ以上ある。x の所有の数が1つ以上である。名前を書いた各 pi は見えて、Repr が RC の対象で、出どころが `(x, L #t, i)` である。その後、x を1つ減らし、各 pi を1つ増やす。1つの位置には1つの名前しか書けないので、同じフィールドを2つの変数が引き継ぐことはない
  - 借りた変数 (所有の数0) は消費できず、`save` の所有の多重集合とも合わないので、呼び出しをまたいで保存されることも、`jump` で渡されることもない。定義が支配する合流のブロックでは見えたままで、持ち主がどの辺でも所有されていれば有効である
  - 持ち主を手放した後は、間の変数を後で `dup` していても、借りた変数を拒む。保守的だが健全で、Perceus はその形を出さない。親をたどる規則に緩めることは、IR を変えずに後でできる
- 変換の段と範囲の段は `release` を拒む (`` `d.0` is released with its fields before Perceus ``)。引数のない `con` は、どの段でも拒む (`` a constructor value without fields is written as a tag `#N`, not `con` ``)
- 所有の段の誤りの文言は次のとおりである
  - `` `x.1` is {used|released} but is only borrowed from `d.0` ``: 持ち主が所有されている間に、所有の数0の変数を消費したか、`decref` か `release` で手放した
  - `` `x.1` is {duplicated|switched on|unpacked|unboxed} after its owner `d.0` was given up ``: 無効な変数を読んだ
  - `` `x.1` is not field 0 of `d.0` as `Option` #1 ``: `release` の名前の出どころが違う
  - `` a release of `d.0` keeps no field `` と `` `x.1` is kept but is not reference counted ``: `release` の名前の誤り
  - 持ち主のない変数を読むか消費するか手放したときと、持ち主も手放した変数を消費するか手放したときは、今までと同じく `` `x.1` is {used|released|duplicated|switched on|unpacked|unboxed} after it was moved `` で報告する
- R8 と R9 のうち境界の検査でないものは、4つの段のどれでも走り、どの段でも次の文言で報告する (`release` は所有の段にだけ現れる)。境界の検査と、`box` と `unbox` の規則は、範囲の段と所有の段で走る。どの文言の後にも、ほかの誤りと同じく `` in `f` `` が付く
  - R8 の extern: ``argument 0 of `Prelude.+` is `s.0` (obj), but the extern takes int``、``argument 1 of `Prelude.+` is (), but the extern takes int``、`` `t.1` (obj) is bound to `Prelude.<`, which returns enum ``。引数の数を確かめた後で、引数を左から、最後に束縛する変数を比べる
  - 表にない配置: ``a con refers to the unknown layout #3`` (`a switch`、`an unpack`、`a release` も同じ形)
  - `switch` の配置の有無: `a switch with tag cases has no layout`、``a switch without tag cases has the layout `Prelude.Bool` ``
  - タグの範囲: ``a con names #2, but `Prelude.Bool` has 2 constructors`` (`a case`、`an unpack`、`a release` も同じ形)
  - フィールドの数: ``a con of `Option` #1 has 2 fields, but the constructor has 1``、``a case of `Option` #1 has 0 fields, but the constructor has 1``、``an unpack of `p.0` as `Pair` #0 has 1 fields, but the constructor has 2``、``a release of `d.0` as `Option` #1 has 2 fields, but the constructor has 1``
  - タグの `switch` の scrutinee: `` `c.1` (int) is switched on as `Prelude.Bool`, which is enum ``、``a switch on `Option` has the constant #1 as its scrutinee``
  - 網羅: ``a switch on `Option` has no default and no case for #0``
  - リテラルの `switch` の scrutinee: `` `s.0` (obj) is switched on Int literals ``、`` `n.0` (int) is switched on String literals ``、``() is switched on Int literals``
  - `unpack` の配置: `` `p.0` (obj) is unpacked as `U`, which is enum ``、``an unpack of `s.0` names `Shape`, which has 2 constructors``
  - `con` の束縛: `` `d.1` (obj) is bound to a con of `Option`, which is tobj ``
  - `tobj` でないフィールド: ``field 1 of `Pair` #0 is `n.2` (obj), but the layout has int`` (case と `unpack` のフィールド)、``argument 1 of a con of `Pair` #0 is (), but the layout has int``
- 検査の順
  - それぞれの命令で、今ある形の検査を先に、R8 と R9 (境界の検査を含む) をその次に、範囲と所有の検査 (R5、R6、R7) を最後に行う。`return` だけは、値の範囲と所有を確かめてから `ret` と比べる
  - 1つの呼び出しの中では、引数の数、引数の Repr (左から)、結果を束縛する変数の Repr の順に比べ、その後で範囲と所有を確かめる。`tail` では、引数の Repr の後で結果と呼び出し元の `ret` を比べる
  - `closure g(..)` では、引数の数の後で g が一様かを確かめ、その後で引数の Repr を比べる。そのため、`closure` の対象が一様でない誤りは、その引数の範囲の誤りより先に出る
  - `&g` は、互換の位置では、定数の当てはめの中で `tobj` に収まるかを確かめた後に g が一様かを確かめる。`extern` の引数では当てはめが通った後に、`drop &g` と case のない `switch` の scrutinee ではその命令の検査の中で確かめる。IR のどこにある `&g` も関数の値だからである
- 4つの段すべての `jump` と `return` の文言は、互換で比べるほかは今のままである。定数では ``5 is returned from a function that returns tobj``、``() is returned from a function that returns obj`` になる。変数の `` `x.1` (int) is returned from a function that returns obj `` と同じ形である
- 範囲の段と所有の段の境界の検査の文言は次のとおりである
  - 直接の呼び出しの引数: ``argument 0 of `g` is `x.1` (int), but the function takes tobj``、``argument 1 of `g` is 5, but the function takes tobj``
  - 直接の呼び出しの結果: `` `t.0` (obj) is bound to `k`, which returns int ``
  - `closure` の引数: ``argument 0 of a closure of `g` is `n.1` (int), but the function takes tobj``
  - 関数の値の対象: `` `g` is used as a function value, but its parameter 0 is int ``、`` `g` is used as a function value, but it returns int ``
  - `apply` のオペランド: ``the callee of an apply is `n.1` (int), but an apply takes tobj``、``argument 0 of an apply is `n.1` (int), but an apply takes tobj``
  - `clause` のオペランド: ``the callee of a clause of `Counter.get` is `c.0` (int), but a clause takes tobj``、``argument 0 of a clause of `Counter.get` is `e.1` (int), but a clause takes obj``、``argument 1 of a clause of `Counter.put` is `n.1` (tobj), but the operation takes int``
  - `prim` のオペランド: ``argument 0 of `prim ev_new[State]` is `n.0` (int), but the primitive takes tobj``
  - `apply` の結果: `` `t.0` (int) is bound to an apply, which returns tobj ``
  - `clause` と `prim` の結果: `` `t.0` (int) is bound to a clause of `State.get`, which returns tobj ``、`` `w.0` (int) is bound to `prim evv_get`, which returns tobj ``
  - `clause` の印の関数: `` `g$entry` is a clause of `Counter.put`, but its parameter 2 is tobj ``、`` `g$entry` is a clause of `Counter.get`, but it returns tobj ``
  - `tail` の結果: ``a tail call to `g` returns int, but this function returns tobj``、``a tail apply returns tobj, but this function returns int``、``a tail clause of `Counter.get` returns int, but this function returns tobj``。呼び出し元を "this function" と書き、呼ばれる側を指す "the function" と分ける
  - `tobj` のフィールド: R9 の文言を `tobj` に広げる。``field 0 of `Option` #1 is `x.3` (int), but the layout has tobj``、``argument 0 of a con of `Option` #1 is 5, but the layout has tobj``
- 範囲の段と所有の段の `box` と `unbox` の文言は次のとおりである。`int and enum` と `int or enum` の部分は、箱を要するスカラーの定義から作る
  - `box` のオペランド: `` `u.1` (unit) is boxed, but only int and enum values and Int constants can be ``、``() is boxed, but only int and enum values and Int constants can be`` (`#1`、`&g` も同じ形)
  - `box` の束縛: `` `b.2` (int) is bound to a box, which is tobj ``
  - `unbox` のオペランド: `` `p.0` (obj) is unboxed, but only tobj can be ``、``5 is unboxed, but only tobj can be``
  - `unbox` の束縛: `` `n.2` (tobj) is bound to an unbox, which gives int or enum ``
- 変換の段と EP の段だけの文言は次のとおりである。`tail` は ``a tail call is formed before contract`` で、`call` のほかは ``a tail apply``、``a tail clause``、``a tail perform``、``a tail resume``、``a tail handler`` を同じ形で使う。`box` と `unbox` は `` `n.1` is boxed before the boxing pass ``、``5 is boxed before the boxing pass``、`` `b.2` is unboxed before the boxing pass `` である
- 引き継ぐ検査は次のとおりである。`mask` の順と番号、直接呼び出しとクロージャの引数の数、文字列定数と関数の番号が表にあること、`extern` 命令の引数の数、case の種類 (1つの `switch` の case が同じ種類であること、リテラルの case がフィールドを持たないこと)、`switch` が行き先を1つ以上持つこと、フィールドを束縛する case を持つ `switch` の scrutinee が RC の対象 (`obj` か `tobj`) の変数であること、リテラルの `switch` の `default`、`perform` の `resumable` がエフェクトの表と一致すること、`handle` の節の数。`handle` の節と `return` の節の関数が分かるとき (関数の値か、同じ関数の中で `closure` で作った値のとき) は、節が捕獲の後にちょうど「操作の引数 + `k` (再開する操作) + 状態」個の引数を持つこと、`return` の節が捕獲の後にちょうど2つ (値と状態) の引数を持つことも確かめる。操作の引数の数は、エフェクトの表の操作の `params` の長さである。`handle`、`perform`、`resume`、`mask` の検査は変換の段にだけ現れる
- EP の段の検査は次のとおりである。範囲の段と所有の段も同じく確かめる
  - `prim` の即値のエフェクトと操作がエフェクトの表にあり、引数の数が表の行と同じである
  - `clause` の操作がエフェクトの表にあり、引数の数が「1 + 操作の引数の数」である
  - `ev_set_clause[E.op]` に渡す値が `&g` か、同じ関数の中の `closure g(..)` なら、g の `clause` の印が op に合い、同じ関数の中で evidence を定義した `ev_new[E]` の E にも合う
  - `clause` の印の関数が、`ev_set_clause` の引数のほかで値として参照されず、直接も呼ばれない。印のエフェクトと操作が表にあり、捕獲の後に evidence と操作の引数を受ける
- verifier は生存解析を使わない。ブロックを番号の順にたどるだけで、反復しない。辺は前向きなので、ブロックに着いたときには入る辺がすべて出そろっている
  - 支配木は Cooper-Harvey-Kennedy の方法で求める。番号の順が辺の向きに沿っているので、1回たどれば決まる。2つのブロックの共通の支配者は、支配木の skew-binary の飛び先 (Myers) を使って、深さの対数の歩みで求める。1段ずつ登ると、深さの違う辺が多く1つのブロックに合流したとき (`a || b || ...` の真の行き先など)、時間はブロックの数と深さの積になる
  - 変数ごとに定義の位置 (ブロックと文の番号。引数は -1) を記録し、支配は支配木の前順と後順の番号で調べる
  - 所有の多重集合は、合流を待つブロックごとに疎に持つ。辺ごとに所有の多重集合を写して比べるので、その時間は辺の数と所有の大きさの積に比例する

## インタプリタ (CEK 機械)

- 制御は (関数、ブロック、文の番号) である。文の番号がブロックの文の数より小さければその文を、そうでなければ終端を実行する。実行は入口の関数から始める。
- `jump` は実引数をすべて読み、行き先の引数に書いてから、行き先の先頭へ進む。同じ関数の中で制御を移すだけで、フレームを積まない。
- 末尾でない呼び出しは、戻りのフレームに再開の番地と退避した変数を積む。再開の番地は実行する側が意味を決める値で、インタプリタは呼び出しの文の (ブロック、文の番号) を入れる。戻ったら、その文の `let` の変数に結果を入れ、次の文から続ける ([コンパイラの構成](../implementation/architecture.md) の「`eml_core_ir`、`eml_runtime`、`eml_interp` の内部」)。
- インタプリタは EP の後の IR を実行する。`handle`、`perform`、`resume` と、空でない `mask` に届いたら、内部の誤り (`an effect instruction reaches the interpreter`) である
- 機械は、継続のフレームのほかに、実行の文脈として `evv` と yield の状態を持つ (上の「実行の文脈」)。始めは、空の `evv` と yield なしである。正しく終わった実行で `evv` が空でないか、yield の状態がなしでなければ、内部の誤りである。残った evidence がリークに見えないように、この検査は `debug_heap` によらず、リークの検査の前に行う
- `prim` は、上の「基本操作」の表のとおりに文脈と evidence を読み書きする。引数をすべて消費し、所有した結果を返す。evidence、入口の表、`evv` のリストの節点は、ヒープの物体である ([ランタイム](runtime.md) の「evidence と `evv` の物体」)
- `clause` は `apply` と同じに動く。操作の ABI は値の表し方を変えないためである
- `prim dummy()` の値は、ヒープの物体でない専用の値 (`Value::Dummy`) である。`dup` と `decref` は何もせず、`box` と `unbox` はそのまま通す (上の「ダミーの値」)。ヒープに置かないので、`peak_objects` は変わらない
- `drop k` と `never` の操作による中断は、継続のクロージャが捕まえていた値を、解放の連鎖で1回ずつ解放する。`Lin` の値の破棄処理はオブジェクトの解放そのものなので、捕まっていた `File` は、この解放で読み出し口が捨てられて閉じる ([ランタイム](runtime.md))。
- `extern` 命令は、引数を受け取ってその場で実行し、値を返す。継続の最下部には、プログラムの終わりを表すフレームがあるだけで、`IO` の handler はない。
- `println` の標準出力は、`run` に渡された `OutputSink` に書く。テストで出力を捕まえるためである ([ランタイム](runtime.md))。`open` は `File` のオブジェクトを確保し、`read_all` は受け取った `File` の参照を、読んだ文字列との組に移して返す。`close` は `File` を解放する ([エフェクトと handler](effects.md) の「組み込みの `IO`」)。
- 変数の消費は所有権の移動 (move) とし、値を複製するのは `dup` 命令だけにする。`switch` の scrutinee、`unpack` の値、`unbox` のオペランドは読むだけで、所有権を動かさない。Perceus の所有権の規則とインタプリタの動作を1対1に対応させるためである。呼び出しのフレームには、呼び出しの後で使う変数だけを退避する。Core IR の呼び出しは、その変数の並び (`saved`) を持つ。そのため、フレームはちょうど所有している参照だけを持ち、フレームを解放するときは退避した値を1回ずつ decref すればよい。
- `switch` は scrutinee を読むだけで、参照の数を変えない。case を選び、フィールドの値をフィールドの変数に書いてから、行き先の先頭へ進む。ヒープからは何も取り出さず、複製もしない。行き先は `switch` の前の所有をそのまま持って始まり、scrutinee を手放す `decref` か `release` と、フィールドの `dup` は、Perceus が行き先の入口に置く。実行時は、scrutinee が即値のタグならその case に入る。オブジェクトなら、そのタグの case に入り、合う case がなければ `default` に進む。`Int` と `String` は case の値と比べる。`String` の scrutinee も `switch` では手放さず、行き先が手放す。
- `unpack` は、1つの case の `switch` と同じく値を読むだけで、フィールドの値をフィールドの変数に書く。値のタグが `unpack` のタグと違うとき、フィールドの数が違うときは、内部の誤りである。
- `release` は、ヒープの `release_fields` で値を手放し、名前を書いた位置のフィールドの参照を残す ([ランタイム](runtime.md) の「ランタイムの API」)。値がオブジェクトでないとき、データでないとき、タグかフィールドの数が違うときは、内部の誤りである。
- `box` と `unbox` は値をそのまま渡す。`Value` が自分の種類を持つためである。どちらも、値がヒープの物体 (`Value::Obj`) なら、内部の誤り (`internal error: a box of a heap object`、`internal error: an unbox of a heap object`) で止める。R9 は値を作った配置を追わないので、verifier を通った IR でも、`tobj` に入ったヒープの物体を `unbox` しうる。インタプリタは Repr を読まずに、この誤りを見つけられる
  - 本当の箱は確保しない。box の変数の RC の釣り合いは、所有の検査がすでに静的に確かめている。そのため、`box` と `unbox` は `RunStats` の参照の数の回数を変えず、`boxes` と `unboxes` だけを1つ増やす
- 機械は配置の表を読まず、`Ctor` のタグだけを使う。`Payload::Data` は配置の ID を持たない。`unpack` のタグと数の検査、case のフィールドの数の検査、`release` の `WrongLayout` は、内部の誤りの見張りとして残す。R9 は値を作った配置を追わないので、verifier を通った IR でもこれらの誤りは起きうる (上の「構造の規則」の R9)
- 再帰の深さは Rust のスタックで制限されない。継続をヒープ上のフレームで表すためである ([コンパイラの構成](../implementation/architecture.md) の「継続と evidence」)。
- 名前付きのレコードの実行時の表し方は、S9 で決める。タプルはコンストラクタが1つの `data` と同じオブジェクトで、位置で分解する ([直積型とレコード](records.md))。

## 実行時エラー

次の場合は実行を止めて実行時エラーにする。CLI の終了コードは 1 である ([コンパイラの構成](../implementation/architecture.md))。

- `Int` のオーバーフローとゼロ除算 ([宣言](declarations.md) の標準の演算子の表)
- 解放済みのオブジェクトへのアクセスと、`debug_heap` が有効なときのリーク ([ランタイム](runtime.md))
- `Fs.open` が開けないとき (``cannot open `<path>`: <reason>``)、`Fs.read_all` が読めないとき (``cannot read `<path>`: <reason>``)、読んだ内容が UTF-8 でないとき (``` `<path>` is not valid UTF-8 ```)。`reason` は `not found`、`permission denied`、`I/O error` のどれかである

実行時エラーは、誤りの種類 (`fault`)、そのとき実行していた Core IR の関数の名前 (`function`)、省略できる位置 (`at`) を持つ。位置を持つ `extern` 命令の実行が起こした誤り (その中のヒープの誤りを含む) にだけ、その命令の位置を付ける。引数の読み出し、`dup`、`decref`、`release`、`switch`、`unpack`、`box`、`unbox` の誤りと、位置を持たない `extern` 命令の誤りには付けない。

位置があるときは、次のように表示する。`path` は `Program.files` の表示用のパスである。

```
{fault}
  at {path}:{line}:{column}
```

位置がないとき (extern 命令の外で起きた誤り、位置のない手書きの IR) は ``{fault} in `{function}` `` と表示する。リークの表示は位置を持たない。

## 実行時の規約

- インタプリタの値とフレームに `Rc` と `RefCell` を使わない。`dup`、`decref`、`release` の命令が、自前のヒープの数を直接増減するためである。
- 継続のフレーム、環境、evidence と `evv` は、`eml_runtime` の RC で管理するランタイムのオブジェクトである ([ランタイム](runtime.md) の「ランタイムの API」)。
