# ランタイム

位置づけ: 規範。

`eml_runtime` が持つオブジェクトのモデル、ヒープ、参照カウント、`debug_heap` の検査、実行の API を定める。`eml_runtime` はインタプリタのためのシングルスレッドのヒープで、並列化はネイティブのランタイムだけで行う ([マルチコア対応の設計](../future/multicore.md))。

## ヒープと参照カウント

- メモリ管理は Perceus 方式の参照カウントである。`Lin` の値は2回以上消費されず、Perceus は `Lin` のフィールドも `dup` しないので、`Lin` の物体の参照の数はいつも1である ([LIR とインタプリタ](lir.md) の「値の表現」)。`File` の物体については、ヒープがこれを実行時に確かめる (下の「`File` の参照の検査」)。
- 値とフレームの管理には Rust の `Rc` を使わず、自前のヒープと参照カウントを `eml_runtime` に持つ。LIR の `dup` / `decref` / `release` 命令が、実際にカウントを増減する。CEK が読むのは LIR である ([LIR とインタプリタ](lir.md) の「インタプリタ (CEK 機械)」)。
- ヒープは、インデックス方式のアリーナと世代番号で実装する。解放済みのオブジェクトへのアクセスは、世代番号の不一致で検出する。この方式は解放済みアクセスの検出がほぼ無料で、`unsafe` が要らない。検出がほぼ無料なので、`debug_heap` に関係なく常に検査する。
- `decref` で解放するときは、子のオブジェクトを再帰ではなく作業リストでたどる。長い連鎖の解放で Rust のスタックを溢れさせないためである。
- ヒープはシングルスレッドで、RC は `u32` である。スレッドをまたぐ RC (共有の印方式) は、ネイティブのランタイムだけが持つ。

## オブジェクトのヘッダ

- ヘッダは、RC と、不死の物体かどうかの印 (`immortal`) を持つ (下の「不死の物体」)。
- オブジェクトの種類は、ペイロード (`Payload` の enum) の種類で決まる。種類ごとの処理 (子のたどり方 `children` と写し方 `copy`) は `match` で書き、`Lin` の破棄処理はオブジェクトの解放 (Rust の `Drop`) で済む。そのため、ヘッダは記述子を持たない。
- 種類の名前 (`String`、`Frame`、`Closure`、`Data`、`File`、`EvTable`、`Evidence`、`Evv`) は `Payload::kind_name` が返し、`debug_heap` のリークの報告に使う。継続のフレームは、どの種類も `Frame` である。
- 静的な型の情報なしにオブジェクトを扱うための記述子は、ネイティブのオブジェクトモデルの要件である。形は S9 で決める ([ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)。データの物体の記述子は、LIR の配置の表 (`Program.layouts`) をもとに作る。配置は、コンストラクタごとのフィールドの数と、宣言したフィールドの Repr (どれが参照になりうるか) を持つ ([LIR とインタプリタ](lir.md) の「データの配置」)。

## 不死の物体

- 不死の物体は解放されない。一意にならないので、`is_unique` は偽を返し、`take` は `Shared` で断り、`release_fields` は共有の側を通る。
- 文字列のリテラルは不死の物体である。インタプリタは、実行を始めるときに `Program::strings` の項目ごとに不死の物体を1つ作り、`Rhs::ConstString(i)` はその物体を返す。リテラルを評価するたびに文字列を写さないためである。
- RC の操作を飛ばしてよいのは、検査付きヒープを持たないバックエンド (ネイティブのランタイム) だけである。LIR は、リテラルについても `dup` と `decref` の釣り合いを保つ。値がリテラルだからといって `dup` や `decref` を消すパスは作らない。
- 検査付きヒープでは、不死の物体の RC は外に出ている参照の数である。`Heap::alloc_immortal` は数を 0 にして作り、`Rhs::ConstString` は `Heap::acquire_immortal` で数を1増やす。`dup` は1増やし、`decref` は1減らす。数が 0 になっても解放しない。
- 数が 0 の不死の物体には、どの操作 (`get`、`get_mut`、`dup`、`decref`、`is_unique`、`take`、`take_or_copy`、`release_fields`) も `UseAfterFree` を返す。判定は、ヒープの中で物体を引く1か所 (`object` と `object_mut`) に置く。`acquire_immortal` だけがこの判定を通らない。

## ランタイムの API

- 確保、`dup` / `decref`、フィールドの読み出し、一意かどうかの判定、分解した値の手放し (`release_fields`)、クロージャの取り出し (`take_or_copy`) を API とする。
- `Heap::release_fields(x, tag, keep)` は、LIR の `release` を実行する。`keep` は、フィールドの位置ごとに参照を残すかどうかを持つ。
  - x がデータでないとき、タグかフィールドの数が違うときは `HeapError::WrongLayout` を返す。機械はこれを内部の誤りとして報告する
  - x が一意なら、箱を解放し、残さないフィールドの値のうち物体を `decref` する。残すフィールドは、箱が持っていた参照をそのまま受け継ぐ
  - そうでなければ (共有の物体と不死の物体)、残すフィールドを `dup` してから、x を `decref` する
  - x の解放後の使用と `WrongLayout` を返すときは、参照の数も中身も変えない
- `take_or_copy` は、クロージャだけを扱う。一意なら中身を取り出し、共有されていれば写す (下の項目)。データ、文字列、`File`、evidence と `evv` の物体は、一意かどうかによらず `NotCopyable` で断る。データと文字列は複製しない。
- 継続のフレームと環境も、同じ RC で管理するランタイムのオブジェクトにする。フレームは、戻りのフレーム (`Frame::Return`)、余った引数を適用するフレーム (`Frame::Apply`)、継続の最下部 (`Frame::Root`) の3種類である。エフェクトの継続はフレームでなく、EP が組み立てるクロージャである ([Core IR](core-ir.md) の「継続の組み立て」)。
- クロージャも、同じ RC で管理するオブジェクトである。関数と、捕まえた値や部分適用で渡された引数の並びを持ち、並びの値を子として所有する ([LIR とインタプリタ](lir.md))。
- 引数を持つコンストラクタの値も、同じ RC で管理するオブジェクト (`Payload::Data`) である。タグとフィールドの並びを持ち、フィールドの値を子として所有する。種類は、どの `data` の型でも `Data` である。配置の ID は持たず、インタプリタは配置の表を読まない。`match` の分岐は物体を読むだけで、フィールドを取り出さない。分解した値を手放すのは `release_fields` で、データを写す手続きはない ([LIR とインタプリタ](lir.md))。
- 標準ライブラリの extern の型 `Fs.File` のオブジェクト (`Payload::File`) は、読み出し口と `open` に渡したパスを持つ。種類は `File` である。`Lin` の破棄処理はオブジェクトの解放で、読み出し口を捨てると OS のファイルが閉じる。`File` は写さず、`take_or_copy` は一意な `File` も `NotCopyable` で断る。`Heap::dup` が `File` の参照を増やさないので (下の「`File` の参照の検査」)、共有された `File` はできない。
- 共有されたクロージャの中身を使う側 (クロージャの呼び出し。エフェクトの継続の再開も含む) は、中身を写し、写した中身の子の参照を1つずつ増やしてから、元の参照を1つ手放す。写すときと解放するときで、数える子を一致させる。捕まえた evidence の物体は写さず、参照を増やして共有する。
- フレームはつねに一意である。フレームを捕まえる命令はなく、フレームは戻りで1回だけ取り出される。

## `File` の参照の検査

- `Heap::dup` は、対象が `File` の物体 (`Payload::File`) なら、参照の数を変えずに `HeapError::LinShared` を返す。文言は `a Lin object is shared` である。`File` の参照が2つになると、閉じ忘れか二重の解放になるためである
- 物体の参照の数を増やす経路は、`dup` 命令 (`Runtime::dup`)、共有の側の `release` が残すフィールド (`release_fields`)、共有されたクロージャを写すときの子 (`take_or_copy`)、基本操作が残す参照で、どれも `Heap::dup` を通る。`acquire_immortal` は文字列のリテラルにしか使わない。そのため、`Heap::dup` の1か所で覆える
- 検査は `debug_heap` によらず常に行う。中身の種類は、`dup` がすでに引いた物体の中で1回見るだけである。`debug_heap` のときだけにすると、検査のためだけにヒープへ旗を渡すことになる。違反はコンパイラの誤りなので、`debug_heap` なしでも止める
- 誤りは、ほかのヒープの誤りと同じく実行時エラーになる ([LIR とインタプリタ](lir.md) の「実行時エラー」)。`dup` 命令で起きたときは ``a Lin object is shared in `f` `` と表示する
- この検査が見つけるのは、`File` の物体の参照の数を増やす違反だけである。`File` を含む `Lin` のデータやクロージャを `dup` する違反は、実行時にはほかの物体と区別できないので見つけられない。それは S8d の V1 で静的に覆う ([ロードマップ](../future/roadmap.md) の「S8 LIR」)

## evidence と `evv` の物体

evidence passing の実行時のモデル ([LIR とインタプリタ](lir.md) の「evidence」と「実行の文脈」) は、次の3種類の物体で表す。どれも普通の物体と同じ RC で管理し、`children` は子をすべてたどる。`debug_heap` のリークの数え方もほかの物体と同じである。

- 入口の表 (`Payload::EvTable { effect, entries }`): エフェクトの番号と、操作ごとの in-place の入口のクロージャ。欄は `ev_new` が空 (`()`) で作り、`ev_set_clause` が handle の場所で1回だけ入れる。再開で作り直した evidence も同じ表を共有する
- evidence (`Payload::Evidence { table, state, outer }`): handler の1回の実行。入口の表、状態、作ったときの `evv` を所有する。書き換えるのは `state` だけで、`outer` はその evidence 自身を含まない。yield の宛先は、この物体の参照そのもので比べる
- `evv` のリストの節点 (`Payload::Evv { evidence, next }`): evidence と次の節点を所有する。リストは書き換えない永続リストで、空のリストは即値の `()` (`Value::Unit`) である

yield 中に返すダミー (`Value::Dummy`) はヒープの物体でない値である。`dup` と `decref` は何もしないので、RC の回数にも `peak_objects` にも現れない ([LIR とインタプリタ](lir.md) の「ダミーの値」)。

## 文字列の連結

- `Heap::append_str(left, right)` は、左辺の `String` の後に右辺の文字列を足し、足したバイト数を返す。左辺の中身をいったん取り出し、右辺を借りて足してから戻す。左辺は一意でなければならず、一意でない物体 (不死の物体を含む) には `Shared` を返す。
- `++` (`Extern::StrConcat`) は、左辺が一意なら `append_str` で足し、右辺を `decref` して左辺を返す。左辺が一意でない場合 (共有された文字列と不死のリテラル) は、両辺の長さの和の容量で新しい文字列を作り、両辺を `decref` する。`x ++ x` は Perceus の `dup` で RC が 2 になって届くので、新しい文字列を作る側に進む。
- 一意な文字列の後ろに足していく連結は、ならして右辺の長さに比例する時間で済む。先頭に足す連結 (`"x" ++ acc`) と、共有された左辺への連結は、両辺を写した新しい文字列を作る。ループで先頭に足していくと、伸びていく右辺を毎回写す ([実装の現在地](../implementation/status.md) の「深さと性能」)。
- 文字列を読むだけの extern (`println` と、文字列の `==`、`!=`、`compare`) は、中身を借りて使ってから `decref` し、写さない。文字列の `show` も中身を借りて読み、エスケープした新しい文字列を作ってから引数を `decref` する。`Fs.open` は、`File` のオブジェクトと誤りの文言のためにパスを1回だけ写す。

## `debug_heap`

- `RunConfig` の `debug_heap` を有効にすると、プログラムの終了時にすべてのオブジェクトが解放されていることを確認する (リーク検出)。残っていれば、種類の名前ごとの件数を添えて実行時エラーにする。不死の物体は、数が 0 でなければその数を件数に足し、数が 0 なら数えない。解放済みのオブジェクトへのアクセスは、`debug_heap` に関係なく検出する (上の「ヒープと参照カウント」)。
- 不死のリテラルでは、見つからない誤りが1つある。同じリテラルを何回評価しても、参照は1つの数にまとめられる。片方の参照を余分に `decref` し、もう片方を手放し忘れると、2つの誤りが打ち消し合って見つからない。
- CLI では `eml run --debug-heap` で有効にする。UI テストでは常に有効にし、違反があればテストを失敗させる ([テスト戦略](../implementation/testing.md))。

## 実行の API

- `run` の出力先 `OutputSink` は、`Rc<RefCell<dyn Write>>` を包む型である。インタプリタはシングルスレッドなので、スレッドをまたいで受け渡さない。テストでは、出力を捕まえられるバッファ (`OutputSink::capture`) を渡す。
- `RunConfig` は `Default` を実装し、`#[non_exhaustive]` にする。フィールドを足しても呼び出し側を壊さないためである。
- `run` は LIR の `Program` を参照で受け取り、正常に終わると `RunStats` を返す。`RunStats` は、実行の仕事の回数と、同時に生きていたヒープの物体の数の最大である。実行時エラーとリークのときは返さない。回数は次の9つで、はじめの8つが仕事の回数である。
  - `evidence_steps`: `ev_lookup` と `evv_mask` がたどった `evv` の節点の数。今有効な handler の数で決まり、呼び出しの深さにはよらない
  - `yields`: `yield_to` と `yield_abort` を実行した回数。すぐに再開する操作は yield しないので数えない
  - `yield_frames`: `yield_cont_set` を実行した回数。yield が handler まで戻る間に、継続 κ に足したフレームの数である。再開する操作では、操作と handler の間のフレームの数に比例する。これは方式の性質である
  - `string_bytes_copied`: インタプリタが文字列の物体の中身に書いたバイト数。`++` では、新しい文字列を作る側が |左辺| + |右辺|、その場で足す側が |右辺| になる。`String` の容量の再確保と、出力への書き込みは数えない。実行を始めるときに不死のリテラルを作る書き込みも、実行の仕事ではないので数えない
  - `rc_increments`: ヒープの物体の参照の数を増やした回数。`Heap::dup` (LIR の `dup`、`release_fields` の共有の側で残すフィールド、共有されたクロージャを写すときの子、基本操作が手放さずに残す参照) と、不死の物体の参照を作る `acquire_immortal` を数える。確保のときの最初の1は数えない
  - `rc_decrements`: 参照の数を減らした回数。`Heap::decref` (LIR の `decref`、インタプリタが手放す参照、解放の連鎖で子とフレームの数を減らした分を含む)、`release_fields` で x の参照を手放す1回 (一意の側でも共有の側でも1回)、一意の側で残さないフィールドの `decref` を数える。箱の解放そのものは数えない
  - `boxes`: 実行した `box` の文の数。インタプリタは値をそのまま渡すので費用はほとんどないが、語の値の表現 ([ロードマップ](../future/roadmap.md) の S9) では費用になる変換なので数える
  - `unboxes`: 実行した `unbox` の文の数。数える理由は `boxes` と同じである
  - `peak_objects`: 同時に生きていたヒープの物体の数の最大。フレームと不死のリテラルを含む。ヒープは空いたスロットを先に使い、空きがないときだけスロットを足すので、スロットの数 (`Heap::peak_objects`) がそのまま最大になり、数える手間はない。仕事の回数ではないので、`main () = ()` でも `Frame::Root` のフレームの分だけ 0 にならない。フレームの伸びを見られる数はこれだけで、末尾呼び出しを失うと反復の数に比例して増える
- どの回数も時間ではなく、仕事か物体を数える。そのため、2乗の時間にならないことと、ループがフレームを積まないことを、ふだんのテストで確かめられる ([テスト戦略](../implementation/testing.md) の「性能のテスト」)。
