# ランタイム

位置づけ: 規範。

`eml_runtime` が持つオブジェクトのモデル、ヒープ、参照カウント、`debug_heap` の検査、実行の API を定める。`eml_runtime` はインタプリタのためのシングルスレッドのヒープで、並列化はネイティブのランタイムだけで行う ([マルチコア対応の設計](../future/multicore.md))。

## ヒープと参照カウント

- メモリ管理は Perceus 方式の参照カウントである。`Lin` の値は2回以上消費されないので、消費のための `dup` は要らない。後の行のパターンが分解した値かその祖先を束縛するときは、`Lin` の値も `dup` され、`release` や `decref` が共有の側を通ることがある ([Core IR とインタプリタ](core-ir.md) の「値の表現」)。
- 値とフレームの管理には Rust の `Rc` を使わず、自前のヒープと参照カウントを `eml_runtime` に持つ。Core IR の `dup` / `decref` / `release` 命令が、実際にカウントを増減する。
- ヒープは、インデックス方式のアリーナと世代番号で実装する。解放済みのオブジェクトへのアクセスは、世代番号の不一致で検出する。この方式は解放済みアクセスの検出がほぼ無料で、`unsafe` が要らない。検出がほぼ無料なので、`debug_heap` に関係なく常に検査する。
- `decref` で解放するときは、子のオブジェクトを再帰ではなく作業リストでたどる。長い連鎖の解放で Rust のスタックを溢れさせないためである。
- ヒープはシングルスレッドで、RC は `u32` である。スレッドをまたぐ RC (共有の印方式) は、ネイティブのランタイムだけが持つ。

## オブジェクトのヘッダ

- ヘッダは、RC と、不死の物体かどうかの印 (`immortal`) を持つ (下の「不死の物体」)。
- オブジェクトの種類は、ペイロード (`Payload` の enum) の種類で決まる。種類ごとの処理 (子のたどり方 `children` と写し方 `copy`) は `match` で書き、`Lin` の破棄処理はオブジェクトの解放 (Rust の `Drop`) で済む。そのため、ヘッダは記述子を持たない。
- 種類の名前 (`String`、`Frame`、`Closure`、`Continuation`、`Data`、`File`) は `Payload::kind_name` が返し、`debug_heap` のリークの報告に使う。継続のフレームは、どの種類も `Frame` である。
- 静的な型の情報なしにオブジェクトを扱うための記述子は、ネイティブのオブジェクトモデルの要件である。形は S9 で決める ([ロードマップ](../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)。データの物体の記述子は、Core IR の配置の表 (`Program.layouts`) をもとに作る。配置は、コンストラクタごとのフィールドの数と、宣言したフィールドの Repr (どれが参照になりうるか) を持つ ([Core IR とインタプリタ](core-ir.md) の「データの配置」)。

## 不死の物体

- 不死の物体は解放されない。一意にならないので、`is_unique` は偽を返し、`take` は `Shared` で断り、`release_fields` は共有の側を通る。
- 文字列のリテラルは不死の物体である。インタプリタは、実行を始めるときに `Program::strings` の項目ごとに不死の物体を1つ作り、`Rhs::ConstString(i)` はその物体を返す。リテラルを評価するたびに文字列を写さないためである。
- RC の操作を飛ばしてよいのは、検査付きヒープを持たないバックエンド (ネイティブのランタイム) だけである。Core IR は、リテラルについても `dup` と `decref` の釣り合いを保つ。値がリテラルだからといって `dup` や `decref` を消すパスは作らない。
- 検査付きヒープでは、不死の物体の RC は外に出ている参照の数である。`Heap::alloc_immortal` は数を 0 にして作り、`Rhs::ConstString` は `Heap::acquire_immortal` で数を1増やす。`dup` は1増やし、`decref` は1減らす。数が 0 になっても解放しない。
- 数が 0 の不死の物体には、どの操作 (`get`、`get_mut`、`dup`、`decref`、`is_unique`、`take`、`take_or_copy`、`release_fields`) も `UseAfterFree` を返す。判定は、ヒープの中で物体を引く1か所 (`object` と `object_mut`) に置く。`acquire_immortal` だけがこの判定を通らない。

## ランタイムの API

- 確保、`dup` / `decref`、フィールドの読み出し、一意かどうかの判定、分解した値の手放し (`release_fields`)、クロージャと継続の取り出し (`take_or_copy`) を API とする。
- `Heap::release_fields(x, tag, keep)` は、Core IR の `release` を実行する。`keep` は、フィールドの位置ごとに参照を残すかどうかを持つ。
  - x がデータでないとき、タグかフィールドの数が違うときは `HeapError::WrongLayout` を返す。機械はこれを内部の誤りとして報告する
  - x が一意なら、箱を解放し、残さないフィールドの値のうち物体を `decref` する。残すフィールドは、箱が持っていた参照をそのまま受け継ぐ
  - そうでなければ (共有の物体と不死の物体)、残すフィールドを `dup` してから、x を `decref` する
  - x の解放後の使用と `WrongLayout` を返すときは、参照の数も中身も変えない
- `take_or_copy` は、クロージャと継続だけを扱う。一意なら中身を取り出し、共有されていれば写す (下の項目)。データ、文字列、`File` は、一意かどうかによらず `NotCopyable` で断る。データと文字列は複製しない。
- 継続のフレームと環境も、同じ RC で管理するランタイムのオブジェクトにする。
- 継続オブジェクトは、`perform` で捕まえた区間の先頭のフレームを所有し、区間の最後の handler フレームを所有せずに指す。handler フレームの次 (handle の外側) は、捕まえられている間は空である。そのため、継続を解放すると、子をたどる解放は handler フレームで止まる ([コンパイラの構成](../implementation/architecture.md) の「継続のフレーム」)。
- handler フレームは、つながり (`Attachment`) を持つ。つながっている間は `Attached { next, state, outer }` で、外側のフレーム `next` と状態 `state` を所有する。切り離されている間 (継続に捕まえられている間) は `Detached { inner }` で、外側のフレームも状態も持たない。つながっているのに状態がない形と、切り離されているのに状態がある形は、型として表せない。状態はフレームの子で、区間を写すときは参照を1つ増やし、解放するときは1つ減らす。外側のエフェクトの区間に入った handler フレームの状態は、この規則で写され、解放される。`outer` と `inner` は、下の「handler の連鎖」の参照である。
- クロージャも、同じ RC で管理するオブジェクトである。関数と、捕まえた値や部分適用で渡された引数の並びを持ち、並びの値を子として所有する ([Core IR とインタプリタ](core-ir.md))。
- 引数を持つコンストラクタの値も、同じ RC で管理するオブジェクト (`Payload::Data`) である。タグとフィールドの並びを持ち、フィールドの値を子として所有する。種類は、どの `data` の型でも `Data` である。配置の ID は持たず、インタプリタは配置の表を読まない。`match` の分岐は物体を読むだけで、フィールドを取り出さない。分解した値を手放すのは `release_fields` で、データを写す手続きはない ([Core IR とインタプリタ](core-ir.md))。
- 標準ライブラリの extern の型 `Fs.File` のオブジェクト (`Payload::File`) は、読み出し口と `open` に渡したパスを持つ。種類は `File` である。`Lin` の破棄処理はオブジェクトの解放で、読み出し口を捨てると OS のファイルが閉じる。`File` は写さず、`take_or_copy` は参照の数によらず `NotCopyable` で断る。
- 共有されたオブジェクトの中身を使う側 (クロージャの呼び出しと、継続の再開) は、中身を写し、写した中身の子の参照を1つずつ増やしてから、元の参照を1つ手放す。写すときと解放するときで、数える子を一致させる。
- フレームはつねに一意である。共有されうるのは継続オブジェクトだけで、共有された継続オブジェクトの複製は、区間のフレームを先頭から切り離された handler フレームまで写す。写したフレームは `next` 以外の子の参照を1つずつ増やし、`next` は写した次のフレームを指す。元のフレームの参照の数は変えないので、写した後も両方の区間のフレームは一意である。区間はループでたどる。連鎖の参照の付け替えは、下の「handler の連鎖」にある。

## handler の連鎖

- `perform` が handler と `Mask` のフレームだけをたどれるよう、これらのフレームは外側へ向かう連鎖でつながる。インタプリタでの使い方は [コンパイラの構成](../implementation/architecture.md) の「継続のフレーム」にある。
- `Frame::Mask` の `outer` と、つながった handler フレームの `Attached` の `outer` は、外側の次の連鎖のフレーム (handler、`Mask`、`Root` のどれか) を指す。切り離された handler フレームの `Detached` の `inner` は、捕まえた区間の中でいちばん内側の連鎖のフレームを指す。区間に連鎖のフレームがなければ、その handler フレーム自身を指す。
- `outer` と `inner` は所有しない。`children` はこの2つをたどらず、RC は変わらない。指す先のフレームは、継続の `next` の側から所有されている。
- 捕まえた区間の中の連鎖の参照は、区間の外を指さない。区間のいちばん外側の連鎖のフレームの `outer` は、切り離された handler フレームを指す。
- `copy_segment` は、区間のフレームを写すとき、区間の中の `outer` と、切り離された handler フレームの `inner` を、元のフレームから写したフレームへの対応で付け替える。対応にない参照は `HeapError::BrokenSegment` にする。区間をすべてたどるついでに、区間の中の連鎖が `inner` から `outer` で handler フレームまでつながっていることも確かめる。

## 文字列の連結

- `Heap::append_str(left, right)` は、左辺の `String` の後に右辺の文字列を足し、足したバイト数を返す。左辺の中身をいったん取り出し、右辺を借りて足してから戻す。左辺は一意でなければならず、一意でない物体 (不死の物体を含む) には `Shared` を返す。
- `++` (`Extern::StrConcat`) は、左辺が一意なら `append_str` で足し、右辺を `decref` して左辺を返す。左辺が一意でない場合 (共有された文字列と不死のリテラル) は、両辺の長さの和の容量で新しい文字列を作り、両辺を `decref` する。`x ++ x` は Perceus の `dup` で RC が 2 になって届くので、新しい文字列を作る側に進む。
- 一意な文字列の後ろに足していく連結は、ならして右辺の長さに比例する時間で済む。先頭に足す連結 (`"x" ++ acc`) と、共有された左辺への連結は、両辺を写した新しい文字列を作る。ループで先頭に足していくと、伸びていく右辺を毎回写す ([実装の現在地](../implementation/status.md) の「深さと性能」)。
- 文字列を読むだけの extern (`println` と、文字列の `==` と `!=`) は、中身を借りて使ってから `decref` し、写さない。`Fs.open` は、`File` のオブジェクトと誤りの文言のためにパスを1回だけ写す。

## `debug_heap`

- `RunConfig` の `debug_heap` を有効にすると、プログラムの終了時にすべてのオブジェクトが解放されていることを確認する (リーク検出)。残っていれば、種類の名前ごとの件数を添えて実行時エラーにする。不死の物体は、数が 0 でなければその数を件数に足し、数が 0 なら数えない。解放済みのオブジェクトへのアクセスは、`debug_heap` に関係なく検出する (上の「ヒープと参照カウント」)。
- 不死のリテラルでは、見つからない誤りが1つある。同じリテラルを何回評価しても、参照は1つの数にまとめられる。片方の参照を余分に `decref` し、もう片方を手放し忘れると、2つの誤りが打ち消し合って見つからない。
- CLI では `eml run --debug-heap` で有効にする。UI テストでは常に有効にし、違反があればテストを失敗させる ([テスト戦略](../implementation/testing.md))。

## 実行の API

- `run` の出力先 `OutputSink` は、`Rc<RefCell<dyn Write>>` を包む型である。インタプリタはシングルスレッドなので、スレッドをまたいで受け渡さない。テストでは、出力を捕まえられるバッファ (`OutputSink::capture`) を渡す。
- `RunConfig` は `Default` を実装し、`#[non_exhaustive]` にする。フィールドを足しても呼び出し側を壊さないためである。
- `run` は Core IR の `Program` を参照で受け取り、正常に終わると `RunStats` を返す。`RunStats` は、実行の仕事の回数と、同時に生きていたヒープの物体の数の最大である。実行時エラーとリークのときは返さない。回数は次の7つで、はじめの6つが仕事の回数である。
  - `handler_visits`: `perform` が handler を探すときに調べたフレームの数。連鎖のフレームだけを数える
  - `string_bytes_copied`: インタプリタが文字列の物体の中身に書いたバイト数。`++` では、新しい文字列を作る側が |左辺| + |右辺|、その場で足す側が |右辺| になる。`String` の容量の再確保と、出力への書き込みは数えない。実行を始めるときに不死のリテラルを作る書き込みも、実行の仕事ではないので数えない
  - `rc_increments`: ヒープの物体の参照の数を増やした回数。`Heap::dup` (Core IR の `dup`、`release_fields` の共有の側で残すフィールド、共有されたクロージャと継続を写すときの子) と、不死の物体の参照を作る `acquire_immortal` を数える。確保のときの最初の1は数えない
  - `rc_decrements`: 参照の数を減らした回数。`Heap::decref` (Core IR の `decref`、インタプリタが手放す参照、解放の連鎖で子とフレームの数を減らした分を含む)、`release_fields` で x の参照を手放す1回 (一意の側でも共有の側でも1回)、一意の側で残さないフィールドの `decref` を数える。箱の解放そのものは数えない
  - `boxes`: 実行した `box` の文の数。インタプリタは値をそのまま渡すので費用はほとんどないが、語の値の表現 ([ロードマップ](../future/roadmap.md) の S9) では費用になる変換なので数える
  - `unboxes`: 実行した `unbox` の文の数。数える理由は `boxes` と同じである
  - `peak_objects`: 同時に生きていたヒープの物体の数の最大。フレームと不死のリテラルを含む。ヒープは空いたスロットを先に使い、空きがないときだけスロットを足すので、スロットの数 (`Heap::peak_objects`) がそのまま最大になり、数える手間はない。仕事の回数ではないので、`main () = ()` でも `Frame::Root` のフレームの分だけ 0 にならない。フレームの伸びを見られる数はこれだけで、末尾呼び出しを失うと反復の数に比例して増える
- どの回数も時間ではなく、仕事か物体を数える。そのため、2乗の時間にならないことと、ループがフレームを積まないことを、ふだんのテストで確かめられる ([テスト戦略](../implementation/testing.md) の「性能のテスト」)。
