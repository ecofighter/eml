# レイアウト規則

位置づけ: 規範。

字下げからブロックの構造を決めるオフサイドルールを定める。lexer と parser の間に置くレイアウト段が、仮想トークンを挿入してブロックの開始・区切り・終了を parser に伝える。

## 基本

レイアウト段は、trivia を除いたトークン列に、幅 0 の仮想トークン `OPEN` (ブロックの開始)、`SEP` (項目の区切り)、`CLOSE` (ブロックの終了) を挿入する。

- 仮想トークンは parser の入力にだけ現れ、イベントには出さない (rowan の木には入らない)。そのため CST は lossless のままである
- レイアウト段は、行の先頭のトークンの列 (0 始まり) を、元のテキストから計算する

## 文脈のスタック

レイアウト段は、`Block(n)` (基準列 n のブロック)、`Bracket` (括弧の内側)、`Interp` (補間の穴の内側) からなるスタックを持つ。ファイル全体は `Block(0)` から始まる。

1. **行の先頭のトークン** (列 c) について、スタックの一番上が `Block(n)` なら次のように扱う
   - `c == n`: そのトークンの前に `SEP` を挿入する
   - `c < n`: `CLOSE` を挿入して `Block(n)` を取り除き、規則 1 をやり直す
   - `c > n`: 前の行の続き (継続行) とみなし、何も挿入しない
2. スタックの一番上が `Bracket` なら、改行は意味を持たない (何も挿入しない)。ただし、行の先頭のトークンが閉じ括弧でなく、その列が囲んでいる `Block(n)` の n 以下なら、閉じていない括弧のエラーとする。そのとき、`Block(n)` より上にある `Bracket` と `Block` をすべて取り除き (`Block` には `CLOSE` を挿入する)、規則 1 でそのトークンを扱う。閉じ忘れた括弧が、ファイルの残りを1つの項目に飲み込まないようにするためである。
3. **ブロックの開始**: 開始トークン `=` `->` `with` `then` `else` `where` が行の最後のトークンで (後ろにコメントがあってもよい)、次の行の先頭のトークンの列 m が、囲んでいる `Block(n)` の n より大きければ、`OPEN` を挿入して `Block(m)` を積む。m ≤ n ならエラーとする (字下げしたブロックが必要。E0009)。ただし、スタックの一番上が `{` の `Bracket` のときの `=` は、ブロックを開かず、エラーにもしない。`{` の中の `=` はいつもフィールドの `=` なので、フィールドの値を次の行に書けるようにするためである
4. **括弧と `,`**: 開き括弧 `(` `[` `{` は `Bracket` を積む。`{` で積んだ `Bracket` は、そのことを覚えておく (規則 3 の例外に使う)。閉じ括弧は、種類にかかわらず一番内側の `Bracket` より上にあるすべての `Block` を `CLOSE` で閉じてから、その `Bracket` を取り除く。`Bracket` がなければ何もしない。閉じ括弧の種類が対応しなければ parser がエラーにし、その括弧を閉じたものとして読む。行末の `,` (後ろにはコメントと空白だけが続く) は、一番内側の `Bracket` より上にある `Block(n)` のうち、次の行の先頭のトークンの列 c が n 以下のものを `CLOSE` で閉じ、その `Bracket` は残す。`,` の後には次の要素が続くので、行末の `->` などで開いたブロックを、次の行の要素の前で閉じるためである。c が n と等しい行も、そのブロックの次の文にはせず、括弧の次の要素として読む。次の行が一番内側のブロックより深ければ、継続行として読み、何も閉じない。ブロックの中で row を行に分けて書いたとき (`<IO,` の次の行に、より深く `Log>` を書く) に、そのブロックを閉じないためである。次の要素をブロックより深く書くと継続行になるので、次の要素はブロックの列か、それより左から書く。次の行の先頭が閉じ括弧のとき (末尾の `,`) と、`,` の後ろにトークンがないとき (ファイルの終わり) は、列によらず、その `Bracket` より上のすべての `Block` を閉じる。`Bracket` がなければ何もしない。行の途中の `,` はブロックを閉じない。ブロックの中の row (`<IO, Log>`) の `,` で、そのブロックを閉じないためである。補間の穴では次のように扱う
   - `INTERP_START` (`\{`) は `Interp` を積む。`INTERP_END` は、一番内側の `Interp` より上にある `Bracket` と `Block` をすべて取り除き (`Block` には `CLOSE` を挿入する)、その `Interp` を取り除く
   - 穴の中の閉じ括弧と `,` は、一番内側の `Interp` より上にある `Bracket` と `Block` だけを見る。そうした `Bracket` がなければ何もしない。穴の中の閉じ括弧と `,` で、穴の外の括弧とブロックを閉じないためである
5. **`;`** は、今のブロックの中での明示的な `SEP` として扱う。`Bracket` の直下で使うとエラーとする
6. ファイルの終わりで、残ったすべての `Block` を閉じる
7. 行の先頭のトークンは、ファイルの最初のトークンと、改行を含む trivia の直後のトークンだけである。`STRING_TEXT` と `RAW_STRING` の中の改行は trivia でないので、その後ろのトークンは行の先頭にならない。そのため、複数行の文字列の中の行と、閉じの `"""` の後ろのトークンは、レイアウトに影響しない。穴の中には改行がないので ([字句](lexical.md) の「穴の中の改行」)、`Interp` が規則 1 と規則 2 に出会うことはない

## 規則の帰結

- 行の性質は「直前の行の末尾」と「深さ」だけで決まる。開始トークンで終わらない行の後に深い行が続けば、それは式の続きになる

  ```haskell
  main () =
    let total =
      lines (read_text "data.txt")
        |> map parse_int
        |> sum
    println (show total)
  ```

- 開始トークンが行の途中にある場合は、ブロックを開かない。`let x = 1` や `if c then a else b` は1行の式になる
- 括弧の中では改行は区切りにならない (字下げは規則 2 の制約を受ける)。また、括弧の中でも開始トークンで行が終われば、ブロックを開ける (`map (fn x ->` の後に本体を続ける、など)。そのブロックは、閉じ括弧で閉じる
- 名前を変えても、ブロックの基準列は変わらない (Haskell の列規則と違い、開始トークンの右側の長さに依存しない)
- 括弧の中の行も、囲んでいるブロックより深く字下げする。閉じ括弧だけは、ブロックと同じ列の行の先頭に置ける。更新の `|` を行の先頭に書くときも、文の列より深く字下げする (`{ p` の次の行の `| age = 1 }` を文と同じ列に置くと、閉じていない括弧のエラーになる)

  ```haskell
  main () =
    run_all (
      first,
      second
    )
  ```

- レコードの `{` の中では、フィールドの `=` の後で改行してよい。括弧の中の要素の値で開いたブロック (行末の `->` の後のラムダの本体など) は、その値の最後の行の行末に書いた `,` で閉じる。次の要素は、そのブロックの列か、それより左から書く。ブロックより深く書くと、前の要素の継続行になる。末尾の `,` の後の閉じ括弧は、どの列に書いてもよい。タプルとリストの要素でも同じである。行の途中の `,` では閉じないので、`(fn x ->⏎  x + 1, n)` のように本体の最後の行の途中に `,` を書くと、その `,` はブロックの中にあり、エラーになる

  ```haskell
  let p = Person {
    name =
      long_name_of user,
    on_save = fn e ->
      log e,
    age = 3,
  }
  ```

- 複数行のシグネチャは、`->` を行の先頭に置いて書く ([宣言](declarations.md) の「シグネチャと等式」)。`->` で行を終えて次の行を同じ列に揃えると、規則 3 によりエラーになる

## `then` / `else` の前の `SEP`

ブロックの中で、`if` の後の `else` (と `then`) を `if` と同じ列に書くと、規則 1 により `SEP` が挿入される。

```haskell
  if c then
    a
  else
    b
```

parser は、`if` の解析中に、`then` / `else` の直前の `SEP` を1つ読み飛ばす (Haskell の DoAndIfThenElse と同じ扱い)。`else` で始まる文は存在しないので、曖昧さはない。
