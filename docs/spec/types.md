# 型と Kind

位置づけ: 規範。

eml の Kind、関数型、型推論の方式、型クラスの制約を定める。線形性の規則は [線形性](linearity.md)、エフェクトの多重度と handler は [エフェクトと handler](effects.md)、直積型の詳細は [直積型とレコード](records.md) で扱う。

## Kind

```
κ ::= Type<m> | Row<s> | κ → κ
m ::= Unr | Lin | μ          (μ は線形性の Kind 変数)
s ::= Never | Once | Multi | σ       (σ は多重度の Kind 変数)
Unr ≤ Lin,  Never ≤ Once ≤ Multi
```

- 線形性は Kind で区別する。`Unr` は何回使ってもよい値、`Lin` はちょうど1回使わなければならない値である。Affine は持たない。値を捨てるときは組み込みキーワード `drop` を明示する ([線形性](linearity.md))。
- `Row<s>` の `s` は、その row に含まれてよい操作の上限を表す。`Never` は `never` の操作だけを含んでよい。`Once` はさらに `once` の操作 (extern のエフェクトの `IO` を含む) まで、`Multi` はさらに `multi` の操作まで含んでよい。
- `Never` は、将来のマルチコア対応のために内部の束に最初から用意しておく。並列タスクの row を `never` の操作だけに制限するためである ([マルチコア対応の設計](../future/multicore.md))。内部の束は、最初から `Never ≤ Once ≤ Multi` の3要素で実装する。
- 内部では最初から Kind 変数と部分 Kind 関係を扱う。表面の構文では当面 Kind を書かせない。ユーザーが Kind を書けるようにするのは将来の拡張である ([ロードマップ](../future/roadmap.md))。
- データ型の Kind は、フィールドの Kind の上限 (join) で推論する。型引数を持つ `data` では、宣言ごとに Kind に効く型引数の位置を求める。フィールドに直接書いた型引数と、別の `data` の効く引数の位置に書いた型引数が効く。再帰する宣言があるので、すべての宣言で不動点を求める。`Option a` の Kind は `a` の Kind になる。フィールドに定数の `Lin` の型 (`File`、またはそれを含む `data`) が関数型の外に現れる `data` は、型引数によらず `Lin` である。関数型の中の型引数は効かない。フィールドに書いた関数型の線形性は、表面の構文で `m` を書けないので `Unr` に固定する (操作の引数の型と同じ扱い。見直しは [ロードマップ](../future/roadmap.md) にある)。
- `data` の型引数ごとに、その型引数が値の中で現れる位置の向き (変位) も求める。変位は「現れない」「作って渡す側 (共変)」「受け取る側 (反変)」「両方」のどれかである。フィールドは作って渡す側にあり、関数型の引数で向きを反転し、戻り値とタプルの要素ではそのまま保つ。別の `data` の型引数の位置では、その型引数の変位を重ねる。row のラベルの型引数は両方とする。extern の型は型引数を書けないが (E0011)、誤りとして書かれた型引数は両方として扱う。Kind と同じく、すべての宣言で不動点を求める。変位は、操作の結果の型の矢印をどう扱うかを決めるのに使う ([エフェクトと handler](effects.md) の「handler の意味」)。
- コンストラクタの型は、宣言の型引数で量化したスキーム (`Some : a -> Option a`) である。矢印の row は `<>`、線形性は `Unr` である。
- extern の型 ([宣言](declarations.md) の「`extern`」) の Kind は、処理系の表の行が決める。`Int`、`String`、`Unit` は `Unr`、標準ライブラリのモジュール `Fs` の `File` は `Lin` で、破棄処理 `close` を持つ ([エフェクトと handler](effects.md) の「組み込みの `IO`」)。
- extern のエフェクト (`IO`) の多重度は `Once` と決める。`IO` の操作は `never` の `io_failed` だけなので、操作から計算すると `Never` になるが、extern の関数がその場で1回だけ戻るので `Once` として扱う。

### 直積型と Unit

直積型は、構造的なタプルと、名前付きのレコード (`data` のコンストラクタの名前付きのフィールド) の2種類である。Unit は要素のないタプルである。タプルの Kind は要素の Kind の join で、`Lin` な要素が1つでもあればタプル全体が `Lin` になる。名前付きのレコードの Kind は、ほかの `data` と同じく上の規則で決まる。

射影と更新のフィールドの引き方は下の「フィールドの解決」で、構文、射影と更新の線形性の規則、実行時の表現は [直積型とレコード](records.md) で定める。

## 関数型

- 内部表現は `a -[m]-> <e> b` である。`m` は関数値自体の線形性、`e` はエフェクトの row を表す。
- 表面の構文では `m` を書かない (`A -> <E> B`)。`m` は Kind 変数として推論する。
- `Lin` の値を捕まえたクロージャは `Lin` になる (Rust の `FnOnce` に相当)。クロージャの `m` は、捕まえた値の Kind 以上になる。
- 後の段階に書き出す型の矢印は、線形性 `Lin` (`Unr`、`Lin`、宣言の Kind 変数 `Var(i)` のどれか) を持つ。instance の代入の後は `Unr`、`Lin`、`Poly` のどれかになる (下の「Kind の書き出し」)。
- 関数型どうしを単一化するときは、`m` も等しくする。`Unr` の関数を `Lin` の関数型の場所に渡す包摂は、まだ行わない ([ロードマップ](../future/roadmap.md))。
- handler の節の継続 `k` の型も普通の関数型である。形は下の「推論」にある。
- `A -> <E> B -> C` の row `<E>` は最初の `->` に付き、`A -> <E> (B -> C)` と読む。内側の `B -> C` の row は省略扱いになる。
- row の書き方は、閉じた row `<IO>`、開いた row `<IO | e>`、row 変数だけの `<e>`、空の row `<>` である。
- row のラベルは、エフェクトとその型引数である (`<State Int | e>`)。scoped labels の単一化では、同じエフェクトのラベルを、それぞれの row の中の順で対にし、対にしたラベルの型引数を単一化する。型引数が一致しなければ E2001 にする。
- **row を省略した `->` は、空の row `<>` を持つ** (純粋な関数)。トップレベルのシグネチャ、型の明示 `(e : T)`、ラムダの引数の型、`data` のフィールドの型のどこで省略しても同じである。エフェクトを持つ関数は row を明示する。

```haskell
twice : Int -> Int                         -- Int -> <> Int
log_twice : Int -> <IO> Unit               -- 本体で println を呼べる
map : (a -> <e> b) -> List a -> <e> List b -- エフェクトを通す高階関数は row 変数を書く
```

- エフェクトの操作のシグネチャ (`get : Unit -> s`) には、この規則を当てはめない。操作の型は [エフェクトと handler](effects.md) で定める。
- 省略した row の意味は、将来「1つのシグネチャの省略を、すべて同じ暗黙の row 変数とする」形に広げる可能性がある。広げるときは、既存のシグネチャの型がその特別な場合になる形でだけ行う ([ロードマップ](../future/roadmap.md))。

## 推論

- 型付けは、check モード (期待する型を上から渡す) と infer モード (型を下から求める) を持つ bidirectional 方式に単一化を組み合わせる。注釈のないローカルの `let` やラムダ式の引数には推論用の型変数を使い、単一化で解く。
- **トップレベルの関数と値は、シグネチャが必須**である。シグネチャは等式とは別の行に書き、対応は HIR で検査する ([宣言](declarations.md))。値の型はシグネチャで完全に決まるので、シグネチャの型変数は本体の中では rigid (固定された型) として扱う。
- シグネチャの型変数と row 変数は、その関数の等式の本体全体で見える。本体の型の明示とラムダの引数の型に書いた型変数は、シグネチャの同じ名前の変数を指す。シグネチャにない名前は、未定義の型の名前 (E1002) とする。型変数と row 変数は別の名前空間に置き、同じ名前を型と row の両方に使うと別々の変数になる。
- 等式の本体は、引数の数だけシグネチャの矢印をたどった残りの型に対して検査する。本体の row は最後にたどった矢印の row で、引数がなければ `<>` である。そのため、引数が矢印より少ない等式 (`add1 : Int -> Int` と `add1 = add 1`) も書ける。
- 値の型の多相化 (let 多相) は行わない。ローカルの `let` は単相で、注釈なしで推論する。
- トップレベルの関数の row は、シグネチャだけで決まる (省略した row は `<>`。上の「関数型」)。`<IO>` は閉じた row で、開くときは `<IO | e>` と書く。シグネチャの row 変数は、型変数と同じく本体の中では rigid とし、呼び出すたびに具体化する。そのため、関数の本体はシグネチャだけを見て1つずつ検査できる。
- 本体が、シグネチャの row に含まれないエフェクトを起こしたらエラーにする (E2002)。row を書き忘れた場合の誤りなので、シグネチャの矢印を指し、row を足す help を付ける。
- トップレベルの関数と extern の関数を値として参照するときは、型を具体化したうえで、戻り値の側に並ぶ矢印の閉じた row を新しい row 変数で開く (Koka と同じ)。純粋な関数を、エフェクトを持つ関数型の引数に渡せるようにするためである。関数型の局所変数と引数の型は開かない。
- 注釈のないラムダの型を推論するときは、各矢印の線形性と row に推論用の変数を使う。ラムダの本体のエフェクトは、外側の関数ではなく、ラムダの最後の矢印の row に入る。その row が閉じていて、含まれないエフェクトを本体が起こしたときも E2002 にする ([診断](diagnostics.md))。
- Kind はシグネチャから決まらないので推論する。シグネチャが必須なので、宣言の型の形はシグネチャだけで決まる。SCC の間で流れる情報は、多相化した後に残す Kind の制約 (Kind のスキーム) だけである。そこで推論を2段に分ける。1段目は関数ごとに、呼び出し先の型の形だけを見て本体を検査し、Kind の制約を集める。参照した宣言の制約は複写せず、どの宣言をどの Kind 変数で具体化したかを、Kind の具体化の記録として残す。2段目は、トップレベルの関数を呼び出しグラフの強連結成分 (SCC) ごとにまとめ、Kind の具体化の記録を展開して束の上で解く。同じ SCC の参照は、多相化する前の Kind 変数を共有するのと同じく、変数どうしの等式にする。前の SCC の宣言の参照は、そのスキームの制約を、具体化した変数について複写する。推論後に残った Kind 変数を多相化し、多相化した Kind 変数に関わる制約をスキームに残す。本体の型は、その SCC を解いた後に書き出す。書き出す型に Kind の解を入れるためである (下の「Kind の書き出し」)。
  - 残す制約は、多相化する変数から、多相化しない変数を通り抜けて、最初に出会う多相化する変数か定数までをたどって求める。多相化する変数どうしが制約の循環に入って等しくなるときは、それらが等しいことを残し、たどって出会った定数の境界をそのすべてに付ける。
  - 例: `dup : a -> (a, a)` を `dup x = (x, x)` と定義すると、本体で `x` を2回使うので、`a : Type<Unr>` という Kind 制約がシグネチャに加わる。
  - 使用回数から出る制約の規則は [線形性](linearity.md) の「基本の規則」にある。関数型の値を呼ぶことは、その値の1回の使用に数える。`twice f x = f (f x)` では `f` の `m` が `Unr` に決まる。
  - 持ち越し規則 ([エフェクトと handler](effects.md)) は、条件つきの制約 `carry(l, s)` を出す。`l` は持っている値の型の Kind の成分、`s` は呼び出しの row の多重度の成分で、「`l` が `Lin` なら `s ≤ Once`」を表す。線形性は多重度に依存しないので、線形性の束と多重度の束を解いた後に、`l` が `Lin` で `s` が `Multi` の組を違反とする。持ち越しの制約は上限を足すだけで、どちらの最小解も動かさない。
  - 多相化するときは、持ち越しの制約の両側を、下限の方向にたどって届く多相化する変数と定数に置き換え、同じ組は1つにまとめ、由来は位置が最も前のものを残す。由来ごとに残すと、多相な関数を重ねるたびに制約が増え、同じ違反を何度も報告するためである。両側が定数の組はその本体の中の違反なので残さない。具体化のたびに複製し、由来は呼んだ関数の名前と、元の由来の1段分の要約 (位置と、持っていた値の名前か通った関数の名前) を持つ形にする。報告は1段しかたどらないので入れ子にしない。表示は `carry(a, <e>)` (値が定数の `Lin` なら `carry(Lin, <e>)`、row が定数なら `carry(a, Multi)`) である。
- 継続の型は普通の関数型である。節の `k` は、状態なしなら `a -[m]-> <outer> r`、状態ありなら `a -[m]-> σ -[m₂]-> <outer> r` の型を持つ。専用の型や推論の種類はない ([エフェクトと handler](effects.md) の「handler の意味」)。`k` の呼び出しは、引数の数が分かる呼び出し先 (状態なしは1、状態ありは2) として評価の手順を決める ([式](expressions.md) の「関数適用」)。引数の個数の誤りは、普通の関数適用の誤りになる。
- 単一化の失敗が矢印の線形性の食い違いだけによるときは、診断の表示に線形性が出ないので、E2001 の期待した型と実際の型が同じ表示になる。このときは E2001 に、2つの関数型は呼べる回数が違う、という趣旨の note を付ける。どちらが線形かは、どちら側でも起こるので言わない ([診断の出し方](../implementation/diagnostics.md))。
- row は Leijen の scoped labels 方式で単一化する (Koka 方式の row 多相)。
- 呼び出しでは、呼び出し先の矢印の row が今の row に含まれることを確かめる。呼び出し先のラベルを今の row のラベルと同じエフェクトどうしで順に対にする。呼び出し先の末尾が推論用の変数なら、対にならなかった今の row の残りのラベルはその変数が受ける。末尾が rigid な row 変数のときは、次の項のとおり、残りのラベルから `mask` を作る。呼び出し先の row が閉じていれば、残りのラベルには関わらない。handler の節の継続 `k` の呼び出し `k v` も普通の呼び出しで、`k` の最後の矢印の row (handle の外側の row) を今の row に含めるので、同じ規則に従う。
- 呼び出し先の矢印の row が `<ls | e>` で `e` が rigid な row 変数のとき、`ls` と対にならずに `e` の手前に余った今の row のラベルを rest と呼ぶ。`e` の操作は、rest の handler をすべて飛ばして、今の row の `e` に当たる handler に届かなければならない。そこで、rest から handle できないラベルを除いたものを、その矢印の `mask` にする。`mask` の意味は [エフェクトと handler](effects.md) の「handler の意味」にある。例えば `run : (Unit -> <e> a) -> <State Int | e> a` の本体で `cb : Unit -> <e> a` を呼ぶと、rest は `State Int` で、`mask` は `State` になる。rest に同じエフェクトが2つあれば、`mask` もそのエフェクトを2つ持つ。呼び出し先の末尾が推論用の変数なら、余ったラベルはその変数が受ける。末尾が閉じた row なら、`ls` のラベルを今の row の同じエフェクトのラベルと前から順に対にするだけで、今の row の残りのラベルには関わらない。どちらも `mask` は空である。
- `mask` のエフェクトが `ls` にも現れたら E2008 にする ([診断](diagnostics.md))。呼び出し先が自分で起こす `L` は今の row の1つ目の `L` の handler に届き、`e` を通る `L` は rest の `L` をすべて飛ばさなければならない。`mask` は呼び出しの中の `L` の操作をすべて同じ数だけ飛ばすので、両方を同時には満たせない。
- `mask` は表面の構文に書かせない。Koka のように包含を拒んで `mask` を書かせると、自分のエフェクトを起こしつつコールバックを呼ぶラッパーのすべてに `mask` が要るためである。row を集合にする案と lacks 制約も採らない。集合にすると単一化の解が1つに決まらず、エフェクトのカプセル化も失う。lacks 制約は、シグネチャに新しい制約の形が要る。
- row を展開するとき、handle できないラベルの2つ目以降を落とす。展開した row は単一化、包含、表示のすべてが使うので、この規則はどこでも同じに効く。例えば `<IO | e>` の `e` に `<IO>` が入った row は `<IO>` である。handle できないラベルは、extern のエフェクトで、今は `IO` だけである。利用者は `IO` を handle できず、Prelude の `try_io` だけが handle する。extern のエフェクトは型引数を持たないので、まとめても型引数は食い違わない。`IO` の失敗は実行の時点で最も近い `try_io` に届くので、どちらの `IO` に届いても意味は同じである ([エフェクトと handler](effects.md) の「健全性」)。同じ理由で、extern のエフェクトは `mask` に入れない ([エフェクトと handler](effects.md) の「組み込みの `IO`」)。
- Kind の制約 (`m₁ ≤ m₂` など) は、束の上で最小の解を求める。相互再帰する関数では、SCC の中で不動点を求める。
- 型の明示 `(e : T)` は、`e` を check モードで `T` に対して検査する。
- 制約には必ず由来 (引数の位置、`if` の各枝、型注釈など) を記録する。型エラーの診断で使うためである ([診断の出し方](../implementation/diagnostics.md) の「型エラー」)。
- エントリポイントは `main : Unit -> <IO> Unit` である。入口のモジュールに `main` があれば、そのシグネチャがこの型でなければエラーにする (E2004)。`main` がないことは `eml check` ではエラーにせず、`eml run` だけがエラーにする (E2003)。`main` を持たないファイルも検査できるようにするためである。

### ローカル関数の推論

関数の形の `let` ([式](expressions.md) の「ローカル関数」) の型は、次のとおり推論する。

- 型は単相である。本体を検査する前に関数の型を置き、自分の参照も同じ型として扱う。外側の関数のシグネチャの型変数と row 変数は、本体でも見える
- 引数の数を n とすると、最初の n − 1 個の矢印の row は `<>` で閉じる。トップレベルの関数と同じく、引数を受け取るだけの矢印は何も起こさないためである。最後の矢印の row は推論する
- 最後の矢印の row は、本体を検査した後で、末尾が自由な推論用の変数なら `<>` で閉じる (`<IO | ρ>` なら `<IO>` になる)
- 外から呼ぶときは、閉じた row を今の row に含める。トップレベルの関数の呼び出しと同じく、handler の中でも外でも、呼ぶ順序によらず通る。これが成り立つのは、末尾が自由な変数のまま本体の検査を終えた場合だけである (下の閉じない例外)
- 値として参照するときは、トップレベルの関数と同じく、最後の矢印の閉じた row を新しい row 変数で開く (`map go xs` で、`go` を `<e>` の関数の引数に渡せる)。本体の中で自分を値として参照するときは、開かない単相の型を使う
- 閉じない例外がある。末尾の変数が捕まえた変数の型に現れるときは閉じない。捕まえた値の型を通して外側の推論とつながっていて、閉じると外側の型を勝手に決めるためである。関数自身の引数か結果の型に現れるときも閉じない。`let app f = f ()` のような高階のローカル関数のエフェクトは、引数から来るためである。外側のローカル関数の自分への呼び出し (下の 2 で記録するもの) がこの関数の中にあり、その呼び出しの位置の今の row に現れるときも閉じない。その包含は外側の row を閉じた後に確かめるので、先に閉じると外側の関数のエフェクトが入らない。末尾が本体の検査中に rigid な row 変数に決まったときも閉じない。例えば外側の関数の引数 `h : Unit -> <e> Int` を呼ぶと、その位置で本体の row の末尾が `<|e>` に決まり、その後の `ask ()` は row を広げられない。閉じる対象の自由な変数が残らないため、row はそのまま残る。これらのときは単相の row のまま残し、今のラムダと同じく、row が最初の呼び出しの位置で決まる。rigid な末尾の例では、`let go k = h () + ask () + k` が E2002 になり、`ask () + h () + k` の順なら通る

ローカル関数の検査は次の順に行う。

1. ローカル関数に、引数の数だけ矢印を持つ型を置く。最後でない矢印の row は `<>`、最後の矢印の row は推論用の変数にする
2. 本体を、ラムダと同じ手順で検査する。本体の中の自分への呼び出しは、包含の確かめをせず、呼び出しと今の row の組を記録しておく。row がまだ決まっていないためである
3. 最後の矢印の row の末尾が自由な推論用の変数のままで (rigid な変数に決まっておらず)、捕まえた変数の型にも、関数自身の引数と結果の型にも、外側のローカル関数の自分への呼び出しで記録した今の row にも現れなければ、`<>` で閉じる
4. 2 で記録した自分への呼び出しについて、包含を確かめ、`mask` を記録する。自分が handler を張って、その中で自分を呼ぶ形も、トップレベルの関数と同じく通る

### row の具体化の記録

Core IR の単相化は、row を「yield しうるか」だけで分ける ([Core IR](core-ir.md) の「row のビットと instance の鍵」)。そのために、型検査は次を記録する。

- 参照ごとの具体化 (`Instantiation`) は、型引数 `args` に加えて、row 変数の具体化 `rows: Vec<RowYield>` を持つ。並びは、参照先のシグネチャの row 変数の順 (`generics.row_vars` の順) である。シグネチャが row 変数を持たなければ空である
- `RowYield` は、具体化した row が yield しうるかを、参照を含む定義の row 変数に対して表す
  - `Always`: ラベルを1つ以上含む。`IO` も含む。`IO` を起こす extern は失敗すると `try_io` まで中断するためである。または、末尾が参照を含む定義の row 変数でない rigid な row 変数である (操作のシグネチャの row 変数を、節の中で具体化したものなど)
  - `Never`: ラベルを含まず、閉じているか、末尾が型検査で最後まで決まらなかった row 変数である。決まらなかった row 変数には、どのエフェクトも求められていないので、yield しうる値はそこを通らない (`fn h -> h 1 + 1` を使わずに置いた形)
  - `Var(i)`: ラベルを含まず、末尾が参照を含む定義の i 番目の row 変数である。ラムダ、ローカル関数、handle の本体、節の中の参照では、それらを含むトップレベルの定義 (instance のメソッドの関数と既定のメソッドを含む) の row 変数を指す
- 関数の本体が動く row (関数の型の、引数の数番目の矢印の row。`BodyTypes::body_yield`)、ラムダとローカル関数の本体が動く row (ラムダで最後にたどった矢印の row。`BodyTypes::lambda_yields`。ローカル関数も引ける)、呼び出しの矢印ごとの row (`BodyTypes::arrow_yields`。キーは `mask` の表と同じく、呼び出しの式と矢印の番号の組)、宣言の型の最初の矢印の row (`BodyTypes::first_arrow_yield`。関数型でなければ `Never`) も、同じ `RowYield` に分類して記録する。最初の矢印の分類は、入口を `()` で呼ぶ関数の印に使う ([Core IR](core-ir.md) の「`yields` の印」)
- 分類は、rigid な row 変数がどの定義のものかを型検査が知っている間に行う。書き出した型の rigid な末尾は名前でしか区別できず、操作の row 変数と定義の row 変数を取り違えるためである

### Kind の書き出し

`eml_types` が後の段階に書き出す型は、矢印の線形性と、決まらなかった型変数の Kind を持つ。Kind の印 (`unr` / `lin` / `poly`) は、この型から決める ([Core IR](core-ir.md) の「Kind の印」)。

印は、解く前の型の形だけからは決められない。そのため、解いた Kind を型に持たせて書き出す。たとえば `tests/ui/run/files/file_in_return_clause_on_abort.em` では、使われない `return x ->` の `x` は型が `_` で、`x` の Kind を `Unr` に決めるのは使用回数のパスである。型の形だけから決めると `x` は `poly` になり、Perceus が出す `decref x` を V1 が拒む ([LIR](lir.md) の「Kind の印の検査」)。

#### 書き出す時点

本体の型は、呼び出しグラフの SCC を呼ばれる側から順に、SCC ごとに「本体の検査、Kind の解決、型の書き出し」の順で処理する。本体の検査はシグネチャしか読まないので、SCC の順に検査しても結果は変わらない。Kind を解く前に型を書き出す箇所 (診断の文言、導出した instance のフィールドの検査) は、線形性を読まない。そこでは、決まっていない矢印を `Poly` に、決まらなかった型変数を `Flexible(Poly)` にする。診断の表示は線形性を書かないので、文字列は変わらない。

#### 書き出す型の形

線形性は公開の型 `Lin` で表す。

- `Unr`、`Lin`: 決まった線形性
- `Poly`: 呼び出し側が決める線形性。instance の代入の後の型、診断のために書き出す型、結果の型にだけ現れる `OpVar` (と、代入でそれから作る `Flexible`)、一様な位置と entry と導出とタプルの生成器の鍵の `Flexible` に現れる
- `Var(i)`: 宣言の Kind 変数。instance の代入が `Unr`、`Lin`、`Poly` に置き換える

型の形は次のとおりである。

- `Fn { param, lin, effects, tail, ret }`: 矢印の線形性 `lin`
- `Flexible(Lin)`: 推論で決まらなかった型変数、一様な位置と entry と生成器の鍵の型変数、代入で `OpVar` から作った型変数の Kind
- `OpVar(名前, Lin)`: handler の節で操作ごとに量化した型変数の Kind
- `Rigid(名前)` は Kind を持たない。シグネチャの型変数の Kind は宣言の Kind 変数 (`μ`) で、instance の代入で型引数に置き換わるためである

多重度 (`once` / `multi`) は書き出さない。

#### 宣言の Kind 変数の番号

`Var(i)` の番号は、宣言ごとに付ける。

- `i < lin_vars` は、宣言自身の線形性の Kind 変数である。番号は、型変数の `μ` と矢印の `m` を外側から数えた順である
- `i >= lin_vars` は、本体の変数の要約である。`Var(lin_vars + k)` は、宣言自身の変数の集合 `joins[k]` の結びを表す。同じ集合は同じ番号を共有し、番号は、式、局所変数、パターン、具体化、更新、捨てたフィールドの表を ID の順にたどって、集合が初めて現れた順に振る
- 集合が1つの変数だけなら、その変数の `Var(i)` を使う。集合の変数がすべて定数に畳まれたときは、集合も定数に畳む

本体の型の `Var` は、その本体を含むトップレベルの宣言 (instance のメソッドの関数と既定のメソッドを含む) の番号で数える。ラムダ、ローカル関数、handler の節も、含む宣言の番号を使う。同じ `Var(3)` でも宣言が違えば意味が違うが、`TypeId` は同じになる。

#### 書き出すときの規則

宣言の中の Kind 変数は、SCC で合わせた制約のグラフの強連結成分の上で決める。同じ成分の変数は等しい。宣言自身の変数を含む成分に出会ったら、そこから先はたどらない。

本体の変数 (ラムダの矢印、部分適用と具体化の変数、handler の状態の矢印など) には、解の最小値を取る。

- 成分が宣言自身の変数を含むなら、その中で番号のいちばん小さい変数の `Var(i)` にする。その変数が定数に畳まれていれば、その定数にする
- そうでなく、下にたどって定数の `Lin` に届けば `Lin` にする
- そうでなく、下にたどって届く宣言自身の変数がなければ `Unr` にする
- そうでなければ `Var(lin_vars + k)` にし、届いた宣言自身の変数の集合を `joins[k]` に記録する。届いた成分が宣言自身の変数を2つ以上含むときは、その中で番号のいちばん小さい変数を記録する
- `joins` の集合は、定数に畳まれた変数で整える。`Lin` に畳まれた変数を含めば集合全体を `Lin` にし、`Unr` に畳まれた変数は集合から除く。残りが空なら `Unr`、1つならその `Var(i)` にする

1つ目の場合を外すと、宣言自身の変数と等しい本体の変数が `Unr` になり、正しくない。たとえば `f : (a -> <IO> Unit) -> a -> Int -> <IO> Unit` を `f eat x n = if n == 0 then eat x else f (fn g -> eat (g ())) (fn () -> x) (n - 1)` と定義すると、`fn () -> x` の矢印は再帰の呼び出しで `μ_a` と等しくなる。`main` が `a` を `File` で呼ぶと、この関数は `File` を捕まえる。

宣言自身の変数のうち、定数だけで値が決まるものは、宣言の型でも本体の型でも定数に畳む。どの instance でも同じ値になるためである。スキームの辺を上にたどって定数の `Unr` に届けば `Unr` に、下にたどって定数の `Lin` に届けば `Lin` に畳む。`Var` は、instance によって値が変わる所にだけ残る。

最小値を取るのは、捕まえた値や束縛した値から決まる下限が、実行時の値の正直な Kind だからである。決まらなかった row 変数を `RowYield::Never` にするのと同じ選び方である (上の「row の具体化の記録」)。「最小と最大が一致すれば確定し、ずれれば `Poly`」という規則は採らない。使い方が `Unr` を強いないラムダは最大が `Lin` になるので、1回だけ呼ぶラムダや `apply` に渡すラムダが軒並み `Poly` になり、`id (fn x -> x)` の鍵も `Int %m -> Int` になって instance が分かれるためである。

#### instance での評価

`TypedProgram::kind_values(decl, args, store)` は、宣言 `decl` の `Var(i)` の値を、型引数 `args` (`Shape::rigids` の順) の instance について求める。値は `Unr`、`Lin`、`Poly` のどれかである。結びの順は `Lin` > `Poly` > `Unr` とする。値は、宣言のスキーム (宣言自身の変数の間の制約と、定数の境界) の上で求める。

- `Unr` への固定: 宣言自身の変数 `v` から、スキームの辺を上にたどって定数の `Unr` の上限に届くとき、`v` は `Unr` に固定されている。たどるのは辺と定数だけで、型変数 `μ` の instance での値は使わない
- 値 `val(v)`: `v` が `Unr` に固定されていれば `Unr` である。そうでなければ、`base(v)`、`v` の定数の下限、スキームで `v` の下にある宣言自身の変数 `w` の `val(w)` の結びである。`base(μ_i)` は `linearity(args[i])`、矢印の `base(m)` は `Poly` である。矢印の値は呼び出し側が決めるためである
- 本体の要約 `Var(lin_vars + k)` の値は、`joins[k]` の各変数の `val` の結びである

スキームで輪になった変数は、どれも同じ値になる。固定は輪を通じて伝わり、結びも輪の中で等しくなるためである。

型変数の値に、下にある矢印の `val` を結ぶのは、SCC の中の多相再帰で、型変数 `a` に関数を渡すと、スキームに `m ≤ μ_a` が残るためである。次の `f` では、`k` が `x`、`eat`、`g` を捕まえ、再帰の呼び出しで `a` として渡される。

```haskell
f : a -> (a -> <IO> Int) -> (Int -> <IO> Int) -> Int -> <IO> Int
f x eat g n =
  if n == 0 then g (eat x)
  else
    let k = fn y -> g (eat x + y)
    f k (fn h -> h 1) (fn z -> z) (n - 1)
```

`main` が `g` に `File` を捕まえたクロージャを渡して `f@[Int]` を呼ぶと、`k` はそのクロージャを捕まえる。`k` の矢印は `μ_a` と同じ成分にあるので `Var(μ_a)` になる。`μ_a` の値を `linearity(Int)` と定数だけから求めると `Unr` になり、`File` を持つ `k` が `unr` になってしまう。`val` では `g` の矢印の `Poly` が `μ_a` に伝わるので、`k` は `Poly` になり、再帰の呼び出しは `f@[Int %m -> Int]` になる。

`Unr` への固定で `μ` の instance での値を使わないのは、次の食い違いを避けるためである。同じ SCC の別の宣言の具体化の変数 (下限を持つ) が、この宣言の `μ` と等しくなると、スキームに `m ≤ μ` が残りうる。このとき、多相再帰の instance `f@[Int]` で `μ` の値 `Unr` を `m` の上限に使って `m` を `Unr` にすると、外の呼び出し元が複写したスキームでは同じ `m` が `Lin` になり、`unr` と `lin` が食い違う。`m ≤ μ ≤ Unr` のように `μ` が定数の `Unr` の上限を持つ場合は、どの instance でも `m` は `Unr` なので、辺をたどって固定としてよい。

instance の鍵は型引数だけである。Kind の値は宣言と型引数から決まるので、鍵に入れない。呼ばれる側の矢印の変数は鍵に入らず、instance の中では `Poly` になる。`map` を `lin` のクロージャで呼んでも `unr` のクロージャで呼んでも、instance は1つである。

#### `Flexible` と `OpVar` の Kind

| 出どころ | Kind |
|---|---|
| 本体で推論が決めなかった型変数 | 上の「書き出すときの規則」の最小値。正しいプログラムでは値を作れる所で型が決まるので、ふつうは `Unr` |
| 関数の一様な位置と entry の鍵 | 呼ばれる側のスキームで `μ` が `Unr` に固定されていれば `Unr`、そうでなければ `Poly` (`TypedProgram::uniform_kind`) |
| 導出とタプルの生成器の一様な位置の鍵 | `Poly` |
| `OpVar` | 操作の引数の型に現れれば `Unr`、結果の型にだけ現れれば `Poly` |

一様な位置と entry の鍵を `Lin` にしないのは、スキームが `Lin ≤ μ` を持っていても、`Int` の呼び出し元は `unr` の値を渡すからである。

`OpVar` の Kind は、一般の規則ではなく、操作ごとの rigid 変数が「操作の引数の型に現れる」かで決める。引数の型に現れる `OpVar` は、節がその `μ` を `Unr` 以下に縛っているので `Unr` にする。結果の型にだけ現れる `OpVar` は、節の中では `Lin` 以上に縛っているので最小値は `Lin` になるが、実際の値は操作を呼ぶ側が決めるので `Poly` にする。節の中でこの値を捕まえたクロージャは、下限が `Lin` なので `Lin` になる。`OpVar` の Kind は定数なので、型変数のない関数の本体にある節のように代入しない型でも、`linearity` が読める。

#### 型の線形性

`TypeStore::linearity(ty)` は、型の値の線形性 (`Unr`、`Lin`、`Poly`) を返す。値は型を登録するときに子の値から求めて型ごとに持つ。

- `Con`: 宣言が `Lin` なら `Lin`。そうでなければ効く型引数の値の結びで、効く型引数がなければ `Unr`
- `Tuple`: 要素の値の結び。要素がなければ `Unr`
- `Fn`: その `lin`
- `Flexible(k)` と `OpVar(_, k)`: `k`
- `Error`: `Unr`
- 値が `Rigid` か `Var` に依存する型は、宣言に対して相対的な型なので、意味のある値を持たない。debug ビルドでは読むと止まる。宣言の中の値は `kind_values` が求める

## フィールドの解決

射影 `e.f` と更新 `{ e | f = v }` のフィールドは、その時点で分かっている `e` の型から引く。`e` の型を推論し、その時点の型の代表を見て、次のように場合を分ける。本体の終わりまで解決を遅らせる仕組みは持たない。

- コンストラクタが1つの `data` で、そのコンストラクタが名前 `f` のフィールドを持つ: そのフィールドの型を、型引数で具体化したものが結果になる
- タプルで、`f` が範囲内の番号である: その要素の型が結果になる
- 推論用の型変数 (まだ決まっていない): E2013 にする。help で型の明示を促す ([診断の出し方](../implementation/diagnostics.md) の「番号ごとの出し方」)
- `Error`: 何も報告しない
- それ以外: E2014 にする。名前のフィールドを持たない型、範囲外の番号、名前で指したタプル、番号で指した `data`、シグネチャの型変数、関数型、コンストラクタが2つ以上の型が当たる。更新は名前でだけ書けるので、タプルの更新も E2014 である

更新では、各 `v` を、引いたフィールドの型に対して検査する。結果の型は `e` の型のままである。`e` の型が決まっていなければ、E2013 を1件出し、フィールドの式は推論だけする。作る式は、コンストラクタを参照と同じく具体化し、各フィールドの式を、そのフィールドの型に対して書いた順に検査する。結果の型、線形性、持ち越し、網羅性は、位置のコンストラクタの呼び出しと同じである。作る式と更新のフィールドの型の誤り (E2001) は、フィールドを由来にして報告する。

射影と更新が捨てるフィールド (射影の残りのフィールドと、更新で上書きされる古いフィールド) は、具体化した型で線形性の検査に渡す。`_` で受けたのと同じ扱いである ([直積型とレコード](records.md) の「線形性の規則」)。型変数の Kind の制約は、今までどおり使い方から推論する。

### 引数のラムダを後で検査する

射影は、その時点で型が分かっていることを求める。そのため、呼び出しの引数のうちラムダは、ほかの引数の後に検査する。`map (.name) people` を注釈なしで書けるようにするためである。後に回すのは、直接の引数として書いたラムダ (`(fn x -> …)` の括弧は HIR で消える) と、HIR が組んだラムダ (フィールドのセクション、演算子のセクション `(+ 1)` と `(+)`) である。`use` が組んだラムダ、型を明示したラムダ (`((fn x -> …) : T)`)、ラムダを返す式は後に回さない。`use` が組んだラムダを後に回さないのは、`use` のブロックの型の誤りを、シグネチャを指す形のまま報告するためである。後に回すと、書いていないラムダの中の誤りとして報告される。

1. 引数を左から1つずつ見る。矢印は、その引数の直前に取り出す。すべての矢印を先に取り出すと、ラムダのない呼び出しの引数の数の誤り (`konst 1 2 3`) が、型の不一致の誤りに変わるためである
2. ラムダでない引数は、すぐ検査する。その矢印の row は、それより前にラムダを後に回していなければ、すぐ今の row に入れる。後に回していれば、row も後に回す
3. ラムダは、矢印の引数の型と由来を覚えて後に回し、その矢印の row も後に回す
4. 次の矢印を取り出すときに、呼ばれる側の型が推論用の型変数で、後に回したラムダがあれば、先に後に回したラムダを検査して、後に回した row を入れる。ラムダが決める型変数を、余りの引数のための関数型にしないためである。`apply (fn x -> x) 1 2` は、ラムダのない呼び出しと同じく、引数の数の誤りになる
5. 引数を見終えたとき、呼び出しを期待する型に対して検査していて (check モード)、後に回したラムダがあれば、結果の型を先に期待する型と単一化する。結果の型は、部分適用の残りの row を開いた後の型である。`people |> map (.name)` で、`map` の型変数を先に決めるためである。単一化の誤りは「期待する型との不一致」として呼び出しの位置に報告し、後で期待する型と比べ直すことはしない
6. 後に回したラムダを、左から、覚えた引数の型に対して検査する
7. 後に回した row を、引数の順に今の row に入れる。ラムダの本体が row 変数を決めてから row を入れるためである (`try (fn () -> deploy ())`)

- 呼ばれる側の型が壊れているとき (`Error`) と、引数が矢印より多いときは、それまでに後に回したラムダを、覚えた引数の型に対して検査する。ラムダの型は誤りより前の矢印で決まっているので、ラムダの中の誤りを、後に回さないときと同じく報告するためである。矢印に当たらない残りの引数のうち、ラムダは `Error` の型に対して検査し、引数を `Error` で束縛する。推論すると引数に新しい型変数が付き、射影の E2013 が連鎖するためである。引数が多すぎるときは、呼び出しの型を `Error` にして、期待する型と1回だけ比べる
- 評価の順と、持ち越しと線形性の検査の順は変えない。どちらも別のパスで、ソースの順にたどる
- 型の誤りを報告する位置が、ラムダを後に回さない検査と変わることがある。たとえば `map (fn x -> x + 1) ["a"]` の誤りは、`"a"` でなく、ラムダの中の `x + 1` に出る
- 後に回したラムダどうしは、左から検査する。そのため、後のラムダが前のラムダの引数の型を決める形は書けない。`compose (fn b -> b.name) (fn p -> p.boss) x` は、最初のラムダを検査する時点で `b` の型が決まらず、E2013 になる。最初のラムダの引数に型を明示する (`fn (b : Person) -> b.name`)

## 制約

シグネチャの文脈 `Eq a =>` に書いたものを制約と呼ぶ。制約は、クラスとシグネチャの型変数の組である。制約を持つ関数やメソッドを参照するたびに、型変数を具体化した制約が満たされなければならない。クラスと instance の宣言は [宣言](declarations.md) の「クラスと instance」にある。

- 制約は、トップレベルのシグネチャに推論で足さない。解けない制約と曖昧な制約はエラーにする。単相性制限と defaulting は持たないので、何も型を決めない値を `Int` に倒すことはしない。例外は REPL の式の入力だけである (下の「REPL の入力」)
- 線形性は Kind のままにする。`Copy` や `Drop` のようなクラスは作らず、Kind は instance の選択に関わらない
- クラスとエフェクトは別の仕組みである。メソッドの row は、普通のシグネチャと同じ規則に従う。Prelude のクラスのメソッドは純粋なので、`par` の中でも使える
- 制約の証拠 (どの instance を使うか) は記録しない。参照ごとの具体化の表の型引数から、単相化が instance を引き直す ([Core IR](core-ir.md) の「メソッドの解決」)。eml の型が rank-1 で、局所的な `let` とラムダが単相で、操作とコンストラクタが制約を持たないので、制約のない本体の中の制約付きの参照は、どれも具体的な型で解ける

### `Unr` のクラス

今のクラスは、すべて `Unr` のクラスである。`Lin` の型を受けるクラスは、将来クラスの性質として区別して入れる。そのときも、今のクラスの意味は変えない ([ロードマップ](../future/roadmap.md) の「型システム」)。`Unr` のクラスは次の規則を持つ。

- 制約 `C a` は `a ≤ Unr` を意味する。シグネチャの制約は、そのシグネチャの Kind のスキームに `a ≤ Unr` を足し、本体はその型変数を `Unr` とみなして検査する
- 本体の検査で足すこの境界は、破れても報告しない (由来 `Provenance::Given`)。境界が破れるのは、同じ SCC の参照が型変数を `Lin` の型で具体化したときだけである。そのときは、その参照の制約が解けない (E2006)、`Lin` の頭の instance で解ける (E2010 を報告済み)、または解いた先の型引数に下の `Ti ≤ Unr` を求める、のどれかになり、誤りはいつもほかの所で報告される
- instance の本体は、頭の型変数をすべて `Unr` とみなして検査する。本体は、頭の型変数の型の値を自由に写し、捨ててよい
- そのため、instance で `C (H T1 … Tn)` を解くたびに、参照のある本体の Kind の制約に `Ti ≤ Unr` をすべて足す。タプルを要素ごとに解くときも、要素の型に `Unr` を求める。導出した instance とタプルの instance は、要素を写し、捨てるためである。`data G b = | G (Unit -> b)` は `b` によらず `Unr` なので、この規則がないと、文脈のない `instance Show (G b)` の本体が `b` の値を作って捨てられ、`G File` で線形性が破れる。`Ti ≤ Unr` は、制約がすべて解けた参照にだけ足す。解けなかった参照は誤りを報告済みなので、線形性の診断を重ねない
- instance の頭は、頭の型変数をすべて `Unr` としたときに `Unr` でなければならない (E2010)。定数の `Lin` のフィールドを持つ `data` と、extern の `Lin` の型 (`Fs.File`) は、instance を持てない。E2010 の instance のメソッドの本体は、使用回数を数えられない本体と同じく扱い、線形性の診断を出さない。本体は頭の値を `Unr` とみなして書いたものなので、その診断は E2010 の連鎖である
- クラスのメソッドのシグネチャに書いた関数型 (一番外側の矢印を除く) の線形性は `Unr` に固定する。操作の引数とフィールドの関数型と同じ規則である。メソッドのシグネチャは本体を持たず、矢印の線形性を推論できないためである

### 制約の解決

- メソッドの型のスキームは、クラスの型変数を先頭に、メソッド自身の型変数を後ろに並べ、制約の先頭にクラスの制約 `C a` を持つ。メソッドへの参照の型引数も、この順に記録する
- 関数の参照はシグネチャの制約を、メソッドの参照はクラスの制約 `C T` (T はクラスの型変数の型引数) とメソッド自身の制約を、型引数に写して求める。求める制約は、参照の位置とともに集める
- 本体の単一化が終わった後で、求める制約をまとめて解く。後の文の単一化で型が決まることがあるためである。線形性の検査 (使用回数のパス) より前に解く
- 与えられた制約は、本体ごとに次のものを上位クラスでたどって閉じたものである
  - トップレベルの関数: シグネチャの制約
  - instance のメソッド: instance の文脈と、メソッド自身の制約
  - 既定のメソッド: クラスの制約 `C a` と、メソッド自身の制約
- `C T` は `T` の形で場合を分けて解く。instance の文脈とタプルの要素へ進んだ先も、同じ規則で解く
  - 型コンストラクタの適用 `H T1 … Tn`: `(C, H)` の instance を探す。あれば、instance の文脈を `Ti` に写して解き、上の `Ti ≤ Unr` を足す。導出した instance も同じである。なければ E2006 にする
  - タプル (`Unit` を含む): `C` が `Eq`、`Ord`、`Show` なら、要素ごとに `C Ti` を解く。ほかのクラスにはタプルの instance がないので、E2006 にする
  - シグネチャの型変数: 与えられた制約にあれば解ける。なければ E2006 にする
  - 関数型と、handler の節の操作ごとの型変数: E2006 にする。操作ごとの型変数はシグネチャに書けないので、与えられた制約に入らない
  - 最後まで決まらない推論用の変数: E2009 にする。本体にほかの誤りがあれば出さない。誤りを直せば型が決まりうるためである
  - `Error` を含む型: 何も出さない (連鎖の抑止)
- 誤りは参照の位置に出す。1つの参照から出た誤りは1つにまとめる。instance がない制約 (E2006) があれば、その最初のものを報告する。なければ、最初の決まらない制約 (E2009) を報告する。決まらない型は注釈で直せるが、instance がないことは注釈では直らないためである。E2006 と E2009 は本体の誤りに数え、線形性の診断を連鎖させない
- 1つの制約を解く間、同じクラスと同じ型 (推論の表の代表) の組は1回だけ解く。推論の表は部分を共有するので、型を木としてたどると型の深さの指数の時間がかかるためである
- 証拠が循環に沿って大きくなる制約付きの多相再帰 (入れ子のデータ型の `Show` など) は、型検査の後に E2012 にする。判定には単相化の一様な位置のグラフを使う ([Core IR](core-ir.md) の「一様な位置と制約付きの多相再帰」)

### instance と既定のメソッドの検査

- 上位クラスの instance があることを確かめる。`instance Ord a => Ord (Option a)` なら、`{Ord a, Eq a}` のもとで `Eq (Option a)` が解けなければならない。上位クラスの instance がないか、その文脈がこの instance の文脈から導けなければ、instance の頭を指して E2006 にする
- instance のメソッドと既定のメソッドは、Kind の推論の SCC に普通の関数として入る。既定のメソッドは、クラスの中で1回だけ検査する
- メソッドの Kind の規則は次のとおりである (E2011)
  - クラスのメソッドの Kind のスキームは、同じシグネチャの extern の関数と同じく、宣言だけから作る (部分適用のクロージャの Kind)。クラスの型変数と、制約を持つ型変数は `Unr` である
  - instance のメソッドの Kind のスキームは、次の前提のもとで、クラスのメソッドのスキームから導けなければならない。前提は、クラスの型変数を頭の型に置き換えたことと、頭の型変数がすべて `Unr` であることである
  - 既定のメソッドの Kind のスキームは、クラスの型変数が `Unr` であることを前提に、クラスのメソッドのスキームから導けなければならない
  - 導けない制約 (線形性と多重度の境界、持ち越しの制約) があれば E2011 にする。残るのは、メソッド自身の型変数と、シグネチャの row の多重度に関わる制約である。たとえば `class Pairable a where pair_with : a -> b -> (b, b)` の instance が `b` の値を2回使うと `b ≤ Unr` が要るので、E2011 になる。`b` の値を持ったまま row `e` の呼び出しをまたぐと `carry(b, e)` が要るので、これも E2011 になる。メソッドのシグネチャで `b` に制約を書けば、`b` は `Unr` になる
  - 本体に誤りがあって使用回数を数えられないときは、E2011 を出さない
  - Prelude のクラスのメソッドはメソッド自身の型変数を持たないので、この規則で誤りになる Prelude の instance はない

### 導出した instance の検査

- 各フィールドの型 `F` について、導出した instance の文脈のもとで `C F` が解けることを確かめる。解けなければ、`deriving` のクラス名を指して E2006 にし、どのフィールドかを note で示す。同じ位置に誤りを重ねないよう、報告は instance ごとに、最初に解けなかったフィールドの1つだけにする
- 頭が `Unr` でなければ E2010 にする。そのときはフィールドの E2006 を重ねない。`Lin` のフィールドには instance がないためである
- 上位クラスの instance の検査は、手で書いた instance と同じである

### 方式を選んだ理由

ネイティブ化と VM の効率を重視し、Haskell の型クラスを第一の候補として次の案を比べた。

| 案 | 結論 |
|---|---|
| 型クラス + 辞書渡し (GHC) | 採らない。VM で `+` が extern 1つから、辞書の取り出しと間接呼び出しになる。実行時に辞書の値、射影の Rhs、借用の扱いが要る |
| 辞書渡し + 既知の instance の静的解決 + 特殊化 | 採らない。無償になるのは文脈のない instance だけで、`List Int` の `==` や導出した instance は辞書を通る。辞書の仕組みと複製の仕組みを両方持つことになる |
| Rust のトレイト + すべての総称の単相化 | 採らない。データの配置まで型ごとに分けると、多相再帰と操作ごとに量化した型変数の節で一様なコードと配置が食い違い、言語を制限することになる。関数のコードの単相化は採った ([Core IR](core-ir.md) の「変換の規則」) |
| 組み込みの型だけの多重定義 | 採らない。ユーザー定義の型に広げられない |
| 実行時に値の構造をたどる方式 (OCaml、Gleam) | 採らない。型クラスに移るときに捨てる機構になる |
| 暗黙の引数 (Koka、modular implicits) | 採らない。修飾付きの import と衝突し、型クラスのまとまりも失う |
| クラスをエフェクトで表す | 採らない。row を汚し、解決が動的になる |
| **型クラス + 関数のコードの単相化** | **採る**。証拠は単相化の instance の表で確定する。データの配置は一様のままにする |

採った案が成り立つのは、eml の型が rank-1 で、シグネチャが必須で、局所的な `let` とラムダが単相で、局所的な instance も第一級の instance もなく、操作とコンストラクタが制約を持たないためである。この条件では、制約のない本体での制約付きの参照は、すべて確定した証拠を持つ。Roc (RC とその場の更新の実行系) と Austral も型クラスや abilities を特殊化で実行するが、どちらも総称をデータの表現まで含めて単相化する。eml は関数のコードを単相化するが、データの配置は一様のまま残し、多相再帰で大きくなる型変数の位置と操作の節の型変数は一様に扱う。そのため、row の多相にも触れない。代償は、複製の分だけ増えるコードの大きさと、REPL で新しい型の組を使うたびに変換が1つ増えることである。

## REPL の入力

REPL の `let` の束縛と式の入力 ([モジュールと名前解決](modules.md) の「REPL のセッション」) は、シグネチャなしで、局所の `let` と同じく単相に推論する。どちらも関数 `input$N : Unit -> <IO> T` の本体として検査し、`T` を推論する。入力の関数はほかの関数から参照されないので、1つだけの SCC として、ほかの関数と同じ道で Kind を解いて書き出す。`let` の束縛を参照する関数は、呼び出しのグラフでその束縛の入力の関数に辺を持つので、束縛の型が決まってから検査する。

- `let x : T = e` の型の明示は、局所の `let` と同じく扱う
- 残った Kind の変数 (関数型の線形性を含む) は `Unr` に、残った row 変数は `<>` に決める。束縛の型は後の入力の宣言の型になるので、変数を残さない
- row が `<IO>` に収まらなければ E2015 にする
- `let` の束縛の型と式の入力の型が `Unr` でなければ E2016 にする。入力の中の `Lin` の値は、線形性の検査でその入力の中で使い切らせる
- 式の入力では、本体の推論を終えた後、制約を解く前に、残った型変数を `Unit` に決める。式の `[]` や `show []` を通すためで、GHCi の拡張の既定の規則と同じ考え方である。決めた型で解けない制約は、E2006 でなく E2009 にする。型を決めたのは処理系で、利用者は型を書いていないためである
- `let` の束縛では defaulting しない。残った型変数は E2017 にし、help で型の明示 (`let x : T = e`) を勧める。`let id = fn x -> x` を `Unit -> Unit` に決めると、型の誤りが何入力も後に、原因から離れて出るためである
- 式の入力の表示の仕方 (`InputDisplay`) は、型が決まった後に決める。型が `Unit` なら `Unit` (何も書かない) である。`Show T` の制約が完全に解ければ `Value` (値だけを書く)、解けなければ `Typed` (値の後に ` : T` を書く) で、`Typed` は診断と同じ形の型の表示を持つ。`Show (List a)` があっても `List (Int -> Int)` は `Show` を持たない。`instance Show a => Show (Box a)` のもとの `Box (Int -> Int)` も、文脈が型引数で解けないので持たない。結果は `TypedProgram::inputs` に記録し、translate が値を書く入口を作る ([Core IR](core-ir.md) の「REPL の入力」)。`let` の束縛の入力は値を書かないので、いつも `Unit` を記録する
- 「`Show` を持つか」の判定は、公開の関数 `eml_types::satisfies(program, types, class, ty)` にまとめる。instance の文脈は頭の型引数へ写し、タプルは要素へ進む。translate の表示器も、値の部分ごとに同じ関数で書き方を決める
- 後の入力の instance によって、前の入力の関数の一様な位置 ([Core IR](core-ir.md) の「一様な位置と制約付きの多相再帰」) が変わることがある。メソッドの節点から、後の入力の instance の実装にも辺が引かれるためである。前の入力の関数はすでに実行のコードにあり、同じ名前で違うコードを足せないので、REPL はその入力を E2018 で受け付けない。めったに起きないので、受け付けないのがいちばん簡単な規則である
- `:type` の問い合わせ ([REPL の端末](repl.md) の「型の表示」) は、式の入力と同じく `input$N` の本体として検査する。違いは次のとおりである
  - 入力の関数の型は `Unit -> <ρ> T` で、`ρ` は `IO` に閉じない。E2015 は起きない
  - 型に現れる型変数を `Unit` に決めない。制約は、型変数に残ったものを残りの制約として集め、型に現れる型変数のものは文脈にする。型に現れない型変数のものは、式の入力と同じく `Unit` とみなして解き、解けなければ E2009 にする。E2009 は線形性の検査より前に足す
  - E2016 は報告しない
  - 型の文字列は、変数を決める前の推論の表の上で作る。型を書く順 (矢印は引数、row のラベルの型引数、row の変数、結果) にたどり、型変数に `a`、`b`、`c`、`d`、`f`、…、`z`、`a1`、`b1`、… (`e` で始まる名前は使わない) を、2回以上現れる row 変数と負の位置に現れる row 変数に `e`、`e1`、… を付ける。正の位置に1回だけ現れる row 変数は閉じた row として書く。負の位置で閉じると、書いた型が、本当の型の受け付ける引数を受け付けなくなるためである。位置の正負は、型全体を正とし、矢印の引数で反転する。矢印の結果と row、データ型とタプルの引数、row のラベルの型引数は正負を保つ。数えるのは書いた型の木の上で、共有した部分は現れるたびに数える。文脈は、型変数が現れた順、クラスの表示の名前の順に並べ、同じ制約と、ほかの制約の上位クラスでたどれる制約は書かない。Kind は書かない
  - 文字列を作った後で、残った row 変数を閉じる。型変数は決めない。結果は `TypedProgram::query` に入れ、`TypedProgram::inputs` には入れない

## エラーの扱い

名前解決と型推論は、エラーが起きた場所に `Error` 型を入れて処理を続ける。`Error` が関わる制約や線形性の検査からは、追加の診断を出さない ([コンパイラの構成](../implementation/architecture.md) の「エラーが出ても止まらない」)。

## 型システムの後に走る検査

推論の後に、型付き HIR の上で別のパスとして次の検査を行う。

- 線形性と継続の多重度の検査 ([線形性](linearity.md))
- 制約付きの多相再帰の検査 (E2012。上の「制約の解決」)
- `match` の網羅性の検査 ([網羅性](exhaustiveness.md))
