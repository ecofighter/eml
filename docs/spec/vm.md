# VM

位置づけ: 規範。

VM は、LIR をレジスタ型のバイトコードに変換し、`eml_rt` の `Ctx` の上で実行する。`eml run` は VM で動く。LIR の命令と規則は [LIR](lir.md) に、物体の形と `Ctx` の基本操作は [オブジェクトモデル](object-model.md) にある。ここでは、実行の API、バイトコードの形、フレーム、呼び出しの規約、命令ごとの実行、誤りと終わりの処理、上限と割り込み、`RunStats` の意味と数え方を定める。テストは [テスト戦略](../implementation/testing.md) の「`eml_vm` のテスト」と「2つのモードで流す」に、計測は [計測の基準](../implementation/benchmarks.md) にある。

判断の基準は、簡潔で洗練された実装を第一に、次に性能である。性能のための工夫は、計測で要ると分かったものだけを入れる。後のマルチコア対応 (VM の並列化と、スレッドをまたぐキュー) を妨げないことも、設計の条件に含める (「並列化への備え」)。

## 置き場所

- バイトコードは LIR から直接作り、中間に別の IR は挟まない。命令列への変換は1回の走査で済むためである
- crate `eml_vm` は、依存先を `eml_lir`、`eml_rt`、`eml_extern` だけにし、フロントエンドには依存しない。中身は、LIR のプログラムを `CodeBase<M>` に変換するコード生成 (`compile`) と、`CodeBase` を `Ctx<M>` の上で実行する VM の繰り返しの2つである
- `eml_vm` は、自分の `RunStats` と実行時エラーの型 `RuntimeError` を持つ。実行時エラーの型は1つだけなので、`RuntimeError` と呼ぶ。誤りの種類は `VmFault` と呼ぶ。`Fault` にすると、包んでいる `eml_rt::Fault` と名前がぶつかるためである
- `eml_lir` は、データの物理的な形を決める関数 `LayoutCtor::shape` を持つ ([オブジェクトモデル](object-model.md) の「ペイロード」)
- `eml_lir` は、文の単位の生存を公開の API にする ([LIR](lir.md) の「生存解析」)。スロットの割り当て (「スロットの割り当て」) が文の単位の干渉を作るために使う
- `eml_rt` は、`Word::from_bits` を公開する。生の `int` と `enum` の値をスロットに置くためである (「スロットとスタック」)
- `eml_rt` の関数には、VM のために `#[inline]` を足していない。インライン化の注釈 (`-C remark=inline`) が「definition is unavailable」と示した `eml_rt` の関数は、どれも実行の繰り返しの外か冷えた道にあったためである。繰り返しの中で呼ぶ関数に同じ注釈が出たときに足し、前後に `bench/rt.sh` を流して [計測の基準](../implementation/benchmarks.md) に記録する。`#[inline]` の置き方によって `map-reuse` の命令の数がビルドごとに約2倍振れたことがあるためである
- `eml_vm` の中の関数には、2つが分かったときだけ `#[inline]` を付ける。1つは、インライン化の注釈 (`-C remark=inline`) で、VM の繰り返し (`vm::run` と、そこに展開される関数) に「definition is unavailable」で展開されていないことである。もう1つは、付けると `bench/run.sh` で命令の数が減ることである。総称な関数の実体は、コード生成単位の1つにしかできず、ほかの単位からは展開できないためである。今は `data` の命令の関数 (`con`、`switch_tag`、`switch_int`、`switch_string`、`unpack`、`release`、`unbox`) と、`apply` の `make_closure` と `apply_rest` に付けている。測った数は [計測の基準](../implementation/benchmarks.md) の「S10b」にある
- release のプロファイルの `codegen-units` は既定の値のままにする。1 にすると、VM の実行の分の命令の数はプログラムによって減ったり増えたりしたためである (`state` で 14.2% 減、`fib` で 2.5% 増。[計測の基準](../implementation/benchmarks.md) の「S10a (VM)」)
- 実行の関数は `eml_vm::execute(program: &eml_lir::Program, config: &RunConfig, host: HostRef) -> Result<RunStats, RuntimeError>` の1つである。`execute` は、新しい `Machine` にプログラムを読み込み、入口を実行して閉じる (「追記」)。`RunConfig` は、検査モードかどうか (`debug_heap`) と、実行を止める情報 (`control: Arc<Control>`) を持つ。`file_root` は Host が持つので、`RunConfig` は持たない
- `RunConfig` は `#[non_exhaustive]` にする。欄を足しても呼び出し側を壊さないためである。`RunConfig::default()` は、速いモードと、上限のない新しい `Control` (`Control::new(Limits::default())`) である。`Control` は `Default` を持たないので、`Default` は手で書く。`with_debug_heap(bool)` と `with_control(Arc<Control>)` で組み立てる
- 1つの `Control` は1回の実行に使う。止める理由のビットは `Control::clear` でしか下りないので、使い回すと、前の実行で立ったビットで次の実行がすぐ止まるためである。`RunConfig` を `clone` すると `Control` を共有するので、UI テストの仕組みと `eml_test_support` は実行ごとに新しい `RunConfig` を作る
- `RunConfig` に `Control` を持たせるのは、CLI が SIGINT のハンドラに同じ `Control` を渡すためである。上限は `Control` が持つので、`RunConfig` に上限の欄は作らない ([オブジェクトモデル](object-model.md) の「実行の制御」)
- `eml_vm` は、`eml_rt` の `Control`、`Limits`、`Stop` を再公開する。`eml_cli` の lib と bin は `eml_rt` に直接は依存せず (テストは依存する)、これらの名前を `eml_vm` から受け取る
- `eml_cli` は、`run` の feature で `eml_vm` に依存する。`RunConfig`、`RunStats`、`RuntimeError`、`VmFault`、`SourceLocation`、`Control`、`Limits`、`Stop`、`HostRef`、`Capture`、`capture_host`、`stdio_host` を `eml_vm` から再公開し、`execute` を同じ名前で公開する
- `eml run` は速いモードで動き、`--debug-heap` を付けると検査モードになる。UI テストは、いつも検査モードで流してから速いモードでも流す ([テスト戦略](../implementation/testing.md) の「2つのモードで流す」)。Host は `stdio_host(PathBuf::new())` で、相対パスはカレントディレクトリを基準にする

## `CodeBase` と `FnEntry`

`CodeBase::new(control)` は組み込みの命令だけを持つ空の表を作り、`CodeBase::load(&mut self, program: &eml_lir::Program) -> Result<u32, CompileError>` はプログラムを追記して入口の関数の番号を返す (「追記」)。`compile::<M>(program, control)` は、新しい表に1つのプログラムを読み込む。呼び出しは関数の番号で指し、VM が `FnEntry` から先頭の位置を引くので、関数の先頭の位置が決まる前に呼び出しを書ける。`CompileError` は、スロットが `u16` に収まらない関数 (`TooManySlots`)、`Heap::freeze` の誤り (`Freeze`)、debug ビルドの一致の確かめの食い違い (`Mismatch`) である。どれも正しいプログラムでは起きないので、`execute` は位置のない内部の誤り (`internal error: …`) として返す。

| 欄 | 中身 |
|---|---|
| `functions` | 関数ごとの `FnEntry`。命令の位置の順に並ぶ |
| `code` | 全関数の命令列 (`Op`)。先頭に組み込みの命令 `Finish` (位置 0) と `ApplyRest` (位置 1) を置く |
| `operands` | 長さの変わるオペランド (`u32` の並び)。呼び出しの関数の番号と引数のスロット、extern の行の番号と引数、`con` のフィールド、switch の表、`release` のフィールド、`ev_new` の操作の数など |
| `effect_lists` | `evv_mask` のエフェクトの並び (`u16` の並び)。`Ctx::evv_mask` が `&[u16]` を受けるので、写さずに渡せるように分けて持つ |
| `constants` | 定数の語。文字列のリテラル、`i32` に収まらない生の `Int` の定数、`box` の定数 (63 ビットに収まれば即値、収まらなければ不死の `BigInt`) |
| `region` | 定数を置いた凍結した塊の鎖の先頭 `Option<Arc<Frozen<M>>>`。定数の物体をまだ作っていなければ `None` |
| `locations` | 命令の位置から源の位置 (`Loc`) への表。命令の位置の昇順に並ぶ (「誤り、止めること、終わり」) |
| `files` | 位置のファイルの表示用のパス。読み込んだ `Program.files` のパスを、初めて現れた順に並べる |
| `index` | 追記で番号を引き直す表。関数の名前、エフェクトの名前、ファイルのパス、文字列と整数の定数の中身から番号を引く (「追記」) |
| `control` | 定数の塊のページを数える `Control`。実行のヒープと同じものである |

- `FnEntry` は、名前、命令列の範囲 `[start, end)`、引数の数 (`arity`)、枠の大きさ (`frame_size`、スロットの数)、`ret` が `obj` か `tobj` か (`ret_rc`) を持つ。`ret_rc` は、その関数を入口として実行したときに、`Finish` が結果を手放すかを決める (「誤り、止めること、終わり」)。`apply` は引数の数を見て、部分適用か、ちょうどか、余るかを決める。ネイティブのコードを混ぜるときは、ここに入口の種類を足す
- 定数は、`load` が `Heap::with_control(control)` で作った作業用のヒープに不死の物体として作り、`freeze` で塊にする。文字列のリテラルは、`Program.strings` の順にすべて引く。塊のページは同じ `Control` の確保量に数える。実行のヒープは、塊を付け替えてから次の入口を実行する ([オブジェクトモデル](object-model.md) の「凍結した領域」)
- 塊の物体は、検査モードでも参照を数えない。そのため、文字列の定数を読む命令は `acquire_immortal` を呼ばず、語を写すだけにする
- `CodeBase` は実行中は読むだけで、`CodeBase<M>: Sync` を型の assert で固定する。書き換えるのは入力の境目の `load` だけである。`CodeBase` は `M` ごとに作るので、検査モードと速いモードを両方動かすテストは2回変換する

### 追記

REPL は入力ごとにプログラム全体を lowering し直し、同じ `CodeBase` に追記する。クロージャは関数の番号を物体の中に持つので、入力をまたいで関数の番号を変えない。

- `Machine<M>` は、`CodeBase<M>` と `Ctx<M>` を入力をまたいで持つ。`Machine::<Fast>::new` と `Machine::<Checked>::new` は `Control` と Host を受け取り、モードごとの確かめを決める。`AnyMachine` は、実行の前にモードを選ぶ呼び出し側のための列挙である
- `Machine::load(program)` は `CodeBase::load` を呼び、新しい塊があれば実行のヒープに付け替えて、入口の関数の番号を `Loaded { entry }` で返す。誤りを返した後の `Machine` は使い続けない
- `Machine::run(entry)` は、入口の関数を `()` で実行する。統計は `Machine` を作ってからの積算で、`peak_stack` だけがその実行の値である。検査モードでは、実行の後にヒープの不変条件だけを確かめる。セッションの根は手放さず、次の実行に残す。続けられる誤り (`is_broken` が偽) の後は `Ctx::abandon` で evv と yield の状態を空に戻し、次の実行が終わりの確かめを通るようにする。スタックと evv に残った語は手放さず、ヒープに残る
- `Machine::close()` は実行の状態を閉じる。根の参照は VM が持つので、`Ctx::take_roots` で取り出して先に手放す。検査モードでは、その後にヒープの不変条件を確かめ、残った物体をリークとして返す
- 名前が同じ関数は、いつも同じコードになる。`load` はこの規則に頼って、関数を名前で照らす。すでにある名前の関数は前の番号を使い、ない名前の関数だけを変換して末尾に足す。新しいコードの中の番号は、次のように引き直す
  - 関数の番号: 名前で引く
  - 文字列の定数と、生の整数と `box` の整数の定数: 中身で引く。前に読み込んだ定数は同じ番号を使う。新しい物体があるときだけ、作業用のヒープに今の先頭の塊を付けてから物体を作り、凍結する。新しい塊は前の塊を親に持つので、鎖が伸びる。新しい物体のない入力では塊を作らない。塊は使う大きさの級ごとに少なくとも1ページを持つためである
  - エフェクトの番号: 名前で引き、なければ次の番号を振る。`Program.effects` の添字は HIR の順で決まり、セッションにエフェクトを足すと後ろのエフェクトの添字がずれるためである。`evv_mask` のエフェクトの並びも引き直し、昇順に並べ直す
  - 位置のファイルの番号: パスで引き、なければ `files` の末尾に足す
  - 配置の番号は、命令列を作るときに形を引くだけで、命令列に残らないので引き直さない
- debug ビルドでは、すでにある名前の関数も同じ引き直しで変換し直し、前の命令列と比べる。比べるのは、逆アセンブラと同じテキストにした命令の並びと、`arity`、`frame_size`、`ret_rc` である。テキストの命令の位置は関数の先頭からの位置で書き、オペランドは指す中身 (呼ぶ関数の名前、エフェクトの番号、定数の番号、位置のパス) で書く。一致しなければ `CompileError::Mismatch` を返す。比べた写しは消す
- `RuntimeError::is_broken()` は、続けて実行できない誤り (ヒープの誤りと内部の誤り。ヒープの誤りには、2つのモードで返す根の誤った読み書き `RootMisuse` も入る) で真を返す。この後のヒープは信用できないので、REPL は後の入力を受け付けない

## 命令とフレーム

### スロットとスタック

- 実行の状態は、ワーカーごとの `Ctx<M>` と、タスクごとの `Task` に分ける。`Task` は、スタック `stack: Vec<Word>`、命令の位置 `pc`、今のフレームの `base` と `frame_size`、最後に戻った `Ret` の位置 `last_ret` (「誤り、止めること、終わり」)、末尾の呼び出しで引数を移す間だけ置く作業用の領域 `scratch` を持つ。VM の繰り返しは `CodeBase`、`Ctx`、`Task` と、検査モードで数える `box` と `unbox` の回数だけを受け、安全点をまたいでほかに状態を持たない
- フレームのスロットはどれも1語である。`obj` と `tobj` の値は語のまま置く。`int` と `enum` は provenance を持たない生のビット列 (`Word::from_bits`) にし、`bits()` で読む。`unit` は語の値 1 (`Word::UNIT`、値 0 の即値) にする
- スタックを `Vec<u64>` にしないのは、ポインタを整数に戻すと provenance が失われ、Miri の strict provenance に反するためである
- 生のビット列の語は、即値やポインタに見えることがある (偶数の値はポインタの形をしている)。そのため、VM は語の形でなく、コード生成が知っている Repr で値を扱う。RC の命令と、即値かどうかの判定は、Repr が `obj` か `tobj` の値にだけ使う (「RC」と「switch」)
- 関数に入るときと、`ApplyRest` のフレームを積むときに、スタックを `base + frame_size` まで伸ばす。スタックは添字で指すので、`Vec` が伸びて場所が変わってもよい。スロットの読み書きは、境界を確かめる添字で行う。確かめない添字に替えるのは、計測で要ると分かったときだけにし、そのときは Miri のテストで覆う ([テスト戦略](../implementation/testing.md) の「Miri」)。`Vec` の容量は `Task::reserve` が倍に伸ばすが、`min(2 × 今の容量, max_depth + u16::MAX + 2)` 語で止める (`reserve_exact`)。深さが `max_depth` を超えると次の安全点で止まり、安全点の前には通常、1つの枠と見出し (`u16::MAX + 2` 語) までを積むので、それより大きい容量は見込まない。余る引数の適用は `ApplyRest` の枠と呼ばれる側の枠を同じ安全点の前に積むので、求める長さが上限を超えうる。そのときは容量をその長さちょうどにする
- 深さはスタックの使っている語の数 (`base + frame_size`) で、`Ctx::poll` に渡す
- スタックはヒープの外にあるので、確保量の上限 (`max_bytes`) には数えず、深さの上限 (`max_depth`) で抑える (「上限と割り込み」)

### フレーム

```
base - 2: 戻り先の命令の位置 (32 ビット) | 結果を書くスロット (16 ビット) | 呼び出し元の frame_size (16 ビット)
base - 1: 呼び出し元の base
base + 0 .. base + frame_size: スロット
```

- 見出しは2語で、関数の番号は持たない。呼ばれる側の base は、呼ぶ側の `base + frame_size + 2` である。`Task` は今のフレームの `frame_size` を持ち、関数に入るときに `FnEntry` から読む。戻るときは、見出しの1語目から呼び出し元の `frame_size` を戻すので、戻り先の命令の位置から関数を引き直さずに済む。見出しの2語はどちらも生のビット列 (`Word::from_bits`) である
- いちばん下には、入口の関数の結果を受けるスロットを1つ持つ空のフレームを置く。入口の関数の見出しの戻り先は `Finish` で、結果はこのフレームのスロット 0 に書く
- `ApplyRest` のフレームの形は、スロット 0 が結果、スロット 1 が残りの引数の数 n (生のビット列)、スロット 2 から 2 + n - 1 が残りの引数で、`frame_size` は 2 + n である。残りの引数の参照は、このフレームが持つ

### 命令の形

- 命令は `Copy` の `enum Op` で、大きさが 8 バイトであることをコンパイル時に assert する。命令の列を密に保ち、1回の読み込みで命令を取れるようにするためである。スロットは `u16`、命令の位置 (`Pc`) と表の添字は `u32` である。オペランドは次の3つの形のどれかに収める
  - 固定のスロット: `Move { dst, src }`、`IntAdd { dst, a, b }` のように `u16` を3つまで持つ。`EvLookup { dst, effect }` と `EvClause { dst, ev, op }` は、エフェクトと操作の番号も `u16` で持つ
  - スロットと即値: `LoadRaw { dst, value: i32 }` (生の `int` と `enum` の値)、`LoadImm { dst, value: i32 }` (即値の語)、`LoadConst { dst, index: u32 }`、`BoxConst { dst, index: u32 }`、`Goto { target: u32 }`
  - スロットと表の添字: `Call { dst, at: u32 }` のように、長さの変わるオペランドを `operands[at..]` に置く。関数の番号、行の番号、引数のスロットの並びは表の側にある
- 呼び出し、`apply`、`clause`、extern、`con`、`closure`、`prim` の引数と `return` の値に定数の atom (`Int`、`#N`、`&f`、`()`) があれば、命令の前に一時のスロットへ読み込み、そのスロットを渡す。一時のスロットは変数のスロットの後に置き、命令ごとに使い回す。枠の大きさは、変数のスロットの数と、1つの命令が使う一時のスロットの数の最大の和である
- 定数の読み込みは、受ける位置の Repr で分ける。`Int` は `LoadRaw` で、`i32` に収まらなければ `constants` に置いて `LoadConst` で読む。`#N` は、`enum` の位置では `LoadRaw`、`tobj` の位置では `LoadImm` である。`&f` は関数の番号の `LoadImm`、`()` は値 0 の `LoadImm` である
- 実行は、`match` で命令を分ける1つのループで、`M: Mode` について総称にする。Rust の再帰は使わない。`ApplyRest` と `Finish` の処理も、ループの中で命令として扱う
- 次のブロックへ進むだけの `jump` には `Goto` を出さない
- 逆アセンブラ (`disassemble`) は、`CodeBase` を関数ごとのテキストにする。テストのスナップショットと、誤りの調べに使う

### スロットの割り当て

- 関数ごとに、文の単位の生存から干渉グラフを作り、色を塗ってスロットを決める。入口のブロックの引数をスロット 0 から n - 1 に固定し、残りの変数を番号の順に、隣と違ういちばん小さい色で塗る
- 干渉の規則は次のとおりである
  - 変数を定義する文 (呼び出しの結果、`let`、`unpack` のフィールド) は、同じ文が定義するほかの変数と、その文の後で生きているすべての変数と干渉する。定義した変数が使われずに死んでいても同じである。使われない呼び出しの結果を `Ret` が書いても、生きている値を上書きしないためである
  - ブロックの引数は入口で同時に書くので、互いと、そのブロックの入口で生きている変数と干渉する
  - case のフィールドは `switch` で書くので、互いと、行き先の入口で生きている変数と、scrutinee と干渉する。`unpack` のフィールドも、その値と干渉する。フィールドを1つずつ読んで書く間に、scrutinee のスロットを上書きしないためである
- 定義する変数は、その文で死ぬオペランドとスロットを共有しうる。そのため、複数の手順に展開する命令 (`con`、`closure`、`apply`、基本操作など) は、オペランドをすべて読み終えてから `dst` を書く
- case と `unpack` のフィールドは、使われるものだけを読んで書く。SSA なので、使われないフィールドは死んでいる
- Repr ごとにスロットを分けない。どの値も1語なので、分けても得るものがないためである。命令の位置ごとの割り当ては静的に決まるので、安全点ごとの「生きていて所有しているスロット」の表は後から作れる。表は生存解析だけでは決まらず、Perceus の所有の状態から作る (「並列化への備え」)
- `jump` のブロック引数の並列な代入は、コンパイル時に `Move` の列へ直す。どの代入も、まだ読まれていない値を上書きしない順に並べ、輪になる代入は一時のスロットを1つ通して切る。変数の代入を先に並べ、定数の引数はその後に行き先のスロットへ直接読み込む。定数の書き込み先が、ほかの代入がまだ読む値のスロットでありうるためである
- ブロック引数と実引数に同じ色を付けやすくする合併は行わない。移動の命令を減らす工夫だが、合併なしで VM の実行の分の命令の数が、S10a で比べた前のインタプリタの約 0.10〜0.17 倍に収まったので、簡潔さを先にした ([計測の基準](../implementation/benchmarks.md) の「S10a (VM)」)
- 呼ぶ側のスロットは、呼び出しの間もスタックに残る。そのため、呼び出しの後で使う変数を退避しない。借りた変数が呼び出しをまたぐときは、その持ち主もスロットに残るので、借りた変数は有効なままである ([LIR](lir.md) の「所有を取る時点」)

## 呼び出しと戻り

- VM は `yields` を読まず、`apply` の `yields` も読まない。evidence passing の後の LIR では、yield は普通の戻りと基本操作で表され、VM が `yields` で動作を変える所はないためである
- **直接の呼び出し** `Call { dst, at }`: `operands[at..]` は [関数の番号, 引数の数, 引数のスロット…] である。呼ばれる側の base を `base + frame_size + 2` とし、見出しを書き、引数を呼ぶ側のスロットから呼ばれる側のスロット 0.. へ写して、関数の先頭へ進む。2つのフレームは重ならないので、引数は作業用の領域を通さない。引数の数は呼ばれる関数の引数の数と等しい (verifier が確かめている)
- 引数をオペランドの表のスロットの並びで渡すのは、直接の呼び出し、`apply`、`clause`、extern で同じである。引数を連続したスロットの範囲で渡すと、引数を連続したスロットへ移す `Move` が引数ごとに要り、色塗りでは連続を保証できないためである
- **戻り** `Ret { src }`: 見出しを読み、呼ぶ側のフレームの結果を書くスロットへ値を書き、base、`frame_size`、命令の位置を戻す
- **末尾呼び出し** `TailCall { at }`: 実引数を作業用の領域 `scratch` へいったん読み、今の base のスロット 0.. に書いてから、呼ばれる関数の先頭へ進む。引数と今のスロットが重なりうるので、作業用の領域を通す。見出しはそのまま使う
- **自己末尾呼び出し** `TailSelf { at }`: 同じ関数への末尾呼び出しは、引数を作業用の領域を通して書いた後、関数の先頭へのジャンプにする。後ろ向きの辺ができるのは自己末尾呼び出しのバイトコードだけで、LIR は Core IR から引き継ぐ R2 (辺はすべて番号の大きいブロックへ向かう) を緩めない ([LIR](lir.md) の「構造の規則」)。このジャンプでも `Ctx::poll` を呼ぶ。呼ばないと `loop n = loop (n + 1)` が呼び出しも戻りも通らず、割り込み、上限、後の協調的なタスクの切り替えのどれも効かなくなるためである
- **`apply`** `Apply { dst, at }`: `operands[at..]` は [呼ばれる値のスロット, 引数の数, 引数のスロット…] で、引数を作業用の領域に読んでから適用する。呼ばれる値は `tobj` である。即値なら関数の番号、物体ならクロージャで、関数を `scanned(w, 0)` で、捕まえた値を `scanned(w, 1..)` で読み、その数を `scanned_len(w) - 1` とする ([オブジェクトモデル](object-model.md) の「クロージャ」)。捕まえた値を先に、渡した引数を後にして並べ、`FnEntry` の引数の数と比べる。関数の番号が表にない値は内部の誤りにする
  - クロージャの中身を取り出すときは、先に `meta` を読んで `lin` ビットを覚えておく。そのうえで、`is_last` なら値を読んでから `free_block` し、そうでなければ値を `dup` してから `decref` する
  - ちょうどの数なら、新しいフレームを積んで関数の先頭へ進む
  - 足りなければ、新しいクロージャを `alloc_data` で作り、`dst` に書く。`lin` ビットは元のクロージャのものを写し、元が即値なら立てない。捕まえた値と引数はどれも一様な位置の値 (`tobj`、`obj`、`unit`) なので、走査する語に入れてよい
  - 余れば、`ApplyRest` のフレームを積んで残りの引数を移してから、先頭の分の引数で関数に入る。関数の見出しの戻り先は `ApplyRest` で、結果は `ApplyRest` のフレームのスロット 0 に書く。`ApplyRest` は、スロット 0 の結果に残りの引数を適用する。この適用は `ApplyRest` のフレームの見出しを引き継ぐ末尾の適用で、引数を作業用の領域に通す
- **`clause`** `Clause { dst, at }`: 呼ばれる値と、evidence を先頭にした引数を `apply` と同じに並べる。引数の Repr は、evidence が `obj`、残りが操作の表の `params` である。ただし引数の数はいつも入口の関数の引数の数と等しく、違えば内部の誤りにする。`clause` の引数は操作の ABI の Repr (生の `int` を含む) を持つので、部分適用でクロージャの走査する語に入れてはならないためである
- **末尾の位置の `apply` と `clause`** (`TailApply`、`TailClause`): 今のフレームの見出しを引き継ぎ、引数は作業用の領域を通す。足りなければ、作ったクロージャを戻りと同じに返す。余れば、`ApplyRest` のフレームが今のフレームの位置と見出しを受け継ぐ
- **安全点**: 呼び出し (末尾呼び出し、`apply`、`clause`、`ApplyRest` の適用を含む)、戻り、自己末尾呼び出しのジャンプで、フレームを移した後に `Ctx::poll(深さ)` を呼ぶ

## 命令ごとの実行

### 値と定数

| LIR | VM の動作 |
|---|---|
| `Int` の定数 | 生のビット列にする |
| `#N` | `enum` の位置では生の N、`tobj` の位置では即値 N |
| `&f` | 即値 (関数の番号) |
| `()` | 語の値 1 |
| `const` (文字列) | `constants` の語を写す |
| `box` | `int` の変数は `alloc_int` (63 ビットに収まれば即値、収まらなければ `BigInt`)、`enum` の変数は即値にする。オペランドが定数なら、コード生成の時点で即値か不死の `BigInt` にして `constants` に置き、`BoxConst` で写す |
| `unbox` | 即値なら値を取り出す。物体なら `unbox_int` で読む。ダミーは値 0 の `BigInt` なので、`int` でも `enum` でも誤りにならず 0 を返す |

### RC

- `dup x` と `decref x` は、`Heap::dup` と `Heap::decref` を呼ぶ。`drop a` も `decref` で実行する ([オブジェクトモデル](object-model.md) の「核の操作」)。`drop` の結果の `()` は、使われるときだけ書く
- RC の命令は、Repr が `obj` か `tobj` の変数にだけ出す。`drop` の atom が定数か、Repr が `int`、`enum`、`unit` の変数なら、コード生成は `decref` を出さない。verifier は `drop` に任意の atom を許し、生のビット列はポインタに見えることがあるためである
- scrutinee が `tobj` の変数のタグの `switch` で、フィールドのない case の行き先では、scrutinee は即値と分かる。その行き先がこの case だけから入るブロックなら、コード生成はそのブロックの中の scrutinee の `decref` を出さない。即値の `decref` は何もしないためである。この省略は、フィールドのない構築子の値がいつも即値であることに頼る。`con` は引数を1つ以上取り、フィールドのない構築子の値は `#N` と書く決まりで ([LIR](lir.md) の「ブロックの列」)、LIR の verifier の `con` の検査がこれを強いる。この決まりを緩めると、省略は成り立たなくなる。IR の規則にはしない。IR の規則にすると、verifier に「即値と分かっている」という3つ目の状態が要るためである
- `release x L #t(..)` は、コード生成の時点で形が分かっているので、オブジェクトモデルの展開をそのまま使う。オペランドは、Repr が `obj` か `tobj` のフィールドの物理的な位置と、残すフィールドかどうかの印である

  ```
  is_last(x)
    真: 残さない走査する語を decref → free_block(x)
    偽: 残す走査する語を dup → decref x
  ```

  残す変数は、前の `switch` か `unpack` ですでにスロットにある。そのため `release` はスロットに書かず、参照の数だけを動かす。検査モードでは、展開の前に、語がポインタで、種類が `Data` で、`meta` の tag と走査する語の数が名指したものであることを確かめ、違えば内部の誤りにする。一般の版の `Heap::release` が返す `WrongLayout` の見張りを残すためである。共有の物体の `lin` ビットの見張り (`LinShared`) は、展開の中の `decref` が受け持つ

### データとクロージャ

- `con L #t(a..)` は、`LayoutCtor::shape` で宣言の位置を物理的な位置へ写す。そのうえで `alloc_data(tag, 走査する語の数, 生の語の数, lin)` で作り、走査する語を `set_field`、生の語を `set_raw` で書く。`lin` は、束縛する変数の印が `lin` なら真である ([オブジェクトモデル](object-model.md) の「`lin` ビット」)
- 走査する語が 255 個以上のデータでは、ペイロードの先頭に数の語がある。`field`、`set_field`、`raw`、`set_raw` の位置はこの数の語を含む物理的な位置なので、VM はその物体の位置を、コード生成の時点で1つずらしておく
- `closure f(a..)` は、`alloc_data(0, 1 + 引数の数, 0, lin)` で作り、最初の走査する語に即値 `&f`、続く語に引数を書く。`lin` の決め方は `con` と同じである。走査する語が 255 個以上なら、`con` と同じく位置をずらす

### switch

- タグの `switch` は、scrutinee の Repr で読み方を分け、命令も分ける。語の形では分けない。生の `enum` の値は即値にもポインタにも見えるためである
  - `enum` (`SwitchEnum`): 生の値をタグにする
  - `obj` (`SwitchObj`): `meta` の tag をタグにする
  - `tobj` (`SwitchTObj`): 即値なら `imm_value` を、物体なら `meta` の tag をタグにする
  - 定数の scrutinee (`#N`、`Int`) は、コード生成の時点で行き先を決めて `Goto` にする
- タグの `switch` は、いつも1つの配置のタグで分ける。タグは 0 から配置のコンストラクタの数 - 1 に収まるので、飛び先の表はいつも密である。そのため、タグの `switch` はいつも表を1回引いて行き先を決める。表にないタグは `default` へ進み、`default` がなければ内部の誤りにする
- フィールドのある case では、検査モードで、語の種類が `Data` で、tag と走査する語の数が case の配置のものであることを確かめ、違えば内部の誤りにする。verifier の R8 は値を作った配置を追わないので、verifier を通った IR でも外れうるためである ([LIR](lir.md) の「構造の規則」)
- フィールドは `field` と `raw` で物理的な位置から読み、スロットに書く (使われるものだけ)。読むだけなので、参照の数は変えない
- `Int` の `switch` (`SwitchInt`) は、生の値を case の値と順に比べる。`String` の `switch` (`SwitchString`) は、scrutinee と定数を両方 `Heap::string` で借りて、バイト列を順に比べる。どちらも手放さない
- 比較と分岐を1つにした命令は持たない。比較の命令が結果を生の `enum` の値としてスロットに書き、`SwitchEnum` がそれで分ける。融合の命令を足すと、`Op` の種類、コード生成の形の照合、逆アセンブラ、テストが増える。融合なしで VM の実行の分の命令の数が、S10a で比べた前のインタプリタの約 0.10〜0.17 倍に収まったので、簡潔さを先にした ([計測の基準](../implementation/benchmarks.md) の「S10a (VM)」)
- `unpack` は、行き先が1つの `switch` と同じ読み方をする。検査モードでは、語がポインタで、種類が `Data` で、tag と走査する語の数が名指したものであることを確かめ、違えば内部の誤りにする

### 基本操作と extern

- `prim` は、基本操作ごとの命令で、`Ctx` の同じ名前のメソッドを呼ぶ。`dummy` だけは `Heap::dummy` である。即値 (エフェクトの番号、操作の番号) と `ev_new` の操作の数は、コード生成の時点で命令か `operands` に書く。`evv_mask` のエフェクトの並びは `effect_lists` に置く。結果が `unit` の基本操作は、結果のスロットに `()` を書く
- エフェクトの番号は 65535 より小さくなければならない。evidence の tag はエフェクトの番号 + 1 だからである ([オブジェクトモデル](object-model.md) の「evidence の3つの物体」)。速いモードの `ev_new` はこれを確かめない。コード生成は、これをコンパイラの内部の不変条件として panic で確かめ、`CompileError` にはしない
- 算術と比較の extern 13個 (`+ - * / % negate`、`Int` の比較6つと `compare`) と、`Bool` の `==` と `!=` は、それぞれ専用の命令 (`IntAdd`、`IntCompare`、`BoolEq` など) にする。`eml_rt::externs` の `#[inline]` の関数を、命令の中に展開して呼ぶ。結果は生のビット列でスロットに書く
- ほかの extern (文字列、表示、`println`、`Fs`) は `Extern { dst, at }` の1つの命令にする。`operands[at..]` は [行の番号, 引数の数, 引数のスロット…] で、行の番号の `match` で `Ctx` のメソッドを呼ぶ
- VM は `Ctx` の基本操作の合間に、`Ctx` が持つ語とそこからたどれる物体に触れない (`heap_mut()` の前提)
- `Bool`、`Ordering`、組のタグの定数が `eml_rt::externs` と `eml_lir` で同じであることを、`eml_vm` のテスト (`tags.rs`) で確かめる。VM の `Bool` と `compare` の命令がこれに頼るためである

## 誤り、止めること、終わり

- 実行時エラー `RuntimeError` は、誤り (`VmFault`)、関数の名前、省略できる位置を持つ `Fault` と、検査モードのリークの `Leak` である。`VmFault` は、extern、基本操作、ヒープの操作の誤り (`Extern(Fault)`)、安全点で止めたこと (`Stopped(Stop)`)、verifier を通った IR では起きないはずの誤り (`Internal`) の3つである
- 表示の形は次のとおりである。位置があれば `{fault}\n  at path:line:column`、なければ ``{fault} in `function` ``、リークは `memory leak: objects were not freed: {n} {name}, …`、内部の誤りの `{fault}` は `internal error: {what}` である
- 関数の名前は、命令の位置から `FnEntry` の範囲を二分探索して引く。`Finish` と `ApplyRest` はどの関数にも属さないので、そこで起きた誤りには、最後に戻った関数の名前を付ける。VM は `Ret` のたびにその位置を `Task::last_ret` に覚える。末尾の位置の部分適用が作ったクロージャを返すときも、関数の中で起きたなら同じく覚える
- 位置は `locations` から命令の位置で引く。表に載せるのは、位置を持つ extern の呼び出しから作った命令である。専用の算術と比較の命令も含む。`run-fail` の UI テストの多くは `/` と `+` の誤りの位置を表示している
- `Arith`、`Output`、`Io`、`NotUtf8`、`Heap(_)` の文言は `eml_rt` のものを使う ([オブジェクトモデル](object-model.md) の「誤り」)。extern の結果と文言は、`crates/eml_rt/src/heap/tests/expected.txt` の表が固定する ([テスト戦略](../implementation/testing.md) の「期待値の表」)
- 安全点の `Ctx::poll` が返す `Stop` と extern の `Fault::Stopped` は、どちらも `Stop` の文言で表示する。`Fs.read_all` の `Fault::Stopped` は extern の誤りなので位置を付け、安全点の `Stop` には付けない
- 割り込みで止めたときの表示も、ほかの実行時エラーと同じ形である。安全点で止めたときは ``interrupted in `f` `` (`f` は止めたときの関数)、`Fs.read_all` の中で止めたときは位置付きの `interrupted` である。`RuntimeError::interrupted()` は、安全点の `Stopped(Stop::Interrupted)` と、`Fs.read_all` の中で止めた `Extern(Fault::Stopped(Stop::Interrupted))` の両方で真を返す。CLI が終了コードを決めるのに使う (「上限と割り込み」)
- 繰り返しが誤りで終わっても、`Finish` に着いても、`Machine::run` は `Ctx::flush` を呼んでから結果を返す。`> out 2>&1` のときに出力と誤りの順を保つためである
- `Finish` に着いたら、次の順に処理する
  1. 入口の関数の結果を手放す。Repr が `obj` か `tobj` のときだけ `decref` する
  2. flush する。誤りなら、位置なしで返す
  3. `Ctx::check_finished` で、`evv` が空で yield の状態がなしであることを確かめる。モードによらず確かめ、満たさなければ内部の誤りにする
  4. 検査モードでは、`Heap::check_invariants` を確かめる。不変条件の誤りには、最後に戻った関数の名前を付ける
- 検査モードの `Machine::close` は `Heap::leaks` を確かめる。リークがあれば、種類の名前ごとの数を持つ誤りにする。`execute` は実行の後に閉じるので、1回の実行の終わりにリークを確かめる

## 上限と割り込み

`eml run` の既定の上限は、`eml_cli::default_limits() -> Limits` が作る。`eml_rt` を vstd だけに依存したままにするため、OS に問い合わせるコードは `eml_cli` に置く。

| 上限 | 既定の値 | 理由 |
|---|---|---|
| `max_depth` | 2^27 語 (1 GiB 分のスタック) | OCaml 5 のスタックの既定の上限 (128M 語) と同じ量である。1段が 8 語なら、約 1600 万段まで入る |
| `max_bytes` | 物理メモリの 80% | GHC がスタックの上限 (`-K`) の既定を物理メモリの 80% にしているのに倣う。ヒープの上限としての前例ではなく、「機械を使い切る前に、分かる誤りで止める」という考え方を借りる。物理メモリを読めない OS では上限なし (`usize::MAX`) にする |
| `max_evv` | 上限なし | `evv` はヒープの物体なので、確保量の上限で抑えられる |

- 物理メモリは `sysconf(_SC_PHYS_PAGES) * sysconf(_SC_PAGESIZE)` で読む。macOS と Linux のどちらもこの2つを持つ。`eml_cli` の `src/` の `unsafe` の呼び出しは、この関数の中だけに置く
- Linux のコンテナでは、物理メモリは cgroup の上限を反映しない。上限が cgroup より大きくなり、分かる誤りの前に OOM で殺されうる。cgroup を読むのは要るときに足す
- VM のスタックはヒープの外にあるので `max_bytes` に数えず、`max_depth` で抑える (「スロットとスタック」)
- 検査モードは解放したブロックを使い回さないので、`--debug-heap` の長い実行は、速いモードより先に `max_bytes` に当たりうる。暴走を止める安全網という上限の役 ([オブジェクトモデル](object-model.md) の「確保と解放」) は変わらないので、受け入れる
- CLI のフラグ (`--max-depth` など) は足さない。要るとき (REPL など) に足す
- 深さか確保量の上限で止まったときは ``the call depth limit is exceeded in `f` `` か ``the memory limit is exceeded in `f` `` と表示し、終了コードは 1 である

`eml run` は、ファイルを読む前に `Control::new(default_limits())` を作り、`ctrlc` crate で SIGINT のハンドラを入れる。読み込みとコンパイルの間の Ctrl-C も、既定の動作 (シグナルで殺される) でなく、このハンドラが受ける。ハンドラは実行の `Control` を持ち、次のように動く。

- `control.stop_bits() & Control::INTERRUPT` が 0 なら、`control.interrupt()` を呼ぶ。VM は次の安全点で止まる。コンパイルの間に立ったビットは、実行の最初の安全点で読まれる
- すでに立っていれば (2回目の Ctrl-C)、`std::process::exit(130)` でその場で終わる。まだ書いていない出力は捨てる。安全点に来ないプログラム (入力を待つ `Fs.read_all` など) を止めるための道だからである
- `ctrlc` はハンドラを専用のスレッドで順に呼ぶので、2つの Ctrl-C が同時に読み書きすることはない。`eml_rt` の `Control` は変えない

割り込みで止まったとき (`RuntimeError::interrupted`) は、1回目でも終了コードを 130 にする。130 は、シェルが SIGINT で終わった子に報告する値と同じである。ほかの実行時エラーは 1 である。

## `RunStats`

`RunStats` は、実行の仕事の回数と、同時に生きていたヒープの物体の数と、スタックの語の数の最大である。検査モードだけで数え、速いモードの欄は 0 のままである。実行時エラーとリークのときは返さない。欄は次の10で、はじめの8つが仕事の回数である。

- `evidence_steps`: `ev_lookup` と `evv_mask` がたどった `evv` の節点の数。今有効な handler の数で決まり、呼び出しの深さにはよらない。検査モードの `evv_mask` は、合う evidence が足りずに誤りを返したときは数えない ([オブジェクトモデル](object-model.md) の「速いモードと検査モード」)。出どころは `Ctx` の `CtxStats` である
- `yields`: `yield_to` と `yield_abort` を実行した回数。すぐに再開する操作は yield しないので数えない。出どころは `CtxStats` である
- `yield_frames`: `yield_cont_set` を実行した回数。yield が handler まで戻る間に、継続 κ に足したフレームの数である。再開する操作では、操作と handler の間のフレームの数に比例する。これは方式の性質である。出どころは `CtxStats` である
- `string_bytes_copied`: extern がヒープの文字列の物体に写したバイト数 ([オブジェクトモデル](object-model.md) の「仕事の回数」)。`++` では、新しい文字列を作る側が |左辺| + |右辺|、一意な左辺に足す側が |右辺| になる。出力への書き込みと、コード生成が定数を作る書き込みは数えない。出どころは `CtxStats` である
- `rc_increments`: 参照の数を増やした回数。`dup`、共有の側の `release` が残すフィールド、基本操作が残す参照を数える。確保のときの最初の1は数えない。凍結した領域の物体とダミーは数えない ([オブジェクトモデル](object-model.md) の「検査モードでは数えない」)。出どころは `Heap` の `Stats` である
- `rc_decrements`: 参照の数を減らした回数。`decref`、`drop`、解放の連鎖で子を手放した分を数える。`release` と `free_block` は、持ち主を空けるときにも1つ足す。出どころは `Heap` の `Stats` である
- `boxes`: VM が実行した `box` (`BoxInt`、`BoxEnum`、`BoxConst`) の数。語の値の表現では確保しうる変換なので数える
- `unboxes`: VM が実行した `unbox` の数。数える理由は `boxes` と同じである
- `peak_objects`: 同時に生きていたヒープの物体の数の最大 (`Heap` の `Stats` の `peak_live`)。ヒープごとのダミーの物体を1つ含む。フレームはスタックにあり、凍結した領域の物体も数えないので、どちらも含まない
- `peak_stack`: タスクのスタックで同時に使った語の数の最大。スタックの `Vec` の長さは縮めないので、`Task::reserve` が伸ばした長さがそのまま最大になり、VM は実行の終わりに `task.stack.len()` を読むだけで済む。フレームはスタックにあって `peak_objects` に表れないので、末尾呼び出しを失ったことはこの欄で見つける

どの回数も時間ではなく、仕事か物体か語を数える。そのため、2乗の時間にならないことと、ループがフレームを積まないことを、ふだんのテストで確かめられる ([テスト戦略](../implementation/testing.md) の「性能のテスト」)。

S10a までの記録の `rc_increments`、`rc_decrements`、`peak_objects` は、S10b で消したインタプリタの数え方の値で、VM の値とは違う。違う理由は [計測の基準](../implementation/benchmarks.md) の「S10a (VM)」にある。

## 並列化への備え

この形の VM は、VM の並列化とスレッドをまたぐキューを後から入れることを妨げない。

- 実行の状態は、ワーカーごとの `Ctx` と、タスクごとの `Task` に分かれる (「スロットとスタック」)。`CodeBase` は読むだけなので、全 worker で共有しても競合しない
- evidence passing により、`perform` で止まったタスクの続きは、ヒープ上の継続のクロージャになる。このタスクはスタックを持たず、別の worker へ移すことはクロージャの語を1つ渡すことと同じである。まだ始まっていないタスク (`spawn` に渡す閉包、`par` の右の子) も同じである
- 一方、安全点で切り替えたタスク (S13 で採りうる `par` の a1 のスケジューラ) と、`join` で子を待つ親は、スタックの途中で止まっているので、`Task` ごとスタックを持ち続ける。こうしたタスクの数は `par` の入れ子の深さで抑えられる

VM は次の4つを守る。

1. 自己末尾呼び出しのジャンプも安全点にする (「呼び出しと戻り」)
2. スレッドに局所的な変数を置かない。`CodeBase<M>: Sync` と `Task: Send` を型の assert で固定する ([マルチコア対応の設計](../future/multicore.md) の「VM の並列化の備え」の制約1と2)
3. 呼び出しのスタックは `Task` が持つデータにし、Rust の再帰を使わない。`ApplyRest` と `Finish` もループの中の命令である (制約5)
4. VM は語をほかのスレッドに渡す経路を持たない。公開は、`eml_rt` の fork、join、キューへの push の中で `share` を通す道だけにする。`Word` は `Send + Sync` なので型では守れず、文書の決まりにする。破った場合は、検査モードの所有者の検査が見つける

安全点ごとの「生きていて所有しているスロット」の表は、今は作らない。a2-cancel で走っている子を安全点で取り消すときの後始末に使える。スロットの割り当てが静的なので、後から作れる。ただし、生きているスロットには借りた語もあるので、表は生存解析だけでは決まらない。Perceus の所有の状態 (verifier の所有の段と同じ計算) から作る。

スレッドをまたぐキューのうち、ランタイムのキュー (work stealing の deque、スケジューラの実行待ち) は、印を付けたクロージャの語を持つ Rust のコードとして `eml_rt` に書ける。言語のキュー (channel など) には、今の `eml_rt` で足りないものがある。足りないものは [マルチコア対応の設計](../future/multicore.md) の「未決の論点と将来の拡張」に挙げてある。
