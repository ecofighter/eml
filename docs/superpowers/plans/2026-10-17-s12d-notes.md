# S12d 作業メモ

スクリプトを書きながら気づいたことを、観点ごとに足す。段の終わりにロードマップの S13 の節へ移して消す。

## 1 線形な値

- wc (`read_input`、main.em:57-64): `Fs.open`、`Fs.read_all`、`Fs.close` の3行は `Fs.read_text` と同じ形で、`let (f, text) = …` の再束縛も読みやすい。`use try_io` の後ろに置けば、失敗の経路でも `File` の後始末を書かずに済む (`try_io` の中断が解放する)。1つのファイルを読み切るだけなら、線形性の負担はほぼない
- grep (`matching`、main.em:46-56): `once` の操作の節は、どの枝でも `k` を呼ぶか `drop k` を書く。枝ごとに `k () (count + 1)` と `k () count` を書き分けた。すぐ再開するだけの節でも `k` を明示する必要がある。Koka の `fun` の節 (暗黙に再開する節) に当たる書き方があれば、`k` は消える
- csv2jsonl (main.em:180-181): `never` の `fail` で中断する枝でも、`once` の `k` に `drop k` を書く必要がある。書かないと E3005 になる。この枝は handler ごと中断して戻らないので、`drop k` は意味のない儀式に見える。S13 の「中断で終わる経路での `Lin` の値の暗黙の後始末」の直接の材料である
- csv2jsonl: `File` は読み切ってすぐ閉じるので、`Fail` で中断する解析の間には生きていない。`Fs.read_all` で全体を読む形だと、`File` が面白い区間をまたぐことはない。`File` を持ったまま1行ずつ読む API (`Fs.read_line` のようなもの) があれば、受け渡しの負担がはっきり出るはずで、今の std では確かめられない

## 3 エフェクト

- wc (`read_input`): `use try_io` で、ブロックの残りを `try_io` に渡せる。`Result` を返す関数の本体を1行足すだけで包めるのは、Koka の `with` と同じ書き心地である
- grep (main.em:3-4、22-30、44-56): `effect Yield a` と、1行ずつ流す生産者 `stdin_lines` と、状態付きの handler `matching` で、生産者と消費者を分けて書けた。`matching` は13行で、`-c` の出力は `return` の節に置けた。型の注釈は handler の関数のシグネチャだけで足り、初回で型検査を通った
- grep (main.em:72-75): `use matching opts prefix` で、ブロックの残りを生産者として渡せる。ただし `use` は文の位置にしか書けないので、`Some (use …)` とは書けず、`let n = …` を挟んだ
- grep: `Yield` は汎用のエフェクトなのに、スクリプトごとに宣言することになる (logstat でも同じものを書く見込み)
- logstat (main.em:185-188): `use aggregate`、`use parsing`、生産者の3段を、do 記法のように上から順に書けた。`parsing` は節の中で次の段の操作 `record` を起こすだけの6行、`aggregate` は5行で、どちらも状態付きの handler である。型の誤りは出ず、初回で通った
- logstat (main.em:4-5、11-12): 解析した行を流すために `Record` を別に宣言した。試したところ、`<Yield String, Yield Int | e>` のように同じエフェクトを型引数を変えて重ねても動く (scoped labels)。ただしシグネチャに両方を書く必要があり、名前のついたエフェクトのほうが読みやすい
- logstat (main.em:73-74): 1行ずつ読む生産者は、`yield line` の後に自分を呼ぶトップレベルの再帰で4行になる。`List.each yield lines` のように、操作をそのまま関数の値として渡せる
- csv2jsonl (main.em:4-5、10-14、206-208): `never` の操作の `Fail` と、それを `Result` にする `catching` で、例外のように中断できた。`use catching`、`use convert …`、生産者の3段を重ねる形は logstat と同じで、読みやすい
- csv2jsonl (main.em:172-187): `convert` の状態は「ヘッダを読んだか」と出力の組 `(Option …, String)` で、節の中の `match` が2段になった。ヘッダの行だけ別に扱う処理は、状態付きの handler より、最初の `yield` で分ける別の handler のほうが素直だったかもしれない
- csv2jsonl: `Fail` は汎用のエフェクトで、`catching` と一緒に std にあれば、スクリプトごとに書かなくて済む

## std に足りないもの

- wc (main.em:22-23): 空白の判定 `is_space` を書き直した。`String` の中にあるが `pub` でない。文字の型がないので、バイトの値 (`b == 10`、`b >= 9 && b <= 13`) で書くことになり、読みにくい
- wc (main.em:46-48): リストの末尾に1つ足す関数がなく、`List.append fields [s]` と書いた
- grep: `-i` を入れられなかった。文字の型も、バイトから文字列を組み立てる関数もなく、大文字と小文字をそろえた文字列を作れない
- logstat (main.em:14-66): 連想配列がなく、二分探索木 (`Tree`、`upsert`、`entries`) と安定なマージソート (`sort_by`)、`split_at`、`take` を書いた。合わせて約50行で、スクリプトの本体 (解析と集計と出力、約60行) と同じくらいの量になった
- logstat: `Yield` を grep と同じく再び宣言した
- csv2jsonl (main.em:142-163): `index_of`、`nth`、`zip` を書いた
- csv2jsonl (main.em:120-133): JSON のエスケープで、バイトから文字列を作る手段がなく、16進の数字を `String.slice d (d + 1) "0123456789abcdef"` で取り出した
- csv2jsonl: バイトの値をリテラルで書けないので、`34` (`"`)、`44` (`,`)、`10` (`\n`)、`13` (`\r`) のような数で書いた。文字のリテラルがないと、解析のコードが読みにくい

## そのほか

- wc (main.em:3-5、85): レコードを `==` で比べるには `deriving (Eq)` が要る。忘れても E2006 がすぐ教えるので困らない。型の誤りはこの1つだけで、初回でほぼ通った
- wc: レコードの更新 `{ shown | lines = True }` と、文字列のリテラルのパターン (`"-l" :: rest`) で、引数の解析が短く書けた
- logstat (main.em:118-125): 複数行のレコードの更新は `{ st | total = …` を1行目に書き、続く行を `,` で始める。`{ st` の直後で改行して `| total = …` を次の行に書くと E0011 になる。`data` の複数行の宣言 (main.em:97-106) では `{` の前で改行できるので、書き方がそろわない
- logstat (main.em:83-88): `[_, _, path, status, duration]` のリストのパターンで欄の数と中身を一度に見られる
- logstat (main.em:166): 2引数のラムダの引数にタプルのパターンを書ける (`fn (_, a) (_, b) -> a > b`)
- csv2jsonl (main.em:47-82): 欄を読む関数、行を流す関数、次の行を始める関数を、ローカル関数の相互再帰で書こうとして E1001 になった (S12c のローカル関数は相互再帰できない)。「1行を読んで組を返す関数」と「行を流すループ」に分け直した。分け直した形も読みやすいが、相互再帰で書けたほうが状態機械をそのまま写せる
- csv2jsonl (main.em:105): `from` がキーワード (パラメータ付き handler の `from`) なので、変数の名前に使えない。E0011 の文言 (`expected =`) からは理由が分からない
- csv2jsonl: 誤りの経路 (欄の数、閉じていない引用符、閉じの引用符の後の文字、空の入力、知らない列、開けないファイル) は、手で動かして文言と終了コードを確かめた。UI テストでは固定していない
