# S13c-1 Unwinding aborts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every abort (`never` operation, IO failure caught by `try_io`, `exit`) unwind the VM task stack to its landing frame, releasing each unwound frame's owned slots from a per-point table, instead of composing a continuation κ that `prompt$` then drops.

**Architecture:** EP marks the two landing calls (`apply body(())` in a handle, `apply κ(v)` in `resume$`) with `prompt ev` on `Call::Apply` in Core IR and LIR. `eml_lir` exposes one ownership walk (`unwind::points`) that the verifier and the VM code generator share; the VM stores, per unwind point, the owned slots and the optional landing slot, keyed by the pc after the instruction. `yield_abort`, `exit` and the `io_failed` entry start the unwind in the VM; landing writes the dummy into the call's result slot and continues into `prompt$`, whose state-2 path no longer handles κ. `RowYield` and EP's yield points stay as they are (S13c-2 changes them).

**Tech Stack:** Rust workspace (`eml_core_ir`, `eml_lir`, `eml_vm`, `eml_rt`), Verus (`cargo verus verify -p eml_rt`), Miri, insta, the UI and REPL test harnesses.

**Spec:** `docs/superpowers/specs/2026-10-17-s13c-unwinding-design.md` (section 「S13c-1 巻き戻し」)

## Global Constraints

- Code comments and docs are Japanese, written with the `yomiyasu:yomiyasu` skill; comments explain why and cite `docs/` paths. CLAUDE.md stays English.
- The marker's text form is `prompt <var>` after the call: `let x: tobj = yields apply body.4(()) prompt ev.2`.
- Only EP emits the marker, at exactly two places: handle's `apply body(())` and `resume$`'s `apply κ(v)` (its evidence is the renewed `ev2`, the first argument of the following `prompt$`).
- Unwind points: non-tail `call` / `apply` / `clause`, `Effectful` extern instructions (`exit` included), `prim yield_abort`. Nothing else.
- No safe point (`Ctx::poll`) during an unwind.
- `RunStats` gains `unwound_frames` (frames removed by unwinding, `ApplyRest` frames included), counted in checked mode only like the other fields; `yields` counts `yield_to` only.
- Test changes allowed without further agreement (spec 「テストの変更」): kind 2 for `RunStats` snapshots, EP Core IR / LIR snapshots, `eml_rt` tests calling `yield_abort`. Any kind-1 change found while working must be added to the spec first.
- A change to `eml_rt` must pass `cargo verus verify -p eml_rt`, `verusfmt --verus-only --check $(git ls-files 'crates/eml_rt/src/*.rs')`, and the Miri `trusted::` run besides the usual gate.
- Gate per task: `cargo test --workspace`, `cargo clippy --all-targets`, `cargo fmt --check`. Use `git diff --no-ext-diff`.
- Commit messages end with the attribution lines the controller gives.

## Review Focus

- An abort while an `ApplyRest` frame is on the stack (an over-applied function whose callee fails): the leftover arguments are released, no leak in checked mode (Task 4 test `unwind/apply_rest`).
- An abort raised from a `return` clause or a clause body that `prompt$` runs in tail position, targeting an outer handler: frames below are unwound and the outer handler receives it (Task 4 test `unwind/from_return_clause`).
- An IO failure under `try_io` while the frame holds a borrowed field whose retained owner crosses the extern (Perceus resolves retained owners only before calls): the owner is released once, the field never (Task 4 test `unwind/borrowed_field_across_extern`).
- A `multi` continuation resumed twice where the second run aborts: captures shared by both runs are released exactly once each (Task 4 test `unwind/multi_resumed_twice`).
- `exit` in a REPL input with a `File` open in deep frames: the session goes on and `close` reports no leak (Task 4 transcript `unwind/exit_with_file.repl`).

### Task 3: The shared unwind-point walk in `eml_lir`

**Files:**

- Modify: `crates/eml_lir/src/lib.rs` (`pub mod unwind;`), `crates/eml_lir/src/verify.rs` (the ownership walk records per-statement owned state through a hook used by `unwind::points`; the verifier keeps its checks)
- Create: `crates/eml_lir/tests/unwind.rs`; Modify: `crates/eml_lir/tests/main.rs`

**Interfaces:**
- Produces:
  ```rust
  pub struct UnwindPoint {
      pub block: BlockId,
      pub stmt: usize,               // index into block.stmts
      pub owned: Vec<(VarId, u32)>,  // owned RC variables right after the statement, minus its own binder, ascending VarId, count >= 1
      pub landing: Option<VarId>,    // the `prompt` var of an apply
  }
  pub fn points(program: &Program, function: &LirFn) -> Vec<UnwindPoint>
  ```
  Input must be post-Perceus LIR that passes `verify`; `points` panics on an ownership inconsistency. Points are exactly the statements listed in Global Constraints, in block then statement order.
