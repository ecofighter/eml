# S13e-2 Handler Specialization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** In `optimize`, replace a `handle` whose body is a known function, and whose path to every `perform` is made only of tail calls, by direct calls into per-handler copies of the path functions. A `perform` then becomes either the clause body inlined in place (immediately resuming clauses) or a tail call of the clause with a continuation closure (other clauses). After this, `Iter.generate` with a tail-recursive producer has 0 yields, and the push form (`Yield.fold`) has 0 evidence steps.

**Architecture:** A new phase `handlers` in `crates/eml_core_ir/src/optimize/handlers/` runs after S13e-1's `specialize` and its `yields` recomputation. For each eligible `handle` it creates handler copies `f{H}` of the path functions and continuation functions `f{H}$kN`. Then `yields` is recomputed again and unreachable functions are dropped.

- Every `perform` that targets H ends the current piece of code. The rest of the function after the `perform` is copied into a continuation function, which takes the live variables, the resume value and, for a stateful handler, the next state.
- For an immediately resuming clause, the inlined clause body ends in a direct tail call of that continuation function. For any other clause, the continuation's closure is passed as `k`.

So the handler state is always a function parameter, and no block-level state threading is needed.

**Tech Stack:** Rust (`crates/eml_core_ir`), insta, `eml_test_support`, the UI and REPL harnesses, `bench/` with `crates/eml_vm/tests/bench.rs`, `bench/run.sh` (macOS).

**Spec:** `docs/superpowers/specs/2026-10-18-s13e-specialization-design.md` (「S13e-2 handler への特殊化」, plus 「最適化パスの共通の形」). S13e-1's implementation is described in `docs/spec/core-ir.md` 「最適化」.

## Global Constraints

- Code comments and docs are Japanese, written with the `yomiyasu:yomiyasu` skill. Comments explain why and cite `docs/` paths. CLAUDE.md stays English.
- Pass order inside `optimize`: `specialize`, then `kept_marks` / `recompute_yields`, then `handlers`, then `kept_marks` / `recompute_yields` again, then `retain_reachable`. `handlers` emits no `tail`, `box`, `unbox` or RC instruction, and its output passes `verify_translated`.
- Determinism:
  - Handler copies and continuation functions are built from the code as it stands after `specialize` and the first `recompute_yields`. That code is already a function of each name.
  - Every decision depends only on the handle's owner function and the path functions' code.
  - Names:
    - A handler copy is `<f>{H=<ret>}`, where `<ret>` is the name of the handle's `return` clause function. Translate makes one per handle, and S13e-1 makes one per owner-keyed copy, so it identifies the handler.
    - A continuation function is `<f{H}>$k<N>`, where N counts the targeted `perform`s of `f{H}` in block and statement order, from 0.
    - A clause copy that takes `k` as a closure is `<g>{k}`.
    - Use S13e-1's `NAME_LIMIT` hashing for long names, hashing the full name, and keep a `$k<N>` suffix outside the hash.
- A handle is specialized only if every condition in the spec's 「対象」 holds for every path function, with path functions found by `crate::tail::tail_position_call`. Path functions are only the tail-reachable functions that are `yields`. A tail call to a non-`yields` function, or a tail `apply` that is not `yields`, becomes a non-tail call followed by a tail call of the `return` clause.
- Effects whose operations are all `never`, and `IO`, are never targeted.
- Statements that came from an inlined clause body are never rewritten as targeting H. A `perform` of E inside a clause body goes to the outer handler.
- `internal`:
  - Handler copies `f{H}` are not `internal`.
  - Continuation functions `f{H}$kN` and clause copies `<g>{k}` are `internal`. All their users sit inside the same name-determined family, so whether each one is used as a value or called directly is fixed by its name.
  - Update the spec's 「鍵と名前」 and `docs/spec/core-ir.md` 「最適化」 to say so.
- The `k` closure of a continuation takes its mark from the clause's `k` parameter (`lin` for `once`).
- Test changes:
  - Kind 1: none expected. If one is found, add it to the spec's 「種類1」 with the reason and get the user's confirmation before commit.
  - Kind 2: within the spec's 「種類2」 scope.
  - Standing ruling: an existing test whose program now gets specialized, and whose purpose was to exercise EP's handle, perform or resume lowering (mostly `crates/eml_core_ir/tests/evidence.rs`, and `perceus.rs` / `lowering.rs` where they dump EP output), is rewritten so the handle body reaches the handle through data (`hide x = Box x`). Its assertions are kept, and it is listed in the commit message. A changed UI stdout/stderr is a bug, never a snapshot update.
- Gate per task: the task's test commands, then `cargo test`, `cargo clippy --all-targets`, `cargo fmt --check`. Use `git diff --no-ext-diff`.
- Commit messages end with the attribution lines the controller gives.

### Task 2: Handler copies for immediately resuming clauses

**Files:**
- Create: `crates/eml_core_ir/src/optimize/handlers/mod.rs` (site discovery, path analysis, the copy table, the phase entry), `crates/eml_core_ir/src/optimize/handlers/piece.rs` (cutting a function at a `perform` into a continuation function, and inlining a clause body)
- Modify: `crates/eml_core_ir/src/optimize/mod.rs` (pass order, per Global Constraints)
- Test: `crates/eml_core_ir/tests/optimize.rs`, `crates/eml_vm/tests/bench.rs` (snapshots), and the UI tests `tests/ui/run/effects/specialized_handler_under_state.em` and `tests/ui/run/effects/specialized_clause_performs_outer.em`
- Docs: update the spec's 「S13e-2 handler への特殊化」 「書き換え」. The immediately resuming case now ends the inlined body with a tail call of the continuation function `f{H}$kN(live…, v, s)` instead of a jump. The reason: the state stays a function parameter, so no block-level threading is needed and no pair is allocated. The cost is one tail call per `perform`. Mark this as decided while planning. Also record the `{H=<ret>}` key and name.

**Interfaces:**
- Produces (crate-private):
  - `pub(crate) fn handlers(program: &mut Program)`.
  - `struct Site { owner: FnIdx, block: BlockId, stmt: usize }`: a `let x = handle …` whose body atom is a known closure (`known::known_closures`) or `Atom::Fn`.
  - `fn path(program: &Program, body: FnIdx, effect: u32) -> Option<Vec<FnIdx>>`: the `yields` functions reachable by tail `Direct` calls, or `None` if any condition of the spec's 「対象」 fails.
  - `enum ClauseForm { Resuming, Other }`: decided per clause function by shape. `Resuming` means every use of the `k` parameter is a tail-position, mask-free `resume k(v, s)`.
  - `fn cut(function: &CoreFn, block: BlockId, stmt: usize) -> (Vec<VarId>, CoreFn)`. It returns the live variables at the `perform` (excluding its result, ascending), and a continuation function. That function's parameters are those variables, then the resume value (the `perform`'s result variable), then the state if stateful. Its body is a new entry block holding the rest of that block, followed by every block reachable from there, in their original order, renumbered. Unreachable blocks are dropped. Variables keep their ids, and live variables become entry parameters.
  - `fn inline_clause(target: &mut CoreFn, at: (BlockId, usize), clause: &CoreFn, args: &[Atom], state: Atom, resume: impl Fn(Atom, Atom) -> Term)`. It splices a copy of the clause's blocks with fresh variables, substitutes its parameters (captures, the operation arguments, the state), and replaces each tail `resume k(v, s)` with `resume(v, s)`.

Rules (spec 「書き換え」, with the Task 2 decision):
- Handler copy `f{H}` parameters are f's parameters, then the clause and `return` captures in clause order, then the state (stateless handlers have no state parameter).
- A `perform E.op(a…)` in `f{H}` whose clause is `Resuming` becomes `inline_clause`, with `resume = |v, s| tail call f{H}$kN(live…, v, s)`. `f{H}$kN` comes from `cut` and is itself a handler copy, rewritten by the same rules.
- `return r` in a path copy becomes `tail call ret(captures…, r, state)`.
- A tail `Direct` call to a path function g becomes `tail call g{H}(args…, captures…, state)`. A tail call to a non-`yields` function, or a non-`yields` tail `apply`, becomes `let r = <call>` followed by `tail call ret(…, r, state)`.
- In the owner, the handle site becomes `let x = call body{H}(body captures…, clause captures…, init)`.
- A handle with any `Other` clause is left alone in this task (Task 3 adds it).

### Task 3: Clauses that keep `k`

**Files:**
- Modify: `crates/eml_core_ir/src/optimize/handlers/mod.rs` and `piece.rs`
- Test: `crates/eml_core_ir/tests/optimize.rs`, `crates/eml_vm/tests/bench.rs`, and the UI tests `tests/ui/run/std/specialized_iter_file_drop.em`, `tests/ui/run/effects/specialized_multi_resume.em` and `tests/ui/run/effects/specialized_never_operation.em`
- Docs: the spec's 「鍵と名前」 and `docs/spec/core-ir.md` 「最適化」 get the `internal` rule for `f{H}$kN` and `<g>{k}`.

**Interfaces:**
- Consumes: Task 2's `cut`, `Site`, `path`, `ClauseForm`.
- Produces: `fn clause_with_k(clause: &CoreFn) -> CoreFn`. It is the copy `<g>{k}`:
  - the `k` parameter keeps its position, with Repr `tobj` and the parameter's mark;
  - `closure cont$(k)` / `closure cont$state(k)` are replaced by `k` itself (their uses are renamed);
  - `resume k(v, s)` becomes `apply k(v)` for a stateless handler and `apply k(v, s)` for a stateful one. The `apply` is `yields` iff the clause function is `yields`.

Rules:
- A `perform E.op(a…)` whose clause is `Other` becomes `let c = closure f{H}$kN(live…)` followed by `tail call <g>{k}(captures…, a…, c, state)`. For a `never` operation (its clause has no `k`), it becomes `tail call g(captures…, a…, state)`, and the rest of the function is dropped.
- The `closure`'s mark is the clause `k` parameter's mark.
