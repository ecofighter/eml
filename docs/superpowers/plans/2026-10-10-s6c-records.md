# S6c レコード 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 名前付きのフィールドを持つコンストラクタ (直和型を含む)、作る式 `Con { f = e }`、更新 `{ e | f = v }`、射影 `e.f` と `t.0`、セクション `(.f)` と `(.0)`、レコードのパターンを使えるようにし、無名のレコードを言語から外す。

**Architecture:** 層ごとに下から積む。Task 1 で型検査のタプルの内部表現からラベルをなくす (振る舞いは変えない)。Task 2 でレイアウトの規則を2つ変える。Task 3 でレコードの構文と CST を入れ、HIR は仮の E0004 を出す。Task 4 で宣言、作る式、パターンを HIR、型検査、translate、`deriving` に通す。Task 5 で射影、更新、セクションを入れる。Task 6 でラムダの引数を後で検査する。Task 7 で文書とベンチマークの記録を段の終わりの形にする。

**Tech Stack:** Rust (edition 2024)、rowan、la-arena、insta、eml の UI テスト、`bench/run.sh`。

**Spec:** `docs/superpowers/specs/2026-10-10-s6c-records-design.md`。spec は main にコミットしてある (5adf3ff)。計画も Task 1 の前にコミットする。実装する人は、各タスクの前に spec の該当する節を読む。spec が規範で、計画とずれたら spec に従い、ずれを報告する。

## Global Constraints

- 各タスクの終わりに、`cargo test` がすべて通り、`cargo clippy --all-targets` が警告を出さず、`cargo fmt --check` が差分を出さない。`cargo clippy -p eml_cli --no-default-features --features types` と `--features core` も通る。`cargo test -p eml_cli --test integration citations` も通る。途中のタスクでも、ワークスペース全体を壊したままコミットしない

- spec の「成否の変更」に挙げていないテストを、消したり、run と check-fail の間で動かしたりしない。必要になったら作業を止めて報告する (CLAUDE.md の Testing)

  - `eml_types`: `TyShape::Tuple(Vec<Ty>)`、`TypeKind::Tuple(Vec<TypeId>)`、`ShapeTy::Tuple(Vec<ShapeTy>)` (Task 1)。`typed.fields: ExprId → FieldTarget`、`typed.updates: ExprId → (ConstructorId, Vec<u32>)`、`typed.discarded: ExprId → Vec<(u32, Ty)>` (Task 5。`typed` は型検査の結果の表で、実際の型の名前は今のコードに合わせる)、`Origin::Field { ctor, field }` (Task 4)、`KindReason::DiscardedField` (Task 4)、`codes::FIELD_NEEDS_KNOWN_TYPE` (`ErrorCode(2013)`)、`codes::NO_SUCH_FIELD` (`ErrorCode(2014)`) (Task 5)

  - `eml_hir`: `Constructor::field_names: Option<Vec<FieldName>>`、`FieldName { name: String, range: TextRange }`、`ExprKind::Record { ctor, fields: Vec<(u32, ExprId)> }` (Task 4)、`ExprKind::Update { base, fields: Vec<(FieldName, ExprId)> }`、`ExprKind::Field { base, field: FieldUse }`、`FieldUse` (Task 5)、`Body::omitted_fields: ArenaMap<PatId, (ConstructorId, u32)>` (Task 4)、`Body::use_lambdas: HashSet<ExprId>` (Task 6)。`codes::DUPLICATE_FIELD` (`ErrorCode(1045)`)、`codes::UNKNOWN_FIELD` (`ErrorCode(1046)`)、`codes::MISSING_FIELDS` (`ErrorCode(1047)`) (Task 4)
- 診断の文言は spec と各タスクに書いたとおりにする。変えるときは、そのタスクのテストと一緒に変え、理由をコミットメッセージに書く

## Review Focus

spec が求めるが、どのタスクのテストも直接は確かめない形のうち、使う人が最初に踏みそうなもの。各行のテストは、対応するタスクに入れてある。

```rust
//! レコードの構文 (docs/superpowers/specs/2026-10-10-s6c-records-design.md の「構文」)。

use crate::common::{diagnostics, lines, shape};

#[test]
fn a_record_alternative_has_field_declarations() {
    insta::assert_snapshot!(shape("data P =\n  | P { name : String, age : Int }\n  | Q Int"), @"");
}

#[test]
fn construction_update_and_patterns() {
    let text = lines(&[
        "f p = match p with",
        "  | P { name, age = a } -> P { name, age = a + 1 }",
        "  | q -> { q | age = 0 }",
    ]);
    insta::assert_snapshot!(shape(&text), @"");
    assert_eq!(diagnostics(&text), Vec::<String>::new());
}

#[test]
fn a_constructor_followed_by_an_update_reads_the_update_as_an_argument() {
    // `Some { p | age = 1 }` は `Some` に更新を渡す式である。`Some P { … }` は `Some (P { … })` と読む
    insta::assert_snapshot!(shape("x = Some { p | age = 1 }\ny = Some P { a = 1 }\nz = M.P { a }"), @"");
}

#[test]
fn an_update_base_needs_parentheses_around_expression_forms() {
    assert_eq!(
        diagnostics("x = { match o with | A -> p | age = 1 }")[0],
        "E0012 1:7 `match` expression must be parenthesized here"
    );
    assert_eq!(diagnostics("x = { p | }"), ["E0011 1:11 expected a field"]);
}

#[test]
fn anonymous_records_are_syntax_errors_and_are_skipped() {
    assert_eq!(diagnostics("t : { name : String }\nt = 1"), ["E0011 1:5 expected a type"]);
    assert_eq!(diagnostics("x = { name = 1 }"), ["E0011 1:12 expected `|`"]);
    assert_eq!(diagnostics("f { a } = a"), ["E0011 1:3 expected a pattern"]);
}

#[test]
fn field_indices_are_plain_decimals() {
    assert_eq!(diagnostics("x = (t.0, t.0.1, (.1))"), Vec::<String>::new());
    assert_eq!(diagnostics("x = t.01"), ["E0011 1:7 expected a field index"]);
    assert_eq!(diagnostics("x = t.0x1"), ["E0011 1:7 expected a field index"]);
}

#[test]
fn multi_line_records_parse_in_every_position() {
    let text = lines(&[
        "f u =",
        "  let p = P {",
        "    name =",
        "      long_name u,",
        "    on_save = fn e ->",
        "      log e,",
        "    age = 3,",
        "  }",
        "  g P {",
        "      name = \"a\",",
        "    } (match p with",
        "      | P { name } -> name)",
    ]);
    assert_eq!(diagnostics(&text), Vec::<String>::new());
}

#[test]
fn record_patterns_in_operator_equations_and_top_level_bindings() {
    assert_eq!(diagnostics("P { a } <+> q = a"), Vec::<String>::new());
    assert_eq!(diagnostics("P { a } = x")[0], "E0011 1:1 top-level pattern bindings are not allowed");
}

#[test]
fn a_brace_counts_as_one_nesting_level() {
    // `(` と同じく1段に数え、フィールドの数は数えない
    let fields: Vec<String> = (0..300).map(|i| format!("f{i} = 0")).collect();
    assert_eq!(diagnostics(&format!("x = P {{ {} }}", fields.join(", "))), Vec::<String>::new());
}
```

射影の解決を1つの関数にまとめ、射影と更新で使う。

```rust
/// 射影と更新のフィールドを、その時点の型から引く。型が決まっていなければ E2013、ないフィールドなら E2014 を出す
/// (docs/superpowers/specs/2026-10-10-s6c-records-design.md の「型検査」)。
fn resolve_field(&mut self, base_ty: Ty, field: &FieldUse, base: ExprId) -> Option<ResolvedField> {
    match self.table.shape(self.table.resolve(base_ty)).clone() {
        TyShape::Var(_) => { /* E2013。base がラムダの引数の局所変数なら help を変える */ None }
        TyShape::Error => None,
        TyShape::Con(ty, args) => { /* 1つのコンストラクタで、field_names に名前があれば、その型を args で具体化 */ }
        TyShape::Tuple(elements) => { /* 番号が範囲内なら elements[i] */ }
        _ => { /* E2014 */ None }
    }
}
```

- `ResolvedField` は、コンストラクタ (タプルなら要素の数)、フィールドの番号、フィールドの型、残りのフィールドの (番号、具体化した型) を持つ
- `ExprKind::Field`: `base` を推論し、`resolve_field` の結果のフィールドの型を返す。`typed.fields` と `typed.discarded` (残りのフィールド) に記録する
- `ExprKind::Update`: `base` を推論して解決する (タプルは E2014)。各フィールドの名前を引き (なければ E2014)、式を `Origin::Field` で検査する。`typed.updates` と `typed.discarded` (上書きされる古いフィールドの型) に記録する。結果は `base` の型
- 型の具体化は、コンストラクタの型 (`path` で具体化した関数型) の矢印を剥がして得る形でよい。`Con` の型引数との単一化で得た型を使う
- `TypedProgram` (`lib.rs`) に `fields`、`updates`、`discarded` の表を足し、書き出しの所で `Ty` を `TypeId` に書き出す (今の `exprs` の表と同じ扱い)
- `usage.rs`: `ExprKind::Field` は `base` の1回の消費、`ExprKind::Update` は `base` とフィールドの式を `in_order` でたどる。どちらも `typing.discarded` の各型に、`KindReason::DiscardedField` で `kind_at_most(ty, Unr)` を出す (範囲は射影か更新の式。セクションから組んだラムダの中なら help を付けない)
- `carry.rs`: `Field` は `base`、`Update` は `base` とフィールドの式を `parts` でたどる
- `codes` に E2013 と E2014 を足す

- [ ] **Step 6: translate を直す**
