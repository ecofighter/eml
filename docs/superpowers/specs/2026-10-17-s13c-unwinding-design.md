# S13c 中断の巻き戻しの設計

## 目的と範囲

S13c (中断の巻き戻し) の設計である。ロードマップの S13c の節 (`docs/future/roadmap.md`) の「決めたこと」を細部まで決め、「論点」に答える。完了の条件は次の3つである。

- 本体で `println` を呼ぶ総称な handler が、`RunStats` で yield を数えない
- 中断で巻き戻した `File` が閉じ、検査モードで漏れがない
- `never` の操作の前の `drop k` が要らない

中断 (`never` の操作、`try_io` が捕まえる IO の失敗、`exit`) は、今は普通の yield と同じく、途中のフレームが継続 κ を組み立て、`prompt$` が κ を捨てて後始末する。そのため `IO` と `never` の操作を「yield しうる」と数えるしかなく、純粋なコールバックを渡した総称な handler でも、`<IO>` の中で呼ぶと1要素ごとに yield する。S13c では、中断をタスクのスタックの巻き戻しにして κ を作らないようにし、そのうえで `IO` と `never` の操作だけのエフェクトを yield の地点から外す。

作業は3つに分け、この順に1つずつ main に入れる (私の判断)。

| 作業 | 中身 | 満たす完了の条件 |
|---|---|---|
| S13c-1 | 巻き戻し。着地の印、巻き戻しの表、VM の巻き戻し、`yield_abort` と `exit_abort` の形の変更 | 2つ目 |
| S13c-2 | yield の地点の分類から `IO` と `never` の操作だけのエフェクトを外すこと、すぐに再開する節の under | 1つ目 |
| S13c-3 | 戻らない呼び出しで終わる経路での `Lin` の値の暗黙の後始末 | 3つ目 |

S13c-2 は S13c-1 に依る。`yields` でない関数の中で中断が起きても、巻き戻しなら κ が要らないためである。S13c-3 はほかの2つに依らないが、巻き戻しが一時の値を解放することを前提に説明しているので最後に置く。計画は作業ごとに書く。

次のものは範囲に入れない。

- row の最小の具体化: S13d で入れる。外側に `State` などユーザーのエフェクトの handler がある所の yield は、S13c では残る
- yield しうる外のエフェクトを呼ぶすぐに再開する節をその場で動かすこと (論文の under の残り): 再開の後に evidence を探し直す仕組みが要る。ロードマップの「evidence passing の最適化」に残す
- 実行時エラー (オーバーフロー、ゼロ除算、ヒープの誤り、止めたこと) を巻き戻しにすること: 今のまま評価全体の中断にする

## 2026-10-17 に決めたこと

- 暗黙の後始末の対象にする「戻らない呼び出し」には、`never` の操作と `exit` だけでなく、`exit` を中で呼ぶ自作の関数 (`die : String -> <IO> a`) も含める (判断の基準はユーザーが決めた。「実用的なプログラムで使いそうか」)。S12d のスクリプトは `eprintln` と `exit 2` の組を何度も書いており (`deploy` だけで4か所)、これを関数に切り出す形はよく出る。直接の `exit` だけを許すと、関数に切り出したとたんに `drop` が要り、規則として一貫しない
- 中断の行き先は、IR の呼び出しに付ける着地の印 `prompt ev` で見分ける (ユーザーが決めた)。evidence の物体にスタック上の位置を持たせる案は、`eml_rt` の evidence (Verus の証明の対象) に VM の都合が入るので採らなかった。印と表の形は、後のネイティブ化でもそのまま使える

## S13c-1 巻き戻し

### 着地の印

- Core IR と LIR の末尾でない `apply` に、省ける印 `prompt v` を足す。v は evidence (`obj`) の変数である。意味は「宛先が v の中断は、この呼び出しの結果にダミーを入れて、呼び出しの次から続ける」である
- テキストの形は `let x: tobj = yields apply body.4(()) prompt ev.2` のように呼び出しの後に書く
- EP だけが付ける。付けるのは、handle の `apply body(())` と、`resume$` の `apply κ(v)` の2か所である。どちらも直後に `prompt$(ev, ret, x)` が続き、`prompt$` が `yield_status(ev)` の状態 2 (この evidence 宛ての中断) の経路に進む
- verifier の規則 (Core IR の evidence の段と、LIR のすべての段): 印の付いた呼び出しは末尾の位置になく、v は呼び出しの後で生きている `obj` の変数である。LIR の所有の段では、v が呼び出しの時点で所有されていることも確かめる。巻き戻しは着地したフレームの値を解放しないので、v は着地の後も有効でなければならない
- 縮約は印の付いた呼び出しを `tail` にしない。直後に `prompt$` の呼び出しが続くので、今の規則のままでも末尾の位置にはならない。verifier の規則で確かめるだけにする

### 巻き戻しの表

- VM のコード生成は、関数ごとに「巻き戻しの地点」の表を作る。地点は、末尾でない呼び出し (`call`、`apply`、`clause`)、`Effectful` の extern の命令 (`exit` を含む)、`prim yield_abort` である
- 各地点が持つのは、その命令の後で生きていて所有している RC の対象 (`obj`、`tobj`) の変数の slot の列と、印があれば着地の evidence の slot である。命令が束縛する変数 (呼び出しの結果、extern の行き先) は含めない
- 所有を求める必要があるのは、Perceus の規則では、持ち主が呼び出しの後も生きているとき、借りたフィールドが呼び出しをまたぐためである ([LIR](../../spec/lir.md) の「所有を取る時点」の 2.)。借りた変数を解放すると、持ち主の解放と合わせて2回手放すことになる
- 生存は既存の `eml_lir::liveness` を使う。所有は、verifier の所有の段と同じ前向きの走査 (合流のブロックはすべて所有で始まり、`switch` の行き先は前の状態を引き継ぐ) で求める。この走査を `eml_lir` の関数として切り出し、verifier と VM のコード生成で共有する
- 表は、地点の命令の次の命令の位置で引く。呼び出しの地点では、それがフレームの見出しにある戻り先と一致するためである。`CodeBase` に位置の順で持ち、二分探索で引く。表の形と置き場所は作る人に任せる

### VM の巻き戻し

中断を始めると、VM は次の手順でタスクのスタックを巻き戻す。

1. 今のフレームの地点の表を、今の命令の次の位置で引く
2. 着地の evidence の slot があり、その語が中断の宛先と同じなら、着地する。呼び出しの結果の slot にダミーの物体を書き、表を引いた位置から続ける。手順を終える
3. そうでなければ、表の slot をすべて手放す (`Heap::decref`。`Lin` の物体でも誤りにならない)。`File` はここで閉じる
4. フレームを外し、見出しの戻り先と呼び出し元のフレームに移る。呼び出し元が `ApplyRest` の枠なら、残りの引数を手放してその枠も外す
5. 戻り先が `Finish` なら手順を終える。`exit` の中断ならそこで終わりの処理をし、そうでなければ内部の誤りにする。そうでなければ 1. に戻る

- 巻き戻しの間は安全点を置かない。フレームの数だけの仕事で終わり、着地の後の `prompt$` の先で次の安全点に当たる (私の判断)
- 中断を始める所は次の3つである
  - `prim yield_abort(ev, c)`: `never` の節の入口が呼ぶ。`Ctx::yield_abort` で yield の記録に宛先と節の本体を入れ、巻き戻す。基本操作は戻らない
  - `exit n`: 終了コードを `Task` に覚え、`Ctx::exit_abort` の後で巻き戻す。宛先は不死のダミーの物体なので、どの着地の印とも合わず、`Finish` まで届く
  - `try_io` が捕まえる IO の失敗: 今と同じく `io_failed` の節の入口を `clause` の呼び出しと同じ形で呼ぶ。入口が `yield_abort` を呼んで巻き戻す。extern の命令のフレームは呼び出し元のフレームになり、extern の地点の表が使われる
- `Finish` での `exit` の後始末は、`yield_finish` で yield の状態をなしに戻し、`evv` を空に戻すだけになる。κ を取り出して手放す手順はなくなる
- 巻き戻しは、途中の handler の実行も同じ表で片付ける。handle を含むフレームが持つ evidence、`return` の節のクロージャ、外側の `evv` は、そのフレームの生きている所有の slot なので、ここで手放す。パラメータ付き handler の状態は evidence の欄にあり、evidence が解放されるときに手放す。今の `prompt$` の状態 3 の経路 (`rewind$` で κ に入れる形) は、中断では通らなくなる
- 中断の途中の `evv` には意味がない。着地した `prompt$` は最初に `evv` を `ev` の外側に戻し、そのとき今の `evv` (内側の evidence を含むリスト) を手放す。`exit` では `Finish` が空に戻す
- `multi` の継続を再開した区間のフレームも、普通のフレームとして同じ表で片付ける。共有されたクロージャへの `apply` は捕獲を写すので、区間のフレームは自分の写しを持っている。特別な扱いは要らない (論点への答え)

### `eml_rt` と EP の変更

- `Ctx::yield_abort` は κ の引数をなくし、`yield_abort(ev, clause)` にする。yield の記録の κ の欄は `()` にする。`exit_abort` も κ を `()` にする (今と同じ)。Verus の証明を合わせて直す
- `never` の節の入口は `prim yield_abort(ev, c)` を呼び、続けて `return` でダミーを返す形のままにする。この `return` には実行が届かない
- `prompt$` の状態 2 の経路は、`drop ret` と `drop x` の後、`c = yield_finish()` と状態を得て `apply c(st)` を末尾で呼ぶ。κ を取り出して `drop` する手順を消す
- `yield_cont_take` と `yield_cont_set` は普通の yield のためだけに残る
- IO の失敗で extern の行き先にダミーを入れる規則 ([LIR](../../spec/lir.md) の「ダミーの値」、[VM](../../spec/vm.md) の「IO の失敗」) と、`io_failed` の節の入口を呼んだ直後の安全点の例外 (失敗した extern の位置を付ける規則) は消す。入口が戻らないためである
- S13c-1 では、yield の地点の分類 (`RowYield`) も EP の yield の確かめも変えない。中断が通る途中のフレームの yield の確かめと遅い道はそのまま残るが、巻き戻しで飛ばされるので実行されない

### `RunStats`

- `yields` は `yield_to` を実行した回数だけにする。中断は yield ではなくなるためである
- `unwound_frames` を足す。巻き戻しで外したフレームの数 (`ApplyRest` の枠を含む) である。中断の仕事が呼び出しの深さに比例することを、スケーリングのテストで確かめるためである (私の判断)

## S13c-2 yield の地点と under

### yield の地点の分類

- `RowYield` で、row のラベルのうち、`IO` と、すべての操作が `never` のエフェクト (`Std.Fail` など) を数えなくする。残りのラベルが1つもなければ、row 変数の末尾で今と同じく分類する。[型と Kind](../../spec/types.md) の「row の具体化の記録」を書き直す
- その結果、`<IO>` だけ、`<Fail x>` だけ、その2つだけの row の関数は `yields` でなくなる。`never` の操作と `exit` と IO の失敗は、巻き戻しで κ を作らずに中断するので、`yields` でない関数の中で起きてかまわない

### EP の変更

- `Effectful` の extern の呼び出しを yield の地点から外す。直後の yield の確かめと遅い道を置かない。`yields` でない関数が `Effectful` の extern を呼ぶと内部の誤りにしていた検査を消す。`$externN` は、行が `Effectful` でも `yields` にしない
- `never` の操作の `clause` の呼び出しを yield の地点から外す。戻らないので確かめは要らない
- `never` の節の入口に `yields` の印を立てない
- `mask` の項目のラベルが yield しないエフェクトだけのとき、`mask` 付きの呼び出しが `yields` でない関数に現れうる。そのときは、包みに yield の確かめと遅い道を置かず、`evv_mask`、`evv_set`、呼び出し、`evv_set(w0)` だけにする。「`mask` を持つ関数はいつも `yields`」という今の前提を消す
- すぐに再開する節の条件 ([Core IR](../../spec/core-ir.md) の「`perform` と節の3つの形」) で、`IO` の extern の呼び出しと、`never` の操作の末尾でない `perform` を、yield の地点に数えなくする

### under

- すぐに再開する節の本体が、呼び出し (`call`、`apply`、`clause`)、`Effectful` の extern、`perform` のどれかを含むとき、入口を under の形にする。この条件は EP が Core IR の形だけで決める。`State` の `get` と `put` のように何も呼ばない節には足さない (私の判断。型から決める案は、関数に新しい印が要るので採らなかった)
- under の形: 入口の先頭で `w = evv_get()`、`o = ev_evv(ev)`、`evv_set(o)` とし、`ev_set_state(ev, s)` の後、`return v` の前に `evv_set(w)` で戻す
- 節の本体は handler の外側の `evv` で動くので、節の中で起きた中断 (`fail`、IO の失敗) は、handle の本体の中の `try_io` や `to_result` ではなく、handle の外の正しい handler に届く。今は、これを避けるために `IO` の extern を yield の地点に数え、節をその場で動かさないでいる
- 節は yield しないので、再開の後に evidence を探し直す仕組みは要らない。中断で巻き戻されるときは、入口のフレームが持つ `w` を表が手放す

## S13c-3 戻らない呼び出しの暗黙の後始末

### 戻らない呼び出し

- 次をすべて満たす呼び出しを「戻らない呼び出し」とする
  - 呼ばれるものが、型スキームを持つ宣言 (トップレベルの関数、extern の関数、エフェクトの操作、クラスのメソッド) への参照である。ローカル関数、ラムダの引数、`let` で束縛した値は単相なので当たらない
  - 宣言の型の矢印をすべて満たす数の引数を渡している。足りない呼び出しは関数を返すだけである
  - 最後の結果の型が量化された型変数で、その変数が型のほかの場所 (引数の型と、どの矢印の row) に現れず、クラスの制約も付いていない
- パラメトリシティから、こういう関数はその型の値を作れないので、普通には戻れない。当たるのは `never` の操作 (`fail : x -> a`)、`exit : Int -> <IO> a`、自作の `die : String -> <IO> a` である。`State.get : Unit -> <State s | e> s` は `s` が row に現れるので当たらない。クラスの制約を除くのは、`default : Default a => a` のように値を返すメソッドがありうるためである
- 戻らない呼び出しが本当に戻らないことは、型の健全性から従う。処理系は実行時に確かめない

### 線形性

- 戻らない呼び出しで終わる経路では、生きている変数を消費しなくてよい。使用回数のパス (`eml_types/src/usage.rs`) で、分岐ごとの消費の一致を確かめるときは、戻らない呼び出しで終わる枝を、どの消費の集合とも合うものとして扱う。すべての枝が戻らなければ、その分岐全体が戻らない
- 戻らない経路でも、二重使用 (E3002) は今と同じく誤りにする。緩めるのは「使わなかった」側だけである
- 節の `k` も同じ扱いにする。`once` の `k` を、戻らない呼び出しで終わる経路では呼ばなくても `drop` しなくてもよい。`csv2jsonl` の `drop k` と `fail …` の組は `fail …` だけで書ける
- 「消費しない」は、使用回数のパスのほかの規則と同じく評価の順を区別せず、その経路のどこでも消費しないことである。戻らない呼び出しの後ろの、実行が届かない所で消費する変数 (`(fail "x", Fs.close f)` の `f`) は暗黙に手放さない。その変数は呼び出しをまたいで生きているので、巻き戻しが解放する
- 1つの経路に戻らない呼び出しが複数あるとき (`g (fail "a") (fail "b")`、ブロックの中の `exit 1` の後の `fail "b"`) は、評価の順で最初に実行される呼び出しだけを記録の対象にする。後ろの呼び出しには実行が届かない。両方の前に `drop` を置くと、2つ目の `drop` が手放し済みの変数を消費し、所有の verifier が拒む
- ラムダと節の本体も同じ規則に従う。本体が捕まえた変数はその本体の変数として扱うので、`File` を捕まえた `ctl` の節が、一方の枝で `File` を使い、もう一方の枝で `fail` を呼ぶ形も書ける。translate は、持ち上げた関数の中に `drop` を置く (私の判断)
- 持ち越しのパス (E3006) は、暗黙に手放す変数を戻らない呼び出しの時点で死んだものとして扱う。translate が呼び出しの前に手放すので、呼び出しをまたいで持たないためである
- 使用回数のパスは、記録の対象の戻らない呼び出しごとに、その経路のどこでも消費されない変数の一覧を副表に記録する。誤りのある本体では記録しなくてよい (translate に届かない)

### translate

- 戻らない呼び出しの引数を評価した後、呼び出しの命令の前に、副表の変数のうち印が `unr` でないものごとに `drop v` を置く。順は変数の番号の順にする (私の判断)。`unr` の変数は、生きていないので Perceus が `decref` する
- 呼び出しの前に評価して一時に持っている値 (`(f, fail "x")` の `f`) と、呼び出し元のフレームが持っている値は、S13c-1 の巻き戻しが解放する。translate は何もしない

### 破棄処理

- 今と同じく、破棄処理は物体の解放だけである (`File` を閉じる)。エフェクトを起こさず、失敗もしない。ユーザーが定義する破棄処理は置かない。これを [線形性](../../spec/linearity.md) の「暗黙の後始末」に書く (論点への答え)
- 暗黙の後始末が起きるのは、中断の巻き戻しと、戻らない呼び出しの前の `drop` だけである。「通常の制御フローでは暗黙の後始末をしない」原則は、この2つを例外として書き直す

## 論点への答え

| 論点 | 答え |
|---|---|
| 呼び出しの位置ごとの表の作り方と大きさ | VM のコード生成が LIR の生存と所有の走査から作る。命令の列には解放を書き出さない。大きさは地点ごとの生きている所有の変数の数の和である |
| 暗黙の後始末がエフェクトを起こしたり失敗したりする場合 | 起こらない。破棄処理は物体の解放だけで、ユーザー定義の破棄処理は置かない |
| 巻き戻しの途中の `prompt$` のフレーム | 着地しないフレームは、生きている所有の slot (evidence、`return` の節、外側の `evv`) を表で手放す。状態は evidence と一緒に解放される |
| `multi` の継続を再開した区間の中での中断 | 区間のフレームは普通のフレームなので、同じ表で片付ける |
| `yield_abort` と `never` の節の入口 | 入口は節の本体のクロージャを作るために残す。`yield_abort` は κ の引数をなくし、戻らない基本操作にする |
| 実行時エラーとの分担 | `never` の操作、IO の失敗、`exit` は巻き戻し。オーバーフロー、ゼロ除算、ヒープの誤り、止めたことは今と同じく評価全体の中断で、REPL は回復で後始末する。これを [VM](../../spec/vm.md) に書く |

## テスト

### S13c-1

## 私の判断で決めたこと

- S13c を S13c-1、S13c-2、S13c-3 に分け、この順に入れる
- 巻き戻しの間は安全点を置かない
- `RunStats` に `unwound_frames` を足し、`yields` は `yield_to` だけを数える
- under は、節の本体が呼び出し、`Effectful` の extern、`perform` を含むときだけ、EP が Core IR の形から決めて足す
- `never` の節の入口は残し、`yield_abort` から κ の引数を消す
- translate が置く暗黙の `drop` の順は変数の番号の順にする
- 1つの経路に戻らない呼び出しが複数あるときは、評価の順で最初のものの前にだけ `drop` を置く。「消費しない」は経路のどこでも消費しないことで、評価の順を区別しない
- 暗黙の後始末はラムダと節の本体の、捕まえた変数にも当てはめる
