# `,` のレイアウト規則の整理

位置づけ: 作業の設計。[レイアウト規則](../../spec/layout.md) の規則 4 のうち `,` に関わる部分を作り直す。作業を終えたら、決まったことを `docs/spec/` と `docs/implementation/` に移し、この文書を削除する。

## 目的

レイアウト段の `,` の規則を「`,` は閉じ括弧と同じく、一番内側の括弧より上のブロックをすべて閉じる」の1文にする。そのために、row の `<` `>` をレイアウト段の括弧として扱う。あわせて、行の先頭に書いた `,` を閉じ括弧と同じに扱い、Haskell と Elm の先頭カンマの書き方を通す。

今の規則には、次の4つの欠点がある。

- 改行の有無で読みが変わる。`(fn x -> x + 1, 2)` はタプルとして読めるが、`(fn x ->⏎    x + 1, 2)` はエラーになる
- 条件が多い。行末の `,` だけがブロックを閉じ、閉じるのは次の行の列 c 以下の基準列を持つブロックだけで、次の行の先頭が閉じ括弧のときとファイルの終わりでは列によらずすべて閉じる
- 正しいプログラムを生まない場合分けがある。次の行が一部のブロックより左で別のブロックより右にあるとき、残したブロックの中に `,` が入り、いつも構文エラーになる
- 先頭カンマの書き方 (`xs =⏎  [ 1⏎  , 2⏎  ]`) が、括弧が文の列から始まると通らない

規則の総量は減らない。`,` の条件はなくなるが、row の始まり、閉じ、打ち切りの規則と、行の先頭の閉じる側のトークンの規則が増える。今の `,` の条件は、レイアウト段に row が見えないことを補うためのものだった。この作業は、その原因の側 (row が見えないこと) を直す。

## 前提として確かめたこと

### 今の規則ができた経緯

`,` の規則は、S6c の4件のコミット (229c94f、831ca4f、66bc96e、703469e) で段階的に絞られた。4件とも、ブロックの中の row の `,` (`apply (fn () ->⏎  let g : Unit -> <IO, Log> Unit = …`) でラムダの本体を閉じないことが理由である。レイアウト段は `<` `>` を括弧として知らないので、`,` が括弧の要素の区切りか row の区切りかを区別できない。

### `,` を使う構文

| 構文 | 囲む括弧 |
|---|---|
| タプルの式、パターン、型 | `(` |
| リストの式とパターン | `[` |
| レコードの作る式、更新、パターン、フィールドの宣言 | `{` |
| 文脈 `(Eq a, Show a) =>` | `(` |
| `deriving (Eq, Show)` | `(` |
| import の並び | `(` |
| row `<IO, Log \| e>` | なし (`<` `>` は演算子のトークン) |
| fixity の宣言 `infixl 6 +, -` | なし |

fixity の宣言はトップレベルにしか書けないので、括弧の中のブロックの中に来ることはない。括弧の中のブロックの中に、レイアウト段が知っている括弧に囲まれずに `,` が来るのは row だけである。

### row の位置

grammar.md の文法では、row は `type ::= btype ('->' row? type)?` の `->` の直後にしか現れない。式の位置の `->` (ラムダ、match の枝、handler の節) の直後には、`<` で始まる演算子のトークンを書けない。前置の演算子は `-` だけで、演算子の参照とセクションは `(` で始まり、`<-` は予約記号 (`LEFT_ARROW`) だからである。したがって、`->` の直後の `<` で始まる演算子のトークンは、正しいプログラムではいつも row の始まりである。

### 今の規則での挙動

一時的なプローブで、レイアウト段の出力と `eml check` の診断を確かめた。

| 入力 | 今の結果 |
|---|---|
| `xs =⏎  [ 1⏎  , 2⏎  ]` | 規則 2 が `[` を打ち切り、`expected ']'` と `expected a statement` が2件連鎖する |
| `run⏎      [ fn x ->⏎          x + 1⏎      , fn y -> y⏎      ]` (`[` が文の列より深い) | 通る |
| `(fn x ->⏎      x + 1, 2)` | `unexpected ','` |
| `apply (fn y ->⏎        y) x, 2)` (ラムダの中) | `unexpected ','` |
| `[fn x ->⏎    x + 1,]` | `unexpected ','` (改行して `]` を書けば通る) |
| `[ fn x ->⏎    x + 1,⏎             fn y -> y ]` | 次の要素が継続行になり、`unexpected ','` |
| `(fn x ->⏎      let y =⏎        1,⏎       y)` | 内側のブロックだけ閉じ、`unexpected ','` |
| `(fn x ->⏎    , 2)` | `,` の列でブロックを開き、`expected a statement` (閉じ括弧なら E0009) |
| `( fn x ->⏎      x + 1⏎      )` | `x + 1 <SEP> <CLOSE> )`。parser は受け流す |

括弧の中の `match`、`handle`、`if`、`let … in`、`,` だけの行、補間の穴の中の `,`、更新の中のラムダは、意図どおりに動いた。

## 決定

### row をレイアウト段の括弧にする

レイアウト段の文脈 `Bracket` に、row の種類を足す。row の `Bracket` は、ほかの括弧のトークンや開始トークンで打ち切られる、弱い括弧である。

- **始まり**: `->` (`THIN_ARROW`) の直後のトークンが `<` で始まる演算子のトークン (`OP`) なら、row の始まりである。`<>` で始まるトークンは空の row なので、`Bracket` を積まない。それ以外は row の `Bracket` を積む。`->` が行末にあり、`<` が次の行の先頭にあるときも同じである (規則 3 の `OPEN` を入れた後に積む)
- **閉じ**: スタックの一番上が row の `Bracket` のとき、`>` で始まる演算子のトークンは row を閉じ、その `Bracket` を取り除く。正しい row の閉じは `>` だけである。`>>` や `>=` のように後ろに演算子の文字が続くトークンは、誤りの回復のときにだけ現れる
- **打ち切り**: スタックの一番上が row の `Bracket` のときに、開始トークン (`=`、`->`、`with`、`then`、`else`、`where`)、`;`、閉じ括弧 (`)`、`]`、`}`)、`INTERP_END` が来たら、まず row の `Bracket` を取り除き、それからそのトークンに規則を当てる。閉じていない row (`<IO Int = …`) が、後ろの式の `,` や `>` を row のものとして読まないためである
- **改行**: row の中の改行は、ほかの括弧と同じく規則 2 に従う。row の続きの行は、囲んでいるブロックより深く書く。今の `<IO,⏎      Log>` (`tests/ui/run/basics/effect_row_across_lines_in_a_block.em`) は、そのまま通る

打ち切るトークンは、row の中身の文法から決めず、row の中にも row に続く型にも直接は現れないトークンから選ぶ。row の中身を許すトークンの集合で決めると、レイアウト段が型の文法に縛られ、row の構文を広げるたびにレイアウト段を直すことになるためである。ロードマップには `<IO, Async@lin>` (「型システム」の row 要素ごとの捕捉 Kind) の案がある。`@` は演算子の文字なので、中身の集合で決める形では `@` で row が打ち切られ、後ろの `,` がブロックを閉じてしまう。打ち切るトークンで決める形なら、この案も変えずに通る。

開始トークンは row を打ち切る。そのため、行末の開始トークンで開くブロックが row の `Bracket` の真上に積まれることはない。row の `Bracket` の真上に来るのは、effect の引数の括弧 (`<State (Int, Int)>`) だけである。

閉じ括弧も row を打ち切るので、`)` が閉じる「一番内側の `Bracket`」は、いつも `(` `[` `{` のどれかになる。parser の括弧の数え方 (`grammar/scan.rs` の `Nesting`) と `close_bracket` は `(` `[` `{` だけを見ており、この解釈と食い違わない。

レイアウト段は row を認識するだけで、トークンを書き換えない。`<` を `L_ANGLE` に、`>` を `R_ANGLE` に読み替えるのは、今までどおり parser である。レイアウト段は仮想トークンを挿入するだけ、という今の分担を保つためである。

### 字句: `-><` を分ける

lexer は、演算子の並びが `-><` で始まるときに、先頭の `->` を `THIN_ARROW` の1つのトークンにし、残りを改めて演算子のトークンにする。最長一致の例外である。`Int -><IO> Int` は `->`、`<`、`IO`、`>` になり、`Int -><> Int` は `->`、`<>` になる。`-><-` は `->`、`<-` になる。`--><` は、`--` の後ろに演算子の文字が続くので1つの演算子 (lexical.md の「空白とコメント」) であり、`-><` で始まらないので分けない。

今は parser の `eat_arrow` が、型の位置で `-><` を分けている。lexer で分ければ、レイアウト段は「`THIN_ARROW` の直後の `<` で始まる `OP`」だけを見ればよく、`eat_arrow` の分割も不要になる。

代わりに、ユーザーは `-><` で始まる演算子を定義できなくなる。`infixl 5 -><` は演算子の代わりに `->` を見つけて E0011 (`expected an operator`) になる。`(-><) : …` と `a ->< b = a` は、項目の始まりとして読めず E0003 になる。標準ライブラリとテストに、`-><` で始まる演算子を定義したり使ったりする箇所はない (`Int -><IO> Int` のように、矢印と row を続けて書く箇所はある)。

### `,` の規則

> `,` は、一番内側の `Bracket` より上にあるすべての `Block` を `CLOSE` で閉じる。その `Bracket` は残す。`Bracket` がなければ何もしない。

`,` が行末にあるかどうか、次の行の列、次の行が閉じ括弧かどうか、ファイルの終わりかどうかは見ない。補間の穴の中では、今と同じく一番内側の `Interp` より上だけを見る。

row の中の `,` では一番内側の `Bracket` が row なので、その上に `Block` はなく、何も閉じない。

この規則で、括弧の要素の区切りは、改行を除いて1行に書いたときと同じになる。`(fn x ->⏎    x + 1, 2)` は `(fn x -> x + 1, 2)` と同じく、ラムダと `2` のタプルである。Haskell の parse-error(t) の規則と同じ結果になる。

一方で、`,` がブロックを閉じた後の行は、閉じたブロックの列とは関係なくなる。`(fn x ->⏎    a, b⏎    c)` は、トークンの並びとしては `(fn x -> a, b c)` になる。括弧の中では改行が意味を持たない、という今の規則どおりの結果である。

### 行の途中の `,` の後の行 (E0015)

上の読み方のままでは、ブロックの中にうっかり書いた `,` が、気づきにくい誤りになる。次の例では、`,` がラムダの本体を閉じ、続く行は `2` の継続行になる。今は `,` を指す構文エラーが出るが、規則を変えた後は構文エラーがなく、型の誤りと名前の誤りが離れた位置に出る (プローブで確かめた)。

```haskell
main () =
  handle (fn () ->
    let x = ask (), 2
    println "a"
    println (show x)) with
    | ask () k -> k 1
    | return v -> v
```

そこで、レイアウト段は次の場合を E0015 にする。

> 行の途中の `,` (同じ行に後ろのトークンがあるもの) が1つ以上の `Block` を閉じたとき、次の行の先頭のトークンが閉じる側のトークンでなく、規則 3 でブロックを開かず、そのときのスタックの一番上がその `,` の一番内側の `Bracket` のままで、列がその `,` の閉じたブロックのどれかの基準列と等しければ、誤りにする。

- 主のラベルはその `,` に置き、「この `,` が `->` (ブロックを開いた開始トークン) のブロックを閉じた」と示す。ブロックを開いた開始トークンと次の行の先頭に、それぞれ「ブロックはここから始まる」「この行はそのブロックの列にある」という副のラベルを置く。help は「ブロックの中にタプルを書くなら括弧で囲む」とする
- 仮想トークンの並びは変えない。誤りを報告するだけで、回復は上の読み方のまま進める
- 行末の `,` には当てない。行末の `,` の次の行を閉じたブロックの列から書くのは、次の要素を書く正しい形 (`g (fn x ->⏎      a,⏎      b)`) だからである。行の途中の `,` の後で、閉じたブロックの列から次の要素を書く正しい形はない
- 列が等しいときだけにする。閉じたブロックより深い行 (`(fn x ->⏎    a, g⏎      b)`) は継続行として読む
- 1行に、ブロックを閉じる `,` が2つ以上あることはない。最初の `,` が一番内側の `Bracket` より上のブロックをすべて閉じるためである

E0015 の名前は `BLOCK_CLOSED_BY_COMMA` とし、`docs/spec/diagnostics.md` の番号の表に足す。

### 行の先頭の閉じる側のトークン

「閉じる側のトークン」を、閉じ括弧 `)` `]` `}`、row を閉じる `>`、`,` とする。`>` が閉じる側のトークンになるのは、そのトークンを扱う前のスタックの一番上が row の `Bracket` のときだけである。

行の先頭のトークンが閉じる側のトークンで、スタックに `Bracket` があるときは、規則 1 と規則 2 を当てない。そのトークンの規則 (規則 4) が、一番内側の `Bracket` より上の `Block` を閉じる。行の先頭の `,` で文を始めることはないので、`SEP` を入れる理由も、括弧を打ち切る理由もない。行の先頭が補間の穴の中になることはない (規則 7) ので、ここでは `Interp` を考えなくてよい。

```haskell
xs =
  [ fn x ->
      x + 1
  , fn y -> y
  ]
```

この例では、`, fn y -> y` の行の `,` が `->` のブロックを閉じ、`[` は残る。今は規則 2 が `[` を打ち切っていた。

row の中の `|` は閉じる側のトークンにしない。row を行に分けて書くときは、`,` と `>` の行も含めて、続きの行を囲んでいるブロックより深く書けば足りるためである。`,` と `>` を行の先頭に書けるのは、括弧の規則をそろえた結果である。

閉じる側のトークンは、今の閉じ括弧と同じく、囲んでいるブロックより左の列にも書ける。そのため、行の先頭の `,` も、列 0 を含めてどの列にも書ける。要素の行は、今までどおり規則 2 に従う。閉じる側のトークンの行は、深いブロックの文の続きにもなれる。たとえば `  let g : Unit -> <IO⏎> Unit = …` の列 0 の `>` は、`let` の文の続きとして row を閉じる。

規則 3 でも、閉じる側のトークンは閉じ括弧と同じに扱う。行末の開始トークンの次の行の先頭が閉じる側のトークンで、スタックに `Bracket` があるなら、ブロックを開かずに E0009 にする。規則 1 と規則 2 を当てない条件と同じく、`Bracket` があることを条件にする。`Bracket` がないとき (`f =⏎  , 1`) は、今までどおりその行でブロックを開き、parser が `,` を1件の構文エラーにする。今の実装は閉じ括弧を `Bracket` の有無によらずこう扱っているが、仕様の規則 3 には書いていないので、あわせて書く。開始トークンは row を打ち切るので、規則 3 の時点でスタックの一番上が row になることはない。規則 3 で実際に当たるのは `)` `]` `}` `,` である。

この E0009 には help を付けず、ラベルを「次の行の `,` (閉じ括弧) の前に、ブロックの中身がない」という文言に変える。今のラベル (「次の行は囲んでいるブロックより深く字下げする」) と `->` の help (「次の行をもっと深く字下げする」) は、次の行が閉じる側のトークンのときには当てはまらないためである。次の行は十分に深いことがあり、深くしても直らない。

`Bracket` がないとき (トップレベルの fixity の宣言の続きの行など) は、行の先頭の `,` も今までどおり規則 1 に従う。

閉じ括弧について規則 1 を当てなくなるので、`( fn x ->⏎      x + 1⏎      )` の `SEP` はなくなる。parser はこの `SEP` を受け流していたので、木と診断は変わらない。

### 処理の順

レイアウト段は、トークンごとに次の順で規則を当てる。

1. 行の先頭のトークンなら
   1. 前のトークンが行末の開始トークンなら、規則 3 を当てる。トークンが閉じる側のトークンでスタックに `Bracket` があるとき、または列が囲んでいるブロックより深くないときは、E0009 の空のブロックを入れる。そうでなければ `OPEN` を入れて `Block` を積む
   2. 規則 3 でブロックを開かなかったとき、トークンが閉じる側のトークンでスタックに `Bracket` があれば、何もしない。そうでなければ規則 1 と規則 2 を当てる
2. スタックの一番上が row の `Bracket` なら、トークンが `>` で始まる `OP` のとき row を閉じて、このトークンの処理を終える。打ち切るトークンのときは row の `Bracket` を取り除き、3 に進む
3. 1 で規則 1 と規則 2 を当てた行の先頭のトークンなら、E0015 を判定する
4. トークンの種類ごとの規則を当てる。開き括弧と row の始まりは `Bracket` を積み、`,` と閉じ括弧は規則 4 で `Block` を閉じ、`INTERP_START` と `INTERP_END` は穴の規則に従う

行の先頭で E0015 を判定するのは、規則 3 でブロックを開かず、閉じる側のトークンでもない場合だけである。閉じる側のトークンかどうか (`>` が row を閉じるかどうか) は、1 の時点のスタックで決める。2 で row を閉じるかどうかの判定と同じスタックである。

### `{` の中の `=`

規則 3 の例外 (スタックの一番上が `{` の `Bracket` のとき、行末の `=` はブロックを開かない) は変えない。row は `=` で打ち切られるので、この判定に row が割り込むことはない。

### 採らないもの

- **parser から閉じる**: Haskell の parse-error(t) のように、parser が読めない `,` でブロックを閉じる形は採らない。レイアウト段を parser から独立した純粋な段に保つためである
- **`,` の今の条件を残して直す**: 同じ行の閉じ括弧の前の `,` で閉じる、診断に help を足す、などの小さな修正で済ませる形は採らない。原因の row が見えないままなので、行の途中の `,` と次の要素の列の問題が残り、条件がさらに増えるためである
- **row の中身を許すトークンの集合で打ち切る**: 上の「row をレイアウト段の括弧にする」のとおり、レイアウト段が型の文法に縛られるので採らない
- **`-><` を書けなくする**: `-><` を最長一致のまま1つの演算子にし、矢印と row の間に空白を求める形も考えた。lexer に例外がいらず、`-><` で始まる演算子も定義できる。採らないのは、今書ける `Int -><IO> Int` が、`-><` という演算子の誤りとして読まれ、分かりにくいエラーになるためである。分かりやすくするには、その場合だけの help が要る
- **`-><` を1つの演算子のまま row の始まりにも数える**: lexer に例外を置かず、レイアウト段が `-><` で始まる `OP` も row の始まりとみなす形も考えた。`-><` で始まる演算子の名前も残せる。採らないのは、ユーザーが `-><` という演算子を定義したとき、式の中の `a -><  b, c` でもレイアウト段が row を始めてしまい、後ろの `,` がブロックを閉じなくなるためである。row の始まりを `THIN_ARROW` の直後に限るには、`->` が独立したトークンでなければならない
- **`,` の後の行を一律に誤りにしない**: E0015 を設けず、`(fn x ->⏎    a, b⏎    c)` を `b c` と読むだけにする形も考えた。規則は1つ減るが、上の `handle` の例のように、ブロックの中の誤った `,` が離れた位置の型の誤りになるので採らない
- **lexer が row の括弧のトークンを出す**: lexer が `->` の直後の `<` を `L_ANGLE` として出し、row の中の `>` を `R_ANGLE` として出せば、レイアウト段は `<` `>` をほかの括弧と同じトークンとして扱える。採らないのは、row の括弧が弱い括弧で、ほかの括弧と同じには扱えないためである。`)` は row を閉じずに打ち切り、開始トークンも row を打ち切る。そのため、row を `is_opening_bracket` に加えることはできず、レイアウト段と parser の `Nesting` に row だけの扱いが残る。そのうえで lexer に打ち切りの規則を置くと、row の認識が lexer、レイアウト段、parser の3か所に分かれる
- **レイアウト段で `<` `>` を書き換える**: レイアウト段が row の `<` `>` を `L_ANGLE` と `R_ANGLE` のトークンに分けて渡せば、parser の `eat_angle` の分割は要らなくなる。採らないのは、レイアウト段が実際のトークンを書き換えるようになり、「仮想トークンを挿入するだけ」という分担が崩れるためである
- **行の先頭の `|`**: 更新の `|` を文の列に書く形 (`{ p⏎  | age = 1 }` の `|` を `{ p` と同じ列に置く) は、今までどおり規則 2 のエラーにする。Elm の書き方でも `|` は `{` より深く書くので、困る場面が少ない

## 実装

- `layout.rs`
  - `Context::Bracket { brace: bool }` を、括弧の種類 `BracketKind { Brace, Row, Other }` を持つ形にする。`is_field_eq` は `Brace` を見る。`(` と `[` を区別する規則はないので、`Other` にまとめる
  - 上の「処理の順」のとおりに、行の先頭の処理、row の閉じと打ち切り、トークンの種類ごとの処理を並べる
  - row の始まりは、`items[i - 1]` が `THIN_ARROW` で、今のトークンが `<` で始まる `OP` のとき。`<>` で始まるときは積まない
  - `COMMA` の分岐から `closes` の先読みを除き、閉じ括弧の分岐と同じく一番内側の `Bracket` より上の `Block` をすべて閉じる (`Bracket` は残す)
  - `missing_block` は、次の行の先頭が閉じる側のトークンなら help を付けず、ラベルを変える
  - 行の途中の `,` が `Block` を閉じたら、その `,` の位置、閉じたブロックの基準列と開始トークン、そのときの一番内側の `Bracket` のスタックの深さを覚えておき、次の行の先頭で E0015 を判定する。行の先頭を1つ過ぎたら忘れる
- `lib.rs` の `codes`: `BLOCK_CLOSED_BY_COMMA` (E0015) を足す
- `lexer/mod.rs`: 演算子の並びが `-><` で始まるとき、`->` と残りの2つのトークンを出す
- `grammar/types.rs`: `eat_arrow` の `-><` の分割をなくし、`p.eat(THIN_ARROW)` にする
- `parser.rs`: 呼び出し元がなくなる `split_prefix` を `split_first_char` にまとめる

## 今後の構文への制約

- row の中に `<` `>` を使う構文を足すときは、`>` が row を閉じないように括弧の中に置くか、レイアウト段の row の規則を改める。今は `docs/future/multicore.md` の Kind の表記 (`Type<Unr>`、`Row<Never>`) が、`<Heap (h : Type<Unr>), IO>` のように括弧の中にあるので問題にならない。括弧なしで row の中に書く構文にすると、その `>` が row を閉じ、後ろの `,` がブロックを閉じる
- row の始まりは `THIN_ARROW` の直後に限る。関数型の矢印に別の形 (`types.md` の内部表現 `-[m]->` を表面の構文にする場合など) を足すときは、その矢印の直後も row の始まりに数える
