# S14c `Array`、`MutArray` と局所的な可変変数の設計

## 目的と範囲

S14c の設計である。出発点は [ロードマップ](../../future/roadmap.md) の「S14 数値計算の整備」の `Array` と `MutArray` の項目と、S14 の設計 (`docs/superpowers/specs/2026-10-19-s14-numeric-design.md`) の S14c の行で、2026-10-20 の議論で範囲を広げた。S14 の設計のほかの節 (作業の分け方、S14a の `Panic`) は、そのまま S14c にも当てはまる。

S14c の目的は、S14d の計測 (エラトステネスのふるい、fannkuch-redux、spectral-norm など) を、読みやすい direct style で書けるようにすることである。ロードマップは `MutArray` を線形に受け渡す API (`write : MutArray a -> Int -> a -> MutArray a`) で使う形を考えていたが、その形ではループのたびに配列を引数と返り値で回すことになり、読みにくい。そこで、`MutArray` の上に、エフェクトで作る局所的な可変変数 `var` を入れる。`var` を使うループが、線形に受け渡す版と同じ速さで動くように、handler への特殊化も広げる。

目指す書き方は次のとおりである。

```
sieve : Int -> <Panic> Array Bool
sieve n =
  var marks = MutArray.make n True
  for 2 n (fn i ->
    if marks[i] then
      var j = i * i
      while (fn () -> j < n) (fn () ->
        marks[j] := False
        j := j + i))
  freeze marks
```

## 2026-10-20 に決めたこと

ユーザーが決めたことは次のとおりである。

- 配列の書き換えは、エフェクトを使った direct style で書けるようにする
- 局所的な可変変数 `var` を入れる。変数ごとに新しいエフェクトを作り、その handler が値を状態として持つ。同じ型の変数が何本あっても、内側の handler が外側を隠さない
- 末尾でない `perform` への handler の特殊化を S14c に含め、`var` を使うループを、線形に受け渡す版と同じ速さにする
- 変数の値がスタック (VM のフレームのスロット、ネイティブ化の後のレジスタ) に載ることは、最適化の普通の結果とし、言語として保証しない。特殊化が効かない形では、今と同じく状態を evidence (ヒープ) に置いて動かす
- 特殊化した関数は、結果と状態の組を返す。組の確保は S14e (小さな単一コンストラクタの型の構造体の表現) で消す。作業の順は S14c、S14d、S14e のままにし、組の確保の分も S14d と S14e の差として記録する

議論の中で私が案を出し、ユーザーが「よい」と答えたことは次のとおりである。

- `MutArray.make n x` と `MutArray.tabulate n f` で作り、`freeze` で `Array` にする。`Array` から戻す `thaw` は、一意ならそのまま渡し、共有されていれば写す
- `Array` は意味が不変で、`Array.set` は RC が 1 ならその場で書き換え、そうでなければ写す。ほかに `from_list`、`to_list`、`length` を置く
- 範囲外の添字は `Panic` にする。`Option` を返す版は入れない
- `Lin` の要素を持つ配列は S14c の範囲外にする。`MutArray` は extern が作る物体なので、`File` と同じく作るときに `lin` ビットを立てる。`poly` の物体の `lin` ビットの実行時の伝播は、マルチコア対応に残す
- `x[i]` は、名前の直後に空白なしで `[` が続くときだけ添字と読む。`f [i]` は今までどおりリストを渡す関数適用である。`Array` の読み出しにも `a[i]` を使える
- `:=` は予約記号にし、`var` は新しいキーワードにする
- `Lin` の変数の名前だけを書くと、値を取り出して変数を終える。`Unr` の変数では、ただ値を読む
- `for` と `while` は Prelude に置く
- S14c を3つの作業に分ける (下の「作業の分け方」)

## 目標、目標にしないこと、避けること

### 目標

- `Array` と `MutArray` が動き、範囲外の添字が `Panic` になる
- `var` で、スカラーと `MutArray` の変数を direct style で書き換えられる。配列を何本同時に使っても、書き方は変わらない
- `for` と `while` と局所関数で書いた `var` のループが、線形に受け渡す版と同じ仕事の回数 (`RunStats`) で動く。evidence を引かず、確保は線形に受け渡す版と同じである。ただし、S14e の前は、経路の関数の末尾でない呼び出しから2つ以上の値 (結果と状態、または2つ以上の状態) が戻る所で、タプルの確保が残る (下の S14c-3 の「速さの見込みと残る差」)
- 特殊化の拡張は `var` に限らない。すべての節がすぐに再開する handler (`Std.State` など) なら、末尾でない `perform` を含むループも同じく特殊化される

### 目標にしないこと

- `Lin` の要素を持つ配列の API (要素を取り替える `replace` など)
- `Float` の要素を箱に入れずに持つ配列。要素は一様な語で持ち、`Float` の要素は箱に入る (下の「表現」)
- `MutArray` の分割と結合 (マルチコア対応)
- 配列のリテラルの構文 (`Array.from_list [1, 2, 3]` で書く)
- `var` をトップレベルや REPL の入力に書くこと。`var` はブロックの中の文である
- 末尾でない再帰の生産者の継続についての特殊化 (ロードマップの「再帰する生産者の継続についての特殊化」)。S14c が広げるのは、すべての節がすぐに再開する handler だけである

### 避けること

- `var` の変数を使う閉包が、変数の範囲の外で別の変数の handler に捕まること。再帰で同じ `var` の地点に入り直すと、静的な地点ごとのエフェクトでは起こりうる (下の「範囲の外へ出る閉包」)
- 範囲外の添字の `Panic` が、`x[i]` を書いた所の `try_panic` に届かないこと。`x[i]` の `Panic` は、書いた所の row に現れ、その場所から最も近い `try_panic` に届く
- 特殊化した版と EP の版で、意味 (結果、`Panic` の届く先、後始末) が変わること
- 線形に受け渡す今のプログラムの実行の仕事の回数が変わること (S14c-2 で `bench/` の期待値が変わるときは、下の「テストの変更」で扱う)

## 作業の分け方と完了の条件

| 作業 | 中身 | 完了の条件 |
|---|---|---|
| S14c-1 | `Array` と `MutArray` の核 | 下の「`Array` と `MutArray`」が動き、範囲外の添字が `try_panic` で捕まる。`MutArray` を線形に受け渡して書いたふるいが、検査モードで漏れなく動く |
| S14c-2 | すぐに再開する節だけの handler の、状態を渡す形の特殊化 | `Std.State` を末尾でない `put` で使うループが特殊化され、`evidence_steps` が 0 になる。手で状態を渡す形に書いた版と、確保、`box`、`unbox`、RC の回数が一致する |
| S14c-3 | `var`、`:=`、添字の構文、`for`、`while` | 上のふるいと、配列を3本使う fannkuch-redux の小さな版が `var` で書けて動く。どちらも `evidence_steps` が 0 で、`MutArray` を線形に受け渡して素直に手で書いた版と、確保の回数が一致する。S14e まで残る確保 (経路の関数の末尾でない呼び出しから2つ以上の値が戻る所のタプルと、その中の `Float` の箱。下の「速さの見込みと残る差」) が入るなら、その分を数えて差として記録する |

## S14c-1 `Array` と `MutArray`

### 型

- `Array a` と `MutArray a` は extern の型である。今の extern の型は型引数を持てない (E0011) ので、`extern data` に型引数を許す。extern のエフェクトに型引数を許さない理由 (row の中で重なったラベルを1つにまとめる規則) は、型には当てはまらない
- `Array a` の Kind は要素の Kind に従う。`MutArray a` の Kind はいつも `Lin` である。どちらも型引数について共変である
- extern の関数の引数に型変数を許す。今は、戻らない extern (`panic`、`exit`) の結果のほかに型変数を書けず、`crates/eml_core_ir/tests/externs.rs` がそれを確かめている。型変数の位置の Repr は `tobj` である
- extern の関数のシグネチャの型変数は `Unr` に固定する (私の判断。操作の引数の型変数を `Unr` に固定する規則と同じ考えで、本体のない宣言の使い方を Kind に推論できないためである)。そのため、`Lin` の要素の配列には、どの関数も使えない
- 型は Prelude に置く。添字の構文が `LangItems` から型と読み出しの関数を名指すためである。利用者向けの関数は `Std.Array` と `Std.MutArray` のモジュールに置き、`Array.length a` のように修飾して使う (私の判断。`Std.Float` と同じく、Prelude の名前を増やさない)

### API

`Std.Array` の関数は次のとおりである。

| 名前 | 型 | 意味 |
|---|---|---|
| `make` | `Int -> a -> <Panic> Array a` | 長さ n で、どの要素も x。n が負なら `Panic` |
| `tabulate` | `Int -> (Int -> <e> a) -> <Panic \| e> Array a` | i 番目を `f i` にする。添字の順に呼ぶ |
| `from_list` / `to_list` | `List a -> Array a` / `Array a -> List a` | リストとの変換 |
| `length` | `Array a -> Int` | 長さ |
| `get` | `Array a -> Int -> <Panic> a` | 読み出し。`a[i]` も同じ |
| `set` | `Array a -> Int -> a -> <Panic> Array a` | 1つを替えた配列。RC が 1 ならその場で書き換え、そうでなければ写す |
| `thaw` | `Array a -> MutArray a` | 一意ならそのまま、共有されていれば写して `MutArray` にする |

`Std.MutArray` の関数は次のとおりである。

| 名前 | 型 | 意味 |
|---|---|---|
| `make` | `Int -> a -> <Panic> MutArray a` | `Array.make` と同じ |
| `tabulate` | `Int -> (Int -> <e> a) -> <Panic \| e> MutArray a` | `Array.tabulate` と同じ |
| `length` | `MutArray a -> (Int, MutArray a)` | 長さ |
| `read` | `MutArray a -> Int -> <Panic> (a, MutArray a)` | 読み出し |
| `write` | `MutArray a -> Int -> a -> <Panic> MutArray a` | その場で書き換える |
| `freeze` | `MutArray a -> Array a` | `Array` にする。写さない |

- `read` と `length` は、配列を返すための組を確保しない (私の判断。数値計算の内側のループで、読み出しのたびに確保が起きないようにするためである)。extern は引数を消費するので、`read` を「組を作る extern」にすると、読み出しのたびに組を確保する。そこで、配列を借りて要素を読む命令と、その結果と配列を `con` で組にする形に translate で開く。組を受け取ってすぐ開く所 (`let (v, m) = MutArray.read m i` や、下の `var` の脱糖) では、融合の既知のコンストラクタで組が消える。借りて読む命令を、extern の行に借用の印を足して作るか、primitive にするかは計画で決める
- 範囲外の添字の `Panic` の文言は、`String` の位置の誤り (`IndexFault`) にならい、添字と長さを含める。文言は計画で決める
- `Panic` を起こす関数を `Panics` の行にし、`try_panic` で捕まえられるようにする。`length`、`freeze`、`thaw`、`from_list`、`to_list` は `Pure` である
- `var` の添字の脱糖 (下の S14c-3) は、`Panic` を起こさずに範囲外を知らせる読み書きを使う。たとえば、範囲内なら値、範囲外なら長さを返す関数である。これは Prelude の中だけの関数にする

### 表現

- `Array` と `MutArray` は同じ物体である。要素を走査する語として並べ、`Data` と同じ形 (255 語以上は拡張した数の語) を使う。要素の位置は一様な位置で、Repr は `tobj` である。`Int` は即値、`Float` は箱になる (私の判断。箱を持たない `Float` の配列は、型から決める呼び出しの規約と一緒に後で考える。Python のリストも `float` を箱で持つので、S14d の比べ方としては対等である)
- `MutArray` の物体は、作るときに `lin` ビットを立てる。`freeze` は一意な物体のビットをその場で下ろし、`thaw` は一意ならその場で立て、共有されていれば写した物体に立てる。`lin` ビットの立った物体を `dup` すると、検査モードが今までどおり `LinDup` で断る
- `Array.set` と `thaw` の写しは、要素を1つずつ `dup` して新しい物体に並べる
- `Data` の種類のまま使うか、同じ形の新しい種類を足すかは、計画で決める。新しい種類にすると、検査モードが `switch` や `unpack` での取り違えを `WrongKind` で断れるが、Verus の不変条件と回復の表に行が増える。どちらでも token にはしない ([オブジェクトモデル](../../spec/object-model.md) の「種類」の、`Array` は別の種類が要るという見通しを、この決定で書き直す)
- 回復は、`lin` ビットのない配列を `Data` と同じく写す。`MutArray` は `lin` ビットを持つので、今の規則どおり `Unrecoverable` になる
- 写しも書き換えも語の単位なので、信頼の一覧に行を足さずに Verus で確かめられる見込みである。長さの桁あふれは、今の `too_large` (T5) を使う

### 実行系

- VM は、`get`、`set`、`read`、`write`、`length` を専用の命令にする (私の判断。数値計算の内側のループで、`Op::Extern` の振り分けを通らないようにする)。誤りの道は、`Int` の算術と同じく `step_failed` から `Panic` に届ける
- そのほかの関数は `Op::Extern` にする
- `eml_extern` の行は、`tobj` の引数と結果、`Array` と `MutArray` の型の行 (型引数と Kind の規則) を持てるようにする

## S14c-2 状態を渡す形の特殊化

### 今の制限

S13e-2 の handler への特殊化 ([Core IR](../../spec/core-ir.md) の「handler への特殊化」) は、handle の本体から末尾の位置の直接の呼び出しでたどれる関数だけを経路にする。末尾でない `yields` の関数の直接の呼び出しが経路にあると、handle を EP の道に残す。そのため、次のようなループは特殊化されない。

```
loop i =
  if i < n then
    bump i          -- bump が perform する。末尾でない
    loop (i + 1)
  else ()
```

2026-10-20 の試作では、`Lin` の状態を持つ `State` に似たエフェクトで1000万回の更新をした。線形に受け渡す版は 0.21 秒 (命令数 74 億)、エフェクトの版は 1.12 秒 (命令数 286 億) だった。EP の道では、`perform` のたびに `ev_lookup`、節の呼び出し、状態の箱の出し入れ、yield の確認がかかる。

### 状態を渡す形

効果の操作がどれも再開する操作で、どの節も「すぐに再開する節」(Core IR の「handler の節の形」) である handler H を、新しい形で特殊化する。

- 経路は、handle の本体から、`yields` の関数の直接の呼び出しを、末尾の位置かどうかによらずたどって届く関数である
- 経路の関数 f の複製 `f{H}` は、f の引数に、節と `return` の節の捕獲と、状態つきなら状態を足して受ける。結果は、状態つきなら f の結果と次の状態の組、状態のない handler なら f の結果である。ただし、状態つきで f の結果の Repr が `unit` なら、次の状態だけを返す (私の判断。`for` の本体のような `Unit` を返す関数が、呼ばれるたびに組を確保しないためである)。`return` の節は複製の中で呼ばない
- handle の地点では、本体の複製を呼んで組を開き、`return` の節を結果と状態で呼ぶ
- 経路の関数への呼び出しは、末尾なら複製の末尾呼び出しにし、末尾でなければ複製を呼んで組を開き、次の状態で続ける
- H 宛ての `perform` には節の本体を展開する。末尾の `resume k(v, s)` は、`perform` の後ろの続きへのジャンプにし、v と s をブロックの引数で渡す。継続の関数 (`$hN`) と合流のブロックの関数 (`$hjJ`) は作らない。ブロックは前向きの辺だけで並べられ、コードは `perform` の数に比例して育つ
- 経路の関数に、`mask` の付いた呼び出し、入れ子の `handle`、`resume`、`yields` の `apply` があれば、今と同じく特殊化しない。入れ子の `handle` を断るのは、`try_panic` のような handler が経路の上に挟まると、展開した節の中の中断の届く先が EP の道と変わるためである
- 入れ子の handler は内側から特殊化する (私の判断)。`var` はどれも handle なので、ふるいでは `marks` の経路の上に `var j` の handle があり、fannkuch では3つの handle が重なる。内側の handle を先に特殊化すると、その handle は複製の呼び出しに変わって消えるので、外側の handler の経路は、内側が作った複製を通ってたどれるようになる。外側の handler は、内側の複製の複製 (`f{H1}{H2}` のように名前を重ねる) を作る。そこで、handlers の段を、経路にまだ特殊化していない handle を含まない handle から順に処理し、変わる handle がなくなるまで繰り返す。各回の複製は、その時点のコードから作るので、名前で中身が決まる規則は保たれる。特殊化しない handle (`try_panic` のような `never` の操作だけのエフェクトの handle を含む) が経路に残る外側の handler は、今と同じく特殊化しない。この段の作業は S14c-2 に含め、`Std.State` を2つ重ねたテストで確かめる
- 経路の関数がほかのエフェクトで yield するのは構わない。その関数の複製は `yields` のまま残り、状態はふつうの変数として EP の継続に捕まる
- 操作に `never` の操作を含む handler と、「それ以外の節」を持つ handler は、今の末尾の経路の形のまま扱う
- すぐに再開する節だけの handler は、経路がすべて末尾呼び出しでも新しい形にする (私の判断。同じ handler に2つの形を持たないためである。状態つきの handler では、handle の実行ごとに組を1つ確保するようになる)
- 複製の名前と、Core IR のテキストでの書き方は計画で決める。鍵に `return` の節の関数を含め、名前で中身が決まる今の規則を保つ

### 速さの見込み

- `for` と `while` は Prelude の高階関数なので、S13e-1 の既知の閉包の写しで本体の閉包が直接の呼び出しになり、経路に入る
- 組を確保するのは、経路の関数が末尾でない呼び出しから戻る所だけである。末尾再帰で回るループでは、ループの終わりに1回だけ確保する。S14e で組が構造体になれば、この確保も消える

## S14c-3 `var`、`:=`、添字、`for`、`while`

2026-10-20 の S14c-3 の議論で、脱糖を、変数の型に基づいて translate が行う形に改めた。改める前の脱糖 (操作 `modify : (once s -> (a, s)) -> a` の1つで書く形) には、次の3つの問題があったためである。

- `modify` の `a` は操作の引数の型に現れるので、`Unr` に固定される ([エフェクトと handler](../../spec/effects.md) の「handler の意味」)。`MutArray` を返す取り出しは E3001 になる
- 節と `return` の節の中身が、変数の Kind で変わる。`Unr` の変数は状態を複製して読み、`return` で捨てる。`MutArray` の変数は状態を捨てられないので `drop` が要る。HIR は型を知らないので、どちらの Kind でも型の通る脱糖を1つに決められない
- 節が `MutArray.read` を呼ぶと、節の型に `<Panic>` が要る。変数を `try_panic` の中だけで使うと、handle の外側の row に `Panic` がないので、合成したコードで E2002 になる

ユーザーは、配列の変数を構文で区別して HIR で脱糖する案ではなく、構文を変えないこの形を選んだ。その後、同じ日の敵対的なレビューで見つかった問題を直した。主なものは、節の中の `Panic` が変数の状態を失わせること、範囲の外へ出る閉包の検査の漏れ、入れ子の handler の特殊化で組の確保が増えることである。直した後の形を、この節に書く。

### 構文

- `var` はキーワード、`:=` は予約記号になる。`:=` は今、`:` で始まるコンストラクタの演算子として字句に切られる。`:=` で始まる演算子の並びは、`-><` と同じく `:=` と残りに分けて切る (`x :=-1` は `x := -1`)。そのため、`:=` で始まるコンストラクタの演算子は宣言できなくなる
- 今 `var` を名前に使っているのは `std/Env.em` の非公開の extern だけなので、`lookup` に改名する。extern の行の名前も `Std.Env.var` から `Std.Env.lookup` に変わる
- `var x = e` と `var x : T = e` は、ブロックの文である。`var` の後には名前を1つだけ書く。パターン (`var (a, b) = …`) は E0011 である
- `lhs := e` は、型が `Unit` の式で、優先順位が最も低い。式の文としても、ラムダの本体、`if` の枝、`match` の腕にも書ける (`for 0 n (fn i -> a[i] := i)`)。右辺に `:=` は書けない。左辺はパーサが式として読み、`var` の名前か `var` の名前の添字かを HIR が確かめる。どちらでもなければ E1053 にする
- `e[i]` は後置の添字で、関数適用より強く結び付く (`f xs[i]` は `f (xs[i])`、`a[i][j]` も書ける)。次のトークンの直後に空白なしで `[` が続くときだけ、添字と読む
  - 名前 (修飾した名前を含む)
  - `)`、`]`、`}`
  - 射影の番号 (`t.0[i]` の `0`)

  空白があれば、今までどおりリストを渡す関数適用である。字句は変えず、パーサが前のトークンとの間に空白があるかを見る。前のトークンは本物のトークンに限る。レイアウトの段階が入れる仮想のトークンは幅が 0 で次のトークンの先頭に置かれるので、行頭の `[` が前に接していると読まないためである
- 行末の `:=` は、`=` と同じくブロックを開く ([レイアウト規則](../../spec/layout.md) の規則 3)。`x :=` で改行して、次の行に値を書ける。REPL の入力の終わりの規則 (同じ文書の「REPL の入力の終わり」の規則 2) の開始トークンにも `:=` を足す
- 上の構文の文法と字句の規則は、[文法](../../spec/grammar.md) と [字句](../../spec/lexical.md) とレイアウトの規則に足す

### HIR

- `var x = e` の範囲は、同じブロックの、その文より後ろのすべてである。`var` の文は、ブロックの残りの文と最後の式を本体に持つ、1つの式のノードになる。変数のブロックの最後の式は、そのブロックの最後の式 (`Block` の `tail`) である。ブロックが文で終われば、最後の式はない
- `var` の地点ごとに、そのモジュールに合成のエフェクトの項目 `L` を1つ作る。`L` は名前空間に入らず、型引数も操作も持たない。変数の型は `L` の型引数でなく `var` のノードの側の表に持つ。型引数に持つと、変数を使う閉包を変数自身に入れたとき (`fs[0] := (fn () -> fs[1] ())`) に、変数の型が自分を含む無限の型になるためである。ラベルの鍵は今のまま `EffectId` なので、row の表、Core IR の効果の表、EP の evidence は今の形で使える
- `L` の名前は、プログラムとセッションの中で地点ごとに異なり、同じ地点からはいつも同じになるように決める。VM は効果を名前で番号に引くので、2つの地点が同じ名前になると、外側の地点の閉包が内側の地点の handler に届いてしまうためである。名前は、地点を含むトップレベルの項目の名前 (REPL の入力の項目の名前を含む)、変数の名前、その項目の中でのソースの順の番号から作る。診断では `var x` と表示する
- `var` の名前に解決した参照は、読み出し、代入、添字の読み、添字の書きの専用のノードになる。変数でない式の添字 `e[i]` も、添字の専用のノードになる

### 型

- `var x = e` は、`e` を変数の型 `T` (注釈があればその型) で検査し、本体を、今の row に `L` を足した row で検査する。handle の本体と同じである。ノードの値は本体の値である
- 変数を使う所は、どれも `perform` と同じく、その場所の row に `L` を求める。範囲の中のラムダと局所関数で変数を使えば、その row に `L` が推論される
  - `x` の型は `T` である
  - `x := e` は `e : T` で、結果は `Unit` である
  - `x[i]` は、その時点で分かっている `T` が `Array E` なら、`x` を読んでから `Std.Array.get` で読む。そうでなければ、`T` を `MutArray E` と単一化して配列の変数の要素を読む。どちらも `i : Int` で、結果は `E` である。row にはさらに `Panic` を求める
  - `x[i] := e` は、`T` を `MutArray E` と単一化し、`i : Int`、`e : E` で、結果は `Unit` である。row には `Panic` も求める
  - どちらの添字も `E ≤ Unr` を求める。extern の行が要素の型変数を `Unr` に固定しているのと同じである。`MutArray.empty` の要素の型変数は結果にだけ現れて固定されないので、この制約がないと `MutArray File` の変数の添字が通ってしまう
- 変数でない式の添字 `e[i]` は、`e : Array E`、`i : Int` で、結果は `E` である。`E ≤ Unr` と `Panic` を求める。`Array` と `MutArray` は Prelude の型なので、型検査は `LangItems` から名指す。translate は `Std.Array.get` の行を直接呼ぶので、`Std.Array` を読み込まなくてよい
- `L` は操作を持たないが、エフェクトの多重度を `Once` とする。今は操作の多重度の最大から決めるので、操作がないと `Never` になり、`may_yield` も Kind と持ち越しの検査も、`L` を yield しないラベルとして扱ってしまう。変数の操作はどれもすぐに再開するので `Once` である。これで、変数を使う関数は `yields` になり、S14c-2 の特殊化の経路に入る
- 変数の分類: 本体の推論と呼び出しの包含を解き、クラスの制約を解いた後、Kind の問題を解く前に、各変数を型で分ける。REPL の入力では、決まらない型変数を `Unit` に決めた後である。`T` が `MutArray _` なら配列の変数、そうでなければ `Unr` の変数にし、`T ≤ Unr` を Kind の問題に足す
  - `T ≤ Unr` が定数の `Lin` に当たれば (`File` を持つ変数など)、E3007 である。Kind の問題の違反の理由に、変数のための理由を足して報告する
  - シグネチャの型変数 `a` の値を持つ変数では、`T ≤ Unr` はスキームの制約になる。その関数は `a` に `Unr` の型だけを受け、`Lin` の型で呼べば呼んだ所で E3001 になる
  - 分類は本体の型付けの表に置き、書き出すときに `BodyTypes` に写す。usage と carry のパスは書き出す前の表を読むためである。トップレベルの本体と REPL の入力の両方で行う

### 範囲の外へ出る閉包

`L` は `var` の地点ごとに1つである。再帰でもループでも、同じ地点に入り直すと、同じ `L` の handler がまた作られる。そのため、前の回で作った、x を使う閉包が、後の回の handler に届くことがありうる。たとえば、`for` の本体で `var x = i` と書き、`x` を読む閉包を外側の `State` の状態に入れると、次の回の本体で取り出したその閉包は、次の回の `x` を読む。これを型で断る。

- 次のどれかに `L` が現れたら、E2019 にする
  - `var` のノードの値の型
  - `var` のノードの場所の row。ほかのラベルの型引数 (`State (Unit -> <L> Int)` など) を含む
  - 範囲の外で束縛したものの型。範囲の外の局所変数、引数、パターンの変数、局所関数、外側の `var` の変数の型である
- 範囲から値が出ていく道は、ノードの値と、外側のエフェクトの操作と、外側の束縛だけである。外側のエフェクトの操作の型は、ノードの場所の row のラベルの型引数に現れる。そのため、この3つを調べれば足りる。トップレベルの関数の型は、シグネチャに `L` を書けないので調べなくてよい
- 範囲の中で定義した局所関数は、自分を再帰で呼んでも `var` の地点に入り直さないので、型に `L` を持ってよい
- 調べるのは、変数の分類と同じ時点である

### 配列の変数の規則

- 配列の変数の名前だけを書いた所は、取り出しである。取り出しは今の配列を返し、変数の状態を、確保しない不死の空の配列に替える。usage のパスは、取り出しを、範囲の中にある線形な局所変数の消費として数える
- 取り出しは、経路ごとにちょうど1回である。2回なら E3002、取り出さない経路があれば E3003 で、文言は変数のものにする。最後の式のないブロックの配列の変数は、どの経路でも取り出さないので E3003 である。戻らない呼び出しで終わる経路は、暗黙の後始末 ([線形性](../../spec/linearity.md) の「暗黙の後始末」) と同じく取り出さなくてよい
- 次は E3008 である
  - 変数のブロックの最後の式の外での取り出し
  - 最後の式の中でも、関数の中での取り出し。関数とは、ラムダ、局所関数、handle の本体、節、`use` の残りの部分 (ラムダになる)、セクションである
  - 最後の式の中で、取り出しのほかにその変数を使うこと
  - 配列の変数への `x := e`。古い配列を捨てることになるためである
- 配列を何本も使ったブロックでは、最後の式でそれぞれを `freeze` するか `drop` する
- 最後の式も、ほかの文と同じく変数の handler の中で評価する。`Unr` の変数は、最後の式の中でも今の値を読む
- 範囲の中で作った閉包を、取り出しの後に最後の式の中で呼ぶと、その閉包の添字は空の配列に対して働くので、範囲外の `Panic` になる
- carry のパスは、配列の変数の範囲を、`Lin` の状態を持つ handle として扱う。外側の row に `multi` の操作があれば、今の持ち越し規則どおり E3006 である

### 脱糖

- translate は、変数の分類をもとに、`L` ごとに Core IR の操作の表を作り、handle、節、`perform` を組む
- `Unr` の変数の操作は、`get : () -> s` と `set : s -> ()` である。節は `fn get () st -> (st, st)` と `fn set v _ -> ((), v)` で、`return` の節は状態を捨てて本体の値を返す
- 配列の変数の操作は、`take : () -> MutArray e`、`length : () -> Int`、`read : Int -> e`、`write : Int -> e -> ()` である
  - `take` の節は、今の配列を返し、状態を不死の空の配列に替える
  - `length` の節は、`Std.MutArray.length` の行を呼ぶ。配列を借りて組を開く、今の translate の形のままである
  - `read` の節は、`Std.MutArray.read` の行を呼ぶ。`length` と同じく配列を借りる
  - `write` の節は、`Std.MutArray.write` の行を呼ぶ
  - `return` の節は、残った状態を `drop` してから本体の値を返す
- `x` は、`Unr` の変数なら `get` を、配列の変数なら `take` を `perform` する。`x := e` は `set` を `perform` する
- `x[i]` は、`i` を評価し、`length` を `perform` して、`i` が範囲の外なら、その場所で範囲外の `Panic` を起こす。範囲の中なら `read` を `perform` する。`x[i] := e` は、`i`、`e` の順に評価し、同じく `length` で確かめてから `write` を `perform` する
  - 節の中では `Panic` が起こらない。入口は状態を evidence から取り出してから節の本体を動かすので、節の中で `Panic` が起こると、変数の handle の内側の `try_panic` が捕まえた後に、変数の状態が失われるためである
  - 範囲外の `Panic` は、Prelude の中だけの extern で起こす。この extern は添字と長さを受け、`Std.MutArray.read` と同じ文言の `IndexFault` を返す。`Panic` は使う所で起こるので、使う所から最も近い `try_panic` に届く。特殊化した版でも同じである
  - 節の入口の形は、今の EP の規則のままにする。`read` と `write` の節は `Panics` の extern を呼ぶので under の形になるが、範囲は確かめてあるので中断しない
- 合成した節は、S14c-2 の状態を渡す形が受け付ける形に作る。節の状態の引数は、`return` の節の状態の引数と同じ Repr と印を持つ。節の本体は、`mask` のない末尾の `resume k(v, s)` で終わり、`k` を返すたびにちょうど1回使う (「すぐに再開する節」)
- 不死の空の配列は、Core IR と LIR の primitive で作る。primitive の結果の印は `lin` である。`verify_translated` は EP の前の `prim` を断るので、この primitive を `root_get` と `root_set` と同じく許す。VM は、`lin` ビットを立てた長さ 0 の `Data` を、凍結した領域の定数として持ち、その語を返す
  - この物体は書き換わらない。長さが 0 なので、`read` と `write` はいつも範囲外になる。範囲は使う所で確かめるので、節がこの物体を書き換えることもない
  - `freeze` されることもない。取り出しは経路ごとに1回で、取り出した後の状態は `return` の節で `drop` するだけだからである
  - RC の命令は、領域の物体には何もしない
  - `eml_rt` には手を入れずに済む。`alloc_immortal` は `lin` ビットのある `Data` を作れ、凍結は参照の数が 0 の物体を受け付け、VM は今も定数をこの形で作っている

### 状態を渡す形の広げ方

2026-10-20 の試作で、`var` を手で脱糖したふるいと fannkuch-redux を、S14c-2 の形で特殊化して測った。どちらも `evidence_steps` は 0 になったが、確保の回数は手で線形に受け渡した版と大きく違った。ふるい (n = 2000) では 307 回と 3 回、配列を3本と変数を10本使う fannkuch-redux (n = 7) では 422,896 回と 20,167 回だった。差のほとんどは組である。原因は次の2つで、S14c-3 で状態を渡す形を広げて直す。

- 経路が広すぎる: 今の経路は、`yields` の関数への直接の呼び出しをすべてたどる。そのため、H の `perform` に届かない関数も複製され、使わない状態を受け渡して組で返す。fannkuch-redux では、配列を逆に並べるループの複製が、使わない7つの `Int` の状態と1つの配列を受け渡していた
  - 直し方: 呼ぶ先の関数が H に触れないなら、経路に入れず、呼び出しをそのまま残す。H に触れるとは、その関数か、直接の呼び出しでたどれる関数が、H の `perform`、`mask` の付いた呼び出し、`handle`、`resume`、`clause`、`yields` の `apply` のどれかを持つことである。触れない関数は H の evidence を引かないので、H の handle を特殊化して evidence がなくなっても、そのまま動く
- 入れ子の組が重なる: 今の複製の結果の形は、複製の元の関数の結果の Repr だけで決まる。2回目からの元は前の回の複製で、その結果は前の回の状態か組なので、外側の handler ごとに組が1つずつ重なる。`Unit` を返す関数でも、2つ目の handler から組を返す
  - 直し方: 複製の結果を「値の並び」で決める。元が基の関数なら、並びは、結果 (Repr が `unit` でなければ) である。元が状態を渡す形の複製なら、その複製の並びである。新しい複製の並びは、それに状態つきの handler の状態を1つ足したものである。並びが1つなら、その値をそのまま返す。2つ以上なら、その大きさのタプルを1つ作って返す
  - 呼ぶ所は、並びの形に合わせてタプルを開く。handle の地点は、本体の複製の並びを開き、`return` の節を結果と自分の状態で呼んで、残りの状態で続ける
  - S14c-2 の `Plain`、`StateOnly`、`Pair` は、この並びの大きさが1つ (結果か状態) か2つ (結果と状態) の場合にあたる。handler が1つだけのときの形は変わらない
- 名前で中身が決まる規則は保つ。並びは、複製の元の名前と handler の鍵から決まるためである

### 速さの見込みと残る差

- `for` と `while` の閉包は、S13e-1 の既知の閉包の写しで経路に入る。入れ子の `var` は内側から特殊化される (2026-10-20 の試作で確かめた)
- 組が残るのは、経路の関数の末尾でない呼び出しから、2つ以上の値 (結果と状態、または2つ以上の状態) が戻る所である。戻るたびにタプルを1つ確保する。たとえば `while` の本体の閉包が2つ以上の変数を書き換えると、回るたびに1つ確保する。融合で展開された複製では、タプルは消える
- 状態が `Float` なら、タプルのフィールドは一様な位置なので、`Float` の箱も確保する
- これらは S14e で構造体になって消える。完了の条件では、残ったタプルと `Float` の箱の確保を数え、差として記録する

### `for` と `while`

```
for : Int -> Int -> (Int -> <e> Unit) -> <Panic | e> Unit      -- lo 以上 hi 未満を順に
while : (Unit -> <e> Bool) -> (Unit -> <e> Unit) -> <e> Unit
```

- Prelude の eml のコードで書く。`for` の `<Panic>` は添字の足し算から来る

### 残る制限

次は S14c-3 では入れない。必要になったら、[ロードマップ](../../future/roadmap.md) の論点として扱う。

- 配列の変数の長さを、範囲の途中で読む書き方。長さは変数とは別に持つ
- 配列の変数を、範囲の途中でトップレベルの関数に貸す書き方。範囲の中の局所関数で書くか、変数にする前に線形に受け渡す
- 取り出して変えて戻す `x := f x`。配列の変数では E3008 になる
- 範囲の外で定義した局所関数に、変数を使う閉包を渡すこと。局所関数の型に `L` が現れるので E2019 になる

### S14c-3 で計画に任せること

### 種類2 (期待値の変更)

- S14c-2 で、すぐに再開する節だけの状態つきの handler は、末尾の経路でも新しい形になる。そのため、`crates/eml_vm/tests/bench.rs` の `RunStats` の期待値 (確保の回数など) と、`crates/eml_core_ir/tests` の特殊化の IR のスナップショットが変わる。特殊化の自動と手書きの組 (`specialization_matches_hand_written_work`、`specialization_matches_hand_written_rc`) の手書きの側も、新しい形に合わせて書き直す。範囲は「すぐに再開する節だけの handler を特殊化するテストのすべて」である
- extern の行と std のシグネチャを結ぶテスト (`crates/eml_core_ir/tests/externs.rs` の型変数の確かめ、`crates/eml_hir/tests/externs.rs`) を、型変数の引数と型引数を持つ extern の型を許す形に緩める
- `extern data` の型引数の E0011 を確かめるテストを、型引数を許す形に変える
- `crates/eml_cli/tests/snapshots/integration__ui__check_fail@kinds__extern_kind.em.snap` の E0011 の文面を、"cannot have parameters, `=` or `where`" から "cannot have `:`, `=` or `where`" に変え、ラベルも "only the name and its type parameters" に変える。`extern data` が型引数を受け付けるようになったためである
- S14c-3: 状態を渡す形の広げ方 (H に触れない関数を経路に入れないこと、入れ子の handler の複製が値の並びを1つのタプルで返すこと) で、特殊化の IR のスナップショットと、`crates/eml_vm/tests/bench.rs` の `RunStats` の期待値 (`state_nested` の確保の回数など) が変わる。範囲は「状態を渡す形で特殊化するテストのうち、入れ子の handler か、H に触れない `yields` の関数を経路に持つもの」である。UI テストの出力と結果は変わらない
- S14c-3: `std/Env.em` の extern の改名 (`var` から `lookup`、行の名前 `Std.Env.var` から `Std.Env.lookup`) で、名前を含む期待値が変わる所

### 足すテスト

- `Array` と `MutArray` の各関数、範囲外の `Panic` と `try_panic`、`freeze` と `thaw` の写す場合と写さない場合、検査モードの漏れと `LinDup` (`run`、`run-fail`、`eml_rt` の単体テスト)
- 状態を渡す形の特殊化の IR のスナップショットと、末尾でない `perform` のループの `RunStats`
- `var` のスカラーと `MutArray`、配列を3本使う計算、ラムダと局所関数からの使用、配列の変数の取り出し、`Unr` の変数を最後の式で読むこと、取り出しの後に閉包の添字が範囲外の `Panic` になること (`run`)
- E1053 (変数でない式への `:=`)、E2019 (ノードの値、ノードの場所の row、範囲の外の束縛のそれぞれ)、E3007 (`File` を持つ変数)、E3008 の各場合 (最後の式の外、ラムダの中での取り出し、最後の式の中のほかの使用、配列の変数への代入)、取り出しの重複 (E3002) と取り出し忘れ (E3003)、`MutArray` でない変数の添字 (E2001)、`multi` の操作をまたぐ配列の変数 (E3006) (`check-fail`)
