# S14e 型から決める呼び出しの規約と構造体の表現の設計

## 目的と範囲

S14e の設計である。出発点は[ロードマップ](../../future/roadmap.md) の「S14 数値計算の整備」の「小さな単一コンストラクタの型の構造体の表現」の決めたことと論点、同じ節の論点「型から決める呼び出しの規約」、S14 の設計 (`docs/superpowers/specs/2026-10-19-s14-numeric-design.md`) の「S14b〜S14e の方向」で、2026-10-21 の議論で詰めた。

S14e は2つの作業からなる。

| 作業 | 中身 |
|---|---|
| S14e-1 型から決める呼び出しの規約 | 関数とクロージャの ABI を型から決める。内部の関数をいつも一様にする規則、`f$boxed`、T3 をやめ、`apply` に型どおりの値を渡す。合わないときは実行時に変換し、末尾呼び出しでは変換を合成する |
| S14e-2 構造体の表現 | コンストラクタが1つで、再帰せず、小さな `data` とタプルを、ヒープの箱でなく構造体の値として表す。LIR で葉の変数に開き、直接の呼び出しと `apply` から複数の値を返す |

S14e-2 の目的は nbody の `Vec3`、mandelbrot の `Complex`、状態を渡す形の複製が返す組で、計算ごとの確保をなくすことである。S14d の計測 ([計測の基準](../../implementation/benchmarks.md) の「S14d」) が、消える確保と消えない確保を見込んでいる。S14e-1 の目的は展開しない内部の関数を直接呼ぶ所と、関数の値を通る所で、スカラーと構造体を箱に入れずに渡すことである。S14e-1 がないと、S14e-2 は展開しないラムダを直接呼ぶ所で、今はポインタで渡す組を呼ぶたびに箱に入れることになり、後退する。

S14e-1 を先にする。S14e-2 は構造体の葉を、S14e-1 が決めた「型どおりに渡す」形にそのまま載せる。逆の順では、S14e-2 で一様な内部の関数に合わせた規則を作り、S14e-1 でまた作り直すことになる。

S14e で S14 を閉じる。S14 の完了の条件は S14d の計測と S14e の記録で満たす。

## 2026-10-21 に決めたこと

- 型から決める呼び出しの規約を、S14e で完全に入れる (ユーザーが決めた)。はじめは S14 から外す案で進めたが、構造体の表現のレビューで、展開しないラムダを直接呼ぶ所の後退が見つかったため、範囲に入れた
- 構造体にする型の語の数の上限は 6 である (ユーザーが決めた)。繰り返しの中で返す組 (最大で5つの値) はすべて覆う。fannkuch-redux の 8 つの値の組は実行の全体で1回しか確保しないので、構造体にしない
- 構造体は、Core IR では Repr が `struct(S)` の1つの変数として扱い、box の挿入の後の新しい LIR のパスで葉の変数に開く (下の「S14e-2 の進め方」)
- 配置で構造体の型を宣言したフィールドは、親の物体の中に葉を並べず、一様な位置 (`tobj`) として箱で持つ。並べる形 (inline) は、配置のフィールドの数がソースのフィールドの数とずれ、同じ配置に具体化の違う形が入って形どうしの変換が要る。計測のプログラムには効かないので、ロードマップの「処理系」に回す
- 規約の正しさは静的な分類に頼らない。`apply` は呼ぶ所と呼ばれる関数の Repr を実行時に比べ、合わなければ変換する。分類を誤っても遅くなるだけで、壊れない
- 末尾呼び出しの保証は変換の合成で保つ。そのため T3 をなくし、関数の ABI は型と役割だけで決まる

## 目標、目標にしないこと

### 目標

- 関数の値を型どおりの Repr で呼び、合う所では `box`、`unbox`、確保を起こさない
- 下の「構造体にする型」に当たる型の値が、関数の引数、結果、ブロックの引数、局所の変数、`apply` で確保を起こさない
- 一様な位置との間では、今の `con` と同じ形の箱に入れて渡し、意味は変わらない
- 末尾の位置の呼び出しの保証 ([LIR](../../spec/lir.md) の「末尾の位置の呼び出し」) を、`apply` の辺も含めて保つ
- 下の「完了の条件」の確保の減りを `RunStats` で示し、記録して S14 を閉じる

### 目標にしないこと

- 構造体のフィールドを親の物体に並べること (上の「決めたこと」)
- スカラーや構造体の要素を生で持つ配列。配列の要素は一様な位置のままである。ロードマップの「処理系」にある
- 操作の表 (`clause` の ABI) と extern の行に構造体を載せること。どちらも構造体の型の位置は箱で受け渡す
- ネイティブ化と、VM とネイティブのコードを混ぜること。ただし、下の「ネイティブ化への見込み」の条件を守る

### 引き換えにすること

型から決める規約では、総称な関数を通して値を素通しする所で、今より確保が増えることがある。今は一様な関数が受けた箱をそのまま返せるが、規約の後は呼ぶ側が箱から取り出して型どおりに渡し、戻った値をまた箱に入れるためである。たとえば、特殊化されない `List.map` に、`Float` をそのまま返すことのある関数の値を渡すと、要素ごとに `Float` の箱が1つ増える。`List (Float, Float)` の組の要素を入れ替える関数の値なら、組の箱と `Float` の箱が増える。展開しない直接の呼び出しを通る構造体も同じである。この形は計測のプログラムに現れないので、引き換えとして受け入れ、UI テストの `RunStats` で回数を固定して記録する (下の「足すテスト」)。

## S14e-1 型から決める呼び出しの規約

### 今の形

- 関数の値として参照される関数は一様でなければならない ([LIR](../../spec/lir.md) の「一様な関数」)。内部の関数 (ラムダ、handle の本体、節、包む関数など) はいつも一様で、内部の関数でない関数は値として使えば一様な包み `f$boxed` を足す
- そのため、展開しない内部の関数を直接呼ぶ所では、呼ぶ側が引数を `box` し、結果を `unbox` する。`Float` なら呼ぶたびに箱を確保する。関数の値として使うトップレベルの関数は、`apply` のたびに `f$boxed` を1段通る
- 捕獲も一様で、捕まえた `Int` と `Float` は箱に入る
- `apply` の結果はいつも `tobj` なので、スカラーを返す関数が末尾の位置で `apply` すると、T3 がその関数の `ret` を `tobj` に上げて末尾呼び出しを保つ ([LIR](../../spec/lir.md) の「T3」)

### 関数の ABI

- どの関数も引数と結果の Repr を具体化した型から決める。今のトップレベルの関数と同じ決め方を、ラムダ、局所関数、handle と `var` の範囲の本体と節、`op$`、`con$`、`$externN` にも当てる
- `op$`、`con$`、`$externN` は型ごとの instance にし、名前に型引数を書く (`con$Some@[Int]`)。スキームから決める今の形だと、型どおりに呼ぶたびに下の変換の遅い道を通るためである
- `cont$` と `cont$state` (利用者が `k` を関数として使うときの包み) も、`k` の型ごとの instance にする。利用者は `k` を型どおりに呼び、包みの中の再開は下の「EP の一様な場所」なので、box の挿入が一様な値に変える
- EP のしくみが総称に呼ぶ関数は、EP が渡す位置を一様にし、捕獲の位置を型どおりの Repr で持つ。一様にする位置は役割で決まり、次のとおりである
  - handle の本体: `()` の引数と結果
  - 操作の節の関数 (`prompt$` が呼ぶ節のクロージャ): `k`、状態、結果
  - `return` の節: 値、状態、結果
  - 継続の関数 `f$kN`: 再開の値、状態、結果
  - EP が作る補助の関数 (`compose$`、`prompt$`、`resume$`、`rewind$`、`mask$[…]`、`id$`): 今のまま、すべての位置
- `var` の範囲と節も、handle の本体と節と同じ役割を持つ
- `clause` の印の関数 (入口の関数) は、今のまま操作の ABI に合わせ、捕獲は一様のままにする
- 役割は、translate と EP が関数を作るときに付ける。optimize の複製は複製元の役割を写す。ただし、handler への特殊化が作る関数 (`f{H}`、`f{H}$hN`、`f{H}$hjJ`、`<g>{k}`) は役割を持たない。これらは直接呼ばれるか、特殊化した経路の中で型どおりに呼ばれるためである。`<g>{k}` の中の `k` への `apply` (EP の再開の `apply` と同じ形) も、EP の一様な場所でなく型どおりの場所である。handler への特殊化の後に直接呼ぶ `return` の節は役割を持ったままなので、呼ぶ所に変換が入る。`return` の節は小さいのでふつうは展開され、変換は覗き穴で消える。消えない形の費用は計測で確かめる。役割は名前で決まるので、名前が同じ関数はいつも同じ ABI になる規則 ([VM](../../spec/vm.md) の「追記」) は保たれる
- `internal` の印は ABI を決めなくなる。印をほかの判断 (optimize の複製の名前など) に使う所はそのまま残す
- T3 をなくすので、関数の `ret` は型と役割だけで決まり、パスが上げることはない

### `apply` の ABI

- `apply` は、その場所の矢印の型から決まる Repr で引数を渡し、結果を受ける。変数の引数と結果の Repr は変数の Repr で、定数の引数だけは Core IR と LIR の `apply` が Repr を持つ。定数の `#N` が `enum` か `tobj` かを型から決めるためである。translate が型から決め、optimize が作る `apply` は置き換えた変数の Repr を写す
- 末尾の位置の `apply` の結果の Repr は、コード生成が、その `apply` を含む関数の LIR の最後の `ret` にする。値はそのまま呼び出し元の結果になるためである。EP が `apply` を継続の関数へ写したり、box の挿入が役割で `ret` を一様にしたりしても、このときの `ret` を使うので食い違わない。EP の一様な場所が末尾の位置にあるとき (`cont$` の中の再開など) も、結果はこの規則に従い、引数だけが一様な場所の規則に従う
- 単相化しているので、関数を作った所と `apply` する所は、ふつうは同じ型を見ている。そのため Repr が合い、変換は要らない
- 合わないことがあるのは、一様な位置 (`_`、多相再帰) の境目と、EP の役割の境目である。`_` の境目では、データの中に入った関数の値も行き来するので、静的には包み切れない。そこで、合わないときは `apply` が実行時に変換する (下の「VM」)
- EP の一様な場所: EP が作る `apply` (補助の関数の中、`Call::Resume` から作る再開の `apply`、`cont$` の中の再開) は、一様な場所である。引数と結果を一様な Repr で持ち、box の挿入がその場所で変換を入れる。呼ばれる関数の一様な位置と合うので、実行時の変換は起きない
- 捕まえた値と部分適用の引数は、呼ばれる関数の引数の Repr で持つ。`closure g(…)` の引数は直接の呼び出しの引数と同じく、`g` の引数の Repr への変換を入れる位置である。`_` の instance の部分適用 (`closure depth@[_](5)`) や、捕獲が一様な入口の関数のクロージャでは、box の挿入が変換を入れる

### box の挿入

- 内部の関数をいつも一様にする規則 (今の手順の 1. の後半)、T3 (手順の 2.)、`f$boxed` (手順の 3.) をなくす。手順は役割による一様化と、位置ごとの変換だけになる
- 位置の規則 ([LIR](../../spec/lir.md) の「位置の規則」) を次のように変える
  - `apply` の呼ばれる値は `tobj` のまま。引数と結果は、`apply` が持つ Repr の並び (EP の一様な場所では一様な Repr) と比べる互換の位置である
  - `closure g(…)` の引数は `g` の引数の Repr
  - 関数の値として使う関数の引数と `ret` に、`tobj` と互換である条件はなくなる
- 末尾の位置の呼び出し (直接の呼び出し、`apply`、`clause`) は、結果の Repr が呼び出し元の `ret` と互換でなくても `tail` になる。結果の変換は、下の「VM」の変換のフレームが行う
  - box の挿入は、末尾の位置の呼び出し (EP と縮約と同じ定義、`tail.rs` の `tail_position_call`) の結果の束縛と、その `return` に変換を入れない。束縛の Repr は呼ばれる側の結果の Repr にする。入れると、`return` の値が変換の束縛になり、末尾の位置の形が消えるためである
  - 縮約は、この形の呼び出しを、互換かどうかによらず `tail` にする
  - 範囲の段の verifier は、互換でない `return` を、この形のときだけ許す
  - Kind の印は両端が同じ型から決まるか `poly` なので、互換である。verifier は今のとおり印を比べる
- `never` の操作の末尾の `clause` は、今のとおりどの `ret` とも互換として扱い、変換も合成もしない ([LIR](../../spec/lir.md) の「`never` の操作」)
- [LIR](../../spec/lir.md) の「末尾の位置の呼び出し」の保証の理由を改める。末尾の位置の呼び出しはどれも `tail` になり、変換のフレームは合成されて、本当のフレーム1つにつき多くとも1つになる。そのため、輪をたどってもスタックは伸びない

### VM

- `FnEntry` は、引数ごとの Repr と結果の Repr を持つ。今の `ret_rc` はこれに含まれる。引数の数 (`arity`) は源の引数の単位で数え、構造体の引数は S14e-2 で葉に開く
- `apply` の命令 (`Apply`、`TailApply`) は、引数ごとの Repr と結果の Repr をオペランドの表に持つ。コード生成が LIR の `apply` の Repr の並びから決める
- Repr の並びは `CodeBase` の中で中身から一意な番号 (シグネチャの番号) にする。追記でも中身で引き直すので、番号は追記の間で変わらない。debug ビルドの一致の確かめ ([VM](../../spec/vm.md) の「追記」) は、`FnEntry` のシグネチャも比べる
- 比べは Repr の等しさでなく、変換の種類で行う。種類は、語のまま渡せるもの (`obj`、`tobj`、`unit`)、`int`、`float`、`enum`、構造体 (形の骨組みで比べる) である。`obj` と `tobj` が違うだけで遅い道に入らないためである
- クロージャの物体は捕まえた値と部分適用の引数を、呼ばれる関数の引数の Repr で持つ。形は今のデータと同じく、走査する語 (`&f` と参照) の後に生の語を並べ、並べ方は `FnEntry` から決まる。捕まえた値の数はクロージャの最初の走査する語 (`&f` の即値) に、関数の番号と一緒に詰める (`f | k << 32`)。1回の読み込みで関数と数が分かり、クロージャの大きさも変わらない。関数の値 `&f` は k が 0 の場合である。tag は、検査モードが evidence とクロージャを見分けるのに使っているので使わない ([オブジェクトモデル](../../spec/object-model.md) の「evidence の3つの物体」)
- VM が部分適用で作るクロージャも、同じく `FnEntry` で並べる。`lin` ビットの規則は今のまま
- `apply` の手順
  1. 呼ばれる関数の `FnEntry` を引き、渡す引数ごとに、呼ぶ所の種類と関数の引数の種類を比べる。ちょうどの数のときは、結果の種類も比べる
  2. 全部合えば、今と同じ道で入る (速い道)。捕まえた値は走査する語と生の語から関数の引数の順に並べて写す。今の `apply` が捕まえた値を一時の `Vec` に集める手間もなくす
  3. 合わない引数は関数の引数の Repr へ変える。一様な値から取り出すときは、値を消費する (一意なら箱を空け、そうでなければ中身を `dup` して箱を `decref` する)。結果が合わなければ、変換のフレームを積んでから入る
  4. 余る引数は今と同じく `ApplyRest` のフレームに預ける。生の語が混ざるので、フレームに呼ぶ所のシグネチャの番号と、残りの引数の最初の位置を置く。後の適用と巻き戻しは、それで語の Repr を知る。余りが続く適用も同じである
- 変換のフレーム: 戻ってきた値を、呼ぶ所の Repr へ変えてから渡すフレームである。中身は `CodeBase` に変換の組 (受ける Repr の並びと渡す Repr の並び) ごとに1つ作る小さな命令列で、組の中身で一意にする。命令列の先頭の直前に、受けるスロットを持つ命令を置くので、`Ret` と `RetN` はふつうの呼び出しと同じ規則で値を書く (S14e-2 の `RetN` の規則)
- 変換のフレームの大きさは、受ける値の最大 (6 語の構造体の葉) と作業用のスロットの分で決まった1つの大きさにする。合成でフレームを置き換えるとき、ずらさずに済むためである
- 変換の命令列は、`CodeBase` の決まった範囲に置く。戻り先が変換のフレームかは、戻り先の位置がその範囲にあるかで見分ける。巻き戻しは、その範囲の位置を表の行を持たないフレームとして扱い、`unwound_frames` に数える。誤りの位置の関数名 (`last_ret`、`function_at`) は、`ApplyRest` と同じく、どの関数にも属さない位置として扱う。逆アセンブラと debug ビルドの一致の確かめは、変換をシグネチャの中身で書く
- 変換の合成: 末尾呼び出し (`TailCall`、`TailSelf`、`TailApply`、`TailClause`) と、`ApplyRest` の2段目の適用 (末尾の適用である) で結果の変換 c2 が要るとき、今のフレームの戻り先が変換のフレーム c1 なら、c1 を c1 と c2 の合成に替える。合成が恒等なら c1 を外し、呼ばれる側が c1 の見出しを引き継ぐ。今のフレームの戻り先が変換のフレームでなければ、変換のフレームを1つ積む。両端はいつも同じ型の Repr なので、合成は恒等か、1つの `box`、`unbox`、構造体と箱の間の変換になる
- 直接の末尾呼び出しの結果の変換は、コード生成が呼ぶ関数と呼び出し元の `ret` から静的に決め、命令に持たせる
- yield 中のダミー: 変換のフレームは yield 中なら値を変換せず、渡す Repr のダミー ([LIR](../../spec/lir.md) の「ダミーの値」) を書く。ダミーを箱に入れて確保しないためである
- 巻き戻し: 変換のフレームは何も持たないフレームとして外す。`ApplyRest` のフレームはシグネチャで参照と分かる引数だけを手放す。着地は `prompt` の印を持つ `apply` (`prompt$` の中の `apply body(())` と `apply κ(v)`) の結果に起き、その場所は一様で、呼ばれる関数も一様なので、今のまま `tobj` のダミーを書く。変換のフレームが間にあれば、着地の手順の「直前に外したフレーム」は変換のフレームになり、その見出しの結果のスロットに書く
- `clause` は今のまま操作の ABI で、変えない
- `RunStats` に `conversions` を足す。数えるのは、`apply` (`ApplyRest` の2段目を含む) で呼ぶ所のシグネチャと `FnEntry` が合わず、実行時に変換した回数である。直接の末尾呼び出しと `clause` の静的な変換のフレームは、設計どおりの変換なので数えない。変換の `box` と `unbox` は `boxes` と `unboxes` にも数える
- 検査モードでは、合わないと見た組が同じ型の Repr どうしであること (たとえば `obj` と `unit` が組にならないこと) と、`&f` の即値に詰めた捕まえた値の数がクロージャの物体の語の数と合うことを確かめる。`&f` の即値を読む所 (`apply`、`clause`、関数の番号の確かめ、逆アセンブラ) は、どれも数を除いて関数の番号を読む
- 安全点は今のとおりで、変換のフレームからの戻りも戻りとして `Ctx::poll` を呼ぶ

### 規約で良くなること

- 展開しないラムダを直接呼ぶ所の `box` と `unbox` がなくなる。`Float` なら確保もなくなる
- 関数の値として使うトップレベルの関数の、`f$boxed` の1段の呼び出しがなくなる
- 捕まえた `Float` を箱に入れなくなる
- T3 がなくなり、`handle` や `get` で終わる関数の `ret` が型どおりになる

## S14e-2 構造体の表現

### 進め方

Core IR では、構造体を「Repr が `struct(S)` の1つの変数」として扱う。命令は増やさない。LIR では、box の挿入が一様な位置との変換を決めた後に、新しいパス「開く」(`flatten`) が構造体の変数を葉の変数の並びに替える。VM は直接の呼び出しと `apply` から複数の値を返す命令を持つ。

ほかに2つの形を比べて、選ばなかった。

- translate の時点で開く形は、Core IR から先のどこでも複数の値の戻りを扱うことになる。optimize と EP (継続の関数、`prompt$`、状態の受け渡し) の全体に手が入る
- Repr を足さずに、LIR で配置を見て逃げない `con` だけを開く形 (SROA) は、関数の境目が今の `obj` のままなので、nbody の `add` と `sub` の結果や `RESIDUAL` のタプルが消えない。ロードマップの「Repr は translate が型から決める」とも合わない

この分担は、Core IR が意味の層で、LIR が表現を明示する層であるという今の分け方と合う。

### 構造体の Repr

- `Repr` に `struct(S)` を足す。S は Program の形の表の番号である。形は配置と、フィールドごとの Repr と Kind の印の組の列を持つ。フィールドの Repr は具体化した型から決める。`Vec3` の形は `Vec3{float, float, float}`、ふるいの組の形は `(,){int, obj lin}` である。入れ子の構造体は、フィールドの Repr が `struct` になる
- 形の番号は Program の中で一意にする (同じ中身の形は同じ番号)。テキストの形では中身を書く。形は具体化した型から決まり、型は instance の名前に入っているので、名前が同じ関数はいつも同じ ABI になる。番号は1回の変換の中だけで意味を持つ。配置の番号と同じである。VM の `CodeBase` は形を中身で引き直す (上の「シグネチャの番号」と同じ)
- 互換 (`Repr::compatible`) は、形の Repr の骨組み (配置と、葉の Repr) が同じときだけ真である。印は互換に入れず、葉ごとに今の印の規則 (`Mark::compatible` と作る所の検査) で比べる。状態を渡す形の複製が値の印から作る形と、型から作る形とで、印だけが違うことがあるためである
- `struct` は `tobj` とも `obj` とも命令なしで行き来しない
- `struct` は、箱を要する Repr の集合に入れる。今の `Repr::BOXED_SCALARS` は定数の配列なので、述語に改め、名前も中身に合わせる。覗き穴と入口で受け直す手順は、この述語から作られているので、構造体にもそのまま当たる
- `struct` は extern の行と操作の表に現れない。操作の表は構造体の型の位置を `obj` にする
- `eml_extern::Repr` は `Copy` のまま保つ。形を番号で指すのはそのためである

### 構造体にする型

`type_repr` が、具体化した型ごとに次の条件で決める。

- コンストラクタが1つでフィールドを持つ `data` (レコードを含む) か、要素のあるタプルである
- `data` は、宣言が再帰の組に入らない。自分自身を、直接か、ほかの宣言のフィールドを通して含む型は外す。`Iter` は `Option (a, Iter e a)` を通して自分を含むので外れ、融合の規則は今のまま `Iter` に当たる。タプルは宣言を持たないので、この条件は当たらない。要素が再帰する型でも、その要素は `obj` の葉になるだけである
- 開いた後の葉の語の数が 6 以下である。`unit` の葉は 0 語と数え、`unit` でない葉が1つ以上要る
- 葉に一様な位置の型変数 (`_`) を含まない。含むと、呼ぶ側の `Pair Float Int` と呼ばれる側の `Pair _ Int` で形が違い、形どうしの変換が要るためである。含む型は今の `obj` のままにする。入れ子のタプルや `data` の中の `_` の葉も数えるので、`(Int, (_, Int))` も構造体にしない。語の数か `unit` の条件だけで構造体にしない入れ子の型は、外側の型の `obj` の1語の葉になる
- 型スキームの型変数 (具体化していない型変数) は `tobj` の葉と数える
- `Lin` のフィールドを許す。ふるいの差の組 `(j, marks)` が `MutArray` を持つためである。構造体の値は `Lin` のまま移す
- row の型引数を持つ型を許す。Repr は row によらないためである

構造体にしない単一コンストラクタの型は、今のまま `obj` である。状態を渡す形の複製が返す組は、型を持たないので、語の数と `unit` の条件だけを当てる。

### 箱に入れる位置

- 一様な位置 (`tobj`、型変数のフィールド、配列の要素、EP の役割の一様な位置と EP の一様な場所) と、配置で構造体の型を宣言したフィールドでは、構造体を箱に入れる。`apply` の引数と結果、`closure` の引数、直接の呼び出しの引数と結果は、S14e-1 の規約で型どおりの位置なので、箱に入れない
- 箱はその型の配置の `con` と同じ形の物体である。葉は配置の宣言したフィールドの Repr に合わせる。`(Int, Float)` の箱は `(,)` の配置で、フィールドはどちらも `tobj` なので、葉を `box` してから入れる。`Vec3` の箱のフィールドは宣言どおり `float` で、葉をそのまま入れる
- 箱はいつもヒープの物体なので、箱の束縛の Repr は `obj` である
- 配置で構造体の型を宣言したフィールドの Repr は `tobj` にする。型変数のフィールドと同じ一様な位置で、互換の位置として box の挿入が変換する。`data Shape = | Ball Vec3 Float | Empty` の `Ball` は `(tobj, float)` である。`data_repr` と `type_repr` を1つの関数で決める今の規則 ([Core IR](../../spec/core-ir.md) の「translate の配置」) は、配置のフィールドの位置でだけ構造体を `tobj` に読み替える形にする
- VM の `apply` の変換が実行時に作る箱には、`lin` ビットを立てない。`FnEntry` と呼ぶ所は Repr だけを持ち、印を持たないためである。立てないのは、`poly` の値のクロージャと同じく、安全な側である ([オブジェクトモデル](../../spec/object-model.md) の「クロージャ」)

### Kind の印と RC

- 構造体の変数の Kind の印はほかの型と同じく型の Kind から決める。今の translate は RC の対象でない Repr の印をいつも `unr` にする (`scalar_or`、[Core IR](../../spec/core-ir.md) の「translate が決める印」) が、構造体は型の Kind に従う
- 開いた葉の印は形の葉の印と、変数の印の小さいほう (`unr` < `poly` < `lin`) にする。複製が開いた引数の印を小さくすること ([Core IR](../../spec/core-ir.md) の「`con` の値の形についての特殊化」) があるためである。箱の印は構造体の変数の印にする
- 「RC の対象」で後始末を決めている所は、`unr` でない RC の葉を持つ構造体も含める。EP の遅い道の `drop x` ([Core IR](../../spec/core-ir.md) の「yield の地点」)、決定木の葉の `drop`、EP の明示の `drop` である。開くパスが構造体の `drop` を葉ごとの `drop` にする

### Core IR

translate
- 構造体の型の `con` は `struct(S)` の変数を束縛する。引数は形のフィールドの Repr と比べ、正確な位置にする。配置の宣言した Repr とは比べない
- 構造体の値を分けるのは、いつも `unpack` である。束縛するフィールドの Repr と印は、形のものになる。構造体の変数はタグの `switch` の scrutinee にならない
- `with_arg` の extern (`Std.MutArray.read` と `length`) が作る組も、条件を満たせば構造体になる。既知のコンストラクタに頼らなくても確保がなくなる
- 入口の関数 `entry$<名前>` の `ret` は値1つにする。入口の値の型が構造体なら `ret` を `obj` にし、box の挿入が箱に入れる

optimize
- 既知のコンストラクタとインライン化は変えない。Repr と印の比べで、構造体は上の互換に従う
- `con` の値の形についての特殊化は、構造体の `con` の値のフィールドを、配置の Repr でなく形の Repr で渡す。複製の中で作り直す `con` の引数が、形と比べる正確な位置になるためである
- 状態を渡す形の複製が2つ以上の値を返すとき (`Returned::info`)、今は `obj` のタプルを返す。これを、値の Repr と印から作るタプルの形の構造体にする。6 語を超えれば今の `obj` のままにする。`RESIDUAL` のタプルはここで構造体になる
- `var` の状態が構造体の型なら (nbody の `offset` の `var p = Vec3 …`)、状態を渡す形の複製の状態の引数も構造体になる。特殊化の条件 (`perform` の引数と節の関数の引数の Repr が同じであること) は、どちらも型から決まるので今のまま成り立つ

EP
- yield の確認の後に返すダミーは、`ret` が構造体なら、構造体の変数に `prim dummy()` を束縛して返す。box の挿入がこの束縛を `unbox` で受け直すので、開いた後は、下の `unbox` のダミーの約束で葉のダミーになる。束縛の印は `poly` である
- EP の役割の一様な位置と EP の一様な場所 (S14e-1) では、構造体は box の挿入が箱に入れる。捕獲の位置は型どおりなので、構造体は葉のまま捕まえる

verifier
- `unpack` の値に `struct` を許す。構造体の `con` の束縛と引数、`unpack` のフィールドを形と比べる
- 構造体の変数をタグの `switch` の scrutinee にすることを拒む

### LIR

パスの順番は変換、box の挿入、開く (`flatten`)、縮約、Perceus、reuse にする。`eml_lir::Pass` に `Flatten` を足す。box の挿入を開くより先に置くのは、一様な位置との変換と覗き穴を、構造体を1つの変数のまま今の規則で済ませるためである。

box の挿入
- 構造体は箱を要する Repr として、今の手順に乗る。EP の役割の一様な位置の構造体の引数は、入口で `unbox` して受け直す
- `box s` (s が構造体) の束縛は `obj` にする。`unbox w` で構造体を得るとき、w は `obj` でも `tobj` でもよい
- `box` と `unbox` で足す変数の印は、構造体なら元の変数の印を写す。スカラーは今のまま `unr` にする
- 覗き穴の2つ目の規則 (`box w` の値を `unbox` する所で w を渡す) を、構造体の箱の `obj` にも当てる
- 型から起きない変換の一覧 (パスがパニックする組) から、構造体と `obj` と `tobj` の間を外し、違う形の構造体どうしと、構造体とスカラーの間を足す。`clause` の入口の関数の構造体の引数 (操作の表は `obj`) は、入口で受け直す

開くパス (構造体の変数を、形の葉の順 (深さ優先) に、葉の変数の並びに替える)
- 葉の変数の名前は元の名前に葉の番号を付けたもの (`d.3.0`、`d.3.1`) にし、Repr は形の葉のもの、印は上の「Kind の印と RC」のものにする。`unit` の葉は変数を作らず、使う所を `()` にする
- 関数の引数、ブロックの引数、`jump` の実引数、直接の呼び出しと `apply` の引数、`closure` の引数を、葉の並びに開く
- 構造体を束縛する `con` は消し、束縛した変数の葉を `con` の引数に置き換える。引数が定数なら、その葉は定数になる。構造体の `unpack` も消し、フィールドの変数を値の葉に置き換える
- `box s` は、配置の宣言したフィールドの Repr に合わせて葉を変換した `con L #0(…)` にする。`tobj` のフィールドならスカラーの葉を `box` し、入れ子の構造体のフィールドは再帰で箱にする。葉が、下の `unbox` が箱のフィールドから取り出した値なら、`box` せずにそのフィールドの語を渡す (葉の単位の覗き穴)。同じ関数の中で組の要素を入れ替えて箱に戻す形で、要素ごとに `Float` の箱を作らないためである
- `unbox w` は、複数の変数を定義する `let (x.0, …) = unbox w L` にする。この命令は箱のフィールドを読み、葉を定義する
  - 使わない葉は `_` と書き、読まない
  - 参照の葉は `unpack` のフィールドと同じ「フィールドの束縛」の規則に従う借りた値である。Perceus は `unpack` と同じく、w の構築子が分かったものとして扱う。w を手放す所は、葉に名前を書いた `release w L #0(…)` (下の「ダミーの約束を広げる」の印を付けたもの) になり、reuse の元になる ([LIR](../../spec/lir.md) の「reuse の元」)。今の `release` と `con … reuse` の組 (組の要素を入れ替えて同じ大きさの組を作る形) が、構造体の後も残る
  - 純粋で、葉がどれも使われなければ縮約が消す。box の挿入の覗き穴が残す使われない `unbox` が消えるので、末尾の位置の呼び出しの形が保たれる
  - w がダミーなら、どの葉もダミーの値 (`prim dummy()` の値、`0`、`0.0`、`#0`) にする。box の挿入は呼び出しの結果を受け直す `unbox` を yield の確認の前に置くので ([LIR](../../spec/lir.md) の「ダミーの値」)、ダミーを受けうるためである。スカラーの `unbox` の今の約束と同じ考え方である
  - 箱の配置の `tobj` のフィールドからスカラーの葉や入れ子の構造体を得るときは、続けて `unbox` を置く
  - w の印が `unr` でなく、葉に `unr` でない RC の葉がなく、w をほかに消費しないなら、その後に `drop w` を置く。`Lin` の箱を、Perceus の `decref` (V1 が拒む) でなく `drop` で手放すためである
- 直接の呼び出しと `apply` の結果が構造体なら、`let (x.0, x.1, …) = call f(…)` のように葉を束縛する。`return` は `return (a, b, …)` にする。関数の結果は値の並び (Repr と印の組の列) になる。テキストの形は `-> (float, float, float)` で、値が1つの関数は今の書き方のままにする
- 構造体の `drop` は RC の対象の葉ごとの `drop` にする。結果の `unit` の変数は `()` に置き換える
- 戻らない呼び出し (`never` の操作の `clause`、`exit`) が構造体を束縛するときは、呼び出しの結果を `unr` の `obj` の変数 r で受け、葉をダミーの値で定義する。box の挿入は戻らない呼び出しの束縛の使いに変換を入れないので、1語の位置 (`tobj` のフィールド、`obj` の引数、`return` の1つの値) の使いが残りうる。開くパスはその使いを r に置き換える。制御が届かないので、どちらも実行されない
- 開いた後の LIR には `struct` の Repr が残らない。extern、`prim`、`clause` の引数と結果には、box の挿入の後に構造体が来ない

パスはブロックと文のループだけで、IR の大きさに比例して再帰しない。入れ子の構造体の再帰は形の深さ (6 語の上限で抑えられる) だけである。

後のパス
- 複数の変数を定義する文 (複数の値を返す呼び出しと `apply`、構造体の `unbox`) を、生存解析、縮約、Perceus、reuse、巻き戻しの表、スロットの割り当てで扱えるようにする。規則は1つの変数を定義する文と同じで、「命令が束縛する変数」を並びに広げる。巻き戻しの表の `owned` は結果の葉をどれも含めない
- 縮約は `let (x.0, …, x.n) = call f(…)` のすぐ後の `return (x.0, …, x.n)` (同じ並び、同じ順) を `tail` にする。`apply` も同じである。[LIR](../../spec/lir.md) の「末尾の位置の呼び出し」の定義を、この形に広げる。構造体の `unbox` は純粋な `let` に数える
- Perceus と reuse の規則は、上の `unbox` の扱いのほか変えない。構造体の箱の `con` はほかの `con` と同じく reuse の相手になる

verifier
- 入口の段と box の挿入の後の段は `struct` を許す。開いた後の段は、変数と関数の結果と配置のどこにも `struct` があれば拒む
- 複数の値の `let` と `return` は開いた後の段だけで許す。並びの長さが同じで、要素ごとに互換であることと、印を要素ごとに比べる。末尾の位置の呼び出しは S14e-1 のとおり互換でなくてよい
- 構造体の `unbox` は開いた後の段だけで許す。値の Repr は `obj` か `tobj` である

### ダミーの約束を広げる

[LIR](../../spec/lir.md) の「ダミーの値」の約束 (`dup`、`decref`、`drop` は何もしない、`unbox` は誤りにしない、`box` はダミーを受けたらダミーを返す) に、次を足す。構造体の `unbox` がダミーを受けると、Perceus が置く `release` もダミーに当たるためである。

- 構造体の `unbox` はダミーを受けたら葉にダミーの値を書く
- 構造体の `unbox` で葉を借りた箱の `release` は、ダミーを受けたら何もしない。名前を書いた葉はすでにダミーの値である。token を作る `release` は空の token を返す

この `release` は、Perceus が構造体の `unbox` の箱に置くものだけである。LIR ではそれと分かる印を付け、VM では別の命令にする。ふつうの `release` の速い道 (`rbtree` や `tree` の繰り返し) に、確かめの分岐を足さないためである。

ダミーかどうかは、速いモードでは物体の種類で見分ける。ダミーは種類 `BigInt` の物体で、構造体の箱はいつも `Data` である。今の速いモードの `release` は、ダミーで `is_last` が偽になって共有の道に入り、`BigInt` のペイロードを読むので、この確かめが要る。検査モードでは、加えてヒープのダミーと同じ語であることも確かめ、ダミーでない `BigInt` を誤りにする。1回の実行の中ではダミーは1つで、回復はスタックを捨てるので、語の比べが使える。`eml_rt` の核の操作は変えず、VM の命令が分ける。

### VM

- 命令を2つ足す。`CallN { at }` のオペランドは [関数の番号, 引数の数, 引数のスロット…, 結果の数, 結果のスロット…] で、`RetN { at }` のオペランドは [値の数, 値のスロット…] である。複数の値を受ける `apply` も結果のスロットの並びをオペランドに持つ。どれも命令の大きさ (8 バイト) に収まる
- `RetN` は、見出しの戻り先の直前の命令から、結果を書くスロットを読む。見出しの形は変えない。末尾呼び出しは見出しを引き継ぐので、そのまま動く。変換のフレームの命令列も先頭の直前に受ける命令を置くので、同じ規則で書ける (S14e-1)。`ApplyRest` を通るときは、最後に戻る先はもとの `apply` の場所なので、その命令を読む
- 検査モードでは、戻り先の直前が複数の値を受ける命令でないか、値の数が合わなければ、内部の誤りにする。`Finish` と `ApplyRest` の位置へ複数の値が戻ることはない。入口の `ret` は値1つで (上の「Core IR」)、`load` は結果が複数の値の入口を断る
- `FnEntry` とシグネチャは構造体の引数と結果の形を持つ。S14e-1 の変換は構造体と箱の間を、配置の物理的な形 ([オブジェクトモデル](../../spec/object-model.md) の「ペイロード」) で変える
- スロットの割り当ては、今の干渉の規則 (同じ文が定義する変数どうしは干渉する) で足りる
- 構造体の箱は `con` なので `allocations` に数える

## ネイティブ化への見込み

- 開いた後の LIR は構造体を葉の変数の並びとして持つ。ネイティブ化では、葉はそのまま Cranelift の値になる。葉はどれも 8 バイトで、`float` の葉は浮動小数のレジスタに、ほかは整数のレジスタに載る
- 複数の値の戻りは eml の中の規約で、extern や C の境目を越えない (`struct` は extern の行に現れない)。eml の中の呼び出しは、`return_call` が求める Cranelift の `tail` の呼び出しの規約を使う。結果がレジスタに収まらなければ、バックエンドが呼ぶ側の用意した領域で返す。`tail` の規約でこの形の `return_call` が使えることは、ネイティブ化の項目で確かめる。6 語の上限は計測のプログラムから決めたもので、ABI から決めたものではない
- 末尾呼び出しの保証はバックエンドの末尾呼び出しの規約に頼る。その規約は呼ぶ側と呼ばれる側の結果の並びが同じであることを求める。要素ごとに互換な葉の並びはどれも 64 ビットの整数か浮動小数に写るので、この条件を満たす。結果の変換が要る末尾呼び出しの扱いは、ネイティブ化の項目で決める未決の危険として残す。Cranelift の `return_call` は今のフレームしか置き換えないので、呼び出し元の変換の包みのフレームを外して合成するには、決まった形の包みを手で書いた命令列で作る必要がある。代わりに、直接の呼び出しの相手を結果の変換の種類ごとの版 (`f[ret=int]` と `f[ret=tobj]`) にして、静的な変換をフレームなしで済ませ、実行時の合成を `apply` の道だけに残す形もある
- ネイティブの `apply` もシグネチャの番号の比べと変換を持つ。捕まえた値の数と並べ方は実行時に決まるので、ネイティブのコードは `f$boxed` の代わりに、バックエンドが作る入口を使う。関数と捕まえた値の数の組ごとの入口 (クロージャの中身と残りの引数を型どおりに受ける) と、シグネチャごとの入口 (VM との行き来と、変換の遅い道のための、語の並びを受ける入口) である。VM のスロットは生の語を持つので、語の並びの入口は箱を要らない
- 変換の遅い道の末尾呼び出しの保証には、`Ctx` に置く作業用の領域 (VM の `scratch` に当たる) と、シグネチャごとの末尾の入口が要る。Rust で書いた実行時の関数からは、保証のある末尾呼び出しができないためである
- VM の `RetN` が戻り先の直前の命令を読むのは、VM の中だけの約束である。VM とネイティブのコードを混ぜるときは、境目の直接の呼び出しを、上のシグネチャごとの入口で扱う
- ネイティブのコードを使い回すときの鍵は、名前だけでも、名前と開いた後のシグネチャでも足りない。関数のコードは中で開く形と配置、呼ぶ関数のシグネチャにも依存するためである。開いた後の LIR と、それが指す形、配置、呼ぶ関数のシグネチャの中身のハッシュを鍵にする
