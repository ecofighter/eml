# S10a VM の本体

位置づけ: S10a の設計。終えたら決めたことを `docs/spec/` などに移し、この文書を消す。

## 目的と範囲

[ロードマップ](../../future/roadmap.md) の S10 (「LIR からのレジスタ型のバイトコード、関数表 `FnEntry` と `CodeBase`、`eml run` を VM に切り替え、CEK の削除」) を、S10a と S10b の2つの作業に分ける。段の列では S10 の1行のままにする。

- S10a (この文書): VM の本体を、CEK と並べて作る。LIR から `CodeBase` を作るコード生成と、`eml_rt` の `Ctx` の上で動く VM、逆アセンブラ、命令の位置から源の位置への表を作る。既定の `eml run` は CEK のままにし、すべての `run` と `run-fail` の UI テストを VM でも流して、CEK と同じ結果になることを確かめる
- S10b: 切り替えと削除。`eml run` を VM にし、SIGINT のハンドラと上限を入れ、CEK、`eml_runtime`、`saved` を消し、spec を書き直す (下の「S10b に残すこと」)

2つに分けるのは、CEK を差分の基準として残したまま VM を作り、命令の形を実際に動かしながら決めるためである。

判断の基準は、簡潔で洗練された実装を第一に、次に性能である。性能の基準は、正しさを先にし、`bench/` のどのプログラムでも VM の実行の分の命令の数が CEK より少ないことを求める (下の「計測」)。それ以上の調整は S10a では行わない。後のマルチコア対応 (VM の並列化と、スレッドをまたぐキュー) を妨げないことも、設計の条件に含める (下の「並列化への備え」)。この文書は、健全性と CEK との一致の観点、設計の一貫性と範囲の観点の2つの敵対的レビューを経ている。

## ロードマップから変えること

- ロードマップの S10 は、算術と比較以外の extern を「行の番号と引数のレジスタの範囲を持つ命令」にすると決めていた。この文書では、引数をオペランドの表のスロットの並びで渡す (下の「命令の形」)。レジスタの範囲にすると、引数を連続したスロットへ移す `Move` の命令が引数ごとに要り、色塗りでは連続を保証できないためである。直接の呼び出し、`apply`、`clause` も同じ形にそろえる
- ロードマップの論点「不死の物体の参照の数え方 (`rc_increments`) を CEK と比べられる形にすること」は、ここで閉じる。凍結した領域の物体は検査モードでも数えない ([オブジェクトモデル](../../spec/object-model.md) の「検査モードでは数えない」) ので、VM は文字列の定数の参照を数えない。CEK はリテラルの参照ごとに1つ数える。この差は `rc_increments` の期待値の違いとして記録し (下の「`RunStats`」)、S10b でスナップショットを替えるときの理由にする
- ロードマップの S10 は `f$boxed` の `yields` の指定を「S10 の VM が読む」としていた ([LIR とインタプリタ](../../spec/lir.md) の「一様な関数」)。evidence passing の後の LIR では、yield は普通の戻りと基本操作で表され、VM が `yields` で動作を変える所はない。VM は `yields` を読まず、`apply` の `yields` も読まない。lir.md のこの文は S10a で直す

## 置き場所

- 新しい crate `eml_vm` を作る。依存先は `eml_lir`、`eml_rt`、`eml_extern` だけで、フロントエンドには依存しない。中身は、LIR のプログラムを `CodeBase<M>` に変換するコード生成 (`compile`) と、`CodeBase` を `Ctx<M>` の上で実行する VM (`run`) の2つである
- `eml_vm` は、自分の `RunStats` と実行時エラーの型 `VmError` を持つ。`eml_interp` には依存しない。`VmError` の表示は、今の `eml_interp::RuntimeError` と1文字も違わない形にする。S10b で `eml_interp` を消すときに、`eml_cli` が再び公開する型をこちらに替える
- S10b では `eml_interp` と `eml_runtime` を書き直さずに消す。S10a の間、2つの crate は変えない
- `eml_lir` に次の2つを足す
  - データの物理的な形を決める関数。`Layout` から、コンストラクタごとに、宣言の位置ごとの物理的な位置と、走査する語と生の語の数を出す。[オブジェクトモデル](../../spec/object-model.md) の「ペイロード」が、S10 で `eml_lir` に足すと決めている関数である
  - 文の単位の生存。今はブロックの入口の生存集合 (`live_in`) だけが公開で、文をさかのぼる `step_back` と終端の後の生存 `live_after_term` は crate の中だけで使える。スロットの割り当て (下の「スロットの割り当て」) が文の単位の干渉を作れるように、これを公開の API にする
- `eml_rt` には次の2つだけを足す。どちらも `cargo verus verify -p eml_rt` と `verusfmt --verus-only --check` を通す
  - 今は crate の中だけで使える `Word::from_bits` を公開する。生の `int` と `enum` の値をスロットに置くためである (下の「スロットとスタック」)
  - 計測で、インライン化の注釈 (`-C remark=inline`) が「definition is unavailable」と示した関数に `#[inline]` を付ける。S9b-2b の計測で、`#[inline]` の置き方によって `map-reuse` の命令の数がビルドごとに約2倍振れたので、付ける前と後に `bench/rt.sh` を流し、[計測の基準](../../implementation/benchmarks.md) に記録する
- `eml_cli` は、`run` の feature で `eml_vm` に依存する。隠しフラグ `eml run --vm` のときだけ `eml_vm` を呼ぶ。`--vm` は速いモードで動き、`--debug-heap` を付けると検査モードになる。Host は `StdHost::stdio(file_root)` で、SIGINT のハンドラはまだ入れない。終了コードは CEK と同じである
- 実行の関数は `eml_vm::execute(program: &eml_lir::Program, debug_heap: bool, host: HostRef) -> Result<RunStats, VmError>` である。`file_root` は Host が持つので、`RunConfig` は受け取らない。`Control` は上限のない既定の値で作る (上限の指定は S10b)。`eml_cli` は同じ形の `execute_vm` を公開する
- `eml_test_support` に `run_vm` と `run_stats_vm` を足す。`run` と `run_stats` と同じ入力を受け、VM の検査モードで実行する

## `CodeBase` と `FnEntry`

`compile::<M>(program: &eml_lir::Program, control: Arc<Control>) -> Result<CodeBase<M>, CompileError>` は、プログラム全体を一度に変換する。`CompileError` は、スロットが `u16` に収まらない関数と、`Heap::freeze` の誤りである。どちらも正しいプログラムでは内部の誤りで、`eml_cli` はコンパイラの内部の誤りとして報告する。

| 欄 | 中身 |
|---|---|
| `functions` | 関数ごとの `FnEntry` |
| `code` | 全関数の命令列 (`Op`)。先頭に組み込みの命令 `Finish` と `ApplyRest` を置く |
| `operands` | 長さの変わるオペランド (`u32` の並び)。呼び出しの関数の番号と引数のスロット、extern の行の番号と引数、`con` のフィールド、switch の行き先、`release` の残すフィールド、`ev_new` の操作の数など |
| `effect_lists` | `evv_mask` のエフェクトの並び (`u16` の並び)。`Ctx::evv_mask` が `&[u16]` を受けるので、写さずに渡せるように分けて持つ |
| `constants` | 定数の語。文字列のリテラル、63 ビットに収まらない `box` の定数、命令に入りきらない `Int` の定数 |
| `region` | 定数を置いた凍結した塊 `Arc<Frozen<M>>` |
| `locations` | 命令の位置から源の位置 (`Loc`) への表 (下の「誤り、止めること、終わり」) |
| `files` | 位置のファイルの表示用のパス。`Program.files` を写す |

- `FnEntry` は、名前、命令列の範囲、引数の数、枠の大きさ (スロットの数) を持つ。`apply` は引数の数を見て、部分適用か、ちょうどか、余るかを決める。ネイティブのコードを混ぜるときは、ここに入口の種類を足す
- 定数は、`compile` が `Heap::with_control(control)` で作った作業用のヒープに不死の物体として作り、`freeze` で塊にする。塊のページは同じ `Control` の確保量に数える。実行のヒープは `attach` でその塊を受け付ける
- 塊の物体は、検査モードでも参照を数えない。そのため、文字列の定数を読む命令は `acquire_immortal` を呼ばず、語を写すだけにする
- `CodeBase` は実行中は読むだけで、`CodeBase<M>: Sync` を型の assert で固定する。`CodeBase` は `M` ごとに作るので、検査モードと速いモードを両方動かすテストは2回変換する。追記の API は、使う S11 で足す

## 命令とフレーム

### スロットとスタック

- 実行の状態は、ワーカーごとの `Ctx<M>` と、タスクごとの `Task { stack: Vec<Word>, pc, base, frame_size }` に分ける。VM は `run(code: &CodeBase<M>, ctx: &mut Ctx<M>, task: &mut Task)` で、安全点をまたいで `Task` の外に状態を持たない
- フレームのスロットはどれも1語である。`obj` と `tobj` の値は語のまま置く。`int` と `enum` は provenance を持たない生のビット列 (`Word::from_bits`) にし、`bits()` で読む。`unit` は語の値 1 (`Word::UNIT`) にする
- スタックを `Vec<u64>` にしないのは、ポインタを整数に戻すと provenance が失われ、Miri の strict provenance に反するためである
- 生のビット列の語は、即値やポインタに見えることがある (偶数の値はポインタの形をしている)。そのため、VM は語の形でなく、コード生成が知っている Repr で値を扱う。RC の命令と、即値かどうかの判定を、Repr が `obj` か `tobj` の値にだけ使う (下の「RC」と「switch」)
- 関数に入るときと、`ApplyRest` のフレームを積むときに、スタックを `base + frame_size` まで伸ばす。スタックは添字で指すので、`Vec` が伸びて場所が変わってもよい。スロットの読み書きは、境界を確かめる添字で行う。確かめない添字に替えるのは、計測で要ると分かったときだけにし、そのときは Miri のテストで覆う
- 深さはスタックの使っている語の数で、`Ctx::poll` に渡す

### フレーム

```
base - 2: 戻り先の命令の位置 (32 ビット) | 結果を書くスロット (16 ビット) | 呼び出し元の frame_size (16 ビット)
base - 1: 呼び出し元の base
base + 0 .. base + frame_size: スロット
```

- 見出しは2語で、関数の番号は持たない。呼ばれる側の base は、呼ぶ側の `base + frame_size + 2` である。`Task` は今のフレームの `frame_size` を持ち、関数に入るときに `FnEntry` から読む。戻るときは、見出しの1語目から呼び出し元の `frame_size` を戻すので、戻り先の命令の位置から関数を引き直さずに済む。見出しの1語目は生のビット列 (`Word::from_bits`) である
- いちばん下のフレームの戻り先は `Finish` である
- `ApplyRest` のフレームの形は、スロット 0 が結果、スロット 1 が残りの引数の数 n、スロット 2 から 2 + n - 1 が残りの引数で、`frame_size` は 2 + n である。残りの引数の参照は、このフレームが持つ

### 命令の形

- 命令は `Copy` の `enum Op` で、大きさが 8 バイトであることをコンパイル時に assert する。オペランドは次の3つの形のどれかに収める
  - 固定のスロット: `Move { dst, src }`、`AddInt { dst, a, b }` のように `u16` を3つまで持つ
  - スロットと即値: `LoadInt { dst: u16, value: i32 }`、`LoadConst { dst: u16, index: u32 }`、`Goto { target: u32 }`
  - スロットと表の添字: `Call { dst: u16, at: u32 }` のように、長さの変わるオペランドを `operands[at..]` に置く。関数の番号、行の番号、引数のスロットの並びは表の側にある
- 呼び出し、`apply`、`clause`、extern、`con`、`closure`、`prim` の引数に定数の atom (`Int`、`#N`、`&f`、`()`) があれば、命令の前に一時の変数へ読み込み、そのスロットを渡す。一時の変数もスロットの割り当てに含める。`i32` に収まらない `Int` の定数は `constants` に置き、`LoadConst` で読む
- 実行は、`match` で命令を分ける1つのループで、`M: Mode` について総称にする。Rust の再帰は使わない。`ApplyRest` と `Finish` の処理も、ループの中で命令として扱う
- 逆アセンブラは、`CodeBase` を関数ごとのテキストにする。テストのスナップショットと、誤りの調べに使う

### スロットの割り当て

- 関数ごとに、文の単位の生存から干渉グラフを作り、色を塗ってスロットを決める。入口のブロックの引数は、スロット 0 から n - 1 に固定する
- 干渉の規則は次のとおりである
  - 変数を定義する文 (呼び出しの結果、`let`、case と `unpack` のフィールド、一時の変数) は、その文の後で生きているすべての変数と干渉する。定義した変数が使われずに死んでいても同じである。使われない呼び出しの結果を `Ret` が書いても、生きている値を上書きしないためである
  - `switch` と `unpack` の scrutinee は、その case で書くフィールドのすべてと干渉する。フィールドを1つずつ読んで書く間に、scrutinee のスロットを上書きしないためである
- case と `unpack` のフィールドは、行き先で生きているものだけを読んで書く。死んでいるフィールドは読まない
- Repr ごとにスロットを分けない。どの値も1語なので、分けても得るものがないためである。命令の位置ごとの割り当ては静的に決まるので、後で安全点ごとの「生きていて所有しているスロット」の表を作ることもできる (下の「並列化への備え」)
- `jump` のブロック引数の並列な代入は、コンパイル時に `Move` の列へ直す。輪になる代入には、関数ごとに1つの作業用スロットを使う。ブロック引数と実引数に同じ色を付けやすくする合併は、移動の命令を減らすための工夫として、計測しながら入れる
- LIR の `saved` は読まない。呼ぶ側のスロットは呼び出しの間もスタックに残るためである

## 呼び出しと戻り

- **直接の呼び出し** `Call { dst, at }`: 呼ばれる側の base を `base + frame_size + 2` とし、引数を呼ばれる側のスロット 0.. へ写し、見出しを書いて、関数の先頭へ進む。命令の dispatch は1回である。引数の数は呼ばれる関数の引数の数と等しい (verifier が確かめている)
- **戻り** `Ret { src }`: 見出しを読み、呼ぶ側のフレームの結果を書くスロットへ値を書き、base と命令の位置を戻す
- **末尾呼び出し** `TailCall { at }`: 実引数を VM が使い回す作業用の領域へいったん読み、今の base のスロット 0.. に書いてから、呼ばれる関数の先頭へ進む。引数と今のスロットが重なりうるので、作業用の領域を通す。見出しはそのまま使う
- **自己末尾呼び出し**: 同じ関数への末尾呼び出しは、引数を書いた後、関数の先頭へのジャンプにする。このジャンプでも `Ctx::poll` を呼ぶ。バイトコードに後ろ向きの辺ができるので、呼ばないと `loop n = loop (n + 1)` が呼び出しも戻りも通らず、割り込み、上限、後の協調的なタスクの切り替えのどれも効かなくなるためである
- **`apply`**: 呼ばれる値は `tobj` である。即値なら関数の番号、物体ならクロージャで、関数を `scanned(w, 0)` で、捕まえた値を `scanned(w, 1..)` で読み、その数を `scanned_len(w) - 1` とする ([オブジェクトモデル](../../spec/object-model.md) の「クロージャ」)。捕まえた値を先に、渡した引数を後にして並べ、`FnEntry` の引数の数と比べる
  - クロージャの中身を取り出すときは、先に `meta` を読んで `lin` ビットを覚えておく。そのうえで、`is_last` なら値を読んでから `free_block` し、そうでなければ値を `dup` してから `decref` する
  - ちょうどの数なら、関数の先頭へ進む
  - 足りなければ、新しいクロージャを `alloc_data` で作り、`dst` に書く。`lin` ビットは元のクロージャのものを写し、元が即値なら立てない。捕まえた値と引数はどれも一様な位置の値 (`tobj`、`obj`、`unit`) なので、走査する語に入れてよい
  - 余れば、`ApplyRest` のフレームを積んで残りの引数を移してから、先頭の分の引数で関数に入る。関数が `ApplyRest` へ戻ると、スロット 0 の結果に残りの引数を適用する。この適用は `ApplyRest` のフレームの見出しを引き継ぐ末尾の適用で、引数を作業用の領域に通す
- **`clause`**: 呼ばれる値と、evidence を先頭にした引数を `apply` と同じに並べる。ただし引数の数はいつも入口の関数の引数の数と等しく、違えば内部の誤りにする。`clause` の引数は操作の ABI の Repr (生の `int` を含む) を持つので、部分適用でクロージャの走査する語に入れてはならないためである
- **末尾の位置の `apply` と `clause`**: 今のフレームの見出しを引き継ぎ、引数は作業用の領域を通す。足りなければ、作ったクロージャを戻りと同じに返す。余れば、`ApplyRest` のフレームが今のフレームの見出しを受け継ぐ
- **安全点**: 呼び出し (末尾呼び出しと `ApplyRest` の適用を含む)、戻り、自己末尾呼び出しのジャンプで `Ctx::poll(深さ)` を呼ぶ

## 命令ごとの実行

### 値と定数

| LIR | VM の動作 |
|---|---|
| `Int` の定数 | 生のビット列にする |
| `#N` | `enum` の位置では生の N、`tobj` の位置では即値 N |
| `&f` | 即値 (関数の番号) |
| `()` | 語の値 1 |
| `const` (文字列) | `constants` の語を写す |
| `box` | `int` は `alloc_int` (63 ビットに収まれば即値、収まらなければ `BigInt`)。`enum` は即値。オペランドが定数なら、コード生成の時点で即値か不死の `BigInt` にしておく |
| `unbox` | 即値なら値を取り出す。物体なら `unbox_int` で読む。ダミーは値 0 の `BigInt` なので、`int` でも `enum` でも誤りにならず 0 を返す |

### RC

- `dup x` と `decref x` は、`Heap::dup` と `Heap::decref` を呼ぶ。`drop a` も `decref` で実行する ([オブジェクトモデル](../../spec/object-model.md) の「核の操作」)
- RC の命令は、Repr が `obj` か `tobj` の変数にだけ出す。`drop` の atom が定数か、Repr が `int`、`enum`、`unit` の変数なら、コード生成は何も出さない。verifier は `drop` に任意の atom を許し、生のビット列はポインタに見えることがあるためである
- フィールドのない `#N` の行き先では、scrutinee は即値と分かる (ロードマップの S10 で決めたこと)。その行き先が `switch` のその case だけから入るブロックなら、コード生成はそのブロックの中の scrutinee の `decref` を出さない。IR の規則にはしない。IR の規則にすると、verifier に「即値と分かっている」という3つ目の状態が要るためである
- `release x L #t(..)` は、コード生成の時点で形が分かっているので、オブジェクトモデルの展開をそのまま使う

  ```
  is_last(x)
    真: 残さない走査する語を decref → free_block(x)
    偽: 残す走査する語を dup → decref x
  ```

  残す変数は、前の `switch` か `unpack` ですでにスロットにある。そのため `release` はスロットに書かず、参照の数だけを動かす。検査モードでは、展開の前に、語がポインタで、種類が `Data` で、`meta` の tag と走査する語の数が名指したものであることを確かめ、違えば内部の誤りにする。一般の版の `Heap::release` が返す `WrongLayout` の見張りを残すためである。共有の物体の `lin` ビットの見張り (`LinShared`) は、展開の中の `decref` が受け持つ

### データとクロージャ

- `con L #t(a..)` は、物理的な形の関数で宣言の位置を物理的な位置へ写す。そのうえで `alloc_data(tag, 走査する語の数, 生の語の数, lin)` で作り、走査する語を `set_field`、生の語を `set_raw` で書く。`lin` は、束縛する変数の印が `lin` なら真である ([オブジェクトモデル](../../spec/object-model.md) の「`lin` ビット」)
- 走査する語が 255 個以上のデータでは、ペイロードの先頭に数の語がある。`field`、`set_field`、`raw`、`set_raw` の位置はこの数の語を含む物理的な位置なので、VM はその物体の位置を、コード生成の時点で1つずらしておく
- `closure f(a..)` は、`alloc_data(0, 1 + 引数の数, 0, lin)` で作り、最初の走査する語に即値 `&f`、続く語に引数を書く。`lin` の決め方は `con` と同じである。走査する語が 255 個以上なら、`con` と同じく位置をずらす

### switch

- タグの `switch` は、scrutinee の Repr で読み方を分ける。語の形では分けない。生の `enum` の値は即値にもポインタにも見えるためである
  - `enum`: 生の値をタグにする
  - `obj`: `meta` の tag をタグにする
  - `tobj`: 即値なら `imm_value` を、物体なら `meta` の tag をタグにする
  - 定数の atom (`#N`、`&f`) は、コード生成の時点で行き先を決める
- フィールドは `field` と `raw` で物理的な位置から読み、スロットに書く (行き先で生きているものだけ)。読むだけなので、参照の数は変えない
- `Int` の `switch` は生の値を比べる。`String` の `switch` は、scrutinee と定数を両方 `Heap::string` で借りて、バイト列を比べる。どちらも手放さない
- 行き先の選び方は、タグが密なら飛び先の表、そうでなければ比較の列にする。比較と分岐を1つにした命令を足すかは、試作で命令の数を測って決める (S10 の論点)
- `unpack` は、行き先が1つの `switch` と同じ読み方をする。検査モードでは、語がポインタで、種類が `Data` で、tag と走査する語の数が名指したものであることを確かめ、違えば内部の誤りにする (CEK の `unpack` の見張りと同じ)

### 基本操作と extern

- `prim` は、`Ctx` の同じ名前のメソッドを呼ぶ。`dummy` だけは `Heap::dummy` である。即値 (エフェクトの番号、操作の番号) と `ev_new` の操作の数は、コード生成の時点で `operands` に書く。`evv_mask` のエフェクトの並びは `effect_lists` に置く
- 算術と比較の extern 13個 (`+ - * / % negate`、`Int` の比較6つと `compare`) と、`Bool` の `==` と `!=` は、それぞれ専用の命令にする。`eml_rt::externs` の `#[inline]` の関数を、命令の中に展開して呼ぶ
- ほかの extern (文字列、表示、`println`、`Fs`) は `Extern { dst, at }` の1つの命令にし、行の番号の `match` で `Ctx` のメソッドを呼ぶ
- VM は `Ctx` の基本操作の合間に、`Ctx` が持つ語とそこからたどれる物体に触れない (`heap_mut()` の前提)
- `Bool`、`Ordering`、組のタグの定数が `eml_rt::externs` と `eml_lir` で同じであることのテストを、`eml_vm` にも置く。VM の `Bool` と `compare` の命令がこれに頼るためである。`eml_interp` の同じテストは S10b で消す

## 誤り、止めること、終わり

- 実行時エラー `VmError` は、誤りの種類、関数の名前、省略できる位置を持つ。表示の形は今の CEK と同じで、位置があれば `{fault}\n  at path:line:column`、なければ ``{fault} in `function` `` である
- 関数の名前は、命令の位置から `FnEntry` の範囲を二分探索して引く。`Finish` と `ApplyRest` はどの関数にも属さないので、そこで起きた誤りには、最後に戻った関数の名前を付ける。VM は戻りのたびに戻った関数の命令の位置を `Task` に覚える。CEK も、最後に動いていた関数の名前を付けている
- 位置は `locations` から命令の位置で引く。表に載せるのは、位置を持つ extern の呼び出しから作った命令である。専用の算術と比較の命令も含む。今の `run-fail` の UI テストの多くは `/` と `+` の誤りの位置を表示している
- `Arith`、`Output`、`Io`、`NotUtf8` の文言は `eml_rt` のものを使う。今の CEK と1文字も違わないことは、S9b-3 の期待値の表で確かめてある。`Heap(_)` の文言は `eml_rt::HeapError` のものになる。この違いを UI テストの期待値として扱うのは S10b である
- 安全点の `Ctx::poll` が返す `Stop` と extern の `Fault::Stopped` は、同じ「止めた」の誤りにし、`Stop` の文言で表示する。`Fs.read_all` の `Fault::Stopped` は extern の誤りなので位置を付け、安全点の `Stop` には付けない
- 実行時エラーと止めたときは、誤りを返す前に `Ctx::flush` を呼ぶ。`> out 2>&1` のときに出力と誤りの順を保つためである
- `Finish` に着いたら、次の順に処理する
  1. 入口の関数の結果を手放す。Repr が `obj` か `tobj` のときだけ `decref` する。CEK のいちばん下のフレームも、結果を手放してから終わる
  2. flush する。誤りなら、位置なしで返す
  3. `Ctx::check_finished` で、`evv` が空で yield の状態がなしであることを確かめる。モードによらず確かめ、満たさなければ内部の誤りにする
  4. 検査モードでは、`Heap::check_invariants` と `Heap::leaks` を確かめる。リークがあれば、種類の名前ごとの数を持つ誤りにする

## 並列化への備え

VM の並列化とスレッドをまたぐキューを後から入れられるかを、設計のときに調べた。結論は、この形の VM はどちらも妨げないということである。

- 実行の状態は、ワーカーごとの `Ctx` と、タスクごとの `Task` に分かれる (上の「スロットとスタック」)。`CodeBase` は読むだけなので、全 worker で共有しても競合しない
- evidence passing により、`perform` で止まったタスクの続きは、ヒープ上の継続のクロージャになる。このタスクはスタックを持たず、別の worker へ移すことはクロージャの語を1つ渡すことと同じである。まだ始まっていないタスク (`spawn` に渡す閉包、`par` の右の子) も同じである
- 一方、安全点で切り替えたタスク (S13 で採りうる `par` の a1 のスケジューラ) と、`join` で子を待つ親は、スタックの途中で止まっているので、`Task` ごとスタックを持ち続ける。こうしたタスクの数は `par` の入れ子の深さで抑えられる

S10a では次の4つを守る。

1. 自己末尾呼び出しのジャンプも安全点にする (上の「呼び出しと戻り」)
2. スレッドに局所的な変数を置かない。`CodeBase<M>: Sync` と `Task: Send` を型の assert で固定する ([マルチコア対応の設計](../../future/multicore.md) の「VM の並列化の備え」の制約1と2)
3. 呼び出しのスタックは `Task` が持つデータにし、Rust の再帰を使わない。`ApplyRest` と `Finish` もループの中の命令である (制約5)
4. VM は語をほかのスレッドに渡す経路を持たない。公開は、`eml_rt` の fork、join、キューへの push の中で `share` を通す道だけにする。`Word` は `Send + Sync` なので型では守れず、文書の決まりにする。破った場合は、検査モードの所有者の検査が見つける

安全点ごとの「生きていて所有しているスロット」の表は、今は作らない。a2-cancel で走っている子を安全点で取り消すときの後始末に使えるが、スロットの割り当てが静的なので、後から生存解析で作れる。

スレッドをまたぐキューのうち、ランタイムのキュー (work stealing の deque、スケジューラの実行待ち) は、印を付けたクロージャの語を持つ Rust のコードとして `eml_rt` に書ける。言語のキュー (channel など) には、今の `eml_rt` で足りないものがある。S10a では埋めず、[マルチコア対応の設計](../../future/multicore.md) の「未決の論点」に書き足す。

- 共有の物体に書き込む操作がない。`set_field` は、ほかのスレッドが読めない物体にしか使えない。Acquire/Release 付きの atomic なフィールドの読み書きと CAS を核の操作に足し、push が値に自動で印を付ける形にする。今の証明の前提 (信頼の一覧の T0) を並行の証明に置き換える作業も、VM の並列化のときに要る
- 別のスレッドからの解放に対応した確保器がない (すでに論点にある)
- キューの中身の置き場所。atomic なフィールドの操作があれば、channel は `Data` の物体の連なりとして書ける。`Foreign` の Rust の値に語を入れる形は採れない。`Foreign` は走査する語を持たないので、中の語は `share`、解放の連鎖、リークの検査から見えず、破棄処理はヒープを受け取らないので中の値を `decref` できないためである
- Rust の側のキュー (deque、実行待ち) が持つ語は、検査モードのリークの数え方と、S11 の根からの走査による回復から見えない。こうした構造を根として登録する仕組みが要る
- channel の受け取りで待つこと (待ちと起こし) の仕組み

## 検証とテスト

### UI テストを2つのエンジンで流す

- `crates/eml_cli/tests/ui.rs` の `run` と `run-fail` で、CEK で実行した後に、同じプログラムを VM の検査モードで実行する。それが通ったときだけ、速いモードでも実行する。速いモードは前提を確かめないので、VM の誤りがあると未定義の動作になり、1つのテストの失敗が glob のテスト全体を壊しうるためである
- 3回の実行の標準出力と誤りの文言は、どれも今あるスナップショットと一致しなければならない。スナップショットは CEK と共有し、VM 用のものは作らない
- 検査モードの VM の `RunStats` のうち、`evidence_steps`、`yields`、`yield_frames`、`string_bytes_copied`、`boxes`、`unboxes` は、CEK の値と等しいことを確かめる。どれも同じ LIR の上で同じ定義を持つためである
- VM には、`StdHost::new` にメモリの書き込み先、そのテストのディレクトリの `file_root`、`Buffering::Block` を渡して出力を捕まえる。`run-fail/files` のテストは `file_root` に頼る
- 速いモードも流すのは、検査モードでしか通らない道と速い道とで、結果が同じことを確かめるためである。検査モードの誤り (リーク、解放の後の使用、`lin` の物体の `dup`) は、検査モードの実行が見つける

### `eml_vm` のテスト

- コード生成のスナップショット: 手書きの LIR (`eml_lir::parse`) を `CodeBase` に変換し、逆アセンブラの出力をインラインスナップショットで固定する。確かめるのは、スロットの割り当て (使われない定義、scrutinee とフィールドの干渉を含む)、入口の引数の固定、並列な代入の展開 (輪を含む)、定数の atom の読み込み、switch の表と Repr ごとの読み方、`#N` の行き先の `decref` を出さないこと、`release` の展開、非 RC の値の `drop` に何も出さないこと、走査する語が 255 個以上の物体の位置のずらし方である
- 実行のテスト: 手書きの LIR を両方のモードで実行する
  - 部分適用、ちょうどの適用、余った引数の `ApplyRest`、末尾の位置のそれぞれ、`clause` の呼び出し
  - 末尾呼び出しと自己末尾呼び出しで、深さが反復の数によらないこと
  - 自己末尾呼び出しのループが、`Control::interrupt()` で止まること
  - 走査する語が 255 個以上のクロージャとデータ、63 ビットに収まらない `box`、`i32` に収まらない `Int` の定数、文字列の `switch`、`Bool` の `if` (生の `enum` の値 0 と 1 と、2 以上のタグ)
  - `release` の両方の枝 (最後の参照か、そうでないか)
  - `lin` の印の `con` と `closure` が `lin` ビットを立てること
  - 物体を返す入口の関数が、検査モードでリークにならないこと
  - 実行時エラーの位置と関数の名前 (`Finish` と `ApplyRest` で起きた誤りを含む)、エラーの前の flush で出力の順が保たれること
- `bench/` の VM の `RunStats` は、`crates/eml_vm/tests/bench.rs` で新しいスナップショットとして固定する。`crates/eml_interp/tests/bench.rs` と同じく、`bench/` のファイルの一覧とテストのプログラムの一覧が一致することも確かめる
- 型の assert: `CodeBase<M>: Sync` と `Task: Send` を、`crates/eml_cli/tests/api.rs` と同じ形で固定する
- Miri: VM は検証していないコードから `eml_rt` の `unsafe fn` を呼ぶ。そのため、`eml_vm` の `miri` の module の小さい実行のテストを、`eml_rt` と同じ2つの設定 (strict provenance と、それに Tree Borrows を足したもの) で流す (`cargo miri test -p eml_vm miri::`)。確かめるのは VM が核の操作の前提を守っていることで、信頼の一覧の確かめ (`eml_rt` の `trusted`) とは目的が違う。テストはメモリの Host だけを使い、実際のファイルを開かない。UI テストは Miri では流さない。[テスト戦略](../../implementation/testing.md) の「ほかの crate は Miri で流さない」は、この例外を足して直す
- `crates/eml_cli/tests/cli.rs` に、`--vm` の成功と実行時エラーの終了コードの2つを足す

### `RunStats`

VM の `RunStats` は、`eml_rt` の数え方に従い、検査モードだけで数える。

| 項目 | VM での出どころ |
|---|---|
| `evidence_steps`、`yields`、`yield_frames`、`string_bytes_copied` | `CtxStats` (ロードマップで決めたとおり) |
| `rc_increments`、`rc_decrements` | `Heap` の `Stats` |
| `peak_objects` | `Heap` の `Stats` の `peak_live` |
| `boxes`、`unboxes` | VM が実行した `box` と `unbox` の数 |

`rc_*` と `peak_objects` は、次の理由で CEK と違う値になる。S10a ではこの差を [計測の基準](../../implementation/benchmarks.md) に書き、S10b でスナップショットを替えるときの理由にする。

- CEK はフレームをヒープの物体にしているので、フレームの分の RC と物体の数を数える。VM のフレームはスタックにあるので、この分を数えない
- CEK は文字列のリテラルの参照を数え、リテラルを物体の数に含める。VM は凍結した領域の物体を数えない
- `eml_rt` の `peak_live` は、ヒープごとのダミーの物体を含む
- `eml_rt` の `free_block` と `release` は、持ち主を空けるときに `rc_decrements` を1つ足す。CEK は解放そのものを数えない

### 計測

- `bench/run.sh` が両方のエンジンの表を出すようにし、同じコミットで比べる
- 完了の条件として、`empty` を除く `bench/` のどのプログラムでも、release ビルドの VM (速いモード) の実行の分 (そのプログラムの命令の数から `empty` の命令の数を引いた値) が、CEK の実行の分より少ないことを求める。`empty` はフロントエンドと起動の費用で、VM はそこにコード生成と凍結の費用を足す。`empty` の値はそのまま記録し、CEK との差を説明する。結果は [計測の基準](../../implementation/benchmarks.md) の「S10a (VM)」に記録する
- 比較と分岐を1つにした命令の有無と、release のプロファイルの `codegen-units` は、この計測の中で決める

## S10b に残すこと

- `eml run` を VM に切り替え、`--vm` を消す
- SIGINT のハンドラ (`ctrlc` で入れ、2回目の Ctrl-C では終了コード 130 で終わる)、上限の既定の値、`RunConfig` での指定
- 期待値の変更: `bench.rs` の `RunStats` のスナップショットを VM のものに替えること、ヒープの誤りの文言の違い、今の `Fault::Internal` がなくなること
- [LIR とインタプリタ](../../spec/lir.md) の「実行時エラー」の書き直し。解放の後の使用と `a Lin object is shared` は、検査モード (`--debug-heap`) でだけ見つかるようになる ([オブジェクトモデル](../../spec/object-model.md) の「受け入れる制約」)。S10a の `--vm` も、`--debug-heap` なしではすでにそう動く
- CEK (`eml_interp` の機械)、`eml_runtime`、LIR の `saved` と Perceus でそれを埋める処理の削除。`rt_externs` のテストと `eml_interp` のタグの定数のテストを消すこと、`scaling` などの CEK のテストを VM へ移すこと、`eml_test_support` の実行の関数を VM に替えること、`eml_cli` が公開する `RunStats` と誤りの型を `eml_vm` のものに替えること
- CEK を消す直前に、`bench/` で CEK と VM の差をもう一度記録すること
- spec の書き直し (`runtime.md`、`lir.md` のインタプリタの節、`core-ir.md`、`multicore.md`) と、段の終わりの `status.md` と `architecture.md`
