# eml マルチコア対応の設計 spec (将来の設計)

- 日付: 2026-10-03
- 状態: レビュー待ち。将来の設計であり、マイルストーン1 では実装しない。マイルストーン1 に入れる予防的な決定は §9 にまとめ、[言語設計 spec](2026-10-03-eml-language-design.md) に反映済み
- 関連: [2026-10-03-eml-language-design.md](2026-10-03-eml-language-design.md)

## 1. 目的と範囲

### 目的

- インタプリタ自体と将来の LLVM バックエンドの両方で、複数のコアを使って実行できるようにする
- 「線形型 × 代数的エフェクト」の性質 (`Lin` による移動、row によるエフェクトの制限) を、並列の安全性の保証にそのまま使う

### 対象

- **決定的な並列計算** (データ並列が主眼): `par`、並列 map / reduce、分割統治
- **並行処理**: 軽量スレッド、非同期 I/O

### 対象外

- 共有の可変状態を伴うマルチスレッド。Rust の `Send` / `Sync` に当たる Kind の次元は導入しない

## 2. 確定した設計判断

| # | 領域 | 決定 |
|---|---|---|
| 1 | 層の構成 | 実行系の核は、並列実行、スレッド間で安全な RC、移動できる `once` 継続、atomic プリミティブ、fork / join の節点を提供する。決定的な並列計算と並行処理は、その上のライブラリとして作る (§3) |
| 2 | 可変状態 | 可変状態はエフェクトの中でだけ扱う。並列の安全性は row の制限で保証する (§4) |
| 3 | `Ref` と `Heap` | 値 `Ref h a` (`Unr`) と組み込みのエフェクト `Heap h` を持ち、`IO` とは分離する。`run_heap` は rank-2 の組み込みとして特別扱いし、ユーザーには rank-2 を書かせない。multi-shot で再開したときの状態は共有する (§4) |
| 4 | `Ref` の中身 | `Ref` には `Unr` の値だけを入れる。`Lin` を `Unr` に変える汎用の操作は作らない (§4) |
| 5 | RC | 共有の印方式 (Koka、Lean 4 と同じ)。符号付きの `AtomicI32` で、正なら局所、負なら共有。局所的なオブジェクトには Relaxed の load / store を使う (§5) |
| 6 | ランタイム | `eml_runtime` を切り出す。継続のフレームと環境もランタイムのオブジェクトにする。インタプリタの値には `Rc` と `RefCell` を使わない。`run` の出力先は `Send + Sync` にする。`RunConfig` に `threads` と `schedule_seed` を持たせる (§8) |
| 7 | マイルストーン1 のヒープ | インデックス方式のアリーナで作る。API とヘッダの意味はマルチコア版と同じものに固定し、マルチコア化では `eml_runtime` の内部だけを差し替える (§8) |
| 8 | 並列 API | 目標は a4 (§6)。a1 → a2-wait → a2-cancel → a4 と段階的に広げる。row の Kind の束は `Never ≤ Tail ≤ Once ≤ Multi`。並行処理は閉じた row の `spawn` にする |
| 9 | 不変条件 | スレッドをまたいで値や制御を渡すプリミティブは、すべて閉じた row か `Row<Tail>` の制約を持つ (§7) |
| 10 | 共有の印付け | 実行系のプリミティブが、送り手のスレッドで、公開する前に自動的に行う (§5) |
| 11 | スレッドに縛られたリソース | 組み込みのリソースは、スレッドに縛られないものに限る。スレッドに縛られたものは、専用のスレッドの handler に閉じ込める (§7) |

## 3. 層の構成

```
ライブラリ:     並列計算 (par / par_map / par_try_map)    並行処理 (Async の handler、spawn、channel)
               ────────────────────────────────────────────────────────────
実行系の核:     並列実行 (worker の起動と join)
               スレッド間で安全な RC (共有の印方式)
               移動できる once 継続
               atomic / CAS のプリミティブ
               fork / join の節点 (perform が認識する。§6)
               協調的な中断 (a2-cancel 以降)
型システム:     row の Kind による制限 + Lin による移動
```

- work stealing などのスケジューラは、エフェクトと `once` の継続を使ってライブラリとして書く。タスクの中断は perform、別のコアでの再開は継続の移動で表す
- 先行例: OCaml 5 は、実行系が `Domain` とエフェクトだけを提供し、並列の task pool (Domainslib) と並行 I/O (Eio) をライブラリとして作っている。Haskell の monad-par は、決定的な並列計算をライブラリとして作っている

## 4. 可変状態: `Heap h` と `Ref h a`

### API

```
new      : a -> <Heap h> Ref h a              (a : Type<Unr>)
get      : Ref h a -> <Heap h> a
set      : Ref h a -> a -> <Heap h> Unit
run_heap : (forall h. Unit -> <Heap h | e> a) -> <e> a
```

- `Ref h a` は `Unr` の値で、データ構造に入れたり、関数に渡したりできる。読み書きの権限は row の `Heap h` が管理する
- `run_heap` は組み込みとして型検査器で特別扱いする。rank-2 の型をユーザーに書かせることはしない。今の型推論の方針 (rank-1 + bidirectional) は変えない
- `new` は `a : Type<Unr>` を要求する。シグネチャの型変数で使った場合は、言語設計 spec §4 と同じ仕組みで `Unr` の制約が加わる
- 実装は実際の可変メモリにする。`Heap h` は組み込みで、実際のメモリなので、multi-shot で再開したときの状態は**共有**される (Koka と同じ意味)

### `IO` と分離する理由

- **局所的な可変状態を外から消せる**: 内部で `run_heap` を使う関数の型は純粋なままになる。並列タスクに渡せる
- **型が決定性を区別する**: `<>` は純粋、`<Heap h>` は状態があるが決定的、`<IO>` は外の世界に触れて非決定的
- **読み書きに同期が要らない**: §7 の不変条件により、`Heap h` の操作は `run_heap` を実行したスレッドでしか実行されない。`get` / `set` は atomic でない普通のロードとストアで済む
- **領域ごとに独立している**: 並列タスクがそれぞれ内部で `run_heap` を使っても互いに干渉しない

並行タスクの間で共有する可変状態 (例えば非同期のタスク同士で共有するカウンタ) は、`Heap` では書けない。channel や atomic な参照などの並行処理用のプリミティブを、`IO` か `Async` の側に用意して扱う (§10)。

### `Lin` の値を `Ref` に入れない場合の書き方

| やりたいこと | 書き方 |
|---|---|
| `Lin` の値を書き換えたい | `Ref` を使わず、値を線形に受け渡す。一意なので、Perceus の reuse でその場の書き換えにコンパイルできる (例: `Lin` な配列の `write : Array a -> Int -> a -> Array a`) |
| 一つのリソースを色々な場所から使いたい | リソースを handler に持たせる。handler が所有して操作を提供し、`return` 節で後始末する |
| 一意性だけが理由の `Lin` (後始末のない可変バッファなど) を、使い終わったら共有したい | 型ごとに `freeze` を用意する (例: `freeze : MutArray a -> Array a`)。後始末を持つ型には定義しない |

- 汎用の「`Lin` → `Unr`」の変換は作らない。`File` などが複製できてしまい、二重の後始末を防げなくなるため。また、RC が 0 になったときに後始末する方式は、「通常の制御フローでは暗黙の後始末を行わない」という言語設計 spec の決定に反する
- `Lin` な配列を重ならない部分に分けて、別々のタスクに移動して並列に書き換え、最後に結合する (Rust の `split_at_mut` に相当)。この処理はエフェクトを使わない純粋な計算なので、a1 の `par` の範囲で書ける。速く動かすには Perceus の reuse analysis が前提になる

## 5. スレッドをまたぐ RC

### オブジェクトがスレッドをまたぐ場面

1. 並列タスクや `spawn` に渡すクロージャが捕まえた値
2. channel などで送る値
3. 別のコアで再開する継続のフレームが参照している値

`Lin` の値は RC を持たず、移動するだけである。ただし、`Lin` な構造の中にある `Unr` のフィールドはスレッドをまたぐ。

### 共有の印方式

```rust
// 局所 (正の値): Relaxed の load/store は、x86 でも ARM でも普通の mov になる
let n = rc.load(Relaxed);
if n > 0 { rc.store(n + 1, Relaxed) }
// 共有 (負の値): 本物の atomic 操作
else     { rc.fetch_sub(1, AcqRel); }
```

- オブジェクトは最初は局所的で、RC の操作は普通の加減算と同じ速さになる。RC 操作ごとに印を確認する分岐が1つ増える
- 上の3つの場面で、渡す値から到達できるオブジェクトをたどって共有の印を付ける。すでに印のあるオブジェクトでたどりを止めるので、各オブジェクトがたどられるのは高々1回である
- **印付けは送り手のスレッドが、公開する前に行う**。受け手が印を付けると、送り手がまだ同じオブジェクトに対して atomic でない RC 操作をしている可能性があり、data race になるため
- 印付けは、§7 の不変条件に挙げる実行系のプリミティブの中で自動的に行う。ライブラリの作者が印付けを忘れることはない
- 共有したオブジェクトは、別のスレッドで RC が 0 になって解放されることがある。ネイティブのランタイムのアロケータは、別のスレッドからの解放に対応している必要がある (Koka は mimalloc を使っている)
- Perceus の reuse は「RC が 1 なら再利用する」判定をする。共有したオブジェクトでは、この判定も atomic な読み出しになる

### 却下した案

- **常に atomic にする (Swift、Rust の `Arc`)**: シングルスレッドのプログラムでも、すべての `dup` / `decref` が atomic 命令になる。インタプリタではもともと遅い実行にさらに上乗せされる
- **Biased RC**: 印付けのたどりは不要になるが、ヘッダに所有するスレッドの ID とカウンタ2つが必要で、実装がかなり複雑になる
- **型で区別する**: Kind に共有の次元が必要になる。決定2に反する

## 6. 並列と並行の API

### 操作の種類と row の Kind

```
操作の種類:  never < tail < once < multi
row の Kind: Row<s>,  s ∈ { Never ≤ Tail ≤ Once ≤ Multi }
  Never : never の操作だけを含む row
  Tail  : さらに tail の操作を含んでよい
  Once  : さらに once の操作を含んでよい
  Multi : さらに multi の操作を含んでよい
```

- **`tail` の操作**: handler の節に `k` がなく、節の値がそのまま操作の結果になる (すぐに再開する操作)。Koka の `fun` 操作に当たる。キーワードは仮で、§10 で決める
  ```
  effect Log {
    tail log : String -> Unit,
  }
  ```
- 組み込みの `IO` の操作は `Tail` に分類する
- 組み込みの `Heap h` の操作は `Tail` に含めない (並列タスクの row から除外するため。決定3の「同期なし」を保つ)
- `tail` の操作は、並列と関係なく、継続を取り出さない直接の呼び出しにコンパイルできる (Koka や evidence passing の主要な最適化)
- マイルストーン1 では、内部の Kind の束だけを4要素で用意し、`IO` を `Tail` に分類する。表面の構文の `tail` は a4 の段階で入れる

### 一般の handler を並列と組み合わせられない理由

言語設計 spec §7 の `run_state` の `get () k => fn st { (resume k st) st }` のように、`once` / `multi` の handler は状態を継続の構造の中に持つ。二つの子タスクがこうした操作を同時に perform すると、どちらの節の `resume` に計算の続きを返すかが決まらない。そのため、並列タスクから外に出る操作は `never` と `tail` に限る。

### `par` の段階

| 段階 | 型 | エフェクトの意味 | 必要なもの |
|---|---|---|---|
| a1 | `par : (Unit -> <> a) -> (Unit -> <> b) -> (a, b)` | なし | spawn / join |
| a2-wait | `par : (Unit -> <e> a) -> (Unit -> <e> b) -> <e> (a, b)`、`e : Row<Never>` | 全員の完了を待ってから、一番左の子の例外を親で投げ直す。決定的 | Kind の束、fork / join の節点、例外の値をスレッド間で渡す仕組み、実行時に記述子から行う drop |
| a2-cancel | a2-wait と同じ | 例外が起きたら兄弟の子を中断する | 協調的な中断と、中断した子の `Lin` の後始末 |
| a4 | `par : (Unit -> <e> a) -> (Unit -> <e> b) -> <e> (a, b)`、`e : Row<Tail>` | インターリーブ。`tail` の操作は任意の順序で起き、`never` は最初に起きたものが勝つ | `tail` の操作、子のスレッドでの節の実行、`par` ごとのロック |

- どの段階でも、`par` が受け付けるプログラムが増える方向の変更である。後の段階に進んでも既存のコードは壊れない
- **row が空なら決定的**という性質は、どの段階でも型の上で見える
- a2-wait は、左の子が例外を投げて右の子が停止しない場合、逐次実行なら例外で終わるはずのプログラムが止まらない。a2-cancel で解消する
- a2-wait で捨てる側の子の結果が `Lin` の場合、`par` は型について多相なので、実行時にヘッダの記述子 (§8) から破棄処理を引いて drop する

### a4 の詳細

- 子タスクから外の handler に抜ける `tail` の操作は、`par` ごとのロックで直列化し、節を子のスレッドで実行する。節の中で `Heap h` を使っても、ロックが happens-before の関係を作るので data race は起きない (§7 の不変条件の唯一の例外)
- `par` が入れ子のとき、ロックは内側から外側の順に取る。順序が固定されているのでデッドロックしない
- `never` の操作が `par` から抜けたら、兄弟の子を協調的に中断する。中断した子が捕まえている `Lin` の値は、`drop k` と同じ後始末の情報で解放する
- 協調的な中断は、安全な地点 (perform、メモリの確保、ループの先頭など) で中断の印を確認して行う。インタプリタでは N ステップごとに確認する
- `par` の節点を perform が認識する必要があるため、`par` 自体は実行系の核のプリミティブ (fork / join の節点) の上に作る。スケジューラはライブラリのままである

### データ並列での使い勝手

- 並列 map / filter / reduce、分割統治、`run_heap` を内部で使うアルゴリズム、分割できる純粋な乱数生成器を使う計算は、a1 で書ける
- エラー処理は a1 では `Result` で返す。「どれか1つが `Err` を返したら残りを打ち切る」処理はスケジューラ側でできるので、`par_try_map : (a -> <> Result e b) -> Array a -> Result e (Array b)` のような関数をライブラリで用意する
- 子タスクの中のデバッグ出力は、a4 で `IO` が `Tail` に入ることで可能になる。row に現れない `trace` のような抜け道は用意しない

### 並行処理

```
spawn         : (Unit -> <IO, Async> Unit) -> <Async> Unit
run_scheduler : (Unit -> <Async, IO> a) -> <IO> a
```

- もともと非決定的なので、子タスクの row を閉じて `IO` を許す
- `IO` は各 worker の最下部にある組み込みの handler が処理する
- ユーザー定義のエフェクトは、子タスクの中で handle し終えている必要がある (OCaml 5 の Eio と同じ扱い)
- `Heap h` は閉じた row によって除外される

## 7. 継続の移動と不変条件

### 不変条件

> スレッドをまたいで値や制御を渡す実行系のプリミティブ (spawn、`par` の fork、channel、スケジューラのキュー) は、すべて閉じた row か `Row<Tail>` の Kind 制約を持つ。したがって、`Heap h` の操作は `run_heap` を実行したスレッドでしか実行されない。唯一の例外は、a4 の `par` のロックの下で `tail` の節が `Heap h` を使う場合で、このときはロックが同期を保証する。

新しいプリミティブを追加するときは、この不変条件を満たすことを確認する。

### `once` の継続の移動

- 非同期のスケジューラでは、`await` したタスクの継続 `k` (`once`、`Lin`) を handler がキューに入れ、別の worker が `resume` する
- `k` の続きに `Heap h` の操作があれば、`resume k v` の row (handle 式の外側の row) に `Heap h` が現れる。キューや `run_scheduler` の型は閉じた row なので、そのような `k` はキューに入れられない (型エラー)
- 移動するときは、送り手が継続のフレームから到達できるオブジェクトに共有の印を付ける (§5)。一度移動した継続のフレームはすでに印が付いているので、次に移動するときは、その後に積んだフレームだけをたどればよい
- work stealing のキューは常に盗まれ得るので、キューに入れた時点で印を付ける。移動しない継続も atomic な RC になるという代償がある。印付けを実際に移動するものだけに限る private deque 方式 (Acar らの方式) は、将来の最適化とする (§10)

### `multi` の継続の並列な再開

```
choose () k => par (fn () { resume k true }) (fn () { resume k false })
```

- 言語設計 spec §4 の規則により、`multi` の操作をまたいで `Lin` の値は生きていない。`k` が捕まえているのは `Unr` の値だけなので、共有しても安全である
- `k` の続きのエフェクトは、上のクロージャの row として `par` の制約で検査される。新しい仕組みは要らない

### スレッドに縛られたリソース

- 組み込みのリソースは、どのスレッドで後始末してもよいものに限る (現状の `File` はこれを満たす)
- スレッドに縛られたリソース (GUI のハンドル、スレッドに局所的なライブラリの状態など) が必要になったら、専用のスレッドの handler に閉じ込める (§4 の「リソースを handler に持たせる」方式)。Kind に共有の次元は足さない

## 8. マルチコアのインタプリタ

### 構成

```
           Arc<Program>  (Core IR。読み取り専用で全スレッドが共有する)
                │
   ┌────────────┼────────────┐
 worker 0    worker 1    worker N    各 OS スレッドが自分の CEK 機械を持つ
 (C, E, K)   (C, E, K)   (C, E, K)   K の最下部に組み込みの IO handler
   └────────────┼────────────┘
          eml_runtime                オブジェクトのモデル、RC、共有の印、
                                     アロケータ、並列実行のプリミティブ
```

### `eml_runtime`

- オブジェクトのヘッダ、確保、`dup` / `decref`、フィールドの読み出し、一意かどうかの判定、共有の印付け (`mark_shared`)、`debug_heap` の検査を、インタプリタから分離した crate にする
- ヘッダは、符号付きの RC と、記述子 (フィールドのレイアウトと `Lin` の破棄処理) への参照を持つ
- 継続のフレームと環境も、同じ RC と共有の印で管理するランタイムのオブジェクトにする。フレームはイミュータブルなので、継続を別のスレッドに移すのは「印を付けて渡す」だけで済む
- 将来の LLVM バックエンドも、このランタイムを C ABI でリンクして使う。インタプリタとネイティブでオブジェクトのモデルが一致するので、並列化のバグをインタプリタで再現しやすい

### ヒープの実装の段階

- **マイルストーン1**: インデックス方式のアリーナと世代番号。解放済みアクセスの検出がほぼ無料で、`unsafe` が要らない。シングルスレッドで、RC は常に正 (局所)
- **マルチコア化**: `eml_runtime` の内部だけを差し替える。候補は、スレッドごとのアリーナにして (スレッド ID, インデックス) で指す方式か、ポインタ方式。どちらにするかはその段階で決める

### 規約

- インタプリタの値とフレームに `Rc` と `RefCell` を使わない。CEK 機械の状態は `Send` にする
- 各段階は「グローバルな可変状態を持たない純粋な関数」という言語設計 spec の既存の規律を守る

### 実行の API

- `run` の出力先は `Send + Sync` な共有の出力先の型にする。複数の worker が `println` するため
- `RunConfig` に `threads` (worker の数) と `schedule_seed` (スケジュールのシード) を足す

### テスト

- 本物のマルチコアで動かすと出力の順序が変わり、UI テストのスナップショットが安定しない。UI テストは `threads = 1` か、シードを固定した決定的なシミュレーションで実行する
- `debug_heap` を拡張し、共有の印のないオブジェクトを所有者でないスレッドから触ったら検出する。印の付け忘れを見つけるためで、リーク検出や解放済みアクセスの検出と同じ位置づけにする。所有者は `debug_heap` が有効なときだけ別のテーブルに記録する
- ランタイムの `unsafe` な部分 (あれば) は、Miri と loom (並行処理のモデル検査) でテストする

## 10. 未決の論点と将来の拡張

- **`tail` のキーワードの名前**: 仮の名前。関数の `fn` と紛らわしくないものにする
- **局所的な可変変数の糖衣構文**: Koka の `var` のように、関数の中に閉じた可変変数を `Heap` を外に見せずに書けるようにする (X3)
- **`Lin` な配列**: 分割と結合のプリミティブ、`freeze`。Perceus の reuse analysis が前提
- **逐次実行と同じ意味の `par_ordered` (a3)**: 任意の row を許し、右の子を最初の perform まで投機的に実行する。意味は逐次実行と完全に一致する。「perform の手前で止まる」プリミティブが実行系の核に必要
- **並行処理用の共有の可変状態**: channel、atomic な参照など。`IO` か `Async` の側に置く
- **`IO` が大域的な領域を含む折衷案**: Koka のように `IO` が `Heap Global` を含む形。便利だが、大域的な領域の読み書きには同期が必要になる。必要になったら検討する
- **「`Heap` を含まない row」の制約**: 子タスクの row を多相に開いたまま `Heap` だけを除外できると、並行処理の API の柔軟性が上がる。言語設計 spec §10 の「row 要素ごとの捕捉 Kind」と同じ種類の拡張として扱う
- **private deque**: 印付けを実際に移動する継続だけに限る最適化
- **ネイティブのアロケータ**: 別のスレッドからの解放に対応したもの (mimalloc など)
- **マルチコア版のヒープの実装方式**: スレッドごとのアリーナか、ポインタ方式か
