# S12d 5本のスクリプトの設計

## 目的と範囲

S12 (スクリプトの MVP) の最後の作業である。wc、grep、ログの集計、CSV の変換、デプロイ手順の5本のスクリプトを eml で書き、UI テストにする。S12 の完了の条件 (ロードマップの段の列) は、この5本が UI テストとして動くことである。

5本は S13 の判断の材料である。書いてみて次の3つを確かめる。

1. 線形な値の受け渡しが実用で辛いかどうか。`let (f, text) = Fs.read_all f` のように `File` を返して受け渡す書き方、`close` と `drop` の義務、handler の節の `once` の `k` を必ず使う義務が、実際のスクリプトでどれだけ負担になるか。S13 の「線形値の受け渡しの糖衣」と「中断で終わる経路での `Lin` の値の暗黙の後始末」の判断に使う
2. 実用的な性能が出るか。目標は、数十 MB のログを数秒以内に処理することで、比べる相手は Python である
3. エフェクトを活用した状態の保持とストリームを簡潔に書けるか。基本は Koka の `yield` と handler の書き方で、目標の簡潔さは Haskell のモナドと do 記法の水準である

S12d では、測って記録するところまでを行う。性能が目標に届かなくても、S12d の中では直さない。どう対処するかは S13 で判断する。

次のものは範囲に入れない。

- std への新しいモジュールや関数の追加。`Yield` や `State` のようなエフェクトと handler は、各スクリプトの中に書く。同じ定義が何本にも出てくること自体が、S13 で std に入れるかを決める材料になるためである
- 性能の改善
- 言語の機能の追加。足りない機能は回避して書き、記録に残す

## 共通の書き方

- 5本はどれも `main : Unit -> <IO> Unit` を入口にし、`Env.args ()` で引数を読む。引数の誤りは使い方を標準エラーに書いて `exit 2` で終える
- `File` を使う所では、`Fs.read_text` で済ませずに `Fs.open`、`Fs.read_all`、`Fs.close` で `File` を受け渡す。1の観点を確かめるためである
- エフェクトは、生産者と消費者を分けて書ける所で使う。handler は関数にまとめ、`use` で重ねる形 (`use each_line`、`use n <- counting`) を試す。素直な再帰や fold のほうが短い所では、無理にエフェクトを使わない。その比較も記録に残す
- IO の失敗は `try_io` で捕まえ、標準エラーに書く
- 自然に書けなかった所 (回避した所、長くなった所、型や Kind の誤りに悩んだ所) は、その場で作業メモに残し、段の終わりの記録に使う (下の「記録」)

## 5本のスクリプト

各スクリプトに、主に見る観点を番号で付ける。出力の細かい形 (桁揃えなど) は、ここに書いていなければ builder が決める。

### wc (1、2)

`wc [-l] [-w] [-c] [FILE...]`

- フラグを1つも書かなければ、行、語、バイトの3つを出す。書いたフラグの数だけを、行、語、バイトの順で出す
- ファイル名 `-` は標準入力で、`Stdin.read_all` で読む。ファイルを1つも書かなければ `-` と同じである
- 行の数は `\n` のバイトの数、語の数は ASCII の空白 (`String.trim` と同じ6種) で区切った空でない列の数、バイトの数は `String.byte_length` である
- ファイルが2つ以上なら、最後に合計の行 (`total`) を出す
- 開けないファイルは、`try_io` で捕まえて `wc: <パス>: <文言>` を標準エラーに書き、残りのファイルを続ける。1つでも失敗したら最後に `exit 1` で終える
- 数える部分はエフェクトを使わずに書く。3の観点で、エフェクトで書いたほかのスクリプトと比べる基準にする

### grep (2、3)

`grep [-v] [-n] [-c] PATTERN [FILE...]`

- パターンは固定の文字列で、`String.contains` で探す。`-v` は一致しない行、`-n` は行番号を付ける、`-c` は一致した行の数だけを出す
- ファイル名 `-` とファイルを書かないときの扱いは wc と同じである。標準入力は `Stdin.read_line` で1行ずつ読み、全体を読まない。ファイルは `Fs.read_all` で読んで `String.lines` で分ける
- ファイルが2つ以上なら、行の前に `<パス>:` を付ける
- 行を `(行番号, 行)` として `yield` する生産者と、絞り込み、番号付け、数え上げをする handler に分けて書く
- 終了コードは、一致した行があれば 0、なければ 1、開けないファイルがあれば 2 (誤りを優先する) である
- `-i` は入れない。今は文字の型も文字列を組み立てる関数もなく、大文字と小文字をそろえた文字列を作れないためである。この不足を記録に残す

### ログの集計 (2、3)

`logstat [-n N] [--whole]`

- 標準入力のアクセスログを読む。1行は `時刻 メソッド パス ステータス 応答時間` の5つの欄を空白1つで区切ったもので、ステータスと応答時間 (ミリ秒) は整数である。例: `2026-10-17T12:00:01Z GET /api/users 200 123`
- 既定では `Stdin.read_line` で1行ずつ読む。`--whole` を付けると `Stdin.read_all` で全体を読み、`String.lines` で分ける。2つの読み方の性能を比べるためにある
- 出力は、行の総数、形の崩れた行の数、ステータスごとの件数 (ステータスの昇順)、パスごとの件数の上位 N 件 (件数の降順、同じ件数ならパスの昇順、N の既定は 10)、応答時間の平均 (整数の割り算) と最大である
- 形の崩れた行 (欄の数が5でない、ステータスか応答時間が整数でない) は数えて集計から除き、最初の1行だけを行番号付きで標準エラーに書く
- 行を `yield` する生産者と、集計の状態を持つ handler に分けて書く。状態はパラメータ付きの handler (`handle … from … with`) で持ち、`use` で重ねる
- std に連想配列も並べ替えもないので、文字列と整数をキーにする二分探索木とマージソートをスクリプトの中に書く。この負担も記録に残す

### CSV の変換 (1、3)

`csv2jsonl --columns NAME,NAME... INPUT OUTPUT`

- `INPUT` はヘッダの行を持つ CSV で、`File` で開いて `Fs.read_all` で全体を読む。欄の区切りは `,`、行の終わりは `\n` か `\r\n` である。`"` で囲んだ欄は `,`、改行、`""` (1つの `"` を表す) を含められる。最後の行の終わりは省ける
- `--columns` で選んだ列を、指定した順に並べた JSON のオブジェクトを1行に1つ書く。値はすべて JSON の文字列にし、型は推し量らない。`"`、`\`、制御文字 (0x00〜0x1F) はエスケープする
- 結果は全体を組み立ててから `Fs.write_text` で `OUTPUT` に書く。途中で誤りがあれば何も書かない
- 欄の数がヘッダと合わない行と、閉じていない引用符は、`never` の操作を持つ `Fail` エフェクトで中断する。handler は `csv2jsonl: line N: <文言>` を標準エラーに書き、`exit 1` で終える。行番号は、その行が始まる入力の行の番号である
- ヘッダにない列名を `--columns` に書いたら、`exit 2` で終える

### デプロイ手順 (1、3)

`deploy [--dry-run] CONFIG`

- `CONFIG` は `key=value` の行と、`#` で始まる注釈の行と、空の行からなる設定ファイルで、`File` で開いて読む。キーは `name`、`report` と、段の `build`、`test`、`package`、`upload` である。段の値はシェルのコマンド行で、`Proc.run "sh" ["-c", value]` で起動する。書いていない段は飛ばす
- 段は build、test、package、upload の順に動かす。各段の始まりと結果 (`ok` か、失敗した終了コード) を `Log` エフェクトで記録する。`Log` の handler は記録を標準出力に書きながら集め、最後に `report` のパスへ `Fs.write_text` で書く
- 段の起動は `Run` エフェクトの操作にする。`--dry-run` では、起動せずにコマンドを表示して 0 を返す handler に差し替える。本物の handler と差し替える handler を1か所で選べることを、3の観点で確かめる
- 段が 0 以外で終わったら、そこで止め、報告を書いてから、その終了コードで `exit` する。`sh` を起動できないような IO の失敗は `try_io` で捕まえ、報告を書いてから `exit 2` で終える
- 段の入れ子を `use step "build"` の形で書く

## UI テスト

### 置き場所

5本を `tests/ui/run/scripts/<名前>/main.em` に置く。名前は `wc`、`grep`、`logstat`、`csv2jsonl`、`deploy` である。入力は付属のファイル (`main.args`、`main.stdin`) と、同じディレクトリの入力ファイルで与える ([テスト戦略](../../implementation/testing.md) の「UI テスト」)。`exit` で終わるテストも `run/` に置く。終了コードはスナップショットの末尾の `--- exit: n ---` で固定する。

今のハーネスは、1つのテストに引数を1組しか渡せない。そのため、主な経路をなるべく多く1回の起動で通す引数を選ぶ (私の判断)。

| 名前 | 起動 | 通す経路 |
|---|---|---|
| `wc` | `wc a.txt - missing.txt` (標準入力あり) | 3つの数、標準入力、合計の行、開けないファイル、`exit 1` |
| `grep` | `grep -n PATTERN a.txt -` (標準入力あり) | 1行ずつ読む標準入力、ファイル、行番号、`<パス>:` の前置き |
| `logstat` | `logstat -n 3` (標準入力に数十行のログ) | 1行ずつ読む経路、上位 N 件、形の崩れた行 |
| `csv2jsonl` | `csv2jsonl --columns ... in.csv out.jsonl` | 引用符、`""`、欄の中の改行、`\r\n`、制御文字のエスケープ、書き出したファイル |
| `deploy` | `deploy deploy.conf` (test の段が `exit 3`) | 設定の読み込み、`Proc.run`、段の失敗での停止、報告のファイル、`exit 3` |

1回の起動で通せない経路 (`wc -l` などのフラグ、`grep -v` と `-c` と終了コード 2、`logstat --whole`、`csv2jsonl` の `Fail` の経路、`deploy --dry-run`) は、UI テストでは固定しない。`--whole` と、wc と grep の標準入力の経路は、下の「性能の計測」で動かす。ほかの経路は、作業の中で手で動かして確かめる (私の判断)。

### 標準エラーの捕捉

今の UI テストの Host (`CaptureHost`) は、プログラムが標準エラーに書いたもの (`eprintln`) を捨てている。`Proc.run` の子の標準エラーも `Stdio::null()` で捨てている。`run` のスナップショットの `--- stderr ---` の節にあるのはコンパイルの診断だけで、`run-fail` のスナップショットには標準エラーの節がない (診断も捨てている)。

スクリプトの誤りの報告を固定するために、次のように変える (私の判断)。

- `CaptureHost` が、プログラムの標準エラーを標準出力とは別に捕まえる。`Proc.run` の子の標準エラーも、子の標準出力と同じく、書き出してから捕まえた標準エラーに足す
- `run` と `run-fail` のスナップショットを同じ形にそろえる。どちらも `--- stdout ---` の後に `--- stderr ---` の節を常に置き、コンパイルの診断 (警告) とプログラムの標準エラーをこの順に出す。端末で `eml run` を動かしたときに見える順と同じである。`run-fail` では、その後に今と同じ `--- runtime error ---` の節が続く
- 速いモードとの比較も、標準出力と同じく標準エラーで行う

## 性能の計測

wc、grep、logstat、csv2jsonl の4本を測る。deploy は子のプロセスを起動するのが中心で、入力の大きさが効かないので測らない。

- `bench/scripts/gen.py` が、種を固定した決定的な生成で、約 30 MB のアクセスログと約 30 MB の CSV を作る。生成したファイルはリポジトリに入れず、`target/` の下に置く
- `bench/scripts/` に、4本と同じ処理を Python で書いたものを置く。Python の版は、Python の標準ライブラリで普通に書く (`csv` モジュール、`collections.Counter`、`sys.stdin` の行の反復など)。速さのために手で凝ったものにはしない。比べたいのは、Python で普通に書いたスクリプトとの差だからである
- `bench/scripts.sh` が、release ビルドの `eml run` (速いモード) と `python3 -I` で、各計測を3回ずつ走らせ、実時間と最大の常駐メモリ (`/usr/bin/time -l` の `maximum resident set size`) の中央値を Markdown の表で出す。表の前に、`bench/run.sh` と同じく測定の環境を出す。`bench/run.sh` と同じく macOS でだけ動く
- 計測は次の6つである。wc (ログを標準入力から)、grep (ログを標準入力から、1行ずつ読む経路)、logstat (1行ずつ)、logstat `--whole`、csv2jsonl (CSV のファイルから)、それぞれの Python の版
- 出力が eml と Python で一致することを、計測の前に確かめる。一致しなければ止まる。Python の版と eml の版の出力の形をそろえるのは、このためである

結果は [計測の基準](../../implementation/benchmarks.md) に新しい節を足して記録する。`bench/*.em` の基準のプログラムと `crates/eml_vm/tests/bench.rs` の回数のテストは変えない。

## 書いている途中の不具合

スクリプトを書く途中で、処理系の不具合 (誤った結果、内部のエラー、panic、検証器の誤り、通るべきプログラムが通らない) が見つかることがある。扱いは次のとおりにする (私の判断)。

- 原因が局所的で、設計を変えずに直せる不具合は、S12d の中で直す。不具合を再現する最小の UI テスト (適切なカテゴリに置く) を先に足し、スクリプトとは別のコミットにする
- 直すのに設計の判断が要る不具合と、言語の機能が足りないことによる不便は、S12d では直さない。回避して書き、記録に残す。回避できず、スクリプトが書けない場合は、作業を止めて相談する

## 記録

段の終わりに、書いてみて分かったことを、ロードマップの S13 の節に「S12d で分かったこと」として書く。S13 の項目ごとに整理し、項目にない発見は別にまとめる。

- 1の観点: `File` と `k` の受け渡しがどこで何行増えたか、`drop` を何回書いたか、中断の経路での後始末に困った所。S13 の「線形値の受け渡しの糖衣」と「中断で終わる経路での `Lin` の値の暗黙の後始末」に結びつける
- 2の観点: 計測の表の要点と、Python との比。目標 (数十 MB を数秒以内) に届いたかどうかと、届かなかった計測で時間のかかっている所の見当
- 3の観点: エフェクトで書いた所と素直に書いた所の比較、`use` の書き心地、型の注釈が要った所。S13 の「省略した row の暗黙の row 変数 ε」「ブロック引数」「多相なローカル関数」「ローカル関数どうしの相互再帰」に結びつける
- std に足りなかったもの (連想配列、並べ替え、文字の型と文字列の組み立て、`replace` など) と、各スクリプトの中に繰り返し書いた定義

スクリプトの書き心地の評価は、具体的な箇所 (スクリプトの名前と行) を挙げて書く。

## テストの変更

- 新しいテストを足すだけで、成否の変更 (種類1) はない
- 期待値の変更 (種類2): 標準エラーの捕捉と形をそろえることで、次のスナップショットが変わる
  - `run` のうち、プログラムか `Proc.run` の子が標準エラーに書くテスト。`--- stderr ---` の節に、書いた行が加わる。今は `tests/ui/run/std/eprintln.em` が該当する
  - `run-fail` のすべてのテスト (今は14本)。`--- stdout ---` と `--- runtime error ---` の間に `--- stderr ---` の節が加わる。中身は、診断とプログラムの標準エラーがあればそれで、なければ空である
- 途中で不具合を直したときは、その修正が既存のテストの期待値を変えるなら、その範囲をこの spec に足してから進める

## 私の判断で決めたこと

- UI テストは1本につき1回の起動とし、通す経路を上の表のとおりに選んだ。固定しない経路は、性能の計測と手での確認で動かす
- wc と grep で、ファイル名 `-` を標準入力として受ける。1回の起動で、ファイルと標準入力の両方の経路を通すためである
- `CaptureHost` が標準エラー (`Proc.run` の子のものを含む) を捕まえ、スナップショットの `--- stderr ---` の節で診断の後ろに出す。`run-fail` のスナップショットにもこの節を常に置き、`run` と形をそろえる
- 生成する入力の大きさを約 30 MB にした
- logstat の `--whole` は、2つの読み方の性能を比べるためのフラグである
- csv2jsonl の値はすべて JSON の文字列にする
- 局所的な不具合は S12d の中で直し、設計の判断が要るものは記録に回す
