# S11b 根からの回復

位置づけ: S11b の設計。終えたら決めたことを `docs/spec/` などに移し、この文書を消す。

## 目的と範囲

[ロードマップ](../../future/roadmap.md) の S11 (REPL) の2つ目の作業である。S11a の REPL は、続けられる実行時エラー (extern の誤り、深さと確保量の上限、割り込み) の後に `Ctx::abandon` で evv と yield の状態を空に戻すだけで、失敗した実行が残した物体を回収しない。そのため、検査モードの `close` はそれをリークとして報告し、確保量の上限で止まった後は、残ったページが確保量に数えられたままになる。

S11b では、続けられる実行時エラーの後に、セッションの根から届く物体を新しいヒープに写し、古いヒープを丸ごと捨てる。回復の後に生きている物体は、根から届くもの (と、凍結した領域とヒープのダミー) だけになる。これはロードマップの S11 の完了の条件「誤りや割り込みの後に、生きている物体が根だけになる」である。

判断の基準は、簡潔で洗練された実装を第一に、次に性能である。この文書は、健全性とコードとの食い違いの観点、設計の一貫性と範囲の観点の2つの敵対的レビューを経ている。

## ロードマップから変えること

- **回復の手順**: ロードマップは「根から届くものを残し、届かないものを解放し、RC を数え直す」としていた。この文書では、根から届くものを新しいヒープに写し、古いヒープを丸ごと捨てる (下の「回復」)。根から届くものだけが残るという意味は同じである。その場で解放して数え直す手順をとらないのは、次の3つのためである
  - Verus の RC のモデルは、ヒープの外からの参照をただの数で持つ。捨てたスタックや evv が持っていた参照がなくなったことを表すには、多くのブロックと辺をまとめて消し、参照の数を数え直す新しい ghost の遷移が要る。今ある、ヒープを書き換える全体の走査は `share` だけで、約 1400 行ある
  - 速いモードでは、token の箱が生きている `Data` の物体と実行時に見分けられない。その場で解放する手順は、届かない箱を中身をたどらずに1つずつ空け、残すものの RC を入ってくる参照から数え直すことになる。数え直しの誤りは、速いモードのメモリの安全性を崩す
  - 小さい物体のページは OS に返さないので、その場で解放しても確保量は減らない。確保量の上限で止まった後にページを確保量から戻すには、確保器に新しい機能が要る
- **SIGINT のハンドラ**: ロードマップは REPL 用の SIGINT のハンドラ (2回目の Ctrl-C でも終わらない) を S11b に置いていた。この文書では S11c に移す。S11b の `Repl` は lib API だけで、入力を読むプロセスの繰り返しがないので、ハンドラが働くのも、`cli.rs` の SIGINT のテストと同じくプロセスにシグナルを送って確かめられるのも、S11c の `eml repl` からである。S11b には、割り込みの意味と、コード表の更新の間の割り込みの保留を残す。S11c に渡す論点は下の「S11c に渡すこと」にある
- **割り込みの保留**: ロードマップは「コード表を更新する区間では、割り込みを保留する」としていた。`Machine::load` (コード表の更新) は止める理由のビットを見ないので、その間に来た割り込みは、ビットに残ったまま同じ入力の実行の最初の安全点まで保留される。S11b は、この扱いを文書に書き、テストで固定する。新しい仕組みは足さない

## 回復

### 意味

- 続けられる実行時エラーの後に、VM はセッションの根から届く物体を新しいヒープに写し、古いヒープを丸ごと捨てる。`eml run` (`execute`) も同じ `Machine::run` を通るので回復する。根がないので、写すものはなく、古いヒープを捨てて届かない `Foreign` の物体を閉じるだけである
- 古いヒープを捨てると、失敗した実行が残したもの (捨てたスタックと evv と yield の語、token の箱) がすべて消える。届かない `Foreign` の物体は、古いヒープの破棄で破棄処理が呼ばれる (`File` なら閉じる)。古いヒープのページはすべて `Control` に戻るので、確保量の上限で止まった後も、確保量は新しいヒープの分に戻る
- 写すと物体の番地が変わる。失敗した実行の後に、ヒープの外がヒープの語を持つのは根だけである。`CodeBase` の定数は凍結した領域にあり、写しても変わらない。`Task` は実行の局所の値として捨てる。Host はヒープの語を持たない
- 根の値は `Unr` なので、`File` のような `Lin` の物体、lin ビットの物体、token の箱には届かない。届いたら回復を止め、セッションを使えない状態にする (下の「失敗」)
- 回復の費用は、根から届く物体の数に比例する。失敗した入力のたびにかかる。写している間は古いヒープと新しいヒープが同時にあり、使うメモリは古いヒープと根から届く分の写しを足した量になる。写すことで確保量の上限を超えることがあり、そのとき立つ `MEMORY` のビットは次の `eval` の `Control::clear` が下ろす。OS の確保が失敗すると、今の確保と同じく処理系が止まる
- 回復は止める理由のビットを見ない

### 物体の種類と写し方

| 種類 | 写し方 |
|---|---|
| 即値 | そのまま |
| RC が 0 の物体 | 古いヒープのダミーなら新しいヒープのダミー、そうでなければ凍結した領域の物体としてそのまま (下の「RC が 0 の物体」) |
| `Data` | 子を写した後に、同じタグ、走査する語の数、容量で作り、走査しない語を写し、走査する語に子の新しい語を置く (下の「走査しない語」) |
| `String` | 古いバイト列 (`string_text`) から `alloc_string` で作る。`alloc_string_room` が作った余りの容量は写さない |
| `BigInt` | 古い値から `alloc_int` で作る (値は 63 ビットに収まらないので、また `BigInt` になる) |
| `Foreign`、lin ビットの物体、token の箱、解放済みの物体、RC が負の物体 (共有) | 写せない (`Unrecoverable`) |

後で物体の種類を足すとき (`Float`、バイト列、`Array` など) は、その種類の写し方もこの表に決める。`Unr` の `Foreign` の種類を足すなら、写すか移す処理を、信頼する部分の新しい行と一緒に足す。この表は [オブジェクトモデル](../../spec/object-model.md) の「種類」に移す。

### 走査しない語

`Data` の物体は、走査しない語 (生の語) の数を持たない。`alloc_data` は生の語の数を大きさを決めるのにだけ使い、生の語を書かないので、確保した直後の生の語は初期化されていない。そのため、`alloc_data` は走査する語の後ろから容量の終わりまでを 0 で埋める。ヒープの不変条件に「生きている `Data` のブロックのペイロードの語は、容量の終わりまですべて初期化されている」を足す。再使用 (`con_at`) は同じ箱に書き直すだけなので、この不変条件を保つ。回復は、容量から走査する語の数 (と数の語) を引いた残りを生の語として写す。前のコンストラクタの残りの語も写すが、走査しないので害はない。

0 で埋める分だけ確保の命令が増える。`bench.rs` の `RunStats` は数え方が変わらないので変わらない。`bench/run.sh` の命令の数は、S11 を終えるときに記録する。

### RC が 0 の物体

速いモードは RC が 0 の物体のページの見出しを読まないので、実行時に凍結した領域の物体かどうかを調べる手段がない。RC が 0 の物体は、凍結した領域の物体と、ヒープのダミーと、そのヒープの `alloc_immortal` / `alloc_string_immortal` が作った物体の3つである。

- ヒープに「不死の物体を作った」という欄を足し、`alloc_immortal` と `alloc_string_immortal` が立てる。ghost の不変条件は「欄が立っていなければ、ヒープの中の RC が 0 のブロックはダミーだけ」である
- `recover` は、欄が立っていれば `Unrecoverable` を返す。実行のヒープで不死の物体を作るのは、定数を作る作業用のヒープだけなので、実行のヒープの欄は立たない
- 欄が立っていなければ、RC が 0 の語は古いヒープのダミーか凍結した領域の物体である

### `Ctx::recover`

`eml_rt` に `Ctx::recover` を足し、`abandon` は `recover` に吸収して消す。置き場所は `crates/eml_rt/src/heap/ctx/recover.rs` で、`verus!` の中に置く。新しい信頼する部分は足さない。古いヒープは今の `Drop` (T4) で捨て、写像には vstd の `HashMapWithView` を使う (vstd が std に置く仮定の仕様で、`Vec` や `Arc` と同じ種類の信頼である)。

```rust
/// # Safety
/// 根の語は、即値か、このヒープか付けた凍結した領域の、生きていて token でない物体で、それぞれ参照を1つ持つ。
pub unsafe fn recover(&mut self) -> Result<(), HeapError>
```

- **requires**: 根の語はどれも `word_in` で、速いモードでは読める (モデルの状態が `Live`)。ヒープは `safe_settleable` で、速いモードでは `settleable` である。`root_get` の前提と同じ形である
- **ensures** (成功のとき): 新しいヒープは `wf` で、evv は `()`、yield していない (`finished`)。新しいヒープの各ブロック b について、外からの参照の数 `ext(b)` は、新しい根の表の中の b の出現の数 (`points_in`) に等しい。根の語はどれも新しいヒープか凍結した領域の語 (`word_in`) である
- **ensures** (`Unrecoverable` のとき): 根の表と古いヒープは変わらない

手順は次のとおりである。

1. `Heap::<M>::with_control` で新しいヒープを作り、同じ worker ID を設定し、古いヒープの凍結した領域の先頭を `attach` する
2. 根の語から深さ優先で帰りがけ順にたどる
   - 枠のスタックは (古いブロック, 次に見るフィールドの番号) を積む。枠を積む前に、そのブロックを写像に「写している途中」として入れる
   - 写した子の新しい語は、別の語のスタックに積む。枠のフィールドを見終えたら、語のスタックの末尾から走査する語の数だけ取って物体を作る
   - 写している途中の物体にまた着いたら、循環なので `Unrecoverable` にする
   - 停止の尺度は (|古いヒープのブロック| − |写像|, 一番上の枠の残りのフィールドの数) である
3. 参照は余分な `dup` なしで配る。新しい物体の最初の参照は最初の使い手 (親のフィールドか根) に渡し、2つ目からの使い手には `dup` を1回ずつする。写像は、最初の参照を渡したかどうかを持つ。写像に入る物体はどれも、それを使うフィールドか根から見つけたものなので、最後に余る参照はない。ループの不変条件は「新しいヒープの各ブロックの `ext` は、語のスタックと書き換えた根の中のその出現の数に等しい」である
4. 根の表を新しい語に書き換え、`mem::replace` でヒープを入れ替え、evv を `()` に、yield の状態を空に戻し、古いヒープを捨てる。新しいヒープには作りかけの物体 (`building`) も token もない

各物体を読む前に、それが写せる状態かを確かめる。速いモードはモデルの状態 (`Live`) から出る。検査モードは `check_reach` と同じく前置きの状態を読み、解放済み (`FREED`) と token (`TOKEN`) を `Unrecoverable` にする。凍結した領域の語は、ブロックの番地として調べない。

### 失敗

- `Unrecoverable` のときは、根の表と古いヒープを変えずに返す。作りかけの新しいヒープは捨て、そのページは `Control` に戻る。作りかけのヒープには `Foreign` の物体がないので、破棄処理は呼ばれない
- VM は、元の誤りと回復の失敗の両方を持つ誤り `RuntimeError::Unrecovered { cause, reason }` を返す。表示は元の誤りの後に、回復できなかった理由を1行足す。`is_broken` は真で、`Repl` は `Broken` になる。検査モードで回復の後の `check_invariants` が失敗したときも、同じ誤りにする

## VM と `Repl`

- `Machine::run` は、続けられる誤りの後に `abandon` の代わりに `ctx.recover()` を呼ぶ。成功したら、検査モードでは新しいヒープの不変条件 (`check_invariants`) を確かめ、元の誤りをそのまま返す
- **統計**: `RunStats` は実行の仕事だけを数え、回復の仕事 (写すための確保と `dup`) は数えない。`Machine` は、入れ替えの前に古いヒープの統計を積算に足し、入れ替えた後の新しいヒープの統計を新しい起点にする。`peak_objects` は、積算の最大と新しいヒープの最大の大きい方である。写している間の、古いヒープと新しいヒープを合わせた数は数えない。[VM](../../spec/vm.md) の「`RunStats`」に書く
- `close` は変えない。回復の後は、検査モードのリークの検査が 0 になる
- **失敗した `let` の根**: `let` の入力は `root_set` の後の `Ret` の安全点や、終わりの flush の `Output` で失敗しうる。そのとき根は埋まったままで、入力は受け付けない。その根を読むコードは後の入力から見えないので、値は `close` まで残り、回復のたびに写される。害はないので受け入れる。[オブジェクトモデル](../../spec/object-model.md) の「セッションの根」の「失敗した `let` の根は空のまま残る」を、この扱いに直す
- `eml_cli::Repl` は変えない。S11b での回収に触れていたドキュメントのコメントを直す

## 割り込み

- 入力の途中の割り込みは、次の安全点でその入力を止める。回復した後、その入力は `Failed` (`runtime error: interrupted …`) になる
- `eval` の始めの `Control::clear` の後、その入力の実行の前に来た割り込み (前端の検査と `Machine::load` の間) は、ビットに残ったまま実行の最初の安全点まで保留される。定義だけの入力は実行しないので、その間の割り込みは次の `eval` の `clear` で捨てられる
- 実行の後に来た割り込み (回復の間と、入力と入力の間) は、次の `eval` の `clear` で捨てられる

## S11c に渡すこと

- 2回目の Ctrl-C でも REPL を終わらせないと、安全点を通らない処理から抜けられなくなる。今その処理は、前端の検査、回復、安全点を持たない読み込み (FIFO からの `Fs.read_all`、S12 の `Stdin`) である。`eml run` が2回目の Ctrl-C で終わるのは、この読み込みのためである。ハンドラの設計と一緒に決める
- 定義だけの入力の前端の検査の間の割り込みを、その入力を受け付けない扱いにするか
- REPL の確保量の上限の既定の値。回復は古いヒープと写しを同時に持つので、`eml run` の既定 (物理メモリの 80%) より余裕を持たせるか

## テスト

- **`eml_rt`** (`both_modes!`)
  - 共有のある DAG (共有した子の RC が 2 になる)、生の語を持つ `Data`、走査する語が 255 個以上の `Data`、文字列 (余りの容量を持つものを含む)、`BigInt`、凍結した領域の語、ダミーを根に置いて回復し、写した値が元と同じで、RC が根と親からの参照の数に等しいことを確かめる
  - 届かない物体 (token の箱と、呼ばれた回数を数える破棄処理を持つ `Foreign` の物体を含む) を置いて回復する。回復の後に、生きている物体の数が根から届く数と同じで、破棄処理がちょうど1回呼ばれ、`bytes_in_use` と `Control::bytes` が減り、`take_roots` で根を手放した後のリークが 0 であることを確かめる
  - `Unrecoverable`: 根が `Foreign` の物体、lin ビットの物体、RC が負の物体に届く場合、不死の物体を作ったヒープの場合、検査モードでは解放済みの物体と token の箱に届く場合に、根の表とヒープが変わらないことを確かめる
  - `alloc_data` が生の語を 0 で埋めること
- **`eml_vm`** (`machine.rs`)
  - 割り込みのビットを立ててから `load` をし、その後で `run` をすると、`load` は成功し、実行は最初の安全点で止まる。`load` の後で立てた場合と同じ結果になる
  - 続けられる誤りの後、検査モードでも `close` がリークを報告しない。今の `a_continuable_error_empties_the_evv_for_the_next_run` の名前を、回復を表す名前に替える
  - 回復の仕事を `RunStats` に数えないこと
  - `RuntimeError::Unrecovered` が `is_broken` で、表示が元の誤りを含むこと
- **`eml_cli`** (api テスト)
  - 割り込みを1回だけ立てられる `Host` で、出力し続ける入力を流す。その入力は割り込まれた `Failed` になり、次の入力は普通に動き、検査モードの `close` はリークを報告しない
  - `open` が割り込みを立て、手放された回数を数える読み手を返す `Host` で、`Fs.read_all` を流す。読み込みは割り込みで止まり、`eval` から戻った時点で読み手が手放されていて (`File` が閉じている)、`close` はリークを報告しない。`Foreign` の破棄処理、`Extern(Fault::Stopped)` の道、古いヒープの lin の物体を確かめる
  - 確保量の上限で止まった後に、大きな確保をする入力が成功する (ページが戻る)。今の `the_memory_stop_bit_is_cleared_for_the_next_input` をこの確かめに広げ、名前を `the_session_continues_after_the_memory_limit` に戻す
- **テストの変更**
  - 成否の変更: `eml_rt` の単体テスト `abandon_forgets_the_evv_and_the_yield_state` を消す。`abandon` を消すためで、回復のテストが代わる
  - 期待値の変更
    - トランスクリプト `errors/runtime` の末尾を `memory leak: objects were not freed: 3 Data` から `no leaks` に変え、そのコメントを直す
    - `eml_vm` の `a_continuable_error_empties_the_evv_for_the_next_run` は、検査モードの `close` が `Leak` を返すことを確かめている。2つのモードとも `Ok` を確かめるように変え、名前を替える
    - 確保量の上限の api テストの名前と確かめ (上)
  - コメントの追随 (機械的な追随): `crates/eml_cli/tests/api.rs` と `crates/eml_vm/tests/machine.rs` の S11b に触れるコメント、`crates/eml_rt/src/heap/tests/roots.rs` のモジュールのドキュメント
