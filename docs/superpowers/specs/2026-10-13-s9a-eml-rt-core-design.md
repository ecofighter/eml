# S9a `eml_rt` の核: 語、ヘッダ、確保器、RC、検査モード

位置づけ: 作業の設計。ロードマップの S9 の1つ目の作業を定める。S9a を終えたら、決まったことを `docs/spec/` と `docs/implementation/` に移し、この文書を削除する。

## 目的

VM とネイティブで共有するランタイム `eml_rt` の核を、新しい crate として作る。核は物体の中身の種類をほとんど知らず、次のものだけを持つ。

- 8 バイトの語 (ポインタか即値)
- 物体のヘッダと、種類ごとの小さな固定の表
- ページ単位の確保器と、両方のモードで使える生存の列挙
- 局所と共有の RC、`share`、`lin` ビット
- reuse の部品 (token)
- 型の引数で選ぶ検査モード (所有者 ID、解放の後の使用の検出、不死の物体の数え方、リーク)
- `unsafe` の核と、その検証 (Miri、Kani)

S9 を S9a と S9b の2つの作業に分ける。S9b は、物体の種類ごとの中身 (データの物理的な形、文字列、クロージャ、evidence、`File`)、`Ctx`、`FnEntry`、`CodeBase`、語の ABI で書く extern と、今の実装との差分テストである。段の列では S9 の1行のままにする。

S9 の間、`eml_rt` はパイプラインから使わない。単体テスト、Miri、Kani、extern の差分テスト (S9b) で確かめ、実際のプログラムで通すのは S10 の VM からである。CEK と `eml_runtime` は S10 まで変えない。S10 で消す CEK に投資しないためである ([ロードマップ](../../future/roadmap.md) の「段の列」)。

設計の基準は、実用的なプログラムで速いことである。そのために受け入れる制約は、下の「受け入れる制約」にまとめる。形は Lean 4 と Koka のランタイムに近く、確保器は mimalloc の考え方を借りる。

完了の条件は次の5つである。

- `eml_rt` の単体テストが、速いモードと検査モードの両方で通る
- Miri が、`-Zmiri-strict-provenance` の設定と、それに `-Zmiri-tree-borrows` を足した設定の両方で通る
- Kani の4つのハーネス (下の「Kani」) が通る。Kani がこの環境で動かないときは、計画の最初の作業でそれを報告し、代わりの確かめ方を相談して決める
- 既存のテストと UI テストが、変えずに通る
- 計測用のプログラムの命令の数を、[計測の基準](../../implementation/benchmarks.md) に記録してある

## 速さを決める経路

関数型のプログラムで回数の多い経路は、多い順に次のとおりである。設計はこの順に速さを優先する。

1. `dup` と `decref`。ほとんどの命令の周りに出る
2. 小さい物体の確保と解放。cons セル、タプル、`Some x` などの多くはすぐ死ぬ
3. `switch` のタグの読み出し
4. `tobj` の位置の `box` と `unbox`。box の挿入の試作では、`List a` のフィールドで 302,149 回あった ([ロードマップ](../../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)
5. Perceus の reuse (後の reuse analysis が入れる)。一意の道で、確保と解放とヘッダの書き込みを省く

`share`、検査モード、生存の列挙、`Lin` の破棄処理は回数が少ないので、速さより単純さを優先する。

## 語

- 語 `Word` は 8 バイトで、Rust ではポインタ型 (`*mut ()` を包む `#[repr(transparent)]` の型) で持つ。`u64` で持たないのは、Miri の strict provenance の下でポインタの出所を失わないためである。即値は `ptr::without_provenance_mut` で作り、ポインタの下位ビットの検査と書き換えは `addr` と `map_addr` で行う
- 下位ビットが 1 なら即値、0 ならヘッダを指すポインタである。物体は 8 バイトに揃えるので、ポインタの下位3ビットはいつも 0 になる
- 即値の値は、語を算術右シフトで1ビットずらした `i64` である。即値で表すものは次のとおりである
  - 63 ビットに収まる `Int` (`tobj` の位置の `box`)
  - `tobj` の位置の `enum` のタグ `#N`
  - `()`。値 0 の即値、つまり語の値 1 にする
  - 関数の値 `&f`。値は関数の番号である
- `int`、`enum`、`unit` の変数とフィールドは、タグのない生の 64 ビットで持つ。`unit` の生の値も `()` の即値と同じ語の値 1 にする。[LIR とインタプリタ](../../spec/lir.md) の「値の表現」の「`unit` の値の機械の形は、`tobj` の即値 `()` と同じにする」を守るためである
- `box` は、`Int` が 63 ビットに収まれば (`(n << 1) >> 1 == n`) 即値にし、収まらなければ種類 `BigInt` の物体を確保する。`unbox` は、即値なら右シフトし、物体なら `BigInt` の中身を読む。`enum` の `box` と `unbox` はいつも即値のシフトである。`tobj` の中の `enum` のタグの表し方 (ロードマップの S9 の論点) は、即値に決める
- `&f` を即値にするのは、捕まえる値のない関数の値で確保しないためである。`apply` は、語が即値なら関数の番号を直接呼び、物体ならクロージャを呼ぶ。クロージャの形は S9b で決める
- `Word` は `Send` と `Sync` を実装する (`unsafe impl`)。語は値で、スレッドをまたいでよいかは型でなく RC の規約 (`share`) が守るためである。`CodeBase` が不死の定数の語を持って `Sync` になるにも、これが要る ([マルチコア対応の設計](../../future/multicore.md) の「VM の並列化の備え」の制約2)。`Heap` は `Send` で `Sync` でない。worker ごとに1つ持ち、worker のスレッドに移せるようにするためである。どちらも型の assert で固定する

## ダミーの値

- EP のダミー (`prim dummy()`) は、`Heap` が作るときに1つ確保する不死の物体を指す語である (`Heap::dummy`)。物体の種類は `BigInt` で、値は 0 である。静的な物体にしないのは、`static` の中の atomic を loom の型に差し替えられないためと、検査モードの前置きを静的な物体のために特別扱いしないためである
- ダミーへの `dup` と `decref` は、rc が 0 (不死) なので速い道から外れ、何もしない。`unbox` は 0 を読む。速い道に、ダミーのための分岐を足さずに済む
- [LIR とインタプリタ](../../spec/lir.md) の「ダミーの値」の約束 (`dup`、`decref`、`drop` は何もしない、`unbox` は誤りにしない、`box` はダミーを受けたらダミーを返す) は、こうして守る。`box` が受けるのは生の `int` か `enum` で、そこでのダミーは `0` か `#0` なので、普通に box してよい
- ダミーは、検査モードの不死の物体の数え方 (下の「不死の物体の数え方」) の対象にしない。EP は、作っていないダミーを `drop` するためである

## 物体

### ヘッダ

ヘッダは 8 バイトで、ポインタはヘッダの先頭を指す。

```
rc:   AtomicI32   0 = 不死、正 = 局所、負 = 共有
meta: u32         tag (16 ビット) | scan (8 ビット) | info (8 ビット)
```

- `tag` はコンストラクタの添字である。データでない種類では、種類ごとに意味を決める (使わなければ 0)
- `scan` は、走査する語 (`obj` と `tobj` の値) の数である。0 から 254 はそのまま数を表す。255 は「数がペイロードにある」印で、そのときは走査の始まりの位置の生の1語が数を持ち、走査する語はその次から並ぶ。走査する語が 255 個以上の物体 (フィールドの多いデータ、EP の継続のクロージャが捕まえる多くの値) も、同じヘッダで扱うためである。継続のクロージャはコンパイラが作るので、数の上限をユーザーの誤りにできない
- `info` は、最上位のビットが `lin` ビット、下位の4ビットが種類である。残りの3ビットは予約する
- ヘッダを `rc` と `meta` の2つに分けるのは、書き込みを1回にするためである。確保は、ヘッダ全体を `ptr::write(Header::new(..))` で書き、ふだんのビルドでは 64 ビットの1回の store になる。reuse でコンストラクタが変わるときは `meta` の 32 ビットの1回の store で済み、rc は 1 のままなので書かない。同じコンストラクタの reuse は、ヘッダに何も書かない
- `meta` は atomic でない。`meta` を書くのは、確保と、一意な箱の reuse と、解放だけである。どれも、ほかのスレッドがその物体を読めないときに起きる
- ヘッダの大きさは、数字の 8 でなく `size_of::<Header>()` で書く。loom の型に差し替えたビルドでは、ヘッダが大きくなるためである
- 物体の大きさはヘッダに持たない。確保器のページが持つ (下の「確保器」)
- 型ごとの記述子の表は持たない。解放とたどりは、ヘッダの `scan` と、種類ごとの固定の表だけで済む。ロードマップの「ヘッダは記述子を持つ」は、この形 (`scan` と種類と `lin` ビット) で満たす。物体だけからは型と配置が分からない (配置の ID を持たず、型をまたぐ reuse でタグの意味も変わる) ので、リークの報告は種類の名前で数える。今の `eml_runtime` が、どの型のデータも `Data` と数えるのと同じである

### ペイロード

- ペイロードは、走査する語を並べ、その後に生の語を並べる。走査する語は、即値なら何もせず、ポインタなら子として RC とたどりの対象にする
- データの物体で、宣言の順のフィールドを走査する語と生の語に並べ替える規則 (物理的な形) は S9b で決める。コンパイラのパス (後の reuse analysis) とランタイム (S9b の `CodeBase`) は、同じ規則を使わなければならない。reuse analysis は、物理的な語の数と物理的な位置で reuse の組を決めるためである。規則を出す関数をどの crate に置くか (`eml_rt` に置いて `eml_lir` から使うか、別の置き場所に置いて結び付けのテストで縛るか) は、`CodeBase` の置き場所と一緒に S9b で決める。S9a の `eml_rt` は依存を持たないままにする

### 種類

種類は `info` の下位4ビットで、最大 16 種類である。種類ごとの固定の表 (ランタイムに組み込んだ `const` の配列) は、次の欄を持つ。

| 欄 | 意味 |
|---|---|
| 名前 | リークの報告の種類の名前 |
| 走査の始まり | 走査する語 (`scan` が 255 なら数の語) がペイロードの何語目から始まるか |
| token にできるか | reuse の token にしてよいか |
| 破棄処理 | 解放のときに呼ぶ処理があるか |

S9a で作る種類は次の4つである。ほかの種類 (クロージャ、文字列、evidence の入口の表、evidence、`evv` の節点) の番号と欄は S9b で足す。

| 種類 | ペイロード | 走査の始まり | token | 破棄処理 |
|---|---|---|---|---|
| `Data` | フィールド | 0 | できる | なし |
| `BigInt` | `i64` の1語 | 0 (`scan` は 0) | できない | なし |
| `Foreign` | 破棄処理の表への `&'static` のポインタ、その後に Rust の値 | 0 (`scan` は 0) | できない | 表の `finalize` |
| `Free` | 空きリストの次のブロックへのポインタ | なし | できない | なし |

- `Foreign` は、`File` のように Rust の値を持つ物体である。`alloc_foreign::<T>(value, lin)` が、`T` ごとに1つの静的な表 (名前と `drop_in_place::<T>`) を作って先頭に置く。`T` は `Send + 'static` で、揃えは 8 バイト以下に限る。後で別のスレッドが最後の参照を手放しても、破棄処理をそのスレッドで呼べるようにするためである ([マルチコア対応の設計](../../future/multicore.md) の「スレッドに縛られたリソース」)。`File` そのものは S9b で作り、S9a はテスト用の型で確かめる
- `Foreign` を token にしないのは、破棄処理を飛ばして別の物体に使い回すと、`Lin` の資源の後始末が漏れるためである。`BigInt` は reuse analysis の対象にならないので、token にしない
- `Free` は、確保器が空いたブロックに付ける内部の種類である (下の「確保器」)。生きている物体がこの種類を持つことはない

## 確保器

### ページ

- 物体は、64 KiB に揃えたページから切り出す。ページは `std::alloc` から揃えを指定して取る。ページの先頭にページの頭 (大きさの級、ブロックの大きさ、大きい物体のページかどうか、まだ切り出していない残りの位置) を置く。物体のポインタの下位 16 ビットを落とせば (`map_addr`)、ページの頭が分かる。mimalloc と同じ方式で、ヘッダに大きさを持たずに済む
- 小さい物体の大きさの級は語の単位で決める。ブロックの語の数 (ヘッダを含み、検査モードの前置きを含む) が 2 語から 16 語 (16 B から 128 B) は1語刻み、その上は 20、24、28、32、40、48、56、64、80、96、112、128 語である。いちばん小さい級を 2 語にするのは、空いたブロックにヘッダと空きリストのポインタを置くためである
- 128 語を超える物体は大きい物体として、その物体だけの揃えたページに置く。ページの頭の形は同じで、解放の道もページの頭を読むところまでは同じである
- 物体の語の数は、ヘッダを含み、前置きを含まない。`alloc(words, ..)` の `words` もこの数である。級は、速いモードでは `words` から、検査モードでは `words + 1` から決める

### 確保と解放

- ヒープは級ごとに、空いたブロックの空きリスト (LIFO) と、今のページの切り出しの位置を持つ。確保は、空きリストから pop し、空なら今のページから切り出し、ページが尽きたら新しいページを取る
- 今のページの切り出しの位置はヒープの欄だけが正しく、速い道はヒープの位置だけを進める。今のページを替えるときに、古いページの最後の位置をそのページの頭に書き戻す。ページを歩く処理 (生存の列挙、`Heap` を落とすとき) は、各級の今のページではヒープの位置を、ほかのページではページの頭の位置を読む。まだ切り出していないメモリをブロックとして読まないためである
- ヒープは、取ったすべてのページの一覧を持つ。ページの頭は一覧の中の自分の添字を持ち、大きい物体のページを返すときは `swap_remove` で一覧から外し、移ってきたページの添字を書き直す。返すたびに一覧を探すと、大きくなっていく文字列を作るループが2乗の時間になるためである
- 解放は、ページの頭を読み、小さい物体のページなら、ブロックの `meta` を種類 `Free` にし、ペイロードの先頭の語に次のブロックへのポインタを書いて、その級の空きリストに push する。書き込みは2回で、どちらもブロックの先頭の同じキャッシュラインに入る。`Free` の印を書くのは、速いモードでもページを歩いて生きている物体を見分けられるようにするためである (下の「生存の列挙」)
- 大きい物体のページなら、解放したときにすぐ `std::alloc::dealloc` で返す。大きい物体を級の空きリストで使い回すことはないので、返さないと、大きくなっていく文字列や配列を作るループで使う量が限りなく増えるためである
- 形の分かっている物体の解放 (`free_block`。下の「核の操作」) も同じ道を通る。ページの頭を読むのは、マスク1回と読み込み1回である
- S9a では、小さい物体のページは、実行中に OS へ返さない。ページは `Heap` を落としたときにまとめて返す。小さい物体のページを返すこと、ページごとの空きリスト、別のスレッドからの解放 (ページの頭に持ち主を置く遠隔の空きリスト) は、VM の並列化かネイティブのランタイムのときに入れる ([マルチコア対応の設計](../../future/multicore.md) の「確定した設計判断」の 7)
- ヒープは、使っているメモリのバイト数を両方のモードで数える。速いモードでは OS から取ったページのバイト数で、ページを取るときと返すときだけ数えるので、速い道の費用はない。検査モードでは、そこから隔離した (解放して使い回さない) ブロックのバイト数を引く。S9b の `Ctx` の確保量の上限と、S10 の安全点の確かめは、この数を使う
- 2つのモードの数は、空きリストに残っているブロックの分だけ違いうる。上限は暴走するメモリを止めるための安全網で、厳密な会計ではないので、この違いは受け入れる。上限すれすれのプログラムは、モードによって止まったり止まらなかったりしうる

### 生存の列挙

- 生きている物体は、両方のモードでページを歩いて列挙できる。各ページの切り出したブロックのうち、速いモードでは種類が `Free` でないもの、検査モードでは前置きの状態が生存か token のものが、生きている箱である
- 列挙は、S11 の根からの走査による回復が使う。届かない物体を解放し、届かない `Foreign` の物体の破棄処理を呼ぶためである ([ロードマップ](../../future/roadmap.md) の「S11 REPL」)。REPL は速いモードでも動けなければならないので、列挙を検査モードだけのものにしない
- 回復の手順は S11 で決めるが、列挙の上で安全に組めるように、次の条件を S9a で決めておく
  - rc が 0 の物体 (ダミーと `alloc_immortal` の物体) は、根から届かなくても解放しない
  - 速いモードの token の箱は、生きている `Data` と区別が付かず、そのフィールドはもう解放した子を指しうる。そのため、届かない箱は、フィールドをたどらずに1つずつ空ける (`Foreign` だけ破棄処理を呼ぶ)。届く物体の RC は、根からたどって数え直す
- `Heap` を落とすときは、ページを歩いて、生きている `Foreign` の物体の破棄処理を呼んでから、すべてのページを返す。Rust の値が持つメモリを漏らさないためである。Miri は漏れを誤りにする

### 自前の確保器にする理由

- 大きさをページの頭から引けるので、ヘッダが 8 バイトに収まる
- 確保と解放が、空きリストの pop と push の数命令で済む。macOS の malloc は1回に数十 ns かかる
- Miri が確保器の経路も検査できる
- 生存の列挙が、ページを歩くだけで済み、別の台帳が要らない

## 参照カウント

### 符号

- rc が 0 の物体は不死で、解放しない。`alloc_immortal` の物体とダミーがこれに当たる
- 正の rc n は、局所の物体の参照の数 n である。局所の rc は、Relaxed の load と store で読み書きする。aarch64 でも x86_64 でも、普通の読み込みと書き込みの命令になる
- 負の rc −n は、共有の物体の参照の数 n である。共有の rc は、atomic の加減算で読み書きする

### 局所の速い道

`dup` と `decref` の速い道は、比較1回で決める。

- `dup`: rc を符号なしで見て `rc − 1 < MAX − 1` なら、つまり rc が 1 以上 `MAX − 1` 以下なら、rc + 1 を書き戻す。それ以外 (不死、共有、上限) は遅い道に進む
- `decref`: rc が 2 以上 `MAX − 1` 以下 (同じく符号なしの比較1回) なら、rc − 1 を書き戻す。rc が 1 なら解放する。それ以外は遅い道に進む
- `tobj` の値には、この前に下位ビットの検査が1回入る。`obj` の値は、つねにポインタなので検査しない

### 上限

- 局所の rc が `MAX` (`i32::MAX`) に達したら、その物体の数は動かさない (張り付き)。その物体は解放されずに残る。速い道の範囲から `MAX` を外してあるので、張り付いた数は速い道で動かない。局所の数は1つのスレッドだけが書くので、境目はちょうど `MAX` でよい
- 共有の側では、上限の判定と加減算の間に別のスレッドが割り込める。そこで境目を2つ置く (ヒステリシス)
  - `dup` は、rc が `DUP_LIMIT = MIN + 2^16` より小さければ数を動かさない
  - `decref` は、rc が `DROP_LIMIT = MIN + 2^17` より小さければ数を動かさない
- 境目を2つにする理由は次のとおりである。境目が1つだと、境目の外の値を読んだ `decref` が加算する前に、別のスレッドの `dup` が数を境目の中に入れ、さらに別の `dup` がそれを見て数えずに飛ばすことがある。その後に最初の `decref` が加算すると、数は境目の外に戻り、数えなかった参照の分だけ実際より少なくなる。2つの境目なら、`dup` を1回でも飛ばした物体の rc は `DUP_LIMIT` より小さい。それを `DROP_LIMIT` まで戻せるのは、rc が `DROP_LIMIT` 以上のうちに読んで、まだ加算していない `decref` だけである。その数は同時に動く worker の数より少ないので、worker が 2^16 未満なら、rc は `DROP_LIMIT` に戻らない。その後の `decref` はすべて飛ばされ、物体は解放されずに残る。数が実際より少なくなっても、参照が残っている物体を解放することはない
- 張り付いた物体は解放しないが、不死 (rc 0) には変えない。`share` が不死の物体でたどりを止めるので、張り付いた局所の物体を不死にすると、その子が共有の印なしに別のスレッドから届くためである

### 共有の側

- `dup` は、`DUP_LIMIT` 以上なら `fetch_sub(1, Relaxed)` で数を増やす (負の向きに進める)
- `decref` は、`DROP_LIMIT` 以上なら `fetch_add(1, AcqRel)` で数を減らし、古い値が −1 なら最後の参照なので解放する。`fence(Acquire)` は使わず、AcqRel の加算で最後の解放を順序付ける
- 解放の連鎖では、子を1つずつ、その子の rc の符号に合う側の `decref` で減らす。共有の物体の子は、共有か不死の物体か、`lin` ビットの立った局所の物体である (下の「`share`」)

### 遷移の関数

RC の遷移は、rc の値だけを受け取って次の状態を返す純粋な関数 (`dup_step(i32) -> Step` など) にする。ヒープはそれを呼んで書き込むだけである。単体テスト、Kani のハーネス、ヒープが同じ関数を使い、遷移の正しさを1か所で確かめるためである。共有の側の加減算そのものは、`sync` の層の `AtomicI32` への参照を受け取る関数にする。後の loom の試験は、この関数を loom の atomic の上で動かす (下の「`unsafe` と同期の層」)。

## `share`

- `share(w, receiver)` は、送り手のスレッドが、値を公開する前に呼ぶ ([マルチコア対応の設計](../../future/multicore.md) の「共有の印方式」)。w から届く物体を明示のスタックでたどり、局所の rc n を −n に変える。局所の上限 `MAX` は共有の上限 `MIN` に変える。−n が `DROP_LIMIT` より小さくなるときも `MIN` に変える
- すでに負の物体と不死の物体で、たどりを止める。印を付けた物体はもう一度たどらないので、`lin` でない物体がたどられるのは高々1回である
- `lin` ビットの立った物体には印を付けず、所有者を `receiver` に移す。ただし、その子はたどり続ける。`Lin` の物体の中の `Unr` の子は、送り手がほかの所からも参照していることがあるためである。`Lin` の物体は rc が 1 なので、受け手は局所の物体としてそのまま使える
  - `lin` の物体は rc が 1 なので、正しいプログラムでは2回届かない。検査モードは、たどりで同じ `lin` の物体に2回届いたら誤りにする (訪れた `lin` の物体の集合を持つ)。速いモードは、正しいプログラムに頼る
- `lin` ビットのない親の中に `lin` ビットの立った子があることは、ふつうに起きる。`poly` の印の `con` (`(a, File)` の組の型は `poly` になる) と、EP の継続のクロージャ (印は捕まえた値の印の結び) は `lin` ビットを持たないが、中の `File` はビットを持つ。このとき `share` の後は、共有の親から局所の `lin` の子が届く。そのため、共有の物体から届いてよいのは、共有か不死の物体か、`lin` ビットの立った局所の物体である
  - そうした親は、実際には `Lin` の値なので参照は1つで、所有も受け手に移っている。親の最後の参照を手放すのは受け手で、子の所有者の検査とも合う
  - 受け手がその親を手放すとき、親の rc は −1 である。−1 の物体は、参照が自分の1つだけなので、最後の参照として扱い、残すフィールドを `dup` せずに受け取る (下の「核の操作」の `is_last`)。残す `lin` の子を `dup` すると、正しいプログラムでも検査モードの誤りになるためである
- たどりのコードは、物体への読み書きを trait の裏に置いて書く。ヒープの物体と、Kani の有界なグラフのモデルで、同じコードを動かすためである
- S9a では物理的なスレッドは1つで、`receiver` は論理的な worker ID である。`par` を入れるまで、`share` は単体テストからだけ呼ぶ

## `lin` ビット

- `info` の `lin` ビットは、検査モードに限らず常に持つ。`par` の fork で、印付けの代わりに所有者を移すのに使うためである ([ロードマップ](../../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」)
- `alloc` と `con_at` は、呼ぶ側が渡す `meta` の `lin` ビットをそのまま書く。どの物体にビットを立てるか (`File` は作るときに立てる、`con` と `closure` は S8 の静的な印が `lin` なら立てる) は、S9b と S10 で呼ぶ側が決める
- `reuse_in_place` はヘッダを書かないので、箱の `lin` ビットがそのまま残る。ビットが欠けるのは安全の側である (`share` で印が付いて共有になり、その場の書き換えができなくなるだけ)。危ないのは、ビットが誤って残ることで、`Unr` の値の正しい `dup` を検査モードが誤りにする。印が `lin` の変数の箱がビットを持つとは限らない (`map Some files` のように、`poly` の `con$Some` が作った箱が `lin` の変数に入る) が、印が `unr` の変数の箱はビットを持たない
- そのため、`reuse_in_place` を使ってよいのは、古い物体の印が `unr` のときか、新しい物体の印が `lin` のときである。それ以外は `con_at` で `meta` を書く。検査モードの照らし合わせも、`lin` ビットについては「箱がビットを持ち、新しい `meta` が持たない」ときだけを誤りにする

## 核の操作

語を受ける操作は `unsafe fn` にする。安全の条件は次のとおりである。速いモードはこれを確かめない。検査モードは、確かめられる違反を `Err` で返す (下の「検査モード」)。戻り値はどちらのモードでも `Result` で、速いモードでは `Err` を作らないので、最適化で分岐が消える。

- 語は即値か、生きている物体を指す
- 参照を消費する操作 (`decref`、`release`、`into_token` など) では、呼ぶ側がその参照を1つ持っている。読むだけの操作 (`field`、`raw`、`is_unique` など) では、呼ぶ側が参照を持っているか、生きている持ち主から借りている。Perceus の借りたフィールドと、基本操作の借用の引数がこれに当たる
- S9a では、物体は同じ `Heap` が確保したものに限る。`share` の後に別の worker の `Heap` が触る形と、`CodeBase` の不死の定数は、`par` と S9b で条件を広げる

| 操作 | 動作 |
|---|---|
| `alloc(words, meta)` | 級のブロックを取り、rc 1 と `meta` を書く。フィールドは呼ぶ側が書く |
| `alloc_immortal(words, meta)` | rc 0 で確保する |
| `acquire_immortal(w)` | 不死の物体の参照を1つ作る。速いモードでは何もしない (下の「不死の物体の数え方」) |
| `alloc_int(n)` / `unbox_int(w)` | 上の「語」の `box` と `unbox` |
| `alloc_foreign::<T>(value, lin)` | 種類 `Foreign` の物体を作る |
| `dup(w)` / `decref(w)` | 上の「参照カウント」。`decref` が 0 にした物体は、解放の連鎖に入れる |
| `is_unique(w)` | rc が 1 か。共有、不死、張り付いた数は、この1回の比較でみな偽になる。reuse とその場の書き換えに使う |
| `is_last(w)` | rc が 1 か −1 か。手放そうとしている参照が最後のものかを判定し、フィールドを `dup` せずに受け取ってよいかに使う。rc は Relaxed で読み、−1 のときだけ Acquire で読み直す。読み直しは同じ値を返し、最後の AcqRel の `decref` と同期する。ふだんの rc が 1 の道に、aarch64 の Acquire の読み込みの費用を足さないためである |
| `field(w, i)` / `set_field(w, i, v)` | ペイロードの物理的な i 語目を読み書きする。ヘッダを読まない。生の語の読み書き (`raw` / `set_raw`) も同じ添字で持つ。VM は形を静的に知っているので、`scan` が 255 かどうかで添字を直す必要がない |
| `scanned(w, i)` | 走査する語の i 番目を読む。`scan` が 255 のときの数の語と、種類の走査の始まりを考える。形を知らない処理 (解放の連鎖、`share`、生存の列挙) が使う |
| `free_block(w)` | `is_last` が真で、子をすでに処理した物体の箱を空ける。ヘッダの `scan` を読まない。破棄処理を持つ種類には使えない |
| `into_token(w)` | 一意な物体の箱を、フィールドに触れずに token にする |
| `con_at(token, words, meta)` | token が空でなければ、その箱に `meta` を書いて返す。空なら `alloc` する。どちらだったかも返す |
| `reuse_in_place(token, meta)` | 同じコンストラクタの reuse。ヘッダに何も書かずに箱を返す。`meta` は検査モードが照らすためだけに渡す |
| `drop_token(token)` | 使わなかった token の箱を空ける |
| `release(w, tag, keep)` | LIR の `release`。`is_last` が真なら、残さない子を手放して箱を空け、残す子は箱の参照を受け継ぐ。そうでなければ、残す子を `dup` してから w を手放す |
| `release_reuse(w, tag, keep)` | w が一意なら、残さない子を手放して箱を token にする。そうでなければ `release` と同じにして、空の token を返す |
| `share(w, receiver)` | 上の「`share`」 |

- LIR の `decref` と `drop` は、どちらも `decref` で実行する。実行時の動作も検査モードの規則も同じだからである。`unr` でない値に `decref` を出さない規則 (V1) は静的な検査で、実行時には区別しない
- `release` と `release_reuse` は、上の部品を組んだ一般の版である。VM は形の分かっている所では部品 (`is_unique`、`is_last`、`decref`、`free_block`、`into_token`) を直接並べ、一般の版は形の分からない所でだけ使う。Perceus の drop の特殊化と、Lean の reset/reuse の展開を、VM の命令の列で作れるようにするためである。形の分かっている `release` の展開は次のとおりである

  ```
  is_last(x)
    真: 残さない子を decref → free_block(x)
    偽: 残す子を dup → decref x
  ```

- 判定を `is_unique` と `is_last` の2つに分けるのは、上の「`share`」の、共有の親から `lin` の子が届く形のためである。rc −1 の物体は最後の参照なので、フィールドを `dup` せずに受け取ってよい (`is_last`)。しかし共有の印を持つので、reuse もその場の書き換えもしない (`is_unique` は偽)
- `keep` は、走査する語ごとに残すかどうかを持つ
- 解放の連鎖は、ヒープが持つ作業リストの `Vec` を使い回してたどる。再帰しないので Rust のスタックを溢れさせず、解放のたびに確保もしない。物体を解放するときは、子を走査の逆の順に1つずつ `decref` し、0 になった子を作業リストに積み、`Foreign` なら破棄処理を呼んでから箱を空ける。逆の順に積むのは、最初のフィールドを先に、最後のフィールドを後に解放するためである。cons セルの物理的な形が要素を前に、残りのリストを後に置くなら、要素を解放し終えてから残りのリストに進むので、要素が物体のリスト (`List (Int, Int)` など) でも作業リストの長さが定数に収まる。cons セルの物理的な形は S9b で決めるので、この性質は S9b の形で確かめ直す
- 写す操作 (共有されたクロージャの中身を使うときの `copy`) は、クロージャの形と一緒に S9b で作る

## reuse

後の reuse analysis は、`release` を `release_reuse` に、それが空けた箱を使う `con` を `con@token` に書き換えて入れる ([ロードマップ](../../future/roadmap.md) の「処理系」の Perceus の最適化)。S9a は、その一意の道が次の命令の列になるように部品を用意する。

```
is_unique(x)
  真: 残さない子を decref → into_token(x)
      → コンストラクタが変わるか、lin ビットが誤って残りうるなら con_at で meta を書き、そうでなければ reuse_in_place
      → 変わったフィールドだけを書く
  偽: is_last(x)
        真: 残さない子を decref → free_block(x) → alloc してすべてのフィールドを書く
        偽: 残す子を dup → decref x → alloc してすべてのフィールドを書く
```

`is_last` の枝は rc −1 の物体 (共有の親から `lin` の子が届く形) のためにあり、そこでも箱は使い回さない。

- token の箱は中身を消さない。一意の道で「同じ位置の同じフィールドは書かない」特殊化 (Koka の reuse の特殊化) は、古いフィールドが箱に残っていることに頼るためである
- token にできるのは、種類の表で「token にできる」物体 (S9a では `Data`) だけである
- reuse の条件は、物理的な語の数が同じことである。型やコンストラクタが違ってもよい (cons の箱をタプルに使える。Koka と同じ)。語の数が同じ物体はいつも同じ級なので、級の刻み方は reuse に関係しない。検査モードが確かめられるのは級が同じことまでで、語の数が同じことはコンパイラが守る
- 共有の物体は reuse しない。`is_unique` が偽になるので、部品の側で特別に扱う必要はない
- token を継続のクロージャに入れない約束 (ロードマップ) はコンパイラが守る。検査モードは、破ったときに起きる2回の使用を見つける (下の「検査モード」)

## 検査モード

### モードの選び方

- モードは `Heap<M: Mode>` の型の引数で選ぶ。`Mode` は封じた trait で、`Fast` と `Checked` の2つがある。各操作は `if M::CHECKED { … }` で検査を書き、速いモードではこの分岐が単相化で消える
- 実行時の旗にしないのは、速いモードの RC の速い道に、検査のための分岐を1つも足さないためである。VM は2つのモードで単相化して2つ作る。ネイティブは、コンパイル時にどちらかを選ぶ
- 仕事の回数 (`rc_increments`、`rc_decrements`、確保の回数、生きている箱の数とその最大) は、検査モードだけで数える。速いモードは数える費用も持たない。S10 では、`RunStats` の回数の固定と UI テストを検査モードで走らせ、`bench/run.sh` の命令の数は速いモードで測ることになる。`RunStats` の各項目の VM での意味は、S10 の論点のままにする。OS から取ったページのバイト数だけは、両方のモードで数える (上の「確保と解放」)

### 前置き

- 検査モードでは、各ブロックがヘッダの前に1語の前置きを持つ。ポインタはどちらのモードでもヘッダを指すので、命令の側のコードは同じである
- 前置きは2つの `AtomicU32` (Relaxed) である
  - 1つ目は、普通の物体では所有者 ID、`alloc_immortal` の物体では参照の数 (下の「不死の物体の数え方」) である。不死の物体は持ち主を持たないので、同じ欄を使う
  - 2つ目は、状態 (生存、token、解放の3つ) と世代の番号 (残りのビット) である。世代の番号は、`into_token` と解放のたびに1つ進める
- 検査モードのどの操作も、rc を見る前に前置きを読む。解放した共有の物体は、最後の `decref` で rc が 0 になっているので、rc を先に見ると不死の物体と区別できないためである
- 検査モードは、解放したブロックを空きリストに戻さず、状態を「解放」にして残す。そのため、解放した物体の語を後で使っても、指す先はまだ確保したままのメモリで、UB にならずに見つけられる。大きい物体のページも、検査モードでは解放したときに返さず、`Heap` を落とすときに返す

### 検査モードの token

token はどちらのモードでも1語である。S10 の VM のレジスタと、後のネイティブの値の大きさを、モードで変えないためである。

- 速いモードの token は、箱を指す語か、空を表す語である
- 検査モードの token は、`Heap` が持つ token の表の添字を入れた語である。表の項目は、箱の語と、`into_token` のときの世代の番号の組である。項目は token を使ったときか `drop_token` のときに空ける
- token を使う操作は、表の項目を引き、箱の状態が token で、世代の番号が項目のものと同じことを確かめる。空けた項目の添字を使うことも誤りにする

番号を持つのは、多重の再開で起きる ABA の形を見つけるためである。たとえば、1回目の再開が `con_at(t)` で y を作り、y が後で一意になって `into_token` でまた token になったとする。箱の状態は token に戻るが、世代の番号は進んでいるので、2回目の再開が古い t を使うと番号の不一致で見つかる。

### 不死の物体の数え方

今の `eml_runtime` の検査付きヒープは、不死の物体の外に出ている参照を数え、数が 0 の物体へのどの操作も解放の後の使用として断る ([ランタイム](../../spec/runtime.md) の「不死の物体」)。今の不死の物体は子を持たない文字列のリテラルだけなので、この形で足りている。`eml_rt` の不死の物体は、`CodeBase` の定数のように子を持ちうる。親が子への参照を構造として持ち、親を作るときに `set_field` で子を書き、子を親から借りて読むので、同じ規則では正しいプログラムを断ってしまう。そこで、検査モードは数え方の役を次の形で引き継ぐ。

- 数えるのは、外に出ている参照、つまり `acquire_immortal` と `dup` で作り、`decref` で手放す参照だけである。不死の親が子に持つ参照は構造の一部で、数えない
- `alloc_immortal` の物体は、数を 0 にして作る。`acquire_immortal` が数を1つ増やし、`dup` が1つ増やし、`decref` が1つ減らす。数が 0 になっても解放しない
- 誤りにするのは、数が 0 の物体への `decref` (作っていない参照を手放すこと) だけである。読む操作 (`field`、`raw`、`scanned`) と `set_field` と `dup` は、数を見ない。`dup` を断らないのは、不死の親から借りた子を `dup` して所有するのが正しい形だからである
- リークの報告では、数が 0 でない不死の物体の数を、件数に足す
- ダミーは数えない (上の「ダミーの値」)。前置きの1つ目の欄を `u32::MAX` にして作り、この値の物体は数を変えも確かめもしない
- 速いモードでは、`acquire_immortal` は何もせず、不死の物体の `dup` と `decref` は rc 0 を見て何もしない
- 今の検査より弱くなるのは、数が 0 の不死の物体を読むことを断らない点である。不死の物体のメモリは解放されないので、読んでも UB にはならない。手放しすぎと手放し忘れは、`decref` の誤りとリークの報告で見つかる

### 報告する誤り

検査モードは次を `Err` で返す。

- 解放した物体の使用。どの操作も、前置きの状態が生存でない語を断る (token を受ける操作は、状態が token でない語を断る)
- 数が 0 の不死の物体への `decref` (上の「不死の物体の数え方」)
- `lin` ビットの立った物体への `dup`。`lin` の物体の rc は 1 なので、rc が 1 を超える誤りは、この `dup` で見つかる
- `lin` ビットの立った物体の共有の側の操作 (`release`、`decref`、`dup`)。`share` は `lin` の物体に印を付けないので、これは印付けの誤りである
- `share` のたどりで、同じ `lin` の物体に2回届くこと
- 所有者の不一致。正の rc の物体への `dup`、`decref`、`set_field`、`is_unique`、`into_token` が、今の worker ID と違う所有者の物体に対して行われたとき
- token の誤り。世代の番号の不一致と、空けた表の項目の使用 (同じ token の2回の使用と ABA の形)、token にできない種類の `into_token`、級の合わない `con_at`、`reuse_in_place` の `meta` の tag と scan と種類が箱と違うこと、`reuse_in_place` で箱が `lin` ビットを持ち新しい `meta` が持たないこと
- `free_block` を、破棄処理を持つ種類の物体に使うこと
- `release` と `release_reuse` で、物体のタグと `scan` が名指したものと違うこと
- 生存の列挙で見つかる不変条件の違反
  - 共有の物体から、共有でも不死でもない物体が届き、それが `lin` ビットの立った局所の物体でもないこと ([ロードマップ](../../future/roadmap.md) の「S9 共通ランタイム `eml_rt`」の「共有の物体から届くのは共有か不死の物体だけ」を、上の「`share`」の理由で広げたもの)
  - 不死の物体から、不死でない物体が届くこと。`share` は不死の物体でたどりを止めるので、不死の物体の子が局所なら、印なしに別のスレッドから届く。Koka の PR #910 の誤りがこの形である (ロードマップの S9 の論点)
- リーク。生きている不死でない物体と、使われずに残った token を、種類の名前ごとに数える。token は種類の名前 `Token` で数える

### 論理的な worker ID

- `Heap` は今の論理的な worker ID を持つ。確保した物体の所有者を今の ID にする
- 物理的な worker が1つでも所有者の検査を働かせるために、ID を切り替える操作を持つ。S9a では単体テストだけが切り替える。UI テストで効き始めるのは `par` を入れたときである

## `unsafe` と同期の層

- `unsafe` は小さい核に閉じる。核は、確保器、ヘッダとフィールドの読み書き、`dup`、`decref`、解放の連鎖、token の操作である。それ以外 (`share` のたどり、`release` の組み立て、生存の列挙) は核の操作を呼んで書く
- atomic とページの確保を薄い層 (`sync` の module) の裏に置き、`cfg(loom)` で loom の型に差し替えられるようにする。tokio の `src/loom/mod.rs` と同じ形である
- loom の atomic は `i32` と同じ配置でなく、生のバイトから作れない。そこでヘッダは `Header::new` で作って `ptr::write` で置き、大きさは `size_of::<Header>()` で数える。こうすると、loom のビルドでもヒープのコードはそのまま組み立てられる。S9a では、`RUSTFLAGS="--cfg loom" cargo check -p eml_rt` が通ることまでを確かめる。loom の試験 (RC と公開の手順のモデルを、`sync` の層の関数の上で書くもの) は、VM の並列化のときに書く
- 核では SeqCst と `fence` を使わない

## 受け入れる制約

| 制約 | 理由 |
|---|---|
| 1つのデータの型のコンストラクタは 65536 個まで | `tag` を 16 ビットにするため |
| 物体の種類は 16 個まで | `info` の4ビットにするため |
| 64 ビットの環境だけを対象にする | 語を 8 バイトにするため |
| 速いモードでは、解放の後の使用、token の2回の使用、`File` の参照の重複を検出しない | 速い道に検査を置かないため。`lin` の物体の rc は 1 なので、その `dup` は速い道を通る。検出は verifier と、検査モードで走らせる UI テスト (S10 から) に任せる。今の `eml_runtime` は、解放の後の使用を世代番号で、`File` の重複を `Heap::dup` で、`debug_heap` によらず常に検出しているので、S10 からはどちらも `--debug-heap` のときだけになる。[ランタイム](../../spec/runtime.md) と [LIR とインタプリタ](../../spec/lir.md) の「実行時エラー」の該当の文は、S10 で改める |
| 小さい物体のページを、実行中に OS へ返さない | S9a を小さく保つため。空きリストは級ごとなので、使う量は級ごとの生きていた量の最大の和で抑えられる (2 語の物体が多い時期の後に 4 語の物体が多い時期が来ると、両方の分を使う)。上の「ページ」のとおり、後で入れる |
| 局所の数が `i32::MAX` に達した物体と、共有の数が `DROP_LIMIT` を下回った物体は解放されない | 張り付きの方式による。物体を 2^31 − 2^17 回参照するには、参照だけで 16 GiB 近くが要る |
| 検査モードでは、使うメモリがそれまでに確保した量の合計になる | 解放したブロックを使い回さないため。生存の列挙とリークの検査の時間も、確保した量の合計に比例する。UI テスト、`bench.rs`、`--debug-heap` の実行が検査モードで動くので、確保の多いプログラムではメモリが増える。足りなくなったら、隔離する量に上限を付ける |
| 検査モードでは、前置きの分だけブロックが大きくなる | 速いモードでちょうど 128 語の物体は、検査モードでは大きい物体の道を通る。2つのモードの確保器の道は、境目の大きさで違う |

## 検証

### 単体テスト

`crates/eml_rt` に単体テストを置く。テストの関数はモードを型の引数に取り、`Fast` と `Checked` の両方で同じ列を流す。検査モードだけのテストは、誤りを1つ起こす最小の列を誤りごとに1つ置く。

- 語: 即値の往復、63 ビットの境界の `alloc_int` と `unbox_int`、ダミー、`Word` と `Heap` の `Send` / `Sync` の型の assert
- 確保器: 級ごとの確保と解放、大きい物体の確保と即時の返却 (ページの一覧から外れること)、ページをまたぐ量、空きリストの使い回し (速いモード)、解放したブロックを使い回さないこと (検査モード)、今のページを替えた後と替える前の両方での生存の列挙、`Heap` を落とすときの `Foreign` の破棄処理、使っているメモリのバイト数
- RC: 局所の上限、共有の2つの境目のそれぞれの前後、不死、不死の物体の数え方 (子を持つ不死の物体を作ること、借りた子の `dup` と `decref`、数が 0 の `decref` の誤り、ダミーを数えないこと)
- 解放の連鎖: 長いリスト (要素が即値のものと、要素が物体のもの。作業リストの長さが定数に収まる)、深い木、`scan` が 255 の物体、`Foreign` の破棄処理が1回だけ呼ばれること
- `share`: 輪のあるグラフ、`lin` の物体の子のたどり、`lin` ビットのない親の中の `lin` の子、不死と共有の物体で止まること、`share` の後の共有の側の `dup` と `decref` と最後の解放、rc −1 の親の `release` が `lin` の子を `dup` しないこと
- `release` と `release_reuse`: 一意な場合、rc −1 の場合、共有の場合、`keep` の組み合わせ。部品を並べた展開 (`is_last` と `free_block`) でも同じ場合を流す
- reuse の列: 手で組んだ「解放して、同じ箱でコンストラクタを作る」列を2種類流す。同じコンストラクタでフィールドを書かずに使い回す列と、型の違う同じ大きさの箱に移る列である。生きている箱の数と RC の釣り合いを確かめ、共有の物体が token にならないことも確かめる
- 検査モードの誤り: 上の「報告する誤り」の各項目。token の ABA の形と、解放した共有の物体の使用を含む

### Miri

- flake に nightly の toolchain の入力 (rust-overlay か fenix) を足し、nightly と `miri` と `rust-src` を持つ別の devShell `nix develop .#miri` を作る。ふだんの devShell と `nix build` は今の stable のままにする
- `cargo miri test -p eml_rt` を、`MIRIFLAGS="-Zmiri-strict-provenance"` で1回、`MIRIFLAGS="-Zmiri-strict-provenance -Zmiri-tree-borrows"` でもう1回流す
- ページの大きさは Miri でも変えない。ほかの crate は Miri で流さない

### Kani

次の4つのハーネスを `#[cfg(kani)]` で置く。どれも逐次のハーネスである。Kani は並行のコードを逐次として扱うためである。共有の側の2つの境目の並行の議論 (上の「上限」) は、Kani では確かめられないので、文書の議論と、後の loom の試験に任せる。

1. ヘッダと語の詰め方: `meta` の詰めと取り出しの往復、即値の往復と 63 ビットに収まるかの判定
2. RC の遷移: 任意の i32 から始めて、任意の長さ k (有界) の `dup`、`decref`、印付け (`share` の1物体分) の列を、上の「遷移の関数」に流す。理想のモデル (数と張り付きの旗) と比べ、張り付いていない間は符号を除いた rc が数に一致すること、数が 0 になったときだけ解放すること、張り付いた物体は解放しないことを確かめる。張り付きの旗は、局所の rc が `MAX` になったとき、または共有の rc が `DROP_LIMIT` より小さくなったときに立つ。逐次の列では、共有の rc が `DUP_LIMIT` 以上 `DROP_LIMIT` 未満の間も `dup` は数えるが `decref` は飛ばすので、そこはもう張り付いたものとして扱う。始めの値には、局所の `MAX` の前後と、共有の2つの境目の前後を含める
3. `share`: 物体が4つまでの有界なグラフのモデルで、根から届く `lin` でない局所の物体がすべて共有になること、届かない物体が変わらないこと、数が保たれること、`lin` の物体の所有者が移ることを確かめる。グラフは rc と辺の数が合うもの (`lin` の物体には辺が1本だけ入る) に限る
4. `release` と `lin` ビットの規則: 一意か rc −1 か共有か、`keep`、`lin` ビットの組み合わせで、手放す数と残す数と、検査モードの誤りの判定を確かめる。一般の `release` と、上の「核の操作」の展開した `release` と、「reuse」の命令の列が、同じ結果になることも確かめる。`reuse_in_place` の `meta` と `lin` ビットの照らし合わせも含める

Kani は、計画の最初の作業で Nix と macOS aarch64 で動くかを試す。動かなければその時点で報告し、代わりの確かめ方を相談して決める。動いたときの導入の方法 (devShell に入れるか、`cargo kani setup` に任せるか) も、その試しで決める。

### 計測

速いモードの計測用のプログラムを `crates/eml_rt/examples/` に置き、release ビルドの `instructions retired` を測る。測るのは次の3つである。

- cons セルのリストを作って捨てる。同じことを `std::alloc` を直接使った `Box` のリストで行い、並べる
- 局所の物体の `dup` と `decref` の繰り返し
- `map` に当たるリストの作り直しを、reuse の部品を使う列と使わない列で行う。reuse analysis はまだないので、列は手で組む。reuse の効果の見込みを、パスを作る前に数字で持つためである

結果は [計測の基準](../../implementation/benchmarks.md) の「記録」に「S9a (`eml_rt` の核)」として足す。測り方は `bench/run.sh` と同じ `/usr/bin/time -l` で、`bench/rt.sh` にまとめる。
