# ロードマップの組み直しの設計

位置づけ: 作業用の設計文書。組み直しを終えたら削除する。

## 目的と範囲

将来の方針に次の4つを足し、今後の実装をマイルストーンの列に組み直す。

- アドホック多相 (`Int` と `Float` での演算子の共有など)
- REPL (Prelude と標準ライブラリに加え、指定したモジュールを読み込んだ環境での対話実行)
- バイトストリーム、配列、バッファード IO の intrinsic
- UTF-8 処理の標準ライブラリ

並べる軸は「型システムの実験を先にする」である。順序を付けるのは、4項目とその前提になるマイルストーン、それに今の S2 と S3 の残りまでとする。ネイティブ化、マルチコア、LSP、salsa、借用などは、マイルストーンの後の項目として分野別の一覧に残し、前提だけを書く。各項目に書くのは方針と論点までで、細かい設計は各マイルストーンに着手するときの spec で行う。

成果物は文書とコメントの変更だけである。コードの振る舞いとテストの期待値は変えない。

## 用語

M2〜M9 を「マイルストーン」と呼ぶ。M1 (マイルストーン1) と同じ呼び方である。docs では「段階」がパイプラインの段階 (crate) を指すので、M の列には使わない。

## マイルストーンの列

S2 を M2 と M3 に分け、名前を M の通し番号にそろえる。

| マイルストーン | 中身 | 前提 |
|---|---|---|
| M2 モジュール | import をたどるローダ、`pub`、修飾名、モジュールとしての Prelude、`T(..)`、import の循環を許すかどうかの決定、複数ファイルの UI テスト。参照ごとの具体化の表を作り、今の `==` を振る舞いを変えずにそれに通す。同じ名前の別の型を区別して表示する | なし |
| M3 レコード、リスト、文字列 | 名前付きのレコードと `type`、row の仕組みを sort 付きの1つにする、射影と更新の線形性、`t.0`、レイアウト規則3と `with` の衝突、借用のオペランドと `Field`。リストのリテラルと `::`。補間 (穴は `String` に限る)、複数行の文字列、raw 文字列、lexer のモード | M2 |
| M4 数値と文字 | `Float` と `Char` の型、リテラル、Prelude の演算。`+ - * < <= > >=`、`==`、前置の `-` を組み込みの型ごとに解決する | M2 |
| M5 型クラス | 構文、検査、特殊化による変換、Prelude のクラス、`deriving`、タプルとレコードの構造的な instance、補間の穴を表示用のクラスに広げる | M3、M4 |
| M6 REPL | Prelude と指定したモジュールを読み込んだ対話実行。M8 の後は標準ライブラリも読み込む | M2、M5 |
| M7 バイト列と入出力 | `Byte`、ビット演算、`Bytes`、`Array`、`Lin` のハンドルとバッファ付きの読み書き | M5 |
| M8 UTF-8 と標準ライブラリ | UTF-8 の核の intrinsic、eml で書く最初の標準ライブラリのモジュール、ストリーム処理のエフェクト | M4、M7 |
| M9 コマンドリテラル | コマンドリテラルの CST と lexer のモード、`Cmd` と `Proc` | M3、M8 |

順序の理由は次のとおり。

- M2 を最初に置くのは、M2 で作る参照ごとの具体化の表が、M4 の演算子の解決と M5 の instance の証拠の表になるためである。型名を区別して表示することと、import の循環の決定も、M5 の前提になる
- M3 を M4 の前に置くのは、S2 の残りを一続きで終えるためである。M4 が必要とするのは M2 だけなので、入れ替えても依存は崩れない
- M4 で、型クラスより先に組み込みの型だけの多重定義を入れる。M5 と同じ曖昧さの規則を使うので、曖昧さの規則に伴うテストの振る舞いの変更 (種類1) への合意は M4 の1回で済む。M5 にも、比べられない型の診断を instance がない診断に置き換えるなど、別の種類1の変更が残る
- M6 を M5 の直後に置くのは、REPL が値を表示用のクラスで表示でき、その場しのぎの表示器が要らないためである。また、M7 以降を REPL で試しながら作れる
- M7 を M5 の後に置くのは、`Byte` と `Int` で演算子を共有するためである

## 各マイルストーンの方針と論点

roadmap.md のマイルストーンごとの節には、この節の内容を「中身」「決めたこと」「論点」の形で書く。

### M2 と M3

- 決めたこと: 中身は上の表のとおり。M2 は今の `Int`、`String`、`Bool` の `==` を具体化の表に移すだけで、振る舞いを変えない。M3 の補間の穴は `String` に限り、M5 で表示用のクラスに広げる
- 論点: 今の `status.md` の「S2 の材料」の「決めること」と「作るもの」を、次のとおり M2、M3、M9 に振り分けて移す
  - M2: 参照ごとの具体化の表と `==` の比べ方の一般化、同じ名前の別の型の表示、import の循環とモジュールの根、import をたどるローダ、複数ファイルの fixture、ディレクトリを1件とする UI テスト、`T(..)` の規則
  - M3: sort 付きの row、名前付きのレコード (`type` を含む) とその実行時の表し方、lexer のモードのスタックと補間のトークン、未対応のリテラルの E0004 の出し方、レイアウト規則3と `with`、借用のオペランドと `Field`、`::` の fixity、補間とリストとレコードの CST、`t.0`、射影と更新の線形性の規則
  - M9: コマンドリテラルの CST

### M4 数値と文字

- 決めたこと
  - リテラルは単相にする。整数のリテラルは `Int`、浮動小数のリテラルは `Float` である。`fromInteger` 相当の脱糖も defaulting も入れない。`Int` と `Float` を混ぜるときは明示的に変換する
  - `Char` は Unicode のスカラー値である
  - `+ - * < <= > >=`、`==`、前置の `-` (`negate`) を、組み込みの型ごとに、本体の終わりで解決する。算術は `Int` と `Float`、順序の比較は `Int`、`Float`、`Char` に使える。`String` の順序の比較は M5 の `Ord` で入れる。何も型を決めないオペランド (使われない `let sq = fn x -> x * x` など) は、`Int` に倒さず曖昧さのエラーにする。この規則は M5 の型クラスと同じである
  - この規則に伴うテストの振る舞いの変更 (曖昧さのエラー、型の不一致の文言、E2006 の注記、`equality.rs` の連鎖を抑える規則) は種類1で、M4 の spec に挙げて合意を取る
- 論点: 型ごとの意味。`Float` の `/` と `%` の有無、`Float` の `==` と NaN の結果、`Float` をリテラルのパターンと `switch` から外すこと、多相な位置での `Int` と `Float` のネイティブの表現

### M5 型クラス

- 決めたこと
  - 表面は Haskell 98 の形の単一引数の型クラスにする。`class`、`instance`、上位クラス、`deriving` を持つ。instance の頭は、`data` の型コンストラクタに互いに異なる型変数を適用した形に限る。高カインドのクラス、多引数のクラス、関連型、`Add<Rhs, Output>` 形の演算子のトレイトは入れない
  - 実装は、制約に沿った特殊化にする。型検査が、制約を持つ名前の参照ごとに証拠 (どの instance を使うか) を記録し、Core IR への変換は、制約を持つ関数を確定した証拠ごとに複製する。制約のない関数は今と同じく1回だけ変換する。実行時の辞書は持たない。そのため、実行時、Value、Perceus、verifier、`debug_heap`、マルチコアの設計は変わらない。組み込みの instance のメソッドは PrimOp に変換するので、単相のプログラムの Core IR はほぼ今のままである。変わる部分は M5 の spec に種類2の変更として挙げる
  - エフェクトの操作のシグネチャと `data` のコンストラクタのフィールドには、制約を書けない。書けると、handler の節が perform の位置で選んだ証拠を実行時に受け取る必要が生じ、実行時の辞書が要るためである
  - 証拠が循環に沿って大きくなる制約付きの多相再帰 (入れ子のデータ型の `Show` など) は、型検査で弾く。これにより、すべての診断が検査の段階から出る。辞書渡しは、この形のためだけに後で足す余地として残す
  - 一貫性を守る。instance は大域的に1つで、クラスか頭の型コンストラクタを定義したモジュールにだけ書ける (モジュール単位の orphan 規則)。重なる instance、局所的な instance、第一級の instance は持たない。instance は名前ではないので、修飾付きの import によらず見える
  - 制約はトップレベルのシグネチャへ推論で足さない。解けない制約と曖昧な制約はエラーにする。単相性制限と defaulting は持たない
  - 線形性は Kind のままにする。`Copy` や `Drop` のようなクラスは作らず、Kind は instance の選択に関わらない
  - レコードとタプルには、処理系が `Eq` と表示用のクラス (タプルは `Ord` も) の構造的な instance を与える。ユーザーのクラスはレコードに instance を持てない
  - クラスとエフェクトは別の仕組みである。メソッドの row は普通のシグネチャと同じ規則に従う。Prelude のクラスは純粋なので、`par` の中でも演算子を使える
  - Prelude のクラスは `Eq`、`Ord`、`Num` (前置の `-` を含む)、表示用のクラスとする。`String` の順序はバイト順で、妥当な UTF-8 ではコードポイント順と一致する
  - 補間の穴は表示用のクラスに広げる。`String` の穴は今と同じく引用符なしで入る
  - M5 で `=>` を予約の記号に、`deriving` をキーワードにする。今は `=>` をユーザーが演算子として定義できるので、これは種類1の変更である。それまで [字句](../../spec/lexical.md) の予約語と予約記号は変えない
- 論点
  - クラスの形: 除算のクラス (instance ごとの小さなクラスにするか、`Integral` / `Fractional` に分けるか)、`Ord` のメソッドを `< <= > >=` にするか `compare` と `Ordering` にするか、`!=` を `Eq` のメソッドにするか普通の関数にするか、`negate` をユーザーに見せるか、既定のメソッドをいつ入れるか、表示用のクラスを `Show` 1つにするか `Show` と `Display` に分けるか、`Float` の `Eq` / `Ord` の法則、レコードの `Ord` のラベルの順
  - Kind: メソッドの Kind を位置ごとにどう決めるか、instance のメソッドが推論した Kind の制約をクラスのメソッドの Kind と照らす規則、畳み込みのメソッドで `Lin` の累積値を持てるか、借用が入った後の `Lin` 型のクラス
  - 導出: 導出した instance で比べないフィールドを `drop` する形
  - 表示: 持ち越しの制約の表示 `a => <e> <= Once` ([型と Kind](../../spec/types.md)) を `=>` と重ならない形に変える。型検査のダンプだけに出るので、種類2の変更である
  - その他: 接頭辞付きリテラルの穴の型付けに多引数のクラスが要るか、多相再帰のための辞書渡し、複製の数の報告、orphan 規則をパッケージ単位に広げるか

### M6 REPL

- 決めたこと
  - Prelude と指定したモジュールを読み込んだ環境で、対話的に実行する。M8 の後は標準ライブラリも読み込む
  - 入力は、定義の追加か式の評価である。式は、まず row が `<IO>` に収まるものに限る
  - 入力をまたいで残せるのは `Unr` の束縛だけで、`Lin` の値はその入力の中で使い切る。今の線形性の検査をそのまま使える
  - orphan 規則では、セッションを1つのモジュールとみなす。後の入力で定義し直すと、変わるのはそれより後の入力だけである
  - 結果は表示用のクラスで表示する。特殊化の複製はキャッシュする
  - コマンドは GHCi に寄せる (`:load`、`:type`、`:quit` など)
- 論点: シグネチャのない定義を単相にするか REPL だけ一般化するか、`IO` 以外のエフェクトを既定の handler で許すか、編集したモジュールの読み直し、定義し直した型の表示、セッションの表し方 (1つの伸びるモジュールか、モジュールの鎖か)

### M7 バイト列と入出力

- 決めたこと
  - `Byte` (0〜255) を専用の型にする。ビット演算のクラスと演算子と fixity を Prelude に足し、`Int` と `Byte` で共有する
  - `Bytes` は `Unr` の値である。`Array a` の Kind は要素の Kind に従う。どちらも意味は不変で、更新は、RC が 1 ならその場で書き換え、そうでなければ写す。分割と結合、並列の書き換えのための `Lin` の `MutArray` と `freeze` は、マイルストーンの後の項目として後で足す
  - ハンドルは `Lin` にする。`Stdin` / `Stdout` / `Stderr` は別の型にする。バッファ付きの読み書きもハンドルにする。intrinsic は、ハンドルに対する read/write の操作にとどめる
- 論点: `Byte` のリテラルの書き方 (リテラルは単相なので、`Byte` を書く形が要る)、`Byte` の算術のオーバーフロー (実行時エラーか wrap か)、範囲外の添字を実行時エラーにするか `Option` にするか、中断のときに書き込みのハンドルを flush するか、`println` と `Stdout` のハンドルの関係、`Lin` の要素を持つ `Array` の API、マルチコアでのハンドルの扱い

### M8 UTF-8 と標準ライブラリ

- 決めたこと
  - `String` は常に妥当な UTF-8 である
  - intrinsic は小さい核にとどめる。検証付きのデコード (`Bytes` から `String`)、エンコード、バイト長、バイト位置から `Char` と次の位置を読む操作、境界を検査する切り出しである
  - 分割、検索、反復などは、eml で書く最初の標準ライブラリのモジュールにする
  - 「行を流す」などのストリーム処理は、ユーザー定義のエフェクトとして、このモジュールの中に書く
  - 書記素クラスタと正規化は対象外にする
- 論点: 位置の単位 (バイト位置を不透明な型にするか)、不正な UTF-8 の扱い (エラーか置換か)、大文字と小文字の変換など Unicode の表が要る操作を intrinsic にするか対象外にするか

### M9 コマンドリテラル

- 決めたこと: 今の S3 の中身 (コマンドリテラルと、標準ライブラリの `Cmd` / `Proc`) と、コマンドリテラルの CST を移す
- 論点: [標準ライブラリへの申し送り](../../future/stdlib.md) の `Cmd` の項目のとおり

## アドホック多相の方式を選んだ理由

ネイティブ化とインタプリタの効率を重視し、Haskell の型クラスを第一の候補として次の案を比べた。

| 案 | 結論 |
|---|---|
| 型クラス + 辞書渡し (GHC) | 採らない。インタプリタで `+` が PrimOp 1つから、辞書の取り出しと間接呼び出しになる。実行時に辞書の値、射影の Rhs、借用の扱いが要る |
| 辞書渡し + 既知の instance の静的解決 + 特殊化 | 採らない。無償になるのは文脈のない instance だけで、`List Int` の `==` や導出した instance は辞書を通る。辞書の仕組みと複製の仕組みを両方持つことになる |
| Rust のトレイト + すべての総称の単相化 | 採らない。row は単相化できず、仕組みが2本になる。多相再帰を検査の段階の後で弾くことになる |
| 組み込みの型だけの多重定義 | M4 の中継ぎとしてだけ使う。ユーザー定義の型に広げられない |
| 暗黙の引数 (Koka、modular implicits) | 採らない。修飾付きの import と衝突し、型クラスのまとまりも失う |
| クラスをエフェクトで表す | 採らない。row を汚し、解決が動的になる |
| **型クラス + 制約に沿った特殊化** | **採る** |

採った案が成り立つのは、eml の型が rank-1 で、シグネチャが必須で、局所的な `let` とラムダが単相で、局所的な instance も第一級の instance もなく、操作とコンストラクタが制約を持たないためである。この条件では、制約のない本体での制約付きの参照は、すべて確定した証拠を持つ。Roc (RC とその場の更新の実行系) と Austral も型クラスや abilities を特殊化で実行するが、どちらも総称をすべて単相化する。eml の案は、制約を持つ関数だけを複製し、制約のない型変数を今の一様な表現のまま残す。そのため、row の多相にも触れない。代償は、弾く多相再帰と、複製の分だけ増えるコードの大きさである。REPL では、新しい型で総称を使うたびに複製を1つ変換するが、かかるのは Core IR への変換だけである。

## 名前の置き換え

S1、S2、S3 という名前をやめ、M の通し番号だけにする。置き換えは、参照が指す中身で決める。中身を名指しする行は、総称の行より優先する。1つの参照が複数のマイルストーンにまたがる中身を並べているときは、マイルストーンごとに分けて書く (例: 「M3 と M9 で lexer と一緒に作り直す」、札なら「(M2、M3)」)。

| 今の参照の中身 | 置き換え |
|---|---|
| S1 | M1 (「S1 で実装した文法」は「M1 で実装した文法」) |
| import、モジュール、`pub`、修飾名、Prelude のモジュール化、`T(..)`、ローダ | M2 |
| 名前付きのレコード、`type`、射影と更新、リスト、`::`、補間、複数行の文字列、raw 文字列、lexer のモード、`t.0`、`Field`、レイアウト規則3、`{…}` と `[…]` の読み飛ばし | M3 |
| 浮動小数と文字 | M4 |
| S3、コマンドリテラル | M9 |
| 「S2 と S3 の構文」のような総称 | 「未実装の構文 ([文法](../../spec/grammar.md) の『実装の段階』に挙げたもの)」 |

例として、`crates/eml_hir/src/lower/expr.rs` の「S2 で実装するリテラル」は、浮動小数、文字、複数行の文字列、raw 文字列を並べているので、「M3 (複数行の文字列、raw 文字列) と M4 (浮動小数、文字) で実装するリテラル」にする。

`crates/eml_syntax/tests/corpus.rs` と `crates/eml_syntax/tests/corpus/s1.em` は変えない。ファイル名 `s1.em`、定数 `S1`、テスト名 `s1_corpus_*`、`s1.em` の先頭のコメントは、M1 で入れた構文のコーパスの名前として残す。テストの名前とファイルを動かすのは振る舞いの変更 (種類1) にあたり、この作業の目的に見合わないためである。`corpus.rs` のほかのコメント (「S2・S3 の構文は E0004 だけを出し」など) は、期待値を変えない機械的な変更 (種類3) として、この作業の計画に挙げて直す。
