# S8b 所有の形と基本操作の借用

位置づけ: 作業の設計。ロードマップの S8 の2つ目の作業を定める。S8b を終えたら、決まったことを `docs/spec/` と `docs/implementation/` に移し、この文書を削除する。

## 目的

Perceus を「フィールドを死ぬ所で手放す形」にし、`Lin` の物体の RC が常に 1 になるようにする。あわせて、基本操作の引数のうち基本操作が自分では物体か文脈に入れないものを借用にし、`File` の物体の参照の数が 1 を超えたら実行時の誤りにする検査を入れる。

完了の条件は次の4つである。

- 全 UI テストが `debug_heap` 付きで通り、出力は変わらない
- どのテストでも、`File` の物体の `dup` は起きない (下の「`File` の実行時の検査」が誤りにする)。今の Perceus では、`tests/ui/run/files/file_in_data_kept_by_a_later_row.em` がこの `dup` を起こす
- 新しい Perceus の出力が、LIR の所有の段の verifier を通る
- テストの成否と期待値は、下の「テストの変更」に挙げたものだけが変わる

## S8 の分け方の改め

S8a の前に、S8 を S8a と S8b の2つに分けた。S8b の設計で、Kind の印に `eml_types` が解いた Kind を書き出す作業が要ると分かったので、S8 を3つに分け直す。ロードマップの段の列では S8 の1行のままにする。

| 作業 | 中身 |
|---|---|
| S8a (終えた) | LIR の crate、パスを LIR に移す、CEK が LIR を読む |
| S8b (この文書) | Perceus の所有の形、基本操作の引数の借用、`File` の実行時の検査 |
| S8c | `eml_types` の Kind の書き出し、translate と EP と box の挿入の Kind の印、extern の行の Kind の列、V1 と V2、テキストの形の印 |

分け直す理由は次のとおりである。

- 書き出す型 (`TypeKind::Fn`) は矢印の線形性を持たず、`KindScheme` は `eml_types` の外から読めない ([コンパイラの構成](../../implementation/architecture.md) の「`eml_types` の内部」)。型だけから印を決めると、関数型の変数がすべて `poly` になり、`twice f x = f (f x)` の `Unr` のクロージャ `f` の `dup` まで V1 が拒む
- そのため S8c には、解いた Kind を後の段階へ書き出す作業が要る。「後の段階は線形性を読まない」という決まりを反転するので、それだけで1つの spec になる大きさである
- S8b の目標 (`Lin` の物体の RC は 1) のうち `File` の物体そのものは、V1 がなくても実行時に確かめられる (下の「`File` の実行時の検査」)。`File` を含む `Lin` のデータとクロージャは、S8c の V1 で静的に覆う

## 所有の形

### 言葉

- 親とスロット: `switch` の case と `unpack` が束縛したフィールドの変数の、分解した値 (親) とフィールドの位置 (スロット)
- 持ち主: verifier の「持ち主」と同じ規則で、束縛の時点で決める ([LIR とインタプリタ](../../spec/lir.md) の「verifier」)。親が束縛の時点で所有されていれば親、そうでなければ親の持ち主である。後で親が所有になっても、持ち主は変わらない
- o に属する変数: 持ち主が o で、その位置で借用 (所有の数が 0) の変数
- 必要な変数: ある命令の位置で、その命令の後で生きている変数と、その命令が使う (消費するか読む) 変数

親、スロット、持ち主は、変数が関数の中で1回だけ定義される (R5) ので、verifier と同じく関数全体の表に持つ。経路ごとに持つのは、所有の変数の集合と、下の「保持」の集合だけである。

### 状態

Perceus は、今と同じくブロックを番号の順に1回たどる。各ブロックでは、後ろから各命令の後の生存を求め、前から状態を持って命令を足す。

- 関数の入口と合流するブロックは、今と同じく、入口で生きている RC の対象の変数と RC の対象の引数をすべて所有して始まる。借用の変数はない
- `switch` の行き先は、`switch` のブロックを前からたどり終えた状態を引き継ぐ。case のフィールドは、借用の変数として加わる
- 保持: 所有していて生きていないが、生きている変数が属している変数。下の「持ち主を手放す時点」で手放す

### 所有を取る時点

借用の変数 v の所有を取るのは、次のどれかに当たるときだけである。

1. v を消費する (呼び出し、`apply`、`clause` の引数と呼ぶ値、`con`、`closure`、`extern`、消費する基本操作の引数、`drop`、`return`、`tail`、`jump` の実引数)
2. v が呼び出しの後で生きている。フレームは借りた値を持てないため (R7)
3. v が `jump` の行き先の入口で生きている。合流するブロックは所有だけで始まるため
4. v の持ち主 o の最後の所有の参照を、ある命令が消費し (o がその命令の後で生きていない)、v がその命令の後で生きている。たとえば `| Box s -> (Some b, s)` の `con Option #1(b)` は、b を消費した後に s を使う

`switch` の scrutinee、`unpack` の値、`unbox` のオペランド、借用の基本操作の引数 (下の「基本操作の引数の借用」) は読む使いなので、借用の変数のまま使う。

所有の取り方は、v の持ち主 o で決める。

- o がその命令で必要なら、命令の前に `dup v` を置く。o はまだ所有されているので、v は有効である。4. はいつもこの場合である
- o が必要でない (保持されている) なら、命令の前で o を解く (下の「持ち主を解く」)

1つの命令で必要な所有の取り方 (`dup` と「持ち主を解く」の命令) は、その命令を消費の数で数える `dup` (今の規則。同じ変数を2回以上消費するときと、消費した後も生きているとき) より前に置く。所有を取った後の変数は、ほかの所有の変数と同じに扱う。

### 持ち主を解く

保持されている o を解くときは、次の順に命令を置く。

1. o に属する変数のうち、必要なものの集合を N とする
2. o の各スロットに、名前を書く代表の変数を1つ決める。そのスロットを束縛した変数のうち、N に入るものか、親をたどると N の変数に着くものから、番号のいちばん小さい変数を選ぶ。同じスロットを2つの変数が束縛するのは、同じ値を2回分解する形 (射影の繰り返し、`p.name ++ p.name`) である
3. N の変数 g で、次のどれかに当たるものに `dup g` を置く。o はまだ所有されているので、g は有効である
   - g から親をたどって o に着くまでの間に、N の変数か、すでに所有になった変数がある。間の変数はこの後も必要か、すでに所有されているので、`release` でその変数から受け取れない
   - g から親をたどる道の途中に、代表でない変数がある
4. `release o L #t(..)` を置く。各スロットに書くのは、代表が N に入るか、代表の子孫に 3. で `dup` していない N の変数があるときの、その代表である。名前を書くスロットがなければ `decref o` にする
5. 4. で名前を書いた代表のうち N に入らないもの (子孫のためだけに受け取ったもの) について、同じく 2. から 4. を当てる。親から子の順に、N の変数がすべて所有になるまで続ける

親から順に手放すのは、上の物体を先に一意にすると、`release` が一意の側を通り、子の参照を増やさずに受け取れるためである。今の Perceus の入口の順 (親を先に手放す) と同じ考え方である。

### 持ち主を手放す時点

- 所有していて生きていない変数は、属している生きている変数がなければ `decref` し、あれば保持する。いつ確かめるかは次のとおりである
  - ブロックの入口: 今と同じく、変数の番号の順に `decref` する。`switch` の行き先でも同じで、scrutinee が借用の変数のときは、その持ち主が保持の対象になる
  - 各命令の直後: その命令で死んだ所有の変数 (定義して使わない変数、`unbox` のオペランドなど読む使いの後に死ぬ値を含む)
  - 保持されている o に属する生きている変数が、最後の1つまで死んだ命令の直後: `decref o`
- `jump` の前: 3. のとおり行き先で生きている借用の変数をすべて所有にした後、保持されている変数は属する生きている変数を持たないので、`decref` する。合流するブロックに入るすべての辺で、所有の集合が入口の生存集合と一致する
- `return` と `tail` の前: 保持されている変数をすべて `decref` し、所有を残さない
- 呼び出しの前: 2. のとおり、呼び出しの後で生きている借用の変数をすべて所有にするので、保持されている変数が呼び出しをまたぐことはない。`saved` の求め方は今と同じで、借りた変数は入らない

### 時間

親、スロット、持ち主を関数全体の表に持つので、経路ごとの状態は所有と保持の集合だけである。`switch` の行き先へ状態を写す時間は、今の Perceus が行き先ごとに所有を写す時間と同じく、辺の数と所有の大きさの積に比例する。「持ち主を解く」の 2. と 3. は、o に属する変数とその親の道をたどるので、時間は o に属する変数の数と分解の入れ子の深さの積で抑えられる。長い借用の `switch` の連なりで Perceus と verifier が線形の時間で終わることを、下の新しいテストで確かめる。

### `Lin` のフィールド

型の正しいプログラムでは、`Lin` のフィールドの持ち主も `Lin` である。データの Kind はフィールドの Kind の上限で決まるためである ([型と Kind](../../spec/types.md) の「Kind」)。`Lin` の持ち主は分解した後に使われないので、所有を取る時点のどれでも、持ち主は必要でなく解かれる。フィールドは `release` で受け取られ、`dup` されない。今の Perceus が `dup` していた形 (後の行が分解した値を束縛する決定木の途中の行き先) では、フィールドはその行き先では借用のままで、所有を取る葉では持ち主が死んでいる。

この議論は、決定木の途中のブロックに呼び出しがないことに依っている。今の決定木の途中は `switch`、`unpack`、`unbox` だけでできている (ガードと as パターンがない)。ロードマップのガードを入れると、ガードの呼び出しの後で、後の行が使う分解した値と `Lin` のフィールドが両方生きる形ができ、2. が `File` を `dup` する。ガードを入れるときは、呼び出しをまたいで借用を保つ形か、別の変換が要る。これを、ロードマップのガードの項目に制約として書く。

### verifier

LIR の所有の段の verifier は、新しい形を今の規則のまま受け入れる。次を確かめた (`crates/eml_lir/src/verify.rs`)。

- 借りた変数への `switch`、`unpack`、`unbox` は、その変数か持ち主が所有されていれば受け入れる
- 有効な借りた変数の `dup` を受け入れる
- `release` が名前を書く変数については、見えること、RC の対象であること、出どころだけを確かめ、有効さは確かめない。そのため、`release o (c)` の後の `release c (g)` (g の持ち主は o) も通る
- 呼び出しをまたいで借りた変数を退避することと、退避せずに後で使うことは拒む。上の 2. の規則はこれに合わせたものである

計画の最初のタスク (下の「試作」) で、全 UI テストの出力が今の verifier を通ることを確かめる。verifier を変える必要が分かったら、この spec に変更を書き足してから先へ進む。

### 試作

計画の最初のタスクで、新しい Perceus を試作し、次を確かめる。

- 全 UI テストと `bench/` のプログラムの Perceus の出力が、今の所有の段の verifier を通る
- 全 UI テストが `debug_heap` 付きで通り、下の `File` の検査が誤りを出さない
- 長い借用の `switch` の連なりで、Perceus の時間が線形である
- `bench/` の `RunStats` の回数がどう変わるか

試作の結果で設計を変える必要があれば、この spec を改めてから本実装に移る。試作のコードは本実装に使い回してよい。

### Perceus の作りの変更

`crates/eml_lir/src/perceus.rs` は次のように作り直す。

- 今の `rewrite` は、後ろからたどる1回のループで命令を決める。新しい形では、命令が前からの状態 (所有と保持) に依るので、後ろからたどって各命令の後の生存を記録するループと、前から状態を持って命令を足すループに分ける
- `switch_entries` は、行き先ごとに状態全体を持ち、`switch` のブロックを前からたどり終えた後に埋める。`case_values`、`Destructured`、`own`、`Owning` と、入口の順の規則はなくなる
- 終端の前の `dup` (`term_dups`) は、`return`、`tail`、`jump` の実引数の所有を取ることと、保持されている変数を手放すことも受け持つ
- タグの case を持つのに配置のない `switch` を見たら、今と同じくその `switch` の所でパニックする (`a_tag_switch_without_a_layout_stops_perceus` が確かめる)

## 基本操作の引数の借用

### 表

`PrimRow` に、引数ごとの借用の印 `borrowed: &'static [bool]` を `params` と並べて足す。長さは `params` と同じで、すべての基本操作でそうであることを単体テストで確かめる。

借用にするのは、基本操作がその引数そのものを物体にも実行の文脈にも入れない引数である。読むだけの引数と、中身の一部を自分で `dup` して共有する引数 (`evv_mask` のリストの残り、`ev_renew` の入口の表) がこれに当たる。

| 基本操作 | 借用にする引数 | 消費のままの引数 |
|---|---|---|
| `ev_clause`、`ev_evv`、`ev_take_state`、`yield_status` | evidence | なし |
| `ev_set_clause` | evidence | クロージャ (入口の表に入れる) |
| `ev_set_state` | evidence | 状態 (欄に入れる) |
| `ev_renew` | 元の evidence | 状態 |
| `evv_mask` | 元の `evv` | なし |
| `evv_set`、`evv_push`、`ev_new`、`yield_to`、`yield_abort`、`yield_cont_set` | なし | すべて (文脈か物体に入れる) |
| `evv_get`、`ev_lookup`、`yielding`、`yield_cont_take`、`yield_finish`、`dummy` | 引数なし | 引数なし |

`ev_take_state` と `ev_set_state` が借りた evidence の状態の欄を書き換えることは、今と同じである ([LIR とインタプリタ](../../spec/lir.md) の「evidence」)。

### 各部分の規則

- 値の使いの分類: `Rhs::for_each_consumed` (`crates/eml_lir/src/lib.rs`) は、基本操作の借用の引数を消費に数えない。Perceus と verifier は、この分類を共有する
- Perceus: 借用の引数は読む使いである。借用の変数をそのまま渡せる。所有の変数がその命令で死ぬなら、命令の直後に `decref` する (上の「持ち主を手放す時点」)
- verifier (所有の段): 借用の引数は、見えて有効であればよい。所有の数を変えない。`unbox` のオペランドと同じく読む使いとして確かめる。範囲の段と境界の検査は変えない
- CEK (`crates/eml_interp/src/prims.rs`): 借用の引数を `decref` しない。`evv_mask` がリストの残りを、`ev_renew` が入口の表を `dup` するのは、今の実装がすでに行っている
- EP、box の挿入、縮約: 出す IR の形は変わらない。借用にする引数の Repr は `obj` (evidence) か `tobj` (`evv`) で、box の挿入が変換を足すことはない。基本操作は今と同じく純粋でないとみなし、縮約は消さない

### 期待する効果

すぐに再開する操作の1回あたりの RC の増減は、`ev_lookup` が作る参照1つと、入口の終わりの `decref` 1つになる。今は `dup` と `decref` が3回ずつ要る ([計測の基準](../../implementation/benchmarks.md) の「S7 (evidence passing)」)。`mask` の包みの `w0` も、`evv_mask` のために `dup` しなくなる。

## `File` の実行時の検査

- `eml_runtime` の `Heap::dup` で、対象が `File` の物体 (`Payload::File`) なら、新しい誤り `HeapError::LinShared` を返す。文言は `a Lin object is shared` である
- 物体の参照の数を増やす経路は、`dup` 命令 (`Runtime::dup`)、共有の側の `release` が残すフィールド (`release_fields`)、共有されたクロージャを写すときの子 (`take_or_copy`)、基本操作が残す参照で、どれも `Heap::dup` を通る。`acquire_immortal` は文字列のリテラルにしか使わない。そのため、ここだけで覆える
- 検査は `debug_heap` によらず常に行う。中身の種類は、`dup` がすでに引いた物体の中で1回見るだけである。ヒープは今 `debug_heap` を知らず、検査のためだけに旗を渡すことになる。違反はコンパイラの誤りなので、`debug_heap` なしでも止める
- 誤りは、ほかのヒープの誤りと同じく `Fault::Heap` として実行時エラーになり、``a Lin object is shared in `f` `` と表示する ([LIR とインタプリタ](../../spec/lir.md) の「実行時エラー」に足す)
- 検査が見つけるのは、`File` の物体の参照の数を増やす違反だけである。`File` を含む `Lin` のデータやクロージャを `dup` する違反は、実行時にはほかの物体と区別できないので見つけられない。それは S8c の V1 で静的に覆う

## テストの変更

[テスト戦略](../../implementation/testing.md) の「テストの変更の運用」の種類で書く。

### 期待値の変更

- Perceus の後のダンプはすべて取り直す。`crates/eml_lir/tests/perceus.rs` の出力と、`crates/eml_core_ir/tests` のうち `lir_text(.., Perceus)` か `lir(..)` の表示を見るスナップショットである。`dup`、`decref`、`release` の位置が新しい形に変わる
- その中で、名前が今の規則を述べていて新しい形と合わなくなるテストは、新しい規則を述べる名前に改める。`crates/eml_lir/tests/perceus.rs` の `prims_consume_their_arguments`、`an_unboxed_field_is_owned_at_the_target_and_released_after_the_unbox`、`a_target_dups_the_fields_of_a_live_scrutinee_before_it_decrefs_a_dead_value`、`a_target_releases_its_scrutinee_and_keeps_the_fields_it_uses` と、`crates/eml_core_ir/tests/perceus.rs` の `a_nested_pattern_gives_up_the_parent_before_the_release` が当たる。どれも成否は変わらず、期待値が変わる。名前を改めるときは、テストの説明のコメントも新しい規則に合わせる
- 借用にする基本操作の引数を消費として扱っている、所有の段に通す手書きの LIR (evidence の `dup` と `decref` の位置) は、入力と期待値を書き直す。`crates/eml_interp/tests/evidence.rs`、`crates/eml_interp/tests/ir/*.lir`、`crates/eml_interp/src/prims.rs` の単体テスト (`a_mask_skips_the_first_matches..` など、生きている物体の数を確かめるもの) が当たる
- `crates/eml_interp/tests/bench.rs` の `RunStats` のスナップショットは取り直す。`rc_increments` と `rc_decrements` が減り、特に `state` で減る。`peak_objects` も変わりうる
- `crates/eml_interp/tests/scaling.rs` で値を固定しているのは、空のプログラムの回数が 0 であることと `peak_objects == 1` だけで、ほかは上限と、長さを変えたときの関係である。変わらない見込みである。変わるテストが見つかったら、この spec に範囲を書き足してから変える
- UI テストの出力は変わらない

## 採らなかった案

- **決定木の葉で所有を決める形**: 今の入口の規則を、決定木の葉の入口で当てる。実装は小さい。しかし、腕の本体の最初のブロックは IR の上で一意に決まらず (本体が `if` で始まるときなど)、読むだけのフィールドの `dup` と `unbox` の後の `decref` も残る
- **`Lin` のフィールドだけを特別に扱う形**: Kind の印がないので S8b では書けない
- **呼び出しをまたいで借用を保つ形**: 持ち主を退避すれば、フィールドを借りたまま呼び出しをまたげる。しかし、フレームが借りた値と所有した値を区別して持つ必要があり、中断でフレームを捨てるときの解放の規則も変わる。借用パラメータと一緒に考える。ガードを入れるときにも要りうる (上の「`Lin` のフィールド」)
- **`File` の検査を `debug_heap` のときだけにする形**: ヒープに旗を渡す必要がある。費用は小さく、違反はコンパイラの誤りなので、常に検査する
- **持ち主を親の道で決め直す形**: verifier の持ち主を、束縛の時点でなく親をたどって決めると、「持ち主を解く」の `dup` (3.) が減る。しかし verifier の有効さの判定が深さに比例し、線形でなくなる。持ち主は束縛の時点で決め、Perceus がそれに合わせる
