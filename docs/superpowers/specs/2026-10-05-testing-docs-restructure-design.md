# テストの文書の整理の設計

位置づけ: 作業用の設計文書。この作業を終えたら、この文書は削除する。決めた内容は `docs/implementation/testing.md` と `docs/implementation/test-changes.md` に入る。

## 目的と範囲

テストとテストの文書の整理を、次の3つのサブプロジェクトに分ける。それぞれ spec、計画、実装の1サイクルで進める。この文書はサブプロジェクト1の設計である。

| # | サブプロジェクト | テストの変更の種類 |
|---|---|---|
| 1 | testing.md の再構成。手引きと変更の記録を分け、現状と将来を分け、テストの置き場所の規約を明文化する | なし (文書だけ) |
| 2 | テスト補助コードの統一。各 crate の `tests/common` と `eml_test_support` の API をそろえる | 種類3だけ |
| 3 | テスト本体の整理。重複したテストと古くなったテストの棚卸しと削除、大きいファイルの分割、UI テストの分類 | 主に種類1 |

サブプロジェクト1が置き場所の規約を先に決め、2と3はその規約に合わせて実装する。

### サブプロジェクト1で直すもの

- testing.md の「テストの変更の記録」が文書の半分を占め、作業のたびに伸びる。手引きを読む人が記録を読み飛ばさなければならない
- 「層ごとの方法」の表に、まだない層 (網羅性、線形性の検査パス) が今ある層と同じ形で並んでいる
- テストの置き場所が crate ごとの散文で書かれていて、新しいテストをどこに書くかを決める規則がない。`src/` の単体テストは一部しか載っていない
- マルチコア対応の段階のテストの方針が testing.md にあり、`future/multicore.md` がそこを指している。将来の設計は `future/` に置く決まり ([docs/README.md](../../README.md)) と向きが逆である

### 範囲の外

- テストのコードとテストのファイルの変更。テストの移動、削除、分割、補助コードの変更は、サブプロジェクト2と3で行う
- 記録の既存の項目の書き直し。S1 から R1 までの項目には種類の番号がないが、履歴なので足さない

### ユーザーと合意済みの決定

- 3つのサブプロジェクトに分け、1 → 2 → 3 の順に進める
- テストの変更の記録は別のファイル `docs/implementation/test-changes.md` に移す
- UI テストは、今の期待のディレクトリ (`run/`、`check-fail/`、`run-fail/`) を保ち、その下に分類のサブディレクトリを切る
- `check-fail/` の分類は、主なエラーの番号の範囲で決める。機能で分けると、エフェクトの誤りが E1 (handler の節、`resume` の引数の個数) と E2 (扱われないエフェクト) にまたがり、置き場所が一意に決まらないためである

## 1. 文書の構成

### testing.md

手引きとして、今のテストの書き方と置き場所だけを書く。節の構成は次のとおりにする。

1. **方針**: TDD と `insta`。今の内容を変えない
2. **テストの変更の運用**: 3種類の表と規則。今の内容を保ち、記録の行き先を `test-changes.md` に変える
3. **テストの置き場所**: 新しい節。2章の「置き場所の規則」と、今あるテストの地図を書く。今の散文の一覧はこの節に置き換える
4. **層ごとの方法**: 今ある層だけを表に残す。線形性の行は、今ある Kind の制約の違反 (E3001) の確かめ方に絞る。網羅性と、線形性の検査パスを分けた後のケース (二重使用、消費漏れ、`_` での破棄、`multi` をまたぐ、継続の扱い忘れ) は、節の最後の「後の段階で足すテスト」の短い一覧に移す
5. **UI テスト**: 今の仕組みに、3章の分類の規則を足す。テストのパスがスナップショットの名前になるので、移動は種類1の変更になることも書く
6. **CLI のテスト**、**よく使うコマンド**: 今の内容を変えない

「テストの変更の記録」と「マルチコア対応の段階のテスト」の節は testing.md から除く。

### test-changes.md

`docs/implementation/test-changes.md` を新しく作り、testing.md の「テストの変更の記録」の項目をすべて、文字を変えずに移す。冒頭には、位置づけ (記録) と、新しい項目の書き方を書く。

- 作業ごとに見出しを1つ立てる
- 変更ごとに箇条を1つ書き、種類 (1か2)、変えた理由、変わらない目的を書く

### その他の文書

- `future/multicore.md` の「テスト」の節に、testing.md の「マルチコア対応の段階のテスト」の本文を移す。testing.md を指していた1文は除く
- `docs/README.md` の文書の地図に test-changes.md の行を足し、testing.md の行の内容を「テスト戦略、テストの置き場所、UI テスト、テストの変更の運用」に変える
- `CLAUDE.md` の Testing の節の「Kinds 1 and 2 are recorded in `testing.md`」を `test-changes.md` に変える
- `implementation/status.md` の「次の作業の注意点」に、サブプロジェクト2と3が残っていることを1項目で書く。testing.md の規約 (UI テストの分類、重複の規則) に、既存のテストがまだ合っていないことを示すためである
- コードのコメント (`eml_test_support`、`eml_interp/tests/run.rs`、`eml_cli/tests/ui.rs` など) と `spec/runtime.md`、`architecture.md` は testing.md 全体を指しているので、変えない

## 2. 置き場所の規則

testing.md の「テストの置き場所」に書く内容である。

### どこに書くか

新しいテストの置き場所は、期待するものを上から順に見て、最初に当てはまる行で決める。

| # | 期待するもの | 置き場所 |
|---|---|---|
| 1 | プログラムを `eml check` / `eml run` にかけたときにユーザーが見るもの。stdout、実行時エラー、プログラム全体が通るか落ちるか | UI テスト (`tests/ui/`) |
| 2 | 1つの段階の出力 (CST、HIR、推論したシグネチャ、Core IR) と、その段階の診断の細部 (位置、回復、端のケース) | その段階の crate の結合テスト (`crates/<段階>/tests/`)。ソースから `eml_test_support` で組み立てる |
| 3 | フロントエンドからは作れない状態。壊れた IR、`decref` の抜けた IR など | `eml_core_ir/tests/verify.rs` か `eml_interp/tests/`。手書きの Core IR で組み立てる |
| 4 | 公開の API から届かないか、内部の状態を直接組まないと確かめにくい部品の振る舞い。レイアウト段、パーサのマーカー、単一化の表、Kind の制約の解消、ヒープなど | `src/` の単体テスト |
| 5 | lib API の流れ、CLI の終了コード、テスト補助そのもの | `eml_cli/tests/api.rs`、`eml_cli/tests/cli.rs`、`eml_test_support/tests/` |

### 重複させない

1つの事実は、それを観測できるいちばん下の層で確かめる。UI テストは機能ごとの代表的な筋書きを確かめ、段階の端のケースを繰り返さない。例えば診断なら、端のケースは段階の crate のテストに置き、代表的な表示を `check-fail/` に1つ置く。サブプロジェクト3の棚卸しは、この規則で削るテストを決める。

### crate の中の置き方

- 結合テストは、話題ごとに1ファイルにする。ファイル名は spec の節か言語の機能から付ける (`effects.rs`、`operators.rs`)。1つのファイルが複数の話題にまたがったら、話題で分ける
- crate の結合テストが使う表示の関数は `tests/common/mod.rs` に置く。形はサブプロジェクト2で決める
- 単体テストは、ファイルの末尾の `#[cfg(test)] mod tests` に置く。大きくなったら、`eml_types/src/table/tests.rs` のように隣の `tests.rs` に分ける

### 今あるテストの地図

今の散文の一覧を、crate ごとに、ファイルと話題を並べた表に書き直す。`src/` の単体テストを持つファイル (`eml_syntax` の `layout.rs`、`parser.rs`、`grammar/scan.rs`、`syntax_kind.rs`、`token_set.rs`、`eml_diagnostics` の `lib.rs`、`render.rs`、`source.rs`、`eml_hir` の `builtin.rs`、`lower/scope.rs`、`eml_types` の `kind.rs`、`ty.rs`、`scc.rs`、`check/mod.rs`、`table/tests.rs`、`eml_runtime` の `heap.rs`、`output.rs`、`eml_interp` の `lib.rs`) も載せる。表は crate とファイルの粒度にとどめ、テストの名前は載せない。

## 3. UI テストの分類

testing.md の「UI テスト」に書く内容である。

- `run/` と `run-fail/` は言語の機能で分け、両方で同じ名前を使う
  - `basics/`: 値、演算子、`let`、`if`、短絡評価
  - `functions/`: クロージャ、高階関数、部分適用
  - `effects/`: エフェクト、`multi`、継続
  - `runtime/`: 実装の性質を確かめるテスト。メモリの解放、スタックの深さ、join point、末尾呼び出し
- `check-fail/` は、主なエラーの番号の範囲 ([診断](../../spec/diagnostics.md) の「番号の範囲」) で分ける
  - `syntax/` (E0xxx)、`names/` (E1xxx)、`types/` (E2xxx)、`linearity/` (E3xxx)。網羅性 (E4xxx) の検査を実装したら `exhaustiveness/` を足す
  - E3001 は今は `eml_types` が出すが、出す crate ではなく番号の範囲に従って `linearity/` に置く
  - E0004 (まだ対応していない構文) は、どの段階が出しても `not-yet-supported/` に置く
- サブディレクトリの名前は、親の `check-fail` と同じくケバブケースにする
- 既存の `.em` をどの分類に移すかと、`ui.rs` の走査のパターンを `**/*.em` にする変更は、サブプロジェクト3で行う
