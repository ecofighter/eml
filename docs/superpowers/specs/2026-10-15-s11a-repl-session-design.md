# S11a REPL のセッションの核

位置づけ: S11a の設計。終えたら決めたことを `docs/spec/` などに移し、この文書を消す。

## 目的と範囲

[ロードマップ](../../future/roadmap.md) の S11 (REPL) を、次の3つの作業に分けて順に進める。段の列では S11 の1行のままにする。

| 作業 | 中身 |
|---|---|
| S11a セッションの核 | lib API だけで動く REPL のセッション。入力の読み分けと終わりの判定、セッションのモジュール、根の表、名前で照らして `CodeBase` に追記すること、`Show` による結果の表示、トランスクリプトのテスト |
| S11b 回復と割り込み | `eml_rt` の根からの走査 (Verus の証明を含む)、evv と yield の状態とスタックに残った語の回収、RC の数え直し、REPL 用の SIGINT のハンドラ、コード表を更新する間の割り込みの保留 |
| S11c 端末の REPL | `eml repl` のコマンド、行の編集、`:{ … :}` の複数行の入力、`:load` / `:reload` / `:type` / `:quit`、`Show` を持たない型の表示器 |

S11b は `eml_rt` を大きく変え、Verus の証明が要るので、独立した作業にする。S11a を先に置くのは、回復が S11a の根の表を前提にするためである。

この文書は S11a の設計である。Prelude と `std/` を読み込んだ環境で、定義の追加と式の評価を lib API から繰り返せるようにする。判断の基準は、簡潔で洗練された実装を第一に、次に性能である。この文書は、健全性とコードとの食い違いの観点、設計の一貫性と範囲の観点の2つの敵対的レビューと、セッションを入力ごとのモジュールで表す変更の敵対的レビューを経ている。

## ロードマップから変えること

- **増分の lowering をしない**: ロードマップは、定義ごとに IR を保存し、総称な定義の instance をキャッシュするとしていた。この文書では、入力ごとにプログラム全体を前端から Perceus まで流し直し、名前で照らして新しい関数だけを `CodeBase` に追記する (下の「追記」)。中段の各パスを純粋な関数のまま保てるためである。ロードマップには、関数が 1000 個のプログラムを処理し直す費用が約 37 ms だったという測定がある。代わりに、セッションが大きくなるほど入力ごとの時間が延びる (下の「伸びる費用」)。増分化が要るようになったら、「名前が同じなら同じコード」の規則があるので後から移れる
- **配置の番号を正規の順にしない**: ロードマップは、定義ごとに IR を保存するので配置の番号を正規の順にするとしていた。VM は実行時に配置の番号を使わず、タグだけを読む ([VM](../../spec/vm.md)) ので、名前で照らす追記では要らない
- **セッションの値を引数で渡さない**: ロードマップは、入力が使うセッションの値を `input$N` の引数として根から `dup` して渡すとしていた。この形では `input$N` の本体しかセッションの値を読めず、`let xs = …` の後で関数の定義から `xs` を参照できない。この文書では、基本操作 `root_get` と `root_set` を足す (下の「根」)。「新しい `Rhs` や `Atom` は要らない」は保てる。足すのは基本操作の行だけである
- **`Control::clear` を S11a に入れる**: ロードマップは割り込みの扱いとともに書いていた。確保量の上限で止まると `MEMORY` のビットが `clear` まで残り、後の入力がすべて止まるので、S11a で入力の始めに呼ぶ。SIGINT のハンドラは S11b に置く
- **セッションの表し方の論点を閉じる**: セッションを1つのモジュールとみなし、名前を入力の番号で解決する。HIR では入力ごとのモジュールで表すが、`pub` と import によらない専用の名前解決で、前の入力の item を見る (下の「セッションのモジュール」)。普通の import でつないだモジュールの鎖にすると、すべての定義に `pub` を付けることになる。古い定義と新しい定義の両方を import すると E1028 になる。orphan 規則の E1034 で、前の入力の型に instance を書けなくなる。入口のモジュールの決まり (E1030) も緩めることになる
- **シグネチャの論点を閉じる**: 関数の定義は、ファイルと同じくシグネチャを必須にする。シグネチャのない値は `let` で束縛し、単相に推論する。REPL だけ一般化することはしない
- **定義し直した型の表示の論点を閉じる**: 定義し直された item の古い版は、利用者向けの表示で版を付ける (下の「版」)

## 入力

### 入力の種類

`eml_syntax` に REPL の入力の入口 `parse_input(file, text)` を足す。入力を次の3つのどれかとして読み、CST の根の種類で区別する。

- **item の並び**: 最初の項目を、今のパーサの先読み (`item_kind`) で item と判定できる場合。ただし等式の形 (`Equation`、`OperatorEquation`) は、最初の項目の中で、括弧の外にあり、かつレイアウトのブロックが開く前にある `=` を持つときだけ item とみなす。`run <| fn () ->` の後の行で `let y = 1` と書いた式は、`->` でブロックが開いた後の `=` なので式になる。演算子のシグネチャの判定 (`at_operator_signature`) は、今は `(+)` の後の `:` を見ていないので、`:` を見るように直す。直さないと `(+) 1 2` がシグネチャとして読まれる。残りは今の `source_file` と同じ規則で読む
- **`let` の束縛**: `let` で始まり、束縛の後ろに `in` が続かない場合。局所の `let` の文と同じ文法で読むので、`let x : T = e` の型の明示と、行末の `=` の後のブロックが使える。パターンによる束縛は受けない
- **式**: 上のどれでもない場合。`f x` や `1 + 2` は、括弧の外に `=` がないので式になる。`let … in …` も式である

`let` の束縛と式の入力は、ちょうど1つの項目でなければならない。列 0 の `SEP` や `;` で2つ目の項目を続けたら構文の誤りにする。trivia だけの入力 (空、コメントだけ) は何もせず、入力の番号も進めない。

入力のテキストは、今のファイルと同じくレイアウト段を通す。入力は列 0 の `Block(0)` から始まる。シグネチャと等式は、`f : Int -> Int; f x = x + 1` のように `;` で1行に書ける (規則 5)。

### 入力の終わり

端末は、行を読むたびに、入力が終わったかどうかを決めなければならない。シグネチャだけの行や、等式の1行目だけを入力として受けると、E1005 や E1004 になる。等式を1行ずつ入力すると、行ごとに新しい版になってしまう。そのため、入力の終わりを決める規則を S11a に置き、トランスクリプトのテストで確かめてから、S11c の端末がそのまま使う。

`eml_syntax::input_status(text) -> InputStatus { Complete, Incomplete }` を足す。入力の番号を使わない純粋な関数で、字句とレイアウト段の状態と、`parse_input` と同じ入力の種類の判定だけを見る。

1. 括弧、row、行をまたげる文字列 (複数行の文字列 `"""` と raw 文字列) が閉じていなければ `Incomplete` である。空行が来ても続く。1行の文字列と補間の穴は行末で閉じるので ([字句](../../spec/lexical.md) の「改行での回復」)、数えない
2. 最後のトークンがブロックの開始トークン (`=` `->` `with` `then` `else` `where`) なら `Incomplete` である
3. 次のどれかに当たる入力は、空行で終わるまで `Incomplete` である
   - 規則 3 のレイアウトのブロック (行末の開始トークンが開いたもの) が閉じていない (レイアウトのスタックが `Block(0)` より上にある)。`main () =` の後の字下げした本体や、`data` のコンストラクタを並べる行が続きうるためである。閉じた複数行の括弧は、閉じた時点で終わる
   - item の並びで、最後の項目がシグネチャか等式である。等式を何本も続けられるようにするためである。`f : Int -> Int; f x = x + 1` の1行も、後ろに空行を1つ要る
4. 上のどれにも当たらなければ `Complete` である。`f x`、`let x = 1`、`import Std.Fs`、1行の `data` は、1行で終わる

最後の行が空白だけなら、空行で終わったとみなす。端末が行を `\n` でつないで渡すと、空行で終わった入力は `\n` で終わるためである。空行で終わった入力は、その空行を含めずに `eval` に渡す。空行を含む貼り付けは、S11c の `:{ … :}` で入力する。

### トランスクリプトの形

- 1つのトランスクリプトは `<分類>/<名前>.repl` か、import するモジュールを並べるときは `<分類>/<名前>/main.repl` (同じディレクトリの `.em` がモジュール) である。UI テストと同じ形である
- `> ` で始まる行が入力の1行目で、`. ` で始まる行が続きの行である。`>` や `.` だけの行は空の行として読む (エディタが行末の空白を消すため)
- 入力の終わりの空行は `.` だけの行で書く
- harness は、各入力について、最後の行より前の行までのテキストが `Incomplete` で、全体が `Complete` であることを確かめる。入力の終わりの規則を、端末と同じ形で確かめるためである

## セッションのモジュール

`eml_hir` では、入力ごとに1つのモジュール (セッションのモジュール) を作り、def_map、lowering、型検査がそれらを1つのセッションとして扱う。利用者から見た意味は、セッションを1つのモジュールとみなすもので、orphan 規則と fixity を1つのモジュールとして当て、名前を入力の番号で解決する。入力ごとにモジュールを分けるのは、`LoadedModule` が構文木と `ItemTree` を1つずつ持ち、モジュールの番号とファイルの番号が同じで、名前ごとに使える定義を1つ持つ (E1003 が頼る) という今の形を変えずに済むためである。

### 並びと読み込み

- 読み込みの段の新しい入口 `load_session` は、標準ライブラリ、受け付けた入力と今の入力のテキストの並び (入力の番号つき)、import の根、import したモジュールのキャッシュ (下) を受け取る
- モジュールの並びは、Prelude (番号 0)、セッションのモジュール (番号 1 から入力の順。最後が今の入力で、入口のモジュール)、Prelude を除く標準ライブラリ、import でたどった依存先の順である。今の `load` と `def_map` が入口を番号 1 に決め打ちしている所は、入口とセッションの範囲を引数で受ける。E1035 は並びで先のモジュールを元の instance とみなすので (`lower/instance.rs` の `duplicate`)、前の入力の instance を元に、今の入力の instance を重なりとして報告する。標準ライブラリと import したモジュールの instance がセッションの instance と重なることは、orphan 規則があるので起きない
- セッションのモジュールは `ModuleOrigin::Session(N)` を持ち、版の規則は入力の番号をここから読む。表示のパスとモジュールの名前は、利用者が書けない `<input N>` にする。`check_main` と、入口のモジュールの import の決まり (E1030) は当てない。ほかのモジュールはセッションのモジュールを import できず、`Main` は今と同じく import できない名前のままにする
- モジュールとファイルの番号は `eval` ごとに振り直す。前の入力は前の入力しか見ないので、どの `eval` でも同じように解決される。`Evaluated` は、その `eval` の診断を表示するための `SourceFiles` を持つ (下の「API」)。`Repl` が `eval` をまたいで持つものは、HIR の番号を使わない。受け付けた入力ごとに (テキスト、入力の番号) を持つ。`let` の根の番号は入力の番号である (下の「根」)。一様な位置は、モジュールの名前とモジュールの中の item の番号で覚える (下の「定義し直しの決まり」)
- **import のキャッシュ**: `Repl` は、import でたどったモジュールについて、解決した先 (ユーザーの根のファイルか、`NotFound` で標準ライブラリに落ちたか) とテキストを、間接の依存先も含めて持つ。後の入力でも同じ先とテキストを使う。ディスクのファイルが変わったり、新しくできたりしても、セッションの中のモジュールは変わらない。読み直すと、同じ名前の関数が違うコードになるためである。キャッシュは入力を受け付けたときにだけ確定し、受け付けなかった入力が読んだものは残さない。読み直しは S11c の `:reload` で決める

### 名前解決

- 重複の検査 (E1003) は、今と同じくモジュールの中、つまり入力の中で行う。後の入力の同じ名前は、エラーにせず新しい版として扱う
- 入力 N のモジュールの修飾しない名前は、次の順に引く ([モジュールと名前解決](../../spec/modules.md) の順に、セッションの段を足したもの)
  1. ローカルの束縛
  2. 自分のモジュールのトップレベル
  3. N より前のセッションのモジュールのトップレベルを、新しい入力から順に。`pub` は見ない。その名前空間でその名前を定義している最も新しいモジュールで止まり、種類が合わなければ今と同じ誤りにする。種類で絞って古い版まで探し続けると、`ask` を操作から関数に定義し直した後の handler の節が古い操作を見つけるように、定義し直した名前の古い版が戻ってくるためである
  4. import の並びで修飾なしにした名前を、入力 N、N − 1、… の順に、入力ごとに引く。E1028 は1つの入力の import の中で2つ以上の別の item に当たったときだけにする。後の入力の import が前の入力の import を隠すので、別々の入力で同じ名前を import しても、ずっと E1028 になることはない
  5. Prelude の `pub` の名前
- 2 は今のファイルと同じく、種類が合わない定義を飛ばして探し続ける。3 の「最も新しいモジュールで止まる」規則は前の入力にだけ当てる
- `let` の束縛は、自分の入力の中では見えない。`let x = x + 1` の右辺の `x` は前の版を指す
- 2 と 3 は、ファイルのトップレベルと同じく、入力の順によらず import した名前と Prelude の名前を隠す。後の入力の item は見えない。同じ入力の中では、今と同じく相互再帰ができる
- import の範囲を読むほかの処理 (修飾子と別名、`targets`、`hidden_std_module`、`unknown_parts`) も、4 と同じく N 以前のセッションのモジュールの import を新しい入力から順に見る。1つの入力の中で import を宣言より前に書く決まりは、今のまま守らせる
- E1028 の2つ目以降のラベルは、前の入力の import を指しうるので、`Resolved::Ambiguous` と修飾子の import の位置は `(FileId, TextRange)` で持つ
- セッションの中では `pub` を見ない。E1032 (公開の範囲) もセッションのモジュールには当てない。セッションのモジュールはどこからも import されないためである

### セッションを1つのモジュールとして扱う所

- **orphan 規則** (E1034): セッションのどのモジュールで定義したクラスや型も、セッションの instance にとって「同じモジュール」に数える
- **fixity**: `fixity_of` と `looser_operator` は、セッションのモジュールを同じモジュールとみなし、`pub` でない fixity も入力をまたいで当てる。今は別のモジュールの fixity を `pub` のときだけ当てるので ([宣言](../../spec/declarations.md))、そのままでは入力 1 の `infixl 6 <+>` が入力 3 で `infixl 9` に戻る
- **利用者向けの表示名** (`DisplayNames`): セッションを1つの定義元として数える。版の表示は下の「版」に従う。セッションの item がほかのモジュールの item と同じ名前のときは、ほかのモジュールの item をモジュール名で修飾し、セッションの item は修飾しない (`Prelude.Bool` と `Bool`)

### item の種類

- 新しい item の種類を2つ足す。`let` の束縛 (根の番号を持つ) と、式の入力である。式の入力は、受け付けて実行した後はセッションの入力の列に残さない。後の入力から参照されないためである

### 定義し直しの決まり

- 版は (名前空間, 名前) ごとに数える。`let` の束縛と関数は同じ値の名前空間にある。版を数えるのは受け付けた入力だけである
- 型を定義し直さずに、そのコンストラクタの名前だけを別の型のコンストラクタで定義し直すこともできる。前の入力のコードは古いコンストラクタを使い続け、後の入力のその名前は新しいコンストラクタを指す
- **fixity**: fixity の宣言は、その演算子を定義した入力の中に書く。fixity は定義に付くので ([宣言](../../spec/declarations.md))、後の入力で前の入力の演算子に fixity を足すと、前の入力の式の結合が変わり、同じ名前の関数が違うコードになるためである。入力ごとにモジュールを分けるので、今の E1022 (このモジュールで定義していない演算子への fixity の宣言) がそのまま当たる。利用者には入力が見えるので、セッションでの E1022 の文言は「この入力で定義していない」にする
- **instance**: 同じ (クラス, 型) の instance は、入力が違っても定義し直せない (E1035 のまま)。定義し直せると、総称な関数の instance を後の入力で初めて作ったときに新しい instance を使い、すでに `CodeBase` にある同じ名前の関数と食い違うためである。間違えた instance を直すには、型かクラスを定義し直し、その新しい版に対して instance を書く
- **一様な位置**: 後の入力の instance によって、前の入力の関数の一様な位置 (`TypedProgram::uniform`) が変わることがある。メソッドの節点から、後の入力の instance の実装にも辺が引かれるためである (`eml_types` の `uniform.rs` の `method_edges`)。`Repl` は受け付けた関数の一様な位置を、モジュールの名前とモジュールの中の item の番号で覚えておき、変わったら新しい診断でその入力を受け付けない。前の入力のテキストもキャッシュした import も変わらないので、この組は `eval` をまたいで同じ関数を指す。めったに起きないので、受け付けないのがいちばん簡単な規則である

### 版

- **利用者向けの表示** (診断の型など): 定義し直された item の古い版に、定義した入力の番号を付けて `T#1` と書く。最新の版には付けない。利用者が今その名前で書けるものを、印なしで見せるためである
- **中段の名前**: 下の「名前」の規則で、最初の版を印なし、2つ目からを `#N` にする。後で定義し直されても、前の版の中段の名前が変わらないようにするためである。利用者向けの表示とは向きが逆になるが、どちらもこの理由で決まる

## 型検査

- `let` の束縛と式の入力は、シグネチャなしで、局所の `let` と同じく単相に推論する。`let x : T = e` の型の明示は、局所の `let` と同じく扱う
- row は `<IO>` に収まらなければならない。収まらなければ新しい診断を出す
- 残った Kind の変数 (関数型の線形性を含む) は `Unr` に決める。残った row 変数は `<>` に決める
- `let` の束縛の型と式の入力の型は `Unr` でなければならない。`Lin` なら新しい診断を出す。入力の中の `Lin` の値は、今の線形性の検査でその入力の中で使い切らせる
- **式の入力の defaulting**: 本体の推論を終えた後、制約を解く前に、残った型変数を `Unit` に決める。式の `[]` や `show []` を通すためである。決めた型で解けない制約は、E2006 でなく E2009 として報告する。決めたのは処理系で、利用者は型を書いていないためである。[型と Kind](../../spec/types.md) の「defaulting は持たない」の、REPL の式の入力だけの例外として spec に書く
- **`let` の束縛では defaulting しない**: 残った型変数は新しい診断にし、help で `let x : T = e` の型の明示を勧める。`let id = fn x -> x` を `Unit -> Unit` に決めると、型の誤りが何入力も後に、原因から離れて出るためである
- 式の入力の型が `Show` を持つかは、型が決まった後に `Show T` の制約が完全に解けるかで決める。`Show (List a)` があっても `List (Int -> Int)` は `Show` を持たない。結果を `TypedProgram` に記録し、translate が表示の呼び出しを作る (下の「表示」)
- 新しい診断の番号は、計画で各段の `codes` に足す

## 名前

「名前が同じ関数は、いつも同じコードになる」ことを、全パスが守る規則にする。セッションのどの定義も後から変わらないので、名前が定義と型引数だけで決まれば、この規則は保てる。今の名前の付け方を次のように直す。

- **中段の名前**: セッションの item は、種類 (型、コンストラクタ、エフェクト、操作、クラス、メソッド、instance、関数) によらず、中段の名前を持つ。前の入力が同じ名前の item を (名前空間によらず) 定義していなければ名前そのもの、定義していれば定義した入力の番号を付けた `名前#N` である。名前空間ごとに数えなくても、前の入力は変わらないので名前は変わらず、型とコンストラクタのように名前空間の違う item は IR の別の表に入るので重ならない。利用者向けの表示の版 (`T#1`) は (名前空間, 名前) ごとに数える。`core_name` がこの名前を使う。エフェクトの名前 (`EffectInfo`)、`op$E.op`、`con$A`、配置の名前、`mask$[E]` も、この名前から作る。こうしないと、定義し直したエフェクト `E` の新しい版が、名前で照らす追記で古い版の番号を受け継ぎ、操作の表の違う evidence が1つの番号を共有する。速いモードでは、メモリの安全性が崩れる
- **instance の名前と生成する関数の名前**: 型引数の表示と、導出した関数の名前 (`"Show Color.show"`) は、利用者向けの表示 (`DisplayNames`) でなく、入力によらない専用の型の表示器で作る。`DisplayNames` は名前が重なるときだけ修飾するので、後の入力が同じ名前を定義すると表示が変わる。たとえば import した `Foo.T` は、重なりがなければ `T` と表示される。後の入力が `T` を定義すると、`id@[T]` が別の instance を指す同じ名前になり、`CodeBase` の古いコードが使い回される。専用の表示器は、型とクラスの名前を次のように書く
  - Prelude の item は修飾しない (`Int`、`Show`)。名前で最もよく出る型を読みやすく保つためである。Prelude は固定なので、重なりは入力で変わらない
  - 入口とセッションの item は中段の名前で書く。Prelude の item と同じ名前のものは `Main.` で修飾する (`Main.Bool`、`Main.Bool#3`)
  - ほかのモジュールの item は、`core_name` と同じくモジュール名で修飾する (`Std.Fs.File`、`Foo.T`)
- **instance の名前の形**: 型引数だけで決まる名前にする
  - 型の表示が上限 (64 文字) に収まれば、今と同じ `f@[Int]` にする
  - 収まらなければ、型の構造から計算するハッシュ (64 ビットを16桁の16進数で書く) で `f@#3fa91c…` にする。今の `f@{序数}` は、その関数のほかの instance の有無と見つけた順で番号が変わるので使えない。ハッシュは、表示と同じ情報 (中段の名前、矢印の線形性 `%1` / `%m`、row、一様な位置 `_`) を、型の DAG の上で節ごとに1回だけ計算する。表示が指数の長さになる型でも線形の時間で済む。`TypeId` にはよらない
  - 異なる型が同じ表示になる場合 (row の末尾、Kind だけが違う型変数など) は、今は後の instance を序数の名前にしている。名前に使う表示の側でこれらを区別し、同じ文字列にならないようにする。そのため、一様な位置と型変数の Kind も名前に書く (`_%m`、`a%1`)
  - プログラムの中で名前が重ならないことを、debug ビルドで確かめる。入力をまたいだハッシュの衝突は、debug ビルドの一致の確かめ (下の「追記」) だけが捕まえる。release ビルドでは古いコードを使い回すことになるが、64 ビットの衝突の確率は低いので受け入れる
- **共有の関数**: `op$`、`con$`、`cont$`、`cont$state` は複数の定義が値として使い、`internal` である。box の挿入は、`internal` で直接呼ばれない関数をその場で一様にし、直接も呼ばれる関数には `f$boxed` を足す。これらの関数は値と部分適用でだけ使われ、直接は呼ばれないので、いつもその場で一様になり、どのプログラムでも同じコードになる (`cont$` と `cont$state` は初めから一様)。そのため形は変えず、直接呼ばれないことをテストで固定する。translate が初めから一様な形で作ることはできない。Core IR には `unbox` がなく、`con` の引数は配置の Repr と合わなければならないためである
- `input$N` は入力の番号で名前が決まる。入力の関数は `()` を1つ受ける (`input$N () = e`)。`main` と同じく `entry$` が `()` で呼ぶためである。`let` の束縛は関数を作らず、参照が `root_get` になる
- IR のテキストの形は、名前に `#` を許していない (`eml_lir` の `syntax.rs` の `is_name_char`)。`#` を含む名前は、空白を含む extern の名前と同じく引用符で書く

## 根

- `eml_rt` の `Ctx` に根の表 `roots` を足す。根は `tobj` の語か空で、語は参照を1つ持つ
- 基本操作を2つ足す
  - `root_get(i) -> tobj`: 根 `i` を `dup` して返す。空の根を読んだら、2つのモードとも `HeapError::RootMisuse` にする
  - `root_set(i, v: tobj) -> unit`: v を消費して根 `i` に置く。根 `i` が空でなければ `HeapError::RootMisuse` にする
  - `RootMisuse` は REPL が根の番号を誤ったことを示すので、ヒープの誤りとして続けられない誤りにする (下の「エラー」)
- 基本操作の表 (`eml_lir` の `Prim::row`) に2行足す。結果と引数の印は `unr` である。束縛の型は `Unr` に限るので、`dup` してよい。`root_get` は、結果を使わなければ contract の「使われない純粋な `let` を消す」対象にする。`root_set` は消さない
- 根の番号は、`let` の入力の番号そのものにする。入力の番号は使い回さないので、根の番号も重ならず、根の番号を数える欄が要らない。根の表は空の根を含めて入力の番号まで伸びる。実行時エラーで失敗した `let` の根は空のまま残る。失敗した入力のコードは `CodeBase` に残るが、受け付けなかった入力の名前は後の入力から見えないので、その根を読むコードは実行されない
- 定義し直された `let` の古い根も手放さない。前の入力の関数が読み続けるためである。手放す順序はロードマップの論点に残す
- `let x = e` の入力は、`root_set(i, e)` を本体とする `input$N` になる。値の型の Repr と `tobj` の変換は、box の挿入が入れる
- `Ctx::take_roots` はすべての根の語を空にして返し、VM が手放す (`Machine::close`)。`Ctx::abandon` は evv と yield の状態を空に戻す (下の「エラー」)
- 根の語は `Ctx` の不変条件 (`wf`) の外に置き、VM のスタックのスロットと同じく VM が保証する。根を `wf` に入れると、ほかの基本操作のすべての証明を直すことになるためである。Verus は、根の基本操作と `take_roots`、`abandon` が `wf` を保つこと、`root_get` が根の語の参照を1つ増やすこと (RC のモデル)、誤った使い方では何も変えずに `RootMisuse` を返すことを証明する

## 追記

`eml_vm` に、`CodeBase<M>` と `Ctx<M>` を入力をまたいで持つ型 `Machine<M>` を足す。

- `Machine::load(&eml_lir::Program)` は、関数を名前で照らす。すでにある名前の関数は前の番号を使い、ない名前の関数だけを命令列にして末尾に足す。新しいコードの中の番号は、次のように引き直す
  - 関数の番号: 名前で `CodeBase` の番号に引く
  - 文字列の定数と、`i32` に収まらない `Int` の定数: 中身で引く。ない定数は、新しい凍結した塊にまとめる。塊を作る作業用のヒープは、先に今の先頭の塊を `attach` してから `freeze` するので、鎖が伸びる。実行のヒープは、新しい先頭を `attach` し直す ([オブジェクトモデル](../../spec/object-model.md) の「凍結した領域」)。新しい定数のない入力では塊を作らない
  - エフェクトの番号: 中段の名前で引き、なければ末尾に足す。今の番号は HIR の順で決まるので、セッションのモジュールにエフェクトを足すと、後ろのモジュールのエフェクトの番号がずれるためである。`evv_mask` のエフェクトの並び (`effect_lists`) も引き直す
  - 位置のファイルの番号: パスで引き、なければ `files` の末尾に足す。`Program.files` は translate が見つけた順に番号を振るためである
  - 配置の番号は、命令列を作るときに形を引くだけで、命令列に残らないので引き直さない
- `Machine::run(entry)` は、入口の関数を受け取る。`CodeBase` は `entry` と `entry_ret_rc` を持たず、`run` が入口の関数から決める
- `eml_vm::execute` は、`Machine` を1回だけ使う形にする。外から見た動作は変わらない
- **一致の確かめ**: debug ビルドでは、すでにある名前の関数も同じ引き直しで命令列にし、前の命令列と中身で比べる。オペランド、`effect_lists`、定数は番号でなく指す中身をたどって比べ、命令の中の位置は関数の先頭からの位置にそろえる。`arity`、`frame_size`、位置の表も比べる。一致しなければ内部の誤りにする。「名前が同じなら同じコード」が破れたことは、ここで分かる

## 実行と表示

| 入力 | 実行 | 表示 |
|---|---|---|
| item の並び | 前端だけを流し、誤りがなければ受け付ける。何も実行しない。定義は、使う入力が来たときに lowering される | なし |
| `let x = e` | `input$N` を実行する | なし |
| 式 | `input$N` を実行する | 下の「表示」 |

- `eval` の始めに `Control::clear` を呼ぶ
- `eval` の終わりに、成功でも失敗でも `Ctx::flush` を呼ぶ。`StdHost` は端末でなければ 64 KiB ずつ書くためである

### 表示

- `Show` を持つ型: translate が `input$N` の本体を、`println` に `show e` の結果を渡す形にする。`println` と `show` は、補間の穴と同じく `LangItems` で引く。利用者が `show` を定義し直しても変わらないようにするためである。`String` は `show` で引用符付きになる
- `Unit`: 何も表示しない
- `Show` を持たない型: 値を評価して手放し、`_ : Int -> Int` の形で型だけを表示する。型の表示は診断と同じ表示器を使う。値の表示器は S11c で足す

### 番号の決まり

- 入力の番号は、受け付けなかった入力も含めて、trivia だけでない入力が来るたびに1つ進める。番号を使い回すと、`CodeBase` にすでに入った `input$N` と同じ名前で違うコードができるためである
- 根の番号も使い回さない (上の「根」)

### エラー

- **診断**: 誤りがどのファイルにあっても、入力を受け付けず、その誤りを返す。前の入力のファイルの誤りは、上の「一様な位置」のような場合に出うる。警告 (E4004、E4005) は、この `eval` で初めて読んだファイル (パスで見分ける) のものだけを返す。セッション全体を入力ごとに検査し直すので、前の入力の警告が毎回出るのを防ぐためである。誤りがあれば、セッションは変えない
- **続けられる実行時エラー**: extern の誤り (Arith、Output、Io、NotUtf8) と、上限と割り込みで止まったとき。`eml run` と同じ形 (`runtime error: …` と位置) で返す。続けて `Ctx` の evv と yield の状態を空に戻し、`let` の束縛は作らない。evv と yield が持っていた語と、スタックに残った語は解放せず、ヒープに残す。回収は S11b の根からの走査で行う。evv と yield の状態を空に戻す操作は `eml_rt` に足し、Verus で証明する。`Ctx` と各基本操作は誤りの道でもヒープの不変条件を保ち、捨てた語はリークするだけなので、`Ctx` を使い続けてもメモリの安全性は保たれる
- **続けられない実行時エラー**: ヒープの誤り (`Fault::Heap`、`RootMisuse` を含む) と内部の誤り (`VmFault::Internal`)、`Machine::load` の誤り (内部の誤り。追記は途中で止まると `CodeBase` が書きかけになる)。ヒープを信用できないので、`Repl` を使えない状態にし、後の `eval` はすべて `Broken` を返す。`RuntimeError` は `Clone` でないので、後の `eval` の誤りは、前に壊れたことを示す内部の誤りにする

### 検査モード

- 入力ごとの実行の後には、`check_invariants` と `check_finished` だけを確かめる。根から届く物体を残しているので、リークの検査はしない
- リークの検査は `close` で根をすべて手放した後に1回だけ行う。S11a では、実行時エラーの後に残した物体がここに数えられる。実行時エラーを含むトランスクリプトでは、S11a はリークを見分けられない。S11b で 0 になる
- 検査モードは解放したブロックを使い回さないので、セッションの間メモリが増え続ける

### 伸びる費用

- 入力ごとに、セッションの定義、`let` の束縛、import のすべてを型検査し直す。式の入力は列に残さないので、検査し直さない
- 新しい定数を持つ入力ごとに凍結した塊が1つ増え、塊は使う大きさの級ごとに少なくとも1ページ (64 KiB) を持つ。塊のページは確保量に数える。塊を詰め直すことは、ロードマップの論点に残す
- 定義し直された `let` の古い根は手放さない

## API

`eml_cli` に `Repl` を足す。

```rust
pub struct Repl { /* 受け付けた入力の列、import のキャッシュ、AnyMachine、次の入力の番号、一様な位置、表示したファイルのパス */ }

impl Repl {
    pub fn new(config: &RunConfig, source: Box<dyn ModuleSource + Send>, root: &str, host: HostRef) -> Repl;
    pub fn eval(&mut self, text: &str) -> Evaluated;
    /// 根をすべて手放す。検査モードでは、その後に残った物体の数を返す。
    pub fn close(self) -> Closed;
}

pub struct Evaluated {
    pub diagnostics: Vec<Diagnostic>,
    /// `diagnostics` の位置を表示するためのファイル。番号は `eval` ごとに振り直す。
    pub files: SourceFiles,
    pub outcome: Outcome, // Empty / Accepted / Rejected / Failed(RuntimeError) / Broken(RuntimeError)
}
```

- `input_status` は `eml_syntax` の関数で、`eml_cli` から再公開する
- 値の表示は host に書く
- `Closed` は検査モードのリークの誤り (`Option<RuntimeError>`) を持つ。`Machine::close` は `Result<(), RuntimeError>` を返す
- `Broken` は続けられない実行時エラーで、`Repl` はこの後使えない。`Empty` は trivia だけの入力である
- `Repl` は `Send` にする。`Session` と同じく、後で並列のコンパイルやクエリに載せる妨げにしないためである
- S11c の `:type` は、検査だけをする入口 (`Repl::type_of` など) を足す。S11a の構造はそれを妨げない

## テスト

- **トランスクリプトのテスト** (`crates/eml_cli/tests/repl/<分類>/<名前>.repl`)
  - 形は上の「トランスクリプトの形」である。harness は入力の終わりの規則を確かめてから、入力を1つずつ `eval` に渡す

  - UI テストと同じく、検査モードと速いモードで流す ([テスト戦略](../../implementation/testing.md) の「2つのモードで流す」)。表示と、各入力の結果の種類が同じになることを確かめる。`close` の数と、検査モードだけが出す誤りは比べない
  - 確かめる場面
    - 定義と式、`let` と型の明示、式の defaulting

  - UI テストの出力は変わらない
