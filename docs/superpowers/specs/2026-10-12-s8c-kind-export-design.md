# S8c 書き出す型の線形性

位置づけ: 作業の設計。ロードマップの S8 の3つ目の作業を定める。S8c を終えたら、決まったことを `docs/spec/` と `docs/implementation/` に移し、この文書を削除する。

## 目的

`eml_types` が後の段階に書き出す型 (`TypeStore` の `TypeKind`) に、矢印の線形性と、決まらなかった型変数の Kind を持たせる。あわせて、宣言の型に残る Kind 変数を instance ごとに評価する関数と、型の線形性を求める関数を公開する。S8d の Kind の印 (`unr` / `lin` / `poly`) は、ここで書き出した型から決める。

完了の条件は次の6つである。

- 本体の型、具体化の型引数、宣言の型のすべてで、矢印が線形性を持つ。線形性の値は下の「値の規則」に従う
- `TypedProgram::kind_values` と `TypeStore::linearity` で、instance の型の線形性が `Unr`、`Lin`、`Poly` のどれかに決まる
- 線形性だけが違う具体化は、別の instance として別の名前になる (`id@[Int %1 -> Int]` と `id@[Int -> Int]`)
- 全 UI テストと `bench/` で、下の「食い違いがないことの検査」が通る
- 全 UI テストが通り、出力は変わらない。診断の文字列も変わらない
- テストの成否と期待値は、下の「テストの変更」に挙げたものだけが変わる

## S8 の分け方の改め

S8b の設計で S8 を3つに分けた。S8c の設計で、Kind の書き出しだけで1つの作業になる大きさだと分かったので、S8c を2つに分け、S8 を4つにする。ロードマップの段の列では S8 の1行のままにする。

| 作業 | 中身 |
|---|---|
| S8a (終えた) | LIR の crate、パスを LIR に移す、CEK が LIR を読む |
| S8b (終えた) | Perceus の所有の形、基本操作の引数の借用、`File` の実行時の検査 |
| S8c (この文書) | 書き出す型の線形性、instance での Kind の評価、型の線形性、instance の名前 |
| S8d | translate と EP と box の挿入の Kind の印、EP の明示の drop、extern の行の Kind の列、V1 と V2、テキストの形の印 |

分ける理由は次のとおりである。

- 型だけから印を決める案は採れない。`tests/ui/run/files/file_in_return_clause_on_abort.em` では、使われない `return x ->` の `x` は型が `_` で、使用回数のパスが `x` の Kind を `Unr` に決めている。型だけから決めると、`x` は `poly` になり、今ある `decref x` を V1 が拒む
- そのため、解いた Kind を型に持たせて書き出す必要がある。これは `eml_types` の段の組み替え (下の「型検査の順」) を伴う
- S8c は S8d がなくても検査できる。書き出した型と評価の結果は `eml_types` の単体テストで、instance の分かれ方は `eml_core_ir` のテストで確かめられる

この作業の前に、別の修正を2つ入れた。どちらも、操作の型を節でどう具体化するかの規則である ([エフェクトと handler](../../spec/effects.md) の「handler の意味」)。

- 結果の型だけに現れる操作ごとの型変数は、節の中で `Lin` 以上にする
- 呼ぶ側から節へ渡る位置の矢印は、操作の型で `Unr` に固定する。節が作って渡す位置の矢印は、節の中で `Unr` 以下にする。操作ごとの row 変数の多重度は、節の中で `Multi` 以上にする

これで、呼ぶ側から節へ渡る関数の矢印は、どちらの側でも `Unr` になる。節が作って渡す関数の矢印は、節の側では `Unr` で、呼ぶ側では縛らない (呼ぶ側はそれを `Lin` の関数として扱ってもよい)。下の「呼び出し元との食い違いがないこと」と `OpVar` の Kind は、この規則を前提にする。

## 書き出す型の形

### `Lin`

書き出した型の矢印の線形性と、決まらなかった型変数の Kind を、公開の型 `Lin` で表す。推論の中の `ArrowLin` は今も crate の中にある。今は公開している `eml_types::Linearity` と `Multiplicity` は、後の段階が使っていないので crate の中に移し、公開する線形性は `Lin` だけにする。

```rust
pub enum Lin {
    Unr,
    Lin,
    /// 呼び出し側が決める。instance の代入の後の型、推論の途中で書き出す型、結果の型だけに現れる `OpVar` (と、
    /// 代入でそれから作る `Flexible`)、一様な位置、entry、導出とタプルの生成器の鍵の `Flexible` に現れる
    Poly,
    /// 宣言の Kind 変数。番号の付け方は下の「宣言の Kind 変数の番号」
    Var(u32),
}
```

`TypeKind` は次のように変わる。

- `Fn { param, lin: Lin, effects, tail, ret }`
- `Flexible(Lin)`: 推論で決まらなかった型変数、一様な位置と entry と生成器の鍵の型変数、代入で `OpVar` から作った型変数の Kind。代入の前の本体の型では `Flexible(Var(_))` もありうる
- `OpVar(String, Lin)`: 操作ごとの型変数の Kind。instance の代入で `Flexible` の同じ Kind になる

`Rigid(String)` は Kind を持たない。シグネチャの型変数の Kind は宣言の Kind 変数 (`μ`) で、instance の代入で型引数に置き換わるためである。

### 宣言の Kind 変数の番号

`Var(i)` の番号は、宣言ごとに付ける。

- `i < lin_vars` (宣言の `Shape` の `lin_vars`) は、宣言自身の線形性の Kind 変数である。番号は `Shape` の番号 (型変数の `μ` と矢印の `m` を外側から数えた順) と同じにする
- `i ≥ lin_vars` は、本体の変数の要約である。`Var(lin_vars + k)` は、宣言自身の変数の集合 `joins[k]` の結びを表す (下の「値の規則」)。同じ集合は同じ番号を共有する。番号は、書き出す順 (式、局所変数、パターン、具体化、更新、捨てたフィールドの表を、それぞれ ID の順にたどる順) で集合が初めて現れた順に振る。ダンプとテストの期待値が実行ごとに変わらないようにするためである
- 集合が1つの変数だけなら、`joins` を作らずにその変数の `Var(i)` を使う。集合の変数がすべて定数に畳まれたときは、集合も定数に畳む

本体の型の `Var` は、その本体を含むトップレベルの宣言 (instance のメソッドの関数と既定のメソッドを含む) の番号で数える。ラムダとハンドラの節も、含む宣言の番号を使う。

同じ `Var(3)` でも宣言が違えば意味が違うが、`TypeId` は同じになる。今の `Rigid("a")` も同じである。型の表の「ID が同じことと型が同じことが一致する」は、宣言に対して相対的な型については、同じ宣言の中で比べたときに成り立つ、と改める。

### 宣言ごとの記録

`TypedProgram.decls` の宣言ごとの記録 (`DeclType`) は、今も宣言の形 (`Shape`) と宣言自身の Kind 変数のスキーム (`KindScheme`) を crate の中だけで持っている。これに、本体の変数の要約 `joins: Vec<Vec<u32>>` を足す。どれも crate の外からは読めず、下の `kind_values` だけが使う。

## 型検査の順

### 今の順

`check_module` は、すべての本体を検査して書き出し (段1)、その後で呼び出しグラフの SCC ごとに Kind を解く (段2)。本体の型は Kind を解く前に書き出すので、矢印の線形性を持てない。段1の推論用の表は `into_problem` で Kind の制約に変わり、捨てられる。

### 新しい順

1. 今と同じく、instance の検査、シグネチャ、本体のない宣言のスキーム、`check_main` を行う。等式のない関数に空のスキームを持たせる処理 (今は段1の後にある) も、ここに移す。SCC の順に解くと、呼ぶ側の SCC を解く時点で呼ばれる側のスキームがそろっていなければならないためである
2. 呼び出しグラフの SCC ごとに、呼ばれる側から順に次を行う
   1. 各メンバーの本体を検査し (段1)、推論用の表を残す。`into_problem` は、表から Kind の制約を取り出すだけの形 (`take_problem`) に変え、表は残す
   2. その SCC の Kind を解く (`solve_scc`)。同時に、書き出す型に現れる本体の変数の要約を求める (下の「値の規則」)
   3. 各メンバーの本体の型を、解と要約を使って書き出し、表を捨てる
3. 今と同じく、メソッドの Kind の検査、違反の報告、宣言ごとの結果、一様な位置、網羅性の検査を行う。メソッドの Kind の検査は、Kind の制約があったかどうかだけを読むので、制約そのものは SCC を解いた後に捨ててよい

この組み替えで結果が変わらない理由は次のとおりである。

- 本体の検査はシグネチャしか読まないので、本体を検査する順を SCC の順に変えても結果は変わらない。診断は `Session` が並べ替えるので、順も変わらない
- 型を登録する順が変わるので、`TypeId` の番号は変わる。instance の番号と後の段階は、今も `TypeId` の値に依存しない

### メモリと時間

- 同時に生きている推論用の表は、処理中の SCC のメンバーの分だけである。ふつうのプログラムでは1つで、今と同じである。大きな SCC (n 個の関数の輪) では n 個になるが、今もすべての Kind の制約を同時に持っているので、同じ大きさの程度である。SCC を解き終えるたびに表を捨てるので、プログラム全体の表を同時に持つことはない
- 新しく増える仕事は要約である。止まる所 (宣言自身の変数) はメンバーごとに違うので、メンバーごとに求める
  - メンバーの書き出す本体の変数の成分から、強連結成分の DAG を下にたどり、「下に届く宣言自身の変数の集合」を成分ごとに覚えながら求める (動的計画法)。そのメンバーの宣言自身の変数を含む成分で止まる。各成分はメンバーごとに1回だけ計算し、集合の大きさは `lin_vars` で抑えられる
  - 宣言自身の変数を持たないメンバー (`lin_vars = 0`) では、集合はいつも空なので、たどらずに SCC 全体の最小解の値 (`solve` が求めた値) を使う。その値は、下の規則の2つ目と3つ目が与える値と同じである
- 要約の仕事は、メンバーごとに、書き出す変数から下に届く範囲 (自分の成分で止まる) の大きさである。上に届く範囲をたどる今の `residual` とは向きが違うので、同じ大きさになるとは言えない。大きな SCC で2乗にならないことは、下の scaling テストで確かめる
- `tests/scaling.rs` に3つ足す。どれも、今ある scaling テストと同じ形 (時間で比べ、ふだんは `#[ignore]`) にする
  - 関数を引数に取る関数の輪
  - 各メンバーが局所のラムダ (`fn u -> x`) を持つ関数の輪
  - 宣言自身の変数を持たない多くのメンバーが、長い矢印の鎖 (`q_n ≤ … ≤ q_1`) の上を参照する SCC

### 推論の途中で書き出す型

Kind を解く前にも、型を書き出す箇所がある。診断の文字列 (`check/report.rs`)、`usage.rs` の `OmittedReturn`、`constraints.rs` の E2006 と E2009、`check_derived_fields`、`check_main` である。

- これらはどれも線形性を読まない。そこで `Exporter` に「診断のための書き出し」の使い方を持たせ、決まっていない矢印を `Poly` に、決まらなかった型変数を `Flexible(Poly)` にする
- 診断の表示は線形性を表示しないので、文字列は変わらない
- `check_main` は、期待する型 `Unit -> <IO> Unit` を `lin: Unr` で作る。シグネチャの一番外の矢印は `Unr` に固定されているので、書き出した `main` の型と ID が一致する

宣言の型は `Exporter` ではなく `Shape::export` が書き出す。これにも2つの使い方を持たせる。

- スキームを使う書き出し: `typed_program` が宣言ごとの結果を作るときに使う。スキームで定数に決まる宣言自身の変数を定数に畳み、残りを `Var(i)` にする
- スキームを使わない書き出し: `check_main` が段0で使う。宣言自身の変数はすべて `Var(i)` にする。`main` の型は矢印が一番外の1つだけで、`Unr` に固定されているので、`Var` は現れず、期待する型と ID が一致する
- `Shape::kind_names` が作る表示用の `Fn` は、診断の表示と同じく線形性を表示しないので、`Poly` で作る

### query への移行に与える影響

本体の書き出した型は、その SCC の解 (呼ばれる側から複写したスキームを含む) に依存する。そのため、salsa に移すときは、本体の型を本体ごとの query ではなく、SCC ごとの query の出力にする。[コンパイラの構成](../../implementation/architecture.md) の「`eml_types` の内部」に、この点を書き足す。

## 値の規則

### 書き出すときの規則

宣言の中の Kind 変数を書き出すときは、次のように決める。たどるのは、SCC で合わせた制約のグラフの強連結成分である。同じ成分の変数は等しい。宣言自身の変数を含む成分に出会ったら、そこから先はたどらない (今の `residual` と同じ止め方)。

- 本体の変数 (ラムダの矢印、部分適用と具体化の変数、handler の状態の矢印など) には、解の最小値を取る
  - 本体の変数の成分が宣言自身の変数を含むなら、その変数と等しいので、その中で番号のいちばん小さい変数の `Var(i)` にする。その変数が定数に畳まれていれば、その定数にする
  - そうでなく、下にたどって定数の `Lin` に届けば `Lin` にする
  - そうでなく、下にたどって届く宣言自身の変数がなければ `Unr` にする
  - そうでなければ `Var(lin_vars + k)` にし、届いた宣言自身の変数の集合を `joins[k]` に記録する。届いた成分が宣言自身の変数を2つ以上含むときは、その中で番号のいちばん小さい変数を記録する (同じ成分の変数は等しい)
  - `joins` の集合は、定数に畳まれた変数で整える。`Lin` に畳まれた変数を含めば集合全体を `Lin` にし、`Unr` に畳まれた変数は集合から除く。残りが空なら `Unr`、1つならその `Var(i)` にする
  - 上にたどって定数の `Unr` に届く場合は、別の規則にしない。宣言自身の変数を通らずに `Unr` に届くなら、下に届く宣言自身の変数も同じ道で `Unr` に届き、スキームで定数の `Unr` に畳まれるので、`joins` も `Unr` に畳まれる
- 1つ目の場合を外すと、宣言自身の変数と等しい本体の変数が `Unr` になり、正しくない。たとえば `f : (a -> <IO> Unit) -> a -> Int -> <IO> Unit` を `f eat x n = if n == 0 then eat x else f (fn g -> eat (g ())) (fn () -> x) (n - 1)` と定義すると、`fn () -> x` の矢印は再帰の呼び出しで `μ_a` と等しくなる。`main` が `a` を `File` で呼ぶと、この関数は `File` を捕まえる。注釈 `let h = (g : Int -> Int)` の矢印も、`g` の矢印と等しいので同じ値になる
- 宣言自身の変数のうち、定数だけで値が決まるものは、宣言の型でも本体の型でも定数に畳む。どの instance でも同じ値になるためである。スキームの辺を上にたどって定数の `Unr` に届けば `Unr` に (「instance での評価」の固定と同じ)、下にたどって定数の `Lin` に届けば `Lin` に畳む。`Var` は、instance によって値が変わる所にだけ残る

最小値を取るのは、捕まえた値や束縛した値から決まる下限が、実行時の値の正直な Kind だからである。行の分類で、決まらなかった row 変数を `RowYield::Never` にするのも同じ選び方である ([型と Kind](../../spec/types.md) の「row の具体化の記録」)。

「最小と最大が一致すれば確定し、ずれれば `Poly`」という規則は採らない。使い方が `Unr` を強いないラムダは最大が `Lin` になるので、1回だけ呼ぶラムダや `apply` に渡すラムダが軒並み `Poly` になる。`id (fn x -> x)` の鍵も `Int %m -> Int` になり、instance が分かれる。

### instance での評価

```rust
impl TypedProgram {
    /// 宣言 `decl` の `Var(i)` の、型引数 `args` (`Shape::rigids` の順) の instance での値。値は `Unr`、`Lin`、`Poly` のどれか
    pub fn kind_values(&self, decl: ValueItem, args: &[TypeId], store: &TypeStore) -> Vec<Lin>;
}
```

結びの順は `Lin` > `Poly` > `Unr` とする。`Lin` を含めば `Lin`、`Lin` を含まず `Poly` を含めば `Poly` である。値は、宣言のスキーム (宣言自身の変数の間の制約と、定数の境界) の上で求める。

- `Unr` への固定: 宣言自身の変数 `v` から、スキームの辺を上にたどって定数の `Unr` の上限に届くとき、`v` は `Unr` に固定されている。たどるのは辺と定数だけで、途中の型変数 `μ` の instance での値 (`args` から求めた値) は使わない
- 値 `val(v)`: 宣言自身の変数ごとに、1つの不動点で求める
  - `v` が `Unr` に固定されていれば `Unr`
  - そうでなければ、`base(v)`、`v` の定数の下限、スキームで `v` の下にある宣言自身の変数 `w` の `val(w)` の結びである
  - `base(μ_i)` は `linearity(args[i])`、矢印の `base(m)` は `Poly` である。矢印の値は呼び出し側が決めるためである
- 本体の要約 `Var(lin_vars + k)`: `joins[k]` の各変数の `val` の結び

同じ成分の変数 (スキームで輪になった変数) は、どれも同じ値になる。固定は輪を通じて伝わり、結びも輪の中で等しくなるためである。そのため、書き出すときの規則の「番号のいちばん小さい変数」の選び方は、値に影響しない。

型変数の値に、下にある矢印の `val` を結ぶのは、次の場合があるためである。SCC の中の多相再帰で、型変数 `a` に関数を渡すと、スキームに `m ≤ μ_a` が残る。たとえば次の `f` の `k` は、`x`、`eat`、`g` を捕まえ、再帰の呼び出しで `a` として渡される。

```
f : a -> (a -> <IO> Int) -> (Int -> <IO> Int) -> Int -> <IO> Int
f x eat g n =
  if n == 0 then g (eat x)
  else
    let k = fn y -> g (eat x + y)
    f k (fn h -> h 1) (fn z -> z) (n - 1)
```

`main` が `g` に `File` を捕まえたクロージャを渡して `f@[Int]` を呼ぶと、`k` はそのクロージャを捕まえる。`k` の矢印は `μ_a` と同じ成分にあるので `Var(μ_a)` になる。`μ_a` の値を `linearity(Int)` と定数だけから求めると `Unr` になり、`File` を持つ `k` が `unr` になってしまう。`val` では `g` の矢印の `Poly` が `μ_a` に伝わるので、`k` は `Poly` になり、再帰の呼び出しは `f@[Int %m -> Int]` になる。

`Unr` への固定で `μ` の instance での値を使わない理由は次のとおりである。宣言自身の `μ` は、1つの宣言の中ではふつう制約の下側にしか現れない。例外は SCC の中の等式で、同じ SCC の別の宣言の具体化の変数 (下限を持つ) が、この宣言の `μ` と等しくなり、スキームに `m ≤ μ` が残りうる。このとき、多相再帰の instance `f@[Int]` で `μ` の値 `Unr` を `m` の上限に使って `m` を `Unr` にすると、外の呼び出し元が複写したスキームでは同じ `m` が `Lin` になり、`unr` と `lin` が食い違う。`μ` が定数の `Unr` の上限を持つ場合 (`m ≤ μ ≤ Unr`) は、どの instance でも `m` は `Unr` なので、辺をたどって固定としてよい。

instance の鍵は、今と同じく型引数だけにする。Kind の値は宣言と型引数から決まるので、鍵に入れる必要がない。呼ばれる側の矢印の変数は鍵に入らず、instance の中では `Poly` になる。たとえば `map` を `lin` のクロージャで呼んでも `unr` のクロージャで呼んでも、instance は1つの `map@[Int, Int]` で、その `f` は `Poly` である。

### 呼び出し元との食い違いがないこと

S8d の V2 は、`unr` と `lin` の受け渡しを拒み、`poly` はどちらとも受け渡せる関係にする (ロードマップの今の V2 は順序の形なので、下の「ドキュメントの変更」で改める)。この規則のもとで、正しいプログラムに `unr` と `lin` の受け渡しが出ない理由は次のとおりである。

- 呼ばれる側の矢印が `Unr` になるのは、スキームで `Unr` に固定されているときだけで (矢印の `base` は `Poly` なので)、どの instance でも同じである。呼び出し元の具体化の変数は、呼ばれる側のスキームを複写した制約を持つので、そのときは呼び出し元でも `Unr` 以下に決まる
- 呼ばれる側の値が `Lin` になるのは、定数の下限か、型引数の `Lin` からである。呼び出し元の具体化の変数も同じ下限 (複写した定数か、型引数の型の Kind) を持つので、最小値は `Lin` になる。書き出しは制約に対して単調なので、呼び出し元の線形性が呼ばれる側の値を下回ることはない
- 型変数の値が `Unr` になるのは、型引数が `Unr` で、下にある宣言自身の変数もすべて `Unr` のときである。instance の中の値は、引数、定数、それらを使った呼び出しから来るので、instance の鍵がそれを保つ
- それ以外の呼ばれる側の値は `Poly` で、どちらとも食い違わない
- 本体の変数は、その宣言の外の変数に依存しないので、全体で1つの選び方 (最小値) をすれば食い違わない
- 1つの本体の中では、矢印の単一化は等式なので、同じ型の値は同じ値になる。宣言自身の変数と等しい本体の変数も、上の規則でその変数の `Var` になる
- 操作を呼ぶ側と節は、スキームを複写する関係にない。呼ぶ側から節へ渡る関数の矢印は、前提の修正でどちらの側でも `Unr` になる。節が作って渡す関数の矢印は、節では `Unr` で、呼ぶ側では `Lin` にもなりうるが、値は `k` (一様な位置) を通って渡り、両側の変数が直接受け渡されることはない。型変数の値は、呼ぶ側では具体的な型、節では `Unr` か `Poly` の `OpVar` で、`Poly` はどちらとも食い違わない。節の関数の入口の引数と戻り値は、操作の宣言の型の `Var` を `Poly` として評価したものになる
- この主張は、下の「食い違いがないことの検査」が debug ビルドで確かめる

## `Flexible` と `OpVar` の Kind

| 出どころ | 値が実際にあるか | Kind |
|---|---|---|
| 本体で推論が決めなかった型変数 | 正しいプログラムではない。`α` の値を作れる所は `α` を決めてしまう | 上の「書き出すときの規則」の最小値。ふつうは `Unr` |
| 関数の一様な位置の鍵 (`instances.rs` の `add_uniform`) | ある。`f@[_]` は `File` の呼び出し元にも使われる | 呼ばれる側のスキームで `μ` が `Unr` に固定されていれば `Unr`、そうでなければ `Poly` |
| 導出とタプルの生成器の一様な位置の鍵 (`add_generated`) | 正しいプログラムでは現れないとみられる。制約付きの一様な位置は E2012 になり、導出の文脈はフィールドに現れる型変数にだけクラスを与えるため | `Poly`。関数の一様な位置と同じく、どの値にも食い違わない安全な側にする |
| entry の鍵 | ある | 関数の一様な位置と同じ |
| `OpVar` | ある | 操作の引数の型に現れれば `Unr`、結果の型にだけ現れれば `Poly` |

関数の一様な位置と entry の鍵の Kind は、次の関数で求める。「`Unr` に固定されている」の意味は、上の「instance での評価」と同じである (スキームの辺を上にたどって定数の `Unr` に届く)。

```rust
impl TypedProgram {
    /// 関数 `function` の一様な位置 `position` の型変数の Kind。`Unr` か `Poly`
    pub fn uniform_kind(&self, function: FunctionId, position: usize) -> Lin;
}
```

一様な位置と entry の鍵を `Lin` にしないのは、スキームが `Lin ≤ μ` を持っていても、`Int` の呼び出し元は `unr` の値を渡すからである。

`OpVar` の Kind は、書き出すときに一般の規則 (最小値) ではなく、次のように決める。表の操作ごとの rigid 変数に「操作の引数の型に現れる」かを記録し (節の具体化はすでにこれを求めている)、書き出しはそれを読む。

- 引数の型に現れる `OpVar` は `Unr` にする。節はその `μ` を `Unr` 以下に縛っているので、最小値とも一致する
- 結果の型にだけ現れる `OpVar` は `Poly` にする。節の中では `Lin` 以上に縛っているので、最小値は `Lin` になるが、実際の値は操作を呼ぶ側が決めるので、一様な位置と同じく `Poly` にする。節の中でこの値を捕まえたクロージャは、下限が `Lin` なので `Lin` になる

## 型の線形性

```rust
impl TypeStore {
    /// 型の値の線形性。`Unr`、`Lin`、`Poly` のどれか
    pub fn linearity(&self, ty: TypeId) -> Lin;
}
```

- `data.rs` の効く型引数の表 (`DataKind`) を `TypeStore::new` で作り、ストアに持たせる
- 値は型を登録するとき (`intern`) に、子の値から求めて型ごとに持つ。今の「誤りを含む」「型変数を含む」の旗と同じ扱いである。読むときに求めて覚える形にすると、内部の可変性が要り、`TypeStore` が `Sync` でなくなるためである
- 型ごとの値は次のとおりである
  - `Con`: 宣言が `Lin` なら `Lin`。そうでなければ効く型引数の値の結びで、効く型引数がなければ `Unr`
  - `Tuple`: 要素の値の結び。要素がなければ `Unr`
  - `Fn`: その `lin`
  - `Flexible(k)` と `OpVar(_, k)`: `k`。`OpVar` の Kind は定数なので、代入しない本体の型 (型変数のない関数の本体にある節) でも読める
  - `Error`: `Unr`
  - `Rigid` と `Var` を含む型: 宣言に対して相対的な型なので、意味のある値を持たない。登録するときは「相対的」の印を持たせ、読むときは `debug_assert` で止めて `Poly` を返す。宣言の中の値は `kind_values` が自分で求める
- 結びの順は `kind_values` と同じである
- S8d の extern の Kind の列を確かめるテストも、この関数を使う

## 代入と単相化

- `Substitution::new(type_args, kind_values)` が、`Rigid` を型引数に、`Var(i)` を `kind_values[i]` に置き換え、`OpVar(name, k)` を `Flexible(k)` にする。`kind_values` は宣言のすべての `Var` の値を持たなければならず、足りなければ `debug_assert` で止める。instance の写しの誤りを、黙って `Poly` にしないためである
- 型引数だけを置き換える `Substitution::partial(type_args)` を別に用意する。`Var` はそのまま残す。今は `crates/eml_core_ir/tests/externs.rs` が、メソッドの宣言の型の型引数だけを置き換えるのに使う
- 型の表は、型ごとに「Kind 変数を含む」旗を持つ。`Var` を持つ `Fn` か `Flexible(Var(_))` を含む型に立てる。代入の早い戻り (型変数を含まない型をそのまま返す) は、この旗も見る
- `instances.rs` の「型変数を含まない関数は写さない」近道は、宣言ごとの判定にする。宣言が型変数を持つか、定数に畳まれなかった宣言自身の線形性の変数を持てば写す (`joins` の変数も宣言自身の変数なので、これで足りる)。たとえば `twice : (Int -> Int) -> Int -> Int` は型変数を持たないが、矢印の `Var` を持つことがある。`OpVar` だけを含む関数は今と同じく写さない。`OpVar` の Kind は定数で、`linearity` がそのまま読めるためである
- instance の型を写した後に `Var` が残らないことを、今の「型変数が残らない」`debug_assert` に足す
- 関数の一様な位置と entry の鍵の `Flexible` は `uniform_kind` の値を、導出とタプルの生成器の鍵の `Flexible` は `Poly` を持つ
- 代入の箇所は、instance の写しのほかに `instances.rs` の `field_types` (構成子の宣言の型の、フィールドの型を取り出す) がある。ここは `kind_values(ValueItem::Constructor(c), args)` を求めて `Substitution::new` に渡す
- 操作と構成子の宣言の型そのものを代入せずに読む箇所 (`translate/program.rs`) は、S8c では線形性を読まないので変えない。S8d の包みの関数 (`op$`、`con$`) は、`Var` を `Poly` として評価し、`Rigid` も `Flexible(Poly)` に置き換える。`Rigid` を含む型では `linearity` が意味を持たないためである

### 食い違いがないことの検査

「呼び出し元との食い違いがないこと」の主張は、S8d の V2 が初めて確かめる。それより前に崩れていれば S8d で初めて見つかるので、S8c で debug ビルドの検査を入れる。参照の検査と操作の検査は両側の食い違いを、捕獲の検査は値の線形性に対する印の正しさを見る。

- 比べ方: 2つの型を構造をそろえてたどり、対応する線形性 (矢印の `lin`、`Flexible` と `OpVar` の Kind) が、一方が `Unr`、他方が `Lin` なら食い違いとする。`Poly` はどちらとも食い違わない。片方が `Flexible(k)` か `OpVar(_, k)` で他方が別の形の型 `T` なら、`k` と `linearity(T)` を比べる。この比べ方は `eml_types` の公開の関数 (`TypeStore::lin_compatible`) にし、`eml_types` の単体テストで、食い違う型と食い違わない型を表に登録して確かめる
- 参照の検査: `instances.rs` は、instance を集めた後に、各関数の instance の中の参照 (`types.exprs` の、関数を指す式) ごとに、代入した参照の型と、呼ばれる instance の型 (`signature`) を比べる。参照ごとに見るので、飽和した呼び出しだけでなく、部分適用と値としての関数の参照も入る。導出とタプルの生成器の instance と extern の関数は、比べる型を持たないので比べない (extern は S8d の Kind の列で確かめる)
- 操作の検査
  - 各 `perform` の参照の型を、その参照の具体化 (`Instantiation`) の `kind_values` で評価した操作の宣言の型と比べる
  - 節の引数のパターンの型と `k` の型は、操作の宣言の型と、`Rigid` をどの型とも合う型、`Var` を `Poly` として比べる。節の具体化 (エフェクトの型引数と操作ごとの型変数) は `BodyTypes` に記録されていないので、`kind_values` は求めない。この比べ方で確かめられるのは、引数の型の矢印 (宣言で `Unr`) と、結果の型の中で呼ぶ側から節へ渡る位置の矢印 (宣言で `Unr`) が、節の側でも `Unr` と食い違わないことである
- 捕獲の検査: 両側の比べ方では、両側が同じに誤った印 (`Lin` の値を持つ `unr` のクロージャ) を見つけられないので、クロージャを作る所で、矢印が `Unr` なら捕まえた値の型の `linearity` がすべて `Unr` であることを確かめる
  - 確かめる所: translate がクロージャを作る所のうち、ラムダ、知っている関数と構成子の部分適用 (`closure` を作る飽和しない呼び出し)
  - 確かめない所: 状態のある `k v` (クロージャでなく `apply` になる)、値として渡された関数の実行時の部分適用 (呼ばれる側が分からない)、操作の節のクロージャ、handle の本体のクロージャ、継続を包む関数。これらの矢印の線形性は、操作と継続の宣言から決まり、S8d の印でまとめて扱う
- 形が一致しない所 (誤りの跡と、上に挙げた `Flexible` との比べ方の外) は比べない
- この検査は、全 UI テストと `bench/` を通る。S8d の V2 と V1 は、この検査を変数の印の上の検査に置き換える

## instance の名前

- 名前の型引数は、診断の表示に矢印の線形性を足した表示で書く。Haskell の LinearTypes に合わせて、`Lin` は `a %1 -> b`、`Poly` は `a %m -> b`、`Unr` は `a -> b` と書く
  - 例: `id k` (`once` の `k`) は `id@[Int %1 -> Int]`、`id inc` は `id@[Int -> Int]` になる。呼び出し元の決まらない矢印からは `id@[Int %m -> Int]` ができる
  - 線形性を表示しないと、2つ目の instance は表示が同じになり、`id@2` の番号付きの名前に落ちる ([Core IR](../../spec/core-ir.md) の「変換の規則」)。正しいが読めない
- 名前の `Flexible` は、今と同じく Kind によらず `_` と書く。一様な位置と entry の鍵の `Flexible` の Kind は呼ばれる側で決まるが、本体で決まらなかった型変数の `Flexible` は、呼び出し元の最小値なので、呼び出し元によって `Unr`、`Lin`、`Poly` のどれにもなりうる。`OpVar` から来た `Flexible` も、操作ごとに `Unr` か `Poly` になる (2つの節の `id x` など)。そのため、同じ関数の鍵が `Flexible` の Kind だけで分かれることはありうる。まれなので表示に足さず、分かれたときは、今と同じく番号付きの名前に落ちる
- 名前は長くなるので、表示の長さの上限 (`NAME_LIMIT`) を超えて番号付きの名前に落ちる場合が、今より少し増える。上限は変えない
- 診断の表示と `eml_types` のダンプの表示は変えない。表面の構文では `m` を書かないからである。E2001 の、線形性だけが違うときの note も今のまま残す
- 今のテストにある名前のうち矢印を含むのは `count@[Int, Unit, Bool, _ -> <_> _]` だけで、その矢印は `id` の一番外の矢印なので `Unr` である。名前の変わるテストはない見込みで、`cargo test -p eml_core_ir` で確かめる

## 範囲に入れないもの

- Kind の印、V1、V2、EP の明示の drop、`switch` の nullary の case の `decref` の扱い、extern の行の Kind の列、テキストの形の印は S8d で行う
- 多重度 (`once` / `multi`) は書き出さない。S8d の継続の印は操作の宣言の多重度から決めるので、書き出す型に要らない
- 診断に線形性を表示することはしない
- 線形性を、instance の鍵の外の Kind の単相化に使うことはしない。`lin` と `poly` のコードは同じなので、分けても得るものがない
