# 縦の貫通 段階2 の設計

位置づけ: 作業用の設計文書。規範に当たる決定は `docs/spec/` に反映済みで、この文書は段階2の内部構造だけを扱う。段階2を終えたら、残す価値のある内容を `docs/implementation/architecture.md` に移し、この文書は削除する。

## 目的

段階1で通した狭い言語に、関数値と多相を加える。ラムダ、クロージャ、部分適用、シグネチャの型変数と row 変数、Kind の SCC ごとの推論を、HIR、型検査、Core IR、インタプリタ、ランタイムの全体に通す。段階3のエフェクトでは、継続や handler の節が関数値とラムダを使うので、その前に関数値の表現を固めておく。

## 段階2の言語

新しく通すものは次のとおり。

- ラムダ `fn x y -> e`。引数は変数、`_`、`()`、型の明示 `fn (x : Int) -> e`
- 最後の引数のラムダ (`each xs fn x -> ...`)。パーサはすでに読めるので、HIR で受けるだけである
- 関数値。トップレベルの関数と組み込みを値として使う、関数型の引数や局所変数を呼ぶ、部分適用、引数が矢印より多い呼び出し (戻った関数にさらに適用する)
- 引数が矢印より少ない等式 (`add1 : Int -> Int` と `add1 = add 1`)。段階1で E0004 にしていた
- シグネチャの型変数と row 変数 (`<e>`、`<IO | e>`)。本体の注釈から参照できる
- `>>` / `<<`
- Kind の推論。SCC ごとに型を検査し、使用回数から `Unr` の制約を出し、解いてから多相化する
- `status.md` に記録した `eml_types` の誤り3件の修正

次のものは、段階2でも E0004 のままにする。

| 構文 | 実装する段階 |
|---|---|
| タプルのパターン `fn (a, b) -> e` | 4 |
| 演算子の参照 `(+)` とセクション | 6 |
| `IO` 以外のエフェクト | 3 |

局所の再帰関数は構文がないので、もともと書けない。段階2には `Lin` の型がまだないので、Kind の推論から出る診断はない。推論の結果は、型検査のテストでスキームの表示を見て確かめる。

## `eml_hir`

### 式とパターン

- `ExprKind::Lambda { params: Vec<PatId>, body: ExprId }` を足す。ラムダの引数は新しい `Local` として束縛し、スコープはラムダの本体だけにする。
- `PatKind::Annot { pat: PatId, ty: TypeRefId }` を足し、`fn (x : Int) -> e` を表す。段階2では、ラムダの引数でだけ受ける。等式の引数の型の明示は今の扱いのままにする。
- 捕まえる変数の一覧は HIR に持たせない。HIR は名前を `Local` に解決済みなので、使用回数のパスと Core IR の変換が、それぞれ自由変数を求めれば足りる。2か所で求めるのが重複として目立つなら、型検査が求めて `TypedModule` に載せる形に寄せる。

### 型変数と row 変数

- `TypeRefKind::Var(TypeVarId)` を足す。`RowRef` に、末尾に row 変数を持つ形 (`<e>` と `<IO | e>`) を足す。
- 型変数と row 変数の名前は、関数ごとの表 `Function::type_vars` と `Function::row_vars` に置く。シグネチャに現れた名前がここに入り、本体の注釈は同じ表を引く。表にない名前は E1002 にする ([型と Kind](../../spec/types.md) の「推論」)。
- 型変数と row 変数の名前空間は分ける。同じ名前 `a` を型と row の両方に使うと、別々の変数になる。

### 演算子

- 固定の演算子の表に `>>` / `<<` (優先順位 9、右結合) を入れる。それぞれ組み込み `Builtin::ComposeFwd` / `Builtin::ComposeBwd` の呼び出しにする。
- `f >> g` は `compose f g`、`f << g` は `compose g f` の意味で、どちらも3引数の `compose` の2引数の部分適用になる。被演算子は左から右に評価する。

段階1で E0004 にしていた「ラムダ」「型変数」「row 変数」は、この節の形で受ける。

## `eml_types`: 型と row の多相

### 表現

- `TyKind::Rigid(RigidVar)` を足す。シグネチャの型変数は本体の中では rigid で、同じ rigid 変数と推論用の変数とだけ単一化できる。row の末尾も、推論用の row 変数と rigid な row 変数の2種類にする。
- 関数ごとの型は、スキーム `Scheme { ty_vars, row_vars, kind_vars, kind_constraints, ty }` で持つ。参照するたびに、変数と Kind の制約を複製して具体化する。
- 関数型の線形性 `m` (`Mult::Var`) を使い始める。2つの関数型を単一化するときは、`m` を等しくする (`≤` を両向きに足す)。部分 Kind による包摂は入れない。シグネチャの `m` は多相化されるので、段階2の範囲では等しくする規則で困る場面はない。

### 呼び出しと関数値

- 呼ばれる側は任意の式になる。型の矢印を引数1つごとにたどり、たどった矢印の row をすべて今の row に含める。呼ばれる側の型が推論用の変数なら、新しい変数で作った関数型と単一化する。
- トップレベルの関数と組み込みを値として参照するときは、スキームを具体化したうえで、戻り値の側に並ぶ矢印の閉じた row を新しい row 変数で開く。純粋な `inc : Int -> Int` を、`(a -> <IO> b)` を受ける引数に渡せるようにするためで、Koka と同じ扱いである。段階1の「呼び出し先の閉じた row を開く」をこの形に広げる。関数型の局所変数と引数の型は開かない。
- 引数が矢印より少ない等式は、残りの型に対して本体を検査する。本体の row は最後にたどった矢印の row で、引数がなければ `<>` になる。

### ラムダ

- check モードでは、期待する関数型の矢印を引数ごとにたどる (等式と同じ)。
- infer モードでは、引数ごとに新しい型変数、線形性の Kind 変数、row 変数を作る。途中の矢印の row も、`<>` ではなく新しい row 変数にする。row の単一化は包摂を持たないので、閉じた `<>` にすると、`<IO>` を期待する場所に渡せなくなるためである。
- ラムダの本体のエフェクトは、外側の関数ではなく、ラムダの最後の矢印の row に入る。
- ラムダの row が閉じていて、そこに含まれないエフェクトを本体が起こしたら E2002 にする。エフェクトを起こした場所を primary にし、ラムダの期待する型の由来 (シグネチャの引数の型や注釈) を secondary にする ([診断](../../spec/diagnostics.md))。

### 誤りの修正

`status.md` に記録した次の3件を直し、それぞれ回帰テストを足す。

- 末尾が同じ row の不一致が `UnifyError::Occurs` として返る。`Mismatch` にする
- `unify(Var, Error)` が変数を束縛せずに残す。変数を `Error` に束縛して、エラーを吸収する
- `Table::export` が未解決の row の末尾を落とす。末尾を残す

### 出力

- `Type` に、型変数 `Var` と row の末尾を足す。関数型の線形性も、Kind 変数のまま残せる形にする。
- 本体の検査の後に残った推論用の変数 (使われないラムダの引数など) は、エラーにしない。`Error` には落とさず、`Type::Var` として出す。
- `TypedModule::signatures` はスキームを持つ。`dump` は Kind の制約も表示する (下の「Kind の推論」)。

## `eml_types`: Kind の推論

### 流れ

1. トップレベルの関数の呼び出しグラフを作り、SCC に分ける。辺は、本体で関数を参照すること (呼び出しと値としての参照の両方) である。
2. SCC を、呼ばれる側から順に処理する。SCC ごとに、各本体の型を検査し、使用回数を数えて Kind の制約を出し、束の上で解き、多相化してスキームを確定する。
3. SCC の中の関数どうしは、同じ Kind 変数を共有したまま検査する (Kind について単相の再帰)。共有した変数を一度に解くことで、SCC の中で不動点を求めるという spec の規則を満たす。
4. 多相化では、スキームに現れる Kind 変数と、それらに関わる制約をスキームに残す。具体化のたびに制約も複製するので、呼び出し側が `Lin` を渡せば、制約の違反として見つかる。違反の診断の番号は、`Lin` が現れる段階5で決める。段階2で違反が起きたら内部エラーにする。

既存の `Lattice` (最小解と、定数の上限の違反の検出) をそのまま使う。row 変数の多重度 `Row<σ>` も同じ流れで扱うが、段階2の制約の出どころは `IO` (`Once`) だけである。

### 使用回数の数え上げ

型付き HIR の上の別のパス (`eml_types` の `usage` モジュール) として作る。これは線形性の検査パスの土台であり、段階5はこのパスに、枝ごとの消費の一致、持ち越し規則、E3xxx を足す。

- 束縛ごとに、制御フローの各経路での使用回数を数える。どこかの経路で 0 回か2回以上なら、その型の Kind に `≤ Unr` の制約を出す。`_` で受けた束縛も同じ扱いにする。`if` の枝は経路を分けて数える。
- 型の Kind は、`Int` / `String` / `Bool` が `Unr`、レコードがフィールドの join、関数型がその `m`、型変数と rigid 変数がその `μ` である。
- ラムダが変数を捕まえることは、ラムダの位置での1回の使用に数える。ラムダの線形性 `m` は、捕まえた変数の Kind 以上にする (`μ ≤ m`)。ラムダの本体の中でも、捕まえた変数の使用回数を別に数え、1回でなければ `≤ Unr` を出す。
- 関数型の値を呼ぶことは、その値の1回の使用に数える。`twice f x = f (f x)` では `f` を2回使うので、`f` の矢印の `m` が `Unr` に決まる。

### 結果の確かめ方

- `eml_types::dump` に Kind を出す。`Unr` に決まった矢印は今と同じ `->` で表示する。多相のままの矢印と型変数の Kind は、スキームの後ろに制約として並べる。表示の細かい形は実装計画で決める。
- テストで確かめるのは次の3点である。
  - `twice` の `f` の矢印が `Unr` になる
  - 1回しか使わない引数の型変数は、Kind が多相のまま残る
  - SCC をまたいで制約が伝わる (`twice` を呼ぶ関数で、`twice` に渡した値の型変数に `Unr` が付く)

## `eml_core_ir`: クロージャ変換

### 命令

```rust
enum Rhs {
    // 既存の Atom、CallDirect、Prim、ConstString、Perform、Nested に加えて
    /// 関数と先頭の引数の並びからクロージャを作る。並びの値の所有権はクロージャに移る。
    MakeClosure(FnIdx, Vec<Atom>),
    /// クロージャの値を呼ぶ。クロージャと引数の所有権は呼び出しに移る。
    Apply(Atom, Vec<Atom>),
}
```

クロージャは「関数 + すでに渡された先頭の引数の並び」である。ラムダの捕獲と部分適用を、この1つの形で表す。

### 変換

- ラムダは、新しい `CoreFn` (`外側の名前$lambda0` のような名前) に持ち上げる。引数は「捕まえた変数 (`LocalId` の順) + ラムダの引数」にする。捕まえた変数は、変換の中で自由変数として求める。入れ子のラムダが捕まえる変数は、外側のラムダも捕まえる。
- 呼ぶ相手が分かっている呼び出し (トップレベルの関数と組み込み) は、相手の引数の個数 `n` と渡した個数 `k` で分ける。`k == n` なら `CallDirect` にする。`k < n` なら `MakeClosure(f, 渡した引数)` にする。`k > n` なら、先頭の `n` 個で `CallDirect` してから、残りを `Apply` する。
- 関数を値として使うと `MakeClosure(f, [])` になる。
- 組み込みを値や部分適用で使うときは、組み込みを呼ぶだけの `CoreFn` を、必要になった分だけ作って包む。`compose` は、`Apply(g, [Apply(f, [x])])` を本体に持つ3引数の `CoreFn` として作る。
- 引数のないトップレベルの値は、参照するたびに `CallDirect(f, [])` で計算し直す。値は純粋なので結果は同じになる。一度だけ計算する形は [ロードマップ](../../future/roadmap.md) に書いた。

### Perceus

- `VarInfo::boxed` を「ヒープの値かもしれない」の意味に広げる。対象は、`String`、関数型、型変数の型を持つ変数である。インタプリタの `dup` / `decref` はすでにヒープにない値を無視するので、型変数の値が実際には `Int` でも正しく動く。
- Kind が多相のまま (`μ`) の変数は、RC の挿入では `Unr` と同じに扱う。`dup` / `decref` が付くのは使用回数が 0 か2以上の変数で、その場合は使用回数のパスが `μ ≤ Unr` を出しているので、矛盾しない。
- `MakeClosure` の先頭の引数と `Apply` の呼び出し先も、変数の使用に数える。捕まえた変数を後でも使うなら、その前に `dup` が入る。

### 門

`eml_types` の門を通った HIR だけが来るので、ここでは新しい E0004 を出さない。

## `eml_runtime` と `eml_interp`: クロージャの実行

### ランタイム

- `Payload::Closure { function: u32, args: Vec<Value> }` を足す。`args` の各値は参照を1つずつ所有する。子の列挙に `args` のヒープの値を入れるので、解放とリークの検出はそのまま効く。
- 記述子の表に「クロージャ」を足す。`debug_heap` のリークの報告に記述子ごとの件数が出るので、クロージャの漏れも区別できる。

### `Apply` の動き

1. クロージャの値を受け取る。参照が1つだけなら、`args` を取り出し、子を decref せずにオブジェクトだけを解放する。共有されていれば、`args` の各値を `dup` してから、クロージャを decref する。
2. 取り出した `args` と渡された引数をつなげ、関数の引数の個数と比べる。
3. 個数が等しければ、`CallDirect` と同じく呼び出しのフレームを積んで呼ぶ。足りなければ、つなげた引数で新しいクロージャを作り、それを結果にする。余れば、余った引数を持つフレームを積んでから、先頭の分で呼ぶ。そのフレームは、戻ってきた値に余った引数を `Apply` する。

型検査を通ったプログラムでは、クロージャでない値を `Apply` することはない。起きたら内部エラーにし、実行時エラーの種類は増やさない。

### フレーム

- 余った引数を持つフレームは、今のフレームとは別の種類にする。`Frame` に種類の enum を持たせ、「呼び出し / 入れ子の式」と「残りの引数の適用」を分ける。段階3の継続の取り出しは、どちらの種類も同じ連結リストの要素として扱える。
- `status.md` の段階3の注意 (`Payload` / `Frame` の `Clone` が `ObjRef` を `dup` しない) は、クロージャの `args` にも当てはまる。注意の文に「クロージャ」を足す。

## テスト

| crate | テスト |
|---|---|
| `eml_hir` | ラムダ、`PatKind::Annot`、型変数と row 変数の表、`>>` / `<<` の変換のスナップショット。本体の注釈に書いたシグネチャにない型変数が E1002 になること |
| `eml_types` | スキームの表示 (多相、row 変数、Kind の制約)。「Kind の推論」の3点。rigid 変数の不一致の E2001 (`f : a -> b` と `f x = x`)。ラムダの中の E2002。純粋な関数を `<IO>` の高階関数に渡せること。誤り3件の回帰テスト |
| `eml_core_ir` | ラムダの持ち上げ、部分適用、引数の多い呼び出し、組み込みの包み、`compose`、捕まえた変数の前の `dup` の位置のスナップショット |
| `eml_runtime` | クロージャの確保と解放、共有されたクロージャの `args` の `dup`、子の解放 |

UI テストには次のプログラムを足す。実行テストでは常に `debug_heap` が有効なので、クロージャのリークもここで検出される。

- `run/`: 高階関数 (`apply`、`twice`)、文字列を捕まえるクロージャ、部分適用と引数の多い呼び出し、`>>` / `<<`、`Int` と `String` で使う多相な `id`、row 変数でエフェクトを通すコールバック (`each` 風の関数に `println` を渡す)、引数が矢印より少ない等式、クロージャを通した深い再帰 (10 万段)
- `check-fail/`: rigid 変数の不一致、ラムダの中で row にないエフェクトを起こす、シグネチャにない型変数、段階2でも E0004 のままの構文 (タプルのパターン、`(+)`)
