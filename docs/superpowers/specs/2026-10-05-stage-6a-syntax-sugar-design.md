# 縦の貫通 段階6a: 糖衣構文と E1xxx の残りの設計

位置づけ: 作業用の設計文書。段階6a を終えたら、残す価値のある内容を `docs/spec/`、`docs/implementation/architecture.md`、`docs/implementation/status.md` に移し、この文書は削除する。

## 目的と範囲

[status.md](../../implementation/status.md) の「名前解決以降の実装段階」の段階6a を通す。段階6a の後に R5 (型検査の SCC ごとの独立)、その後に段階6b (パラメータ付き handler) を行う。

### 6a に含めるもの

- Core IR の `simplify` の拡張: join point の外出し (F)、分かっているコンストラクタの `switch` (K1)、フィールドを持つコンストラクタへの B2 の拡張、使われない純粋な束縛の削除 (DCE)
- 複数の等式と、その宣言の検査 (E1018〜E1020)、網羅されていない等式の診断の形、到達しない等式の Warning (E4005)
- 等式の検査の連鎖の修正 (`check_function` の余計な E2002)
- 演算子の定義、fixity の宣言 (E1021、E1022)、標準の演算子の fixity の Prelude への移動
- セクションと演算子の参照 (E1023)、`use` (E1024)、`let ... in`
- パターンの型の明示 `(p : T)` を、ラムダの引数だけでなくすべての `apat` の位置で書けるようにする文法の拡張
- ラムダの引数の並びと handler の節の引数の並びの重複束縛 (E1017 の対象を広げる)

### 後に回すもの

- `(.name)` のセクションとフィールドの参照 (S2)。今どおり E0004 にする
- `pub` の付いた fixity (S2)。`pub` 自体が E0004 である
- `::` (S2 のリスト)。今どおり E0004 にする
- `from` の handler と、`resume` の3引数の形 (段階6b)
- 演算子の名前の関数をネイティブ化するときの名前の変換
- `simplify` を不動点まで繰り返すこと。1巡だけ回す今の方針を変えない

### ユーザーと合意済みの決定

- 段階6 を 6a と 6b に分け、6a → R5 → 6b → S2 の順に進める
- 6a には、5つの構文と演算子の定義に加えて、等式の検査の連鎖の修正、パターンの型の明示、ラムダと節の重複束縛を含める
- パターンの型の明示は、今の文法ではラムダの引数 (`param`) にしか書けず、そこはすでに実装済みだった。`apat` に `'(' pat ':' type ')'` を足して文法を広げる
- 複数の等式は、spec どおり HIR で引数のタプルに対する `match` に脱糖する (案1)。等式が1つの関数は今の形のままにする
- 脱糖で作るタプルの確保は、決定木の特別扱いではなく、`simplify` の一般の書き換え (K1 と DCE) で消す
- case-of-case の拡張は、F、K1、B2 の拡張、DCE の4つをすべて 6a に入れる (甲)

## 1. Core IR の簡約

### 今の制限

1. B2 は、引数のないコンストラクタのタグを渡す `jump` にしか効かない。`jump j0(d)` の `d` が `let d = con #1(s)` で作った値でも、枝へ直接向けない。向けても、使われなくなった `con` を消すパスがないので確保が残る
2. `match` にワイルドカードの枝があると、B2 が効かない。決定木が、`if` の join point の本体の中、`Switch` の手前に、残りの枝の join point を置くので、B2 が `Switch` を見つけられない (例: `match (if b then Red else Green) with | Red -> 1 | _ -> 2`)
3. まっすぐなコードの `let t = con #0(a, b)` の後の `switch t { #0(x, y) -> … }` を消さない。等式の脱糖で作るタプルの `match` も、ユーザーが書く `match (a, b) with` もこの形である

### 書き換えの順

今の「B3、B2、B5、B3、B4 を1巡」を、次の順の1巡にする。

| 順 | 書き換え | 役目 |
|---|---|---|
| 1 | F | join point の本体の中の join point の定義を、外側の join point の引数を使わないなら外へ出す |
| 2 | B3 | `jump` が1つの join point を、その位置に戻す |
| 3 | K1 | 範囲にある `con` で作った値の `switch` を、その枝で置き換える |
| 4 | B2 | 分かっているコンストラクタを渡す `jump` を、枝へ直接向ける (フィールドを持つコンストラクタを含む) |
| 5 | B5 | 本体が1命令の join point への `jump` を、その命令にする |
| 6 | B3 | 同上 |
| 7 | B4 | `jump` のない join point を消す |
| 8 | DCE | 使われない純粋な束縛を消す |

- F を最初に置くのは、制限2の join point を外へ出して、最初の B3 と B2 が `Switch` に届くようにするためである
- K1 を B3 の後に置くのは、B3 が join point を戻すときに作る引数の束縛 (`let t = d`) を通して、`d` の `con` までさかのぼるためである
- DCE を最後に置くのは、K1 と B2 が使わなくした `con` をまとめて消すためである

### F: join point の外出し

- join point `j` の本体の先頭に並ぶ join point の定義 `j'` が、`j` の引数を使わないとき (`j'` の `captures` に `j` の引数がないとき)、`j'` の定義を `j` の定義の外側 (直前) に移す
- `j'` の本体が使う外側の変数は、`j` の定義の位置でも範囲にある。`j` の引数以外に `j` の本体の中で束縛した変数を `j'` が使う場合は、移さない
- scrutinee そのものを受ける枝 (`| x -> f x`) の join point は `j` の引数を使うので、移せない。この形では B2 は効かないまま残る

### K1: 分かっているコンストラクタの `switch`

- 根から下へたどりながら、範囲にある束縛のうち `let v = con #k(a1, …, an)` と `let v = u` (別名) を環境に覚える。枝と join point の本体に入るときは、その位置で範囲にある束縛だけを持つ (ANF の範囲は字句的なので、join point の定義を囲む `let` はその本体からも見える)
- `switch v` の `v` が、別名をたどって `con #k(a…)` に行き着くなら、`switch` を #k の枝の本体で置き換える。枝のフィールドの変数 `x1 … xn` の使用は `a1 … an` に置き換える
- 枝が `v` そのものも使う場合も置き換えてよい。その場合 `con` は残る
- 引数のないコンストラクタの値 (`Atom::Tag`) を直接 `switch` している場合も、同じく枝で置き換える

### B2 の拡張

- 対象の join point は今と同じく、引数を1つだけ持ち、本体がその引数で `switch` するものである
- `jump j(v)` の `v` が、K1 と同じ環境で `con #k(a…)` に行き着くなら、#k の枝を、フィールドを引数に取る join point `jk(x1, …, xn)` に切り出し、その `jump` を `jump jk(a1, …, an)` にする
- #k の枝が join point の引数そのものも使う場合は、引数の並びの最後にその値も渡す (`jump jk(a1, …, an, v)`)。その場合 `con` は残る
- 引数のないタグを渡す `jump` の扱いは今と同じである
- 同じ join point に、分かっている値の `jump` と分からない値の `jump` が混ざってよい。分からない値の `jump` は元の join point へ行き、元の `switch` にはすべての枝が残る (切り出した枝は `jump jk(…)` になる)

### DCE: 使われない純粋な束縛の削除

- 根からたどれる式で一度も使われない変数の `let` のうち、右辺が次のものを消す: `Atom`、`ConstString`、`Con`、`MakeClosure`、実行時エラーを起こさないプリミティブ (比較、`++`、`show_int`、`not`、`BoolEq` など)
- 呼び出し、`Io`、`Drop`、実行時エラーを起こしうるプリミティブ (`+`、`-`、`*`、`/`、`%`、`negate`。オーバーフローとゼロ除算) は消さない
- 消した右辺が使っていた変数が、それで使われなくなれば、同じ巡の中で続けて消す (後ろから前へたどる)
- `con` が所有権を受け取っていた値 (`File` など) は、`con` を消すと使われなくなる。Perceus がその値の生存の終わりに `decref` を入れるので、解放される時点が早まるだけで、観測できる出力は変わらない

### 守る性質

- どの書き換えも Perceus の前に行うので、所有権は扱わない。式をその式が実行されるときにだけ実行される位置へ動かすか、純粋な式を消すだけなので、エフェクトの順と短絡評価は変わらない
- 書き換えの後、パイプラインが `captures` を埋め直し、`verify_scopes` で確かめる (今と同じ)
- 等式の脱糖で作るタプルは、K1 と DCE で消える。決定木 (`translate/pattern.rs`) にタプルのリテラルの特別扱いは入れない

## 2. 等式と宣言の検査

### 脱糖

- 等式が2つ以上ある関数は、HIR で次の形にする
  - `Body::params` は、引数の位置ごとの隠れた局所変数を束縛するパターンである。名前は `$0`、`$1`、…で、HIR のダンプにもこの名前で出す。範囲は最初の等式のその位置のパターンの範囲にする (引数が矢印より多いときの診断が指す)
  - `Body::root` は、それらのタプル (引数が1つなら変数そのもの) に対する `match` である。各等式が1つの枝になり、枝のパターンはその等式の引数のパターンのタプル (引数が1つならそのパターン) である
  - `ExprKind::Match` に由来 (`MatchSource::{Expr, Equations}`) を持たせる。`Function` に各等式の先頭 (関数名の位置) の範囲の並び (`equation_ranges`) を持たせる
- 隠れた局所変数は、どの経路でもちょうど1回 (scrutinee で) 使われるので、線形性の診断に現れない
- E1017 は今と同じく、1つの等式の引数の並びを1つの組として調べる
- 等式が1つの関数と、引数のない値 (`pi = 3`) は今の形のままにする。網羅性の検査は引数の並びを1行として調べるので、spec の「等式が1つの場合も同じ」と意味が一致する
- 中置の等式 (`dir </> name = …`、節3) は、引数が2つの等式としてこの経路に乗る

### 新しい E1xxx

| 番号 | 名前 | 誤り | primary | secondary |
|---|---|---|---|---|
| E1018 | `NON_CONSECUTIVE_EQUATIONS` | 同じ名前の等式が連続していない (間に別の item がある) | 離れた等式の関数名 | 直前の等式の並びの最後の等式の関数名 |
| E1019 | `SIGNATURE_NOT_ADJACENT` | シグネチャと最初の等式が隣り合っていない | 最初の等式の関数名 | シグネチャの関数名 |
| E1020 | `EQUATION_ARITY_MISMATCH` | 等式ごとに引数の個数が違う | 個数の違う等式の関数名 | 最初の等式の関数名 |

- 今の E0004 (`defining a function with several equations is not supported yet` と `an equation that does not directly follow its signature is not supported yet`) は、これらに置き換える
- E1018 と E1019 には、等式をシグネチャの直後にまとめるよう help で伝える ([診断](../../spec/diagnostics.md) の「シグネチャに関する E1xxx の診断には…help」)
- 回復は次のとおりである
  - E1018 と E1019 の後も、同じ名前の等式をソースの順に1つの関数として扱う。網羅性の誤りを連鎖させないためである
  - E1020 の等式は、引数のパターンと本体の名前解決だけを行って誤りを報告し、`match` の枝には入れない。本体の `has_errors` を立てる

### 網羅性

- 由来が `Equations` の `match` は、`match` 式としてではなく等式として報告する
- E4002 `NON_EXHAUSTIVE_EQUATION`: 今の形を等式の数だけ広げる。primary はシグネチャの関数名 (シグネチャがなければ最初の等式の関数名)、secondary は各等式の先頭である。漏れの例は note に `f None _` の形で示す (関数名に続けて、タプルの要素を空白で並べる)
- 新しい **E4005 `UNREACHABLE_EQUATION` (Warning)**: 到達しない等式。その等式の引数のパターン全体の範囲を指す。spec の表の「なし」の欄を埋める

### 等式の検査の連鎖の修正

- `check_function` で、シグネチャの矢印をたどる途中に `Arrow::Error` (壊れたシグネチャ) か `Arrow::NotFunction` (引数が矢印より多い) に当たったら、今の row (`ambient`) を末尾が `Error` の row にしてから本体を検査する。ラムダの検査が同じ場合にしている扱いに合わせる
- これで、`f : Int -> Undefined` を `f a b = println "x"` と定義したときの E1002 + E2002、`f : Int -> Unit` を `f a b = println "x"` と定義したときの E2001 + E2002 が、それぞれ E2002 なしになる
- status.md の「診断の連鎖の残り」の項を消す

## 3. 演算子の定義と fixity

### fixity の表

- `builtin.rs` の `fixity()` の表をなくす。標準の演算子の fixity は `prelude.em` の宣言で持つ

```haskell
infixr 0 <|
infixl 1 |>
infixr 2 ||
infixr 3 &&
infix 4 ==, !=, <, <=, >, >=
infixr 5 ++, ::
infixl 6 +, -
infixl 7 *, /, %
infixr 9 >>, <<
```

- HIR は、Prelude の宣言とユーザーの宣言から表 (`Fixities`) を作る。演算子の列の組み直し (`lower/ops.rs`) と、中置のコンストラクタのパターンの組み直し (`lower/expr.rs` の `lower_infix_pat`) は、どちらもこの表を引く
- fixity は、演算子の名前が解決した先の定義に付く
  - Prelude の演算子 (組み込みと、Prelude の `data` の中置のコンストラクタ) は、Prelude の宣言を使う
  - ユーザーが定義した演算子 (関数と中置のコンストラクタ) は、ユーザーの宣言を使う。宣言がなければ `infixl 9` である
  - ユーザーが `+` を定義して Prelude の `+` を隠すと、その `+` は宣言がなければ `infixl 9` になる (Haskell と同じ)
- 宣言の位置は問わない。後ろに書いた fixity の宣言も、モジュール全体の組み直しに効く。本体は item をすべて集めてから変換するので、今の順で足りる
- 中置のコンストラクタのパターンの組み直し (`climb_pat`) も、式の `climb` と同じく、同じ優先順位で結合の向きが違う並びと、結合しない演算子の並びに E1006 を報告する。誤りのパターンは `Missing` にする。ユーザーが `:` で始まる演算子に fixity を宣言できるので、この並びが起きるためである
- 単項の `-` は今どおり優先順位 6 の `negate` として扱い、表を引かない
- `&&`、`||`、`|>`、`<|`、`::` は、Prelude にシグネチャのない演算子である。Prelude の中でだけ、これらへの fixity の宣言を許す。Prelude の変換は誤りがないことを `debug_assert` で確かめている (今と同じ)

### ユーザーによる脱糖用の演算子の定義

- `&&`、`||`、`|>`、`<|` も、ほかの Prelude の名前と同じく、ユーザーの定義が隠す。その場合、その演算子は短絡しない普通の関数である
- そのため `binary()` は、演算子の文字列で脱糖を選ぶ前に名前を解決する。ユーザーの定義に解決すれば呼び出しにし、そうでなければ今の脱糖にする

### 演算子の定義

- シグネチャ `(</>) : Path -> String -> Path` と、中置の等式 `dir </> name = …` を受け付ける。今の E0004 (`defining operators is not supported yet`) はなくす
- 関数名は演算子の文字列 (`</>`) である。名前空間は値と同じで、E1003 の重複の検査もそのまま効く
- Core IR のダンプでも関数名は演算子の文字列のまま出す

### 新しい E1xxx

| 番号 | 名前 | 誤り | primary | secondary |
|---|---|---|---|---|
| E1021 | `DUPLICATE_FIXITY` | 同じ演算子への2回目の fixity の宣言 | 2回目の宣言の演算子 | 1回目の宣言の演算子 |
| E1022 | `FIXITY_WITHOUT_DEFINITION` | このモジュールで定義していない演算子への fixity の宣言。Prelude の演算子の fixity を変えようとした場合を含む | 宣言の演算子 | なし |

- E1022 の後は、その宣言を表に入れない
- 1つの宣言に同じ演算子を2回並べた場合 (`infixl 6 +., +.`) も E1021 にする

## 4. 式の糖衣構文とパターン

### セクションと演算子の参照

HIR でラムダに脱糖する ([式](../../spec/expressions.md) の「セクション」の表)。

| 書き方 | 脱糖後 |
|---|---|
| `(op)` | `fn $a $b -> $a op $b` |
| `(op e)` | `fn $x -> $x op e` |
| `(e op)` | `fn $x -> e op $x` |

- 本体の `$a op $b` は、節3の組み直しと同じ `binary()` で作る。そのため、`(&&)` は短絡の `if` に、中置のコンストラクタはコンストラクタの呼び出しに、ユーザー定義の演算子は関数の呼び出しになる
- `(==)` と `(== 1)` の比べ方は、ラムダの本体の `==` の呼び出しについて今の仕組みで決まる。比べ方はラムダの引数の型から決まり、決まらなければ E2006 を演算子の位置に出す。status.md の「比べ方ごとに包む関数を作る」はこの脱糖で満たされるので、その項を消す
- `(- e)` はセクションではなく、今どおり単項の `-` である (Haskell と同じ)。`(-)` と `(e -)` は引き算の参照とセクションになる
- 被演算子 `e` は、spec の意味どおり、ラムダを呼ぶたびに評価する
- 隠れた引数の名前 `$a`、`$b`、`$x` は HIR のダンプにこの名前で出す。どれもちょうど1回使われる
- 脱糖で作る式の範囲は、セクション全体の範囲にする。演算子の呼び出しの callee だけは演算子のトークンの範囲にする (E2006 などが演算子を指すため)

### セクションの優先順位の可否

- 被演算子が演算子の列のときは、空いた側に仮の被演算子を置いた列を、同じ `climb` で組み直す
- 組み直した木の根がセクションの演算子で、仮の被演算子がその直接の被演算子のときだけ許す。左結合の `+` では `(a + b +)` を許し、`(+ a + b)` を拒む。`(* a + b)` も拒む
- 拒むときは新しい **E1023 `INVALID_SECTION`** にする。primary はセクション全体で、被演算子を括弧で囲むよう help で伝える。回復ではセクション全体を `Missing` にする

### `use`

- ブロックの変換で `use` の文に出会ったら、その後の文を内側のブロックにし、ラムダで包んで、`use` の式の最後の引数に足す

| 書き方 | 脱糖後 |
|---|---|
| `use f a b` の後にブロックの残り | `f a b (fn () -> 残り)` |
| `use p <- f a b` の後にブロックの残り | `f a b (fn p -> 残り)` |

- `use` の式が呼び出し (`ExprKind::Call`) なら引数の並びの最後に足し、そうでなければ1引数の呼び出しにする
- `p` はラムダの引数と同じに扱う。反駁可能なら E4003 になる
- ラムダと内側のブロックの範囲は、`use` の文の始まりからブロックの終わりまでにする
- ブロックの最後の文が `use` なら、新しい **E1024 `USE_AT_END_OF_BLOCK`** にする。primary は `use` の文である。回復では、最後の引数を `Missing` にした呼び出しにし、型の誤りを連鎖させない

### `let p = e in e2`

- `Block { stmts: [Let { pat: p, ty, init: e }], tail: e2 }` に脱糖する。ブロックの `let` と同じ経路で、`e` を先に変換し、`p` の束縛は `e2` の中でだけ見える

### パターンの型の明示

今の文法 ([文法](../../spec/grammar.md)) では、型の明示は `param ::= apat | '(' pat ':' type ')'`、つまりラムダの引数にしか書けない。ラムダの引数の `(x : Int)` は実装済みで、`lower_pat` の `AnnotPat` の E0004 は、パーサがその位置に `ANNOT_PAT` を作らないので到達しない。6a では文法を広げる。

- `grammar.md` の `apat` に `'(' pat ':' type ')'` を足し、`param` の規則を消す (`param` は `apat` と同じになる)。等式の引数、`match` の枝、`let` の左辺、`use` のパターン、handler の節の引数、入れ子のパターンのどこでも書ける
- パーサは、`paren_pat` の `annotated` の引数をなくし、括弧のパターンでつねに `: type` を受け付ける。`patterns::param` は `apat` にまとめる
- HIR は、`lower_pat_in_group` で `AnnotPat` を `PatKind::Annot` にする。ラムダの引数の専用の経路 (`lower_lambda_param`) はこれにまとめて消す。到達しない E0004 (`type annotations in patterns are not supported yet`) もなくす
- 型検査は、今はラムダの引数の一番外側の `Annot` だけを `bind_param` で照合し、`bind_pat` の `Annot` は明示した型を見ずに内側へ進む。`bind_pat` の `Annot` で、明示した型を期待する型と照合してから、内側を明示した型で束縛する。由来は新しい `Origin::AnnotatedPattern` (note: 「an annotated pattern must have the type of the value it matches」) にする。ラムダの引数の一番外側は今どおり `Origin::LambdaParameter` で照合し、今の診断の文言を変えない
- 網羅性と決定木は `Annot` の内側を見るので、変えない
- `let (x : Int) = e` と `let x : Int = e` の両方が書ける。前者はパターンの明示、後者は `let` の注釈である

### ラムダと節の重複束縛

- 次の並びを、それぞれ1つの組として E1017 を調べる: ラムダの引数の並び、操作の節の引数の並びと `k`、`return` の節の引数
- 等式の引数の並びと同じく、2つ目の束縛を primary、1つ目を secondary にする
- status.md の「ラムダの引数の並びと handler の節の引数の並びで同じ名前を2回束縛しても…」の項を消す
