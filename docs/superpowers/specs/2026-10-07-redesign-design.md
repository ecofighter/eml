# eml の再設計 (全体設計)

位置づけ: 作業の設計。サブプロジェクト S0〜S5 の決定事項、作り直した後の構成、順序と完了の条件をまとめる。S0 の詳細もこの文書で定める。S1 以降は、着手するときにそれぞれ個別の spec を書く。決まったことは S0 で `docs/` の該当文書に移し、全体の作業が終わったらこの文書を削除する。

## 目的

spec とコードベースを、互換性を気にせずに作り直す。優先順は次のとおりである。

1. 実装を簡潔にする。段階をまたいだ特別扱い、表現を保つための手間、運用の手間を減らす
2. ネイティブ化とマルチコアの土台を、後で書き直さずに済む形にする
3. 日常のスクリプトに使える言語にする

1 と 2 が作り直しの主な理由で、3 は spec を変えるついでに上げる。

## 分析で確かめた事実

6つの観点 (表層の言語、型と線形性とエフェクト、フロントエンド、バックエンド、ネイティブ化とマルチコアの土台、実用性) で spec とコードを調べ、批判役2人がその結論を検証した。次の事実は再現して確かめた。

- row の健全性に穴がある。`run : (Unit -> <e> a) -> <State Int | e> a` の本体で `cb ()` を呼ぶと、型検査は `cb` のエフェクトが `State Int` を飛ばして外側に届くとみなす (`eml_types/src/table/row.rs` の `include_row` の、末尾が rigid な変数の分岐)。実行時は、いちばん内側の `State` の handler が `cb` の `get` を捕まえる。`e := <State String>` のとき、`check` は通り、`run` は `internal error: a string operation on a value that is not a string` で止まる
- `<IO | e>` に `e := <IO>` が入ると `<IO, IO>` になり、`main : Unit -> <IO> Unit` から呼ぶと E2002 になる。`examples.md` の最初の例も同じ形である。help は、すでに書いてある `IO` を足すよう表示する
- `perform` は handler を探すときにすべてのフレームをたどるので、エフェクトを使う深い再帰は2乗の時間がかかる。文字列の `++` は毎回全体を写す
- ランタイムのマルチコアへの備えは形だけである。`AtomicI32` の参照カウントは `get_mut` からしか触られず、`mark_shared` は空の実装で、記述子は名前しか持たない
- `ItemTree` が rowan の red node を持つので、`eml_cli::Session` は `Send` でない
- 588 コミットのうち 312 が `docs/` を変えている。今の Prelude で書けるのは `println`、`open`、`read_all`、`close`、`Int`、`++` だけで、現実的なスクリプトはまだ書けない

## 決定事項

### 言語の核

- `multi` (multi-shot の継続) を残す。eml の実験として新しい部分は、`multi` と線形性の衝突 (持ち越し規則と、`map` などの総称の関数が注釈なしで推論する条件付きの制約 `a => <e> <= Once`) にあるためである。持ち越し規則と段2の Kind 推論は残し、実装の形だけを整理する
- 採らなかった案: `multi` を捨てて one-shot のエフェクトに絞る案は、実装は最も小さくなるが、実験の独自な部分を失う

### row の健全性 (S1)

- row の包含で、rigid な末尾の手前にラベルが足される場合 (上の `cb ()` の `State Int`)、型検査はその位置と飛ばすラベルを side table に記録する。Core IR はその呼び出しを `mask` で包み、実行時の `mask` は handler を探すときに同じエフェクトの handler を1つ飛ばす。型が約束した意味を実行時が守るので健全になり、エフェクトのカプセル化も保たれる。今通るプログラムの書き方は変わらない
- handle できないラベル (`IO`) は、row の中で重なったら1つにまとめる。誰も handle できないので、どちらの `IO` に届いても意味は同じである
- 採らなかった案: row を集合にする案は、単一化の解が一意に決まらず、カプセル化を失う。lacks 制約は、シグネチャに新しい制約の形が要る。Koka と同じく包含を拒否して `mask` を構文にする案は、自分のエフェクトを起こしつつコールバックを呼ぶラッパーのすべてに `mask` を書かせる
- 同じエフェクトのインスタンスが入れ子で並ぶ問題 (`Heap h` の入れ子の `run_heap`) は扱わない。名前付きの handler が要るかどうかは、可変参照を入れるときに決める

### 継続 (S2a)

- 継続 `k` を普通の関数にし、`resume` キーワードを廃止する。再開は `k v`、状態付きの handler では `k v st` と書く。`once` の `k` は `Lin` の矢印、`multi` の `k` は `Unr` の矢印を持つ。状態があるかどうかは `from` の有無で構文的に決まる
- `Cont` 型、状態の欄の推論 (Slot / SlotVar)、E2007、E1011、`carry.rs` の `resume` の特別扱いを削除する。引数の個数の誤りは普通の関数適用の誤りとして報告する。`drop k` は今のまま使える
- `Lin` の矢印の診断での表示は S2a の spec で決める

### 組み込み (S2b)

- 宣言の修飾子 `extern` を足す (`pub extern println : String -> <IO> Unit`、`pub extern data Int`、`pub extern effect IO`)。「等式のないシグネチャ」「`=` のない `data`」を組み込みの印にする今の規則は廃止する
- `IO` は操作を持たないラベルだけのエフェクトにする。`println` などは `<IO>` を持つ普通の extern 関数になる。extern のエフェクトは handle できない、という一般の規則が E1009 に代わる。`Rhs::Io`、`IoOp`、`op$Prelude.open` という包み関数を削除する
- extern の実装は1枚の表で、名前、arity、純粋かどうか、Repr、Rust の実装を結ぶ。HIR、Core IR、インタプリタはこの表を引く。ネイティブ化では、この表がランタイムとの ABI の一覧になる
- 標準ライブラリは、バイナリに埋め込んだ `std/` ツリーから読む。Prelude は `std/Prelude.em` になる。「標準ライブラリは import なしで修飾付きで使える」(modules.md) はそのまま守る

### 土台 (S3)

- インタプリタはシングルスレッドにする。`par` の子は決定的なので、順に実行しても意味は変わらない。実際の並列化はネイティブのランタイムだけで行う
- Core IR v2 では、値の表現 (Repr) と box/unbox、scrutinee を消費しない `Switch` を、ブロック木への書き換えと同時に入れる。Perceus、verifier、インタプリタの `Switch` を1回で作り直すためである
- evidence passing、ネイティブのオブジェクトモデル、`Int` の幅、コード生成のバックエンド (Cranelift か LLVM か)、バイトコード VM は、ネイティブ化の段階で決める。evidence passing を入れても、今の CEK は直接の意味論の参照実装として残し、差分テストの基準にする

### スクリプトの MVP (S4)

- ロードマップの軸を「型システムの実験を先にする」から「使えるスクリプトを先にする」に変える。S4 で MVP を作り、型クラスなどの実験はその後に置く
- レコードは名前的なレコードにする

  ```haskell
  data Person = Person { name : String, age : Int }

  let p = Person { name = "a", age = 3 }
  p.name
  { p | age = 31 }
  let Person { name, age } = p
  ```

  - フィールド付きの構文は、コンストラクタが1つの `data` に限る
  - `p.name` は、その時点で `p` の型が分かっていることを求める。分からなければ型の注釈を求める診断を出す。本体の終わりまで解決を遅らせる仕組みは作らない
  - 射影と更新の線形性の規則 (取り出さない残りのフィールドは `Unr`、上書きされる古い値は `Unr`) は今の records.md から引き継ぐ
  - タプルは構造的なまま残し、`t.0` で射影できるようにする。Unit は 0 要素のタプル `()` である
  - 採らなかった案: row 多相の構造的なレコード (今の spec) は、レコードの row の sort、ネイティブでのオフセットの証拠か単相化、`with` とレイアウトの衝突を持ち込み、ユーザーの instance も書けない
- 等価、比較、表示は、組み込みのクラス `Eq` / `Ord` / `Show` の閉じた集合で作る。シグネチャの制約 `Eq a =>`、`deriving (Eq, Ord, Show)`、具体化の表からの証拠の解決、translate での特殊化 (実行時の辞書は持たない) を、roadmap.md の M5 の設計のとおりに作る。型クラスの段階では `class` / `instance` の宣言を足すだけで済み、作り直す部分がない。今の `==` の特別扱い (`equality` と E2006) は、この仕組みに置き換える
  - `Num` は `Float` を入れる段階に回す。それまで算術は `Int -> Int -> Int` のままにする
  - `Ord` のメソッドの形、`Show` を1つにするか分けるか、`deriving` で比べないフィールドの扱いは、S4 の spec で決める
  - 採らなかった案: 実行時に値の構造をたどる方式 (OCaml、Gleam) は MVP では小さいが、型クラスに移るときに捨てる機構になる
- IO の失敗は中断として伝え、組み込みの `try_io : (Unit -> <IO | e> a) -> <IO | e> Result IOError a` で捕まえる。中断の途中で捕まっていた `Lin` の値は、`never` の操作の中断と同じく破棄処理で後始末する。捕まえなければ、エラーを表示して終了コード 1 で止まる
- `exit : Int -> <IO> a` は、同じ中断で `Lin` の値を後始末してから終了する。`<IO>` を持たせるのは、`par` の子から呼べないようにするためである。`try_io` は `exit` を捕まえない
- ローカルの再帰関数を入れる。`let (f, text) = read_all f` のような再束縛を壊さないように、引数を持つ関数の形のローカル定義だけを再帰的にする。単相で、lambda lifting する。構文の細部は S4 の spec で決める

### S5 に回すもの

S4 で書いたスクリプトの書き心地を見て、採るかどうかを決める。

- Kind の宣言化。宣言にするなら、持ち越しの条件付きの制約を書く形が要る。`map`、`fold`、`keep` を注釈なしで書ける今の性質を失わないことを条件にする
- fixity の宣言をやめ、先頭の文字で決まる固定の優先順位の表にすること
- 字句的な負号 (`f -1` を `f (-1)` と読む。GHC の LexicalNegation と同じ)
- ブロック引数 (末尾の `fn`、`match`、`if`、`handle` を括弧なしで渡す)
- 暗黙の row 変数 ε (高階関数のシグネチャで省略した row を同じ変数とみなす)
- 中断で終わる経路での `Lin` の値の暗黙の後始末
- 線形な値の受け渡しの糖衣 (`inout` 風の構文)
- トップレベルの値を一度だけ評価すること (単相で `Unr` の値に限る)

## 作り直した後の構成

crate の並びと「各段階は純粋な関数」という規律は変えない。

| crate | 変わること |
|---|---|
| `eml_diagnostics` | 変えない |
| `eml_syntax` | `extern`、名前的なレコード、`deriving`、`=>` の制約、ローカルの再帰関数、リストのリテラル、補間、複数行と raw の文字列の文法を足す。`resume` を削除する |
| `eml_hir` | `ItemTree` を `Send` にする。表示用のフィールドを除く。名前解決の重複した enum をまとめ、`Reporter` を入れる。`std/` ツリーを読む複数の根のローダーにする。`extern` の項目を足す |
| `eml_types` | 暗黙の `mask` の side table、`IO` の重なりをまとめる規則、普通の関数としての `k`、`Eq` / `Ord` / `Show` の制約の検査と証拠の解決を入れる。段2の Kind 推論は残し、実装を整理する |
| `eml_core_ir` | translate を、型に依存する唯一の段にする (特殊化、Repr、`mask` の挿入、レコードの配置、末尾呼び出し)。Core IR v2 → 縮約パス → Perceus → verifier の順に流す。テキスト形式をテスト用に作り直す |
| `eml_runtime` | 安全なアリーナを、インタプリタ用の検査付きヒープとして残す。形だけのマルチコア対策を削除する。不死のオブジェクトと handler の連鎖を足す |
| `eml_interp` | Core IR v2 を実行するシングルスレッドの CEK にする。extern の表の Rust の実装を持つ |
| `eml_cli` | パイプラインの駆動を1本にし、`eml_test_support` からも使う。`eml file.em args...` で直接起動できるようにする |
| `std/` (新設) | `Prelude.em` と、extern で書いた標準ライブラリのモジュール |

将来の拡張は、この構成の上に載せる。

- ネイティブ化: Perceus の後の Core IR から、コード生成のバックエンドへ渡す。ネイティブのランタイムは extern の表を C ABI の関数として持つ
- evidence passing: Core IR から Core IR への変換パスとして、Perceus の前に入れる
- マルチコア: ネイティブのランタイムだけで実装する
- 型クラス: 組み込みのクラスの閉じた集合に、`class` / `instance` の宣言を足す

各サブプロジェクトで spec、計画、実装のサイクルを回す。S3a と S3b は互いに依存しないので、どちらを先にしてもよい。

| S3b バックエンドの土台 | Core IR v2 (ブロック木、Repr と box/unbox、消費しない `Switch`、extern の表、位置情報、translate で作る末尾呼び出し)、simplify を縮約パスに置き換える、テキスト形式の作り直し、handler の連鎖、一意な文字列のその場の連結、不死のリテラル、ランタイムの形だけの対策の削除、runtime.md と multicore.md の整理 | S2a、S2b | UI テストの出力が変わらない (実行時エラーに位置が付く run-fail のスナップショットは除く)。エフェクトを使う再帰と文字列の連結が2乗の時間にならないことをテストで確かめる |
| S4 スクリプトの MVP | リスト、`Option`、`Result`、補間と文字列の形、名前的なレコード、`Eq` / `Ord` / `Show` と `deriving` と特殊化、ローカルの再帰関数、`try_io` と `exit`、extern の標準ライブラリ (`String`、`Env`、`Stdin`、`Fs`、`Proc.run`、`eprintln`)、`eml file.em args...` | S3a、S3b | wc、grep、ログの集計、CSV の変換、デプロイ手順の5本のスクリプトが UI テストとして動く |
| S5 実例による判断 | 上の「S5 に回すもの」 | S4 | 各項目を採るか採らないか決め、採ったものを実装する |

S5 の後は、言語の項目を次の順に並べる。

1. 型クラス (`class` / `instance` を開く)
2. `Float`、`Char`、`Num`
3. REPL
4. バイト列、`Array`、`Lin` のハンドル
5. UTF-8 の核と標準ライブラリの拡充
6. コマンドリテラル

処理系の項目 (Perceus の最適化、evidence passing、ネイティブ化、マルチコア) は、言語の項目とは別の列にする。

## S0 の詳細

### テストの変更の運用

`implementation/testing.md` の「テストの変更の運用」を次の規則に置き換える。

| 変更 | 合意と記録 |
|---|---|
| 成否の変更 (`run` / `run-fail` / `check-fail` の間の移動、UI テストの削除) | 作業の spec に1件ずつ挙げる。spec の承認を合意とみなす |
| 期待値の変更 (UI テストの出力、診断の番号と文言、各段階のダンプのスナップショット、成否を変えない UI テストの移動) | 作業の spec に、変わるテストを範囲で書く (「E2007 を使う UI テストはすべて書き換える」「Core IR のダンプはすべて取り直す」など)。spec の承認を、その範囲の変更すべてへの合意とみなす |
| 機械的な追随 (期待値が1文字も変わらない) | 合意は要らない。記録はコミットメッセージで足りる |

次の規則は変えない。

- テストを先に書く
- 既存のテストを守るために設計を曲げない。テストの変更が要るなら、上のどれに当たるかを示して spec に書く
- UI テストの最上位のディレクトリが成否を決める

あわせて、`testing.md` の「今あるテストの地図」を削除する。テストの置き場所は、ファイル名とディレクトリの規則から分かるためである。

| `grammar.md` | 「実装の段階」(E0004 をどの層で出すか) を `implementation/status.md` に移す |
| `records.md` | 「実装の段階」を `implementation/status.md` に移す。records.md の本体は S4 で名前的なレコードに書き直す |
