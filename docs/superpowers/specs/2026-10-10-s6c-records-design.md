# S6c レコード

位置づけ: 作業の設計。ロードマップの S6c を定める。S6c を終えたら、決まったことを `docs/spec/` と `docs/implementation/` に移し、この文書を削除する。

## 目的

名前的なレコード (`data` のコンストラクタに名前付きのフィールドを持たせる形) と、その作る式、射影、更新、分解のパターン、フィールドのセクション、タプルの射影 `t.0` を使えるようにする。S9 (`eml_rt`) でデータの表現を決めるときに、名前付きのフィールドを持つ実際のプログラムで詰められるようにするためである。

ロードマップの S6c の決定を、次の4点で改める。

- フィールド付きの構文は、コンストラクタが1つの `data` に限らない。直和型のどのコンストラクタにも名前付きのフィールドを持たせてよい。射影と更新だけを、コンストラクタが1つの型に限る (Rust の enum の構造体の選択肢と同じ)
- 名前付きのフィールドを持つコンストラクタも、位置の引数で使える (Haskell と同じ)
- 呼び出しの引数のうちラムダは、ほかの引数の後に型を検査する。射影は「その時点で型が分かっていること」を求めるので、`map (.name) people` を注釈なしで書けるようにするためである。本体の終わりまで解決を遅らせる仕組みは作らない、という決定は変えない
- 無名のレコードがなくなるので、型検査の中のタプルと `Unit` の表現から、ラベルの文字列をなくす (下の「タプルの内部表現」)

ロードマップの論点は、次のとおり決める。

- `{…}` とレイアウト規則3: 更新に `with` を使わない。そのうえで、`{` の括弧の中の行末の `=` はブロックを開かないことにし、括弧の中の `,` は括弧より上のブロックを閉じることにする (下の「レイアウト」)
- 借用のオペランドと `Field`: Core IR に新しい命令を足さず、今の `unpack` で射影する。借りたまま読む命令は S8 (LIR) で検討する (下の「translate」)
- レコードの CST: 下の「CST」
- レコードの `Ord` のフィールドの順: 宣言の順 (Haskell と同じ)

## 前提として確かめたこと

- 設計とレビューで、リポジトリの複製の型検査に、ラムダの引数を後で検査する形と、期待する型を先に単一化する形を入れ、全テストを流した。2回の測定とも、期待値が変わったのは UI テスト `check-fail/types/pipe_into_function_parameter.em` の1件だけだった
- 同じ測定で、次のことが分かった
  - 後に回したラムダの呼び出しの row は、ラムダを検査した後で今の row に入れる必要がある。先に入れると、`run/effects/io_twice.em` の `try (fn () -> deploy ())` が E2002 で落ちた。ラムダの本体の row が、row を入れる時点で決まっていないためである
  - 引数ごとの矢印をすべて先に取り出すと、ラムダのない呼び出しの診断が変わる (`konst 1 2 3` が「2引数なのに3引数」でなく型の不一致になる)。矢印は今と同じく、引数ごとにその直前に取り出す
  - 後に回したラムダの後に引数が余ると (`apply (fn x -> x) 1 2`)、余りの矢印を作るときに、ラムダが決めるはずの型変数を関数型にしてしまい、ラムダの中に誤りが出た
  - `use` が組むラムダを後に回すと、`use` のブロックの型の誤りの位置と文言が変わった (シグネチャを指す secondary が消え、書いていないラムダについての note が出る)
  - 誤りの経路 (`Arrow::Error`、`Arrow::NotFunction`) でラムダを推論すると、引数に新しい型変数が付き、`mapp (fn p -> p.name) xs` (名前の誤り) で E2013 が連鎖した
- 今のコンストラクタは、どれもいつも型と一緒に公開される (`pub data` がコンストラクタも公開する。コンストラクタを隠す仕組みはない)
- `t.0.1` は、今の lexer がすでに2つの `INT` に分ける

## 構文

### 宣言

```haskell
data Person =
  | Person { name : String, age : Int }
  deriving (Eq, Ord, Show)

data Shape =
  | Circle { radius : Int }
  | Rect { width : Int, height : Int }
  | Empty
```

- 選択肢は今の規則どおり `|` で始める。フィールド付きの選択肢は `'|' UIDENT '{' list(ftype) '}'`、`ftype ::= LIDENT ':' type` とする
- どの `data` にも書け、位置のコンストラクタや中置のコンストラクタと同じ `data` に混ぜてよい
- `{}` (フィールドが0個) も書ける。フィールドが0個のレコードのコンストラクタになる

### 式

| 用途 | 書き方 | 文法 |
|---|---|---|
| 作る | `Person { name = "a", age = 3 }`、省略形 `Person { name, age }` | `atom ::= qcon '{' list(field) '}'`、`field ::= LIDENT ('=' expr)?` |
| 更新 | `{ p \| age = 31 }`、省略形 `{ p \| age }` | `atom ::= '{' op_expr '\|' field (',' field)* ','? '}'` |
| 射影 | `p.name`、`t.0` | 今の `postfix` |
| セクション | `(.name)`、`(.0)` | 今の `'(' '.' LIDENT ')'` に、`'(' '.' INT ')'` を足す |

- `qcon '{'` は、`{` の後が `}` か、`LIDENT` の後に `=`、`,`、`}` が続くときだけ、作る式として1つの `atom` に読む。そのほかの `{` は、引数としての更新の始まりである。そのため `Some { p | age = 1 }` は、`Some` に更新を渡す式として読める。`Some Person { … }` は `Some (Person { … })` と読む (Haskell と同じく、作る式は適用より強く結びつく)
- 作る式の省略形 `{ name }` は `{ name = name }` と同じである。更新の省略形 `{ p | age }` も、`{ p | age = age }` と同じである
- 更新の元の値は `op_expr` として読む。`if`、`match`、`handle`、`fn`、`let` の形は、演算の項と同じく括弧が要る (E0012)。`match` の枝の `|` と、更新の `|` を取り違えないためである
- 更新にはフィールドが1つ以上要る。`{ p | }` は、フィールドを期待する E0011 にする。更新のフィールドは名前だけで、タプルは更新できない
- 射影とセクションの番号は、先頭に 0 のない10進数 (`0`、`1`、`12`) で、`u32` に収まるものに限る。`t.01`、`t.1_0`、`t.0x1` と範囲外の番号は、フィールドの番号を期待する E0011 にする

### パターン

| 用途 | 書き方 | 文法 |
|---|---|---|
| 分解 | `Person { name, age = a }` | `apat ::= qcon '{' list(fpat) '}'`、`fpat ::= LIDENT ('=' pat)?` |

- パターンの省略形 `{ name }` は、フィールドの名前の変数を束縛する。パターンに書かないフィールドは `_` と同じに扱う (Haskell と同じ)
- `cpat` は、`qcon apat*` より先に `UIDENT '{'` を見る。演算子の等式の先読み (`apat_len`) は、`qcon '{' … '}'` を1つの apat として数える。そのため `Person { a } <+> q = …` は演算子の等式として読め、トップレベルの `Person { a } = x` は、`(a, b) = …` と同じくトップレベルのパターンの束縛の誤りになる
- コンストラクタのない `{ … }` をパターンの位置に書くと (`let { a } = x`、`fn {x} -> …`)、E0011 にして、対応する `}` まで読み飛ばす
- フィールドの名前を持たないコンストラクタに `{}` を書いたパターン (`P {}`) は E1046 にする (Haskell の `P {}` とは違う)

### 言語から外すもの

- 無名のレコードの型と値 (`{ name : String }`、`{ name = "a" }`)、拡張 `{ l = v | e }`、row 変数 `{ … | r }`、`{ p with … }` を文法から消す
- 型の位置の `{` は E0011 にする。コンストラクタのない `{ name = "a" }` は、更新の `|` がないので、`|` を期待する E0011 になる。どちらも対応する `}` まで読み飛ばし、中のフィールドの名前から E1001 や型の誤りを連鎖させない (今の `unsupported_group` と同じ読み飛ばし)
- これで、パーサが E0004 を出す構文はなくなる

### CST

| 節点 | 子 |
|---|---|
| `RECORD_EXPR` | `PATH`、`{`、`FIELD` と `,` の並び、`}` |
| `FIELD` | `NAME_REF`、省略しなければ `=` と式 |
| `UPDATE_EXPR` | `{`、式、`\|`、`FIELD` と `,` の並び、`}` |
| `RECORD_PAT` | `PATH`、`{`、`FIELD_PAT` と `,` の並び、`}` |
| `FIELD_PAT` | `NAME_REF`、省略しなければ `=` とパターン |
| `RECORD_FIELDS` (`ALT` の子) | `{`、`FIELD_DECL` と `,` の並び、`}` |
| `FIELD_DECL` | `NAME`、`:`、型 |

typed AST は、`ast::RecordExpr` (`ast::Expr` の選択肢)、`ast::UpdateExpr` (同)、`ast::RecordPat` (`ast::Pat` の選択肢) と、`fields()` などのアクセサを足す。

### レイアウト

レイアウトの規則を2つ変える ([レイアウト規則](../../spec/layout.md))。

- 規則3の開始トークンのうち `=` は、一番内側の文脈が `{` の `Bracket` のときはブロックを開かない。`{` の中の `=` は、いつもフィールドの `=` である。そのため、フィールドの値を次の行に書ける
- 規則4に足す: 括弧の中の `,` は、一番内側の `Bracket` より上にあるすべての `Block` を `CLOSE` で閉じる (閉じ括弧と同じ)。行末の `->` などで開いたブロックを、次の要素の前で閉じるためである。今は `,` がブロックの中に入って構文の誤りになる (`(fn x ->⏎ x + 1,⏎ n)` は E0011 になる)。この変更は、今は誤りになる形だけを受け付けるようにする

```haskell
let p = Person {
  name =
    long_name_of user,
  on_save = fn e ->
    log e,
  age = 3,
}
```

- `Bracket` を積む `{` と、括弧の中で改行が意味を持たないことは、今と同じである。規則2により、括弧の中の行は囲んでいるブロックより深く字下げする。そのため、更新の `|` を行の先頭に書くときは、文の列より深く字下げする (`{ p⏎| age = 1 }` で `|` を文と同じ列に置くと、閉じていない括弧の誤りになる)

### 深さ

- `{` は括弧と同じく1段に数える。フィールドの数は深さに数えない

## HIR

### フィールドの名前

- `Constructor` に `field_names: Option<Vec<FieldName>>` を足す。`FieldName` は名前と位置である。位置のコンストラクタは `None`、`{}` で宣言したコンストラクタは `Some([])` である。型は今の `fields` のまま使う
- フィールドの名前は値の名前空間に入れない。セレクタの関数は作らず、`p.name` は型から引く。別々の `data` も、同じ `data` の別々のコンストラクタも、同じフィールドの名前を持ってよい
- フィールドは見える範囲を検査しない。射影と更新は型から引くので、型の名前がそのモジュールで見えている必要もない。今はコンストラクタがいつも型と一緒に公開されるので、これで足りる。抽象型を入れるときに、コンストラクタと一緒にフィールドも隠す規則を決める

### 作る式

- コンストラクタは今のとおり名前で引く (`M.Person { … }` も書ける)
- 新しい `ExprKind::Record { ctor: ConstructorId, fields: Vec<(u32, ExprId)> }` にする。並びはソースの順で、`u32` は宣言の中のフィールドの番号である。ソースの順で持つのは、フィールドの式を書いた順に評価するためである
- フィールドが0個の作る式 (`A {}`) は、コンストラクタの参照 `ExprKind::Path` にする。コンストラクタの参照と同じく値に入れ、`f a A {} b` と `f a A b` の評価のまとまりをそろえるためである (S6a の `[]` と同じ)
- 省略形 `{ name }` の値は、その位置で `name` を普通に名前解決した参照にする
- 誤り
  - E1045 (`DUPLICATE_FIELD`): 同じフィールドを2回書いた
  - E1046 (`UNKNOWN_FIELD`): コンストラクタにないフィールドを書いた。フィールドの名前を持たないコンストラクタに `{…}` を書いた場合を含む
  - E1047 (`MISSING_FIELDS`): 書いていないフィールドがある。足りない名前をすべて並べ、作る式の位置に1件出す
- 誤りがあれば、式全体を `Missing` にする。正しく書いたフィールドの式は lower し、その中の誤りは報告する

### 更新と射影とセクション

- 更新 `{ e | f = v }` は `ExprKind::Update { base: ExprId, fields: Vec<(FieldName, ExprId)> }` にする。並びはソースの順である。フィールドは名前のまま持ち、型検査が解決する。HIR が検査するのは重複 (E1045) だけである
- 射影 `e.f` は `ExprKind::Field { base: ExprId, field: FieldUse }` にする。`FieldUse` は、名前か番号 (`u32`) に、位置を添えたものである
- セクション `(.f)` は、HIR が `fn p -> p.f` のラムダに組む。`p` は新しい局所変数で、範囲はセクション全体である
- `Record` (フィールドが1つ以上)、`Update`、`Field` は、引数をまとめて渡す規則の「値」に入れない ([式](../../spec/expressions.md) の「関数適用」)

### パターン

- `Person { name, age = a }` は、今の `PatKind::Con { ctor, args }` に組む。`args` は宣言の順に並べ、書かないフィールドは `Wildcard` にする。書かないフィールドの `Wildcard` の範囲は、レコードのパターン全体である
- HIR は、書かないフィールドから作った `Wildcard` を、本体の表 `Body.omitted_fields: ArenaMap<PatId, (ConstructorId, u32)>` に記録する。線形性の診断が、書き手の `_` と区別してフィールドの名前で報告するためである (今の `return` の節の省いた状態と同じ考え方)
- 中のパターンはソースの順に lower する。局所変数の番号と E1017 の報告の順を、書いた順にそろえるためである (S6a のリストのパターンと同じ)
- 誤りは、作る式と同じ E1045 と E1046 を使う。書かないフィールドは誤りにしない。誤りがあっても中のパターンは lower して変数を束縛し、パターン全体は `PatKind::Missing` にする (今の E1016 と同じ)。同じフィールドを2回書いた `{ name, name }` は E1045 だけを報告し、E1017 を重ねない

### `use` のラムダの印

- HIR は、`use` が残りの文を包むために組んだラムダを、本体の表 `Body.use_lambdas: HashSet<ExprId>` に記録する。型検査は、これを後に回さない (下の「ラムダを後で検査する」)

### 宣言

- 同じコンストラクタの中で同じフィールドの名前を2回書けば、E1045 にする

### ダンプ

- `pretty` は、作る式を `Person { name = …, age = … }` (ソースの順)、パターンを `Person { name = …, age = … }` (宣言の順で、全フィールド)、更新を `{ e | age = … }`、射影を `e.name` と書く

## 型検査

### 射影 `e.f`

- `e` の型を推論し、その時点の代表を見て、場合に分ける
  - コンストラクタが1つの `data` で、そのコンストラクタが名前 `f` のフィールドを持つ: 結果は、そのフィールドの型を型引数で具体化したものになる
  - タプルで、`f` が範囲内の番号である: その要素の型になる
  - 推論用の型変数 (まだ決まっていない): E2013 (`FIELD_NEEDS_KNOWN_TYPE`) を出す。help は、`e` がラムダの引数なら引数の型の明示 (`fn (p : Person) -> …`)、それ以外なら型の明示 `(e : T)` を示す
  - `Error`: 何も報告しない
  - それ以外: E2014 (`NO_SUCH_FIELD`) を出す。名前のフィールドを持たない型、番号の範囲外、名前で指したタプル、番号で指した `data`、型変数 `a`、関数型が当たる。コンストラクタが2つ以上の型には「`Shape` has more than one constructor」の note と、`match` で分解する help を付ける
- 解決の結果を、型の表 `typed.fields: ExprId → FieldTarget` に残す。`FieldTarget` は、コンストラクタとフィールドの番号か、タプルの要素の数と番号である
- 線形性: 取り出さない残りのフィールドは、`_` で受けたのと同じ扱いにする。型検査は、残りのフィールドの具体化した型を、型の表 `typed.discarded: ExprId → Vec<(u32, Ty)>` に残す。線形性の検査 (`usage.rs`) は、この表から `Unr` の制約を出す。`Lin` なら E3004 で、新しい `KindReason::DiscardedField` がフィールドの名前を文言に出す。help は分解のパターンを示す。ただし、セクションから組んだラムダでは、隠れた引数の分解を示せないので、help を付けない
- 型変数の Kind の制約は、今と同じく使い方から推論する。`b.x` を `Box a` に使うと、残りのフィールドの `a` に `Unr` の制約が付く (`Box x _` と同じ)

### 更新 `{ e | f = v }`

- `e` の型の解決は射影と同じで、E2013 と E2014 を使う。各 `v` は、そのフィールドの型 (具体化したもの) に対して検査する。結果の型は `e` の型のままにする。型を変える更新は入れない
- 解決の結果を、型の表 `typed.updates: ExprId → (ConstructorId, Vec<u32>)` に残す。`Vec<u32>` は、ソースの順のフィールドの番号である
- 線形性: 上書きされる古いフィールドは `_` と同じ扱いにし、射影と同じく `typed.discarded` に残す (`Lin` なら E3004)。`e` は1回消費し、残りのフィールドは新しい値に移る
- 評価の順: `e` を先に評価し、次にフィールドの式を書いた順に評価する

### 作る式

- コンストラクタを今と同じく具体化し、各フィールドの式をその型に対して、書いた順に検査する。結果の型と線形性、持ち越し、網羅性は、位置のコンストラクタの呼び出しと同じである

### フィールドの不一致の由来

- 作る式と更新のフィールドの式の型の誤りには、新しい由来 `Origin::Field { ctor, field }` を付ける。文言は「field `name` of `Person`」とし、位置のコンストラクタの「argument 1 of `Person`」と区別する

### ラムダを後で検査する

呼び出しの引数のうち、ラムダ (`ExprKind::Lambda`) は、ほかの引数の後に検査する。後に回すのは、直接の引数として書いたラムダ (`(fn x -> …)` の括弧は HIR で消える) と、HIR が組んだラムダ (フィールドのセクション、演算子のセクション `(+ 1)` と `(+)`) である。`use` が組んだラムダ (`Body.use_lambdas`)、型の明示 `((fn x -> …) : T)`、ラムダを返す式は後に回さない。

1. 引数を左から1つずつ見る。矢印は今と同じく、その引数の直前に取り出す
2. ラムダでない引数は、すぐ検査する。その矢印の row は、それより前にラムダを後に回していなければ、今と同じくすぐ今の row に入れる。後に回していれば、row も後に回す
3. ラムダは、矢印の引数の型と由来を覚えて後に回す
4. 次の矢印を取り出すときに、呼ばれる側の型が推論用の型変数で、新しい関数型を作る必要があり、後に回したラムダがあれば、先に後に回したラムダを検査して row を入れる。ラムダが決める型変数を、余りの引数のための関数型にしないためである (`apply (fn x -> x) 1 2` は、今と同じく「2引数なのに3引数」になる)
5. 引数を見終えたら、呼び出しを期待する型に対して検査していて (`check_expr` から来た呼び出し)、後に回したラムダがあれば、結果の型を期待する型に単一化する。結果の型は、部分適用の残りの row を開いた後の型である (`open_spine` の後)。`people |> map (.name)` で、`map` の型変数を先に決めるためである。単一化の誤りは、今と同じ「期待する型との不一致」として呼び出しの位置に報告し、後の期待する型との検査では重ねない
6. 後に回したラムダを左から検査する
7. 後に回した row を、引数の順に今の row に入れる

- 誤りの経路 (`Arrow::Error`、`Arrow::NotFunction`) では、後に回したラムダと、残りの引数のうちのラムダを、`Error` の型に対して検査する。引数を `Error` で束縛して、射影の E2013 などを連鎖させないためである
- 評価の順と、持ち越しと線形性の検査の順は変えない。どちらも別のパスで、ソースの順にたどる
- 型の誤りの報告の位置が変わりうる。たとえば `map (fn x -> x + 1) ["a"]` は、今は `"a"` の位置に出るが、変更後はラムダの中の `x + 1` に出る
- 後に回したラムダどうしは、左から検査する。そのため `compose (fn b -> b.name) (fn p -> p.boss) x` は、最初のラムダの時点で `b` の型が決まらず E2013 になる。この制限は [型と Kind](../../spec/types.md) に書く

### 使用と持ち越し

- `usage.rs`: 射影は `e` の1回の消費、更新は `e` とフィールドの式を評価の順に、作る式はフィールドの式を書いた順にたどる。射影と更新の捨てるフィールドは `typed.discarded` から、パターンの書かないフィールドは `Body.omitted_fields` から報告する
- `carry.rs`: 作る式と更新を、タプルと同じ「左から評価する部分」として扱う

### タプルの内部表現

- 無名のレコードがなくなるので、`TyShape::Record`、`TypeKind::Record`、`ShapeTy::Record` を、ラベルを持たない `Tuple(Vec<_>)` に替える。`Unit` は要素のないタプルである。ラベルの文字列 (`"0"`、`"1"`) と、`{ l : t }` の形の表示は消す
- タプルの表示 (`(A, B)`、`()` を `Unit` と書くこと) と、構造的な instance の解決 (`Resolution::Tuple`) は変えない

## translate

- 作る式: フィールドの式を書いた順に評価して変数に入れ、宣言の順に並べ替えて `con L #t(…)` を作る。配置はほかの `data` と同じで、フィールドの Repr は宣言の型から決まる。名前付きのフィールドのためだけの配置や命令は作らない
- 射影 `e.f`: `e` を評価し、`unpack v L #t(f0, …, fn)` で分解して、`f` の位置の変数を結果にする。`unpack` の各変数の Repr は、配置のフィールドの Repr にする。結果の変数を式の型の Repr で使うときの変換 (型変数のフィールドの `tobj` から `int` への `unbox` など) は、今と同じく boxing が足す。タプルの `t.0` も同じ形 (タプルの配置) である。取り出したフィールドは、今の規則どおり Perceus が所有にする (`dup`、または値が一意なら `release` で参照を引き継ぐ)
- 更新 `{ e | f = v }`: `e` を評価し、フィールドの式を書いた順に評価してから、`unpack` で古いフィールドを取り出し、置き換えるもの以外を並べて新しい `con` を作る。意味としては写しで、残したフィールドは Perceus が所有にし、上書きされる古い値は手放す。一意な値をその場で書き換えるのは、Perceus の reuse (ロードマップの「処理系」) に任せる
- パターンは今のコンストラクタのパターンなので、決定木は変えない。セクションはラムダとして変換する
- boxing、contract、Perceus、verifier、インタプリタ、ランタイムは変えない

## `deriving`

- `Eq` と `Ord`: 今のまま、フィールドを宣言の順に比べる
- `Show`: 名前付きのフィールドのコンストラクタ (`field_names` が `Some`) は `Person { name = "a", age = 3 }` と書く。フィールドの値は `show_prec 0` で書く (中括弧の中なので括弧が要らない)。`Con { … }` は atom なので、引数の位置でも外側に括弧を付けない (`Some Person { name = "a" }`)。フィールドが0個なら `A {}` と書く。どれも、そのまま読み戻せる形である。位置のコンストラクタ (`field_names` が `None`) の表示は変えない
- `display` は今のまま既定 (`show`) である
