# S13d row の最小の具体化の設計

## 目的と範囲

S13d (row の最小の具体化) の設計である。ロードマップの S13d の節 (`docs/future/roadmap.md`) の「決めたこと」を細部まで決め、「論点」に答える。完了の条件は roadmap のとおり、次の1つである。

- 純粋なコールバックを渡した総称な handler を、外側にユーザーのエフェクト (`State` など) の handler がある所で呼んでも、`RunStats` で yield を数えない

今は、呼び出し先の矢印の row の末尾が推論用の変数だと、`Table::include_row` (`crates/eml_types/src/table/row.rs`) がその row を今の row とまるごと単一化する。変数が今の row の残りのラベルを受けるので、引数が純粋でも、総称な関数の instance が「yield しうる」になる。S13d では、この単一化をやめて「呼んだ場所の row に含まれる」という制約として残し、トップレベルの本体ごとに最小の解で解く。

次のものは範囲に入れない。

- 外側のエフェクトの操作を起こす節の yield (`Yield a` を `Yield b` に変える handler の `yield` の節など): 節の本体に再開する操作の `perform` があるので、row の具体化に関係なく1要素ごとに yield する。ロードマップの「evidence passing の最適化」の under の項目で扱う (2026-10-18 にユーザーが決めた)
- handle の外側の row と `k` の呼び出しの row を、handle の位置の今の row とみなすこと (`docs/implementation/status.md` の「持ち越し規則は、開いた row の呼び出しを今の row と同じとみなす」の後半): handle の本体は外側の row の末尾を共有して動くので、S13d の包含では変わらない
- `let` で束縛したラムダの値の row 変数を多相化すること

## 2026-10-18 に決めたこと

- 外側の操作を起こす節の yield は、S13d と別の作業にした (ユーザーが決めた)。ロードマップの S13d の「決めたこと」、「判断の材料」、「処理系」の under の項目に記録した
- 末尾が推論用の変数の呼び出しを、すべて後で確かめる包含にし、トップレベルの本体ごとに1つの固定点で解く (ユーザーが了承した)。ローカル関数の組の固定点 (`docs/spec/types.md` の「ローカル関数の推論」) を一般にした形である。その結果、ローカル関数の「本体の後で row を閉じる」規則と「閉じない例外」はなくなる。`mask` は解いた後で決める。E2002 は包含を解く時点で、呼び出しの位置に出す

## 計測 (S13d の前)

2026-10-18 に、1,000要素のプログラムで `RunStats` の yield を数え、release ビルドで実時間と命令数を測った (Apple M4)。プログラムは使い捨てで、リポジトリには入れていない。

| 形 | yields |
|---|---|
| `Yield.fold` に純粋なラムダを渡す (`<IO>` だけ) | 0 |
| 同じ `fold` を `State.run` の中で呼ぶ | 1000 |
| `Yield.for_each` のコールバックで `List.map` (ラムダ) を使い、`State.run` の中で呼ぶ | 1000 |
| `Yield (List a)` を `Yield (List b)` に変える handler の節で `List.map` を呼ぶ | 1000 |
| 同じ変換を `State.run` の中で使う | 2000 |

- 100万要素の `fold` は、`<IO>` の中で0.09秒 (命令数 2.18e9)、`State.run` の中で0.28秒 (8.00e9) だった
- `map` が yield しうる instance になるのは、渡す関数の row が開いているとき (ラムダやトップレベルの関数の参照) だけである。引数 `f : a -> b` のように row が `<>` に閉じた型を渡すと、`map` は yield しない instance のままだった。yield しうる `map` でも実行時の yield は増えず、300万要素で命令数が約4%増えた (5.51e9 から 5.74e9)

S13d の後の見込みは、1行目が0のまま、2行目と3行目が0、4行目が1000のまま、5行目が1000 (変換の節の分) である。

## 規則

### 呼び出しの包含の記録

呼び出しの矢印ごとに、呼び出し先の row を `<ls | t>`、今の row を A とする。

- `t` が閉じているか `Error` のとき: 今と同じである。`ls` を A の同じエフェクトのラベルと前から順に対にし、A の自由な末尾に足りないラベルを足す。制約は残さない
- `t` が row 変数 (推論用でも rigid でも) のとき: `ls` の対にし方は上と同じで、今すぐ行う。新しい row 変数 `r` を作り、`<ls | r>` を A と単一化する。そのうえで、制約「`<ls | t>` が A に含まれる」を、呼び出しのキー (式と矢印の番号の組、`mask` の表と同じ)、呼び出し先の名前、今の row の由来 (`AmbientSource`)、呼び出しの範囲と一緒に本体の制約の列に積む。`t` は単一化しない。制約には `ls` を含む呼び出し先の row 全体を持たせる。4 で作る `mask` の残す数 n は、呼び出し先が明示したラベルの数から決まるためである (`Table::mask`)

`ls` は、制約を積む時点で解いた呼び出し先の row のラベルである。宣言に書いたラベルだけではない。呼び出しの中で後に回したラムダの引数は、row の包含より先に検査する (`check_postponed`) ので、ラムダの本体が `t` に入れたラベルも、ここで今すぐ対になる。

`ls` の対にし方を今すぐ行うのは、対にしたラベルの型引数の単一化を遅らせないためである。操作の結果の型 (`get ()` の `s` など) が後の射影 (`x.name`) より前に決まらないと、E2013 になる。遅れるのは、制約を積んだ後で `t` に入ったラベルの型引数だけである。

これで E2013 になる形が1つ残る。高階のローカル関数 `let run h = h ()` を `<State Person>` の本体で `(run get).name` と使う形である。今は `h ()` の呼び出しで `h` の row と `run` の row が単一化されるので、`run get` の包含で `s` が `Person` に決まってから射影を検査する。S13d では `run` の row に `State` が入るのが 1 の固定点なので、射影の時点で `s` が決まっていない。この形は、`docs/implementation/status.md` の「型と row の推論」に制限として書き、受け入れる (私の判断)。この形に当たる既存のテストがあれば、種類1の変更として下の「テストの変更」に足す。結果の型を注釈すれば (`(run get : Person).name`) 通る。

`t` が rigid な変数の場合も制約にする。今は rigid な末尾の手前の残りが自由な変数なら、その場でその変数を rigid な変数に束縛する。そのため、ラムダやローカル関数の本体では、呼ぶ順序で通るかが決まる (`let go k = h () + ask () + k` が E2002 になる。`docs/implementation/status.md` の「型と row の推論」)。制約にすれば、下の解き方でラベルを足し終えてから束縛するので、順序によらず通る。

この規則は、トップレベルの関数、extern、操作、メソッドの参照の呼び出しにも、ローカル関数、`let` で束縛したラムダ、引数、`k`、型の分からない呼び出し先 (`next_arrow` が作る関数型) にも同じに当てはめる。ローカル関数の組の中の呼び出しを別に扱う仕組み (`LocalFrame`、`DeferredRow`、`add_missing_labels`、`close_group`、`closed_locals`) は、この制約の列に置き換えて消す。

### 解き方

トップレベルの本体 (instance のメソッドと既定のメソッドを含む) と REPL の入力ごとに、本体の検査 (`check_function`) が終わった直後、クラスの制約を解く (`solve_constraints`) 前に、積んだ制約を次の順に解く。`usage::constrain` と `carry::constrain` より前、段2の Kind の問題を取り出す (`take_problem`) より前でなければならない。row を束縛するときに足す多重度の制約と、持ち越しの組が、解いた row を見るためである。

以下、制約の呼び出し先の row を C、今の row を A と書く。

1. **ラベルの固定点**: 何も足さなくなるまで、制約を積んだ順に繰り返したどる。制約ごとに、C の今のラベルのうち A に足りないものを、scoped labels の対にし方で数え (`missing_labels`)、A の自由な末尾に足す。今のローカル関数の組の固定点の 3 と同じく、次の制約は足さずに飛ばす
   - A の末尾が rigid な変数か閉じた row で、足せない制約
   - C と A が同じ開いた末尾に行き着く制約 (`shares_tail`)
   - C のあるエフェクトのラベルの数が上限を超えた制約。上限は、エフェクトごとに、固定点を始めたときの、すべての制約の C と A のラベルの数の和である (同じ row は1回だけ数える)
2. **rigid な末尾の固定点**: 何も束縛しなくなるまで繰り返す。C の末尾が rigid な変数 `ρ` で、A から C のラベルと対になる分を除いた残りの末尾が自由な変数のとき、その変数を `<| ρ>` に束縛する。ラベルを足し終えた後で束縛するので、束縛した row にラベルを足す必要は残らない。2つの制約が同じ自由な末尾に別々の rigid な変数を求めたら、2つ目は 4 で E2002 になる
3. **閉じる**: C の末尾がまだ自由な変数 `t` で、`t` が次のどれにも当たらない制約について、`t` を `<>` に閉じる。どの引数からもエフェクトが入らなかった変数である。これが最小の解になる
   - その制約の A に現れる (ラベルの型引数の中を含む)。4 の単一化に任せ、今と同じ誤り (E2005 など) にするためである。C と A が共有する末尾が A の末尾に現れることは、これに当たらない
   - REPL の `:type` の入力で、問い合わせた式の型に現れる (下の「REPL の入力」)
4. **確かめる**: 積んだ順に C を A に含める。手順は今の `include_row` と同じで、今の `include_call_row` の誤りの報告 (E2002、E2005、E2001) と `mask` の記録を、保存した呼び出しのキー、名前、由来で行う。1つの呼び出しの誤りは1件だけ報告する
   - 閉じた末尾: C のラベルを A と前から順に対にし、型引数を単一化する。`mask` は空である。`ls` はすでに対にしてあるので、ここで新しく対になるのは後から入ったラベルだけである
   - rigid な末尾: 今と同じく C 全体から `mask` を作るので、残す数 n は `ls` の数になる。2 で束縛できなかったら E2002 である
   - 自由な末尾 (3 で閉じなかったもの): 今と同じく単一化する。A の中で同じ変数の手前にラベルがあれば、今と同じく E2005 (無限の row) か E2002 になる

1 と 2 と 3 が止まることは、今のローカル関数の組の固定点と同じ議論で言える。1 で足すラベルの数は上限で抑えられ、2 は自由な変数を減らす一方である。

解き方の中で row を束縛すると (1 の `add_labels`、2 の束縛、4 の単一化)、多重度の制約が足される。その由来は、その制約の呼び出しの範囲にする。今の呼び出しの包含が `with_kind_origin` で呼び出しの範囲を由来にしているのと同じである。

#### 末尾を共有する呼び出し (`k` など)

C と A が同じ開いた末尾に行き着く制約は、1 では飛ばし、3 ではほかの制約と同じく閉じる。3 で A を見るときは A のラベルの中だけを見る。共有する末尾が A の末尾に現れることは、閉じない理由にならない。自分の handler の中で自分を呼ぶローカル関数 (`let go k = ask () + (handle go (k - 1) with …)`) と、節の中で呼ぶ `k` がこれに当たる。

節の中で同じエフェクトの handler を張り、その中で `k` を呼ぶ形 (`handle (k x) with …`) では、今の row は `<L, L | ρ>`、`k` の row は `<L | ρ>` になる。`ρ` を閉じると、`k` の row の `L` は今の row の最も内側の `L`、つまり節の中で張った handler と対になる。rigid な末尾 `ρ` では、`L` の n = 1、m = 1 の `mask` が付き、n = 1 が最も内側の handler を残すので、`k` の継続の `L` の操作は同じ内側の handler に届く。閉じた row を外側の row に持つ節でも、`k` の row `<L>` は `<L, L>` に `mask` なしで含まれ、同じく内側の handler に届く。3つの場合の意味がそろうので、継続の呼び出しは特別に扱わない。`k` を直に呼ぶ形、包み (`let resume x = k x`) を通す形、引数に渡す形 (`apply k x`) も区別しない。

最初の設計では、継続を直に呼ぶ制約の共有する末尾を閉じず、4 の単一化で誤りにしていた (末尾を共有する制約を 4 で先に確かめる順序も、そのためのものだった)。継続の row のラベルは外側の特定の handler を指すので、閉じると意味が変わる、という理由だった。この理由は正しくなかった。上のとおり、rigid な末尾の `mask` も `k` の `L` を内側の handler に届けるので、閉じた形は rigid な形と同じ意味になる。2026-10-18 の最終レビューで、この規則と順序を外した (種類1の変更を下の「テストの変更」に足した)。

### ローカル関数とラムダ

- ローカル関数の最後の矢印の row は、本体の後で閉じない。組の関数の呼び出しも、自分への呼び出しも、上の制約になる。値として参照するときに row を開く処理 (`closed_locals` に入った関数の `open_spine`) もなくす。値の参照は、関数の row 変数をそのまま共有する
- 呼び出しが包含になるので、`let` で束縛したラムダとローカル関数の row は、呼ぶ順序によらず決まる。`<IO>` の本体で `let g = fn x -> x + 1` を呼んでから `g` を `(Int -> Int)` の引数に渡す形も通る。`g` の row は受け渡しの単一化で `<>` に決まり、呼び出しの制約は `<>` を `<IO>` に含めるだけになる
- 同じローカル関数を、row が閉じた別々の関数型の位置に値として渡す形 (`Int -> <IO> Int` の引数と `Int -> Int` の引数の両方に渡す) は、今は開いて通るが、S13d では E2001 か E2002 になる。row 変数を共有するためである。単相のローカル関数の制限として受け入れる (私の判断)。既存のテストがこの形に当たったら、通過と失敗の変更 (種類1) として下の「テストの変更」に足す
- ローカル関数の組の文書の 1〜5 の手順 (`docs/spec/types.md` の「ローカル関数の推論」) は、本体全体の解き方に吸収される。組で1つの row を共有しないこと、組の関数ごとに最後の矢印の row を持つこと、再帰する組の関数が `Unr` の値しか捕まえられないことは変わらない

### `mask` と yield の分類

- `mask` は 4 で決まる。今と同じく、`n` が正の項目は呼び出し先の末尾が rigid な変数のときだけ付く
- yield の分類 (`RowYield`) は、今も本体の検査と段2の Kind の解の後 (`export_body`) で行っている。分類の規則 (`crates/eml_types/src/table/yields.rs`) は変えない。3 で閉じた変数は `Never` になる。閉じない自由な変数も、今と同じく `Never` である
- `Instantiation::rows`、`BodyTypes::body_yield`、`lambda_yields`、`arrow_yields`、`first_arrow_yield` は、どれも解いた row から作られるので、変える所はない

### Kind と持ち越し

- row を束縛するとき (`bind_row`) に足す多重度の制約は、解き方の中の束縛でも同じに足す。末尾の変数を今の row と単一化しなくなるので、その変数の多重度は今の row の多重度に引き上げられない
- 持ち越しの制約 (`carry::constrain`) は、解いた後の呼び出しの row を読む。純粋なラムダの呼び出しと、純粋な関数を渡したエフェクト多相な関数の呼び出しは、`multi` の操作を起こしうると判定されなくなる。`docs/implementation/status.md` の「持ち越し規則は、開いた row の呼び出しを今の row と同じとみなす」のうち、`let` で束縛したラムダと `keep f (fn () -> ())` の例は直る

### REPL の入力

- `check_input` (`crates/eml_types/src/check/input.rs`) でも、`check_function` の直後、`undecided_binding` より前に同じ手順で解く。`undecided_binding` は決まらなかった型変数を `Error` と単一化するので、4 で決まる型変数を先に `Error` にしないためである
- `:type` の表示 (`query::render`) は解いた後、今の `default_unsolved` の前で作る。3 は、問い合わせた式の型に現れる row 変数を閉じない。閉じると `:type fn f -> f ()` が `(Unit -> <e> a) -> <e> a` でなく `(Unit -> a) -> a` になり、型の一般さを失うためである。閉じない変数は、問い合わせた式の型に現れる row 変数から、包含の C の末尾から A の末尾へと外側へたどって集める (最終レビューで足した)。途中のラムダやローカル関数の row を閉じると、4 の単一化で問い合わせの型の変数まで `<>` に決まり、`:type fn f xs -> List.map (fn x -> f x) xs` が `(a -> b) -> List a -> List b` になるためである。C と A が共有する末尾で A が C より多くラベルを持つものは集めない。開いたままでは 4 が必ず誤りにするので、閉じる解しかない。トップレベルの本体では、本体の外へ出る型は rigid なシグネチャだけなので、閉じても一般さは失わない。`let` の入力は今も `default_unsolved` がすべての自由な row を閉じるので、変わらない

### 診断

- E2002 の形 (呼び出しを指し、「`map` performs `State`, which the signature of `f` does not allow」と、シグネチャの row か、ラムダか入力を指す) は変えない。今もラムダに渡した関数のエフェクトは、呼び出しの位置で報告している
- 報告する時点が本体の検査の後になる。そのため、今は呼ぶ順序で先に失敗していた別の誤り (E2001 など) が出なくなり、包含の E2002 に変わる所がある。診断は位置で並べ直すので、順序は変わらない

## テストの変更

テストの変更は3種類に分ける (`docs/implementation/testing.md`)。

### 種類1 (通過と失敗の変更)

次の2つは、今の誤りが出なくなることが分かっている。この spec の承認をもって合意とする。

- `crates/eml_types/tests/rows.rs` の `a_rigid_tail_in_a_local_function_is_order_dependent`: `h () + ask () + k` の順の E2002 が出なくなる。順序によらず通ることを確かめるテストに書き換え、名前も変える。理由は、rigid な末尾の束縛をラベルを足した後に回したことである
- `crates/eml_types/tests/linearity.rs` の `a_local_lambda_takes_the_row_of_its_caller`: `log ()` の E3006 が出なくなる。純粋なラムダの呼び出しをまたいで `File` を持てることを確かめるテストに書き換える。理由は、ラムダの row が今の row を受けなくなったことである
- `crates/eml_types/tests/effects.rs` の `a_rigid_ambient_reports_e2002_in_a_group` (作る途中で見つけた): `f n = h () + g n` の `g n` の E2002 が出なくなる。誤りがないことを確かめるテストに書き換え、名前を `a_rigid_ambient_takes_the_labels_of_a_group_first` に変える。理由は1つ目と同じく、rigid な末尾の束縛をラベルを足した後に回したことである
- `crates/eml_types/tests/masks.rs` の `resuming_under_a_handler_of_the_same_effect` の前半 `in_lambda` (最終レビューで決めた): 推論用の末尾のラムダの節で、同じエフェクトの handler の中で `k 1` を呼ぶ形の E2002 (「`k` performs `L`, which this lambda does not allow」) が出なくなる。誤りがなく `mask` もないことを確かめる形に書き換える。後半の `in_signature` の `[L@1]` はそのまま確かめる。理由は、継続を直に呼ぶ制約の共有する末尾を閉じない規則を外したことである。その規則は、閉じると `k` の `L` が内側の handler に届いて意味が変わる、という理由に立っていた。しかし rigid な末尾の `mask` (`L@1`) も `k` の `L` を内側の handler に届けるので、閉じた形は rigid な形と同じ意味になる (上の「末尾を共有する呼び出し」)。同じ形が rigid な形と同じ値を出すことを、UI テスト `tests/ui/run/effects/resume_under_a_handler_of_the_same_effect.em` で確かめる

実装の途中で、ほかにも誤りが出なくなるテストや、新しく誤りになるテスト (上の「ローカル関数とラムダ」の、同じローカル関数を別々の閉じた row の位置に渡す形など) が見つかったら、作る人はコミットの前にこの節に1つずつ足し、理由を書いて、ユーザーの確認を受ける。

### 種類2 (期待値の変更)

次の範囲の期待値は、規則の変更に合わせて書き換えてよい。理由は、row の最小の解が今の row を受けなくなったことと、ローカル関数の row を閉じなくなったことである。

- `crates/eml_types/tests` の `rows.rs`、`check.rs`、`effects.rs`、`linearity.rs`、`yields.rs`、`masks.rs` と、`crates/eml_types/src/table/tests.rs` のうち、row の表示 (`<_>` と `<>`)、`RowYield`、`mask`、診断の位置と文言が変わるもの
- Core IR と LIR の段の出力のスナップショットのうち、instance の名前の row のビット (`<e>` の有無)、`yields` の印、yield の確かめの有無が変わるもの
- UI テスト (`tests/ui/`) と REPL のトランスクリプトのうち、診断の位置と文言が変わるもの (通過と失敗の区分は変えない)
- `crates/eml_vm/tests/bench.rs` の `RunStats` のうち、`state` などの回数が変わるもの

### 足すテスト

- `crates/eml_types/tests`: `State.run` の中の `Yield.fold` に純粋なラムダを渡すと `fold` の具体化の row が `Never` になること、`let` で束縛したラムダを handler の中と外で呼ぶ順序によらず通ること、`g` を呼んでから `(Int -> Int)` に渡す形が通ること、`k` を同じエフェクトの handler の中で呼ぶ形が、推論用の末尾では `mask` なしで、rigid な末尾では `mask` で通ること、呼び出し先が明示したラベルと同じエフェクトの `mask` の残す数 n が正しいこと、`:type fn f -> f ()` の表示が今と同じであること、`(run get).name` の形が E2013 になること (制限の固定)、エフェクト多相な関数に純粋な関数を渡して `File` を持つ形が E3006 にならないこと、引数から後で入ったラベルの型引数が対にした今の row のラベルと単一化されること
- `bench/` に、`State.run` の中で `Yield.fold` に純粋なラムダを渡すプログラムを足し、`crates/eml_vm/tests/bench.rs` で `RunStats` を固定する。`yields` が0であることが完了の条件の確かめになる。名前と要素の数は作る人に任せる
