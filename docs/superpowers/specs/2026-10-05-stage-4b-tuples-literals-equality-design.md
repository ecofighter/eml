# 縦の貫通 段階4b: タプル、リテラルのパターン、等値の設計

位置づけ: 作業用の設計文書。段階4b を終えたら、残す価値のある内容を `docs/spec/`、`docs/implementation/architecture.md`、`docs/implementation/status.md` に移し、この文書は削除する。

## 目的と範囲

[status.md](../../implementation/status.md) の「名前解決以降の実装段階」の段階4b を、HIR、型検査、網羅性の検査、Core IR、インタプリタの全体に通す。

### 4b に含めるもの

- タプルの式 `(a, b)`、型 `(A, B)`、パターン `(x, y)`。パターンは `match`、`let`、ラムダの引数、等式の引数、handler の節の引数に書ける
- `Int` (負の数を含む) と `String` のリテラルのパターン
- `==` と `!=` を `Int`、`String`、`Bool` で使えるようにする。比べ方は型検査が引数の型から決める

### 後に回すもの

- タプルの射影 `t.0`。開いたレコードの row が要るので、名前付きのレコード (S2) と一緒に入れる。今の E0004 のままにする
- `data` の型とタプルの `==`、多相な関数の中の `==`。型クラスの `Eq` の制約がないと書けないので、型クラス (ロードマップ) で扱う
- `String` の順序の比較 (`<` など)。順序は `Int -> Int -> Bool` のまま
- `==` の演算子の参照 `(==)` とセクション `(== 1)`。どちらも段階6で、今は E0004 である

### ユーザーと合意済みの決定

- 等値は「`==` を決まった型でだけ使える」形にする。型ごとの名前の関数 (`string_eq`) にする案は、文字列を `==` で比べられず、型クラスを入れた後も名前の関数が残るので採らない。構造的な多相の `==` (OCaml の `=`) にする案は、関数や継続を比べると実行時エラーになり、将来の型クラスと振る舞いが合わないので採らない。決まった型の `==` は、将来の型クラス `Eq` の `Int`、`String`、`Bool` のインスタンスとしてそのまま引き継げる
- 射影 `t.0` は入れず、タプルはパターンで分解する。線形なタプル (段階5) も分解パターンで扱うので形がそろう
- タプルは、Core IR と実行時でコンストラクタが1つの `data` と同じに表す。決定木、Perceus、verifier、分解 (`take_or_copy`) をそのまま使える

## 1. HIR

### タプル

- 式、型、パターンのタプルの E0004 を外す。

```rust
// ExprKind に追加
Tuple(Vec<ExprId>),

// PatKind に追加
Tuple(Vec<PatId>),

// TypeRefKind に追加
Tuple(Vec<TypeRefId>),
```

- HIR ではタプル専用の種類にし、数字ラベルのレコードへの変換は型検査で行う。名前付きのレコード (S2) を入れるときに、HIR のレコードの形と一緒に作り直す。[直積型とレコード](../../spec/records.md) の「タプルのレコードへの変換は HIR で行う」は、この形に合わせて「型検査で行う」に直す。
- 要素が1つの括弧は今までどおり括弧で、`()` は今までどおり `Unit` である。構文の段階で要素が2つ以上のときだけ `TUPLE_EXPR` などになる。
- `Body` の走査関数 (`walk_child_exprs`、`pat_bindings`、`captures`) に `Tuple` を足す。
- HIR の表示は `(a#0, b#1)` の形にする。

### リテラルのパターン

- `PatKind::Literal(Literal)` を足す。`Int` と `String` を受ける。`-1` のような負の数は、`Literal::Int` の負の値にする。`()` は今の `PatKind::Unit` のままにする。
- 浮動小数と文字のリテラルは、今と同じく字句の段階で E0004 にする。
- `-9223372036854775808` のように、`-` の後の数が `i64` に収まらないパターンは、式と同じく字句の段階で E0007 になる。そのパターンは `Missing` にする。

### 等値

- HIR は変えない。`==` と `!=` は今と同じく組み込み (`Builtin::IntEq`、`Builtin::IntNe`) に解決する。比べる型は型検査が決める。

## 2. 型検査

### タプル

- 式 `(a, b)` は、数字ラベルの閉じたレコード `Record([("0", A), ("1", B)])` の型にする。型の表の `TyShape::Record` と単一化はそのまま使う。
- パターン `(x, y)` は、期待する型を要素の数だけの新しい変数でできたレコードと単一化してから、要素のパターンを検査する。要素の数が違えば E2001 にし、パターンを primary にする。
- 型の注釈 `(A, B)` も同じレコードにする。
- 表示は、ラベルが 0 から連番の閉じたレコードを `(A, B)` と書く ([直積型とレコード](../../spec/records.md))。
- Kind は、今の `kind_bounds` がフィールドの join を取っているので変えない。

### リテラルのパターン

- `Int` と `String` のリテラルのパターンは、それぞれの型を期待する型と単一化する。食い違いは E2001 で、パターンを primary にする。

### 等値

- Prelude の `(==)` と `(!=)` のシグネチャを `a -> a -> Bool` にする。
- 型検査は、`==` と `!=` を参照した位置 (呼ばれる側の `Path` の式) を記録しておく。関数の本体の検査が終わった後に、その位置で具体化した `a` の型を引き、次のように決める。

| `a` の型 | 決まる比べ方 |
|---|---|
| `Int` | `Equality::Int` |
| `String` | `Equality::String` |
| `Bool` (Prelude の `data Bool`) | `Equality::Bool` |
| `Error` を含む | 何も報告せず、表にも入れない |
| それ以外 (`data` の型、タプル、関数型、継続、シグネチャの型変数、決まらなかった変数) | E2006 |

- 決まった比べ方は、`BodyTypes` の新しい表 `equalities: ArenaMap<ExprId, Equality>` に、呼ばれる側の式の ID で入れる。Core IR はこの表から比べ方を選ぶ。

```rust
pub enum Equality {
    Int,
    String,
    Bool,
}
```

- 多相な関数の中の `x == y` (`x : a`) も E2006 になる。型クラスの制約を書けないためで、将来の型クラスで解く。
- 引数の Kind は、`Int`、`String`、`Bool` がどれも `Unr` なので、新しい制約は要らない。
- `<` などの順序は `Int -> Int -> Bool` のままにする。

### 診断

| 番号 | 定数 | 内容 |
|---|---|---|
| E2006 | `NOT_COMPARABLE` | `==` か `!=` で、`Int`、`String`、`Bool` のどれでもない型の値を比べた。演算子を primary にし、比べようとした型をメッセージに出す。note で「`==` で比べられるのは `Int`、`String`、`Bool` である」と伝える |

## 3. 網羅性の検査

- タプルは、要素の数だけのフィールドを持つコンストラクタが1つの型として扱う。コンストラクタの集合はつねにそろっているので、行列を特殊化して調べる。漏れの例は `(Some _, None)` の形で書く。
- `Int` と `String` のリテラルは、spec のとおり無限に値があるものとして扱う ([網羅性](../../spec/exhaustiveness.md))。リテラルだけの列の集合はつねにそろっていないので、残りの行列で調べる。ワイルドカードの行がなければ網羅されておらず、漏れの例はその位置を `_` にする。
- 同じリテラルの2つ目の枝は、1つ目に対して有用でないので E4004 (到達しない枝) になる。
- 変数、`_`、`()`、型の注釈のパターンの扱いは今のままにする。

## 4. Core IR

### タプル

- タプルの値は、引数を持つコンストラクタと同じ `Rhs::Con { tag: 0, args }` にする。結果の変数の名前は `d` である。
- 要素が2つ以上の閉じたレコードの型の変数は boxed にする。`Unit` (`Record([])`) は今の `Atom::Unit` のままで、boxed にしない。
- タプルのパターンは、決定木でコンストラクタが1つの型 (タグ 0、要素の数のフィールド) として扱い、枝が1つの `Switch` (`#0(x, y)`) にする。フィールドの型はレコードのフィールドの型である。
- 枝が1つの `Switch` は、今の規則どおり scrutinee を move で受け取って分解する。B2 は引数のないタグだけを扱うので、タプルの `Switch` には働かない。

### リテラルのパターン

- 決定木で列を選ぶときに、リテラルのパターンもコンストラクタのパターンと同じく候補にする。最初の行でコンストラクタかリテラルのパターンを持ついちばん左の列を選ぶ。
- 選んだ列がリテラルの列なら、その列に上の行から現れる異なるリテラルの順に、比べる命令の連なりを作る。
  1. 出現とリテラルを比べる `prim` (`Int` は `IntEq`、`String` は `StrEq`) の結果を変数に束縛する。`String` のリテラルは比べるたびに `ConstString` で作る。
  2. その `Bool` の値で `Switch` する。`True` の枝は、行列をそのリテラルで特殊化した行列 (その列がそのリテラルかワイルドカードの行だけを残し、列を除く) で決定木を続ける。`False` の枝は、次のリテラルの比較に進む。
  3. 最後のリテラルの `False` の枝は、残りの行列 (その列がワイルドカードの行だけを残し、列を除く) で決定木を続ける。
- 比べる `prim` は引数の所有権を受け取る。後の比較や枝で使う出現は、Perceus が今の規則どおりに `dup` する。
- 残りの行列は最後のリテラルの `False` の枝からだけ届くので、join point にせずにその位置に置く。

### 等値

- `PrimOp` に `StrEq`、`StrNe`、`BoolEq`、`BoolNe` を足す。
- `==` と `!=` の呼び出しは、型検査の `equalities` の表から、`Int` なら `IntEq` / `IntNe`、`String` なら `StrEq` / `StrNe`、`Bool` なら `BoolEq` / `BoolNe` を選ぶ。表に入っていない呼び出しは、誤りのないプログラムには現れない。
- 表示の名前は、`IntEq` と `IntNe` を今の `==` と `!=` のままにし、既存の Core IR のスナップショットを変えない。`StrEq` は `string==`、`StrNe` は `string!=`、`BoolEq` は `bool==`、`BoolNe` は `bool!=` と書く。
- `==` を値として使う形 (演算子の参照とセクション) は今も E0004 なので、`==` を包む関数は作らない。`==` を部分適用する形 (引数が1つの呼び出し) も演算子の構文からは書けない。

## 5. ランタイムとインタプリタ

- ランタイムは変えない。
- インタプリタは、`StrEq` と `StrNe` で2つの文字列を比べ、両方の参照を手放す (ほかのプリミティブと同じく、引数の所有権を受け取る)。`BoolEq` と `BoolNe` はタグを比べる。
