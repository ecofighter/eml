# OxCaml mode system for data-race freedom (prior design for type-level parallel safety)

Scope note: research done 2026-10-10. "Read directly" = I read the primary text (paper PDF via pdftotext, oxcaml.org pages, GitHub source via `gh api`). Items marked (inferred) are my reasoning. Correction to the brief: the POPL 2025 paper "Data Race Freedom à la Mode" is by Georges, Peters, Elbeheiry, White, Dolan, Eisenberg, Casinghino, Pottier, Dreyer (MPI-SWS / Jane Street / Inria), not Lorenzen/Lindley. Lorenzen, White, Dolan, Eisenberg, Lindley wrote the ICFP 2024 paper ("Oxidizing OCaml with Modal Memory Management") on locality/uniqueness/affinity that DRFCaml builds on.

## Q1. What the modes mean, how they combine, and the POPL 2025 result

### Takeaway
A mode is a tuple with one point per independent axis. Values may move only to "greater" (more restrictive) modes. Contention (past) and portability (future) are dual axes that rule out data races. They are linked by capture rules: a closure that captures uncontended state is nonportable. DRFCaml (POPL 2025) proves data-race freedom with a semantic model in Iris/Rocq, and that proof also covers the unsafe-implemented Capsule and RwLock APIs. The deployed OxCaml has since grown more axes (shared/shareable, corrupted/corruptible, forkable, yielding, statefulness, visibility).

### Cited Findings
**Axes in current OxCaml (oxcaml.org "Modes intro", read directly):**
- Locality (future): local > **global** (default global). Contention (past): contended on top; shared and corrupted incomparable; **uncontended** at the bottom. Portability (future): portable; shareable and corruptible incomparable; **nonportable**. Forkable (future): unforkable / forkable, default depends on locality. Uniqueness (past): unique / **aliased**. Linearity (future): once / **many**. Yielding (future): yielding / unyielding, default depends on locality. Visibility (past): immutable; read and write incomparable; **read_write**. Statefulness (future): stateful; reading and writing incomparable; **stateless**. Bold = legacy default — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Past vs. future: a past mode "tracks whether the operation has happened to this value in the past", and a future mode tracks "whether the operation is allowed to happen to this value in the future". Contention, uniqueness and visibility are past axes. Portability, locality, linearity and the others are future axes — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Contention: "A value is contended if another thread can both read and write to it." A shared value can be read by several threads but not written. A corrupted value can be written but not read. An uncontended value is accessible to only one thread — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Portability: "Functions that capture uncontended state are nonportable, so cannot escape the current thread." "Functions that capture shared state are shareable, so may be executed in parallel." "Functions that capture all values at contended are portable, so may execute concurrently." Closures that capture only corrupted values are corruptible — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Statefulness: "a future axis that tracks whether a function reads or writes to some mutable state that it closes over" (stateless / reading / writing / stateful). Visibility: "a past axis that controls access to mutable portions of values". Unlike contention, it blocks even thread-safe access — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Forkable: "tracks whether a function is permitted to access shared values in its parent stack". Yielding: tracks whether a function may perform effects that a handler in its parent stack will handle. Global values default to forkable and unyielding; local values default to unforkable and yielding — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Linearity: "A closure that captures a unique value is once" — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Submoding: values "may move freely to greater modes ... but not to lesser modes". Modes are deep, and "OxCaml's modality feature cuts off the deepness of a mode; modalities can be placed on record and constructor fields" (syntax `'a @@ m`) — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/)
- Modality semantics: on future axes a field modality acts as a `min` with the record's mode, and on past axes as a `max`. Contention and portability are "diamond-shaped lattices". For example, the join of corrupted and shared is contended, and the meet of shareable and corruptible is portable — [OxCaml modes reference](https://oxcaml.org/documentation/modes/reference/)
- Mode crossing: per-type escape from axes. Immutable data crosses contention, types without functions cross portability, and `int` crosses locality. Syntax `type t : value mod contended portable` — [OxCaml modes intro](https://oxcaml.org/documentation/modes/intro/); [OxCaml modes reference](https://oxcaml.org/documentation/modes/reference/)

**The DRFCaml paper (POPL 2025, read directly from PDF):**
- Abstract: DRFCaml "guarantees data race freedom for multi-threaded OCaml programs while retaining backward compatibility with existing sequential OCaml code". It introduces "two new mode axes, contention and portability", and the basic system "has limited expressive power by itself" but expresses Capsule and reader-writer-lock APIs. Soundness comes from "a semantic model ... in the Iris program logic on top of the Rocq proof assistant" — [Georges et al., POPL 2025 PDF](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf); [POPL'25 page](https://popl25.sigplan.org/details/POPL-2025-popl-research-papers/23/Data-Race-Freedom-la-Mode) (distinguished paper per search snippet)
- The paper version has 5 axes and orders contention as uncontended ≤ shared ≤ contended. "A reference can be written only if it is uncontended, and can be read only if it is shared or uncontended." Portability is portable ≤ nonportable — [paper §2.4](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Cross-axis rule: "a closure that captures an uncontended or shared value ... must be nonportable", equivalently "the free variables of a portable closure must be contended". The paper explains why even read-only *shared* capture is forbidden: `let y @ shared = x in Thread.create (fun () -> !y)` must be rejected because the parent can still write through the uncontended alias `x`. The paper notes that "portable closures are seriously restricted: they cannot have any access to mutable references from their environment" — [paper §2.4](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Legacy mode: `(global, many, aliased, nonportable, uncontended)`. All legacy OCaml code typechecks at it — [paper §2.5](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Typing duality used by context "locks": once† = unique, many† = aliased, nonportable† = uncontended, portable† = contended. `fork(e)` requires the closure to be global and portable — [paper §4.2](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Atomic references: "always global, many, aliased, portable, and contended" contents, and they can be accessed even when contended. The paper calls this "very restrictive, but necessary" because atomics transfer values across threads — [paper §4.4](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Two kinds of non-atomic reference (portable and nonportable), because letting a reference's own mode govern its contents "would effectively give us covariant references, which are unsound" — [paper §2.6](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- **How soundness is argued**: (1) The operational semantics has a built-in race detector. Each memory slot carries a lock state, and non-atomic accesses take two steps (na1/na2), so a racing access gets stuck. Theorem 3.1 ("No Crash Implies No Race") says that if no reachable configuration is stuck, no reachable configuration has a race. (2) An Iris weakest-precondition program logic with adequacy gives Corollary 3.1: `⊢ wp e {Φ}` implies no data race. (3) A logical relation (semantic typing) gives Compatibility (Thm 5.1), then the Fundamental Theorem (5.2), then "Semantically Typed Expressions are Data Race Free" (5.3). (4) The Capsule and RwLock APIs are implemented with `Obj.magic` and unsafe mode casts, and are proven *semantically* well-typed (Thms 6.1, 6.2). "All results in this paper have been mechanized in Rocq." The method follows RustBelt — [paper §1.2-1.3, §3, §5, §6](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- The paper says the proof of Thm 5.1 is "inherently extensible": new APIs can be added by proving them semantically sound — [paper §5](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Follow-up (ICFP 2026, "Mode Crossing", Peters, Jacobs, Kalinichenko, Stevenson, Smith, Dreyer, Eisenberg): under the POPL rules, "mode-checking rules must be uniformly sound for all types and are therefore pessimistic". An immutable `int iarray` passed to `fork_join2` must be annotated `@ portable` everywhere. The paper adds mode crossing plus *modal kinds*, interpreted "as monotone functions on a lattice of modes", with soundness verified "in Rocq on top of Iris" by building on the DRFCaml model. Its formal core (SMoKi) does not cover all axes, the full module system, or GADTs. The implementation handles GADTs "conservatively" — [Mode Crossing PDF](https://people.mpi-sws.org/~bpeters/papers/mode-crossing.pdf); [ICFP'26 page](https://icfp26.sigplan.org/details/icfp-2026-icfp-papers/9/Mode-Crossing)

### Inferences
- The axis set has grown since POPL 2025. The paper has 3 contention points and 2 portability points; current OxCaml has diamonds (shared/corrupted, shareable/corruptible) plus forkable, yielding, statefulness and visibility. The paper's rule that shared capture makes a closure nonportable was refined into a separate "shareable" point. Shareable closures may run in parallel under structured fork/join (see Q2), presumably because the structured API controls what the parent may do meanwhile (inferred; I did not find a formal account of shareable in a paper).
- Statefulness is effectively an *effect* axis on functions: it records whether calling the function reads or writes captured mutable state. It is the axis closest to eml's "row contains Heap h" (see Q5).

### Gaps
- I found no published formal soundness proof covering the newer axes (shareable, corrupted, forkable, yielding, statefulness/visibility). The Mode Crossing paper says SMoKi covers only the axes in Georges et al.
- The ICFP 2024 Lorenzen et al. paper was not fetched. I know of it only through the DRFCaml paper's citation [21].

## Q2. The Parallel library and effects/continuations under modes

### Takeaway
`Parallel.fork_join2` takes `shareable` closures; the first is also `forkable` (it cannot capture capsule passwords). Parallel tasks may therefore read but not write their environment. Effect handlers in OxCaml carry a `Handler.t @ local` capability, and the yielding axis tracks whether a function may perform to a parent-stack handler. Jane Street's `handled_effect` library gives statically one-shot (`unique`) continuations. In its `Portable` variant the continuations are portable and *can be resumed on a different domain*, which a test shows.

### Cited Findings
- `fork_join2` argument modes (README, oxcaml branch): first closure `(t @ local -> 'a) @ forkable local once shareable`, second `(t @ local -> 'b) @ once shareable`, result an unboxed pair `#('a * 'b)`. The closures are "shareable, so can capture both shared and uncontended references" and "[f] is also [forkable], so cannot capture capsule passwords". The README says subtasks may read but not mutate the environment, and the leftmost exception is re-raised after both finish — [janestreet/parallel](https://github.com/janestreet/parallel)
- `with_parallel : ?max_workers:int -> (Parallel_kernel.t @ local -> 'a) @ once`. Schedulers are `Parallel.Sequential` and `Parallel_scheduler` (work-stealing deques). Creating one is "an expensive operation" — [janestreet/parallel](https://github.com/janestreet/parallel)
- The ICFP 2026 paper's illustrative (simplified) signature is `val fork_join2 : (unit → 'a) @ portable → (unit → 'b) @ portable → 'a * 'b`: "Functions are portable if they can be executed in parallel without introducing data races: they neither access unsynchronized shared mutable state themselves nor call functions that do." — [Mode Crossing PDF](https://people.mpi-sws.org/~bpeters/papers/mode-crossing.pdf)
- OxCaml stdlib `Effect` (read from `stdlib/effect.mli`): `Handler.t` "at mode local is proof that the current function is running within an effect handler". `Safe.perform : Handler.t @ local -> 'a t -> 'a`. `Deep.Safe.match_with : (Handler.t @ local -> 'c -> 'a) @ unyielding -> ...`. The stdlib `continue` still raises `Continuation_already_resumed` at runtime. A `Preemption` effect and preemptible handlers (`Domain.Tick`) exist and are marked unfinished — [oxcaml/oxcaml stdlib/effect.mli](https://github.com/oxcaml/oxcaml/blob/main/stdlib/effect.mli)
- The OxCaml compiler lowers the yielding mode to a `Lambda.yielding_kind` (`Unyielding` / `May_yield`) on applications. The `@ yielding` mode appears on `Handler.t` in `stdlib/effect.ml` — [oxcaml/oxcaml lambda/translmode.ml (code search)](https://github.com/oxcaml/oxcaml/blob/main/lambda/translmode.ml)
- `handled_effect` ("Typed algebraic effects for OxCaml"): the stdlib interface "is not effect-safe". OxCaml's `local` mode tracks whether a handler is installed: "Each effect handler can be represented as a `local` argument, which is needed to perform its operations", and functions taking local functions are effect-polymorphic — [janestreet/handled_effect README](https://github.com/janestreet/handled_effect)
- `handled_effect` interface: `type (-'a, +'b, 'es) Continuation.t : value mod contended many`. `continue : ('a,'b,'es) Continuation.t @ unique -> 'a @ once unique -> 'es Handler.List.t @ local -> 'b @ once unique`. `Continuation_already_resumed` is "Only achievable with [Obj.magic_unique] or similar escape hatches", so one-shotness is static. Each effect has `Contended` (mode instance portable/nonportable) and `Portable` (portable/portable) submodules. The signature is "not a truly mode-polymorphic signature. Only select instances may be used, and each instance requires its specific result type for soundness." — [handled_effect intf (raises_in_jsoo/handled_effect_intf.ml)](https://github.com/janestreet/handled_effect/blob/oxcaml/raises_in_jsoo/handled_effect_intf.ml)
- Test "portable continuations": the test builds `Eff.Portable.fiber`, stores the continuation (`@@ portable`) in a `Unique.Atomic`, and resumes it from 10 successively spawned domains. The expected output is "Jump! Now in domain 1 ... domain 10" — [handled_effect test/portable.ml](https://github.com/janestreet/handled_effect/blob/oxcaml/test/portable.ml)
- Test "cross capsule data sharing": an effect performed from inside a `Capsule.Prim.Data.iter` callback, via `Eff.Contended.perform`, carries data out of a capsule to a handler outside it — [handled_effect test/cross_capsule.ml](https://github.com/janestreet/handled_effect/blob/oxcaml/test/cross_capsule.ml)
- A search snippet from an OxCaml changelog says "effect-handler cases force the function nonportable/stateful". I could not open the primary page, so this is unverified — (search result only; no URL confirmed)
- A Jane Street engineer (ColinMelendez, Aug 2026) says they are "statically guaranteeing that effects are handled ... using modes", which is "not fully typed effects" — [discuss.ocaml.org thread](https://discuss.ocaml.org/t/whats-the-status-of-typed-effects/18439)
- The 2023 Jane Street blog said they were "exploring modal representations for algebraic effects" as future work — [Jane Street blog, Oxidizing OCaml: Data Race Freedom (2023-09-01)](https://blog.janestreet.com/oxidizing-ocaml-parallelism/)

### Inferences
- OxCaml does *not* forbid effects across threads in a blanket way. Instead: (a) handler capabilities are `local`, so a closure performing to an enclosing handler is local and therefore cannot be passed to `fork`, which needs global. (b) Yielding/forkable defaults tie "may perform to a parent-stack handler" and "may touch the parent's shared values" to locality. (c) A suspended continuation is an ordinary value whose portability follows from the portability of the computation it was built from. In eml terms, OxCaml permits migrating a one-shot continuation to another thread when the captured computation is portable. That is strictly more permissive than eml's `par` requiring `Row<Never>`, which allows no resumptions.
- The `local` handler-capability encoding is capability-passing (like Effekt, or "effects as capabilities") rather than row typing. Effect polymorphism comes from local-function polymorphism instead of row variables.

### Gaps
- Parallel arrays/sequences, `Atomic`, and the parallel library's internal use of effects (if any) are not documented in the README. I did not read the source.
- I found no formal treatment, paper or proof, of yielding/forkable or of portable continuations.

## Q3. How mutable references are made safe (capsules, keys, contended)

### Takeaway
The core rule is a mode-level AXM: write requires uncontended, read requires uncontended or shared, and contended mutable fields are inaccessible. Sharing mutable state requires capsules. A capsule is a brand `'k` with a uniquely owned key or a local password, and these permissions pass between threads via a runtime mutex or rwlock. The capsule API is implemented unsafely and proven sound semantically.

### Cited Findings
- Paper Capsule API: `Key.create : unit -> packed @ unique` (existential brand `'k`). `Data.map : 'k Key.t @ unique -> ('a -> 'b) @ local once portable -> ('a,'k) t -> 'k Key.t * ('b,'k) t @@ aliased @ unique`. `map_shared` takes `'k Key.t @ local` (aliased) and gives a read-only `portable shared` view. "If a thread has unique ownership of the key, it can mutate the shared data ... If a thread merely possesses an aliased key, it can obtain only read access." Inspired by GhostCell — [paper §1.2, Fig. 3](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Callbacks run inside a capsule must be `portable`, which is the key restriction. Paper §2.9 limitation: modules with "static mutable state" (mutable state hidden in closure environments) cannot be portable, so they cannot be used inside capsule callbacks; the paper calls this "fundamental and intentional". Libraries must be annotated with portable/shared, which may require "multiple versions of the same signature for each mode use case". Mode polymorphism is proposed as the fix — [paper §2.9](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Current OxCaml "expert" capsule API (oxcaml.org): `('a,'k) Capsule.Data.t` crosses portability and contention. `'k Capsule.Access.t` does not cross contention ("`unwrap` requires an `uncontended` access"). `'k Capsule.Password.t` crosses contention but "always `local`", so it cannot reach another domain. `'k Capsule.Key.t` is "the capsule itself", and `with_password` requires it unique. `'k Capsule.Mutex.t`: "at runtime ... will enforce that only one domain at a time can access `'k`", and it is shareable freely. `Data.map : password:'k Password.t @ local -> f:('a -> 'b) @ local once portable -> ...`. Rwlock is "Coming Soon". A newer WIP API lives in `Portable.Capsule` — [OxCaml capsules](https://oxcaml.org/documentation/parallelism/capsules/)
- Lazy values: forcing "requires the lazy value to be `uncontended`". Exception constructors are tied to the capsule that defined them — [OxCaml modes reference](https://oxcaml.org/documentation/modes/reference/)
- Earlier design (2023 blog) used a single `sync`/`unsync` mode, exclusive mutability, and mutexes over `unique sync` values. Keys "take zero bits to store, and don't have to exist at runtime at all" — [Jane Street blog 2023](https://blog.janestreet.com/oxidizing-ocaml-parallelism/)

### Inferences
- The capsule brand `'k` is structurally the same device as eml's `Heap h` region variable with rank-2 `run_heap` (`ST`-style). A capsule additionally separates the *permission* (key, password, access) from the *data pointer*, so the data pointer can be freely portable while the permission is unique, local, or mutex-guarded. eml's `Ref h a` together with the `Heap h` row combines the data pointer and the permission in one place: permission = row membership.

### Gaps
- Not checked: the Rwlock implementation status in 2026, and the details of `Portable.Capsule`.

## Q4. Runtime checks that remain, and testing

### Takeaway
The guarantee is static. What remains at runtime: mutex/rwlock locking, atomics, the stdlib one-shot continuation check (statically removed in `handled_effect`), and the runtime cost of the capsule primitives, which have no keys at runtime. Upstream OCaml ≥5.2 ships ThreadSanitizer as an opt-in dynamic detector. In OCaml a race cannot break type/memory safety; it is a correctness concern only.

### Cited Findings
- Parallel README: data-race freedom is enforced at compile time, and "portable functions do not close over unprotected mutable state" — [janestreet/parallel](https://github.com/janestreet/parallel)
- The capsule mutex is the runtime enforcement point — [OxCaml capsules](https://oxcaml.org/documentation/parallelism/capsules/)
- OCaml memory model: races "never invalidate type safety", but cause nondeterministic bugs (counter example printed 118533 instead of 200000) — [Jane Street blog 2023](https://blog.janestreet.com/oxidizing-ocaml-parallelism/); the paper says OCaml races have "well-defined semantics" — [paper §1.1](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Stdlib continuations still raise `Continuation_already_resumed` dynamically — [oxcaml stdlib/effect.mli](https://github.com/oxcaml/oxcaml/blob/main/stdlib/effect.mli). In `handled_effect`, this is reachable only via `Obj.magic_unique` — [handled_effect intf](https://github.com/janestreet/handled_effect/blob/oxcaml/raises_in_jsoo/handled_effect_intf.ml)
- TSan: OCaml 5.2 added ThreadSanitizer support (configure `--enable-tsan`), with a 2-7x slowdown per the release announcement, and a small chance of missing simultaneous accesses — [OCaml manual 5.2, TSan](https://ocaml.org/manual/5.2/tsan.html); [OCaml 5.2.0 release](https://discuss.ocaml.org/t/ocaml-5-2-0-released/14638)
- Known soundness hole: first-class modules do not yet account for the portability/contention of extension constructors defined inside them — [OxCaml modes reference](https://oxcaml.org/documentation/modes/reference/)

### Inferences
- OxCaml's design leans on GC: the runtime never needs to know whether an object is shared. eml uses Perceus RC, so a race on a non-atomic refcount is a *memory-safety* bug, not merely a logic bug. eml's runtime "mark shared before publishing" step (atomic RC) is therefore a load-bearing runtime half of the guarantee with no counterpart in OxCaml. That is a real asymmetry: OxCaml's types alone suffice for its goal, while eml's types must be paired with a correct share-marking runtime.

### Gaps
- No source found on whether Jane Street runs TSan on OxCaml code or in OxCaml's CI, or on whether OxCaml supports `--enable-tsan`.

## Q5. Limitations, ergonomics, and comparison to eml's effect-row restriction (plus Rust and Pony)

### Takeaway
OxCaml's main costs are annotation burden (needing portable or shared versions of library signatures, and redundant `@ portable` on immutable data) and the restriction that portable code cannot touch any captured unsynchronized mutable state. Mode crossing and modal kinds were added in production to relieve the annotation burden. OxCaml tracks what a closure *captures* (coeffect-like). eml tracks what a function *does* (effect row). The two line up most closely through OxCaml's statefulness axis and through "contended ref ≈ Ref h a without Heap h in the row".

### Cited Findings
- Annotation burden was "a major usability issue" in Jane Street's 80M-line codebase: "redundant annotations pollute type signatures and burden callers". By February 2026 there were ~6,000 modal-kind annotations, "added only when needed to fix concrete type errors". Without mode crossing, the annotation burden "would simply be impractical in a large codebase" — [Mode Crossing PDF §1, §5](https://people.mpi-sws.org/~bpeters/papers/mode-crossing.pdf)
- Paper limitations: no mode polymorphism (needed to avoid duplicated signatures), capsule callbacks that must be global in some APIs, and `local` too coarse compared with Rust lifetimes. The paper also states DRFCaml type/mode inference "remains to be demonstrated and evaluated in future work" — [paper §2.1, §2.9, §7](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- `handled_effect` must hand-instantiate mode combinations because the signature is "not a truly mode-polymorphic signature" — [handled_effect intf](https://github.com/janestreet/handled_effect/blob/oxcaml/raises_in_jsoo/handled_effect_intf.ml)
- Paper's own placement: capturing types "decorate closures with sets of variables to keep track of which capabilities each closure has access to", while reachability types "track the reachable set of a function's free variables rather than tracking the effect of using them". "DRFCaml does not express purity (portable closures may still atomically mutate data)". Portability of a function is independent of its arguments' modes, so `map` can be portable while taking a nonportable function — [paper §7](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Paper vs. structured-parallelism systems: capturing/reachability-type calculi rely on "structured fork-join to regain mutable access", whereas "DRFCaml prevents data races even in the presence of unstructured concurrency" (Thread.create, rwlocks) — [paper §7](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)
- Rust: the paper frames Rust as enforcing "aliasing XOR mutability" via ownership. Its cost is that "the Rust programmer must think about ownership of data at a fine granularity". DRFCaml's contention/portability enforce "a variant of Rust's AXM discipline" only for data that crosses threads, and only in a "pay as you go" manner — [paper §1](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf). (Background, not re-fetched: Rust's `Send`/`Sync` are auto-traits on types, i.e. a property of the type rather than of a use-site mode, and `T: Sync ⇔ &T: Send` — [Rustonomicon, Send and Sync](https://doc.rust-lang.org/nomicon/send-and-sync.html).) The 2023 blog contrasts OxCaml's capsules with Rust's ownership, which "results in complicated code, especially in the presence of concurrency" — [Jane Street blog 2023](https://blog.janestreet.com/oxidizing-ocaml-parallelism/)
- Pony / Verona: the paper cites Reggio/Verona reference capabilities and "view adaptations" as resembling DRFCaml's modes and context locks, and Milano et al.'s `iso` regions. (Background, not re-fetched: Pony's six reference capabilities `iso, trn, ref, val, box, tag` annotate each reference; only `iso`, `val`, `tag` are sendable between actors — [Pony tutorial, reference capabilities](https://tutorial.ponylang.io/reference-capabilities/).) — [paper §7](https://iris-project.org/pdfs/2025-popl-drfcaml.pdf)

### Inferences
Comparison with eml (all inferred):
- **Capture-based vs. effect-based.** OxCaml: a closure is nonportable if it *captures* uncontended mutable state. eml: a function cannot be passed to `par` if its latent row *uses* `Heap h` (or any resuming op). These coincide for "closure over a ref that it reads or writes". They differ in two ways. (1) OxCaml flags capture even if the ref is never used, unless the value is downgraded to contended at capture time; that downgrade is allowed. (2) eml flags use even without capture, e.g. a function that receives a `Ref h a` as an argument and writes it; in OxCaml that argument's mode would instead be checked at the call. OxCaml's *statefulness* axis ("reads or writes mutable state that it closes over") is the closest analogue to eml's row membership, but it is still capture-scoped.
- **Contended ≈ ref without its row.** An OxCaml portable closure may capture a ref at `contended`, but it cannot read or write it. In eml, a `par` thunk may capture a `Ref h a` value, but with `Heap h` absent from its row it cannot dereference it. Both separate "holding the pointer" from "permission to access". In OxCaml the permission is a past mode on the value, while in eml it is a capability in the computation's row. eml's single dimension (row) thus does the work of OxCaml's two dual axes (contention, past, on data; portability, future, on closures), because eml stores no mutable state outside `Heap h`. OxCaml must handle legacy code that mutates arbitrary fields anywhere, so it needs the per-value contention mode.
- **Read sharing.** OxCaml has `shared`/`shareable` and capsule `map_shared` (aliased key, read-only), so parallel tasks may *read* parent mutable state under structured fork_join. With `par` requiring `Row<Never>`, eml forbids even read-only `Heap h` access in parallel branches, assuming Heap's get is a resuming op. Read sharing is a known expressiveness gap that OxCaml chose to fill with an extra lattice point.
- **Effects across threads.** eml forbids any resuming op inside `par` and uses closed rows for `spawn`. OxCaml (via `handled_effect.Portable`) allows a portable fiber's unique continuation to be resumed on another domain. If eml ever wants to migrate continuations (work-stealing schedulers implemented with effects), OxCaml's "continuation portability = portability of its computation, plus static one-shotness via uniqueness" is a direct prior design. eml already has Lin kinds, which could play the `unique`/`once` role.
- **Shared mutable state.** eml has no counterpart to capsules plus mutex. A capsule-like extension for eml could be a `Heap h` whose permission (the right to run handlers for h) is transferred through a lock, i.e. "run_heap under a mutex". OxCaml's proof strategy (an unsafe implementation proven semantically sound in an Iris logical relation) is the template for justifying such a primitive.
- **Soundness methodology split.** OxCaml: syntactic type/mode system, plus a few trusted unsafe APIs, each proven semantically well-typed in a RustBelt-style Iris model with a race-detecting operational semantics. For eml, an analogous plan would be a race-detecting semantics for the Core IR or interpreter plus a logical relation in which "row ⊆ Row<Never> ∧ closed" implies no access to non-atomic heap cells. The runtime share-marking for RC would also have to be modelled, since it is a safety obligation in eml (see Q4).
- **Rust/Pony positioning.** Rust and Pony attach the thread-safety property to *types or references* (`Send`/`Sync` auto-traits; Pony's per-reference capabilities). OxCaml attaches it to *modes on values and closures*, orthogonal to types, with per-type crossing via modal kinds. eml attaches it to *effect rows of computations*. eml's choice avoids a new kind dimension, but the price is that "data at a type is safe to share" cannot be expressed independently of the computation. OxCaml found that pricey enough to add modal kinds, though in eml immutable data is always shareable, so the need may be smaller.
