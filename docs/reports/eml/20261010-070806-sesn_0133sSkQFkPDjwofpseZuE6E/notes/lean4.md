## Q1. How `lean_mark_mt` works, and where it is called

### Takeaway
An object's 32-bit `m_rc` sign encodes its kind: >0 means single-threaded (ST, non-atomic RC), <0 means thread-shared (MT, atomic RC stored negated), 0 means persistent (no RC). `lean_mark_mt` is an iterative DFS with an explicit stack. It flips each reachable ST object to MT, and it does not descend below an object that is already shared or persistent. Its callers are the runtime primitives that hand a value to another thread: task creation (spawn/map/bind), task and promise resolution, MT or global `ST.Ref` writes, thunk forcing, and the explicit `Runtime.markMultiThreaded`.

### Cited Findings
**Header and sign convention (read directly)**
- `lean_object` is `{ int m_rc; unsigned m_cs_sz:16; unsigned m_other:8; unsigned m_tag:8; }`. The header comment says: "The reference counter `m_rc` field also encodes whether the object is single threaded (> 0), multi threaded (< 0), or reference counting is not needed (== 0). We don't use reference counting for objects stored in compact regions, or marked as persistent." — [lean.h L143-179 @5e96ee1](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/include/lean/lean.h#L143-L179)
- The predicates are `lean_is_mt(o)` = `rc < 0`, `lean_is_st(o)` = `rc > 0` and `lean_is_persistent(o)` = `rc == 0`. — [lean.h L631-645](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/include/lean/lean.h#L631-L645)
- An MT count is stored negated, so an MT increment is `atomic_fetch_sub(..., n, memory_order_relaxed)`. The inline `lean_inc_ref_n` takes the ST path (`if (LEAN_LIKELY(lean_is_st(o)))`) with a plain add, and otherwise does the atomic fetch_sub only if `lean_is_unstuck_mt(o)`. — [lean.h `lean_inc_ref_n` ~L705-725](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/include/lean/lean.h#L705-L725)
- `lean_dec_ref` checks `if (rc > 1) rc -= 1 (non-atomic); else if (rc != 0) lean_dec_ref_cold(o)`. MT counts are negative, so they always take the cold path. `lean_dec_ref_cold` frees immediately when `rc == 1` (the ST last-reference case). Otherwise it returns if the object is never-freed (persistent or sticky), and then does `atomic_fetch_add(..., 1, memory_order_acq_rel)` and frees only if the old value was `-1`. — [lean.h `lean_dec_ref` ~L733](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/include/lean/lean.h#L733-L740); [object.cpp `lean_dec_ref_cold` L455-471](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/object.cpp#L455-L471)
- `lean_is_exclusive(o)` returns `rc == 1` only for ST objects and **returns `false` for every MT object**. `lean_is_shared` likewise returns false for MT objects. — [lean.h L776-794](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/include/lean/lean.h#L776-L794)

**`lean_mark_mt` algorithm (read directly)** — [object.cpp L639-720](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/object.cpp#L639-L720)
- It compiles to a no-op without `LEAN_MULTI_THREAD` (`#ifndef LEAN_MULTI_THREAD return;`).
- Early exit: `if (lean_is_scalar(o) || !is_unshared(o)) return;`. `is_unshared(o)` is `rc > 0 || rc <= LEAN_RC_STUCK_ST`, that is, ST or an ST count that overflowed into the sticky band.
- Traversal: a `buffer<object*> todo` worklist (iterative, no recursion). For each popped non-scalar `is_unshared` object it sets the count to `-rc`, or freezes it at `LEAN_RC_STICKY` when `rc < 0 || -rc <= LEAN_RC_STICKY_DROP`. It then pushes children by tag:
  - constructor (`tag <= LeanMaxCtorTag`): all boxed fields (`lean_ctor_obj_cptr` .. `+lean_ctor_num_objs`)
  - `LeanClosure`: the fixed (captured) args only (`lean_closure_arg_cptr`, `lean_closure_num_fixed`)
  - `LeanArray`: all elements
  - `LeanThunk`: `m_closure` if non-null and `m_value` if non-null
  - `LeanRef`: `m_value` if non-null
  - `LeanTask`: `lean_task_get(o)`, the task's value
  - `LeanPromise`: its `m_result` task
  - `LeanExternal`: it calls the external class's `m_foreach(data, mark_mt_fn)`, a user-supplied callback that visits children
  - `LeanScalarArray`, `LeanString`, `LeanMPZ`: leaves
- Already-MT or persistent objects are skipped together with everything below them. This relies on the invariant "MT/persistent objects only point to MT/persistent objects" (see Q2).
- `lean_mark_persistent` ([object.cpp L567-635](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/object.cpp#L567-L635)) has the same traversal shape. It sets `rc = 0` on every object with `lean_has_rc` and also calls `__lsan_ignore_object` under ASan. It runs on `g_array_empty`, on the stdin/stdout/stderr stream objects ([io.cpp L1658-1662](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/io.cpp#L1658-L1662)), and on initialized globals ([object.cpp ~L2934](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/object.cpp#L2930-L2936)).

### Inferences
- The `LeanTask` case of `mark_mt` calls `lean_task_get`, which blocks until the task finishes. Only ST tasks reach that case, and ST tasks are created only by `lean_task_pure`, which already has `m_value`. So in practice the case never blocks. (Inferred from `alloc_task` overloads; not stated in a comment.)
- Marking happens on the **sender** thread while the graph is still only reachable from it, before the publishing store, which happens under a mutex or via an atomic. This matches eml's planned "mark shared before publishing in runtime primitives on the sender thread". Lean has no compiler/IR-level MT instruction: all marking lives in a small set of C++ runtime primitives, and grep over `src/Lean/Compiler/IR` found no `mark_mt`.
- The `m_foreach` hook for external objects is a trust point. A foreign object whose `foreach` misses a child silently breaks the invariant.

### Gaps
- I did not check whether the `Std.Sync` primitives (Mutex, Channel, etc.) add their own `mark_mt` calls. They appear to build on `IO.Ref`/`Promise`/`Task` (not verified), and grep over `src/runtime` found no other call sites.

## Q2. What "Counting Immutable Beans" says about MT marking, cost and correctness

### Takeaway
Section 7.2 introduces the ST/MT/persistent tag and the invariant "persistent → only persistent; MT → only MT or persistent; ST → anything". It argues that the unsynchronized tag test is sound because the tag changes only before a value is shared, and that markMT visits each value at most once. An ablation (`-ST` = atomic RC everywhere) shows a 1.13x-2.31x slowdown on single-threaded benchmarks. There is no formal proof for the MT part: the formal treatment (λpure → λRC) is single-threaded.

### Cited Findings
- On the earlier approach: "This approach has been used in the previous version of the Lean compiler, and we have observed that the memory fences have a significant performance impact even when only one thread is being executed. This is quite unfortunate because most values are only touched by a single execution thread." It describes the standard scheme as relaxed fetch_add for increments, plus release on decrement and acquire before the deletion check. — [Ullrich & de Moura, IFL'19, §7.2](https://arxiv.org/abs/1908.05647)
- Invariant: "Our runtime enforces the following invariant: from persistent values, we can only reach other persistent values, and from multi-threaded values, we can only reach persistent or multi-threaded values. There are no constraints on the kind of value that can be reached from a single-threaded value. By default, values are single-threaded, and our runtime provides a markMT(o) procedure that tags all single-threaded values reachable from o as multi-threaded." — [paper §7.2](https://arxiv.org/abs/1908.05647)
- Call points in the paper: "This procedure is used to implement Task.mk f and Task.bind x f. We use markMT(f) and markMT(x) to ensure that all values reachable from these values are tagged as multi-threaded before we create a new task, that is, while they are still accessible from only one thread." — [paper §7.2](https://arxiv.org/abs/1908.05647)
- Cost argument: "Our invariant ensures that markMT does not need to visit values reachable from a value already tagged as multi-threaded. Thus values are visited at most once by markMT during program execution. Note that task creation is not a constant time operation in our approach because it is proportional to the number of single-threaded values reachable from x and f. This does not seem to be a problem in practice, but if it becomes an issue we can provide a primitive asMT g that ensures that all values allocated when executing g are immediately tagged as multi-threaded." — [paper §7.2](https://arxiv.org/abs/1908.05647)
- Soundness of the unsynchronized tag test: "The reference counting operations perform an extra operation to test the value tag and decide whether a memory fence is needed or not. This additional test does not require any synchronization because the tag is only modified before a value is shared with other execution threads." — [paper §7.2](https://arxiv.org/abs/1908.05647)
- Generalization advice: "The approach above can be adapted to more complex libraries for writing multi-threaded code. We just need to identify which functions may send values to other execution threads, and use markMT." — [paper §7.2](https://arxiv.org/abs/1908.05647)
- Ablation, Fig. 6, "`-ST` uses atomic RC operations for all values", run time normalized to base: binarytrees 1.22, deriv 1.42, const_fold 1.23, parser 1.68, qsort 1.13, rbmap 1.71, rbmap_10 2.43 (base 1.49), rbmap_1 8.02 (base 4.72), unionfind 2.31. Geometric mean: base 1.24 vs -ST 1.89. binarytrees is the only parallel benchmark (it uses `Task`). — [paper §8, Fig. 6](https://arxiv.org/abs/1908.05647)
- Related work: Ungar et al. 2017 tag Swift objects possibly shared between threads with one bit, "much like our approach. However, because of mutability, every single store operation must be intercepted to (recursively) tag objects before becoming reachable from an already tagged object." Choi et al. 2018 (biased RC) avoid tagging by storing the owning thread ID and two counters. — [paper §9](https://arxiv.org/abs/1908.05647)

### Inferences
- The paper's correctness argument is informal and has two parts: (1) the invariant is closed under markMT and immutable construction; (2) a value's tag is written only while a single thread owns it. Lean can avoid Swift's write barrier because values are immutable. The mutable cells (`ST.Ref`, thunk, task result) are exactly where the runtime has to re-mark (Q1, Q4), and these are Lean's equivalent of Swift's "intercept every store".
- For eml, linear types and effect rows could play the role that immutability plays for Lean: they would restrict where a store can create an MT → ST edge.

### Gaps
- The paper gives no per-operation cost (cycles) for the sign check. Its only data is the whole-program ablation above (2019 hardware: the setup section mentions Ubuntu 18.04 and Clang 9).

## Q3. The IR interpreter and threads

### Takeaway
The IR interpreter (`src/library/ir_interpreter.cpp`) uses the same runtime objects and RC functions as compiled code, so MT safety for interpreted code comes entirely from the runtime marking described above. Interpreter state is per-thread: a `LEAN_THREAD_PTR` holds the current interpreter, and a fresh `interpreter` instance is built when a closure is called on another thread or in another context. Shared global state is limited to a native-symbol cache guarded by a `std::shared_mutex` and an init-globals map that the code assumes is never written concurrently. Interpreted code therefore can run concurrently on multiple task threads.

### Cited Findings
- Header comment (Sebastian Ullrich): "A simple interpreter for evaluating λRC IR code" that "reuse[s] the existing compiler IR instead of inventing something like a new bytecode format". It keeps a "homogeneous stack of `value`s, which are either unboxed values or pointers to boxed objects", and switches to native code via dlsym when possible, always calling the "boxed" versions of native functions. — [ir_interpreter.cpp L1-28](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/library/ir_interpreter.cpp#L1-L28)
- Per-thread interpreter: `LEAN_THREAD_PTR(interpreter, g_interpreter);`. `interpreter::with_interpreter(env, opts, fn, f)` reuses `*g_interpreter` only when its env and opts are pointer-equal (`is_eqp`). Otherwise it constructs a new `interpreter interp(env, opts)` and installs it via `flet`. The comment there reads "We changed threads or the closure was stored and called in a different context." and "the caches contain data from the Environment, so we cannot reuse them when changing it". — [ir_interpreter.cpp L366, L436-448](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/library/ir_interpreter.cpp#L366-L448)
- Interpreter-local state: an arg stack, a join-point stack, a call stack, `m_constant_cache` (values of nullary constants), and `m_symbol_cache`. The comment on the symbol cache says that "as local IR can be backtracked, this cache needs to be local as well". — [ir_interpreter.cpp L368-410](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/library/ir_interpreter.cpp#L368-L410)
- Global state:
  - `g_native_symbol_cache`, guarded by `std::shared_mutex * g_native_symbol_cache_mutex`: shared lock for lookup, upgraded to a unique lock to insert. The comment says "we assume no native code is loaded or unloaded after the interpreter is first invoked, so this can be a global cache." — [L372-378, ~L841-850](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/library/ir_interpreter.cpp#L372-L378)
  - `g_init_globals`: "constants (lacking native declarations) initialized by `lean_run_init`. We can assume this variable is never written to and read from in parallel; see `enableInitializersExecution`." — [L207-209](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/library/ir_interpreter.cpp#L207-L209)
- Interpreted closures are ordinary runtime closures. `mk_stub_closure` allocates a closure pointing to a static C stub (`stub_N_aux`) whose first three captured fields are the `env`, the `opts` and the IR `decl` object, followed by the partially applied args. When such a closure is called from any thread (for example as a task body), `stub_m_aux` re-enters through `with_interpreter`. Because env, opts and decl are captured fields, `mark_mt` on the closure also marks them. — [L477-488, L994-1013](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/library/ir_interpreter.cpp#L477-L488)
- RC instructions are interpreted with the same runtime functions: `fn_body_kind::Inc` calls `inc(obj, n)`; `Reset` checks `is_exclusive(o)` to decide on in-place reuse; `isShared` evaluates to `!is_exclusive(...)`. Since `lean_is_exclusive` is false for MT objects, interpreted code never reuses or destructively updates an MT object. — [L494-520, L625, L742](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/library/ir_interpreter.cpp#L494-L520)

### Inferences
- Lean's interpreter needs no thread-specific RC logic. Making interpreter state thread-local and keeping heap-object semantics in the shared runtime is a direct precedent for eml's "VM over shared `eml_rt`" plan: if `eml_rt`'s RC and publication primitives are right, a VM instance per thread inherits safety.
- The interpreter frame stack is a C++ object rather than heap objects, so there is no "continuation object" to mark. eml's VM with effect handlers may capture continuations as heap objects; those would need `mark_mt` traversal like Lean's closures and thunks.

### Gaps
- I did not find documentation stating outright that "the interpreter is thread-safe". That conclusion is inferred from the code structure above and from the fact that Lean's elaborator runs interpreted code inside `Task`s (not separately verified here).

## Q4. How `IO.Ref` / `ST.Ref` stays safe under threads

### Takeaway
A `Ref` is created ST. Once it is marked MT, or if it is persistent (a global created at initialization), every operation switches to a lock-free protocol over the `m_value` pointer slot. `get` atomically takes the token (`exchange(nullptr)`), duplicates it and puts it back. `take`/`put` form a spin "critical section", with null as the "taken" marker. `swap` uses CAS. Any value stored into an MT or persistent ref is `mark_mt`'d first.

### Cited Findings
- `lean_st_mk_ref` allocates the ref with an ST header. — [io.cpp L1434-1439](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/io.cpp#L1434-L1439)
- `ref_maybe_mt(ref)` is `lean_is_mt(ref) || lean_is_persistent(ref)`. The comment explains that `ST.Ref`s created during initialization are marked persistent, so "to make `ST.Ref` API thread-safe, we must treat persistent `ST.Ref` objects created during initialization as a multi-threaded object ... the global `ST.Ref` may be used to communicate data between threads." — [io.cpp L1444-1456](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/io.cpp#L1444-L1456)
- `lean_st_ref_get` (MT path) loops on `val = exchange(nullptr)`, and once it gets a non-null value it does `inc(val)` and `exchange(val)` back. The comment: "We cannot simply read `val` from the ref and `inc` it ... since someone else could write to the ref in between and remove the last owning reference to the object. Instead, we must take ownership of the RC token in the ref via `exchange`, duplicate it, then put one RC token back." — [io.cpp L1458-1481](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/io.cpp#L1458-L1481)
- `lean_st_ref_take` (MT) spins on `exchange(nullptr)` until it gets a non-null value. `lean_st_ref_put` (MT) does `mark_mt(a)` and then `exchange(a)`, asserting that the old value was null. Its comment: "our runtime relies on the fact that a single-threaded object cannot be reached from a multi-thread object." — [io.cpp L1483-1518](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/io.cpp#L1483-L1518)
- `lean_st_ref_swap` (MT) does `mark_mt(a)` and then loops `load` + `compare_exchange_strong(old, a)` while `old != nullptr`, so it waits while the ref is taken. `Ref.set` is `discard <| Ref.swap r a`. — [io.cpp L1520-1536](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/io.cpp#L1520-L1536); [ST.lean L199-200](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/Init/System/ST.lean#L199-L200)
- `Ref.modify` and `Ref.modifyGet` are `@[implemented_by Ref.modifyUnsafe]`, which runs `take` → `f v` → `put`. The user-facing docstring says "Atomically modifies a mutable reference cell". `Ref.take` and `Ref.put` are `unsafe`. `put` "assumes that `ST.Ref.take` has been called on `r` before and no other `ST.Ref.put` has since acted on `r`. Breaking this invariant may lead to undefined behavior." — [ST.lean L190-276](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/Init/System/ST.lean#L190-L276)
- ST path: plain loads and stores, no marking (the `else` branches in the same functions).

### Inferences
- The take/put protocol makes `modify` a short spin-lock critical section in which the taker owns the sole token of the ref's value. The value is MT, though, so `lean_is_exclusive` is false and `f` will copy rather than update in place, for example `Array.set` on a value in an MT ref. Lean's runtime cannot recover exclusivity for MT objects. Issue #885 (below) is related.
- The busy-wait spin in get/take is visible in the code. There is no futex or backoff, other than `yield` in the thunk path.

### Gaps
- I did not find benchmarks of MT-ref contention.

## Q5. Known bugs and issues, and how Lean CI verifies thread safety

### Takeaway
Verification is layered:
1. CI runs a ThreadSanitizer job, added July 2026, on a curated subset of concurrency tests. Under TSan every `m_rc` access is made a seq_cst atomic so that the intended non-atomic ST fast paths are not reported.
2. ASan/UBSan/LSan jobs run on a larger subset.
3. Since August 2026, a Lean-language model of the RC arithmetic (`tests/elab/rc_model.lean`) carries machine-checked proofs, including that `mark_mt` leaves counts that never read as unshared again.
4. In 2026 the runtime received several soundness fixes for RC overflow interacting with MT marking.
No runtime debug assertion of the "MT → only MT/persistent" invariant was found.

### Inferences
- Under TSan, RC-field accesses are always atomic, so TSan **cannot** detect a missing `mark_mt` through RC races. It would detect one only through racy non-atomic accesses elsewhere, for example destructive updates on an object wrongly left ST and written while another thread reads it, or a use-after-free surfacing via ASan. This is a structural blind spot: the most likely bug class, a missing mark, is not directly checked by any tool in Lean's CI. The 2026 bugs were found by reasoning, with formal modelling of the count arithmetic, and not by TSan.
- For eml, a cheap debug-mode check could close this gap: on every field read or `inc` of an MT object's child, assert that the child is not ST (a "debug_heap"-style invariant walk). Lean does not do this; it is a suggestion, not prior art.
- The proven scope is the count arithmetic in isolation (single object, sequential, plus a bounded "in-flight" argument). The reachability invariant and publication ordering remain trusted C++.

- I could not confirm whether earlier MT-marking bugs (2020-2024) existed beyond issue #885. GitHub search for "mark_mt", "markMT", "tsan" and "data race" returned only the items above.

## Q6. Cost data: the sign check and atomic RC on shared objects

### Takeaway
The only published whole-program number is the IFL'19 ablation: atomic RC on all objects costs 1.13x-2.31x (geometric mean 1.89 vs 1.24 base, i.e. about 1.5x relative) on single-threaded workloads. The ST/MT sign branch is an inline `LEAN_LIKELY` test whose individual cost Lean has never published. Recent sticky-overflow checks cost +0.6-0.8% instructions and no measurable wall-clock change. Design-level costs: MT objects lose in-place updates, and task spawn is O(reachable ST graph).

### Cited Findings
- `-ST` ablation numbers (Fig. 6): see Q2. Binarytrees 1.22, deriv 1.42, const_fold 1.23, parser 1.68, qsort 1.13, rbmap 1.71, unionfind 2.31. — [paper Fig. 6](https://arxiv.org/abs/1908.05647)
- The paper: "the additional test is much cheaper than memory fences on modern hardware." — [paper §7.2](https://arxiv.org/abs/1908.05647)
- Sticky RC overhead: "+0.8/0.6% instructions build overhead on core/Mathlib ... no statistically significant effect on wall-clock." — [PR #14838](https://github.com/leanprover/lean4/pull/14838)
- Current fast paths: an ST inc is one compare plus a non-atomic add. An MT inc additionally does `lean_is_unstuck_mt` (one unsigned compare) plus a relaxed `fetch_sub`. A dec on ST with `rc > 1` is a non-atomic sub; an MT dec always goes out-of-line to `lean_dec_ref_cold` and an `acq_rel` `fetch_add`. — [lean.h L705-740](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/include/lean/lean.h#L705-L740); [object.cpp L455-471](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/runtime/object.cpp#L455-L471)
- Over-marking cost acknowledged by maintainers: unconditional thunk-result marking degrades "the entire freshly computed result graph to atomic reference counting" (PR #15047, open). Captured exclusive objects in tasks are marked MT unnecessarily (issue #885, open). — [PR #15047](https://github.com/leanprover/lean4/pull/15047); [issue #885](https://github.com/leanprover/lean4/issues/885)
- `lean_is_exclusive` is false for MT objects, so MT data is never destructively updated or reused. — [lean.h L776-782](https://github.com/leanprover/lean4/blob/5e96ee1153f945234f126ed024043a0697c9d6f3/src/include/lean/lean.h#L776-L782)

### Inferences
- The largest practical MT cost in Lean is probably not the atomic op itself. It is losing FBIP reuse on MT objects, plus over-marking (closures, thunk results), because MT is a one-way, irreversible state. eml's row-kind discipline could mark less; for example, linearly owned values moved into a child might not need marking at all, which is issue #885's wish. Inference only.
- Lean has no reverse transition from MT to ST, even when an MT object's count reaches `-1`. The dec path frees at `-1`, but no path re-tags to ST.

### Gaps
- I found no microbenchmark or perf study that isolates the sign-branch cost or atomic-RC cost on modern (2024-2026) hardware in Lean. Nothing from Lean's "radar" benchmarking was published in a form I could cite beyond the PR #14838 remark.
