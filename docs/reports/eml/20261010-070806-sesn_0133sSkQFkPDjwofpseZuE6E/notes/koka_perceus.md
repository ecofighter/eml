Scope note: source code was read directly from a shallow clone of `koka-lang/koka` branch `dev` at commit `9c55695dd2f7d4db8d93011693d37295e2b76c53` (2026-09-30, Koka version 3.3.0 in `package.yaml`). Permalinks below are pinned to that commit. Commit/PR/issue metadata came from the GitHub API (`gh`). Papers were downloaded and read as text. "Read directly" = I saw the code/text; "Inferred" = my reading, not stated by the source.

## Q1. How kklib implements thread-shared RC (sign convention, sticky ranges, mark_shared, slow paths) and where marking is triggered

### Takeaway
kklib uses one signed `_Atomic int32` per block: `>= 0` is thread-local (0 = unique, N = N+1 refs, updated with relaxed load + relaxed store, no RMW), `< 0` is thread-shared (counts grow *downward*, -1 = last shared ref, atomic RMW), and a large negative "sticky" band (incl. `INT32_MIN` = static/stuck) where objects are never freed. Fast paths do a single signed test (`rc <= 0` on drop, `rc < 0` on dup) and branch to out-of-line `kk_block_check_*`. Marking (`kk_block_mark_shared`) is done by the *sender* before publication, recursing until it meets an already-shared block; it is called only from a handful of runtime primitives (task schedule, promise set, lvar, thread-shared `ref` store). This is almost exactly eml's planned design, including the "positive = local, negative = shared, stop at marked" choices.

### Cited Findings

**Header and sign convention (read directly)**
- Header is 64 bits: `uint8 scan_fsize; uint8 _field_idx; uint16 tag; _Atomic(int32) refcount`. New blocks start at rc 0 (unique); static blocks use `KK_HEADER_STATIC` with `INT32_MIN` (stuck). — [kklib.h L134-147](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L134-L147)
- `kk_refcount_is_thread_shared(rc) = rc < 0`; `kk_refcount_is_unique_or_thread_shared(rc) = rc <= 0`; comment: "Are there (possibly) references from other threads? (includes static variables)". — [kklib.h L106-117](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L106-L117)
- All plain reads/writes of the count are `kk_atomic_load_relaxed` / `kk_atomic_store_relaxed` (not plain C accesses), so the local path is data-race-free in the C11 sense without emitting RMW instructions. — [kklib.h L298-304](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L298-L304)
- The full range table in `refcount.c` (verbatim summary):
  - `0` unique; `1..INT32_MAX` thread-local count (N means N+1 refs). Dup past `INT32_MAX` overflows "automatically into the sticky range".
  - `INT32_MIN` = `RC_STUCK`: single-threaded overflow, never freed.
  - `INT32_MIN+1 .. INT32_MIN+0x10000000`: sticky, neither inc nor dec (`RC_STICKY`).
  - `INT32_MIN+0x10000001 .. INT32_MIN+0x20000000`: sticky, "still decrements (dup) but no more increments (drop)" (`RC_STICKY_DROP`).
  - `INT32_MIN+0x20000001 .. -2`: thread-shared counts with atomic inc/dec (~1.6e9 counts).
  - `-1` = `RC_SHARED_UNIQUE`: thread-shared and now unique.
  - "The reference count grows down ... to dup a thread-shared reference will _decrement_ the count, and to drop will _increment_ the count."
  - Rationale for a sticky *range* rather than a single value: "Since we first read the reference count non-atomically we need a range for stickiness ... We assume that the relaxed reads of the reference counts catch up to the atomic value within the sticky range (which has a range of ~0.5e9 counts)." — [refcount.c L98-153](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L98-L153)
- Memory ordering policy (comment, verbatim gist): increments relaxed; decrements `release`; if the decrement frees, also `acquire` (cites Raymond Chen's oldnewthing post). Implemented as `kk_atomic_dup = kk_atomic_dec_relaxed`, `kk_atomic_drop = kk_atomic_inc_release`, plus `kk_atomic_load_acquire` before freeing. — [refcount.c L137-166](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L137-L166)

**Inline fast paths (read directly)**
- `kk_block_dup`: relaxed load; if `rc < 0` call `kk_block_check_dup` (noinline, cold), else store `rc+1`. — [kklib.h L752-762](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L752-L762)
- `kk_block_drop`: relaxed load; if `rc <= 0` call `kk_block_check_drop`, else store `rc-1`. Header comment: "The main performance trick is to do one single test in a dup/drop for the fast path." `kk_block_check_*` are declared `kk_decl_cold` (`noinline,cold`). — [kklib.h L733-773](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L733-L773)
- `kk_block_check_dup`: if `rc0 > RC_STICKY` atomic decrement (relaxed), else sticky no-op. — [refcount.c L182-190](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L182-L190)
- `kk_block_check_drop`: `rc0 == 0` → free recursively; `rc0 <= RC_STICKY_DROP` → no-op; else `atomic_inc_release`; if the *old* value was `RC_SHARED_UNIQUE` (-1) → `atomic_load_acquire`, reset rc to 0 ("no longer shared"), then `kk_block_drop_free`. Comment: "Currently compiles without register spills (on x64) which is important for performance." — [refcount.c L192-214](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L192-L214)
- `kk_block_decref` (shallow free used by Perceus' unpacking-style drops): same structure; comment says "the only time it could become zero is if it happened to be thread shared and another thread decremented the count as well." — [kklib.h L781-794](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L781-L794), [refcount.c L237-254](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L237-L254)
- When the recursive free reaches a shared child it uses `block_thread_shared_decref_no_free` (atomic drop; if last, set rc 0 and continue freeing in this thread). So a thread that drops the last shared ref frees the whole subgraph; children freed later by that thread were allocated in other threads' mimalloc heaps (mimalloc supports cross-thread free). — [refcount.c L260-290](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L260-L290)

**Marking (`kk_block_mark_shared`) (read directly)**
- `kk_block_make_shared(b)` converts a local count to a shared count with `rc = ~rc` (i.e. `-(rc+1)`), and if that falls into the sticky range sets `RC_STICKY`. — [refcount.c L168-179](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L168-L179)
- `kk_block_mark_shared` → `kk_block_mark_shared_rec`: returns immediately if already shared; marks the block *before* its children (pre-order); single-field and `(non-ptr, ptr)` "list-like" blocks are handled by a loop (tail call); leaf children (`scan_fsize == 0`) are marked inline. Recursion up to `MAX_RECURSE_DEPTH = 100`, then switches to a stackless pointer-reversal algorithm `kk_block_mark_shared_recx` ("the recursive algorithm is about twice as fast as the stackless one"). — [refcount.c L556-652](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L556-L652), [L769-778](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L769-L778)
- Stackless marking cannot use `_field_idx` for its traversal index because "we also use it for tail recursion context paths. Such TRMC structure may be captured under a lambda (by yielding for example) and that might become thread shared and we cannot overwrite such indices." Instead it steals the low 8 bits of the (still local) refcount (`rc << 8`, capped at `KK_RC_MARK_MAX = 0x7FFFFF`, if larger it becomes stuck). — [refcount.c L668-706](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L668-L706)
- The "stop at already-marked" rule relies on the invariant that a shared block only points to shared (or static) blocks; the 2026 commit message states it explicitly: "Everything reachable from a thread-shared block must itself be thread-shared, since another thread can reach it and dup or drop it; `kk_block_mark_shared` establishes that when a block is shared." — [commit 046254c](https://github.com/koka-lang/koka/commit/046254c139)

**Where marking is triggered (read directly; full grep of kklib/lib/src for `mark_shared`)**
- `kk_task_schedule(fun)`: `kk_block_mark_shared(fun)` "mark everything reachable from the task as shared" before enqueuing. — [thread.c L362-371](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/thread.c#L362-L371)
- Promises: the promise box itself is marked at allocation; `kk_promise_set` marks the result before storing it under the mutex. — [thread.c L387-412](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/thread.c#L387-L412)
- LVars: `kk_lvar_alloc` marks `init` and the lvar; `kk_lvar_put` marks the combined result inside the mutex (`// todo: can we mark outside the mutex?`). — [thread.c L506-530](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/thread.c#L506-L530)
- Thread-shared mutable `ref`: `kk_ref_swap_thread_shared_borrow` now marks the stored value before the CAS publishes it (added 2026-09-29). `kk_ref_get_thread_shared` avoids the read-then-dup race by CAS-ing a guard value `0` into the ref, dup-ing, then writing back. — [ref.c L11-52](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/ref.c#L11-L52), [ref.h L48-77](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib/ref.h#L48-L77)
- There is no marking in channels or `std/async` on `dev`: the async library (2026, Tim Whiting / Daan Leijen) is a single-threaded libuv event loop. — [lib/std/async/async.kk](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/lib/std/async/async.kk)
- The Perceus TR describes the same policy: "when starting a new thread, the argument passed to the thread is marked as thread-shared. The only other operation that can cause thread sharing is setting a thread-shared mutable reference." — [Perceus TR §2.7.2](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)

**Daan Leijen on why relaxed local ops are sound (GitHub issue #276, 2022)**
- "On most architectures, _relaxed_ atomic loads and stores are just like regular loads and stores ... the exact same instructions are generated."
- "if the object is not (thread) shared, the refcount is always >= 0 and it is explicitly made negative once it can be shared. So, we can safely read the refcount and if it is >= 0, we can just increment/decrement it without needing (non-relaxed) atomic operations (as it can't become shared in-between the read and the inc/dec)." "just before making an object thread shared, you can safely make the refcounts shared (=negative); only after that atomic operations are required."
- "When designing a language, make sure that potential thread sharing of objects can be detected (in Koka: global values and the captured values when spawning a `task`)."
- Anton Lorenzen in the same thread argues against plain (non-atomic) C loads even if "benign", citing compiler-introduced stores. — [koka issue #276](https://github.com/koka-lang/koka/issues/276)

### Inferences
- Inferred: the soundness argument has two parts that eml must also uphold. (1) *Monotonic sharing*: a block goes local → shared, never back while other threads can reach it. kklib does reset `rc` to 0 after the last shared drop, but at that point no other thread holds a reference. (2) *Publication after marking*: marking must happen-before the release operation that hands the object to another thread (mutex unlock, queue enqueue, CAS). In kklib that ordering is provided by the pthread mutex in the task queue / promise.
- Inferred: kklib's sign convention is the reverse of eml's for 0: kklib uses 0 = unique and `INT32_MIN` = static/stuck, while eml plans 0 = immortal. kklib's choice lets the drop fast path test `rc <= 0` once to cover "free now", "shared" and "sticky". eml's plan (1 = unique, 0 = immortal, < 0 shared) needs a test like `rc <= 1` and a separate immortal test in the slow path. Neither is wrong, but kklib's encoding is the reason it gets one branch per drop.
- Inferred: shared counts grow downward, so dup on a shared object is an atomic *decrement* and drop is an atomic *increment*. The overflow of shared counts therefore runs into the sticky band rather than wrapping to positive (local) values, which would be catastrophic.
- Inferred (possible latent bugs on `dev`, not reported anywhere I found):
  - `kk_block_mark_shared_recx_large` calls `kk_block_mark_shared_recx(b, ctx)` on the *parent* `b` instead of the child returned by `kk_block_field_should_mark`. Since `b` is not yet marked and is still a large block, this looks like unbounded recursion. It is only reached on the stackless path (depth > 100, or `kk_box_mark_shared_recx`) with a vector of ≥ 255 scan fields. — [refcount.c L657-666](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L657-L666)
  - `kk_block_mark_shared_recx` contains a leftover `fprintf(stderr, "mark shared recx\n");`, which suggests this path is rarely exercised. — [refcount.c L711](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L711)
  - `kk_block_check_decref` / `_small` free after the last shared drop *without* the `kk_atomic_acquire` that `kk_block_check_drop` does. The comment block's own ordering rule says an acquire is needed there. — [refcount.c L237-276](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L237-L276)
- Inferred: a lesson for eml is that marking must be *exhaustive over all publication channels*, and every channel is a separate place where a bug can hide. kklib had (and on `dev` may still have, see Q2) unmarked publication channels: shared `ref` stores (fixed 2026-09), lazily initialised process-global heap blocks, and computed top-level constants.

### Gaps
- The kklib source does not state how globals / top-level values are made safe in general. Daan's comment in #276 says "global values" are a sharing source, but on `dev` only compile-time static blocks get `RC_STUCK`; PR #910's fix for computed constants (`kk_box_mark_static`) was not merged (see Q2).
- I found no Koka documentation of the memory model or of which primitives mark; the list above comes from grepping the code.

## Q2. Actual status of parallelism/concurrency in Koka; how effects interact with threads

### Takeaway
Parallelism in Koka is explicitly experimental and minimal. `std/os/task` offers `task`/`await`/`parallel` over a simple pthread pool (no work stealing), restricted to *total* functions, so no effect handler or continuation ever crosses a thread. Each OS thread has its own `kk_context_t` (heap, evidence vector, yield state). `std/async` is single-threaded (libuv). A 2026 PR that added OS threads to async found heap corruption in ~30-50% of two-thread runs. It was closed unmerged, and only its RC-conversion fix landed separately.

### Cited Findings
- `std/os/task` header comment: "Experimental: Parallel tasks. Note: very experimental and may not work as intended :-)". API: `task( work : () -> a ) : promise<a>` (C `kk_task_schedule`), `await` (C `kk_promise_get`), `parallel( xs : list<() -> a> )`, `task-set-default-concurrency`; LVars are marked "currently unsafe in the pure effect!! needs work". — [lib/std/os/task.kk](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/lib/std/os/task.kk)
- README task list: "The current parallel task support is very basic; we need a great work-stealing thread pool, LVar's etc." — [readme.md L254](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/readme.md#L254)
- Thread pool: a single global task group (`pthread_once`), FIFO queue under one mutex and condvar; `kk_promise_get` lets a waiting thread run other queued tasks ("let main thread participate instead of blocking"). — [thread.c L190-460](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/thread.c#L190-L460)
- `kk_context_t` is "The thread local context" holding `yielding`, the thread-local `heap`, `evv` ("the current evidence vector for effect handling"), the inlined `yield` structure, `task_group`, etc. — [kklib.h L435-462](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L435-L462)
- The benchmark usage wraps work in `pretend-no-div` to fit the total `() -> a` signature: `task{ pretend-no-div{ sum-count( partc, depth ) } }`. — [test/bench/koka/binarytrees.kk L131-137](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/test/bench/koka/binarytrees.kk#L131-L137)
- PR #910 "std/async: OS threads with thread-safe channels, and cross-thread refcount fixes" (Tim Whiting, closed 2026-09-30, `mergedAt: null`). It reports: "Running Koka code on two threads concurrently corrupted the heap (~30-50% of runs) because several process-global heap blocks carry plain, non-atomic reference counts". The fixes it lists: (1) `kk_evv_empty_singleton` was a heap-allocated shared block, so make it static/stuck; (2) the `make_shared` off-by-one (`-rc` → `~rc`); (3) racy lazy string-literal init, fixed by publishing with a CAS and giving literals a stuck refcount; (4) computed top-level constants in C statics, marked static at module init (`kk_box_mark_static`). Design notes from the PR: a regular `channel` "cannot be shared across threads: its state transitions are not atomic, and emitting to a waiting receiver would run the receiver's continuation (and drive its uv loop) on the wrong thread". The thread-safe `xchannel`'s sender "carries no Koka state, so it is the only part that crosses threads". Values are marked shared before they are enqueued. — [koka PR #910](https://github.com/koka-lang/koka/pull/910)
- On `dev` at 9c55695, fix (2) landed as commit cf56076 (2026-09-30) and the `ref` publication fix as 046254c (2026-09-29). `kk_evv_empty_singleton` is still a lazily allocated heap block with an unsynchronised `if (evv == NULL)` init and plain dup, and string literals still use the lazy non-CAS `kk_init_string_literal`. — [init.c L278-286](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/init.c#L278-L286), [string.h L127-139](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib/string.h#L127-L139), [commit cf56076](https://github.com/koka-lang/koka/commit/cf56076400)
- Open issue #566 (2024): lazy (`delayed`) values may be evaluated twice under concurrency; "sound for pure computations ... but not for arbitrary algebraic effects", and the proposed fix is a CAS-installed blackhole "only necessary if the value is thread-shared". Still open; `force` writes `XBlocking` with a plain `:=`, and readers seeing `XBlocking` spin by re-calling `go`. — [koka issue #566](https://github.com/koka-lang/koka/issues/566), [lib/std/core/delayed.kk L42-51](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/lib/std/core/delayed.kk#L42-L51)
- Open issue #98 (2020) asks for a thread model; Daan's answer focuses on libuv-based async, not on multithreaded effects. — [koka issue #98](https://github.com/koka-lang/koka/issues/98)
- `doc/spec/why.kk.md`: "inductive data types cannot form cycles, and potential sharing across threads can be reliably determined." — [why.kk.md L222-225](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/doc/spec/why.kk.md#L222-L225)

### Inferences
- Inferred: Koka avoids the hard "effects × threads" problem by construction. A task body has a total effect, so there is no `yield` to a handler on another thread, and evidence vectors and continuations stay thread-local. The cross-thread values are data plus closures, which are marked. For eml (evidence passing, continuations as closures), any primitive that sends a *continuation closure* to another thread must mark it like any other closure. Marking will then traverse the captured evidence/handler state, and that state must also be safe to touch from another thread (no thread-local `ctx` pointers inside). Koka has not solved or tested this.
- Inferred: the shared process-global "singleton" blocks (empty evidence vector, string literals, computed constants) were the main source of real multithreaded corruption found in 2026. For eml, every runtime-global or lazily initialised heap object should be immortal (eml's RC 0) from creation, and its initialisation should be a once/CAS operation.
- Inferred: Koka's thread support is lightly exercised. Two serious RC bugs (the off-by-one in `make_shared` and the missing marking on `ref` store) survived until 2026-09 even though the binarytrees benchmark used tasks since 2021. The likely reason is that binarytrees tasks share little mutable or long-lived data.

### Gaps
- When the `-rc` mapping was first introduced is not determined (the shallow history only shows the fix). I did not check whether the 2021 Perceus artifacts were affected.
- I found no Koka book section on tasks or threads.

## Q3. What the Perceus paper / TR and "Counting Immutable Beans" say about concurrency, the shared flag, and measured overhead

### Takeaway
Perceus (TR MSR-TR-2020-42 v4 / PLDI'21) adopts Lean's scheme: mark-on-share with a recursive `tshare`, a negative RC as the shared flag so one inlined test covers the slow path, a sticky range, and a fast-path check of the shared bit on mutable refs. All-atomic RC measured 5% (rbtree) to 59% (nqueens) slower. Counting Immutable Beans (Ullrich & de Moura, IFL'19) introduced the single-threaded / multi-threaded / persistent tagging with the reachability invariant and `markMT` at `Task.mk` / `Task.bind`. It notes that immutability is what lets tagging live only in threading primitives, without store barriers.

### Cited Findings
- Perceus §2.7.2: "Ungar et al. [47] report slowdowns up to 50% when atomic reference counting operations are used." "Following the solution of Ullrich and de Moura [46], we mark each object with whether it can be thread-shared or not, and supply an internal polymorphic operation `tshare : forall a. a -> io ()` which marks any object and its children recursively as being thread-shared. Even though marking is linear, it happens at most once for any object since shared objects cannot be unshared. All objects start out as unshared, and are only marked through explicit operations." — [Perceus TR v4](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)
- Perceus §2.7.2 also shows the naive flag test (`if (b->header.thread_shared) atomic_dec ... else rc--`) and says "this may still present quite some overhead as many drop operations are emitted". It then gives the negative-encoding version with a single `rc <= 1` test (the TR's encoding was 1-based; the current kklib is 0-based). Footnote: "Since the thread-shared sign-bit is stable, we can do the test ... without needing expensive atomic operations and can use a memory_order_relaxed atomic read." Sticky range: "very large reference counts (2^30 in our implementation) stay without being further adjusted". — [Perceus TR v4](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)
- Perceus §2.7.3 (mutable refs): it describes the `!` vs `:=` race, where a read is followed by a dup while another thread overwrites and drops the old value. It says correctness needs "a double-CAS, using hazard pointers, or using some other locking mechanism", and that Koka avoids the slow path because "we can also check if a mutable reference is actually thread-shared". — [Perceus TR v4](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)
- Perceus evaluation: "we also ran our benchmarks using just atomic operations for our reference counts to see the impact of the thread-shared flag. We observed a slowdown from 5% (rbtree) up to 59% (nqueens) across our benchmarks. This matches the observations by Ungar et al. [47] who performed a similar experiment in Swift." — [Perceus TR v4](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)
- The Perceus intro lists "multi-threaded operations" among the classical drawbacks of RC; the formal calculus and proofs do not model threads (my reading: there is no concurrency in the λ1 semantics). — [Perceus TR v4](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/perceus-tr-v4.pdf)
- Counting Immutable Beans §7.2: standard thread-safe RC uses relaxed increments and release-decrement + acquire-before-delete. In the previous Lean compiler "the memory fences have a significant performance impact even when only one thread is being executed." Values are tagged "single-threaded, multi-threaded, or persistent". Invariant: "from persistent values, we can only reach other persistent values, and from multi-threaded values, we can only reach persistent or multi-threaded values." `markMT(o)` is used in `Task.mk f` and `Task.bind x f` "while they are still accessible from only one thread". "values are visited at most once by markMT"; "task creation is not a constant time operation"; and a proposed `asMT g` primitive would allocate directly as MT. "This additional test does not require any synchronization because the tag is only modified before a value is shared with other execution threads." "We just need to identify which functions may send values to other execution threads, and use markMT." — [Ullrich & de Moura, Counting Immutable Beans, arXiv:1908.05647](https://arxiv.org/abs/1908.05647)
- Beans evaluation includes a "-ST" ablation that "uses atomic RC operations for all values" (Fig. 6). The text only says the approach "significantly boosts performance"; I did not extract per-benchmark numbers from the figure. — [arXiv:1908.05647](https://arxiv.org/abs/1908.05647)
- Beans related work: Ungar et al. (Swift) tag shared objects with a bit but "because of mutability, every single store operation must be intercepted to (recursively) tag objects". Choi et al. (biased RC) instead store an owner thread ID plus two counters. "Thanks to immutability, we can make use of the simpler scheme without introducing store barriers during normal code generation. Object tagging instead only has to be done in threading primitives." — [arXiv:1908.05647](https://arxiv.org/abs/1908.05647)

### Inferences
- Inferred: eml's planned scheme (sender-side recursive marking, stop at marked, relaxed local ops) matches the Lean/Koka design point exactly. Its safety rests on the same precondition: mutation is confined to explicit primitives (refs, arrays), which act as the "store barrier" points. If eml adds in-place mutation primitives that can store into a shared object (shared mutable cells, arrays), each one must mark the stored value before publishing, as Koka's `ref` fix shows.
- Inferred: the 5-59% figure is the best available primary estimate of "all-atomic vs marked" for a Perceus-style RC with reuse; nqueens (allocation-heavy, small objects) is the worst case.

### Gaps
- The PLDI'21 camera-ready version was not separately checked; I used TR v4 (2021-06-07), which postdates PLDI acceptance and contains the same §2.7.2 and evaluation text as far as I could tell.

## Q4. Reuse under thread sharing: how Koka checks uniqueness, and known bugs

### Takeaway
Reuse in kklib only fires when a relaxed load sees `rc == 0`. A thread-shared object (even at -1 = "shared but now unique") is never reused in place: the drop-reuse slow path does an atomic drop and frees it if it was the last reference, but returns `NULL` (no reuse token). The relaxed `== 0` read is sound only because a local (positive) count cannot change concurrently and a shared count is never 0 while other threads hold it. Beans adds a related rule: a *borrowed* parameter may look unique while it is not, so `reset` must never apply to borrowed values.

### Cited Findings
- `kk_block_is_unique(b) = kk_likely(kk_block_refcount(b) == 0)` (relaxed load). Generated code uses `kk_datatype_ptr_is_unique` for reuse specialisation's `is_unique` test. — [kklib.h L306-308](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L306-L308), [src/Backend/C/FromCore.hs L1134-1138](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/src/Backend/C/FromCore.hs#L1134-L1138), [src/Backend/C/ParcReuse.hs L520-540](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/src/Backend/C/ParcReuse.hs#L520-L540)
- `kk_block_drop_reuse`: if `rc <= 0` call `kk_block_check_drop_reuse`; there, `rc0 == 0` drops the children and returns the block as the reuse token; otherwise ("may be shared or sticky") it calls `kk_block_check_drop` and returns `kk_reuse_null`. — [kklib.h L807-818](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L807-L818), [refcount.c L216-235](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/src/refcount.c#L216-L235)
- `kk_reuse_drop` asserts `kk_block_is_unique(r)` before freeing an unused token. — [kklib.h L913-918](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib.h#L913-L918)
- Thread-shared `ref` and lazy blocks branch on `kk_block_is_thread_shared` to choose an atomic slow path (`ref.h`, `lazy.h`). — [ref.h L48-77](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib/ref.h#L48-L77), [lazy.h L18-35](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib/lazy.h#L18-L35)
- Known bug fixed 2026-09-30 (commit cf56076, "Fix thread-shared reference count"): `make_shared` mapped local rc N (N+1 refs) to `-N` (N refs), losing one reference per marked block with rc ≥ 1. The regression test `test/lib/task-shared.kk` describes the failure: "the shared refcount must keep both references, or the task's drop frees `xs` while `main` still reads it, after the allocation of `ys` has reused its cells." — [commit cf56076](https://github.com/koka-lang/koka/commit/cf56076400), [test/lib/task-shared.kk](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/test/lib/task-shared.kk)
- Known bug fixed 2026-09-29 (commit 046254c): a value stored into a thread-shared `ref` was not marked, so other threads did non-atomic RC on it. `std/core/delayed` publishes through such a ref, so a `delayed` value captured by tasks broke. The regression test "crashed on all 40 runs without this fix and passes on all 40 with it." — [commit 046254c](https://github.com/koka-lang/koka/commit/046254c139), [test/lib/task-publish.kk](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/test/lib/task-publish.kk)
- Beans: "If a function f takes a parameter x as a borrowed reference, then at runtime x may be a shared value even when its reference counter is 1. Thus, we must never mark x as borrowed if it is used by a `let y = reset x` instruction." Also: "If reset is used on a shared, non-reusable reference, it behaves like dec ... we cannot simply return the reference in both cases and do another uniqueness check in reuse because other code between the two expressions may have altered its reference count." — [arXiv:1908.05647](https://arxiv.org/abs/1908.05647)

### Inferences
- Inferred: Koka's conservative choice (no reuse of shared objects, even at -1) removes the need for an atomic acquire on the reuse fast path. eml's plan, "atomic read on shared objects to allow reuse", is strictly more aggressive. If eml reuses a shared object whose count reads as "shared-unique", it needs at least an `acquire` load (or the acquire fence used before free). Without it, the other thread's last writes or reads of the fields, which happened-before its release-decrement, are not ordered before this thread's in-place writes. eml should also reset the count to local-unique only after that acquire. The simpler alternative is to copy Koka: treat shared as non-unique for reuse and free through the normal shared-drop path.
- Inferred: the `task-shared` bug shows that an off-by-one in the local↔shared conversion turns into a *use-after-free through reuse*: the freed cells get reused by the next allocation. So tests that pair "mark, then keep using the object on the sender thread, then allocate" are high-value regression tests for eml.
- Inferred: the TRMC `_field_idx` comment shows that in-place constructor contexts captured by a continuation (via yield) can become thread-shared. eml's planned FBIP/TRMC plus continuation closures will hit the same interaction, so any runtime scratch use of header bits must not clobber state that a shared, captured context depends on.

### Gaps
- I found no Koka issue that discusses reusing shared-unique (-1) objects. That this was a deliberate decision is inferred from the code shape, not stated.

## Q5. Frame-limited reuse (drop-guided reuse) and FP²: concurrency notes

### Takeaway
These papers say almost nothing about concurrency. Frame-limited reuse (MSR-TR-2021-30, the TR behind the ICFP'22 "drop-guided reuse" work) mentions it only in passing: it lists thread-sharing as a separate concern, and its parallel binarytrees result credits the upfront shared check. FP² (MSR-TR-2023-19 / ICFP'23) is about uniqueness and borrowing in a sequential calculus and does not discuss threads.

### Cited Findings
- Frame-limited reuse intro: Perceus "still needs separate mechanisms to address cyclic data and mitigate the impact of thread shared" data (paraphrased from a line split in extraction). In §6.2 binarytrees, Koka beats all compared languages except C++ (0.66×) "even though it uses a simple thread pool implementation without work-stealing ... Since the benchmark does concurrent allocations reference counting generally needs to be atomic. However, due to careful language design, Koka can avoid most of the overhead by checking upfront if a reference count needs to be atomic or not." §7 builds a faster FBIP version of the *parallel* binarytrees. — [Lorenzen & Leijen, Reference Counting with Frame Limited Reuse, MSR-TR-2021-30 v2](https://www.microsoft.com/en-us/research/uploads/prod/2021/11/flreuse-tr.pdf)
- Its related work repeats Ungar et al. (tagging potentially shared objects) and Choi et al. (biased RC: owner thread ID plus a shared atomic counter and a biased local counter). — [MSR-TR-2021-30](https://www.microsoft.com/en-us/research/uploads/prod/2021/11/flreuse-tr.pdf)
- FP²: grepping the TR for thread/concurrency/atomic/parallel finds no concurrency discussion. "Shared" there means non-unique (multiply referenced) values, which the authors list as future work for the FIP calculus. — [Lorenzen, Leijen, Swierstra, FP²: Fully in-Place Functional Programming, MSR-TR-2023-19](https://www.microsoft.com/en-us/research/uploads/prod/2023/05/fbip.pdf)

### Inferences
- Inferred: the reuse literature treats thread-sharing as orthogonal. Reuse correctness rests on the runtime's `is_unique` returning false for shared objects, so none of these papers gives guidance on reusing shared-unique objects.

### Gaps
- I did not locate a separate ICFP'22 camera-ready PDF. The TR v2 (Mar 2022) was used as its stand-in.

## Q6. How Koka tests its runtime (sanitizers, KK_DEBUG_FULL, refcount checks)

### Takeaway
Koka's checks are opt-in. `KK_DEBUG_FULL` (enabled when the optimisation level is below 0) turns on `kk_assert_internal` and mimalloc `MI_DEBUG=3`, and poisons freed blocks with `0xDF`. A hidden `--fasan` flag builds with ASan + UBSan (+ LSan off macOS) and the system allocator. CMake has `KK_DEBUG_SAN` (thread, memory, address, undefined; clang only). CI runs `stack test --fast` with output-comparison tests and no sanitizer or TSan job. Threading tests are two tiny output-comparison programs added in 2026 plus an unmerged stress test.

### Cited Findings
- `kk_assert_internal(x)` is a no-op unless `KK_DEBUG_FULL` is defined. — [platform.h L244-250](https://github.com/koka-lang/koka/blob/9c55695dd2f7d4db8d93011693d37295e2b76c53/kklib/include/kklib/platform.h#L244-L250)

### Inferences
- Inferred: Koka has no systematic way to check parallel safety. It has no TSan in CI, no checker for the invariant "a shared block reaches only shared or static blocks", and no assertion that a local-count block is touched only by its owner thread. Bugs were found by stress-running small programs many times. Checks eml could add beyond Koka:
  - In a debug-heap mode, record the owner thread ID per block. Assert on every local (positive-RC) dup/drop that the current thread is the owner, which catches missing marks at the first wrong access instead of at a later corruption.
  - After every mark, verify the reachability invariant (shared → shared ∪ immortal) by a full walk.
  - Run tests under TSan with the RC operations as real atomics so that TSan can see the accesses (kklib's relaxed atomics are visible to TSan, plain accesses would also be).
  - Use a mark/publish test matrix covering every publication primitive.
- Inferred: kklib's relaxed-atomic typing of the refcount field (rather than plain `int`) is what makes a TSan run meaningful. TSan reports races on the *non-atomic* parts (fields, plain globals), which is exactly where Koka's real bugs were.

### Gaps
- I did not run Koka's tests or try TSan on kklib, so whether TSan would have caught the 2026 bugs is not verified.
- I found no Koka documentation describing a recommended debugging workflow for runtime or RC bugs beyond these flags.
