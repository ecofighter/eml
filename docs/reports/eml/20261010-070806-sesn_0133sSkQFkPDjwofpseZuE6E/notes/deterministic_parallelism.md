# Deterministic parallelism designs and how their determinism / race freedom is verified

Scope note: "Cited Findings" are read directly from the cited primary source (paper PDF text or official docs) unless marked "(search snippet)". "Inferences" are my own reasoning, including all eml applicability claims. Research date 2026-10-10.

## Q1. monad-par (Marlow, Newton, Peyton Jones 2011) and Strategies: how determinism is guaranteed, how the scheduler is a library, how it was tested

### Takeaway
monad-par gets determinism from write-once IVars plus a pure `runPar :: Par a -> a`; the argument is an informal confluence argument over an operational semantics (full proof deferred to Featherweight CnC), not testing. The scheduler is an ordinary Haskell library: `Par` is a continuation monad whose answer type is a `Trace` data type, consumed by a sequential or work-stealing scheduler. Strategies get determinism more cheaply: parallelism is only an evaluation annotation on a pure value, so the result cannot depend on it, but purity of the sparked work is the user's obligation.

### Cited Findings
- API: `fork`, `new`, `get`, `put :: NFData a => IVar a -> a -> Par ()`, `runPar :: Par a -> a`. "An IVar is a write-once mutable reference cell ... put ... may only be executed once per IVar (subsequent puts are an error). The get operation waits until the IVar has been assigned a value." — [Marlow, Newton, Peyton Jones, A Monad for Deterministic Parallelism, Haskell 2011, §3](https://simonmar.github.io/bib/papers/monad-par.pdf)
- "the type of runPar indicates that the result has no side effects and does no I/O; hence, we are guaranteed that runPar produces a deterministic result for any given computation in the Par monad." — [monad-par paper §3](https://simonmar.github.io/bib/papers/monad-par.pdf)
- `put` is fully strict (NFData) by default to avoid the pitfall of putting a lazy thunk into an IVar and deferring work to the consumer; `put_` is head-strict only. — [monad-par paper §3](https://simonmar.github.io/bib/papers/monad-par.pdf)
- `spawn` (new + fork + put) "gives a static guarantee that a multiple-put exception cannot occur at runtime"; raw `fork/new/put` were kept for convenience, so the multiple-put error remains a dynamic check. — [monad-par paper §3.1](https://simonmar.github.io/bib/papers/monad-par.pdf)
- Safety gap: nothing in the shipped API stops an IVar escaping `runPar` and being used by another `runPar` ("the behaviour ... is undefined"); the paper notes the ST-style rank-2 fix `runPar :: (forall s. Par s a) -> a` but the implementation does not use it. — [monad-par paper §3.3](https://simonmar.github.io/bib/papers/monad-par.pdf)
- Determinism argument (§5.2): no transition empties a full IVar or changes its contents; a second `put` on a full IVar has no transition (error modeled as stuck); the (RunPar) rule only fires when the rest of the state has completed or deadlocked and been GC'd, so in the case of competing puts "one of them will not be able to complete ... and thus the runPar transition will never be applicable." Result: runPar either produces the same value consistently or no value (≡ ⊥). Full proof referred to Budimlić et al.'s Featherweight CnC. — [monad-par paper §5.2](https://simonmar.github.io/bib/papers/monad-par.pdf)
- Library scheduler: following Claessen's "poor man's concurrency", `data Trace = Fork Trace Trace | Done | Get (IVar a) (a -> Trace) | Put (IVar a) a Trace | New (IVar a -> Trace)`; "implementing suspension and resumption is to use continuation-passing ... a continuation-passing monad. The continuation result is fixed to be of type Trace". A blocked `get` stores its continuation in the IVar (`Blocked [a -> Trace]`); a `put` on a full IVar is `error "multiple put"`. — [monad-par paper §6.1–6.3](https://simonmar.github.io/bib/papers/monad-par.pdf)
- Two schedulers share the same monad: a sequential scheduler (IO, "using only deterministic operations (runPar uses unsafePerformIO)") and a work-stealing one (per-core `workpool :: IORef [Trace]`, steal loop). Deforesting `Trace` into `SchedState -> IO ()` was tried but gave no significant benefit at the time due to GHC optimiser issues. — [monad-par paper §6.2–6.4](https://simonmar.github.io/bib/papers/monad-par.pdf)
- Exceptions/⊥ in children: "If some subterm evaluates to ⊥ during execution of runPar, then the value of the whole runPar should be ⊥. The sequential scheduler implements this, but the parallel scheduler given above does not. In practice ... the likely result is a deadlock ... Since deadlock is semantically equivalent to ⊥, the result in this case is equivalent." A fix was planned. — [monad-par paper §6.3.1 Correctness](https://simonmar.github.io/bib/papers/monad-par.pdf)
- Evaluation was performance-only (overhead vs par/pseq, scaling vs Strategies; Strategies versions "on average 1% faster at 1 core, 2% slower at 12 cores"). I found no description of determinism testing in the paper. — [monad-par paper §7](https://simonmar.github.io/bib/papers/monad-par.pdf)
- Strategies docs: they "express deterministic parallelism: the result of the program is unaffected by evaluating in parallel. The parallel tasks evaluated by a strategy may have no side effects." A `Strategy` "should not return a value different from the one it was passed"; the runtime may discard sparks whose result is no longer required. Version 3 API is based on "Seq no More: Better Strategies for Parallel Haskell". — [Control.Parallel.Strategies, parallel-3.3.0.0](https://hackage-content.haskell.org/package/parallel-3.3.0.0/docs/Control-Parallel-Strategies.html)

### Inferences
- eml's `par` is closest to monad-par restricted to `spawn`-only use (fork-join with exactly one result per child), which is the subset where the paper itself says the dynamic multiple-put error is statically ruled out. eml has no IVars, so eml's determinism argument is simpler than monad-par's: each child is a closed computation whose only outputs are its return value or a Never-kind effect.
- The monad-par "Trace + scheduler" split is the same shape eml's VM can take: a sequential scheduler first, then a work-stealing scheduler that consumes the same suspended-continuation representation. monad-par's lesson is that the sequential scheduler is the reference semantics and the parallel one must agree on ⊥/exceptions too; monad-par's parallel scheduler originally did not (exceptions became deadlock). eml should make "exception in a child" a first-class case of the parallel scheduler from the start, not a later fix.
- Strategies' guarantee depends on an unchecked "no side effects" obligation; eml instead enforces the equivalent obligation by the effect row of `par` children (Never-kind only, no `Heap h`), which is strictly stronger.

### Gaps
- I did not find how the monad-par package itself is tested (e.g., whether its test suite compares schedulers); the paper is silent and I did not inspect the repo.
- I did not verify whether later monad-par releases fixed exception propagation in the parallel scheduler.

## Q2. LVars / LVish (Kuper, Newton et al.): determinism by construction, quasi-determinism, and deterministic errors

### Takeaway
LVars generalize IVars to lattice-valued monotone state with threshold reads; determinism follows from a confluence-style "Independence" lemma. Adding `freeze` breaks full determinism, giving quasi-determinism: every run that produces a value produces the same value, but some runs may raise an error. The determinism level is tracked in the type (`Par Det` vs `Par QuasiDet`), and only `Det` code can be run as pure. Conflicting writes produce an error deterministically (they reach the lattice top regardless of order), which is the LVars analogue of "the error itself is schedule-independent".

### Cited Findings
- Quasi-determinism: "all executions that produce a final value produce the same final value ... a quasi-deterministic program can be trusted to never change its answer due to nondeterminism; at worst, it might raise an exception on some runs." The exception "can in principle pinpoint the exact pair of freeze and write operations that are racing." — [Kuper, Turon, Krishnaswami, Newton, Freeze After Writing, POPL 2014, §1](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf)
- Conflicting puts whose lub is ⊤ make the program "deterministically raise an exception, indicating that conflicting writes to lv have occurred. This exception is analogous to the 'multiple put' error" of IVars; repeated puts of the same value do not raise. — [LVish POPL 2014 §2](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf)
- Freeze-after pattern: when `freeze` is used only after a global barrier (`runParThenFreeze`), determinism is regained "since no writes can subsequently occur." — [LVish POPL 2014 §1, §6](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf)
- Proof structure: quasi-determinism via "Strong Local Quasi-Confluence" (either the two steps rejoin within one step each, up to permutation of locations, or one side steps to `error`) built on an "Independence" frame lemma (an LVar computation taking p to p' would take p ⊔ pF to p' ⊔ pF). A runnable PLT Redex model was provided for experimentation. — [LVish POPL 2014 §4–5](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf)
- Static tracking: "data Determinism = Det | QuasiDet"; "if code uses freeze, it is marked as QuasiDet; thus, code that types as Det is guaranteed to be fully deterministic"; `runPar :: Par Det a -> a`, `runParIO :: Par lvl a -> IO a`, `freezeLV :: ... -> Par QuasiDet ()`. — [LVish POPL 2014 §6](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf)
- Library docs: `runParIO` on QuasiDet input "may throw a LVishException nondeterministically", but if it returns without exception "it always returns the same answer"; exception constructors `ConflictingPutExn`, `PutAfterFreezeExn`, `LVarSpecificExn`; `runParDetailed` "catches ALL exceptions that occur within the runPar, and returns them via an Either"; caveat that "nondeterminism may leak out" if users supply invalid `Eq` or non-total `compare` instances. — [Control.LVish, lvish-1.1.4](https://hackage.haskell.org/package/lvish-1.1.4/docs/Control-LVish.html)
- Debug support: `DbgCfg.dbgScheduling` — "In addition to logging debug messages, control thread interleaving at these points when this is True." — [Control.LVish, lvish-1.1.4](https://hackage.haskell.org/package/lvish-1.1.4/docs/Control-LVish.html)
- Related deterministic-by-construction systems compared in the paper: DPJ (type-and-effect system for disjoint regions, with an unsafe escape hatch), FlowPools (handlers but no general freeze, so fully deterministic). — [LVish POPL 2014 §8](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf)

### Inferences
- Compare to eml's "left child's exception wins": LVish's deterministic error comes from the lattice (the error state ⊤ is reached by every interleaving), while eml's comes from a fixed priority between siblings. Both make the *identity* of the error schedule-independent, but only if the implementation waits for (or deterministically resolves) the left child before reporting. LVish's quasi-determinism is exactly what eml would get if it allowed "first exception observed wins": same value when successful, but the error reported could vary. eml's rule is stronger than quasi-determinism provided the runtime never reports a right-child exception while the left child is still running.
- LVish's type-level `Det/QuasiDet` index is a precedent for eml's effect-row restriction on `par`: the guarantee is read off the type, and the "unsafe" route (`runParIO`) is the only way out. eml's Never-kind restriction plays the role of `Det`.
- `dbgScheduling` (controlling interleavings at log points) is a precedent for a VM debug mode that perturbs scheduling at `par`/join points to test that UI snapshots are schedule-independent.

### Gaps
- I did not read "Taming the Parallel Effect Zoo" (Kuper et al., PLDI 2014), which extends LVish with cancellation, memoization, and deadlock-related effects; it would be relevant to cancelling a sibling after an exception.
- I could not confirm from primary sources whether LVish's `dbgScheduling` randomizes schedules or how the LVish test suite used it.

## Q3. Cilk: determinacy races, SP-bags (Nondeterminator), Cilkscreen/Cilksan; cost; usefulness when the type system forbids sharing

### Takeaway
A determinacy race is two logically parallel accesses to the same location with at least one write. SP-bags detects all determinacy races for a given input by running the program serially (depth-first, i.e., the serial elision) while maintaining union-find "S-bags/P-bags" per procedure plus reader/writer shadow memory; it is near-linear time, constant-factor space, and measured at under 12x slowdown. It checks one input, all schedules, not all inputs. In a language whose types already forbid shared mutable state in parallel children, such a detector has nothing to find in user code; its value moves to checking the runtime/VM itself.

### Cited Findings
- Definition and guarantee: determinacy races "result when one thread updates a location in shared memory while another thread is concurrently accessing the location"; "If a Cilk program run on a given input data set has a determinacy race, our debugging tool ... the 'Nondeterminator,' guarantees to detect and localize the race." — [Feng & Leiserson, Efficient Detection of Determinacy Races in Cilk Programs, SPAA 1997, abstract](https://homes.cs.washington.edu/~mernst/teaching/6.893/readings/feng-spaa97.pdf)
- Cost: for a program running in T time on one processor with v shared locations, O(T α(v,v)) time (α = inverse Ackermann); at most a constant factor more space; "slowdown of less than 12 compared with the serial execution time of the original optimized code." — [Feng & Leiserson 1997, abstract](https://homes.cs.washington.edu/~mernst/teaching/6.893/readings/feng-spaa97.pdf)
- Scope: "The Nondeterminator is not a program verifier ... it cannot certify that the program is race free for all input data sets ... What it verifies is that every possible scheduling of the program execution produces the same behavior. Moreover ... it is itself a serial program." — [Feng & Leiserson 1997 §1](https://homes.cs.washington.edu/~mernst/teaching/6.893/readings/feng-spaa97.pdf)
- Mechanism: every read/write is instrumented by the compiler; the program runs "in a serial, depth-first fashion (like a C execution)"; each procedure F has an S-bag (descendants of completed children that logically precede the current strand) and a P-bag (those that operate logically in parallel), kept as disjoint sets (Tarjan union-find); shadow spaces `writer(l)` and `reader(l)` store procedure IDs; a race is reported when the previous writer/reader of l is found (FIND-SET) in a P-bag. — [Feng & Leiserson 1997 §2, Fig. 7–8](https://homes.cs.washington.edu/~mernst/teaching/6.893/readings/feng-spaa97.pdf)
- Follow-ups: Nondeterminator-2 (ALL-SETS, data races with locks; Cheng et al. SPAA 1998); Nondeterminator-3 uses a parallel SP-maintenance (SP-hybrid); the current OpenCilk tool is Cilksan, which "instruments a program to detect determinacy race bugs at runtime". — (search snippet) [Cilk tool suite](https://cilk.mit.edu/tools/), [Cheng et al. SPAA 1998](https://courses.csail.mit.edu/6.895/fall03/handouts/papers/p298-cheng.pdf)
- Serial elision as the semantics: "The behavior of a deterministic OpenCilk program is defined in terms of its serialization" (C/C++ with `_Cilk_spawn`/`_Cilk_sync` deleted, `_Cilk_for` → `for`); data races are a "new kind of undefined behavior"; "If the serialization has undefined behavior, the OpenCilk program also has undefined behavior." — [OpenCilk Language Extension Specification](https://cilk.mit.edu/docs/OpenCilkLanguageExtensionSpecification.htm)
- Modern race detectors remain expensive: "race detection remains expensive in practice (with overheads exceeding an order of magnitude for sequential runs, e.g., [Utterback et al. 2016; Xu et al. 2020])". — [Westrick, Arora, Acar, ICFP 2022 §1](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- I found no primary figure for Cilkscreen's (Intel Cilk Plus) slowdown. — (search only)

### Inferences
- The structure "run the serial elision, maintain series/parallel relation, check every access against shadow state" maps directly onto an eml VM that runs `par` children sequentially: the sequential VM *is* the serial elision, so an SP-bags-style checker could be added as a debug mode at modest cost (union-find per task + shadow per heap cell).
- But in eml user code it would be checking an invariant the type system already proves (no `Heap h` in `par` children, Never-kind effects only, linear values moved not shared). The remaining sources of races are in the implementation: RC updates on shared immutable objects (dup/decref from two tasks), in-place reuse (Perceus reuse of a cell that is actually shared), and the scheduler's own data structures. A determinacy-race checker for *VM-internal writes* (e.g., "this in-place update/reuse target was allocated by a logically parallel task, or is reachable from one") is the useful analogue — essentially MPL's entanglement check (Q4) specialized to RC/reuse.
- Because the guarantee is per input and all schedules, the cheapest practical eml check is: run the UI test corpus under the sequential VM with such instrumentation; any hit is a compiler/runtime bug, not a user bug.

### Gaps
- No primary source found for Cilkscreen's algorithm or overhead (it is believed to derive from SP-bags, but I did not confirm this).
- I did not read Cilksan's paper/docs for its current overhead.

## Q4. MPL / MaPLe: disentanglement, hierarchical heaps, and runtime entanglement detection/management

### Takeaway
MPL's hierarchical heaps mirror the fork-join task tree: each leaf task allocates in its own heap, heaps merge into the parent at join, and GC of each heap is independent provided there are no cross-pointers between concurrently allocated heaps ("disentanglement"). Determinacy-race-freedom implies disentanglement, and purely functional programs are disentangled by construction. Since no type system was known for disentanglement with effects, MPL first detected entanglement dynamically (ICFP 2022, checks only on mutable dereferences, <5% overhead, program safely terminated on detection), then managed it (PLDI 2023: entangled objects are tracked and pinned, so all programs run).

### Cited Findings
- MPL README lists "Provably efficient parallel garbage collection based on hierarchical memory management and disentanglement", with papers: Raghunathan et al. ICFP 2016; Guatto et al. PPoPP 2018; Westrick et al. POPL 2020; Arora et al. POPL 2021; Westrick et al. ICFP 2022; Arora et al. PLDI 2023. The README itself documents no entanglement flag; `-debug-runtime true` uses a runtime with assertions enabled. — [MPLLang/mpl README](https://github.com/MPLLang/mpl)
- Hierarchical heaps: when two siblings complete, "their heaps are merged with their parent task"; pointers are classified as up, down, internal, or cross by relative heap position; "Disentanglement allows for pointers to point up, down, or internal ... and disallows cross-pointers"; without cross-pointers each heap can be collected independently (suspended heaps by concurrent non-moving mark-sweep, leaf heaps by local Cheney copying, pausing only that task); GC relies on "lightweight snapshots, remembered sets, and a write barrier". — [ICFP 2022 §2](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- Why it must be enforced: Arora et al.'s memory manager "assumes disentanglement, but they do not enforce or check for it ... if an entangled program is executed, the garbage collector will not behave correctly, which could cause the program to crash, or (worse) return an incorrect result." — [ICFP 2022 §1](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- By construction: "in a strict call-by-value language (e.g. Parallel ML), if mutable data is outlawed ... then disentanglement is guaranteed by construction." — [ICFP 2022 §1](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- POPL 2020 proves that determinacy-race-free nested-parallel programs are disentangled: "Intuitively speaking, race-free programs are disentangled because they prohibit communication between concurrently executing threads. Disentanglement, however, is weaker than race-freedom." — [Westrick, Yadav, Fluet, Acar, Disentanglement in Nested-Parallel Programs, POPL 2020 §1, §3.3](https://www.cs.cmu.edu/~swestric/20/popl-disentangled.pdf)
- Static vs dynamic: no type system for disentanglement is known; a race-freedom type system would ensure it by implication but "would also outlaw the non-deterministic programs that we wish to allow"; entanglement is undecidable. — [ICFP 2022 §1](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- Detection design: a dynamic semantics consults the computation graph's parallel/sequential relation on mutable dereferences only ("the semantics requires checks for mutable objects only"; immutable reads "are always safe for disentanglement", even when reached through a mutable object); entanglement steps to an `ERROR` state that cannot step, i.e., "the program is (safely) terminated". Soundness ("no missed alarms") and completeness ("no false alarms") are proved (Thms 3.1, 3.2). — [ICFP 2022 §1, §3](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- Execution dependence: "on the exact same program—even on the same input—it is possible that a different execution might not exhibit entanglement"; good diagnostics are left as future work. — [ICFP 2022 §1](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- Implementation cost: a direct SP-order-maintenance implementation (borrowed from race detection) cost "as much as 2x overhead"; tracking a small set of "entanglement candidates" and pruning queries on others brought overhead to "typically around 5% or less on both 1 and 72 processors"; 23 benchmarks, all naturally disentangled (detector confirms); per-object vertex IDs replaced by per-chunk IDs (space O(min(N, M/B))). Integrated with read/write barriers and GC. — [ICFP 2022 §1](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- Management (PLDI 2023): distinguishes disentangled and entangled objects "by observing the memory actions of parallel threads using read/write barriers", barriers only for mutable data; entangled objects may not be relocated, so a hybrid GC "pins live entangled objects in place and copy-collects disentangled objects"; the extended compiler supports "all features of the Parallel ML language, including unrestricted effects". — [Arora, Westrick, Acar, Efficient Parallel Functional Programming with Effects, PLDI 2023](https://www.cs.cmu.edu/~swestric/23/epfpe.pdf)
- A separation logic for disentanglement exists: "DisLog: A Separation Logic for Disentanglement" (POPL 2024). — [Westrick's publication page](https://www.cs.cmu.edu/~swestric/) (title only; not read)

### Inferences
- eml's `par` restriction (no `Heap h` in children) is precisely MPL's "mutable data outlawed ⇒ disentangled by construction" case, applied per `par` rather than globally. So eml should not need entanglement detection for user-visible semantics. The analogue that still matters is RC: in an RC runtime (Perceus-style), a child doing `dup`/`decref` on an object allocated by the parent is a *write* to that object's header even though the object is immutable at the language level. MPL avoids this because it is a tracing GC; eml cannot. This is where "mark objects shared before publishing" comes in.
- Relation to "mark shared before publishing": MPL's up-pointers (child reads parent's objects) are allowed and free; the hazard in eml is not cross-pointers but concurrent non-atomic RC on objects reachable from two tasks. Marking everything reachable from a continuation/argument as "shared" (atomic RC) at the moment it may become visible to another worker is the RC analogue of MPL's invariant "a leaf task may only mutate (here: RC-update non-atomically) objects in its own heap". MPL's ICFP 2022 candidate-pruning idea suggests the cost can be confined to the few objects that actually cross; with private deques (Q5) the "crossing moment" is exactly a steal.
- A cheap, MPL-style runtime check eml's VM could keep on in debug builds: tag each heap object with the allocating task (or chunk), and assert on every non-atomic RC update / in-place reuse that the object is either marked shared or allocated by the current task or an ancestor that is suspended. This mirrors MPL's "check only mutable operations" pruning, with RC updates and reuse as the "mutable operations". eml's existing `debug_heap` checks are a natural home.

### Gaps
- I did not read POPL 2021 (Arora et al., space-efficient) or PLDI 2023 in full; details of how entangled objects are "pinned" and unpinned at joins are only from the abstract/intro.
- I found no statement of whether MPL ships with detection or management enabled by default today.

## Q5. Acar, Charguéraud, Rainey: work stealing with private deques (PPoPP 2013)

### Takeaway
Each processor's deque is private (no concurrent access, no fences on push/pop); load balancing is by message passing, with idle processors sending steal requests (receiver-initiated) or busy ones periodically offering work (sender-initiated), and owners answering when they poll. They prove bounds comparable to concurrent-deque work stealing, with a parameter for polling delay.

### Cited Findings
- Problem: concurrent deques "require expensive memory fences in modern weak-memory architectures" and are hard to extend; private deques "eliminate the need for memory fences from local operations and enable the design and implementation of efficient techniques for reducing task-creation overheads", at the cost of communication. — [Acar, Charguéraud, Rainey, Scheduling Parallel Programs by Work Stealing with Private Deques, PPoPP 2013, abstract](http://www.chargueraud.org/research/2013/ppopp/full.pdf)
- Mechanism: a thief "sends a message to a randomly chosen victim", which replies with tasks or "indicates that victim's deque is empty"; "each processor periodically polls ... its message queue". Two algorithms (sender- and receiver-initiated) with efficiency proofs under a probabilistic model that accounts for polling delay (parameter δ). — [PPoPP 2013 §1–3](http://www.chargueraud.org/research/2013/ppopp/full.pdf)

### Inferences
- For eml the useful property is that, with private deques, a task leaves its owner only at a well-defined point (the owner's reply to a steal request), executed by the owner itself. That is the natural place to do the "mark shared" traversal on exactly the continuation being handed off, so un-stolen `par` children pay nothing — matching the eml note about marking only actually-moved continuations. With concurrent (Chase–Lev) deques the thief takes the task without the owner's involvement, so marking must happen eagerly at push time or be done by the thief under synchronization.
- Polling also gives a deterministic safe-point structure that an eml bytecode VM already has (instruction dispatch loop), so the cost of polling is likely low.

### Gaps
- I did not extract the paper's measured overheads or whether it discusses memory-management interaction (sharing/marking); none was evident from the abstract.

## Q6. Exceptions in fork/join: who wins, waiting vs cancelling, determinism

### Takeaway
Rayon (`join`) and Cilk/OpenCilk both pick the exception deterministically by serial order (first closure / serially earliest) and both wait for all children; Java ForkJoin `invokeAll` throws "any one" and may cancel others (nondeterministic); Domainslib re-raises a task's exception on `await`, so the winner is determined by the order in which the program awaits; JCilk aborts siblings. eml's "left child's exception wins" matches Rayon and Cilk.

### Cited Findings
- Rayon `join`: "No matter what happens, both closures will always be executed. If a single closure panics, whether it be the first or second closure, that panic will be propagated ... If both closures panic, join() will panic with the panic value from the first closure." — [rayon::join docs](https://docs.rs/rayon/latest/rayon/fn.join.html)
- OpenCilk: "If a spawned function terminates with an exception, the exception propagates from the point of the corresponding sync"; with multiple pending exceptions, "later exception objects (in the serial execution order of the program) are destructed in an unspecified order" before "the earliest exception is caught"; for `_Cilk_for`, "it is unspecified which other loop iterations execute, but no other iteration is terminated early", and the loop "throws the exception that would have occurred first in the serialization of the program"; implicit sync on block exit "including abnormal exit due to an exception"; implicit sync before a `throw`. — [OpenCilk Language Extension Specification](https://cilk.mit.edu/docs/OpenCilkLanguageExtensionSpecification.htm)
- WG14 Cilk draft notes that a thrown exception can cause code to run that the serial execution would not have run. — (search snippet) [WG14 N1665](https://open-std.org/JTC1/SC22/WG14/www/docs/n1665.htm)
- JCilk: an exception thrown by one computation signals its siblings to abort, so only a single exception from the enclosing try block is handled; on one processor semantics match serial Java. — (search snippet) [Programming with Exceptions in JCilk, MIT](https://dspace.mit.edu/handle/1721.1/30275)
- Java `ForkJoinTask.invokeAll(t1, t2)`: returns when all are done "or an (unchecked) exception is encountered, in which case the exception is rethrown. If more than one task encounters an exception, then this method throws any one of these exceptions. If any task encounters an exception, the other may be cancelled. However, the execution status of individual tasks is not guaranteed upon exceptional return." Rethrown exceptions carry stack traces of both the joining and the throwing thread "when possible". — [Java 21 ForkJoinTask](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ForkJoinTask.html)
- OCaml Domainslib `Task.await`: "If the task have raised an exception, then [await] raises the same exception." No documented exception behavior for `parallel_for`/`parallel_for_reduce`/`parallel_scan`. — [domainslib task.mli](https://raw.githubusercontent.com/ocaml-multicore/domainslib/main/lib/task.mli)
- monad-par: original parallel scheduler turned a child's ⊥ into a likely deadlock (see Q1). LVish: errors (conflicting put) are deterministic; freeze/put races give nondeterministic exceptions (quasi-determinism) (see Q2). — [monad-par §6.3.1](https://simonmar.github.io/bib/papers/monad-par.pdf), [LVish POPL 2014](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf)

### Inferences
- Two designs give determinism: (a) wait for both, then pick by fixed priority (Rayon, Cilk, eml) — deterministic but the right child runs to completion even when its result is discarded; (b) cancel siblings (JCilk, Java "may") — faster but then which exception is observed, and which side effects happened, depend on timing. Since eml children have no observable side effects other than the result and Never-kind effects (and output is presumably excluded from Never-kind rows), cancelling the right child after the left raises is semantically invisible *as long as the left's exception is reported*. But cancelling the left child because the right raised first would break "left wins". So the safe optimization is asymmetric: a left exception may cancel the right; a right exception must wait for the left to finish (or raise).
- Divergence: if the left child diverges and the right raises, "left wins" (Rayon/Cilk semantics) means the whole `par` diverges, matching the sequential elision (left then right). A runtime that reported the right exception early would differ from the sequential VM — UI tests would not catch this (they terminate), so it should be a stated rule.
- Rayon's choice of the first closure's panic is the precedent closest to eml in a systems language with work stealing; its "both closures always run" is the conservative variant.

### Gaps
- No primary source for Intel Cilk Plus's runtime behavior (whether it actually aborts siblings) beyond the OpenCilk spec text; the spec does not say siblings are aborted.
- Domainslib's behavior for `parallel_for` when an iteration raises is undocumented; I did not read the implementation.
- Rayon `scope` panic behavior not checked.

## Q7. How determinism is tested in practice

### Takeaway
The dominant practical oracle is the serial elision: Cilk defines semantics by it and the Nondeterminator runs the serial execution with instrumentation to certify all schedules for one input. The Haskell libraries rely on proofs/type restrictions rather than schedule testing, with LVish offering a debug knob to control interleavings. MPL relies on an always-on cheap runtime check. General tools (rr chaos mode, Hermit) randomize or fix thread schedules for any program.

### Cited Findings
- Cilk: semantics defined by serialization; Nondeterminator verifies "every possible scheduling of the program execution produces the same behavior" for the given input by a serial run. — [OpenCilk spec](https://cilk.mit.edu/docs/OpenCilkLanguageExtensionSpecification.htm), [Feng & Leiserson 1997](https://homes.cs.washington.edu/~mernst/teaching/6.893/readings/feng-spaa97.pdf)
- monad-par: determinism by semantics argument; two schedulers (sequential and work-stealing) over the same Trace; paper evaluates only performance. — [monad-par paper](https://simonmar.github.io/bib/papers/monad-par.pdf)
- LVish: proof of quasi-determinism plus a runnable PLT Redex model; library `dbgScheduling` "control[s] thread interleaving" at debug points. — [LVish POPL 2014](https://users.soe.ucsc.edu/~lkuper/papers/lvish-popl14.pdf), [Control.LVish](https://hackage.haskell.org/package/lvish-1.1.4/docs/Control-LVish.html)
- MPL: entanglement detection proven sound/complete and cheap enough (<5%) to "remain deployed"; on 23 benchmarks the detector confirmed they were disentangled. — [ICFP 2022](https://www.cs.cmu.edu/~swestric/22/icfp-detect.pdf)
- rr chaos mode assigns random priorities to threads to reproduce intermittent bugs; Hermit's `--chaos` with `--sched-seed` explores interleavings deterministically from a seed. — (search snippets) [rr chaos mode](https://robert.ocallahan.org/2016/02/introducing-rr-chaos-mode.html), [Hermit](https://developers.facebook.com/blog/post/2022/11/22/hermit-deterministic-linux-testing/)

### Inferences
- For eml's UI snapshot tests, the natural oracle is "parallel VM output == sequential VM output" (serial elision), checked by running each `run`/`run-fail` test under (1) the sequential scheduler, (2) the parallel scheduler with N workers, and (3) a seeded randomized scheduler (random steal victims, random yields at `par`/join, optionally "always steal" to force every child to migrate). Seeds should be printed on failure for replay, like Hermit.
- A "steal everything" mode is especially valuable for eml: it forces every `par` child through the mark-shared / migration path, so RC-sharing bugs show up deterministically on a single core instead of probabilistically under load.
- Because eml's determinism is by construction (types), these tests test the *implementation* (scheduler, RC sharing, exception priority), not user programs — the same division MPL draws between "disentangled by construction" and "runtime must still be correct".
- Combined with existing `debug_heap` and `RunStats`: work counts like boxes/unboxes are schedule-independent if the parallel VM does the same work as the sequential one; `peak_objects` will not be, so benchmark snapshots should be pinned only under the sequential scheduler.

### Gaps
- I found no published account of a Haskell parallel library systematically testing determinism across randomized schedules; the claim that they rely on proofs is based on absence in the papers read.
- I did not check Rayon's or Domainslib's test suites for schedule-randomization tooling (e.g., loom is used in some Rust crates, but I did not confirm Rayon uses it).
