# OCaml 5 multicore runtime and effect handlers: continuations across domains and how parallel safety is tested

Notation: "[read]" = read directly in the primary source (paper text extracted with pdftotext, runtime source, manual, library source). "[inferred]" = my inference. Sources fetched 2026-10-10.

## Q1. Can a continuation captured on one domain be resumed on another? Runtime mechanics; Domainslib async/await

### Takeaway
Yes. OCaml 5 continuations are heap-detached fiber stacks that any domain may resume. The runtime enforces one-shot use with an atomic CAS that takes the stack pointer out of the continuation object; it skips the CAS when only one domain is running. Domainslib relies on this: `await` parks the continuation in the promise, and whichever pool worker dequeues the resumption job resumes it. The manual does not explicitly promise cross-domain resumption; it is shown by runtime code and by library practice.

### Cited Findings
- [read] Fibers are allocated on the C heap with malloc and freed when the handled computation returns a value or raises. Resuming twice was an `Invalid_argument` in the paper; OCaml 5 raises `Continuation_already_resumed`. Effects may not cross C frames: "we do not allow effects to propagate across C frames as the C frames would become part of the captured continuation." — [Retrofitting Effect Handlers onto OCaml, PLDI 2021, §3 and §5.2](https://arxiv.org/abs/2104.00250)
- [read] Fiber layout (§5.2): `handler_info` sits at the stack bottom (parent fiber pointer plus value, exception and effect closures). The initial OCaml frame area is 16 words; on overflow the whole fiber is copied to a region twice the size, with overflow checks in function prologues and a 16-word red zone for leaf functions. A switch saves and loads only the exception pointer and the stack pointer. — [PLDI 2021](https://arxiv.org/abs/2104.00250)
- [read] Unresumed continuations leak the fiber's malloc'd stack and other resources. The paper's trade-off is to expect user code to resume each continuation exactly once. It suggests an optional `Gc.finalise (fun k -> try ignore (discontinue k Unwind) with _ -> ()) k`, which is not the default because finalisers on every continuation are expensive (§5.6). — [PLDI 2021](https://arxiv.org/abs/2104.00250)
- [read] Manual: "OCaml does not support multi-shot continuations"; "Attempting to use a continuation more than once raises a Continuation_already_resumed exception" (a dynamic check); "every continuation must be eventually either continued or discontinued"; "Not resuming continuations will leak the memory allocated for the fibers"; effects are "incompatible with the use of callbacks from C to OCaml"; an effect cannot be performed from a signal handler. — [OCaml manual, Effect handlers](https://ocaml.org/manual/5.3/effects.html)
- [read] Runtime one-shot enforcement in `caml_continuation_use_noexc` (runtime/fiber.c). It swaps the continuation's stack field with NULL, with the comment "this forms a barrier between execution and any other domains that might be marking this continuation":
  `if (caml_domain_alone()) { Field(cont, 0) = null_stk; return v; } if (atomic_compare_exchange_strong(Op_atomic_val(cont), &v, null_stk)) return v; else return null_stk;`
  `caml_continuation_use` raises `Effect.Continuation_already_resumed` when it gets NULL. `caml_continuation_replace` writes a stack back with a CAS from NULL, guarded by `CAMLassert`. Each stack gets a unique id from `atomic_fetch_add(&fiber_id, 1)`. — [ocaml/ocaml runtime/fiber.c](https://github.com/ocaml/ocaml/blob/trunk/runtime/fiber.c)
- [read] ICFP 2020: the concurrent mark-and-sweep GC uses a deletion barrier, so "before switching control to a fiber, all the objects on the fiber stack must be marked". This creates "a race between a mutator wanting to switch to a fiber and other domains marking the fiber stack". In Multicore OCaml (2020) the fix was a per-fiber lock: a mutator spin-waits on a locked fiber, and a GC thread skips one. The paper contrasts this with Go, whose hybrid write barrier avoids marking goroutines before a switch. — [Retrofitting Parallelism onto OCaml, ICFP 2020, §5.4 and related work](https://arxiv.org/abs/2004.11663)
- [read] Domainslib `Task` (lib/task.ml): a promise is `Atomic.t` of `Pending of (('a, unit) continuation * task_chan) list | Returned | Raised`. `async` enqueues `Work (fun _ -> step (do_task f) p)` on the pool's multi-channel. `await` returns at once if the promise is resolved; otherwise it does `perform (Wait (promise, pd.task_chan))`. The `step` handler for `Wait` uses a CAS loop to push `(k, c)` onto `Pending`, or resumes `k` at once if the promise resolved in the meantime. `do_task` does `Atomic.exchange p result` and, for each waiter, sends `Work (fun _ -> continue k v)` to the waiter's channel. The continuation is therefore resumed by whichever worker domain dequeues that job, not necessarily the one that captured it. `Task.run` lets the calling domain help run pool work until its promise resolves, and is wrapped in `Domain_local_await.using` so that resumption from foreign domains (`send_foreign`) works. — [domainslib lib/task.ml](https://github.com/ocaml-multicore/domainslib/blob/main/lib/task.ml)
- [read] Eio: "Promises are thread-safe; you can wait for a promise in one domain and resolve it in another"; but "Fibers are scheduled cooperatively within a single domain, but fibers in different domains run in parallel". For `Domain_manager.run`: "You must ensure that the function passed to `run` doesn't have access to any non-threadsafe values... The type system does not check this." — [Eio README](https://github.com/ocaml-multicore/eio)
- [read] `Mutex.unlock` "Raises `Sys_error` if the mutex is unlocked or was locked by another thread" (error-checking mutexes since 4.12). The docs do not mention effects. — [Mutex API](https://ocaml.org/manual/5.3/api/Mutex.html)

### Inferences
- [inferred] The CAS in `caml_continuation_use_noexc` plays two roles: it is the dynamic one-shot (linearity) check, and it is the synchronisation point with other domains' GC marking of the stack. The comment says the latter, and it appears to be the OCaml 5 successor of the ICFP 2020 per-fiber lock. The `caml_domain_alone()` fast path shows the runtime paying for atomics only once a second domain exists. For eml, a statically linear `once` continuation would not need the CAS as a one-shot check. It may still need a publication or ownership-transfer barrier when the continuation moves to another worker, and must handle interaction with any concurrent heap scanning (RC does not scan stacks, but "mark shared before publishing" plays the analogous role).
- [inferred] Because the runtime allows cross-domain resumption, hidden thread-affine state in the suspended computation is a real hazard. One example is a `Mutex` held across `perform`: after resumption on another systhread or domain, `unlock` raises `Sys_error`. Another is domain-local storage (DLS) read before and after suspension, which can differ. OCaml catches neither statically. eml's closed rows plus linearity could rule these out by type.
- [inferred] Domainslib's resume-by-enqueue design (the completer does not resume the waiter inline; it sends a `Work` closure to the waiter's pool channel) maps directly onto "once continuation as a heap closure moved to another worker".

### Gaps
- I found no normative statement in the OCaml manual or the `Effect` API docs that resuming on a different domain is supported. The evidence is runtime code comments and library practice (Domainslib, Eio promises). The Effect API page does not mention domains.
- I did not verify how systhreads (Thread) interact with continuations moved between threads in the same domain, for example `Thread.self` or masking state.

## Q2. Unhandled effects at a domain/task boundary; how libraries scope effects across workers

### Takeaway
Handlers do not cross domains. `Domain.spawn f` runs `f` with no user handlers installed. A `perform` with no matching handler raises `Effect.Unhandled` at the perform site, and if uncaught the exception is re-raised by `Domain.join`. Libraries handle this by installing their scheduler's handler around every task, at the bottom of each job they run (Domainslib `step`, Moonpool runners, Picos schedulers). Code performing a library's effects outside its runner fails dynamically.

### Cited Findings
- [read] "`Unhandled e` is raised when effect `e` is performed and there is no handler for it"; `perform` "Raises `Unhandled` if there is no handler". — [Effect API](https://ocaml.org/manual/5.3/api/Effect.html)
- [read] The design rationale (PLDI 2021 §3): since handlers "do not ensure that all the effects are handled", when such an effect "bubbles up to the top-level, we discontinue the continuation with an Unhandled exception so that the exception handlers may run and clean up the resources". The formal semantics models this as rule EffUnHn; the Callback rule makes an effect hitting a C frame also raise Unhandled. — [PLDI 2021](https://arxiv.org/abs/2104.00250)
- [read] `Domain.join d`: "If `d` raises an uncaught exception, then that is re-raised by `join d`." The Domain docs say nothing about effects. — [Domain API](https://ocaml.org/manual/5.3/api/Domain.html)
- [read] Domainslib wraps every job in `step` (the handler for `Wait`), both in `async` (`Work (fun _ -> step (do_task f) p)`) and in `run`. `Task.run` on the pool's channel fails with `failwith "Task.run: tasks are active on pool"` on `Quit`. — [domainslib task.ml](https://github.com/ocaml-multicore/domainslib/blob/main/lib/task.ml)
- [read] Moonpool: `Fut.await` "suspends its caller task; the suspended task is then parked, and will be resumed when the future is completed", while the worker "moves on to another task". Fork-join "needs to run inside an effect handler provided by the thread pool" and "must run on a pool (using `Runner.run_async` or inside a future via `Fut.spawn`)". Moonpool provides "task local storage (like thread-local storage, but per task)". — [Moonpool README](https://github.com/c-cube/moonpool)
- [read] Picos defines a small set of effects (`Trigger.Await`, `Computation.Cancel_after`, `Fiber.Current`, `Fiber.Yield`, `Fiber.Spawn`) that any scheduler implements. It calls itself "the POSIX of effects based schedulers", and "A central idea of Picos is to provide a collection of building blocks for parallelism safe cancelation". Example multi-domain scheduler: `Picos_mux_random.run_on ~n_domains:2 main`. — [Picos docs](https://ocaml-multicore.github.io/picos/doc/picos/Picos/index.html)
- [read] Eio: "most Eio functions can only be used from Eio domains"; "You can resolve an Eio promise from non-Eio domains (or systhreads)". — [Eio README](https://github.com/ocaml-multicore/eio)
- [read] The multicoretests bug list includes "Crash on unhandled Effect in bytecode" ([ocaml/ocaml#11669](https://github.com/ocaml/ocaml/issues/11669)) and effect-related crashes involving frame pointers ([#12535](https://github.com/ocaml/ocaml/issues/12535)) and s390x ([#12486](https://github.com/ocaml/ocaml/issues/12486)). — [multicoretests README](https://github.com/ocaml-multicore/multicoretests)

### Inferences
- [inferred] OCaml has no static effect typing, so "this code may only run under scheduler X" is enforced only by `Unhandled` at runtime. That is why Picos standardises a shared effect vocabulary, so that libraries do not need to know which scheduler is running them. eml's requirement that spawn take closed rows, and that `par` children perform only `never` operations, is the static counterpart of this runtime failure mode.
- [inferred] Domainslib, Moonpool and Picos all re-install the scheduler handler at the bottom of every job on every worker. Effect scoping is therefore per job, not per domain. A continuation moved to another worker carries its handler chain inside the fiber (`handler_info` at the stack bottom), so the resumed computation sees the same handlers. The outermost scheduler handler, however, is whichever `step` frame the resuming worker runs (`continue k v` runs inside that worker's job).

### Gaps
- I did not confirm the exact OCaml 5 runtime behaviour when an effect reaches the bottom of a domain's main fiber (whether it is discontinued with `Unhandled` as in the 2021 paper or raised at the perform site; the manual says "raised at the point of the corresponding perform").
- I did not fetch Picos' detailed docs on cross-domain fiber resumption (whether `Trigger` signalling from another domain resumes the fiber on the signaller's domain or the original one); the index page does not say.

## Q3. OCaml 5 memory model: local DRF, guarantees for racy programs, runtime implications

### Takeaway
The model comes from Dolan, Sivaramakrishnan and Madhavapeddy, "Bounding Data Races in Space and Time", PLDI **2018** (the task's "PLDI 2022" is wrong; the OCaml manual cites PLDI 2018). It gives local DRF-SC (race-free fragments behave sequentially even if other parts race), memory and type safety under races, and no out-of-thin-air values. The cost on ARMv8 is a cheap barrier or a branch per load or store (about 0.6%); x86 has no overhead.

### Cited Findings
- [read] Abstract: "Our local data race freedom property guarantees that all data-race-free portions of programs exhibit sequential semantics… (no overhead on x86, ~0.6% on ARM)". — [Dolan, Sivaramakrishnan, Madhavapeddy, PLDI 2018](https://kcsrk.info/papers/pldi18-memory.pdf)
- [read] Data races in Java are bounded in space but "not bounded in time". Local DRF requires preventing load buffering, because it would let future races affect present computations. On ARMv8 the scheme either adds "a branch after loads" or "a dmb ld barrier before stores". Atomic stores compile to exchanges (not `stlr`), plus `dmb ld` on atomic loads and `dmb st` on atomic stores, so that ordering with neighbouring non-atomic accesses holds. The model "prohibits out-of-thin-air behaviours at a small" cost (§9). — [PLDI 2018](https://kcsrk.info/papers/pldi18-memory.pdf)
- [read] Manual: "A program without data races will only exhibit sequentially consistent behaviours"; "While programs with data races may observe non-sequentially consistent behaviours, they will not crash"; "even for programs with data races, memory safety is preserved"; "The OCaml memory model is bounded both in space and time". Atomic locations come from the `Atomic` module, and races on them are not data races. Non-atomic locations are modelled as timestamped histories: a read may return any history entry not older than the reader's frontier. Named non-compliant operations that can tear: `Array.blit` on float arrays, flat-float arrays and float-only records on 32-bit, and mixed-size access through `Bytes`. — [OCaml manual, Memory model](https://ocaml.org/manual/5.3/memorymodel.html)
- [read] TSan blog: "data races in OCaml do not cause crashes and do not constitute undefined behaviour." — [Tarides, Off to the races (2023)](https://tarides.com/blog/2023-10-18-off-to-the-races-using-threadsanitizer-in-ocaml/)
- [read] multicoretests found "Tearing in `Array.sub`/`Array.copy` memcpy" ([ocaml/ocaml#13950](https://github.com/ocaml/ocaml/issues/13950)). Runtime C primitives can break the model's no-tearing promise even though compiled OCaml code honours it. — [multicoretests README](https://github.com/ocaml-multicore/multicoretests)

### Inferences
- [inferred] Why it matters for runtime design: a memory-safety guarantee for racy programs means every runtime primitive (allocation, initialisation, blit/copy, GC marking, RC updates) must stay safe under arbitrary races in user code. Publication safety of newly allocated objects (initialising writes become visible before the pointer) must be built into the allocation and store compilation scheme. The `Array.sub`/`copy` tearing bug shows that C runtime helpers using plain `memcpy` are where this breaks. For eml's "mark shared before publishing" RC scheme, the analogue is that the shared mark and the object's contents must be visible before (release-ordered with) the pointer's publication, and that non-atomic RC on objects that are not yet shared must be unobservable by other workers.
- [inferred] eml's static design (closed rows, `never`-only `par` children, linear transfer) aims at race freedom by construction. OCaml chose a dynamic-language-style guarantee (racy but safe) instead. eml still needs a fallback answer for what a race does if a type-system or runtime bug lets one through. OCaml's answer is "no crash, bounded weirdness".

### Gaps
- I did not confirm how OCaml 5's current native backends implement the PLDI 2018 scheme (for example, whether ARM64 uses the branch-after-load or the dmb-ld variant, and how `caml_initialize`/allocation publication is fenced). The PLDI 2018 paper predates OCaml 5.

## Q4. ThreadSanitizer support (OCaml 5.2+): integration, findings, limits, effects/fibers

### Takeaway
Since OCaml 5.2, `--enable-tsan` (opam `ocaml-option-tsan`) makes ocamlopt instrument every memory access and function entry and exit. The runtime tells TSan which frames are exited and re-entered across exceptions, `perform` and `continue`. The slowdown is 2-7x with 4-7x more memory. TSan found races in the runtime, Domainslib, Saturn, Eio and Irmin. Its limits: it reports only executed races, keeps a 4-access history per location, needs every linked object instrumented, and delays signals. It cannot find logical races, which is how PBT found a GC compaction race that TSan would miss.

### Cited Findings
- [read] Enabling: "configure the compiler with --enable-tsan" or `opam switch create … ocaml-option-tsan`. "all programs compiled by ocamlopt are instrumented with calls to the TSan runtime." Initialising writes and reads of immutable locations are not instrumented. "There is no way to disable instrumentation in OCaml code"; C functions can opt out with `CAMLno_tsan`. Platforms: x86_64 FreeBSD/Linux/macOS; arm64 Linux/macOS; POWER, riscv and s390x Linux. Requires GCC 11 or Clang 14 or later. — [OCaml manual, TSan chapter](https://ocaml.org/manual/5.3/tsan.html)
- [read] Limits (manual): "TSan reports only the data races encountered during execution"; "TSan remembers only a finite number of memory accesses per memory location" (4 at time of writing); "a tiny probability to miss a race if two threads access the same location at the same time"; no false positives between two OCaml accesses, with one theoretical OCaml/C case (values initialised from C without `caml_initialize`); instrumented programs "should only be linked with OCaml or C objects also instrumented with TSan"; "asynchronous signals such as SIGINT will be delayed until the next call to the TSan runtime", so non-allocating pure recursive functions cannot be interrupted. Slowdown "2x to 7x", memory "4 and 7" times. The view of races "involves two memory models – OCaml and C11". — [OCaml manual, TSan](https://ocaml.org/manual/5.3/tsan.html)
- [read] Integration (blog): "The OCaml compiler performs this instrumentation in a dedicated pass"; `Domain.spawn`/`Domain.join` are instrumented as synchronisation. For exceptions, "the OCaml runtime informs TSan about every exited function". For effects, "the OCaml runtime must signal to TSan which functions are exited when an effect is performed", and re-entered when a continuation is resumed. Bugs found: Saturn ("TSan found a benign data race", plus a semaphore race), Domainslib ("benign data races in Chan"), "a number of race conditions in the OCaml runtime", and help to Eio and Irmin. Comparison: "about a 2-7x slowdown (compared to 5-15x for C/C++)". TSan support first shipped in 5.1 per the announcement. — [Tarides blog, 2023-10-18](https://tarides.com/blog/2023-10-18-off-to-the-races-using-threadsanitizer-in-ocaml/); [Discuss announcement](https://discuss.ocaml.org/t/ann-tsan-support-in-ocaml-5-1-and-blog-post/13306)
- [read] Workshop paper: "Runtime Detection of Data Races in OCaml with ThreadSanitizer", OCaml Workshop 2023. I saw the listing but did not read the full text. — [ICFP 2023 OCaml Workshop](https://icfp23.sigplan.org/details/ocaml-2023-papers/12/Runtime-Detection-of-Data-Races-in-OCaml-with-ThreadSanitizer)
- [read] Runtime source `runtime/tsan.c` contains a section on effects: on `perform` the runtime emits exit hooks for every function on the current fiber, and on resume it re-enters them. (Seen via a search-result summary of a mirror, not read line by line.) — [runtime/tsan.c mirror](https://fossies.org/linux/ocaml/runtime/tsan.c)
- [read] The GC compaction race found by multicoretests "was not a data race… meaning that it would not have been caught using a developer tool such as ThreadSanitizer… Rather the race was logical: The global pool_freelist was intended to be empty for compaction to function correctly, and changes to it were coordinated via a protecting mutex." — [Midtgaard, OLIVIERFEST 2025, §5.2](https://www.janmidtgaard.dk/papers/Midtgaard%3aOLIVIERFEST25.pdf)

### Inferences
- [inferred] TSan's vector-clock model treats each systhread or domain as a TSan thread. A fiber that migrates between domains is invisible to TSan as a unit. The runtime only maintains TSan's shadow call stack on switches; happens-before from moving a continuation comes from the atomics used to transfer it (for example the Domainslib CAS or channel). For eml's VM, a "migrate a once-continuation" operation should go through an explicit release/acquire pair, so that a TSan-instrumented runtime build (Rust supports `-Zsanitizer=thread`) sees the edge.
- [inferred] TSan and PBT/STM are complementary: TSan finds low-level data races on executed paths, STM finds logical and atomicity violations and crashes. OCaml used both.

### Gaps
- I did not read the OCaml 2023 workshop paper for specifics on fiber-switch handling cost or known TSan false negatives specific to effects.
- I found no published list of the specific runtime races TSan found (the blog says only "a number of race conditions").

## Q5. The multicoretests project (QCheck-Lin, QCheck-STM): methodology and bugs

### Takeaway
Lin and STM generate a random sequential prefix followed by two random command sequences that run in two freshly spawned domains, record the results, and search for a sequential interleaving that explains them. Lin compares against the module's own sequential behaviour; STM compares against a pure user model. Tests repeat each case many times (25 by default per the 2025 paper) to "manufacture bad luck". Negative tests confirm that known-unsafe modules do fail, and stress tests skip the interleaving check and look only for crashes. The suite has found more than 40 issues in the OCaml 5 runtime, stdlib, Domainslib and lockfree, many of them GC and runtime races.

### Cited Findings
- [read] Lin "performs a sequence of random operations in parallel, records the results, and checks whether the observed results are linearizable by reconciling them with a sequential execution". The specification is a combinator DSL of type signatures, e.g. `val_ "Hashtbl.add" Hashtbl.add (t @-> a @-> b @-> returning unit)`. Each test instance is "a 'sequential prefix' of calls… followed by a spawn of two parallel Domains". Lin "does its best to schedule the two parallel Domains on top of each other. It also repeats each test instance… and it fails if just one of the repetitions fail". Counterexamples are shrunk to a local minimum. A Thread mode replaces `Domain.spawn/join` with `Thread.create/join` to test concurrent but non-overlapping execution. — [Midtgaard, Nicole, Osborne, "Multicoretests – Parallel Testing Libraries for OCaml 5.0", OCaml Workshop 2022](https://github.com/ocaml-multicore/multicoretests/blob/main/doc/paper.pdf)
- [read] STM requires `type state` (a pure model, e.g. an association list for Hashtbl), `cmd`, `arb_cmd` (a state-dependent generator), `next_state`, `run`, `precond` and `postcond`. `agree_test` is sequential and `agree_test_par` is parallel with interleaving search. Example counterexample: `Length : -1` after a parallel `Remove`, which no interleaving explains. Lineage: qcstm, Quviq QuickCheck's parallel state-machine testing (Claessen et al.), Erlang PropEr, Hedgehog. ParaFuzz (AFL-controlled scheduling) "assumes data race freedom". — [Workshop 2022 paper](https://github.com/ocaml-multicore/multicoretests/blob/main/doc/paper.pdf)
- [read] 2025 paper: "By default we therefore check each test case 25 times and fail if just one of the repetitions fail"; a random sequential prefix avoids always starting from the same state. Negative tests (`neg_agree_test_par`) pass only if a counterexample is found; for example, `Array.set` in parallel with `Array.sort` shrank in 29 steps to 3 commands. Stress tests (`stress_test_par`) "skip the interleaving search and thus only fail on an unexpected exception or a crash"; 1000 Array stress cases took 104.7 s. — [Midtgaard, "Property-Based Testing of OCaml 5's Runtime System: Fun and Segfaults with Interpreters and State Transition Functions", OLIVIERFEST 2025](https://www.janmidtgaard.dk/papers/Midtgaard%3aOLIVIERFEST25.pdf)
- [read] GC as the system under test: each GC PBT (sequential, parallel, stress) runs as a separate executable with a fresh heap, because an earlier test "could potentially leave the heap in a bad state". `Util.fork_prop_with_timeout` runs a property in a child process, so that crashes do not kill the runner and shrinking still works. For the compaction race this did not reproduce in a forked child, and the authors fell back on manual reduction and source study. CI covers native, bytecode, debug runtime, 32-bit, frame pointers and musl; AMD64, ARM64 (earlier PPC64, s390x); Linux, macOS, and Windows via Cygwin, MinGW and MSVC (earlier FreeBSD). Limitations: deadlocks and infinite loops need CI timeouts; short PBT runs cannot catch memory leaks; failures already fixed upstream still trigger on releases, so the tests are disabled per affected version. — [OLIVIERFEST 2025](https://www.janmidtgaard.dk/papers/Midtgaard%3aOLIVIERFEST25.pdf)
- [read] Bug statistics: "Collectively, the test suite has found over 40 issues". Of the 8 analysed (Array, weak hash set and GC case studies): 2 outdated docs, 2 code-generation/runtime interactions (PPC64 signal-based bounds checks corrupting the stack, [#12540](https://github.com/ocaml/ocaml/pull/12540); dangling bytecode fragments, [#13549](https://github.com/ocaml/ocaml/pull/13549)), 1 missing GC root registration (`Gc.counters`, [#13370](https://github.com/ocaml/ocaml/pull/13370)), 1 assertion (pool stats during compaction, [#13090](https://github.com/ocaml/ocaml/issues/13090)), and 2 race conditions (`ephe_get_field_copy` in weak hash sets, [#11934](https://github.com/ocaml/ocaml/issues/11934); a domain terminating during compaction adds orphaned pools to `pool_freelist`, [#14025](https://github.com/ocaml/ocaml/pull/14025)). "Half… used sequential tests to trigger, and the other half required parallel testing", which a core developer described as "manufacturing bad luck on an industrial scale". — [OLIVIERFEST 2025](https://www.janmidtgaard.dk/papers/Midtgaard%3aOLIVIERFEST25.pdf)
- [read] Broader bug list from the README. Runtime/GC: `Gc.compact` pool orphaning race (#13739), `Array.sub`/`copy` tearing (#13950), deadlocks from replacing blocking functions (#13713), backup-thread races (#13677, #12707, #13386), orphaned ephemeron marking colour (#13580), shared heap assertion (#13090), `domain.c`/`memprof.c`/`caml_reset_young_limit` assertions (#12824, #12817, #12742), hard abort on domain creation failure (#12855), ARM64 infinite loop in `caml_scan_stack` (#11425), ephemeron assertion abort (#11503), weak values (#11749). Effects: unhandled effect crash in bytecode (#11669), effect + frame-pointer crash (#12535), s390x effect crash (#12486). Stdlib: Buffer (#11279, #12103), `Bytes.escaped` (#11508), In/Out_channel (#10960, #12898, #11878, #13586). Libraries: Domainslib `parallel_for_reduce` on empty arrays (domainslib#67), segfault (#58), deadlock (#47); lockfree `Ws_deque.size` returning -1 for a stealer (lockfree#43). A Gc.Memprof callback (PR #540) is used to increase context switching for thread-based tests. — [multicoretests README](https://github.com/ocaml-multicore/multicoretests)

### Inferences
- [inferred] A direct template for eml: (1) write a pure model or reference interpreter of a runtime component (RC heap, work-stealing deque, continuation queue), (2) run random command sequences sequentially against the model, (3) run a shared prefix plus two parallel suffixes and search for a linearization, (4) repeat about 25 times, (5) add negative tests that prove the harness can detect a known-unsafe structure, (6) add stress tests that only check for crashes and for debug-heap invariants, and (7) isolate each test in a fresh process with a timeout. In Rust, `loom` and `shuttle` could complement this with exhaustive or randomized schedule exploration, which OCaml lacked (ParaFuzz aside).
- [inferred] The lockfree `Ws_deque.size` = -1 bug and the Domainslib deadlocks/segfaults are directly relevant to a work-stealing scheduler library: linearizability tests of the deque, with `size` and `steal` as commands, catch them.

## Q6. Lessons and bugs from OCaml multicore development relevant to runtime correctness

### Takeaway
The recurring bug sources were: GC/fiber interaction (marking stacks while mutators switch to them), domain lifecycle (domain termination racing with GC compaction, the backup thread, domain creation failure), C runtime helpers that bypass the memory model (memcpy tearing), unregistered roots, and effects interacting with frame pointers, bytecode and exotic backends. They were found by combining parallel PBT, TSan, the debug runtime's assertions and broad platform CI.

### Cited Findings
- [read] The fiber-marking race between a mutator switching to a fiber and other domains' GC is an inherent design point, solved first by a fiber lock (ICFP 2020 §5.4). In OCaml 5 it is the CAS on the continuation's stack field, with the comment that it "forms a barrier between execution and any other domains that might be marking this continuation". — [ICFP 2020](https://arxiv.org/abs/2004.11663); [runtime/fiber.c](https://github.com/ocaml/ocaml/blob/trunk/runtime/fiber.c)
- [read] A domain-termination race with compaction: "a central precondition for GC compaction could be invalidated if a domain would terminate simultaneously with a major heap compaction", which "leave[s] an invalid heap with broken pointers". It was first seen on macOS ARM64 machines. — [OLIVIERFEST 2025](https://www.janmidtgaard.dk/papers/Midtgaard%3aOLIVIERFEST25.pdf)
- [read] Unresumed continuations leak; OCaml chose not to finalise continuations by default for performance. — [PLDI 2021 §5.6](https://arxiv.org/abs/2104.00250)
- [read] Retrofitting effects required tool compatibility (backtraces, DWARF, gdb) as a design requirement (R2). The PLDI 2021 evaluation reports a mean 1% overhead on macro benchmarks for code that does not use effects. — [PLDI 2021](https://arxiv.org/abs/2104.00250)
- [read] Eio's warning that cross-domain thread safety is a user obligation ("The type system does not check this"), and its examples of `Condition` code "not safe to share across domains", show that OCaml leaves parallel safety of user-level abstractions unchecked. — [Eio README](https://github.com/ocaml-multicore/eio)

### Inferences
- [inferred] For eml's VM, the riskiest runtime areas by analogy are: (a) continuation transfer between workers (ownership hand-off plus any heap-scanning or RC "shared" marking at the same time); (b) worker start and stop racing with global heap operations; (c) bulk primitives (copy, blit) that must respect the publication and tearing guarantees; (d) the work-stealing deque's linearizability. Each can get an STM-style model test plus a stress test, run under TSan or `loom`.
- [inferred] OCaml never checked parallel safety statically; it relied on "racy but memory-safe" semantics, dynamic one-shot checks and testing. eml's static guarantees (linear `once`, closed rows, `never`-only `par` children) remove whole classes of these bugs at the user level. They do not remove runtime-internal races, which is where most of the OCaml findings were.
