# eml: VM のマルチコア対応の方針と、並列の安全性の確かめ方

2026-10-10 の議論の結論をまとめる。対象は commit `6c00f54` の `eml` である。ここに書いた決定は、まだ `docs/` の spec と設計文書に入れていない。各段 (S8、S9、S10、S13) の spec を書くときに、決定をその spec に移し、あわせて下の「docs に移すときに直す箇所」を改める。

同じディレクトリの `research.md` は、議論の途中で行った先行実装の調査レポートで、`notes/` はその調査ノートである。下で「調査」と書くときは、この2つを指す。

## 案 B を選んだ理由

今の設計 ([マルチコア対応の設計](../../../future/multicore.md) の決定6と7) は、VM をシングルスレッドにし、並列化をネイティブのランタイムだけで行う。議論では、次の2点からこれを見直した。

- **混在実行と両立しない**。`FnEntry` で VM とネイティブのコードを混ぜて動かすと、ネイティブの標準ライブラリの `par_map` が、ユーザーのバイトコードの閉包を worker のスレッドで呼ぶ。VM がスレッドをまたいで使える作りでなければ、混在させた `par` を順に実行するしかなくなる
- **確かめる時期が遅い**。ネイティブ化は S13 の後の言語の項目より後にある。共有の印付け、別スレッドからの解放、`Row<Never>` と `Heap h` の不変条件は、それまで実装で確かめられない

VM を並列にする費用は小さいと見積もった。S7 の evidence passing の後は継続がヒープのクロージャになり、`Ctx` は worker ごとに1つ持つ想定になっている。RC の分岐は、不死の物体 (0) を区別する比較に負の側を足すだけで済む。`par` と `run_scheduler` は構造化された並行性なので、REPL の入力の境目では worker が1つも動いていない。

並列化を S10 で行う案 (案 C) は、VM の最初の版で並列化と性能の両方を詰めることになるので採らなかった。

## 制約3: 共有の印付けを fork と join で必ず行う

### 印付けの位置

印付けをいつ行うかで、どの物体が共有になるかがスケジュールに依存するかが決まる。

| 印付けの時点 | 共有になる物体の集合 | 逐次の実行で通る経路 |
|---|---|---|
| 盗まれた時点 (private deque の方式) | スケジュールに依存する | 印付けが一度も起きない |
| fork と join の時点 | スケジュールによらず決まる | 並列のときと同じ物体に印が付く |

fork と join の時点を採る。印を付けるのは次の2か所である。

- fork: 右の子の閉包から届く物体。rayon の `join` と同じく、別の worker に渡りうるのは右の子だけで、左の子は親の worker で動く
- join: 右の子の結果から届く物体。右の子の worker が、公開する前に付ける

印付けは `par` の実行時の意味の一部で、検査モードだけの動作ではない。共有した物体は reuse しないので (下の節)、共有の集合が決まれば reuse の判断も決まる。そのため、逐次と並列で `RunStats` の作業の回数が一致する (`peak_objects` は除く)。multicore.md の「work stealing のキューに入れた時点で印を付ける」という決定と同じ考え方である。private deque は、将来の最適化のまま残す。

代償は、シングルスレッドの VM でも `par` に渡したデータが atomic の RC になり、reuse されなくなることである。シングルスレッドの `par` には速さの目標がないので、受け入れる。

### 論理的な worker ID

物理的な worker が1つだと、所有者の検査で全物体が同じ所有者になり、何も検出しない。そこで `Ctx` に論理的な worker ID を持たせる。

- 逐次の `par` は、左の子を親の ID のまま実行し、右の子を新しい ID で実行する
- 右の子が確保した物体の所有者は、右の子の ID である
- 検査モードのヘッダは所有者 ID を持つ。Relaxed の `AtomicU32` にする。正の RC の物体への `dup`、`decref`、フィールドの書き込み、reuse のたびに、所有者が今の ID と一致するかを確かめる

fork で印を付け忘れた物体に右の子が触れると、所有者が親の ID なので、検査は必ず失敗する。スケジュールに依存せず、`par` を使うすべての UI テストで毎回確かめられる。

### 逐次の実行で確かめられないこと

逐次の実行で確かめられるのは論理の誤りまでである。公開するときの順序 (Release と Acquire)、2つのスレッドからの同時の `decref`、deque の正しさは、本物のスレッドでしか現れない。これらは並列 VM の項目で、loom、Miri、TSan を使って確かめる (下の「検証の計画」)。

### 調査からの根拠

- Lean 4 と Koka は eml と同じ符号の規約を使うが、どちらも印付けの漏れを直接見つける仕組みを持たない。2026 年に両者で直した use-after-free の実バグのうち、Koka の `make_shared` の 1 ずれと、共有 `ref` への格納での印付け漏れは、この方式で確実に見つかる種類である (`research.md` の「2026 年の実バグ」)
- 局所の経路を `AtomicI32` の Relaxed で書くと、印を付け忘れても言語のメモリモデルの上ではデータ競合にならず、Miri、TSan、loom のどれも直接は報告しない。直接効く先例は、CPython (PEP 703) の `ob_tid` のような所有者の記録である (`research.md` の「どの検査道具も」)

## 共有した物体は reuse しない

RC が負の物体は、RC の値によらず reuse しない。Lean 4 の `lean_is_exclusive` と Koka の `kk_block_drop_reuse` と同じ規則である。multicore.md の「共有したオブジェクトでは、この判定も atomic な読み出しになる」は採らない。

join の後に共有の物体を局所へ戻す最適化 (Koka は最後の共有の drop で 0 に戻す) も、検証の手段がそろうまで入れない。

## `par` の a1 を協調的マルチタスクとして入れる

`par : (Unit -> <> a) -> (Unit -> <> b) -> (a, b)` を、並列 VM より前に、シングルスレッドの協調的マルチタスクとして入れる。a1 は `Row<Never>` の Kind の制約も型システムの変更も要らないので、組み込みの関数1つで入れられる。入れるかどうかと時期は、S13 で判断する項目にする。

### 形

- 右の子を1つのタスクにし、左の子は親のタスクがそのまま実行する
- スケジューラは、呼び出しと戻りの安全点でタスクを切り替えてよい。方針は2つ持つ
  - 逐次: 切り替えない。左の子を終えてから右の子を実行する。Cilk の serial elision に当たり、`eml run` の既定と、ベンチの `RunStats` の固定に使う
  - 乱数種付き: 種で決めた間隔で切り替える。テストで使い、失敗したときは種を表示して再現できるようにする
- 右のタスクは新しい論理的な worker ID で動く。制約3の印付けと所有者の検査は、そのまま働く

協調的マルチタスクは「worker が1つの並列 VM」で、後の並列 VM と同じコードの経路を通る。

### 逐次の実行より確かめられること

- 2つのタスクが同じ共有の物体に `decref` し、どちらが最後に解放するかが種で変わる。所有者でない worker が解放する経路を通せる
- タスクの中断、再開、join の待ちといった、スケジューラの処理そのもの
- 実行時エラーの優先の規則。右の子が先にエラーになっても、左の子を最後まで実行してから報告する。右のタスクは止めたまま解放せず、評価全体を中断する。残った物体は、S11 の根からの走査による回復で片付ける。左の子が停止しなければ右のエラーは報告されず、逐次の実行と一致する

a1 の子は row が `<>` なので、どう切り替えても出力は変わらない。UI テストは、逐次と乱数種付きの両方で走らせ、出力が一致することを確かめる。

## `Lin` の値は move だけを許す

`Lin` の物体の RC は常に 1 である、という不変条件を立てる。S8 に入れる。multicore.md の「`Lin` の値は RC を持たず、移動するだけである」は、すでにこの前提で書かれているが、今の実装は満たしていない。

### 今の実装が満たしていない箇所

`docs/spec/core-ir.md:120` によると、後の行のパターンが分解した値かその祖先を束縛するとき (`| other -> ..`、`| W h _ -> ..`)、Perceus は case の行き先の入口で、`Lin` のものも含めて生きているフィールドを `dup` する。ソースでは1回ずつしか使っていなくても、フィールドの所有を入口で一度に決めているために `dup` が出る。

### 直し方

ロードマップの Perceus の最適化にある「フィールドを死ぬ所で手放す形」を、S8 で必須の前提として入れる。読むだけの `switch` でどの行かを決め、所有はその行の葉で決める。

- 祖先をそのまま使う行では、祖先を move するだけで、フィールドに触れない
- フィールドを消費する行では、祖先が死んでいるので、`release` で一意な箱からフィールドを受け取る

ほかに `dup` が出る原因はないと見ている。ソースで2回使えば型検査が `Unr` の制約を付ける。`multi` の継続は持ち越し規則で `Unr` しか捕まえない。EP の継続のクロージャ、ブロック引数、handler の状態は move で、呼ばれる側の閉包は `apply` で消費される (`core-ir.md:49`)。

S8 の完了の条件「パスを移す前後でダンプがバイト単位で一致する」との両立 (Perceus を LIR に移す作業と、形を変える作業の順序) は、S8 の議論で決める。

### 得られるもの

- スレッドをまたぐとき、`Lin` の物体は印を付けず、所有者を移すだけで済む。中の `Unr` のフィールドには印を付ける。共有した物体を reuse しない規則のもとでも、`Lin` の `MutArray` を分けて子でその場で書き換える形が成り立つ
- `File` を閉じる時点が、`close` や `drop` を書いた所と一致する
- extern (`read_all`、`close`) が一意性を前提にできる
- 「`Lin` の物体の RC は 1」が単純な assertion になる

## LIR の Kind の印

### 3値の印

単相化の後でも、変数の Kind が決まらない場合が3つある。一様な位置の型変数 (`Flexible`)、instance の鍵に入らない矢印の線形性の Kind 変数、EP が多相な関数のフレームの続きとして作るクロージャである。そこで印を3値にする。

| 印 | 意味 | `dup` | `decref` |
|---|---|---|---|
| `unr` | 静的に `Unr` と示せる | 許す | 許す |
| `lin` | 静的に `Lin` と分かる | 拒む | 拒む |
| `poly` | 静的には分からない | 拒む | 拒む |

`poly` に `dup` を拒んでも困らない。ソースで2回使うか使わなければ型検査が `Unr` の制約を付けるので、制約のない Kind 変数の値はちょうど1回使われている。`decref` を拒むのは、`Lin` の物体の RC が 0 になると破棄処理が呼ばれ、暗黙の後始末になるためである。`never` の中断の経路で Perceus が `decref` を置かないことは、S7 の設計で確かめる。

### 印の出どころ

印は translate が型から決め、Core IR から LIR に写す。Repr と同じ流れである。

- translate は、instance の代入をかけた型から Kind を求める。定数の `Lin` を含めば `lin`、すべて `Unr` なら `unr`、`Flexible` か解けない Kind 変数に依存すれば `poly` にする。スキームの制約で `Unr` に決まる Kind 変数は `unr` にする
- EP が足す変数: evidence は `unr` である。`perform` の箇所の継続は、操作の宣言の多重度から、`once` なら `lin`、`multi` なら `unr` にする。多相な関数のフレームの続きは `poly` にする
- box の挿入が足す変数はスカラーなので `unr` である。`f$boxed` の引数は元の関数の印を写す
- extern の行には、Repr の `params` と `ret` と並べて Kind の列を足す。`std/` のシグネチャとの結び付けは、Repr と同じテストで確かめる

### verifier の規則

所有の段 (R6、R7) に次の2つを足す。

- V1: `unr` でない変数に `dup` と `decref` を置かない
- V2: 値の受け渡し (`jump` の実引数と行き先の引数、呼び出しの引数と仮引数、`return` と `ret`) で、受け手の印が送り手の印以上である。順序は `unr ≤ poly ≤ lin` である。Repr の互換を比べる所と同じ場所で比べる

`unpack` で得た変数の印は、配置の表からは確かめられない。配置は型ごとに1つで、フィールドの Kind を持たないためである。この印は translate を信用し、下のヘッダのビットで実行時に覆う。V1 と V2 が成り立つと、`unr` でない変数に Perceus が出す命令は、分解のときの `release` だけになる。

### ヘッダの `lin` ビット

`release` の共有の側の経路 (一意でない箱のフィールドを `dup` する) は、`poly` の物体を `release` する箇所があるので静的には除けない。そこで実行時にも確かめる。

- ヘッダに `lin` のビットを、検査モードに限らず常に持つ。`par` の fork で所有者を移すのに、通常の実行でも使うためである
- `File` などの extern の資源は、作るときにビットを立てる。`con` と `closure` は、静的な印が `lin` なら立て、`unr` と `poly` なら立てない
- 検査モードでは、ビットの立った物体への `dup`、共有の側の `release` / `decref`、RC が 1 を超えることを誤りとして報告する
- fork の印付けのたどりは、ビットの立った物体では印を付けず、所有者を移す。中の `Unr` のフィールドには印を付ける

`poly` のコードで作った `Lin` の物体はビットを持たないので、fork で共有になり、その場の書き換えができなくなる。安全の側に倒れるだけである。`poly` の `con` でフィールドのビットの OR を取って実行時に伝える案は、`MutArray` の項目で決める。

### テキスト形式

LIR のテキスト形式では、`unr` を既定にして書かず、`lin` と `poly` だけを書く (`x: tobj lin`)。S8 の期待値の変更の範囲は、`lin` か `poly` の変数を含むダンプになる。

## 検証の計画

この節は調査から導いた計画で、項目ごとの採否は各段の spec で決める。制約3の所有者 ID の検査は、上で決めたものである。

### S9 で入れること

| 項目 | 確かめ方 |
|---|---|
| `mark_shared` (印の付いた物体でたどりを止める)、負の RC の `dup` / `decref`、最後の参照での解放 | `eml_rt` の単体テスト、Miri (strict provenance) |
| 桁あふれの規則 (sticky な範囲) | Kani で、任意の inc / dec / 印付けの列が理想的な数を正しく表すことを i32 の全域で証明する (Lean の `rc_model.lean` に当たる。下の「Kani と Miri で確かめられる範囲」) |
| 共有した物体を reuse しないこと | 単体テスト |
| 検査モードの所有者 ID | UI テストの `debug_heap` で常に有効 |
| 「共有の物体から届くのは共有か不死だけ」の走査 | 確保の台帳による生存の列挙に組み込む |
| `CodeBase` の定数、文字列リテラル、空の evidence を、生成したときから不死にする | 検査モードで「`CodeBase` から届くものは不死」を確かめる。Koka の PR #910 のヒープ破壊を避けるため |
| atomic、cell、確保を薄い層の裏に置き、`cfg(loom)` で差し替えられるようにする。核では SeqCst と `fence` を使わない | tokio の `src/loom/mod.rs` と同じ形 |

### `par` の a1 を入れるとき

- 逐次と乱数種付きの2つの方針で、`run` と `run-fail` の UI テストを走らせ、出力が一致することを確かめる
- 負の試験: 検査用のフラグで印付けを1か所外したとき、上の試験のどれかが必ず失敗することを確かめる (multicoretests の負の試験に当たる)
- 実行時エラーの優先の規則を `run-fail` の UI テストにする

### 並列 VM の項目で入れること

- 本物のスレッドでの実行。UI テストを、逐次、N 個の worker、乱数種付きで走らせ、逐次のスナップショットと比べる。`RunStats` は逐次でだけ固定する
- 印付けと公開、両側からの `dup` / `decref`、最後の解放、join の手順の loom のモデル (2〜3 スレッド、`LOOM_MAX_PREEMPTIONS=2`)
- Miri で `eml_rt` の並行の単体テスト (strict provenance、many-seeds)
- TSan で VM に `par` の UI テストを走らせる。RC の語の誤りは見えず、フィールドの競合として結果だけが見えることを前提にする
- work stealing の deque を自作するなら、スロットを atomic の語にして、crossbeam-deque の意図的な競合を避ける
- 試験ごとに新しいプロセスとタイムアウトで動かすストレス試験

### Kani と Miri で確かめられる範囲

Kani と Miri でマルチコア VM のバグをどこまで検査できるかを、議論の後に検討した。

Miri はマルチコアの検査に使える。ただし対象は、`eml_rt` の核の単体テストと、ごく小さい VM のプログラムに限られる。印付けの漏れは直接は報告せず、その結果 (解放後の使用、フィールドの競合、リーク) を、探索した実行がたまたま踏んだときにだけ見つける。速さはネイティブの約 3000〜7000 倍遅い ([Miri, POPL 2026](https://research.ralfj.de/papers/2026-popl-miri.pdf))。

Kani はマルチコアの検査には使えない。公式の文書は、並行の機能を対象外とし、並行のコードは警告を出して逐次のコードとして扱い、データ競合は検出しないと書いている ([Kani: Rust feature support](https://model-checking.github.io/kani/rust-feature-support.html)。Rust の標準ライブラリの検証の取り組みも、この制限を挙げている。[arXiv 2510.01072](https://arxiv.org/pdf/2510.01072))。一方で、逐次のコードを有界な範囲で網羅し、ビット単位で正確に扱うので、符号付きの RC の状態機械にはよく合う。

| バグの種類 | 先例 | Kani | Miri | ほかの手段 |
|---|---|---|---|---|
| RC の数の算術 (符号の変換、sticky な範囲) | Koka の `make_shared` の 1 ずれ、Lean の桁あふれ | ◎ i32 の全域でビット単位に証明できる | × | Lean は `bv_decide` で同じことをした |
| `mark_shared` のたどり (届く物体をすべて訪れる、正しく止まる、不変条件が保たれる) | Lean の PR #15288 | ○ 物体が4〜5個までの有界なヒープで網羅できる | △ 単体テストの入力だけ | 検査モードの走査 |
| `release` の意味 (一意なら移す、共有なら `dup`) と `lin` ビットの規則 | | ◎ | △ | |
| 核の未定義動作 (provenance、解放後の使用、二重解放) | | ○ ハーネスの範囲で | ◎ strict provenance、Tree Borrows | |
| 公開の経路での印付けの漏れ | Koka の commit 046254c | × VM の規模に届かない | △ 間接的で、確率的にしか見つからない | 論理的な worker ID と所有者の検査 |
| 公開と join の順序 (Release / Acquire)、同時の最後の `decref` | | × | ○ many-seeds で確率的に見つかる | loom (有界で網羅的)、Miri と GenMC の連携 (まだ実験的) |

#### Kani のハーネス

S9 では、次のハーネスを書く。

1. ヘッダの詰め方: RC、タグ、`lin` ビット、検査モードの所有者 ID を詰めて取り出すと元に戻ること
2. RC の状態機械: 正 / 0 / 負の遷移、`mark_shared` での符号の変換、sticky な範囲で、任意の操作の列が理想的な数を正しく表すこと。性質テストの抜き取りでなく、全域で確かめる
3. `mark_shared` のたどり: `kani::any()` で作った有界な物体のグラフで、たどった後に「共有の物体から届くのは共有か不死だけ」が成り立ち、各物体を高々1回しか訪れないこと
4. `release` と `lin` ビット: 一意な箱でフィールドが移ること、`lin` ビットの立った物体では共有の側を通らないこと

S9 か並列 VM の項目では、印付けの手順そのものを逐次のプログラムに書き直して検査する。2つの論理的な worker が物体1〜3個に対して操作する場面で、次の形にする。

- どちらの worker が次の操作をするかを、`kani::any()` で非決定的に選ぶ
- 局所の `dup` / `decref` を「読む」と「書く」の2段に分け、その間でも worker が入れ替われるようにする
- fork と join で印を付ける手順を、そのまま書く

印付けを1か所外すと数の取りこぼしが起きることを Kani が見つけ、外さなければ起きないことを有界な範囲で示せる。確かめられるのは操作を単位とした交互実行で、弱いメモリの振る舞いは含まない。制約3の手順の設計が正しいことを示す役で、メモリの順序は loom が受け持つ。

#### Miri の使い方

- S9: `eml_rt` の単体テストを `-Zmiri-strict-provenance` で走らせる。Tree Borrows の実行も1本足す
- 並列 VM の項目: `eml_rt` の並行の単体テスト (公開、join、両側からの `decref`) を `-Zmiri-many-seeds` で走らせる
- 並列 VM の項目: `par` を使う小さい UI テストを、VM ごと Miri で走らせる。ネイティブで数ミリ秒のプログラムなら、数秒から数十秒で済む。`Fs` の extern はファイルを触るので、`-Zmiri-disable-isolation` が要る
- Miri と GenMC の連携は、弱いメモリの振る舞いを網羅できるが、まだ「highly experimental」である ([Ralf Jung のブログ](https://www.ralfj.de/blog/2025/12/22/miri.html))。成熟してから loom と比べて選ぶ

#### 注意点

- Kani は atomic を逐次の操作として扱うので、loom 用の薄い層 (`cfg(loom)`) の裏の atomic は、そのまま Kani でも使える。ただし、並行のハーネスを誤って書くと、警告だけで逐次として扱われ、証明できたように見える。Kani のハーネスは逐次のものだけにし、並行の検査は loom と Miri に任せる
- Kani は専用のツールチェインと CBMC を要する。Nix の devShell に入れられるか、macOS の aarch64 で動くかは確かめていない。導入するときに確かめる
- 並行の Rust を検証できる道具として、Verus、VeriFast、RustMC (GenMC を Rust に広げたもの) もある。どれも導入の費用が Kani より大きいので、今は候補に挙げるだけにする

| 時期 | 道具 | 対象 |
|---|---|---|
| S9 | Kani | ヘッダの詰め方、RC の状態機械、有界なヒープでの `mark_shared`、`release` と `lin` ビット |
| S9 | Miri | `eml_rt` の単体テスト (strict provenance、Tree Borrows) |
| S9 か並列 VM の項目 | Kani | 2つの論理的な worker で、印付けの手順を交互実行で確かめるモデル |
| 並列 VM の項目 | loom | 公開と join の順序、同時の最後の `decref` |
| 並列 VM の項目 | Miri | 並行の単体テスト (many-seeds)、`par` を使う小さい UI テスト |
| 並列 VM の項目 | TSan | `par` を使う UI テスト全体 |

## 未決の論点

- **S8 の中の順序**: Perceus を LIR に移す作業 (ダンプがバイト単位で一致する) と、「死ぬ所で手放す形」に変える作業 (期待値の変更) の分け方。S8 の議論で決める
- **V2 で `poly` から `lin` へ渡す箇所**: 実際にどこに出るか。`lin` から `poly` への受け渡しは許されるが、逆は拒まれるので、拒まれる箇所が正しいプログラムに出ないかを translate の出力で確かめる
- **EP の継続の印と S7**: 継続のクロージャの印の付け方と、`never` の中断の経路で `decref` を置かないことを、S7 の spec で決める
- **`par` の a1 の時期**: S13 で判断する
- **fork での `Lin` の移し替え**: 中の `Unr` のフィールドをたどって印を付ける手順と、所有者 ID の検査の関係
- **`poly` の物体のビットの実行時の伝播**: `MutArray` の項目で決める
- **読むだけの共有**: OxCaml は `par` の子が親の環境を読めるが書けない形を持つ。eml の `par` の子は親の `Ref` を読めない。表現力の不足として現れたときに検討する
- **実行時エラーの報告の決定性**: extern の失敗の位置、`debug_heap` が報告するリークと不変条件の違反も、スケジュールによらず同じ内容で出す必要がある。左の子が失敗した後、右の子をどう止めるかは、a2-cancel の協調的な中断と一緒に決める
