# 実装の現在地

位置づけ: 手引き。

M1 (言語の全体を一通り通す vertical slice と、本番の構文の最初の部分) と M2 (モジュールと、参照ごとの具体化の表) は完了した。今は再設計 (S0〜S13) を進めていて、S10 (VM と切り替え) と S11 (REPL) を終え、S12 (スクリプトの MVP) を終え、S13a (Kind の記法)、S13b (位置つきの `mask`、`fn` と `ctl` の節とローカル関数の組、std のエフェクトと `Iter`)、S13c (中断をタスクのスタックの巻き戻しにすること、`IO` と `never` の操作だけのエフェクトを yield の地点から外すこと、すぐに再開する節の under、戻らない呼び出しの前の暗黙の後始末)、S13d (row の最小の具体化)、S13e-1 (既知の閉包への特殊化) を終えた ([ロードマップ](../future/roadmap.md) の「段の列」)。S12d で書いた5本のスクリプト (wc、grep、ログの集計、CSV の変換、デプロイ手順) は `tests/ui/run/scripts/` の UI テストで、書いてみて分かったことはロードマップの「S13 実例による判断」にある。`eml run` は、Perceus の後の LIR をレジスタ型のバイトコードに変換し、`eml_rt` の上の VM で実行する ([VM](../spec/vm.md))。Perceus は、`switch` と `unpack` のフィールドを借りたまま使い、所有が要る所でだけ所有を取る ([LIR](../spec/lir.md) の「Perceus」)。S11 で `eml repl` を入れた ([REPL の端末](../spec/repl.md))。次は S13e-2 (handler への特殊化) である。この文書は、今の言語の範囲と既知の制限をまとめる。実装が進んだら更新する。

## 今の言語の範囲

### 実装したもの

- 基本型: `Int`、`Bool`、`String`、`Unit`。`Bool` は Prelude の `data Bool = | False | True` で、キーワード `true` / `false` はない。単項の `!` はなく、関数 `not` を使う
- タプルと射影 `t.0`、型引数を持つ代数的データ型 (`data`)、`match` と入れ子のパターン、`Int` と `String` のリテラルのパターン
- 名前付きのレコード: `data` のコンストラクタの名前付きのフィールド、作る式 `Person { name = "a", age = 3 }` と省略形、射影 `p.name`、更新 `{ p | age = 31 }`、分解のパターン、フィールドのセクション `(.name)` と `(.0)`、導出した `Show` の `Person { … }` の表示 ([直積型とレコード](../spec/records.md))。呼び出しの引数のラムダは、ほかの引数の後に型を検査する ([型と Kind](../spec/types.md) の「引数のラムダを後で検査する」)
- Prelude の `List`、`Option`、`Result` と、その `Eq`、`Ord`、`Show` の instance ([宣言](../spec/declarations.md) の「Prelude のクラス」)。リストのリテラル `[…]` とパターン、コンストラクタ `::` (`infixr 5`。Prelude だけが宣言できる、E1044) ([式](../spec/expressions.md) の「リスト」)。リストを扱う関数 (`map`、`length` など) はまだない
- 文字列: エスケープ、補間 `\{式}`、複数行の文字列 `"""`、raw 文字列 `r"…"` / `r#"…"#` ([字句](../spec/lexical.md) の「文字列」)。補間の穴は、Prelude の `Show` のメソッド `display` で文字列にする ([式](../spec/expressions.md) の「補間」)。文字列の関数は標準ライブラリの `String` にある。位置は UTF-8 のバイトの位置である ([標準ライブラリ](../spec/stdlib.md))
- トップレベルの関数 (シグネチャが必須)、複数の等式による定義、ローカルの `let` と `let ... in`、ローカルの再帰関数 (`let go acc xs = …`。引数を1つ以上持つ関数の形の `let` は自分自身を参照でき、単相で、lambda lifting する。`let … and …` で書いた組の関数は互いに呼び合える。[式](../spec/expressions.md) の「ローカル関数」)、`if` (then 節が `Unit` なら `else` を省略できる)、再帰、ラムダとクロージャ、部分適用、型の明示 `(e : T)`
- シグネチャの型変数と row 変数による多相
- 1回だけ呼べる関数の型 `once a -> b` (`Lin` の矢印。`data` のフィールドにも書ける)、`data` の row の型引数 (`data Iter <e> a`、使う所は `Iter <IO> Int`)、`data` の Kind の宣言 `data T : Lin`、トップレベルの関数と extern の関数とコンストラクタとクラスのメソッドと REPL の `let` の値を `once` の位置に置くこと (参照ごとに一番外側の矢印が新しい Kind 変数になる)。row の型引数を持つ型の instance と `deriving` は E0004 ([型と Kind](../spec/types.md)、[宣言](../spec/declarations.md))
- fixity の宣言とユーザー定義の演算子、演算子のセクション、`use`
- `drop` キーワード
- エフェクトの宣言 (`never` / `once` / `multi`、型引数)、`handle` (deep)、`k` の呼び出しによる再開、`drop k`、パラメータ付き handler (`handle ... from ... with`)。操作の節は、`k` を受け取る `ctl` の節 (`| ctl op x k -> …`) と、本体の値ですぐに再開する `fn` の節 (`| fn op x -> …`) である ([式](../spec/expressions.md) の「handler」)
- 位置つきの `mask`: 型検査が呼び出しごとに決め、エフェクトごとに内側の n 個の handler を残して続く m 個を飛ばす。`Yield Int` を受けて `Yield String` を出すような、型を変換する handler を書ける ([エフェクトと handler](../spec/effects.md) の「handler の意味」、[型と Kind](../spec/types.md) の「推論」)
- `extern` の宣言と `eml_extern` の表。`Int`、`String`、`Unit`、`IO`、`println`、算術の演算子などは Prelude の `extern` である。`Int`、`String`、`Bool` の比較と表示のメソッドは、instance の中の `extern` で表の行に結ぶ。`IO` を、`println` と標準ライブラリのモジュール `Fs` の `open`、`read_all`、`close` などが起こし、`Fs.File` は線形型である。ユーザーは `IO` を handle できず (Prelude の `try_io` だけが handle する)、`extern` を書けない (E1033) ([エフェクトと handler](../spec/effects.md) の「組み込みの `IO`」)
- IO の失敗と終了: Prelude の `try_io : (Unit -> <IO | e> a) -> <IO | e> Result IOError a` が、IO の extern の失敗 (書き出しの失敗を除く) を `IOError { kind, message }` の値にする。`exit : Int -> <IO> a` は途中のフレームの値を後始末し、終了コード `n & 255` で終わる。REPL では入力を終えるだけである ([標準ライブラリ](../spec/stdlib.md) の「`try_io`」と「`exit`」)
- 標準ライブラリのツリー: リポジトリの `std/` (`Prelude.em`、`Fs.em`、`List.em`、`String.em`、`Env.em`、`Stdin.em`、`Proc.em`、`Yield.em`、`Fail.em`、`State.em`、`Iter.em`) をバイナリに埋め込む。Prelude はいつも読み込み、ほかのモジュールは import か修飾子で使うものだけを読み込む。`Fs.open` のように import なしで修飾付きで使え、`import Std.Fs` でも読める。予約した根は `Std` である ([モジュールと名前解決](../spec/modules.md) の「標準ライブラリ」)
- std のエフェクトと `Iter`: エフェクトのモジュール `Yield` (`for_each`、`fold`、`collect`)、`Fail` (`to_result`、`to_option`)、`State` (`run`、`eval`、`exec`) と、`once` の継続で作る引いて使うジェネレータ `Iter` とその変換。`File` から1行ずつ読む `Fs.read_line` ([標準ライブラリ](../spec/stdlib.md) の「エフェクトのモジュール」と「`Fs`」)。S12d の `grep`、`logstat`、`csv2jsonl` は std のエフェクトを使い、`csv2jsonl` の CSV の読み取りは `let … and …` の組で書く
- 線形性、持ち越し規則、網羅性の検査。`fail` や `exit` のような戻らない呼び出しで終わる経路では、消費しない `Lin` の値を手放さなくてよい ([線形性](../spec/linearity.md) の「暗黙の後始末」)
- 型クラス: `class` (上位クラス、既定のメソッド、メソッド自身の型変数と制約)、`instance` (文脈、標準ライブラリの中の `extern`)、シグネチャの制約 `Eq a =>`、`deriving (Eq, Ord, Show)`、Prelude のクラス `Eq`、`Ord`、`Show` と `Ordering`、タプルと `Unit` の構造的な instance。証拠は単相化で決め、実行時の辞書は持たない ([宣言](../spec/declarations.md) の「クラスと instance」、[型と Kind](../spec/types.md) の「制約」)
- モジュール: 入口のファイルのディレクトリを根にして import をたどる読み込み、`pub`、修飾した名前、別名、import の並び、`T(..)` と `E(..)`、修飾子の合流、モジュールとしての Prelude と `Prelude.` の修飾、import の循環の禁止 (E1027)、公開の範囲の検査 (E1032) ([モジュールと名前解決](../spec/modules.md))
- 同じ名前の別の型、エフェクト、コンストラクタは、名前を定義するモジュールが2つ以上あるとき、`Prelude.Bool` と `Main.Bool` のようにモジュール名で修飾して表示する
- REPL (`eml repl`): 入力をまたいで定義と `let` の束縛を残すセッション、定義し直し、実行時エラーと割り込みの後の回復、`:load` / `:reload` / `:type`、型に従う結果の表示器 (予算と深さと長さの上限、幅に合わせた整形) ([REPL の端末](../spec/repl.md))

### まだないもの

- 浮動小数と文字 (字句として予約し、使うと E0004。`Float`、`Char`、`Num` の段)
- まだ実装していない構文: 型の別名 `type` ([ロードマップ](../future/roadmap.md) の「言語機能と構文」)、コマンドリテラル (コマンドリテラルの段)。字句と文法の置き場所を用意してあり、使うと E0004 (未対応) を出して回復する。どの層が E0004 を出すかは下の「未対応の構文と E0004」にある
- バイト列、配列、標準入出力のハンドル (バイト列と `Array` の段)。文字の型を使う文字列の関数、連想配列、並べ替えなどの標準ライブラリ (UTF-8 と標準ライブラリの段)
- ユーザーが書く extern (FFI)
- 可変参照 `Ref`、再エクスポート (`pub import`)、抽象型、修飾した演算子の構文、`data` のフィールドの矢印の線形性の多相、`: Unr` の宣言、row の型引数の省略、`Lin` の型を受けるクラス、or パターン、ガード、as パターン、Perceus の reuse analysis と借用の最適化、LSP、フォーマッタ、ネイティブ化 ([ロードマップ](../future/roadmap.md) の「その後の項目」)


今後のマイルストーンと将来の拡張は [ロードマップ](../future/roadmap.md) にまとめてある。

### 未対応の構文と E0004

まだ実装していない構文は、パーサが CST まで組み、HIR が E0004 (未対応) を出す。意味を与える最初の段階が未対応を判定するという方針である。HIR が E0004 を出すのは、`type` の宣言、浮動小数、文字、コマンドリテラルである。パーサが E0004 を出す構文はない。未対応のリテラル (浮動小数、文字、コマンドリテラル) の E0004 は、すべて HIR が出す。コマンドリテラルは lexer が文字列と同じ形のトークンに分け ([字句](../spec/lexical.md) の「コマンドリテラル」)、HIR がリテラル全体に E0004 を1件出す。穴の中の式は lower しない。

型の位置の `[` と `{`、コンストラクタのない `{ … }` は、未対応の構文でなく、構文の誤り (E0011) である。リストの型は `List a` と書き、レコードは `data` で宣言する ([文法](../spec/grammar.md) の「文法上の補足」)。

### タプルの扱い

- HIR はタプルを専用の形 (`ExprKind::Tuple`、`PatKind::Tuple`、`TypeRefKind::Tuple`) で持ち、型検査がラベルのないタプルの型 (`Tuple(Vec<_>)`) に写す。`Unit` は要素のないタプルである
- タプルの射影 `t.0` は、名前付きのレコードの射影と同じく `ExprKind::Field` で持ち、型検査が型から引く ([型と Kind](../spec/types.md) の「フィールドの解決」)。タプルは更新できない

## 既知の制限

### 診断の表示と言い方

- `data T <e> e = | T e` のように row の型引数と型引数が同じ名前を持つと、E1003 を出した後に、続けて E1002 も出る。2つ目は1つ目の連鎖で、宣言の名前の重複を片づけるときに直す
- ariadne は、同じファイルの区画の見出しに、どの区画でも primary の位置を出す (`ariadne` 0.6 の `write.rs`)。そのため、secondary が primary より前の行にあって区画が分かれると (E3002 の「first used here」、E1003 の「first defined here」など)、2つ目の区画の見出しも primary の行と列になる。設定では変えられないので、直すときは表示を ariadne 以外で組むか、ariadne を書き換える
- HIR が呼び出しを1つにまとめるので、`(1 + 1) 2` は「`+` は2引数なのに3引数が渡された」と報告される。呼び出しをまとめるのは、`(f a) b` と `x |> f a` を引数の揃った1つの呼び出しとして扱うためである。まとめた呼び出しで引数が余ったときは、元の呼び出しの区切りで報告する方がよい
- E3003 の `drop x` の fix は、ファイルの改行が CRLF でも改行に `\n` を入れる。字下げは元のテキストから写すが、改行の種類は写さない。直すときは、挿入する行の改行を、その行の周りの改行に合わせる
- 網羅性の漏れの例のコンストラクタと E1013 の help の節の先頭は、表示名の表と既存の節の修飾子に従って書く。診断を出したモジュールで書ける形 (別名の修飾子を含む) にはしない

### 深さと性能

- 演算子の列は、演算子1つを入れ子の1段と数え、それまでの被演算子の高さの最大も足す ([文法](../spec/grammar.md))。そのため、外側の入れ子がなければ、1つの列に書ける演算子は比較と `||` を合わせて約250個までである (`x == 0 || x == 1 || …` なら約125項)。括弧に入れた列を左に重ねると、各段の演算子の数の和が上限に数えられる。`use` の文も1つで1段と数えるので、1つのブロックに書ける `use` は約250個までである
- パターンのリストは、k 番目の要素を k - 1 段深く読む ([文法](../spec/grammar.md) の「文法上の補足」)。そのため、外側の入れ子がなく、要素が変数か `_` なら、1つのパターンのリストに書ける要素は256個までである (`f [x1, …, x256] = 0` は通り、257個で E0013)。式のリストは要素の数を数えない
- 呼び出しを要素に持つリストのリテラル (`[f 1, f 2, …]`) では、末尾でない呼び出しのたびに、それまでに評価した要素がすべて生きている。そのため、VM のスロットの割り当ての干渉グラフの辺の数が、要素の数の2乗になる。タプルも同じである。要素を先に評価して逆順のリストに積み、後で反転すれば避けられるが、確保が倍になるので採らない。要素が変数とリテラルだけなら線形である ([Core IR](../spec/core-ir.md) の「変換の規則」)
- 字下げの足りない行 (E0009) で本体を失ったラムダが文の位置にあると、`Unit` との型の誤り (E2001) が連鎖する (`fn x ->` の次の行を字下げしない場合)
- 引数の多い1つの呼び出しでは、持ち越しのパスが、生きている値と矢印の組ごとに制約を作る (`carry.rs` の `carry` と `row_multiplicities`)。そのため、`ident ident … ident 5` と、引数を渡さない部分適用 (`let g = ident ident … ident`) は、適用の数の2乗の時間がかかる (`ident : a -> a`)。release ビルドの `eml check` では、2000個の適用で約0.13秒である
- Kind の検査は、値を使うたびにその型をたどる (`kind_at_most`)。そのため、`let p1 = (p0, p0)` のように前の値の組を作る `let` の列は、`let` の数の2乗の時間がかかる
- 単一化は、単一化を終えた複合の型の組を、1回の呼び出しの中でだけ覚える ([コンパイラの構成](architecture.md) の「`eml_types` の内部」)。そのため、同じ大きな型の組を何度も単一化すると、そのたびに推論の表の大きさに比例する時間がかかる。2本の `let` の列の後で、`let h1 = if c then f1 else g1`、`let h2 = if c then f2 else g2` のように、対応する値を1つずつ合わせる形がこれに当たる
- 単一化、occurs の検査、書き出し、表示の再帰の深さは、型の深さに比例する。そのため、非常に深い型ではスタックが尽きる。既定で 8 MiB の release の CLI のメインスレッドでは、`let` の列 (`let f1 = f0 ident` の列) 1本は長さ20000まで通り、30000で尽きた。その列を2本作って `if` で合わせる形は、長さ10000まで通り、20000で尽きた。単相化の型の置換 (`TypeStore::substitute` と `eml_core_ir/src/translate/instances.rs` の `vars_in`) も型の深さまで再帰する。そのため、同じ列が総称な関数 (`run : a -> a` で、最後が `f{n} x`) の中にあると、`eml run` は Core IR への変換で先に尽きる。同じ release の CLI では、長さ17500まで通り、20000で尽きた。再帰を作業の列に置き換えれば、型の深さによらなくなる (置換の再帰も同様である)
- 状態を持つ handler が `return` を省くと、`usage.rs` は状態の型を、そのたびに新しい `Exporter::diagnostic` で書き出す。状態の型が大きな共有の型のとき、そうした handler が多いと、handler の数と型の大きさの積の時間がかかる。10000個の `let` の列と、`from f0` を使うそうした handler 2000個の組み合わせは、release で約3.3秒かかった (`from 1` なら約0.15秒)。使用の検査の全体で1つの記録を共有すれば避けられるが、`Exporter` は推論の表を借りている間しか生きない、という決まりを手放すことになる ([コンパイラの構成](architecture.md))
- 型の誤りの文言は、型を木として表示する (`TypeStore::display`)。そのため、部分を多く共有する型を文言に含む誤り (長い `let` の列の後の `let x : Int = f0` など) では、文言の長さが列の長さの指数になる。型の表そのものの大きさは、列の長さに比例したままである
- 単相化は instance の総数に上限を置かない ([Core IR](../spec/core-ir.md) の「変換の規則」)。多相再帰がなくても、関数の鎖の各段で次の関数を2通りの型で呼ぶと (`fi` の本体が `f(i+1) (x, 1)` と `f(i+1) (x, "s")` を呼ぶ形)、instance の数が段ごとに倍になり、鎖の長さの指数になる
- instance の鍵は型そのものなので、`List Int` と `List String` のように Repr が同じ型引数でも別の instance になり、同じ形のコードが複数できる。まとめるのは処理系の最適化に回す ([ロードマップ](../future/roadmap.md) の「処理系」)
- 決定木の再帰 (`translate/pattern.rs` の `decide`) の深さは、1つの `match` のパターンの大きさで決まる。コンストラクタやタプルの入れ子の深さは E0013 で抑えられるが、決定木の再帰の深さそのものは抑えていない。リテラルの列は1つの `switch` になり、複数の葉から届く枝は合流のブロックとして平らに並ぶので、リテラルが1000個の `match` や、そうした枝の多い `match` (`match (a, b) with | (0, 0) -> 0 | (_, 1) -> 1 … | (_, 999) -> 999 | _ -> 7`) は debug ビルドでも動く
- Kind のスキームを作る処理 (`residual`) は、1つの SCC の中で、関数ごとに残す成分から残さない領域をたどる。DAG の形によっては、残さない成分を関数ごとに何度もたどる。たとえば環状の相互再帰で、各関数の矢印の Kind 変数がどれも定数の境界を持つと、その成分は何もない成分にならず、関数の数の2乗の時間がかかる。また、持ち越しの制約を関数ごとに SCC 全体から見るので、関数の数と持ち越しの制約の数の積がかかる。どちらも、大きな SCC が多くの持ち越しの制約を持つ場合だけに起きる
- 1つの SCC の各メンバーが、トップレベルの矢印を返す関数の長い鎖 (`q_n ≤ … ≤ q_1`) を参照すると、既存の Kind のスキームの計算 (`residual`) が2乗の時間がかかる。鎖の長さを4倍にすると、release ビルドで時間が約14倍になった。S8c で入れた書き出しの要約 (`kind/summary.rs`) の費用ではない
- 直前のラムダを捕まえるラムダの鎖 (`let q{i} = fn x -> q{i-1} x`) は、型の書き出しより前の段階で2乗の時間がかかる。鎖の長さを4倍にすると、release ビルドで時間が約13.6倍になった。どのパスが原因かは調べていない
- 操作は evidence passing で実装し、evidence を `evv` の先頭から探す ([LIR](../spec/lir.md) の「evidence を探す」)。探す費用は今有効な handler の数に比例し、呼び出しの深さにはよらない。すぐに再開する操作 (状態の `get` と `put` など) は、その場で節を実行するので、yield も継続の組み立てもない。ただし、再帰の各段で別のエフェクトの handler を設ける形では、`evv` の長さが深さに比例するので、1回の探す費用も深さに比例する。探す場所ごとのキャッシュか静的な添字で解く ([ロードマップ](../future/roadmap.md) の「処理系」)
- すぐに再開しない操作は handler まで yield し、戻る途中の各段が自分の続きを継続に足す。1回の yield の費用は、操作と handler の間のフレームの数に比例する。これは方式の性質である
- 中断 (`never` の操作、`try_io` が捕まえる IO の失敗、`exit`) は継続を組み立てず、タスクのスタックを巻き戻す ([VM](../spec/vm.md) の「巻き戻し」)。費用は外すフレームの数と手放す値の数に比例する。`IO` と `never` の操作だけのエフェクトは yield の地点に数えないので ([型と Kind](../spec/types.md) の「row の具体化の記録」)、`<IO>` の中で呼んだ総称な handler は、`println` を呼ぶコールバックを渡しても yield しない。S13d からは、外側にユーザーのエフェクト (`State` など) の handler がある所でも、純粋なコールバックを渡せば yield しない。呼び出し先の row が今の row を受けず、どの引数からもエフェクトが入らなければ `<>` に閉じるためである ([型と Kind](../spec/types.md) の「呼び出しの包含を解く」)。ただし、`Yield a` を `Yield b` に変える handler の `yield` の節は、節が外側の `yield` を起こすので、1要素ごとに yield する ([計測の基準](benchmarks.md) の「S13d」)
- すぐに再開する操作は、1回の操作で、evidence を探す基本操作と入口を読む基本操作、入口の関数の呼び出し、状態の出し入れの基本操作、yield の確認を実行する。節の本体が何かを呼ぶときは、入口の under の基本操作 (`evv_get`、`ev_evv`、`evv_set` と、戻す `evv_set`) も加わる ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。evidence passing に変えた S7 では、handler を探していた前の形より `bench/state.em` の実行の分が約70% 増えた ([計測の基準](benchmarks.md) の「S7 (evidence passing)」)。S8b で基本操作が evidence を借りるようにしたので、RC の増減は `ev_lookup` が作る参照と入口の終わりの `decref` の1回ずつになり、実行の分は S7 の記録より約11% 減った ([計測の基準](benchmarks.md) の「S8b (所有の形と基本操作の借用)」)
- yield しうる要素を n 個並べたリストのリテラルでは、yield の地点ごとの遅い道が生きている変数を捕獲するので、遅い道の捕獲の大きさが n の2乗になる ([Core IR](../spec/core-ir.md) の「継続の関数」)
- `++` は一意な左辺をその場で伸ばすが、先頭に足す連結 (`"x" ++ acc`) と、共有された左辺への連結は、両辺を写した新しい文字列を作る。ループで先頭に足していくと、伸びていく右辺を毎回写すので、全体で2乗の時間がかかる ([オブジェクトモデル](../spec/object-model.md) の「文字列の操作」)
- 末尾呼び出しの保証は、末尾の位置の呼び出しをたどって元の関数に戻る輪の上にだけある ([LIR](../spec/lir.md) の「末尾の位置の呼び出し」)。輪の上にない末尾の位置の呼び出しのうち、結果に変換の要るものは普通の呼び出しになる。UI のプログラムでは、`$handleN` の本体が `Int` を返すトップレベルの関数を末尾の位置で呼ぶ形がこれに当たる。輪をたどらないので、積むフレームは有界である
- 呼び出しの値が、文を持つ合流のブロックを通って `return` に届く形 (`let r = if n == 0 then 0 else f (n - 1) in let s = "unused" in r`) は、末尾の位置の呼び出しでなく、末尾呼び出しにならない。translate の転送は文のない合流のブロックにしか効かないので、この形のループは反復の数に比例してフレームを積む。縮約が使われない `let` を消した後で、`return` だけになった合流のブロックへの転送をやり直せば、保証の範囲を広げられる
- eml で1バイトずつまわすループは、Python の組み込みの関数より約20倍遅い。`bench/loop.em` の1反復は約330命令かかる。30 MB の入力を1バイトずつ数える `wc` のスクリプトは約1.7秒で、`Stdin.read_line` や `String.find_from` のような extern に任せられる処理は速い ([計測の基準](benchmarks.md) の「S12d (スクリプト)」と「S13c」)
- `Iter` で引くと、1要素ごとに yield と確保が起きるので、push の形の `Yield.for_each` より遅い。状態機械への特殊化は S13e で入れる ([標準ライブラリ](../spec/stdlib.md) の「`Iter`」)
- 既知の閉包への特殊化 (S13e-1、[Core IR](../spec/core-ir.md) の「最適化」) は、同じ関数の中で `closure` か `&f` で束縛した閉包と、複製が捕獲に開いた引数の組だけを既知とする。ブロック引数を通って合流する閉包と、データに入れてから取り出した閉包は特殊化しない。データを通る閉包は S13e-3 で扱う
- 呼び出し先がすでに特殊化した複製である呼び出しは、それ以上特殊化しない。鍵の入れ子の深さが上限 (`MAX_KEY_DEPTH`、今は4) を超える位置でも、閉包を作り直して渡す
- 一様な instance (`_:poly`) の中では、既知の閉包への `apply` でも、`unr` でない引数を箱を要するスカラーの引数で受ける閉包の関数には、直接の呼び出しにしない。値が型変数の印 (`poly`) のままで、直接の呼び出しにすると Perceus が `poly` の値を `decref` で手放すことになるためである ([LIR](../spec/lir.md) の「Kind の印の検査」の V1)
- 包む関数と同じ形のユーザーのラムダ (`fn x -> Some x` や `fn x -> yield x`) と、translate の `op$` の値 (`List.each yield lines` の `yield`) は、鍵の閉包の関数にしない。包む関数は名前でなく形で見分けるので、同じ形のラムダも包む関数として扱われるためである。これらを渡す高階関数の呼び出しは、S13e-1 では特殊化しない
- S13e-1 はインライン化しないので、閉包の本体を埋め込んだ手書きの版に比べ、要素ごとに直接の呼び出しが1回残る。直接の呼び出しは要素の所有権を受け取るので、呼び出しの後も要素を使う形 (`filter` の `x :: acc`) では、1要素ごとに `dup` が残る。確保と `box` / `unbox` の回数は手書きの版と同じだが、RC の回数と命令の数が手書きの版に届くのは S13e-3 である ([計測の基準](benchmarks.md) の「S13e-1」)

### 型と row の推論

- ローカル関数は単相で、多相にできない。シグネチャと結果の型の明示もない (引数の後の `:` は誤りになる)。相互再帰は `let … and …` の組で書く。多相にすることは採らなかった ([ロードマップ](../future/roadmap.md) の「S13 実例による判断」)
- `File` を捕まえた再帰するローカル関数が、自分を呼ぶ前に `multi` の操作を起こすと、E3001 のほかに、その関数に冗長な E3006 も出る。`let … and …` の組でも同じで、組の関数が `multi` の操作を起こしてから組の別の関数を呼ぶと、呼ばれる関数に冗長な E3006 が出る (`and b n = if choose () then a n else a n` の `a`)。自分への参照がネストしたラムダの中にだけある場合、E3001 はそのラムダを指す
- 持ち越し規則は、`handle` の外側の row と `k` の呼び出しの row (handle の外側の row) を、handle の位置の今の row とみなす。そのため、今の row に `multi` があれば、本体が `multi` の操作を起こさなくても、handle をまたぐ `File` が拒否される。健全な側に外れるだけである。handle の本体が起こすエフェクトを本体の中の呼び出しの row から集めるときに見直す
- 高階のローカル関数の結果を射影する形は E2013 になる。`<State Person>` の本体で `let run h = h ()` を `(run get).name` と使うと、`run` の row に `State` が入るのは本体の後で包含を解くときなので、射影の時点では `get` の結果の型が決まっていない。結果の型を明示すれば通る (`(run get : Person).name`)。呼び出しの包含は、包含を積む時点で分かっているラベルの型引数だけをその場で単一化する ([型と Kind](../spec/types.md) の「推論」)
- 同じローカル関数を、row が閉じた別々の関数型の位置に値として渡す形 (`Int -> <IO> Int` の引数と `Int -> Int` の引数の両方に渡す) は、E2001 か E2002 になる。値の参照が関数の row 変数を共有するためで、単相のローカル関数の制限である ([型と Kind](../spec/types.md) の「ローカル関数の推論」)
- 有限の解のない組や呼び出しの輪の E2002 は、本体の大きさに比例する手間をかけてから見つかる。ラベルの固定点の上限を本体全体の包含のラベルで数えるので、輪は上限に達するまでラベルを足し続けるためである ([型と Kind](../spec/types.md) の「呼び出しの包含を解く」)。足したラベルは今の row に残るが、E2002 の文言はエフェクトの名前を1回ずつ書く

- 射影と更新は、その時点で分かっている型からフィールドを引く。呼び出しの引数のラムダは後で検査するが、後に回したラムダどうしは左から検査するので、後のラムダが前のラムダの引数の型を決める形 (`compose (fn b -> b.name) (fn p -> p.boss) x`) は E2013 になる。`let` で束縛したラムダの中の射影 (`let f = fn p -> p.name`) も、`f` を呼ぶ前に検査するので E2013 になる。どちらも引数の型を明示して書く ([型と Kind](../spec/types.md) の「引数のラムダを後で検査する」)

### 型クラス

- メソッドの呼び出しの評価の順は、メソッドのシグネチャの矢印の数で決まり、instance の等式の引数の数によらない ([式](../spec/expressions.md) の「関数適用」)。どの instance を選んでも同じ順になるようにするためである。そのため、等式の引数が矢印より少ない instance のメソッドは、等式の引数で呼んだ結果に残りを `apply` する。等式の数の引数で1回に呼ぶ形より、呼び出しが1つ増える
- 一様な位置のグラフで、関数の参照の制約を解いた先は、instance のすべてのメソッドへ辺を引く。既定のメソッドに解決したメソッドの参照も、根の制約の instance の節点へ辺を引く ([Core IR](../spec/core-ir.md) の「一様な位置と制約付きの多相再帰」)。どちらも保守的なので、E2012 が偽の循環を報告しうる。クラスの制約を使わない既定のメソッド (`differ x y = True`) を、instance のメソッドが大きな型で呼ぶ形 (`same (Box x) (Box y) = differ (Box (Box x)) (Box (Box y))`) は、単相化が止まるのに E2012 になる。既定のメソッドの本体が使う証拠を辺に写せば、偽の循環を減らせる
- 演算子のメソッドの等式で、被演算子に括弧のないコンストラクタのパターンを書くと (`Box x == Box y = …`)、等式として読まれない。演算子の等式の先読み (`grammar/items.rs` の `at_operator_equation`) が、演算子の前に単純なパターン (`patterns::apat_len`) を1つしか認めないためで、S5 より前からある。パーサは「expected a method equation」(E0011) を出す。そのメソッドに既定のメソッドがなければ、等式がないことの E1036 も続く。`(Box x) == (Box y) = …` と括弧に入れて書く。手で書く instance ではこの形がよく現れる
- 導出した instance のフィールドの E2006 は、instance ごとに最初のフィールドの1つだけを報告する。ほかのフィールドの誤りは、最初の誤りを直した後に出る
- instance のメソッドの関数と生成した関数の名前は、クラスと型を診断と同じ表示で書く。そのため、別のモジュールが同じ名前の型を足すと、Core IR の関数の名前が変わることがある

### HIR の位置

- HIR の関数は、シグネチャの関数名の位置 (`Function::signature_name_range`) と等式の関数名の位置 (`Function::equation_ranges`) を持つ。S3a で HIR から見た目の情報 (行頭と字下げ) を除いたが、この2つはソースに書かれた名前の位置なので残した。等式の数は、E1020 の後の網羅性の診断の連鎖を抑えるのにも使う。HIR の位置を別の表に分けるのは、[ロードマップ](../future/roadmap.md) の「処理系」にある source map の項目で行う

### verifier

- R8 は、`con`、タグの `switch`、`unpack`、`release` を、それぞれが指す配置と比べるだけで、値がどの配置で作られたかを追わない。そのため、配置の違う値を読む IR も verifier を通る。タグかフィールドの数が違えば、検査モードの VM が内部の誤りで止まり、形が同じなら気付かない。`tobj` に入ったヒープの物体を `unbox` する IR も verifier を通り、検査モードの VM がヒープの誤り (`WrongKind`) で止まる。translate の型が、この形を作らないことを保証する ([LIR](../spec/lir.md) の「構造の規則」)
- LIR の変数は Kind の印を持ち、verifier の V1 が `unr` でない変数の `dup` と `decref` を、V2 が `unr` と `lin` の受け渡しを、作る所の検査が `con` と `closure` の印を静的に拒む ([LIR](../spec/lir.md) の「Kind の印の検査」)。`lin` ビットの立った物体 (`File` など) の参照を増やす違反は、検査モードの `eml_rt` も実行時に `a Lin object is shared` で止める ([オブジェクトモデル](../spec/object-model.md) の「`lin` ビット」)。`unpack` と case で得たフィールドの印は、配置の表がフィールドの Kind を持たないので verifier が確かめず、translate を信用する。検査モードの `lin` ビットの誤りが実行時に覆う
