# 実装の現在地

位置づけ: 手引き。2026-10-03 時点のリポジトリの状態を書いている。

マイルストーン1 の目標と範囲、構文の実装段階、各 crate の実装状況、次の作業の注意点、S1 の後始末、決定済みで実装待ちの方針をまとめる。実装が進んだら、この文書を更新する。

## マイルストーン1 の成功条件

マイルストーン1 は、言語の全体を一通り通す vertical slice である。成功条件は次のとおり。

1. 本番の構文で書いた eml プログラムを `eml run <file>` で実行できる
2. `eml check <file>` で、構文・名前解決・型・線形性・エフェクト・`match` の網羅性のエラーを、ソース位置を指す診断として表示できる。1回の実行で、独立した複数のエラーを報告できる
3. ユーザー定義のエフェクト (`never` / `once` / `multi`) と handler (`resume` と `drop k`) が動く
4. 線形なリソース (`File`) を扱うプログラムで、消費漏れ・二重使用・`multi` をまたぐ持ち越しをコンパイル時に検出できる
5. すべての実行テストで RC のリーク検出と解放済みアクセスの検出が有効になっており、通過している

## マイルストーン1 の範囲

### 含めるもの

- 基本型: `Int`、`Bool`、`String`、`Unit`。`Bool` は組み込みの `data Bool = | False | True` で、キーワード `true` / `false` はない。単項の `!` はなく、関数 `not` を使う
- タプル (数字ラベルの閉じたレコードとして表現する。[直積型とレコード](../spec/records.md))、ユーザー定義の代数的データ型 (`data`) と `match` (網羅性の検査つき)
- トップレベルの関数 (シグネチャが必須)、ローカルの `let`、`if` (then 節が `Unit` なら `else` を省略できる)、再帰、クロージャ、型の明示 `(e : T)`
- `drop` キーワード
- エフェクトの宣言 (`never` / `once` / `multi`)、`handle` (deep)、`resume`、`drop k`
- 組み込みの `IO` エフェクト: `println : String -> <IO> Unit`、ファイル操作 (`open : String -> <IO> File`、`read_all : File -> <IO> (File, String)`、`close : File -> <IO> Unit`)
- 組み込みの線形型 `File`
- 本番の構文のうち S1 に含めたもの: 複数の等式による定義、fixity の宣言、`let ... in`、`use`、パラメータ付き handler (`handle ... from ... with`)、演算子のセクション、最後の引数のラムダ、16進などの整数リテラル、ブロックコメント

### 含めないもの

- LSP、フォーマッタ、REPL
- LLVM バックエンド
- 型クラスやトレイトなどのアドホック多相
- モジュールシステム (マイルストーン1 は単一ファイル。構文は [モジュールと名前解決](../spec/modules.md) で定めた)
- 可変参照 `Ref`
- Perceus の reuse analysis と借用の最適化
- 表面構文でのユーザーによる Kind の記述 (関数型の線形性 `m` を含む)
- `IO` をユーザーが handle すること
- or パターン、ガード、as パターン
- 名前付きのレコード (構文は定めた。実装は S2)
- 浮動小数、文字型 (字句として予約し、使うと E0004)

将来の拡張は [ロードマップ](../future/roadmap.md) にまとめてある。

## 構文の実装段階

本番の構文は3段階で実装する。

| 段階 | 内容 | 状態 |
|---|---|---|
| S1 | lexer (新しいトークン、`--` と `{- -}`、shebang、`'` を含む識別子、数値の形、浮動小数と文字は E0004)、レイアウト段、M1 の機能の文法 (宣言、式、パターン、型と row、エスケープだけの通常の文字列) | 完了 |
| S2 | 名前付きのレコードと `type`、モジュールと import / `pub`、`Prelude`、リストのリテラル、補間、複数行の文字列、raw 文字列 | 未着手 |
| S3 | コマンドリテラル (標準ライブラリの `Proc` と一緒に) | 未着手 |

S2、S3 の構文は、S1 の時点でも字句と文法の置き場所を用意してある。使うと E0004 (未対応) を出して回復する。暫定構文の文法は実装せずに捨てた。

## 次の作業の注意点

- 名前解決に入る前に、下の「S1 の後始末」を行う。診断の位置と回復を先に固めておき、HIR 以降をその上に作るため
- 名前解決以降の各段階は、TDD で中身を実装する
- `la-arena` は、HIR で ID を使い始める段階で追加する
- 型検査器を実装するときは、S2 の名前付きレコードを待たずに、M1 のタプルを最初から「数字ラベルの閉じたレコード」として表現することを勧める。後の作り直しを避けるため
- 直積型の構造的なレコードへの統一 (`RecRow<m>`、射影・更新の線形性の規則) と、操作のカリー化に合わせた handler の節の引数の個数は、本番の構文を決めたときに型システムへ加えた規則である。実装は型検査器の計画で扱う
- パーサは、セクション (`LEFT_SECTION` / `RIGHT_SECTION`) の中の前置の `-` を平たく置いている。HIR の変換では、セクションの中でも単項マイナスを扱う必要がある

## S1 の後始末

HIR の前に1つの作業としてまとめて行う。方針は 2026-10-03 に決め、spec に反映済みである。合意済みのテストの期待値が変わるものは、その旨を書いた。

| 課題 | 方針 | 規範 |
|---|---|---|
| 仮想トークンとファイル末尾でのエラーの位置 | 直前の実トークンの直後の空の範囲を指す。`tests/expressions.rs` の `missing_operand_does_not_affect_the_next_item` は 2:1 から 1:8 に、パーサの単体テスト `error_at_eof_points_at_end_of_text` は位置 2 から 1 に変わる (テスト名も直す) | [レイアウト規則](../spec/layout.md) の「エラー回復」 |
| 回復用の空の `BLOCK` が次の行の位置に置かれる | 上と同じ位置に置く | 同上 |
| `match` / `handle` と同じ列に書いた枝 | E0009 を1件だけ出し、枝を深く字下げするよう促す help を付ける。続く `\|` の行は追加の診断なしで読み飛ばす。`tests/control.rs` の `arms_at_the_column_of_match_need_indentation` の期待値は E0009 だけになる | 同上 |
| 行末の `->` で揃えた複数行のシグネチャ | spec は変えず、行頭に `->` を置く書き方を推奨として文書にした。この場合の E0009 に `->` を次の行の先頭に置くよう促す help を付け、診断を1件にする | [宣言](../spec/declarations.md) の「シグネチャと等式」 |
| 左側が型の適用になっている中置のコンストラクタ (`\| List a :: L a`) | 受け付ける (`btype CONOP btype`) | [文法](../spec/grammar.md) |
| 被演算子が複数あるセクション (`(+ a * b)`、`(a * b +)`) | 演算子の列を受け付け、優先順位の可否は HIR で検査する (E1xxx、HIR の計画で実装) | [式](../spec/expressions.md) の「セクション」 |
| 括弧の中の `;` で診断が連鎖する | 規則 5 のエラーを1件だけ出し、対応する閉じ括弧まで読み飛ばす | [レイアウト規則](../spec/layout.md) |
| 型の中の `-><` が1つのトークンになる | 型の位置では `->` と `<` に分割して読む | [文法](../spec/grammar.md) の「文法上の補足」 |
| 括弧の種類が対応しないとき、レイアウト段とパーサの解釈が食い違う | レイアウト段が括弧の種類を覚え、対応しない閉じ括弧はエラーにして一番内側の括弧を閉じる。パーサも同じ解釈をする | [レイアウト規則](../spec/layout.md) の規則 4 |
| 閉じ忘れた括弧がファイルの残りを飲み込む | 規則 2 を変えた。括弧の中で、囲んでいるブロックの列以下に置いた行 (閉じ括弧を除く) は、閉じていない括弧のエラーにして括弧を閉じる | [レイアウト規則](../spec/layout.md) の規則 2 |
| 再帰の深さの上限がない (括弧を約2万重に入れ子にするとスタックが溢れる) | 入れ子の深さを 256 までにし、超えたら E0013 `NESTING_TOO_DEEP` を出す | [文法](../spec/grammar.md)、[診断](../spec/diagnostics.md) |
| いくつかの回復の経路にテストがない | `expected(p, what)` のような補助関数を作り、繰り返しているエラーの呼び出しをまとめる。テストのない回復の経路にテストを足す | — |
| BOM が診断の表示で1列に数えられる | 表示の層 (`render.rs`) で BOM を除き、位置をずらす。`TextRange` は元のテキストのバイト位置のまま | [字句](../spec/lexical.md)、[診断](../spec/diagnostics.md) |
| 警告がプログラムの出力の後に表示される | lib API の `run` を `compile` と `execute` に分け、CLI と UI テストは診断を表示してから実行する | [アーキテクチャ](architecture.md) の「CLI と lib API」 |
| `Severity::Note` が ariadne では「Advice」と表示される | 使っていないので `Severity::Note` を削除する | [診断](../spec/diagnostics.md) |

## spec に反映済みで、実装は後の計画で扱うもの

- コンストラクタは値の名前空間に置く。型とコンストラクタは同じ名前を持てる。import の並びではコンストラクタを `T(..)` でだけ取り込む ([モジュールと名前解決](../spec/modules.md))。HIR の計画で実装する
- 操作名の重複は、一般の「トップレベルの定義の重複」の規則の帰結として扱う。handler の節の先頭の名前は、エフェクトの操作だけから解決する ([モジュールと名前解決](../spec/modules.md))。HIR の計画で実装する
- `resume` の引数の個数の診断は E1xxx とする。E1xxx は「名前解決と HIR での検査」の範囲である ([診断](../spec/diagnostics.md))。HIR の計画で実装する
- 網羅されていない等式の診断は、シグネチャの関数名を primary、各等式の先頭を secondary にする。等式が1つの場合も同じ扱いにする ([網羅性](../spec/exhaustiveness.md)、[診断](../spec/diagnostics.md))。網羅性の検査の計画で実装する

## 採用しないもの

- Haskell 形式の `\x ->` のラムダに対するヒント。他の言語の書き方を前提にした診断は、煩雑になるだけなので入れない
