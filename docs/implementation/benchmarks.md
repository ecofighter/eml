# 計測の基準

位置づけ: 手引き。

段の前後で実行の費用を比べるための、基準のプログラムと測り方をまとめる。S10 の VM は、ここの記録と比べる ([ロードマップ](../future/roadmap.md))。S4b の単相化、S5 の型クラス、S6a のリスト、S6b の文字列、S6c のレコード、S7 の evidence passing、S8b の所有の形と基本操作の借用のそれぞれの前後は、下の「記録」にある。

費用は2つの数で見る。

- 実行の仕事の回数 (`RunStats`): 決定的なので、テストのスナップショットで固定する。回数が変わると、スナップショットの差分として出る
- 実行した命令の数: macOS の `/usr/bin/time -l` が出す `instructions retired` を、`bench/run.sh` で測る。測定の環境と一緒に、下の「記録」に書く

## 基準のプログラム

リポジトリの `bench/` に置く。各プログラムは結果を1行出力する。`empty.em` だけは何も出力しない。大きさは、debug ビルドで `debug_heap` を付けたときに1本1秒以内で終わるように決めた。

| ファイル | 中身 | 主に見るもの |
|---|---|---|
| `empty.em` | 何もしない `main` | 起動と標準ライブラリのコンパイルの分 |
| `fib.em` | `fib 25` | 呼び出しと `Int` の算術 |
| `loop.em` | 末尾再帰のループ | 末尾呼び出し |
| `state.em` | `get` と `put` を持つ `Counter` の handler の下で数える再帰 | すぐに再開する操作 |
| `list.em` | プログラムの中で定義した `List a` を `range`、`map`、`foldl` で合計する | 型変数のフィールドの `Int`、高階関数 |
| `tree.em` | 線形合同法で作った `Int` を二分探索木に入れ、総称な `size` と `fold` で畳む | 再帰的なデータ、`switch` と `unpack` |

`list.em` と `tree.em` はデータ型を自分で定義する。S6a で Prelude に `List` とリストのリテラルが入った後も、前の段の記録と比べられるように、自分のデータ型を使い続ける。`list.em` と `tree.em` の多相な関数 (`map`、`foldl`、`size`、`fold`) では、型変数の位置の `Int` が `box` と `unbox` を通る。単相化の前後でこの回数がどう変わったかは、下の「記録」の「S4b (単相化)」にある。

## 回数のテスト

`crates/eml_interp/tests/bench.rs` は、プログラムごとに1つのテストで、`debug_heap` を付けて走らせ、出力を確かめ、`RunStats` の全項目をインラインスナップショットで固定する。`bench/` のファイルの一覧と、テストのプログラムの一覧が一致することも確かめる。回数は機械の速さに左右されないので、ふだんの `cargo test` で流す。

段の前後の回数は、このスナップショットの差分で残る。回数を変える変更は、その段の spec に期待値の変更として書く ([テスト戦略](testing.md) の「テストの変更の運用」)。

## 命令の数の測り方

```sh
bench/run.sh
```

`bench/run.sh` は、release ビルドの `eml run` で各プログラムを3回走らせ、`instructions retired` と実時間の中央値を Markdown の表で出す。表の前に、測定の環境 (機種と CPU、macOS の版、`rustc -V`、コミット) を出す。コミットしていない変更があれば、コミットの後に `-dirty` が付く。プログラムが実行時エラーで止まったときと、`time -l` の出力から命令の数か実時間を読めなかったときは、その出力を見せて止まる。macOS でだけ動く。

valgrind が arm64 の macOS で動かないので、callgrind は使わない。`instructions retired` は callgrind ほど決定的ではないが、S4a の設計のときに release ビルドの `fib 30` を3回測った揺れは約0.1%だった。arm64 の命令の数なので、過去の調査で x86_64 の callgrind を使って測った値とは直接比べない。

`empty.em` の命令の数は、起動と標準ライブラリのコンパイルの分である。ほかのプログラムの値からこれを引くと、実行の分の目安になる。実時間は 0.01 秒単位なので、命令の数を主に見る。

段の終わりに `bench/run.sh` を流し、出力の環境と表を、下の「記録」に段の見出しを付けて足す。

S7 で `RunStats` の項目が変わった。CEK が handler を探すときに調べたフレームの数を消し、`evidence_steps`、`yields`、`yield_frames` を足した ([ランタイム](../spec/runtime.md) の「実行の API」)。`crates/eml_interp/tests/bench.rs` のスナップショットで回数が変わったのは `state` だけである。調べたフレームの数の 200000 は `evidence_steps` の 200000 になり、`yields` と `yield_frames` は 0 である。`get` と `put` はどちらもすぐに再開する節なので、その場で実行され、yield も継続の組み立てもない。`rc_increments` は 0 から 600005 に、`rc_decrements` は 2 から 600010 に、`peak_objects` は 6 から 7 に増えた。1回の操作で RC の増減が3回ずつ増えるのは、基本操作が引数をすべて消費するためである。`ev_lookup` が evidence の参照を1つ作り、それを消費する `ev_clause`、節の呼び出し、入口の `ev_take_state` と `ev_set_state` のために `dup` が2回要り、消費した基本操作の3回が `decref` になる。基本操作の引数を借用にすれば減らせる ([ロードマップ](../future/roadmap.md) の「S8 LIR」)。ほかのプログラムは handler を使わず、row のビットで純粋な instance には EP が何も足さないので、回数は変わらない。

命令の数は、`state` で大きく増えた。`empty` の値を引いた実行の分は、S6c の約10.209億から約17.383億になり、約70% 増えた。`state` の `count` は末尾再帰なので、S6c の CEK でも handler は操作の1つ外側のフレームにあり、`perform` が調べるフレームは1つだった。evidence passing の利点は、すぐに再開する操作の費用が呼び出しの深さによらないことで、この利点は `crates/eml_interp/tests/scaling.rs` の `immediate_operations_cost_the_same_at_any_depth` で確かめている。深さが一定のこのプログラムでは、その利点は命令の数に現れない。逆に、1回の操作で実行する文が増えた。evidence を探す基本操作と入口を読む基本操作、入口の関数の呼び出し、入口の中の状態の出し入れの基本操作、呼び出しの後の yield の確認 (`yielding` と `switch`) である。入口の中の `unbox` と `box` は、S6c から入口へ移ったもので、増えてはいない。`boxes` と `unboxes` は 100002 と 100001 のまま変わらない。インタプリタは基本操作の引数を毎回 `Vec` に組み立てて渡すので、文の1つ1つが重い。どの寄与がどれだけかは分けて測っていない。

`empty` は S6c より約40万 (約1.4%) 増えた。同じビルドで `eml check bench/empty.em` を3回測ると約2868万から2941万で、ばらつきが大きいので、増分をフロントエンド (row の分類の記録) と Core IR の変換 (EP) に分けていない。`empty` の値を引いた実行の分は、`list` で約1.5%、`fib` で約1.6%、`tree` で約1.7%、`loop` で約2.7% 増えた。どれも handler を使わず、仕事の回数は同じである。インタプリタの値に `Value::Dummy` を足し、呼び出しの経路に `Call::Clause` と `mask` の検査を足したが、原因は調べていない。

S8a は命令の数を記録していないので、この表は S7 の記録と比べる。S7 と S8b の間には、S8a (LIR を作り、CEK が LIR を読むようにした作業) と S8b の両方の変更が入っている。2つを分けるため、同じ環境で S8a の終わりのコミット (49a5cc1) も3回ずつ測った。その中央値は、`empty` が 29118757、`fib` が 984142040、`list` が 1794331455、`loop` が 1535974372、`state` が 1747515874、`tree` が 1573805078 である。

`crates/eml_interp/tests/bench.rs` のスナップショットで回数が変わったのは、`state` の `rc_increments` と `rc_decrements` だけである。`rc_increments` は 600005 から 200001 に、`rc_decrements` は 600010 から 200006 に減った。どちらも、200000 回の操作で1回あたり2回ずつ減り、ほかに1回だけの分が4回ずつ減った。S8a の前後では回数は変わっていない。

- 1回の操作の RC の増減は、`ev_lookup` が作る evidence の参照1つと、入口の関数の終わりの `decref` 1つになった。S7 では、`ev_clause` と、入口の `ev_take_state` と `ev_set_state` が evidence を消費した。そのため、後でも evidence を使う `ev_clause` と `ev_take_state` の前に `dup` が1回ずつ要り、消費した3つの基本操作の中で `decref` が3回あった ([LIR とインタプリタ](../spec/lir.md) の「基本操作」)。
