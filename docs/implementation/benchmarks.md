# 計測の基準

位置づけ: 手引き。

段の前後で実行の費用を比べるための、基準のプログラムと測り方をまとめる。S10 の VM は、ここの記録と比べる ([ロードマップ](../future/roadmap.md))。S4b の単相化、S5 の型クラス、S6a のリスト、S6b の文字列、S6c のレコード、S7 の evidence passing、S8b の所有の形と基本操作の借用のそれぞれの前後は、下の「記録」にある。

費用は2つの数で見る。

- 実行の仕事の回数 (`RunStats`): 決定的なので、テストのスナップショットで固定する。回数が変わると、スナップショットの差分として出る
- 実行した命令の数: macOS の `/usr/bin/time -l` が出す `instructions retired` を、`bench/run.sh` で測る。測定の環境と一緒に、下の「記録」に書く

## 基準のプログラム

リポジトリの `bench/` に置く。各プログラムは結果を1行出力する。`empty.em` だけは何も出力しない。大きさは、debug ビルドで `debug_heap` を付けたときに1本1秒以内で終わるように決めた。

|---|---|---|
| `empty.em` | 何もしない `main` | 起動と標準ライブラリのコンパイルの分 |
| `fib.em` | `fib 25` | 呼び出しと `Int` の算術 |
| `loop.em` | 末尾再帰のループ | 末尾呼び出し |

| `list.em` | プログラムの中で定義した `List a` を `range`、`map`、`foldl` で合計する | 型変数のフィールドの `Int`、高階関数 |

| `tree_map.em` | 8191 節の完全二分木の全節を、`incr` で20回作り直す (S13e-4 で足した) | 書かないフィールドとその場の書き換え |
| `std_list.em` | 2万要素のリストに、std の `List.map` と `List.filter` を5回通す (S13e-4 で足した) | std のリストの関数の reuse |
| `sieve_var.em` | 20000 より小さい素数の数を、`var` で書いたふるいで数える (S14c-3 で足した) | 入れ子の `var` の、状態を渡す形の特殊化 |

`_by_hand` の版は、対応する自動の版と同じ出力を出す。特殊化の効果は、自動の版の `RunStats` が手書きの版に近づくことで測る。

`list.em` と `tree.em` はデータ型を自分で定義する。S6a で Prelude に `List` とリストのリテラルが入った後も、前の段の記録と比べられるように、自分のデータ型を使い続ける。`list.em` と `tree.em` の多相な関数 (`map`、`foldl`、`size`、`fold`) では、型変数の位置の `Int` が `box` と `unbox` を通る。単相化の前後でこの回数がどう変わったかは、下の「記録」の「S4b (単相化)」にある。

## 回数のテスト

`crates/eml_vm/tests/bench.rs` は、プログラムごとに1つのテストで、VM の検査モードで走らせ、出力を確かめ、`RunStats` の全項目 (S13e で足した `allocations` と、S13e-4 で足した `reuses` を含む) をインラインスナップショットで固定する。`bench/` のファイルの一覧と、テストのプログラムの一覧が一致することも確かめる。`specialization_matches_hand_written_work` は、自動の版と `_by_hand` の版の6つの組で、`allocations`、`boxes`、`unboxes` が同じことを確かめる (S13e-1 の完了の条件。下の「S13e-1」。6つ目の `state_loop` の組は S14c-2 の完了の条件で、下の「S14c-2」)。`handler_specialization_removes_yields_and_evidence` は、`iter_generate` と `iter_pipeline` の `yields` と、`push_fold` と `fold_state` の `evidence_steps` が0であることを確かめる (S13e-2 の完了の条件。下の「S13e-2」)。`state_loop` と `state_nested` の `evidence_steps` が0であることも確かめる (S14c-2 の完了の条件)。`specialization_matches_hand_written_rc` は6つの組で RC の回数が同じことを、`iter_allocations_do_not_grow_with_the_input` と `iter_generate_allocates_as_much_as_the_direct_loop` は `Iter` で引く形の確保の数を確かめる (S13e-3 の完了の条件。下の「S13e-3」)。`rebuilding_programs_reuse_boxes` は、関数の中で手放して作り直す8つのプログラムで `reuses` が 0 より大きいことを確かめる (S13e-4 の完了の条件。下の「S13e-4」)。`var_matches_hand_written_work` は、`var` で書いた版と手書きの版の2つの組で、`var` の版の `evidence_steps` と `yields` が0であることと、確保の数の差が表 `RESIDUAL` の値に等しいことを確かめる (S14c-3 の完了の条件。下の「S14c-3」)。回数は機械の速さに左右されないので、ふだんの `cargo test` で流す。

段の前後の回数は、このスナップショットの差分で残る。回数を変える変更は、その段の spec に期待値の変更として書く ([テスト戦略](testing.md) の「テストの変更の運用」)。S10a までの記録の回数は S10b で消したインタプリタのもので、`rc_increments`、`rc_decrements`、`peak_objects` は VM と数え方が違う (下の「S10a (VM)」)。`peak_stack` は S10b で足した欄で、それより前の記録にはない。

## 命令の数の測り方

```sh
bench/run.sh
```

`bench/run.sh` は、release ビルドの `eml run` (VM の速いモード) で各プログラムを3回ずつ走らせ、`instructions retired` と実時間の中央値と、実行の分を Markdown の表で出す。実行の分は、各プログラムの命令の数から `empty` の命令の数を引いた値である。`empty` はフロントエンド、コード生成、起動の費用なので、段の前後は実行の分で比べる。実行の分が 0 以下になったときは、理由を出して止まる。比べられる値でないものを記録しないためである。表の前に、測定の環境 (機種と CPU、macOS の版、`rustc -V`、コミット) を出す。コミットしていない変更があれば、コミットの後に `-dirty` が付く。プログラムが実行時エラーで止まったときと、`time -l` の出力から命令の数か実時間を読めなかったときは、その出力を見せて止まる。macOS でだけ動く。

valgrind が arm64 の macOS で動かないので、callgrind は使わない。`instructions retired` は callgrind ほど決定的ではないが、S4a の設計のときに release ビルドの `fib 30` を3回測った揺れは約0.1%だった。arm64 の命令の数なので、過去の調査で x86_64 の callgrind を使って測った値とは直接比べない。

`empty.em` の命令の数は、フロントエンド、コード生成、起動の分である。ほかのプログラムの値からこれを引くと、実行の分の目安になる。実時間は 0.01 秒単位なので、命令の数を主に見る。

段の終わりに `bench/run.sh` を流し、出力の環境と表を、下の「記録」に段の見出しを付けて足す。

`bench/rt.sh` は、`eml_rt` の速いモードを測る ([オブジェクトモデル](../spec/object-model.md))。`crates/eml_rt/examples/rt_bench.rs` を release ビルドにし、次の14の計測を `bench/run.sh` と同じ方法で3回ずつ走らせて、同じ形の表を出す。`bench/` のプログラムでなく、ヒープの操作を直接呼ぶ。

| `list` | 1,000,000 個の cons セルのリストを作って捨てることを、10回繰り返す |

## スクリプトの計測

S12d の5本のスクリプト (`tests/ui/run/scripts/`) のうち、入力の大きさが効く4本を、実際の大きさの入力で Python と比べる。目標は、数十 MB のログを数秒以内に処理することである。`bench/` の基準のプログラムと違い、命令の数でなく実時間と最大の常駐メモリを見る。比べる相手の Python の実行が、命令の数で比べられる形でないためである。

```sh
bench/scripts.sh
```

- 入力は `bench/scripts/gen.py` が種を固定して生成する、約 30 MB のアクセスログ (`access.log`) と CSV (`data.csv`) で、`target/bench-scripts/` に置く。すでにあれば作り直さない
- 比べる Python の版は `bench/scripts/<名前>.py` で、Python の標準ライブラリで普通に書いたものである。速さのために手で凝ったものにはしない
- 各計測の前に `bench/scripts/compare.sh` で、eml と Python の標準出力と終了コード (と書き出したファイル) が一致することを確かめる。一致しなければ止まる
- release ビルドの `eml run` (VM の速いモード) と `python3 -I` を3回ずつ走らせ、`/usr/bin/time -l` の実時間と最大の常駐メモリの中央値を出す。`bench/run.sh` と同じく macOS でだけ動く
- 計測は `wc` (ログを標準入力から)、`grep -n` (約 0.5% の行が一致するパターン)、`logstat` (1行ずつ読む)、`logstat --whole` (全体を読んでから分ける)、`csv2jsonl` (3つの列を選ぶ) の5つである

`bench/scripts/compare.sh` は、UI テストの付属のファイルで出力を確かめるとき (`compare.sh --fixture <名前>`) にも使う ([テスト戦略](testing.md) の「分類」)。

| プログラム | 項目 | CEK | VM |
|---|---|---:|---:|

差の理由は、[VM](../spec/vm.md) の「`RunStats`」に挙げた次の4つである。

1. CEK はヒープの物体にしたフレームを数える。VM のフレームはスタックにあるので数えない
2. CEK は文字列のリテラルの参照と物体を数える。VM のリテラルは凍結した領域にあるので数えない
3. `eml_rt` の `peak_live` は、ヒープごとのダミーの物体を1つ含む
4. `eml_rt` の `release` と `free_block` は、持ち主を空けるときに `rc_decrements` を1つ足す。CEK は解放そのものを数えない

項目ごとの差は、次のように説明できる。

- `peak_objects`: CEK の値はフレームとリテラルの物体の分 (1と2) だけ大きく、VM の値はダミーの分 (3) だけ大きい。再帰の深さの分だけフレームが同時に生きるので、`fib` の差の大部分はフレームの分である
- `tree` の `rc_increments`: 出力の `" "` のリテラルの参照である (2)。CEK は `acquire_immortal` を1回数え、VM は凍結した領域の物体を数えない
- `tree` の `rc_decrements`: 等しいのは、2つの差が打ち消し合った結果である。リテラルを除いて `size` と `fold` の結果だけを出す形に `main` を書き換えると、CEK が 266463、VM が 266464 になった。CEK はリテラルの `decref` を1回多く数え (2)、VM はリテラルのない形でも1回多く数える。VM の1回は4つ目の理由の分と見ているが、どの文で起きるかは確かめていない

性能の調整は、基準を最初の計測で満たしたので、入れなかった。決めたことは次のとおりである。

- `#[inline]`: `RUSTFLAGS="-C remark=inline"` の release ビルドで、`eml_vm` の関数に `eml_rt` の関数が「definition is unavailable」で展開されなかった所を集めた。出てきた20の関数は、どれも実行の繰り返しの外か冷えた道にある。panic で止める関数 (`too_large`、`not_an_immediate`、`not_a_descendant`、`too_many_acquires`)、Host の入出力 (`host_write_line`、`host_flush`、`host_open`、`read_text`、`StdHost::new`、`StdHost::stdio`)、`Fault` と `Stop` の表示、検査モードの走査 (`leaks`、`check_invariants`、`Pages::blocks`)、終わりの解放 (`Pages`、`HostRef`、`Arc<Control>` の `Drop`)、`Vec` の伸長、`String.show` のエスケープを探す `next_escape` である。`bench/` のプログラムの繰り返しで呼ぶ関数はないので、`eml_rt` は変えていない。そのため `bench/rt.sh` は流していない
- ブロック引数の合併: 入れていない。ブロック引数と実引数に同じ色を付けやすくして移動の命令を減らす工夫だが、基準は合併なしで満たしたためである ([VM](../spec/vm.md) の「スロットの割り当て」)
- 比較と分岐を1つにした命令: 入れていない。基準は大きな余裕で満たしており、命令を足すと、`Op` の種類、コード生成の形の照合、逆アセンブラ、テストが増えるためである。判断の基準 (簡潔な実装が先で、性能はその次) に従った
- `codegen-units`: `[profile.release]` に足さず、既定の値のままにした。`codegen-units = 1` を `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1` で測ると、VM の実行の分は `state` で 14.2%、`tree` で 6.1%、`list` で 4.6%、`loop` で 1.1% 減り、`fib` で 2.5% 増えた。CEK の実行の分も 3.7〜7.8% 減った。基準は既定の値で満たしており、結果がプログラムによって違ううえ、CEK の記録との比べ方も変わるためである

### S13 の前の試作

S13 の項目と順は、ここに書く S12d のスクリプトの書き心地と、その後の議論と試作から決めた。S13 を終えたときに、[ロードマップ](../future/roadmap.md) から移した。

S12d では、5本のスクリプト (`tests/ui/run/scripts/` の `wc`、`grep`、`logstat`、`csv2jsonl`、`deploy`) を書き、4本を Python と比べて測った。表は上の「S12d (スクリプト)」にある。その後、議論の中で使い捨ての試作を書いて測った (2026-10-17、Apple M4、Python 3.14.7)。

- VM は、素のループでは CPython より速い。3,000万回のループは VM が0.26秒で Python が0.66秒、`fib 32` は VM が0.09秒で Python が0.15秒だった。`wc` を1バイトずつのループで書くと、VM が1.56秒で Python が1.45秒になり、ほぼ同じである。`wc` の20倍の差は、Python の版が C で書かれた `bytes.count` と `bytes.split` に任せている分である
- `wc` の内側のループを、LIR をそのまま写した Rust (`opt-level=1`) で書くと、1バイトごとの `dup`、`String.byte_at` の呼び出しと `decref`、`is_space` の呼び出しを残しても、読み込みを含めて約0.10秒 (Python の約1.2倍) だった。借用とインライン化を足すと約0.035秒 (約0.45倍) になる。ネイティブ化で1.5倍以内に届く見込みはあるが、Cranelift のコードは LLVM より遅いことがある。確保の多い `logstat` (Python は C のハッシュ表、eml は永続的な木) は測っていない
- 60万行のうち `GET` を含む行を数える処理は、直接のループが0.17秒、push の形 (handler で回す形) が0.32秒、引いて使う形 (`multi` の `yield` で作った試作) が0.38秒、Python が0.06秒だった
- push の形では、`take`、`keep`、`enumerate` を「`Yield` を受けて `Yield` を出す関数」として書くと E2008 になった。そのため、変換をループの本体に手で書くことになり、「1行目をヘッダにする」「条件に合う最初の3行に番号を付ける」のような処理は、引いて使う形のほうが Python に近く読めた
- 純粋なコールバックを渡した総称な `fold` は、`<IO>` の中で呼ぶと1要素ごとに yield した。コールバックを取らない専用の handler では yield しなかった
- 線形な値の受け渡しの負担は小さかった。`File` を開いて読み切って閉じるだけなら、`let (f, text) = Fs.read_all f` の再束縛を含めても負担はほぼない。ただし、今の std には `File` を持ったまま1行ずつ読む関数がないので、`File` が解析や中断の区間をまたぐ形は確かめていない
- エフェクトでの状態とストリームは簡潔に書けた。行を `yield` する生産者と状態付きの handler の消費者を分けられ、handler を値として差し替えられ、`use` を重ねると段の列が上から読める。`try_io` で全体を包むと、`Err` の中断がパラメータ付き handler の状態も捨てるので、中断と handler の状態の関係は書くときに意識する必要がある
- S13d に入る前に、1,000要素のプログラムで `RunStats` の yield を数え、release ビルドで実時間と命令数を測った (2026-10-18)。`Yield (List a)` を `Yield (List b)` に変える handler の節で `List.map` を呼ぶ形は、`map` を外しても1要素ごとに1回 yield した。節が外側の `yield` を起こすためである。`map` が yield しうる instance になるのは、渡す関数の row が開いているとき (ラムダやトップレベルの関数の参照) だけだった。そのときも実行時の yield は増えず、300万要素の `map` で命令数が約4%増えた。純粋なラムダを渡した `Yield.fold` は、`<IO>` の中では yield しないが、`State.run` の中では1要素ごとに yield し、100万要素で0.09秒が0.28秒 (命令数は約3.7倍) になった
- 型の誤りで手が止まったのは `deriving (Eq)` の書き忘れ (E2006) だけで、5本ともほぼ初回で型検査を通った。処理系の不具合は見つからなかった

もう1回流すと、eml の実時間は順に 1.64、0.39、2.05、2.04、3.84 秒だった。書き換えていない `wc` も 1.60 と 1.64 の間で揺れたので、約 0.04 秒 (2〜3%) までの差は揺れの範囲とみる。上の「S12d (スクリプト)」の値と比べると、行ごとの理由は次のとおりである。最大 RSS は、2回目の `logstat` の 9 MB のほかは変わっていない。

- `wc`: スクリプトを変えていない。1.61 秒から 1.60 秒で、揺れの範囲である

4 倍では `std_iter_lin.em` の `main` の余裕が 13 文しかないので、8 倍にした。8 倍では、どのプログラムも予算に届かず、`RunStats` も Core IR も予算を置く前と同じである。

#### ABI を名前で決めた費用

S13e-3 で、関数の ABI を使い方でなく名前で決めるようにした ([LIR](../spec/lir.md) の「一様な関数」)。値として生まれる内部の関数はいつも一様で、直接呼ぶ所が引数を `box` し結果を `unbox` する。名前で追記する REPL で、名前が同じ関数の ABI がプログラムによって変わらないようにするためである。費用は次の所に出る。

- 展開されない内部の関数への直接の呼び出しは、呼び出しごとにスカラーを `box` と `unbox` で受け渡す。ループになったラムダの複製、EP の継続の関数 `f$kN` の速い道からの呼び出し、`never` の操作の節の呼び出しがこれに当たる
- 値として使うローカル関数は、`f$boxed` を通る。値として呼ぶたびに呼び出しが1つ増える
- 型から呼び出しの規約を決める形 (閉包の ABI を矢印の型から決め、変換の包みを一様な `_:poly` の境目だけに置く) は、ロードマップの「Float、Char、Num」に後の項目として書いた

#### 完了の条件

`var_matches_hand_written_work` が、2つの組で次のことを確かめる。

- `var` の版の `evidence_steps` と `yields` が 0 である。どの `var` の handle も状態を渡す形に特殊化され、最適化した Core IR に `handle` と `perform` が残らない
- `var` の版の確保の数から手書きの版の確保の数を引いた値が、表 `RESIDUAL` の値に等しい。値は、ふるいが 2262、fannkuch-redux が 38669 である

差はどれも、経路の関数の末尾でない呼び出しから2つ以上の値が戻る所のタプルである (S14c の設計の「速さの見込みと残る差」)。S14e で構造体の表現が入れば消える。どちらのプログラムも `Float` の状態を持たないので、`Float` の箱の確保はない。タプルのフィールドは一様な位置なので、`Int` の状態は `box` と `unbox` を通る。`Int` は即値なので、これは確保にならない。2つの版に共通する確保 (配列、結果を書く文字列、`empty` も作る1つ) は、ふるいで3回、fannkuch-redux で9回である。

#### 差の内訳
