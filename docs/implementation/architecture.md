# コンパイラの構成

位置づけ: 手引き。

eml の処理系をどの crate に分け、各段階がどんな規律に従うかを説明する。言語の意味は [spec/](../spec/) の各文書が定める。この文書は、それを実装する側の構造と、構造を選んだ理由を扱う。型や関数の細部はコードとそのコメントにある。

## 全体の方針

- 処理系はバッチ型のパイプラインである。各段階を純粋な関数とし、Arena と ID で表現して、後でクエリ化 (salsa など) できるようにしておく
- 実行系は、2つの層の IR と、レジスタ型のバイトコードの VM からなる。型付き Core IR (前向きの辺だけを持つ基本ブロックの列で、中間値に名前を付け、エフェクトを明示する) は意味の層で、EP の後に LIR (エフェクトの命令を持たず、box、RC、末尾呼び出しを明示する) に写す。VM は reuse の後の LIR をバイトコードに変換して実行し、後のネイティブ化も同じ LIR を入力にする。ネイティブのバックエンドは未実装で、Cranelift で JIT と AOT のコードを出す設計である ([ネイティブ化の設計](../future/native.md))。物体の形、ヒープ、RC は、VM とネイティブで共有するランタイム `eml_rt` に置く
- 構文木には rowan (Red-Green Tree) を使い、その上にリッチな診断と LSP を整える

## プログラム全体の構成

- 処理系は、item を単位にしたプログラム全体のパイプラインである。rust-analyzer の item tree と DefMap の分け方を、eml の規模に合わせた。名前解決は、`ItemTree` (ファイルごとの宣言の要約)、`DefMap` (モジュールごとのスコープ表)、item ごとの変換の3段で、item の ID (`ItemId`) はプログラム全体で一意である。型検査は宣言、本体、SCC の粒度で動き、モジュールの境目を使わない
- モジュールごとに検査して、依存先のモジュールのインタフェースを借りる方式は採らない。次の3つの負担が生じるためである
  - 相互再帰がモジュールをまたぐと SCC もまたぐので、import の循環を許せなくなる
  - 型検査が、自分のモジュールの表と依存先の表の2系統を引くことになる
  - モジュールのインタフェースとしての型検査の出力を、別に設計する必要がある
- item を単位にすれば、import の循環を許すかどうかは `DefMap` の作り方だけの問題になる

採らなかった形は次のとおり。

- salsa を今入れること。段階をクエリの形にしてあるので、後で載せ替えられる。LSP を作るまでは手間が大きい
- モジュールごとに Core IR を作ってリンクすること。VM では得るものがない
- HIR の位置を今 source map に移すこと。利点が出るのはクエリ化した後である ([ロードマップ](../future/roadmap.md))
- プログラム全体の item を1つのアリーナに置くこと。モジュールの変換が共有のアリーナを書き換えるので、段階が純粋な関数でなくなる
- どの item も Core IR の関数にして、書き換えのパスで命令に戻し、使わない関数を取り除くパスで消すこと。変換が満ちた呼び出しをすでに命令にしているので、飽和の場合分けを `saturate` にまとめれば足りる
- `Bool` のタグを VM まで運ぶこと。タグは Prelude の宣言の順で決まるので、定数 `FALSE` と `TRUE` をテストで照らし合わせれば足りる

## リポジトリ

```
eml/
  Cargo.toml            # [workspace] members = ["crates/*"], resolver = "3"
  Cargo.lock
  CLAUDE.md             # 作業の決まりと docs/ への案内
  crates/
    eml_diagnostics/
    eml_extern/         # 依存を持たない extern の表
    eml_syntax/
    eml_hir/
    eml_types/
    eml_core_ir/
    eml_lir/            # LIR とそのパス。workspace の crate では eml_extern だけに依存する
    eml_cabi/           # C の関数を呼ぶコードのポインタ。eml_extern だけに依存する
    eml_clink/          # Cの関数をつなぐ (Craneliftの橋渡しの関数、Cの関数のシグネチャ`c_signature`、Cのライブラリと記号の解決)。workspaceのcrateではeml_cabi、eml_externだけに依存し、eml_native、eml_vm、eml_nrtには依存しない
    eml_native/         # ネイティブのコード生成器の土台。workspaceのcrateではeml_extern、eml_cabi、eml_clink、eml_lir、eml_nrt、eml_rtに依存し、eml_vmには依存しない
    eml_nrt/            # ネイティブのコードが呼ぶエントリ、エントリのstub、実行の駆動。workspaceのcrateではeml_extern、eml_rows、eml_rt、eml_schedに依存し、Cranelift、eml_lir、eml_vm、eml_nativeには依存しない
    eml_rows/           # 組み込みの関数が実行時に何であるかを、VMとネイティブのコードのどちらにも与える層 (externの行の一覧と本体、組み込みが持つ値を作る関数、利用者のCの関数の呼び出しの部品、`Std.Tls`と`Std.Gui`の腕)。workspaceのcrateではeml_cabi、eml_extern、eml_rt、eml_schedだけに依存し、feature `tls`の下ではeml_tlsに、feature `gui`の下ではeml_guiにも依存する。Cranelift、eml_lir、eml_vm、eml_nrt、eml_nativeには依存しない
    eml_rt/             # VM とネイティブで共有するランタイムの核。vstd だけに依存し、Verus で検証する
    eml_io/             # I/Oのdriver (本物のdriverとテストのdriver。本物のdriverはOSを呼ばない核とOSごとのbackendからなり、ブロックする呼び出しの仕事はdriverの中の自前のプールで動き、スレッドは32本まで) と、`eml run`とREPLのHostを作る関数。workspaceのcrateではeml_rtだけに依存し、feature `tls`の下ではeml_tlsにも依存する
    eml_tls/            # rustlsのクライアント接続を包むTLSの状態 (I/Oを持たない)。証明書はOSの検証器で確かめる。workspaceのcrateには依存しない
    eml_gui/            # ネイティブのGUIのtoolkitの共通の層と、画面を開かないstubのbackend。workspaceのcrateには依存しない
    eml_sched/          # 実行の方式によらない層 (タスクのセルの核、実行のインタフェース、時計、doorbell、Park、実行の設定と結果の型)。workspaceのcrateではeml_io、eml_rtだけに依存し、Cranelift、eml_lir、eml_vm、eml_nrt、eml_nativeには依存しない
    eml_vm/             # LIRのレジスタ型のバイトコードVM。workspaceのcrateではeml_lir、eml_io、eml_rows、eml_rt、eml_sched、eml_cabi、eml_externだけに依存する
    eml_cli/            # lib + バイナリ (バイナリ名 `eml`)
    eml_test_support/   # 開発専用。結合テストのパイプラインと診断の文字列
  std/                  # 標準ライブラリ (Prelude.em、Fs.em、List.em など)。eml_hir がバイナリに埋め込む
  tests/ui/             # UI テストのコーパス
    run/
    run-fail/
    check-fail/
  bench/                # 基準のプログラムと測るスクリプト ([ベンチマーク](benchmarks.md))
  docs/
  flake.nix
  nix/verus.nix         # Verus の release の zip を展開する
  nix/verusfmt.nix      # verusfmt の release の archive を展開する
```

- `version`、`edition = "2024"`、依存する crate のバージョンは、workspace のルートの `Cargo.toml` でまとめて管理する
- `flake.nix` は、workspace のルートの `Cargo.lock` を使って `eml_cli` だけを組み立て、`eml` バイナリを作る
- nixpkgs は nixos-unstable を追う。Rust の toolchain は、stable も nightly も flake が fenix から取る。stable のバージョンは `rust-toolchain.toml` に書く。flake がその `channel` を読み、nix の外では rustup が同じファイルを読む。devShell の cargo は rustup を通らないので、shell の中ではファイルは効かない。ふだんの devShell、`nix build`、Verus と、ほかの target を検査する devShell (`nix develop .#cross`) が同じバージョンを使う。nightly は Miri の devShell (`nix develop .#miri`) だけにあり、Miri、AddressSanitizer、ThreadSanitizer が使う ([テスト戦略](testing.md) の「Miri」、「AddressSanitizer」、「ThreadSanitizer」)
- Verus と verusfmt は、release の archive を flake の input にし、`nix/verus.nix` と `nix/verusfmt.nix` が展開してふだんの devShell に入れる ([テスト戦略](testing.md) の「Verus」)。flake の対象は x86_64-linux、aarch64-linux、aarch64-darwin で、Verus の release に archive のない aarch64-linux では、Verus と verusfmt を devShell にも packages にも入れない
- `eml_rt` は vstd に依存するので、`Cargo.lock` に vstd とその依存が入る。`eml_cli` は `eml_vm` を通して `eml_rt` に依存するので、vstd は `eml` バイナリにも入る。`eml_rt` の `verus!` の中は verusfmt で、外は `cargo fmt` で整える
- どの devShell の shellHook も、`CARGO_HOME` を `${XDG_CACHE_HOME:-$HOME/.cache}/eml-cargo-home` にする。cargo は外部のサブコマンドを PATH より先に `$CARGO_HOME/bin` から探すので、rustup が入っていると `~/.cargo/bin` の `cargo-clippy` や `cargo-miri` (rustup のプロキシ) が fenix のものより先に当たるためである。そのため、devShell は crate の取得の置き場所を別に持ち、最初の1回は crate を取り直す

## crate の依存関係

依存は上から下への一方向だけにする。

```
eml_cli          check / run コマンド。パイプラインを組む唯一の場所 (Session)。テストから呼べる lib API を公開する
eml_vm           LIR → レジスタ型のバイトコード (CodeBase)。eml_rt の Ctx の上で、worker のスレッドごとに1つの Ctx で実行する
eml_sched        実行の方式によらない層。VMとネイティブの実行系が共有する、タスクのセルの核 (cells.rs)、実行のインタフェース (error.rsの実行時エラーの型など)、時計の選び方 (driver.rs)、自己パイプ (doorbell.rs)、メインのworkerの`Park` (park.rs)、実行の設定と結果の型 (config.rsのRunConfig、Finished、RunStats、Sched、Seat)。eml_io、eml_rtだけに依存し、Cranelift、eml_lir、eml_vm、eml_nrt、eml_nativeには依存しない
eml_rows         組み込みの関数が実行時に何であるかを、VMとネイティブの実行系のどちらにも与える層。externの行の一覧 (rows.rsのマクロ`extern_rows!`と、行の関数、表`SHARED`、関数`call`) と、組み込みが持つ値 (定数の箱と空の`MutArray`) を作る関数 (constants.rs) と、どちらのエンジンも使う利用者のCの関数の呼び出しの部品 (ハンドルの中身`CHandle`、`Panic`の理由`Raise`、`handle_new`。ffi.rs) と、`Std.Tls`の腕 (tls.rs) と、`Std.Gui`の腕とGUIの`Park` (gui.rs。スケジューラにはtrait `GateHost`を通して触れる)。eml_cabi、eml_extern、eml_rt、eml_schedだけに依存し、feature `tls`の下ではeml_tlsに、feature `gui`の下ではeml_guiにも依存する。Cranelift、eml_lir、eml_vm、eml_nrt、eml_nativeには依存しない
eml_io           eml_rtのIoDriverの実装 (本物のdriverとテストのdriver。本物のdriverはOSを呼ばない核とOSごとのbackendからなり、ブロックする呼び出しの仕事はdriverの中の自前のプールで動き、スレッドは32本まで)。時計とI/Oの待ちを受け持ち、`eml run`とREPLのHostを作る`stdio_host`と`script_host`も持つ
eml_tls          rustlsのクライアント接続を包むTLSの状態 (I/Oを持たない)。aws-lc-rsのproviderとrustls-platform-verifierを使い、emlのどのcrateにも依存しない
eml_gui          ネイティブのGUIのtoolkitの共通の層 (Widgets、EventLoop、Toolkit、EventQueue)、画面を開かないstubのbackend、feature nativeの下のAppKit (macOS)、Qt 6 (Linux)、WinUI 3 (Windows) のbackend。emlのどのcrateにも依存しない
eml_clink        Cの関数をつなぐ。Craneliftの橋渡しの関数と、Cの関数のシグネチャ`c_signature`と、Cのライブラリと記号の解決 (Linker::linkがLinkedを作る)。eml_cabi、eml_externだけに依存し、eml_native、eml_vm、eml_nrtには依存しない
eml_native       ネイティブのコード生成器の土台 (emlのコード、adapter、補助の関数、thunkのCraneliftのフラグを作る唯一の関数abi::isa、シグネチャ、thunk)。eml_extern、eml_cabi、eml_clink、eml_lir、eml_nrt、eml_rt (レイアウトの定数だけ) に依存し、eml_vmには依存しない
eml_nrt          ネイティブのコードが呼ぶエントリ (記述子の表、plainとshimの包み、利用者のCの関数の呼び出しの補助)、エントリのstub (eml_enter、eml_fatal)、実行の駆動 (Image、workerの構造体、run、census)。eml_extern、eml_rows、eml_rt、eml_schedに依存し、Cranelift、eml_lir、eml_core_ir、eml_vm、eml_nativeには依存しない
eml_cabi         C の関数を呼ぶコードのポインタ (Bridge、Dtor、CCall、Linked)。eml_extern だけに依存する
eml_rt           VM とネイティブで共有するランタイムの核 (語、物体、確保器、RC、検査モード、Ctx、extern)。vstd だけに依存する
eml_core_ir      型付き HIR → Core IR (基本ブロックの列)。最適化と evidence passing のパスと、LIR への変換
eml_lir          LIR (box、RC、末尾呼び出しを明示する基本ブロックの列)。box/unbox の挿入、構造体を葉に開くパス、縮約、dup/decref/release の挿入、reuse のパス
eml_types        Kind・型・row の推論、線形性・多重度の検査、match の網羅性検査
eml_hir          モジュールの読み込み、CST → HIR の変換、名前解決、脱糖
eml_syntax       SyntaxKind、lexer、レイアウト段、イベント方式のパーサ、rowan、型付き AST ラッパ
eml_diagnostics  Diagnostic 型、FileId と SourceFiles、行と列、ariadne による表示
eml_extern       extern の表 (型、エフェクト、関数)。依存を持たず、HIR、型検査、Core IR、LIR、VM が引く
```

- 段階の連なりに`eml_rt`は入らず、`eml_vm`、`eml_sched`、`eml_rows`、`eml_io`、`eml_nrt`、`eml_native`と、開発専用の`eml_test_support`だけが依存する。`eml_rt`はworkspaceのほかのcrateに依存しない
- `eml_io`はworkspaceのcrateでは`eml_rt`と、feature `tls`の下の`eml_tls`だけに依存し、`eml_vm`には依存しない。依存の順は`eml_cli` > `eml_vm` > `eml_sched` > `eml_io` > `eml_rt`で (`eml_vm`は`eml_io`にも直に依存する)、feature `tls`の下では`eml_io` > `eml_tls`と`eml_rows` > `eml_tls`が加わる。`eml_rows`のfeature `tls`は`eml_io`のfeature `tls`を有効にしない。`tls.localhost`の終端器はテストのdriverの道具で、有効にするのはツールの`eml_cli`だけである。trait `IoDriver`とdriverに渡す型は`eml_rt`が持ち、`eml_io`はその実装だけを持つ ([VM](../spec/vm.md)の「時計と driver」)
- `eml_tls`はworkspaceのどのcrateにも依存しない。`eml_rows`と`eml_io`が依存するのはfeature `tls`の下だけである。`eml_cli`のfeature `tls`も`eml_tls`を省ける普通の依存として足す。`eml_cli`の`src/`はこれを使わず、本物のソケットの上でTLSのサーバーを立てる結合テスト (`tests/tls.rs`) が使う。rustlsはaws-lc-rsのproviderだけで使い、サーバーの証明書はrustls-platform-verifierを通してOSの検証器で確かめる。aws-lc-sysが要るのはCのツールチェーンだけで、Windowsのx86_64ではNASMを使い、NASMがなければ組み済みのオブジェクトを使う。Cのツールチェーンを持たない`.#cross`のclippyが`eml_tls`を除くのはこのためである
- `eml_gui`はworkspaceのどのcrateにも依存せず、`Park`、`Pending`、`Ctx`、`eml_io`の型を名指さない。`eml_rows`がfeature `gui` (`eml_cli`の既定)で`eml_gui`に依存し、`gui.rs`が`Std.Gui`の腕とメインのworkerのGUIの`Park`を持つ (docs/spec/vm.mdの「GUIのPark」)。ネイティブのループが待つOSの源は、VMの`PollSource`と同じ形の`IoSource`を`eml_gui`が自分で持つ。CIのtestのjobの手順`dependency edges of eml_gui`が、`eml_gui`の依存に`eml_`で始まるcrateがないことを確かめる。ネイティブのbackendはfeature `gui-native`だけが足す。`eml_cli`の`gui-native` (既定に入れない) が`eml_rows`の`gui-native`を、それが`eml_gui`の`native`を有効にし、`native`だけが`objc2`の系統のcrate (macOSだけ)、`cxx`、`cxx-build`、`qt-build-utils`、生成したWinUIのbindingが使う`windows-core`の0.100の系統のcrate (Windowsだけ) を引く。既定のビルドはtoolkitの開発用のファイルを要らず、同じ手順が、`eml_cli`の既定の依存の木にnativeのtoolkitのcrateがないことと、`gui-native`の木に3つのtoolkitのcrate (Qtの`cxx`と`qt-build-utils`、AppKitの`objc2`、WinUIでは生成したbindingだけが使う`windows-collections`) がどれも入ることを確かめる
- aws-lc-sys は、target の C のツールチェーンだけで組めることを前提にする。対応する OS か `nix build` で、組めない、リンクできない、動かないときは、OS ごとのツールや環境変数を足さず、provider を ring に替える。ring でも同じことが起きたら、設計から決め直す
- `eml_lir`は、workspaceのcrateでは`eml_extern`だけに依存する葉のcrateである。`eml_core_ir` (LIRへの変換とパスの順番のため)、`eml_vm`、`eml_native`、`eml_cli`が依存する。`eml_vm`が読むIRは`eml_lir`だけなので、フロントエンドなしにビルドできる。2つのIRが共有する型 (`Atom`、`VarInfo`、`Layout`、`Prim`、`EffectInfo`など) と定数、テキスト形式とverifierの共通の部品も`eml_lir`に置き、`eml_core_ir`は再公開しない。使う側は`eml_lir`から読む。`Repr`も`eml_lir`が再公開するものを使う
- `eml_cabi`は、`eml_cabi → eml_extern`の辺だけを持つ葉のcrateである。`Ctx`に関わらないコードのポインタだけを持つ。`eml_vm`、`eml_clink`、`eml_native`、`eml_rows`が依存し、`eml_clink`が作った`Linked`を`eml_vm`の`load`が受け取る。`eml_rows`は`handle_new`のシグネチャの`Dtor`を`ffi::Dtor`として再exportする
- `eml_native`は、workspaceのcrateでは`eml_extern`、`eml_cabi`、`eml_clink`、`eml_lir`、`eml_nrt`、`eml_rt`への辺を持ち、Craneliftの5つのcrateに依存する。libloadingには依存しない。`eml_rt`を名指すのは`mem.rs`だけで、使うのはレイアウトの定数だけである。`eml_vm`はCranelift、`eml_native`、`eml_nrt`のどれにも依存しない。`eml_native`に依存するのは、`eml_cli`と`eml_test_support`のfeature `run`だけである。別のcargoのfeatureは作らない。C の関数をつなぐ道は`eml_clink`が持ち、`eml_native`に例外のない置き場所の規則 (下の「`eml_native` の内部」) を保つ。`eml_native`が`eml_clink`から使うのは、Cの関数のシグネチャを作る`c_signature`だけである。`nix/crate-graph.sh --check` (CIのtestのjobの手順`crate graph`) が、`eml_native`が`eml_vm`に依存しないこと、`eml_lir`が`eml_rt`に依存しないこと、`eml_extern`の`src/`に`unsafe`がないことを確かめる。`eml_native`の`[dependencies]`は`eml_sched`、`eml_rows`、`eml_io`、`eml_vm`の名前を持たず、`src/`も`eml_sched`と`eml_rows`を名指さない (`tests/placement.rs`)
- `eml_clink`は、Cの関数をつなぐcrateである。workspaceのcrateでは`eml_cabi`と`eml_extern`だけに依存し、Craneliftの5つのcrateとlibloadingに依存する。`eml_native`、`eml_vm`、`eml_nrt`には依存しない。コード生成器と共有するのはシグネチャを作る`c_signature`だけで、Craneliftのフラグは自分で作るので、`eml_native`の置き場所の規則に例外を置かずに済む。`eml_cabi`の`Bridge`、`Dtor`、`CCall`、`Linked`を作る。`eml_clink`に依存するのは、`eml_native`と`eml_cli`と`eml_test_support`のfeature `run`だけである。別のcargoのfeatureは作らない。
- `eml_nrt`は、workspaceのcrateでは`eml_extern`、`eml_rows`、`eml_rt`、`eml_sched`に依存し、Cranelift、`eml_lir`、`eml_core_ir`、`eml_vm`、`eml_native`に依存しない。ネイティブの実行系とエントリのstubは、コンパイラなしで組めなければならないためである (AOTのバイナリは実行系をリンクするが、コード生成器は要らない)。`eml_vm`は`eml_nrt`に依存しない。同じ手順が、`eml_vm`の依存にCranelift、`eml_native`、`eml_nrt`がないことと、`eml_nrt`の依存にコンパイラ、エンジン、ツールのcrate (Cranelift、`eml_lir`、`eml_core_ir`、`eml_vm`、`eml_native`など) とCのツールチェーンを要するcrateがないことを確かめる
- `eml_sched`は実行の方式によらない層で、VMとネイティブの実行系が共有するもの、つまりタスクのセルの核 (`cells.rs`)、実行のインタフェース、時計の選び方 (`driver.rs`)、自己パイプ (`doorbell.rs`)、メインのworkerの`Park` (`park.rs`)、実行の設定と結果の型 (`config.rs`) を持つ。workspaceのcrateでは`eml_io`、`eml_rt`だけに依存し (unixでは`libc`にも)、Cranelift、`eml_lir`、`eml_vm`、`eml_nrt`、`eml_native`のどれにも依存しない。ネイティブの実行系がVMとコンパイラなしにこれを使えるようにするためである。`eml_vm`は`eml_sched`に依存し、その`cells`、`doorbell`、`driver`、`error`、`park`をcrateの中の道として使い、`execute`のシグネチャの型`RuntimeError`、`RunConfig`、`Finished`だけを再公開する。`eml_sched`は`eml_rt`の`Control`、`Limits`、`Stop`、`HostRef`を再公開する。スケジューラとworkerの表はまだ`eml_vm`にある ([マルチコア対応の設計](../future/multicore.md)の「層の構成」)。手順`crate graph`が、`eml_sched`の依存に`eml_extern`、`eml_rows`、`eml_cabi`、`eml_tls`、`eml_gui`、Cranelift、`eml_lir`、`eml_vm`、`eml_nrt`、`eml_native`がないことを確かめる
- `eml_sched`は開発だけのfeature `testing`を持つ。切り替えるのは、`eml_vm`と`eml_rows`の単体テストが使う`cells.rs`のテストの道具 (セルと`Ctx`を作る関数、`Mail`のhook) だけで、それも項目だけを切り替える。`cfg!(feature = "testing")`の式はない。有効にするのは`eml_vm`と`eml_rows`のdev-dependencyだけで、同じ手順が、`eml`のバイナリの依存の木にこのfeatureがないことを確かめる。スケジューラとworkerの表を`eml_sched`へ移すときにこのfeatureを消し、まだ道具の要るテストは公開のAPIの上に書き直す ([テスト戦略](testing.md)の「`eml_sched`のテスト」)
- `eml_rows`は、組み込みの関数が実行時に何であるかを、VMとネイティブの実行系のどちらにも与える層で、externの行の一覧 (`rows.rs`。マクロ`extern_rows!`が、行の関数と、表`SHARED`と、変種で行を流す関数`call`を作る元になる1つの一覧で、行の種類は`eml_extern`の表と等しいことをconstで確かめる) と、組み込みが持つ値を作る関数 (`constants.rs`。定数の箱の表現を1か所で決める) を持つ。一覧は、タスクの行と`Par`、`Exit`、`Panic`を除くどの行の本体も持つ。VMの汎用の`Extern`の命令は`call`を通し、専用の命令は行の関数を直に呼ぶ ([VM](../spec/vm.md)の「基本操作と extern」)。workspaceのcrateでは`eml_extern`、`eml_rt`、`eml_sched`だけに依存し、Cranelift、`eml_lir`、`eml_vm`、`eml_nrt`、`eml_native`のどれにも依存しない。行の本体はexternの表の意味で、タスクの層とは別の理由で変わるので、`eml_sched`には置かない。`eml_vm`と`eml_nrt`が依存する。行の関数と一覧はどのcrateも再公開せず、`eml_native`のテストはdev-dependencyでここから読む。feature `tls`を持つ。有効にすると`eml_tls`に依存し、`Std.Tls`の腕 (`tls.rs`。`Foreign`の中身`TlsConn`と接続の設定) が実体を持つ。外すと、腕は値のない`Conn`の上に同じ名前で組まれ、接続は`NotAvailable`で失敗する。feature `gui`も持つ。有効にすると`eml_gui`に依存し、`Std.Gui`の腕とGUIの`Park` (`gui.rs`) が実体を持つ。外すと、`UiToken`は値を持たず、`want`は`NotAvailable`で失敗する。`gui.rs`は、`eml_vm`の`Scheduler`が実装するtrait `GateHost` (ゲートを開いて放す、workerのdriverを作る、runの外の待ちの印を上げ下げする、workerを起こす) を通してだけスケジューラに触れるので、`eml_rows`はエンジンの型を名指さない
- 成果物でないcrateがfeatureを宣言するのは、自分の`src/`か`tests/`にそのfeatureの`cfg`があるときだけで、中身がほかのcrateのfeatureだけのfeatureを宣言するのは成果物のcrateだけである。`eml_rows`が`tls`、`gui`、`gui-native`を宣言し、`eml_cli`が有効にする。`eml_vm`、`eml_nrt`、`eml_native`、`eml_sched`はどれも持たず、どのcrateもこれらを中継しない。ほかには、`eml_io`が`tls`を、`eml_gui`が`native`を、`eml_sched`が`testing`を宣言する。例外は`eml_test_support`の段階のfeatureだけである
- workspaceのcrateは3つの層に分かれる。実行系の閉包は、配布するネイティブのアプリがリンクするもので、`eml_rt`、`eml_extern`、`eml_io`、`eml_cabi`、`eml_sched`、`eml_rows`、`eml_nrt`と、featureの下の`eml_tls`、`eml_gui`である。コンパイラとエンジンは、フロントエンド、`eml_lir`、`eml_core_ir`、`eml_vm`、`eml_native`と、Cの関数をつなぐ`eml_clink`である。成果物は`eml_cli`で、`eml_test_support`は開発専用である。実行系の閉包からコンパイラやエンジンのcrateへ向かう辺は作らない。`eml_rt`、`eml_extern`、`eml_tls`、`eml_gui`はworkspaceのどのcrateにも依存しない。`eml_native`の`[dependencies]`は`eml_sched`、`eml_rows`、`eml_io`、`eml_vm`を挙げない。`eml_rows`、`eml_sched`、`eml_nrt`、`eml_io`の`src/`にある`#[cfg(test)]`のコードは、エンジンのcrateと`eml_test_support`を名指さない。dev-dependencyの循環で、テスト対象のcrateの2つ目のコピーがリンクされるためで、そのようなテストは`tests/`の結合テストにする
- crateがworkspaceのほかのcrateから再公開するのは、自分の公開のシグネチャに現れる型だけで、関数、module、定数、マクロは再公開しない。例外は`eml_nrt`の隠した名前`__rt`だけで、ほかのcrateで展開した`entries!`がこれを名指す。ほかの項目は、使う側がそれを定義するcrateから名指す。項目の置き場所を変えると、ファサードの裏でなく使う側のimportに表れる。成果物の`eml_cli`と開発専用の`eml_test_support`はこの規則の外にある
- `nix/crate-graph.sh`は、workspaceのcrate間の直接の辺の表、`[features]`の節の表、`eml_cli`と`eml_test_support`の外にあるほかのcrateからの再公開 (`pub use eml_…`) の表を持ち、cargoが解決した結果とソースの行と比べる。`--check`はさらに`cargo tree`の行を数えて、`eml_vm`がコード生成器に届かないこと、`eml_native`が`eml_vm`に届かないこと、`eml_lir`が`eml_rt`に届かないこと、`eml_sched`が自分より上のcrateに届かないこと、`eml_nrt`の実行系の閉包にコンパイラ、エンジン、ツールのcrateがなくCのツールチェーンも要らないこと、featureなし、`eml_rows/tls`、`eml_rows/gui-native`、その両方の閉包にコンパイラ、エンジン、ツールのcrateがなく、featureなしの閉包にTlsとGuiのcrateがなく、`tls`の閉包にGuiの、`gui-native`の閉包にTlsのcrateがないこと、`eml_sched`のfeature `testing`が`eml_cli`の依存の木にないことを確かめ、`eml_extern`の`src/`に`unsafe`がないことと、`eml_vm`が`eml_sched`のmoduleの別名を通して再公開しないことも確かめる。引数なしで流すと、いまの表の文面を書き出すので、スクリプトの表へ貼る。辺、feature、再公開を足したり消したりする変更は、同じコミットで表を直す。CIのtestのjobの手順`crate graph`が`--check`を流す
- `eml_diagnostics`は、診断を出すcrateのすべてから使う。`eml_core_ir`、`eml_lir`、`eml_vm`、`eml_sched`、`eml_rt`が診断を出さず、`eml_extern`は何にも依存しない。`eml_core_ir`だけは、externの呼び出しの位置を行と列にするために`SourceFiles`を使うので依存する。残りの5つは依存しない
- `eml_extern` は表だけを持つ。`eml_hir`、`eml_types`、`eml_core_ir`、`eml_lir`、`eml_vm` が引く。`eml_extern` を一番下に置くのは、どの段階も実装を表の行で引くようにして、名前の文字列で実装を探す処理をなくすためである。表 (`Extern`、`ExternType`、`ExternEffect`) は `table!` が1つの並びから変種、`ALL`、静的な行を作り、`row` は行への参照を返す。VM のコード生成は `self as usize` を行の番号に使い、VM は `ALL` で引き戻すので、並びが1つなら2つの順は食い違わない。C の関数に由来する `ExternRef` (`C`、`CSubmit`、`CTake`) の変種を `match` で照合してよいのは、`eml_extern` の `src/`、`eml_core_ir` の `translate/program.rs`、`eml_lir` の `src/syntax.rs` (IR のテキストの読み書き)、`eml_vm` の `compile/emit.rs` だけである。ほかのコードは `ExternRef::row`、`std`、`from_name` を通して引く。`ExternRef::Std(..)` をその場で分解して `C` の変種を見落とす書き方もしない
- `eml_cli`は`eml_diagnostics`と`eml_hir`に常に依存し、下流の段階をfeatureで足す。`types`は`eml_types`、`core`は`eml_core_ir`と`eml_lir`、`run`は`eml_vm`と、実行のインタフェースの型を持つ`eml_sched`と、本物のHostを作る`eml_io`と、行の本体を持つ`eml_rows`と、Cの関数をつなぐ`eml_clink`と、ネイティブのコードを作る`eml_native`と、端末の行の編集の`rustyline`と、unixではSIGINTのハンドラと物理メモリを読む`libc`を、Windowsではコンソールのhandlerを入れて物理メモリを読む`windows-sys`を足す。`eml_lir`はフロントエンドに依存しないので、段階のfeatureは増やさない。既定は`run`、`tls`、`gui`で、`tls`は`eml_rows/tls`、`eml_io/tls`の順にfeatureを有効にし、`gui`は`eml_rows/gui`を、既定に入れない`gui-native`は`eml_rows/gui-native`を有効にする。バイナリ`eml`は`run`がなければ作らない (`required-features`)。ワークスペースの`eml_cli`の依存は既定のfeatureを外してあり、依存する側が段階を選ぶ
- `eml_test_support`は開発専用のcrateで、パイプラインに入らない。各crateの結合テストがdev-dependencyとして使う。パイプラインは`eml_cli::Session`で組み、段階をfeature (`hir` < `types` < `core` < `run`) で選ぶ。各featureは、`eml_cli`の同じ段階までのfeatureを有効にする。各crateは自分の段階までを有効にする。破壊的な変更の途中で下流のcrateがまだ組み立たなくても、変更している段階のテストを流せるようにするため ([テスト戦略](testing.md))。feature `run`は`eml_sched`にも依存し、`Finished`、`HostRef`、`RunConfig`、`RunStats`、`RuntimeError`をそこから名指す。`eml_rt`にも依存し、書いた行とスレッドを覚えるHost `RecordingHost`を持つ。`eml_vm`と`eml_rows`の結合テストが使う

## 各段階の規律

- 各段階は `fn stage(input: &In) -> (Out, Vec<Diagnostic>)` の形の純粋な関数にする。グローバルな可変状態は持たない。例外は `eml_core_ir` で、診断のエラーがないプログラムだけを受け取り、`Program` を返す (下の「エラーが出ても止まらない」)
- HIR 以降は ID で参照する (`la-arena`)。型などの解析結果は、`ExprId → TypeId` のような別テーブルに置く
- HIR の各ノードは、元の構文の範囲 (`TextRange`) を持つ。演算子の列を組み直した部分式のように、対応する構文ノードのない式があるため
- HIR が持つ位置は、ソースに書かれた名前やノードの位置に限る。行頭や字下げのような、そこから導ける見た目の情報は持たず、要る段階がソースのテキストから求める。E3003 の fix の字下げがその例である (下の「`eml_types` の内部」)
- 型付き HIR は HIR を複製せず、宣言ごとと本体ごとの結果の別テーブルと、それらが指す型の表 (`TypedProgram::types`) だけを持つ。本体ごとの結果には、式、局所変数、パターンの型と、参照ごとの具体化の表 (`instantiations`) と、row が yield しうるかの分類 (`body_yield`、`lambda_yields`、`arrow_yields`、`first_arrow_yield`) がある。そのため `eml_core_ir` は HIR と `TypedProgram` の両方を受け取る

現在の各段階のエントリは次のとおり。

| crate | 関数 |
|---|---|
| `eml_syntax` | `parse(FileId, &str) -> (Parse, Vec<Diagnostic>)` |
| `eml_hir` | `load(&str, &str, &dyn ModuleSource) -> (Loaded, Vec<Diagnostic>)`、`def_map(&Loaded) -> (DefMap, Vec<Diagnostic>)`、`lower(&DefMap, &[LoadedModule]) -> (Program, Vec<Diagnostic>)` の順に呼ぶ。`load` はエントリの表示のパスと本文を受け取り、ファイルごとに `item_tree(FileId, &Parse) -> (ItemTree, Vec<Diagnostic>)` を呼ぶ。モジュールの並びは、0番目が Prelude、1番目がエントリのモジュールで、その後に import をたどって見つけた順のモジュールが続く。標準ライブラリのモジュールとユーザーのモジュールは混ざって並ぶ |
| `eml_types` | `check(&Program, &SourceFiles) -> (TypedProgram, Vec<Diagnostic>)`。`SourceFiles` は E3003 の fix の字下げを求めるのに使う |
| `eml_core_ir` | `lower(Input) -> eml_lir::Program`。`Input` は HIR の `Program`、`TypedProgram`、エントリの `FunctionId`、`SourceFiles` の組で、どのエントリも同じものを受け取る。translate、`optimize`、EP、LIR への変換 (`to_lir`)、LIR のパス (`eml_lir::passes_until`) の順に呼ぶ。LIR のパスの途中で止める `lower_until(Input, eml_lir::Pass)` と、Core IR の段で止める `core_until(Input, Pass) -> Program` もある。エントリの関数は呼ぶ側が渡す。`SourceFiles` は extern の呼び出しの位置を行と列にするのに使う |
| `eml_lir` | `passes_until(&mut Program, Pass)`。変換の直後の LIR に、box の挿入から指定したパスまでをかける |
| `eml_vm` | `execute(&eml_lir::Program, &Linked, &RunConfig, HostRef) -> Result<Finished, RuntimeError>`。`CodeBase::new(Arc<Control>)` の表に `CodeBase::load(&eml_lir::Program, &Linked) -> Result<u32, CompileError>` でバイトコードを足し、`Ctx<M>` の上で実行する |

## エラーが出ても止まらない

- `eml_cli::Session` の段階のメソッド (`def_map`、`lower`、`check`、`compile`) は、エラーがあっても途中で止めずに、その段階までのすべての段階を実行し、診断を集める。1回の実行で、独立した複数のエラーを報告するため
- パーサは壊れた入力でも `ERROR` ノードを作って回復し、必ず `SOURCE_FILE` の木を作ってパニックしない。名前解決と型推論は、誤りの場所に `Error` 型を入れて診断の連鎖を抑える。規則は下の「構文解析の回復」と「名前解決の回復」、[診断](../spec/diagnostics.md) の「連鎖する診断の抑止」にある
- Core IR は、診断のエラーがないプログラムだけを受け取る。`compile` は、エラーがあれば IR を作らない。型付きで正しい入力を前提にできるので、Core IR と LIR への変換は診断を返さない

### 構文解析の回復

- 列 0 の `SEP` (トップレベルの項目の区切り) を、最も強い回復の同期点にする
- ブロックの中では、`SEP` と `CLOSE` を同期点にする
- parser の診断が仮想トークンかファイルの終わりの位置で出る場合は、直前の実トークンの直後の空の範囲を指す。仮想トークンは次の行の先頭にあり、そこを指すと誤りのない行を指してしまうためである。E0009 で回復のために作る空のブロックも、同じ位置に置く
- `match` / `handle` の `with` の後に E0009 を出し、次の行からが `|` で始まる行の並びなら、parser はそれらを枝として読み飛ばし、追加の診断を出さない。E0009 には、枝を `match` / `handle` より深く字下げするよう促す help を付ける
- 行末の `->` で E0009 を出した次の行もまた `->` で終わり、今のブロックが `->` で開いたものなら、その `->` の E0009 は出さない。揃えた複数行のシグネチャ (`f : A ->` の次の行から `B ->`、`C ->` と同じ列に並べたもの) の誤りを1件にするためである。ブロックを開いたトークンを見るのは、トップレベルや `where` の中で、続けて `->` で終わる別々の行の誤りの診断を抑えないためである
- [レイアウト規則](../spec/layout.md) の規則 5 の `;` のエラーは1件だけ出し、parser は対応する閉じ括弧まで読み飛ばす
- 範囲の終わりを決める `Nesting` (`grammar/scan.rs`) は、`INTERP_START` と `INTERP_END` を入れ子の対として数え、穴の外の `INTERP_END` で止まる。穴の中の括弧の読み飛ばしを、穴の閉じで止めるためである。`INTERP_START` と `INTERP_END` は、開き括弧と閉じ括弧 (`is_opening_bracket`、`is_closing_bracket`) に入れない。入れると、パターンの始まりの判定が `INTERP_START` を始まりとみなし、読まないまま回り続ける。`close_bracket` も `INTERP_END` を閉じ括弧として読まない。そのため `"\{(x}"` は `)` がない E0011 を1件出し、穴は `INTERP_END` で閉じる
- 閉じていない穴の幅 0 の `INTERP_END` の位置では、parser は診断を出さない (`Parser::error`)。lexer が E0002 などを報告済みのためである。`"\{1 +` や `"\{(x` のように穴の中の式が途中で終わっても、診断は lexer の1件だけになる。`ERROR_TOKEN` の位置で出さないのと同じ扱いである
- 演算子の等式の先読みが使う `apat_len` は、文字列のパターンを `STRING_START` から `STRING_END` まで (なければ文字列の最後のトークンまで) の長さで数える。穴の中の入れ子の文字列も、`INTERP_START` と `INTERP_END` の対で数えて飛ばす
- 診断のトークンの名前 (`token_name` と `unexpected`) は、`STRING_START` を「a string」、`CMD_START` を「a command literal」と書く。文字列の最初のトークンを引用すると、`"` だけが出てしまうためである。幅 0 の `INTERP_END` はテキストを持たないので、「the end of the line」(`unexpected` では「unexpected end of line」) と書く
- コンストラクタのない `{` (型、パターン、式の位置の無名のレコード) は、`grammar/mod.rs` の `skipped_group` が E0011 を1件出して、対応する閉じ括弧まで読み飛ばし、呼び出し側が `ERROR` で包む。中のフィールドの名前を HIR に渡さず、E1001 や型の誤りを連鎖させないためである。閉じ括弧の種類は見ない。レイアウト段の規則 4 と同じ解釈にするためである

### 名前解決の回復

- 見つからないモジュール (E1026) と予約したモジュール (E1030) の import も、修飾子と並びの名前をスコープに登録し、壊れた import の印を付ける。壊れた import は、どの名前にも「不明」として答える
- 名前を引いたとき、壊れていないモジュールの定義がちょうど1つ見つかれば、それを使う。壊れた import は E1028 の候補に数えない。定義が1つも見つからず、合流した修飾子か競合する import のどれかが壊れていれば、診断を出さずに誤りの式にする。E1031、E1001、E1028 が連鎖しないようにするためである
- `import Missing (show)` は、[モジュールと名前解決](../spec/modules.md) の「名前の解決」の手順3の名前として Prelude の `show` を隠す。その `show` を使った位置は、診断を出さずに誤りの式になる
- 部品の分からない `T(..)` か `E(..)` (壊れた import のものか、モジュールにない型やエフェクトのもの) を並びに持つモジュールでは、修飾しない値の名前がどこにも見つからなければ、診断を出さずに誤りにする。どの名前も、分からない部品の1つでありうるためである
- パスの後ろ (別名と並びを含む) に構文の誤りがある import (`import Report.csv`、`import Report as`、閉じていない並び) は、構文の誤りだけを報告し、ファイルを読まずに壊れた import として扱う。読めたところまでで import を解釈すると、書いたつもりと違うモジュールや取り込み方を黙って選ぶためである。並びの `(:+)` (E0011) はその名前だけを落とす誤りなので、import は壊れない
- import の並びで報告した名前 (定義がない名前と `pub` でない名前) を本体で使った位置は、診断を出さずに誤りにする
- 宣言の後の import (E0011) も、ほかの import と同じく読み込み、スコープに登録する。報告するのは E0011 だけである
- handler の節の先頭の名前が曖昧 (E1028) なときや、壊れた import から来たときは、その handler の節のない操作 (E1013) を報告しない。その節がどの操作を指すか分からず、書いてある節を「ない」と報告しうるためである
- 曖昧な演算子 (E1028) と、壊れた import から来た演算子を含む演算子の列は、fixity で組み直さず、診断を出さずに誤りの式にする。既定の `infixl 9` で組み直すと、E1006 が連鎖しうるためである
- E0013 で一部を読み飛ばした等式 (読み飛ばした部分は `ERROR` と分けて `TOO_DEEP` のノードになる) は、本体を変換せずに誤りの式にする。読み残した形を組み上げると、`else` を失った `if` や項を失った演算子の列、束縛を失ったパターンが、構文の誤りに名前や型の誤りを連鎖させるためである
- 文のないブロック (E0009 や E0011 の回復で作られるもの) は、`Unit` ではなく誤りの式にする。同じく型の誤りを連鎖させないためである
- 循環 (E1027) を報告した後も、名前解決と型検査を続ける。item 単位の検査なので、循環があっても下流の段階は困らない

## 構文を差し替えられるようにする

- パーサは rust-analyzer と同じイベント方式にする。ノード開始、トークン、ノード終了のイベントを出し、別の処理 (`sink.rs`) で rowan の木を組み立てる
- 構文の規則は `eml_syntax/src/grammar/` に閉じ込める。構文の変更は、原則として `grammar/`、`SyntaxKind`、lexer、型付き AST ラッパ、レイアウト段の変更だけで済むようにする

## `eml_syntax` の内部構成

```
lexer/         字句解析。トークン列をつなげると元のテキストに戻る (lossless)
literal.rs     リテラルの値の解釈。lexer の検査と AST の値の取り出しが同じエスケープの表を使う
layout.rs      レイアウト段。trivia を除いたトークン列に仮想トークンを挿入する
parser.rs      イベント方式のパーサの仕組み。文法の規則は持たない
grammar/       文法の規則 (items / types / patterns / expressions)
sink.rs        イベント列から rowan の木を組み立てる
ast.rs         型付き AST ラッパ
syntax_kind.rs SyntaxKind
token_set.rs   トークンの集合 (u128 のビット集合)
debug_dump.rs  木のダンプ。構文のテストとデバッグに使う
```

- lexer は logos で単純なトークンを切り出し、文字列、コメント、演算子の分類などを手書きの層で扱う。手書きの層は `Code`、`String`、`Command` のモードのスタックを持ち、文字列とコマンドリテラルをトークン列 ([文法](../spec/grammar.md) の `string`) に分ける ([字句](../spec/lexical.md) の「モードのスタック」)。穴の `Code` は `\{` の位置を持ち、閉じていない穴の E0002 に使う。改行かファイルの終わりで閉じていない層を閉じるのは `close_layers` の1か所で、一番内側の層だけを報告する ([字句](../spec/lexical.md) の「改行での回復」)。lexer は、位置をいつも文字の境界に置く。`&text[pos..]` で panic しないためである
- 値に直す規則 (エスケープ、複数行の文字列の形と字下げ、改行の正規化) は `literal.rs` に置く。lexer の検査 (E0008、E0014) と、型付き AST の値の取り出し (`StringLit::parts`、`Literal::value`) が、同じ表と同じ判定を使うためである
- 文字列は `STRING_LIT` の節点にする。子は `STRING_START`、`STRING_TEXT`、`ESCAPE`、穴の `INTERP` の節点、`STRING_END` で、閉じていない文字列には `STRING_END` がない。`INTERP` の子は `INTERP_START`、式、`INTERP_END` で、コマンドリテラルの穴では式の前に `DOT2` を置ける。コマンドリテラルは `COMMAND_LIT` の節点で、子の形は `STRING_LIT` に引用の `CMD_QUOTE` を足したものである。式の位置では、`STRING_LIT` と `COMMAND_LIT` を `LITERAL` で包まずに置き、型付き AST は `Expr::StringLit` と `Expr::CommandLit` になる。`RAW_STRING` は `LITERAL` の中のトークンである。パターンの `LITERAL_PAT` は、`INT`、`CHAR`、`RAW_STRING` のトークンか、`STRING_LIT` の節点を持つ
- `StringLit::parts()` は、`Text` (値に直した文字列) と `Hole` (穴の式) の列を返す。隣り合う本文とエスケープは1つの `Text` にまとめ、空の `Text` は返さない。閉じていない文字列、不正なエスケープを含む文字列、E0014 のある文字列には `None` を返す。どれも lexer が報告済みである。`LiteralPat::value()` は、穴のある文字列と、`parts()` が `None` の文字列には `None` を返す
- レイアウト段は、幅 0 の仮想トークン `LAYOUT_OPEN` / `LAYOUT_SEP` / `LAYOUT_CLOSE` を挿入する。規則は [レイアウト規則](../spec/layout.md) が定める。パーサは仮想トークンを読んでも `Event::Token` を出さないので、仮想トークンは木に入らず、CST は lossless のまま
- `grammar/` は [文法](../spec/grammar.md) に従う。演算子の列は `OP_SEQ` ノードに平たく並べ、木への組み直しは HIR で行う
- 作る式の `qcon '{'` の先読みは `grammar/expressions.rs` の `at_record_body`、フィールドの並び (作る式、更新、パターン、宣言で共通) は `grammar/mod.rs` の `field_list` である。`field_list` は要素がどれも小文字の名前で始まることを使い、末尾のカンマを受け、更新ではフィールドを1つ以上求める。射影とセクションの番号の形は `field_index` が確かめる。レイアウト段の文脈 `Context::Bracket` は括弧の種類 (`BracketKind` の `Brace`、`Row`、`Other`) を持つ。`Brace` は規則 3 の例外 (`{` の中の行末の `=`) を `is_field_eq` が判定するため、`Row` は row の閉じと打ち切り (規則 4) のためである
- 行の先頭の `then` / `else` / `and` の直前の `SEP` は、`grammar/expressions.rs` の `skip_sep_before` が1つ読み飛ばす ([レイアウト規則](../spec/layout.md) の「`then` / `else` / `and` の前の `SEP`」)。`and` の束縛は `and_binding` が読み、`LET_STMT` か `LET_EXPR` の子の `AND_BINDING` にする。値の `let` の後の `and` も、E0011 を出したうえで同じ形に組んで回復する
- トークンの種類 (`EOF` まで) は 128 未満に収める。`TokenSet` が `u128` のビット集合であるため
- `eml_hir` は、型付き AST の API、識別子や演算子の `SyntaxToken`、`eml_syntax` が再公開する `AstPtr` だけを使う。CST の木の構造 (`.syntax()`) には、`AstPtr` を解決する根を作るときのほかは触れず、`rowan` に依存しない
- E0004 (未対応) は HIR が出し、パーサは出さない。HIR が E0004 を出す構文は [診断](../spec/diagnostics.md) の「未対応の構文と E0004」にある。E0004 はどの段階でも同じ意味なので、番号とラベルは `eml_diagnostics` に置く

## `eml_hir` で行う脱糖と検査

HIR への変換では、名前解決に加えて、名前の重複と未定義の名前の検査、シグネチャと等式の対応の検査、spec が HIR に割り当てた脱糖と検査を行う。式の脱糖と検査の一覧は [式](../spec/expressions.md) の「HIR で行う脱糖と検査」に、宣言とレコードに関するものは [宣言](../spec/declarations.md) と [直積型とレコード](../spec/records.md) にある。実装上の判断は下の「`eml_hir` の内部」に書く。

## `eml_hir` の内部

- 読み込みの段 (`load.rs`) は、エントリの本文を parse して `ItemTree` を作り、import を宣言の順に幅優先でたどって読む。各モジュール (`LoadedModule`) は、構文木 (`parse: eml_syntax::Parse`) と `ItemTree` を持つ。`Parse` の中身は green node なので、読み込みの結果と `eml_cli::Session` は `Send + Sync` である。ファイルの読み方は `ModuleSource` の trait で受け取り、IO は実装 (`eml_cli` の `FsProvider` と、メモリの上の並びを読む `eml_hir` の `MemorySource`) だけが持つ。同じ読み方を渡せば同じ結果を返すので、段階は純粋な関数のままである。依存先の表示のパスは、エントリの表示のパスのディレクトリに根からの相対パスをつないだものにする。標準ライブラリのモジュールの表示のパスは `<std>/Fs.em` のようにする。E1026 と E1030 はこの段で報告する。パスの後ろに構文の誤りがある import は、ファイルを読まずに壊れた import にする (上の「名前解決の回復」)。標準ライブラリは、リポジトリの `std/` のファイルを `eml_hir::STD` (ファイル名と本文の組の並び。最初が Prelude) として `include_str!` で埋め込む。`load` は `STD` を使い、`load_with_std` は標準ライブラリの並びを引数で受け取る。標準ライブラリを差し替えるテストが、`eml_cli::Session::load_with_std` を通して使う (`eml_test_support::with_std`)。並びは `Prelude.em` を含めなければならない。extern の索引が Prelude の行を引き、足りなければ panic するためである。ほかの標準ライブラリのモジュールは、import したものだけを読み込む ([モジュールと名前解決](../spec/modules.md) の「標準ライブラリ」)。モジュールは出どころ (`ModuleOrigin::User` か標準ライブラリ) を持つ。`import Fs` は、ユーザーの根にファイルが見つからないときだけ `std/` を探し、`import Std.X` はいつも `std/` を探す ([モジュールと名前解決](../spec/modules.md) の「標準ライブラリ」)。標準ライブラリのモジュールの import は `std/` だけを探す
- トップレベルの名前の解決は3つの段階に分ける。`item_tree` はファイルごとに宣言を集め、シグネチャと等式を名前で1つの関数にまとめ、名前を解決しなくても判定できる誤り (型引数の重複 E1003 を含む) を出す。`def_map` は読み込んだモジュールの列から、item の ID、モジュールごとの名前の表、import のスコープ (修飾子からモジュールの列への表と、修飾なしにした名前の表)、定義に付く fixity、lang item、extern の索引、表示名の表 `DisplayNames` を作り、import の循環 (E1027) と import の並びを検査する。`lower` は `DefMap` で名前を引き、item を `DefMap` と同じ局所の番号の順にアリーナへ置く
- `ItemTree` は rowan の red node を持たない。名前解決の前に決まる宣言の情報 (名前とその位置、`extern` のキーワード、重複を除いた型引数、コンストラクタがあるか) は、木を作るときに取り出す。型の変換のように resolver の要るもの (シグネチャ、等式、コンストラクタ、操作) だけを `AstPtr` で指す。`lower` は各モジュールの根を1回だけ作り、ポインタを解決して item と本体の変換に使う。`item_tree` が `&ast::SourceFile` ではなく `&Parse` を受け取るのは、ポインタと、それを解決する木の組を取り違えないためである
- 名前を変換より先にすべて集めるので、宣言の順によらず、`data` どうしの相互再帰や、後ろで宣言したエフェクトへの参照ができる
- HIR の出力は `Program` で、読み込みの段が読んだモジュールの列と、表示名の表を持つ。モジュールの番号は、Prelude が 0、エントリが 1 で、その後は import をたどって見つけた順である。標準ライブラリのモジュールとユーザーのモジュールは混ざって並ぶ ([モジュールと名前解決](../spec/modules.md) の「標準ライブラリ」)。順が決まるので診断の並びが安定する。item の ID はモジュールと局所の番号の組で、プログラム全体で一意である。各モジュールは item のアリーナと関数の本体を分けて持つ。本体を書き換えても item が変わらないようにするため。本体は関数ごとの `Body` で、後でクエリ化したときに関数単位で再計算できるようにする (rust-analyzer と同じ分け方)。型の注釈も、シグネチャのものと本体のものを分けて置き、本体を書き換えてもシグネチャが変わらないようにする
- `DefMap` は、モジュールごとに値と型の2つの名前空間を持ち、名前ごとに定義をソースの順にすべて持つ。重複の扱いは [modules.md](../spec/modules.md) の「名前空間」、引く順は「名前の解決」が定める。重複した `data` のコンストラクタと `effect` の操作は使えない印を持ち、それらへの参照は診断を重ねずに `Missing` にする。名前を引いた結果は `Resolved` である。診断を出さずに誤りにする名前は `Silent(Silence)` になり、`Silence::Unusable` は重複した宣言の部品、`Silence::Broken` は壊れた import から来た名前、import の並びで報告済みの名前、不明な `T(..)` の部分である。診断を出さない点はどちらも同じで、違いは fixity の求め方にだけ現れる (下の fixity の項)
- 値の item は `ValueItem` (関数、操作、コンストラクタ、メソッド) の1つの形で表す。型の名前空間の item は `TypeItem` (型、エフェクト、クラス) で表す。式の参照 (`Res::Item`)、型検査の宣言ごとの表 (`TypedProgram::decls`) も同じキーを使う
- item の変換は、モジュールごとの文脈 `ItemLowering` (ファイル、モジュール、`DefMap`、resolver、構文木の根、診断の出し先) のメソッドで行う。`ItemTree` の `AstPtr` は、この構文木の根で解決する。ファイルと診断の出し先の組だけを束ねる型は作らない。受け渡しの多い組の半分しかまとまらず、複数のファイルを扱う箇所 (`check_cycles`、`Loader`) に合わないためである
- 組み込みは、`extern` と書いた宣言と `eml_extern` の表の行の組である。宣言は標準ライブラリ (`std/` の `Prelude.em`、`FileIn.em` など) に eml のソースで書き、`SourceFiles` に登録した普通のファイルとして、エントリのファイルとは別のモジュールに変換する。`extern` のシグネチャは `FunctionKind::Extern(Option<Extern>)`、`extern data` は `TypeDefKind::Extern(Option<ExternType>)`、`extern effect` は `EffectKind::Extern(Option<ExternEffect>)` になる。`Some` の行は、宣言をモジュールの正式な名前で修飾した名前 (`Prelude.println`、`Std.FileIn.open`) を表で引いて決める。ユーザーのモジュールの `extern` は E1033 にして `None` を持たせ、`None` を持つ宣言のあるプログラムは Core IR に届かない。E1005 と E1025 は、`extern` でない宣言にはどのモジュールでも出す。instance の中の `extern` の行は `MethodImpl::Extern(Extern)` になり、行は `<モジュールの正式な名前>.<クラス> <型>.<メソッド>` (`Prelude.Eq Int.==`) で引く。ユーザーのモジュールの行は E1033 にして、行を持たせない
- `def_map` は、処理系が役割で引く item を2つの形で持つ。extern でないもの (`Bool` とそのコンストラクタ、`&&`、`||`、クラス `Eq`、`Ord`、`Show` と型 `Ordering`、`List` とそのコンストラクタ `Nil` と `::`、補間の穴が呼ぶ `display`、REPL の表示が呼ぶ `show`、前置の `-` が呼ぶ `negate`、コマンドリテラルの脱糖が呼ぶ `cmd_new` と `cmd_spread`) は `LangItems` で、Prelude から名前で引いて作る。extern の型、`IO`、`Panic` は `ExternIndex` で、標準ライブラリのモジュールから正式な名前で引いて作る。`ExternIndex` の型は、読み込んだモジュールが宣言するものだけを持つ。lowering は両方を使うので、どちらも `def_map` で作る。Prelude の item や行が足りなければ名前を添えて panic する。これは `std/` が壊れているときだけ起こり、表と `std/` を照らし合わせる結合テストが防ぐ
- handler の節の先頭の名前は、まず操作として引く。見つからないときだけ、同じ段を extern の関数だけに絞って引き直し、extern のエフェクトを起こす関数なら E1009、そうでなければ E1001 にする。ユーザーが定義した同名の関数が、Prelude の extern の関数を隠さないようにするためである
- リストの構文 `[…]` は、名前を引かずに `LangItems` の `nil` と `cons` を指す。そのため、ユーザーが自分の `Nil` を定義しても意味は変わらない。式のリストは平らな `ExprKind::List(Vec<ExprId>)` で持ち、`[]` も要素のない `ExprKind::List` にする。要素が多くても、後の段階がループでたどり、再帰を深くしないためである。パターンのリストは `p1 :: (… (pn :: Nil))` の `PatKind::Con` に組み、変数は要素の順に束縛する ([式](../spec/expressions.md) の「リスト」)
- 補間の穴は、名前を引かずに `LangItems` の `display` (`Show` のメソッド) を指す。リストの構文と同じく、ユーザーが自分の `display` を定義しても、補間の意味は変わらない。`++` は extern なので `LangItems` に入れず、translate が表の行を直接使う。穴のある文字列は `ExprKind::Interpolation(Vec<Segment>)` で持つ。`Segment` は `Text(String)` か `Hole(ExprId)` で、穴が1つ以上あるので列は空でない。`Hole` の式は、HIR が組んだ `display e` の呼び出し (`ExprKind::Call` と、`lang.display` を指す `ExprKind::Path`) で、`Call` と `Path` の範囲は `\{…}` の全体である。型検査はこれをメソッドの参照として普通に扱い、translate は普通に instance を解決する。穴の式が欠けていれば (`"\{}"`)、`Missing` の式を引数にする。穴のない文字列は、複数行の文字列と raw 文字列も含めて `Literal::String` にする
- コマンドリテラルは、新しい節点を作らずに、`LangItems` の `cmd_new` への呼び出しにする ([式](../spec/expressions.md) の「コマンドリテラル」)。各引数は文字列と同じく `Literal::String` か `Interpolation` で、文字列と同じ組み立てを使う。違いは穴の包み方だけで、文字列は `display e` の呼び出し、コマンドリテラルは `String` の型の明示 `ExprKind::Annot` で包む。`Annot` の `TypeRef` は、`ExternIndex` の `String` を指す `TypeRefKind::Con` を lowering が直に組む。この `Annot` は本体の表 `Body::command_holes: HashSet<ExprId>` に記録する。型検査が、E2001 の由来を書いた型の明示 (`Origin::Annotation`) でなく穴 (`Origin::CommandHole`) にするためである。引数のリストは `ExprKind::List` でなく、後ろから `lang.cons` と `lang.cmd_spread` の呼び出しで組む。spread の穴が途中に入るためである。E1055 と E1056 のリテラルは、全体を `Missing` にし、穴の中の式は lower しない
- `StringLit::parts()` が `None` の文字列は、全体を `Missing` にし、穴の中の式は lower しない。lexer が報告済みの誤りのある文字列では、穴の中の名前や型の誤りを重ねて報告しないためである。パターンでは、`LiteralPat::value()` が `None` のもの (穴のある文字列と、`parts()` が `None` の文字列) を `PatKind::Missing` にする。どれもパーサか lexer が報告済みである。コマンドリテラルも、`CommandLit::words()` が `None` なら全体を `Missing` にし、穴の中の式は lower しない
- HIR のダンプ (`pretty`) は、`Interpolation` を `"` で囲み、`Text` を文字列のリテラルと同じ規則 (Rust の `{:?}` のエスケープ) で引用符なしに書き、`Hole` を `\{` と `}` の間に式のダンプで書く (`"a\{(@Prelude.display x)}b"`)
- 名前付きのフィールドは `Constructor::field_names: Option<Vec<FieldName>>` に持つ。`FieldName` は名前と位置で、位置のコンストラクタは `None`、`{}` で宣言したコンストラクタは `Some([])` である。フィールドの型は `fields` にあり、名前と同じ数である。フィールドの名前は `DefMap` の名前の表に入れない
- レコードの変換は `lower/record.rs` に置く。作る式は `ExprKind::Record { ctor, fields: Vec<(u32, ExprId)> }` で、並びはソースの順、`u32` は宣言の中のフィールドの番号である。translate が書いた順に評価するために、ソースの順で持つ。フィールドが0個の `A {}` は、コンストラクタの参照 `ExprKind::Path` にする。更新は `ExprKind::Update { base, fields: Vec<(FieldName, ExprId)> }` で、フィールドは名前のまま持つ。HIR が検査するのは重複 (E1045) だけで、名前は型検査が引く。射影は `ExprKind::Field { base, field: FieldUse }` で、`FieldUse` は名前か番号 (`FieldKey`) と位置である。不正な番号はパーサが報告済みなので、その射影は `Missing` にする
- レコードのパターンは、宣言の順の引数を持つ `PatKind::Con` に組む。中のパターンはソースの順に変換する。局所変数の番号と E1017 の順を、書いた順にそろえるためである (リストのパターンと同じ)。書かないフィールドは、範囲がパターン全体の `Wildcard` にし、本体の表 `Body::omitted_fields: ArenaMap<PatId, (ConstructorId, u32)>` に記録する。線形性の診断が、書き手の `_` と区別して、フィールドの名前で報告するためである
- フィールドのセクション `(.f)` は、`lower/section.rs` が、隠れた局所変数 `$p` を引数に持つ `fn $p -> $p.f` のラムダに組む。隠れた局所変数は `Local::is_hidden` で分かり、E2013 の help がセクションの言い方を選ぶのに使う
- 関数の形の `let` (`let go acc xs = …`) は、`lower/expr.rs` が `Stmt::Functions(Vec<LocalFunction>)` に変換する。`LocalFunction { pat, lambda }` は、名前を束縛する `PatKind::Bind` のパターンと、引数と本体を持つ `ExprKind::Lambda` の式の組である。専用の閉包の型を作らないのは、束縛の検査、使用回数の検査、網羅性の検査のラムダの引数の扱い、`lambda_yields`、捕まえる変数の計算が、ラムダの式のまま使えるためである。本体の表は `Body::local_functions` (名前の `LocalId` からラムダの式) と、その逆の `Body::defining` (ラムダの式から名前) を持つ。`defining` は、ラムダの本体が組の関数を参照するかを調べるのに使う ([式](../spec/expressions.md) の「ローカル関数」)
- `let` と、続く `and` の定義 (CST の `AND_BINDING`) は、1つの `Stmt::Functions` に定義の順に並べる。組のすべての名前を先に束縛してから、本体を順に変換する。組の中の同じ名前の2つ目は E1017 にして束縛せず、参照は1つ目を指す。本体の表 `Body::local_groups: Vec<LocalGroup>` は `Stmt::Functions` ごとの組で、`LocalGroup { members, recursive }` は関数を定義の順に持ち、`recursive` はどれかの本体が組の関数 (自分を含む) を参照するときに真である。`and` のない `let` も1つだけの組になる。並びは局所変数の番号の順で、外側の組が本体に入れ子の組より先に来る。`Body::group_of(local)` が関数の組を引く。使用回数と持ち越しのパスは、組の関数への参照を捕まえた値に数えず、再帰する組の関数に `Unr` を求める。Core IR の持ち上げは、再帰する組の捕まえる変数を共通にする
- `fn` の節は、`lower/handler.rs` が `ctl` の節の形に下ろす。操作の引数の後に隠れた引数 `$k` を足し、本体を `let $r = 本体 in $k $r` (パラメータ付き handler では `let ($v, $st) = 本体 in $k $v $st`) のブロックにする。HIR の `OpClause` は1つの形のままなので、型検査、translate、EP は節の種類を区別しない。隠れた名前はスコープに積まないので、利用者のコードから解決できない。`pretty` は下ろした形 (`$k` を含む) を書く。下ろした節は `Body::fn_clauses: Vec<FnClause>` (隠れた `$k`、書いた本体の式、節の範囲) に記録する。型検査は本体の期待する型の由来を `Origin::FnClauseBody` にし、持ち越しのパスは `$k` の持ち越しを `CarriedValue::FnClauseContinuation` として節を指して報告する ([診断の出し方](diagnostics.md))
- `use` が残りの文を包むために組んだラムダは、本体の表 `Body::use_lambdas: HashSet<ExprId>` に記録する。型検査が、これを引数のラムダとして後に回さないためである ([型と Kind](../spec/types.md) の「引数のラムダを後で検査する」)
- `pretty` は、作る式を `Person { name = …, age = … }` (ソースの順)、レコードのパターンを `Person { name = …, age = … }` (宣言の順で、すべてのフィールド)、更新を `{ e | age = … }`、射影を `e.name` と書く
- パターンのリストを組んだ木の範囲は次のとおりである。1つ目の `::` は `[` から `]` まで、k 番目 (k ≥ 2) の `::` は p_k の始まりから `]` までで、`Nil` は `]` である。`]` がないときは、`Nil` をノードの終わりの空の範囲にする。`[]` のパターンは `Nil` 1つで、範囲は `[]` 全体である
- シグネチャか等式のない関数も `Function` として残し、呼び出し側で名前の誤りを連鎖させない。引数の個数の違う等式 (E1020) は `match` の枝に入れず、本体に誤りの印を立てる
- 等式が2つ以上ある関数は、引数の位置ごとの隠れた局所変数に対する `match` に脱糖する。この `match` は由来 (`MatchSource::Equations`) を持ち、網羅性の検査が等式として報告する。等式が1つの関数と引数のない値は、脱糖しない
- fixity は定義に付く ([宣言](../spec/declarations.md) の「fixity」)。`DefMap` が item をすべて集めてから付けるので、宣言の位置は問わない。fixity は解決の結果から `Resolver::fixity_of` で求める。見つかった item はその fixity を使い、宣言がないときと、別のモジュールの `pub` でない宣言しかないときは既定の fixity を使う。`Silent(Unusable)`、見つからない名前、`pub` でない名前、不明な修飾子は既定の fixity で組み直す。`Silent(Broken)` と曖昧な名前を含む列は組み直さない (上の「名前解決の回復」)。演算子の列とセクションは、各演算子を1回だけ値として解決し、その結果を fixity と変換の両方に使う。中置のパターンも、fixity は各演算子を1回だけ値として解決して求める。組み直しが決まらない列では、ほかの演算子の E1001 も出さない。セクションの先読み (`looser_operator`) は被演算子を変換する前に被演算子の中の演算子の fixity が要るので、名前から引く `Resolver::fixity` を使う
- 式とパターンの組み直しは同じ fixity を引く。パターンの演算子は `constructor()` で引き直すが、`:` で始まる演算子は文法上コンストラクタにしかならないので、式として引いても同じ item と fixity になる
- `&&` と `||` は、解決した先が lang item のときだけ `if` に脱糖する。`|>` と `<|` は脱糖せず、Prelude の関数の普通の呼び出しにする。`let` に脱糖すると左辺が推論になり、関数の引数の型を期待した診断 (E2001 が `x |> f` の `f` を指す) が失われるため
- クラスは `ClassDef` (型変数、上位クラスの列、メソッドの列)、メソッドは `Method` (シグネチャと、既定のメソッドの関数)、instance は `InstanceDef` (クラス、頭の型、頭の型変数、文脈、メソッドごとの定義 `MethodImpl`、出どころ `InstanceOrigin`) で、モジュールごとの `classes`、`methods`、`instances` のアリーナに置く。`ItemTree` は、クラス (名前、型変数、文脈、メソッドのシグネチャと既定の等式)、instance (クラスの名前、頭、文脈、メソッドの等式と `extern` の行)、`data` の `deriving` の並びを集める。名前か型変数のないクラスはパーサが報告済みなので捨て、そのクラスを使う位置は E1002 になる
- 既定のメソッドの本体 (`FunctionKind::DefaultMethod`) と instance のメソッドの本体 (`FunctionKind::InstanceMethod`) は、普通の関数と同じく、等式を `match` に脱糖した `Function` として、`ItemTree` の関数の後ろに置く。名前の表に入れず、E1003 の対象にもしない。名前で引けるのは `ValueItem::Method` だけである。本体を持つ関数かは `FunctionKind::has_equations` で見分ける
- instance は、クラスが別のモジュールにありうるので、すべてのモジュールの item を置いた後に置く。モジュールごとに、手で書いた instance を置いてから導出した instance を置く。重複 (E1035) は、(クラス, 頭の型) の索引 (`Program::instance`) で判定する。置かなかった instance (クラスか頭の型を解決できないもの、頭がないか誤ったもの (E1039、E1015、E1043)、orphan (E1034)、重複 (E1035)) のメンバーと、クラスにないメソッド (E1037) の本体も変換して名前の誤りを報告し、変換した本体は捨てる。最初の誤りを直すまで本体の誤りが見えないことを避けるためである。関数を置かないので、型検査と translate からは見えない。本体の注釈で引ける型変数は、頭に書いた型変数である。上位クラスの循環 (E1042) は、すべてのクラスを置いた後に、自前のスタックでたどって切る。上位クラスの推移的な閉包 (`Program::superclasses`) も作業の列で求め、直接の上位クラスから宣言の順に幅優先で並べる。どちらも、上位クラスの鎖の長さに比例して Rust のスタックを使わない
- 導出した instance は本体を持たず、`InstanceOrigin::Derived` に `deriving` のクラス名の位置を持つ。どのメソッドの本体を処理系が作るかは `Program::core_method` (`CoreMethod`) が決める。導出した `Show` のために、中置のコンストラクタの fixity を HIR に残す
- 呼び出しの評価の順は `eval.rs` の `call_steps` が決める ([関数適用](../spec/expressions.md))。持ち越しのパス (`eml_types`) はこの手順を逆に、Core IR の変換 (`eml_core_ir`) は順にたどる。順の組み立てを1か所に置くのは、2か所で組むとずれたときに持ち越し規則が実行と食い違うためである。直接呼ぶ範囲 (`known_arity`) も、両方の段階がここから引く
- `Body` の走査関数 (`walk_child_exprs`、`pat_bindings`、`captures`) は、式やパターンの種類を足す段階が直す。誤った handler の節は診断を出して節に入れず、扱うエフェクトが決まらなければ `effect` を `None` にして、型検査に診断を連鎖させない。誤りのあるセクションも、被演算子の名前の誤りを報告してから全体を `Missing` にする
- タプルは専用の形 (`ExprKind::Tuple`、`PatKind::Tuple`、`TypeRefKind::Tuple`) で持ち、要素は2つ以上である。型検査がラベルのない要素の列 (下の「`eml_types` の内部」のタプルの箇条) に写す。`Unit` は要素のないタプルである。タプルの射影 `t.0` は、名前付きのレコードの射影と同じく `ExprKind::Field` で持ち、型検査が型から引く ([型と Kind](../spec/types.md) の「フィールドの解決」)
- HIR の関数は、シグネチャの関数名の位置 (`Function::signature_name_range`) と、等式の関数名の位置 (`Function::equation_ranges`) を持つ。どちらもソースに書かれた名前の位置で、HIR が見た目の情報 (行頭と字下げ) を持たない規律 (上の「各段階の規律」) に反しない。等式の数は、E1020 の後の網羅性の診断の連鎖を抑えるのにも使う。位置を別の表に分ける形は [ロードマップ](../future/roadmap.md) の「処理系」の source map の項目にある

## `eml_types` の内部

- 型は検査器の中の表 (推論の表、`Table`) に置いて ID で引き、型変数の束縛を辿って単一化する。row は「ラベルの並び + 末尾の row 変数」で、scoped labels の書き換えで単一化する。Kind の変数と `≤` の制約は束の上で最小解を求める。推論の対象は [型と Kind](../spec/types.md) が定める
- 推論の後に、型付き HIR の上で別のパスとして、線形性の検査 ([線形性](../spec/linearity.md)) と網羅性の検査 ([網羅性](../spec/exhaustiveness.md)、Maranget の usefulness) を行う
- `Context::new` はプログラム全体の情報 (データ型の Kind、名前、多重度) を1回だけ作り、関数ごとの推論の表はこれを借りる。データ型の Kind の表は型の表 (`TypeStore`) とも共有する。表を作る費用を関数の大きさに比例させるため。型検査は次の順に進める。書き出す先の型の表 (`TypeStore`) はプログラム全体で1つの共有の登録表で、追記だけする。そのため、本体を検査する順は結果の意味を変えない
  1. instance の検査、シグネチャを閉じた形 `Shape` にすること、本体のない宣言のスキーム、`check_main`、等式のない関数の空のスキームを先に行う。SCC の順に解くとき、呼ぶ側を解く時点で呼ばれる側のスキームがそろっていなければならないためである
  2. 呼び出しグラフの SCC ごとに、呼ばれる側から順に次を行う。(a) 各メンバーの本体を、新しい推論の表で、全宣言の `Shape` だけを見て検査する (段1)。Kind の制約は `take_problem` で取り出すだけで、表は残す。(b) その SCC の Kind を解く (`solve_scc`)。(c) 解と本体の変数の要約 (`kind/summary.rs`) を使って各メンバーの本体の型を書き出し、表を捨てる
  3. メソッドの Kind の検査、違反の報告、宣言ごとの結果、一様な位置、網羅性の検査を行う
  - 同時に生きている推論の表は、処理中の SCC のメンバーの分だけである。ふつうは1つで、大きな SCC でもすべての Kind の制約を同時に持つ程度の大きさに収まる
  - 要約の仕事は、メンバーごとに、書き出す変数から下に届く範囲 (自分の宣言自身の変数を含む成分で止まる) の大きさである。強連結成分の DAG を下にたどり、「下に届く宣言自身の変数の集合」を成分ごとに覚える。宣言自身の変数を持たないメンバーは、たどらずに SCC 全体の最小解の値を使う。大きな SCC で2乗にならないことは、`eml_types` の `scaling` テストが確かめる
  - 本体の書き出した型は、その SCC の解 (呼ばれる側から複写したスキームを含む) に依存する。salsa に移すときは、本体の型を本体ごとの query ではなく、SCC ごとの query の出力にする
- `Shape` は推論の表を指さず、変数をスキームの中の番号で持つ。参照するたびに具体化し、段1は呼び出し先の制約を複写せずに Kind の具体化の記録 (`Instance`) を残して、段2が展開する。extern の関数、操作、コンストラクタの型も、ユーザーの関数と同じ経路で `Shape` に閉じる
- シグネチャに書いた row 変数の上限 (`<never e>`) は、本体の検査 (`check_body`) と宣言の問題 (`declaration_problem`) が呼ぶ `Shape::instantiate_rigid` の1か所で、由来 `Provenance::Bound` の制約 `σ ≤ Never` として足す。参照ごとの `Shape::instantiate` では足さない。スキームに残った上限を段2が参照ごとに複写するので、そこでも足すと同じ上限が2つになる。`never` の位置のファイルは `signature_file` が決め、instance と既定のメソッドではクラスのファイルである
- 段1は、Kind の具体化の記録とは別に、参照ごとの具体化の表 (`BodyTypes::instantiations`) を作る。式の中のトップレベルの item への参照 (`ExprKind::Path` の式と、レコードの構築 `ExprKind::Record` の式) ごとに、宣言と型引数 (型の表の ID) を持つ。単相化の instance の表、型クラスの証拠、後の `Num` の解決は、この型引数から決める。型引数は `Shape::rigids` の順に並ぶ。関数はシグネチャに最初に現れた順、操作はエフェクトの型引数が先、コンストラクタは `data` の頭の型引数の順である。メソッドは、クラスの型変数が先で、メソッド自身の型変数が後である。型引数の中の矢印は線形性を持つ。宣言の Kind 変数そのものは持たず、型クラスと、後の `Num` の解決は型引数だけで決まる。row 変数の具体化は、yield しうるかの分類 (`RowYield`) だけを `rows` に持つ ([型と Kind](../spec/types.md) の「row の具体化の記録」)。分類は `table/yields.rs` が、rigid な row 変数がどの定義のものかを推論の表が知っている間に行う。本体が動く row (`body_yield`)、ラムダの row (`lambda_yields`)、呼び出しの矢印の row (`arrow_yields`)、宣言の型の最初の矢印の row (`first_arrow_yield`) も同じ分類で記録する
- 具体化の表は本体の検査の間に推論の表の変数のまま記録し、持ち越しのパスの後で `exprs` と同じく書き出す。後の文の単一化で決まる型 (`let` で束縛したラムダの引数など) を取り込むためである。最後まで決まらない型引数は `Flexible` になる。局所変数の参照は具体化しないので記録しない。パターンのコンストラクタと handler の節の操作も記録しない。コンストラクタと操作は制約を持てず、解決が要らないためである。型ごとの解決が要る参照は、HIR で `ExprKind::Path` に脱糖してこの表に届ける。前置の `-` の `negate`、`&&` と `||` の `True` と `False`、セクションのラムダの中の演算子、補間の穴の `display` がそうである。処理系が暗黙に持ち込む参照は、この形に脱糖する。別の形を選ぶときは、表のキーと記録の場所を広げる
- 段1は、呼び出しの `mask` の表 (`BodyTypes::masks`) も作る。キーは呼び出しの式と矢印の番号の組で、`k v` も普通の呼び出しとして同じ形で記録する。値は `mask` の項目 (`MaskItem`。エフェクトと、残す数 n と、飛ばす数 m) の並びで、エフェクトが rest に初めて現れた順のまま持つ。昇順に並べるのは Core IR への変換である。空の `mask` は記録しない。`mask` は row の包含 (`Table::include_row`) が返し、呼び出しの row を含める1か所 (`include_call_row`) で記録する。Core IR への変換は、この表から呼び出しごとの `mask` を作る ([Core IR](../spec/core-ir.md))
- extern の型の Kind は `eml_extern` の表の行から決め、`Context` が extern のエフェクトの印 (`EffectKind::Extern`) を持つ。extern のエフェクトのラベルの重なりは、row を展開する `resolve_row` の1か所で落とし、`mask` には入れない。多重度も表の行が決める (`IO` は `Once`、`Panic` は `Never`)。重なりを `resolve_row` の1か所で落とすのは、単一化、包含、表示がどれも展開した row を使うためである ([型と Kind](../spec/types.md) の「推論」)
- 制約は `check/constraints.rs` が解く ([型と Kind](../spec/types.md) の「制約の解決」)。本体の検査の後、使用回数のパスの `usage::reliable` より前に、具体化の表の参照ごとに求める制約を解く。E2006 と E2009 を本体の誤りに数え、線形性の診断を連鎖させないためである。解き方は作業の列で、同じクラスと同じ代表の組は1回だけ列に足す。推論の表は部分を共有するので、型を木としてたどると型の深さの指数の時間がかかるためである。同じ規則の `solve` を、導出した instance のフィールドの検査 (`check_instances`) も使う
- 制約が解けた参照には、instance とタプルで解いた節点の型引数に、参照を由来として `Unr` を求める。シグネチャの制約の型変数に本体が足す `a ≤ Unr` は、由来 `Provenance::Given` を持つ。この境界の破れは、いつもほかの所 (E2006、E2010、解いた先の `Ti ≤ Unr`) で報告されるので、`Given` の破れは報告しない
- `never` を書いたシグネチャの宣言を指す参照はどれも、参照を由来とする `σ_参照 ≤ Never` を1つ持つ。SCC の外の参照は、残した制約の複写 (`copy_scheme`) で持つ。SCC の中の参照 (自分自身、相互再帰、ローカル関数の中からの参照を含む) は、`Merged::equate` が呼ばれる宣言の書いた上限を写して持つ。`Provenance::Bound` の制約は報告しない。SCC の中では参照の変数と宣言の変数が等しいので、参照が上限を破れば宣言の制約も破れるが、報告するのは参照に写した制約だけにして参照の位置を指す。本体のどこからのトップレベルの値への参照も、ローカル関数の中を含めて囲む宣言の `Instance` になるので、すべての参照がこの形に当たる。写した上限の由来は `KindReason::RowBound` で、スキームの `bound_sources` が持つ上限の出どころを入れる。row 変数にラベルを入れる下限 (`bind_row`) は、今の由来が `At` なら理由を `KindReason::Performs` にして記録する。段2は破れた上限の下側の変数の値を決めた下限の由来を読み、E2020 の原因にする
- 型の表の型で instance を引くのは `resolve.rs` の `resolve` (`Resolution`) である。型検査の後の一様な位置のグラフと、Core IR の変換が使う。型検査の中の解決と同じ規則を、書き出した型の上で適用する
- E2011 は、instance のメソッドと既定のメソッドの Kind のスキームが、クラスのメソッドの宣言から作ったスキームから導けるかを `kind/entail.rs` で確かめる。導き方は健全だが完全ではなく、前提の制約を辺としてたどった先の定数と、変数どうしの到達だけを見る。本体に誤りがあれば (`usage::reliable` でない本体)、由来を抑止した使用回数の制約もスキームに残るので、E2011 を確かめない
- 一様な位置のグラフ (`uniform.rs`) は、型検査の後に、書き出した本体の表 (`BodyTypes::instantiations`) と宣言の型から作り、結果を `TypedProgram::uniform` (`Uniform`) に入れる。節点は関数、instance (`InstanceNode`。タプルは大きさごとに1つ)、メソッドの型変数の位置である ([Core IR](../spec/core-ir.md) の「一様な位置と制約付きの多相再帰」)。参照の型引数に型変数が現れるかは、本体ごとに型の結果を覚えてたどる (`vars_in`) ので、共有された型を1回しかたどらない。強連結成分は Tarjan の方法を作業の列で求め、グラフの深さに比例して Rust のスタックを使わない。Tarjan の方法は `kind/graph.rs` の1か所にあり、呼び出しグラフの SCC (`scc.rs`) と Kind の解 (`kind/solve.rs`) も同じ関数を使う。E2012 もここで出す
- 型の表は rigid な型変数を名前で登録するので、同じ種類で同じ名前の変数は同じ ID になる。そこで、handler の節で操作ごとに量化した型変数 (`Shape::instantiate_with_effect_args` が作る変数) は、関数のシグネチャの型変数 (`TypeKind::Rigid`) と別の種類 `TypeKind::OpVar` で書き出す。分けないと、関数の型変数と同じ名前の節の型変数が同じ ID になり、単相化の代入で区別できない。推論の表の rigid な変数は、操作ごとの変数かどうかと、そのときの `OpVar` の Kind を `RigidInfo::operation: Option<Lin>` に持ち、書き出し (`table/export.rs`) がそれで種類と Kind を選ぶ。表示は種類によらず同じ名前で、推論 (単一化、Kind、持ち越し) は推論の表の上で動くので、`OpVar` は推論を変えない
- `OpVar(名前, Lin)` と、代入でそれから作る `Flexible(Lin)` は Kind を持つ。操作の引数の型に現れる変数は `Unr`、結果の型にだけ現れる変数は `Poly` である ([型と Kind](../spec/types.md) の「`Flexible` と `OpVar` の Kind」)。そのため、関数の本体の型と宣言の型に現れる `Rigid` は、その関数自身のシグネチャの型変数だけである。`OpVar` は節の中だけに現れるとは限らない。節の値が handle の結果になると (`ctl put x k -> drop k; id x`)、handle の外の本体の型にも現れる。操作とコンストラクタの宣言の型 (`$op$`、`$con$`、データの配置が読むスキーム) の `Rigid` は、そのまま残る
- Core IR は、extern を値として使う場所ごとに包む関数を作る。instance の `extern` で結んだメソッドの参照は、instance の代入をかけた型引数で instance を引いてから行を決めるので、同じ本体でも instance ごとに包む行が変わりうる
- 宣言の型は `TypedProgram::decls` の `DeclType` にある。結果を宣言ごとに持つのは、クエリ化したときに宣言ごとのクエリの結果として使い、REPL で前の入力の宣言を検査し直さずに使い回せるようにするためである。`DeclType` は型 `ty` のほかに、`Shape`、Kind のスキーム、本体の変数の要約 `joins` を crate の中だけで持つ。外から読むのは `kind_values`、`uniform_kind`、`needs_substitution` と、宣言の型変数の名前から代入を作る `substitution` と `partial_substitution` だけである。`DeclType` の型は型の表の ID で、型そのものはプログラム全体で追記だけする共有の型の表にある。クエリ化したときは、型の表を salsa の interned に置き換える
- 型検査が後の段階に渡す型は、プログラムに1つの型の表 (`TypeStore`、`TypedProgram::types`) に置き、`TypeId` で指す。表の中身 (`TypeKind`) の子も `TypeId` である。`intern` は、同じ形の型がすでにあればその ID を返す (hash consing)。そのため、ID が同じことと型が同じことが一致し、部分を共有する型も表の大きさに比例する場所しか使わない。宣言に対して相対的な型 (値が `Rigid` か `Var` に依存する型) では、この一致は同じ宣言の中で比べたときに成り立つ。同じ `Var(3)` でも宣言が違えば意味が違うが、`TypeId` は同じになる。型が `Error` を含むかは登録するときに子から求めて持つので、`contains_error` は型をたどらない。決まった型 (`Unit`、`Int`、`String`、`Bool`、`_`、`{error}`) は `TypeStore::new` が最初に登録し、`unit()` などで引く。決まった型のない表を作れないよう、`TypedProgram` は `Default` を持たない。`intern` は crate の中だけに公開する。後の段階が表に型を足せるのは、`substitute` (次の項目) を通したときだけである。ID は検査の順で決まるが、後の段階は ID の値に意味を持たせない
- 型の表は、型ごとに型変数 (`Rigid` か `OpVar`) を含むかの印 (`contains_type_vars`)、Kind 変数 (`Var`) を含むかの印 (`contains_kind_vars`)、型の値の線形性 (`TypeStore::linearity`) を、`Error` の印と同じく登録するときに子から求めて持つ。線形性は、効く型引数の表 (`DataKind`) から求め、値が `Rigid` か `Var` に依存する型には持たない (debug ビルドでは読むと止まる)。`TypeStore::substitute` は、単相化が instance の型を作るための代入である ([Core IR](../spec/core-ir.md) の「変換の規則」)。代入 `Substitution` は、シグネチャの型変数の名前から型への対応と、宣言の Kind 変数の値の列 (`Substitution::new(型引数, kind_values)`)、代入した結果を型ごとに覚える表を持つ。型引数だけを置き換える `Substitution::partial` もある。`substitute` は、`Rigid` を対応の型に置き換え (対応にない名前の `Rigid` は残す)、`Var(i)` を `kind_values[i]` に置き換え (足りなければ debug ビルドで止まる)、`OpVar(名前, k)` を、関数の型引数と名前が同じでも、いつも `Flexible(k)` に置き換える。型構成子の引数、タプルの要素、関数型の引数と結果とエフェクトの型引数に代入し、row の末尾には触れない。結果は `intern` で登録するので、同じ型は同じ ID になる。型変数も Kind 変数も含まない型は、印を見てたどらずに返す。1つの `Substitution` で代入した型は覚えた結果を返すので、その `Substitution` での代入の費用の合計は、たどった型の表の節点の数に比例する
- `display` は型を木としてたどるので、部分を共有する型では表示の長さが表の大きさの指数になる。`display_name_bounded` は、表示が上限の文字数を超えた時点で書くのをやめて `None` を返し、費用を上限に比例させる。単相化の instance の名前は、これで作る
- `Exporter` は推論の表の型を型の表に書き出し、後の段階と診断の文言の両方に渡す形を作る。書き出す型は矢印の線形性を持つ。使い方は2つある。診断のための書き出し (`Exporter::diagnostic`) は、Kind を解く前に診断の文言、導出した instance のフィールドの検査で使い、決まっていない矢印を `Poly` に、決まらなかった型変数を `Flexible(Poly)` にする。診断の表示は線形性を書かないので、文字列は変わらない。SCC を解いた後の書き出し (`Exporter::solved`) は、Kind 変数の値を `BodyKinds` (`kind/summary.rs`) から引く。宣言の型は `Shape::export` が書き出し、スキームを渡す使い方 (`typed_program` が宣言ごとの結果を作るとき。定数に決まる宣言自身の変数を畳み、残りを `Var(i)` にする) と、渡さない使い方 (`check_main`。宣言自身の変数をすべて `Var(i)` にする。`main` の検査は `Exporter::diagnostic` を使わない) がある。`Shape` と `KindScheme` は crate の外から読めず、後の段階は `kind_values` と `linearity` を通して値を得る
- `Exporter` は推論の表と型の表を借り、書き出した結果を、渡された `Ty` とその代表の両方について覚える。借りている間は推論の表を変更できないので、覚えた結果は古くならない。本体の検査の後は、1つの `Exporter` で式、局所変数、パターン、具体化の型引数をすべて書き出すので、推論の表の各節点を書き出すのは1回だけである。推論の途中で診断の文言のために書き出す箇所 (`check/report.rs`、`usage.rs`) は、その場で短命の `Exporter::diagnostic` を作り、同じ型の表に登録する。記録を推論の表の大きさの配列でなく `HashMap` にするのは、短命の `Exporter` を何度作っても、費用が書き出した節点の数に比例するようにするためである。シグネチャから作る型 (`Shape::export`) も同じ型の表に登録する
- `KindReason::OmittedReturn` は状態の型を ID で持ち、破れた制約を報告するときだけ表示する。誤りのない経路で型を表示すると、型を木として書き下した大きさの時間がかかるためである。破れた制約を並べる鍵 (`order_key`) も、ID でなく表示した文字列を使う。ID は検査の順で決まるので、鍵にすると並びが検査の順に左右される
- 持ち越しのパスは、使用回数のパスの直後に、同じ本体を Core IR の評価の順の逆にたどる。型検査器が記録した呼び出しごとの row を読み、持っている値と row の多重度を組にした制約を出す。この制約は、段2が線形性と多重度の両方の束を解いた後に検査する
- 持ち越しのパスは、リストの要素を、タプルの要素と同じく左から評価する部分として扱う。ただし、評価済みの要素は、最初の要素1つで代表させる (`carry.rs` の `list`)。要素の型はどれも同じなので、持ち越しの制約も同じになるためである。タプルのように要素を1つずつ持つと、生きている値の集合を要素ごとに写すので、要素の数の2乗の時間がかかる。持ち越しの誤りは、代表の最初の要素の位置で報告する
- 型検査は、穴のある文字列を `String` にし、各穴 (`display e` の呼び出し) を `String` に対して検査する。使用回数のパス (`usage.rs`) は、穴を左から順にたどる。持ち越しのパスは、穴を左から評価する部分として扱い、今の生きている値の集合を穴から穴へ渡す。組み立て中の文字列は、持っている値に足さない。`String` は `Unr` なので、持っていても制約が増えないためである。そのため、穴の数に比例する時間で済む
- タプルは、推論の表 (`TyShape::Tuple(Vec<Ty>)`)、型の表 (`TypeKind::Tuple(Vec<TypeId>)`)、シグネチャの形 (`ShapeTy::Tuple(Vec<ShapeTy>)`) のどれでも、ラベルを持たない要素の列である。`Unit` は要素のないタプルである。表示 (`(A, B)`、`Unit`) と構造的な instance の解決 (`Resolution::Tuple`) は、この形から作る
- 射影と更新は `check/field.rs` が検査する ([型と Kind](../spec/types.md) の「フィールドの解決」)。結果は本体の表 `BodyTypes` に残す。`fields: ArenaMap<ExprId, FieldTarget>` は射影が指すフィールド (コンストラクタとフィールドの番号か、タプルの要素の数と番号)、`updates: ArenaMap<ExprId, Update>` は更新のコンストラクタ、書いたフィールドの番号 (ソースの順)、すべてのフィールドの具体化した型 (宣言の順) で、`discarded: ArenaMap<ExprId, Vec<(u32, TypeId)>>` は射影と更新が捨てるフィールドの番号と型である。Core IR の変換は `fields` と `updates` を、使用回数のパスは `discarded` を読む。作る式と更新のフィールドの値の由来は `Origin::Field { ctor, field }` である
- 引数のラムダを後に回す手順は、`check/body.rs` の `call` にある。後に回したラムダと row は `Postponed` に覚え、`check_postponed` が、ラムダを覚えた引数の型に対して検査してから、row を引数の順に今の row に入れる。後に回すかは `postponable` が決め、`ExprKind::Lambda` のうち `Body::use_lambdas` にないものを後に回す。矢印に当たらない引数のラムダは `check_against_error` が `Error` の型に対して検査する
- 呼び出しの包含は、`check/inclusion.rs` が解く ([型と Kind](../spec/types.md) の「呼び出しの包含を解く」)。`check/body.rs` の `include_arg_row` は、呼び出し先の row から末尾を外したラベルだけを `include_call_row` で今の row と対にし、末尾が row 変数なら `Inclusion` (呼び出し先と今の row、今の row の由来、呼び出しのキーと名前) を `BodyCheck::inclusions` に積む。`solve_inclusions` は `check_function` の直後 (REPL の入力では `undecided_binding` の前) に呼ばれ、4つの手順を順に行う。`add_missing_labels` は、`Table::missing_labels` で表を変えずに足りないラベルを数えてから、`Table::add_labels` で今の row の自由な末尾に足す。`include_row` を使わないのは、呼び出し先の末尾を今の row とつないでしまうためである。`extend_to_rigid_tails` は `Table::extend_to_rigid` で、`close_unused_tails` は `Table::closable_tail` と `Table::close_row` で row を束縛する。`:type` の問い合わせで閉じない変数は、その前に `kept_open` が `Table::unsolved` と包含から集める。`check_inclusions` は、`with_ambient` で覚えた今の row と由来に戻して `include_call_row` を呼び直し、誤りと `mask` を記録する。誤りになった呼び出しは `failed_calls` に覚え、1つの呼び出しの誤りを1件にする。row を束縛する手順は、`with_kind_origin` で多重度の制約の由来を呼び出しの範囲にする
- ローカル関数の組は、`check/body.rs` の `local_functions` が検査する ([型と Kind](../spec/types.md) の「ローカル関数の推論」)。組の関数の型を先に置いて名前を束縛し、本体をラムダとして検査する。組の中の呼び出しも、ほかの呼び出しと同じく包含になるので、組のための仕組みは持たない
- 使用回数のパス (`usage.rs`) は、射影と更新が捨てるフィールドを `discarded` から、パターンに書かないフィールドを `Body::omitted_fields` から読み、`KindReason::DiscardedField { name, site }` を由来にして `Unr` の制約を出す。`DiscardSite` (パターン、射影、更新。射影はタプルかとセクションかの印を持つ) が E3004 の言い方と help を変える。持ち越しのパス (`carry.rs`) は、作る式と更新を、タプルと同じく左から評価する部分として扱う
- 戻らない呼び出しかは、`diverge.rs` の `diverging_call` が、呼ばれる宣言の HIR のシグネチャだけから決める ([線形性](../spec/linearity.md) の「戻らない呼び出し」)。使用回数のパスの経路ごとの使い方 (`Uses`) は、すべての経路が戻らない呼び出しで終わるとき、経路ごとに評価の順で最初の呼び出しを `diverges` に持つ。分岐の合流と束縛の有効範囲の終わりで手放す変数を決め、`BodyTypes::implicit_drops` に入れる。持ち越しのパスは、同じ表を `carry::constrain` の引数で受け取る
- Kind の制約は由来 (`Provenance`) を持ち、推論の表の「今の由来」から記録する。段2は破れた制約の由来を返し、`Suppressed` の制約は捨てる。そのため、報告したい制約には必ず由来を付ける。既定の由来 `Unattributed` は付け忘れを見つけるためのもので、それが破れたときと、宣言の型だけで作った制約が破れたときは処理系の誤りとして扱う
- 報告済みの誤りのある本体 (誤りの跡がある、型の誤りを報告済み、HIR の誤りがある) では、使用回数のパスも持ち越しのパスも由来を記録しない ([診断](../spec/diagnostics.md))
- `check` は `Program` と `SourceFiles` を受け取る。HIR のブロックは最後の文の開始位置 (`last_start`) だけを持ち、E3003 の fix は `check/report.rs` が作る。開始位置の行の先頭からそこまでのテキストが空白とタブだけなら、それをそのまま写した字下げで `drop x` の行を入れる。ほかの文字があれば (最後の文がその行の最初のトークンでなければ) fix を出さない。字下げを HIR に持たせないのは、HIR が見た目の情報を持たないためである (上の「各段階の規律」)
- 由来の位置は、ファイルと範囲の組 (`Span`) で持つ。具体化を通った由来は、呼んだ関数のある別のモジュール (Prelude など) の中を指しうるためである。報告は由来のファイルを使い、ファイル、範囲の順に並べる
- row の末尾には `Error` がある。未定義のエフェクトか解決できない row 変数の跡で、相手の側にしかないエフェクトを受け入れるが、自分の側の既知のエフェクトは受け入れない。綴り誤りの E1002 と無関係なエフェクトの誤りを隠さないためである。ラムダやシグネチャの矢印が壊れているときも、末尾が `Error` の row で本体を検査し、エフェクトの誤りを連鎖させない
- 型の走査は `TypeKind`、`TyShape`、`ShapeTy` の `for_each_child` だけがたどり、そこでは `..` を使わず欄をすべて名前で受ける。欄を足したときに、occurs の検査などから漏れないようにするためである。内部の型の形は `TyShape`、推論の中の矢印の線形性は `ArrowLin` と呼び、Kind と取り違えないようにする。公開の線形性は、書き出した型の `Lin` (`Unr`、`Lin`、`Poly`、`Var(u32)`) だけである。推論の中の `Linearity` と `Multiplicity` は crate の中に置く。結びは `Lin::join` の1か所にあり、順は `Lin` > `Poly` > `Unr` である。宣言の順と違うので、`Lin` に `Ord` は持たせない
- 推論の表の型を1つたどる処理 (`occurs`、`row_occurs`、`kind_bounds`、`kind_vars`) は、子を代表ごとに印を付けてたどり、同じ代表を2回訪れない。表は部分を共有するので、木としてたどると型の深さの指数の時間がかかるためである。印は表が持つ世代番号付きの配列 (`Marks`) に付け、処理のエントリ (`start_walk`) でだけ世代を進める。呼び出しごとに表の大きさの配列を作ると、呼び出しが多いときに2乗の時間になるためである。`kind_bounds` は境界を最初に現れた順に重複なく並べる。書き出し (`Exporter`) は、印の代わりに書き出した結果を覚える
- 単一化はこの規則の外にある。`unify` は、1回の呼び出しの中で単一化を終えた複合の型 (型構成子、タプル、関数型) の代表の組を覚え (`Unified`)、同じ組はすぐに終える。row のラベルの型引数の単一化にも同じ記録を渡す。もう一度たどっても同じ Kind の制約を同じ由来で出すだけなので、飛ばしても結果は変わらない。記録は呼び出しの中だけなので、同じ大きな型の組を何度も単一化すると、そのたびに表の大きさに比例する時間がかかる ([実装の現在地](status.md) の「コンパイルの時間と深さ」)
- `TypeKind::Con` は `{ id, args, rows }` で、型の引数と row の引数を別の並びに持つ (どちらも宣言の順。HIR の `TypeRefKind::Con` は `(def, args, rows)` で、宣言の `generics` の各引数が `ParamSort` を持つ)。型の引数の番号は `generics.type_vars` の順なので、Kind と変位の計算は並びを混ぜずに引け、表示だけが宣言の順に混ぜ直す。`TypeKind::Con` と `EffectLabel` は ID だけを持ち、名前を持たない。表示は `TypeStore::display` と `EffectLabel::display` で、`eml_hir` の `DisplayNames` を引く。同じ名前の型やエフェクトを、名前を定義するモジュールが2つ以上あるときだけモジュール名で修飾して表示するためである。名前の表がモジュールの文脈によらないので、HIR の診断、型検査の診断、`dump`、`pretty` が同じ表を引ける

## `eml_core_ir`、`eml_lir`、`eml_vm` の内部

- Core IR の構成と translate、`optimize`、EP の規則は [Core IR](../spec/core-ir.md) が、2つの IR に共通する規則、LIR のパス、実行の意味、パスの境界の不変条件は [LIR](../spec/lir.md) が、バイトコードと VM は [VM](../spec/vm.md) が、物体の形とヒープと RC は [オブジェクトモデル](../spec/object-model.md) が定める。translate の組み立てと、継続と evidence の実行時の表し方は、下の「translate の組み立て」と「継続と evidence」に書く
- Core IR の関数 (`CoreFn`) と LIR の関数 (`LirFn`) は、前向きの辺だけを持つ基本ブロックの列 (`blocks`) である。2つの IR は別の型を持つ。Core IR の型は RC の命令、`box`、`unbox`、`tail` を持たず、LIR の型はエフェクトの命令と `mask` を持たない。命令ごとの表示、読み込み、検査、命令の列をたどる部分は IR ごとに書き、重なる部品 (共有する型、`syntax` のテキスト形式の部品、`check` の verifier の部品) は `eml_lir` から借りる。骨格を `Function<D: Dialect>` のように generic にすると、ジェネリクスとフックがすべてのパスと verifier に広がるので採らない。命令の位置はブロックの番号 (`BlockId`) と文の番号で表せるので、式のアリーナ、式ごとの ID、join point の索引は持たない。パスの間で古くなる情報 (生存集合など) も IR に書かず、要るパスがその場で求める
- パスの順番は、各crateの`pipeline.rs`だけが持つ。`eml_core_ir`の`pipeline.rs`はtranslateと最適化とevidence passing (`Pass::{Translate, Optimize, Evidence}`、`core_until`) と、LIRへのつなぎ (`lower`、`lower_until`) を持つ。`eml_lir`の`pipeline.rs`はboxの挿入、開くパス、縮約、借用のパス、Perceus、reuse (`Pass::{Boxing, Flatten, Contract, Borrow, Perceus, Reuse}`、`passes_until`) を持つ。verifierはデバッグビルドだけでかける。Core IRではtranslateと`optimize`の後に変換の段 (`verify_translated`)、EPの後にEPの段 (`verify_evidence`) を、LIRでは`passes_until`のエントリでエントリの段 (`verify_lowered`)、boxの挿入の後に範囲の段 (`verify_scopes`)、開くパスと縮約の後に開いた後の段 (`verify_flattened`)、借用のパスの後に借用の段 (`verify_borrowed`)、Perceusとreuseの後に所有の段 (`verify`) を通す。LIRの段は`eml_lir`の`verify.rs`の`Level` (`Lowered < Scopes < Flattened < Borrowed < Ownership`) で、境界の検査は範囲の段から走る。借用の段は、開いた後の段に貸された引数の静的な規則を足す段である。呼ばれる関数の引数と結果と`split`は、`verify_at`が関数ごとに1回作った表 (`FnSummary`) を引く。2つのverifierが共有する部品 (辺の検査と支配木、定義と範囲のR5とR6、R7とR8、`jump`と`return`と`switch`の頭の検査、呼び出しと`closure`の相手と引数の数、基本操作と`clause`の検査、プログラム全体の表の組み立て`with_tables`) は`eml_lir::check`にある
- box の挿入 (`eml_lir` の `boxing.rs`) は、`split` による一様化と変換を、プログラム全体に1回ずつ行う ([LIR](../spec/lir.md) の「box の挿入」)。関数の ABI は具体化した型と `split` だけで決まるので、関数の間の不動点は求めない。一様化 (`conform_split`) は `split` 以降の引数と `ret` を一様な Repr にし、`clause` の印の関数は `conform_clause` が操作の ABI に合わせる。変種 `<f>$uniform` の作成と、値の参照と末尾の振り替えの向け直しは `variants.rs` が行う ([LIR](../spec/lir.md) の「関数の ABI」)。変換 (`Converter`) は関数ごとにブロックを番号の順に見て、case のフィールドの受け直しを行き先のブロックの先頭から決めた所に置く。呼ぶ関数は変換の前に作ったシグネチャの表 (`Signature`) でだけ見る。覗き穴の表 (`unboxed_from`、`boxed_from`) は、パスが作った定義からだけ作る。`never` の操作の `clause` の束縛は、`Converter` と verifier が関数ごとに変数の番号の表で覚え、その使いを変換せず、互換の位置で比べない。末尾の位置の呼び出しは `tail_position_call` で形から決め、変種の作成と縮約が使う。EP は `eml_core_ir` の `tail.rs` にある Core IR の上の写しを使う ([LIR](../spec/lir.md) の「末尾の位置の呼び出し」)。生存解析も、`eml_lir` の `liveness.rs` と、EP のための `eml_core_ir` の `liveness.rs` の2つの写しがある。箱を要する Repr は `Repr::needs_box`、互換は `Repr::compatible` (構造体の形まで比べるときは `Structs::compatible`) で決め、box の挿入、縮約、verifier が同じ関数を使う。verifier の文言の箱を要するスカラーの部分は `check::boxed_scalars` が作る
- 借用のパス (`eml_lir`の`borrow.rs`) は、変数の根の表を関数ごとに1回作り、直接の呼び出しのグラフと末尾のグラフの強連結成分を、再帰を使わないTarjanのアルゴリズムで求める ([LIR](../spec/lir.md)の「借用の推論」)。成分の中では、印が変わった関数と、同じ成分の中のその呼び出し元だけを作業の列に戻す。写しは、どの関数も変える前に、元の関数と作ると決めた写しを順に見て決め、適応の前の元の関数から作る。`passes_until`は縮約とPerceusの間にこのパスをかける
- 開くパス (`eml_lir` の `flatten.rs`) は、構造体の変数を形の葉の順 (深さ優先) に葉の変数の並びに替える ([LIR](../spec/lir.md) の「開く」)。box の挿入が一様な位置との変換を構造体の変数のまま済ませた後に走るので、位置ごとの変換を決めない。葉の変数は元の名前に葉の番号を付けた名前 (`d.0`) を持つ。葉を置き換えるとタグの `switch` の scrutinee が定数になる形 (定数を引数にした構造体の `con` を分けるもの) は、合う行き先への `jump` に替え、届かなくなったブロックを落として番号を振り直す (`prune`)。verifier がタグの `switch` の scrutinee を変数に限るためである ([LIR](../spec/lir.md) の「構造の規則」の R8)
- 変換 (`translate/`) は、エントリと、ランタイムが名前で呼ぶ std の関数 (`eml_extern::RuntimeEntry`) から届く instance だけを変換する ([Core IR](../spec/core-ir.md) の「変換の規則」)。ブロックの組み立て (`FnBuilder`) は `translate/` の外の `src/builder.rs` にある。`instances.rs` は単相化の instance の表 (下の「translate の組み立て」)、`mod.rs` は式の値の渡し先 (行き先) と条件の分かれ方、`expr.rs` は式ごとの変換、`pattern.rs` は決定木と case-of-case、`program.rs` は関数の表と包む関数とデータの配置の表、`types.rs` は型から決まる Repr を持つ。`names.rs` は、instance の名前と生成する関数の名前に使う item の名前の表と型のハッシュを持ち、名前を型引数と item だけで決める。`derive.rs` は、導出した instance とタプルと `Unit` の instance の中心のメソッドを `FnBuilder` で組む ([Core IR](../spec/core-ir.md) の「導出とタプルの生成器」)。`display.rs` は、REPL の式の入力の値を書く表示関数を組み、値の形と値を分けて読む命令を `derive.rs` と共有する ([Core IR](../spec/core-ir.md) の「表示関数」)。handler の節の `k` は、節ごとに HIR で使い方を調べ、2つの形のどちらかに変換する。使用がすべて引数をそろえた直接の呼び出しか `drop k` なら、クロージャを作らず、呼び出しを生の継続への `Call::Resume` にする (直接の形)。`k` を関数の値として使うなら、節のエントリで生の継続を `$cont$` か `$cont$state` のクロージャに包んで `k` とし、呼び出しを `Call::Apply` にする (包む形)。`$cont$` と `$cont$state` は、使うときだけ1つずつ作る ([Core IR](../spec/core-ir.md))
- 最適化 (`optimize/`) は、`mod.rs` の `optimize` がエントリで、`specialize.rs` の作業リストが関数を1つずつ書き換える。`known.rs` は関数ごとの書き換え (既知の閉包への `apply` を直接の呼び出しにすること、包む関数の命令への戻し、既知の閉包を受ける呼び出しと捕獲を複製に向けること、使われなくなった `closure` の除去) を、`specialize.rs` は複製の鍵と名前と、translate の出力を凍らせた写しからの複製の組み立てを持つ。書き換えの後、`yields.rs` が `yields` の印を付け直す。続いて `handlers/` が本体の既知な `handle` を handler の複製の呼び出しに替え、`yields.rs` がもう一度印を付け直す。そのあと `fuse/` が融合の段を動かし、`yields.rs` が3回目の付け直しをする。`direct.rs` が値の参照の残らない持ち上げた関数と、`k` として渡す継続の関数 `f{H}$hN` の `split` を外してから ([Core IR](../spec/core-ir.md) の「直接だけ呼ばれる持ち上げた関数」)、`reach.rs` がエントリから届かない関数を落とす。`handlers/mod.rs` は対象の判断と複製の組み立てを、`handlers/piece.rs` は部品 (`perform` の地点で切って継続の関数を作ること、節の本体の展開と定数の `switch` の畳み込み、節の写し `<g>{k}` と、その継続についての複製) を持つ。`handlers/passing.rs` は、どの節もすぐに再開する handler の複製を、状態を変数で持ち回る1つの関数に写す部分を、`handlers/touch.rs` は、その経路に入れる関数を決める、handler に触れるかの判断を持つ。`fuse/mod.rs` は書き換える順と複製の輪の扱いを、`fuse/inline.rs` はインライン化を、`fuse/known_con.rs` は既知のコンストラクタと jump threading と、解いたフィールドの既知の閉包への `apply` の書き換えを、`fuse/copies.rs` は `con` の値の形についての複製を持つ。`blocks.rs` は、handler への特殊化と融合が共有するブロックの片付け (定数の `switch` の畳み込み、届かないブロックの除去、1本の `jump` だけが入るブロックのつなぎ) を持つ ([Core IR](../spec/core-ir.md) の「最適化」)
- EP (`evidence/`) は、`mod.rs` の `evidence` がエントリで、節ごとの in-place のエントリを作ってから、関数ごとに `handlers.rs` で handle、`perform`、`resume`、`mask` を基本操作と呼び出しに替え、`clause` の印のない `yields` の関数を `split.rs` で yield の地点ごとに継続の関数に分ける。IO の extern の呼び出しと `never` の操作の `clause` は yield の地点にしない ([Core IR](../spec/core-ir.md) の「yield の地点」)。本体が何かを呼ぶ in-place のエントリは、`handlers.rs` の `into_entry` が under の形にする ([Core IR](../spec/core-ir.md) の「`perform` と節の3つの形」)。継続の関数の変数の表は、その本体に現れる変数だけに詰める ([Core IR](../spec/core-ir.md) の「継続の関数」)。補助の関数 (`id$`、`compose$`、`prompt$`、`resume$`、`rewind$`、`mask$[…]`) の中身は `helpers.rs` が作り、`Helpers` が使うときに1つずつ足す。作る前の関数の数で対象を限り、EP が作った関数は書き換えない ([Core IR](../spec/core-ir.md) の「evidence passing」)。`evidence` は最後に、fork しうるプログラムに `forks.rs` で fork の関数 (`fork$E.op` と `reperform$E.op`) を足す ([Core IR](../spec/core-ir.md) の「`par` の子の中断」)。基本操作の表 (`Prim::row`) は `eml_lir` の `prim.rs` にある
- 既知の呼ばれる式への呼び出しは、種類 (`Callee`) ごとに、引数の数、足りないときの包む関数、ちょうどのときの命令だけを決める。足りない・ちょうど・余るの場合分けは `saturate` の1か所で行う
- 変数の Repr は `translate/program.rs` の `ProgramBuilder::repr` が決め (`FnLowering::type_repr` がこれを呼ぶ)、箱の位置の Repr は `types.rs` の `boxed_repr` が決める。extern の型の Repr は、`eml_extern` の型の行の `repr` を読む。`boxed_repr` は `eml_core_ir::boxed_repr` として公開し、extern の表との結び付けのテストが使う ([テスト戦略](testing.md))。`Repr` は extern の行も持つので、依存のない `eml_extern` に置き、`eml_lir` が再公開する。RC の対象 (`Repr::is_rc`) は `obj` と `tobj` である。extern の名前と実装の対応を置くのは `eml_extern` の表だけである。表の行がすべて `std/` にちょうど1回宣言されていることは、`eml_hir` の結合テストが確かめる。本体のある標準ライブラリの関数は表に持たず、普通の関数として変換する。extern の呼び出しは `Rhs::Extern` になり、引数の数は表の行の `params` の長さである
- データの配置の表 (`Program.layouts`) は、`translate/program.rs` の `ProgramBuilder` が組む。`con`、タグの `switch`、`unpack`、`release` を出す所で、コンストラクタか型から `data_layout` (data の型ごと) か `tuple_layout` (タプルの大きさごと) を引き、最初に引いたときに表に入れる。値の型からは引かない。フィールドの Repr はコンストラクタのスキームのフィールドの型から決め、配置の Repr は型の Repr と同じ `data_repr` で決める ([Core IR](../spec/core-ir.md) の「translate の配置」)
- レコードの作る式、射影、更新は `translate/expr.rs` が変換する。射影と更新は `unpack_fields` で値を `unpack` し、射影では取り出すフィールドの変数だけを式の型の Repr に、更新では残すフィールドの変数を `Update::fields` の型の Repr にする ([Core IR](../spec/core-ir.md) の「変換の規則」)。導出した `Show` の名前付きのフィールドの表示は `translate/derive.rs` の `show_record` が作る
- 変換は、渡されたエントリの関数を `()` で呼ぶ関数 `entry$<名前>` を足す。エントリの関数を引数で受け取るのは、REPL で `main` の代わりにその回の式から作った関数を渡せるようにするためである
- translate は、持ち上げた関数 (ラムダ、ローカル関数、handle の本体と節) と補助の関数 (`$op$`、`$con$`、`$externN`、`$cont$`、`$cont$state`) に内部の印 (`CoreFn::internal`) を付ける。トップレベルの関数、instance のメソッドと既定のメソッドの関数、生成した関数と `tag$`、エントリの関数には付けない。この印は関数の ABI を決めない。ABI は具体化した型と一様な位置の始まり (`CoreFn::split`) で決まる ([LIR](../spec/lir.md) の「関数の ABI」)
- translate は、関数に `yields` の印 (`CoreFn::yields`) を、`apply` に yield しうるかの印を、instance の row のビットで `RowYield` を解いて付ける ([Core IR](../spec/core-ir.md) の「`yields` の印」と「`apply` の印と分け方」)
- ローカル関数は、instance の本体を変換する前に、本体のローカル関数すべてを定義の順に予約してから変換する。自分と組の相手への参照と、後で変換する入れ子の関数からの参照のために、関数の番号と持ち上げの捕まえる変数の表が先に要るためである。表は `translate/mod.rs` の `lifted_functions` が `Body::local_groups` の順に組ごとに作る。再帰する組の関数は、組の関数の捕まえる変数の和から組の関数を除いたもの (変数の番号の順) を共通に持ち、再帰しない組の関数はそれぞれ自分の捕まえる変数を持つ。文の位置では何も出さない。参照は持ち上げた関数への直接呼び出しで、捕まえる変数は引数の前に渡す ([Core IR](../spec/core-ir.md) の「ローカル関数の持ち上げ」)
- 持ち上げた関数の名前は、ラムダが `外側の名前$lambdaN`、ローカル関数が `外側の名前$let$関数の名前` (同じ instance の中で名前が重なるときは、HIR の順で2つ目から `#2`、`#3`)、handle の本体と節が `外側の名前$handleN` (と `$操作名`、`$return`)、値として使う extern を包む関数が `外側の名前$externN`、コンストラクタと操作を包む関数が `$con$` と `$op$`、継続を包む関数が `$cont$` (状態のない handler 用) と `$cont$state` (状態のある handler 用) である。エントリ以外のモジュールの関数、`$con$` と `$op$` の後ろの名前、エフェクトの表の名前には、`モジュール名.` を付ける (`Report.Csv.parse`、`$con$Report.Csv.Row`)。ラムダ、handle、extern を包む関数は外側の名前を前に付けるので、同じく修飾される ([Core IR](../spec/core-ir.md))。型変数を持つ関数では、外側の名前は instance の名前 (`twice@[Int]`) なので、持ち上げた関数の名前も instance の名前を根にする (`twice@[Int]$lambda0`)。instance のメソッドの関数、既定のメソッドの関数、生成した関数、`tag$` の名前は、[Core IR](../spec/core-ir.md) の「メソッドの解決」にある。N は、本体を変換する前に HIR を1回たどって、式の ID の順に振る (`numbering`)。変換の順で番号が変わらないようにするためである。Core IR のエフェクトの番号は `eml_hir::Program::effects` の順から、extern のエフェクトを飛ばして数える。この数え方は `effect_index` と `effect_table` が同じ補助関数を使う。`IO` は Prelude の最初のエフェクトなので、表からだけ外すと、ユーザーのエフェクトの番号がすべて1つずれるためである
- extern を値として使うときは、参照する場所ごとに包む関数を作り、その `extern` 命令に参照した場所の位置を持たせる。extern ごとに1つの共有の包みにすると、実行時エラーが包む関数の中を指し、どこで使った extern かが分からなくなるためである
- `lower` と `core_until` は `SourceFiles` を受け取り、extern の呼び出しの位置 (`Loc`) を `SourceFiles::line_col` で行と列にする。`Program.files` には、位置に使った表示用のパスを使った順に入れる。`eml_core_ir` が `eml_diagnostics` に依存するのはこのためで、診断は出さない。`line_col` は、`SourceFiles::add` が作った行の先頭の表を二分探索し、その行の中だけ文字を数える
- 文と終端の値と行き先をたどる処理 (生存解析、Perceus、verifier、縮約、`pretty`、LIR への変換、VM のコード生成) は、`Stmt::for_each_atom`、`Term::successors` などの visitor を通すか、`..` を使わずに欄をすべて名前で受ける `match` で分解する。欄を IR に足したときに、たどる処理のすべてがコンパイルエラーになるようにするため
- アトムの使い方は「消費」と「読む」に分かれる ([LIR](../spec/lir.md)の「ブロックの列」)。`for_each_atom`は両方を返し、`Rhs::for_each_consumed`、`Stmt::for_each_consumed`、`Term::for_each_consumed`は消費だけを返す (`unpack`の値、`switch`のscrutinee、`unbox`のオペランド、`prim`とexternと直接の呼び出しと`jump`の借用の引数を除く)。`Rhs::for_each_lent`と`Stmt::for_each_lent`は借用の引数だけを返す。引数が借用かは、基本操作の表の`PrimRow::borrowed`とexternの表の`FunctionRow::borrowed`で、直接の呼び出しと`jump`では呼ばれる関数のエントリのブロックと行き先のブロックの`borrowed`で決まる。分類は、この文脈を具体的な構造体`Lends`で受ける。`Lends::new`が`Program::lends()`から作る。生存解析と縮約は前者を使い、Perceusは後者で所有を取る変数と`dup`の数を決める。Perceusとverifierは、この分類を共有する。verifierは、読む使いを`Unpack`、`Dup`、`Switch`、`Unbox`の腕と、`Prim`と`Extern`の腕の借用の引数で直接確かめる
- Perceus (`eml_lir` の `perceus.rs`) は、ブロックを番号の順に1回たどり、各ブロックで2つのループを回す ([LIR](../spec/lir.md) の「Perceus」)。命令が前からの状態 (所有と保持) に依るので、後ろからたどるループで各文で死ぬ変数と定義して後で使う変数を記録し (`deaths`)、前からたどるループで状態を持って命令を足す。文ごとに生存集合を写さないのは、長いブロックで時間が文の数と生存集合の大きさの積になるためである
  - 関数全体の表 (`Fields`) は、変数ごとの RC の対象かの印、親とスロット (`Parent`)、束縛の時点の持ち主を持つ。経路ごとの状態 (`State`) は、所有の集合と、持ち主ごとのそれに属する生きている変数 (`lent`) だけである。保持は「所有していて生きていないが、`lent` が空でない」ことから決まり、別には持たない
  - `switch` の行き先の状態 (`switch_entries`) は、`switch` のブロックを前からたどり終えた後に、行き先ごとに状態を写し、case のフィールドを借りた変数として加えて作る。行き先に着いたときに取り出す
  - 文の前の命令は `stmt` が、終端の前の命令は `term` が置く。どちらも、所有を取る変数を集めて `take` に渡し、その後に消費の数の `dup` を置く。`term` は、`return`、`tail`、`jump` の実引数と、`jump` の行き先で生きている借りた変数の所有を取り、保持している変数を手放す。`take` は、持ち主がその命令で必要なら `dup` し、そうでなければ `resolve` で持ち主を解く。`resolve` は、属する変数から親をたどって道と代表を決め、`release` を作業リストで親から子の順に置く。深い入れ子で Rust のスタックを使わないためである
  - タグの case を持つのに配置のない `switch` を見たら、その `switch` の所でパニックする (`a_tag_switch_without_a_layout_stops_perceus` が確かめる)
- reuse (`eml_lir` の `reuse.rs`) は、関数ごとに `Planner` がブロックを番号の順に1回たどって組を決め、`Plan::apply` がまとめて書き換える ([LIR](../spec/lir.md) の「reuse」)。道ごとの状態 (`Path`) は、構築子が分かっている変数と使える token の並びで、`switch` の行き先へ写し、合流するブロックでは構築子の事実を入る道の共通部分にし、token を空にする。たどり終えてから、どの道でも使わなかった元を元の文に戻し、一部の道でだけ使う token の `drop_token` を行き先のエントリに置く。yield しうる呼び出しは `may_yield` が決め、verifier も同じ関数で、yield しうる呼び出しの後に token が生きていないことを確かめる
- パス、verifier、`pretty`、`parse`、VM のコード生成は、ブロックと文の並びをループでたどり、IR の大きさに比例して再帰しない。生存解析は、ブロックを後ろからたどる1回のループで、ブロックごとのエントリの生存集合を側の表 (`liveness::live_in`) に返す。辺がすべて前向きなので、不動点の計算は要らない
- 縮約 (`eml_lir` の `contract.rs`) は、使われない純粋な `let` を消し、その後ですべてのブロックに末尾呼び出しの規則を当てるパスである。末尾呼び出しを作るのは縮約だけで、呼び出しの結果が関数の `ret` と互換なときだけ `tail` にする ([LIR](../spec/lir.md) の「末尾の位置の呼び出し」)。合流の畳み込み、値が分かっているコンストラクタへの `switch`、case-of-case、末尾呼び出しの書き換えは、translate が組み立てるときに行う。組み立てた後に別のパスで書き換えると、書き換えのたびに枝の部分木を置き換えるので、長い `else if` の連鎖で2乗の時間がかかるためである
- `eml_vm`は、コード生成 (`compile/`) と実行に分かれる。`compile/`では、`slots.rs`が文の単位の生存から干渉グラフを作ってスロットを塗り、`moves.rs`がブロック引数への並列な代入を`Move`の列に直し、`emit.rs`が関数ごとに命令を出し、`constants.rs`が定数を作業用のヒープに作って凍結する ([VM](../spec/vm.md)の「スロットの割り当て」と「`CodeBase`と`FnEntry`」)。実行は`vm.rs`の、命令を`match`で分ける1つのループである。関数の値の適用とクロージャは`apply.rs`、`CodeBase`と`FnEntry`と組み込みの命令 (`Finish`、`ApplyRest`、`par`の子の終わりの`ChildDone`。位置は`op.rs`の`FINISH`、`APPLY_REST`、`CHILD_DONE`) は`code.rs`、データの命令は`data.rs`にあり、基本操作の命令も`vm.rs`の`match`の腕で`Ctx`のメソッドを呼び、externの命令は`eml_rows::rows`の行の関数か`call`を呼ぶ。命令の型は`op.rs`、実行時エラーの型と表示の文言は`eml_sched`の`error.rs`、テストが使うHost (`CaptureHost`と、その出力を持つ`Capture`と`Written`) は`hosts.rs`にある。`eml run`とREPLのHost (`stdio_host`と`script_host`) は`eml_io`の`hosts.rs`にある。スケジュールの方針 (`Sched`、`Policy`、`Normal`、`Sequential`、`Seeded`) とタスクの表とjoinの節点を持つ`Scheduler`は`sched.rs`に、`Scheduler`が持つ監視のスレッドは`monitor.rs`に、監視のスレッドを起こす自己パイプ`Doorbell`は`eml_sched`の`doorbell.rs`に、runの表`Run` (workerごとの受け箱と実行待ちの列と待ち)、worker - `lib.rs`の`execute`は、`Seat::Separate`の`Machine`を作り、呼んだスレッドで読み込んで実行する。このスレッドはrunの間メインのworkerである。`run_scheduled`はrunの中でworker 0 (`eml-worker-0`、スタックは`WORKER_STACK`の8 MiB) を作る。worker 0はチャネルの門で待ち、呼んだスレッドは`eml_io::Masked`でSIGINTとSIGTERMを塞いでから門を開け、worker 0をjoinし終えるまで塞いだままにする。worker 0の本体 (`entry_body`。driver、`Scheduler::new`、`begin_run`、worker 1..N-1をまとめて作ること、`vm::run`、`END`、join、静止) は、合わせたrunでは呼んだスレッドでそのまま動く。`execute`を呼ぶスレッドはRustの既定のスタック (2 MiB) で足りる。LIRのパスとVMのコード生成はIRの大きさに応じて再帰しないためである。`eml.exe`はフロントエンドのために8 MiBを予約する (`crates/eml_cli/build.rs`の`/STACK`)。worker 1..N-1は、workerを作ってよいrunの始め、最初の命令の前に、worker 0の`entry_body`が`thread::scope`の中で`eml_io::spawn_scoped_masked`で一度に作り、runの終わりにjoinする。worker 1..N-1は監視のスレッドを持たず、`Ctx`を自分のスレッドで作ってrunの終わりにworker 0へ返す。I/Oのdriverは、本物の時計のrunでだけ、最初に要るときに自分のスレッドでrunの時間の基準から作る。メインのworkerも同じである。仮想の時計のrunではdriverはworker 0の1つだけで、どのworkerのタスクのI/Oもworker 0が受け付ける。`Async`のタスクは、`start`のときに`Run`の数`next_place`で置けるworkerをworker 1から順に回して置き、`Place`の知らせで運ぶ。置いたタスクはほかのworkerへ移らない。登録表`Registry`とmailを持つ`Shared`はrunに1つで、`Machine`を持つスレッドで`run_scheduled`が作り、すべての`Scheduler`に配る。分かれたrunでは、worker 0ができる前に作る。ハンドルを縛ったworkerと違うworkerのタスクのI/Oは、`Submit`、`CancelIo`、`Completion`の知らせでハンドルを縛ったworkerのdriverへ回す。本物のdriverの`accept`は受けたソケットを縛らずに`RawSocket`で返し、最初にそのストリームを使うタスクのworkerが`IoDriver::adopt`で自分のdriverに取り込む ([VM](../spec/vm.md)の「上限と割り込み」、「タスクとスケジュール」、「メインのworker」、「時計と driver」、「`Async`のタスク」)
- VM は状態を `Ctx` と `Task` だけに置き、Rust の再帰を使わない。呼び出しのスタックは `Task` のデータである ([マルチコア対応の設計](../future/multicore.md) の「VM の並列化の備え」の制約5)
- 位置を持つ `extern` 命令から作った命令にだけ、`Tables::locations` で源の位置 (`SourceLocation`) を付ける ([LIR](../spec/lir.md) の「実行時エラー」)
- `RunStats` の回数は、`Ctx` の `CtxStats` とヒープの `Stats` が検査モードで数える。`boxes`、`unboxes`、`reuses`、`unwound_frames` は VM が数え、`peak_stack` はタスクごとの深さの起点とスタックの長さの和の最大で、`Scheduler` が取る。`tasks`、`parks`、`timers`、`dropped_failures`、`cancels`、`channel_ops`、`channel_waits`、`channels_swept`、`completions` は登録表が数える ([VM](../spec/vm.md) の「`RunStats`」)

### translate の組み立て

- 本体を変換する前に、`translate/instances.rs` の `collect` が単相化の instance の表を作る。規則は [Core IR](../spec/core-ir.md) の「変換の規則」にある。番号と名前がすべて決まってから本体を変換するので、変換の途中で instance を足すことはない。手順は次のとおりである
  - 一様な位置は、型検査が計算した `TypedProgram::uniform` を読む (上の「`eml_types` の内部」)
  - 型検査の型の表 (`typed.types`) を複製して持ち、代入の結果をその複製に足す。`eml_core_ir::lower` は `&TypedProgram` を受けたままである
  - エントリの instance から FIFO で instance を集める。各 instance の本体の参照の型引数に instance の代入をかけ、一様な位置を `Flexible` にし、参照の `rows` を instance の row のビットで解いて、呼ぶ先の鍵を作る ([Core IR](../spec/core-ir.md) の「row のビットと instance の鍵」)。本体の中の定義された関数とメソッドへの参照ごとに、行き先 (`Target`) を記録する。メソッドの参照は、`eml_types::resolve` で instance を引き、instance のメソッドの関数、既定のメソッドの関数、`extern` の行、生成する関数 (`Generated`) のどれかを行き先にする ([Core IR](../spec/core-ir.md) の「メソッドの解決」)。生成する関数も同じ列で集め、それが呼ぶフィールドの型のメソッドの行き先 (`GeneratedInstance::calls`) も記録する。REPL の式の入力では、エントリの型から幅優先で表示関数 (`Found::Display`) も集め、型ごとの最小の段と部分の書き方 (`Part`) を記録する ([Core IR](../spec/core-ir.md) の「表示関数」)
  - 同じ代入で、宣言の型に代入をかけた型 (`Instance::signature`、引数と `ret` の Repr を決める) と、本体の型の表 (`exprs`、`locals`、`pats`、`instantiations` の型引数) に代入をかけた表 (`Instance::types`) を作る。`masks` は型を持たないので、そのまま写す。debug ビルドでは、代入をかけた表に型変数が残っていないことを確かめる。型変数を持たない関数の instance は、表を写さずに型検査の表を使う。その本体の型に残りうる型変数は節の `OpVar` だけで、`OpVar` の Repr は `Flexible` と同じ `tobj` だからである。参照の型引数には、鍵を作るために代入をかける
  - `order` が、instance を HIR の関数の順に並べ直し、名前を付ける
- `translate` は、`Instances::list` の順に関数の番号を予約し、instance の番号から関数の番号への表 (`indices`) を作る。本体の文脈 (`BodyCtx`) は、代入の結果を足した型の表 (`store`)、instance の本体の型の表 (`types`)、参照の行き先の instance の表 (`targets`)、`indices` を持つ。関数への参照の行き先は、`BodyCtx::target` が `targets` と `indices` で引く。持ち上げた関数の名前の根 (`root_name`) は instance の名前である。`BodyCtx` は `Copy` で、型の表を読むだけである
- 関数のブロックの列は、`builder.rs` の `FnBuilder` が前から組み立てる。`FnBuilder` は、文を足す (`emit`)、終端を置いてブロックを閉じる (`terminate`)、ラベルを作る (`new_label`)、開いたままのブロックに戻る (`reopen`) を持ち、終端のないブロックを複数開いたまま持てる。ブロックは作った順に番号が付く。`switch` の行き先は `switch` を置くときに作り、ラベルのブロックはそこへ向かう辺がすべて出そろってから作るので、作った順は前向きの辺だけになる。`finish` は、ブロックをたたんだ後に番号を詰める
- ラベルは、そこへ向かう開いたままのブロックの一覧を持つ。ラベルを持つ式を変換し終えたら、一覧の数で扱いを決める。0本なら本体を変換しない。1本ならそのブロックに戻り、本体をそこで変換する (引数は変数の対応で渡す)。2本以上なら、各ブロックを `jump` で閉じ、ラベルのブロックを置いて本体を変換する。前もってラベルの使用を数えないので、HIR を1回たどるだけで済む。`switch` の行き先が2本以上から入るラベルへ向かうときは、`jump` だけを持つ辺のブロックを挟む (R3)
- 式の値の渡し先 (行き先) は、`Return`、`Jump(ラベル)`、`Scrutinize(文脈)` の3つである。値の `if` と `match` は、続きをラベルにして `Jump` で変換する。`Scrutinize` は、値がそのまま `match` に入る行き先である。文脈 (`Ctx`) は、行 (パターン)、枝ごとのラベル、決まらない枝の終わりの一覧、枝の本体の行き先を持つ。条件は `Bool` の文脈 (`True` と `False` のラベル) の `Scrutinize` で変換するので、`&&`、`||`、入れ子の `if`、条件の位置の `match` は `Bool` の値を作らない
- 値は出現 (`Occ`) で表す。出現は、値のアトムか、タグと出現のフィールドを持つ既知のコンストラクタである。タプルはタグ 0 のコンストラクタである。出現は型も Repr も持たないが、`Occ::Con` は Kind の印を持つ。`let x = con ..` で束縛した変数は、`FnLowering.cons` が変数から引数への対応を覚える。変数は1回だけ定義され、定義は使う位置を支配するので、この対応はどこから引いても正しい。決定木で頭が既知の出現に当たれば、その場で case を選ぶ。ただし印が `unr` でない `con` の変数は、その変数が唯一の使用で、かつ決定が静的に決まるか、どの枝もその変数を受け取らないときだけ開く ([Core IR](../spec/core-ir.md) の「Kind の印」)。局所変数に束縛した `con` の変数が、参照のちょうど1つでない局所変数に入ったときは `FnLowering.shared` に覚え、決定木は開かない。値全体を束縛する枝では、その葉でだけ `con` を作る。使われない `con` は縮約が消す
- 出現が型を持たないので、Repr は出現の外から決める。既知のコンストラクタの出現を値にするときの Repr は、`ConValue` から決める。`Data` と `Tuple` は値の型を持ち、その型の Repr にする。構造体にする型なら構造体の Repr で、ほかは `obj` である ([Core IR](../spec/core-ir.md) の「構造体にする型」)。値の分からない枝の終わりをまとめるラベルの Repr は、調べる値から決める。`Scrutinee::Expr` なら式の型から、`Scrutinee::Occ` なら呼び出し側が渡した変数の Repr である。`unpack` と `switch` で作るフィールドの変数の Repr は、そのコンストラクタ (タプル) が最初に現れる行の引数のパターンの型 (`BodyTypes::pats`) から決める。型検査は入れ子を含むすべてのパターンに受けた値の型を記録し、case はどれかの行に現れるコンストラクタにだけ作るので、引数のパターンはいつもある。`con` で作った値 (`FnLowering.cons`) のフィールドは、`con` に渡したアトムをそのまま出現にする。`materialize_once` は同じ値を1回だけ作る。まとめるのは印が `unr` の出現に限り、`unr` でない出現は作った `con` の表に入れない。`unr` でない値を2か所で使うと Perceus が `dup` し、印の違う同じ形の出現を1つにすると、`unr` の出現が `lin` の `con` を使い回してその `con` に `dup` が要るためである。`unr` の出現は型を持たないので、型引数だけ違う同じ値も1回にまとめる。値は同じなので意味は変わらない
- 印は Repr と並べて運ぶ。`lower`、`lift`、`bind` は Repr と印の組と関数の戻り値の印を運び、`Scrutinee::Occ` は調べる値の Repr と印を持つ。型のある所は `mark(store, ty)` (`TypeStore::linearity`) で決め、宣言の型を代入せずに読む `$op$`、`$con$`、操作の表は `TypeStore::linearity_or_poly` で決める (`Rigid` と `Var` に依存する値は `poly`)。導出とタプルの生成器の変数は `unr` にする。決定木の葉は、`unr` でない値を分解して `unr` でない変数を何も束縛しないとき、`FnLowering.parents` (分解で得たフィールドから分解した値への表) をたどって根を決め、`drop` を出す ([Core IR](../spec/core-ir.md) の「決定木の葉の `drop`」)
- `match`、分解する `let`、分解する引数は、`decide` が決定木 (`Switch`、`Unpack`、`Leaf`) を作り、それを出してから、枝を枝の順に変換する。`Unpack` は値が `obj` か構造体の変数のときだけ使う。R7 がほかの Repr の `unpack` を拒み、R8 が、コンストラクタが1つの配置にだけ `unpack` を許すためである。フィールドを持つコンストラクタが1つの型の値は、いつも `obj` か構造体の変数である
- case-of-case: 枝の終わりの値で、決定木が未知の値を調べずに1つの枝に行き着けば、その枝のラベルへフィールドのアトムを引数にして `jump` し、コンストラクタを作らない。行き着かない枝の終わりは集めておき、scrutinee を変換し終えてから決める。0 個なら `switch` を出さない。1 個ならそのブロックで決定木を出す (タプルのリテラルも作らない)。2 個以上なら、各枝の終わりで値を作って1つの合流のブロックへ `jump` し、そこで決定木を出す。枝の本体は文脈の行き先で変換するので、入れ子の case-of-case もそのまま組み合わさる。呼び出しの結果と translate の後に現れる case-of-case は translate では扱わず、融合の既知のコンストラクタが扱う ([Core IR](../spec/core-ir.md) の「既知のコンストラクタ」)
- `finish` は、最後にブロックの形から `return` への転送を行い、構文の規則には頼らない。文がなく、`return p` だけを持ち、引数が `p` だけのブロックがあれば、そこへの `jump b(a)` をすべて `return a` にしてそのブロックを消す。番号の大きいブロックから処理するので、連鎖も1回でたたまれる。`finish` は末尾呼び出しを作らず、`let x = <呼び出し>` と `return x` を残す。末尾呼び出しは、box の挿入の後に縮約が作る

### 継続と evidence

- 関数の呼び出しの継続は、VM のタスクのスタックの枠の列で表す。枠は見出しに戻り先の命令の位置、結果を書くスロット、呼び出し元の枠の位置と大きさを持つ ([VM](../spec/vm.md) の「フレーム」)。いちばん下の枠はエントリの関数の結果を受け、その戻り先は `Finish` である
- エフェクトは EP が普通の呼び出しと基本操作に変えているので ([Core IR](../spec/core-ir.md) の「evidence passing」)、VM は handler を探さず、継続も切り出さない。エフェクトの継続 κ は EP が組み立てるクロージャで、`multi` の再開は共有されたクロージャへの `apply` として捕獲だけを写す。LIR は `handle`、`perform`、`resume`、`mask` を型に持たないので、VM に届くことはない
- 実行の文脈 (`evv` と yield の状態) は `eml_rt` の `Ctx` が持ち、基本操作は `Ctx` のメソッドである ([オブジェクトモデル](../spec/object-model.md) の「実行文脈 `Ctx`」)。借用の引数 (`PrimRow::borrowed`) は手放さず、ほかの引数は所有した参照として受け取り、結果に残さないものは手放す ([LIR](../spec/lir.md) の「基本操作」)
- `Call::Clause` は `Call::Apply` と同じく関数の値を適用する。ただし引数の数は、いつもエントリの関数の引数の数と等しい ([VM](../spec/vm.md) の「呼び出しと戻り」)
- EP が足す変数の印は `evidence/` が決める。EP が作るクロージャ (`f$kN`、作り直す `compose$`、`yielding_entry` の `g`) は `captured_mark` で捕まえた値の印の結びにし、補助の関数 (`helpers.rs`) の κ、状態、値は `poly`、evidence は `unr` にする。遅い道と `prompt$` の経路の `drop` は、結果の Repr が RC の対象で印が `unr` でないときだけ出す ([Core IR](../spec/core-ir.md) の「EP の明示の `drop`」)
- `prim dummy()` は、ヒープごとに1つ確保する不死の物体 (値 0 の `BigInt`) を指す語である。`dup`、`decref`、`drop` は何もせず、`unbox` は 0 を読む ([オブジェクトモデル](../spec/object-model.md) の「ダミーの値」)
- 正しく終わった実行では、`Ctx::check_finished` で `evv` が空で yield の状態がなしであることを確かめてから、検査モードのリークを数える。残った evidence がリークに見えないように、この検査はモードによらず行う
- `drop k` は、継続のクロージャを解放する。物体は捕まえた値だけを所有するので、子をたどる解放が、捕まっていた値を1回ずつ解放する。捕まっていた `FileIn` は `Foreign` の物体で、この解放で読み出す端が捨てられて閉じる ([オブジェクトモデル](../spec/object-model.md) の「読み手」)
- 中断 (`never` の操作、`try_io` が捕まえる IO の失敗、`exit`) は継続を組み立てず、VM がタスクのスタックを巻き戻す。外すフレームの値と生きている token は、コード生成が LIR の所有の走査 (`eml_lir::unwind::points`) から作った巻き戻しの表で手放し、着地の印 (`apply … prompt ev`) の evidence が宛先と同じフレームで止まる ([VM](../spec/vm.md) の「巻き戻し」)
- `extern` 命令は、フレームを積まずにその場で実行して値を返す。extern は eml のコードを呼び返さないので、継続を組み立てる必要がないためである。ただし、IO の extern が `try_io` の捕まえる種類の誤りで失敗すると、VM が最も近い `IO` の evidence (`Ctx::ev_find`) の `io_failed` の節のエントリを呼んで、失敗を届ける。エントリは中断を始め、巻き戻しが `try_io` の handle のフレームまでスタックを戻す
- `exit` は、`Ctx::exit_abort` で宛先を不死のダミーの物体にした中断を始め、`Finish` まで巻き戻す。途中のフレームが持っていた値は、巻き戻しの表で後始末される ([VM](../spec/vm.md) の「extern の中断」)

## `eml_io` の内部

- `eml_io` は `eml_rt` の `IoDriver` を実装する2つの driver を持つ。`real.rs` の `RealDriver` は本物の driver で、OS を呼ばない核 `driver::Driver` を OS ごとの backend `sys::Os` の上で動かす包みである。backend の時計は単調な時計 (`Instant`) で、driver は内部の刻みを持たない。`test.rs` の `TestDriver` はテストの driver で、仮想の時計、`test/net.rs` の仮想のネットワーク (メモリの上の端、リスナー、ポート)、seed で混ぜる決着の順、`submit` の中で終えた操作の数 (`immediate()`) を持つ ([VM](../spec/vm.md) の「時計と driver」)
- feature `tls` のときだけ組む `test/tls.rs` は、テストの driver の TLS の終端器である。`tls.localhost` と `tls-cut.localhost` への接続ごとに `eml_tls::Conn` のサーバーを1つ持ち、決着の始めに汲む。仮想のネットワークに足したのは、ポートを振った端の対を作る `Network::pair` だけで、端の表には `test` の子のモジュールとして触れる。`eml_io` の `src/` で `eml_tls` を参照するのはこのファイルだけである
- driverは`Word`、`Ctx`、RCに触れず、記憶には`RawBuf`を通してだけ届く。そのため`eml_io`は`eml_vm`を知らずに組み立てられる。どちらのdriverを使うかは`eml_sched`の`Clock`が決める
- `RealDriver::new` は `io::Result` を返す。`eml_vm` は driver を最初の run で作り、作れなければその run を `RunFault::Driver` で終える
- `RealDriver::new_at(epoch)` と `TestDriver::new_shared(seed, clock)` は、run の時間の基準を共有する driver を作る。`eml_vm` は本物の時計の run の worker 1..N-1 の driver を前者で作り、どの worker の driver も同じ時刻を読む。仮想の時計は run に1つの数を後者に渡す ([VM](../spec/vm.md) の「時計と driver」)
- 本物の driver の受けは、受けたソケットを登録せずに `Done::Accepted` の `RawSocket` で返し、`IoDriver::adopt` がソケットを自分の driver に取り込む。受けたストリームを、受けたリスナーと違う worker の driver に縛るためである。テストの driver の `adopt` は通常のファイルだけ取り込み、ソケットとパイプは断る。受けはいつも `Done::Stream` で終える ([VM](../spec/vm.md) の「時計と driver」)
- `RealDriver::with_lookup(lookup)` は、名前の解決の関数を差し替えた driver を作る。テストと組み込み先のためで、テストは機械の `/etc/hosts` に頼らない。`RealDriver::new` は `sys::lookup` (std の解決器) を使う
- driver は作ったスレッドの上でだけ使う。`eml_io` は driver の型に `unsafe impl Send` を書かない
- `hosts.rs`には、`eml run`とREPLが使うHostの`stdio_host`と`script_host`がある。どちらも標準出力と標準エラーに書く`eml_rt::StdHost`で、`StdHost::with_around_spawn`に渡すフックが、子を作る間だけ`Unmasked`でシグナルの塞ぎを外す。`CaptureHost`などの出力を捕まえるテスト用の道具は`eml_vm`に残る
- `mask.rs`の`spawn_masked`と`spawn_scoped_masked`は、unixで新しいスレッドの本体の始めでSIGINTとSIGTERMを塞ぎ、呼んだスレッドの塞ぎには触れない。`eml_vm`の監視のスレッドと`CaptureHost`の読むスレッド、本物のdriverのプールと解決のスレッドがこれで始まる。`eml_vm::execute`を呼んだスレッド (`Machine`を持つスレッド) は、worker 0が最初の命令を動かす前からjoinし終えるまで`Masked`で塞ぐ。`Unmasked`は、塞いだスレッドが子を1つ作る間 (`eml_io`の`hosts.rs`の`StdHost::with_around_spawn`に渡すフックと、`eml_vm`の`hosts.rs`の`CaptureHost::spawn`) 2つの塞ぎを外す。Appleでは、塞いだ後に自分のスレッドの保留に残った2つのシグナルを`sigwait`で取り、`kill`で送り直す ([VM](../spec/vm.md)の「上限と割り込み」)
- 本物の driver のモジュール
  - `driver/mod.rs` は核である。保留の操作の表 (呼ぶ側が振った `OpKey` で引き、作り直さずに使い回す)、届いた完了、ハンドルの表 (向きごとの保留の印と閉じた印)、札から鍵への表、プール、解決器、`HandleBin`、壊れた印を持つ。続き (短い書きの残り、`ConnectionAborted` の受けの出し直し、接続の次の番地、解決の答えからの接続) を出すのは核だけで、どれも同じ `OpKey` の下で次の歩として出す。受けたソケットはハンドルの表に入れずに `Done::Accepted` で返し、`adopt` が backend に登録させてから表に入れる。ハンドルは種類 (`Class`) を持ち、ソケットは全部の操作を、パイプは読みと書きだけを受ける。通常のファイルの読み書きは backend に出さず、プールの仕事 (`Kind::FileRead`、`Kind::FileWrite`) にする。子の終わりの待ち (`Op::Wait`) はハンドルを持たない操作の記録で、backend が登録する。`wait`、`quiesce`、`Drop` は1回分の待ち `turn` を共有し、`turn` は受け箱の答えと backend の event が名指した欄にだけ触れる。表を歩くのは `quiesce` と `Drop` だけである。`completions` は届いた完了を移すだけである
  - `driver/backend.rs` は、核と backend の境界の trait `Backend` と、その型 (`Step`、`Outcome`、`Hold`、`Start`、`Cancel`、`Arrival`、`Event`) を持つ。backend は OS の資源と時計とスレッドの作り方を持ち、`start` 1回で歩の1回の試みだけを OS に出す。受けの歩は、受けたソケットを登録せずに `RawSocket` で返し、`Backend::adopt` がほかの backend の受けたソケットも含めて登録する。`Hold::Memory` は OS が完了まで書きうる記憶があることを表し、核は driver を落とすときだけ読む。readiness の backend は `Retry`、`Pending(Hold::None)`、`Cancel::Done` だけを使い、完了型の backend はすべての値を使う。`wait` は event を積んだ後に `Err` を返さない
  - `driver/inbox.rs` は、プールと解決のスレッドの答えを積む受け箱である。答えは driver の中で使い回さない札 (`Ticket`) を持ち、スレッドは積んでから waker を鳴らす。核は札で欄を引き、外した札の答えは捨てる
  - `driver/pool.rs`はブロックする呼び出しのプールで、`Op::Job`のためにある。stdのスレッドを`Backend::spawn`で32本 (`POOL_LIMIT`) まで作り、満ちたら仕事は列で待つ。列はファイルの仕事と`Op::Job`の2つで、同時に走る`Op::Job`は24 (`JOB_LIMIT`) までに抑え、空いたスレッドはファイルの仕事を先に取る。仕事は`catch_unwind`の下で走り、空いたスレッドは10秒で抜ける。`Op::Job`を出すのはVMの`blocking`のCの関数の呼び出しで、仕事は箱のRustの値を`Done::Job`で返す。静止は`Op::Job`を渡された予算まで待ち、残りを見捨てる。見捨てた仕事は`pending()`に数えず、戻るかdriverを落とすまでスレッドを1本持つ。ファイルの仕事は`Std.Stream`の読み書きの仕事である。この仕事は貸した記憶をプールのスレッドで使うので、`Drop for Driver`は走っているファイルの仕事が終わるまで待つ (`lends_memory`。[VM](../spec/vm.md)の「時計と driver」)
  - `driver/resolve.rs` は名前の解決器で、切り離せるスレッド (`eml-resolve`、スタック 256 KiB) を `Backend::spawn` で作る。手放していない解決は同時に8本 (`RESOLVE_LIMIT`) まで走り、残りは受け付けの順に待つ。取り消した解決のスレッドは手放して別に数え、まだ戻らないものが64本 (`ABANDONED_LIMIT`) たまっている間は、新しい解決をその場で誤りにする
  - `driver/tests/` は、核の単体テスト (`mod.rs`)、偽の backend (`fake.rs`)、abort の子プロセスのテスト (`abort.rs`) を持つ。核のテストは Miri でも流す ([テスト](testing.md) の「核の Miri」)
  - `sys/mod.rs` は、OS ごとの `type Os` (Linux は `unix::Unix<epoll::Epoll>`、Apple は `unix::Unix<kqueue::Kqueue>`、Windows は `iocp::Iocp`。ほかの OS は `compile_error!`)、待ちの長さをミリ秒に切り上げる `millis`、OS の解決器 `lookup` を持つ
  - `sys/unix.rs` は、epoll と kqueue に共通の backend `Unix<P: Poller>` である。fd ごとの行の表 (読める印とその新しさ、向きごとの待ち手1つ、接続中の印、世代) と、各歩と、ソケットとパイプの作り方を持つ。パイプは親の端だけを `O_NONBLOCK` にし、`read` と `write` で進める。OS に渡す識別子は行番号と世代から1か所で作り、`wait` は世代の合わない event を捨てる。ソケットは作るか `adopt` で取り込んだ後に1回だけ edge で登録し、`close` まで登録を変えない。受けただけのソケットは登録しない
  - `sys/epoll.rs` と `sys/kqueue.rs` は `Poller` の実装で、登録と待ちと起こしだけを持つ。起こしは、Linux では level で登録した eventfd、Apple では `EVFILT_USER` である。子の終わりの待ちは、Linux では pidfd を epoll に、Apple では `EVFILT_PROC` を kqueue に登録して知らせを受け、子はまだ回収しない (`waitid` の `WNOWAIT` で、登録の前にすでに終わった子も拾う)。回収は Host が行う
  - `sys/iocp.rs` は Windows の backend である。`Sock` はソケットとアドレスの族、パイプの端、ディスクのファイルのハンドルのどれかを持つ。パイプは親の端を overlapped の名前付きパイプ (`CreateNamedPipeW`) に、子の端を継承させない同期のハンドル (`CreateFileW`) にし、`ReadFile` と `WriteFile` をソケットと同じ箱で出す。子の終わりの待ちは `RegisterWaitForSingleObject` で登録し、callback は鍵を列に積んでポートを起こすだけにする。登録の文脈とプロセスのハンドルの写しは、`UnregisterWaitEx` が戻った後でだけ放す。ディスクのファイルは `GetFileType` で通常のファイルだけを通す。行の表は持たず、OS が持つ箱を2つの表に置く。番地で引く `boxes` は、知らせの箱を取り戻す前に番地を確かめるためにあり、鍵で引く `waiters` は、鍵しか受け取らない `cancel` のためにある。Winsock はプロセスごとに1回だけ始め、`AcceptEx` と `ConnectEx` は `WSAIoctl` で得る。操作ごとの `OVERLAPPED` の箱は backend が持ち、OS に渡してから知らせを読むまでは所有を OS に預ける。`into_raw` と `from_raw` を書くのはこのファイルだけである。箱を放すのは、知らせを読んだときと、呼び出しが同期に失敗したときだけで、取り消しも `close` も箱に触れない。`AcceptEx` の受けのソケットは箱の中にあり、成功の知らせでだけ箱を出る。受けたソケットはポートに結び付けずに返し、`adopt` が結び付ける。箱が残ったまま backend が落ちるときは、プロセスを止める
- `unsafe` は `mask.rs`、`test.rs`、`sys/unix.rs`、`sys/epoll.rs`、`sys/kqueue.rs`、`sys/iocp.rs`、`driver/tests/fake.rs` にだけ置き、`trust.rs` のテストが一覧を固定する ([テスト](testing.md) の「`unsafe` の一覧」)。核と `real.rs` は OS を名指さず、`RawBuf` の番地は backend の OS を呼ぶ関数の中でだけ読み、slice を作らない
- 壊れる条件と壊れた後の振る舞い、`quiesce`、driver を落とすときの規則は [VM](../spec/vm.md) の「時計と driver」にある
- 起こしが長い待ちを終わらせることは、結合テストが遠い期限と期限 `u64::MAX` の `wait` で確かめる
- 結合テストは `tests/main.rs` が1つのバイナリ `integration` にまとめる。本物の driver の時計、期限までの待ち、別のスレッドからの起こしの後も待ちが動くこと、プールの仕事とその上限、unix でプールのスレッドが SIGINT と SIGTERM を塞ぐこと、仕事が走る driver を落としても仕事を待たないこと、落とした後の起こしと、待つ前の起こしが次の待ちだけを終えること、ループバックの TCP の上の読めるまでの待ち、読み、書き、取り消し、EOF、`quiesce` と、待ち受け、受け、接続、拒まれた接続、閉じた相手への書き、`shutdown_write`、長い書きの出し直しとその取り消し、1つのストリームで待つ読みと待つ書きが両方終わること、溜まった接続の受け、受けたソケットを別のスレッドの driver が取り込んで読み書きすることと取り込まずに落とすと閉じること、リセットで終わる待つ書き、unix でシグナルに割り込まれた待ち、名前の解決とその2つの上限と、テストの driver の性質 (時計は終わる操作がないときだけ進むこと、seed が決着の組の中身を変えないこと、`HandleBin` を先に空にすること、閉じた相手への書きが `BrokenPipe` になること、まだ終わっていない操作の取り消しが次の決着で `cancelled` で終わり、すでに終わった操作は取り消しても結果のまま渡すこと、仮想のネットワークのポートの振り方と backlog と EOF、OS のソケットを取り込まないこと) を確かめる。`tests/tls.rs` は `tls` のときだけ組み、Rust の `eml_tls::Conn` のクライアントで終端器の handshake、平文の受け渡し、close_notify とその省略、半分の閉じ、証明書の拒否、閉じる順ごとの EOF とポートの解放を確かめる。`tests/tls_off.rs` は `tls` を外したときだけ組み、TLS の名前が `NotFound` で終わることを確かめる ([テスト](testing.md) の「feature の組み合わせの確認」)

## `eml_tls` の内部

- `Conn`はrustlsの接続 (`rustls::Connection`) と、復号した平文の列を持ち、I/Oを持たない。暗号文は呼ぶ側が`push_tls`で渡し、`pull_tls`で受け取る。相手のEOFは`push_eof`で知らせる。providerは接続ごとに`builder_with_provider`でaws-lc-rsのものを渡し、`install_default`は呼ばない。プロセスの全体で共有する状態を持たず、検証器は`Trust`ごとに、`ClientConfig`は接続ごとに作る。そのため、LinuxではOSの検証器が`Trust`を作るたびに根のファイルを読み直す。接続ごとに`ClientConfig`を持つので、ある接続がほかの接続のsessionを再開することはない
- `Conn::client(&Name, &Trust)`はクライアントの接続を作り、I/Oをしない。`Name::parse`は、SNIと証明書の名前の照合に使うサーバーの名前を確かめる (`Error::ServerName`)。`Trust`はサーバーの証明書を確かめる方法を決める。複製は安く、別のスレッドに送れるので、`Conn::client`と分けて、ブロックしてよい所で作れる。`Trust::platform(extra_ca_pem)`はrustls-platform-verifierのOSの検証器を使い、OSの根に加えてPEMのCAを信頼する。`Trust::platform_at`は同じことを与えた時刻で行い、OSの検証器のテストのためにある。`Trust::fixtures(ca_pem)`は、PEMのCAだけを根にしたrustlsのWebPKIの検証器を、`fixtures::NOW`の時刻で使う。VMがこれを使うのは、`Machine`が自分で作ったテストのdriverのrunだけである ([VM](../spec/vm.md) の「時計と driver」)。受ける版はTLS 1.2と1.3である
- 足すCAのPEMは検証器を作る前に確かめるので、`Error::CaPem`はどのOSでも同じになる。PEMが読めないとき、証明書を根に足せないとき、空でない入力から証明書が1つも出てこないときは`Error::CaPem`である。CAを渡さないときは、OSの検証器を作るのに失敗すると、理由によらずどのOSでも`Error::NoRoots`になる。よくあるのは、根のファイルのないLinuxである。CAを渡したときは、検証器を作るときの証明書の誤りは`Error::CaPem`、ほかの失敗は`Error::Config`になる。空のPEMの`Trust::fixtures`は`Error::NoRoots`である
- どちらの検証器も`Opaque`で包む。`Opaque`は証明書の誤り (`InvalidCertificate`) をそのまま通し、rustlsが理由に合ったalertを送れるようにする。ほかの検証器の誤りはすべて理由のない拒否に変え、OSの文言を文言に届かせない。代わりに診断が損をする。検証の中でOSの側が失敗したとき (Windowsの証明書のエンジンの誤りなど) も拒まれた証明書と同じに見え、文言は理由を言わない
- 作るときに `set_buffer_limit(None)` を呼び、送る側の buffer の上限を外す。上限があると、`write_plain` が平文の一部しか受け取らないことがある。受けた平文の buffer にはこの呼び出しと別の上限 (16 KiB) があり、満ちると `read_tls` が失敗する。そこで `push_tls` は `process_new_packets` を呼ぶたびに、rustls の平文を自分の列へすべて移す。移す前に読み終えた部分を詰めるが、`plaintext()` が返すバイトの並びは変わらないので、その中の位置は `push_tls` の呼び出しをまたいでも同じバイトを指す。`consume` で列が空になったら `Vec` を手放す
- `status()` は次の5つの印の和を返す
  - `HANDSHAKING` (1): rustls の `is_handshaking()` が真である
  - `HAS_OUTGOING` (2): rustls の `wants_write()` が真で、`pull_tls` で出すバイトがある
  - `PEER_CLOSED` (4): 相手の close_notify を処理した
  - `TRUNCATED` (8): `push_eof` を受け、close_notify はまだ受けていない。handshake の途中の EOF もこれになる
  - `FAILED` (16): 失敗を記録した
- 失敗は最初の1つだけを記録し、その後の `push_tls` は何も読まず、`write_plain` は平文を捨てる。同じ `push_tls` の中で失敗の前に復号できた平文は列に残す。それを捨てるかどうかは呼ぶ側が決める。失敗の後も rustls が積んだ alert は `pull_tls` で取り出せるので、呼ぶ側は相手に失敗を伝えてから閉じられる。close_notify を受けた後も `push_tls` は何も読まず、その後ろのレコードは捨てる
- 文言は固定である。作るときの誤り (`Error`) はそれぞれ1つの文言を持つ。証明書の拒否 (rustls の `InvalidCertificate`) は理由によらず `the server certificate was rejected` とし、rustls の詳細を付けない。ほかの TLS の誤りと `read_tls` の誤りは rustls の文言をそのまま使う
- `send_close_notify` は rustls のものを呼ぶだけで、2度目は何もしない。致命的な alert を送った後も何もしない。close_notify を送った後の `write_plain` も、rustls は止めずにレコードを作る。そのため、呼ぶ側がソケットの送る向きを閉じた後に書くと、そのレコードはソケットまで届いてそこで失敗する。close_notify を送った後に相手の壊れたレコードが届くと、rustls は致命的な alert を積む前の `debug_assert!` で panic する。そこで workspace の `Cargo.toml` は dev の profile で rustls の debug assertions を切り、release と同じく `FAILED` になるようにしている
- `Conn::server`は、テストのdriverの終端器とテストのためだけにある。`fixtures`は、テストのCA`ca.pem`と、leafの`cert.pem`とその鍵 (有効期間は2026-01-01〜2026-02-01) と、拒否を期待するテストのための、何にも署名していない2つ目のCA`other-ca.pem`を持つ。handshakeの成功を期待するテストは`fixtures::NOW` (2026-01-15T00:00:00Z) の時刻で確かめるので、結果は日付に左右されない。現実の時刻では、証明書は期限切れである。作り直すには`fixtures/gen.sh`を流す。`fixtures`の鍵は公開されたテスト用の定数で、何も認証しない
- `examples/https_server.rs`は`bench/scripts.sh`の行`https-get`の相手である。`Conn`を使わず、rustlsの`StreamOwned`でブロックするソケットに書く。計測の相手はI/Oを持たない形である必要がないためである。`https_server CERT_PEM_PATH KEY_PEM_PATH MIB`で呼び、証明書と鍵は`bench/scripts.sh`がrunのたびに作るPEMのファイルから読む。`fixtures`は使わない。動き方は [計測の基準](benchmarks.md) の「スクリプトの計測」にある

## `eml_native` の内部

- `abi.rs`は、emlのコード、adapter、補助の関数、thunkのCraneliftのフラグを作る唯一の関数`isa`、emlの関数の`tail`のシグネチャ、記述子から作るエントリのシグネチャ、importを宣言する関数`declare_import` (エントリ、Cの関数、ハンドルのdtor) と、`isa(false)`のISAと`JIT_REGION_BYTES`の予約した領域からJITのmoduleのbuilderを作る関数`jit_builder`を持つ ([ネイティブの実行系](../spec/native.md) の「`eml_enter`」)。`thunk.rs`は、`eml_enter`が呼ぶthunkを作る。どちらも`cranelift_module::Module`について総称で、`JITModule`を名指すのは`jit.rs`だけである。ABIのテストが結合テストなので、この2つは`pub`である
- `mem.rs`は`eml_rt`を名指す唯一のmoduleで、`REUSE_SCANNED_LIMIT`が`layout::INLINE_SCAN_LIMIT`以下であることをコンパイル時のassertで確かめる。メモリに触るコード生成はここに置く
- `jit.rs`は、JITのホスト`NativeMachine`と`execute`を持つ。マシンは、JITのmodule 1つとその領域、`Image`の表、thunkを持ち、プログラムを1回だけ読み込んで`eml_nrt::run::run`で走らせる ([ネイティブの実行系](../spec/native.md)の「関数の形」「実行の始めと終わり」)
- `lower/`は、LIRをCLIFに下ろす。`mod.rs`はどの関数を定義するよりも前にすべての関数を宣言し、`names.rs`は記号の名前を作り、`function.rs`はLIRの関数1つ (ブロック、ブロックの引数、文、終端、atom) を下ろす。`call.rs`は直接の呼び出しと末尾呼び出しを、`unwind.rs`は巻き戻しの地点の後のコード、後始末、`eml$raise`を、`safepoint.rs`は入口の安全点を、`rc.rs`はインラインの`dup`と`decref`を、`data.rs`は構築子、欄、`switch`、箱、`release`、token、reuseを、`consts.rs`は読み込み時の値のデータの記号を下ろす。`apply.rs`は関数の値を下ろす。適用する所、`closure`、クロージャのエントリ`c<k>:<f>`、`n < m`の腕でスタックの上限を確かめる`apply`の補助の関数`eml$apply$m`、PAPのアダプタ`eml$pap$<r>`である ([ネイティブの実行系](../spec/native.md)の「関数の値」)。`rows.rs`は、ネイティブのコードがインラインに展開するstdの行 (`INLINE`) を挙げ、`lowering`は規則で、行をインラインに展開するか、エントリで呼ぶか、断るか (`None`) を返す
- `unsupported.rs`は、ネイティブのコードが断るLIRの形を述べる唯一の所である (`Form`、`unsupported`)。診断、ネイティブのUIテスト、下ろしは、どれもこれを使う ([ネイティブの実行系](../spec/native.md)の「断る形」)
- コード生成器は、次の置き場所の規則を守る。`tests/placement.rs`が、規則ごとにソースのファイルを走査して確かめる
  - importを宣言する (`Linkage::Import`) のも、`tail`の呼び出し規約を名指す (`CallConv::Tail`) のも、`preserve_frame_pointers`を置くのも、`abi.rs`だけである。Craneliftのフラグを作る (`settings::builder`) のは、`abi.rs`だけである
  - 生成したコードは、`mem.rs`を通してだけメモリをロードしストアする (狭い幅の形、アトミック、スタックの枠への読み書きを含む)。ほかにロードとストアを書くのは、`thunk.rs` (`eml_enter`の引数と結果の配列) だけである
  - `call_indirect`は、呼ぶ先が実行時の値である所、つまり`lower/apply.rs` (関数の値の適用)、`thunk.rs`だけで使う
  - `CTX_*`のずれを定めない。`mem.rs`を通して`eml_rt`から読む。`eml_rt::Ctx`、`eml_rt::Heap`、`Ctx<…>`の型も、`Checked`も名指さない
  - `eml_sched`と`eml_rows`への辺を持たない。実行の境界の型には`eml_nrt`の再エクスポートを通して届き、テストは共有の行の関数をdev-dependencyの`eml_rows`から読む。thread-localは使わない
  - `eml_native`、`eml_nrt`、`eml_sched`、`eml_rows`、`eml_clink`のファイル (コード、コメント、マニフェスト) が引く`docs/`の文書は、`docs/spec/`と`docs/implementation/`の下だけである
- `unsafe`を書いてよいのは`jit.rs`だけである ([テスト戦略](testing.md)の「`eml_native` の検証」)

## `eml_clink`の内部

- `bridge.rs` の `Bridges` は、`CSignature` ごとの橋渡しの関数を cranelift-jit で作り、署名で引く表に持つ。ISA は `cranelift_native` で動いている機械に合わせ、`opt_level=speed`、`is_pic=false` にする。`JITModule` は空でない最初の要求で作るので、C の関数のないプログラムは JIT の費用を払わない。1回の `get` は、まだない署名をまとめて定義し、`finalize_definitions` を1回だけ呼ぶ。`free_memory` は呼ばず、`JITModule` も落とさない。`Bridges` を落とすときは、module をプロセス全体の表 `RETIRED` に移す。cranelift-jit が module を落とすときにコードを解放するかどうかに頼らず、`Linker` を落としても作ったコードがプロセスの間ずっと残るようにするためである。`ManuallyDrop` で手放さず表に残すのは、届かなくなった確保を LeakSanitizer が漏れとして報告するためである。1回の `get` の定義か finalize が失敗したら、その module を `RETIRED` に移し、次の要求で新しい module を作る。途中まで定義した関数が次の finalize に混ざらないためで、前に作った橋渡しのコードは残る。橋渡しの CLIF の形は [VM](../spec/vm.md) の「橋渡しの関数」にある
- `library.rs` は、名前の飾り (`candidates`)、動いている OS (`running_os`)、開いたライブラリの表 `Libraries` を持つ。`Libraries` は、`link` から開いたライブラリを最初の候補の道で引く表と、プロセスの範囲のライブラリを持つ。どれも最初に使うときに開き、`ManuallyDrop<libloading::Library>` で持って閉じない
- `linker.rs` の `Linker` は、`--link` の上書き、登録した記号、`Libraries`、`Bridges` を持つ。`link` は、関数とハンドルの dtor の記号をすべて解決してから、関数の `c_signature()` について `Bridges::get` を1回呼び、入力に並びをそろえた `Linked` を返す。解決の順は [VM](../spec/vm.md) の「ライブラリと記号」にある。`Linker` は `Send` で、`Sync` は要らない。`with_symbols` は `unsafe` で、登録するアドレスの署名と寿命は呼び手が約束する。`--link` で同じ KEY を2回以上渡すと、後のものが効く
- `error.rs` の `LinkError` は、`Library`、`Symbol`、`UnknownOverride`、`Unsupported` の4つの変種を持ち、文言は固定である
- trait はない。呼び手はプログラムを持ってから読み込む前につなぎ、結果の `Linked` の値を渡す。VM の側に linker も、それを作る関数も置かない
- `signature.rs`の`c_signature`は、`CSignature`から、Cの型どおりの型を持つ素の`AbiParam`の署名を作る。`I32`にも拡張の印を付けない。`bridge.rs`はこの署名で呼び、`eml_native`はCの関数のimportの宣言に使う
- `bridge.rs`は自分のCraneliftのフラグを持つ。Cの橋渡しの関数は既定の呼び出し規約だけを使い、フレームポインタもstack probeも要らないためである。コード生成器 (`eml_native`) のフラグは作らず、`abi.rs`の`isa`も使わない
- `unsafe`を書いてよいのは`bridge.rs`、`library.rs`、`linker.rs`だけである ([テスト戦略](testing.md)の「`eml_native` の検証」)

## `eml_nrt`の内部

- `lib.rs`は`#![deny(unsafe_code)]`を持ち、ほかのmoduleの公開の項目を再エクスポートする。エントリの表の一覧`TABLES`と、それをたどる`entries()`もここにある。`eml_rt`を隠した名前`__rt`で再エクスポートし、ほかのcrateで展開した`entries!`がそれを名指す。実行の境界の型`RunConfig`、`Finished`、`RuntimeError`、`RunFault`、`HostRef`も再エクスポートする。`eml_native`はこれらを`eml_nrt`を通して名指し、`eml_sched`への辺を持たない
- `entries.rs`は、`Kind`、`Entry`と、マクロ`entries!`とその補助 (`__entry!`、`__kind!`、`__ty!`、`__result!`) を持つ。`shim`の本体の規則を書くのは`__entry!`だけである ([ネイティブの実行系](../spec/native.md) の「包みの本体」)
- `enter.rs`は、`Thunk`、`Fatal`、致命的な誤りの符号 (`FATAL_PANICKED`、`FATAL_FAULT`、`FATAL_RECORDED`)、`Raise`とその3つの実装、`enter`、`detached`と、エントリ`eml_fatal`を持つ
- `rows.rs`は、一覧`extern_rows!`の展開`entries`で、接頭辞`eml_x_`の行のエントリの表`ROWS`を作る。表は組`rows`の変種ごとのエントリと、手で書く`Exit`と`Panic`を持つ ([ネイティブの実行系](../spec/native.md)の「externの失敗」)
- `services.rs`はサービス`eml_nrt_failed`と`eml_nrt_safepoint` (表`SERVICES`) を、`heap.rs`はヒープのエントリ (表`HEAP`) を、`closures.rs`はPAPの鎖を作るエントリ`eml_nrt_pap` (表`CLOSURES`) を、`c.rs`は利用者のCの関数の呼び出しの補助`eml_x_c_*` (表`C`) を持つ ([ネイティブの実行系](../spec/native.md)の「ヒープのエントリ」「externの失敗」「安全点」「関数の値」)
- `image.rs`は`Image`とその行の型、`Start`、`Options`、`Census`、行動の語を持つ。`run.rs`は実行の駆動`run`と、スタックの形の3つの定数を持つ。`worker.rs`はworkerの構造体と`record`、`park_panic`を、`census.rs`はcensusを、`constants.rs`は読み込み時の値を凍結した塊に作る関数を持つ ([ネイティブの実行系](../spec/native.md)の「`Image`」「実行の始めと終わり」)
- `arch/`は、ISAとABIごとのstub (`eml_enter`、longjmpの側、`JmpBuf`、`SUPPORTED`) を持ち、`arch/mod.rs`が対象ごとに1つを選ぶ。`aarch64.rs`はWindowsでないaarch64のAAPCS64、`x86_64_sysv.rs`はWindowsでないx86_64のSysV、`x86_64_win64.rs`はWindowsのx86_64のWin64で、`unsupported.rs`はほかのすべての対象である。stubは`#[unsafe(naked)]`の関数と`naked_asm!`で書き、外のアセンブラもbuild scriptも使わない
- thread-localは使わない。ネイティブのコードは`Ctx<Fast>`だけを使うので、`Checked`も名指さない
- `eml_fatal`を呼ぶのは、`entries.rs`の`shim`の規則と`enter.rs`だけである。`stack_limit`を書くのは`run.rs`だけで、スレッドの始めに1回だけ書く。`CTX_*`のずれは定めない。`crates/eml_native/tests/placement.rs`が、これらの規則を`eml_native`の規則と一緒に確かめる
- `examples/nrt_bench.rs`は、stubの往復と2つのエントリの形の費用を測る ([計測の基準](benchmarks.md) の「命令の数の測り方」)
- `unsafe`を書いてよいのは、`trust.rs`が挙げるファイル (`enter.rs`、`entries.rs`、`image.rs`、`worker.rs`、`run.rs`、`census.rs`、`constants.rs`、`services.rs`、`heap.rs`、`rows.rs`、`closures.rs`、`c.rs`、`arch/`のstubのファイル) だけである ([テスト戦略](testing.md)の「`eml_nrt`の検証」)

## `eml_gui`の内部

- `Widgets`と`EventLoop`は、`Send`でない2つのtraitである。`Widgets`はネイティブのウィジェットを作り、変え、測り、置き、表示し、壊す。`EventLoop`はネイティブのイベントループを回す。`Backend::create`は、この2つをtraitのオブジェクトとして持つ`Native`と、2つが共有する`EventQueue`を返す。呼び分けを動的にするのは、stubとネイティブのbackendを1つのバイナリに同居させ、backendを実行のときに選ぶためである
- ウィジェットは`Id` (`(window_no << 32) | seq`) で名指す。ウィンドウの番号は`Toolkit::new`に渡した番号の次から始まる。GUIの`Park`は回収した`Toolkit`の`last_window()`を次の`Toolkit`に渡すので、番号はrunを通して1から数え、seqの0はウィンドウ自身である。どちらも使い回さないので、閉じたウィジェットの`Id`は`UnknownId`で失敗し、壊したウィジェットのイベントは`Toolkit::poll`が捨てる
- `Toolkit`は、ウィジェットの表と、作りかけの入れ物の積み重ねを持つただの値である。ウィジェットは一番内側の開いた入れ物の中に作る。開いた入れ物がなければ、作るのは`NoContainer`で、`end`は`NothingOpen`で失敗する。`set`は値をすぐにネイティブのウィジェットに渡す。`Text`はWindow、Label、Button、TextField、CheckBoxに、`Value`はProgressBar (0..=100に収める。作るときの値も同じ) とChoice (項目の数より小さい番号で、ほかは`OutOfRange`) に、`Checked`はCheckBoxに、`Enabled`はWindow、Grid、Label以外のすべての種類に効き、ほかの組み合わせは`WrongKind`である
- 配置 (`layout.rs`) は、自動で並べるTaffyの格子である。ウィンドウ自体が外側の格子`[Fr 1]`になり、余白12を置いてウィンドウいっぱいに広がる。`begin_grid`は、列と行のテンプレートをtrackから作り、暗黙の行を`auto`、間隔を8とする格子を作る。子は、直前の`next_cell`が決めた升目 (spanと揃え方) を、なければ`Cell::default()`を取る。升目は作るのに失敗しても使い切り、`end`、`begin_window`、`close_window`は升目を捨てる。ウィンドウはTaffyの木を`flush`をまたいで持ち続ける。葉の大きさは、Taffyのmeasure関数を通して`Widgets::measure`から得る。ウィジェットごとに問い合わせをキーとして最大8つの測った大きさを覚え、`Text`、`add_item`、`Invalidate`がそれを消す。Taffyのmin-contentの問い合わせは`AtMost(0.0)`として聞く。新しいウィンドウは中身のmax-contentの大きさで表示する。ネイティブの最小の幅はmin-contentの幅、最小の高さはその幅での高さとするが、自然な高さは超えない。折り返すラベルは幅が狭いほど高くなるからである。最小の大きさは後から変えない。配置を計算するのは、`flush`で変わったウィンドウについてと、`Toolkit::settle`で`Resized` (新しい大きさで) と`Invalidate` (今の大きさで) についてだけである。丸めた位置と大きさが変わった子だけを置き直す。数値はすべて論理pxである
- ネイティブのcallbackは`EventQueue`に積むだけで、`Widgets::set`と`Widgets::add_item`はイベントを出さない。`take_control`は制御のイベント (`QuitRequested`、`Resized`、`Invalidate`) を取り出し、ユーザーのイベントは列に残す。`pop_user`を呼ぶのは`Toolkit::poll`だけである。`Toolkit`がないときに積まれたユーザーのイベントは捨てる。1つの列に同時に付く`Toolkit`は1つだけで、2つ目を付けるとpanicする。`request_close_all`は、OSの終了の操作を、`close_window`で閉じていないウィンドウごとに1つの`CloseRequest`に変える。閉じる要求だけではウィンドウは閉じない
- stub (`stub.rs`) は画面を開かない。呼び出しを1つずつ1行にして、スレッドごとの記録 (`stub::take_transcript`) に書く。行は`create Button #1:3 in #1:1 "-"`、`set #1:2 Text("1")`、`place #1:2 (0, 0) 54x24`、`show_window #1:0 78x80 min 78x80`のような形である。ウィジェットは幅`7 * 文字数 + 16`、高さ24と測る (Choiceは一番長い項目で、ProgressBarは0文字とする)。ループは、それより前に起こしが鳴っていても、まず`step(Woken)`を呼ぶ。`Continue`のたびに、筋書きの次のイベントを積んで`step(Events)`を呼び、これは起こしと期限より先である。初めから空の筋書きでは、`Continue`のたびに、まだ閉じる要求を送っていない表示中のウィンドウごとに1つの`CloseRequest`を送る。それ以外では起こしか期限を待ち、何もないまま5秒たつと`stub: nothing woke the loop for 5 s`で失敗する。I/Oの源を渡されると、stubは源を見ないが、1回の待ちを10 msまでにし、起こしなしに終わった待ちのたびに`step(Io)`を呼ぶ。5秒は、最後の起こし、筋書きのイベント、期限からの時間で数え、`step(Io)`では数え直さないので、源があっても止まったループは失敗する
- 筋書き (`Script::parse`) は1行に1つのイベントを書く。`click W:S`、`text W:S <行の残り>` (末尾の空白も含めてそのまま値にする)、`toggle W:S true|false`、`select W:S <整数>`、`close W:S`、`quit`である。空の行と`#`で始まる行は飛ばす
- `Backend::Native`は、feature `native`のmacOSではAppKitのbackend (`appkit/`) を、LinuxではQt 6のbackend (`qt/`) を、WindowsではWinUI 3のbackend (`winui/`) を作り、ほかのビルドでは`NotAvailable("cannot open the GUI: built without the native toolkit")`で失敗する。作るのは、runが初めてGUIを求めた`Park::wait`の中だけである ([VM](../spec/vm.md)の「GUIのPark」)。それまでtoolkitには触れないので、GUIを使わないプログラムはnativeのbackendを選んだ`eml run`でもNSApplicationもQApplicationも作らず、Windows App SDKのruntimeも読み込まない。どのbackendもメインのスレッドでしか作らず、ほかのスレッドでは`NotAvailable("cannot open the GUI: AppKit needs the main thread")`、`NotAvailable("cannot open the GUI: Qt needs the main thread")`、`NotAvailable("cannot open the GUI: the GUI opens only on the main thread")`で失敗し、そのときもtoolkitに触れない。`eml run`ではMachineのスレッドがプロセスのメインのスレッドである。WinUIが求めるのはシングルスレッドのアパートメントだけで、Windowsでメインのスレッドに限るのはemlの決まりである。テストの中でruntimeを読み込まず、ウィンドウを開かないためにある。メインのスレッドかどうかの決め方はbackendごとに違う。AppKitはOSに問い (`MainThreadMarker`)、Qtはスレッドのidをプロセスのidと比べるので、どちらも何が始めたかによらずプロセスの最初のスレッドで開く。Cの`main`を持つAOTのバイナリでも、Machineを埋め込んで最初のスレッドから呼ぶhostでも開ける。WinUIだけは、Rustのruntimeが`main`と名づけたスレッドかどうかで決める。そのためWindowsでは、GUIのスレッドがRustの`main`でないhost (Machineを埋め込むhostや、Cの`main`を持つ将来のAOTのバイナリ) では開けない。native-aotの段は、Windowsでこれを見直す必要がある。Linuxで`DISPLAY`も`WAYLAND_DISPLAY`もないときは、QApplicationを作る前に`Backend("cannot open the GUI: no display (DISPLAY and WAYLAND_DISPLAY are unset)")`で失敗する。画面のないQApplicationはプロセスを止めてしまうからである
- AppKitのbackendの部品は、Windowが`NSWindow` (閉じても解放しない。閉じるアニメーションは切る。既定のアニメーションでは、runが続く間、閉じたウィンドウが画面に残った) と上を原点にする中身の`NSView` (`isFlipped`がYES)、Gridが同じ`NSView`、Labelが折り返す`NSTextField`のラベル (選べない)、Buttonが`NSButton`、TextFieldが`NSTextField`、CheckBoxがスイッチの`NSButton`、Choiceが`NSPopUpButton`、ProgressBarが0..100の棒の`NSProgressIndicator`である。Choiceの項目はメニューに直接足す。`addItemWithTitle:`は同じ名前の項目を消して末尾に足すので、番号がずれるからである。`NSProgressIndicator`は使えない状態を持たないので、ProgressBarの`Enabled`は何もしない
- callbackはウィジェットごとの`Target` (コントロールのtargetか、TextFieldのdelegate) とウィンドウごとの`WindowWatcher`が受け、`EventQueue`に積むだけである。AppKitはtargetとdelegateを弱く持つので、backendが持つ。ボタンの`click:`は`Click`、スイッチの`toggle:`は`Toggle`、ポップアップの`select:`は`Select`、TextFieldの`controlTextDidChange:`は打つたびの`Text`になる。値を変える`set`はこれらを出さない。`windowShouldClose:`は`CloseRequest`を積んでNOを返し、ウィンドウを閉じるのはプログラムだけにする。`windowDidResize:`は中身の`NSView`の大きさで`Resized`を積む。アプリケーションのdelegateの`applicationShouldTerminate:`は`QuitRequested`を積んで`TerminateCancel`を返すので、ループが自分で終わることはない。⌘Qが効くように、メニューのバーにはQuitだけのアプリケーションのメニューを置く。activation policyは作るときに`Prohibited`にし、`set_presence`が`Regular`にして前に出すか、`Prohibited`に戻す。Dockのアイコンは`Ui`が開いている間だけ出る
- AppKitのbackendは`fittingSize`で測る。これはフレームの大きさ (枠の飾りを含む) で、`place`もフレームを置くので、両者は同じ大きさを指す。ラベルは`preferredMaxLayoutWidth`に幅の上限を入れて測る。上限は`Exact`か`AtMost`の幅で、上限なしは0 (1行) である。min-contentの問い合わせ (`AtMost(0.0)`) では、画面に出さないラベルで測った一番長い語の幅で折り返す。AppKitは編集する欄と進み具合の棒に自然な幅を与えない (`fittingSize`の幅が0になる) ので、TextFieldとProgressBarの自然な幅は160とする。`Exact`の軸は与えた値を返す
- AppKitのループは`NSApplication::run`で回り、`step`をrun loopの源から呼ぶ。源はどれもcommon modesに置くので、ウィンドウの大きさを変える間も`step`は進む。起こしは`CFRunLoopSource`で、どのスレッドからでも`CFRunLoopSourceSignal`と`CFRunLoopWakeUp`で鳴らせ、`step(Woken)`になる。最初の`step(Woken)`は、`run`の前にこの源を鳴らして呼ぶ。I/Oの源のfdは`CFFileDescriptor`で待ち (fdはdriverのものなので、無効にするときに閉じさせない)、読めるたびに`step(Io)`を呼んで、1回ごとに切れるcallbackをまた有効にする。`Continue`の期限は、繰り返しの`CFRunLoopTimer`の次の発火の時刻として置き、`step(Timeout)`になる。callbackが積んだイベントは、run loopが眠る前の`CFRunLoopObserver`が拾い、前の`step`の後に積まれたもの (`EventQueue::take_pushed`) があれば`step(Events)`を呼ぶ。callbackは積むだけで、`step`を呼ばない。`step`の最中に来た源は覚えておき、`step`が戻ってから呼ぶ。`Stop`では`NSApplication::stop`を呼び、`stop`は次のイベントの後に効くので、何もしないアプリケーション定義のイベントを1つ送る。`run`が戻ったら源を外して無効にする。`step`のpanicは捕まえてループを止め、`run`が戻ってから投げ直す
- QtのbackendはC++のshim (`qt/shim.cpp`) で、Rustからはcxxの橋 (`qt/mod.rs`) を通して呼ぶ。`build.rs`は、feature `native`のLinuxのビルドでだけこれを組む。Qtはqt-build-utilsで探し (`QMAKE`のqmake、なければ`PATH`の`qmake6`か`qmake`)、Qt 5なら`eml_gui needs Qt 6 (found Qt {v})`でpanicし、Qt Core、Qt Gui、Qt Widgetsに動的にリンクする。Windowはトップレベルの`QWidget`、Gridはただの`QWidget`、Labelは平文を折り返す`QLabel`、Buttonは`QPushButton`、TextFieldは`QLineEdit`、CheckBoxは`QCheckBox`、Choiceは`QComboBox`、ProgressBarは0..100の`QProgressBar`である。子はQtのレイアウトを使わず、`setGeometry`で親の中に置く。ButtonとCheckBoxの文字の`&`は、Qtがニーモニックの印として読むので重ねる。shimはウィジェットを`Id`をキーとする表に`QPointer`で持つので、ウィンドウを壊すと、その子の項目も空になる
- Qtのcallbackは`EventQueue`に積むだけである。ボタンの`clicked`は`Click`、行の欄の`textEdited` (`setText`では出ず、打つたびに出る) は`Text`、チェックボックスの`clicked`は`Toggle`、コンボボックスの`activated`は`Select`になる。`set`と`add_item`はウィジェットのシグナルを塞ぐ。ウィンドウの`closeEvent`はイベントを無視して`CloseRequest`を積み、`resizeEvent`は`Resized`を積み、字体かスタイルが変わるとウィンドウの`Invalidate`を積む。`setQuitOnLastWindowClosed(false)`なので、最後のウィンドウが閉じてもループは終わらない。Linuxにはアプリケーション全体の終了の操作がない。デスクトップがアプリケーションを終わらせるときはウィンドウを1つずつ閉じるので、ウィンドウごとに1つの`CloseRequest`になる。`set_presence`は何もしない。QApplicationの構築は`setlocale(LC_ALL, "")`でプロセスのCのロケールをシステムのものに替えるので、shimは構築の前のロケールを覚え、構築の直後に戻す。ただし`LC_CTYPE`はQtが選んだもの (UTF-8) を残す。QtはUTF-8のロケールを前提とし、UTF-8でなければ自分で`C.UTF-8`に切り替えるからである。替えてから戻すまでの間にほかのスレッドがロケールを読むと競合になるが、これはQtの構築が起こすもので、emlからは避けられない
- Qtのbackendは`sizeHint`と`minimumSizeHint`で測る。min-contentの問い合わせ (`AtMost(0.0)`) の幅は`minimumSizeHint`、`AtMost`の上限の下の幅は上限と`minimumSizeHint`の間に収めた`sizeHint`、上限なしの幅は`sizeHint`である。折り返すラベルは、まず並べる幅を決め、高さはその幅での`heightForWidth`とする。幅は1行の幅 (`AtMost`の上限に収める) で、min-contentの問い合わせでは一番長い語の幅 (`minimumSizeHint`) である。折り返す`QLabel`の`sizeHint`は縦横の比で選んだ幅なので、1行の幅は画面に出さない折り返さないラベルで測る。`Exact`の軸は与えた値を返す。`place`は端を丸めるので、隣り合う升目の間に隙間も重なりもできない
- Qtのループは`WaitForMoreEvents`で`QCoreApplication::processEvents`を呼び、それが戻った後に自分で`step`を呼ぶ。Qtのcallbackの中からは呼ばない。起こしは印を立て、メインのスレッドの`QAbstractEventDispatcher`の`wakeUp`を呼ぶ。`wakeUp`はどのスレッドから呼んでもよい。QApplicationを壊す前に、起こしからdispatcherを外す。I/Oの源のfdは`QSocketNotifier`で、`Continue`の期限は1回だけの`QTimer` (`PreciseTimer`で、ミリ秒に切り上げる) で待ち、どちらも印を立てるだけである。待ちの後、ループは立ったすべての印について1回の`step`を呼ぶ。理由は`Woken`、`Events` (前の`step`の後に積まれたものがある。`EventQueue::take_pushed`)、`Io`、`Timeout`の順で最初のものとする。`step`はVMを1回動かし、それがすべてを見るからである。`step`自身がイベントを積んだときは、次の`processEvents`は待たないので、そのイベントは関係のない起こしを待たない。I/Oの見張りと時計は、`step`のpanicも含め、`run_loop`のどの出口でも外す
- WinUIのbackend (`winui/`) は、emlのbinding `winui/bindings.rs`を通してWinUI 3を呼ぶ。bindingは、windows-bindgenが`--minimal --flat`で、Windows App SDK 2.6.4のメタデータ (`Microsoft.UI.winmd`と`Microsoft.UI.Xaml.winmd`) とwindows-bindgenが持つWindowsのメタデータから、backendが使うAPI (`nix/winui-bindings/filter.txt`) に絞って生成する。メタデータは、microsoft/windows-rs (MIT OR Apache-2.0) がNuGetのパッケージから写して`crates/tools/reactor-metadata/winmd`に置いたものである。そこにあるMicrosoft自身のWinUI 3のprojectionであるwindows-reactorは、これから生成したbindingを同じライセンスで公開している。NuGetのパッケージのライセンスは、アプリケーションを作るための利用を認め、メタデータにも生成したprojectionにも触れないので、emlはMicrosoft自身のやり方に従う。emlがコミットするのは生成したbindingだけで、`.winmd`はコミットせず、ビルドにも配布にもWindows App SDKのファイルは要らない。bindingは`nix/winui-bindings.sh`が作り直す。2つのファイルを固定したwindows-rsのコミットから取り、ファイルごとのSHA-256を確かめ、workspaceの外のcrate `nix/winui-bindings/`でwindows-bindgenを走らせるので、emlのどのcrateもwindows-bindgenに依存しない。ネットワークが要るのでCIでは走らせず、filterかメタデータの版を変えたときに手で走らせ、コミットしたファイルを`--check`で確かめる。ウィンドウのHWNDを渡す`IWindowNative`はメタデータになく、backendが`windows_core::interface`で宣言する
- backendを作るとき、まず`RtlGetVersion`でOSのビルドの番号を読み、22000 (Windows 11) より小さければ`NotAvailable("cannot open the GUI: WinUI needs Windows 11 or later")`で失敗する。そのWindowsのkernelbaseは動的な依存の関数を持たないからである。Windows 11では、bootstrap (`winui/bootstrap.rs`) が`TryCreatePackageDependency`と`AddPackageDependency`を、importせずに、どのプロセスも読み込んでいるkernelbaseから引く。importすると、GUIを使わないときもWindows 10で`eml`が起動できなくなるからである。この2つで、利用者が入れたWindows App SDK 2のruntimeのframeworkのパッケージ (family `Microsoft.WindowsAppRuntime.2_8wekyb3d8bbwe`、最小の版2.6.4.0) をプロセスに加える。最小の版はメタデータの版なので、bindingのAPIはどれもruntimeにある。runtimeのDLLを名前で読み込むことはない。加えるのはプロセスで1度で、依存はプロセスの終わりまで外さない。加えられない (runtimeがない) と、作るのは`NotAvailable("cannot open the GUI: the Windows App SDK 2 runtime is not installed (https://learn.microsoft.com/windows/apps/windows-app-sdk/downloads)")`で失敗する。加えた後、スレッドのWindows Runtimeをシングルスレッドのアパートメントで始める。Windowは中身が`Canvas`の`Window`、Gridは`Canvas`、Labelは語の間でだけ折り返す`TextBlock`、Buttonは`Button`、TextFieldは`TextBox`、CheckBoxは`CheckBox`、Choiceは項目が`ComboBoxItem`の`ComboBox`、ProgressBarは0..100の`ProgressBar`である。子は親の`Canvas`の中に、`Canvas.Left`、`Canvas.Top`、`Width`、`Height`で置く
- WinRTの委譲はCOMのオブジェクトで、WinUIはウィジェットがなくなった後も持ちうる。そこでWinUIのcallbackはウィジェットの`Id`だけを持ち、メインのスレッドのスレッドローカルを通して`EventQueue`に積み、積むことだけをする。積んだcallbackは、まだ予約がなければ、`step(Events)`を呼ぶ仕事を`DispatcherQueue`に1つ予約する。callbackが自分で`step`を呼ぶことはない。ボタンの`Click`は`Click`、チェックボックスの`Click` (プログラムが`IsChecked`を変えても出ない) は`Toggle`、テキストボックスの`TextChanged`は`Text`、コンボボックスの`SelectionChanged`は`Select`になる。WinUIは、プログラムが値を変えたときも`TextChanged`と`SelectionChanged`を出し、`TextChanged`は後から出す。callbackは出した時の値でなく今の値を読むので、1回の変更に何回出るかは決まらない。そこでbackendはウィジェットごとに、最後に知らせたか`set`が置いた値を覚え、今の値がそれと違うときだけ、その値を覚えてイベントを積む。これで`set`の知らせも、同じ変更の2度目の知らせも捨てる。ユーザーの変更は値を今の値と違うものにするので、ユーザーの変更は失われない。`AppWindow.Closing`は`Cancel`を立てて`CloseRequest`を積み、ウィンドウの`SizeChanged`は`Resized`を積み、中身のテーマが変わると`Invalidate`を積む。Windowsにはアプリケーション全体の終了の操作がない。タスクバーの「すべてのウィンドウを閉じる」はウィンドウを1つずつ閉じるので、ウィンドウごとに1つの`CloseRequest`になる。`set_presence`は何もしない
- WinUIのbackendは`Measure`と`DesiredSize`で測る。単位のeffective pixelは論理pxである。測る間は`place`が置いた`Width`と`Height`を外す。外さないと、それがそのまま求める大きさになるからである。折り返すラベルは、まず並べる幅を決め、高さはその幅で求める高さとする。幅は、`Exact`なら与えた幅、`AtMost`なら上限の下で求める幅、上限なしなら1行の幅で、min-contentの問い合わせ (`AtMost(0.0)`) では一番長い語の幅である。語の幅は、画面に出さない`TextBlock`で1語ずつ測る。WinUIはTextFieldとProgressBarに中身によらない自然な幅を与えないので、その自然な幅は160以上とする。ほかのウィジェットは自然な大きさである。`Exact`の軸は与えた値を返す。`AppWindow`の大きさは物理的なpxなので、`show_window`でだけウィンドウのDPI (`GetDpiForWindow`) の倍率を掛ける。最小の大きさは、枠を含むウィンドウ全体の大きさとして`OverlappedPresenter`で置く
- WinUIのループは`Application::Start`で、`Exit`まで戻らない。その`OnLaunched`が、`XamlControlsResources`をアプリケーションの資源に加え、メインのスレッドの`DispatcherQueue`を取り、1回だけ鳴る`DispatcherQueueTimer`を作って、最初の`step(Woken)`を呼ぶ。アプリケーションの`DispatcherShutdownMode`は`OnExplicitShutdown`なので、最後のウィンドウを閉じてもループは終わらない。起こしはどのスレッドからでも鳴らせ、印を立てて`TryEnqueue`で`step(Woken)`の仕事を1つ積む。積んだ仕事がまだ走っていなければ、重ねて積まない。`Continue`の期限は時計の間隔 (100 nsの刻みに切り上げる) で、`step(Timeout)`になる。I/Oの源はなく、メインのworkerのdriverに出した操作がある間は、VMが1回の待ちを10 msまでにする ([VM](../spec/vm.md)の「メインのworkerの待ち」)。`step`の最中に来た理由は覚えておき、`step`が戻ってから呼ぶ。`Stop`では`Application::Exit`を呼ぶ。`step`のpanicは捕まえてループを止め、`Start`が戻ってから投げ直す。ループが終わった後は、XAMLの核が止まっているので、WinUIの呼び出しをしない。時計は止めず、callbackの登録は外す呼び出しをせずに忘れ (`EventRevoker::forget`)、ウィンドウを閉じずに、オブジェクトの参照を手放すだけにする。`Application`の子のクラスとXAMLの型の情報の渡し方は、winio (MIT) の`winio-ui-winui`に倣った
- 単体テストは`src/`にあり、結合テストはない

## ソースファイルと位置

- `FileId` と `SourceFiles` (`FileId` → パスとテキスト) は `eml_diagnostics` に置く。`SourceFiles` には読み込みの段が読んだすべてのファイルが入る。`FileId` はモジュールの番号と同じ順である
- `TextRange` は `text-size` crate を直接使う (`rowan` が再公開しているものと同じ型)。`eml_diagnostics` は `rowan` に依存しない
- `SourceFiles::add` は、テキストの先頭の BOM を取り除いてから保存する ([字句](../spec/lexical.md))。lexer、レイアウト段、表示は BOM を扱わない
- インクリメンタル化 ([ロードマップ](../future/roadmap.md) の「処理系」) では、`SourceFiles` を salsa の入力に置き換え、必要なら別の crate に切り出す

## CLI と lib API

- 引数の解析は `clap` (derive) を使う
- `eml FILE ARGS...`は`eml run FILE ARGS...`と同じである。`run`のファイルより後ろの引数は、`-`で始まるものも含めてclapに読ませず、`split_script_args`で切り離してスクリプトに渡す ([標準ライブラリ](../spec/stdlib.md) の「起動」)。ファイルは、値を取るフラグの値でない、`-`で始まらない最初の引数である。値を取るフラグの集まりは、`<Cli as clap::CommandFactory>::command()`の`run`の定義から読む。フラグを足しても分け方を直さずに済むためである。引数は`Env.args`で読め、`eml_io`の`script_host` (`eml_cli`が再公開する) が標準入力と一緒にHostに持たせる
- `eml check <file>` は、診断を stderr に表示する。`eml run <file>` は、診断 (警告を含む) を先に stderr に表示し、エラーがなければ実行する。警告がプログラムの出力の後に出ないようにするため
- `eml run` は VM の速いモードで実行し、`eml run --debug-heap` は検査モードで実行する。検査モードは、RC のリーク、解放済みの物体の使用、`lin` の物体の `dup` などを見つける ([オブジェクトモデル](../spec/object-model.md) の「報告する誤り」)
- `eml run --stats`も検査モードで実行し、実行時エラーで終わらなかったrunの後に、標準エラーに`stats: <欄>=<値> ...`の1行を出す。欄は`RunStats::fields()`が宣言の順に返す名前そのままである。`Finished::preemptions`は出さない。`eml run`はいつも`Normal`で動き、その数はいつも0だからである。検査モードのrunなので、そのrunの時間は物差しに使えない。REPLには足さない
- `eml run` は、ファイルを読む前に Ctrl-C と `Terminate` のシグナル (SIGTERM と、Windows のコンソールを閉じることとシャットダウン) のハンドラを入れ、`default_limits()` の上限で実行する ([VM](../spec/vm.md) の「上限と割り込み」)
- 終了コードは、0 = 成功、1 = 診断のエラーあり、または実行時エラー、2 = 使い方の誤り (引数の誤り、エントリのファイルが読めない)、130 = 割り込みで止まった、143 = `Terminate` のシグナルで止まった、とする。2 は、clap が引数の誤りで返す値に合わせた。130 と 143 は、シェルが SIGINT と SIGTERM で終わった子に報告する値と同じである。import したモジュールが見つからないことは診断 (E1026) なので 1 である
- `eml run --link KEY=VALUE` と `eml repl --link KEY=VALUE` は、`link` の item のライブラリを上書きする ([標準ライブラリ](../spec/stdlib.md) の「起動」)。`eml run` はコンパイルの後、`Compiled::link_keys` にない KEY を断り、`eml_clink::Linker` でつないでから `execute` を呼ぶ。つなぐ失敗は `link error: {e}` を標準エラーに書いて終了コード 1 にする。`eml check` は `Linker` を作らない ([VM](../spec/vm.md) の「`--link`」)
- `eml run --gui <native|stub>` (と環境変数`EML_GUI`。なければ`native`) は`Std.Gui`のbackendを選ぶ。`eml_cli`のfeature `gui`があれば、`eml run`は`gui_park(backend, interrupt)`を`RunConfig::with_main_park`で置く。`interrupt`は`Control::interrupt`を呼んで`Doorbell`を鳴らすので、ウィンドウが開いていないときのOSの終了の操作はCtrl-Cと同じ割り込みになる ([VM](../spec/vm.md)の「GUIのPark」)。`gui`がないと`Park`を置かず、`Gui.run`は`NotAvailable`で失敗する。`eml_cli`は`gui_park`、`ParkFactory`、`Backend`、`Script`を再公開し、UIテストのharnessが`-- gui: stub`の印のファイルにstubを置くのに使う ([標準ライブラリ](../spec/stdlib.md)の「起動」)
- `eml run --native`は、`Session::compile_native`でコンパイルし、`eml_cli::execute_on(Engine::Native, ..)`でVMの代わりにネイティブのコードを1つのworkerで流す。`--debug-heap`、`--stats`、`--gui`とは同時に使えず、1でない`--workers`と`EML_WORKERS`、置いた`EML_GUI`は使い方の誤り (終了コード2) である。メッセージは段を名指さない ([ネイティブ](../spec/native.md)の「VMとの違い」)。診断はVMと同じく実行の前に表示する。ネイティブのコードが使えない機械 (`eml_native::SUPPORTED`が偽) では、`error: native code is not supported on this machine`を出して終了コード2にする。終了コードは、`exit n`の下位8ビットも含めてVMと同じである
- `eml run --workers <N>` (と環境変数 `EML_WORKERS`) は worker の数を選ぶ。`eml repl` は持たず、`repl_limits().workers` は 1 である ([起動](../spec/stdlib.md) の「起動」)
- `eml run` と `eml repl` はスケジュールの方針がいつも `Normal` である (ライブラリの既定の `Sched::default()` は `Sequential` である。[VM](../spec/vm.md) の「タスクとスケジュール」)
- `eml repl [--debug-heap] [--link KEY=VALUE]... [file]`は、`file`を渡すと`:load`と同じく最初の入力として読み、`repl_limits()`の上限で`eml_cli::Repl`を使う。端末の繰り返しはbinの`terminal.rs`で、行を入力にまとめるのはlibの`eml_cli::lines`である。規則は [REPLの端末](../spec/repl.md)にある。終了コードは、0 = `:quit`かEOFで終わった、1 = 検査モードのリーク、続けられない誤り、行を読めない誤り、2 = 使い方の誤り、である。入力の誤りと実行時エラーは終了コードを変えない
- Ctrl-C と `Terminate` のシグナルのハンドラは bin の `interrupt` モジュールが入れる。unix では `interrupt/unix.rs` が `libc::sigaction` で、Windows では `interrupt/windows.rs` が `SetConsoleCtrlHandler` で入れる。`src/` の `unsafe` は、`interrupt` モジュールと、`physical_memory` と、端末の列の数を読む bin の `terminal.rs` の `stdout_width` の中だけに置く

`eml_cli` の lib は次の API を公開する。`Session` はパイプラインを組む唯一の場所で、CLI、UI テスト、`eml_test_support` がこれを通す。UI テストはこれをプロセス内で呼ぶ。どのメソッドも読み込みの結果から計算し直し、途中の結果を持たない。途中の結果を使い回すのは、salsa でクエリ化するときに考える。`Session` は `Send + Sync` で、`crates/eml_cli/tests/api.rs` が確かめる。salsa への載せ替えと、フロントエンドの並列のコンパイルに備えるためで、実行とは関係ない。読み込みの結果が持つのは緑の木 (green tree) と `AstPtr` だけで、ノードを持たないので `Send + Sync` にできる。`Repl` は `Machine` を持つので `Send` でなく、作ったスレッドの上でだけ使う ([VM](../spec/vm.md) の「時計と driver」)。

- `Session::load(entry_path, entry_text, &dyn ModuleSource) -> Session` は、エントリの表示のパスと本文を受け取り、読み込みの段で Prelude と、import をたどって見つけたモジュールを読む ([モジュールと名前解決](../spec/modules.md) の「標準ライブラリ」)。`Session::user_module_names` は出どころがユーザーのモジュールの名前を返し、UI テストの harness が1ファイルのテストの import を確かめるのに使う。`Session` は1回の検査や実行で読むソースの集まりである。エントリのファイルは `main.rs` が読み、読めなければ終了コード 2 にする。ファイルシステムから読む `ModuleSource` は `FsProvider` で、パスの各段の名前がディレクトリの一覧と大文字小文字まで一致することを確かめる。macOS のように大文字小文字を区別しないファイルシステムで、`import Report.Csv` が `report/Csv.em` に当たらないようにするためである。大文字小文字だけが違う名前があれば、実際の名前を読めない理由として返す (E1026)。`main.rs` は、エントリのファイル名をディレクトリの一覧にある綴りに直してから `Session::load` に渡す。`t/server.em` で `t/Server.em` を開けたときも、依存先の `import Server` がエントリを指すと分かるようにするためである。実行を始める `main` はエントリのモジュールからだけ探し (`hir::Program::main`)、Prelude には置かない
- `Session::def_map() -> DefMapped`、`Session::lower() -> Lowered`、`Session::check() -> Checked` (feature `types`)。結果は段階の出力 (`DefMap`、HIR の `Program`、`TypedProgram`) と診断を持つ。診断は読み込みの段からその段階までのすべてで、`sort_diagnostics` で並べて返す。各段階は診断の順を約束しない。`eml check` は `check().diagnostics` を表示する
- `Session::compile() -> Compiled<eml_lir::Program>` (feature `core`)。`Compiled<P>` は、検査で出た診断 (警告を含む) と、エラーがなければ IR (`program: Option<P>`) を持つ。`compile` は reuse の後の LIR を返す。`main` がないこと (E2003) は `compile` だけが検査する ([型と Kind](../spec/types.md) の「推論」)。`link_keys` は、読み込んだすべてのモジュールの `link` の item に書いた文字列の集まりで、HIR から取る。誤りがあっても持つ
- `Session::compile_native() -> Compiled<eml_lir::Program>` (feature `run`)。`compile`の後、`eml_native::unsupported`の要素ごとに、エントリのファイルの`main`の名前にE0004を1つ足し、プログラムを返さない。メッセージは`` native code does not support {形} yet (first in `{関数}`) `` である ([ネイティブ](../spec/native.md)の「断る形」)。`eml_cli`でE0004を出すのはここだけである。`Engine`と`execute_on(engine, &Program, &Linked, &RunConfig, HostRef)`は、同じ`Linked`のプログラムをVMかネイティブのコードで流す
- テストのためのインターフェースが2つある。`Session::load_with_std(std, entry_path, entry_text, source)` は標準ライブラリを `(ファイル名, 本文)` の並びに差し替えて読む。`Session::compile_with(lower: impl FnOnce(eml_core_ir::Input) -> P) -> Compiled<P>` は、検査が通れば `lower` で IR を作る。`compile` は `eml_core_ir::lower` を渡したものである。パスの順番は `eml_core_ir` と `eml_lir` だけが知るので、テストは `eml_core_ir::lower_until` や `core_until` を渡して、確かめたいパスの直後で止める
- `execute(&eml_lir::Program, &Linked, &RunConfig, HostRef) -> Result<Finished, RuntimeError>` (feature `run`)。`eml_vm::execute`の再公開で、`Linked`は`eml_clink`から再公開する。`Linked`はプログラムのCの関数をつないだ結果で、`Machine::load(program, &Linked)`も同じものを受け取る ([VM](../spec/vm.md)の「C の関数の命令」)。`execute`はプログラムを信頼し、実行の前提を確かめない。前提を約束するのは呼ぶ側である ([LIR](../spec/lir.md)の「実行の前提」)。VMで実行し、成功すると`Finished { stats, exit, preemptions, workers, placed, placed_tasks, pinned_tasks, placed_jobs }`を返す ([VM](../spec/vm.md)の「`RunStats`」)。`workers`と`placed`は、作ったworkerの数とほかのworkerに置いた右の子の数で、`placed_tasks`は`start`を実行したworkerと違うworkerに置いた`Async`のタスクの数、`pinned_tasks`はメインのworkerに固定して始めたタスクの数、`placed_jobs`は`fork_job`を実行したworkerと違うworkerに置いた`compute`の仕事の数である。`exit`は`exit n`で終わったときの`Some(n)`で、`eml run`は`n & 255`を終了コードにする。`stats`の`RunStats`は実行の仕事の回数と、同時に生きていたヒープの物体の数とスタックの語の数の最大で、CLIは使わない。テストが2乗の時間にならないことと、ループがフレームを積まないことを確かめるのに使う
- `Linker` と `LinkError` (feature `run`)。`eml_clink` の再公開で、`eml run` と `Repl` がプログラムの C の関数をつなぐのに使う ([VM](../spec/vm.md) の「ライブラリと記号」)
- `default_limits() -> Limits` (feature `run`)。`eml run` の既定の上限を作る ([VM](../spec/vm.md) の「上限と割り込み」)
- `pretty::format(text, suffix, width) -> String` と `pretty::LIMIT`。REPL の結果を切って整形する純粋な関数で、`lines` と同じく feature によらない ([REPL の端末](../spec/repl.md) の「整形の規則」)
- `Repl` (feature `run`)。REPLのセッションで、`Repl::new`が空のセッションを作り、`Repl::eval`が入力を1つずつ評価する ([モジュールと名前解決](../spec/modules.md)の「REPL のセッション」)。`Repl::with_file`は`:load`のファイルを最初の入力とする新しいセッションを作り、`Repl::type_of`は`:type`の問い合わせを検査して型の文字列を返す。受け付けた入力はファイルの表示のパスも覚え、セッションを読み直すたびにファイルとして読む。セッションを空にするメソッドはなく、呼び出し側が新しい`Repl`を作って古いものを閉じる。式の入力の結果は、`Machine::run_shown`が返した文字列を`eml_cli::pretty::format`で整形し、`Machine::write_line`で書く。幅は`Repl::set_width`で変える ([REPLの端末](../spec/repl.md)の「結果の表示」)。`Repl`は1つの`Linker`を持ち、入力ごとに`Machine::load`の前にその入力のプログラムをつなぐ。`Repl::new`は上書きのない`Linker`を入れ、`Repl::with_linker`で替える。`Repl::with_file`は、ファイルの入力より前に入れる`Linker`を引数で受ける。つなげない入力は`Outcome::Unlinked`で、`load`を呼ばず、セッションを変えない ([REPLの端末](../spec/repl.md)の「C の関数」)。端末は`--link`の上書きを持ち、`:load`と`:reload`で作るセッションにも同じ上書きの`Linker`を渡す。
- `eml_test_support::link(program) -> Linked` (feature `run`)。テストの道具がプログラムの C の関数をつなぐ。テストの binary に1つの `Linker` を `Mutex` で持ち、ライブラリと橋渡しを使い回す。lock が毒になっても使い続ける。つなぐ途中の panic で壊れる不変条件を `Linker` が持たないためである。C の関数もハンドルの型もないプログラムは、lock を取らずに `Linked::default()` を返す。つなぐ失敗で panic する。`eml_test_support::execute_on` と UI テストの道具がこれを通す

検査と実行を別の関数に分けるのは、呼び出し側が実行の前に診断を表示できるようにするためである。CLI と UI テストは、`compile` の診断を表示してから `execute` を呼ぶ。

`RunConfig`、`Finished`、`RunStats`、`Sched`、`Seat`、`RuntimeError`は`eml_sched`で定義し、`eml_cli`は`Seat`のほかを再公開する。`eml_vm`が再公開するのは、`execute`のシグネチャに現れる`RunConfig`、`Finished`、`RuntimeError`だけである ([VM](../spec/vm.md)の「置き場所」)。`RunConfig`は`#[non_exhaustive]`にしてあり (`RunStats`はしない。別のcrateのテストが構造体の更新の式で欄を指定して作るため)、`RunConfig::default()`から`with_debug_heap`、`with_control`、`with_sched`、`with_clock`、`with_doorbell`、`with_job_budget`、`with_seat`で作る。`with_seat`は、`Machine`を持つスレッドとworker 0の関係`Seat` (既定の`Seat::Merged`か`Seat::Separate`) を選び、`Machine::with_seat`も同じである ([VM](../spec/vm.md)の「メインのworker」)。`with_main_park`は、分かれたrunのメインのworkerの`Park`を作る`ParkFactory`を渡し、`Machine::with_main_park`も同じである。`Park`、`Pending`、`Progress`、`ParkFactory`、`DefaultPark`は`eml_sched`の`park.rs`で定義し、使う側は`eml_sched::park`から名指す ([VM](../spec/vm.md)の「メインのworkerの待ち」)。`RunConfig::job_budget`は、静止が走っている`Op::Job`をrunで合わせて待つ長さで、既定は1秒である。`eml_cli`は変えず、1秒より短い予算が要るテストが渡す。`Machine`は同じ予算を`Machine::with_job_budget`で受け取る。`RunStats`の定めは[VM](../spec/vm.md)の「`RunStats`」にある。

`eml`バイナリには、aws-lcとrustlsが入る。どちらもemlと別のライセンスに従う。aws-lcは`ISC AND (Apache-2.0 OR ISC) AND Apache-2.0 AND MIT AND BSD-3-Clause`ほか、rustlsは`Apache-2.0 OR ISC OR MIT`である。Craneliftのcrateと、それが使うregalloc2とtarget-lexiconは`Apache-2.0 WITH LLVM-exception`で、Craneliftからhashbrownを通して、またcxxから入るfoldhashは`Zlib`である。`about.toml`の`accepted`はこの2つも認める。LLVMの例外は、Apache-2.0の条件を、コンパイルした出力について緩めるだけである。`flake.nix`の`meta.license`はeml自身のライセンス (MIT) だけを書く。

`gui-native`を足した`eml`は、crateでないプラットフォームのGUIのtoolkitにもリンクする。LinuxではQt 6で、LGPL-3.0に従って動的にリンクする。`flake.nix`は`eml`を`gui-native`で組み、LinuxではQtをnixpkgsの`qt6.qtbase`から取り、`wrapQtAppsHook`がQtのプラグインの場所を置くラッパーを作る。WindowsのWinUI 3は、利用者が入れたWindows App SDK 2のruntimeから実行のときに読み込み、リンクの時には名指さない。emlはそのファイルを配らない。`about.hbs`は、これを`THIRD-PARTY-LICENSES.md`の「System libraries」の節に書く。LGPLv3はGNU GPLv3に許可を足す形なので、両方の全文を配る。全文は`licenses/GPL-3.0.txt`と`licenses/LGPL-3.0.txt`で、FSFの文面をそのまま置く。利用者が入れるものと、emlやそれから作ったものを配る人が負うことは、[配布とGUIの前提](distribution.md)にある。

バイナリに入る他者の crate と、そのライセンスの全文は、リポジトリの直下の `THIRD-PARTY-LICENSES.md` にまとめる。このファイルは cargo-about が `about.toml` と `about.hbs` から生成するので、手では直さない。依存を変えたら `nix develop -c nix/third-party-licenses.sh` で書き直す。cargo-about は devShell に入れてあり、バージョンは `flake.lock` で決まる。

- 対象は、既定のfeatureに`gui-native`を足した`eml_cli`がCIの4つのtarget (x86_64とaarch64のLinux、aarch64のmacOS、x86_64のWindows) で依存するcrateである。dev-dependenciesとbuild-dependenciesは除く。手続きマクロとその依存はビルドの間にしか動かないが、cargo-aboutはこれを除けないので一覧に残る。ワークスペースのcrateはeml自身なので、`about.hbs`が除く
- cargo-about は `--frozen` で走らせる。ClearlyDefined を引かず、crate に入っているファイルだけを読むので、出力はネットワークに左右されない。ライセンスのファイルを持たない crate には、SPDX が定めるそのライセンスの文面が入る
- aws-lc-sys、aws-lc-rs、windows-sys、windows-link のライセンスのファイルは、自動の判定では読めない。そこで `about.toml` で、使うファイル (aws-lc-sys は切り出す範囲も) とその SHA-256 を指定する。crate を上げてファイルが変わると、cargo-about は警告を出して指定を捨てる。`nix/third-party-licenses.sh` はこの警告で止まるので、そのときは `about.toml` の範囲と SHA-256 を今のファイルに合わせる
- CI の `licenses` ジョブが、コミットしたファイルと生成した結果を比べる ([テスト戦略](testing.md) の「CI」)
- `nix build`は`LICENSE.txt`、`THIRD-PARTY-LICENSES.md`、`GPL-3.0.txt`、`LGPL-3.0.txt`を`$out/share/doc/eml/`に入れる
